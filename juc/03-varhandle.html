VarHandle и режимы доступа к памяти

VarHandle (Java 9) — официальная замена sun.misc.Unsafe: типобезопасная ссылка на поле, элемент массива или участок памяти, через которую можно выполнять атомарные операции и выбирать силу упорядочивания каждого обращения — plain, opaque, release/acquire, volatile. На нём построены все атомики и AQS. С лакмус-тестами покажем, какие результаты возможны в каждом режиме на x86 и ARM.

3.1Получение и операции

final class Node {
    volatile Node next;
    private static final VarHandle NEXT;
    static {
        try {
            NEXT = MethodHandles.lookup().findVarHandle(Node.class, "next", Node.class);
        } catch (ReflectiveOperationException e) { throw new ExceptionInInitializerError(e); }
    }
    boolean casNext(Node expect, Node update) { return NEXT.compareAndSet(this, expect, update); }
    void lazySetNext(Node n)                  { NEXT.setRelease(this, n); }
}
// массив:       MethodHandles.arrayElementVarHandle(long[].class)
// байты как int: MethodHandles.byteArrayViewVarHandle(int[].class, ByteOrder.BIG_ENDIAN)
// внешняя память (FFM): ValueLayout.JAVA_INT.varHandle()
ГруппаМетоды
Чтениеget (plain), getOpaque, getAcquire, getVolatile
Записьset, setOpaque, setRelease, setVolatile
CAScompareAndSet (volatile), compareAndExchange[Acquire|Release] (возвращает фактическое значение), weakCompareAndSet[Plain|Acquire|Release]
Атомарные измененияgetAndSet, getAndAdd, getAndBitwiseOr/And/Xor + варианты Acquire/Release
Барьеры (статические)VarHandle.fullFence(), acquireFence(), releaseFence(), loadLoadFence(), storeStoreFence()
Производительность VarHandle — сигнатурно-полиморфный: вызов NEXT.compareAndSet(this, a, b) компилируется в точный дескриптор, а JIT встраивает его до одной инструкции — но только если VarHandle лежит в static final поле (константа для JIT). Неверные типы аргументов дают WrongMethodTypeException в рантайме.

3.5Самопроверка

Какой минимальный режим нужен, чтобы безопасно опубликовать объект: записать поля, затем ссылку-флаг?

  • plain
  • opaque
  • setRelease для флага и getAcquire для чтения
  • только synchronized
Release/acquire гарантирует видимость всего, что было до release.

Почему release/acquire недостаточно для алгоритма Деккера?

  • Он не атомарен
  • Он медленнее volatile
  • Он не работает на x86
  • Он допускает перестановку записи и последующего чтения другой переменной — оба потока могут не увидеть флаги друг друга
Нужна последовательная согласованность (volatile) или fullFence.

Почему VarHandle держат в static final поле?

  • JIT считает его константой и встраивает операцию до одной инструкции
  • Иначе он не скомпилируется
  • Так требует GC
  • Для сериализации
То же правило, что для MethodHandle.
Что такое lazySet и почему он быстрее volatile-записи?

lazySet (AtomicXxx.lazySet, VarHandle.setRelease) — release-запись: предыдущие записи не переставятся после неё, но последующие чтения могут обогнать её (нет StoreLoad-барьера). На x86 это обычная mov без lock-барьера — в разы дешевле volatile-записи. Подходит, когда записывает один поток (обнуление ссылки, публикация в очереди с одним производителем).
