15.1ctl: состояние и число потоков в одном int

private final AtomicInteger ctl = new AtomicInteger(ctlOf(RUNNING, 0));
private static final int COUNT_BITS = Integer.SIZE - 3;          // 29 бит под число потоков (до ~536 млн)
private static final int RUNNING    = -1 << COUNT_BITS;           // 111
private static final int SHUTDOWN   =  0 << COUNT_BITS;           // 000
private static final int STOP       =  1 << COUNT_BITS;           // 001
private static final int TIDYING    =  2 << COUNT_BITS;           // 010
private static final int TERMINATED =  3 << COUNT_BITS;           // 011
// один CAS атомарно проверяет состояние и меняет число рабочих — без блокировки

15.2Алгоритм execute()

public void execute(Runnable command) {
    int c = ctl.get();
    if (workerCountOf(c) < corePoolSize) {                 // 1. меньше core — новый поток, задача — его первая
        if (addWorker(command, true)) return;
        c = ctl.get();
    }
    if (isRunning(c) && workQueue.offer(command)) {        // 2. иначе — в очередь
        int recheck = ctl.get();
        if (!isRunning(recheck) && remove(command)) reject(command);
        else if (workerCountOf(recheck) == 0) addWorker(null, false);   // ни одного потока — завести
    }
    else if (!addWorker(command, false))                    // 3. очередь полна — поток сверх core до max
        reject(command);                                    // 4. и это не удалось — отказ
}

15.3Рабочий поток и жизненный цикл задачи

final void runWorker(Worker w) {
    Runnable task = w.firstTask; w.firstTask = null;
    w.unlock();                                       // разрешить прерывания
    boolean completedAbruptly = true;
    try {
        while (task != null || (task = getTask()) != null) {   // getTask: take()/poll(keepAlive); null — поток должен умереть
            w.lock();                                  // Worker сам — нереентерабельная блокировка на AQS:
                                                       // shutdown() прерывает только НЕ захваченных (простаивающих) рабочих
            try {
                beforeExecute(w.thread, task);         // хук для наследников (MDC, метрики)
                task.run();
                afterExecute(task, null);
            } catch (Throwable ex) { afterExecute(task, ex); throw ex; }   // исключение убивает поток → будет создан новый
            finally { task = null; w.completedTasks++; w.unlock(); }
        }
        completedAbruptly = false;
    } finally { processWorkerExit(w, completedAbruptly); }
}

15.4Остановка

МетодЧто делает
shutdown()RUNNING → SHUTDOWN: новые задачи отклоняются, очередь дорабатывается, простаивающие потоки прерываются
shutdownNow()→ STOP: прерывает все потоки, возвращает список невыполненных задач из очереди; задачи, игнорирующие прерывание, продолжат работать

close() (Java 19+)shutdown + ожидание завершения; ExecutorService — AutoCloseable, можно в try-with-resources
pool.shutdown();
try {
    if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
        pool.shutdownNow();
        if (!pool.awaitTermination(10, TimeUnit.SECONDS)) log.error("пул не завершился");
    }
} catch (InterruptedException e) { pool.shutdownNow(); Thread.currentThread().interrupt(); }
Ловушки Executors newFixedThreadPool и newSingleThreadExecutor — неограниченная LinkedBlockingQueue: при перегрузке очередь растёт до OOM. newCachedThreadPool — SynchronousQueue и max = Integer.MAX_VALUE: тысячи потоков. В продакшене создавайте ThreadPoolExecutor явно: ограниченная очередь, политика отказа, именованная ThreadFactory, метрики (Micrometer ExecutorServiceMetrics).

Что хранит ctl?

  • 3 старших бита — состояние пула, 29 младших — число рабочих потоков
  • Число задач в очереди
  • Ссылку на очередь
  • Флаг shutdown
Один CAS меняет согласованно оба значения.

Задача, отправленная через submit, бросила исключение. Где оно?

  • В логе пула
  • Поток умер, исключение в stderr
  • Потеряно бесследно
  • В Future: его увидит только тот, кто вызовет get()
Не забывайте получать результат или обрабатывать ошибки.

Зачем Worker наследует AQS?

  • Для честности очереди
  • Как нереентерабельная блокировка «занят задачей»: shutdown прерывает только простаивающие (не захваченные) потоки
  • Для подсчёта задач
  • Для связи с ForkJoinPool
Задача не будет прервана shutdown-ом посреди выполнения.
Как настроить пул для HTTP-обработчиков, обращающихся к БД?

Явный ThreadPoolExecutor: core = max = число, согласованное с пулом соединений БД (больше потоков, чем соединений, бессмысленно); ограниченная ArrayBlockingQueue (например, несколько сотен) — защита от перегрузки; политика отказа — AbortPolicy с ответом 503 или CallerRunsPolicy для противодавления; именованная ThreadFactory; метрики очереди и активных потоков; таймауты задач. С Java 21 для I/O-задач рассмотрите виртуальные потоки + Semaphore на ресурс.
