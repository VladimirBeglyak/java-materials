StructuredTaskScope, ScopedValue и утилиты

Новое поколение конкурентного API, рассчитанное на виртуальные потоки. Структурная конкурентность (StructuredTaskScope, preview в Java 25) делает время жизни подзадач вложенным в блок кода: никаких «осиротевших» задач, автоматическая отмена при ошибке. ScopedValue (финальный в Java 25) — неизменяемая замена ThreadLocal, передающаяся в подзадачи. В конце — небольшие, но важные утилиты: ThreadLocalRandom и TimeUnit.

23.1StructuredTaskScope

Response handle(Request req) throws InterruptedException {
    try (var scope = StructuredTaskScope.open()) {                 // по умолчанию: все подзадачи должны завершиться успешно
        Subtask<User>   user   = scope.fork(() -> userService.find(req.userId()));    // каждая — в своём виртуальном потоке
        Subtask<Orders> orders = scope.fork(() -> orderService.list(req.userId()));
        scope.join();                                              // ждать; при первой ошибке остальные ОТМЕНЯЮТСЯ, join бросает FailedException
        return new Response(user.get(), orders.get());
    }                                                              // выход из блока гарантирует: ни одной живой подзадачи
}
// другие стратегии:
StructuredTaskScope.open(Joiner.anySuccessfulResultOrThrow())     // первый успешный результат, остальные отменить
StructuredTaskScope.open(Joiner.allSuccessfulOrThrow())           // поток всех результатов
StructuredTaskScope.open(Joiner.awaitAll())                        // дождаться всех, ошибки разбирать вручную
StructuredTaskScope.open(Joiner.awaitAllSuccessfulOrThrow(), cf -> cf.withTimeout(Duration.ofSeconds(2)))   // таймаут на всю область
Что вернёт область и кого отменит
Preview API StructuredTaskScope прошёл несколько итераций preview (Java 19–25) и в Java 25 сменил API на open() + Joiner. Для продакшена без preview — ExecutorService в try-with-resources + invokeAll/invokeAny или CompletableFuture с явной отменой. Подзадачи нельзя форкать из других потоков, кроме владельца области; дамп потоков (jcmd Thread.dump_to_file -format=json) показывает иерархию областей.

23.2ScopedValue вместо ThreadLocal

static final ScopedValue<User> CURRENT_USER = ScopedValue.newInstance();

void serve(Request req) {
    User u = authenticate(req);
    ScopedValue.where(CURRENT_USER, u).run(() -> handle(req));     // значение видно только внутри run и ниже по стеку
}
void audit(String action) {
    User u = CURRENT_USER.get();                                   // NoSuchElementException вне области; isBound(), orElse(…)
    log.info("{} by {}", action, u.name());
}
// подзадачи StructuredTaskScope автоматически наследуют привязки — без копирования (в отличие от InheritableThreadLocal)

23.4Самопроверка

Что гарантирует закрытие StructuredTaskScope?

  • Что все подзадачи завершились успешно
  • Что ни одна подзадача не переживёт область: незавершённые отменены и дождались завершения
  • Что результаты сохранены в кэше
  • Что исключения подавлены
Время жизни задач совпадает со структурой кода.

Чем ScopedValue лучше ThreadLocal для контекста запроса?

  • Он изменяемый
  • Он работает только в платформенных потоках
  • Он быстрее при записи
  • Неизменяем, ограничен областью (без утечек), дёшево передаётся в подзадачи
Особенно важно с миллионами виртуальных потоков.

Почему нельзя сохранить ThreadLocalRandom.current() в статическое поле?

  • Генератор привязан к потоку, который его получил; использование из других потоков нарушает его гарантии
  • Он не сериализуем
  • Это запрещено компилятором
  • Он слишком большой
Вызывайте current() в месте использования.
Как обработать запрос, требующий трёх параллельных вызовов, на Java 21 без preview?

try (var exec = Executors.newVirtualThreadPerTaskExecutor()) { var a = exec.submit(...); var b = ...; ... } — close() дождётся всех задач. Для «всё или ничего» нужна ручная отмена: при ошибке одного Future — cancel(true) остальных. Альтернатива — CompletableFuture.allOf с orTimeout и отменой в exceptionally. StructuredTaskScope делает это автоматически, поэтому его стоит отслеживать и включить, когда API станет финальным.
