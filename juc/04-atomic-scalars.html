AtomicInteger, AtomicLong, AtomicReference

Атомики — это volatile-поле плюс атомарные операции над ним через CAS. Разберём на симуляторе с ручным планированием потоков, почему count++ над volatile теряет обновления, а incrementAndGet и CAS-цикл — нет; как работают updateAndGet и accumulateAndGet (и почему функция может вызываться несколько раз); и мощный приём — неизменяемое состояние в AtomicReference.

4.3AtomicReference и неизменяемое состояние

Когда несколько полей должны меняться согласованно, их можно упаковать в неизменяемый объект и атомарно заменять ссылку на него — без блокировок, с согласованными снимками для читателей.

record Stats(long count, long sum, long max) {
    Stats add(long v) { return new Stats(count + 1, sum + v, Math.max(max, v)); }
}
private final AtomicReference<Stats> stats = new AtomicReference<>(new Stats(0, 0, 0));
void record(long v) { stats.updateAndGet(s -> s.add(v)); }    // CAS-цикл: при конкуренции новый объект создаётся заново
Stats snapshot()   { return stats.get(); }                     // всегда согласованный снимок трёх полей

// «горячая» замена конфигурации
private final AtomicReference<Config> config = new AtomicReference<>(load());
void reload() { config.set(load()); }                          // читатели видят старую или новую — не смесь
Когда атомики хуже блокировки При сильной конкуренции CAS-цикл с тяжёлой функцией повторяет работу и создаёт мусор (новые объекты на каждую неудачную попытку). Если состояние большое или обновления частые и дорогие — блокировка (ReentrantLock) честнее и экономнее. Для простых счётчиков под нагрузкой — LongAdder (тема 06).

4.4Самопроверка

Почему volatile int count; count++ из двух потоков теряет обновления?

  • volatile не гарантирует видимость
  • count++ — три операции (чтение, сложение, запись); volatile не делает их атомарными
  • int не атомарен
  • JIT удаляет инкремент
Нужен incrementAndGet или блокировка.

Почему функция в updateAndGet должна быть без побочных эффектов?

  • Так требует компилятор
  • Она выполняется под блокировкой
  • Она выполняется в другом потоке
  • При неудачном CAS она вызывается повторно
Логирование или отправка сообщений внутри — дублируются.

Как атомарно обновить три связанных значения без блокировки?

  • Неизменяемый объект в AtomicReference и CAS-замена ссылки
  • Три AtomicLong
  • volatile-поля
  • Это невозможно
Три отдельных атомика не дают согласованного снимка.
incrementAndGet против CAS-цикла: в чём разница на уровне процессора?

getAndAdd/incrementAndGet компилируются в lock xadd — одна инструкция, которая всегда успешна, даже при конкуренции (хотя ядра всё равно сериализуются на кэш-линии). CAS-цикл (updateAndGet) может проваливаться и повторяться, тратя время и пересчитывая функцию. Поэтому для простых сложений используйте специализированные методы, а не updateAndGet(x -> x + 1).
