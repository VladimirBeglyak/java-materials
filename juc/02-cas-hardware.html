CAS, барьеры и кэш-линии на железе

Всё в пакете в конечном счёте сводится к нескольким инструкциям процессора. Как compare-and-swap реализован на x86 и ARM, почему успешный CAS стоит десятки наносекунд, а при конкуренции — сотни, что такое протокол когерентности кэшей и «пинг-понг» кэш-линии, как ложное разделение (false sharing) замедляет независимые счётчики в разы и что делают барьеры памяти.

2.1Compare-and-swap

boolean compareAndSet(V expected, V newValue) {
    // АТОМАРНО:
    if (this.value == expected) { this.value = newValue; return true; }
    return false;
}
// на этом строится любая lock-free операция — цикл «прочитать, вычислить, попытаться записать»:
int v;
do { v = value; } while (!compareAndSet(v, v + 1));

В Java CAS доступен через VarHandle.compareAndSet (тема 03), классы Atomic* и внутренний jdk.internal.misc.Unsafe. JIT превращает их в одну инструкцию (интринсик).

2.2Когерентность кэшей и цена конкуренции

Каждое ядро работает со своим кэшем; протокол когерентности (MESI и его варианты) гарантирует, что запись в линию 64 байта делает её копии в других ядрах недействительными. Атомарная операция требует линию в состоянии Modified/Exclusive — если линией владеет другое ядро, она пересылается через кэш общего уровня или межпроцессорную шину. Это и есть цена конкуренции.

Цифры — модель порядков величин, а не измерение; реальные зависят от процессора. Проверяйте JMH с @Threads.

2.3Ложное разделение

Два независимых поля, которые пишут разные потоки, но которые попали в одну кэш-линию, ведут себя как одно общее: каждая запись одного потока инвалидирует линию у другого. Код без единой общей переменной масштабируется плохо.

2.4Барьеры памяти

Процессоры и компиляторы переставляют обращения к памяти. Барьер (fence) запрещает определённые перестановки. На x86 (модель TSO) разрешено только одно переупорядочивание — более поздняя загрузка может обогнать более раннюю запись (StoreLoad), поэтому volatile-запись в HotSpot на x86 — это обычная запись + lock addl $0,(%rsp), а volatile-чтение — обычное чтение. На ARM (слабая модель) нужны инструкции ldar/stlr и dmb. Отсюда практический вывод: код с гонками данных, «работающий» на ноутбуке x86, может ломаться на ARM-серверах.

2.5Самопроверка

Почему 8 потоков, увеличивающих один AtomicLong, могут работать медленнее одного?

  • AtomicLong использует блокировку
  • Кэш-линия со счётчиком постоянно передаётся между ядрами — операции сериализуются, а передача дорога
  • JIT отключается
  • Из-за GC
Решение — распределённые счётчики (LongAdder).

Что такое false sharing?

  • Два потока пишут в одну переменную
  • Утечка памяти
  • Гонка данных
  • Разные переменные разных потоков в одной кэш-линии — запись одной инвалидирует линию у другого ядра
Лечится разнесением по линиям (@Contended).

Какую перестановку разрешает модель памяти x86?

  • Только Store → Load (поздняя загрузка обгоняет раннюю запись)
  • Все
  • Никаких
  • Только Load → Load
Поэтому volatile-запись на x86 требует барьера, а чтение — нет.
Чем LL/SC отличается от CAS и зачем в Java weakCompareAndSet?

LL/SC: загрузка с «резервированием» адреса и условная запись, которая не удаётся, если между ними линию кто-то тронул (или произошло прерывание) — даже если значение не изменилось. Поэтому реализация строгого compareAndSet на LL/SC сама содержит цикл. weakCompareAndSet разрешает ложные неудачи — его можно скомпилировать в одну пару LL/SC без внутреннего цикла; он подходит, когда вы и так повторяете CAS в своём цикле.
