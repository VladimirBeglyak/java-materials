LockSupport: park и unpark

Два метода, на которых держится вся блокирующая часть пакета: park() усыпляет текущий поток, unpark(thread) будит конкретный поток. В отличие от wait/notify, им не нужен монитор, а будить можно до того, как поток уснул. Разбираем семантику «разрешения» (permit) в симуляторе, ложные пробуждения, прерывания, blocker-объекты в дампах потоков — и пишем свою блокировку на park/unpark.

7.1Модель «разрешения»

У каждого потока есть одно двоичное разрешение (permit), изначально отсутствующее. unpark(t) выдаёт разрешение (если его не было). park() потребляет разрешение и сразу возвращается, если оно было, иначе — блокируется до unpark, прерывания, таймаута или без причины (ложное пробуждение).

7.3Свой FIFO-мьютекс

final class FifoMutex {
    private final AtomicBoolean locked = new AtomicBoolean();
    private final Queue<Thread> waiters = new ConcurrentLinkedQueue<>();

    public void lock() {
        Thread current = Thread.currentThread();
        waiters.add(current);
        // ждём, пока мы не окажемся первыми в очереди И не захватим флаг
        while (waiters.peek() != current || !locked.compareAndSet(false, true)) {
            LockSupport.park(this);                     // в цикле: ложные пробуждения и чужие unpark
            // прерывания игнорируем, но запомним, чтобы восстановить флаг
        }
        waiters.remove();
    }
    public void unlock() {
        locked.set(false);
        LockSupport.unpark(waiters.peek());             // разбудить следующего (unpark(null) — no-op)
    }
}
// AQS (тема 08) — промышленная версия той же идеи: CAS по состоянию + очередь + park/unpark

7.4Самопроверка

Поток M вызвал unpark(W) трижды, затем W вызвал park() дважды. Что произойдёт?

  • Оба park вернутся сразу
  • Оба park заблокируются
  • Первый park вернётся сразу (одно разрешение), второй заблокируется
  • Исключение
Разрешение двоичное, не счётчик.

Почему park вызывают в цикле с проверкой условия?

  • park может вернуться без unpark (ложное пробуждение), из-за прерывания или чужого unpark
  • park работает только в цикле
  • Иначе не скомпилируется
  • Для экономии CPU
То же правило, что для wait и Condition.await.

Что делает park(), если у потока установлен флаг прерывания?

  • Бросает InterruptedException
  • Блокируется навсегда
  • Сбрасывает флаг и блокируется
  • Сразу возвращается; флаг остаётся установленным
Вызывающий код сам решает, как реагировать.
Почему unpark до park не теряется и почему это важно?

Разрешение запоминается: если поток-освобождающий успел вызвать unpark раньше, чем ждущий дошёл до park, park вернётся сразу. Это устраняет гонку «потерянного пробуждения», которая есть у notify без монитора, и позволяет строить очереди ожидания на CAS без глобальной блокировки (AQS сначала ставит узел в очередь, затем паркуется — даже если освобождение произошло между этими действиями).
