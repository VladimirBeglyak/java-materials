Condition: очереди ожидания

Condition — аналог wait/notify для Lock, но с главным отличием: у одной блокировки может быть несколько условий, и производители ждут «место есть», а потребители — «есть данные» в разных очередях. Разбираем, как await отпускает блокировку и переносит поток между очередью условия и очередью блокировки, почему условие всегда проверяют в цикле, и строим ограниченный буфер с симулятором.

Потребитель C взял блокировку и видит пустой буфер.

await(): создаёт узел в очереди условия, полностью отпускает блокировку (даже при повторных захватах — запоминает счётчик) и паркуется. Отпускание блокировки и постановка в очередь атомарны относительно signal — потерянного сигнала не будет.

Производитель P захватывает свободную блокировку и кладёт элемент.

signal() не будит C немедленно — он переносит его узел из очереди условия в очередь блокировки. C сможет продолжить только после того, как захватит блокировку снова. Вызывать signal можно только владея блокировкой (иначе IllegalMonitorStateException).

P выходит из критической секции — блокировка будит C из очереди блокировки.

C заново захватывает блокировку (с прежним числом захватов) и возвращается из await — и снова проверяет условие в цикле: между signal и захватом другой потребитель мог забрать элемент, а пробуждение могло быть ложным.

10.2Ограниченный буфер

final Lock lock = new ReentrantLock();
final Condition notFull = lock.newCondition(), notEmpty = lock.newCondition();
final Object[] items = new Object[3]; int putIndex, takeIndex, count;

public void put(Object x) throws InterruptedException {
    lock.lockInterruptibly();
    try {
        while (count == items.length) notFull.await();       // производители ждут «есть место»
        items[putIndex] = x; putIndex = (putIndex + 1) % items.length; count++;
        notEmpty.signal();                                    // разбудить ОДНОГО потребителя
    } finally { lock.unlock(); }
}
public Object take() throws InterruptedException {
    lock.lockInterruptibly();
    try {
        while (count == 0) notEmpty.await();                  // потребители ждут «есть данные»
        Object x = items[takeIndex]; items[takeIndex] = null; takeIndex = (takeIndex + 1) % items.length; count--;
        notFull.signal();
        return x;
    } finally { lock.unlock(); }
}
Буфер на 3 элемента: два производителя, два потребителя
Почему два условия лучше одного С одним монитором (wait/notifyAll) производители и потребители ждут в одной очереди: notify() может разбудить «не того» (производителя, когда нужен потребитель) — отсюда вынужденный notifyAll и «стадо» лишних пробуждений. С двумя Condition сигнал адресный, и достаточно signal().

10.4Самопроверка

Что делает signal() с ожидающим потоком?

  • Немедленно продолжает его выполнение
  • Переносит его из очереди условия в очередь блокировки; он продолжит, когда снова захватит блокировку
  • Освобождает блокировку
  • Бросает в нём InterruptedException
Сигнализирующий поток продолжает владеть блокировкой до unlock.

Почему условие проверяют в while, а не в if?

  • Так быстрее
  • if не компилируется с await
  • Чтобы не терять сигнал
  • Из-за ложных пробуждений и потому, что между signal и повторным захватом другой поток мог изменить состояние
Правило без исключений для wait, await и park.

Что произойдёт при await(), если поток захватил блокировку трижды?

  • Блокировка отпускается полностью, а при возврате восстанавливается счётчик 3
  • Отпускается один уровень
  • IllegalMonitorStateException
  • Deadlock
fullyRelease запоминает и восстанавливает holdCount.
Когда signalAll всё-таки нужен?

Когда изменение состояния может сделать выполнимыми условия нескольких ожидающих (например, освобождено сразу много места, закрытие очереди — все ждущие должны увидеть «закрыто»), или ожидающие в одном условии ждут разного (тогда signal может разбудить того, чьё условие всё ещё ложно, а нужный останется спать). Если все ожидающие в условии эквивалентны и одно изменение позволяет продолжить ровно одному — достаточно signal.
