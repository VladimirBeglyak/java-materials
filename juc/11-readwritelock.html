ReentrantReadWriteLock

Пара блокировок над одним AQS: много читателей одновременно или один писатель. Разберём, как в одном int state упакованы счётчики читателей и писателя, почему «повысить» чтение до записи нельзя (взаимная блокировка), а «понизить» запись до чтения — можно, как нечестный режим защищает писателей от голодания — и когда эта блокировка медленнее обычной.

11.1Два счётчика в одном int

Старшие 16 бит state — число захватов чтения (всех потоков вместе), младшие 16 — число повторных захватов записи владельцем. Поэтому предел — 65 535 захватов каждого вида. Сколько раз захватил чтение конкретный поток, хранится отдельно: первый читатель — в полях firstReader/firstReaderHoldCount, последний — в кэше cachedHoldCounter, остальные — в ThreadLocal readHolds.

Захваты и state
синие биты — счётчик чтения (старшие 16), жёлтые — счётчик записи (младшие 16)

11.2Правила

СитуацияРезультат
Владелец записи берёт чтение (downgrade)разрешено: затем unlock записи — остаётся только чтение, другие читатели могут войти
Владелец чтения берёт запись (upgrade)запрещено фактически: поток будет ждать сам себя вечно
Повторный захватоба вида реентерабельны
Conditionтолько у writeLock; readLock.newCondition → UnsupportedOperationException
Нечестный режим и писателиновый читатель блокируется, если в голове очереди ждёт писатель (эвристика против голодания писателей)
rwl.readLock().lock();
if (!cacheValid) {
    rwl.readLock().unlock();               // upgrade невозможен — сначала отпустить чтение
    rwl.writeLock().lock();
    try {
        if (!cacheValid) { data = load(); cacheValid = true; }   // перепроверка: кто-то мог успеть
        rwl.readLock().lock();             // downgrade: взять чтение, пока держим запись
    } finally { rwl.writeLock().unlock(); }   // остаёмся с чтением
}
try { use(data); } finally { rwl.readLock().unlock(); }

11.3Когда RWLock не стоит брать

  • Короткие чтения: захват чтения — это CAS по общему state; при множестве читателей кэш-линия state становится горячей, и RWLock оказывается медленнее обычного ReentrantLock. Выигрыш — при длинных чтениях.
  • Чтений не намного больше записей — накладные расходы без выгоды.
  • Альтернативы: StampedLock с оптимистичным чтением (тема 12), неизменяемые снимки в volatile/AtomicReference (copy-on-write), ConcurrentHashMap.

11.4Самопроверка

Что произойдёт, если поток с захваченным readLock вызовет writeLock().lock()?

  • Блокировка повысится до записи
  • IllegalStateException
  • Поток будет ждать вечно: запись ждёт ухода всех читателей, включая его самого
  • Чтение будет автоматически отпущено
Upgrade не поддерживается — это классическая ловушка.

Как упакован state в ReentrantReadWriteLock?

  • Старшие 16 бит — счётчик чтения, младшие 16 — счётчик записи
  • Два отдельных AQS
  • Знак — запись, модуль — чтения
  • Отдельные поля readers и writers
Один CAS меняет согласованное состояние обеих блокировок.

Почему RWLock может быть медленнее ReentrantLock при коротких чтениях?

  • Чтения сериализуются
  • Каждый захват чтения — CAS по общему state: горячая кэш-линия при многих читателях, плюс учёт удержаний
  • Он всегда честный
  • Он использует synchronized
Выигрыш — при длинных операциях чтения.
Как реализовать «читать часто, обновлять редко» без RWLock?

Copy-on-write: состояние — неизменяемый объект в volatile-поле или AtomicReference; читатели просто читают ссылку (без блокировок и записи в общую память), писатель строит новую копию и атомарно заменяет ссылку (под блокировкой или CAS, если писателей несколько). Подходит, когда копирование недорого относительно частоты записей: конфигурации, маршруты, справочники.
