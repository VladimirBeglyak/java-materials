ТЕМА 08 · LOCKS

AbstractQueuedSynchronizer изнутри

AQS — каркас, на котором построены ReentrantLock, ReentrantReadWriteLock, Semaphore, CountDownLatch, ThreadPoolExecutor.Worker и десяток других классов. Идея проста: одно атомарное int state, смысл которого задаёт наследник, и FIFO-очередь потоков, которые не смогли его захватить и спят в park. Симулятор с четырьмя потоками покажет захват, очередь, освобождение с передачей следующему и отмену по таймауту; в конце — свой синхронизатор за 15 строк.

8.1Шаблонный метод

AQS реализует всю сложную часть — очередь, парковку, пробуждение, таймауты, прерывания, условия. Наследник определяет только, что значит захват:

Метод наследникаСмыслПример
tryAcquire(arg)попытаться захватить эксклюзивно, без ожиданияReentrantLock: CAS state 0 → 1 или повторный вход владельца
tryRelease(arg)освободить; true, если ожидающих можно будитьstate − 1; при 0 — владелец = null
tryAcquireShared(arg)разделяемый захват: ≥ 0 — успехSemaphore: уменьшить разрешения; CountDownLatch: успех, если state == 0
tryReleaseShared(arg)разделяемое освобождениеSemaphore: вернуть разрешения; CountDownLatch: countDown

public final void acquire(int arg) {
    if (!tryAcquire(arg))              // быстрый путь: без очереди
        acquire(null, arg, false, false, false, 0L);   // медленный: в очередь и park (JDK 14+)
}
public final boolean release(int arg) {
    if (tryRelease(arg)) { signalNext(head); return true; }   // разбудить первого ожидающего
    return false;
}
// а также acquireInterruptibly, tryAcquireNanos, acquireShared, releaseShared, hasQueuedPredecessors, getQueueLength…

8.2Симулятор эксклюзивного захвата

Мьютекс на AQS: state 0 — свободен, 1 — захвачен
Что попробовать T1 acquire, затем T2, T3, T4 acquire — они выстроятся в очередь. Таймаут у T3 — узел отменяется. T1 release — управление перейдёт строго первому живому в очереди (T2). Обратите внимание: этот симулятор «честный»; в нечестном ReentrantLock только что пришедший поток может перехватить блокировку раньше проснувшегося (тема 09).

8.3Очередь

  • Вариант очереди CLH (Craig, Landin, Hagersten): двусвязный список узлов с фиктивной головой; добавление в хвост — CAS по tail, поэтому вставка неблокирующая.
  • Голова — узел потока, который сейчас владеет (или фиктивный). Будится только следующий за головой — без «стада» одновременно проснувшихся потоков.
  • Перед park поток немного крутится (спин), если он первый в очереди — часто блокировку освобождают за микросекунды.
  • Узлы условий (ConditionObject) живут в отдельной однонаправленной очереди и переносятся в основную при signal (тема 10).
  • В режиме shared освобождение распространяется: проснувшийся узел будит следующий, если ресурс ещё доступен (так все ожидающие CountDownLatch.await просыпаются каскадом).

8.4Свой синхронизатор

final class BooleanLatch {
    private static final class Sync extends AbstractQueuedSynchronizer {
        boolean isSignalled() { return getState() != 0; }
        protected int tryAcquireShared(int ignore) { return isSignalled() ? 1 : -1; }   // ждём, пока state != 0
        protected boolean tryReleaseShared(int ignore) { setState(1); return true; }    // разбудить всех
    }
    private final Sync sync = new Sync();
    public boolean isSignalled()           { return sync.isSignalled(); }
    public void signal()                   { sync.releaseShared(1); }
    public void await() throws InterruptedException { sync.acquireSharedInterruptibly(1); }
}

Обёртка делегирует внутреннему классу Sync, а не наследует AQS сама — чтобы не выставлять наружу методы acquire/release. Так устроены все синхронизаторы JDK. AbstractQueuedLongSynchronizer — то же с long state.

8.5Самопроверка

Что наследник AQS обязан определить для эксклюзивного синхронизатора?

  • Очередь ожидающих
  • tryAcquire и tryRelease — смысл state
  • park/unpark
  • Обработку прерываний
Остальное делает AQS.

Кого будит release в эксклюзивном режиме?

  • Все ожидающие потоки
  • Случайный поток
  • Последний пришедший
  • Первый неотменённый узел после головы очереди
FIFO-передача без «стада».

Почему вставка в очередь AQS не требует блокировки?

  • Узел присоединяется к хвосту CAS-ом по полю tail
  • Очередь — ThreadLocal
  • Вставка делается под synchronized
  • Очередь не меняется
AQS сам построен без блокировок — на CAS и park.
Расскажите, как работает ReentrantLock.lock() при занятой блокировке.

lock → acquire(1) → tryAcquire: state != 0 и владелец другой → false. Медленный путь: создать узел, CAS-ом прицепить к хвосту, если узел первый после головы — повторить tryAcquire и немного покрутиться; затем LockSupport.park(this). Владелец вызывает unlock → release → tryRelease уменьшает state до 0, обнуляет владельца → signalNext будит первый узел; тот в цикле повторяет tryAcquire, при успехе становится головой и выходит из lock().
