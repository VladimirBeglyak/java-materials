ReentrantLock: честность и захват

ReentrantLock — это AQS, где state — число повторных захватов владельцем. Главное архитектурное решение — режим честности: нечестная блокировка позволяет только что пришедшему потоку «влезть без очереди» (barging), пока разбуженный поток ещё просыпается. Это нечестно, но в разы быстрее. Симулятор временной шкалы покажет обе стратегии, а затем — весь API: tryLock с таймаутом, прерываемый захват, диагностика.

9.1Реализация

abstract static class Sync extends AbstractQueuedSynchronizer {
    final boolean tryLock() {                                   // и для nonfair lock()
        Thread current = Thread.currentThread();
        int c = getState();
        if (c == 0) { if (compareAndSetState(0, 1)) { setExclusiveOwnerThread(current); return true; } }
        else if (getExclusiveOwnerThread() == current) {        // повторный вход
            if (++c < 0) throw new Error("Maximum lock count exceeded");
            setState(c); return true;                           // без CAS: владеет только текущий поток
        }
        return false;
    }
    protected final boolean tryRelease(int releases) {
        int c = getState() - releases;
        if (getExclusiveOwnerThread() != Thread.currentThread()) throw new IllegalMonitorStateException();
        boolean free = (c == 0);
        if (free) setExclusiveOwnerThread(null);
        setState(c);                                            // volatile-запись публикует изменения критической секции
        return free;
    }
}
static final class FairSync extends Sync {
    protected final boolean tryAcquire(int acquires) {
        if (getState() == 0 && !hasQueuedPredecessors()         // ← честность: не обгонять очередь
            && compareAndSetState(0, acquires)) { setExclusiveOwnerThread(Thread.currentThread()); return true; }
        return false;   // + реентерабельность, как выше
    }
}

9.3API

lock.lock();
try {
    // критическая секция
} finally {
    lock.unlock();                        // всегда в finally; lock() — ДО try (иначе unlock без lock → IllegalMonitorStateException)
}

if (lock.tryLock()) { try { … } finally { lock.unlock(); } }          // без ожидания; НЕ уважает честность (может обогнать очередь)
if (lock.tryLock(200, TimeUnit.MILLISECONDS)) { … } else { отказ }    // с таймаутом — защита от взаимных блокировок
lock.lockInterruptibly();                                             // ожидание можно прервать Thread.interrupt()

// диагностика (не для логики!)
lock.isHeldByCurrentThread(); lock.getHoldCount(); lock.isLocked(); lock.hasQueuedThreads(); lock.getQueueLength();

9.5Самопроверка

Почему нечестная блокировка обычно даёт большую пропускную способность?

  • Она не использует CAS
  • Она не ставит потоки в очередь
  • Работающий поток захватывает освободившуюся блокировку сразу, не ожидая пробуждения спящего — меньше простоев
  • Она использует несколько очередей
Цена — возможная неравномерность и долгое ожидание отдельных потоков.

Что хранит state у ReentrantLock?

  • Число повторных захватов владельцем (0 — свободна)
  • Число ожидающих потоков
  • id владельца
  • Признак честности
Владелец — в exclusiveOwnerThread.

Уважает ли tryLock() без аргументов честность честной блокировки?

  • Да
  • Нет — захватывает, если свободна, даже при наличии очереди; tryLock(0, …) уважает
  • Только в Java 21
  • tryLock недоступен у честной блокировки
Это явно описано в Javadoc.

Почему lock() пишут перед try, а не внутри?

  • Так быстрее
  • Так требует компилятор
  • Чтобы finally не выполнился
  • Если lock() бросит исключение (например, прерывание у lockInterruptibly), finally не должен вызывать unlock без захвата
Иначе IllegalMonitorStateException замаскирует исходную ошибку.
Когда выбрать ReentrantLock вместо synchronized в новом коде?

Когда нужны таймауты или неблокирующая попытка (защита от взаимных блокировок), прерываемое ожидание, несколько условий ожидания, честность, захват в одном методе и освобождение в другом, или код на виртуальных потоках до Java 24 с блокирующими операциями внутри критической секции. Иначе synchronized проще и безопаснее (не забыть unlock).
