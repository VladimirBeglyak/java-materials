ТЕМА 05 · ATOMIC

Field updaters, атомарные массивы, ABA

Когда атомарных полей миллионы (у каждого узла структуры), объект AtomicReference на каждое поле — роскошь: +16 байт и лишняя ссылка. Для этого есть field updaters (и VarHandle). Атомарные массивы дают volatile-семантику каждому элементу. А в lock-free алгоритмах на ссылках подстерегает проблема ABA — разберём её на стеке Трайбера по шагам и способы защиты: штампы и метки.

5.1Field updaters: атомарность без лишних объектов

final class Node {
    final Object item;
    final AtomicReference<Node> next = new AtomicReference<>();
}
// на узел: Node 16 Б + AtomicReference 16 Б
// + лишний переход по ссылке при каждом обращении
final class Node {
    final Object item;
    volatile Node next;
    static final AtomicReferenceFieldUpdater<Node, Node> NEXT =
        AtomicReferenceFieldUpdater.newUpdater(Node.class, Node.class, "next");
}
NEXT.compareAndSet(node, null, newNode);
// сегодня в JDK чаще используется VarHandle (тема 03)
  • Поле должно быть volatile и не static; для примитивов — int/long (AtomicIntegerFieldUpdater, AtomicLongFieldUpdater).
  • Updater создаётся рефлексией и проверяет доступ; операции проверяют тип объекта — чуть медленнее VarHandle. Используйте, если нужна совместимость с Java 8 или привычнее API атомиков.
  • Атомарность гарантируется только относительно других операций через тот же updater/VarHandle: обычная запись в поле в обход — гонка.

5.2Атомарные массивы

volatile int[] arr делает volatile только ссылку на массив, а не его элементы. AtomicIntegerArray, AtomicLongArray, AtomicReferenceArray дают каждому элементу volatile-чтение/запись и CAS. Внутри — обычный массив и VarHandle на элемент (MethodHandles.arrayElementVarHandle).

final AtomicLongArray buckets = new AtomicLongArray(64);
void record(long micros) { buckets.incrementAndGet(63 - Long.numberOfLeadingZeros(Math.max(1, micros))); }
// осторожно: соседние элементы в одной кэш-линии → false sharing при конкурентной записи соседних ячеек (тема 02)

5.3Проблема ABA на стеке Трайбера

AtomicReference<Node> top = new AtomicReference<>();
void push(Node n) { Node t; do { t = top.get(); n.next = t; } while (!top.compareAndSet(t, n)); }
Node pop() {
    Node t, next;
    do { t = top.get(); if (t == null) return null; next = t.next; }
    while (!top.compareAndSet(t, next));      // CAS сравнивает только ССЫЛКУ
    return t;
}
Как стек ломается, если узлы переиспользуются (пул узлов)
Стек (top →)
A → B → C
Поток 1 (pop)
t = A, next = B
Поток 2
pop A, pop B, push A

Поток 1 начал pop: прочитал вершину A и её следующий B, но перед CAS его вытеснили.

Поток 2 снимает A, снимает B (узел B уходит в пул и будет переиспользован), затем снова кладёт A. Стек теперь: A → C. Вершина снова A — «та же» ссылка.

Поток 1 возобновляется: CAS(top, A, B) — вершина равна A, CAS успешен. Вершиной становится B, который давно снят и, возможно, принадлежит кому-то ещё. Узел C потерян, структура повреждена.

В Java с GC проблема ABA на ссылках встречается редко: пока поток 1 держит ссылку на A, этот объект не может быть освобождён и создан заново. ABA возникает при переиспользовании объектов (пулы), при CAS над числами (индексы, счётчики версий с переполнением) и в off-heap структурах.

Решение — менять вместе со ссылкой версию: AtomicStampedReference сравнивает пару (ссылка, int-штамп), каждая операция увеличивает штамп — возврат той же ссылки уже не обманет CAS.

AtomicStampedReference<Node> top = new AtomicStampedReference<>(null, 0);
int[] stampHolder = new int[1];
Node t = top.get(stampHolder);
top.compareAndSet(t, t.next, stampHolder[0], stampHolder[0] + 1);   // успех, только если и ссылка, и штамп прежние
// внутри — неизменяемая пара Pair(reference, stamp) в volatile-поле: каждое изменение создаёт объект

AtomicMarkableReference<Node> next;     // пара (ссылка, boolean) — «логически удалён» в lock-free списках (Харрис)

5.4Самопроверка

Делает ли volatile long[] arr атомарными изменения элементов?

  • Да
  • Только для long
  • Нет: volatile относится к ссылке на массив, нужен AtomicLongArray или VarHandle на элементы
  • Только в Java 21
Элементы массива — обычные поля.

Что такое проблема ABA?

  • CAS проходит, потому что значение вернулось к ожидаемому, хотя между чтением и CAS состояние менялось
  • Взаимная блокировка двух потоков
  • Потерянное обновление volatile
  • Голодание потока
CAS сравнивает значения, а не историю.

Зачем field updater вместо AtomicReference в узлах структуры?

  • Он быстрее CAS
  • Экономия памяти и косвенности: volatile-поле прямо в узле плюс один общий статический updater
  • Он потокобезопаснее
  • Он работает со static-полями
Так устроены многие классы JDK (сейчас чаще VarHandle).
Как работает AtomicStampedReference и чем платим?

Хранит volatile-ссылку на неизменяемую пару (reference, stamp); compareAndSet сравнивает обе компоненты и CAS-ом заменяет ссылку на новую пару. Плата — создание объекта Pair на каждое изменение (давление на GC) и ручное управление штампом. Для большинства Java-структур с GC ABA не возникает; штампы нужны при переиспользовании объектов или числовых состояниях.
