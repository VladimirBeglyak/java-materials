Flow API и SubmissionPublisher

java.util.concurrent.Flow (Java 9) — четыре интерфейса стандарта Reactive Streams: издатель, подписчик, подписка и процессор. Главная идея — противодавление: подписчик сам говорит, сколько элементов готов принять (request(n)), и быстрый источник не может завалить медленного получателя. В JDK есть готовый издатель SubmissionPublisher с буфером на каждого подписчика. Симулятор покажет, что происходит с быстрым издателем и медленным подписчиком при разных стратегиях.

22.1Протокол

public final class Flow {
    public interface Publisher<T> { void subscribe(Subscriber<? super T> s); }
    public interface Subscriber<T> {
        void onSubscribe(Subscription s);   // ровно один раз, первым
        void onNext(T item);                // не больше, чем запрошено через request
        void onError(Throwable t);          // терминальный сигнал
        void onComplete();                  // терминальный сигнал
    }
    public interface Subscription { void request(long n); void cancel(); }
    public interface Processor<T, R> extends Subscriber<T>, Publisher<R> {}
}
// правила (сокращённо из спецификации Reactive Streams): сигналы подписчику последовательны (не параллельны);
// после onError/onComplete — ничего; request(n ≤ 0) → onError(IllegalArgumentException); request можно вызывать из onNext.

22.3SubmissionPublisher

try (SubmissionPublisher<Event> pub = new SubmissionPublisher<>(executor, 256)) {   // буфер 256 на подписчика
    pub.subscribe(new Flow.Subscriber<>() {
        Flow.Subscription sub;
        public void onSubscribe(Flow.Subscription s) { sub = s; s.request(32); }
        int received;
        public void onNext(Event e) { handle(e); if (++received % 16 == 0) sub.request(16); }   // подпитываем спрос
        public void onError(Throwable t) { log.error("stream failed", t); }
        public void onComplete() { log.info("done"); }
    });
    events.forEach(pub::submit);                      // блокирует при полном буфере самого медленного подписчика
}                                                     // close() → onComplete всем подписчикам
// pub.consume(e -> …) — подписаться функцией с неограниченным спросом; возвращает CompletableFuture<Void>
  • Каждому подписчику — свой буфер и свой поток доставки из executor (по умолчанию commonPool); медленный подписчик не тормозит быстрых при offer, но тормозит издателя при submit.
  • Исключение в onNext отменяет подписку и вызывает onError.
  • Flow — это только интерфейсы. Операторы (map, filter, flatMap, retry, окна) дают библиотеки: Project Reactor, RxJava, Mutiny; адаптеры — JdkFlowAdapter, FlowAdapters (reactive-streams). java.net.http.HttpClient использует Flow для тел запросов и ответов.

22.4Самопроверка

Сколько элементов может отправить издатель подписчику после request(10)?

  • Сколько угодно
  • Ровно 10, обязательно
  • Не больше 10 (до следующих request)
  • Один
Спрос копится: request(5) + request(5) = 10.

Чем submit отличается от offer у SubmissionPublisher?

  • submit блокирует при полном буфере подписчика, offer — отбрасывает элемент (с обработчиком отказа)
  • Ничем
  • offer блокирует
  • submit отправляет всем, offer — одному
Выбор между противодавлением и потерей.

Может ли издатель вызвать onNext после onComplete?

  • Да
  • Только с одним элементом
  • Только при ошибке
  • Нет: onComplete и onError — терминальные сигналы
Нарушение — ошибка реализации издателя.
Нужна ли реактивщина, если есть виртуальные потоки?

Для обычного запрос–ответ с блокирующими вызовами виртуальные потоки дают ту же масштабируемость с простым императивным кодом. Реактивные потоки остаются полезными для настоящих потоков данных: стриминг событий с противодавлением, комбинирование бесконечных источников, окна и буферизация, WebSocket/SSE, интеграция с реактивными драйверами. Противодавление в императивном коде на виртуальных потоках — ограниченные BlockingQueue и Semaphore.
