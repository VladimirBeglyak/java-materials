ForkJoinPool и work-stealing

ForkJoinPool создан для рекурсивного «разделяй и властвуй»: задача делится на подзадачи, пока они не станут маленькими. Ключевая идея — у каждого рабочего потока своя двусторонняя очередь: свои задачи поток берёт с одного конца (LIFO, горячие в кэше), а свободные потоки крадут с другого конца (FIFO, самые крупные куски). Симулятор покажет, как работа сама растекается по потокам. Этот же пул исполняет параллельные стримы, CompletableFuture по умолчанию и виртуальные потоки.

17.1RecursiveTask

final class SumTask extends RecursiveTask<Long> {
    static final int THRESHOLD = 10_000;
    final long[] a; final int lo, hi;
    SumTask(long[] a, int lo, int hi) { this.a = a; this.lo = lo; this.hi = hi; }
    @Override protected Long compute() {
        if (hi - lo <= THRESHOLD) { long s = 0; for (int i = lo; i < hi; i++) s += a[i]; return s; }
        int mid = (lo + hi) >>> 1;
        SumTask left = new SumTask(a, lo, mid);
        left.fork();                                        // в СВОЮ деку: её может украсть другой поток
        long right = new SumTask(a, mid, hi).compute();     // правую половину считаем сами, без лишнего fork
        return right + left.join();                         // join: если левую не украли — выполним сами (pop)
    }
}
long sum = ForkJoinPool.commonPool().invoke(new SumTask(data, 0, data.length));
Частая ошибка left.fork(); right.fork(); return left.join() + right.join(); — работает, но текущий поток просто ждёт, вместо того чтобы считать сам; а порядок join важен (сначала последний форкнутый — LIFO). Идиома: fork одну половину, compute другую, затем join.

17.2Симулятор work-stealing

SumTask[0, 64) на 4 потоках, порог 8 элементов
Почему именно так Владелец работает с вершиной деки (последняя форкнутая — самая маленькая и «горячая» в кэше) без конкуренции с ворами. Вор берёт с дна — самые старые и крупные задачи: одной кражи хватает надолго, краж мало. Владелец и вор конфликтуют, только когда в деке остаётся один элемент (разрешается CAS).

17.3Пул и общий пул

АспектПодробности
commonPool()статический общий пул: параллелизм = число процессоров − 1 (вызывающий поток тоже участвует в invoke/join); настраивается -Djava.util.concurrent.ForkJoinPool.common.parallelism. Используют параллельные стримы, CompletableFuture.*Async без executor, Arrays.parallelSort
Блокирующие операциизаблокированный поток FJP не берёт задачи — пул «теряет» параллелизм. ForkJoinPool.managedBlock(blocker) позволяет пулу временно добавить компенсирующий поток
asyncMode = trueсвои задачи — FIFO: для событийных задач, которые никогда не join (так настроен планировщик виртуальных потоков)
Исключенияпробрасываются в join/invoke (в RuntimeException-обёртке, если проверяемые); getException()
CountedCompleterпродолжения без блокирующего join: задача завершается, когда счётчик ожидаемых подзадач дошёл до нуля (так устроены параллельные стримы)
Не блокируйте общий пул I/O, sleep или ожидание блокировок в задачах параллельного стрима или supplyAsync без своего executor занимают потоки commonPool, общие для всего приложения: другие параллельные стримы и CompletableFuture начинают ждать. Для блокирующих задач — свой пул или виртуальные потоки.

17.4Самопроверка

С какого конца деки вор крадёт задачи и почему?

  • С вершины — там свежие задачи
  • Случайно
  • С дна — там самые старые и крупные задачи, и вор не мешает владельцу, работающему с вершиной
  • Воровство запрещено
Минимум краж и конфликтов.

Настраивается системным свойством.

Почему в compute() лучше fork() одну половину и compute() вторую, а не fork() обе?

  • Иначе не скомпилируется
  • fork() дорогой
  • Так меньше памяти
  • Текущий поток сразу выполняет полезную работу вместо ожидания в join, меньше задач в деке
Стандартная идиома из Javadoc.
Чем ForkJoinPool отличается от ThreadPoolExecutor?

TPE — одна общая очередь задач для всех потоков (конкуренция за неё), задачи независимы. FJP — у каждого потока своя дека и кража работы; оптимизирован для множества мелких задач, порождающих подзадачи и ждущих их (join без блокировки потока — поток в это время выполняет другие задачи). FJP плохо переносит блокирующие задачи (нужен ManagedBlocker); TPE — универсальный.
