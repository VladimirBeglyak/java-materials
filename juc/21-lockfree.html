Lock-free структуры: CLQ и SkipList

Неблокирующие структуры обходятся без блокировок вообще: каждое изменение — один или несколько CAS, а потоки, заставшие операцию другого незавершённой, помогают её закончить. Разберём по шагам очередь Майкла–Скотта (основа ConcurrentLinkedQueue) с её «отстающим» хвостом и список с пропусками (ConcurrentSkipListMap) — упорядоченную конкурентную карту без деревьев и поворотов.

21.2Очередь Майкла–Скотта

public boolean offer(E e) {
    Node<E> newNode = new Node<>(e);
    for (Node<E> t = tail, p = t;;) {
        Node<E> q = p.next;
        if (q == null) {                                   // p — последний узел
            if (NEXT.compareAndSet(p, null, newNode)) {    // CAS №1: прицепить узел — ТОЧКА ЛИНЕАРИЗАЦИИ
                if (p != t) TAIL.weakCompareAndSet(this, t, newNode);   // CAS №2: подвинуть tail (может не удаться — не страшно)
                return true;
            }
        } else p = (p != t && t != (t = tail)) ? t : q;    // tail отстаёт → идём вперёд (помогаем)
    }
}
Два потока одновременно делают offer
Очередь
head → [A] → [B]·tail… [B] → [C]… [C] → [D]
Поток 1: offer(C)
t = tail = B
Поток 2: offer(D)
t = tail = B

Оба потока видят, что B — последний узел.

T1 успешно прицепил C к B. С этого момента C логически в очереди — даже если tail пока не сдвинут.

CAS T2 провалился: B.next уже не null. T2 не ждёт T1 — он просто переходит по ссылке к C (tail «отстаёт» на один узел).

T2 прицепляет D к C и двигает tail (через узел). Если бы T1 «умер» после CAS №1, другие потоки всё равно продвигали бы tail — никто не ждёт никого.

Порядок сохранён, блокировок не было. В JDK tail и head намеренно сдвигаются не на каждой операции (реже CAS по горячим полям), а удалённые узлы «самоссылаются» для быстрой помощи GC. Цена — size() обходит всю очередь (O(n)), итераторы слабо согласованы.

21.3Список с пропусками

Упорядоченный связный список, над которым надстроены «экспресс-полосы»: каждый узел с вероятностью 1/2 получает уровень 1, с 1/4 — уровень 2 и т. д. Поиск спускается сверху: по верхнему уровню — большими прыжками, затем ниже. В среднем O(log n), без поворотов: вставка меняет только соседние ссылки — поэтому его легко сделать неблокирующим на CAS (в отличие от красно-чёрного дерева).

21.4Самопроверка

Что значит «lock-free»?

  • Каждый поток завершает операцию за ограниченное число шагов
  • Система в целом всегда продвигается: хотя бы один поток завершает операцию, даже если другие остановлены
  • Нет синхронизации вообще
  • Используется только volatile
Каждый поток — это уже wait-free.

Почему в очереди Майкла–Скотта tail может отставать от реального последнего узла?

  • Это ошибка
  • Из-за GC
  • Так задумано для FIFO
  • Добавление узла и сдвиг tail — два разных CAS; любой поток, заметивший отставание, помогает сдвинуть tail
Точка линеаризации — CAS next.

Почему ConcurrentSkipListMap, а не конкурентное красно-чёрное дерево?

  • Вставка в список с пропусками меняет только соседние ссылки и хорошо ложится на CAS; балансировка дерева поворотами затрагивает много узлов сразу
  • Skip list всегда быстрее дерева
  • Деревья не поддерживают порядок
  • Так исторически сложилось
Вероятностная балансировка — локальная.
Почему lock-free структуры не всегда быстрее блокировок?

При сильной конкуренции CAS проваливаются и повторяются, кэш-линии горячих полей (head, tail) «пинг-понгом» гоняются между ядрами, а помощь чужим операциям добавляет работы. Блокировка при высокой конкуренции может быть эффективнее: потоки засыпают, а не крутятся. Выигрыш lock-free — в отсутствии взаимных блокировок, инверсии приоритетов и в устойчивости к вытеснению потоков, а также в низкой задержке при умеренной конкуренции.
