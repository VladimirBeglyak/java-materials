StampedLock и оптимистичное чтение

StampedLock (Java 8) добавляет к чтению и записи третий режим — оптимистичное чтение: читатель вообще ничего не пишет в общую память, просто запоминает версию («штамп»), читает поля и проверяет, не было ли записи. Если не было — данные согласованы, а читатели не мешают друг другу даже на уровне кэша. Платить за это приходится сложностью: копировать поля, терпеть несогласованные значения до проверки, отсутствие реентерабельности.

12.1Идиома оптимистичного чтения

class Point {
    private double x, y;
    private final StampedLock sl = new StampedLock();

    void move(double dx, double dy) {
        long stamp = sl.writeLock();                        // эксклюзивная запись: версия +1
        try { x += dx; y += dy; } finally { sl.unlockWrite(stamp); }
    }
    double distanceFromOrigin() {
        long stamp = sl.tryOptimisticRead();                // 0, если сейчас идёт запись
        double curX = x, curY = y;                          // 1) копируем поля в локальные переменные
        if (!sl.validate(stamp)) {                          // 2) была ли запись после получения штампа?
            stamp = sl.readLock();                          // 3) да — читаем заново под обычной блокировкой чтения
            try { curX = x; curY = y; } finally { sl.unlockRead(stamp); }
        }
        return Math.hypot(curX, curY);                      // 4) используем только проверенные копии
    }
}

12.3Режимы и конверсии

void moveIfAtOrigin(double newX, double newY) {
    long stamp = sl.readLock();
    try {
        while (x == 0.0 && y == 0.0) {
            long ws = sl.tryConvertToWriteLock(stamp);      // атомарно, если мы единственный читатель
            if (ws != 0L) { stamp = ws; x = newX; y = newY; break; }
            sl.unlockRead(stamp); stamp = sl.writeLock();   // не вышло — отпустить и взять запись (и перепроверить в цикле)
        }
    } finally { sl.unlock(stamp); }
}
Ограничения Не реентерабелен: повторный writeLock в том же потоке — взаимоблокировка с самим собой. Нет Condition. Нет понятия владельца: штамп можно отпустить из другого потока, но ошибки не обнаруживаются. readLock()/writeLock() не прерываемы (есть readLockInterruptibly()). Используйте внутри хорошо изолированных классов, а не как общую блокировку по коду.

12.4Самопроверка

Почему оптимистичное чтение масштабируется лучше блокировки чтения?

  • Оно использует несколько блокировок
  • Читатель ничего не пишет в общую память — нет конкуренции за кэш-линию состояния
  • Оно не проверяет данные
  • Оно выполняется в отдельном потоке
Блокировка чтения — CAS по общему state.

Что можно делать с данными, прочитанными оптимистично, до validate?

  • Что угодно
  • Вызывать методы объектов по прочитанным ссылкам
  • Возвращать их вызывающему
  • Только копировать в локальные переменные — они могут быть несогласованными
Действия — только после успешного validate.

Что произойдёт, если поток с writeLock StampedLock снова вызовет writeLock()?

  • Он заблокируется навсегда — StampedLock не реентерабелен
  • Увеличится счётчик захватов
  • IllegalMonitorStateException
  • Вернётся тот же штамп
Главное отличие от ReentrantReadWriteLock.
Когда StampedLock — правильный выбор?

Небольшое изолированное состояние (несколько примитивных полей), читаемое очень часто многими потоками и изменяемое редко, где важна масштабируемость чтения: координаты, статистика, кэш небольших значений. Код блокировок сосредоточен в одном классе, нет вызовов чужого кода под блокировкой, не нужны реентерабельность и условия. Иначе — ReentrantReadWriteLock или неизменяемые снимки.
