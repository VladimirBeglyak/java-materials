LongAdder, LongAccumulator и Striped64

Когда счётчик увеличивают десятки потоков, один AtomicLong становится узким местом (тема 02). LongAdder (Java 8) распределяет запись по массиву ячеек: без конкуренции — одно поле, при конкуренции — у каждого потока своя ячейка на своей кэш-линии. Симулятор покажет, как растёт массив ячеек и как потоки перехешируются при столкновениях.

6.1Устройство

abstract class Striped64 extends Number {
    @jdk.internal.vm.annotation.Contended static final class Cell { volatile long value; }  // каждая ячейка — на своей кэш-линии
    transient volatile Cell[] cells;      // null, пока нет конкуренции; размер — степень двойки, не больше ≈ NCPU
    transient volatile long base;         // быстрый путь без конкуренции
    transient volatile int cellsBusy;     // спин-блокировка на создание/расширение cells
}
public void increment() {               // LongAdder.add(1)
    Cell[] cs; long b, v; int m; Cell c;
    if ((cs = cells) != null || !casBase(b = base, b + 1)) {          // нет конкуренции → CAS base и всё
        int probe = getProbe();                                       // «хэш» потока (поле Thread, как в ThreadLocalRandom)
        if (cs == null || (m = cs.length - 1) < 0 || (c = cs[probe & m]) == null
            || !c.cas(v = c.value, v + 1))
            longAccumulate(1, null, uncontended);                     // медленный путь: создать/расширить cells, перехешировать probe
    }
}
public long sum() { long s = base; for (Cell c : cells) if (c != null) s += c.value; return s; }   // НЕ атомарный снимок

6.2Симулятор

Потоки одновременно вызывают increment()
Что видно С одним потоком всё идёт в base — LongAdder не дороже AtomicLong. При конкуренции массив ячеек растёт до ≈ NCPU, после чего потоки распределяются по ячейкам перехешированием — провалы CAS почти исчезают. Ячейки никогда не уменьшаются: адрес памяти — плата за масштабируемость.

Поэтому она обязана быть ассоциативной, коммутативной и без побочных эффектов: max, min, сумма, побитовое ИЛИ — да; «последнее значение» или среднее — нет.

6.4Самопроверка

Почему LongAdder масштабируется лучше AtomicLong под конкурентной записью?

  • Он использует блокировку
  • Потоки пишут в разные ячейки на разных кэш-линиях — нет общей точки конкуренции
  • Он не использует CAS
  • Он буферизует записи в ThreadLocal
Ячейки помечены @Contended.

Можно ли использовать LongAdder для генерации уникальных последовательных id?

  • Да, он быстрее
  • Да, через sum()
  • Да, через incrementAndGet
  • Нет: нет атомарной операции «увеличить и вернуть новое значение», sum() не атомарен
Для id — AtomicLong.getAndIncrement.

Какая функция допустима для LongAccumulator?

  • Long::max
  • (a, x) -> x (последнее значение)
  • (a, x) -> (a + x) / 2
  • (a, x) -> a - x
Ассоциативна и коммутативна только первая.
Как Striped64 выбирает ячейку для потока и что делает при столкновениях?

Каждый поток имеет «зонд» (probe) — псевдослучайное число в поле Thread (общее с ThreadLocalRandom). Индекс ячейки = probe & (n − 1). Если CAS в ячейку провалился — сначала перехешировать probe (xorshift) и попробовать другую ячейку; если провалы продолжаются и размер меньше числа процессоров — удвоить массив под спин-блокировкой cellsBusy. Создание отсутствующей ячейки — тоже под cellsBusy.
