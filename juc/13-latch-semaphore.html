CountDownLatch и Semaphore

Два самых простых синхронизатора — оба на разделяемом режиме AQS. CountDownLatch — одноразовые ворота: открываются, когда счётчик дошёл до нуля. Semaphore — пул разрешений: не больше N потоков одновременно. Разбираем, как каждый выражается через state, типичные схемы использования (стартовые и финишные ворота, ограничение параллелизма для виртуальных потоков) и ловушки: семафор без владельца и «утечка» разрешений.

13.1CountDownLatch

private static final class Sync extends AbstractQueuedSynchronizer {
    Sync(int count) { setState(count); }
    protected int tryAcquireShared(int acquires) { return (getState() == 0) ? 1 : -1; }   // await проходит, только когда 0
    protected boolean tryReleaseShared(int releases) {                                   // countDown
        for (;;) {
            int c = getState();
            if (c == 0) return false;                  // уже открыт — лишние countDown игнорируются
            int nc = c - 1;
            if (compareAndSetState(c, nc)) return nc == 0;   // true → разбудить ВСЕХ ожидающих каскадом
        }
    }
}
CountDownLatch start = new CountDownLatch(1), done = new CountDownLatch(nThreads);
for (int i = 0; i < nThreads; i++) executor.submit(() -> {
    try { start.await(); work(); }                  // все стартуют одновременно
    catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    finally { done.countDown(); }                   // countDown — в finally, иначе при исключении await зависнет навсегда
});
long t0 = System.nanoTime(); start.countDown();
if (!done.await(30, TimeUnit.SECONDS)) throw new TimeoutException();   // всегда с таймаутом в продакшене
long elapsed = System.nanoTime() - t0;

Счётчик нельзя увеличить или сбросить — защёлка одноразовая. Для многократного использования — CyclicBarrier или Phaser (тема 14). countDown() имеет семантику release, await() — acquire: действия до countDown видны после await.

Semaphore(2): нажимайте на потоки — acquire / release
ОсобенностьСледствие
Нет владельцаrelease можно вызвать из любого потока, даже без acquire — ошибки в учёте молча увеличивают лимит. Всегда acquire перед try, release в finally.

private final Semaphore apiPermits = new Semaphore(20);
Response call(Request r) throws InterruptedException, TimeoutException {
    if (!apiPermits.tryAcquire(500, TimeUnit.MILLISECONDS)) throw new TimeoutException("API перегружен");
    try { return client.send(r); }
    finally { apiPermits.release(); }
}

13.3Самопроверка

Почему countDown() надо вызывать в finally?

  • Так быстрее
  • Иначе не скомпилируется
  • Если работа бросит исключение, счётчик не дойдёт до нуля, и await зависнет навсегда
  • Для сброса счётчика
И всегда await с таймаутом.

Что будет, если вызвать semaphore.release() без предшествующего acquire()?

  • Число разрешений увеличится — у семафора нет владельца
  • IllegalMonitorStateException
  • Ничего
  • Deadlock
Отличие от Lock: учёт целиком на совести кода.

Можно ли повторно использовать CountDownLatch после того, как счётчик дошёл до нуля?

  • Да, через reset()
  • Да, через countUp()
  • Да, если создать заново в том же поле
  • Нет: защёлка одноразовая; для повторяющихся фаз — CyclicBarrier или Phaser
Пересоздание объекта — уже другая защёлка.

Как ограничить число одновременных запросов к БД из 10 000 виртуальных потоков?

  • Пул платформенных потоков на 20
  • Semaphore на 20 разрешений (или ограниченный пул соединений)
  • synchronized
  • CountDownLatch(20)
Ограничивают ресурс, а не потоки.
Как выразить через AQS семантику Semaphore и CountDownLatch?

Оба используют разделяемый режим. Semaphore: state — число свободных разрешений; tryAcquireShared вычитает запрошенное CAS-ом и возвращает остаток (отрицательный — ждать); tryReleaseShared прибавляет. Честный вариант сначала проверяет hasQueuedPredecessors. CountDownLatch: state — счётчик; acquire успешен только при 0; release уменьшает и возвращает true при достижении нуля — тогда AQS будит всех ожидающих каскадом.
