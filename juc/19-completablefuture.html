CompletableFuture изнутри

CompletableFuture — это одно поле результата и стек зависимых действий. Как только результат установлен, стек «разматывается» и запускает продолжения. Отсюда главный практический вопрос — в каком потоке выполнится колбэк — и ответ на него в симуляторе. Затем — распространение ошибок по цепочке (тоже интерактивно), таймауты, комбинаторы и почему cancel ничего не прерывает.

19.1Устройство

public class CompletableFuture<T> implements Future<T>, CompletionStage<T> {
    volatile Object result;       // null — не завершён; AltResult(null) — значение null; AltResult(ex) — исключение
    volatile Completion stack;    // стек Трайбера зависимых действий (thenApply, thenCompose, …)

    boolean completeValue(T t) { return RESULT.compareAndSet(this, null, (t == null) ? NIL : t); }   // завершить можно ровно один раз
    final void postComplete() { /* снять все Completion со стека и выполнить их (каждое может завершить свой CF и т.д.) */ }
}
// thenApply(fn): если результат уже есть — fn выполняется СРАЗУ в вызывающем потоке;
//                иначе в стек кладётся UniApply, и fn выполнит тот поток, который завершит исходный CF.

19.3Как ошибка идёт по цепочке

Цепочка этапов
supplyAsync(() -> load())                 // 1
    .thenApply(raw -> parse(raw))         // 2
    .thenApply(doc -> enrich(doc))        // 3
    .exceptionally(ex -> fallback(ex))    // 4
    .thenApply(doc -> render(doc))        // 5
    .whenComplete((r, ex) -> log(r, ex)); // 6
МетодКогда вызываетсяМеняет результат
exceptionally(ex -> v)только при ошибкеда — восстановление
handle((v, ex) -> r)всегдада
whenComplete((v, ex) -> …)всегданет (побочные эффекты: лог, метрики)

19.4Комбинирование и таймауты

CompletableFuture<User>   user   = supplyAsync(() -> users.find(id), io);
CompletableFuture<Orders> orders = supplyAsync(() -> orderApi.list(id), io)
        .completeOnTimeout(Orders.empty(), 300, MILLISECONDS);         // запасное значение, если не успел
CompletableFuture<Page> page = user.thenCombine(orders, Page::new)    // оба результата
        .orTimeout(1, SECONDS);                                         // TimeoutException по истечении

CompletableFuture.allOf(a, b, c).thenRun(…);                           // allOf возвращает Void — результаты берите из a, b, c (join())
CompletableFuture.anyOf(r1, r2).thenAccept(…);                          // первый завершившийся (в том числе с ошибкой!)
user.thenCompose(u -> supplyAsync(() -> prefs.load(u), io));           // flatMap: функция возвращает CF
cancel не прерывает и таймаут не останавливает cf.cancel(true) лишь завершает CF исключением CancellationException — параметр игнорируется, работа задачи в пуле продолжается. orTimeout так же завершает только CF (через служебный поток-«Delayer»), а не саму операцию. Останавливайте операции собственными таймаутами I/O и проверкой флага.

19.5Самопроверка

CF уже завершён. В каком потоке выполнится cf.thenApply(fn)?

  • В commonPool
  • В потоке, который его завершил
  • В вызывающем потоке, синхронно внутри thenApply
  • В новом потоке
Неочевидная, но важная деталь.

Что сделает thenApply, если предыдущий этап завершился исключением?

  • Не вызовет функцию и передаст исключение дальше
  • Вызовет функцию с null
  • Проглотит исключение
  • Бросит его в вызывающем потоке
До первого exceptionally/handle.

Прервёт ли cf.cancel(true) выполняющуюся задачу supplyAsync?

  • Да
  • Только с true
  • Только в виртуальном потоке
  • Нет: CompletableFuture не связан с выполняющим потоком, отмена лишь завершает его CancellationException
Отличие от FutureTask.

Что возвращает allOf(a, b, c)?

  • Список результатов
  • CompletableFuture<Void>, завершающийся, когда завершились все; результаты берутся из a, b, c
  • Первый результат
  • Массив Future
Если хоть один упал — allOf завершится исключением после завершения всех.
Как устроена цепочка CompletableFuture внутри, и почему она не блокирует потоки?

Каждый этап — отдельный CompletableFuture; регистрация зависимости (thenApply и др.) кладёт объект Completion в стек источника (CAS). Когда источник получает результат (CAS по полю result), вызывается postComplete: он снимает и выполняет все Completion; каждый вычисляет свою функцию и завершает свой CF, который запускает уже свои зависимые. Никто не ждёт в get — продолжения выполняются по мере появления результатов в потоках, которые эти результаты установили (или в указанных executor-ах).
