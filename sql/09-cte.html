CTE и рекурсивные запросы

CTE (WITH) позволяет разбить сложный запрос на именованные шаги, которые читаются сверху вниз. Рекурсивный CTE (WITH RECURSIVE) даёт то, чего нет у обычного SQL, — итерации: обход дерева, генерацию последовательностей, раскрутку графов.

9.1WITH как читаемые шаги

Каждый CTE — именованный подзапрос, на который можно ссылаться ниже. Сложная логика раскладывается на шаги, которые читаются как параграфы.

WITH paid AS (
    SELECT o.customer_id, SUM(i.qty * i.price) AS total
    FROM orders o JOIN order_items i ON i.order_id = o.id
    WHERE o.status IN ('paid', 'shipped')
    GROUP BY o.customer_id
),
big_spenders AS (
    SELECT customer_id, total FROM paid WHERE total > 10000
)
SELECT c.name, b.total
FROM big_spenders b JOIN customers c ON c.id = b.customer_id
ORDER BY b.total DESC;

9.2MATERIALIZED и встраивание

С PostgreSQL 12 нерекурсивный CTE, на который ссылаются один раз, встраивается в основной запрос (как обычный подзапрос) — оптимизатор видит его целиком. MATERIALIZED заставляет вычислить шаг отдельно и зафиксировать результат, что полезно, когда подзапрос дорогой и используется многократно.

WITH heavy AS MATERIALIZED (   -- вычислить один раз, зафиксировать
    SELECT customer_id, SUM(qty * price) AS total
    FROM order_items GROUP BY customer_id
)
SELECT * FROM heavy WHERE total > 1000
UNION ALL
SELECT * FROM heavy WHERE total <= 1000;

9.3Рекурсивный CTE: анатомия

Рекурсивный CTE состоит из двух частей, объединённых UNION ALL: база (начальные строки) и шаг (как из текущих строк получить следующие), который ссылается на сам CTE.

WITH RECURSIVE t(n) AS (
    SELECT 1                       -- база: старт с 1
    UNION ALL
    SELECT n + 1 FROM t WHERE n < 10   -- шаг: +1, пока меньше 10
)
SELECT n FROM t;                   -- 1..10
Защита от бесконечного цикла Шаг должен иметь условие остановки (WHERE), иначе запрос зациклится. Некоторые СУБД ограничивают глубину рекурсии параметром (в PostgreSQL — max_recursive_iterations).

9.4Обход дерева категорий

Таблица categories(id, name, parent_id) задаёт дерево. Рекурсивный CTE раскручивает его от корня к листьям.

WITH RECURSIVE tree AS (
    SELECT id, name, parent_id, 1 AS depth, name AS path
    FROM categories WHERE parent_id IS NULL          -- корни
    UNION ALL
    SELECT c.id, c.name, c.parent_id, t.depth + 1,
           t.path || ' → ' || c.name                 -- накапливаем путь
    FROM categories c JOIN tree t ON c.parent_id = t.id
)
SELECT path, depth FROM tree ORDER BY path;

Этот приём решает: «все подкатегории категории», «путь до корня», «все потомки узла», «иерархия сотрудников». Направление обхода меняется перестановкой условия соединения (от корня вниз или от узла вверх).

9.6Самопроверка

Из чего состоит рекурсивный CTE?

  • Только из одного SELECT
  • Из базы и шага, объединённых UNION ALL
  • Из базы и шага, объединённых UNION
  • Из двух независимых SELECT
База задаёт стартовые строки, шаг (ссылающийся на сам CTE) — как получить следующие; они объединяются UNION ALL.

Что делает MATERIALIZED у CTE?

  • Заставляет вычислить шаг отдельно и зафиксировать результат
  • Ускоряет любой запрос
  • Запрещает ссылаться на CTE дважды
  • Превращает CTE в таблицу навсегда
MATERIALIZED вычисляет и сохраняет результат шага; полезно, когда шаг дорогой и используется многократно.

Что произойдёт, если рекурсивный шаг не имеет условия остановки?

  • Ничего, запрос завершится
  • CTE выполнится один раз
  • Бесконечный цикл (пока не сработает лимит глубины)
  • Ошибка синтаксиса
Рекурсия итерирует, пока шаг добавляет строки. Без условия WHERE она не остановится — СУБД прерывает по лимиту глубины.

Какую задачу решает рекурсивный CTE по таблице с parent_id?

  • Поиск дубликатов
  • Сортировку
  • Дедупликацию строк
  • Обход дерева/иерархии (потомки, путь, глубина)
Рекурсия по parent_id раскручивает иерархию: поддеревья, пути, уровни вложенности.
Чем CTE отличается от обычного подзапроса?

Семантически почти то же, но CTE именован и может использоваться многократно, а читается сверху вниз как последовательность шагов. Нерекурсивный CTE в PostgreSQL 12+ обычно встраивается в основной запрос.

Как вывести путь от корня до каждого узла дерева?

Накапливать путь в шаге: база берёт корни с path = name, шаг добавляет t.path || ' → ' || c.name. Так в каждой строке окажется полный путь от корня.
