Подзапросы: скалярные, IN, EXISTS

Подзапрос — это SELECT внутри другого запроса. Он бывает скалярным (одно значение), списочным (набор для IN/ANY/ALL) и коррелированным (ссылается на строку внешнего запроса). Во многих случаях подзапрос и JOIN дают один и тот же результат — важно выбирать форму по читаемости и знать, когда EXISTS надёжнее NOT IN.

7.1Скалярный подзапрос

Возвращает ровно одну строку с одним столбцом — его можно использовать там, где ожидается значение: в SELECT, WHERE, выражении.

-- последний заказ каждого клиента (коррелированный скалярный подзапрос)
SELECT c.name,
       (SELECT max(o.created_at) FROM orders o WHERE o.customer_id = c.id) AS last_order
FROM customers c;

-- товары дороже среднего (некоррелированный)
SELECT name, price FROM products
WHERE price > (SELECT avg(price) FROM products);
Скалярный подзапрос должен вернуть ≤ 1 строки Если подзапрос вернёт несколько строк, СУБД выдаст ошибку. Убедитесь условием или агрегатом (max/min/avg), что строк не больше одной.

7.2IN, ANY, ALL

-- IN: равно любому из списка
SELECT name FROM products
WHERE id IN (SELECT product_id FROM order_items WHERE qty >= 2);   -- заказывали в количестве ≥ 2

-- ANY (= SOME): истинно, если условие верно хотя бы для одного значения
SELECT name, price FROM products
WHERE price > ANY (SELECT price FROM products WHERE category = 'электроника');  -- дороже самого дешёвого из электроники

-- ALL: истинно, если условие верно для всех значений
SELECT name, price FROM products
WHERE price > ALL (SELECT price FROM products WHERE category = 'электроника');  -- дороже всей электроники
NOT IN с NULL x NOT IN (подзапрос с NULL) возвращает пустоту (тема 02). Для «нет в наборе» используйте NOT EXISTS — он не ловит эту проблему.

7.3Коррелированные EXISTS / NOT EXISTS

EXISTS проверяет, вернул ли подзапрос хотя бы одну строку. Коррелированный подзапрос ссылается на строку внешнего запроса — он выполняется «для каждой строки», но планировщик часто превращает его в полу-соединение и останавливается на первом совпадении.

-- клиенты, у которых есть хотя бы один заказ (полусоединение)
SELECT c.name FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- товары, которые ни разу не покупали (антисоединение)
SELECT p.name FROM products p
WHERE NOT EXISTS (SELECT 1 FROM order_items i WHERE i.product_id = p.id);
EXISTS против IN EXISTS не сравнивает значения — только наличие строк, поэтому NULL не мешает. Для проверки существования он читается точнее: «есть ли заказ у этого клиента», а не «равен ли id какому-то из списка».

7.4LATERAL

Обычный подзапрос в FROM не видит строки «слева». LATERAL (PostgreSQL) разрешает это — удобно для «для каждого X взять N последних».

-- для каждого клиента — три последних заказа
SELECT c.name, o.id, o.created_at
FROM customers c
CROSS JOIN LATERAL (
  SELECT id, created_at FROM orders
  WHERE customer_id = c.id
  ORDER BY created_at DESC LIMIT 3
) o;

7.6Самопроверка

Что произойдёт, если скалярный подзапрос вернёт две строки?

  • Возьмётся первая строка
  • Ошибка — скалярный подзапрос должен вернуть не больше одной строки
  • Возьмётся последняя
  • Вернётся NULL
Скалярный подзапрос используется как одно значение, поэтому несколько строк — ошибка.

Чем EXISTS надёжнее NOT IN?

  • Он быстрее всегда
  • Он поддерживает несколько столбцов
  • Он не ломается, когда в подзапросе есть NULL
  • Ничем
NOT IN с NULL в списке никогда не истинен; EXISTS проверяет только наличие строк и NULL не мешает.

Что вернёт price > ANY (SELECT …)?

  • True, если price больше хотя бы одного значения из набора
  • True, если price больше всех значений
  • Всегда true
  • Ошибку
ANY (синоним SOME) истинен, если условие верно хотя бы для одного значения. ALL — для всех.

Зачем нужен LATERAL?

  • Ускоряет любой JOIN
  • Это то же, что CROSS JOIN
  • Заменяет GROUP BY
  • Позволяет подзапросу видеть столбцы из строки слева
LATERAL разрешает корреляцию в FROM: например, «для каждого клиента три последних заказа».
Когда подзапрос коррелированный, а когда — нет?

Коррелированный ссылается на столбец внешнего запроса и пересчитывается для каждой внешней строки. Некоррелированный независим и выполняется один раз. Коррелированные часто переписываются планировщиком в JOIN.

Подзапрос или JOIN — что выбрать?

Если нужны столбцы обеих таблиц — JOIN. Если нужна только проверка существования или одно значение — EXISTS/скалярный подзапрос читаются яснее. Ориентируйтесь на читаемость; современные оптимизаторы часто дают одинаковый план.
