JSON и полуструктурированные данные

Когда структура данных меняется или вложена (настройки, события, ответы внешних API), реляционные столбцы неудобны — выручает JSON. В PostgreSQL тип jsonb даёт быстрые операторы извлечения, проверку структуры и индексы GIN, так что JSON можно не только хранить, но и запрашивать.

15.1json против jsonb

ТипХранениеКогда
jsonтекст «как есть» (с пробелами и порядком ключей)нужен точный исходный текст

15.2Операторы извлечения

ОператорВозвращаетПример

-- таблица с jsonb-столбцом
CREATE TABLE events (id bigint GENERATED ALWAYS AS IDENTITY, payload jsonb NOT NULL);

INSERT INTO events (payload) VALUES
  ('{"type":"order","user":"anna","total":95000,"tags":["vip","mobile"]}');

SELECT payload ->> 'type' AS type,
       payload ->> 'user' AS user,
       payload #>> '{tags,0}' AS first_tag
FROM events;

-- фильтр по JSON-полю
SELECT * FROM events WHERE payload ->> 'user' = 'anna';

-- проверка существования ключа
SELECT * FROM events WHERE payload ? 'total';

15.3Агрегация в JSON

Можно собрать строки в JSON-массив или объект прямо в базе:

-- все товары категории в один JSON-массив
SELECT json_agg(json_build_object('id', id, 'name', name, 'price', price)) AS items
FROM products WHERE category = 'электроника';

-- развернуть JSON-массив в строки
SELECT * FROM json_array_elements('[1,2,3]'::jsonb) AS n;

15.4Индексы GIN на jsonb

Поиск payload ->> 'user' = 'anna' без индекса просматривает все строки. GIN-индекс ускоряет проверки ?, @> и ->>.

CREATE INDEX events_payload_gin ON events USING GIN (payload);          -- универсальный
CREATE INDEX events_user_btree ON events ((payload ->> 'user'));      -- выражение → B-tree

-- вхождение подструктуры
SELECT * FROM events WHERE payload @> '{"type":"order"}';
Диалекты MySQL хранит JSON в типе JSON и использует JSON_EXTRACT(), ->, ->>; SQLite — функции json_extract()/json_each() (расширение JSON1). Идея одинакова: хранить документ и доставать из него поля.

15.5Песочница

SQL-песочница: JSON (SQLite JSON1)

SQLite использует json_extract()/json_each(), а не операторы PostgreSQL ->/->>. Сами операторы ->, #>, @>, ? и GIN-индексы проверяются на настоящем PostgreSQL.

15.6Самопроверка

Чем jsonb отличается от json в PostgreSQL?

  • Ничем
  • jsonb хранится в разобранном бинарном виде и поддерживает индексы, json — текстом
  • json быстрее для запросов
  • jsonb не поддерживает вложенность
jsonb разбирается при вставке, хранит ключи отсортированными и индексируется GIN; json — просто текст.

Что возвращает data ->> 'name'?

  • Значение ключа name как текст
  • JSON-объект
  • Булево значение
  • Ошибку
->> извлекает значение как текст; -> вернул бы JSON-объект/массив.

Какой оператор проверяет вхождение подструктуры в jsonb?

  • =
  • LIKE
  • @>
  • <-
@> — «содержит»: payload @> '{"type":"order"}' истинно, если в документе есть такой ключ со значением.

Какой индекс ускоряет запросы по jsonb в PostgreSQL?

  • B-tree
  • Hash
  • BRIN
  • GIN
GIN индексирует ключи и значения jsonb; B-tree — по конкретному выражению извлечения (payload ->> 'user').
Когда хранить данные в JSON, а когда — в реляционных столбцах?

Реляционные столбцы — для данных с фиксированной структурой, по которым нужны JOIN и ограничения. JSON — для вложенных/меняющихся структур, которые запрашиваются как целое или по отдельным полям без строгих связей.

Как развернуть JSON-массив в строки таблицы?

Через json_array_elements() (PostgreSQL) или json_each() (SQLite): каждая функция возвращает по строке на элемент массива, после чего элементы можно фильтровать и агрегировать.
