Сортировка, DISTINCT, LIMIT

Три инструмента доводят выборку до готового ответа: ORDER BY задаёт порядок, DISTINCT убирает повторы, LIMIT/OFFSET отсекает страницу. Здесь же главный приём постраничной выдачи — keyset-пагинация, которая не замедляется на больших смещениях.

3.1ORDER BY и NULLS

Сортировка задаётся списком выражений с направлением ASC (по возрастанию, по умолчанию) или DESC. Здесь псевдонимы из SELECT уже доступны — ORDER BY выполняется после SELECT в логическом порядке.

SELECT name, price FROM products ORDER BY price DESC;           -- дорогие первыми
SELECT name, price FROM products ORDER BY category, price DESC;  -- по категории, внутри — по цене
SELECT name, price FROM products ORDER BY price DESC LIMIT 5;    -- топ-5 по цене

Где оказывается NULL при сортировке — зависит от СУБД. В PostgreSQL NULL считается «больше» всего: в ASC он в конце, в DESC — в начале. Управлять явно можно NULLS FIRST / NULLS LAST.

SELECT name, city FROM customers ORDER BY city ASC NULLS FIRST;  -- NULL первыми
Порядок не сохраняется Если запрос без ORDER BY «всегда возвращает по порядку вставки» — это совпадение физического хранения. Добавление индекса, конкурентный доступ или смена плана могут изменить порядок. Сортировка — только через ORDER BY.

3.2DISTINCT

SELECT DISTINCT возвращает уникальные комбинации всех выбранных столбцов. Он применяется ко всей строке, а не к одному столбцу.

SELECT DISTINCT city FROM customers;           -- уникальные города (без NULL-ов-дублей)
SELECT DISTINCT city, status FROM ...;         -- уникальные пары

3.3LIMIT, OFFSET и keyset-пагинация

LIMIT n возвращает не больше n строк, OFFSET m пропускает первые m. Классическая пагинация LIMIT 20 OFFSET 40 проста, но на глубоких страницах замедляется: СУБД всё равно читает и отбрасывает первые m строк.

SELECT id, name FROM products ORDER BY id LIMIT 20 OFFSET 40;   -- 3-я страница по 20

Keyset-пагинация — вместо смещения передаём «последний ключ» прошлой страницы и берём строки после него. Она стабильна и быстра при любом номере страницы, но требует сортировки по уникальному ключу.

-- страница 1
SELECT id, name FROM products ORDER BY id LIMIT 20;
-- страница 2: помним последний id = 20
SELECT id, name FROM products WHERE id > 20 ORDER BY id LIMIT 20;
Правило для продакшена Офсетную пагинацию оставьте для маленьких списков и админок. Для лент и больших таблиц проектируйте keyset: сортировка по столбцу с уникальным суффиксом (обычно id) и фильтр >/< по нему.

3.5Самопроверка

Где окажется NULL при ORDER BY city ASC в PostgreSQL?

  • В начале
  • В конце (NULL считается больше всех значений)
  • Зависит от случайности
  • Строки с NULL не попадают в результат
В PostgreSQL NULL больше любого значения: ASC — в конце, DESC — в начале. Управляется NULLS FIRST / NULLS LAST.

Что делает SELECT DISTINCT a, b FROM t?

  • Убирает дубликаты только столбца a
  • Убирает дубликаты только столбца b
  • Убирает дубликаты комбинаций (a, b)
  • Возвращает только строки с уникальным a
DISTINCT применяется ко всей строке результата — уникальными должны быть пары значений.

Почему офсетная пагинация LIMIT 20 OFFSET 1000000 медленная?

  • СУБД читает и отбрасывает миллион строк перед выдачей
  • Она не поддерживается
  • Она возвращает миллион строк
  • OFFSET не может быть больше LIMIT
OFFSET не «перепрыгивает» строки — база должна пройти их, чтобы выбросить. Keyset-пагинация через WHERE id > … использует индекс и не зависит от глубины.
Почему ORDER BY может использовать псевдоним из SELECT, а WHERE — нет?

Логический порядок: FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT. Псевдоним создаётся на шаге SELECT, поэтому виден только начиная с ORDER BY.

Когда DISTINCT можно заменить на GROUP BY?

Когда параллельно нужны агрегаты: SELECT city FROM t GROUP BY city эквивалентно SELECT DISTINCT city FROM t, но GROUP BY позволит добавить COUNT(*) и другие агрегаты. Если агрегаты не нужны — DISTINCT короче.
