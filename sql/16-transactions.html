Транзакции: BEGIN, COMMIT, ROLLBACK

Транзакция объединяет несколько операций в одну атомарную единицу: либо все изменения применяются, либо ни одно. Это защищает данные от частичного состояния — когда из двух связанных UPDATE выполнился только один. Понимание транзакций отделяет надёжный код от кода, который «иногда портит данные».

16.1ACID

A — Атомарность

Либо все операции транзакции применяются, либо ни одна. Нет «наполовину выполненной» транзакции.

C — Согласованность

Транзакция переводит базу из одного согласованного состояния в другое (соблюдая ограничения).

I — Изоляция

Параллельные транзакции не видят «сырые» промежуточные состояния друг друга.

D — Долговечность

После COMMIT данные переживают сбой (журнал предзаписи, тема 10 соседнего пособия).

16.2BEGIN, COMMIT, ROLLBACK

BEGIN;

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

-- если всё хорошо:
COMMIT;

-- если что-то пошло не так:
-- ROLLBACK;
Без транзакции Если первый UPDATE выполнится, а второй упадёт с ошибкой, деньги «испарятся»: у одного сняли, другому не начислили. Транзакция гарантирует, что такого не случится — ошибка откатит всё.
Неявные транзакции Одиночный INSERT/UPDATE/DELETE вне явной транзакции всё равно выполняется в своей (автоматической) транзакции. Явные BEGIN…COMMIT нужны, когда операций несколько и они должны быть атомарны.

16.3SAVEPOINT

SAVEPOINT позволяет откатить только часть транзакции, не теряя всё.

BEGIN;
INSERT INTO orders (customer_id, status) VALUES (1, 'new');

SAVEPOINT after_order;
UPDATE products SET price = price * 2;     -- ошиблись

ROLLBACK TO after_order;                   -- откатили только UPDATE
COMMIT;                                    -- вставка заказа сохранилась

16.4Уровни изоляции

Уровень изоляции определяет, какие «аномалии» параллельного доступа допустимы. По умолчанию в PostgreSQL — READ COMMITTED.

УровеньСутьКогда
READ COMMITTEDвидишь только закоммиченные данные (по умолчанию)обычные операции
REPEATABLE READснимок данных стабилен на всю транзакциюотчёты, несколько согласованных чтений
SERIALIZABLEполная изоляция, как последовательное выполнениестрогие инварианты (например, бронирование)
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM orders;      -- все последующие SELECT видят один и тот же снимок
COMMIT;
Глубже — в соседнем пособии Аномалии (потерянное обновление, фантомное чтение, write skew), MVCC и блокировки подробно разобраны в темах 11–13 пособия «Реляционные базы данных изнутри».

16.5Пессимистичные и оптимистичные блокировки

Когда несколько транзакций меняют одни и те же данные, есть два подхода к защите от конфликтов: блокировать заранее или проверять в момент записи.

Пессимистичная блокировка

Предполагаем, что конфликт случится, и заранее блокируем строки (SELECT … FOR UPDATE). Другие транзакции ждут. Гарантия сильная, рассуждать просто, но блокировки удерживаются дольше и создают конкуренцию.

Оптимистичная блокировка

Предполагаем, что конфликт редок, и ничего не блокируем, а в момент UPDATE проверяем, не изменилась ли строка (по полю version или updated_at). Изменилась — повторяем или откатываем. Блокировок нет, но нужна логика повтора.

-- оптимистичная блокировка по версии: обновляем только если версия не изменилась
UPDATE products SET price = 950, version = version + 1
WHERE id = 1 AND version = 5;
-- вернуло 0 строк? значит, строку уже изменили — прочитайте заново и повторите
Что выбрать Оптимистичная — для редких конфликтов и длинных операций (форма, редактирование в UI), пессимистичная — когда конфликты вероятны или операция короткая и критична (перевод денег, списание остатков). В JPA/Hibernate оптимистичная — @Version, пессимистичная — @Lock(PESSIMISTIC_WRITE).

16.6Блокировки строк: FOR UPDATE, FOR SHARE, SKIP LOCKED

В PostgreSQL строка блокируется на уровне строки через SELECT … FOR …. Разные режимы блокируют разное и под разные сценарии.

РежимЧто блокируетТиповой сценарий
FOR UPDATEизменение/удаление строки и другие FOR UPDATEпрочитал-изменил-записал: баланс счёта, остаток на складе
FOR NO KEY UPDATEто же, но не мешает FOR KEY SHARE (вставка дочерних строк по FK)обновить неключевые поля, не блокируя вставку ссылающихся строк
FOR SHAREUPDATE/DELETE, но разрешает другим FOR SHAREзафиксировать строку для чтения: выставить счёт, не дав заказу измениться
FOR KEY SHAREтолько удаление/смену ключаудерживать родителя, пока вставляются дочерние строки
-- пессимистичная блокировка: забрать строку на изменение
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;   -- строка заблокирована до COMMIT
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;

-- SKIP LOCKED: взять первую НЕзаблокированную задачу из очереди
BEGIN;
SELECT * FROM jobs WHERE status = 'new'
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 1;                                    -- другие worker'ы пропустят эту строку
-- … обработать, затем UPDATE jobs SET status = 'done'
COMMIT;

-- NOWAIT: не ждать, а сразу получить ошибку, если строка занята
SELECT * FROM orders WHERE id = 105 FOR UPDATE NOWAIT;

-- FOR SHARE: строка не изменится до конца нашей транзакции
BEGIN;
SELECT * FROM orders WHERE id = 101 FOR SHARE;   -- другой UPDATE будет ждать
-- … сформировать счёт на основе неизменных данных
COMMIT;
Сценарии по шаблону FOR UPDATE — read-modify-write; FOR UPDATE SKIP LOCKED — очередь задач, несколько worker'ов без дублей; FOR SHARE — согласованное чтение, пока готовите производные данные; NOWAIT — когда лучше быстро ответить «занято», чем ждать.

16.7Deadlock

Deadlock (взаимная блокировка) возникает, когда две транзакции ждут друг друга; СУБД сама прерывает одну из них.

-- транзакция A:            -- транзакция B:
UPDATE t SET x = 1 WHERE id = 1;   UPDATE t SET x = 2 WHERE id = 2;
UPDATE t SET x = 2 WHERE id = 2;   UPDATE t SET x = 1 WHERE id = 1;  -- deadlock
Правила против deadlock Блокируйте ресурсы всегда в одном и том же порядке и держите транзакции короткими. Повтор при ошибке deadlock — нормальная практика (в Spring это @Retryable).

16.8Практика

Транзакции и блокировки нужно наблюдать на настоящей СУБД — в браузерной SQLite-песочнице параллельные сессии недоступны. Поднимите PostgreSQL и выполните в двух окнах psql:

-- окно 1: пессимистичная блокировка строки
BEGIN;
SELECT * FROM products WHERE id = 1 FOR UPDATE;   -- строка заблокирована, НЕ COMMIT

-- окно 2: попытка изменить ту же строку
UPDATE products SET price = 2 WHERE id = 1;       -- ждёт блокировку окна 1

Затем в окне 1 выполните COMMIT — окно 2 сразу продолжит.

-- окно 1                          -- окно 2
BEGIN;                             BEGIN;
SELECT * FROM jobs                  SELECT * FROM jobs
WHERE status = 'new'               WHERE status = 'new'
ORDER BY id                        ORDER BY id
FOR UPDATE SKIP LOCKED             FOR UPDATE SKIP LOCKED
LIMIT 1;                           LIMIT 1;
-- взяли задачу 1                  -- взяли задачу 2 (не ждали 1)

Оба окна получают разные строки, никто не ждёт — это стандартный паттерн параллельной обработки очереди.

16.9Самопроверка

Что гарантирует атомарность транзакции?

  • Быстрое выполнение
  • Либо все операции применятся, либо ни одна
  • Только одна операция за раз
  • Отсутствие блокировок
Атомарность — «всё или ничего»: частичное состояние невозможно.

Чем ROLLBACK TO savepoint отличается от ROLLBACK?

  • Откатывает только часть транзакции до метки, а не всю
  • Ничем
  • Откатывает другую транзакцию
  • Сохраняет изменения навсегда
SAVEPOINT ставит метку, до которой можно откатиться, сохранив остальное.

Какой уровень изоляции в PostgreSQL по умолчанию?

  • SERIALIZABLE
  • READ UNCOMMITTED
  • READ COMMITTED
  • REPEATABLE READ
По умолчанию READ COMMITTED: транзакция видит только закоммиченные данные.

Что происходит при deadlock?

  • Обе транзакции ждут вечно
  • База перезапускается
  • Одна из транзакций теряет данные
  • СУБД прерывает одну из транзакций
СУБД обнаруживает цикл ожидания и откатывает одну транзакцию, чтобы разблокировать другую.

Что делает SELECT … FOR UPDATE?

  • Блокирует выбранные строки для изменения до конца транзакции
  • Только читает строки без блокировок
  • Удаляет строки
  • Сортирует результат
FOR UPDATE ставит исключительную блокировку строк до COMMIT/ROLLBACK — другие транзакции не могут их изменить.

Зачем нужен SKIP LOCKED?

  • Пропускать уже заблокированные строки — паттерн очереди задач без дублей
  • Ускорять сортировку
  • Пропускать NULL
  • Отменять транзакцию
SKIP LOCKED выбирает только незаблокированные строки, поэтому параллельные worker'ы забирают разные задачи и не ждут друг друга.

Чем оптимистичная блокировка отличается от пессимистичной?

  • Пессимистичная блокирует заранее, оптимистичная проверяет версию при записи
  • Ничем
  • Оптимистичная всегда быстрее
  • Оптимистичная использует FOR UPDATE
Пессимистичная — SELECT FOR UPDATE заранее; оптимистичная — UPDATE … WHERE version = X с повтором при конфликте.
Почему одиночный UPDATE не требует явного BEGIN?

Каждый одиночный оператор выполняется в своей неявной транзакции — СУБД сама оборачивает его. Явные BEGIN…COMMIT нужны, когда атомарными должны быть несколько операторов.

Как избежать deadlock?

Блокировать ресурсы в едином порядке во всех транзакциях, держать транзакции короткими и обрабатывать ошибку deadlock повторным выполнением.
