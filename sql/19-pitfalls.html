Ловушки и антипаттерны SQL

Большинство «непонятных» результатов и медленных запросов происходит из небольшого набора повторяющихся ошибок. Зная их в лицо, вы перестанете наступать на одни и те же грабли и быстрее найдёте чужую ошибку на ревью.

19.1NOT IN с NULL

Классическая ловушка: x NOT IN (подзапрос) возвращает пустоту, если в подзапросе есть NULL (тема 02).

-- ОШИБОЧНО: вернёт пусто, если в городах клиентов есть NULL
SELECT * FROM customers c
WHERE c.city NOT IN (SELECT city FROM customers WHERE id IN (1, 4));   -- подзапрос содержит NULL

-- ПРАВИЛЬНО: NOT EXISTS
SELECT * FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM customers x WHERE x.city = c.city AND x.id IN (1, 4));

19.2SELECT в цикле (N+1)

Выполнять запрос внутри цикла по результатам другого запроса — N+1 обращений вместо одного.

-- ПЛОХО (псевдокод): для каждого клиента — отдельный запрос
for customer in (SELECT id FROM customers):
    SELECT * FROM orders WHERE customer_id = customer.id;

-- ХОРОШО: один JOIN
SELECT c.id, o.* FROM customers c JOIN orders o ON o.customer_id = c.id;

19.3OR против UNION

OR в WHERE может мешать оптимизатору использовать индексы; иногда то же условие через UNION ALL работает быстрее.

-- может не использовать индексы на обоих столбцах
SELECT * FROM t WHERE a = 1 OR b = 2;

-- альтернатива: два поиска по индексам, объединённые
SELECT * FROM t WHERE a = 1
UNION
SELECT * FROM t WHERE b = 2;
Не всегда нужно Современные оптимизаторы часто справляются с OR. Применяйте UNION, когда EXPLAIN показывает плохой план для OR.

19.4Неявные преобразования типов

Сравнение числа со строкой заставляет СУБД приводить типы, что ломает индексы и порождает сюрпризы.

-- ПЛОХО: '1' приводится к числу, индекс по числовому столбцу может не использоваться
SELECT * FROM orders WHERE id = '101';

-- ХОРОШО: явный тип
SELECT * FROM orders WHERE id = 101;

19.5SELECT * и ORDER BY по позиции

-- ПЛОХО: код зависит от порядка столбцов
SELECT * FROM products ORDER BY 3;   -- сортировка по третьему столбцу

-- ХОРОШО: явные столбцы и имена
SELECT id, name, price FROM products ORDER BY price;

19.6Чек-лист ревью запроса

  1. Есть ли WHERE у UPDATE/DELETE? Не заденет ли запрос больше строк, чем нужно?
  2. Нет ли NOT IN с потенциальным NULL? Замените на NOT EXISTS.
  3. Нет ли SELECT * вместо нужных столбцов?
  4. Нет ли запросов в цикле (N+1)?
  5. Нет ли функций/преобразований над индексируемым столбцом в WHERE?
  6. Есть ли ORDER BY, где порядок важен? Есть ли LIMIT на больших выборах?
  7. Не искажаются ли агрегаты размножением строк при JOIN?

19.7Самопроверка

Почему NOT IN опасен?

  • Он медленный
  • При NULL в списке он никогда не истинен
  • Он не поддерживается
  • Он работает только с числами
NOT IN превращается в цепочку x<>… с AND; NULL в списке делает результат пустым. Используйте NOT EXISTS.

Что такое N+1?

  • N+1 запросов для каждой из N строк — запрос в цикле
  • Число индексов
  • Число столбцов
  • Уровень изоляции
Для N строк выполняется ещё по одному запросу; лечится одним JOIN или пакетной выборкой.

Почему сравнение id = '101' (строка с числовым столбцом) — плохо?

  • Это синтаксическая ошибка
  • Оно всегда false
  • Неявное преобразование может сломать использование индекса
  • Оно запрещено стандартом
СУБД приводит строку к числу; из-за преобразования индекс по столбцу может не использоваться.

Что делает запрос с SELECT * и ORDER BY 3?

  • Сортирует по третьему столбцу — хрупко при изменении схемы
  • Сортирует по 3 первым столбцам
  • Возвращает 3 строки
  • Ошибку
ORDER BY по позиции хрупок: при изменении порядка столбцов сортировка незаметно ломается. Именуйте столбцы явно.
Как быстро проверить запрос перед продакшеном?

Прогнать EXPLAIN, проверить WHERE у UPDATE/DELETE, поискать N+1, SELECT *, NOT IN и функции над индексируемыми столбцами, и сверить агрегаты на малых данных.

Когда OR стоит переписывать на UNION?

Когда EXPLAIN показывает, что из-за OR не используются индексы и запрос делает Seq Scan. Тогда два отдельных поиска с UNION могут быть быстрее.
