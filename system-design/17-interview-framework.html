ТЕМА 17 · ПРОЕКТИРОВАНИЕ НА ПРАКТИКЕ

Каркас решения задачи System Design

Предыдущие темы дали кирпичи: балансировщики, базы, кэши, очереди. Задача на собеседовании и в работе — сложить из них систему под конкретные требования и объяснить, почему именно так. У этого процесса есть устойчивая структура. С ней 45 минут превращаются из хаотичного рисования квадратов в последовательное рассуждение, которое интервьюеру легко оценить.

17.1Что на самом деле оценивают

Оценивают

Умение прояснять размытую задачу, структуру рассуждения, знание компромиссов, способность оценить нагрузку и найти узкие места, реакцию на изменение условий, ясность объяснения.

Не оценивают

Знание «правильной» архитектуры (её нет), количество названных технологий, идеальную схему. Решение без названных компромиссов хуже простого решения с честным перечнем его слабых мест.

1. Прояснить требования

Спрашиваю: кто пользователи? Заметки только текст? Нужны ли аккаунты? Редактирование? Срок жизни? Приватные заметки? Поиск?

Фиксирую функциональные: создать заметку (текст до 1 МБ) и получить короткую ссылку; прочитать по ссылке; срок жизни по выбору; без редактирования и поиска.

Нефункциональные: чтение быстрее 200 мс (p99); высокая доступность чтения; созданная заметка не теряется; ссылки нельзя перебрать.

Вне рамок (сказать явно): аналитика, совместное редактирование, модерация.

2. Оценить масштаб

«Пусть 1 млн новых заметок в сутки, читают в 10 раз чаще».

  • Запись: 10⁶ / 10⁵ ≈ 12 в секунду, пик ~50.
  • Чтение: ~120 в секунду, пик ~500.
  • Объём: средняя заметка 10 КБ → 10 ГБ в сутки → 3,6 ТБ в год.
  • Число объектов за 5 лет: ~2 млрд.

Выводы: нагрузка по запросам небольшая — пара серверов. Сложность в объёме текста: тела заметок — в объектное хранилище, метаданные (200 байт × 2 млрд = 400 ГБ) — в базу.

3. Определить API

POST /api/pastes   { "content": "...", "ttl": "7d", "visibility": "unlisted" }
                   → 201 { "id": "aZ3kQ9x", "url": "https://pst.io/aZ3kQ9x", "expiresAt": "..." }
GET  /{id}         → 200 text/plain  |  404  |  410 Gone (истёк срок)
DELETE /api/pastes/{id}   (с токеном удаления, выданным при создании)

API — это контракт: он фиксирует, что система делает, и не даёт расползтись обсуждению.

4. Модель данных и хранилища

pastes(id CHAR(8) PK, object_key, size, created_at, expires_at, delete_token_hash, visibility)
тело заметки → объектное хранилище: s3://pastes/aZ/3k/aZ3kQ9x

Выбор: доступ только по ключу, связей нет → подойдёт и key-value хранилище, и PostgreSQL. Беру PostgreSQL: 400 ГБ метаданных он выдержит, а индекс по expires_at упростит очистку. Называю альтернативу: при росте в 10 раз — DynamoDB/Cassandra с TTL из коробки.

Генерация id: 8 случайных символов base62 = 62⁸ ≈ 2 · 10¹⁴ вариантов: при 2 млрд заметок вероятность угадать существующую — одна из ста тысяч на попытку; коллизию при вставке ловит первичный ключ, тогда повтор.

Проговариваю оба пути. Запись: проверка размера → генерация id → тело в S3 → строка в БД → ответ. Чтение: CDN → (промах) сервис → Redis → (промах) БД + S3 → положить в кэш.

Сначала простая работающая схема, потом усложнение там, где этого требуют цифры.

6. Углубиться в 2–3 места

  • Согласованность записи. Тело в S3 записано, а вставка в БД упала → «сирота» в хранилище. Порядок: сначала S3, потом БД; сироты чистит фоновый процесс по списку объектов. Обратный порядок хуже: ссылка есть, а тела нет.
  • Истечение срока. При чтении проверять expires_at (ленивое удаление) + фоновая очистка пачками по индексу + lifecycle-правило в S3. TTL кэша и CDN не больше оставшегося срока.
  • Горячая заметка (ссылка в популярном посте): CDN и Redis принимают удар; заметки неизменяемы, поэтому кэшировать можно агрессивно.
  • Злоупотребления. Лимит запросов по IP на создание, предельный размер, проверка содержимого асинхронно.

Выбирайте то, что интересно интервьюеру, и то, где вы сильны.

7. Узкие места, отказы, развитие

  • Единые точки отказа: PostgreSQL → реплика с автоматическим переключением; Redis — кэш, его потеря некритична.
  • Что сломается первым при росте в 10 раз: объём метаданных на одном сервере → шардирование по id или переход на key-value хранилище.
  • Наблюдаемость: доля ошибок и p99 чтения, доля попаданий кэша, отставание очистки.
  • Чем пожертвовали: нет редактирования и поиска; чтение может секунды отдавать удалённую заметку из кэша CDN.

17.6Чек-лист перед словом «готово»

  • Оба пути — чтение и запись — прослежены от клиента до хранилища и обратно.
  • Для каждого хранилища названо, почему оно, и что является ключом доступа.
  • Для каждого компонента — что при его отказе; нет необъяснённой единой точки отказа.
  • Названо узкое место и способ его расширить.
  • Обработаны повторы: идемпотентность записи, дубликаты сообщений.
  • Есть слова о безопасности (аутентификация, лимиты) и наблюдаемости (какие метрики покажут проблему).
  • Перечислены компромиссы и то, что осталось за рамками.

17.7Самопроверка

С чего начинать решение задачи «спроектируйте X»?

  • С выбора базы данных
  • С рисования схемы
  • С уточнения требований и масштаба
  • С выбора языка программирования
Без требований нельзя ни выбрать решение, ни оценить его.

Интервьюер спрашивает: «Почему PostgreSQL, а не Cassandra?» Лучший ответ…

  • «PostgreSQL лучше»
  • Через требования: «записей 50 в секунду, данных 400 ГБ, нужен индекс по сроку — это возможности одного сервера; при росте записи в сто раз перешёл бы на wide-column хранилище, потеряв гибкость запросов»
  • «Я с ней работал»
  • «Cassandra устарела»
Выбор обосновывается цифрами и названным компромиссом, с условием, при котором он изменится.

Что делать, если не знаете технологию, о которой спросили?

  • Честно сказать и рассуждать от требований: какими свойствами должен обладать компонент и какие есть классы решений
  • Выдумать ответ
  • Сменить тему
  • Назвать самую популярную технологию
Ценится умение рассуждать о свойствах; названия вторичны.
Перечислите шаги решения задачи System Design.

Требования (функциональные, нефункциональные, вне рамок) → оценка нагрузки и объёмов с выводами → API → модель данных и выбор хранилищ → высокоуровневая схема с путями чтения и записи → углубление в ключевые места → узкие места, отказы, компромиссы, развитие.

Как показать понимание компромиссов?

Для каждого решения назвать альтернативу, ось выбора (согласованность/доступность, чтение/запись, простота/масштаб) и условие, при котором выбрали бы иначе. В конце перечислить слабые места своей схемы.
