Аутентификация и авторизация

Два вопроса, которые система задаёт каждому запросу: «кто ты?» и «что тебе можно?». Глава разбирает модели прав доступа, устройство JWT и то, как OAuth 2.0 позволяет приложению действовать от имени пользователя, не зная его пароля.

5.1Аутентификация и авторизация#23

Аутентификация (authentication, AuthN) проверяет личность: пароль, одноразовый код, биометрия. Авторизация (authorization, AuthZ) решает, разрешено ли этой личности конкретное действие над конкретным ресурсом. Первая происходит при входе, вторая — при каждом обращении.

Модели авторизации

МодельКак принимается решениеСильная сторонаСлабая сторона
RBAC
Role-Based		Права назначены ролям, роли — пользователямПросто понять и проверить; подходит большинству систем«Взрыв ролей», когда нужны условия вроде «только свои заказы»
ABAC
Attribute-Based		Правило над атрибутами пользователя, ресурса, действия и окруженияТонкие условия: отдел, время, владелец, суммаСложнее писать, тестировать и объяснять

На практике комбинируют: RBAC для грубого деления (админ / оператор / клиент) плюс проверка владения ресурсом в коде или через политику. В Spring Security это @PreAuthorize("hasRole('ADMIN') or #order.ownerId == authentication.name").

Самая частая уязвимость API — не в аутентификации Первое место в OWASP API Security Top 10 — Broken Object Level Authorization: сервис проверил токен, но не проверил, что /orders/123 принадлежит именно этому пользователю. Валидный токен отвечает на вопрос «кто», но не на вопрос «можно ли к этому объекту». Проверка владения нужна в каждом эндпоинте с идентификатором в пути.
  • Пароли хранят только в виде медленного хэша с солью: bcrypt, scrypt, argon2. Не SHA-256 — он слишком быстрый для перебора.
  • Эндпоинты входа — первая цель перебора: на них обязателен rate limiting (тема 04).
  • Сообщения об ошибках не должны различать «нет такого пользователя» и «неверный пароль».

5.2JWT#24

JSON Web Token — компактный токен из трёх частей, разделённых точками: header.payload.signature. Сервер, получив токен, проверяет подпись и доверяет содержимому, не обращаясь к хранилищу сессий. Отсюда главное достоинство — отсутствие состояния на сервере — и главный недостаток: выданный токен трудно отозвать.

ClaimСмыслПроверять?
issКто выдал токенДа — совпадает с ожидаемым сервером авторизации
subСубъект — идентификатор пользователяИспользовать как идентификатор
audДля кого предназначенДа — токен для другого сервиса нужно отклонить
exp / nbf / iatИстекает / не раньше / выданДа, с небольшим допуском на расхождение часов
jtiУникальный идентификатор токенаНужен для списка отозванных
Что важно понимать сверх конспекта
  • Payload закодирован, а не зашифрован. Base64url читает любой, у кого есть токен. В payload не кладут секреты и персональные данные. (Шифрованный вариант — JWE — существует, но используется редко.)
  • HS256 или RS256. HS256 — один общий секрет: кто умеет проверять, тот умеет и выпускать, поэтому годится только внутри одного сервиса. RS256/ES256 — приватный ключ только у сервера авторизации, остальные проверяют публичным (берут его по адресу JWKS). В микросервисах — всегда асимметричная подпись.
  • Алгоритм фиксируют на стороне проверяющего. Нельзя доверять полю alg из самого токена: атаки alg: none и подмена RS256 на HS256 (публичный ключ как HMAC-секрет) основаны именно на этом.
  • Отзыв. Варианты: короткий срок жизни access-токена (5–15 минут) + refresh-токен с ротацией; чёрный список по jti в Redis с TTL до истечения токена; версия токена в профиле пользователя. Любой из них возвращает часть состояния на сервер — «stateless» всегда компромисс.
  • Где хранить в браузере. localStorage доступен любому скрипту на странице (XSS крадёт токен). Cookie с флагами HttpOnly; Secure; SameSite недоступна JavaScript, но требует защиты от CSRF.

5.3OAuth 2.0#25

OAuth 2.0 — фреймворк делегированной авторизации: пользователь разрешает приложению ограниченный доступ к своим данным на другом сервисе, не сообщая приложению пароль. Конспект подчёркивает главное: OAuth 2.0 сам по себе не протокол аутентификации.

Четыре роли

РольКто этоПример «Войти через Google»
Resource OwnerВладелец данныхВы
ClientПриложение, которому нужен доступСайт, на который вы входите
Authorization ServerАутентифицирует владельца, спрашивает согласие, выдаёт токеныaccounts.google.com
Resource ServerХранит данные, принимает access-токенAPI профиля Google

Поток Authorization Code

  1. Клиент перенаправляет браузер на сервер авторизации, указывая запрашиваемые права (scope).
  2. Пользователь входит и даёт согласие — на стороне сервера авторизации; клиент пароль не видит.
  3. Сервер авторизации возвращает браузер к клиенту с одноразовым кодом авторизации.
  4. Клиент по защищённому каналу «сервер–сервер» обменивает код на access token (и refresh token).
  5. Клиент обращается к API с access-токеном; сервер ресурсов проверяет токен и отдаёт данные.

Зачем промежуточный код, а не сразу токен? Код проходит через браузер (URL, история, логи), а токен — нет: он выдаётся только в обмен на код в прямом запросе, где клиент подтверждает свою подлинность.

Access tokenRefresh token
Срок жизниМинутыДни, недели
Куда отправляетсяНа сервер ресурсов с каждым запросомТолько на сервер авторизации
Если украденУщерб ограничен коротким сроком и scopeСерьёзно — поэтому ротация: каждый refresh выдаёт новый, старый гасится
Конспект частично устарел: OAuth 2.1
  • PKCE обязателен. Клиент создаёт случайный code_verifier, отправляет его хэш в первом запросе и сам verifier — при обмене кода. Перехваченный код бесполезен без verifier. Сначала PKCE придумали для мобильных приложений и SPA, которые не могут хранить секрет клиента; сейчас он рекомендован всем.
  • Implicit grant и Password grant исключены. Конспект называет Implicit «legacy» — точнее сказать «запрещён»: токен в URL-фрагменте утекает. Для SPA сейчас — Authorization Code + PKCE, часто через серверный компонент (BFF), чтобы токены вообще не попадали в браузер. Password grant требовал отдавать пароль клиенту — то, от чего OAuth и должен избавлять.
  • Параметр state в первом запросе защищает от CSRF: клиент проверяет, что вернулся тот же случайный токен.
  • Client Credentials остаётся основным способом для взаимодействия «сервис–сервис», где пользователя нет.
OAuth 2.0 и OpenID Connect Access-токен говорит «предъявителю можно читать профиль», но не говорит, кто вошёл и когда. Использовать его как доказательство личности — ошибка. OIDC — слой поверх OAuth 2.0, добавляющий ID Token (JWT с данными о пользователе и факте аутентификации), эндпоинт /userinfo и стандартные scope (openid, profile, email). «Войти через Google» — это OIDC. В Spring Security: oauth2Login() для входа, oauth2ResourceServer().jwt() для проверки токенов в API.

5.4Интерактив: что внутри JWT

Инспектор токена

Вставьте JWT или возьмите пример. Разбор выполняется в браузере — токен никуда не отправляется. Не вставляйте боевые токены в онлайн-инструменты: они дают доступ.

5.5Самопроверка

Зашифровано ли содержимое обычного JWT (JWS)?

  • Да, ключом сервера
  • Да, открытым ключом клиента
  • Нет: оно закодировано Base64URL и подписано — подпись защищает от изменения, но не от чтения
  • Зависит от алгоритма подписи
Шифрованный вариант — JWE, он встречается редко. В JWT нельзя класть секреты.

Главная сложность stateless-токенов?

  • Они медленные
  • Отзыв: выданный токен действует до exp, сервер не хранит состояния, чтобы его отменить
  • Их нельзя передавать по HTTPS
  • Они не поддерживают роли
Решения: короткий срок жизни + refresh-токен, список отозванных jti, версия токена у пользователя.

Зачем в OAuth 2.0 Authorization Code Flow нужен PKCE?

  • Чтобы перехваченный код авторизации нельзя было обменять на токен без секрета, известного только начавшему процесс клиенту
  • Для шифрования токена
  • Для ускорения входа
  • Чтобы не использовать HTTPS
Клиент отправляет хэш случайной строки при старте и саму строку при обмене кода. Обязателен для публичных клиентов (SPA, мобильные), рекомендован для всех.
Когда вернуть 401, а когда 403?

401 — личность не установлена: токена нет, он просрочен или подпись неверна; клиенту нужно аутентифицироваться заново. 403 — личность установлена, но прав на действие нет; повторная аутентификация не поможет.

Можно ли положить в JWT номер паспорта пользователя, раз токен подписан?

Нет. Подпись защищает от изменения, а не от чтения: payload — это Base64url, его декодирует кто угодно. Токены попадают в логи, заголовки, прокси. В payload — только идентификаторы и права.

Пользователь нажал «Выйти со всех устройств». Как это реализовать с JWT?

Сам токен отозвать нельзя — он действителен до exp. Варианты: удалить все refresh-токены пользователя (доступ закончится, когда истечёт короткий access-токен); вести чёрный список jti в Redis; хранить у пользователя «версию токенов» или время, раньше которого токены недействительны, и сверять при проверке. Для мгновенного выхода нужна проверка на стороне сервера при каждом запросе.

Зачем в Authorization Code нужен обмен кода на токен, если можно сразу вернуть токен?

Чтобы токен никогда не проходил через браузер. Редирект с кодом виден в адресной строке, истории и логах; код одноразовый, живёт секунды и бесполезен без секрета клиента или PKCE-verifier. Токен выдаётся в прямом запросе клиента к серверу авторизации.

Чем OIDC отличается от OAuth 2.0?

OAuth 2.0 — про доступ к ресурсам (авторизация): результат — access-токен для API. OIDC — про личность (аутентификация): добавляет ID Token в формате JWT с claims о пользователе и о самом входе (sub, iss, aud, auth_time, nonce), предназначенный для клиента, а не для API.
