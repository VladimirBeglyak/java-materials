Разбор: лента новостей

Лента социальной сети — классическая задача о том, когда делать работу: в момент публикации (разложить пост по лентам подписчиков) или в момент чтения (собрать ленту из постов тех, на кого подписан). Ни один вариант не работает для всех пользователей сразу — и на этом строится всё решение.

19.1Требования и оценка

Функции: опубликовать пост (текст, фото); подписаться; получить ленту — посты тех, на кого подписан, от новых к старым, постранично. Качество: открытие ленты быстрее 200 мс; новый пост появляется у подписчиков за секунды (не мгновенно — итоговая согласованность допустима); лента доступна, даже если что-то сломано.

Оценка: 100 млн активных в сутки; каждый открывает ленту 10 раз → 1 млрд чтений ленты в сутки ≈ 12 000 в секунду (пик 40 000); публикует 0,5 поста → 50 млн постов в сутки ≈ 600 в секунду. В среднем 200 подписчиков, но распределение с тяжёлым хвостом: у единиц — десятки миллионов.

19.2Два способа собрать ленту

Fan-out on read («вытягивание»)

При открытии ленты: взять список подписок (200 авторов) → запросить последние посты каждого → слить и отсортировать.

+ публикация мгновенна и дёшева; нет лишней работы для неактивных пользователей.
− чтение дорогое: сотни запросов и слияние на каждое открытие ленты — а чтений в 20 раз больше, чем записей.

Fan-out on write («проталкивание»)

При публикации: взять список подписчиков автора → дописать id поста в готовую ленту каждого (список в Redis).

+ чтение — один запрос готового списка, миллисекунды.
− публикация автора с 50 млн подписчиков — 50 млн записей; работа делается и для тех, кто никогда не откроет ленту.

Калькулятор: сколько стоит каждый способ

19.5Пагинация: курсор, а не offset

GET /feed?offset=40&limit=20
# пока пользователь читал первую страницу, появилось 3 новых поста → вся лента сдвинулась:
# на второй странице он снова увидит 3 поста с первой. А OFFSET 100000 заставит базу пройти 100 000 строк.
GET /feed?limit=20                       → { "items": […], "next": "eyJ0IjoxNzYwMDg…" }
GET /feed?limit=20&cursor=eyJ0IjoxNzYwMDg…  → посты СТАРШЕ позиции курсора (время + id последнего показанного)
# запрос: WHERE (created_at, id) < (:t, :id) ORDER BY created_at DESC, id DESC LIMIT 20 — по индексу, за постоянное время

Курсор непрозрачен для клиента (закодированная пара «время, id»): можно менять внутреннее устройство, не ломая API. Новые посты сверху подгружаются отдельным запросом «новее чем».

19.6Ранжирование и отказоустойчивость

Ранжированная лента

Вместо хронологии — оценка релевантности. Схема та же, но в два этапа: дешёвый отбор кандидатов (несколько сотен свежих постов из push и pull) и дорогое ранжирование моделью. Результат кэшируется на минуты.

Деградация

Упал кэш лент — собрать ленту вытягиванием для активных, остальным показать популярное. Отстали воркеры fan-out — лента запаздывает, но открывается. Недоступен сервис ранжирования — отдать хронологическую. Лента должна открыться всегда.

19.7Самопроверка

Почему fan-out on write не подходит для автора с 50 млн подписчиков?

  • Redis не хранит столько ключей
  • Посты звёзд длиннее
  • Один пост порождает десятки миллионов записей: долго, дорого и в основном впустую
  • У звёзд нет ленты
Их посты подмешивают при чтении: авторов мало, посты кэшируются.

Почему в ленте хранят идентификаторы постов, а не сами посты?

  • Так медленнее читать
  • Пост существует в одном экземпляре: изменение и удаление не требуют обхода миллионов лент, а память экономится на порядки
  • Redis не умеет хранить текст
  • Так требует CDN
Тела достаются одной пакетной операцией из кэша постов.

Чем курсорная пагинация лучше offset для ленты?

  • Стабильна при появлении новых элементов и не замедляется на глубоких страницах
  • Позволяет перейти на произвольную страницу
  • Не требует индекса
  • Ничем
Цена — нельзя прыгнуть на «страницу 57», но в ленте это и не нужно.
Опишите гибридную модель построения ленты.

Обычные авторы — fan-out on write: при публикации id поста асинхронно дописывается в кэшированные ленты активных подписчиков. Авторы с огромной аудиторией — fan-out on read: их посты подмешиваются при запросе ленты. Чтение: готовый список id + посты звёзд → слияние → загрузка тел пачкой → фильтрация.

Что произойдёт при потере кэша лент и как восстановиться?

Кэш — производные данные: источник истины — посты и граф подписок. Ленту пересобирают вытягиванием при первом обращении (ленивое восстановление) и прогревают фоном для самых активных. На время восстановления — ограничение нагрузки и упрощённая лента.
