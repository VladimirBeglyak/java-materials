Распределённый SQL и NewSQL

Можно ли получить SQL и ACID-транзакции, но масштабировать запись горизонтально и пережить потерю целого региона без потери данных? Да — Spanner, CockroachDB, YugabyteDB, TiDB делают именно это, а Citus и Vitess шардируют PostgreSQL и MySQL. Цена — физика: каждая запись проходит консенсус по сети. Разбираем устройство (диапазоны, Raft, распределённые транзакции), задержки в мультирегионе, особенности схемы и когда это оправдано.

Каждый диапазон — группа Raft из 3–5 репликлидер (leaseholder) принимает запись, она считается зафиксированной после записи большинством; при падении — новый лидер за секунды
↓

Диапазоны автоматически делятся при росте и переносятся между узлами для баланса — шардинг прозрачен для приложения. Транзакция, затрагивающая несколько диапазонов, использует двухфазную фиксацию поверх Raft и MVCC с отметками времени (TrueTime с атомными часами в Spanner, гибридные логические часы в CockroachDB/YugabyteDB).

SQL-узел определяет диапазон ключа и отправляет запись его лидеру.

Лидер добавляет запись в журнал и параллельно отправляет репликам.

Как только большинство (лидер + одна реплика) записало — запись зафиксирована. Медленная или упавшая зона C не задерживает ответ.

При потере зоны оставшиеся две выбирают нового лидера; всё подтверждённое есть у большинства — RPO = 0. Ценой одной сетевой задержки до ближайшей реплики на каждую запись.

14.3Физика мультирегиона

Задержка записи в зависимости от размещения реплик

Приёмы: regional by row — у строки есть регион, и её лидер живёт там же (пользователи Европы пишут быстро в Европе); global tables — справочники, которые читаются отовсюду быстро, а пишутся медленно; follower reads — чтение слегка устаревших данных с ближайшей реплики.

14.4Особенности схемы

  • Последовательные ключи создают горячую точку: все вставки идут в последний диапазон на одном лидере. Используйте UUID (случайные здесь — правильно!) или hash-sharded индексы.
  • Совместное размещение: дочерние строки рядом с родителем (interleaving в Spanner, colocation в YugabyteDB, распределённые таблицы по tenant_id в Citus) — JOIN и транзакции внутри одного диапазона/узла.
  • Транзакции дороже и чаще прерываются конфликтами: обязательны повторы (SERIALIZABLE по умолчанию в CockroachDB).
  • Совместимость с PostgreSQL/MySQL — по протоколу и большей части SQL, но не по всем расширениям, триггерам и поведению планировщика. Проверяйте ORM и миграции.

14.6Когда оправдано

Да

  • Запись и данные выросли за пределы одного сервера, а SQL и транзакции нужны.
  • Требование RPO = 0 и автоматического переживания потери зоны/региона.
  • Пользователи в разных регионах, требования к размещению данных (резидентность).

Нет

  • Данные и нагрузка помещаются в один PostgreSQL с репликами — так у большинства.
  • Критична задержка каждой операции в единицы миллисекунд при межрегиональном размещении.
  • Нужны специфичные расширения PostgreSQL.

14.7Самопроверка

Почему в CockroachDB/Spanner рекомендуют UUID вместо последовательного bigint для первичного ключа?

  • bigint не поддерживается
  • UUID короче
  • Последовательные ключи направляют все вставки в последний диапазон — горячая точка на одном узле
  • Для совместимости с JPA
Случайность распределяет запись по диапазонам и узлам.

Реплики в Франкфурте, Вирджинии и Сингапуре. Почему запись медленная?

  • Фиксация требует подтверждения большинства, а ближайшая реплика — за океаном (~90 мс туда-обратно)
  • Неверные индексы
  • Мало памяти
  • Raft пишет на все реплики последовательно
Скорость света не оптимизируется.

Что даёт Citus для мультиарендного SaaS?

  • Отказ от PostgreSQL
  • Автоматический мультирегион
  • Документную модель
  • Распределение таблиц по tenant_id между узлами: запросы одного арендатора локальны, а масштаб — горизонтальный
Совместное размещение данных арендатора — ключ к производительности.
Глобальный сервис платежей: пользователи в ЕС, США и Азии, данные ЕС должны храниться в ЕС. Как бы вы организовали хранение?

Распределённая SQL-база с размещением строк по региону (regional by row / геопартиционирование): строки пользователя и его платежей — с лидером и репликами в его регионе (RPO 0 при потере зоны, быстрые записи), справочники — global tables. Межрегиональные операции редки и допустимо медленнее. Альтернатива — отдельные региональные кластеры PostgreSQL с маршрутизацией по пользователю и асинхронной сводкой для глобальной аналитики.

Чем распределённый SQL отличается от «PostgreSQL + реплики»?

Запись масштабируется горизонтально (каждый диапазон имеет своего лидера на разных узлах), фиксация через консенсус даёт RPO 0 и автоматическое переключение без внешнего оркестратора, данные автоматически перераспределяются. Цена — сетевая задержка на запись, более дорогие транзакции между диапазонами, неполная совместимость, сложнее отладка производительности.
