Движки хранения: B-tree, LSM, колонки

Под любым хранилищем — одна из немногих структур данных на диске. Поняв B-дерево, LSM-дерево и колоночное хранение, вы предскажете, почему Cassandra пишет быстрее PostgreSQL, почему ClickHouse не любит UPDATE, а RocksDB тратит диск на компакции, — и не будете удивляться в продакшене.

2.1Три усиления: нельзя оптимизировать всё

Любая структура хранения торгуется между тремя «усилениями» (RUM-гипотеза):

Чтение (Read amp.)

Сколько страниц или файлов прочитать, чтобы найти одну запись.

Запись (Write amp.)

Сколько байт реально пишется на диск на один байт данных (журнал, перезапись страниц, компакции).

Место (Space amp.)

Во сколько раз занятое место больше полезных данных (незаполненные страницы, старые версии, дубликаты до компакции).

Улучшение двух неизбежно ухудшает третье. Выбор движка — это выбор, какое усиление вы готовы терпеть.

2.2B-tree: обновление на месте

Данные и индексы — в страницах фиксированного размера, упорядоченных в дерево (подробно — в пособии по реляционным БД). Запись: найти страницу, изменить, записать журнал и позже саму страницу.

  • Чтение: отлично — 3–4 страницы, верхние уровни в памяти; диапазоны — последовательно по листьям.
  • Запись: каждое изменение — случайная запись страницы (8–16 КБ ради одной строки) + журнал; при случайных ключах — разделения страниц.
  • Место: страницы заполнены на 50–90%.

Где: PostgreSQL, MySQL InnoDB, Oracle, SQL Server, MongoDB WiredTiger (B-tree с элементами LSM), большинство OLTP-баз.

2.3LSM-tree: только дописывать

Log-Structured Merge-tree превращает любую запись в последовательную: новые записи копятся в памяти (memtable) и журнале, затем сбрасываются на диск неизменяемыми отсортированными файлами (SSTable). Файлы периодически сливаются (компакция). Удаление — запись-«надгробие» (tombstone).

2.4Строки против колонок

Строковое хранение кладёт все поля записи рядом: идеально «достать заказ целиком». Колоночное — все значения одного столбца рядом: идеально «посчитать сумму по одному столбцу у миллиарда строк». Плюс соседние значения одного типа отлично сжимаются (словари, RLE, дельты) и обрабатываются векторно (SIMD).

2.5В памяти и гибриды

  • In-memory (Redis, Memcached, Tarantool, VoltDB): структуры данных целиком в ОЗУ, долговечность — снимками и журналом. Микросекунды, но объём ограничен памятью и стоимостью.
  • HTAP (TiDB с TiFlash, SingleStore, AlloyDB columnar engine): строковое хранение для транзакций + колоночная копия для аналитики в одной системе.
  • Hash-индексы на диске (Bitcask): ключи в памяти, значения в журнале — максимально просто для key-value.

2.6Самопроверка

Почему LSM-движки пишут быстрее B-tree?

  • Они не пишут журнал
  • Запись превращается в последовательную: memtable в памяти, затем сброс целого отсортированного файла
  • Они не поддерживают чтение
  • Они хранят данные только в памяти
Цена — компакции в фоне и чтение по нескольким уровням.

Зачем LSM-движку Bloom-фильтры?

  • Для сжатия
  • Для сортировки ключей
  • Для шифрования
  • Чтобы не читать SSTable, в котором ключа точно нет
Фильтр отвечает «точно нет» или «возможно есть».

Почему очередь задач (вставка и быстрое удаление) плохо работает на Cassandra?

  • Удаления оставляют надгробия, и чтение «головы очереди» проходит через тысячи надгробий до компакции
  • Cassandra не умеет удалять
  • Нет индексов
  • Запись слишком медленная
Известный антипаттерн «queue on Cassandra».

Почему колоночная база неудачна для «показать заказ со всеми полями по id»?

  • Она не поддерживает фильтр по id
  • Она не сжимает данные
  • Строку нужно собрать из множества столбцовых файлов, а гранулы чтения рассчитаны на тысячи строк
  • Она хранит только числа
Колонки — для сканов и агрегатов, строки — для точечного доступа.
Объясните усиление записи у B-tree и LSM.

B-tree: запись в журнал + перезапись целой страницы (8–16 КБ) ради маленького изменения, полные образы страниц после контрольной точки, разделения страниц. LSM: запись в журнал + сброс memtable + многократная перезапись тех же данных при компакциях между уровнями (в leveled-компакции — порядка 10–30×). LSM выигрывает за счёт последовательности записи и сжатия, но суммарно может писать больше байт.

Как структура хранения влияет на выбор базы для журнала событий на 200 тыс. записей в секунду?

Нужна дешёвая последовательная запись и, вероятно, агрегаты по времени: LSM-подобные или append-only структуры (Kafka для журнала, ClickHouse MergeTree для аналитики, Cassandra для чтения по ключу) подходят лучше B-tree OLTP-базы, где каждая вставка обновляет страницы всех индексов. Удаление старого — через TTL/партиции целиком, а не построчно.
