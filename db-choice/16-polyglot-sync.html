Несколько хранилищ: CDC, outbox, CQRS

Как только рядом с основной базой появляется кэш, поисковый индекс или аналитическое хранилище, возникает главный вопрос: как держать их согласованными? «Записать в обе» не работает. Разбираем, почему двойная запись ломается, паттерны transactional outbox и CDC, CQRS с моделями чтения, идемпотентность и упорядочение, и как жить с задержкой согласования.

16.1Почему двойная запись ломается

Три способа сломать «записать в базу и в поиск»

Корень проблемы: нет общей транзакции между двумя системами (2PC/XA между базой и брокером почти никто не использует — медленно, хрупко, многие системы не поддерживают). Решение — одна запись в одну систему, а распространение изменения — надёжным асинхронным процессом.

16.2Transactional outbox

Outbox: событие в той же транзакции, что и данные
сервис заказов
→
orders + outbox (одна база)
→
ретрансляторpoller или CDC
→
Kafka
→
потребители: поиск, кэш, аналитика

Сервис в одной локальной транзакции меняет данные и вставляет событие в таблицу outbox. Либо оба факта записаны, либо ни одного — атомарность обеспечивает база.

Отдельный процесс забирает новые события: опросом таблицы или, лучше, через CDC (Debezium с Outbox Event Router читает вставки в outbox из WAL — без нагрузки опросами).

События публикуются в Kafka с ключом агрегата (порядок по заказу сохраняется). После подтверждения строки outbox удаляются или помечаются. Падение между публикацией и пометкой — повторная публикация: at-least-once.

Потребители обновляют свои хранилища идемпотентно: учитывают event_id или версию агрегата и пропускают устаревшие события. Новый потребитель может прочитать топик с начала (при достаточной ретенции) или получить начальный снимок.

@Transactional
public Order place(PlaceOrder cmd) {
    Order order = orders.save(Order.from(cmd));
    outbox.save(new OutboxEvent(UUID.randomUUID(), "Order", order.getId(), "OrderPlaced",
                                json(new OrderPlaced(order.getId(), order.getTotal(), order.getVersion()))));
    return order;                     // оба INSERT — в одной транзакции
}
// Spring Modulith: события модулей с Event Publication Registry и externalization в Kafka — готовая реализация идеи

16.3CDC: изменения прямо из журнала базы

Change Data Capture читает журнал базы (WAL PostgreSQL через логическую репликацию, binlog MySQL, oplog/change streams MongoDB) и превращает каждое изменение строки в событие. Debezium — стандартный инструмент (Kafka Connect или Debezium Server).

Эксплуатация CDC Логический слот репликации держит WAL, пока коннектор не прочитал его: остановленный Debezium = растущий диск primary (тема 15 первого пособия). Мониторьте отставание слота, задайте max_slot_wal_keep_size. Начальный снимок больших таблиц — инкрементальный (Debezium incremental snapshots). Изменения схемы таблиц должны быть совместимы с потребителями.

16.4CQRS: отдельные модели записи и чтения

Команды → модель записинормализованная схема в PostgreSQL, инварианты, транзакции
↓ события (outbox/CDC)
Проекции → модели чтенияденормализованные витрины под конкретные экраны и запросы: документ в OpenSearch, ключ в Redis, таблица в ClickHouse, отдельная таблица в той же базе
↓
Запросы читают готовые витриныбыстро, без JOIN, масштабируются независимо
  • CQRS не требует event sourcing и отдельных баз: начать можно с материализованного представления или таблицы-витрины в той же базе.
  • Проекции должны уметь пересобираться с нуля (из событий или из модели записи) — это и лечение ошибок, и миграция.
  • Интерфейс должен учитывать задержку: после команды показывать результат из ответа команды, а не перечитывать витрину.

16.6Самопроверка

Какую проблему решает transactional outbox?

  • Ускоряет запись в базу
  • Атомарно связывает изменение данных и факт публикации события, без распределённой транзакции
  • Гарантирует exactly-once доставку потребителям
  • Заменяет Kafka
Доставка остаётся at-least-once — нужна идемпотентность.

Debezium читает изменения таблицы orders. Чем это хуже outbox для интеграции между командами?

  • Debezium медленнее
  • Debezium теряет события
  • CDC невозможен в PostgreSQL
  • Внутренняя схема таблицы становится публичным контрактом; переименование столбца ломает потребителей
Outbox публикует доменные события с явным контрактом.

Как не допустить, чтобы устаревшее событие перезаписало свежие данные в витрине?

  • Хранить версию агрегата и применять событие, только если его версия больше сохранённой
  • Увеличить число партиций
  • Обрабатывать события параллельно
  • Отключить повторы
Плюс ключ партиции по id агрегата для порядка.

Что из перечисленного верно про CQRS?

  • Требует event sourcing
  • Требует отдельной базы для чтения
  • Модели чтения — производные, их можно пересобрать; начать можно с витрины в той же базе
  • Устраняет eventual consistency
Разделение моделей — идея, а не обязательный набор технологий.
Как добавить нового потребителя (например, поиск), если события публикуются уже год, а ретенция топика — 7 дней?

Начальная загрузка: снимок текущего состояния из базы (Debezium snapshot, выгрузка или отдельный «bootstrap»-топик с компактизацией), затем чтение событий с позиции, соответствующей моменту снимка (или с перекрытием и идемпотентностью). На будущее — компактизированный топик с текущим состоянием агрегатов позволяет любому новому потребителю восстановить состояние.

Сервис должен списать деньги в своей базе и отправить событие в другой сервис. Как сделать надёжно?

Outbox: в одной транзакции списание и запись события в outbox; ретранслятор публикует в брокер; получатель обрабатывает идемпотентно. Для процессов из нескольких сервисов с компенсацией — сага (оркестрация или хореография) поверх тех же механизмов. Никаких HTTP-вызовов другого сервиса внутри транзакции базы.
