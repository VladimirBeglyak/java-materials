Реляционные СУБД как выбор по умолчанию

Почему для большинства приложений первой базой должна быть реляционная, что именно она даёт «бесплатно», как далеко масштабируется один сервер, чем различаются PostgreSQL, MySQL и коммерческие СУБД — и по каким признакам понять, что вы упираетесь в её пределы. Подробности внутреннего устройства — в пособии «Реляционные базы данных изнутри».

3.1Что даёт реляционная база

Гарантии

  • Транзакции между любыми строками и таблицами (ACID).
  • Ограничения: уникальность, внешние ключи, CHECK — инварианты, которые не обойдёт ни один баг в коде.
  • Предсказуемая согласованность: прочитал после коммита — видишь.

Гибкость запросов

  • Произвольные запросы, о которых не думали при проектировании: JOIN, агрегаты, окна.
  • Новый путь доступа — это индекс, а не перепроектирование хранилища.
  • Один язык (SQL) для приложения, аналитиков, поддержки.

Последнее особенно ценно в начале продукта: требования неизвестны, и через полгода появятся отчёты и фильтры, о которых никто не думал. В key-value или wide-column базе каждый новый запрос — новая таблица под него и миграция данных.

3.6Признаки, что вы упираетесь в пределы

  • Запись упёрлась в один primary после оптимизаций, батчей и вертикального роста → шардинг (Citus, Vitess) или распределённый SQL (тема 14).
  • Аналитические запросы мешают OLTP даже на реплике, отчёты идут минутами → колоночная копия (тема 09).
  • Поиск требует релевантности и фасетов на миллионах документов → поисковый движок (тема 07).
  • Поток событий на сотни тысяч в секунду, нужны многие потребители и перечитывание → журнал событий (тема 12).
  • Мультирегиональная запись с низкой задержкой → распределённые базы (темы 06, 14).
  • Горячие ключи с микросекундными требованиями → кэш (тема 04).

3.7Самопроверка

Почему реляционная база — хороший выбор на старте продукта, когда требования меняются?

  • Она быстрее всех других на любой нагрузке
  • Новые запросы решаются индексами и SQL без перепроектирования хранилища
  • Она не требует схемы
  • Она масштабирует запись горизонтально
Гибкость запросов — главное преимущество реляционной модели.

Каталог с разными атрибутами у разных категорий товаров. Что разумно в PostgreSQL?

  • EAV-таблица (entity, attribute, value) для всего
  • По таблице на категорию
  • Только MongoDB
  • Общие поля столбцами + различающиеся атрибуты в jsonb с GIN-индексом
Гибрид даёт ограничения для общих полей и гибкость для остальных.

Что из перечисленного — реальный повод добавить систему рядом с PostgreSQL?

  • Отчёты по миллиардам событий тормозят OLTP даже на реплике
  • В таблице 10 млн строк
  • Хочется гибкой схемы
  • Нужен JOIN трёх таблиц
10 млн строк — маленькая таблица; аналитика по миллиардам — задача колоночных систем.
PostgreSQL или MySQL для нового сервиса — как решить?

Если у команды и платформы нет сильной экспертизы в одном из них — PostgreSQL как более универсальный (типы, индексы, расширения, строгая изоляция). MySQL — если есть опыт, инфраструктура и инструменты (бэкапы, мониторинг, Vitess), или нужен его профиль (кластерный индекс, простая репликация). Различия в типичных OLTP-задачах меньше, чем различия в качестве эксплуатации.

Почему внешние ключи и ограничения важны, если «всё проверяется в коде»?

Кода много (сервисы, миграции, скрипты, ручные правки), он меняется и содержит гонки. Ограничение в базе проверяется атомарно при каждой записи из любого источника. Цена — небольшая стоимость проверки при записи и необходимость индексов на внешних ключах.
