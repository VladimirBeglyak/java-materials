Временные ряды и метрики

Метрики серверов, показания датчиков, котировки, телеметрия приложений: данные приходят непрерывно, почти никогда не меняются, читаются агрегатами по окнам времени, а старые нужны всё реже. Специализированные хранилища временных рядов сжимают такие данные в 10–20 раз и отвечают на «среднее за 5 минут по 1000 серверов за неделю» за миллисекунды. Разбираем модель, кардинальность — главного врага, сжатие, ретенцию и выбор между Prometheus, VictoriaMetrics, TimescaleDB, InfluxDB и ClickHouse.

8.2Кардинальность — главный враг

Каждая уникальная комбинация меток — отдельная серия со своим индексом и буферами в памяти. Метка с неограниченными значениями (user_id, request_id, URL с параметрами) взрывает число серий.

8.3Как сжимаются ряды

Классический алгоритм Gorilla (Facebook, 2015), используемый Prometheus и многими TSDB: время кодируется дельтой от дельты (при регулярном шаге — почти всегда 0, один бит), значения — XOR с предыдущим (похожие числа дают много нулевых битов). В среднем ~1,4 байта на точку вместо 16.

8.4Ретенция и даунсэмплинг

Метрики с шагом 15 с нужны за последние дни; за год достаточно 5-минутных или часовых агрегатов. Типовая схема: сырые данные 15–30 дней → агрегаты (min/max/avg/count/sum, не только среднее!) 1 год → архив в объектном хранилище.

CREATE TABLE metrics (time timestamptz NOT NULL, device_id int, temperature double precision);
SELECT create_hypertable('metrics', by_range('time', INTERVAL '1 day'));   -- автопартиции по времени

CREATE MATERIALIZED VIEW metrics_5m WITH (timescaledb.continuous) AS
SELECT time_bucket('5 minutes', time) AS bucket, device_id,
       avg(temperature) AS avg_t, max(temperature) AS max_t, count(*) AS n
FROM metrics GROUP BY bucket, device_id;
SELECT add_continuous_aggregate_policy('metrics_5m', start_offset => INTERVAL '1 hour',
       end_offset => INTERVAL '5 minutes', schedule_interval => INTERVAL '5 minutes');

ALTER TABLE metrics SET (timescaledb.compress, timescaledb.compress_segmentby = 'device_id');
SELECT add_compression_policy('metrics', INTERVAL '7 days');    -- колоночное сжатие старых чанков
SELECT add_retention_policy('metrics', INTERVAL '30 days');     -- удаление целыми чанками

8.6Самопроверка

Разработчик добавил метку user_id к метрике задержки запросов. Что случится?

  • Дашборды станут подробнее, проблем нет
  • Метрика перестанет собираться
  • Число серий вырастет до миллионов — память и производительность хранилища метрик под угрозой
  • Prometheus автоматически агрегирует по пользователям
Неограниченные значения — в логи и трейсы, не в метки.

Почему при даунсэмплинге хранят не только среднее?

  • Среднее скрывает пики: для алертов и анализа нужны max/min и count/sum для корректной переагрегации
  • Среднее нельзя вычислить
  • Так требует SQL
  • Для сжатия
Среднее от средних неверно без весов (count).

Почему удаление старых точек в TSDB дешёвое?

  • Данные не удаляются никогда
  • Используется DELETE с индексом
  • Точки помечаются надгробиями
  • Данные лежат блоками/чанками по времени, и удаляется блок целиком
Тот же принцип, что DROP PARTITION в реляционных базах.
Метрики, логи и трейсы — одно хранилище или разные?

Исторически разные: метрики — TSDB (Prometheus/VictoriaMetrics), логи — Loki/Elasticsearch, трейсы — Tempo/Jaeger. Сейчас популярны колоночные базы (ClickHouse) как единое хранилище для всех трёх с высокой кардинальностью и SQL. Выбор зависит от объёмов, требований к запросам и экосистемы (Grafana, OpenTelemetry).

Датчики шлют 50 тыс. точек в секунду, нужны графики по датчику и сводки по цеху. Ваш выбор?

Если есть PostgreSQL и нужен SQL с бизнес-данными (датчики, цеха, оборудование) — TimescaleDB: гипертаблица по времени, segmentby device_id, непрерывные агрегаты 1 мин/1 час, сжатие через 7 дней, ретенция сырых данных. Если объёмы растут к миллионам точек в секунду и много аналитики — ClickHouse. Для чисто операционных метрик — VictoriaMetrics.
