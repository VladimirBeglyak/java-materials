Документные базы: MongoDB

Документ — самодостаточный агрегат (заказ со строками, профиль с адресами), который читается и пишется целиком. Документные базы хороши, когда данные естественно группируются в такие агрегаты и важна горизонтальная масштабируемость. Разбираем моделирование «встроить или сослаться», паттерны схемы, индексы и агрегации, гарантии записи и выбор ключа шардирования — и честно сравниваем с jsonb в PostgreSQL.

5.1Модель: документ как агрегат

{
  _id: ObjectId("6650…"),
  number: "A-1001",
  status: "paid",
  createdAt: ISODate("2026-10-01T10:15:00Z"),
  customer: { id: 42, name: "Анна", city: "Минск" },     // копия нужных полей (extended reference)
  items: [
    { sku: "NB-14", name: "Ультрабук 14", qty: 1, price: 120000 },
    { sku: "MS-01", name: "Мышь", qty: 2, price: 2500 }
  ],
  total: 125000,                                          // вычисленное поле (computed pattern)
  delivery: { type: "courier", address: { city: "Минск", street: "…" } }
}

Плюсы

  • Чтение агрегата — одно обращение, без JOIN.
  • Структура в базе совпадает с объектом в коде.
  • Разные документы в коллекции могут иметь разные поля.
  • Встроенные репликация и шардинг.

Минусы

  • Связи между агрегатами — в приложении ($lookup есть, но ограничен и дорог при шардинге).
  • Дублирование данных → обновлять копии.
  • «Без схемы» = схема в коде, и все её версии живут в базе одновременно.
  • Лимит документа 16 МБ; неограниченно растущие массивы — антипаттерн.

5.2Встроить или сослаться

Решение для связи «родитель → дочерние»

Главное правило документного моделирования: проектируйте под запросы. «Что читается вместе — хранится вместе». Это обратное нормализации: вы заранее решаете, какие запросы дешёвые.

5.3Запросы, индексы, агрегации

db.orders.find({ "customer.id": 42, status: "paid" }).sort({ createdAt: -1 }).limit(20)
db.orders.createIndex({ "customer.id": 1, status: 1, createdAt: -1 })   // правило ESR: Equality, Sort, Range
db.orders.createIndex({ "items.sku": 1 })                                // multikey: индекс по элементам массива

// агрегация: выручка по городам за октябрь
db.orders.aggregate([
  { $match: { status: { $in: ["paid", "shipped"] }, createdAt: { $gte: ISODate("2026-10-01") } } },
  { $unwind: "$items" },
  { $group: { _id: "$customer.city", revenue: { $sum: { $multiply: ["$items.qty", "$items.price"] } } } },
  { $sort: { revenue: -1 } }
])
db.orders.find({ … }).explain("executionStats")   // IXSCAN против COLLSCAN, totalDocsExamined

Индексы — B-tree, как в реляционных базах; правила составных индексов те же (равенство, сортировка, диапазон). Схему можно и нужно проверять: $jsonSchema-валидатор коллекции.

5.5Шардинг и ключ шардирования

Оценка ключа шардирования для коллекции заказов

Ключ шардирования определяет, на какой шард попадает документ, и почти не меняется после выбора (с 5.0 есть resharding, но это тяжёлая операция). Ошибку в нём обычно исправляют миграцией данных.

5.7Самопроверка

Пост и его комментарии (до сотен тысяч). Как моделировать?

  • Все комментарии массивом в документе поста
  • Комментарии в отдельной коллекции со ссылкой на пост; в посте — счётчик и последние N
  • Пост внутри каждого комментария
  • Одна коллекция для всего без структуры
Неограниченный массив упирается в 16 МБ и переписывание документа; subset pattern даёт быстрый первый экран.

Почему createdAt — плохой ключ шардирования для потока вставок?

  • Даты нельзя индексировать
  • Низкая кардинальность
  • Он не поддерживает диапазоны
  • Монотонный рост отправляет все вставки в последний чанк на одном шарде
Добавьте ведущее поле с распределением (клиент, тенант) или хэшируйте.

Что гарантирует w: "majority"?

  • Подтверждённая запись сохранена большинством узлов и не откатится при переключении primary
  • Запись на всех узлах
  • Чтение с реплики увидит запись
  • Запись выполнена в транзакции
Чтение с реплик всё равно может быть устаревшим.

«Схема не нужна, MongoDB же schemaless» — что на практике?

  • Схемы действительно нет
  • Схема только в индексах
  • Схема живёт в коде, и в коллекции одновременно лежат документы всех её версий — нужны валидация и стратегия миграций
  • Схему нельзя менять
Используйте $jsonSchema-валидатор и версию схемы в документе.
Как мигрировать структуру документов без простоя?

Добавить в документы поле версии схемы; код читает обе версии (ленивая миграция при чтении/записи); фоновая задача порциями переписывает старые документы; после завершения убрать поддержку старой версии из кода. Это тот же expand/contract, что и в реляционных базах, только без DDL.

Когда документная модель не подходит?

Когда данные сильно связаны и читаются в разных разрезах (многие-ко-многим, отчёты по любым комбинациям), когда важны транзакции и ограничения между сущностями (финансы, учёт), когда агрегат не определяется однозначно (одни и те же данные нужны разным «родителям») — тогда дублирование и ручные JOIN в приложении дороже реляционной модели.
