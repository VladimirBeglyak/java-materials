Встраиваемые базы: SQLite, DuckDB, RocksDB

Не каждой базе нужен сервер. Встраиваемая СУБД — библиотека внутри вашего процесса: нет сети, нет администрирования, данные — файл. SQLite — самая распространённая база в мире (в каждом телефоне и браузере), DuckDB — «SQLite для аналитики», RocksDB — движок внутри десятков распределённых систем. Разбираем, где они уместны, их ограничения и как SQLite выходит на сервер. Песочницы этого курса работают как раз на SQLite в браузере.

15.2SQLite в деталях

  • Один писатель на файл в каждый момент; читателей много. В режиме journal_mode=WAL читатели не блокируют писателя и наоборот.
  • Транзакция на запись — миллисекунды; тысячи транзакций в секунду с synchronous=NORMAL в WAL-режиме, сотни тысяч вставок в секунду пачкой.
  • Типизация «по значению» (type affinity): в столбец INTEGER можно записать строку — используйте STRICT-таблицы (3.37+).
  • Внешние ключи выключены по умолчанию: PRAGMA foreign_keys = ON на каждом соединении.
  • Есть: CTE, оконные функции, JSON, полнотекстовый поиск FTS4 (в новых сборках — FTS5), R-Tree, UPSERT, RETURNING.
PRAGMA journal_mode = WAL;        -- читатели не мешают писателю
PRAGMA synchronous = NORMAL;      -- в WAL: долговечность при сбое приложения, окно потерь при сбое ОС
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;       -- ждать блокировку записи до 5 с вместо мгновенного SQLITE_BUSY
PRAGMA cache_size = -64000;       -- 64 МБ кэша страниц
CREATE TABLE notes (id INTEGER PRIMARY KEY, body TEXT NOT NULL, created_at INTEGER NOT NULL) STRICT;
Песочница: возможности SQLite (это настоящий SQLite 3, скомпилированный в WebAssembly)

15.3SQLite на сервере

Для небольших и средних веб-приложений с одним сервером SQLite — серьёзный вариант: нулевая задержка запросов (функция, а не сеть), простота, дешёвые бэкапы. Ограничения — один узел-писатель и один процесс-владелец файла.

  • Litestream — непрерывная репликация WAL в S3 (восстановление на момент времени).
  • LiteFS, rqlite, Turso/libSQL — реплики для чтения на edge, распределение.
  • Не подходит: много серверов приложения пишут в одну базу; сетевые файловые системы (NFS) — блокировки ненадёжны, возможна порча файла.

15.4DuckDB: аналитика без кластера

try (Connection c = DriverManager.getConnection("jdbc:duckdb:");          // в памяти
     Statement s = c.createStatement()) {
    ResultSet rs = s.executeQuery("""
        SELECT date_trunc('day', ts) AS day, count(*) AS events, approx_count_distinct(user_id) AS users
        FROM read_parquet('/data/events/*.parquet')
        WHERE ts >= DATE '2026-10-01'
        GROUP BY ALL ORDER BY day""");
}

Обрабатывает сотни миллионов строк на одном ноутбуке за секунды, умеет данные больше памяти (выгрузка на диск), читает PostgreSQL напрямую (ATTACH 'postgres:…'). Не для конкурентной записи многими процессами.

15.6Самопроверка

Что даёт journal_mode=WAL в SQLite?

  • Несколько одновременных писателей
  • Читатели не блокируют писателя и писатель не блокирует читателей
  • Репликацию на другой сервер
  • Шифрование файла
Писатель по-прежнему один.

Почему H2 в тестах вместо PostgreSQL — источник проблем?

  • H2 медленнее
  • H2 не поддерживает SQL
  • H2 нельзя запускать в CI
  • Диалект, типы, блокировки и поведение отличаются — тесты проходят, а на проде ошибки; лучше Testcontainers с той же СУБД
Тестируйте на том, что работает в продакшене.

Где RocksDB встречается чаще всего?

  • Как движок хранения внутри других систем (Kafka Streams, CockroachDB, TiKV, Flink)
  • Как основная база веб-приложений с SQL
  • Как кэш браузера
  • Как брокер сообщений
Это библиотека key-value на LSM.
Мобильное приложение заметок с синхронизацией между устройствами — как хранить данные?

Локально — SQLite (Room на Android, GRDB/Core Data на iOS) для офлайн-работы и мгновенного интерфейса; на сервере — основная база (PostgreSQL) как источник истины. Синхронизация — журнал изменений с версиями/отметками времени и разрешением конфликтов (последняя запись, слияние по полям или CRDT). Готовые решения: PowerSync, ElectricSQL, Couchbase Lite.

Когда DuckDB заменит кластер аналитики?

Когда данные анализирует один человек или один пайплайн, объём — до единиц ТБ, а данные лежат в файлах (Parquet в S3) или выгружаются из базы. Один современный сервер с DuckDB обрабатывает удивительно много. Кластер нужен при многих одновременных пользователях, постоянной загрузке данных и общем доступе.
