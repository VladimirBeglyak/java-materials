Сначала весь доступ к данным собирается за одним интерфейсом (репозиторий, сервис), чтобы переключать источник флагом, а не правкой сотни мест.

Запускается непрерывный перенос изменений из старой базы в новую через CDC. Запись в новую — идемпотентная, с версией: старые события не перезаписывают новые.

Параллельно порциями переносятся исторические данные с ограничением нагрузки. Пересечения с потоком изменений разрешаются по версиям.

Приложение читает из обеих баз, отвечает из старой, а расхождения пишет в метрики. Плюс фоновая сверка (количества, контрольные суммы диапазонов). Заодно — нагрузочная проверка новой базы реальным трафиком.

Чтение постепенно переключается на новую базу (1% → 100%). Запись пока идёт в старую — откат мгновенный: вернуть флаг.

Запись переключается на новую базу. Для возможности отката включают обратную синхронизацию в старую на оговорённый срок.

После периода стабильности старая база выводится: финальный бэкап в архив, удаление кода двойного чтения. Длительность всего процесса — недели; простоя — ноль.

Что ломается при переезде чаще всего Различия семантики: регистр и сортировка строк (collation), точность чисел и времени (миллисекунды против микросекунд, часовые пояса), NULL против отсутствующего поля, уникальность, которую раньше обеспечивал индекс, а теперь — никто; автоинкрементные id; поведение транзакций. Составьте список инвариантов и проверяйте их в сверке.

18.5Самопроверка

Главная опасность общей базы между несколькими сервисами?

  • Медленные запросы
  • Нехватка места
  • Сложность бэкапов
  • Схема становится неявным контрактом: изменения одного сервиса ломают другие, независимые релизы невозможны
Интеграция через API и события вместо общих таблиц.

Зачем при миграции «теневые чтения»?

  • Чтобы ускорить старую базу
  • Чтобы сравнивать ответы новой базы со старой на реальном трафике до переключения, без влияния на пользователей
  • Чтобы удалить старые данные
  • Чтобы шифровать данные
Расхождения видны в метриках раньше, чем у пользователей.

Почему запись переключают на новую базу последней?

  • Пока запись идёт в старую базу, откат переключения чтения мгновенный и без потери данных
  • Запись в новую базу невозможна до конца миграции
  • Так требует CDC
  • Порядок не важен
Каждый шаг должен быть обратимым.
Команда хочет переехать с MongoDB на PostgreSQL. С чего начать?

Выяснить причину (транзакции, связи, отчёты, стоимость), спроектировать реляционную схему по реальным запросам (часть данных останется jsonb), собрать доступ к данным за абстракцией, настроить поток изменений (change streams/Debezium) в PostgreSQL с идемпотентной записью, перенести историю, включить теневые чтения и сверку, переключать чтение, затем запись, держать обратную синхронизацию до стабилизации. Отдельно — проверка различий семантики (типы, null/отсутствие поля, точность дат).

Как понять, что выбор хранилища был ошибкой, а не просто нужна оптимизация?

Признаки ошибки модели: основные запросы противоречат модели хранения (JOIN и транзакции в NoSQL, обходы графа в SQL на большую глубину, произвольные фильтры в wide-column), обходные решения в коде множатся, инварианты нарушаются, эксплуатация требует непропорциональных усилий. Признаки нужды в оптимизации: проблема в конкретных запросах, индексах, настройках, и после их исправления модель работает.
