17.3Подробно: мессенджер

-- Cassandra/ScyllaDB
CREATE TABLE messages (
  chat_id uuid, bucket int, message_id timeuuid, sender_id uuid, body text, attachments list<text>,
  PRIMARY KEY ((chat_id, bucket), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
-- bucket = номер «окна» (например, 10 дней) — партиции ограничены по размеру

-- Redis: непрочитанное и присутствие
-- HINCRBY unread:{user} {chat} 1   /  HDEL при прочтении
-- SET presence:{user} gateway-7 EX 60  (продлевается heartbeat-ом)

Путь сообщения: шлюз WebSocket → сервис чатов пишет в Cassandra (QUORUM в локальном ДЦ) → событие в Kafka → доставка онлайн-участникам через их шлюзы (адрес из Redis), офлайн — пуш. Порядок в чате — по timeuuid; дубликаты при повторной отправке отсекаются клиентским id сообщения.

17.4Подробно: платежи

CREATE TABLE accounts (id bigint PRIMARY KEY, currency char(3) NOT NULL, balance numeric(20,2) NOT NULL CHECK (balance >= 0));
CREATE TABLE transfers (id uuid PRIMARY KEY, idempotency_key text UNIQUE NOT NULL, created_at timestamptz NOT NULL DEFAULT now());
CREATE TABLE entries (                     -- неизменяемые проводки; сумма по transfer_id = 0
  transfer_id uuid REFERENCES transfers, account_id bigint REFERENCES accounts, amount numeric(20,2) NOT NULL,
  PRIMARY KEY (transfer_id, account_id)
);
-- перевод: блокировать счета в порядке id (SELECT … ORDER BY id FOR UPDATE), вставить transfer (повтор с тем же
-- idempotency_key → конфликт → вернуть прежний результат), две проводки, обновить балансы, outbox — одна транзакция

17.5Общие закономерности

  • Почти везде есть реляционная база как источник истины; специализированные хранилища — производные и пересобираемые.
  • Связующее звено — outbox/CDC + журнал событий; двойной записи нет нигде.
  • Байты — в объектном хранилище, в базе — метаданные.
  • Аналитика — отдельно от OLTP, как только становится тяжёлой.
  • Специализированное хранилище появляется, когда масштаб или тип запросов этого требует, а не «на вырост».

17.6Самопроверка

Где хранить баланс кошелька в платёжной системе?

  • В Redis — быстро
  • В Cassandra — масштабируемо
  • В реляционной базе (или распределённом SQL) с транзакциями, ограничениями и синхронной репликацией
  • В Kafka как в журнале
Деньги требуют ACID и RPO = 0.

Почему посты знаменитостей не раскладывают по лентам всех подписчиков при публикации?

  • Миллионы записей на один пост — дорого и медленно; их подмешивают при чтении ленты
  • Знаменитостям нельзя публиковать
  • Redis не поддерживает списки
  • Из-за прав доступа
Гибрид fan-out on write/read — классика систем лент.

IoT-проект: зачем Kafka перед хранилищем временных рядов?

  • Kafka хранит агрегаты
  • Буферизует приём при пиках и сбоях хранилища, позволяет нескольким потребителям (запись, алерты) читать один поток
  • Kafka быстрее TSDB в запросах
  • Без Kafka TSDB не принимает данные
Развязка производителей и потребителей.
Спроектируйте хранение для сервиса бронирования отелей.

PostgreSQL: отели, номера, тарифы, бронирования; отсутствие пересечений — EXCLUDE USING gist (room_id WITH =, during WITH &&) или инвентарь по датам с атомарным уменьшением. Поиск по городу/датам/цене/удобствам — OpenSearch с данными о доступности (обновляется событиями, финальная проверка — в PostgreSQL при бронировании). Redis — кэш цен и сессии. Фото — S3 + CDN. Аналитика спроса — ClickHouse.

Как обосновать отказ от «модной» базы на архитектурном ревью?

Показать, что все ключевые запросы и объёмы закрываются текущей базой с запасом (прототип, расчёт), что новая база не даёт нужных гарантий (транзакции, ограничения) или требует перепроектирования под запросы, и оценить стоимость эксплуатации: мониторинг, бэкапы, обновления, дежурства, обучение. Зафиксировать в ADR условия, при которых решение пересматривается (рост до X, новый тип запросов).
