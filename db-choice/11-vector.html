Векторный поиск и RAG

Модели превращают текст, изображения и товары в векторы-эмбеддинги так, что близкие по смыслу объекты оказываются рядом. Найти «похожее» — значит найти ближайшие векторы среди миллионов за миллисекунды. Разбираем меры близости, почему точный поиск не масштабируется, как работают HNSW и квантование, сколько это стоит по памяти, как фильтровать, строить RAG — и когда хватит pgvector, а когда нужна отдельная векторная база.

11.1Эмбеддинги и близость

Эмбеддинг — вектор из сотен–тысяч чисел (384, 768, 1536, 3072 измерения). Мера близости зависит от модели: косинусная (угол между векторами, самая частая для текста), скалярное произведение (для нормированных векторов совпадает с косинусной), евклидово расстояние. 11.2Точный и приближённый поиск

Точный поиск (kNN) сравнивает запрос с каждым вектором: 10 млн × 1536 измерений = 15 млрд умножений на запрос. Индексы приближённого поиска (ANN) жертвуют небольшой долей точности (recall — доля настоящих ближайших соседей в ответе) ради скорости в сотни раз.

HNSW

Многоуровневый граф «малого мира»: верхние уровни — редкие длинные связи, нижний — все векторы с ближайшими соседями. Поиск: жадный спуск сверху вниз, на каждом уровне идём к соседу ближе к запросу. Высокий recall и скорость, но граф в памяти и долгое построение. Параметры: m (связей на узел), ef_construction, ef_search (ширина поиска: больше — точнее и медленнее).

IVF (+PQ)

Векторы кластеризуются (k-means) на списки; запрос сравнивается с центрами и просматривает nprobe ближайших списков. Меньше памяти, быстрое построение, хорошо сочетается с квантованием (PQ) для миллиардов векторов. Recall чувствителен к nprobe и к дрейфу данных (центры устаревают).

11.4pgvector: векторы рядом с данными

CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE chunks (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  doc_id     bigint NOT NULL REFERENCES documents(id),
  tenant_id  bigint NOT NULL,
  content    text NOT NULL,
  embedding  vector(1536) NOT NULL
);
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);

SET hnsw.ef_search = 100;
SET hnsw.iterative_scan = relaxed_order;     -- pgvector 0.8+: дочитывать граф, если фильтр отсёк результаты
SELECT id, content, 1 - (embedding <=> $1) AS similarity
FROM chunks
WHERE tenant_id = $2
ORDER BY embedding <=> $1
LIMIT 8;
Фильтрация — главная сложность ANN Индекс находит 40 ближайших, а фильтр tenant_id = 7 оставляет 0 из них. Варианты: итеративный поиск (pgvector 0.8+), фильтрация внутри обхода графа (Qdrant, Weaviate — payload-индексы), отдельные индексы или партиции на крупных арендаторов, частичные индексы. Проверяйте recall на реальных фильтрах.

11.5RAG: поиск для языковой модели

Индексациядокументы → разбиение на фрагменты (300–800 токенов с перекрытием) → эмбеддинги → векторное хранилище + метаданные (источник, права, дата)
↓
Запросвопрос → эмбеддинг → гибридный поиск (векторы + BM25) с фильтрами по правам → 20–50 кандидатов
↓
Переранжированиеcross-encoder/reranker отбирает 5–10 лучших фрагментов
↓
ГенерацияLLM отвечает по найденным фрагментам со ссылками на источники
  • Качество RAG чаще определяется разбиением, метаданными и гибридным поиском, чем выбором векторной базы.
  • Смена модели эмбеддингов = пересчёт всех векторов (храните версию модели рядом с вектором).
  • Права доступа — фильтром при поиске, а не после генерации.

11.7Самопроверка

Что такое recall в ANN-поиске?

  • Скорость ответа
  • Доля настоящих k ближайших соседей, найденных индексом
  • Размер индекса
  • Число запросов в секунду
ANN жертвует частью recall ради скорости; ef_search/nprobe регулируют баланс.

Векторный поиск с фильтром по арендатору возвращает слишком мало результатов. Причина?

  • Неверная метрика
  • Мало измерений
  • Нужно больше реплик
  • Индекс нашёл ближайших среди всех, а фильтр отбросил большинство — нужен итеративный поиск или фильтрация внутри обхода
Post-filtering — частая ловушка.

Что произойдёт при смене модели эмбеддингов?

  • Нужно пересчитать все векторы: пространства разных моделей несовместимы
  • Ничего, векторы совместимы
  • Достаточно перестроить индекс
  • Нужно изменить только метрику
Храните версию модели и планируйте переиндексацию.

Почему гибридный поиск часто лучше чисто векторного?

  • Он дешевле
  • Он не требует индексов
  • Векторы плохо находят точные идентификаторы и редкие термины, а BM25 — перефразирования; вместе они дополняют друг друга
  • Он всегда возвращает больше результатов
Результаты объединяют, например, через RRF.
Как оценить качество векторного поиска перед продакшеном?

Собрать набор запросов с размеченными релевантными документами; измерить recall@k индекса относительно точного поиска и метрики качества выдачи (nDCG, MRR) для всей цепочки; подобрать параметры (ef_search, m, квантование) по компромиссу recall/задержка; проверить на реальных фильтрах и арендаторах; мониторить качество после изменений модели и данных.

pgvector или Qdrant для поиска по базе знаний компании на 2 млн фрагментов?

pgvector: объём небольшой (2 млн × 1536 × 4 байта ≈ 12 ГБ + граф), данные и права доступа уже в PostgreSQL, фильтры SQL, транзакционное обновление. Qdrant стоит рассматривать при росте до сотен миллионов, при сложной фильтрации на большом масштабе или если команда хочет отдельный сервис поиска.
