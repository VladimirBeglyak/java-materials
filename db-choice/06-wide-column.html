Wide-column: Cassandra, ScyllaDB, DynamoDB

Базы для огромной записи и предсказуемого чтения по ключу на любом масштабе и в нескольких регионах — без единой точки отказа. Цена — запросы проектируются заранее: таблица под каждый запрос, никаких JOIN и произвольных фильтров. Разбираем модель «ключ партиции + ключ кластеризации», кольцо и репликацию, настраиваемую согласованность, DynamoDB и single-table design, и где эти базы ломаются.

6.1Модель данных

Таблица — это распределённая отсортированная карта: ключ партиции определяет узлы, где лежат данные; внутри партиции строки отсортированы по ключу кластеризации. Эффективные запросы — только «одна партиция, диапазон по кластерному ключу».

CREATE TABLE messages_by_chat (
  chat_id    uuid,
  bucket     text,          -- месяц: '2026-10' — ограничивает размер партиции
  sent_at    timeuuid,
  author_id  uuid,
  body       text,
  PRIMARY KEY ((chat_id, bucket), sent_at)     -- ((ключ партиции), ключ кластеризации)
) WITH CLUSTERING ORDER BY (sent_at DESC)
  AND default_time_to_live = 31536000;          -- TTL год

-- эффективно: одна партиция, срез по порядку
SELECT * FROM messages_by_chat WHERE chat_id = ? AND bucket = '2026-10' LIMIT 50;

-- невозможно без ALLOW FILTERING (= полный просмотр кластера):
SELECT * FROM messages_by_chat WHERE author_id = ?;

6.2Проектирование от запросов

В реляционной модели сначала данные, потом запросы. Здесь наоборот: для каждого запроса — своя таблица, данные дублируются при записи (запись дешёвая).

Запрос приложенияТаблицаPRIMARY KEY
Сообщения чата, новые сверхуmessages_by_chat((chat_id, bucket), sent_at)
Чаты пользователя по последней активностиchats_by_user((user_id), last_activity, chat_id)
Сообщения автора (для модерации)messages_by_author((author_id, bucket), sent_at)

Одна отправка сообщения = запись в три таблицы (logged batch для атомарности по нескольким партициям, или асинхронно). Изменение запроса = новая таблица + перенос данных.

6.3Кольцо, репликация и кворумы

Узлы равноправны и образуют кольцо токенов: хэш ключа партиции (Murmur3) определяет первый узел, следующие RF−1 узлов по кольцу (с учётом стоек и дата-центров) хранят реплики. Любой узел может принять запрос и стать координатором.

Калькулятор кворумов: N реплик, W подтверждений записи, R ответов на чтение
«Последняя запись побеждает» Конфликтующие записи в одну ячейку разрешаются по отметке времени клиента/координатора — без транзакций и без ошибки. Расхождение часов или параллельные «прочитать-изменить-записать» тихо теряют обновления. Для условных операций есть lightweight transactions (IF NOT EXISTS, IF balance = ?) на Paxos — в разы медленнее; в новых версиях — Accord-транзакции (Cassandra 5+).

6.4Размер партиции и антипаттерны

Не разрастётся ли партиция
  • Горячая партиция: популярный ключ (знаменитость, глобальный счётчик) — все запросы на 3 узла. Решение — шардирование ключа (user_id + bucket, counter_id + shard 0..N).
  • Надгробия: удаления и TTL оставляют tombstones; запрос, проходящий тысячи надгробий, падает (tombstone_failure_threshold). Не используйте таблицу как очередь.
  • ALLOW FILTERING и вторичные индексы — опрос многих узлов; почти всегда признак, что нужна ещё одна таблица.
  • Чтение перед записью — сводит на нет главное преимущество (дешёвую запись).

6.5DynamoDB и single-table design

Управляемое key-value/wide-column хранилище AWS: партиционный ключ (PK) + ключ сортировки (SK), оплата за операции или выделенную ёмкость, почти без эксплуатации. Популярный подход — одна таблица для нескольких типов сущностей с перегруженными ключами:

PKSKДанныеЗапрос
CUSTOMER#42PROFILEимя, emailQuery PK = CUSTOMER#42 → профиль и все заказы одним запросом; SK begins_with ORDER# → только заказы
CUSTOMER#42ORDER#2026-10-01#A1001статус, сумма
CUSTOMER#42ORDER#2026-10-05#A1002статус, сумма
ORDER#A1001ITEM#NB-14кол-во, ценаQuery PK = ORDER#A1001 → позиции

Другие пути доступа — глобальные вторичные индексы (GSI, асинхронные, со своей ёмкостью). Транзакции — TransactWriteItems до 100 элементов. Потоки изменений — DynamoDB Streams. Предел — 1000 WCU/3000 RCU на партицию: горячий ключ троттлится.

6.6Когда выбирать

Подходит

  • Огромная запись: события, сообщения, IoT, история действий.
  • Известные заранее пути доступа по ключу.
  • Активная запись в нескольких регионах, нет единой точки отказа.
  • Линейное масштабирование добавлением узлов.

Не подходит

  • Произвольные запросы, отчёты, JOIN.
  • Транзакции между сущностями, инварианты (деньги, остатки).
  • Небольшие объёмы — кластер из 3+ узлов и эксплуатация не окупаются.
  • Часто меняющиеся требования к запросам.

6.7Самопроверка

RF = 3. Какие уровни дают чтение последней подтверждённой записи?

  • W = ONE, R = ONE
  • W = ONE, R = QUORUM
  • W = QUORUM, R = QUORUM
  • Никакие
2 + 2 > 3: множества реплик пересекаются.

Новый запрос «сообщения по автору» к таблице с ключом ((chat_id, bucket), sent_at). Правильное решение?

  • Новая таблица messages_by_author, заполняемая при записи
  • SELECT … ALLOW FILTERING
  • Вторичный индекс и забыть
  • JOIN с таблицей пользователей
Запрос-ориентированное моделирование: таблица под путь доступа.

Почему в ключ партиции добавляют корзину времени (месяц, сутки)?

  • Чтобы работал TTL
  • Для сортировки
  • Чтобы ускорить запись
  • Чтобы партиция не росла бесконечно и нагрузка распределялась
Неограниченные партиции — главная причина проблем в Cassandra.

Что произойдёт при двух одновременных «прочитать баланс → записать новый» в Cassandra без LWT?

  • Ошибка конфликта
  • Победит запись с большей отметкой времени, другое обновление тихо потеряется
  • Оба применятся
  • Кластер заблокирует строку
Last-write-wins — не место для балансов.
Спроектируйте хранение истории просмотров видео (миллиард событий в день) с запросом «последние 100 просмотров пользователя».

Таблица views_by_user, PRIMARY KEY ((user_id, month), viewed_at DESC, video_id), TTL на срок хранения. Запрос — одна партиция с LIMIT 100 (при необходимости — предыдущий месяц). Запись с consistency ONE/LOCAL_QUORUM, асинхронно. Аналитика по просмотрам — не здесь, а в колоночном хранилище через поток событий.

Cassandra или DynamoDB?

DynamoDB — если вы в AWS и хотите почти ноль эксплуатации, нагрузка умеренная или неравномерная (on-demand), подходит single-table моделирование; минусы — стоимость при большой стабильной нагрузке, привязка к AWS, лимиты на элемент (400 КБ) и партицию. Cassandra/ScyllaDB — своя инфраструктура или мультиоблако, очень большая стабильная нагрузка (дешевле на своём железе), нужен контроль над настройками; минус — эксплуатация кластера (ремонты, компакции, обновления).
