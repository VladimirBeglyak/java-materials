Key-value и кэши: Redis и другие

Самая простая модель — значение по ключу — и самая быстрая: данные в памяти, ответ за микросекунды. Redis (и его форк Valkey) — это не только кэш, но и сервер структур данных: счётчики, множества, рейтинги, очереди, блокировки, ограничение частоты. Разбираем модель, долговечность, кластер, паттерны кэширования и типичные аварии: лавина промахов, горячие ключи, рассинхронизация с базой.

Redis выполняет команды в одном потоке (ввод-вывод многопоточный с версии 6): каждая команда атомарна, а сложные операции — через MULTI/EXEC или Lua-скрипты. Отсюда же главное правило: никаких медленных команд (KEYS *, SMEMBERS на миллион элементов) — они блокируют всех.

4.3Долговечность и масштабирование

Персистентность

  • RDB — периодический снимок (fork + копирование при записи): потеря данных с последнего снимка.
  • AOF — журнал команд, appendfsync everysec: потеря ~1 секунды.
  • Репликация асинхронная: при переключении (Sentinel/Cluster) подтверждённые записи могут пропасть.

Вывод: Redis — хороший источник истины только для данных, потеря которых терпима.

Redis Cluster

  • 16384 слота, ключ → CRC16(key) mod 16384, слоты распределены по мастерам.
  • Многоключевые операции — только в одном слоте: хэш-теги {user42}:cart и {user42}:profile.
  • Клиент знает карту слотов и получает MOVED при перестройке.
Память и вытеснение Задайте maxmemory и политику: для кэша — allkeys-lru или allkeys-lfu; если там же лежат данные без TTL, которые нельзя терять, — volatile-* или, лучше, отдельный инстанс. При политике noeviction заполненный Redis начинает отвечать ошибками на запись.

4.5Аварии кэша и защита

Лавина промахов (cache stampede)
ключ home:feed5000 запросов/с
→
приложение ×20
→
базазапрос 300 мс

Горячий ключ главной страницы читается 5000 раз в секунду, все — попадания.

TTL истёк. Пока первый запрос пересчитывает значение (300 мс), приходят ещё 1500 запросов — все видят промах и тоже идут в базу.

Полторы тысячи одинаковых тяжёлых запросов. База замедляется, пересчёт занимает уже секунды, промахов ещё больше — положительная обратная связь. Падают и другие функции, использующие базу.

Защита: один пересчёт на ключ (блокировка SET NX или single-flight в процессе — остальные ждут или получают старое значение); stale-while-revalidate — хранить значение дольше TTL и обновлять в фоне; вероятностное раннее обновление; разброс TTL (±10%), чтобы тысячи ключей не истекали одновременно; прогрев после деплоя.

  • Горячий ключ — один ключ получает больше, чем может обслужить узел кластера: локальный кэш в процессе (Caffeine) на секунды, реплики чтения, разбиение ключа на N копий.
  • Проникновение кэша — запросы несуществующих ключей всегда идут в базу (перебор id): кэшировать «отсутствие» с коротким TTL, Bloom-фильтр.
  • Рассинхронизация — удалять ключ после коммита (не до), при сомнениях — короткий TTL как страховка; не кэшировать то, что требует строгой согласованности (баланс перед списанием).
  • Большие значения — сотни КБ в одном ключе блокируют поток и сеть: дробить, сжимать, хранить ссылку.
@Cacheable(cacheNames = "product", key = "#id", sync = true)   // sync: один пересчёт на ключ в пределах экземпляра
public ProductDto find(long id) { ... }

@CacheEvict(cacheNames = "product", key = "#cmd.id")           // удалить ключ после успешного обновления
@Transactional
public void update(UpdateProduct cmd) { ... }
// внимание: @CacheEvict срабатывает при выходе из метода — до коммита, если транзакция внешняя;
// надёжнее удалять по событию @TransactionalEventListener(phase = AFTER_COMMIT)

4.6Самопроверка

Почему KEYS * опасна в продакшене?

  • Она удаляет ключи
  • Она не поддерживается в кластере
  • Она проходит все ключи, а Redis выполняет команды в одном потоке — все остальные клиенты ждут
  • Она сбрасывает TTL
Используйте SCAN с курсором.

При обновлении товара в cache-aside что делать с кэшем?

  • Удалить ключ после коммита в базу; следующее чтение загрузит свежие данные
  • Обновить ключ до записи в базу
  • Ничего, TTL разберётся
  • Очистить весь кэш
Удаление после коммита проще и безопаснее записи нового значения.

Можно ли хранить в Redis единственную копию балансов пользователей?

  • Да, Redis всегда долговечен
  • Да, если включён RDB
  • Да, если есть реплика
  • Рискованно: асинхронная репликация и AOF everysec допускают потерю подтверждённых записей
Для денег нужен источник истины с ACID и синхронным журналом.

Тысячи ключей кэша создаются при деплое с одинаковым TTL 1 час. Чем это грозит?

  • Ничем
  • Через час все истекут одновременно — всплеск нагрузки на базу
  • Redis перестанет принимать запросы
  • Ключи никогда не истекут
Добавляйте случайный разброс к TTL.
Как реализовать ограничение частоты запросов (rate limiting) на Redis?

Фиксированное окно: INCR rate:{user}:{minute} + EXPIRE 60, отказ при превышении. Скользящее окно: sorted set с отметками времени запросов (ZADD, ZREMRANGEBYSCORE старше окна, ZCARD) в Lua-скрипте для атомарности. Token bucket: хэш с токенами и временем последнего пополнения, Lua-скрипт. В кластере — ключи одного пользователя с хэш-тегом.

Когда кэш не нужен?

Когда база и так отвечает быстро для нужной нагрузки; когда доступ равномерный и доля попаданий будет низкой; когда данные должны быть строго актуальными; когда проблема в плохом запросе, который правильнее починить. Кэш — дополнительная система с инвалидацией, прогревом, авариями и устаревшими данными.
