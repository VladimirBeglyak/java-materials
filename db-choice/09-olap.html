Аналитика: ClickHouse и колоночные СУБД

«Сколько выручки по регионам за квартал», «воронка регистрации по дням», «топ-100 страниц по уникальным посетителям за месяц» — запросы, которые читают миллиарды строк ради нескольких чисел. OLTP-база для этого не создана. Колоночные аналитические СУБД — ClickHouse, BigQuery, Snowflake, Redshift — отвечают за секунды. Разбираем, как устроен ClickHouse MergeTree, как выбрать ключ сортировки, почему там не делают UPDATE, и тренируем аналитический SQL в песочнице.

9.2ClickHouse MergeTree изнутри

CREATE TABLE events (
  event_date  Date,
  event_time  DateTime,
  user_id     UInt64,
  event_type  LowCardinality(String),     -- словарное кодирование
  page        String,
  country     LowCardinality(String),
  revenue     Decimal(12, 2)
) ENGINE = MergeTree
PARTITION BY toYYYYMM(event_date)            -- для ретенции и отсечения, не для скорости
ORDER BY (event_type, event_date, user_id)   -- порядок хранения = разреженный первичный индекс
TTL event_date + INTERVAL 13 MONTH;
  • Каждая вставка создаёт part — неизменяемый каталог с файлом на каждый столбец, отсортированный по ORDER BY. Фоновые слияния объединяют части (родство с LSM). Вставлять нужно пачками (от тысяч строк) или через асинхронные вставки — тысячи мелких вставок в секунду создают «Too many parts».
  • Разреженный индекс: в памяти хранится значение ключа для каждой 8192-й строки (гранулы). Запрос по префиксу ключа сортировки отбрасывает гранулы, не читая их.
  • Каждый столбец сжат кодеками (LZ4/ZSTD, Delta, DoubleDelta, Gorilla) и читается только если нужен запросу.
Какие гранулы прочитает запрос (ORDER BY event_type, event_date, user_id)
Как выбрать ORDER BY Столбцы, по которым чаще всего фильтруют, от низкой кардинальности к высокой: (tenant_id, event_type, toDate(time), user_id). Это одновременно и индекс, и порядок, определяющий сжатие: похожие строки рядом сжимаются лучше.

9.6Самопроверка

Сервис вставляет в ClickHouse по одной строке 3000 раз в секунду. Что произойдёт?

  • Всё в порядке, ClickHouse создан для этого
  • ClickHouse сам объединит строки в памяти без настроек
  • Строки будут потеряны
  • Каждая вставка создаёт часть, слияния не успевают — ошибка «Too many parts»; нужны пачки, буфер или async_insert
Колоночные базы рассчитаны на пакетную запись.

Что определяет ORDER BY в таблице MergeTree?

  • Только порядок результата SELECT
  • Физический порядок данных и разреженный первичный индекс
  • Уникальность строк
  • Партиционирование
PRIMARY KEY в ClickHouse не уникален — это префикс ORDER BY.

Как в ClickHouse хранить заказы, статус которых меняется?

  • ReplacingMergeTree с версией: вставлять новую версию строки, читать последнюю
  • Частые ALTER TABLE UPDATE на каждую смену статуса
  • Удалять и вставлять заново через DELETE
  • Хранить только финальный статус, отбрасывая изменения
Неизменяемые части + схлопывание версий при слияниях.

Почему аналитику не стоит строить на реплике OLTP-базы при росте объёмов?

  • Реплика не поддерживает SELECT
  • Аналитика требует транзакций
  • Строковое хранение читает все столбцы и плохо сжимает, тяжёлые запросы конфликтуют с применением WAL и растёт отставание
  • Реплику нельзя индексировать
До определённого объёма реплика — разумный старт.
Как доставить данные из PostgreSQL в ClickHouse для аналитики?

CDC: Debezium читает логическую репликацию PostgreSQL → Kafka → таблица с движком Kafka + материализованное представление в ReplacingMergeTree (версия — LSN или updated_at). Удаления — флаг is_deleted. Для небольших справочников — словари (dictionary) с периодической загрузкой из PostgreSQL. Готовые решения: ClickPipes, PeerDB, Airbyte.

Как спроектировать таблицу для дашборда «выручка по магазинам по часам» при 1 млрд событий в сутки?

Сырые события в MergeTree с ORDER BY (shop_id, toStartOfHour(time), …) и TTL; материализованное представление в SummingMergeTree/AggregatingMergeTree с ключом (shop_id, hour) — дашборд читает тысячи строк агрегата вместо миллиардов событий. Вставка пачками из Kafka.
