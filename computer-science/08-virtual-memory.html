Виртуальная память

Ни одна программа не видит настоящих адресов оперативной памяти. Каждый процесс живёт в собственном виртуальном адресном пространстве, а процессор на каждом обращении переводит виртуальный адрес в физический по таблицам страниц, которые ведёт ядро. Это даёт изоляцию процессов, защиту памяти, ленивое выделение, отображение файлов, общие библиотеки и copy-on-write. И объясняет, почему у JVM с -Xmx4g «виртуальной» памяти 7 ГБ, а «настоящей» — 100 МБ.

8.1Зачем нужна виртуальная память

Без неё программа работала бы с физическими адресами: любая ошибка в одной программе портила бы чужую память, каждая программа должна была бы знать, куда её загрузили, а памяти было бы ровно столько, сколько стоит планок. Виртуальная память решает всё это одним механизмом — трансляцией адресов:

  • Изоляция: адрес 0x7fff… в процессе A и тот же адрес в процессе B — разные физические ячейки. Процесс физически не может адресовать чужую память.
  • Защита: у каждой страницы есть права — чтение, запись, исполнение, доступ из пользовательского режима. Запись в код или исполнение данных вызывает аппаратное исключение.
  • Ленивость: адресное пространство можно зарезервировать, не выделяя физической памяти; страница появляется при первом обращении.
  • Общие страницы: код libc или libjvm.so загружен в память один раз и отображён во все процессы; после fork родитель и потомок делят страницы до первой записи.
  • Отображение файлов: файл можно «положить» в адресное пространство и работать с ним как с массивом.

8.2Страницы и таблицы страниц

Память делится на страницы — обычно по 4 КБ (на Apple M и некоторых ARM-серверах — 16 КБ или 64 КБ). Трансляция работает постранично: младшие 12 бит адреса — смещение внутри страницы, остальные — номер виртуальной страницы, который отображается в номер физической (кадра, frame).

Таблица «номер страницы → кадр» для 48-битного адресного пространства содержала бы 2³⁶ записей — 512 ГБ на процесс. Поэтому она многоуровневая: дерево, где хранятся только используемые ветви. На x86-64 — четыре уровня по 9 бит индекса (PML4 → PDPT → PD → PT), с 5-уровневыми таблицами (LA57) — пять уровней и 57-битные адреса.

8.3MMU и TLB

Трансляцию выполняет блок процессора MMU (memory management unit), аппаратно — ядро ОС лишь заполняет таблицы. Чтобы не обходить четыре уровня на каждом обращении, MMU кэширует готовые переводы в TLB (translation lookaside buffer): L1 dTLB — 64–96 записей, общий L2 TLB — 1–3 тысячи. С 4-КБ страницами L2 TLB покрывает лишь несколько мегабайт: программа, случайно гуляющая по гигабайтам (как в лабе 06.1), промахивается и мимо TLB. Промах TLB — обход таблиц (page walk): 4 зависимых чтения, которые, к счастью, часто попадают в кэш.

  • Большие страницы (huge pages): 2 МБ (запись PD указывает сразу на кадр, без уровня PT) и 1 ГБ. Одна запись TLB покрывает в 512 раз больше памяти. Для больших куч JVM — заметный выигрыш (5–20% на некоторых нагрузках): -XX:+UseLargePages (заранее выделенные huge pages) или -XX:+UseTransparentHugePages (THP Linux).
  • Переключение процессов меняет CR3 — переводы старого процесса в TLB становятся недействительными. Метки PCID позволяют не сбрасывать TLB полностью. Потоки одного процесса делят таблицы — переключение между ними TLB не трогает.
  • TLB shootdown: когда ядро меняет отображение (munmap, mprotect, перенос страницы), оно должно сбросить устаревшие переводы на всех ядрах, где работают потоки процесса, — межпроцессорным прерыванием. Это одна из скрытых цен частых mmap/munmap (в том числе в JVM, когда она отдаёт память ОС).

8.4Page fault: что происходит при первом обращении

Если запись таблицы отсутствует (present = 0) или права не позволяют операцию, процессор генерирует исключение page fault и передаёт управление ядру (тема 10) с адресом и причиной. Ядро смотрит, что должно быть по этому адресу в описании адресного пространства процесса (области VMA — то, что видно в /proc/<pid>/maps):

8.5Сколько памяти на самом деле: VSZ, RSS, overcommit

  • VSZ / VmSize — размер всех областей адресного пространства, в том числе только зарезервированных. JVM с -Xmx4g сразу резервирует 4 ГБ под кучу, сотни мегабайт под code cache и class space, по мегабайту под стек каждого потока — VSZ легко достигает 7–10 ГБ.
  • RSS / VmRSS (resident set size) — сколько физических страниц сейчас принадлежит процессу. Именно это потребляет оперативную память (за вычетом общих страниц библиотек, которые учитываются у всех). Лимиты контейнеров считают похожую величину.
  • Commit в терминах JVM — часть зарезервированного, которую JVM разрешила использовать (-Xms — начальный commit кучи). Физически страницы всё равно появляются при касании; -XX:+AlwaysPreTouch касается их все при старте — медленнее запуск, но без page faults в работе и с честным RSS.
  • Overcommit: Linux по умолчанию разрешает зарезервировать больше, чем есть памяти, надеясь, что всё сразу не понадобится. Если понадобится — OOM killer выбирает процесс-жертву и убивает его SIGKILL без предупреждения (в контейнере — по лимиту cgroup, тема 15). Для JVM это выглядит как внезапная смерть без OutOfMemoryError и без дампа.
  • Swap: ядро может выгружать редко используемые страницы на диск. Для JVM это губительно: сборщик мусора обходит всю кучу, и выгруженные страницы превращаются в major faults и паузы в секунды. Серверы с JVM обычно запускают без swap или с минимальной «склонностью» к нему (vm.swappiness).

8.6mmap, copy-on-write и общие страницы

Системный вызов mmap добавляет область в адресное пространство: анонимную (просто память) или отображающую файл. Через него работают malloc для больших блоков, загрузчик библиотек, стеки потоков, куча JVM, FileChannel.map (MappedByteBuffer) и FFM API (Arena, MemorySegment).

  • Отображение файла: чтение страницы — копирование не нужно, процесс работает прямо со страницами page cache ядра (тема 12). Так базы данных и Kafka читают большие файлы, а JVM открывает модули JDK (lib/modules) и архив CDS.
  • Общие библиотеки: код libjvm.so (~20 МБ) отображён во все Java-процессы машины, а в RAM лежит в одном экземпляре. То же для архива CDS — поэтому он экономит память на машине с десятком JVM.
  • fork и copy-on-write: потомок получает копию таблиц страниц, а сами страницы становятся общими и только для чтения. При первой записи любой из сторон происходит page fault, ядро копирует одну страницу. Поэтому fork гигантского процесса быстр, а ProcessBuilder в JVM использует posix_spawn/vfork, чтобы не копировать даже таблицы гигабайтной кучи.

Лаба 8.1VmSize против VmRSS у JVM15 мин

Увидеть, что JVM резервирует гигабайты адресов, а физическая память появляется по мере касания.

  1. Создайте файл Rss.java:
    import java.nio.file.Files;
import java.nio.file.Path;

public class Rss {
    static String mem() throws Exception {
        StringBuilder b = new StringBuilder();
        for (String line : Files.readAllLines(Path.of("/proc/self/status")))
            if (line.startsWith("VmSize") || line.startsWith("VmRSS"))
                b.append(String.format("%-8s %,10d КБ   ", line.substring(0, line.indexOf(':') + 1),
                        Long.parseLong(line.replaceAll("[^0-9]", ""))));
        return b.toString();
    }

    public static void main(String[] args) throws Exception {
        System.out.println("старт:                    " + mem());
        long[] big = new long[128 * 1024 * 1024];          // 1 ГБ
        System.out.println("после new long[] на 1 ГБ: " + mem());
        big = null;
        System.gc();
        System.out.println("после GC:                 " + mem());
    }
}
    docker run --rm -v "${PWD}:/lab" cs-lab java -Xmx4g Rss.java
    Вывод (JDK 25.0.2)

после GC:                 VmSize:   8,092,104 КБ   VmRSS:    1,179,388 КБ
  2. Насколько VmSize больше 4 ГБ кучи? Вырастет ли VmRSS сразу после new long[] или только после записи в массив? Уменьшится ли RSS после GC?

    VmSize на старте ~7 ГБ: 4 ГБ резерва под кучу плюс class space (1 ГБ), code cache (240 МБ), стеки, библиотеки. VmRSS — около 100 МБ. После new long[] RSS сразу растёт на гигабайт: JVM обязана заполнить массив нулями и тем самым касается каждой страницы — хотя мы ещё ничего не записали. После GC RSS здесь не уменьшился, а VmSize даже вырос (GC выделил служебные структуры): G1 умеет возвращать ОС свободные регионы (uncommit), но делает это не всегда и не сразу — память процесса Java редко «отдаётся» мгновенно.

  3. Теперь с предварительным касанием всей кучи:
    docker run --rm -v "${PWD}:/lab" cs-lab java -Xmx4g -Xms4g -XX:+AlwaysPreTouch Rss.java
    Вывод (JDK 25.0.2)
    старт:                    VmSize:   8,356,296 КБ   VmRSS:    4,378,084 КБ   
после new long[] на 1 ГБ: VmSize:   8,356,296 КБ   VmRSS:    4,386,408 КБ   
после GC:                 VmSize:   8,356,296 КБ   VmRSS:    4,387,436 КБ

    С AlwaysPreTouch RSS на старте — все 4 ГБ: JVM коснулась каждой страницы кучи при запуске. Запуск дольше, зато в работе нет page faults на первом касании, а нехватка памяти обнаружится сразу, а не через час под нагрузкой.

Лаба 8.2Page faults и copy-on-write20 мин

Посчитать page faults при первом касании памяти и увидеть copy-on-write после fork.

  1. Создайте файл cow.c:
    #include <stdio.h>
#include <stdlib.h>
#include <sys/mman.h>
#include <sys/resource.h>
#include <sys/wait.h>
#include <unistd.h>

long faults(void) { struct rusage u; getrusage(RUSAGE_SELF, &u); return u.ru_minflt; }

int main(void) {
    long page = sysconf(_SC_PAGESIZE);
    size_t n = 64UL << 20;                                       // 64 МБ
    long f0 = faults();
    char *p = mmap(NULL, n, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    long f1 = faults();
    for (size_t i = 0; i < n; i += page) p[i] = 1;               // касаемся каждой страницы
    long f2 = faults();
    for (size_t i = 0; i < n; i += page) p[i] = 2;               // второй проход
    long f3 = faults();
    printf("страница %ld байт\nmmap 64 МБ:           +%ld page faults\nпервая запись:        +%ld\nвторая запись:        +%ld\n",
           page, f1 - f0, f2 - f1, f3 - f2);

    int x = 42;
    fflush(stdout);                                              // иначе буфер stdio скопируется в потомка
    pid_t pid = fork();
    if (pid == 0) {
        long a = faults();
        for (size_t i = 0; i < n; i += page) p[i] = 3;           // пишем во все страницы — каждая копируется
        x = 100;
        printf("потомок:  &x=%p x=%d, page faults при записи в 64 МБ: +%ld (copy-on-write)\n", (void *)&x, x, faults() - a);
        exit(0);
    }
    wait(NULL);
    printf("родитель: &x=%p x=%d, p[0]=%d — адреса те же, данные свои\n", (void *)&x, x, p[0]);
    return 0;
}
    docker run --rm -v "${PWD}:/lab" cs-lab sh -c "gcc -O0 -o cow cow.c && ./cow"

  2. Сколько page faults даст mmap 64 МБ, первая запись и вторая? Сколько — запись потомка в те же 64 МБ после fork?

    mmap — ноль: только резервирование. Первая запись — 16384 (64 МБ / 4 КБ): по minor fault на страницу. Вторая — ноль: страницы уже есть. Потомок после fork снова получает около 16384 faults: все страницы общие и только для чтения, каждая запись — копия страницы (плюс пара страниц стека). Адрес &x у родителя и потомка одинаковый, а значения разные: одинаковые виртуальные адреса отображены на разные физические кадры.

Поэкспериментируйте
  • Уберите fflush(stdout) и запустите с выводом в канал: ./cow | cat.
    Первые строки напечатаются дважды: при выводе в канал stdio буферизует целиком, буфер с ещё не выведенным текстом копируется в потомка вместе с памятью, и оба процесса выводят его при завершении. Copy-on-write копирует всё — даже то, о чём вы забыли.
  • Добавьте флаг MAP_POPULATE в mmap.
    Page faults переедут из «первой записи» в сам вызов mmap (ядро заполнит таблицы сразу) — аналог AlwaysPreTouch.
Лаба 8.3Карта памяти Java-процесса15 мин

Найти в адресном пространстве JVM кучу, code cache, библиотеки и стеки потоков.

  1. Создайте файл Maps.java:
    import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;

public class Maps {
    public static void main(String[] args) throws Exception {
        List<String> maps = Files.readAllLines(Path.of("/proc/self/maps"));
        System.out.println("всего областей: " + maps.size());
        long total = 0;
        for (String l : maps) {
            String[] f = l.split("\\s+", 6);
            String[] ab = f[0].split("-");
            long size = Long.parseUnsignedLong(ab[1], 16) - Long.parseUnsignedLong(ab[0], 16);
            total += size;
            String name = f.length > 5 ? f[5].trim() : "";
            if (size >= 64L << 20 || name.contains("libjvm") || name.contains("[stack]") || name.endsWith("modules") || name.endsWith(".jsa"))
                System.out.printf("%12s  %s  %,9d КБ  %s%n", ab[0], f[1], size / 1024, name.isEmpty() ? "(анонимная)" : name);
        }
        System.out.printf("сумма областей: %,d МБ%n", total >> 20);
    }
}

  2. Найдите в выводе кучу (1 ГБ), class space, code cache, libjvm.so и архив CDS. Какие у них права?

    Куча — две соседние анонимные области с адреса 0xc0000000 (3 ГБ): ~246 МБ rw-p (commit, -Xms по умолчанию) и ~776 МБ ---p (резерв до -Xmx1g). Она заканчивается ровно на 4 ГБ — JVM специально положила кучу ниже 4 ГБ, чтобы сжатые ссылки работали без базы и сдвига (zero-based compressed oops). Class space — ~1 ГБ ---p сразу за архивом CDS classes.jsa (их адрес меняется от запуска к запуску — рандомизация адресного пространства, ASLR). Code cache — две области по ~114 МБ ---p: сегменты для профилируемого и оптимизированного кода, пока почти целиком только зарезервированы. lib/modules — r--s: файл модулей JDK отображён только на чтение и общий (s — shared) для всех процессов. libjvm.so — несколько областей: код r-xp (17 МБ), константы r--p, данные rw-p. Сумма — около 4 ГБ адресов при RSS ~100 МБ.

8.9Самопроверка

Сколько уровней таблиц страниц обходит процессор x86-64 при промахе TLB (48-битные адреса)?

  • 1
  • 2
  • 4
  • 12
PML4 → PDPT → PD → PT, по 9 бит индекса на уровень и 12 бит смещения. С 5-уровневыми таблицами (57 бит) — пять.

JVM запущена с -Xmx8g, но top показывает RSS 300 МБ. Почему?

  • JVM резервирует адресное пространство под кучу, а физические страницы появляются только при первом касании
  • JVM сжимает кучу
  • top показывает неправильно
  • куча хранится на диске
Резервирование (VSZ) и резидентная память (RSS) — разные вещи. -XX:+AlwaysPreTouch заставит коснуться всех страниц при старте.

Что происходит при записи в страницу после fork?

  • SIGSEGV
  • запись идёт в общую страницу, и её видят оба процесса
  • ядро копирует весь процесс
  • page fault, ядро копирует одну эту страницу, и процесс пишет в свою копию
Copy-on-write: общие страницы помечены «только чтение», копия делается лениво по одной странице.

Зачем большие страницы (2 МБ) для JVM с большой кучей?

  • они быстрее заполняются нулями
  • одна запись TLB покрывает 2 МБ вместо 4 КБ — меньше промахов TLB и обходов таблиц
  • они не учитываются в RSS
  • без них нельзя больше 32 ГБ
Цена — фрагментация и задержки при выделении (у THP), поэтому включают осознанно и проверяют замером.
Как процессор переводит виртуальный адрес в физический?

MMU сначала ищет перевод номера страницы в TLB. При промахе обходит многоуровневую таблицу страниц текущего процесса, начиная с адреса в CR3: индексы уровней — части виртуального адреса. Последняя запись даёт номер физического кадра и права; к нему прибавляется смещение внутри страницы. Если записи нет или права не позволяют — page fault, и решение принимает ядро.

Чем minor page fault отличается от major?

Minor — страницу можно предоставить без ввода-вывода: обнулённый новый кадр, страница файла, уже лежащая в page cache, copy-on-write. Major — нужно читать с диска (файл не в кэше, swap): процесс блокируется на время ввода-вывода. Major faults в горячем пути — причина непредсказуемых пауз.

Почему OOM killer убивает Java-процесс без OutOfMemoryError?

OutOfMemoryError — это когда JVM не может выделить объект в пределах своей кучи. OOM killer срабатывает на уровне ОС: процесс суммарно (куча + metaspace + стеки + прямые буферы + нативная память) превысил физическую память или лимит cgroup, и ядро завершает его SIGKILL, который нельзя перехватить. Лечение — ограничить все области JVM так, чтобы их сумма с запасом помещалась в лимит.

Как HotSpot использует аппаратную защиту памяти?

Неявные проверки на null: обращение по адресу около нуля вызывает SIGSEGV, обработчик JVM превращает его в NullPointerException. Защитные страницы стека — StackOverflowError. Страница опроса safepoint — чтобы остановить потоки. Права W^X на code cache. Отображение файлов (CDS, lib/modules) — для быстрой загрузки и общего использования между процессами.
