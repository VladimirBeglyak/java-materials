18.1java Hello: от Enter до пикселя

Трасса запуска java Hello
[железо → ядро]  клавиша Enter: контроллер клавиатуры → прерывание (тема 10)
драйвер → подсистема ввода → терминал (в Windows — conhost/Windows Terminal,
в Linux — эмулятор терминала через псевдотерминал pty)
оболочка (bash/PowerShell) спала в read() на stdin — ядро её будит (тема 11)[оболочка → ядро]  разбор строки, поиск java в PATH (stat/access)
создание процесса: fork/posix_spawn (Linux) или CreateProcess (Windows)
СОЗДАНО: процесс — task_struct, PID 48, копия дескрипторов (stdin/stdout/stderr — тот же терминал)
оболочка ждёт его в wait() (тема 11)[ядро]  execve("/opt/java/openjdk/bin/java", …) (тема 14)
СОЗДАНО: новое адресное пространство, сегменты ELF лаунчера (16 КБ) и ld-linux,
стек ГЛАВНОГО потока процесса (лимит ulimit -s = 8 МБ) с argv, envp, auxv на вершине (темы 04, 08)
RIP = точка входа динамического загрузчика[ld.so]  отображает libc.so.6, libjli.so (по RPATH $ORIGIN/../lib), релокации, GOT
→ main() лаунчера: разбор -cp, -Xss, -Xmx, JDK_JAVA_OPTIONS
dlopen(".../lib/server/libjvm.so") — 30 МБ кода виртуальной машины (тема 14)[лаунчер]  НЕ запускает JVM в изначальном потоке: размер его стека задан ОС
pthread_create с размером стека из -Xss (1 МБ) → mmap(MAP_STACK) + clone(CLONE_VM|CLONE_THREAD…)
СОЗДАНО: поток TID 49 — будущий Java-поток main, его нативный стек 1 МБ (тема 04)
изначальный поток 48 будет ждать его в pthread_join[JVM, поток 49]  JNI_CreateJavaVM: разбор флагов, эргономика по /proc и cgroups (тема 15)
СОЗДАНО: резерв кучи (mmap -Xmx, ниже 4 ГБ для сжатых ссылок), class space 1 ГБ,
code cache 240 МБ, metaspace — пока почти без физических страниц (тема 08)
генерация шаблонного интерпретатора и заглушек в машинный код (тема 09)[JVM]  служебные потоки — каждый со своим стеком (clone): VM Thread, потоки GC,
C1/C2 CompilerThread, Signal Dispatcher, Reference Handler, Finalizer, Common-Cleaner…
→ около 18 потоков ОС в процессе (лаба 18.2)
mmap lib/modules (r--s) и архива CDS classes.jsa: java.base уже разобран (темы 08, 09)[JVM]  initPhase1–3: System.out (FileOutputStream на дескрипторе 1 + буфер + кодировка),
система модулей, загрузчики классов; прикладной загрузчик читает /tmp/Hello.class (openat, read)
линковка и инициализация класса Hello (JVM, темы 05–06)[интерпретатор, поток 49]  ПЕРВЫЙ JAVA-КАДР: Hello.main(String[]) на нативном стеке потока
кадр: слот 0 = args (ссылка на String[] в куче), стек операндов, Method*, bcp (тема 04, JVM 03)
каждый вызов (println → PrintStream.write → … ) — новый кадр ниже предыдущего
объекты строки — в TLAB в куче (bump pointer, JVM 11)[JVM → ядро]  "Привет!" → UTF-8 (12 байт + \n, тема 01) → write(1, …, 14) — системный вызов (тема 10)
ядро: дескриптор 1 → псевдотерминал → процесс терминала просыпается и читает байты[терминал → GPU]  декодирует UTF-8, берёт глифы шрифта, растеризует текст,
композитор окон собирает кадр на GPU → буфер кадра → контроллер дисплея на следующей VSync (тема 16)
пиксели «Привет!» на экране — ~примерно через 100–300 мс после Enter[завершение]  main вернулся → DestroyJavaVM: ожидание недемонов, shutdown hooks,
потоки JVM завершаются; изначальный поток 48 выходит из pthread_join и вызывает exit_group(0)
ядро освобождает адресное пространство, закрывает дескрипторы, процесс — зомби до wait() оболочки
оболочка получает код 0 и печатает приглашение (тема 11)

Аппаратное прерывание, драйвер, пробуждение спящей оболочки.

Оболочка создаёт процесс; он наследует открытые терминальные дескрипторы.

Ядро загружает исполняемый файл и строит стек главного потока.

Лаунчер — маленькая C-программа; виртуальная машина подгружается как библиотека.

Ключевой момент: Java-метод main исполнится не в изначальном потоке, а в новом, со стеком размера -Xss.

Резервируются области; физические страницы появятся при касании.

GC, JIT, VM Thread и другие — каждый со своим стеком и guard-зонами.

Ядро java.base — из CDS, Hello.class — с диска (через page cache).

Интерпретатор создаёт кадр main и исполняет байткод.

Строка превращается в байты и уходит системным вызовом.

Терминал и GPU превращают байты в пиксели.

Обратная последовательность: потоки, память, процесс, wait.

  2. Найдите в выводе: (1) какой поток загружает libjvm.so и создаёт следующий поток; (2) какой поток открывает lib/modules, Hello.class и выполняет write(1, …); (3) кто вызывает exit_group. Сколько времени прошло от execve до первого write?

    (1) Изначальный поток процесса (строки без [pid N] — это PID процесса): execve, libjli.so, libjvm.so и первый clone — создание потока, который станет Java-потоком main. (2) Всё остальное делает именно этот новый поток: отображает lib/modules и classes.jsa, создаёт полтора десятка служебных потоков (GC, JIT, VM Thread…), читает Hello.class и выполняет оба write(1, …) — в первом видно, что TID потока main не равен PID. (3) exit_group(0) вызывает снова изначальный поток: он всё это время ждал в pthread_join. От execve до первого write — порядка 200–300 мс под strace (без трассировки — 50–80 мс): трассировка каждого вызова замедляет запуск.

Поэкспериментируйте
  • Добавьте -Xss4m в команду запуска java и найдите первый clone с mmap перед ним (добавьте mmap в -e trace=).
    Перед первым clone — mmap(NULL, 4198400, …, MAP_STACK) или похожий размер: стек потока main берётся из -Xss, а не из ulimit -s.
Лаба 18.2Потоки JVM глазами ядра10 мин

Сопоставить потоки ОС процесса Java с их ролями.

  1. Создайте файл Threads.java:
    import java.nio.file.Files;
import java.nio.file.Path;
import java.util.stream.Stream;

public class Threads {
    public static void main(String[] args) throws Exception {
        try (Stream<Path> tasks = Files.list(Path.of("/proc/self/task"))) {
            tasks.sorted((a, b) -> Integer.compare(Integer.parseInt(a.getFileName().toString()), Integer.parseInt(b.getFileName().toString())))
                 .forEach(t -> {
                     try {
                         String name = Files.readString(t.resolve("comm")).trim();       // имя потока в ядре (до 15 символов)
                         String stat = Files.readString(t.resolve("stat"));
                         String state = stat.substring(stat.lastIndexOf(')') + 2, stat.lastIndexOf(')') + 3);
                         System.out.printf("TID %-4s %-16s состояние %s%n", t.getFileName(), name, state);

18.7Самопроверка

В каком потоке исполняется Java-метод main при запуске java Hello?

  • в изначальном потоке процесса, созданном execve
  • в потоке VM Thread
  • в новом потоке, который лаунчер создаёт со стеком размера -Xss
  • в виртуальном потоке
Так JVM контролирует размер стека и защитные зоны; изначальный поток ждёт в pthread_join и в конце вызывает exit_group. TID потока main ≠ PID процесса.

Где хранится ссылка args метода main и где — сам массив строк?

  • ссылка — в слоте 0 кадра main на стеке потока; массив и строки — в куче
  • оба — в куче
  • оба — в metaspace
  • ссылка — в куче, массив — на стеке
Кадр хранит локальные переменные, включая ссылки; объекты всегда в куче (если JIT не устранил их).

Сервис отвечает медленно, CPU пода загружен на 30%, лимит limits.cpu: 1. Что проверить первым?

  • утечку памяти
  • троттлинг cgroup (nr_throttled в cpu.stat) и ожидания в дампе потоков
  • предсказатель переходов
  • размер кэш-линии
Низкая средняя загрузка не исключает исчерпания квоты на всплесках; плюс ожидание БД и сети не видно в CPU.
Расскажите по шагам, что происходит от ввода java Hello до вывода на экран.

Прерывание клавиатуры будит оболочку; она создаёт процесс (fork/spawn) и делает execve лаунчера java; ядро строит адресное пространство и стек главного потока, ld.so подключает libc и libjli; лаунчер dlopen-ит libjvm и создаёт новый поток со стеком -Xss, в котором стартует JVM: резервирует кучу и другие области, генерирует интерпретатор, создаёт служебные потоки, отображает CDS и модули, загружает Hello.class; интерпретатор строит кадр main и исполняет байткод; println превращает строку в UTF-8 и делает write(1); терминал получает байты, растеризует текст, композитор и GPU выводят кадр. При выходе — DestroyJavaVM, exit_group, wait оболочки.

Что такое поток, стек и кадр, и как они связаны?

Поток — контекст исполнения, который планирует ядро: регистры (RIP, RSP…) и собственный стек. Стек — область памяти потока, выделенная при его создании (mmap + guard-страницы), где по дисциплине LIFO лежат кадры всех незавершённых вызовов. Кадр — участок стека одного вызова: адрес возврата, сохранённые регистры, локальные переменные (в Java — слоты, стек операндов, ссылка на метод). Объекты, на которые ссылаются локальные переменные, живут не в кадре, а в куче.

Почему «быстрее посчитать» почти никогда не главное в серверной производительности?

Большая часть времени запроса — ожидание: сети, базы, диска, блокировок, памяти (промахи кэша), планировщика и квот контейнера. Операции процессора на порядки дешевле любого ожидания. Поэтому оптимизация начинается с измерения, где запрос ждёт, и сокращения числа и длительности ожиданий: кэши, пакетирование, параллелизм ожиданий, локальность данных.
