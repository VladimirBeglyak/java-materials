Поток, стек и кадр вызова

Что такое поток для процессора и для операционной системы, откуда берётся стек, как устроен кадр (frame) функции и что в нём лежит, как команды call и ret делают возможными вложенные вызовы, кто и когда выделяет память под стек нового потока — и как всё это устроено в JVM: где лежат кадры Java-методов, что такое -Xss, откуда берётся StackOverflowError. Это одна из самых важных глав курса: на этих механизмах стоят рекурсия, исключения, стек-трейсы, отладчик, профилировщики и виртуальные потоки.

4.1Что такое поток

Процессорное ядро в каждый момент делает одно: исполняет команду по адресу в RIP, используя значения в своих регистрах. Всё «состояние вычисления» в данный момент — это:

  • счётчик команд RIP — где мы в программе;
  • указатель стека RSP — где вершина стека (и, через него, вся цепочка незавершённых вызовов);
  • остальные регистры — промежуточные значения, флаги, векторные регистры;
  • стек в памяти — локальные переменные и адреса возврата всех незавершённых функций.

Поток (thread) — это и есть такое состояние исполнения: «куда смотрит» RIP, свой стек и свой набор значений регистров. Процессор о потоках ничего не знает — он просто исполняет команды. Потоки создаёт и переключает ядро операционной системы: когда ядро решает отдать процессор другому потоку, оно сохраняет все регистры текущего в свою структуру данных (в Linux — task_struct и область сохранения регистров на стеке ядра) и загружает регистры другого. Для потока это незаметно: он продолжает с той же команды, с теми же регистрами (переключение контекста — тема 11).

Процесс — контейнер ресурсов (адресное пространство, дескрипторы, права) и один или больше потоков. Потоки одного процесса видят одну и ту же память — поэтому они быстро обмениваются данными и поэтому нужна синхронизация (тема 07 и Java Concurrency, тема 02). Стеки при этом разные: локальная переменная одного потока недоступна другому, пока на неё не дали указатель.

4.2Стек: зачем он и как работает

Функции вызываются вложенно: main вызвала f, f — g; закончиться первой должна g, затем f, затем main. Последний вызванный завершается первым — это ровно дисциплина LIFO (last in, first out). Поэтому данные вызовов хранят в стеке: непрерывной области памяти, у которой есть вершина.

  • Стек растёт вниз — к меньшим адресам (на x86-64, ARM64, RISC-V). Вершину хранит регистр RSP. «Положить» 8 байт — push: RSP -= 8, затем запись по адресу RSP. «Снять» — pop: чтение и RSP += 8.
  • Выделение памяти на стеке бесплатно: одна команда sub rsp, 48 резервирует 48 байт под локальные переменные функции. Освобождение — add rsp, 48 или восстановление RSP при выходе. Никакого поиска свободного блока, никакой сборки мусора — сравните с выделением в куче (JVM, тема 11).
  • Время жизни данных на стеке = время вызова. Когда функция вернулась, её область стека считается свободной и будет перезаписана следующим вызовом. Поэтому в C нельзя возвращать адрес локальной переменной, а в Java на стеке вообще нельзя разместить объект, на который может остаться ссылка (компилятор делает это только для «не убегающих» объектов — escape analysis).
  • Стек близко и «горячий»: его вершина почти всегда в кэше L1 (тема 06), поэтому обращения к локальным переменным дешёвые даже без регистров.

4.3call и ret: как процессор вызывает функцию и возвращается

У процессора нет понятия «функция». Есть две команды:

  • call f = положить в стек адрес следующей команды (адрес возврата) и перейти на f: push rip_следующей; jmp f.
  • ret = снять адрес со стека и перейти по нему: pop rip.

Этого достаточно для любой вложенности и рекурсии: каждый вызов кладёт свой адрес возврата, каждый возврат снимает свой. Если функция испортит стек (переполнение буфера в C перезаписало адрес возврата), ret «вернётся» куда угодно — классическая атака на программы без защиты памяти. В Java такое невозможно: нет арифметики указателей, а массивы проверяют границы.

main выполняется, её кадр на стеке. RBP указывает на начало кадра, RSP — на вершину.

Аргументы кладутся в регистры RDI и RSI (соглашение System V). call кладёт в стек адрес возврата и переходит на функцию.

Функция сохраняет RBP вызывающего, делает RBP своим якорем и опускает RSP — кадр готов.

Тот же механизм для square: новый адрес возврата, новый кадр ниже предыдущего.

Результат — в RAX. leave сносит кадр, ret снимает адрес возврата в RIP.

Следующий вызов занимает ту же память: стек — это постоянно переиспользуемая область.

Стек вернулся к началу. Освобождение памяти вызова — просто восстановление RSP.

4.5Соглашение о вызовах (ABI)

Чтобы функция из одной библиотеки могла вызвать функцию из другой, скомпилированной другим компилятором (или даже на другом языке), все должны одинаково договориться: где аргументы, где результат, какие регистры можно портить, как выровнен стек. Это двоичный интерфейс приложений (ABI) платформы.

Как с этим живёт JVM. Интерпретатор HotSpot и JIT-код используют собственное внутреннее соглашение для вызовов Java → Java (оно ближе к ABI платформы, но со своими правилами для регистров), а на границе с нативным кодом (JNI, FFM API) переходят на ABI ОС — это одна из причин, почему нативный вызов дороже обычного (JVM, тема 19). Foreign Function & Memory API (Java 22) как раз описывает ABI платформы в коде: класс Linker знает, как разложить аргументы по регистрам для текущей ОС.

4.7Как операционная система создаёт поток и его стек

Главный поток

При запуске программы (execve, тема 14) ядро создаёт процесс с одним потоком: строит адресное пространство, отображает в него исполняемый файл и загрузчик библиотек, выделяет стек главного потока у верхней границы пользовательской памяти и кладёт на него аргументы командной строки, переменные окружения и вспомогательный вектор (auxv). RSP указывает на argc, RIP — на точку входа. Размер стека главного потока ограничен ulimit -s (по умолчанию 8 МБ), и ядро растит его автоматически: при обращении ниже текущей границы происходит page fault, и ядро добавляет страницу.

Дополнительный поток

  1. Выделить память под стек. Библиотека потоков (pthread_create в glibc) вызывает mmap(NULL, размер, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS|MAP_STACK) — заказывает адресное пространство. Физическая память не выделяется: страницы появятся при первом касании (ленивое выделение, тема 08). Поэтому 1000 потоков с «стеком 1 МБ» не занимают 1 ГБ RAM.
  2. Поставить guard-страницу. Нижнюю страницу (или несколько) делают недоступной: классически — mprotect(PROT_NONE), в Linux 6.13+ с glibc 2.42+ — более лёгким madvise(MADV_GUARD_INSTALL). Любое обращение к ней — аппаратное исключение, и вместо тихой порчи соседней памяти поток получает SIGSEGV. Так переполнение стека становится видимым.
  3. Создать поток в ядре. Системный вызов clone (или clone3) с флагами CLONE_VM | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD … — «новая задача, разделяющая с родителем память, файлы и сигналы», и параметром child_stack — начальным значением RSP нового потока. Для ядра Linux поток и процесс — одна и та же структура task_struct, разница только в том, что разделяется.
  4. Начать исполнение. Ядро ставит новый поток в очередь планировщика. Когда он впервые получает процессор, RSP указывает в его новый стек, а RIP — на стартовую функцию библиотеки потоков, которая вызывает вашу функцию потока.
  5. Завершение. Функция потока вернулась → библиотека вызывает exit для потока; стек освобождается (munmap) или кэшируется для следующего потока.

На Windows аналог — CreateThread: стек резервируется (по умолчанию 1 МБ, значение из заголовка исполняемого файла), а физические страницы «коммитятся» постепенно через guard-страницу, которая сдвигается вниз при росте стека.

4.8Потоки и кадры в JVM

Платформенный поток Java (new Thread(...)) — это обычный поток ОС, 1:1. thread.start() проходит путь: Thread.start0 (native) → JVM_StartThread → создание C++-объекта JavaThread → os::create_thread → pthread_create с размером стека из -Xss (или параметра stackSize конструктора Thread). В новом потоке JVM инициализирует свои структуры (TLAB для выделения памяти, зоны защиты стека) и вызывает Java-метод Thread.run(). Это видно в лабораторной 4.4 прямо по системным вызовам.

Откуда берётся StackOverflowError

Кроме того, перед входом в метод JIT-код делает stack banging — пробное обращение на несколько страниц ниже (StackShadowPages), чтобы переполнение случилось в предсказуемом месте Java-кода, а не внутри нативной функции, вызванной из него. Поэтому StackOverflowError — обычное исключение, которое можно поймать (хотя продолжать работу после него рискованно).

  • -Xss (-XX:ThreadStackSize) — размер стека платформенных потоков. По умолчанию 1 МБ на Linux x64 и macOS; на Windows — размер из заголовка java.exe (1 МБ). Главный поток Java тоже получает этот размер: лаунчер не исполняет main в изначальном потоке процесса, а создаёт для него новый поток (JVM, тема 01).
  • Глубина рекурсии = размер стека / размер кадра. Интерпретируемый кадр больше JIT-кадра, поэтому один и тот же код до прогрева «падает» раньше (JVM, тема 09).
  • Виртуальные потоки (Java 21) своего стека ОС не имеют: работают на стеке потока-носителя, а при блокировке их кадры копируются в кучу (объекты StackChunk). Поэтому миллион виртуальных потоков возможен, а миллион платформенных — нет: каждому нужен clone, структура в ядре и резерв адресного пространства под стек.

4.9Стек-трейс, исключения и раскрутка стека

Стек-трейс — это просто проход по цепочке кадров от текущего к самому старому с переводом адресов возврата в имена функций и номера строк. Для Java: new Throwable() вызывает fillInStackTrace, и JVM обходит кадры потока (интерпретируемые, скомпилированные с учётом встроенных методов), записывая пары «метод + номер байткода», а номера строк берёт из атрибута LineNumberTable class-файла. Это дорого (сотни наносекунд – микросекунды на глубоком стеке), поэтому исключения не используют для обычного управления потоком, а HotSpot для часто бросаемых встроенных исключений (NPE, ArithmeticException) в горячем коде может отдавать заранее созданный объект без стек-трейса (-XX:-OmitStackTraceInFastThrow отключает).

Бросок исключения — тоже раскрутка: JVM ищет в таблице исключений текущего метода обработчик для этого адреса; если нет — снимает кадр (как ret, только без результата) и ищет в вызывающем, и так далее. Блоки finally исполняются по дороге (JVM, тема 03).

Профилировщики (async-profiler, JFR) сотни раз в секунду останавливают поток и записывают его стек — из миллионов таких снимков строится флеймграф (JVM, тема 21). Отладчик показывает переменные каждого кадра, потому что знает, в каком слоте или регистре лежит каждая переменная в каждой точке кода.

Увидеть, что стек растёт вниз, что кадры связаны сохранёнными RBP, и что адрес возврата указывает на строку вызова.

  1. Создайте файл frames.c:
    #include <stdio.h>
#include <stdlib.h>
#include <string.h>

long global_counter = 42;

void walk(void) {
    void **fp = __builtin_frame_address(0);          // RBP текущего кадра
    for (int depth = 0; depth < 4; depth++) {
        printf("  кадр %d: RBP=%p  [RBP]=сохранённый RBP=%p  [RBP+8]=адрес возврата=%p\n",
               depth, (void *)fp, fp[0], fp[1]);
        fp = (void **)fp[0];                          // переход к кадру вызывающего
    }
}

long square(long x) {
    long local_sq = x * x;
    printf("square(%ld): &x=%p  &local_sq=%p\n", x, (void *)&x, (void *)&local_sq);
    if (x == 3) walk();
    return local_sq;
}

long sum_sq(long a, long b) {
    long local_a = square(a);
    long local_b = square(b);
    printf("sum_sq:     &local_a=%p &local_b=%p\n", (void *)&local_a, (void *)&local_b);
    return local_a + local_b;
}

int main(void) {
    long m = 1;
    long *heap = malloc(sizeof(long));
    printf("main:       &m=%p\n", (void *)&m);
    printf("куча:       %p\nглобальная: %p\nкод:        main=%p sum_sq=%p square=%p\n",
           (void *)heap, (void *)&global_counter, (void *)main, (void *)sum_sq, (void *)square);
    printf("результат:  %ld\n\n", sum_sq(3, 4));

    FILE *maps = fopen("/proc/self/maps", "r");       // карта памяти этого процесса
    char line[512];
    while (fgets(line, sizeof line, maps))
        if (strstr(line, "[stack]") || strstr(line, "[heap]") || strstr(line, "/frames")) fputs(line, stdout);
    return 0;
}

    Адреса убывают: main > sum_sq > square — стек растёт вниз. Оба вызова square показывают одинаковые адреса: второй вызов занял ту же память, что и первый (он был снесён). Лаба 4.3Стеки потоков в карте памяти20 мин

Создать потоки pthread и найти их стеки и guard-страницы в /proc/self/maps.

  1. Создайте файл threads.c:
    #include <pthread.h>
#include <stdio.h>
#include <string.h>

pthread_barrier_t ready, done;
void *locals[2];

void *worker(void *arg) {
    long local = (long)arg;
    locals[local - 1] = &local;
    printf("поток %ld: &local = %p\n", local, (void *)&local);
    pthread_barrier_wait(&ready);   // сообщить main, что стек создан
    pthread_barrier_wait(&done);    // и жить, пока main читает карту памяти
    return NULL;
}

int main(void) {
    long local_main = 0;
    printf("main:     &local = %p\n", (void *)&local_main);
    pthread_attr_t attr;
    pthread_attr_init(&attr);
    size_t sz, guard;
    pthread_attr_getstacksize(&attr, &sz);
    pthread_attr_getguardsize(&attr, &guard);
    printf("стек нового потока по умолчанию: %zu КБ, guard: %zu КБ\n", sz / 1024, guard / 1024);

    pthread_barrier_init(&ready, NULL, 3);
    pthread_barrier_init(&done, NULL, 3);
    pthread_t t[2];
    for (long i = 0; i < 2; i++) pthread_create(&t[i], NULL, worker, (void *)(i + 1));
    pthread_barrier_wait(&ready);

    FILE *maps = fopen("/proc/self/maps", "r");
    char line[512], prev[512] = "";
    puts("\nкарта памяти: области, в которых лежат стеки (и строка перед каждой):");
    while (fgets(line, sizeof line, maps)) {
        unsigned long a, b;
        sscanf(line, "%lx-%lx", &a, &b);
        int hit = strstr(line, "[stack]") != NULL;
        for (int i = 0; i < 2; i++) hit |= (unsigned long)locals[i] >= a && (unsigned long)locals[i] < b;
        if (hit) printf("  %s\n  %.*s   <- %lu KB\n", prev, (int)strcspn(line, "\n"), line, (b - a) / 1024);
        strcpy(prev, line);
        prev[strcspn(prev, "\n")] = 0;
    }
    pthread_barrier_wait(&done);
    for (int i = 0; i < 2; i++) pthread_join(t[i], NULL);
    return 0;
}

    1 МБ (ThreadStackSize = 1024 КБ) плюс выравнивание — значение -Xss по умолчанию на Linux x64. С java -Xss4m — 4 МБ.
Лаба 4.5Глубина рекурсии и StackOverflowError15 мин

Измерить, сколько кадров помещается в стек, и как это зависит от размера стека, размера кадра и режима исполнения.

  1. Создайте файл Depth.java:
    public class Depth {
    static int depth;

    static void small() { depth++; small(); }

    static long big(long a, long b, long c, long d) {
        depth++;
        long x = a + 1, y = b + 2, z = c + 3, w = d + 4, v = x * y, u = z * w;
        return big(x, y, z, w) + v + u;
    }

    static int measure(Runnable r, long stackSize) throws InterruptedException {
        int[] res = new int[1];
        Thread t = new Thread(null, () -> {
            depth = 0;
            try { r.run(); } catch (StackOverflowError e) { res[0] = depth; }
        }, "probe", stackSize);
        t.start();
        t.join();
        return res[0];
    }

    public static void main(String[] args) throws Exception {
        for (long kb : new long[] {256, 1024, 4096}) {
            int s = measure(Depth::small, kb * 1024);
            int b = measure(() -> big(1, 2, 3, 4), kb * 1024);
            System.out.printf("стек %4d КБ: small() — %7d кадров (~%d байт на кадр), big() — %6d кадров (~%d байт)%n",
                    kb, s, kb * 1024 / s, b, kb * 1024 / b);
        }
    }
}
  2. Во сколько раз вырастет глубина при стеке 4 МБ вместо 1 МБ? У какого метода кадр больше? Как изменится картина с -Xint (только интерпретатор)?
    javac Depth.java
java Depth
java -Xint Depth
    Вывод (JDK 25.0.2)
    стек  256 КБ: small() —    3382 кадров (~77 байт на кадр), big() —    845 кадров (~310 байт)
стек 1024 КБ: small() —   24906 кадров (~42 байт на кадр), big() —   8892 кадров (~117 байт)
стек 4096 КБ: small() —  103532 кадров (~40 байт на кадр), big() — 129428 кадров (~32 байт)
стек  256 КБ: small() —    2383 кадров (~110 байт на кадр), big() —    843 кадров (~310 байт)

    С -Xint картина «учебная»: глубина почти пропорциональна размеру стека, кадр small около 90 байт, big — около 250 (больше аргументов и локальных переменных). В обычном режиме числа «плавают»: первые вызовы идут в интерпретаторе (большие кадры), потом метод компилируется, и кадры уменьшаются. А C2 ещё и встраивает рекурсию на несколько уровней — один нативный кадр на несколько Java-вызовов, поэтому при стеке 4 МБ «байт на кадр» у big() может оказаться меньше, чем у small(). Глубина рекурсии до StackOverflowError — не константа программы.

    Чтобы задать размер стека параметром stackSize конструктора Thread, не перезапуская JVM с другим -Xss. Спецификация разрешает JVM игнорировать этот параметр, но HotSpot его учитывает.

Пройти по кадрам текущего потока средствами Java и увидеть, какие потоки JVM создаёт ещё до main.

  1. Создайте файл Walk.java:
    import java.util.Map;

public class Walk {
    public static void main(String[] args) {
        level1();
        System.out.println("\nпотоки JVM при старте:");
        Map<Thread, StackTraceElement[]> all = Thread.getAllStackTraces();
        all.keySet().stream()
                .sorted((a, b) -> a.getName().compareTo(b.getName()))
                .forEach(t -> System.out.printf("  %-20s daemon=%-5s кадров в стеке: %d%n",
                        t.getName(), t.isDaemon(), all.get(t).length));
    }

    static void level1() { level2(42); }

    static void level2(int x) {
        StackWalker.getInstance(StackWalker.Option.RETAIN_CLASS_REFERENCE)
                .forEach(f -> System.out.printf("  %s.%s строка %d (bci %d)%n",
                        f.getDeclaringClass().getSimpleName(), f.getMethodName(), f.getLineNumber(), f.getByteCodeIndex()));
    }
}

4.11Самопроверка

Что из этого есть у каждого потока своё, а не общее с другими потоками процесса?

  • куча
  • открытые файлы
  • стек и значения регистров, включая RIP и RSP
  • глобальные переменные
Потоки процесса разделяют адресное пространство и ресурсы; собственные у них только контекст исполнения (регистры), стек и TLS.

Что делает команда call f?

  • кладёт адрес следующей команды в стек и переходит на f
  • создаёт новый поток
  • выделяет кадр под локальные переменные
  • копирует аргументы в стек
Кадр строит уже сама функция в прологе; аргументы обычно в регистрах. call — только адрес возврата + переход.

Почему создание 10 000 платформенных потоков со стеком 1 МБ не требует 10 ГБ оперативной памяти сразу?

  • JVM сжимает стеки
  • стек выделяется в куче
  • ОС ограничивает число потоков до 1000
  • mmap резервирует только адресное пространство, физические страницы появляются при первом касании
Ленивое выделение памяти. Занятым становится лишь реально использованный «верх» стека, обычно десятки килобайт.

Как HotSpot превращает переполнение стека в StackOverflowError, а не в падение процесса?

  • проверяет глубину рекурсии счётчиком
  • ставит недоступные защитные страницы (yellow zone) в конце стека, ловит аппаратное исключение и бросает Java-исключение
  • увеличивает стек автоматически
  • никак: процесс всегда падает
Защитные зоны reserved/yellow/red и stack banging. Если переполнение случится в коде самой JVM (red zone) — процесс аварийно завершится.

Где лежит кадр Java-метода, исполняемого интерпретатором HotSpot?

  • в куче
  • в metaspace
  • на нативном стеке потока ОС, рядом с кадрами C++-кода JVM
  • в отдельной области «стек JVM», не связанной со стеком ОС
Спецификация описывает стек JVM абстрактно; HotSpot использует для него стек потока ОС. Исключение — виртуальные потоки: их кадры при парковке переезжают в кучу.
Что такое поток с точки зрения процессора и с точки зрения ОС?

Для процессора есть только текущее состояние: регистры (RIP, RSP и другие) и память. Поток — абстракция ОС: сохранённый контекст исполнения (значения регистров), собственный стек и данные планировщика. Ядро переключает потоки, сохраняя регистры одного и загружая регистры другого; потоки одного процесса разделяют адресное пространство и ресурсы.

Что лежит в кадре вызова и что — в стеке целиком?

Стек — область памяти потока, где друг под другом лежат кадры всех незавершённых вызовов. Кадр одного вызова: адрес возврата в вызывающего, сохранённый указатель кадра вызывающего, сохранённые регистры, локальные переменные и временные значения, не поместившиеся в регистры, аргументы для следующего вызова (если их больше, чем регистров). Для интерпретатора Java: слоты локальных переменных, стек операндов, ссылка на метод и текущий байткод, мониторы.

Как создаётся стек нового потока в Linux?

Библиотека потоков резервирует область mmap нужного размера (физические страницы появятся при касании), делает нижнюю страницу недоступной (guard), затем вызывает clone с флагами разделения памяти и ресурсов и указателем на вершину нового стека. Ядро создаёт задачу, планировщик запускает её с RSP в новом стеке. HotSpot дополнительно размечает свои защитные зоны для StackOverflowError.

Почему выделение на стеке быстрее, чем в куче?

Выделить место — одна команда (уменьшить RSP на размер кадра), освободить — восстановить RSP при выходе. Не нужно искать свободный блок, синхронизироваться между потоками и потом собирать мусор: время жизни данных совпадает со временем вызова. Цена — данные нельзя пережить вызов; поэтому объекты Java живут в куче, а на стеке — только локальные переменные и ссылки.

Как строится стек-трейс, если компилятор не сохраняет RBP?

По таблицам раскрутки (.eh_frame / DWARF CFI), где для каждого адреса кода описано, на каком смещении от RSP лежат адрес возврата и сохранённые регистры. JVM для своего JIT-кода хранит собственные метаданные: размер кадра каждого скомпилированного метода и карты встраивания, поэтому показывает и встроенные методы.

Чем стек виртуального потока отличается от стека платформенного?

У платформенного потока — стек ОС фиксированного резерва (-Xss), созданный при старте. Виртуальный поток исполняется на стеке потока-носителя; при блокировке его кадры копируются в кучу (StackChunk) и носитель освобождается, при продолжении — лениво копируются обратно на стек какого-либо носителя. Память — пропорционально реальной глубине, а не резерву.
