Аппаратная безопасность: кольца, Spectre, шифрование

Всё, что делает компьютер безопасным, опирается на механизмы из предыдущих глав: кольца привилегий, виртуальную память, проверку подписей при загрузке. И почти всё, что его ломает, — это способы обойти эти механизмы: переполнение буфера, которое перезаписывает адрес возврата, побочные каналы, по времени выдающие секреты, спекулятивное исполнение, которое заглядывает туда, куда нельзя. Разберём атаки и защиты на уровне железа и ОС — и почему Java по построению избавлена от целого класса уязвимостей, но не от всех.

17.2Переполнение буфера и защиты от него

В C массив — это просто адрес; запись за его конец портит то, что лежит рядом. На стеке рядом — другие переменные и адрес возврата (тема 04). Классическая атака: передать программе строку длиннее буфера так, чтобы strcpy перезаписал адрес возврата адресом кода атакующего. При ret управление уйдёт туда.

ЗащитаИдеяКак обходят

Почему Java избавлена от этого класса уязвимостей В Java нет арифметики указателей, каждый доступ к массиву проверяет границы (ArrayIndexOutOfBoundsException вместо порчи памяти), каждое приведение типа проверяется, память не освобождается вручную (нет «использования после освобождения»), стек нельзя адресовать. Эта безопасность памяти — главная причина, почему Microsoft и Google сообщают, что ~70% их уязвимостей — ошибки памяти в C/C++, а Java-сервисы страдают от другого: инъекций, десериализации, ошибок логики. Но граница прорывается там, где Java касается нативного: JNI, sun.misc.Unsafe, FFM API с --enable-native-access, нативные библиотеки (парсеры изображений, драйверы) — и сама JVM, написанная на C++.

17.3Побочные каналы: секреты утекают по времени

Даже корректная программа может выдать секрет не через данные, а через время работы, потребление энергии или состояние кэша. Простейший пример — сравнение строк, которое выходит на первом несовпадающем символе: сравнение с почти правильным токеном работает чуть дольше, и атакующий подбирает его посимвольно.

Атака по времени на сравнение секрета

Секрет — 6 символов из алфавита a…h. «Сервер» сравнивает посимвольно и выходит при первом несовпадении; каждый совпавший символ добавляет 1 условную единицу времени (плюс шум). Атакующий для каждой позиции пробует все символы и берёт самый «медленный».

  • В Java: сравнивать секреты (HMAC, токены, хэши паролей) только через MessageDigest.isEqual — он проверяет все байты независимо от первого расхождения. String.equals и Arrays.equals выходят рано (лаба 17.2).
  • Кэш как канал: атакующий в соседнем процессе или ВМ на том же ядре может определить, к каким линиям кэша обращалась жертва (Flush+Reload, Prime+Probe) — по времени своих обращений. Так извлекали ключи AES из табличных реализаций; аппаратный AES-NI (тема 16) не использует таблиц и защищён от этого.
  • Rowhammer: частое чтение одной строки DRAM вызывает переворот битов в соседних строках (тема 06) — так получали права ядра, меняя биты в таблицах страниц. Защита — ECC, обновление «соседей» в контроллерах памяти.

17.4Spectre и Meltdown: спекуляция против изоляции

Внеочередное ядро выполняет команды по предсказанному пути до того, как известно, нужны ли они (тема 05). Неверно предсказанные результаты отбрасываются из регистров — но не из кэша. Это превращает спекуляцию в способ читать запрещённое:

if (x < array1_size) {              // предсказатель «натренирован» на x в пределах
    y = array2[array1[x] * 4096];   // спекулятивно: x за границей → читается секретный байт,
}                                   // и он определяет, какая линия array2 попадёт в кэш
// затем атакующий измеряет время доступа к array2[0], array2[4096], … — быстрая линия раскрывает байт
  • Meltdown (2018, Intel): спекулятивное чтение памяти ядра из пользовательского режима — проверка прав происходила позже чтения. Защита — KPTI: при работе программы таблицы страниц ядра почти не отображены, а каждый вход в ядро переключает таблицы (поэтому системные вызовы подорожали, тема 10). Новые процессоры не уязвимы — в лабе 17.3 ядро сообщает «meltdown: Not affected».
  • Spectre v2: отравление предсказателя косвенных переходов, чтобы жертва спекулятивно прыгнула на нужный атакующему «гаджет». Защиты — retpoline, IBRS/eIBRS, IBPB при переключении контекста.
  • Что это значит для JVM: JIT вставляет барьеры против Spectre в критичных местах (маскирование индекса), браузеры изолировали сайты по процессам и огрубили таймеры (тот же класс атак из JavaScript). Для обычного серверного Java-кода главное следствие — более дорогие переходы в ядро и переключения контекста на уязвимых процессорах.

17.5Аппаратные средства доверия

  • TPM — хранение ключей и измерения загрузки (тема 09); на нём основано шифрование диска без ввода пароля.
  • Анклавы и конфиденциальные вычисления: Intel SGX (изолированная область памяти внутри процесса), AMD SEV-SNP и Intel TDX (шифрование всей памяти ВМ ключом, неизвестным гипервизору), ARM TrustZone и CCA. Облачный провайдер не может прочитать память вашей ВМ, а внешняя сторона — проверить, какой именно код в ней запущен (аттестация).
  • Шифрование памяти (Intel TME, AMD SME) — защищает от физического извлечения модулей DRAM.
  • Аппаратный генератор случайных чисел (RDRAND/RDSEED) — источник энтропии для ядра. Пользовательским программам надо брать случайность из ядра (getrandom, /dev/urandom, BCryptGenRandom): SecureRandom в Java делает именно это. java.util.Random — предсказуемый генератор: по нескольким выходам восстанавливается его состояние, для токенов и ключей он недопустим.

Лаба 17.1Переполнение буфера и канарейка стека20 мин

Перезаписать соседнюю переменную и адрес возврата через strcpy и посмотреть, как срабатывает защита.

  1. Создайте файл bof.c:
    #include <stdio.h>
#include <string.h>

struct account { char name[8]; int is_admin; };

void login(const char *input) {
    struct account acc = {"", 0};
    strcpy(acc.name, input);                         // длина не проверяется!
    printf("login: name='%s' is_admin=%d\n", acc.name, acc.is_admin);
}

void smash(const char *input) {
    char buf[8];
    strcpy(buf, input);                              // 40 байт в буфер на 8 — портим кадр и адрес возврата
    printf("smash: buf='%.8s…'\n", buf);
}

int main(int argc, char **argv) {
    setvbuf(stdout, NULL, _IONBF, 0);                // без буфера: иначе вывод пропадёт при аварии
    login("bob");
    login("AAAAAAAA\x01");                           // 8 букв + байт 0x01 залезает в is_admin
    smash(argv[1]);
    puts("вернулись из smash");
    return 0;
}
  2. Без защиты стека:
    docker run --rm -v "${PWD}:/lab" cs-lab sh -c "gcc -O0 -w -fno-stack-protector -o bof1 bof.c && ./bof1 AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA; echo код завершения \$?"
    Вывод (JDK 25.0.2)
    login: name='bob' is_admin=0
login: name='AAAAAAAA' is_admin=1
smash: buf='AAAAAAAA…'

код завершения 139
  3. Что напечатает второй login? Что произойдёт после smash — напечатается ли «вернулись из smash»?

    Второй вызов: is_admin=1 — девятый байт строки лёг в соседнее поле структуры, и «обычный пользователь» стал администратором, хотя код нигде не присваивает is_admin. smash печатает строку, а затем ret берёт из стека «адрес возврата» 0x4141414141414141 (байты 'A'), процессор прыгает в никуда — Segmentation fault, код 139 = 128 + 11 (SIGSEGV). «вернулись из smash» не печатается. Атакующий на месте 'A' положил бы нужный ему адрес.

  4. С канарейкой стека:
    docker run --rm -v "${PWD}:/lab" cs-lab sh -c "gcc -O0 -w -fstack-protector-all -o bof2 bof.c && ./bof2 AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA; echo код завершения \$?"
    Вывод (JDK 25.0.2)
    login: name='bob' is_admin=0
login: name='AAAAAAAA' is_admin=1
smash: buf='AAAAAAAA…'
*** stack smashing detected ***: terminated
код завершения 134
Aborted (core dumped)

    Эпилог smash обнаружил испорченную канарейку и вызвал __stack_chk_fail: «*** stack smashing detected ***», процесс завершён SIGABRT (код 134 = 128 + 6) до ret по поддельному адресу. Подмену is_admin внутри структуры канарейка не ловит — она стоит только перед адресом возврата. В Java аналог strcpy за границу — ArrayIndexOutOfBoundsException ещё до записи.

Лаба 17.2Атака по времени на сравнение15 мин

Измерить, зависит ли время сравнения массивов от длины совпавшего префикса.

  1. Создайте файл Timing.java:
    import java.security.MessageDigest;
import java.util.Arrays;

public class Timing {
    public static void main(String[] args) {
        int n = 1 << 20;                                  // большие массивы, чтобы разница была видна
        byte[] secret = new byte[n];
        for (int i = 0; i < n; i++) secret[i] = (byte) i;
        int[] prefixes = {0, n / 4, n / 2, n - 1};
        long sink = 0;
        for (int round = 0; round < 3; round++) {
            StringBuilder line = new StringBuilder("совпадает префикс:");
            for (int p : prefixes) {
                byte[] guess = secret.clone();
                guess[p] ^= 1;                            // первое расхождение — на позиции p
                long t0 = System.nanoTime();
                for (int k = 0; k < 200; k++) sink += Arrays.equals(secret, guess) ? 1 : 0;
                long t1 = System.nanoTime();
                for (int k = 0; k < 200; k++) sink += MessageDigest.isEqual(secret, guess) ? 1 : 0;
                long t2 = System.nanoTime();
                line.append(String.format("  %4d КБ: equals %5.1f мкс, isEqual %5.1f мкс |", p / 1024, (t1 - t0) / 200e3, (t2 - t1) / 200e3));
            }
            if (round == 2) System.out.println(line);
        }
        System.out.println("(" + sink + ")");
    }
}
  2. Как меняется время Arrays.equals и MessageDigest.isEqual в зависимости от позиции первого расхождения?
    javac Timing.java
java Timing
    Вывод (JDK 25.0.2)
    совпадает префикс:     0 КБ: equals   0.1 мкс, isEqual 746.2 мкс |   256 КБ: equals   6.2 мкс, isEqual 822.2 мкс |   512 КБ: equals  12.5 мкс, isEqual 885.4 мкс |  1023 КБ: equals  44.5 мкс, isEqual 753.9 мкс |
(0)

    Arrays.equals растёт почти линейно с длиной совпавшего префикса: при расхождении в первом байте — доли микросекунды, в последнем — десятки микросекунд (сравнение векторизовано, но выходит на первом отличии). MessageDigest.isEqual тратит одно и то же время независимо от позиции (здесь ~0,7 мс на мегабайт — он ещё и не векторизован: проходит весь массив байт за байтом, накапливая XOR различий). Безопасность здесь важнее скорости, а секреты на практике короткие — 32–64 байта. Для коротких HMAC разница — наносекунды, но по сети её вытягивают статистикой из тысяч запросов.

Лаба 17.4Случайные числа: Random против SecureRandom10 мин

Увидеть, почему java.util.Random предсказуем, и откуда берёт энтропию SecureRandom.

  1. Создайте файл Rng.java:
    import java.security.SecureRandom;
import java.util.Random;

public class Rng {
    public static void main(String[] args) throws Exception {
        Random r1 = new Random(42), r2 = new Random(42);
        System.out.println("Random(42):   " + r1.nextInt() + " " + r1.nextInt() + " " + r1.nextInt());
        System.out.println("ещё Random(42): " + r2.nextInt() + " " + r2.nextInt() + " " + r2.nextInt());

        // восстановление состояния по одному выходу nextInt(): перебор 2^16 младших бит
        Random victim = new Random(System.nanoTime());
        int out1 = victim.nextInt(), out2 = victim.nextInt();
        long mult = 0x5DEECE66DL, add = 0xBL, mask = (1L << 48) - 1;
        for (long low = 0; low < (1 << 16); low++) {
            long state = ((long) out1 << 16) + low & mask;
            long next = (state * mult + add) & mask;
            if ((int) (next >>> 16) == out2) {
                long predicted = (next * mult + add) & mask;
                System.out.println("по двум выходам предсказано следующее: " + (int) (predicted >>> 16)
                        + ", настоящее: " + victim.nextInt());
                break;
            }
        }
        SecureRandom sr = new SecureRandom();
        System.out.println("SecureRandom по умолчанию: " + sr.getAlgorithm() + ", провайдер " + sr.getProvider().getName());
        System.out.println("getInstanceStrong(): " + SecureRandom.getInstanceStrong().getAlgorithm());
    }
}
  2. Одинаковы ли последовательности у двух Random(42)? Удастся ли предсказать следующее число по двум выходам?
    javac Rng.java
java Rng
    Вывод (JDK 25.0.2)
    Random(42):   -1170105035 234785527 -1360544799
ещё Random(42): -1170105035 234785527 -1360544799
по двум выходам предсказано следующее: 559249585, настоящее: 559249585
SecureRandom по умолчанию: DRBG, провайдер SUN
getInstanceStrong(): Windows-PRNG

    Последовательности одинаковые: Random — детерминированный генератор, семя полностью задаёт выход. По двум значениям nextInt() перебором 65 536 вариантов недостающих младших битов состояние восстанавливается за миллисекунды, и следующее число предсказывается точно. SecureRandom на Windows по умолчанию — DRBG (криптографический генератор по NIST SP 800-90A) с энтропией из ОС (Windows-PRNG для «сильного»); на Linux — NativePRNG поверх /dev/urandom и getrandom.

17.8Самопроверка

Почему бит NX (запрет исполнения) не останавливает атаки переполнения буфера полностью?

  • его можно выключить из пользовательского режима
  • атакующий может не приносить свой код, а собрать нужное поведение из кусочков существующего кода (ROP)
  • он работает только на ARM
  • он защищает только кучу
Против ROP — ASLR, канарейки и аппаратные теневые стеки (CET).

Почему для сравнения HMAC в Java нужен MessageDigest.isEqual?

  • он быстрее
  • equals не работает с byte[]
  • он сравнивает хэши, а не байты
  • он работает постоянное время, а Arrays.equals выходит при первом расхождении и выдаёт по времени длину совпавшего префикса
Классическая атака по времени: подбор подписи посимвольно.

Что общего у Spectre и Meltdown?

  • спекулятивно выполненные команды оставляют следы в кэше, которые можно измерить по времени доступа
  • обе — ошибки в ОС
  • обе требуют физического доступа
  • обе исправлены в Java
Архитектурное состояние откатывается, микроархитектурное (кэш) — нет.
Как работает атака переполнения буфера на стеке и какие защиты против неё есть?

Запись за пределы локального массива перезаписывает соседние данные кадра и адрес возврата; при ret управление уходит на адрес атакующего. Защиты: NX (стек не исполняем), ASLR/PIE (адреса неизвестны), канарейка перед адресом возврата, аппаратные теневые стеки и проверка целей переходов (CET, PAC/BTI). Java недоступна для этой атаки, потому что проверяет границы массивов и не даёт адресовать стек.

Что такое побочный канал и как он связан с кэшем процессора?

Утечка информации не через результат, а через наблюдаемые побочные эффекты: время, энергию, состояние кэша. Если обращения программы к памяти зависят от секрета, атакующий, разделяющий с ней кэш, по времени своих обращений узнаёт, какие линии она использовала. Защита — код с постоянным временем и без зависящих от секрета обращений к памяти, аппаратные инструкции шифрования.

Почему java.util.Random нельзя использовать для токенов?

Это линейный конгруэнтный генератор с 48-битным состоянием: по паре выходов состояние восстанавливается, и все следующие значения предсказуемы. SecureRandom берёт энтропию из ядра ОС (а ядро — в том числе из аппаратного генератора) и использует криптографически стойкий алгоритм.
