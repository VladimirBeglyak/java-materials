Устройства, диски и файловые системы

Как процессор разговаривает с устройствами, почему SSD быстрее HDD в тысячу раз на случайном чтении и при этом не любит перезапись, как файловая система превращает имя файла в блоки на диске, и что на самом деле происходит после write(). Главный практический урок: успешный write не означает, что данные на диске — это знает каждая база данных и должен знать каждый, кто пишет в файл что-то важное.

12.1Как процессор работает с устройствами

  • Шина PCI Express соединяет процессор с видеокартой, NVMe-дисками, сетевыми картами. Это не общая шина, а набор последовательных линий «точка-точка»: PCIe 4.0 даёт ~2 ГБ/с на линию, NVMe-диск использует 4 линии (~8 ГБ/с), видеокарта — 16. PCIe 5.0 — вдвое больше.
  • Регистры устройства отображены в память (MMIO): драйвер пишет в «адрес памяти», а на самом деле — в регистр контроллера диска. Эти адреса доступны только ядру (тема 10).
  • DMA (прямой доступ к памяти): устройство само читает и пишет оперативную память, без участия процессора. Драйвер готовит в памяти описание операции («прочитай 8 блоков с адреса X диска в физические страницы Y, Z»), сообщает устройству и занимается другими делами. По завершении устройство посылает прерывание. Без DMA процессор копировал бы каждый байт сам.
  • IOMMU — MMU для устройств: ограничивает, к какой памяти устройство имеет доступ (защита от вредоносных устройств, проброс устройств в виртуальные машины).

Почему SSD «не любит» перезапись

Флеш-память читается и пишется страницами (4–16 КБ), а стирается только блоками (сотни страниц, мегабайты), и записать можно только в стёртую страницу. Поэтому SSD никогда не перезаписывает данные на месте: новая версия пишется в свободную страницу, а старая помечается недействительной. Контроллер ведёт таблицу «логический адрес → физическая страница» (FTL, flash translation layer — та же идея, что виртуальная память) и в фоне собирает мусор: переносит живые страницы из полупустых блоков и стирает блоки целиком.

  • Усиление записи (write amplification): ради записи 4 КБ контроллеру иногда приходится переписать больше — когда свободных блоков мало. Поэтому заполненный на 95% SSD медленнее на запись, чем на 50%.
  • TRIM: ОС сообщает диску, какие блоки файловой системы освобождены, чтобы он не таскал «мёртвые» данные при сборке мусора.
  • Ресурс: ячейка выдерживает от тысяч до десятков тысяч циклов стирания; контроллер равномерно распределяет износ (wear leveling).
  • NVMe — протокол, спроектированный под флеш: до 64 тысяч очередей команд, у каждого ядра своя очередь, без общей блокировки. Старые протоколы (SATA/AHCI) — одна очередь на 32 команды.

12.3Файловая система

Диск — массив блоков (секторы 512 Б или 4 КБ). Файловая система превращает его в дерево каталогов с именами, правами и временем изменения.

  • inode (индексный узел) — метаданные файла и где лежат его данные (в ext4 и XFS — экстенты: «блоки с N по M»). Имени в inode нет: имя — запись в каталоге, а каталог — особый файл со списком «имя → номер inode». Отсюда жёсткие ссылки (два имени одного inode) и то, что переименование внутри одной файловой системы атомарно и мгновенно — меняется только запись каталога.
  • Символическая ссылка — отдельный маленький файл с путём внутри; может указывать в никуда.
  • Открытый удалённый файл продолжает существовать, пока открыт: место на диске не освободится, хотя файла «нет» (классика: удалили гигантский лог, а диск по-прежнему полон — lsof | grep deleted).
  • Журналирование (ext4, XFS, NTFS): изменения метаданных сначала пишутся в журнал, затем на место. После сбоя питания файловая система проигрывает журнал и остаётся согласованной — без многочасового fsck. Журналируются по умолчанию метаданные, а не ваши данные.
  • Copy-on-write файловые системы (Btrfs, ZFS, APFS) никогда не перезаписывают блоки на месте — как SSD — и поэтому дешёво делают снимки (snapshots).
  • Windows NTFS хранит метаданные в главной таблице файлов (MFT); маленькие файлы целиком помещаются прямо в запись MFT.

12.4Page cache: что на самом деле делает write()

Ядро держит в свободной оперативной памяти кэш страниц файлов (page cache) — именно поэтому free в Linux показывает почти всю память «занятой» в buff/cache: она занята полезным кэшем и отдаётся программам по первому требованию.

Запись — это копирование в память ядра. Быстро, но ещё не надёжно.

Все процессы видят файл через один и тот же page cache.

Ядро сбрасывает грязные страницы позже, большими порциями — это выгодно диску.

Всё, что не дошло до диска, теряется. Это нормальное поведение, а не ошибка ОС.

Именно так устроены базы данных: журнал упреждающей записи (WAL) — каждая транзакция дописывается в конец журнала и сбрасывается fsync перед ответом «закоммичено», а сами страницы таблиц пишутся позже (пособие «Реляционные БД»). Kafka по умолчанию fsync не делает вовсе и полагается на репликацию: копия на трёх машинах надёжнее, чем сброс на одну.

  • Readahead: при последовательном чтении ядро заранее читает следующие блоки — аналог предвыборки кэша процессора (тема 06).
  • O_DIRECT: чтение и запись мимо page cache, прямо в буфер программы через DMA — для баз данных со своим кэшем. В Java — ExtendedOpenOption.DIRECT.
  • Zero-copy: FileChannel.transferTo в сокет превращается в sendfile — данные идут из page cache в сетевую карту, не копируясь в память процесса (тема 13).

Лаба 12.1Цена fsync15 мин

Сравнить запись маленьких записей «как журнал» с принудительным сбросом на диск и без него.

  1. Создайте файл Journal.java:
    import java.nio.ByteBuffer;
import java.nio.channels.FileChannel;
import java.nio.file.*;

public class Journal {
    public static void main(String[] args) throws Exception {
        Path f = Path.of("journal.log");
        ByteBuffer record = ByteBuffer.allocate(100);
        for (int round = 0; round < 2; round++) {
            for (boolean sync : new boolean[] {false, true}) {
                try (FileChannel ch = FileChannel.open(f, StandardOpenOption.CREATE, StandardOpenOption.WRITE,
                        StandardOpenOption.TRUNCATE_EXISTING)) {
                    int n = 1000;
                    long t0 = System.nanoTime();
                    for (int i = 0; i < n; i++) {
                        record.clear();
                        ch.write(record);
                        if (sync) ch.force(false);                 // fdatasync / FlushFileBuffers
                    }
                    double us = (System.nanoTime() - t0) / 1000.0 / n;
                    System.out.printf("%s %8.1f мкс на запись → %,9.0f записей в секунду%n",
                            sync ? "write + force:" : "только write: ", us, 1e6 / us);
                }
            }
        }
        Files.delete(f);
    }
}
  2. Во сколько раз force замедлит запись? Сколько «коммитов» в секунду выдержит такой журнал?
    javac Journal.java
java Journal
    Вывод (JDK 25.0.2)
    только write:       6.1 мкс на запись →   163,313 записей в секунду
write + force:   1585.1 мкс на запись →       631 записей в секунду
только write:       1.5 мкс на запись →   647,836 записей в секунду
write + force:   1843.9 мкс на запись →       542 записей в секунду

    Простой write — единицы микросекунд: копирование в page cache. С force — около 1,5 мс на Windows (в WSL 2 — около 3,5 мс через виртуальный диск): в сотни и тысячи раз медленнее, всего несколько сотен сохранённых записей в секунду. Поэтому базы данных группируют коммиты (group commit): один fsync на пачку транзакций разных клиентов, а брокеры вроде Kafka вместо fsync полагаются на репликацию.

Поэкспериментируйте
  • Откройте файл с StandardOpenOption.DSYNC и уберите force.
    Скорость будет как у варианта с force: каждый write теперь сам ждёт диска (флаг O_DSYNC / FILE_FLAG_WRITE_THROUGH).

    echo 3 > /proc/sys/vm/drop_caches выбрасывает чистые страницы page cache (и кэши метаданных) — нужен привилегированный контейнер, и действует это на всю виртуальную машину WSL. Перед этим sync сбрасывает грязные страницы, иначе их нельзя выбросить.

  2. Во сколько раз второе чтение того же файла быстрее первого?

    Первое чтение идёт с диска (здесь NVMe через виртуальный диск WSL — около 2–2,5 ГБ/с), второе — из page cache: 10+ ГБ/с, примерно в пять раз быстрее, и упирается уже в копирование памяти. На HDD разница была бы в десятки раз. Cached в /proc/meminfo вырос на прочитанный файл — память «занята» кэшем, но будет отдана по первому требованию.

12.7Самопроверка

Что гарантирует успешный write() в файл в Linux?

  • данные на диске
  • данные в кэше диска
  • данные в page cache ядра; на диск они попадут позже
  • ничего — запись может не выполниться
Для сохранности — fsync/fdatasync (в Java FileChannel.force). Другие процессы при этом уже видят новые данные.

Почему переименование файла внутри одной файловой системы атомарно и мгновенно даже для файла в 100 ГБ?

  • меняется только запись каталога «имя → inode», данные не трогаются
  • ФС копирует файл в фоне
  • rename выполняет диск
  • это не так
На этом построен паттерн «записать во временный файл и переименовать».

Почему SSD не перезаписывает данные на месте?

  • так быстрее читать
  • из-за шифрования
  • ОС запрещает
  • флеш-память пишется только в стёртые страницы, а стирается крупными блоками, поэтому новая версия пишется в свободное место, а таблица FTL переназначает адрес
Отсюда сборка мусора контроллера, усиление записи и TRIM.

Удалили лог-файл на 50 ГБ, а место на диске не освободилось. Почему?

  • файл в корзине
  • файл всё ещё открыт процессом: inode живёт, пока на него есть ссылки и открытые дескрипторы
  • ФС не поддерживает удаление
  • нужен TRIM
lsof покажет его как (deleted). Освободится после закрытия или перезапуска процесса; либо обрезать через /proc/<pid>/fd.
Как данные попадают с диска в память программы?

read → ядро проверяет page cache. Если страницы нет — блочный слой формирует запрос, драйвер кладёт команду в очередь NVMe-контроллера; контроллер через DMA пишет данные в страницу page cache и посылает прерывание. Ядро будит ожидающий поток, копирует данные в буфер программы (или при mmap просто отображает страницу). Повторное чтение берётся из page cache без диска.

Как надёжно сохранить файл, чтобы после сбоя был либо старый, либо новый вариант?

Записать содержимое во временный файл в том же каталоге, вызвать fsync (FileChannel.force), атомарно переименовать на место старого (Files.move с ATOMIC_MOVE), затем fsync каталога, чтобы сохранилась запись о переименовании. Прямая перезапись на месте может оставить после сбоя наполовину записанный файл.

Почему flush() не гарантирует сохранность данных?

flush выталкивает данные из буфера Java (BufferedOutputStream и т. п.) в ядро системным вызовом write. Дальше они в page cache и будут записаны на диск позже. Для сохранности нужен sync/force — fsync в ядре.

Что такое page cache и почему «свободной памяти» в Linux всегда мало?

Кэш содержимого файлов в оперативной памяти ядра. Ядро использует всю незанятую программами память под кэш, потому что пустая память бесполезна, а кэшированная ускоряет повторные чтения. При нехватке памяти кэш вытесняется. Смотреть надо на «available», а не на «free».
