От исходника до процесса: компиляция, линковка, загрузка

Исходный текст становится процессом через несколько преобразований: компилятор превращает его в машинный код с «дырами» на месте внешних функций, компоновщик связывает куски и библиотеки в исполняемый файл, загрузчик ядра и динамический загрузчик раскладывают его по адресному пространству и подключают разделяемые библиотеки. 14.1Цепочка сборки C

ШагКомандаВход → выходЧто делает
препроцессорgcc -E.c → .iподставляет #include (текст заголовков), раскрывает #define, условная компиляция #ifdef
компиляторgcc -S.i → .sразбор, типы, оптимизация (тема 03), генерация ассемблера под целевую ISA

Объектный файл — машинный код одного файла исходника, который ещё нельзя запустить: вызов printf в нём — команда call с нулевым адресом и запись в таблице релокаций: «по смещению 0x1a вставь адрес символа printf». В таблице символов — что файл определяет (T main) и что ему нужно извне (U printf). Компоновщик сводит эти таблицы: ошибка «undefined reference to foo» — символ нужен, но никто его не определил; «multiple definition» — определён дважды.

Сравните с Java javac делает только первые два шага, и то частично: class-файл — не машинный код, а байткод, а ссылки на другие классы — не адреса, а символические имена в пуле констант (JVM, тема 02). Компоновки как отдельного шага нет: разрешение ссылок — часть загрузки класса в JVM и происходит лениво, при первом использовании (JVM, тема 06). Ошибка «undefined reference» в Java проявляется как NoClassDefFoundError или NoSuchMethodError — во время работы, а не сборки.

14.2Исполняемый файл: ELF и PE

Linux использует формат ELF (Executable and Linkable Format), Windows — PE (.exe, .dll), macOS — Mach-O. Устроены они похоже:

  • заголовок: магическое число (7F 45 4C 46 — «\x7FELF»; у PE — «MZ»), архитектура, точка входа;
  • секции — для компоновщика и отладчика: .text (код), .rodata (константы, строковые литералы), .data (инициализированные глобальные переменные), .bss (нулевые глобальные — в файле не занимают места), .symtab, отладочная информация .debug_*, таблицы раскрутки .eh_frame (тема 04);
  • сегменты (program headers) — для загрузчика: «отобрази этот кусок файла по такому адресу с такими правами» — R-X для кода, RW- для данных, INTERP — путь к динамическому загрузчику, DYNAMIC — список нужных библиотек.

Секции и сегменты — две точки зрения на один файл: компоновщику важна логическая разбивка, загрузчику — что и с какими правами отобразить в память (тема 08). Именно поэтому в /proc/<pid>/maps программа видна тремя-четырьмя областями с разными правами.

Как работает вызов функции из .so. Адрес библиотеки неизвестен до запуска (ASLR кладёт её в случайное место), а код программы — только для чтения и общий. Поэтому вызов printf идёт через трамплин в PLT (procedure linkage table), а тот прыгает по адресу из таблицы GOT (global offset table) в области данных. Динамический загрузчик заполняет GOT адресами — сразу при запуске или лениво при первом вызове. Код при этом не меняется — только данные.

Кто находит библиотеки. В сегменте INTERP указан динамический загрузчик /lib64/ld-linux-x86-64.so.2. Ядро запускает его, а он читает список NEEDED, ищет библиотеки по RUNPATH, LD_LIBRARY_PATH, кэшу /etc/ld.so.cache и стандартным каталогам, отображает их, выполняет релокации и конструкторы, и только потом передаёт управление программе. Ошибка «error while loading shared libraries: libX.so: cannot open shared object file» — это он.

JVM совмещает всё: шаблонный интерпретатор (сам — машинный код, сгенерированный при старте, тема 09), два JIT-компилятора (C1 и C2) и возможность AOT — архив AOT cache проекта Leyden или Native Image (JVM, тема 16, тема 20). JIT-компилятор — это компоновщик и загрузчик в одном: он кладёт машинный код в code cache и сам «исправляет адреса» (патчит вызовы) при деоптимизации и перекомпиляции.

Нативный код из Java: JNI требует написать C-обёртку и собрать .so/.dll; Foreign Function & Memory API (Java 22) находит функцию в загруженной библиотеке по имени (как dlsym) и вызывает её по ABI платформы (тема 04) без единой строки C — лаба 14.4.

Лаба 14.4Вызов libc из Java через FFM API15 мин

Найти функцию в загруженной библиотеке по имени и вызвать её по ABI платформы — без JNI и без C-кода.

  1. Создайте файл Ffm.java:
    import java.lang.foreign.*;
import java.lang.invoke.MethodHandle;

public class Ffm {
    public static void main(String[] args) throws Throwable {
        Linker linker = Linker.nativeLinker();                       // знает ABI текущей платформы (тема 04)
        SymbolLookup libc = linker.defaultLookup();                  // как dlsym по уже загруженным библиотекам

        MethodHandle getpid = linker.downcallHandle(libc.find("getpid").orElseThrow(),
                FunctionDescriptor.of(ValueLayout.JAVA_INT));
        MethodHandle strlen = linker.downcallHandle(libc.find("strlen").orElseThrow(),
                FunctionDescriptor.of(ValueLayout.JAVA_LONG, ValueLayout.ADDRESS));

        System.out.println("адрес функции getpid в памяти: " + libc.find("getpid").orElseThrow());
        System.out.println("getpid() из libc = " + (int) getpid.invokeExact()
                + ", ProcessHandle.pid() = " + ProcessHandle.current().pid());
        try (Arena arena = Arena.ofConfined()) {
            MemorySegment s = arena.allocateFrom("привет");          // строка C в нативной памяти, UTF-8 + '\0'
            System.out.println("strlen(\"привет\") = " + (long) strlen.invokeExact(s) + " байт");
        }
    }
}
    docker run --rm -v "${PWD}:/lab" cs-lab java --enable-native-access=ALL-UNNAMED Ffm.java
    Вывод (JDK 25.0.2)

strlen("привет") = 12 байт
  2. Совпадут ли PID от libc и от Java? Что вернёт strlen("привет")?

    PID совпадут — это один и тот же процесс; адрес getpid — где-то в области libc.so.6 (тема 08, карта памяти). strlen вернёт 12: C-функция считает байты до нуля, а «привет» в UTF-8 — 12 байт (тема 01). Флаг --enable-native-access разрешает «ограниченные» операции FFM без предупреждения: вызов нативного кода может обрушить JVM, и это явный выбор приложения.

14.7Самопроверка

Что значит ошибка компоновщика «undefined reference to foo»?

  • синтаксическая ошибка в foo
  • foo объявлена дважды
  • какой-то объектный файл использует символ foo, но ни один из компонуемых файлов и библиотек его не определяет
  • библиотека не найдена при запуске
Ошибка при запуске — уже от динамического загрузчика: «cannot open shared object file» или «symbol lookup error».

Почему код разделяемой библиотеки можно держать в памяти одной копией на все процессы, хотя адреса у всех разные?

  • код позиционно-независимый, а адреса внешних функций и данных лежат в таблице GOT в собственной (записываемой) памяти каждого процесса
  • все процессы загружают её по одному адресу
  • ядро патчит код при переключении процессов
  • это не так, у каждого своя копия
Меняются только данные (GOT), код остаётся неизменным и общим.

Что ядро делает при execve с уже открытыми дескрипторами процесса?

  • закрывает все
  • копирует в новый процесс
  • передаёт ld.so
  • оставляет открытыми, кроме помеченных close-on-exec
Так перенаправления shell (stdin/stdout) достаются новой программе. Поэтому Java открывает свои файлы с O_CLOEXEC — чтобы они не утекали в запускаемые процессы.
Что внутри объектного файла и что делает компоновщик?

Объектный файл содержит секции машинного кода и данных одного модуля, таблицу символов (что определено и что требуется) и релокации — места, куда нужно подставить адреса внешних символов. Компоновщик объединяет секции всех модулей, назначает им адреса, находит определение каждого требуемого символа (в объектных файлах и библиотеках) и исправляет адреса по релокациям, создавая исполняемый файл или разделяемую библиотеку.

Как запускается динамически скомпонованная программа?

execve: ядро проверяет формат, создаёт новое адресное пространство, отображает сегменты программы и динамического загрузчика из INTERP, строит стек с argv, envp и auxv и передаёт управление ld.so. Загрузчик находит и отображает библиотеки из NEEDED, выполняет релокации, заполняет GOT, вызывает конструкторы и прыгает на точку входа программы, откуда libc вызывает main.

Чем модель Java отличается от C с точки зрения сборки и связывания?

javac порождает переносимый байткод с символическими ссылками; отдельного компоновщика нет. Загрузка, проверка и связывание классов происходят во время работы, лениво, по первому обращению; машинный код создаёт JIT по профилю. Это даёт переносимость и динамические возможности (загрузка классов, прокси, агенты), но переносит часть ошибок связывания со сборки на время выполнения и добавляет прогрев.
