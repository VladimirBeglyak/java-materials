14.1Цепочка сборки C

С нуля: перевод книги по главам

Большую книгу переводят несколько переводчиков, каждый — свою главу. В главе 3 есть фраза «как описано в главе 7, стр. ???» — переводчик третьей главы ещё не знает, на какой странице будет седьмая глава. Он оставляет пометку. Потом редактор собирает все главы в одну книгу, проставляет номера страниц и заполняет все «???». Так же устроена сборка программы: компилятор переводит каждый файл исходника в машинный код с «дырами» на месте внешних функций, а компоновщик (linker) собирает куски вместе и заполняет адреса.

Строго

ШагКомандаВход → выходЧто делает

Объектный файл — машинный код одного файла исходника, который ещё нельзя запустить: вызов printf в нём — команда call с нулевым адресом и запись в таблице релокаций (relocation — «перемещение», пометка «здесь надо подставить адрес»): «по смещению 0x1a вставь адрес символа printf». В таблице символов (символ — имя функции или глобальной переменной) — что файл определяет (T main, T — text, код) и что ему нужно извне (U printf, U — undefined, «не определено»). Компоновщик сводит эти таблицы: ошибка «undefined reference to foo» («ссылка на неопределённое foo») — символ нужен, но никто его не определил; «multiple definition» («повторное определение») — определён дважды.

Сравните с Java javac делает только первые два шага, и то частично: class-файл — не машинный код, а байткод, а ссылки на другие классы — не адреса, а символические имена в пуле констант (таблице строк и имён внутри class-файла) (JVM, тема 02). Компоновки как отдельного шага нет: разрешение ссылок — часть загрузки класса в JVM и происходит лениво, при первом использовании (JVM, тема 06). Ошибка «undefined reference» в Java проявляется как NoClassDefFoundError («нет определения класса») или NoSuchMethodError («нет такого метода») — во время работы, а не сборки.
Главное Сборка C: препроцессор → компилятор → ассемблер → компоновщик. Объектный файл — машинный код с «дырами» и списком нужных имён, компоновщик заполняет адреса. В Java ссылки разрешаются не при сборке, а при загрузке классов, поэтому ошибки видны во время работы.

14.2Исполняемый файл: ELF и PE

Исполняемый файл — не просто машинный код, а «посылка» с описью: где код, где данные, с какого адреса начинать. Linux использует формат ELF (Executable and Linkable Format — «формат исполняемых и компонуемых файлов»), Windows — PE (Portable Executable; .exe, .dll), macOS — Mach-O (Mach object, по имени ядра Mach). Устроены они похоже:

  • заголовок: магическое число (первые байты, по которым узнают формат) (7F 45 4C 46 — «\x7FELF»; у PE — «MZ», инициалы Марка Збиковского, автора формата), архитектура, точка входа (адрес первой команды);
  • секции — для компоновщика и отладчика: .text (код), .rodata (константы, строковые литералы), .data (инициализированные глобальные переменные), .bss (Block Started by Symbol: нулевые глобальные — в файле не занимают места), .symtab (symbol table, таблица символов), отладочная информация .debug_*, таблицы раскрутки .eh_frame (тема 04);
  • сегменты (program headers, «заголовки программы») — для загрузчика: «отобрази этот кусок файла по такому адресу с такими правами» — R-X (чтение и исполнение) для кода, RW- (чтение и запись) для данных, INTERP — путь к динамическому загрузчику, DYNAMIC — список нужных библиотек.

Секции и сегменты — две точки зрения на один файл: компоновщику важна логическая разбивка, загрузчику — что и с какими правами отобразить в память (тема 08). Именно поэтому в /proc/<pid>/maps программа видна тремя-четырьмя областями с разными правами.

Главное Исполняемый файл (ELF, PE, Mach-O) — заголовок, секции для компоновщика и отладчика, сегменты для загрузчика с правами доступа.

14.3Библиотеки: статические и динамические

Библиотека — готовый код, которым пользуются многие программы (например, функция печати printf). Её можно вклеить в программу при сборке (статическая) или подключать при каждом запуске из общего файла (динамическая) — как переписать нужные страницы из справочника себе в тетрадь или пользоваться общим справочником в библиотеке.

Как работает вызов функции из .so. Адрес библиотеки неизвестен до запуска (ASLR — Address Space Layout Randomization, «случайное размещение адресного пространства» — кладёт её в случайное место), а код программы — только для чтения и общий. Поэтому вызов printf идёт через трамплин (маленький переходник) в PLT (Procedure Linkage Table — «таблица связывания процедур»), а тот прыгает по адресу из таблицы GOT (Global Offset Table — «таблица глобальных смещений») в области данных. Динамический загрузчик заполняет GOT адресами — сразу при запуске или лениво при первом вызове. Код при этом не меняется — только данные.

Кто находит библиотеки. В сегменте INTERP указан динамический загрузчик /lib64/ld-linux-x86-64.so.2. Ядро запускает его, а он читает список NEEDED, ищет библиотеки по RUNPATH (путь, записанный в самом файле), переменной окружения LD_LIBRARY_PATH (настройке, передаваемой программе при запуске), кэшу /etc/ld.so.cache и стандартным каталогам, отображает их, выполняет релокации и конструкторы (код инициализации библиотек), и только потом передаёт управление программе. Ошибка «error while loading shared libraries: libX.so: cannot open shared object file» — это он.

Главное Статическая библиотека вклеивается в программу, динамическая подключается при запуске и лежит в памяти в одном экземпляре. Вызов функции из динамической библиотеки идёт через PLT и GOT, адреса которой заполняет динамический загрузчик ld.so.

Главное execve заменяет программу в процессе: ядро отображает сегменты файла в память, готовит стек и передаёт управление динамическому загрузчику, тот подключает библиотеки и вызывает программу. Адреса случайны (ASLR) ради защиты.

JVM совмещает всё: шаблонный интерпретатор (template interpreter: для каждой команды байткода — заранее сгенерированный кусок машинного кода) (сам — машинный код, сгенерированный при старте, тема 09), два JIT-компилятора (C1 и C2) и возможность AOT — архив AOT cache проекта Leyden или Native Image (JVM, тема 16, тема 20). JIT-компилятор — это компоновщик и загрузчик в одном: он кладёт машинный код в code cache и сам «исправляет адреса» (патчит вызовы) при деоптимизации (откате от оптимизированного кода к интерпретатору, когда предположение JIT оказалось неверным) и перекомпиляции.

Нативный код из Java (код на C/C++, скомпилированный под процессор): JNI (Java Native Interface) требует написать C-обёртку и собрать .so/.dll; Foreign Function & Memory API (Java 22) находит функцию в загруженной библиотеке по имени (как dlsym — dynamic load symbol, «найти символ в библиотеке») и вызывает её по ABI платформы (тема 04) без единой строки C — лаба 14.4.

Главное AOT — быстрый старт, интерпретатор — переносимость, JIT — переносимость и скорость по реальному профилю ценой прогрева. JVM совмещает все три подхода.

    java — около 16 КБ, libjvm.so — около 30 МБ. В NEEDED лаунчера — только libjli.so (Java Launcher Infrastructure) и libc.so.6, а RPATH — $ORIGIN:$ORIGIN/../lib: искать библиотеки относительно каталога самого файла, поэтому JDK работает из любого места без установки. libjvm.so в NEEDED нет: лаунчер сам выбирает вариант VM (server, client) и загружает её во время работы через dlopen — следующий шаг это покажет.

Лаба 14.4Вызов libc из Java через FFM API15 мин

Найти функцию в загруженной библиотеке по имени и вызвать её по ABI платформы — без JNI и без C-кода.

  1. Создайте файл Ffm.java:
    import java.lang.foreign.*;
import java.lang.invoke.MethodHandle;

public class Ffm {
    public static void main(String[] args) throws Throwable {
        Linker linker = Linker.nativeLinker();                       // знает ABI текущей платформы (тема 04)
        SymbolLookup libc = linker.defaultLookup();                  // как dlsym по уже загруженным библиотекам

        MethodHandle getpid = linker.downcallHandle(libc.find("getpid").orElseThrow(),
                FunctionDescriptor.of(ValueLayout.JAVA_INT));
        MethodHandle strlen = linker.downcallHandle(libc.find("strlen").orElseThrow(),
                FunctionDescriptor.of(ValueLayout.JAVA_LONG, ValueLayout.ADDRESS));

        System.out.println("адрес функции getpid в памяти: " + libc.find("getpid").orElseThrow());
        System.out.println("getpid() из libc = " + (int) getpid.invokeExact()
                + ", ProcessHandle.pid() = " + ProcessHandle.current().pid());
        try (Arena arena = Arena.ofConfined()) {
            MemorySegment s = arena.allocateFrom("привет");          // строка C в нативной памяти, UTF-8 + '\0'
            System.out.println("strlen(\"привет\") = " + (long) strlen.invokeExact(s) + " байт");
        }
    }
}
    docker run --rm -v "${PWD}:/lab" cs-lab java --enable-native-access=ALL-UNNAMED Ffm.java
    Вывод (JDK 25.0.2)
    адрес функции getpid в памяти: MemorySegment{ kind: native, address: 0x7490a40da700, byteSize: 0 }
getpid() из libc = 1, ProcessHandle.pid() = 1
strlen("привет") = 12 байт
  2. Совпадут ли PID от libc и от Java? Что вернёт strlen("привет")?

    PID совпадут — это один и тот же процесс; адрес getpid — где-то в области libc.so.6 (тема 08, карта памяти). strlen вернёт 12: C-функция считает байты до нуля, а «привет» в UTF-8 — 12 байт (тема 01). Флаг --enable-native-access разрешает «ограниченные» операции FFM без предупреждения: вызов нативного кода может обрушить JVM, и это явный выбор приложения.

14.8Самопроверка

Что значит ошибка компоновщика «undefined reference to foo»?

  • синтаксическая ошибка в foo
  • foo объявлена дважды
  • какой-то объектный файл использует символ foo, но ни один из компонуемых файлов и библиотек его не определяет
  • библиотека не найдена при запуске
Ошибка при запуске — уже от динамического загрузчика: «cannot open shared object file» или «symbol lookup error».

Почему код разделяемой библиотеки можно держать в памяти одной копией на все процессы, хотя адреса у всех разные?

  • код позиционно-независимый, а адреса внешних функций и данных лежат в таблице GOT в собственной (записываемой) памяти каждого процесса
  • все процессы загружают её по одному адресу
  • ядро патчит код при переключении процессов
  • это не так, у каждого своя копия
Меняются только данные (GOT), код остаётся неизменным и общим.

Что ядро делает при execve с уже открытыми дескрипторами процесса?

  • закрывает все
  • копирует в новый процесс
  • передаёт ld.so
  • оставляет открытыми, кроме помеченных close-on-exec
Так перенаправления shell (stdin/stdout) достаются новой программе. Поэтому Java открывает свои файлы с O_CLOEXEC — чтобы они не утекали в запускаемые процессы.

Что означает ошибка компоновщика «undefined reference to foo»?

  • Функция foo используется, но ни один объектный файл или библиотека её не определяет
  • В foo синтаксическая ошибка
  • foo определена дважды
  • Не хватает памяти
Компоновщик не смог разрешить символ. В Java аналог — NoClassDefFoundError во время работы.

Чем хороша динамическая библиотека?

  • Программа запускается без неё
  • Файл программы самодостаточен
  • Её код лежит в памяти в одном экземпляре на все процессы и обновляется заменой одного файла
  • Она быстрее статической
Цена — нужна совместимая версия библиотеки в системе.
Что внутри объектного файла и что делает компоновщик?

Объектный файл содержит секции машинного кода и данных одного модуля, таблицу символов (что определено и что требуется) и релокации — места, куда нужно подставить адреса внешних символов. Компоновщик объединяет секции всех модулей, назначает им адреса, находит определение каждого требуемого символа (в объектных файлах и библиотеках) и исправляет адреса по релокациям, создавая исполняемый файл или разделяемую библиотеку.

Как запускается динамически скомпонованная программа?

execve: ядро проверяет формат, создаёт новое адресное пространство, отображает сегменты программы и динамического загрузчика из INTERP, строит стек с argv, envp и auxv и передаёт управление ld.so. Загрузчик находит и отображает библиотеки из NEEDED, выполняет релокации, заполняет GOT, вызывает конструкторы и прыгает на точку входа программы, откуда libc вызывает main.

Чем модель Java отличается от C с точки зрения сборки и связывания?

javac порождает переносимый байткод с символическими ссылками; отдельного компоновщика нет. Загрузка, проверка и связывание классов происходят во время работы, лениво, по первому обращению; машинный код создаёт JIT по профилю. Это даёт переносимость и динамические возможности (загрузка классов, прокси, агенты), но переносит часть ошибок связывания со сборки на время выполнения и добавляет прогрев.
