19.2Оценки на салфетке

На собеседованиях по проектированию систем и в инженерной работе ценится умение быстро оценить порядок величины. Попробуйте ответить сами, затем раскройте решение.

Сколько времени займёт суммирование массива из 10⁹ int на одном ядре?

4 ГБ данных. Последовательное чтение упирается в полосу памяти одного ядра ~10–20 ГБ/с → 0,2–0,4 с. Вычисления (векторное сложение, 8 int за команду) быстрее памяти. Ответ: около 0,3 с; на нескольких ядрах — до предела полосы памяти всей машины.

Сколько памяти займут 10 000 платформенных потоков и 1 000 000 виртуальных?

Платформенные: резерв адресов 10 000 × 1 МБ = 10 ГБ, реально занятые стеки — по десяткам КБ, то есть сотни МБ, плюс структуры ядра. Виртуальные: в куче по реальной глубине стека, ~1–10 КБ на ожидающий поток → 1–10 ГБ кучи на миллион. Платформенный миллион невозможен: столько задач ядро и адресное пространство не выдержат.

Поиск ключа в HashMap на 10⁸ записей: сколько промахов кэша и сколько времени?

Таблица бакетов (~1 ГБ ссылок), узлы, ключи — всё вне кэша. Цепочка: бакет → узел → ключ (equals) → значение — 3–4 зависимых промаха по ~100 нс плюс промахи TLB. Около 0,3–0,5 мкс на поиск; на маленькой «горячей» карте — десятки наносекунд.

Сервис пишет в журнал каждый запрос с fsync. Каков предел RPS на одном SSD?

fsync ~1–3 мс → 300–1000 последовательных сбросов в секунду. Чтобы обработать больше, группируют записи (group commit: один fsync на пачку), пишут асинхронно или реплицируют вместо fsync.

Сколько системных вызовов сделает побайтовое чтение файла в 100 МБ без буфера и с BufferedInputStream?

Без буфера — 10⁸ вызовов по ~0,2–1 мкс = 20–100 с. С буфером 8 КБ — ~12 800 вызовов, доли секунды; остальное — чтение из массива в памяти процесса.

Под с limits.cpu: 2, JVM на старте компилирует и собирает мусор в 20 потоков. Сколько длится «окно работы» в периоде 100 мс?

Квота 200 мс CPU на период; 20 потоков выжгут её за ~10 мс, затем группа заморожена ~90 мс. Старт растягивается в разы, первые запросы ловят паузы — поэтому для JVM лимиты CPU ставят с запасом или не ставят вовсе.

19.3Разбор инцидентов

Инцидент 1. p99 задержки — 300 мс, средняя загрузка CPU пода — 25%, GC-паузы короткие.

Причина: троттлинг cgroup — на всплесках параллельных запросов квота cpu.max выгорает за часть периода (тема 15). Как увидеть: nr_throttled и throttled_usec в /sys/fs/cgroup/cpu.stat, метрика container_cpu_cfs_throttled_periods_total. Решение: поднять или убрать limits.cpu, ограничить параллелизм, снизить число потоков GC/JIT.

Инцидент 2. Под перезапускается с кодом 137 и OOMKilled, а куча по логам GC заполнена на 60%.

Причина: лимит памяти превышен не кучей: metaspace, стеки сотен потоков, прямые буферы (Netty), code cache, malloc-арены glibc (темы 08, 15). Как увидеть: NMT (jcmd VM.native_memory summary), RSS процесса против -Xmx. Решение: MaxRAMPercentage 60–75%, ограничить MaxDirectMemorySize, число потоков, MALLOC_ARENA_MAX.

Инцидент 3. После распараллеливания подсчёта статистики на 8 потоков программа замедлилась вдвое.

Причина: счётчики потоков в одном long[] или общий AtomicLong — ложное разделение и пинг-понг кэш-линии (тема 07). Решение: локальные счётчики в потоке с суммированием в конце, LongAdder, разнесение на 128 байт.

Инцидент 4. Тесты проходят на ноутбуках разработчиков, а на серверах Graviton изредка видны «наполовину созданные» объекты конфигурации.

Причина: публикация объекта через обычное поле без синхронизации. x86 (TSO) почти не переставляет записи, ARM переставляет: другой поток видит ссылку раньше полей (тема 07). Решение: volatile-ссылка, final-поля, безопасная публикация.

Инцидент 5. После отключения питания в файле состояния — нули или старая версия, хотя приложение «успешно записало».

Причина: write и flush довели данные только до page cache (тема 12). Решение: запись во временный файл, force, атомарный rename, force каталога; либо хранить состояние в базе данных с WAL.

Инцидент 6. Обработка CSV на 2 ГБ идёт 20 минут, профилировщик показывает время в нативном методе readBytes.

Причина: чтение FileInputStream.read() по байту — системный вызов на каждый байт (тема 10). Решение: BufferedReader/Files.lines, крупные блоки; время упадёт до секунд.

Инцидент 7. Под нагрузкой сервис падает с «Too many open files».

Причина: исчерпан лимит дескрипторов (ulimit -n): утечка незакрытых соединений или файлов, либо лимит слишком мал для числа соединений (тема 13). Как увидеть: ls /proc/<pid>/fd | wc -l, lsof. Решение: try-with-resources, пул соединений, поднять лимит.

Инцидент 8. Диск заполнен на 100%, но du показывает 40 ГБ из 100 ГБ.

Причина: удалённый лог-файл всё ещё открыт процессом — inode жив (тема 12). Как увидеть: lsof | grep deleted. Решение: перезапуск или обрезка через /proc/<pid>/fd/N; ротация логов с переоткрытием файла.

    На Windows: 18 логических процессоров, куча до ~8 ГБ (25% от 32 ГБ памяти), сборщик G1 («G1 Young Generation»), файлов /sys нет — кэши и cgroups не видны («—»), nanoTime ~25 нс (счётчик QueryPerformanceCounter). 19.5Итоговый тест

Почему переполнение int в Java не вызывает исключение?

  • JVM его не замечает из-за JIT
  • это ошибка спецификации
  • сложение в дополнительном коде идёт по модулю 2³², процессор лишь выставляет флаг переполнения, а Java его не проверяет
  • переполнения в Java не бывает
Math.addExact использует этот флаг явно.

Что из этого хранится в кадре Java-метода?

  • ссылки на объекты и значения примитивных локальных переменных
  • сами объекты, созданные в методе
  • static-поля класса
  • байткод метода
Объекты — в куче, static-поля — в объекте Class (куча), байткод — в metaspace.

Что из этого НЕ требует входа в ядро?

  • Thread.sleep
  • чтение файла без буфера
  • new Thread().start()
  • System.nanoTime() на Linux
vDSO. Остальные — futex/nanosleep, read, mmap + clone.

Обход какой структуры хуже всего использует кэш?

  • int[] по порядку
  • LinkedList с узлами, разбросанными по куче
  • ArrayList<Integer>, заполненный подряд
  • long[] с шагом 1
Погоня за указателями: каждый следующий адрес известен только после чтения текущего.

Что произойдёт при первом обращении к странице кучи после mmap?

  • SIGSEGV
  • ничего — страница уже есть
  • minor page fault: ядро выделит обнулённый кадр и впишет его в таблицу страниц
  • major fault с чтением с диска
Ленивое выделение физической памяти.

Почему volatile-запись на x86 дороже volatile-чтения?

  • после записи нужен барьер, опустошающий буфер записи, чтобы запретить переупорядочивание store → load
  • запись идёт сразу в оперативную память
  • чтение кэшируется в регистре
  • запись блокирует шину
Чтение с семантикой acquire на TSO бесплатно.

Какой системный вызов создаёт поток в Linux?

  • fork
  • execve
  • pthread_create
  • clone (или clone3) с флагами разделения памяти и ресурсов
pthread_create — функция библиотеки, которая делает mmap стека и clone.

Контейнер с -m 512m. Что покажет /proc/meminfo внутри и что выберет JVM для кучи по умолчанию?

  • 512 МБ и 128 МБ
  • память всей машины (ВМ) и 128 МБ — JVM читает лимит из cgroups
  • 512 МБ и 512 МБ
  • память машины и четверть памяти машины
/proc/meminfo не знает о cgroups; JVM — знает (MaxRAMPercentage = 25%).

Почему виртуальные потоки дешевле платформенных при блокирующем вводе-выводе?

  • они быстрее исполняют код
  • у них больше приоритет
  • при ожидании они паркуются в пользовательском режиме и освобождают поток ОС, а их стек хранится в куче по реальной глубине
  • они не используют сокеты
Счётную работу виртуальные потоки не ускоряют.

Что гарантирует FileChannel.force(false)?

  • данные файла сброшены из page cache на устройство (fdatasync)
  • данные отправлены другим процессам
  • буфер Java сброшен в ядро
  • файл закрыт
force(true) — ещё и метаданные (fsync).

Почему Java-программа защищена от классического переполнения буфера на стеке?

  • JVM шифрует стек
  • стек Java в куче
  • JIT вставляет канарейки
  • доступ к массивам проверяет границы, арифметики указателей нет, адресовать стек нельзя
Граница прорывается только в нативном коде: JNI, Unsafe, FFM, сама JVM.

Что делает ядро, когда поток делает socket.read(), а данных нет (блокирующий сокет)?

  • возвращает 0
  • переводит поток в сон (S) и ставит в очередь ожидания сокета; разбудит при приходе данных
  • опрашивает сетевую карту в цикле
  • бросает исключение
Для неблокирующего сокета — EAGAIN, и программа сама решает, ждать ли через epoll.
