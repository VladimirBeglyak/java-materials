Иерархия памяти и кэши

Процессор выполняет сложение за доли наносекунды, а чтение из оперативной памяти занимает около 100 нс — время сотен команд. Между ними стоят кэши: маленькие, быстрые, автоматические. Почти вся современная производительность — это попадания в кэш. Разберём, как устроены уровни L1–L3, что такое кэш-линия и ассоциативность, почему важны локальность и предвыборка, и что из этого следует для массивов, списков и объектов в Java.

Машина, на которой сняты лабы (Intel Core Ultra 5 125H): L1d — 48 КБ на P-ядро, L2 — 2 МБ, L3 — 18 МБ общий. Измерение в лабе 6.1 даёт ступени: ~1,3 нс, ~5 нс, ~30 нс и 120–200 нс — каждая отражает уровень, в который помещается рабочий набор данных.

Почему не сделать всю память быстрой? Быстрая память — SRAM в 6 транзисторов на бит, она большая, горячая и дорогая (тема 02); кроме того, чем больше массив памяти, тем длиннее провода и тем дольше сигнал. Поэтому рядом с ядром — маленький быстрый кэш, дальше — больше и медленнее. Иерархия работает, потому что программы обладают локальностью.

6.2Локальность и кэш-линия

  • Временная локальность: к недавно использованным данным скоро обратятся снова (переменные цикла, вершина стека, горячие объекты).
  • Пространственная локальность: после обращения к адресу скоро обратятся к соседним (обход массива, поля одного объекта, следующая команда).

Поэтому кэш работает не с байтами, а с кэш-линиями — блоками по 64 байта, выровненными по адресу, кратному 64. Промах при чтении одного int загружает всю линию — 16 int, 8 long или ссылок; следующие 15 обращений к соседям бесплатны. Все обмены между уровнями — целыми линиями.

6.3Как устроен кэш: тег, набор, ассоциативность

Кэш должен быстро ответить: «есть ли у меня линия с адресом A?». Перебирать все тысячи линий некогда, поэтому адрес делится на три части:

  • Прямое отображение (1 линия в наборе): каждый адрес может лежать ровно в одном месте. Просто и быстро, но два адреса с одинаковым индексом постоянно вытесняют друг друга — конфликтные промахи.
  • N-канальная ассоциативность: в наборе N линий, адрес может лечь в любую из них; при поиске сравниваются N тегов параллельно. L1 — 8–12 каналов, L2 — 10–16, L3 — 12–20.
  • Замещение: когда набор полон, вытесняется линия, к которой дольше всего не обращались (приближения LRU).
  • Запись: кэши write-back — изменённая линия помечается «грязной» и пишется в следующий уровень только при вытеснении. Запись в отсутствующую линию сначала загружает её (write-allocate).

Типы промахов («три C»): обязательные (compulsory — первое обращение), ёмкостные (capacity — данные не помещаются), конфликтные (conflict — помещаются, но мешают друг другу в одном наборе). Последний тип объясняет «загадочное» падение скорости на матрицах размером ровно степень двойки: строки длиной 4096 × 4 байта = 16 КБ отображаются в одни и те же наборы, и обход по столбцам выталкивает сам себя.

6.4Предвыборка и полоса пропускания

Аппаратный предвыборщик (prefetcher) замечает регулярные шаблоны — последовательный обход, постоянный шаг вперёд или назад — и загружает линии заранее, до того как программа к ним обратится. Поэтому последовательное чтение большого массива упирается не в задержку памяти (100 нс на линию), а в её пропускную способность: DDR5 даёт десятки ГБ/с на канал, то есть линию раз в несколько наносекунд.

Предвыборщик бессилен против погони за указателями (pointer chasing): адрес следующего элемента становится известен только после чтения текущего. Связный список, дерево, граф объектов, HashMap с цепочками — каждое звено может стоить полного промаха. Это измерение в лабе 6.1: случайный обход по кругу 512 МБ — около 200 нс на шаг.

6.5Оперативная память изнутри

  • DRAM организована в банки, строки (row, ~8 КБ) и столбцы. Чтобы прочитать данные, нужно «открыть» строку (activate) в буфер усилителей, затем читать столбцы. Попадание в уже открытую строку быстрее; переход к другой строке банка — дольше. Отсюда снова выигрыш последовательного доступа.
  • Каналы памяти: у настольного процессора 2 канала, у серверного — 8–12. Полоса пропускания суммируется; поэтому сервер на 128 ядер может «голодать», если все ядра одновременно читают память.
  • NUMA (многосокетные серверы, тема 07): у каждого процессора своя память; чтение «чужой» дороже на 30–100%. JVM умеет выделять память рядом с потоком (-XX:+UseNUMA для Parallel GC и G1).
  • Регенерация: конденсаторы теряют заряд, каждые ~64 мс каждая строка перечитывается и перезаписывается — небольшая доля времени памяти уходит на это.
  • ECC в серверах: дополнительные биты на слово исправляют одиночные ошибки (от космических лучей и износа) и обнаруживают двойные.

«Почему ArrayList быстрее LinkedList даже на вставках в середину?» Асимптотика говорит: вставка в середину LinkedList — O(1), в ArrayList — O(n). Но до места вставки в списке нужно дойти — O(n) погони за указателями с промахом кэша на каждом узле, а ArrayList сдвигает хвост одним System.arraycopy по последовательной памяти со скоростью полосы пропускания. Константы различаются в десятки раз, и на практике ArrayList выигрывает почти всегда (Java Core, тема 08).

Лаба 6.1Лестница задержек20 мин

Найти по времени доступа границы L1, L2, L3 и оперативной памяти своего процессора.

  1. Создайте файл Latency.java:
    import java.util.Random;

public class Latency {
    public static void main(String[] args) {
        Random rnd = new Random(1);
        for (int kb : new int[] {16, 32, 64, 256, 1024, 2048, 8192, 16384, 32768, 131072, 524288}) {
            int n = kb * 1024 / 4;
            // случайный цикл: next[i] — индекс следующего элемента; предвыборщик его не угадает
            int[] perm = new int[n];
            for (int i = 0; i < n; i++) perm[i] = i;
            for (int i = n - 1; i > 0; i--) { int j = rnd.nextInt(i + 1); int t = perm[i]; perm[i] = perm[j]; perm[j] = t; }
            int[] next = new int[n];
            for (int i = 0; i < n; i++) next[perm[i]] = perm[(i + 1) % n];

            int p = 0;
            for (int i = 0; i < 1_000_000; i++) p = next[p];         // прогрев
            long steps = 20_000_000, t0 = System.nanoTime();
            for (long i = 0; i < steps; i++) p = next[p];             // каждое чтение зависит от предыдущего
            long t1 = System.nanoTime();
            System.out.printf("рабочий набор %7d КБ: %6.1f нс на обращение%s%n", kb, (t1 - t0) / (double) steps, p < 0 ? "!" : "");
        }
    }
}

Лаба 6.2По строкам или по столбцам15 мин

Сравнить два порядка обхода одной матрицы и плоский массив.

  1. Создайте файл Traverse.java:
    public class Traverse {
    static final int N = 4096;

    static long rows(int[][] m)  { long s = 0; for (int i = 0; i < N; i++) for (int j = 0; j < N; j++) s += m[i][j]; return s; }
    static long cols(int[][] m)  { long s = 0; for (int j = 0; j < N; j++) for (int i = 0; i < N; i++) s += m[i][j]; return s; }
    static long flat(int[] f)    { long s = 0; for (int k = 0; k < f.length; k++) s += f[k]; return s; }

    public static void main(String[] args) {
        int[][] m = new int[N][N];
        int[] f = new int[N * N];
        for (int i = 0; i < N; i++) for (int j = 0; j < N; j++) { m[i][j] = i ^ j; f[i * N + j] = i ^ j; }
        for (int r = 0; r < 4; r++) {
            long t0 = System.nanoTime(); long a = rows(m);
            long t1 = System.nanoTime(); long b = cols(m);
            long t2 = System.nanoTime(); long c = flat(f);
            long t3 = System.nanoTime();
            System.out.printf("по строкам %4d мс | по столбцам %5d мс | плоский массив %4d мс  (%b)%n",
                    (t1 - t0) / 1_000_000, (t2 - t1) / 1_000_000, (t3 - t2) / 1_000_000, a == b && b == c);
        }
    }
}

Лаба 6.3Кэш-линия своими глазами10 мин

Увидеть, что стоимость определяется числом затронутых линий, а не числом обращений.

  1. Создайте файл Stride.java:
    public class Stride {
    public static void main(String[] args) {
        int[] a = new int[64 * 1024 * 1024];            // 256 МБ
        for (int step : new int[] {1, 2, 4, 8, 16, 32, 64, 128}) {
            long best = Long.MAX_VALUE;
            for (int r = 0; r < 3; r++) {
                long t0 = System.nanoTime();
                for (int i = 0; i < a.length; i += step) a[i]++;
                best = Math.min(best, System.nanoTime() - t0);
            }
            long touched = a.length / step;
            System.out.printf("шаг %3d int (%4d байт): %5d мс, обращений %,11d, %.2f нс на обращение%n",
                    step, step * 4, best / 1_000_000, touched, best / (double) touched);
        }
    }
}
  2. Как изменится время цикла при шагах 1, 2, 4, 8, 16? А после 16?

С шага 16 int (64 байта) каждое обращение — отдельная линия, и время на обращение растёт до цены промаха с предвыборкой. Дальше общее время падает, хотя и медленнее, чем число затронутых линий: часть цены — переходы между страницами памяти (TLB) и предвыборка, которая тянет и ненужные соседние линии.

Лаба 6.4Массив, ArrayList, LinkedList15 мин

Сравнить обход одних и тех же чисел в трёх раскладках памяти и увидеть цену перемешанных объектов.

  1. Создайте файл Layouts.java:
    import java.util.*;

public class Layouts {
    public static void main(String[] args) {
        int n = 5_000_000;
        int[] arr = new int[n];
        List<Integer> list = new ArrayList<>(n), shuffled;
        LinkedList<Integer> linked = new LinkedList<>();
        for (int i = 0; i < n; i++) { arr[i] = i; Integer boxed = i + 1000; list.add(boxed); linked.add(boxed); }
        shuffled = new ArrayList<>(list);
        Collections.shuffle(shuffled, new Random(1));   // те же объекты, другой порядок обхода

        for (int r = 0; r < 3; r++) {
            long t0 = System.nanoTime(); long s1 = 0; for (int x : arr) s1 += x;
            long t1 = System.nanoTime(); long s2 = 0; for (int x : list) s2 += x;
            long t2 = System.nanoTime(); long s3 = 0; for (int x : shuffled) s3 += x;
            long t3 = System.nanoTime(); long s4 = 0; for (int x : linked) s4 += x;
            long t4 = System.nanoTime();
            System.out.printf("int[] %3d мс | ArrayList по порядку %3d мс | ArrayList перемешанный %4d мс | LinkedList %3d мс  (%b)%n",
                    (t1 - t0) / 1_000_000, (t2 - t1) / 1_000_000, (t3 - t2) / 1_000_000, (t4 - t3) / 1_000_000,
                    s2 == s3 && s3 == s4 && s1 < s2);   // суммы печатаем, чтобы JIT не выбросил циклы
        }
    }
}
  2. Расставьте четыре варианта по скорости. Почему перемешанный ArrayList медленнее, хотя это тот же список тех же объектов?
    javac Layouts.java
java -Xmx2g Layouts
    Вывод (JDK 25.0.2)
    int[]   7 мс | ArrayList по порядку  19 мс | ArrayList перемешанный   64 мс | LinkedList  24 мс  (true)
int[]  11 мс | ArrayList по порядку  33 мс | ArrayList перемешанный  109 мс | LinkedList  20 мс  (true)
int[]   1 мс | ArrayList по порядку   9 мс | ArrayList перемешанный  101 мс | LinkedList  20 мс  (true)

    int[] — быстрее всех (последовательные значения, векторизация). ArrayList по порядку — в разы медленнее, но терпимо: объекты Integer создавались подряд и лежат в куче почти последовательно, предвыборщик помогает. LinkedList — ещё медленнее (узел → следующий узел, узел → объект), хотя узлы тоже созданы подряд. Перемешанный ArrayList — самый медленный: массив ссылок читается последовательно, но каждая ссылка ведёт в случайное место кучи — промах на каждом элементе. Порядок данных в памяти важнее, чем «тип коллекции». Отдельные раунды могут выбиваться — например, из-за сборки мусора посреди замера.

Поэкспериментируйте
  • Запустите с -XX:+UseParallelGC и добавьте System.gc() после перемешивания.
    Копирующий сборщик перекладывает живые объекты в порядке обхода графа ссылок — из массива shuffled они могут оказаться в новом порядке подряд, и перемешанный список ускорится. GC меняет локальность данных — иногда к лучшему.

6.8Самопроверка

Какой размер кэш-линии на современных x86 и ARM?

  • 8 байт
  • 4 КБ
  • 64 байта
  • 1 МБ
64 байта. Apple M-серии используют 128-байтные линии в некоторых кэшах — ещё одна причина не закладываться на конкретное число в коде, а использовать @Contended.

Почему обход связного списка из миллиона элементов медленнее обхода массива той же длины?

  • каждый следующий адрес известен только после чтения текущего узла, предвыборка не работает, почти каждый шаг — промах
  • список занимает меньше памяти
  • у списка нет индексов
  • JIT не компилирует методы LinkedList
Погоня за указателями: задержка памяти не перекрывается. Массив читается последовательно с предвыборкой.

Что такое конфликтный промах?

  • промах при первом обращении
  • промах из-за того, что данные больше кэша
  • промах при записи из двух потоков
  • промах, когда данных немного, но они отображаются в один набор и вытесняют друг друга
Лечится большей ассоциативностью или изменением раскладки (например, длина строки матрицы не степень двойки).

Почему при обходе массива по порядку скорость упирается в полосу пропускания памяти, а не в её задержку?

  • массивы кэшируются целиком
  • предвыборщик загружает следующие линии заранее, и много запросов к памяти идут параллельно
  • JVM копирует массив в регистры
  • у массивов нет задержки
Задержка перекрывается параллельными запросами; остаётся предел — сколько байт в секунду отдаёт память.
Опишите иерархию памяти и порядок задержек.

Регистры (0 тактов), L1 32–64 КБ (~1 нс), L2 1–3 МБ (~4 нс), L3 десятки МБ (~10–30 нс), DRAM гигабайты (~100 нс), SSD (~десятки мкс), HDD (~мс), сеть (~0,1–100 мс). Каждый уровень на порядок больше и медленнее предыдущего; работает это благодаря временной и пространственной локальности программ.

Как кэш находит линию по адресу?

Младшие 6 бит — смещение в 64-байтной линии, следующие биты — номер набора, остальные — тег. Аппаратно выбирается набор, и теги всех его линий (N для N-канального кэша) сравниваются параллельно. Совпадение — попадание; нет — промах и загрузка линии из следующего уровня с вытеснением давно неиспользованной линии набора.

Почему обход двумерного массива по столбцам медленнее?

Элементы строки лежат подряд, строки — отдельными объектами. По строкам одна загруженная линия даёт 16 int подряд; по столбцам каждое обращение — в другую строку и другую линию, и к моменту возврата к соседнему элементу линия уже вытеснена. Плюс предвыборщик хуже распознаёт такой шаблон.

Как бы вы сделали структуру данных дружелюбной к кэшу?

Данные, которые обрабатываются вместе, — рядом в памяти: массивы примитивов вместо коллекций объектов, «структура массивов» (отдельные массивы полей) вместо «массива структур» для обработки одного поля, открытая адресация вместо цепочек в хеш-таблице, B-деревья с широкими узлами вместо бинарных. Меньше уровней косвенности — меньше промахов.
