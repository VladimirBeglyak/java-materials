GPU и ускорители

Центральный процессор оптимизирован под задержку: выполнить один поток команд как можно быстрее, со всеми хитростями конвейера, предсказания и кэшей. Графический процессор оптимизирован под пропускную способность: тысячи простых ядер выполняют одну и ту же программу над разными данными. Рядом — ещё целый зоопарк специализированных блоков: тензорные ядра, NPU, шифрование, сжатие, сетевые сопроцессоры. Разберём, как они устроены, когда выгодны, как картинка попадает на экран и как до них дотягивается Java.

16.2SIMT: потоки, варпы, расхождение

Программа для GPU — ядро (kernel): функция, которую запускают сразу на сетке из миллионов потоков; каждый знает свой индекс и обрабатывает свой элемент. Аппаратно потоки объединены в варпы (warp, 32 потока у NVIDIA; wavefront, 32–64 у AMD): все потоки варпа выполняют одну и ту же команду одновременно — это SIMD, только с удобной моделью «у каждого потока свой код» (SIMT, single instruction, multiple threads).

  • Расхождение (divergence): если часть потоков варпа идёт в if, а часть — в else, варп выполняет обе ветки по очереди, отключая (маскируя) неактивные дорожки. Ветвистый код на GPU теряет производительность пропорционально.
  • Объединение обращений (coalescing): если 32 потока варпа читают 32 соседних слова, это одна транзакция с памятью; если вразнобой — 32 транзакции. Раскладка данных важна так же, как на CPU (тема 06), только сильнее.
  • Занятость (occupancy): на мультипроцессоре одновременно живут десятки варпов; пока одни ждут память (сотни тактов), исполняются другие. Если программе нужно много регистров на поток, варпов помещается меньше — и прятать задержку нечем.
  • Разделяемая память (shared memory) — программно управляемый «кэш» блока потоков на кристалле; основа быстрых алгоритмов вроде умножения матриц блоками.

16.3Цена передачи данных

У дискретной видеокарты своя память. Данные нужно скопировать туда по PCIe (16 линий PCIe 4.0 — ~25 ГБ/с на практике), посчитать, скопировать результат обратно. Если вычислений на байт мало, копирование съедает весь выигрыш:

  • сложить два массива по 1 ГБ: копирование 3 ГБ туда-обратно — ~120 мс, само сложение на GPU — ~2 мс, на CPU — ~150 мс. Выигрыш почти нулевой;
  • умножить две матрицы 8192×8192: 1 трлн умножений-сложений на 0,8 ГБ данных — GPU выигрывает в десятки раз.

Мера — арифметическая интенсивность (операций на байт). Поэтому на GPU переносят крупные куски работы целиком (обучение нейросети держит веса в памяти GPU всё время), а встроенные GPU (Intel Arc в процессоре машины из лаб, Apple M) делят оперативную память с CPU и копирования не требуют.

16.4Как пиксель попадает на экран

  1. Приложение (браузер, IDE) рисует окно: через графический API (Direct3D, Vulkan, Metal, OpenGL) отправляет GPU списки команд — треугольники, текстуры, шейдеры. Java Swing/JavaFX делают это через Java2D/Prism поверх Direct3D, OpenGL или Metal.
  2. Конвейер GPU: вершинные шейдеры преобразуют координаты, растеризатор превращает треугольники в фрагменты-пиксели, пиксельные шейдеры считают цвет — миллионы пикселей параллельно, по SIMT.
  3. Композитор окон (DWM в Windows, Mutter/KWin в Linux) собирает окна всех приложений в один кадр — тоже на GPU.
  4. Буфер кадра (framebuffer) — область памяти: 1920×1080×4 байта ≈ 8 МБ (тема 01). Используется двойная буферизация: пока один кадр показывается, рисуется следующий.
  5. Вывод (scanout): контроллер дисплея построчно читает буфер и передаёт по HDMI/DisplayPort; смена буферов синхронизируется с обновлением экрана (VSync, 60–240 раз в секунду) — иначе видны «разрывы» кадра.

16.6Java и GPU

  • Через библиотеки — основной путь сегодня: обучение и вывод моделей через DJL, ONNX Runtime, TensorFlow Java, которые внутри вызывают CUDA или другие бэкенды через JNI (или FFM API).
  • FFM API (тема 14) позволяет вызывать CUDA Driver API или OpenCL напрямую, без JNI-обёрток, а MemorySegment — работать с памятью вне кучи, которую понимает драйвер.
  • TornadoVM — надстройка над OpenJDK/GraalVM, которая компилирует Java-методы в ядра для GPU и FPGA (OpenCL, PTX, SPIR-V).
  • Проект Babylon (OpenJDK, экспериментальный) — «отражение кода» (code reflection): доступ к модели Java-метода во время работы, чтобы библиотеки могли транслировать его, например, в ядро GPU (прототип HAT — Heterogeneous Accelerator Toolkit). В стандартный JDK пока не входит.
  • Vector API (тема 05) — SIMD на CPU, ближайший к GPU-стилю способ писать на чистой Java.

Лаба 16.2AES-NI: специализированные команды в JVM15 мин

Измерить скорость шифрования AES-GCM с интринсиками JIT на аппаратных командах и без них.

  1. Создайте файл Aes.java:
    import javax.crypto.Cipher;
import javax.crypto.SecretKey;
import javax.crypto.spec.GCMParameterSpec;
import javax.crypto.spec.SecretKeySpec;

public class Aes {
    public static void main(String[] args) throws Exception {
        SecretKey key = new SecretKeySpec(new byte[16], "AES");
        byte[] block = new byte[16 * 1024], out = new byte[block.length + 16];
        for (int round = 0; round < 5; round++) {
            long bytes = 0, t0 = System.nanoTime();
            for (int m = 0; m < 4000; m++) {
                Cipher c = Cipher.getInstance("AES/GCM/NoPadding");
                byte[] iv = {(byte) round, (byte) m, (byte) (m >> 8), 0, 0, 0, 0, 0, 0, 0, 0, 0};   // nonce не повторяется
                c.init(Cipher.ENCRYPT_MODE, key, new GCMParameterSpec(128, iv));
                c.doFinal(block, 0, block.length, out, 0);
                bytes += block.length;
            }
            System.out.printf("раунд %d: AES-GCM %,6.0f МБ/с%n", round, bytes / 1048576.0 / ((System.nanoTime() - t0) / 1e9));
        }
    }
}
  2. Насколько быстрее шифрование с аппаратными командами? Почему первый раунд медленнее остальных?
    javac Aes.java
java Aes

    С интринсиками — 2–4,5 ГБ/с: C2 заменяет код раундов AES командами aesenc (раунд шифрования — одна команда) и вычисление GHASH — командой умножения без переносов pclmulqdq, обрабатывая сразу несколько блоков векторно. Без них — ~70 МБ/с: те же вычисления таблицами и сдвигами на Java, в 30–60 раз медленнее. Первый раунд медленный, потому что методы шифрования ещё интерпретируются: интринсик срабатывает только в JIT-коде.

Поэкспериментируйте

    Список флагов CPU (avx2, aes, clmul, sha, bmi2…) — по нему JIT решает, какие интринсики включать. На процессоре без AES-NI флаг UseAESIntrinsics выключен сам.
Лаба 16.3Умножение матриц: интенсивность и раскладка20 мин

Увидеть, как одна и та же арифметика (2n³ операций) работает в разы быстрее при другом порядке циклов.

  1. Создайте файл MatMul.java:
    public class MatMul {
    static final int N = 768;

    static void ijk(double[] a, double[] b, double[] c) {           // внутренний цикл идёт по столбцу b — шаг N
        for (int i = 0; i < N; i++)
            for (int j = 0; j < N; j++) {
                double s = 0;
                for (int k = 0; k < N; k++) s += a[i * N + k] * b[k * N + j];
                c[i * N + j] = s;
            }
    }

    static void ikj(double[] a, double[] b, double[] c) {           // внутренний цикл идёт по строкам b и c подряд
        java.util.Arrays.fill(c, 0);
        for (int i = 0; i < N; i++)
            for (int k = 0; k < N; k++) {
                double aik = a[i * N + k];
                for (int j = 0; j < N; j++) c[i * N + j] += aik * b[k * N + j];
            }
    }

    public static void main(String[] args) {
        double[] a = new double[N * N], b = new double[N * N], c = new double[N * N];
        for (int i = 0; i < a.length; i++) { a[i] = i % 7; b[i] = i % 5; }
        double flops = 2.0 * N * N * N;
        for (int r = 0; r < 3; r++) {
            long t0 = System.nanoTime(); ijk(a, b, c); double s1 = c[N + 1];
            long t1 = System.nanoTime(); ikj(a, b, c); double s2 = c[N + 1];
            long t2 = System.nanoTime();
            System.out.printf("ijk: %4d мс (%5.2f GFLOPS) | ikj: %4d мс (%5.2f GFLOPS)  %b%n",
                    (t1 - t0) / 1_000_000, flops / (t1 - t0), (t2 - t1) / 1_000_000, flops / (t2 - t1), s1 == s2);
        }
    }
}
  2. Порядок операций сложения в двух вариантах одинаков для каждой ячейки — результат совпадёт. Во сколько раз будет различаться скорость и почему?
    javac MatMul.java
java MatMul
    Вывод (JDK 25.0.2)
    ijk:  436 мс ( 2.08 GFLOPS) | ikj:  192 мс ( 4.70 GFLOPS)  true
ijk:  445 мс ( 2.03 GFLOPS) | ikj:  159 мс ( 5.70 GFLOPS)  true
ijk:  428 мс ( 2.12 GFLOPS) | ikj:  176 мс ( 5.13 GFLOPS)  true

    ikj быстрее в 2–3 раза. В ijk внутренний цикл читает b по столбцу с шагом 768 × 8 байт — каждое обращение в новую кэш-линию (тема 06), плюс одна длинная цепочка зависимых сложений s += (тема 05). В ikj внутренний цикл идёт по строкам b и c подряд и его итерации независимы — C2 векторизует его (AVX2: 4 double за команду). На одном ядре CPU это единицы гигафлопс; GPU с тензорными ядрами делает то же на два-три порядка быстрее — но только если матрицы уже в его памяти. Библиотеки (BLAS) добавляют ещё блочное разбиение под кэши и многопоточность.

Поэкспериментируйте
  • Увеличьте N до 1536.
    Разрыв вырастет: матрицы перестанут помещаться в L2/L3, и «столбцовый» доступ ijk упрётся в память, тогда как ikj по-прежнему читает подряд с предвыборкой.

16.8Самопроверка

Как GPU справляется с задержкой памяти в сотни тактов?

  • огромным кэшем и предсказанием переходов
  • не справляется — поэтому GPU медленнее
  • держит много варпов одновременно и переключается на те, чьи данные готовы
  • копирует данные в регистры заранее
Параллелизм вместо кэшей. Нужна высокая занятость — много независимой работы.

Что происходит, когда потоки одного варпа идут в разные ветки if?

  • варп выполняет обе ветки по очереди с маской неактивных потоков
  • варп делится на два независимых
  • GPU выдаёт ошибку
  • выполняется только одна ветка
Расхождение снижает эффективность; на GPU стараются обходиться без ветвлений, зависящих от данных.

Когда перенос вычисления на дискретный GPU невыгоден?

  • когда данных больше гигабайта
  • когда используется double
  • никогда
  • когда операций на байт мало, и передача данных по PCIe туда и обратно дольше, чем расчёт на CPU
Арифметическая интенсивность решает. Сложение векторов — плохой кандидат, умножение больших матриц — отличный.
Чем архитектура GPU отличается от CPU?

CPU тратит транзисторы на ускорение одного потока: внеочередное исполнение, предсказание, большие кэши. GPU — на количество простых вычислительных дорожек, объединённых в варпы, которые выполняют одну команду над разными данными, и прячет задержку памяти переключением между множеством варпов. CPU выигрывает на ветвистом последовательном коде, GPU — на массово-параллельной однородной работе.

Что такое арифметическая интенсивность и почему она важна для ускорителей?

Отношение числа вычислительных операций к объёму перемещаемых данных. Если она низкая, производительность ограничена пропускной способностью памяти и передачей по шине, а не вычислениями; ускоритель не успевает получать данные. Для дискретного GPU добавляется ещё и копирование по PCIe.

Какие «ускорители» использует обычная JVM без всяких GPU?

Интринсики на специальных командах процессора: AES-NI и PCLMULQDQ для AES-GCM, SHA-NI, CRC32/CRC32C, векторные команды для Arrays.equals/fill/sort, String.indexOf, кодирования UTF-8 и Base64, Vector API, атомарные команды для CAS. JIT подставляет их вместо обычного кода, если процессор их поддерживает.
