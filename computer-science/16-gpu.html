GPU и ускорители

Центральный процессор оптимизирован под задержку: выполнить один поток команд как можно быстрее, со всеми хитростями конвейера, предсказания и кэшей. Графический процессор оптимизирован под пропускную способность: тысячи простых ядер выполняют одну и ту же программу над разными данными. Рядом — ещё целый зоопарк специализированных блоков: тензорные ядра, NPU, шифрование, сжатие, сетевые сопроцессоры. Разберём, как они устроены, когда выгодны, как картинка попадает на экран и как до них дотягивается Java.

16.1Два способа потратить транзисторы

С нуля: профессор и класс школьников

Нужно проверить 10 000 простых примеров на сложение. Можно отдать их профессору: он считает очень быстро, но всё равно по одному. А можно раздать класс из тысячи школьников — каждый считает медленнее профессора, но все одновременно, и работа закончится намного раньше. Зато сложную задачу с множеством «если» школьникам не поручишь. CPU — несколько профессоров, GPU — огромный класс школьников, которые выполняют одну и ту же инструкцию каждый над своими данными.

Пиковая производительность современных GPU — десятки – сотни терафлопс (FLOPS — FLoating-point Operations Per Second, операций с дробными числами в секунду; тера — триллион) (а с тензорными ядрами в низкой точности — петафлопсы, квадриллионы) против единиц терафлопс у многоядерного CPU с AVX-512. Но достаётся она только задачам, где параллелизм огромный, а ветвлений и обмена с CPU мало.

Главное CPU тратит транзисторы на то, чтобы один поток шёл как можно быстрее, GPU — на тысячи простых вычислителей для одинаковой работы над огромными массивами. GPU выигрывает только при большом параллелизме и малом числе ветвлений.

16.2SIMT: потоки, варпы, расхождение

Программа для GPU — ядро (kernel; не путать с ядром ОС и ядром процессора): функция, которую запускают сразу на сетке из миллионов потоков; каждый знает свой индекс и обрабатывает свой элемент. Аппаратно потоки объединены в варпы (warp — «основа ткани», 32 потока у NVIDIA; wavefront, «фронт волны», 32–64 у AMD): все потоки варпа выполняют одну и ту же команду одновременно — это SIMD, только с удобной моделью «у каждого потока свой код» (SIMT — Single Instruction, Multiple Threads, «одна команда, много потоков»).

  • Расхождение (divergence — «расхождение» путей): если часть потоков варпа идёт в if, а часть — в else, варп выполняет обе ветки по очереди, отключая (маскируя) неактивные дорожки. Ветвистый код на GPU теряет производительность пропорционально.
  • Объединение обращений (coalescing — «слияние»): если 32 потока варпа читают 32 соседних слова, это одна транзакция (один обмен) с памятью; если вразнобой — 32 транзакции. Раскладка данных важна так же, как на CPU (тема 06), только сильнее.
  • Занятость (occupancy): на мультипроцессоре (SM — Streaming Multiprocessor, блоке GPU с общими регистрами и памятью) одновременно живут десятки варпов; пока одни ждут память (сотни тактов), исполняются другие. Если программе нужно много регистров на поток, варпов помещается меньше — и прятать задержку нечем.
  • Разделяемая память (shared memory) — программно управляемый «кэш» блока потоков (группы варпов, которая работает на одном мультипроцессоре) на кристалле; основа быстрых алгоритмов вроде умножения матриц блоками.
Расхождение в варпе (8 дорожек для наглядности)

Каждая дорожка обрабатывает элемент x[i]: if (условие) { 4 команды } else { 6 команд }. Выберите, как распределены данные.

Главное Потоки GPU объединены в варпы по 32, и все потоки варпа выполняют одну команду. Расходящиеся if, разбросанные обращения к памяти и нехватка варпов съедают производительность.

16.3Цена передачи данных

У дискретной видеокарты (отдельной платы, в отличие от встроенной в процессор) своя память. Данные нужно скопировать туда по PCIe (16 линий PCIe 4.0 — ~25 ГБ/с на практике), посчитать, скопировать результат обратно. Если вычислений на байт мало, копирование съедает весь выигрыш:

  • сложить два массива по 1 ГБ: копирование 3 ГБ туда-обратно — ~120 мс, само сложение на GPU — ~2 мс, на CPU — ~150 мс. Выигрыш почти нулевой;
  • умножить две матрицы 8192×8192: 1 трлн умножений-сложений на 0,8 ГБ данных — GPU выигрывает в десятки раз.

Мера — арифметическая интенсивность (сколько вычислений приходится на каждый переданный байт). Поэтому на GPU переносят крупные куски работы целиком (обучение нейросети держит её веса — миллиарды чисел-параметров — в памяти GPU всё время), а встроенные GPU (Intel Arc в процессоре машины из лаб, Apple M) делят оперативную память с CPU и копирования не требуют.

Главное Данные для дискретной видеокарты надо скопировать по PCIe и обратно. Выгодно, только если вычислений на каждый байт много (арифметическая интенсивность): умножение матриц — да, сложение массивов — нет.

16.4Как пиксель попадает на экран

  1. Приложение (браузер, IDE) рисует окно: через графический API (Application Programming Interface — программный интерфейс: Direct3D, Vulkan, Metal, OpenGL) отправляет GPU списки команд — треугольники, текстуры (картинки, натягиваемые на поверхности), шейдеры (маленькие программы для GPU). Java Swing/JavaFX делают это через Java2D/Prism поверх Direct3D, OpenGL или Metal.
  2. Конвейер GPU: вершинные шейдеры преобразуют координаты, растеризатор превращает треугольники в фрагменты-пиксели (решает, какие точки экрана треугольник закрывает), пиксельные шейдеры считают цвет — миллионы пикселей параллельно, по SIMT.
  3. Композитор окон (DWM — Desktop Window Manager в Windows, Mutter/KWin в Linux) собирает окна всех приложений в один кадр — тоже на GPU.
  4. Буфер кадра (framebuffer) — область памяти: 1920×1080×4 байта ≈ 8 МБ (тема 01). Используется двойная буферизация: пока один кадр показывается, рисуется следующий.
  5. Вывод (scanout): контроллер дисплея построчно читает буфер и передаёт по HDMI (High-Definition Multimedia Interface)/DisplayPort; смена буферов синхронизируется с обновлением экрана (VSync — vertical synchronization, 60–240 раз в секунду) — иначе видны «разрывы» кадра.
Главное Приложение отправляет GPU команды рисования, GPU превращает треугольники в пиксели, композитор собирает окна в кадр, а контроллер дисплея выводит буфер кадра на экран синхронно с его обновлением.

Тренд ясен из темы 02: когда транзисторов много, а частоту не поднять, выгоднее построить специализированную схему, чем исполнять ту же работу общими командами. Даже внутри CPU JVM пользуется этим постоянно: Cipher с AES-GCM на лабе 16.2 в 50 раз быстрее с аппаратными инструкциями, чем без них; CRC32C, Base64, String.indexOf, Arrays.sort (библиотека libsimdsort, тема 14) — интринсики (методы, которые JIT заменяет готовым оптимальным машинным кодом) на специальных и векторных командах.

Главное Когда частоту не поднять, выгоднее специализированная схема: тензорные ядра, TPU, NPU, AES-NI, FPGA. JVM пользуется специальными командами процессора через интринсики — AES-GCM в разы быстрее.

16.6Java и GPU

  • Через библиотеки — основной путь сегодня: обучение и вывод моделей через DJL (Deep Java Library), ONNX Runtime (Open Neural Network Exchange — открытый формат нейросетей), TensorFlow Java, которые внутри вызывают CUDA (Compute Unified Device Architecture — платформа NVIDIA для вычислений на GPU) или другие бэкенды через JNI (Java Native Interface) или FFM API.
  • FFM API (Foreign Function & Memory API, тема 14) позволяет вызывать CUDA Driver API или OpenCL (Open Computing Language — открытый стандарт вычислений на GPU) напрямую, без JNI-обёрток, а MemorySegment — работать с памятью вне кучи, которую понимает драйвер.
  • TornadoVM — надстройка над OpenJDK/GraalVM, которая компилирует Java-методы в ядра для GPU и FPGA (OpenCL, PTX — Parallel Thread Execution, промежуточный код NVIDIA, SPIR-V — промежуточный код Khronos).
  • Проект Babylon (OpenJDK, экспериментальный) — «отражение кода» (code reflection): доступ к модели Java-метода во время работы, чтобы библиотеки могли транслировать его, например, в ядро GPU (прототип HAT — Heterogeneous Accelerator Toolkit). В стандартный JDK пока не входит.
  • Vector API (тема 05) — SIMD на CPU, ближайший к GPU-стилю способ писать на чистой Java.
Главное Java обычно работает с GPU через библиотеки (DJL, ONNX Runtime) поверх CUDA; напрямую — через FFM API или TornadoVM. На CPU ближайший к GPU стиль даёт Vector API.

Лаба 16.2AES-NI: специализированные команды в JVM15 мин

Измерить скорость шифрования AES-GCM с интринсиками JIT на аппаратных командах и без них.

  1. Создайте файл Aes.java:
    import javax.crypto.Cipher;
import javax.crypto.SecretKey;
import javax.crypto.spec.GCMParameterSpec;
import javax.crypto.spec.SecretKeySpec;

public class Aes {
    public static void main(String[] args) throws Exception {
        SecretKey key = new SecretKeySpec(new byte[16], "AES");
        byte[] block = new byte[16 * 1024], out = new byte[block.length + 16];
        for (int round = 0; round < 5; round++) {
            long bytes = 0, t0 = System.nanoTime();
            for (int m = 0; m < 4000; m++) {
                Cipher c = Cipher.getInstance("AES/GCM/NoPadding");
                byte[] iv = {(byte) round, (byte) m, (byte) (m >> 8), 0, 0, 0, 0, 0, 0, 0, 0, 0};   // nonce не повторяется
                c.init(Cipher.ENCRYPT_MODE, key, new GCMParameterSpec(128, iv));
                c.doFinal(block, 0, block.length, out, 0);
                bytes += block.length;
            }
            System.out.printf("раунд %d: AES-GCM %,6.0f МБ/с%n", round, bytes / 1048576.0 / ((System.nanoTime() - t0) / 1e9));
        }
    }
}

Лаба 16.3Умножение матриц: интенсивность и раскладка20 мин

Увидеть, как одна и та же арифметика (2n³ операций) работает в разы быстрее при другом порядке циклов.

  1. Создайте файл MatMul.java:
    public class MatMul {
    static final int N = 768;

    static void ijk(double[] a, double[] b, double[] c) {           // внутренний цикл идёт по столбцу b — шаг N
        for (int i = 0; i < N; i++)
            for (int j = 0; j < N; j++) {
                double s = 0;
                for (int k = 0; k < N; k++) s += a[i * N + k] * b[k * N + j];
                c[i * N + j] = s;
            }
    }

    static void ikj(double[] a, double[] b, double[] c) {           // внутренний цикл идёт по строкам b и c подряд
        java.util.Arrays.fill(c, 0);
        for (int i = 0; i < N; i++)
            for (int k = 0; k < N; k++) {
                double aik = a[i * N + k];
                for (int j = 0; j < N; j++) c[i * N + j] += aik * b[k * N + j];
            }
    }

    public static void main(String[] args) {
        double[] a = new double[N * N], b = new double[N * N], c = new double[N * N];
        for (int i = 0; i < a.length; i++) { a[i] = i % 7; b[i] = i % 5; }
        double flops = 2.0 * N * N * N;
        for (int r = 0; r < 3; r++) {
            long t0 = System.nanoTime(); ijk(a, b, c); double s1 = c[N + 1];
            long t1 = System.nanoTime(); ikj(a, b, c); double s2 = c[N + 1];
            long t2 = System.nanoTime();
            System.out.printf("ijk: %4d мс (%5.2f GFLOPS) | ikj: %4d мс (%5.2f GFLOPS)  %b%n",
                    (t1 - t0) / 1_000_000, flops / (t1 - t0), (t2 - t1) / 1_000_000, flops / (t2 - t1), s1 == s2);
        }
    }
}

    ijk:  436 мс ( 2.08 GFLOPS) | ikj:  192 мс ( 4.70 GFLOPS)  true
ijk:  445 мс ( 2.03 GFLOPS) | ikj:  159 мс ( 5.70 GFLOPS)  true
ijk:  428 мс ( 2.12 GFLOPS) | ikj:  176 мс ( 5.13 GFLOPS)  true

    ikj быстрее в 2–3 раза. В ijk внутренний цикл читает b по столбцу с шагом 768 × 8 байт — каждое обращение в новую кэш-линию (тема 06), плюс одна длинная цепочка зависимых сложений s += (тема 05). В ikj внутренний цикл идёт по строкам b и c подряд и его итерации независимы — C2 векторизует его (AVX2: 4 double за команду). На одном ядре CPU это единицы гигафлопс; GPU с тензорными ядрами делает то же на два-три порядка быстрее — но только если матрицы уже в его памяти. Библиотеки (BLAS) добавляют ещё блочное разбиение под кэши и многопоточность.

Поэкспериментируйте
  • Увеличьте N до 1536.
    Разрыв вырастет: матрицы перестанут помещаться в L2/L3, и «столбцовый» доступ ijk упрётся в память, тогда как ikj по-прежнему читает подряд с предвыборкой.

16.9Самопроверка

Как GPU справляется с задержкой памяти в сотни тактов?

  • огромным кэшем и предсказанием переходов
  • не справляется — поэтому GPU медленнее
  • держит много варпов одновременно и переключается на те, чьи данные готовы
  • копирует данные в регистры заранее
Параллелизм вместо кэшей. Нужна высокая занятость — много независимой работы.

Что происходит, когда потоки одного варпа идут в разные ветки if?

  • варп выполняет обе ветки по очереди с маской неактивных потоков
  • варп делится на два независимых
  • GPU выдаёт ошибку
  • выполняется только одна ветка
Расхождение снижает эффективность; на GPU стараются обходиться без ветвлений, зависящих от данных.

Когда перенос вычисления на дискретный GPU невыгоден?

  • когда данных больше гигабайта
  • когда используется double
  • никогда
  • когда операций на байт мало, и передача данных по PCIe туда и обратно дольше, чем расчёт на CPU
Арифметическая интенсивность решает. Сложение векторов — плохой кандидат, умножение больших матриц — отличный.

Почему ветвистый код с множеством if плохо работает на GPU?

  • GPU не поддерживает if
  • Потоки варпа выполняют одну команду, поэтому разные ветки выполняются по очереди с маскированием
  • Ветвление требует копирования по PCIe
  • GPU медленнее CPU всегда
Это расхождение (divergence): часть дорожек простаивает.

Какая задача выиграет от дискретной видеокарты сильнее всего?

  • Сложение двух массивов по 1 ГБ один раз
  • Разбор JSON-запроса
  • Обработка одного HTTP-запроса
  • Умножение двух больших матриц
Много вычислений на байт — копирование по PCIe окупается.
Чем архитектура GPU отличается от CPU?

CPU тратит транзисторы на ускорение одного потока: внеочередное исполнение, предсказание, большие кэши. GPU — на количество простых вычислительных дорожек, объединённых в варпы, которые выполняют одну команду над разными данными, и прячет задержку памяти переключением между множеством варпов. CPU выигрывает на ветвистом последовательном коде, GPU — на массово-параллельной однородной работе.

Что такое арифметическая интенсивность и почему она важна для ускорителей?

Отношение числа вычислительных операций к объёму перемещаемых данных. Если она низкая, производительность ограничена пропускной способностью памяти и передачей по шине, а не вычислениями; ускоритель не успевает получать данные. Для дискретного GPU добавляется ещё и копирование по PCIe.

Какие «ускорители» использует обычная JVM без всяких GPU?

Интринсики на специальных командах процессора: AES-NI и PCLMULQDQ для AES-GCM, SHA-NI, CRC32/CRC32C, векторные команды для Arrays.equals/fill/sort, String.indexOf, кодирования UTF-8 и Base64, Vector API, атомарные команды для CAS. JIT подставляет их вместо обычного кода, если процессор их поддерживает.
