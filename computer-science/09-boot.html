Загрузка: от кнопки питания до ядра

Когда вы нажимаете кнопку питания, в памяти нет ни операционной системы, ни драйверов, ни даже настроенной оперативной памяти. Процессор начинает с одного фиксированного адреса, и дальше каждая ступень загружает и проверяет следующую: прошивка инициализирует железо, загрузчик находит ядро, ядро настраивает процессор, память и устройства и запускает первый процесс, от которого происходят все остальные. Разберём эту цепочку — в том числе потому, что JVM при запуске проходит похожий путь в миниатюре.

9.1Питание и вектор сброса

С нуля: эстафета

Запуск компьютера — эстафета. Первый бегун очень простой и знает только одно: где найти второго. Второй умеет больше и находит третьего, и так далее, пока палочку не получит операционная система, а от неё — ваша программа. Каждый следующий бегун сложнее предыдущего, и каждый проверяет, что следующий — «свой», а не подменённый злоумышленником.

Строго

  1. Питание. Блок питания выводит напряжения на рабочий уровень и выставляет сигнал «питание в норме» (Power Good). До этого процессор удерживается в состоянии сброса (reset — исходное «выключенное» состояние, из которого он начинает работу).
  2. Служебные процессоры. Ещё до основного процессора стартуют встроенные контроллеры со своей прошивкой: Intel Management Engine / AMD Platform Security Processor (служебные процессоры безопасности внутри чипсета и процессора), контроллер встраиваемых функций (EC — Embedded Controller: клавиатура, батарея, вентилятор) в ноутбуке, BMC (Baseboard Management Controller — контроллер удалённого управления сервером) в сервере. Они проверяют подпись прошивки и выпускают основной процессор из сброса.
  3. Вектор сброса. Одно ядро (BSP — bootstrap processor, «загрузочный процессор») начинает исполнять команды с фиксированного адреса 0xFFFFFFF0 — 16 байт ниже 4 ГБ. Этот адрес аппаратно отображён не на оперативную память, а на микросхему флеш-памяти (памяти, не стирающейся без питания) с прошивкой. Остальные ядра (AP — application processors) спят до явной команды.
  4. Наследие 8086. x86-процессор по-прежнему просыпается в реальном режиме (real mode) — 16-битном, без защиты памяти, как процессор 8086 в 1978 году. Первые же команды прошивки переводят его в защищённый (protected mode, 32 бита, с защитой памяти) и длинный (long mode, 64 бита) режимы. С 2020-х Intel предлагает убрать это наследие (архитектура x86S — упрощённый x86 без старых режимов), а ARM-машины такого груза не несут вовсе.
Оперативной памяти пока нет Контроллер DRAM (оперативной памяти) не настроен: прошивка не знает, какие модули стоят и на каких таймингах (задержках между командами памяти) они работают. Первый код исполняется прямо из флеш-памяти, а в качестве памяти использует кэш процессора в специальном режиме (cache-as-RAM — «кэш вместо оперативной памяти»). Один из первых больших шагов прошивки — тренировка памяти: подбор задержек и уровней сигналов для каждой линии данных. Поэтому первый запуск после замены модулей длится десятки секунд, а потом результат кэшируется.
Главное После включения процессор начинает с фиксированного адреса в микросхеме прошивки, в старом 16-битном режиме и без настроенной оперативной памяти. Первым делом прошивка переводит его в 64-битный режим и настраивает память.

9.2Прошивка: UEFI

Старый BIOS (Basic Input/Output System — «базовая система ввода-вывода», 1981) уступил место UEFI (Unified Extensible Firmware Interface — «единый расширяемый интерфейс прошивки») — по сути маленькой операционной системе со своими драйверами (программами управления устройствами), файловой системой FAT (File Allocation Table — простая файловая система, понятная всем ОС), сетью и командной оболочкой. Как ОС узнаёт о железе. Прошивка оставляет в памяти таблицы ACPI (Advanced Configuration and Power Interface — «интерфейс конфигурации и управления питанием»: сколько ядер и как они связаны, NUMA-узлы, таймеры, контроллеры прерываний, управление питанием, байткод AML — ACPI Machine Language — для специальных устройств) и SMBIOS (System Management BIOS: производитель, модель, версия прошивки, модули памяти). Именно отсюда lscpu, «Сведения о системе» Windows и JVM узнают топологию процессора. Карта памяти — какие физические адреса заняты прошивкой, какие свободны — передаётся загрузчику вызовом GetMemoryMap («получить карту памяти»).

Главное UEFI — маленькая ОС в прошивке: по фазам инициализирует процессор, память и устройства, выбирает, откуда загружаться, и оставляет для ОС таблицы ACPI и SMBIOS с описанием железа.

9.3Цепочка доверия: Secure Boot и TPM

В эстафете важно, чтобы палочку не перехватил чужой бегун. Если злоумышленник подменит загрузчик или ядро, никакой антивирус внутри ОС этого не увидит: вредоносный код запустится раньше. Поэтому каждая ступень проверяет следующую:

  • Secure Boot («безопасная загрузка»): прошивка запускает только загрузчики, подписанные (снабжённые цифровой подписью, которую нельзя подделать без секретного ключа) ключами из своей базы (обычно ключ Microsoft; Linux-дистрибутивы используют подписанный Microsoft промежуточный загрузчик shim («прокладка»), который проверяет GRUB (GRand Unified Bootloader — «великий единый загрузчик») и ядро ключом дистрибутива). Дистрибутив — готовая сборка Linux: Ubuntu, Fedora, Debian. Ядро, в свою очередь, проверяет подписи модулей.
  • TPM (Trusted Platform Module — «доверенный платформенный модуль», отдельный защищённый чип) и измеряемая загрузка: каждая ступень вычисляет хэш (короткий «отпечаток») следующей и «добавляет» его в регистры PCR (Platform Configuration Register) чипа TPM. Изменить значение назад нельзя — только продолжить цепочку. Ключи шифрования диска (BitLocker в Windows, LUKS — Linux Unified Key Setup — с TPM) «запечатаны» на определённые значения PCR: изменённый загрузчик — другие хэши — диск не расшифруется.
Главное Каждая ступень загрузки проверяет подпись следующей (Secure Boot), а TPM записывает хэши всех ступеней. Подменённый загрузчик не запустится или не получит ключ к зашифрованному диску.

9.4Загрузчик

На диске с таблицей разделов GPT (GUID Partition Table — современный способ разбить диск на разделы, независимые части) есть системный раздел EFI (ESP — EFI System Partition) с файловой системой FAT32. Прошивка читает с него программу-загрузчик — обычный исполняемый файл формата PE (Portable Executable — формат программ Windows и UEFI): \EFI\BOOT\BOOTX64.EFI, \EFI\Microsoft\Boot\bootmgfw.efi (Windows), \EFI\ubuntu\shimx64.efi → grubx64.efi (Linux).

Загрузчик (GRUB, systemd-boot, Windows Boot Manager) показывает меню выбора системы, затем загружает в память:

  • ядро — Linux: сжатый образ vmlinuz (vm — virtual memory, z — сжатый); Windows: winload.efi → ntoskrnl.exe;
  • initramfs (initial RAM filesystem) — маленькую файловую систему в памяти с драйверами и программами, нужными, чтобы найти и смонтировать (подключить в дерево файлов) настоящий корневой диск (тот, на котором лежит «/») (который может быть на RAID, зашифрован, по сети);
  • командную строку ядра: какой диск корневой, параметры отладки, ограничения (в лабе 9.2 видно, что WSL — Windows Subsystem for Linux, Linux внутри Windows, — передаёт ядру nr_cpus=18 и путь к initrd, initial RAM disk).

Затем загрузчик вызывает ExitBootServices («завершить загрузочные службы») — прошивка «уходит» и больше не управляет железом — и передаёт управление точке входа ядра.

Главное Загрузчик с раздела ESP показывает меню, загружает в память ядро, initramfs и командную строку ядра, после чего прошивка уходит со сцены.

9.5Старт ядра

  1. Распаковка и ранняя настройка. Ядро распаковывает себя, строит свои таблицы страниц (тема 08) и включает виртуальную память: с этого момента ядро живёт в верхней половине адресного пространства.
  2. start_kernel — общая инициализация: учёт физической памяти по карте от прошивки, распределители памяти ядра, таблица обработчиков прерываний (IDT — Interrupt Descriptor Table, тема 10), таймеры и источник времени (TSC — Time Stamp Counter, счётчик тактов процессора; HPET — High Precision Event Timer, таймер высокой точности), планировщик (кому из потоков давать процессор, тема 11), модель устройств.
  3. Запуск остальных ядер. BSP посылает каждому спящему ядру межпроцессорные прерывания INIT («инициализация») и SIPI (Startup Inter-Processor Interrupt — «прерывание запуска») с адресом стартового кода. Каждое ядро проходит свою короткую инициализацию и сообщает о готовности — в журнале ядра Linux это строки smp: Brought up 1 node, 18 CPUs («подняты 1 узел, 18 процессоров»; SMP — Symmetric MultiProcessing, симметричная многопроцессорность).
  4. Драйверы. Перебор шин (PCIe, USB), сопоставление устройств с драйверами, загрузка модулей ядра (частей ядра, подключаемых по необходимости).
  5. Корневая файловая система. Ядро распаковывает initramfs и запускает из неё /init, тот находит настоящий корневой диск, монтирует его и передаёт управление (switch_root — «сменить корень»).
  6. PID 1. (PID — Process ID, номер процесса.) Ядро запускает первую программу пользовательского режима (обычных программ, без прав ядра, тема 10) — /sbin/init (в современных дистрибутивах это systemd). Это единственный процесс, созданный не через fork (системный вызов «создать копию процесса»); все остальные — его потомки.
Главное Ядро включает свою виртуальную память, прерывания, таймеры и планировщик, будит остальные ядра процессора, находит драйверы и корневой диск и запускает первый процесс — PID 1.

9.6Пользовательское пространство и PID 1

systemd («system daemon», системная служба) читает описания юнитов (unit — файлов с описанием службы) и параллельно запускает службы (фоновые программы, «демоны») с учётом зависимостей: монтирование дисков, сеть, журнал, SSH (Secure Shell — удалённый вход), Docker (запуск контейнеров), базы данных, ваше Java-приложение как .service. Особые обязанности PID 1:

  • Усыновление сирот: если процесс завершился раньше детей, они становятся детьми PID 1; он обязан забирать их статус завершения (код, с которым процесс закончился) вызовом wait, иначе они остаются «зомби» — записями о завершённых процессах, занимающими место в таблице.
  • Сигналы (уведомления ОС процессу, тема 10): ядро не доставляет PID 1 сигналы, для которых он не установил обработчик (даже SIGTERM — «пожалуйста, завершись»), — защита от случайного убийства init.
Java как PID 1 в контейнере В контейнере (изолированной «коробке» для программы, тема 15) первым процессом своего пространства PID становится то, что указано в ENTRYPOINT (команда запуска в описании образа Docker). Если это java — она PID 1: JVM устанавливает обработчик SIGTERM, поэтому docker stop корректно запускает shutdown hooks (код, который Java выполняет при завершении). Но если запустить через shell (командную оболочку; ENTRYPOINT java -jar app.jar в shell-форме), PID 1 — это sh, который сигнал не перешлёт: через 10 секунд придёт SIGKILL, и приложение умрёт без корректного завершения (JVM, тема 22). Решения — exec-форма ENTRYPOINT ["java", …], exec java в скрипте или маленький init (tini — крошечная программа-init для контейнеров, docker run --init).

Windows проходит похожий путь: winload загружает ядро ntoskrnl.exe и драйверы загрузки, ядро запускает диспетчер сеансов smss.exe (Session Manager Subsystem), тот — wininit.exe (службы через services.exe, проверка подлинности через lsass.exe — Local Security Authority Subsystem Service) и winlogon.exe (вход пользователя, затем explorer.exe).

Процессор просыпается в режиме совместимости с 8086 и исполняет код прямо из флеш-памяти прошивки.

Пока DRAM не настроена, временной памятью служит кэш. Тренировка памяти — одна из самых долгих фаз.

UEFI находит устройства и описывает их для ОС в таблицах ACPI.

Проверка подписи (Secure Boot), загрузка ядра и initramfs, прошивка уходит со сцены.

Ядро включает свою виртуальную память, прерывания и планировщик, будит остальные ядра процессора.

Временная файловая система в памяти помогает найти настоящий корневой диск, затем стартует первый процесс.

Init запускает службы; ваше приложение — одна из них, и его запуск — уже следующий слой загрузки.

Главное PID 1 (обычно systemd) запускает все службы, «усыновляет» сирот и не получает сигналов без обработчика. В контейнере Java должна быть PID 1 через exec-форму ENTRYPOINT, иначе не завершится корректно.

9.7Загрузка JVM — та же идея в миниатюре

Запуск Java-программы повторяет схему «каждая ступень готовит следующую» (подробно — JVM, тема 01):

КомпьютерJVM
прошивка находит загрузчик по BootOrderлаунчер java (программа запуска) разбирает аргументы, находит и загружает libjvm.so (саму JVM как библиотеку)
ядро размечает память и включает виртуальную памятьJVM резервирует кучу (память объектов), metaspace (описания классов), code cache (машинный код JIT) — тема 08
ядро генерирует таблицы и инициализирует подсистемыJVM генерирует машинный код интерпретатора и заглушки («Interpreter generation» в логе -Xlog:startuptime), запускает служебные потоки (сборщика мусора, JIT-компиляторов)
initramfs с минимумом драйверовбазовые классы java.base из архива CDS (Class Data Sharing — заранее подготовленные классы) или lib/modules

И проблема та же: старт — это работа, которую хочется сделать один раз. Компьютеры для этого засыпают и просыпаются (сохраняя состояние в памяти или на диске), JVM — использует CDS, AOT cache (Ahead-Of-Time — «заранее»: кэш подготовленного кода; проект Leyden) или снимки CRaC (Coordinated Restore at Checkpoint — сохранение запущенной JVM и мгновенное восстановление) (JVM, тема 20).

Главное Запуск JVM повторяет ту же эстафету в миниатюре: лаунчер → резервирование памяти → генерация интерпретатора → базовые классы → main. Ускоряют её CDS, AOT cache и CRaC.

9.8Практикум: пишем и запускаем

Перезагружать компьютер ради лабы не будем — посмотрим на следы загрузки: что прошивка сообщила ОС, какую командную строку получило ядро, что оно писало в журнал при старте, кто PID 1 в контейнере, — и как по шагам «загружается» сама JVM. Модуль IDEA — cs09.

Код набирайте руками — так он запоминается. Перед запуском запишите предсказание в поле «Ваш прогноз», затем сверьтесь с реальным выводом (снят на JDK 25.0.2; адреса, времена и хэши у вас будут другими). Как подготовить окружение — на странице курса.

Лаба 9.1Прошивка вашего компьютера10 мин

Узнать тип прошивки и данные SMBIOS, которые она передала операционной системе.

  1. В PowerShell (Windows):
    $env:firmware_type
Get-CimInstance Win32_BIOS | Format-List Manufacturer, SMBIOSBIOSVersion, ReleaseDate
(Get-CimInstance Win32_OperatingSystem).LastBootUpTime
    Вывод (JDK 25.0.2)
    UEFI
Manufacturer      : XIAOMI
SMBIOSBIOSVersion : RMAMT6B0P0A0A
ReleaseDate       : 6/4/2024 3:00:00 AM

    firmware_type — UEFI или Legacy (BIOS). Производитель и версия — из таблицы SMBIOS. Проверка Secure Boot — Confirm-SecureBootUEFI в PowerShell от имени администратора (иначе «Access was denied»). На Linux то же самое: ls /sys/firmware/efi (каталог есть — UEFI), sudo dmidecode -t bios, mokutil --sb-state.

Лаба 9.2Командная строка и журнал ядра15 мин

Посмотреть, с какими параметрами загрузчик запустил ядро Linux и что ядро писало о себе при старте. На Windows Docker работает внутри лёгкой виртуальной машины WSL 2 — это её ядро.

  1. docker run --rm cs-lab cat /proc/cmdline
docker run --rm cs-lab uname -sr
    Вывод (JDK 25.0.2)
    initrd=\initrd.img WSL_ROOT_INIT=1 panic=-1 nr_cpus=18 hv_utils.timesync_implicit=1 console=hvc0 debug pty.legacy_count=0 WSL_ENABLE_CRASH_DUMP=1
Linux 6.18.33.2-microsoft-standard-WSL2
  2. Сколько ядер процессора ядро ОС «подняло» при старте (раздел 9.5, INIT/SIPI) и сколько оно уже работает:
    docker run --rm cs-lab sh -c "cat /sys/devices/system/cpu/online; nproc; cut -d' ' -f1 /proc/uptime"
    Вывод (JDK 25.0.2)
    0-17
18
421267.90

    Журнал загрузки ядра читается командой dmesg (в контейнере — только с --privileged). Это кольцевой буфер: на долго работающей машине самые ранние строки уже вытеснены, поэтому смотреть журнал загрузки лучше сразу после старта — или в сохранённом журнале journalctl -k -b на обычном Linux.

  3. Что из командной строки ядра передал загрузчик? Сколько процессоров ядро разбудило при старте?

    В командной строке WSL: initrd=\initrd.img — путь к initramfs (обратная косая черта — путь Windows: ядро грузит загрузчик Hyper-V), nr_cpus=18 — сколько процессоров разрешено поднять, console=hvc0 — консоль через гипервизор, panic=-1 — немедленная перезагрузка при панике ядра. Онлайн процессоры 0-17 — все 18 логических процессоров разбужены. /proc/uptime — секунды с момента старта ядра (у WSL это время с первого запуска Docker или WSL, а не с включения компьютера).

Лаба 9.3Кто PID 110 мин

Увидеть, что в контейнере первым процессом становится точка входа, и почему это важно для сигналов.

  1. docker run --rm cs-lab ps -o pid,ppid,comm
docker run --rm cs-lab sh -c "sleep 1 & ps -o pid,ppid,comm"
docker run --rm --init cs-lab ps -o pid,ppid,comm
    Вывод (JDK 25.0.2)
        PID    PPID COMMAND
      1       0 ps
    PID    PPID COMMAND
      1       0 sh
      7       1 sleep
      8       1 ps
    PID    PPID COMMAND
      1       0 docker-init
      7       1 ps
  2. Кто будет PID 1 в каждом из трёх запусков?

    В первом — сам ps: точка входа контейнера и есть PID 1, родитель — 0 (его создало ядро/рантайм, а не fork внутри контейнера). Во втором PID 1 — sh, а sleep и ps — его дети. В третьем с --init PID 1 — маленький init (docker-init, это tini), он пересылает сигналы и собирает зомби, а ваша программа — PID 2. Для Java: exec-форма ENTRYPOINT ["java", …] делает JVM PID 1, и она сама корректно обрабатывает SIGTERM.

  2. Какие фазы займут больше всего времени? Что означает строка «Interpreter generation»?

    «Genesis» (создание базовых структур VM, кучи и metaspace) и «Initialize java.lang classes» — самые долгие, вся «Create VM» укладывается в 40–60 мс. «Interpreter generation» — JVM при старте генерирует машинный код своего шаблонного интерпретатора под конкретный процессор (с учётом его расширений), подобно тому как ядро строит свои таблицы под железо. Затем запускается VM Thread, инициализируется система модулей, и только потом — ваш main.

  3. Сравните время запуска с архивом CDS (по умолчанию) и без него:

java -Xshare:off -Xlog:startuptime Hello
    Вывод (JDK 25.0.2)
    [0.050s][info][startuptime] Create VM, 0.0446356 secs
[0.109s][info][startuptime] Create VM, 0.1036229 secs

Здесь «Create VM» без архива — примерно втрое дольше. Это аналог «быстрой загрузки» Windows, которая не загружается с нуля, а восстанавливает ядро из гибернации.

9.10Самопроверка

Откуда процессор x86 берёт первую команду после сброса?

  • с начала диска
  • с фиксированного адреса 0xFFFFFFF0, отображённого на флеш-память прошивки
  • из оперативной памяти по адресу 0
  • от загрузчика по сети
Вектор сброса. Оперативная память в этот момент ещё даже не настроена.

Как ОС узнаёт, сколько у компьютера ядер, какие NUMA-узлы и устройства?

  • перебирает адреса памяти
  • из реестра
  • спрашивает пользователя
  • из таблиц ACPI и SMBIOS, которые прошивка оставляет в памяти
Плюс перебор шин PCIe и USB при инициализации драйверов.

Зачем нужен initramfs?

  • чтобы иметь драйверы и утилиты для поиска и монтирования настоящего корневого диска
  • для хранения логов загрузки
  • это swap-раздел
  • для Secure Boot
Корень может быть на RAID, LVM, зашифрованном разделе или в сети — ядру нужны модули и логика, которых нет внутри него самого.

Java-приложение в контейнере запущено как ENTRYPOINT java -jar app.jar (shell-форма). Что будет при docker stop?

  • JVM корректно завершится
  • контейнер не остановится
  • SIGTERM получит sh (PID 1) и не перешлёт его; через таймаут придёт SIGKILL, shutdown hooks не выполнятся
  • JVM сделает дамп памяти
Exec-форма ENTRYPOINT ["java", …] делает java PID 1, и SIGTERM доходит до JVM.

Откуда процессор берёт первую команду после включения?

  • С диска
  • С фиксированного адреса, отображённого на микросхему прошивки
  • Из оперативной памяти
  • Из сети
Оперативная память в этот момент ещё даже не настроена.

Почему ENTRYPOINT java -jar app.jar в shell-форме мешает корректному завершению?

  • Java не поддерживает контейнеры
  • Не хватает памяти
  • PID 1 становится sh, который не пересылает SIGTERM; через 10 секунд приходит SIGKILL
  • Docker не умеет останавливать Java
Используйте exec-форму ENTRYPOINT ["java", …] или tini.
Перечислите ступени загрузки компьютера.

Питание и служебные контроллеры → вектор сброса, код прошивки из флеш-памяти → инициализация процессора и тренировка памяти → драйверы UEFI и таблицы ACPI → выбор устройства и проверка подписи загрузчика → загрузчик грузит ядро, initramfs и командную строку → ядро включает свою виртуальную память, прерывания, планировщик, будит ядра процессора, инициализирует драйверы → initramfs монтирует корень → PID 1 (systemd) → службы и приложения.

Что такое Secure Boot и чем он отличается от измеряемой загрузки с TPM?

Secure Boot — проверка подписи каждой следующей ступени до её запуска: неподписанный загрузчик не запустится. Измеряемая загрузка ничего не запрещает, а записывает хэши всех ступеней в регистры TPM; секреты (ключи шифрования диска) выдаются только при ожидаемых значениях. Вместе они защищают от подмены кода, исполняемого раньше ОС.

Почему PID 1 особенный и как это касается Java в контейнерах?

PID 1 усыновляет осиротевшие процессы и должен собирать их статус, а ядро не доставляет ему сигналы без явного обработчика. В контейнере PID 1 — точка входа. Если это shell без exec, SIGTERM не дойдёт до JVM, и при остановке процесс убьют SIGKILL без shutdown hooks. Нужна exec-форма ENTRYPOINT или init-процесс (tini, --init).
