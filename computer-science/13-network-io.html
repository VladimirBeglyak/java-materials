Сетевая карта сама пишет пакеты в память — процессор не копирует ни байта.

Под нагрузкой прерывания «склеиваются»: ядро переходит в режим опроса и забирает пакеты пачками.

Протоколы разбираются в ядре, в контексте softirq — время видно в top как si.

Пока программа не прочитала, данные лежат в ядре. Буфер полон — TCP уменьшает окно, и отправитель притормаживает.

Последнее копирование — из ядра в память процесса.

Отправка — зеркально: write() копирует данные в буфер отправки сокета и обычно возвращается сразу; ядро нарезает их на сегменты, строит заголовки и ставит в очередь передачи карты. Возврат write не означает, что данные дошли до получателя, — только что ядро их приняло. Аппаратные разгрузки (TSO, GRO, контрольные суммы) переносят нарезку и склейку сегментов в сетевую карту.

13.2Сокет — это файловый дескриптор

Для программы сокет — небольшое целое число, дескриптор, как у открытого файла: read, write, close работают так же. За ним в ядре — структура с состоянием TCP-соединения, буферами приёма и отправки, очередью ожидающих потоков.

  • Лимит дескрипторов (ulimit -n, часто 1024 по умолчанию для сессии, в контейнерах — больше): каждое соединение — дескриптор. «Too many open files» под нагрузкой — классическая авария.
  • Эфемерные порты клиента: исходящих соединений к одному адресу и порту не больше ~28 тысяч (диапазон 32768–60999) — причина ошибок «Cannot assign requested address» у клиентов без пула соединений. После закрытия соединение ещё ~60 секунд в состоянии TIME_WAIT.
  • Loopback (127.0.0.1): пакеты не доходят до карты, но проходят весь стек TCP/IP в ядре. Unix-сокеты (тема 11) — быстрее, без TCP.

13.3Модели ввода-вывода

Блокирующий: поток на соединение

read() на сокете без данных усыпляет поток в ядре (состояние S, хотя в Java — RUNNABLE, тема 11). Код простой и линейный: принял соединение — отдал его потоку, поток читает запрос, ходит в базу, пишет ответ. Цена — поток ОС на каждое одновременное соединение: стек (резерв 1 МБ и реально занятые десятки КБ), структура в ядре, переключения контекста. Тысячи потоков — терпимо, десятки и сотни тысяч — нет. Так работали сервлет-контейнеры (Tomcat с пулом 200 потоков).

Неблокирующий с мультиплексированием: epoll

Сокет переводят в неблокирующий режим: read без данных сразу возвращает EAGAIN. А чтобы не опрашивать тысячи сокетов вхолостую, ядро предоставляет мультиплексор: «вот мои сокеты — разбуди меня, когда хотя бы на одном что-то случится».

МеханизмОСОсобенность
select, pollPOSIXна каждый вызов передаётся весь список сокетов — O(n) на вызов
epollLinuxсписок регистрируется в ядре один раз (epoll_ctl), epoll_wait возвращает только готовые — O(готовых)
kqueuemacOS, BSDто же, плюс события файлов, процессов, таймеров
IOCPWindowsмодель завершения: «прочитай в этот буфер и сообщи, когда готово»
io_uringLinux 5.1+общие с ядром кольца запросов и ответов в памяти: пачки операций (сеть, файлы) почти без системных вызовов

Цикл событий (event loop): один поток вызывает epoll_wait, получает список готовых сокетов, для каждого читает доступные данные, продвигает обработку и снова ждёт. Пока он не возвращается в цикл, все остальные соединения ждут — поэтому в обработчиках событий нельзя блокироваться (запросом в БД через JDBC, Thread.sleep). Так устроены nginx, Node.js, Netty, Vert.x, Spring WebFlux (пособие WebFlux).

Виртуальные потоки: блокирующий код поверх epoll

Виртуальные потоки Java объединяют обе модели: код пишется блокирующим (socket.read()), но JVM внутри делает сокет неблокирующим. Если данных нет (EAGAIN), виртуальный поток регистрирует сокет в системном poller (epoll на Linux, kqueue на macOS, IOCP-подобный механизм на Windows) и паркуется, освобождая поток-носитель; когда poller сообщает о готовности, виртуальный поток снова ставится в очередь. Лаба 13.3 показывает это по системным вызовам.

13.4Копирования и zero-copy

Отдача файла по сети «в лоб» — read(file) в буфер программы, затем write(socket): данные копируются из page cache в память процесса и обратно в ядро, плюс два системных вызова на каждый кусок. sendfile отправляет данные из page cache прямо в сокет, не поднимая их в пользовательское пространство; с поддержкой карты (scatter-gather DMA) копирований в процессоре нет совсем. В Java это FileChannel.transferTo(…, socketChannel) — так Kafka отдаёт сообщения потребителям и так веб-серверы отдают статику. Дальше по шкале — обход ядра (DPDK, RDMA) для бирж и хранилищ, где важны единицы микросекунд.

Лаба 13.1Блокирующий сервер15 мин

Найти socket, bind, listen, accept, read и write в работе простейшего эхо-сервера.

  1. Создайте файл BlockingEcho.java:
    import java.io.IOException;
import java.io.UncheckedIOException;
import java.net.InetAddress;
import java.net.ServerSocket;
import java.net.Socket;

public class BlockingEcho {
    public static void main(String[] args) throws Exception {
        InetAddress lo = InetAddress.getLoopbackAddress();
        try (ServerSocket server = new ServerSocket(9000, 50, lo)) {          // socket + bind + listen
            Thread client = new Thread(() -> {
                try (Socket s = new Socket(lo, 9000)) {                          // connect
                    s.getOutputStream().write("ping\n".getBytes());
                    s.getInputStream().read();
                } catch (IOException e) { throw new UncheckedIOException(e); }
            });
            client.start();
            try (Socket conn = server.accept()) {                                // accept — новый дескриптор
                byte[] buf = new byte[16];
                int n = conn.getInputStream().read(buf);                         // read — спим, пока нет данных
                conn.getOutputStream().write(buf, 0, n);                         // write — в буфер отправки
            }
            client.join();
        }
    }
}

Лаба 13.2NIO Selector — это epoll15 мин

Убедиться, что Selector на Linux реализован через epoll, и увидеть цикл событий.

  1. Создайте файл NioEcho.java:
    import java.io.IOException;
import java.io.UncheckedIOException;
import java.net.InetAddress;
import java.net.InetSocketAddress;
import java.nio.ByteBuffer;
import java.nio.channels.*;

public class NioEcho {
    public static void main(String[] args) throws Exception {
        InetSocketAddress addr = new InetSocketAddress(InetAddress.getLoopbackAddress(), 9001);
        Selector selector = Selector.open();                                     // epoll_create
        ServerSocketChannel server = ServerSocketChannel.open().bind(addr);
        server.configureBlocking(false);
        server.register(selector, SelectionKey.OP_ACCEPT);                       // epoll_ctl(ADD, слушающий сокет)

        Thread client = new Thread(() -> {
            try (SocketChannel s = SocketChannel.open(addr)) {
                s.write(ByteBuffer.wrap("ping".getBytes()));
                s.read(ByteBuffer.allocate(8));
            } catch (IOException e) { throw new UncheckedIOException(e); }
        });
        client.start();

        boolean done = false;
        while (!done) {
            selector.select();                                                   // epoll_wait — ждём любого события
            for (SelectionKey key : selector.selectedKeys()) {
                if (key.isAcceptable()) {
                    SocketChannel ch = server.accept();
                    ch.configureBlocking(false);
                    ch.register(selector, SelectionKey.OP_READ);                 // epoll_ctl(ADD, новое соединение)
                } else if (key.isReadable()) {
                    SocketChannel ch = (SocketChannel) key.channel();
                    ByteBuffer buf = ByteBuffer.allocate(8);
                    ch.read(buf);
                    buf.flip();
                    ch.write(buf);
                    ch.close();
                    done = true;
                }
            }
            selector.selectedKeys().clear();
        }
        client.join();
    }
}

  2. Сколько раз поток сервера вызовет epoll_wait и что будет между вызовами?

    epoll_create1 — создание селектора; epoll_ctl(…, EPOLL_CTL_ADD, fd, {events=EPOLLIN…}) — регистрация слушающего сокета. Затем цикл: epoll_wait (ждём) → событие на слушающем сокете → accept → epoll_ctl(ADD) нового соединения → снова epoll_wait → событие чтения → read(…, "ping") и write. Один поток обслуживает любое число соединений: между ожиданиями он занят только теми сокетами, где что-то произошло.

Лаба 13.3Виртуальный поток паркуется на сокете15 мин

Увидеть, что блокирующий read() в виртуальном потоке на самом деле неблокирующий: EAGAIN, регистрация в poller и пробуждение.

  1. Создайте файл VirtualRead.java:
    import java.io.IOException;
import java.io.UncheckedIOException;
import java.net.InetAddress;
import java.net.ServerSocket;
import java.net.Socket;

public class VirtualRead {
    public static void main(String[] args) throws Exception {
        InetAddress lo = InetAddress.getLoopbackAddress();
        try (ServerSocket server = new ServerSocket(9002, 50, lo)) {
            Thread client = new Thread(() -> {
                try (Socket s = new Socket(lo, 9002)) {
                    Thread.sleep(300);                                           // данные придут не сразу
                    s.getOutputStream().write("ping\n".getBytes());
                    s.getInputStream().read();
                } catch (Exception e) { throw new RuntimeException(e); }
            });
            client.start();
            Socket conn = server.accept();
            Thread vt = Thread.ofVirtual().start(() -> {
                try {
                    byte[] buf = new byte[16];
                    int n = conn.getInputStream().read(buf);                     // обычный блокирующий код
                    conn.getOutputStream().write(buf, 0, n);
                } catch (IOException e) { throw new UncheckedIOException(e); }
            });
            vt.join();
            client.join();
            conn.close();
        }
    }
}

  2. Какой результат вернёт первый read виртуального потока? Как он потом получит данные?

    Остальные строки EPOLL_CTL_ADD с другими номерами дескрипторов — служебные: потоки-poller JVM регистрируют свои внутренние каналы пробуждения. Нас интересует дескриптор соединения из строки с EAGAIN. Первый read(fd, …) возвращает -1 EAGAIN (Resource temporarily unavailable): JVM перевела сокет в неблокирующий режим. Затем epoll_ctl(…, EPOLL_CTL_ADD, fd, {events=EPOLLIN|EPOLLONESHOT…}) — сокет регистрируется в системном poller, а виртуальный поток паркуется: его носитель свободен для других. Когда клиент через 300 мс присылает данные, поток-poller в epoll_wait получает событие и снимает виртуальный поток с парковки; повторный read возвращает «ping». Посмотрите на номер в [pid N]: второй read часто выполняет другой поток ОС — виртуальный поток продолжил работу на другом носителе. Код при этом выглядит как обычный блокирующий.

Лаба 13.4Zero-copy: transferTo превращается в sendfile10 мин

Проверить, что отдача файла в сокет через transferTo не копирует данные через память Java.

  1. Создайте файл ZeroCopy.java:
    import java.io.IOException;
import java.io.UncheckedIOException;
import java.net.InetAddress;
import java.net.InetSocketAddress;
import java.nio.ByteBuffer;
import java.nio.channels.FileChannel;
import java.nio.channels.ServerSocketChannel;
import java.nio.channels.SocketChannel;
import java.nio.file.Files;
import java.nio.file.Path;

public class ZeroCopy {
    public static void main(String[] args) throws Exception {
        Path file = Files.write(Path.of("/tmp/payload.bin"), new byte[1 << 20]);   // 1 МБ
        InetSocketAddress addr = new InetSocketAddress(InetAddress.getLoopbackAddress(), 9003);
        try (ServerSocketChannel server = ServerSocketChannel.open().bind(addr)) {
            Thread client = new Thread(() -> {
                try (SocketChannel s = SocketChannel.open(addr)) {
                    ByteBuffer b = ByteBuffer.allocate(1 << 16);
                    long total = 0;
                    for (int n; (n = s.read(b)) > 0; b.clear()) total += n;
                    System.out.println("клиент получил " + total + " байт");
                } catch (IOException e) { throw new UncheckedIOException(e); }
            });
            client.start();
            try (SocketChannel conn = server.accept(); FileChannel fc = FileChannel.open(file)) {
                System.out.println("отправлено " + fc.transferTo(0, fc.size(), conn) + " байт");
            }
            client.join();
        }
    }
}

  2. Каким системным вызовом JDK отправит файл? Сколько вызовов понадобится на мегабайт?

    Сначала JDK пробует copy_file_range (он годится для «файл → файл», для сокета ядро отвечает EINVAL), затем — sendfile(сокет, файл, [0], 1048576): данные идут из page cache в сокет внутри ядра. Один-два вызова на весь мегабайт (если буфер сокета заполнился, sendfile отправит часть, и JDK повторит). Через read/write было бы десятки вызовов и двойное копирование через память JVM.

13.7Самопроверка

Что гарантирует успешный write() в TCP-сокет?

  • что получатель прочитал данные
  • что ядро скопировало данные в буфер отправки; доставка — позже
  • что пакет ушёл в сеть
  • что пришёл ACK
Подтверждение доставки в приложение даёт только протокол уровня приложения (ответ сервера).

Чем epoll лучше select для 100 000 соединений?

  • epoll работает в пользовательском режиме
  • select не поддерживает TCP
  • epoll читает данные за программу
  • набор сокетов хранится в ядре, и epoll_wait возвращает только готовые — не нужно передавать и проверять весь список на каждом вызове
Цена вызова пропорциональна числу готовых, а не всех сокетов.

Почему в обработчике цикла событий (Netty, WebFlux) нельзя делать блокирующий JDBC-запрос?

  • пока поток цикла ждёт базу, он не обслуживает все остальные соединения, привязанные к нему
  • JDBC не работает в Netty
  • это вызовет утечку памяти
  • epoll отключится
Блокирующие вызовы — на отдельный пул (Schedulers.boundedElastic) или переход на реактивный драйвер / виртуальные потоки.

Что делает виртуальный поток, если при socket.read() данных нет?

  • блокирует поток-носитель в ядре
  • крутится в цикле опроса
  • регистрирует сокет в poller (epoll), паркуется и освобождает носитель; продолжит, когда данные придут
  • бросает исключение
Код блокирующий, реализация — неблокирующая.
Опишите путь входящего пакета до read() в программе.

Сетевая карта по DMA кладёт кадр в кольцо приёма и посылает прерывание; драйвер в softirq (NAPI) забирает пачку пакетов; стек ядра разбирает Ethernet, IP, TCP, находит сокет, кладёт данные в его буфер приёма и отправляет ACK; ожидающий в read или epoll_wait поток просыпается, read копирует данные из буфера сокета в память программы.

Почему модель «поток на соединение» плохо масштабируется и что делать?

Каждое соединение держит поток ОС: стек, структуру в ядре, переключения контекста при каждом событии. На десятках тысяч соединений это память и время планировщика. Решения: мультиплексирование (epoll, цикл событий: Netty, WebFlux) или виртуальные потоки, которые сохраняют блокирующий стиль кода, но паркуются вместо блокировки потока ОС.

Что такое zero-copy и где он используется в Java?

Передача данных из файла в сокет без копирования через память процесса: системный вызов sendfile отправляет страницы page cache прямо в сетевой стек (и при поддержке карты — без копирования процессором). В Java — FileChannel.transferTo в SocketChannel. Использует Kafka для отдачи сообщений и веб-серверы для статики.
