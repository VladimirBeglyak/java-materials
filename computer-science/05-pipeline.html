Конвейер, предсказание ветвлений, SIMD

Современное ядро выполняет не одну команду за такт, а 4–8, хотя каждая отдельная команда проходит десяток этапов. Как: конвейер, несколько исполнительных блоков, внеочередное исполнение с переименованием регистров, предсказание переходов и спекуляция, векторные команды. Это объясняет загадки производительности: почему обработка отсортированного массива в 7 раз быстрее неотсортированного, почему четыре сумматора вместо одного ускоряют цикл вдвое и почему JIT превращает ваш цикл в векторные команды — а иногда нет.

5.1Конвейер: много команд одновременно

Цикл исполнения (тема 03) состоит из этапов: выборка (IF), декодирование (ID), исполнение (EX), обращение к памяти (MEM), запись результата (WB). Если ждать, пока команда пройдёт все пять этапов, и только потом начинать следующую, каждый блок большую часть времени простаивает. Конвейер работает как сборочная линия: пока одна команда исполняется, следующая декодируется, а третья выбирается из памяти. Каждый этап отделён регистрами, поэтому такт можно сделать короче — он определяется самым медленным этапом, а не всей командой (тема 02).

  • Задержка команды не уменьшается (пять этапов — пять тактов), а пропускная способность растёт: в идеале одна команда завершается каждый такт.
  • Реальные конвейеры длиннее — 14–20 этапов у современных x86 и ARM: чем короче этап, тем выше частота.

5.2Предсказание переходов

Условный переход встречается в среднем каждые 5–7 команд. Узнать, куда он пойдёт, можно только на этапе исполнения — через 10–15 тактов после выборки. Ждать нельзя: конвейер опустеет. Поэтому процессор угадывает направление и адрес перехода сразу при выборке и продолжает выбирать команды по предсказанию. Если угадал — ничего не потеряно. Если нет — всё, что выбрано после перехода, выбрасывается, и выборка начинается заново: штраф 15–20 тактов.

  • Буфер целей переходов (BTB) помнит для адресов переходов, куда они прыгали в прошлый раз, — так процессор знает адрес цели ещё до декодирования.
  • Двухбитный счётчик на каждый переход: состояния «точно нет / скорее нет / скорее да / точно да». Одна аномалия (выход из цикла) не переучивает предсказатель.
  • Предсказатели с историей (gshare, TAGE, перцептронные) учитывают, как шли последние десятки переходов, и распознают шаблоны вроде «через раз» или «каждый пятый». Точность на типичном коде — 95–99%.
  • Возвраты предсказываются отдельным стеком адресов возврата (RAS), косвенные переходы (виртуальные вызовы, switch по таблице) — своим предсказателем по истории.
Предсказатель переходов: 1 бит, 2 бита, 2 бита с историей

Задайте последовательность исходов перехода: T — переход выполнен, N — нет. Сравните точность трёх схем.

Как избежать штрафа

// данные случайны — переход «x >= 128» угадывается в 50% случаев
for (int x : data) if (x >= 128) sum += x;

// без перехода: маска из знакового бита (x - 128) >> 31 — это 0 или -1
for (int x : data) sum += x & ~((x - 128) >> 31);

// компиляторы часто делают это сами командой условной пересылки:
//   cmp eax, 128 ; cmovge edx, eax  — обе ветки вычисляются, выбор без перехода

C2 решает, ставить ли переход или cmov, по профилю, собранному интерпретатором: если ветка почти всегда идёт в одну сторону, переход выгоднее (он предсказуем, а cmov удлиняет цепочку зависимостей); если 50/50 — может выбрать cmov. Поэтому тот же код на других данных может работать по-разному. Классический пример — отсортированные данные: переход превращается в «сначала всегда N, потом всегда T» и предсказывается почти идеально (лаба 5.1).

5.3Суперскалярность и внеочередное исполнение

Конвейер даёт до одной команды за такт. Чтобы получить больше, ядро суперскалярное: выбирает и декодирует 4–8 команд за такт и имеет много исполнительных блоков (несколько АЛУ, блоки загрузки и сохранения, FP/SIMD-блоки). Но соседние команды часто зависят друг от друга, поэтому ядро ещё и исполняет их не по порядку (out-of-order):

  1. Переименование регистров. Каждой записи в архитектурный регистр (RAX) выделяется новый физический регистр из пула в 200–300. Это убирает ложные зависимости: две независимые команды, пишущие в RAX в разных местах цикла, больше не мешают друг другу.
  2. Окно команд (буфер переупорядочивания, ROB, на 300–600 мест). Команды ждут в нём своих операндов; любая, у которой операнды готовы, отправляется на свободный блок — даже если стоит позже ожидающей.
  3. Завершение по порядку (retirement). Результаты становятся «официальными» строго в порядке программы — так прерывания и исключения видят согласованное состояние, как будто команды шли по одной.

Главное следствие для программиста — параллелизм на уровне команд (ILP) ограничен цепочками зависимостей. Сумма массива одним аккумулятором — цепочка: каждое сложение ждёт предыдущее (4 такта у double). Четыре аккумулятора — четыре независимые цепочки, которые ядро исполняет одновременно:

double s = 0;
for (int i = 0; i < n; i++) s += a[i];                 // цепочка: такт задержки FP-сложения на элемент

double s0 = 0, s1 = 0, s2 = 0, s3 = 0;                   // 4 независимые цепочки — в лабе 5.2 вдвое быстрее
for (int i = 0; i + 3 < n; i += 4) { s0 += a[i]; s1 += a[i+1]; s2 += a[i+2]; s3 += a[i+3]; }

Почему JIT не делает это сам? Сложение double не ассоциативно (тема 01): перестановка изменила бы результат в последних битах, а Java требует точной семантики. Для целых чисел ассоциативность есть, и там C2 переставляет и векторизует смело. Тот же эффект объясняет, почему LongAdder и параллельные стримы иногда дают разные результаты суммирования double.

Спекуляция и Spectre Внеочередное ядро исполняет команды по предсказанному пути задолго до того, как становится известно, нужны ли они. Отменяются результаты в регистрах — но не следы в кэше. На этом построены атаки Spectre (2018): спекулятивно выполненный код читает секрет и оставляет его отпечаток в кэше, который потом измеряется по времени доступа. Подробно — тема 17; для JVM это означает, в частности, отключение некоторых оптимизаций и барьеры в коде, работающем с недоверенными данными.

5.4SIMD: одна команда — много данных

Векторные регистры хранят сразу несколько чисел, а одна команда обрабатывает их все: vaddps ymm0, ymm1, ymm2 складывает восемь пар float за раз.

  • Автовекторизация. C2 (оптимизация SuperWord) векторизует простые циклы по массивам: поэлементные операции, копирование, заполнение, некоторые целочисленные редукции. Внутренние функции JDK (Arrays.fill, equals, mismatch, String.indexOf, кодирование UTF-8) — интринсики на векторных командах.
  • Чего C2 не векторизует: циклы с зависимостью между итерациями, условными переходами внутри, вызовами, а также редукции double/float (из-за неассоциативности).
  • Vector API (jdk.incubator.vector, в инкубаторе с Java 16, в Java 25 — десятый раунд; ждёт проекта Valhalla) — явное векторное программирование, переносимое между AVX и NEON: FloatVector.SPECIES_PREFERRED выбирает ширину под процессор. Применяется в библиотеках машинного обучения, поиска (Lucene), обработки изображений.
static final VectorSpecies<Float> S = FloatVector.SPECIES_PREFERRED;   // 8 float на AVX2

static float dot(float[] a, float[] b) {
    var acc = FloatVector.zero(S);
    int i = 0;
    for (; i < S.loopBound(a.length); i += S.length())
        acc = FloatVector.fromArray(S, a, i).fma(FloatVector.fromArray(S, b, i), acc); // 8 умножений-сложений
    float s = acc.reduceLanes(VectorOperators.ADD);
    for (; i < a.length; i++) s += a[i] * b[i];     // хвост
    return s;
}

Лаба 5.1Отсортированный массив быстрее?15 мин

Воспроизвести знаменитый эффект: один и тот же цикл по тем же данным, но в другом порядке, работает в разы быстрее.

  1. Создайте файл Branch.java:
    import java.util.Arrays;
import java.util.Random;

public class Branch {
    static long sumIf(int[] a) {
        long s = 0;
        for (int x : a) if (x >= 128) s += x;
        return s;
    }

    static long sumBranchless(int[] a) {
        long s = 0;
        for (int x : a) s += x & ~((x - 128) >> 31);   // маска: 0, если x < 128, иначе все единицы
        return s;
    }

    public static void main(String[] args) {
        int[] data = new Random(42).ints(32 * 1024 * 1024, 0, 256).toArray();
        int[] sorted = data.clone();
        Arrays.sort(sorted);
        for (int r = 0; r < 4; r++) {
            long t0 = System.nanoTime(); long a = sumIf(data);
            long t1 = System.nanoTime(); long b = sumIf(sorted);
            long t2 = System.nanoTime(); long c = sumBranchless(data);
            long t3 = System.nanoTime();
            System.out.printf("if, случайные: %4d мс | if, отсортированные: %4d мс | без перехода, случайные: %4d мс  (%b)%n",
                    (t1 - t0) / 1_000_000, (t2 - t1) / 1_000_000, (t3 - t2) / 1_000_000, a == b && b == c);
        }
    }
}
  2. Во сколько раз будут различаться три столбца? Ведь данные и число операций одни и те же.
    javac Branch.java
java Branch
    Вывод (JDK 25.0.2)
    if, случайные:  116 мс | if, отсортированные:   12 мс | без перехода, случайные:   13 мс  (true)
if, случайные:  114 мс | if, отсортированные:   21 мс | без перехода, случайные:   15 мс  (true)
if, случайные:  114 мс | if, отсортированные:   14 мс | без перехода, случайные:   10 мс  (true)
if, случайные:  115 мс | if, отсортированные:   15 мс | без перехода, случайные:    9 мс  (true)

    На этой машине: около 115 мс на случайных данных против 11–17 мс на отсортированных — в 7–10 раз. На случайных данных переход x >= 128 угадывается в половине случаев, и каждая ошибка стоит ~15–20 тактов. На отсортированных — сначала всегда «нет», потом всегда «да»: предсказатель ошибается один-два раза на 32 млн итераций. Версия без перехода быстра на любых данных: ей нечего предсказывать. C2 мог бы и сам поставить cmov — но решает по профилю, и здесь оставил переход.

Поэкспериментируйте
  • Поменяйте порог на 255 (переход почти всегда «нет»).
    Случайный массив станет почти таким же быстрым, как отсортированный: переход стал предсказуемым. Дорого не ветвление само по себе, а непредсказуемое ветвление.
Лаба 5.2Цепочки зависимостей и ILP15 мин

Увидеть, что ядро исполняет независимые цепочки параллельно, а одна длинная цепочка ограничена задержкой операции.

  1. Создайте файл Ilp.java:
    public class Ilp {
    static double one(double[] a) {
        double s = 0;
        for (int i = 0; i < a.length; i++) s += a[i];
        return s;
    }

    static double four(double[] a) {
        double s0 = 0, s1 = 0, s2 = 0, s3 = 0;
        int i = 0;
        for (; i + 3 < a.length; i += 4) { s0 += a[i]; s1 += a[i + 1]; s2 += a[i + 2]; s3 += a[i + 3]; }
        for (; i < a.length; i++) s0 += a[i];
        return s0 + s1 + s2 + s3;
    }

    static long oneLong(long[] a) {
        long s = 0;
        for (int i = 0; i < a.length; i++) s += a[i];
        return s;
    }

    public static void main(String[] args) {
        double[] a = new double[4096];
        long[] l = new long[4096];
        for (int i = 0; i < a.length; i++) { a[i] = i * 0.5; l[i] = i; }
        int reps = 20_000;
        double n = (double) reps * a.length;
        for (int r = 0; r < 4; r++) {
            long t0 = System.nanoTime(); double x = 0; for (int k = 0; k < reps; k++) x += one(a);
            long t1 = System.nanoTime(); double y = 0; for (int k = 0; k < reps; k++) y += four(a);
            long t2 = System.nanoTime(); long z = 0;  for (int k = 0; k < reps; k++) z += oneLong(l);
            long t3 = System.nanoTime();
            System.out.printf("double, 1 сумматор: %.3f нс/эл | double, 4 сумматора: %.3f нс/эл | long, 1 сумматор: %.3f нс/эл%n",
                    (t1 - t0) / n, (t2 - t1) / n, (t3 - t2) / n);
        }
    }
}
  2. Какой вариант медленнее всех? Как поведёт себя long с одним сумматором по сравнению с double?
    javac Ilp.java
java Ilp
    Вывод (JDK 25.0.2)
    double, 1 сумматор: 0.528 нс/эл | double, 4 сумматора: 0.295 нс/эл | long, 1 сумматор: 0.300 нс/эл
double, 1 сумматор: 0.463 нс/эл | double, 4 сумматора: 0.240 нс/эл | long, 1 сумматор: 0.232 нс/эл
double, 1 сумматор: 0.466 нс/эл | double, 4 сумматора: 0.254 нс/эл | long, 1 сумматор: 0.237 нс/эл
double, 1 сумматор: 0.476 нс/эл | double, 4 сумматора: 0.246 нс/эл | long, 1 сумматор: 0.243 нс/эл

    double с одним сумматором — самый медленный: каждое сложение ждёт предыдущее (задержка FP-сложения — несколько тактов). Четыре сумматора — примерно вдвое быстрее: четыре независимые цепочки идут параллельно. long с одним сумматором идёт так же быстро, как четыре сумматора double: задержка целого сложения — 1 такт, и даже единственная цепочка не тормозит (здесь упираемся уже в чтение массива и накладные расходы цикла). Целое сложение ещё и ассоциативно — C2 вправе переставлять и векторизовать его, а для double не вправе: изменился бы результат.

Лаба 5.3SIMD: автовекторизация и Vector API20 мин

Сравнить обычный цикл, который C2 векторизует сам, с редукцией, которую он не векторизует, и то же на Vector API.

  1. Создайте файл Simd.java:
    import jdk.incubator.vector.FloatVector;
import jdk.incubator.vector.VectorOperators;
import jdk.incubator.vector.VectorSpecies;

public class Simd {
    static final VectorSpecies<Float> S = FloatVector.SPECIES_PREFERRED;

    static void mapScalar(float[] a, float[] b, float[] c) {
        for (int i = 0; i < a.length; i++) c[i] = a[i] * b[i] + 1f;
    }

    static void mapVector(float[] a, float[] b, float[] c) {
        int i = 0;
        for (; i < S.loopBound(a.length); i += S.length())
            FloatVector.fromArray(S, a, i).mul(FloatVector.fromArray(S, b, i)).add(1f).intoArray(c, i);
        for (; i < a.length; i++) c[i] = a[i] * b[i] + 1f;
    }

    static float dotScalar(float[] a, float[] b) {
        float s = 0;
        for (int i = 0; i < a.length; i++) s += a[i] * b[i];
        return s;
    }

    static float dotVector(float[] a, float[] b) {
        var acc = FloatVector.zero(S);
        int i = 0;
        for (; i < S.loopBound(a.length); i += S.length())
            acc = FloatVector.fromArray(S, a, i).fma(FloatVector.fromArray(S, b, i), acc);
        float s = acc.reduceLanes(VectorOperators.ADD);
        for (; i < a.length; i++) s += a[i] * b[i];
        return s;
    }

    public static void main(String[] args) {
        System.out.println("предпочтительный вектор: " + S + " — float в регистре: " + S.length());
        float[] a = new float[1 << 16], b = new float[a.length], c = new float[a.length];
        for (int i = 0; i < a.length; i++) { a[i] = i % 7; b[i] = i % 5; }
        double n = 2000.0 * a.length;
        for (int r = 0; r < 4; r++) {
            long t0 = System.nanoTime(); for (int k = 0; k < 2000; k++) mapScalar(a, b, c);
            long t1 = System.nanoTime(); for (int k = 0; k < 2000; k++) mapVector(a, b, c);
            long t2 = System.nanoTime(); float x = 0; for (int k = 0; k < 2000; k++) x += dotScalar(a, b);
            long t3 = System.nanoTime(); float y = 0; for (int k = 0; k < 2000; k++) y += dotVector(a, b);
            long t4 = System.nanoTime();
            System.out.printf("c=a*b+1: цикл %.3f, Vector API %.3f нс/эл | скалярное произведение: цикл %.3f, Vector API %.3f нс/эл%n",
                    (t1 - t0) / n, (t2 - t1) / n, (t3 - t2) / n, (t4 - t3) / n);
        }
    }
}

    IDEAВ IDEA: Run → Edit Configurations → VM options: --add-modules jdk.incubator.vector; и Settings → Build → Compiler → Java Compiler → Additional command line parameters: то же.

5.7Самопроверка

Что даёт конвейер?

  • уменьшает задержку каждой команды
  • повышает пропускную способность: одновременно в работе несколько команд на разных этапах
  • убирает зависимости между командами
  • позволяет обойтись без кэша
Каждая команда проходит все этапы, но новая начинается каждый такт; плюс короткие этапы позволяют поднять частоту.

Почему цикл if (x >= 128) sum += x по отсортированному массиву быстрее, чем по случайному?

  • отсортированный массив лучше кэшируется
  • JIT пропускает половину элементов
  • в отсортированном меньше элементов ≥ 128
  • переход становится предсказуемым, и процессор не сбрасывает конвейер
Объём данных и обращения к памяти одинаковые; разница — в ошибках предсказания (≈ 50% против ≈ 0%).

Зачем нужно переименование регистров?

  • чтобы убрать ложные зависимости между независимыми командами, пишущими в один архитектурный регистр
  • чтобы увеличить число регистров в ISA
  • для защиты от Spectre
  • для совместимости с 32-битным кодом
Каждая запись получает свой физический регистр; остаются только настоящие зависимости по данным.

Почему C2 не векторизует суммирование массива double?

  • double не помещается в векторный регистр
  • векторных команд для double нет
  • сложение с плавающей точкой не ассоциативно, и перестановка изменила бы результат
  • из-за проверки границ массива
Java гарантирует строгий порядок вычислений. Целые редукции векторизуются; для double — явный Vector API или несколько аккумуляторов вручную.
Что происходит при неверном предсказании перехода?

Команды, выбранные и частично исполненные по предсказанному пути, выбрасываются (результаты в физических регистрах не фиксируются), выборка начинается с правильного адреса. Конвейер заново заполняется — 15–20 тактов потерь. Побочные эффекты в кэше остаются — это основа атак класса Spectre.

Объясните разницу между задержкой и пропускной способностью на примере сложения double.

Задержка — через сколько тактов готов результат одной операции (около 4). Пропускная способность — сколько независимых операций можно начать за такт (2 на современных ядрах). Цепочка зависимых сложений ограничена задержкой, независимые — пропускной способностью; отсюда выигрыш нескольких аккумуляторов.

Что такое внеочередное исполнение и почему программа этого не замечает?

Ядро держит окно из сотен команд и исполняет те, чьи операнды готовы, не дожидаясь более ранних. Результаты фиксируются (retire) строго в порядке программы, исключения и прерывания возникают «точно». Для одного потока это невидимо; другим ядрам порядок записей в память может быть виден иначе — это модель памяти (тема 07).

Когда стоит использовать Vector API?

Когда горячий цикл — это численная обработка массивов, которую C2 не векторизует сам: редукции с плавающей точкой, сложные условия через маски, поиск, обработка байтовых буферов. Перед этим стоит проверить JMH и профилировщиком, что цикл действительно узкое место. API в инкубаторе — нужен --add-modules jdk.incubator.vector, а сигнатуры могут меняться.
