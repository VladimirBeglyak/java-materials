21.2Производственные ситуации

После релиза p99 запроса списка заказов вырос с 20 мс до 2 с. С чего начать?

Сравнить планы до и после (auto_explain, pg_stat_statements по queryid): изменился запрос (ORM сгенерировал другой SQL, добавился OR/функция, N+1) или план (статистика, новый индекс отвлёк планировщик, рост данных). EXPLAIN (ANALYZE, BUFFERS) на продовых данных с «тяжёлыми» параметрами. Быстрое смягчение — откат релиза; затем исправление: индекс под новый запрос, переписывание, ANALYZE (темы 08–09).

Диск базы заполнился на 95% за ночь, данных больше не стало.

Проверить pg_wal: упал archive_command или неактивный слот репликации держит WAL (pg_stat_archiver, pg_replication_slots). Проверить временные файлы (огромная сортировка/хэш, log_temp_files). Проверить раздувание горячих таблиц из-за долгой транзакции. Действия: починить архив/удалить мёртвый слот, завершить виновную сессию, освободить место; затем алерты на эти причины (темы 10, 14, 15, 19).

Периодические ошибки «deadlock detected» при массовом обновлении статусов.

Две задачи обновляют пересекающиеся наборы строк в разном порядке. Решение: обрабатывать порциями в едином порядке (ORDER BY id) с предварительным SELECT … ORDER BY id FOR UPDATE или SKIP LOCKED, чтобы задачи не пересекались; повтор при 40P01; проверить внешние ключи без индексов (тема 13).

«Иногда» продаётся товар, которого нет на складе.

Гонка «проверить остаток → списать» в READ COMMITTED (потерянное обновление или write skew). Исправить атомарным UPDATE … SET qty = qty − n WHERE id = ? AND qty >= n с проверкой числа строк, или FOR UPDATE, или оптимистической блокировкой; добавить CHECK (qty >= 0) как последнюю линию защиты (тема 12).

Миграция с индексом прошла на стейдже за секунду, а на проде положила сервис на 20 минут.

Обычный CREATE INDEX блокирует запись на время построения; на стейдже — тысячи строк, на проде — сотни миллионов. Использовать CREATE INDEX CONCURRENTLY вне транзакции, lock_timeout, линтер миграций, проверку на копии продовых объёмов (тема 18).

21.3Вопросы с собеседований

Что такое ACID? Какая буква обеспечивается каким механизмом в PostgreSQL?

Атомарность — статус транзакции в pg_xact и правила видимости MVCC (версии прерванной транзакции невидимы). Согласованность — ограничения (PK, FK, CHECK, UNIQUE, EXCLUDE) и триггеры, плюс логика приложения. Изоляция — MVCC-снимки и блокировки строк, SSI для SERIALIZABLE. Долговечность — WAL и fsync при коммите, репликация для защиты от потери сервера.

Чем кластерный индекс отличается от некластерного?

В кластерном индексе (InnoDB, SQL Server) листья содержат сами строки — таблица упорядочена по ключу; он один на таблицу. Некластерный хранит ключ и ссылку на строку (в InnoDB — значение первичного ключа, в PostgreSQL — ctid). В PostgreSQL все индексы некластерные; команда CLUSTER упорядочивает таблицу однократно, порядок не поддерживается.

Почему индекс может не использоваться, хотя он есть?

Условие отбирает большую долю строк (полный просмотр дешевле); функция или приведение типа над столбцом; LIKE с ведущим %; нет левого префикса составного индекса; неверная статистика; несовпадение типов параметра и столбца; collation для LIKE; маленькая таблица; generic plan для подготовленного выражения; OR по разным столбцам.

Что такое N+1 и как его найти и исправить в Spring Data JPA?

Загрузка списка одним запросом и связей — отдельным запросом на каждый элемент. Найти: логирование SQL/статистика Hibernate (число запросов на HTTP-запрос), pg_stat_statements (calls), тесты с подсчётом запросов. Исправить: JOIN FETCH / @EntityGraph, batch fetch size, DTO-проекции, двухшаговая загрузка для пагинации.

OFFSET-пагинация медленная на дальних страницах. Почему и что делать?

OFFSET N заставляет прочитать и отбросить N строк. Keyset-пагинация: WHERE (created_at, id) < (:c, :i) ORDER BY created_at DESC, id DESC LIMIT 20 с индексом (created_at, id) — стоимость постоянна и нет дублей при вставках.

Как работает MVCC и что такое VACUUM?

UPDATE/DELETE создают новые версии и помечают старые номером транзакции; снимок определяет, какие версии видимы. Читатели не блокируют писателей. Старые версии, невидимые никому, удаляет VACUUM (также обновляет visibility map и замораживает старые xid против wraparound). Долгие транзакции мешают очистке.

Какие уровни изоляции вы знаете и какой выбрать?

READ UNCOMMITTED (в PG = READ COMMITTED), READ COMMITTED (снимок на запрос; по умолчанию), REPEATABLE READ (снимок на транзакцию; в PG — snapshot isolation, защищает и от фантомов, но не от write skew), SERIALIZABLE (SSI, требует повторов). Для OLTP — READ COMMITTED + атомарные операции и явные блокировки; отчёты — REPEATABLE READ; сложные инварианты — SERIALIZABLE с повтором.

Как избежать deadlock-ов?

Единый порядок захвата ресурсов, короткие транзакции, блокировать заранее всё нужное (SELECT … ORDER BY id FOR UPDATE), индексы на внешних ключах, повтор при 40P01, NOWAIT/SKIP LOCKED там, где ожидание не нужно.

Как масштабировать реляционную базу?

По порядку: оптимизация запросов и индексов, вертикальное масштабирование, пулы соединений и кэширование, реплики для чтения (с учётом лага), партиционирование больших таблиц, разделение по сервисам/доменам, шардинг или распределённая SQL-база. Запись масштабируется только шардингом.

Что такое WAL и зачем он нужен?

Журнал предзаписи: каждое изменение сначала описывается в последовательном журнале, при коммите сбрасывается только журнал. Обеспечивает долговечность и восстановление после сбоя, служит основой репликации, PITR и логического декодирования (CDC).

Нормализация vs денормализация — когда что?

Нормализация (до 3НФ) — по умолчанию для OLTP: нет аномалий обновления, каждый факт в одном месте. Денормализация — осознанно для чтения: агрегаты, счётчики, материализованные представления, копии для поиска и аналитики, с явным механизмом синхронизации (транзакция, триггер, событие) и пониманием, какой источник главный.

UUID или bigint для первичного ключа?

bigint (IDENTITY/последовательность) — компактный и быстрый, но выдаётся базой и перечислим. UUID v4 — генерируется где угодно, но случайный порядок вредит B-tree (кэш, разделения страниц, WAL). Компромисс — UUID v7 или Snowflake: глобально уникальны и почти монотонны. Наружу можно отдавать отдельный публичный идентификатор.

21.4Итоговый тест

Что из перечисленного НЕ даёт реплика?

  • Переключение при отказе primary
  • Разгрузку чтения
  • Защиту от ошибочного DELETE
  • Копию данных на другом сервере
Ошибки реплицируются; нужен PITR.

Таблица быстро растёт при постоянном числе строк, autovacuum работает. Первое, что проверить?

  • Долгие транзакции, idle in transaction и слоты репликации, удерживающие горизонт
  • Размер shared_buffers
  • Число индексов
  • Версию JDBC-драйвера
VACUUM не может удалить версии, которые кто-то ещё может видеть.

Какой индекс нужен для WHERE tenant_id = ? AND created_at > ? ORDER BY created_at?

  • (created_at)
  • (created_at, tenant_id)
  • Два отдельных индекса
  • (tenant_id, created_at)
Равенство первым, затем диапазон/сортировка.

Почему COMMIT в PostgreSQL быстрый, хотя данные «на диске»?

  • Данные пишутся только в память
  • Сбрасывается только последовательный журнал WAL; страницы данных пишутся позже
  • COMMIT асинхронный по умолчанию
  • Страницы пишутся параллельно
WAL — ключ к долговечности без случайной записи.

Как безопасно добавить NOT NULL к столбцу таблицы на 1 млрд строк?

  • ALTER COLUMN SET NOT NULL в обычной миграции
  • Пересоздать таблицу
  • CHECK (col IS NOT NULL) NOT VALID → VALIDATE → SET NOT NULL → DROP CHECK
  • Это невозможно без простоя
Проверенный CHECK позволяет SET NOT NULL без полного скана под эксклюзивной блокировкой.
