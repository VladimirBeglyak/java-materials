Блокировки и deadlock

MVCC избавил чтение от блокировок, но запись по-прежнему блокирует запись, а DDL — всех. Разбираем блокировки строк и таблиц, матрицу конфликтов, очередь блокировок (из-за которой безобидный ALTER TABLE кладёт продакшен), взаимные блокировки, очереди задач на SKIP LOCKED и диагностику «кто кого ждёт».

13.1Блокировки строк

UPDATE, DELETE и SELECT … FOR … блокируют строки. В PostgreSQL блокировка строки хранится в самой строке (поле xmax + флаги), а не в памяти — поэтому можно заблокировать миллионы строк без «эскалации». Ожидающий ждёт завершения транзакции-владельца.

РежимКто берётКонфликтует с
FOR KEY SHAREпроверка внешнего ключа при вставке дочерней строкиFOR UPDATE (удаление строки, изменение ключа)
FOR SHARE«не меняйте, пока я читаю»FOR NO KEY UPDATE, FOR UPDATE
FOR NO KEY UPDATEобычный UPDATE, не меняющий ключевых столбцовFOR SHARE, FOR NO KEY UPDATE, FOR UPDATE
FOR UPDATEDELETE, UPDATE ключа, явный SELECT … FOR UPDATEсо всеми

Разделение на «ключевые» и «неключевые» нужно, чтобы вставка заказа (проверка FK → FOR KEY SHARE на клиента) не ждала обновления имени клиента (FOR NO KEY UPDATE).

SELECT * FROM seats WHERE id = 7 FOR UPDATE;              -- ждать сколько угодно (до lock_timeout)
SELECT * FROM seats WHERE id = 7 FOR UPDATE NOWAIT;       -- сразу ошибка 55P03, если занято
SELECT * FROM jobs WHERE status = 'ready'
ORDER BY id LIMIT 10 FOR UPDATE SKIP LOCKED;              -- пропустить занятые (очереди задач)

По таблице orders идёт долгий отчёт. Он держит самую слабую блокировку — никому не мешает.

Деплой запускает ALTER TABLE orders ADD COLUMN note text. Само изменение мгновенное (только каталог), но нужна блокировка ACCESS EXCLUSIVE, которая конфликтует с ACCESS SHARE отчёта. Миграция ждёт.

Ключевой момент: новые запросы проверяют конфликт не только с держателями, но и с ожидающими раньше них (иначе миграция никогда бы не дождалась). Обычные SELECT из API конфликтуют с запрошенным ACCESS EXCLUSIVE и встают в очередь. Таблица недоступна никому.

Через несколько секунд все соединения пула висят в ожидании, API отвечает таймаутами, оркестратор перезапускает поды. Всё из-за «мгновенной» миграции и отчёта, который ей мешал.

Решение: миграции выполнять с коротким lock_timeout (2–5 с) и повторять при неудаче. Если блокировку не получили за 3 секунды — ошибка, очередь сразу рассасывается, а инструмент миграций повторит попытку. Плюс statement_timeout для отчётов и вынесение аналитики на реплику.

SET lock_timeout = '3s';
SET statement_timeout = '15s';
ALTER TABLE orders ADD COLUMN note text;
-- Flyway: эти SET можно вписать в начало скрипта миграции; Liquibase — sql-изменение с теми же командами

13.4Взаимная блокировка (deadlock)

Симулятор: два перевода навстречу друг другу
T1: перевод X → Y
строка X
строка Y
T2: перевод Y → X

T1 списывает деньги со счёта X и блокирует строку X.

Одновременно T2 списывает со счёта Y и блокирует Y.

T1 хочет зачислить на Y — строка занята T2. Ждёт.

T2 хочет зачислить на X — строка занята T1. Цикл: каждая ждёт другую, сами они его не разорвут.

Если ожидание длится дольше deadlock_timeout (1 с), процесс проверяет граф ожиданий, находит цикл и прерывает одну из транзакций с ошибкой 40P01. Другая продолжает. Приложение должно повторить прерванную транзакцию.

Главное лекарство — единый порядок захвата: всегда блокировать строки по возрастанию id (например, SELECT … WHERE id IN (:a, :b) ORDER BY id FOR UPDATE в начале транзакции). Тогда цикл невозможен. Плюс короткие транзакции и повтор при 40P01.

Неочевидные источники deadlock Массовый UPDATE без ORDER BY в двух параллельных задачах (строки блокируются в разном физическом порядке); внешние ключи без индекса (удаление родителя сканирует дочернюю таблицу); пакетные вставки в таблицу с уникальным индексом в разном порядке ключей; Hibernate, сбрасывающий изменения в порядке, отличном от вашего (включите hibernate.order_updates).

13.5Очередь задач на SKIP LOCKED и advisory-блокировки

-- воркер забирает пачку задач; параллельные воркеры не ждут друг друга
WITH picked AS (
  SELECT id FROM jobs
  WHERE status = 'ready' AND run_at <= now()
  ORDER BY run_at
  LIMIT 10
  FOR UPDATE SKIP LOCKED
)
UPDATE jobs j SET status = 'running', locked_at = now(), attempts = attempts + 1
FROM picked WHERE j.id = picked.id
RETURNING j.*;
-- частичный индекс: CREATE INDEX jobs_ready ON jobs (run_at) WHERE status = 'ready';
SELECT pg_try_advisory_lock(hashtext('nightly-report'));   -- true: мы владельцы; false: уже кто-то выполняет
-- … работа …
SELECT pg_advisory_unlock(hashtext('nightly-report'));
-- pg_advisory_xact_lock(...) — снимется сам по окончании транзакции (безопаснее с пулом соединений)
-- в Spring: ShedLock с JdbcTemplateLockProvider решает ту же задачу таблицей блокировок

13.6Диагностика: кто кого ждёт

SELECT a.pid, a.wait_event_type, a.state, now() - a.query_start AS waiting,
       pg_blocking_pids(a.pid) AS blocked_by, left(a.query, 60) AS query
FROM pg_stat_activity a
WHERE cardinality(pg_blocking_pids(a.pid)) > 0;

-- корень дерева ожиданий: сессия, которая блокирует, но сама не ждёт
-- аккуратно завершить: SELECT pg_cancel_backend(pid);  крайняя мера: pg_terminate_backend(pid)

-- в журнал — все ожидания дольше deadlock_timeout:
ALTER SYSTEM SET log_lock_waits = on;

13.7Самопроверка

Почему ALTER TABLE ADD COLUMN (мгновенная операция) может остановить все запросы к таблице?

  • Он переписывает таблицу
  • Он блокирует всю базу
  • Он ждёт ACCESS EXCLUSIVE за долгим запросом, а новые запросы встают в очередь за ним
  • Он отключает индексы
Защита — lock_timeout и повторы.

Как надёжнее всего предотвратить deadlock при переводах между счетами?

  • Блокировать строки всегда в одном порядке (например, по возрастанию id)
  • Увеличить deadlock_timeout
  • Использовать READ UNCOMMITTED
  • Убрать индексы
Без цикла ожидания взаимной блокировки быть не может.

Зачем в очереди задач FOR UPDATE SKIP LOCKED?

  • Чтобы не блокировать строки
  • Чтобы параллельные воркеры брали разные задачи, не ожидая друг друга
  • Чтобы задачи выполнялись строго по порядку
  • Чтобы ускорить индекс
Каждый воркер пропускает строки, захваченные другими.

Совместимы ли CREATE INDEX (без CONCURRENTLY) и INSERT в ту же таблицу?

  • Да
  • Да, если индекс уникальный
  • Только на репликах
  • Нет: SHARE конфликтует с ROW EXCLUSIVE — запись ждёт всё время построения
Поэтому на живых таблицах — CREATE INDEX CONCURRENTLY.
Как найти причину внезапного «зависания» запросов к таблице?

Посмотреть pg_stat_activity с wait_event_type = 'Lock' и pg_blocking_pids(), пройти по цепочке до корня — сессии, которая блокирует, но не ждёт. Частые корни: idle in transaction, долгий отчёт перед DDL, долгая миграция. Решение на месте — pg_cancel_backend; системно — lock_timeout для DDL, idle_in_transaction_session_timeout, statement_timeout, log_lock_waits.

Можно ли сделать очередь задач на PostgreSQL вместо брокера сообщений?

Да, для умеренной нагрузки (сотни–тысячи задач в секунду): таблица задач, выборка FOR UPDATE SKIP LOCKED, частичный индекс по готовым задачам, повторы через attempts и run_at, LISTEN/NOTIFY для пробуждения. Плюсы — транзакционность с бизнес-данными, нет дополнительной инфраструктуры. Минусы — нагрузка на основную базу, раздувание таблицы (нужен агрессивный autovacuum), нет fan-out и долгого хранения как в Kafka.
