9.1Сначала найти: pg_stat_statements

Оптимизировать «на глаз» бесполезно. Расширение pg_stat_statements собирает статистику по каждому нормализованному запросу (параметры заменены на $1). Сортировка по суммарному времени показывает, что реально грузит базу: часто это не самый медленный запрос, а быстрый, вызываемый миллион раз.

-- postgresql.conf: shared_preload_libraries = 'pg_stat_statements'
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT round(total_exec_time) AS total_ms, calls,
       round(mean_exec_time::numeric, 2) AS mean_ms, rows,
       round(100 * total_exec_time / sum(total_exec_time) OVER (), 1) AS pct,
       shared_blks_hit + shared_blks_read AS blocks,
       left(query, 80) AS query
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 15;

Признак N+1

Запрос вида SELECT … WHERE order_id = $1 с calls в 50 раз больше, чем у запроса списка заказов. Среднее время 0.05 мс, но суммарно — первое место.

Признак плохого плана

Большое mean_ms и огромные blocks на rows — запрос читает тысячи страниц ради единиц строк. Дальше — EXPLAIN (тема 08).

9.2N+1: главный убийца производительности ORM

List<Order> orders = orderRepo.findByStatus("paid"); // 1 запрос
for (Order o : orders) {
    o.getItems().size();       // LAZY → +1 запрос на КАЖДЫЙ заказ
    o.getCustomer().getName(); // ещё +1
}
// 100 заказов = 201 запрос, каждый — сетевой круг ~0.3 мс
@Query("""
  select distinct o from Order o
  join fetch o.customer
  left join fetch o.items
  where o.status = :status""")
List<Order> findPaidWithItems(String status);

// или @EntityGraph(attributePaths = {"customer", "items"})
// или hibernate.default_batch_fetch_size = 100
//   → связи грузятся WHERE id IN (… 100 id …)
Цена N+1
Ловушки JOIN FETCH Две коллекции через join fetch дают декартово произведение (Hibernate выдаст MultipleBagFetchException для List). Пагинация с join fetch коллекции происходит в памяти (предупреждение HHH90003004). Решение: сначала страница идентификаторов, затем загрузка связей по id IN (…), или batch fetch.

9.3Пагинация: OFFSET против keyset

SELECT * FROM orders
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 100000;
-- прочитать 100 020 строк, отдать 20;
-- строка вставлена между запросами →
-- дубли и пропуски на страницах
SELECT * FROM orders
WHERE (created_at, id) < (:lastCreated, :lastId)
ORDER BY created_at DESC, id DESC
LIMIT 20;
-- индекс (created_at, id): всегда ~20 строк,
-- стабильно при вставках
Сколько строк читает база для страницы N

Связанная проблема — SELECT count(*) для «всего страниц». На большой таблице это полный просмотр (MVCC не даёт хранить точный счётчик). Варианты: не показывать точное число («более 1000»), запросить LIMIT 1001, оценка из pg_class.reltuples или EXPLAIN, счётчик в отдельной таблице.

9.5Массовые операции

spring:
  datasource:
    url: jdbc:postgresql://db/app?reWriteBatchedInserts=true   # INSERT … VALUES (…),(…),(…)
  jpa:
    properties:
      hibernate.jdbc.batch_size: 50
      hibernate.order_inserts: true
      hibernate.order_updates: true
# IDENTITY-ключи отключают батч-вставку в Hibernate: используйте SEQUENCE с pooled optimizer (allocationSize = 50)
-- плохо: одна транзакция на 10 млн строк — долгие блокировки, раздувание, огромный WAL, отставание реплик
-- хорошо: порции по 5–10 тыс. строк, каждая — своя транзакция, пауза между ними
WITH batch AS (
  SELECT id FROM events WHERE created_at < now() - interval '90 days'
  ORDER BY id LIMIT 5000
)
DELETE FROM events e USING batch WHERE e.id = batch.id;
-- повторять, пока удаляется > 0; для регулярной чистки — партиции и DROP PARTITION (тема 17)

-- загрузка больших объёмов: COPY в 10–50 раз быстрее INSERT
COPY staging_products FROM STDIN WITH (FORMAT csv, HEADER true);   -- в Java: CopyManager драйвера

9.6Когда запрос не ускорить — хранить результат

  • Материализованное представление: CREATE MATERIALIZED VIEW sales_daily AS …, обновление REFRESH MATERIALIZED VIEW CONCURRENTLY (нужен уникальный индекс) по расписанию. Данные отстают на период обновления.
  • Таблица-агрегат, обновляемая в той же транзакции или асинхронно по событиям: счётчики, балансы, рейтинги.
  • Кэш приложения (Redis, Caffeine) — для горячих неизменных данных; цена — инвалидация.
  • Отдельное аналитическое хранилище — если тяжёлые отчёты мешают OLTP (пособие по выбору БД, OLAP).

9.8Самопроверка

Какой запрос стоит оптимизировать первым?

  • Самый медленный: 8 с, вызывается раз в сутки
  • Любой с Seq Scan
  • Тот, у которого наибольшее суммарное время в pg_stat_statements (например, 3 мс × 2 млн вызовов)
  • Самый длинный по тексту
Нагрузку на базу определяет суммарное время; редкий тяжёлый отчёт может быть вообще не проблемой.

Почему WHERE city NOT IN (SELECT city FROM …) может вернуть пустой результат?

  • Если в подзапросе есть NULL, сравнение даёт UNKNOWN для всех строк
  • NOT IN не поддерживается подзапросами
  • Из-за отсутствия индекса
  • Из-за регистра букв
x NOT IN (a, NULL) = x<>a AND x<>NULL → никогда не TRUE.

Почему keyset-пагинация быстрее OFFSET на дальних страницах?

  • Она кэширует результаты
  • Она начинает чтение индекса сразу с нужной позиции, а OFFSET читает и выбрасывает все предыдущие строки
  • Она не использует ORDER BY
  • Она читает таблицу параллельно
Стоимость keyset не зависит от номера страницы.

Почему в Hibernate батч-вставки не работают с GenerationType.IDENTITY?

  • IDENTITY запрещает транзакции
  • PostgreSQL не поддерживает батчи
  • Батчи работают только с UUID
  • Hibernate должен узнать id сразу после каждой вставки, поэтому выполняет их по одной
С SEQUENCE и allocationSize Hibernate получает пачку id заранее.
Как удалить 50 млн старых строк из живой таблицы?

Не одной командой: долгая транзакция держит блокировки строк, мешает VACUUM, генерирует огромный WAL и отставание реплик. Удалять порциями по несколько тысяч строк по индексу, каждая — отдельная транзакция, с паузами и мониторингом отставания реплик; затем VACUUM. Если такое удаление регулярно — перейти на партиционирование по времени и удалять партиции целиком (DROP/DETACH — мгновенно).

Список заказов с позициями и пагинацией в Spring Data JPA — как сделать эффективно?

Шаг 1: страница идентификаторов заказов (keyset или Pageable по индексу). Шаг 2: загрузить заказы с позициями по id IN (:ids) через JOIN FETCH или EntityGraph. Либо batch fetch size для коллекций. Для чтения — DTO-проекции вместо сущностей, read-only транзакции. Count-запрос — отдельно, при необходимости приблизительный.
