Безопасность и наблюдение

Две обязанности разработчика по отношению к базе: не дать ею злоупотребить (SQL-инъекции, лишние права, утечки) и видеть, что с ней происходит, до того как пользователи заметят. Роли и минимальные привилегии, построчная безопасность для мультиарендных систем, шифрование, аудит — и набор метрик и запросов, который должен быть у каждой команды.

20.2Роли и минимальные привилегии

-- владелец схемы: только для миграций, приложение им НЕ подключается
CREATE ROLE app_owner LOGIN PASSWORD '…';
CREATE SCHEMA shop AUTHORIZATION app_owner;
REVOKE ALL ON SCHEMA public FROM PUBLIC;          -- до PG 15 любой мог создавать объекты в public

-- приложение: только DML, никакого DDL
CREATE ROLE app_rw LOGIN PASSWORD '…' CONNECTION LIMIT 100;
GRANT USAGE ON SCHEMA shop TO app_rw;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA shop TO app_rw;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA shop TO app_rw;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA shop
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_rw;   -- и для будущих таблиц

-- аналитика и поддержка: только чтение, желательно на реплике
CREATE ROLE readonly LOGIN PASSWORD '…';
GRANT pg_read_all_data TO readonly;               -- PG 14+
ALTER ROLE readonly SET default_transaction_read_only = on;
  • Пароли — scram-sha-256 (не md5), хранение в секрет-менеджере (Vault, Kubernetes Secrets), ротация; лучше — короткоживущие учётные данные (Vault database engine, IAM-аутентификация облаков).
  • pg_hba.conf: доступ только из нужных подсетей, hostssl — только TLS; база не должна быть доступна из интернета.
  • Приложение под суперпользователем — антипаттерн: инъекция превращается в выполнение команд ОС (COPY … PROGRAM).

20.3Построчная безопасность для мультиарендных систем

Когда данные всех клиентов (tenants) в одних таблицах, забытый WHERE tenant_id = ? в одном запросе = утечка чужих данных. RLS добавляет условие на уровне базы, независимо от кода.

ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders FORCE ROW LEVEL SECURITY;          -- и для владельца таблицы

CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.tenant_id')::bigint)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::bigint);

-- приложение в начале каждой транзакции (SET LOCAL — безопасно с пулом и PgBouncer):
BEGIN;
SET LOCAL app.tenant_id = '42';
SELECT * FROM orders;                                 -- видны только строки tenant 42
COMMIT;
Нюансы RLS Обязательно SET LOCAL (иначе значение «прилипнет» к соединению пула и уйдёт следующему запросу другого клиента). Индексы должны начинаться с tenant_id. Суперпользователь и роли с BYPASSRLS политики обходят. Политики с функциями могут ломать планы — проверяйте EXPLAIN.

20.5Что мониторить

Панель здоровья: выставьте значения и посмотрите, что тревожно
-- что выполняется сейчас
SELECT pid, usename, application_name, state, wait_event_type, wait_event,
       now() - query_start AS running, left(query, 80)
FROM pg_stat_activity WHERE state <> 'idle' ORDER BY running DESC;

-- доля попаданий в кэш и транзакции по базе
SELECT datname, round(100.0 * blks_hit / nullif(blks_hit + blks_read, 0), 2) AS hit_pct,
       xact_commit, xact_rollback, deadlocks, temp_bytes
FROM pg_stat_database WHERE datname = current_database();

-- таблицы, которые читаются полным просмотром
SELECT relname, seq_scan, seq_tup_read, idx_scan, n_live_tup
FROM pg_stat_user_tables ORDER BY seq_tup_read DESC LIMIT 10;

-- неиспользуемые индексы (проверьте и на репликах!)
SELECT indexrelid::regclass, pg_size_pretty(pg_relation_size(indexrelid)), idx_scan
FROM pg_stat_user_indexes WHERE idx_scan = 0 ORDER BY pg_relation_size(indexrelid) DESC;
Стек наблюдения postgres_exporter → Prometheus → Grafana (готовые дашборды), алерты на метрики из панели выше; pg_stat_statements для запросов; журнал с log_min_duration_statement, auto_explain, log_lock_waits, log_autovacuum_min_duration; со стороны приложения — метрики HikariCP (hikaricp_connections_pending, …_usage) в Micrometer и трассировка запросов. Готовые решения: pgwatch, PMM, okmeter, облачные Performance Insights.

20.6Самопроверка

Как безопасно реализовать сортировку по полю, выбранному пользователем?

  • Передать имя столбца параметром PreparedStatement
  • Экранировать кавычки во вводе
  • Сопоставить ввод с белым списком допустимых столбцов
  • Подставить строку как есть, если она короче 20 символов
Идентификаторы параметрами не передаются; только белый список (или безопасный построитель запросов).

Почему в RLS-схеме с пулом соединений нужно именно SET LOCAL app.tenant_id?

  • Значение действует до конца транзакции и не «утечёт» к следующему пользователю соединения
  • SET LOCAL быстрее
  • SET не работает с пользовательскими параметрами
  • Иначе RLS не включится
Соединения пула переиспользуются разными запросами и арендаторами.

Под какой ролью должно работать приложение?

  • postgres (суперпользователь) — так проще
  • Владелец схемы, чтобы выполнять миграции
  • Любая, права не важны при наличии TLS
  • Отдельная роль только с нужными DML-правами; миграции — под ролью владельца
Минимальные привилегии ограничивают ущерб от инъекции или утечки пароля.

Какая метрика раньше всех предупредит о будущем раздувании и проблемах VACUUM?

  • Число таблиц
  • Возраст самой долгой транзакции (и idle in transaction)
  • Размер shared_buffers
  • Версия PostgreSQL
Долгие транзакции держат горизонт — первопричина многих проблем.
Какие алерты по базе вы бы настроили в первый день?

Доступность и роль (primary/replica), заполнение диска и прогноз, лаг репликации, неудачи архивации WAL и возраст последней копии, возраст xid, долгие транзакции и idle in transaction, ожидания блокировок, исчерпание соединений (и pending в HikariCP), deadlock-и, рост задержек ключевых запросов (из pg_stat_statements или APM), ошибки в журнале (FATAL/PANIC, out of memory).

Как изолировать данные клиентов в SaaS на PostgreSQL?

Варианты: общая схема с tenant_id + RLS (дёшево, масштабируется на тысячи клиентов, требует дисциплины и индексов с tenant_id); схема на клиента (лучше изоляция, сложнее миграции при тысячах схем); база на клиента (максимальная изоляция, для крупных клиентов и требований регуляторов). Часто комбинируют: мелкие — в общей схеме с RLS, крупные — отдельно. Шардинг (Citus) по tenant_id при росте.
