7.2GIN: «что содержит»

Инвертированный индекс, как алфавитный указатель в конце книги: для каждого элемента (ключа jsonb, элемента массива, слова, триграммы) — отсортированный список строк, где он встречается. Запрос «содержит A и B» пересекает списки.

-- jsonb: поиск по содержимому документа
CREATE INDEX products_attrs ON products USING gin (attrs jsonb_path_ops);
SELECT * FROM products WHERE attrs @> '{"color": "red", "size": "M"}';

-- массивы тегов
CREATE INDEX posts_tags ON posts USING gin (tags);
SELECT * FROM posts WHERE tags @> ARRAY['postgres', 'index'];

-- полнотекстовый поиск
ALTER TABLE articles ADD COLUMN tsv tsvector
  GENERATED ALWAYS AS (to_tsvector('russian', title || ' ' || body)) STORED;
CREATE INDEX articles_tsv ON articles USING gin (tsv);
SELECT id, ts_rank(tsv, q) FROM articles, websearch_to_tsquery('russian', 'индексы postgres') q
WHERE tsv @@ q ORDER BY 2 DESC LIMIT 10;

-- подстрока и опечатки: триграммы
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX users_name_trgm ON users USING gin (name gin_trgm_ops);
SELECT * FROM users WHERE name ILIKE '%петров%';
SELECT name, similarity(name, 'Пятров') FROM users WHERE name % 'Пятров';
Цена GIN — запись Одна строка с 50 словами — 50 обновлений списков. Чтобы вставки не тормозили, GIN копит изменения в «pending list» (fastupdate) и вливает их позже — поиск при этом просматривает и этот список. Для таблиц с интенсивной записью следите за gin_pending_list_limit и autovacuum.

7.4GiST: пересечения, расстояния, исключения

GiST хранит в узлах «ограничивающие области» (прямоугольник, диапазон), покрывающие всё под ними. Поиск спускается во все поддеревья, чья область пересекается с запросом. Это даёт поиск по пересечению, вхождению и ближайших соседей (ORDER BY geom <-> точка LIMIT 10).

CREATE EXTENSION IF NOT EXISTS btree_gist;   -- чтобы в GiST можно было использовать = для room_id
CREATE TABLE bookings (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  room_id bigint NOT NULL,
  during  tstzrange NOT NULL,
  EXCLUDE USING gist (room_id WITH =, during WITH &&)   -- нет двух броней одной комнаты с пересечением
);
INSERT INTO bookings (room_id, during) VALUES (1, '[2026-05-01 10:00, 2026-05-01 12:00)');
INSERT INTO bookings (room_id, during) VALUES (1, '[2026-05-01 11:00, 2026-05-01 13:00)');
-- ERROR: conflicting key value violates exclusion constraint

-- геоданные (PostGIS): кафе в радиусе 1 км, ближайшие первыми
SELECT name FROM places
WHERE ST_DWithin(geog, ST_MakePoint(27.56, 53.90)::geography, 1000)
ORDER BY geog <-> ST_MakePoint(27.56, 53.90)::geography LIMIT 10;
Exclusion constraint — недооценённый инструмент Проверка «нет пересечений» в коде приложения подвержена гонкам (две транзакции одновременно проверили и обе вставили — тема 12). Ограничение исключения в базе решает это без блокировок вручную.

7.5BRIN: индекс на килобайты для таблицы на терабайт

BRIN хранит для каждого блока из 128 страниц только минимум и максимум столбца. Если данные добавляются по времени, блоки «сами отсортированы»: для запроса за последний час подходят единицы блоков. Индекс в тысячи раз меньше B-tree и почти не замедляет вставку.

BRIN: когда работает, а когда нет
CREATE INDEX events_ts_brin ON events USING brin (created_at) WITH (pages_per_range = 64);
-- проверка корреляции: близко к 1 — BRIN подходит
SELECT correlation FROM pg_stats WHERE tablename = 'events' AND attname = 'created_at';

7.6Hash и прочее

  • Hash — с PostgreSQL 10 журналируется и безопасен. Только равенство, без уникальности и сортировки. Выигрыш — на длинных ключах (URL, токены), где B-tree большой. В большинстве случаев B-tree достаточно.
  • SP-GiST — для данных, которые естественно делятся на непересекающиеся части: точки (quad-tree), IP-сети (inet), префиксный поиск строк.
  • bloom (расширение) — один индекс на много столбцов для произвольных сочетаний равенств; вероятностный, с перепроверкой.
  • pgvector HNSW — приближённый поиск ближайших векторов для семантического поиска и RAG; подробно — в пособии по выбору хранилищ.

7.8Самопроверка

Какой индекс ускорит WHERE description ILIKE '%кофе%'?

  • B-tree по description
  • Hash
  • GIN с gin_trgm_ops
  • BRIN
Подстрока с начальным % — задача для триграмм.

Когда BRIN бесполезен?

  • Когда значения столбца разбросаны по таблице случайно (низкая корреляция с физическим порядком)
  • Когда таблица очень большая
  • Когда данные пишутся по времени
  • Когда запросы — диапазоны
BRIN хранит min/max блока; при случайном порядке у каждого блока диапазон почти весь.

Как гарантировать отсутствие пересекающихся бронирований одной комнаты при конкурентных вставках?

  • Проверить SELECT-ом в приложении перед INSERT
  • UNIQUE (room_id, start_time)
  • Триггер с SELECT
  • EXCLUDE USING gist (room_id WITH =, during WITH &&)
Ограничение исключения проверяется базой атомарно; проверки в приложении и триггере без блокировок подвержены гонкам.

Почему GIN-индекс может замедлять вставки сильнее, чем B-tree?

  • Он не журналируется
  • Одна строка содержит много элементов (слов, ключей), каждый — обновление своего списка строк
  • Он блокирует таблицу
  • Он хранит строки целиком
Поэтому есть fastupdate и pending list.
Когда полнотекстового поиска PostgreSQL достаточно, а когда нужен отдельный поисковый движок?

Достаточно для поиска по тысячам–миллионам документов с простой релевантностью, стеммингом, фразами, когда важна транзакционная согласованность с данными. Отдельный движок (OpenSearch/Elasticsearch) — при сложной релевантности (BM25 с бустами, синонимы, исправление опечаток, фасеты и агрегации), больших объёмах и нагрузке на поиск, которую не хочется класть на основную базу.

Индекс по jsonb: GIN или B-tree по выражению?

GIN — когда запросы ищут по разным ключам документа (@>, ?). B-tree по выражению ((attrs->>'sku')) — когда ищут по одному известному ключу на равенство или диапазон; он меньше и поддерживает сортировку. Если ключ используется постоянно, возможно, его стоит вынести в обычный столбец.
