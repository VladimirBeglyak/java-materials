Партиционирование и большие таблицы

Таблица на миллиарды строк и терабайты: VACUUM идёт сутки, индексы не помещаются в память, удаление старых данных — многочасовой DELETE. Партиционирование делит таблицу на части по ключу. Когда оно действительно помогает, как выбрать ключ, что такое отсечение партиций, какие ограничения появляются и чем партиционирование отличается от шардинга.

17.1Зачем — и когда не нужно

Реальные выгоды

  • Удаление старых данных — DROP/DETACH партиции мгновенно вместо DELETE миллионов строк с раздуванием.
  • Отсечение партиций: запросы за последний месяц читают одну партицию и её маленькие индексы.
  • Обслуживание по частям: VACUUM, REINDEX, pg_repack — по партиции; старые партиции заморожены и не трогаются.
  • Разные хранилища (табличные пространства) для горячих и архивных данных.

Когда вредно

  • Запросы не содержат ключ партиционирования — читаются все партиции, планирование дороже.
  • Таблица меньше ~50–100 ГБ без требований ретенции — обычный индекс быстрее и проще.
  • Тысячи мелких партиций — планирование и блокировки на каждую.
  • Нужна глобальная уникальность по столбцу вне ключа — PostgreSQL её не поддерживает.

17.2Три вида

-- RANGE: по времени — самый частый случай
CREATE TABLE events (
  id         bigint GENERATED ALWAYS AS IDENTITY,
  tenant_id  bigint NOT NULL,
  created_at timestamptz NOT NULL,
  payload    jsonb,
  PRIMARY KEY (id, created_at)          -- ключ партиционирования обязан входить в PK и UNIQUE
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_10 PARTITION OF events
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
CREATE TABLE events_default PARTITION OF events DEFAULT;   -- страховка для «неожиданных» дат
CREATE INDEX ON events (tenant_id, created_at);            -- создаётся в каждой партиции

-- LIST: по набору значений
CREATE TABLE orders_by_region (...) PARTITION BY LIST (region);
CREATE TABLE orders_eu PARTITION OF orders_by_region FOR VALUES IN ('DE', 'FR', 'PL');

-- HASH: равномерно по ключу, когда нет естественного диапазона
CREATE TABLE sessions (...) PARTITION BY HASH (user_id);
CREATE TABLE sessions_p0 PARTITION OF sessions FOR VALUES WITH (MODULUS 8, REMAINDER 0);

17.4Эксплуатация

  • Создавать партиции заранее: если партиции на следующий месяц нет, вставки упадут (или уйдут в DEFAULT, из которой потом сложно вынести). Автоматизация: расширение pg_partman + pg_cron или задача в приложении.
  • Удаление: ALTER TABLE events DETACH PARTITION events_2025_10 CONCURRENTLY; затем выгрузить в архив (S3, Parquet) и DROP.
  • Индексы: CREATE INDEX на родителе создаёт индекс во всех партициях и блокирует запись; для живой системы — CREATE INDEX CONCURRENTLY на каждой партиции, затем CREATE INDEX ON ONLY родителя и ATTACH PARTITION индексов.
  • Число партиций: десятки–сотни — нормально, тысячи — проблемы планирования. Месячные партиции для данных за несколько лет; дневные — для огромных потоков с короткой ретенцией.
  • Перевод существующей таблицы: создать партиционированную, старую подключить как одну большую партицию (с CHECK-ограничением, чтобы ATTACH не сканировал), новые данные — в новые партиции.

17.5Партиционирование ≠ шардинг

ПартиционированиеШардинг
Где частина одном серверена разных серверах
Что масштабируетуправляемость, ретенция, скорость запросов с ключомзапись, объём, память — сверх одного сервера
Транзакции и JOINкак обычномежду шардами — дорого или невозможно
Инструментывстроенное в PostgreSQLCitus, шардинг в приложении (по tenant_id), Vitess (MySQL), распределённые SQL-базы (YugabyteDB, CockroachDB)
Порядок масштабирования Оптимизация запросов и индексов → больше железа (вертикально — современные серверы держат десятки ТБ и сотни ядер) → реплики для чтения → партиционирование больших таблиц → вынос частей системы в отдельные базы (по сервисам) → и только потом шардинг. Шардинг — необратимое усложнение каждой фичи.

17.6Самопроверка

Главная практическая выгода партиционирования таблицы событий по месяцам?

  • Ускорение любых запросов
  • Мгновенное удаление старых данных (DROP партиции) и чтение только нужных месяцев
  • Возможность хранить больше столбцов
  • Автоматический шардинг
Ретенция и отсечение партиций — основные причины.

Почему в партиционированной таблице первичный ключ должен включать ключ партиционирования?

  • Так требует стандарт SQL
  • Для ускорения вставки
  • Чтобы работал VACUUM
  • Уникальность проверяется индексом внутри каждой партиции; глобальных индексов нет
Уникальность (id, created_at) гарантируется, уникальность одного id — нет.

Запросы в основном ищут по tenant_id, а таблица партиционирована по дате. Что происходит?

  • Каждый запрос проходит по всем партициям
  • PostgreSQL автоматически перестроит партиции
  • Запросы станут быстрее
  • Запросы вернут ошибку
Ключ партиционирования выбирают по основным запросам и по ретенции.

Что случится при вставке строки с датой, для которой нет партиции и нет DEFAULT?

  • Создастся новая партиция
  • Строка попадёт в последнюю партицию
  • Ошибка: no partition of relation found for row
  • Строка будет проигнорирована
Поэтому партиции создают заранее и мониторят.
Таблица событий 4 ТБ, хранить нужно 13 месяцев. Как организовать?

RANGE по created_at помесячно (или понедельно при очень большом потоке), pg_partman создаёт партиции на несколько периодов вперёд, ежемесячная задача отключает (DETACH CONCURRENTLY) партицию старше 13 месяцев, выгружает её в объектное хранилище и удаляет. Все запросы приложения содержат диапазон дат. Первичный ключ (id, created_at). BRIN или B-tree по created_at внутри партиций, индексы под основные запросы.

Когда переходить к шардингу?

Когда исчерпаны вертикальное масштабирование, реплики, оптимизация и разделение по сервисам, а запись или рабочий набор данных не помещаются в один сервер. Предпосылка — естественный ключ шардирования (tenant, пользователь), по которому почти все запросы и транзакции локальны. Варианты: Citus для PostgreSQL, шардинг в приложении, распределённая SQL-база.
