18.1Два вопроса к каждой миграции

1. Какую блокировку берёт и как долго?

Почти любой ALTER TABLE берёт ACCESS EXCLUSIVE. Если на миллисекунды — нормально (с lock_timeout, тема 13). Если на время перезаписи таблицы в 200 ГБ — простой.

2. Совместима ли со старым кодом?

Во время rolling-деплоя старые экземпляры работают с новой схемой. Удалили или переименовали столбец — старый код падает. Миграция должна быть совместима с версией N−1.

18.3Expand / contract

Переименование столбца name → full_name без простоя
Схема
namefull_name
Код: запись
→ name→ full_name
Код: чтение
← name← full_name

Версия 1 приложения работает со столбцом name.

Миграция добавляет full_name (nullable, без перезаписи). Версия 1 продолжает работать — лишний столбец ей не мешает.

Версия 2 пишет в оба столбца, читает старый. Пока идёт rolling-деплой, v1 и v2 работают одновременно — обе корректны. Фоновая задача заполняет full_name у старых строк порциями (тема 09).

Когда заполнение завершено и сверено, версия 3 читает новый столбец. Пишет по-прежнему в оба — чтобы откат на v2 был безопасным.

Версия 4 использует только full_name. После того как её выкатили везде и откат на v3 больше не нужен, отдельная миграция удаляет name. Четыре релиза вместо одного — цена нулевого простоя.

18.4Flyway и Liquibase в Spring Boot

# src/main/resources/db/migration/
#   V1__init.sql
#   V2__orders_add_note.sql
#   V3__orders_customer_idx.sql        ← CREATE INDEX CONCURRENTLY
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
    validate-on-migrate: true      # контрольные суммы: применённые скрипты менять нельзя
    out-of-order: false
  # для V3 рядом положить V3__orders_customer_idx.sql.conf с executeInTransaction=false
  # (или в Flyway 10+ — скрипт-директива в начале файла)
Миграции при старте приложения Запуск миграций при старте каждого пода удобен, но: десять подов стартуют одновременно (Flyway берёт блокировку — ждут), долгая миграция превышает таймаут readiness-проверки, и под перезапускается посреди работы. Для долгих операций — отдельный шаг пайплайна (job/init-контейнер) до выкатки приложения, а длительные заполнения данных — фоновыми задачами, не миграцией.
  • Одна миграция — одно логическое изменение; скрипты после применения не редактируются, исправления — новой миграцией.
  • Проверка на копии продовых данных: время выполнения и блокировки на 10 строках и на 100 млн строк различаются радикально.
  • Откат схемы на практике — это новая миграция «вперёд», а не down-скрипт; поэтому каждый шаг expand/contract обратимо совместим.
  • Линтеры: squawk для SQL-миграций PostgreSQL ловит большинство опасных операций из таблицы выше в CI.

18.5Самопроверка

Как безопасно добавить индекс на таблицу в 300 ГБ под нагрузкой?

  • CREATE INDEX в транзакции миграции
  • Остановить приложение на ночь
  • CREATE INDEX CONCURRENTLY вне транзакции
  • Создать индекс на реплике
CONCURRENTLY не блокирует запись, но дольше и не может выполняться в транзакционном блоке.

Почему нельзя просто переименовать столбец в одном релизе?

  • Во время деплоя старая версия приложения ещё работает и обращается к старому имени
  • PostgreSQL не умеет переименовывать столбцы
  • Переименование переписывает таблицу
  • Переименование удаляет индексы
Rolling-деплой = две версии кода одновременно.

Как добавить внешний ключ на большую таблицу с минимальной блокировкой?

  • Обычный ADD FOREIGN KEY
  • Сначала удалить все данные
  • Внешние ключи на больших таблицах не нужны
  • ADD … NOT VALID, затем VALIDATE CONSTRAINT отдельной командой
VALIDATE берёт более слабую блокировку и не мешает записи.

Какая из операций мгновенна в PostgreSQL 11+?

  • ADD COLUMN … DEFAULT gen_random_uuid()
  • ADD COLUMN … NOT NULL DEFAULT 'new'
  • ALTER COLUMN … TYPE bigint
  • CREATE INDEX
Постоянное значение по умолчанию хранится в каталоге; изменчивое — вычисляется для каждой строки.
Нужно сменить тип orders.amount с integer на numeric на таблице в 1 млрд строк. План?

Expand/contract: добавить столбец amount_new numeric; код (или триггер) пишет в оба; фоновое заполнение порциями с паузами и контролем отставания реплик; сверка; переключение чтения на новый столбец; создание нужных индексов CONCURRENTLY; затем в короткой миграции с lock_timeout — удаление старого столбца и переименование нового (или код сразу работает с новым именем). Всё — с проверкой на копии продовых данных.

Что включить в CI для миграций?

Применение всех миграций на пустую базу той же версии PostgreSQL (Testcontainers), линтер squawk на опасные операции, проверку, что применённые миграции не изменены (validate), тесты приложения на новой схеме и, в идеале, совместимость предыдущей версии приложения с новой схемой.
