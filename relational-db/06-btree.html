Индекс B-tree изнутри

99% индексов в OLTP-базах — B-деревья. Почему поиск среди миллиарда строк стоит 4 чтения страниц, что происходит при вставке, почему порядок столбцов в составном индексе решает всё и когда индекс не может помочь. С живым B+-деревом, в которое можно вставлять ключи.

6.1Почему дерево и почему «широкое»

Без индекса поиск строки — чтение всей таблицы. Двоичное дерево дало бы log₂(10⁹) ≈ 30 уровней, то есть 30 случайных чтений. B-дерево хранит в узле не один ключ, а сотни: узел = страница 8 КБ. При ветвлении (fanout) 300 высота дерева на миллиард ключей — 4, а верхние два-три уровня всегда в кэше. Итог: поиск = 1–2 реальных чтения с диска.

Листья: ключ → ctid строки, упорядоченысвязаны в двусвязный список — диапазон читается последовательным проходом вправо (или влево для ORDER BY … DESC)

Особенность PostgreSQL — алгоритм Лемана–Яо: у каждой страницы есть «high key» (верхняя граница) и ссылка на правого соседа. Если страницу разделили, пока читатель спускался, он увидит, что ключ больше high key, и перейдёт вправо. Поэтому поиск не блокирует дерево на время разделений.

6.3Живое дерево: поиск, диапазон, вставка

B+-дерево: вставляйте ключи и ищите
Что попробовать Очистите дерево и нажмите «+20 последовательных» — листья заполнены почти на 100%: PostgreSQL при вставке в правый край делит страницу не пополам, а оставляет левую полной. Затем очистите и нажмите «+20 случайных» — заполнение около 60–70%, листьев больше. Это и есть цена случайных ключей (UUID v4) из темы 02.

6.4Составные индексы: правило левого префикса

Индекс (customer_id, created_at) упорядочен сначала по клиенту, внутри клиента — по дате, как телефонная книга «фамилия, имя». Отсюда, что он может:

УсловиеИндекс (customer_id, created_at)
WHERE customer_id = 7✔ левый префикс
WHERE customer_id = 7 AND created_at >= '2026-01-01'✔ равенство + диапазон — идеальный случай
WHERE customer_id = 7 ORDER BY created_at DESC LIMIT 20✔ без сортировки: читает 20 записей с конца диапазона
WHERE created_at >= '2026-01-01'✘ нет первого столбца (в PostgreSQL 18 возможен skip scan при малом числе клиентов, но не рассчитывайте)
WHERE customer_id IN (1,2,3) ORDER BY created_atчастично: найдёт строки, но сортировать придётся
WHERE customer_id > 7 AND created_at = '2026-05-01'частично: диапазон по первому столбцу — второй уже только фильтр
Правило порядка столбцов Сначала столбцы с равенством, затем один столбец с диапазоном или сортировкой. Столбцы после диапазонного для поиска уже не работают — только как фильтр внутри индекса. «Селективность первым» — миф: важнее, какие условия реально встречаются в запросах.

6.5Когда B-tree не помогает

WHERE lower(email) = 'a@b.c'     -- функция над столбцом
WHERE email LIKE '%@gmail.com'   -- шаблон с начальным %
WHERE id::text = '42'            -- приведение типа столбца
WHERE amount + 0 > 100
WHERE created_at::date = '2026-05-01'
CREATE INDEX ON users (lower(email));      -- индекс по выражению
-- LIKE '%x' → триграммный GIN (тема 07)
WHERE id = 42                              -- приводите параметр
WHERE amount > 100
WHERE created_at >= '2026-05-01'
  AND created_at <  '2026-05-02'

Ещё: LIKE 'abc%' использует B-tree только при сортировке (collation) C или с классом операторов text_pattern_ops. Низкоселективное условие (status = 'active' у 90% строк) индекс не использует сознательно: полный просмотр дешевле — тема 08.

6.6Index Only Scan, INCLUDE, частичные индексы

-- 1. Покрывающий индекс: запрос берёт всё из индекса, таблицу не читает
CREATE INDEX orders_cust_created ON orders (customer_id, created_at) INCLUDE (status, total);
SELECT created_at, status, total FROM orders WHERE customer_id = 7 ORDER BY created_at DESC LIMIT 20;
-- работает, только если страницы помечены all-visible в visibility map (после VACUUM)

-- 2. Частичный индекс: индексируем только нужные строки
CREATE INDEX orders_unpaid ON orders (created_at) WHERE status = 'new';
-- крошечный, быстрый; запрос должен содержать то же условие status = 'new'

-- 3. Частичный уникальный индекс: «один активный адрес на клиента»
CREATE UNIQUE INDEX one_default_addr ON addresses (customer_id) WHERE is_default;

6.7Удаление, раздувание, обслуживание

  • DELETE и UPDATE не удаляют записи из индекса сразу — их убирает VACUUM (или «bottom-up deletion» при вставке в PostgreSQL 14+). Опустевшие страницы переиспользуются, но индекс сам не сжимается.
  • С PostgreSQL 13 дубликаты ключа хранятся сжато (deduplication) — индекс по status или внешнему ключу стал в разы меньше.
  • Пересоздать раздутый индекс без блокировки записи: REINDEX INDEX CONCURRENTLY orders_cust_created;
  • Создавать индексы на живой таблице — только CREATE INDEX CONCURRENTLY (тема 18): обычный блокирует запись на всё время построения.
  • Неиспользуемые индексы ищите по pg_stat_user_indexes.idx_scan = 0 (с учётом реплик!) — каждый стоит места, записи и HOT-обновлений.

6.8Самопроверка

Сколько примерно страниц читается при поиске одного ключа в B-дереве на 1 млрд bigint-ключей?

  • около 30
  • около 4 (высота дерева) + 1 страница таблицы
  • 1
  • около 1000
Ветвление в сотни ключей делает дерево очень низким.

Индекс (status, created_at). Какой запрос использует его эффективнее всего?

  • WHERE created_at > now() - interval '1 day'
  • WHERE status > 'a' AND created_at = '2026-01-01'
  • WHERE status = 'new' ORDER BY created_at LIMIT 50
  • WHERE lower(status) = 'new'
Равенство по первому столбцу и сортировка по второму — индекс отдаёт строки уже в нужном порядке.

Почему WHERE created_at::date = '2026-05-01' не использует индекс по created_at?

  • Даты нельзя индексировать
  • Индекс используется только для первичного ключа
  • Нужен hash-индекс
  • Функция (приведение) применена к столбцу — индекс построен по исходным значениям; нужно условие-диапазон или индекс по выражению
Перепишите как диапазон >= '2026-05-01' AND < '2026-05-02'.

Чем INCLUDE-столбцы отличаются от столбцов ключа индекса?

  • Хранятся только в листьях и не участвуют в поиске и порядке — нужны, чтобы запрос обошёлся без чтения таблицы
  • Ничем
  • По ним проверяется уникальность
  • Они сжимаются TOAST
INCLUDE делает индекс покрывающим, не раздувая внутренние узлы.
Как выбрать порядок столбцов в составном индексе?

Смотреть на реальные запросы: сначала столбцы, сравниваемые на равенство, затем один столбец с диапазоном или ORDER BY. Учитывать, что левый префикс может обслужить другие запросы (индекс (a, b) заменяет индекс (a)). Не добавлять столбцы «на всякий случай»: каждый увеличивает индекс и стоимость записи.

Почему случайные UUID плохи для B-tree?

Каждая вставка попадает в случайный лист: при большом индексе это чтение «холодной» страницы с диска, разделения страниц посередине оставляют их заполненными наполовину, после контрольной точки первое изменение каждой страницы пишет её целиком в WAL. Последовательные ключи (bigint, UUID v7) пишут в один горячий правый лист.
