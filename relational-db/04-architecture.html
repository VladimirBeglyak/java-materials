Архитектура СУБД: путь запроса

Между executeQuery() в вашем коде и байтами на диске — процесс-обработчик, разбор, переписывание, планирование, исполнение, кэш страниц, журнал предзаписи и фоновые процессы. Эта карта нужна, чтобы дальнейшие темы (индексы, MVCC, VACUUM, репликация) легли на место. Основа — PostgreSQL; в конце — чем отличается MySQL InnoDB.

1. Синтаксический разбор

Текст превращается в дерево разбора. Проверяется только грамматика: опечатка в ключевом слове — ошибка здесь; несуществующая таблица — ещё нет. Для подготовленных выражений (PreparedStatement) разбор выполняется один раз.

2. Семантический анализ и переписывание

Имена связываются с объектами каталога (таблицы, столбцы, типы, функции), проверяются права. Переписывание раскрывает представления (view) в их определение и применяет правила, политики построчной безопасности (RLS).

3. Выбор плана

Планировщик перебирает способы выполнить запрос (полный просмотр, индекс, способы соединения), оценивает стоимость каждого по статистике таблиц и выбирает самый дешёвый. Здесь — поиск по первичному ключу. Об этом — темы 08–09.

4. Исполнение: найти строку

Исполнитель — дерево узлов, каждый отдаёт строки родителю по запросу. Узел Index Scan идёт по B-дереву индекса и получает адрес строки (ctid: страница 12, позиция 4). Затем нужна сама страница таблицы: менеджер буферов ищет её в shared buffers. Нет — читает из файла (возможно, из кэша ОС) в свободный буфер, вытесняя давно неиспользуемый.

5. UPDATE = новая версия строки

Строка не перезаписывается на месте: старая версия помечается как удалённая транзакцией 742, рядом записывается новая (MVCC, тема 11). Если изменённый столбец не входит в индексы и на странице есть место — индексы не трогаются (HOT, тема 05). Страница в shared buffers становится «грязной»; на диск её запишут позже.

6. Запись в журнал предзаписи

Описание изменения добавляется в буфер WAL. Правило WAL: запись журнала попадает на диск раньше, чем изменённая страница данных. Поэтому страницы можно сбрасывать когда угодно — при сбое всё восстановится из журнала (тема 10).

7. COMMIT: долговечность

При фиксации транзакции её запись в WAL сбрасывается на диск (fsync) и только потом клиент получает подтверждение. Сами страницы таблицы при этом ещё в памяти. Цена коммита — один последовательный сброс журнала; несколько одновременных коммитов объединяются в один сброс (group commit).

8. Позже: контрольная точка

Checkpointer записывает грязные страницы в файлы данных. После этого старый WAL для восстановления не нужен. Чем реже контрольные точки, тем меньше записи, но дольше восстановление после сбоя.

4.3Кэш страниц: почему важна «тёплая» база

Двойное кэширование

Страница может быть в shared buffers и в кэше ОС одновременно. Обычный совет — shared_buffers около 25% памяти; остальное эффективно использует кэш ОС. Узнать долю попаданий: pg_stat_database.blks_hit / (blks_hit + blks_read) — для OLTP ожидается 99%+.

Рабочий набор

Скорость определяется тем, помещаются ли в память часто используемые страницы — верхние уровни индексов и «горячие» данные, а не вся база. Отсюда эффект последовательных ключей (тема 02): новые записи концентрируются в немногих страницах.

4.5Самопроверка

Когда изменённая UPDATE-ом страница таблицы оказывается на диске?

  • Сразу при выполнении UPDATE
  • Позже — при контрольной точке или вытеснении из кэша; при COMMIT на диск сбрасывается только WAL
  • Только при остановке сервера
  • Никогда, данные живут в памяти
Долговечность обеспечивает журнал; страницы пишутся асинхронно.

Почему для PostgreSQL рекомендуют пул соединений?

  • Без пула нельзя выполнять транзакции
  • Пул шифрует соединения
  • Каждое соединение — отдельный процесс ОС: тысячи соединений расходуют память и процессор на переключения
  • Пул ускоряет диск
Небольшое число активных соединений обслуживает больше запросов, чем тысячи конкурирующих.

На каком этапе обнаружится ошибка «relation "ordrs" does not exist»?

  • При анализе: имена связываются с объектами каталога
  • При синтаксическом разборе
  • При планировании
  • При коммите
Парсер проверяет только грамматику; существование объектов — анализатор.
Опишите путь запроса внутри PostgreSQL.

Соединение → backend-процесс → разбор → анализ и переписывание (представления, RLS) → планирование по статистике → исполнение дерева узлов; страницы читаются через shared buffers (кэш ОС, диск); изменения — новые версии строк в буферах и записи в WAL; COMMIT — сброс WAL на диск; страницы данных записываются позже контрольной точкой.

Чем heap-таблица PostgreSQL отличается от кластерного индекса InnoDB?

В PostgreSQL строки лежат без порядка, все индексы (включая первичный) ссылаются на физический адрес строки. В InnoDB таблица и есть B-дерево первичного ключа; вторичные индексы хранят первичный ключ, и поиск по ним требует второго прохода по кластерному индексу. Отсюда в InnoDB особая важность короткого и последовательного первичного ключа.
