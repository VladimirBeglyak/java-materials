MVCC: версии строк

Многоверсионное управление конкурентным доступом: читатели не блокируют писателей, писатели не блокируют читателей. Каждое изменение создаёт новую версию строки, а каждая транзакция видит ту версию, которая соответствует её снимку. В песочнице с двумя сессиями вы увидите это своими глазами — и поймёте, откуда берутся мёртвые строки и почему опасны долгие транзакции.

11.1Идея: не перезаписывать, а добавлять версию

Без MVCC читатель должен ждать, пока писатель закончит (иначе увидит незафиксированные данные), а писатель — пока читатели прочитают. При тысячах запросов в секунду это очереди на каждой популярной строке. MVCC решает иначе: UPDATE не меняет строку на месте, а создаёт новую версию; старая остаётся для тех, кому она ещё нужна.

Что даёт

Чтение никогда не ждёт записи. Отчёт на час видит согласованное состояние на момент начала, не мешая OLTP. ROLLBACK мгновенный — просто пометить транзакцию прерванной.

Чем платим

Старые версии занимают место, пока их не уберёт VACUUM (тема 14). Долгая транзакция не даёт убирать мусор во всей базе. Две записи одной строки всё равно конфликтуют — блокировка строки (тема 13).

11.2Версия строки и снимок

Как мы видели в теме 05, у каждой версии есть xmin (кто создал) и xmax (кто удалил или заменил). Номер транзакции (xid) выдаётся при первой записи; читающие транзакции обходятся виртуальным номером.

Снимок (snapshot) — три вещи: xmin снимка (все транзакции раньше уже завершены), xmax снимка (первый ещё не выданный номер — всё, что начнётся позже, невидимо) и список xip — транзакции, активные в момент снимка. Версия видна, если:

  1. её xmin — это я, либо транзакция, зафиксированная до снимка (номер < xmax снимка, не в списке активных, статус «committed»);
  2. и её xmax пуст, либо принадлежит прерванной транзакции, либо транзакции, невидимой для снимка (ещё активной или начавшейся позже).
BEGIN;
SELECT pg_current_xact_id_if_assigned();   -- NULL: пока ничего не писали
UPDATE accounts SET balance = balance + 10 WHERE id = 1;
SELECT pg_current_xact_id();                -- 742
SELECT pg_current_snapshot();               -- 738:742:738,740  (xmin:xmax:активные)
SELECT xmin, xmax, * FROM accounts WHERE id = 1;
COMMIT;

Сценарии, которые стоит прокрутить 1. Читатель не ждёт: A: UPDATE → B: SELECT (видит 100, не ждёт) → A: COMMIT → B: SELECT (READ COMMITTED: 110).
2. Неповторяемое чтение: то же при REPEATABLE READ — B после коммита A продолжает видеть 100, пока не завершит свою транзакцию.
3. Конфликт записи: A: UPDATE → B: UPDATE (ждёт) → A: COMMIT. В READ COMMITTED B перечитает 110 и запишет 120; в REPEATABLE READ получит ошибку сериализации. Попробуйте вместо COMMIT сделать ROLLBACK у A.
4. Мусор: посчитайте строки таблицы с «нет/нет» — это мёртвые версии, которые никто уже не увидит.

11.4Статусы транзакций и hint bits

Чтобы проверить «зафиксирована ли транзакция 742», PostgreSQL смотрит в pg_xact (раньше — clog): по 2 бита статуса на транзакцию (в процессе, зафиксирована, прервана). Чтобы не ходить туда при каждом чтении, первый прочитавший строку процесс ставит в заголовке кортежа hint bits «xmin committed». Следствие, которое удивляет: первый SELECT после массовой загрузки пишет на диск — проставляет hint bits (и генерирует WAL, если включены контрольные суммы).

11.5Горизонт: почему долгие транзакции вредны всем

Мёртвую версию можно удалить, только если её не может увидеть ни одна активная транзакция. Граница — самый старый xmin среди всех снимков в базе (и слотов репликации, и реплик с hot_standby_feedback). Одна транзакция, открытая час назад, запрещает VACUUM убирать любые версии, умершие за этот час, во всех таблицах.

Кто держит горизонтКак найти

«idle in transaction» — приложение открыло транзакцию и ушло делать HTTP-вызовstate = 'idle in transaction'; защита: idle_in_transaction_session_timeout

SELECT pid, usename, state, now() - xact_start AS age, backend_xmin, left(query, 60)
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL
ORDER BY age(backend_xmin) DESC LIMIT 5;
Типичный инцидент Spring-метод с @Transactional вызывает внешний сервис, который «завис» на 10 минут. Всё это время соединение в состоянии idle in transaction держит горизонт, таблицы с частыми UPDATE пухнут, запросы замедляются. Правило: никаких сетевых вызовов внутри транзакции, таймауты на всё.

11.6MVCC в InnoDB и Oracle

Там в таблице лежит только последняя версия строки, а для старых снимков версия реконструируется из undo-журнала (сегмента отката). Плюсы: таблица не пухнет от UPDATE, нет VACUUM. Минусы: долгий снимок заставляет хранить и проходить длинные цепочки undo (рост undo-пространства, медленное чтение старой версии), откат большой транзакции — долгий, так как надо применить undo. Проблема долгих транзакций остаётся в любой MVCC-системе — меняется только место, где копится мусор.

11.7Самопроверка

Транзакция A изменила строку и ещё не зафиксирована. Что увидит SELECT транзакции B?

  • Будет ждать завершения A
  • Новое значение
  • Старую версию: версия A не видна, так как A активна в снимке B
  • Ошибку
Читатели не ждут писателей — в этом суть MVCC.

Две транзакции READ COMMITTED делают UPDATE … SET balance = balance + 10 одной строки. Что произойдёт?

  • Вторая ждёт первую, затем перечитывает новейшую версию и прибавляет к ней: итог +20
  • Обе прибавят к исходному значению: итог +10
  • Вторая получит ошибку сериализации
  • Возникнет deadlock
Атомарный UPDATE с выражением от текущего значения безопасен в READ COMMITTED. Опасен «прочитал в приложении — записал вычисленное».

Почему транзакция, открытая 2 часа, вредит таблицам, к которым она даже не обращалась?

  • Она блокирует все таблицы
  • Она занимает все соединения
  • Она держит WAL в памяти
  • Её снимок может требовать старые версии в любой таблице, и VACUUM не удаляет версии новее её горизонта
Горизонт общий для базы (для обычных таблиц — для всего кластера).

Почему первый SELECT по только что загруженной таблице может писать на диск?

  • Он строит индекс
  • Он проставляет hint bits в заголовках кортежей, чтобы следующие чтения не ходили в pg_xact
  • Он запускает VACUUM FULL
  • Он пишет статистику в таблицу
Hint bits пачкают страницы, и их нужно записать.
Объясните MVCC на собеседовании за минуту.

Каждое изменение создаёт новую версию строки с номером создавшей транзакции; удаление помечает версию номером удалившей. Каждый запрос (READ COMMITTED) или каждая транзакция (REPEATABLE READ) работает со снимком — списком транзакций, зафиксированных к моменту снимка — и видит только версии, созданные ими и не удалённые ими. Поэтому чтение не блокирует запись и наоборот. Конфликтуют только две записи одной строки — через блокировку строки. Цена — старые версии, которые убирает VACUUM, и вред от долгих транзакций.

Как обнаружить и предотвратить «idle in transaction»?

Обнаружить: pg_stat_activity с state = 'idle in transaction' и большим now() - state_change; метрика в мониторинге. Предотвратить: не делать внешних вызовов и долгой обработки внутри @Transactional, держать транзакции короткими, ставить idle_in_transaction_session_timeout (например, 60 с) и statement_timeout, следить за утечками соединений в пуле (leakDetectionThreshold в HikariCP).
