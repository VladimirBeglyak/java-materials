JOIN, подзапросы, CTE и оконные функции

Большинство разработчиков используют 20% SQL и вытаскивают данные в приложение, чтобы досчитать остальное в цикле. Между тем база умеет за один запрос и за миллисекунды делать то, на что в коде уходят десятки строк и сотни обращений: «последний заказ каждого клиента», нарастающий итог, обход дерева, «вставить или обновить». Всё из этой главы можно сразу выполнить в песочнице.

3.2Подзапросы

-- скалярный: одно значение
SELECT name, (SELECT max(created_at) FROM orders o WHERE o.customer_id = c.id) AS last_order
FROM customers c;

-- коррелированный EXISTS: для каждой строки внешнего запроса — проверка
SELECT * FROM products p
WHERE NOT EXISTS (SELECT 1 FROM order_items i WHERE i.product_id = p.id);   -- товары, которые ни разу не покупали

-- LATERAL (PostgreSQL): подзапрос, видящий строку слева, — «для каждого клиента N последних заказов»
SELECT c.name, o.*
FROM customers c
CROSS JOIN LATERAL (SELECT id, created_at FROM orders o
                    WHERE o.customer_id = c.id ORDER BY created_at DESC LIMIT 3) o;

Современные планировщики переписывают IN/EXISTS в соединения сами, поэтому выбирайте форму по смыслу и читаемости. Исключение — NOT IN с NULL-ами (тема 01).

3.3CTE и рекурсия

WITH paid AS (                                  -- именованный шаг: читается сверху вниз
    SELECT o.customer_id, SUM(i.qty * i.price) AS total
    FROM orders o JOIN order_items i ON i.order_id = o.id
    WHERE o.status IN ('paid', 'shipped')
    GROUP BY o.customer_id
)
SELECT c.name, p.total
FROM paid p JOIN customers c ON c.id = p.customer_id
WHERE p.total > 10000;

С PostgreSQL 12 нерекурсивные CTE встраиваются в основной запрос (как подзапрос), если на них ссылаются один раз; WITH x AS MATERIALIZED (…) заставляет вычислить шаг отдельно. В старых версиях CTE были «барьером оптимизации».

WITH RECURSIVE tree AS (
    SELECT id, name, parent_id, 1 AS depth, name AS path
    FROM categories WHERE id = 1                                  -- якорь: стартовая строка
  UNION ALL
    SELECT c.id, c.name, c.parent_id, t.depth + 1, t.path || ' / ' || c.name
    FROM categories c JOIN tree t ON c.parent_id = t.id           -- шаг: дети найденных
)
SELECT * FROM tree ORDER BY path;

3.4Оконные функции

Окно — это набор строк, «видимых» из текущей строки, при этом строки не схлопываются, как при GROUP BY: каждая строка остаётся и получает вычисленное значение.

SELECT customer_id, id, created_at,
       ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC) AS rn,   -- номер внутри клиента
       LAG(created_at) OVER (PARTITION BY customer_id ORDER BY created_at) AS prev,   -- предыдущий заказ
       COUNT(*)     OVER (PARTITION BY customer_id)                         AS orders_of_customer
FROM orders;

-- последний заказ каждого клиента (top-1 в группе): окно + фильтр снаружи
SELECT * FROM (
    SELECT o.*, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC) AS rn FROM orders o
) t WHERE rn = 1;
-- в PostgreSQL то же короче: SELECT DISTINCT ON (customer_id) * FROM orders ORDER BY customer_id, created_at DESC;

-- нарастающий итог выручки по дням
SELECT day, revenue, SUM(revenue) OVER (ORDER BY day ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running
FROM daily_revenue;

3.5Агрегаты, о которых мало кто знает

SELECT date_trunc('month', created_at) AS month,
       COUNT(*)                                     AS all_orders,
       COUNT(*) FILTER (WHERE status = 'cancelled') AS cancelled,       -- условная агрегация без CASE
       string_agg(DISTINCT city, ', ')              AS cities,
       percentile_cont(0.95) WITHIN GROUP (ORDER BY total) AS p95_total
FROM orders_view
GROUP BY ROLLUP (date_trunc('month', created_at));                       -- плюс строка общего итога

3.6UPSERT, RETURNING и изменяющие CTE

-- атомарное «вставить или обновить» — без гонки check-then-insert
INSERT INTO daily_stats (day, product_id, sold) VALUES (current_date, 7, 1)
ON CONFLICT (day, product_id) DO UPDATE SET sold = daily_stats.sold + EXCLUDED.sold
RETURNING sold;

-- перенести старые заказы в архив одним атомарным оператором
WITH moved AS (
    DELETE FROM orders WHERE created_at < now() - interval '3 years' RETURNING *
)
INSERT INTO orders_archive SELECT * FROM moved;

-- MERGE (PostgreSQL 15+): синхронизация с несколькими ветками
MERGE INTO products p USING price_import s ON p.sku = s.sku
WHEN MATCHED AND s.price IS NULL THEN DELETE
WHEN MATCHED THEN UPDATE SET price = s.price
WHEN NOT MATCHED THEN INSERT (sku, name, price) VALUES (s.sku, s.name, s.price);

3.8Самопроверка

Что происходит с LEFT JOIN, если условие на правую таблицу поставить в WHERE?

  • Ничего не меняется
  • Запрос не выполнится
  • Строки левой таблицы без пары отбрасываются — LEFT JOIN превращается во внутренний
  • Появляются дубликаты
В строках без пары правые столбцы NULL, условие даёт unknown. Условие для присоединяемых строк — в ON.

Чем ROW_NUMBER отличается от RANK при равных значениях?

  • ROW_NUMBER даёт разные номера равным строкам (в произвольном порядке), RANK — одинаковые с пропуском следующих
  • Ничем
  • RANK работает только с числами
  • ROW_NUMBER не поддерживает PARTITION BY
Для детерминированного результата добавьте в ORDER BY окна уникальный столбец.

Почему INSERT … ON CONFLICT лучше, чем «SELECT, и если нет — INSERT»?

  • Он короче
  • Он атомарен: при параллельных запросах нет гонки между проверкой и вставкой
  • Он не требует индекса
  • Он работает без транзакции
ON CONFLICT опирается на уникальный индекс — тот же механизм, что ловит дубликаты.

Можно ли отфильтровать по оконной функции в WHERE того же запроса?

  • Да
  • Да, если указать псевдоним
  • Только в PostgreSQL
  • Нет — окна вычисляются после WHERE; нужен подзапрос или CTE (или QUALIFY в некоторых СУБД)
Логический порядок из темы 01.
Как найти top-N строк в каждой группе?

ROW_NUMBER() OVER (PARTITION BY группа ORDER BY критерий) в подзапросе + фильтр rn <= N; в PostgreSQL для N = 1 — DISTINCT ON; для малого N и индекса по (группа, критерий) — LATERAL с LIMIT N, которое читает индекс точечно.

Как работает рекурсивный CTE?

Выполняется якорь — начальный набор строк. Затем рекурсивная часть многократно выполняется над строками, полученными на предыдущем шаге, пока она возвращает новые строки; результаты объединяются (UNION ALL). Для защиты от циклов — счётчик глубины или массив пройденных id.
