Уровни изоляции на практике

Буква I в ACID — самая коварная: по умолчанию база не гарантирует, что параллельные транзакции ведут себя как последовательные. Разбираем аномалии на конкретных сценариях (потерянное обновление, неповторяемое чтение, фантомы, write skew), что от чего защищает в PostgreSQL и MySQL и какие приёмы применять в коде.

12.2Что гарантирует каждый уровень

АномалияREAD COMMITTED (PG, по умолчанию)REPEATABLE READ (PG)REPEATABLE READ (MySQL, по умолчанию)SERIALIZABLE (PG)
Грязное чтение✔ нет✔ нет✔ нет✔ нет
Неповторяемое чтение✘ есть✔ нет✔ нет (обычный SELECT)✔ нет
Фантом✘ есть✔ нет✔ для обычного SELECT; для FOR UPDATE — gap-блокировки✔ нет
Read skew✘ есть✔ нет✔ нет✔ нет
Потерянное обновление✘ есть (при чтении в приложение)✔ ошибка сериализации✘ есть: UPDATE читает текущую версию✔ ошибка сериализации
Write skew✘ есть✘ есть✘ есть✔ ошибка сериализации (SSI)
REPEATABLE READ в PostgreSQL — на самом деле Snapshot Isolation Вся транзакция видит один снимок, поэтому в ней нет ни неповторяемых чтений, ни фантомов (стандарт SQL их здесь допускает). Но snapshot isolation не равна сериализуемости: остаётся write skew. SERIALIZABLE в PostgreSQL — это SSI: отслеживаются зависимости «прочитал то, что другой изменил», и при опасном цикле одна из транзакций получает ошибку 40001.

12.4Приёмы защиты в коде

ПриёмКогдаЦена
Атомарный UPDATE с условиемсчётчики, остатки, балансы: SET qty = qty − :n WHERE id = :id AND qty >= :n, проверить число изменённых строкпочти бесплатно — лучший вариант, когда логика выражается в SQL
Пессимистическая блокировка SELECT … FOR UPDATEсложная логика между чтением и записью, высокая конкуренция за строкуожидания, риск deadlock (тема 13), держать коротко
Оптимистическая блокировка (@Version)низкая конкуренция, долгие «пользовательские» сценарии (форма редактирования)при конфликте — исключение и повтор/сообщение пользователю
SERIALIZABLE + повторсложные инварианты по многим строкам (write skew), когда сложно перечислить блокировкиошибки 40001 под нагрузкой, обязательный повтор всей транзакции
Ограничения в схемеUNIQUE, CHECK, EXCLUDE, внешние ключи — инвариант проверяет базане все инварианты выразимы
// 1. Атомарный UPDATE — предпочтительно
@Modifying
@Query("update Stock s set s.qty = s.qty - :n where s.id = :id and s.qty >= :n")
int reserve(long id, int n);          // 0 → недостаточно товара

// 2. Пессимистическая блокировка: SELECT … FOR UPDATE
@Lock(LockModeType.PESSIMISTIC_WRITE)
@QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
Optional<Stock> findLockedById(long id);

// 3. Оптимистическая: UPDATE … SET version = version + 1 WHERE id = ? AND version = ?
@Entity class Stock { @Id Long id; int qty; @Version long version; }
// конфликт → ObjectOptimisticLockingFailureException → повтор

// повтор при 40001/40P01/оптимистическом конфликте — снаружи транзакции!
@Retryable(retryFor = { CannotAcquireLockException.class, ObjectOptimisticLockingFailureException.class },
           maxAttempts = 3, backoff = @Backoff(delay = 50, multiplier = 2, random = true))
@Transactional(isolation = Isolation.SERIALIZABLE)
public void transfer(...) { ... }
Повтор должен охватывать всю транзакцию После ошибки сериализации транзакция мертва: повторять нужно с BEGIN, перечитав данные. Если @Retryable стоит внутри @Transactional-метода, повтор произойдёт в уже прерванной транзакции. И помните о побочных эффектах: отправленное письмо повтором не отменить — выносите их после коммита (outbox).

12.5Как выбирать уровень

  • READ COMMITTED — по умолчанию для OLTP. Достаточно, если запись идёт атомарными UPDATE, ограничениями и явными блокировками там, где читаете-проверяете-пишете.
  • REPEATABLE READ — отчёты, выгрузки, сверки: согласованный снимок для нескольких запросов. В PostgreSQL ещё и защита от потерянного обновления (с повтором).
  • SERIALIZABLE — когда корректность важнее пропускной способности и инварианты сложны. Требует повторов и коротких транзакций; объявляйте read-only транзакции как READ ONLY — им меньше ошибок.
BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY;
-- … отчёт …
COMMIT;

SET default_transaction_isolation = 'serializable';   -- для роли или базы

12.6Самопроверка

Какой уровень изоляции PostgreSQL защищает от write skew?

  • READ COMMITTED
  • REPEATABLE READ
  • Никакой
  • SERIALIZABLE
Snapshot isolation (REPEATABLE READ) не видит конфликт, когда транзакции пишут разные строки.

Самый простой и надёжный способ списать товар со склада без потерянных обновлений?

  • SELECT, проверить в Java, UPDATE с новым значением
  • UPDATE stock SET qty = qty - :n WHERE id = :id AND qty >= :n и проверка числа изменённых строк
  • synchronized-метод в Java
  • Кэш в Redis
Проверка и изменение атомарны внутри одной команды; synchronized не работает при нескольких экземплярах приложения.

Что должно сделать приложение при ошибке 40001?

  • Повторить транзакцию целиком с начала
  • Повторить только последнюю команду
  • Проигнорировать
  • Перезапустить базу
Транзакция прервана; повторять нужно с BEGIN и перечитыванием данных.

Чем отличается REPEATABLE READ в MySQL InnoDB от PostgreSQL в контексте потерянного обновления?

  • Ничем
  • MySQL выдаёт ошибку сериализации, PostgreSQL — нет
  • В MySQL UPDATE работает с текущей зафиксированной версией (current read), и обновление может быть потеряно без ошибки
  • MySQL не поддерживает REPEATABLE READ
В InnoDB для защиты нужен SELECT … FOR UPDATE или атомарный UPDATE.
Объясните разницу между оптимистической и пессимистической блокировкой и когда что выбирать.

Пессимистическая: блокировать строку при чтении (FOR UPDATE), другие ждут. Подходит при высокой конкуренции и коротких операциях. Оптимистическая: не блокировать, а при записи проверять, что версия не изменилась (WHERE version = ?); при конфликте — повтор или ошибка пользователю. Подходит при редких конфликтах и длинных сценариях (форма открыта минуты — держать блокировку нельзя).

Как реализовать «не продать больше билетов, чем мест» при конкурентных покупках?

Варианты: атомарный UPDATE счётчика свободных мест с условием free > 0; если места именные — UNIQUE (event_id, seat_no) на таблице билетов; при сложной логике — SELECT … FOR UPDATE строки события, затем проверки и вставка; или SERIALIZABLE с повтором. Нельзя: проверить count(*) и вставить в READ COMMITTED/REPEATABLE READ без блокировки — это write skew.
