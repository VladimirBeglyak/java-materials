VACUUM, bloat, wraparound

Обратная сторона MVCC в PostgreSQL: мёртвые версии строк надо убирать, статистику — обновлять, а старые номера транзакций — «замораживать», иначе база остановится. Что делает VACUUM, как настроить autovacuum для больших и горячих таблиц, как измерить и устранить раздувание и не допустить аварии wraparound.

14.1Что делает VACUUM

1. Просмотр таблицытолько страниц, не отмеченных в visibility map как all-visible; собирает адреса мёртвых версий (невидимых никому — старше горизонта)
↓
2. Очистка индексовудаляет из каждого индекса записи, указывающие на мёртвые версии — самая дорогая часть при многих индексах
↓
3. Очистка таблицыосвобождает место на страницах, обновляет карту свободного места — новые строки займут его
↓
4. Visibility map и заморозкаотмечает all-visible страницы (для Index Only Scan) и замораживает старые версии (защита от wraparound)

VACUUM

Работает параллельно с чтением и записью (SHARE UPDATE EXCLUSIVE). Место не возвращает ОС — только делает его доступным для новых строк (кроме пустого хвоста таблицы).

VACUUM FULL

Переписывает таблицу заново, компактно, и возвращает место. Но держит ACCESS EXCLUSIVE всё время работы — таблица недоступна. Для продакшена — pg_repack или pg_squeeze.

14.2Autovacuum: когда он приходит

Autovacuum запускает VACUUM для таблицы, когда число мёртвых строк превышает autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × строк (по умолчанию 50 + 20%). ANALYZE — при 50 + 10% изменённых строк. С PostgreSQL 13 — и по числу вставок (для visibility map и заморозки в таблицах «только вставка»).

Симулятор: раздувание таблицы за сутки
ALTER TABLE orders SET (
  autovacuum_vacuum_scale_factor = 0.01,     -- 1% вместо 20%
  autovacuum_vacuum_threshold = 10000,
  autovacuum_analyze_scale_factor = 0.02,
  autovacuum_vacuum_cost_limit = 2000        -- разрешить работать быстрее
);

-- postgresql.conf (современное железо):
-- autovacuum_max_workers = 5
-- autovacuum_vacuum_cost_limit = 1000..2000   (по умолчанию 200 — очень осторожно)
-- autovacuum_naptime = 15s
-- maintenance_work_mem / autovacuum_work_mem = 1GB   (больше мёртвых адресов за один проход по индексам)

14.3Измерить раздувание

SELECT relname, n_live_tup, n_dead_tup,
       round(100.0 * n_dead_tup / nullif(n_live_tup + n_dead_tup, 0), 1) AS dead_pct,
       last_autovacuum, last_autoanalyze, autovacuum_count
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;

-- точная оценка свободного места (читает таблицу!): расширение pgstattuple
SELECT * FROM pgstattuple('orders');           -- dead_tuple_percent, free_percent
SELECT * FROM pgstatindex('orders_pkey');      -- avg_leaf_density, leaf_fragmentation

-- что сейчас делает vacuum
SELECT * FROM pg_stat_progress_vacuum;

14.4Wraparound: авария, которую можно не допустить

Номер транзакции — 32 бита, около 4 млрд значений, и сравнение идёт «по кругу»: для любой транзакции 2 млрд номеров — прошлое, 2 млрд — будущее. Если строке 2 млрд транзакций, её xmin «перескочит» в будущее, и строка исчезнет. Защита — заморозка: VACUUM помечает достаточно старые версии как frozen («видны всем, всегда»).

Возраст самой старой незамороженной транзакции
SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;
SELECT relname, age(relfrozenxid), pg_size_pretty(pg_total_relation_size(oid))
FROM pg_class WHERE relkind IN ('r', 'm', 't') ORDER BY 2 DESC LIMIT 10;
-- алерт: age > 500 млн
Реальные инциденты Известные публичные истории простоя (Sentry в 2015, Mailchimp/Mandrill в 2019) — wraparound на нагруженных базах, где autovacuum не успевал или был заблокирован. Многочасовое восстановление в однопользовательском режиме. Метрика возраста xid и алерт на неё дешевле.

14.5Самопроверка

Возвращает ли обычный VACUUM место операционной системе?

  • Да, всегда
  • Нет, освобождённое место переиспользуется для новых строк этой таблицы (кроме пустых страниц в конце файла)
  • Только для индексов
  • Только с параметром ANALYZE
Сжать файл можно VACUUM FULL (с блокировкой) или pg_repack.

Autovacuum регулярно запускается по таблице, но n_dead_tup не уменьшается. Вероятная причина?

  • Слишком мало индексов
  • Отключена статистика
  • Что-то держит горизонт: долгая транзакция, idle in transaction, забытый слот репликации
  • Слишком большой shared_buffers
Мёртвые версии, которые ещё может увидеть чей-то снимок, удалять нельзя.

Зачем VACUUM замораживает старые версии строк?

  • Чтобы при переполнении 32-битного счётчика транзакций старые строки не стали «невидимыми из будущего»
  • Чтобы сжать таблицу
  • Чтобы ускорить запись
  • Чтобы запретить их изменение
Замороженная версия видна всем независимо от номеров.

Почему для таблицы на 500 млн строк настройки autovacuum по умолчанию плохи?

  • Autovacuum не работает с большими таблицами
  • Нужно отключить autovacuum и запускать VACUUM вручную
  • Он будет запускаться слишком часто
  • Порог 20% = 100 млн мёртвых строк между запусками: раздувание и очень долгие проходы
Для больших таблиц уменьшают scale_factor и поднимают cost_limit.
Таблица выросла с 10 до 80 ГБ при том же числе строк. Ваши действия?

1) Убедиться, что это раздувание: pgstattuple или оценочные запросы, n_dead_tup. 2) Найти причину: долгие транзакции и idle in transaction, слоты репликации, hot_standby_feedback, отменяемый autovacuum (блокировки), недостаточные настройки для этой таблицы. 3) Устранить причину, настроить autovacuum таблицы. 4) Вернуть место: pg_repack таблицы, REINDEX CONCURRENTLY индексов. 5) Добавить мониторинг dead_pct и возраста транзакций.

Можно ли отключить autovacuum на таблице, чтобы он не мешал нагрузке?

Нет: без него растёт раздувание, устаревает статистика (плохие планы), не обновляется visibility map (нет Index Only Scan), и приближается wraparound — тогда агрессивный vacuum всё равно запустится в худший момент. Правильно — сделать его быстрее и чаще (меньшие порции работы), а не реже.
