Реляционная модель и SQL

Реляционная база хранит данные как множество таблиц и отвечает на вопросы, сформулированные декларативно: вы описываете, что нужно получить, а СУБД сама решает, как. Чтобы писать правильные запросы, нужно понимать три вещи, на которых спотыкаются чаще всего: ключи, NULL с его трёхзначной логикой и логический порядок выполнения SELECT. Внизу страницы — настоящая SQL-песочница, в которой всё можно проверить.

1.1Идея реляционной модели

Эдгар Кодд в 1970 году предложил хранить данные как отношения — множества кортежей с одинаковым набором атрибутов — и работать с ними операциями алгебры: выборка, проекция, соединение, объединение. Из этого следуют свойства, которые до сих пор делают реляционные базы выбором по умолчанию:

Независимость от хранения

Запрос не говорит, где лежат данные и какими индексами их искать. Можно добавить индекс или поменять физическое устройство — запросы не меняются.

Произвольные вопросы

Данные нормализованы и связаны ключами — значит, можно задать вопрос, о котором не думали при проектировании, соединив нужные таблицы.

Целостность

Типы, ключи, внешние ключи и CHECK-ограничения проверяет сама база — для любого приложения, которое к ней подключится.

1.2Ключи и ограничения

CREATE TABLE customers (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,   -- первичный ключ: уникален и не NULL
    name        text NOT NULL,
    city        text,                                              -- NULL допустим: город может быть неизвестен
    email       text UNIQUE,                                       -- уникальность, но NULL-ов может быть много
    created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE orders (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id  bigint NOT NULL REFERENCES customers(id),         -- внешний ключ: заказ без клиента невозможен
    status       text NOT NULL CHECK (status IN ('new', 'paid', 'shipped', 'cancelled')),
    created_at   timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE order_items (
    order_id    bigint NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
    product_id  bigint NOT NULL REFERENCES products(id),
    qty         integer NOT NULL CHECK (qty > 0),
    price       numeric(12, 2) NOT NULL,                           -- цена на момент покупки, а не текущая
    PRIMARY KEY (order_id, product_id)                             -- составной ключ
);

PRIMARY KEYзначение уникально и не NULL; по нему строка однозначно находитсяавтоматически создаёт уникальный индекс
UNIQUEнет двух одинаковых не-NULL значенийиндекс; NULL не равен NULL, поэтому строк с NULL может быть много (в PostgreSQL 15+ можно NULLS NOT DISTINCT)

Ограничения — последняя линия обороны Проверка «email уникален» в коде приложения не работает при параллельных запросах (тема 13). Ограничение в базе работает всегда, для любого клиента, включая ручной SQL и соседний сервис. Правило: всё, что является инвариантом данных, выражайте ограничениями схемы.

1.3NULL и трёхзначная логика

NULL означает «значение неизвестно или отсутствует». Сравнение с неизвестным даёт не true и не false, а unknown. WHERE пропускает только строки, где условие true — строки с unknown отбрасываются.

ВыражениеРезультат
NULL = NULLunknown
NULL <> 1unknown
NULL IS NULLtrue
true AND unknownunknown
false AND unknownfalse
true OR unknowntrue
NOT unknownunknown
ЛовушкаПочему
WHERE city <> 'Минск' не вернёт клиентов без городаNULL <> 'Минск' → unknown
NOT IN (подзапрос) возвращает пустоту, если в подзапросе есть NULLx NOT IN (1, NULL) = x<>1 AND x<>NULL → никогда не true
COUNT(city) меньше COUNT(*)агрегаты пропускают NULL; COUNT(*) считает строки
SUM по пустому множеству — NULL, а не 0оборачивайте в COALESCE(SUM(x), 0)
сравнение «равно, включая NULL»a IS NOT DISTINCT FROM b

1.4Логический порядок выполнения SELECT

SELECT пишется в одном порядке, а вычисляется в другом. Этот логический порядок объясняет, почему в WHERE нельзя сослаться на псевдоним из SELECT, почему агрегаты фильтруют в HAVING и почему оконные функции нельзя использовать в WHERE. (Физически планировщик может выполнять шаги иначе, если результат тот же.)

SELECT c.city, COUNT(*) AS orders_cnt                -- 6
FROM customers c JOIN orders o ON o.customer_id = c.id  -- 1
WHERE o.status IN ('paid', 'shipped')                 -- 2
GROUP BY c.city                                       -- 3
HAVING COUNT(*) >= 2                                  -- 4
ORDER BY orders_cnt DESC                              -- 7   (5 — оконные функции, здесь их нет)
LIMIT 1;                                              -- 8
Симулятор: промежуточный результат на каждом шаге

FROM customers JOIN orders

Соединение: каждая строка заказа получает поля своего клиента. Клиент Глеб без заказов в результат не попал — это внутреннее соединение.

c.name c.city o.id o.status Анна Минск 101 paid Анна Минск 102 shipped Борис Москва 103 paid Вера Минск 104 cancelled Борис Москва 105 new Дина Алматы 106 paid Анна Минск 107 paid Егор Москва 108 shipped — 8 строк

WHERE o.status IN ('paid', 'shipped')

Фильтр по отдельным строкам. Агрегатов ещё нет — поэтому WHERE COUNT(*) > 1 невозможен. Псевдонимов из SELECT тоже ещё нет.

Анна Минск 101 paid Анна Минск 102 shipped Борис Москва 103 paid Дина Алматы 106 paid Анна Минск 107 paid Егор Москва 108 shipped — 6 строк (отброшены 104 и 105)

GROUP BY c.city

Строки собираются в группы по городу. После этого в SELECT можно использовать только столбцы группировки и агрегаты — у группы нет «одного» имени клиента.

Минск → [101, 102, 107] Москва → [103, 108] Алматы → [106]

HAVING COUNT(*) >= 2

Фильтр по группам, уже с агрегатами.

Минск → 3 Москва → 2 (Алматы отброшен: 1 < 2)

Оконные функции, затем SELECT

Вычисляются выражения списка выборки и назначаются псевдонимы. Окна (OVER) считаются здесь — после группировки, поэтому их нельзя использовать в WHERE: для фильтрации по оконной функции нужен подзапрос или CTE.

city orders_cnt Минск 3 Москва 2

ORDER BY orders_cnt DESC

Сортировка — уже после SELECT, поэтому здесь псевдоним orders_cnt доступен. Без ORDER BY порядок строк не определён, даже если «всегда выходило по порядку».

LIMIT 1

Последним отсекается нужное число строк. LIMIT без ORDER BY возвращает «какие-то» строки.

city orders_cnt Минск 3

1.6Изменение данных

INSERT INTO customers (name, city, email) VALUES ('Жанна', 'Минск', 'zh@ex.com')
RETURNING id, created_at;                                   -- сразу получить сгенерированные значения

UPDATE orders SET status = 'paid' WHERE id = 105 AND status = 'new'   -- условие на текущее состояние
RETURNING id;                                               -- пусто — значит, статус уже был другим

DELETE FROM orders WHERE status = 'cancelled' AND created_at < now() - interval '1 year';

INSERT INTO product_stock (product_id, qty) VALUES (7, 5)  -- вставить или увеличить (UPSERT)
ON CONFLICT (product_id) DO UPDATE SET qty = product_stock.qty + EXCLUDED.qty;
UPDATE и DELETE без WHERE изменяют всю таблицу. Привычка для ручной работы: сначала SELECT с тем же условием, потом BEGIN; UPDATE …; проверить; COMMIT; — внутри транзакции ошибку можно откатить.

1.7Самопроверка

Что вернёт SELECT * FROM t WHERE x NOT IN (1, 2, NULL)?

  • Все строки, кроме x = 1 и x = 2
  • Ошибку
  • Ни одной строки
  • Только строки с x = NULL
Условие эквивалентно x <> 1 AND x <> 2 AND x <> NULL; последнее всегда unknown. Для «нет в подзапросе» используйте NOT EXISTS.

Почему нельзя написать WHERE orders_cnt > 1, если orders_cnt — псевдоним из SELECT?

  • Псевдонимы запрещены в PostgreSQL
  • WHERE вычисляется раньше SELECT, псевдонима ещё не существует; а для агрегата нужен HAVING
  • Нужно взять псевдоним в кавычки
  • Можно, это работает
Логический порядок: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.

Создаёт ли PostgreSQL индекс для внешнего ключа автоматически?

  • Нет — индекс на ссылающийся столбец нужно создать самому
  • Да, всегда
  • Только при ON DELETE CASCADE
  • Только для составных ключей
Без индекса медленными станут соединения по этому столбцу и удаление строк родительской таблицы (проверка ссылок — полный просмотр дочерней).

Гарантирован ли порядок строк в SELECT * FROM orders?

  • Да, по первичному ключу
  • Да, по порядку вставки
  • Да, если есть индекс
  • Нет — без ORDER BY порядок не определён и может меняться
Он зависит от плана, физического расположения, параллельного выполнения и даже от того, что другой запрос уже читает таблицу (synchronized scans).
В чём ценность декларативности SQL?

Запрос описывает результат, а способ получения выбирает оптимизатор по статистике и доступным индексам. Добавление индекса или рост данных меняют план без изменения кода. Обратная сторона — нужно уметь читать план (тема 08), когда оптимизатор ошибается.

Как NULL ведёт себя в агрегатах, сравнениях и уникальных индексах?

Агрегаты (кроме COUNT(*)) пропускают NULL; SUM/AVG по пустому множеству — NULL. Сравнения с NULL дают unknown, WHERE их отбрасывает; нужен IS NULL / IS DISTINCT FROM. В уникальном индексе NULL-ы не конфликтуют друг с другом (кроме NULLS NOT DISTINCT).

Назовите логический порядок выполнения SELECT.

FROM и JOIN → WHERE → GROUP BY → HAVING → оконные функции → SELECT (выражения, псевдонимы) → DISTINCT → ORDER BY → LIMIT/OFFSET.
