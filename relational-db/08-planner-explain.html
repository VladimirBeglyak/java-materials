Планировщик и EXPLAIN

SQL говорит «что», планировщик решает «как». Он оценивает число строк по статистике, считает стоимость вариантов и выбирает дешёвый. Почти все медленные запросы — это ошибка оценки или отсутствие пути, который был бы дешевле. Учимся читать EXPLAIN ANALYZE так, чтобы находить причину за минуту.

8.1Модель стоимости

Стоимость — условные единицы, где 1 = последовательное чтение одной страницы. Основные параметры:

ПараметрПо умолчаниюСмысл
seq_page_cost1.0чтение страницы подряд
random_page_cost4.0случайное чтение; для SSD обычно ставят 1.1–1.5
cpu_tuple_cost0.01обработка строки
cpu_index_tuple_cost0.005обработка записи индекса
cpu_operator_cost0.0025вычисление оператора или функции
effective_cache_size4GBсколько данных, по мнению планировщика, в кэше — влияет на привлекательность индексов

Главный вход формулы — оценка числа строк (cardinality) на каждом шаге. Ошибка оценки в 100 раз почти гарантирует плохой план: Nested Loop там, где нужен Hash Join, или индекс там, где дешевле прочитать всё.

8.2Способы чтения таблицы

8.3Три алгоритма соединения

Nested Loop

Для каждой строки внешней стороны — поиск во внутренней (обычно по индексу). Отлично, когда внешних строк мало. Катастрофа, если оценили 10, а пришло 100 000.

Hash Join

Меньшую сторону загружает в хэш-таблицу (в work_mem), большую проходит один раз. Лучший для больших соединений по равенству. Не влезла хэш-таблица — пишет пачки на диск (Batches: 8).

Merge Join

Обе стороны отсортированы по ключу — проход «молнией». Хорош, если порядок уже есть (индексы) или нужен на выходе.

Порядок соединения таблиц планировщик тоже выбирает сам: до join_collapse_limit (8) таблиц перебирает варианты, больше — генетический алгоритм (GEQO). Поэтому запрос на 15 таблиц может иметь нестабильный план.

8.4Статистика: откуда берутся оценки

ANALYZE (вручную или autovacuum) читает выборку из 300 × default_statistics_target строк и сохраняет для каждого столбца в pg_stats:

  • null_frac, n_distinct — доля NULL и число различных значений;
  • most_common_vals + most_common_freqs — частые значения и их доли;
  • histogram_bounds — границы корзин равной заполненности для остальных значений;
  • correlation — насколько физический порядок совпадает с порядком значений.
SELECT most_common_vals, most_common_freqs, n_distinct
FROM pg_stats WHERE tablename = 'orders' AND attname = 'status';

-- столбцы зависимы (city и country): по умолчанию планировщик перемножает доли → недооценка
CREATE STATISTICS orders_geo (dependencies, ndistinct, mcv) ON city, country FROM customers;
ANALYZE customers;

-- для столбца с «длинным хвостом» значений — подробнее статистика
ALTER TABLE events ALTER COLUMN tenant_id SET STATISTICS 1000;
Типичные причины плохих оценок Статистика устарела (массовая загрузка без ANALYZE), коррелированные столбцы, условия на выражения (lower(email) без индекса по выражению — нет статистики), функции с неизвестной селективностью, параметризованные запросы с «общим» планом при сильно неравномерных данных, CTE и подзапросы, результат которых сложно оценить.

Как читать план: пять вопросов

План — дерево. Листья (самые глубокие отступы) выполняются первыми и отдают строки родителям. Верхний узел возвращает результат клиенту. Узлы работают конвейером: Limit, получив 20 строк, останавливает всё дерево — поэтому Nested Loop с оценкой 1000 строк реально выдал только 20.

Главная проверка: rows= в оценке и actual … rows= на каждом узле. Расхождение в 10+ раз (без объяснения через Limit) — источник плохого плана. Ищите самый нижний узел с расхождением: выше ошибка только размножается.

Время и строки показаны за один цикл. Внутренняя сторона Nested Loop с loops=50000 и временем 0.02 мс — это 1 секунда. Классическая находка: Nested Loop с огромным loops из-за недооценки внешней стороны.

shared hit — страницы из shared buffers, read — пришлось читать, dirtied/written — запрос сам пачкал и писал страницы, temp read/written — сортировка или хэш ушли на диск. Число страниц точнее времени показывает объём работы и не зависит от «прогретости» кэша.

Ищите: Rows Removed by Filter огромное → индекс не по тому условию; Sort Method: external merge Disk → мало work_mem или нужен индекс для порядка; Heap Fetches большие в Index Only Scan → таблице нужен VACUUM; Hash Batches > 1 → хэш не влез в память; Seq Scan по большой таблице во внутренней стороне Nested Loop.

Инструменты EXPLAIN (ANALYZE, BUFFERS, SETTINGS, FORMAT TEXT); визуализаторы explain.dalibo.com и explain.depesz.com; расширение auto_explain пишет в журнал планы запросов дольше порога — незаменимо для редких медленных запросов в продакшене. Помните: EXPLAIN ANALYZE выполняет запрос — для UPDATE/DELETE оборачивайте в BEGIN … ROLLBACK.

8.6Подготовленные запросы и «общий» план

JDBC-драйвер PostgreSQL после 5 выполнений одного PreparedStatement переходит на серверные подготовленные выражения; сервер после 5 выполнений может выбрать generic plan — план без учёта конкретных значений параметров. Если данные неравномерны (у одного клиента 10 заказов, у другого 10 млн), общий план может быть плох для части значений.

-- увидеть план для параметров
PREPARE q(bigint) AS SELECT * FROM orders WHERE customer_id = $1;
EXPLAIN EXECUTE q(42);

-- для проблемного запроса/сессии: всегда планировать заново под значения
SET plan_cache_mode = force_custom_plan;

8.8Самопроверка

В плане: Nested Loop (rows=12) (actual rows=480000), внутренняя сторона — Index Scan с loops=480000. В чём корень проблемы?

  • Мало shared_buffers
  • Недооценка числа строк внешней стороны: план выбран под 12 строк
  • Индекс повреждён
  • Nested Loop всегда плох
Ищите нижний узел с расхождением оценки и факта и чините статистику или запрос.

Почему условие, отбирающее 40% строк, обычно выполняется Seq Scan даже при наличии индекса?

  • Индексы не работают с большими таблицами
  • Планировщик игнорирует индексы для текста
  • Это ошибка, нужно отключить enable_seqscan
  • Случайные чтения страниц по индексу дороже последовательного чтения всей таблицы
При большой доле строк индекс трогает почти каждую страницу, да ещё в случайном порядке.

Что значит Sort Method: external merge Disk: 120MB?

  • Сортировка не поместилась в work_mem и шла через временные файлы
  • Сортировка по индексу
  • Таблица хранится на диске
  • Сортировка распараллелена
Варианты: индекс, дающий нужный порядок; меньше строк до сортировки; увеличение work_mem для этого запроса.

Чем опасно запускать EXPLAIN ANALYZE DELETE … на проде?

  • Ничем, это только план
  • Блокирует всю базу
  • Запрос реально выполнится и удалит строки
  • Сбрасывает статистику
ANALYZE выполняет запрос. Оборачивайте в BEGIN … ROLLBACK.
Ваш порядок действий с медленным запросом?

1) Получить реальный план: EXPLAIN (ANALYZE, BUFFERS) или auto_explain, на продовых данных. 2) Найти узлы, где больше всего времени и буферов. 3) Сравнить оценки и факт, найти нижнее расхождение. 4) Проверить актуальность статистики (ANALYZE), коррелированные столбцы. 5) Проверить, есть ли подходящий индекс и «индексируемо» ли условие. 6) Переписать запрос, если план ограничен формой запроса. 7) Перепроверить на реальных параметрах, включая «тяжёлых» клиентов.

Почему один и тот же запрос быстр в psql и медленный из приложения?

Частые причины: приложение использует подготовленные выражения и получает generic plan; разные значения параметров (в psql проверяли «лёгкого» клиента); типы параметров не совпадают со столбцом (строка вместо числа → приведение и нет индекса); другие настройки сессии; холодный кэш; ожидание блокировок или пула соединений, а не выполнение.
