WAL и долговечность

Буква D в ACID: после «COMMIT OK» данные переживут выключение питания. Как это достигается одним последовательным журналом, что происходит при восстановлении после сбоя, зачем контрольные точки и как настройки synchronous_commit и fsync меняют гарантии на скорость.

10.1Задача: быстро и надёжно

Транзакция может изменить десятки страниц в разных местах файлов. Записывать их все на диск при каждом COMMIT — десятки случайных записей и fsync: медленно. Не записывать — потеря данных при сбое. Решение — журнал предзаписи (Write-Ahead Log):

  1. Любое изменение страницы сначала описывается записью в журнале (последовательный файл).
  2. При COMMIT на диск принудительно сбрасывается только журнал до записи о коммите — одна последовательная запись.
  3. Изменённые страницы данных пишутся позже, в фоне, пачками.
  4. Правило WAL: страница данных не может попасть на диск раньше, чем журнал с её изменениями (каждая страница хранит LSN последней записи журнала, менеджер буферов это проверяет).

LSN (Log Sequence Number) — позиция в журнале, растущее 64-битное число вида 0/3A2F1A0. Им измеряется всё: отставание реплик, положение контрольной точки, объём сгенерированного WAL.

Последняя контрольная точка на LSN 0/100: все изменения до неё записаны в файлы данных. Счета: A = 100, B = 50.

T1 переводит 30 с A на B. Страницы в памяти изменены (A = 70, B = 80) и помечены грязными. Записи журнала добавлены в буфер WAL — возможно, уже на диске, возможно, нет: до COMMIT это неважно.

При COMMIT журнал сбрасывается на диск вместе с записью о фиксации, и только потом клиент получает OK. Файлы данных по-прежнему содержат A = 100, B = 50.

T2 начала обнулять A, её запись журнала даже успела попасть на диск (walwriter сбрасывает буфер в фоне), но COMMIT не было.

Память потеряна полностью. На диске — устаревшие страницы данных и журнал. Без журнала перевод T1 был бы потерян, хотя клиенту сказали OK.

При старте PostgreSQL видит, что остановка была аварийной, и проигрывает журнал от последней контрольной точки: каждая запись применяется к странице, если LSN страницы меньше LSN записи. Повторяются все записи, включая незавершённую T2.

T1 восстановлена: A = 70, B = 80. Изменения T2 физически применены, но T2 не зафиксирована — по правилам видимости MVCC (тема 11) её версии строк никто не увидит, их уберёт VACUUM. Поэтому PostgreSQL не нужна фаза отката (undo), в отличие от InnoDB и классического алгоритма ARIES.

10.3Контрольные точки и full page writes

Контрольная точка ограничивает, сколько журнала проигрывать при восстановлении: она сбрасывает все грязные страницы и отмечает в журнале «до этой точки всё на диске». Запускается по времени checkpoint_timeout (по умолчанию 5 мин) или по объёму WAL max_wal_size (1 ГБ).

Full page writes Страница 8 КБ, а диск гарантирует атомарность записи блоками 4 КБ или 512 байт. Сбой в середине записи оставит «разорванную» страницу, которую журналом не починить. Поэтому при первом изменении страницы после каждой контрольной точки в WAL пишется её полный образ. Следствие: сразу после checkpoint объём WAL резко растёт, особенно при случайных обновлениях по большой таблице (снова случайные UUID).
Частота контрольных точек: компромисс
SELECT num_timed, num_requested, write_time, sync_time, buffers_written
FROM pg_stat_checkpointer;   -- PostgreSQL 17+; раньше — pg_stat_bgwriter
-- num_requested >> num_timed → увеличьте max_wal_size
-- в журнале: "checkpoints are occurring too frequently"

10.4Ручки долговечности

synchronous_commit и fsync: что вы теряете при сбое
Диск, который врёт Гарантия держится на том, что fsync действительно доводит данные до энергонезависимого носителя. Потребительские SSD с кэшем записи без конденсаторов и некоторые виртуальные диски подтверждают запись раньше — тогда потеря данных возможна при любых настройках. Проверка: pg_test_fsync (нереально быстрый fsync — подозрительно).

10.5Журнал — основа всего остального

Репликация

Реплики получают тот же поток WAL и проигрывают его — физическая репликация (тема 15).

PITR

Базовая копия + архив WAL = восстановление на любую секунду (тема 19).

Логическое декодирование

WAL раскладывается в события INSERT/UPDATE/DELETE — основа CDC (Debezium) и логической репликации.

EXPLAIN (ANALYZE, WAL) UPDATE orders SET status = 'paid' WHERE id = 105;
--   WAL: records=3 fpi=1 bytes=8410        ← fpi: полный образ страницы

SELECT pg_current_wal_lsn(),
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), '0/0')) AS total_wal;
SELECT * FROM pg_stat_wal;   -- wal_records, wal_fpi, wal_bytes, wal_buffers_full

10.6Самопроверка

Что гарантированно оказывается на диске к моменту ответа «COMMIT» при настройках по умолчанию?

  • Все изменённые страницы таблиц и индексов
  • Записи WAL транзакции, включая запись о фиксации
  • Ничего, всё в памяти
  • Только страницы индексов
Страницы данных можно восстановить по журналу, поэтому их запись откладывается.

Зачем в WAL пишутся полные образы страниц после контрольной точки?

  • Для сжатия
  • Для логической репликации
  • Чтобы ускорить чтение
  • Чтобы восстановить страницу, разорванную частичной записью при сбое
Журнальная запись описывает изменение, а не страницу целиком — к испорченной странице её не применить.

Что потеряется при сбое сервера с synchronous_commit = off?

  • Последние доли секунды подтверждённых транзакций; целостность базы сохранится
  • Вся база станет повреждённой
  • Ничего
  • Только незафиксированные транзакции
В отличие от fsync = off, это безопасная для целостности настройка с ограниченным окном потерь.

Почему PostgreSQL не нужна фаза undo при восстановлении?

  • Он не пишет незавершённые транзакции в WAL
  • Он откатывает транзакции при каждой контрольной точке
  • Версии строк незафиксированных транзакций невидимы по правилам MVCC, а мусор потом убирает VACUUM
  • Он хранит undo в отдельном файле
Статус транзакции хранится отдельно (pg_xact); незафиксированная после сбоя считается прерванной.
Объясните, как СУБД обеспечивает долговечность коммита, не записывая все изменённые страницы при каждом COMMIT.

Журнал предзаписи: изменения описываются в последовательном журнале; при COMMIT журнал сбрасывается на диск (fsync), что дёшево — последовательная запись, объединяемая для параллельных коммитов (group commit). Страницы данных пишутся позже фоновыми процессами. Правило WAL гарантирует, что страница не попадёт на диск раньше своего журнала. После сбоя журнал проигрывается от последней контрольной точки.

Как снизить задержку коммита, если часть данных некритична?

Для некритичных транзакций — SET LOCAL synchronous_commit = off: окно потери ограничено долями секунды, целостность сохраняется. Объединять мелкие транзакции в более крупные (батчи). Для пересоздаваемых данных — UNLOGGED-таблицы. Для критичных — быстрые диски с защитой от потери питания и отдельный том под pg_wal.
