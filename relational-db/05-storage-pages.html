Хранение: страницы и кортежи

База читает и пишет не строки, а страницы. Как устроена страница в 8 КБ, что лежит в заголовке каждой строки, почему порядок столбцов влияет на размер таблицы, куда деваются длинные значения и как PostgreSQL обновляет строку, не трогая индексы (HOT).

5.1Файлы таблицы

Каждая таблица и каждый индекс — набор файлов в каталоге данных (base/<oid базы>/<relfilenode>), разрезанных на сегменты по 1 ГБ. У таблицы есть «вилки» (forks):

ФайлСодержимоеЗачем
16384основные данные (main fork)страницы со строками
16384_fsmкарта свободного места (free space map)быстро найти страницу, куда поместится новая строка
16384_vmкарта видимости (visibility map): по 2 бита на страницу«все строки страницы видны всем» — VACUUM пропускает такие страницы, а Index Only Scan не ходит в таблицу
SELECT pg_relation_filepath('orders');          -- base/16384/24576
SELECT pg_size_pretty(pg_relation_size('orders')),          -- только данные
       pg_size_pretty(pg_table_size('orders')),             -- + TOAST, FSM, VM
       pg_size_pretty(pg_total_relation_size('orders'));    -- + все индексы

5.2Устройство страницы

Страница (блок) — 8 КБ, единица чтения, записи и кэширования. Указатели растут сверху, данные — снизу, свободное место — посередине:

Заголовок страницы, 24 байтаLSN последней записи WAL, контрольная сумма, границы свободного места (pd_lower, pd_upper)
Массив указателей (line pointers), по 4 байта(1) → смещение 8100, (2) → 8040, (3) → 7980 … — адрес строки (ctid) = (номер страницы, номер указателя)
свободное местоуказатели растут вниз, кортежи — вверх, навстречу друг другу
Кортежи (версии строк)записываются с конца страницы к началу
Special spaceпусто у таблиц; у индексов — служебные данные (ссылки на соседние страницы B-дерева)
Зачем косвенность через указатели Индекс хранит ctid = (страница, номер указателя), а не смещение байтов. Поэтому внутри страницы кортежи можно передвигать при уплотнении — указатель меняется, ссылки из индексов остаются верными.

5.3Заголовок строки и выравнивание

У каждой версии строки есть заголовок в 23 байта (с выравниванием — 24):

ПолеСмысл
xminномер транзакции, создавшей версию
xmaxномер транзакции, удалившей или заблокировавшей версию (0 — жива)
ctidадрес этой или более новой версии строки — так строятся цепочки обновлений
infomaskфлаги: есть ли NULL, «xmin зафиксирована» (hint bits), HOT-обновление и др.

SELECT ctid, xmin, xmax, id, status FROM orders WHERE id = 105;
--  ctid   | xmin | xmax |  id | status
-- (12,4)  |  731 |    0 | 105 | new

Значения выравниваются по своему размеру: bigint, timestamptz, double — по 8 байт, int — по 4, smallint — по 2, boolean — по 1. Между ними вставляются пустые байты. Поэтому порядок столбцов в CREATE TABLE влияет на размер: сначала широкие фиксированные, потом узкие, в конце — переменной длины.

5.4TOAST: длинные значения

Строка должна поместиться в страницу, а длинный text, jsonb или bytea может весить мегабайты. Если кортеж больше ~2 КБ, PostgreSQL сначала сжимает длинные значения, а если не помогло — выносит их в отдельную TOAST-таблицу кусками по ~2 КБ; в строке остаётся ссылка на 18 байт.

Плюс

Запрос, не читающий большой столбец, его и не трогает: SELECT id, status не распаковывает 1 МБ описания. Таблица остаётся компактной.

Минусы

SELECT * тянет всё; изменение одного ключа в большом jsonb переписывает значение целиком (новая версия в TOAST); частые обновления больших документов — источник раздувания и объёма WAL.

Стратегию задают на столбец: ALTER TABLE t ALTER COLUMN body SET STORAGE EXTERNAL (выносить без сжатия — быстрее подстроки), с PostgreSQL 14 — алгоритм сжатия SET COMPRESSION lz4.

5.5HOT-обновления и fillfactor

UPDATE создаёт новую версию строки (тема 11). Наивно новую версию пришлось бы добавить во все индексы таблицы, даже если индексированные столбцы не менялись. HOT (heap-only tuple) избегает этого, если выполнены два условия: не изменён ни один индексированный столбец и новая версия помещается на ту же страницу.

Симулятор: страница 12 при обновлениях
Индекс orders_pkey
105 → (12,4)105 → (13,1)
Указатели страницы 12
(4) → кортеж A(7) → кортеж B(8) → кортеж C
Кортежи
A: status=newB: status=paidC: status=shipped

Строка 105 — кортеж A по адресу (12,4). Индекс первичного ключа указывает на этот адрес. На странице осталось свободное место — его даёт fillfactor (о нём ниже).

status не входит в индексы, место на странице есть → HOT. Новая версия B ложится на ту же страницу, A получает ссылку ctid на B. Индекс не меняется: поиск по 105 приходит в (12,4) и идёт по цепочке A → B.

Цепочка растёт: A → B → C. Индексов по-прежнему ноль изменений — экономия записи и WAL пропорциональна числу индексов.

Когда старые версии уже никому не видны, любой процесс, читающий страницу, может её «подрезать» (page pruning) без VACUUM: указатель (4) превращается в перенаправление на (8), место A и B освобождается для следующих HOT-обновлений.

Если места на странице нет или изменился индексированный столбец, новая версия уходит на другую страницу, и в каждый индекс добавляется новая запись. При пяти индексах одно UPDATE = 1 запись в таблицу + 5 в индексы + WAL на всё это.

SELECT relname, n_tup_upd, n_tup_hot_upd,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 1) AS hot_pct
FROM pg_stat_user_tables ORDER BY n_tup_upd DESC LIMIT 10;

-- часто обновляемая таблица: оставить 20% страницы под новые версии
ALTER TABLE orders SET (fillfactor = 80);   -- действует для новых страниц; старые — после VACUUM FULL / pg_repack
Практический вывод Каждый лишний индекс не только замедляет вставку, но и может лишить таблицу HOT-обновлений: индекс на updated_at делает каждое UPDATE не-HOT. Проверяйте hot_pct у горячих таблиц.

5.6Для сравнения: страница InnoDB

Страница InnoDB — 16 КБ, и это лист кластерного индекса: строки упорядочены по первичному ключу. UPDATE меняет строку на месте, а старое значение пишется в undo-журнал — поэтому «HOT» там не нужен, но вторичные индексы обновляются при изменении их столбцов, а поиск по вторичному индексу идёт через первичный ключ. Длинные значения уходят на overflow-страницы (аналог TOAST).

5.7Самопроверка

Что хранит индекс PostgreSQL в качестве ссылки на строку?

  • Значение первичного ключа
  • Смещение в байтах от начала файла
  • ctid — номер страницы и номер указателя на ней
  • Хэш строки
Косвенность через массив указателей позволяет двигать кортеж внутри страницы.

UPDATE поменял status. На таблице есть индекс по status. Будет ли обновление HOT?

  • Да, если на странице есть место
  • Нет: изменён индексированный столбец
  • Да, всегда
  • Только при fillfactor = 100
HOT возможен, только если ни один индексированный столбец не изменился и версия помещается на ту же страницу.

Почему (boolean, bigint, boolean, bigint) занимает больше, чем (bigint, bigint, boolean, boolean)?

  • boolean хранится как 8 байт
  • Порядок не влияет на размер
  • Таблица с чередованием типов сжимается хуже TOAST
  • bigint выравнивается по 8 байт — после каждого boolean вставляется 7 пустых байт
32 байта против 18: выравнивание — реальная цена на миллиардах строк.

Зачем нужна карта видимости (visibility map)?

  • Отмечает страницы, где все строки видимы всем: VACUUM их пропускает, Index Only Scan не читает таблицу
  • Хранит права доступа к строкам
  • Показывает, какие страницы в кэше
  • Хранит удалённые строки
2 бита на страницу: all-visible и all-frozen.
Что такое HOT-обновление и как увеличить их долю?

Новая версия строки размещается на той же странице без новых записей в индексах; старая ссылается на новую через ctid. Условия: не изменены индексированные столбцы, на странице есть место. Увеличить: убрать индексы на часто меняющиеся столбцы, снизить fillfactor у часто обновляемых таблиц (80–90), следить за n_tup_hot_upd.

Почему SELECT * по таблице с большим jsonb медленнее, чем выбор нужных столбцов?

Большие значения лежат в TOAST, часто сжатые: SELECT * читает дополнительные страницы TOAST-таблицы и распаковывает данные, а затем гонит их по сети и в память приложения. Выбор только нужных столбцов эти расходы убирает и даёт шанс на Index Only Scan.
