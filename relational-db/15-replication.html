Репликация и отказоустойчивость

Одна база — одна точка отказа и один предел чтения. Репликация даёт копии для переключения при аварии и для разгрузки чтения. Разбираем физическую и логическую репликацию, синхронный и асинхронный режим (сколько данных можно потерять), отставание реплик и «чтение своих записей», автоматическое переключение (Patroni) и что должно уметь приложение.

15.1Физическая (потоковая) репликация

Primaryпишет WAL
→ walsender
сетьпоток записей WAL
→ walreceiver
Standby (hot standby)пишет WAL на свой диск, startup-процесс применяет его; доступна для чтения

Реплика — побайтовая копия всего кластера, получающая тот же WAL (тема 10). Применяет всё: таблицы, индексы, DDL. Поэтому одна версия PostgreSQL и одна архитектура, нельзя реплицировать отдельную таблицу, а на реплике нельзя ничего писать.

-- на реплике: копия с primary + настройки подключения и слот
-- pg_basebackup -h primary -U replicator -D /var/lib/postgresql/data -R -X stream -S replica1 -C

-- на primary: состояние реплик
SELECT application_name, state, sync_state,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)) AS replay_lag_bytes,
       write_lag, flush_lag, replay_lag
FROM pg_stat_replication;

-- на реплике
SELECT pg_is_in_recovery(), now() - pg_last_xact_replay_timestamp() AS lag;
Слоты репликации — защита и угроза Слот гарантирует, что primary не удалит WAL, пока реплика его не получила. Но если реплику выключили навсегда и забыли удалить слот, WAL копится на primary до заполнения диска, а горизонт (тема 11) не двигается. Ограничьте: max_slot_wal_keep_size, мониторинг pg_replication_slots (неактивные слоты).

По умолчанию репликация асинхронная: primary подтверждает COMMIT после локального fsync. Реплика получит WAL через миллисекунды — или позже, при нагрузке и проблемах сети.

Primary физически потерян (диск, зона доступности) раньше, чем WAL ушёл на реплику. Клиенту сказали «OK», а на реплике заказа нет.

Реплику повышают до primary. Потеряны транзакции, подтверждённые за время отставания: RPO (сколько данных можно потерять) = лаг. Обычно миллисекунды, но при пиковой нагрузке — секунды и минуты.

В синхронном режиме COMMIT ждёт, пока хотя бы одна синхронная реплика подтвердит получение и сброс WAL на диск (synchronous_commit = on) или применение (remote_apply).

«OK» получен только после записи на реплику, поэтому авария primary ничего не теряет: RPO = 0. Цена — сетевая задержка в каждом коммите (в той же зоне ~0.5 мс, между регионами — десятки мс) и риск остановки записи, если синхронных реплик не осталось. Поэтому — ANY 1 (r1, r2): хватит любой из двух.

15.3Чтение с реплик и отставание

Разгрузка чтения на реплики работает, но приложение должно мириться с тем, что реплика отстаёт. Классическая ошибка — «прочитать свою запись»:

Пользователь сохранил профиль и сразу открыл его
public class RoutingDataSource extends AbstractRoutingDataSource {
    @Override protected Object determineCurrentLookupKey() {
        return TransactionSynchronizationManager.isCurrentTransactionReadOnly() ? "replica" : "primary";
    }
}
// Оберните в LazyConnectionDataSourceProxy — иначе соединение берётся ДО того, как известен readOnly.
// @Transactional(readOnly = true) → реплика; обычные транзакции → primary.
Конфликты на реплике Долгий запрос на реплике может мешать применению WAL (VACUUM на primary удалил версии, которые запрос ещё читает). Тогда запрос отменяется: «canceling statement due to conflict with recovery», или применение WAL ждёт до max_standby_streaming_delay, и лаг растёт. hot_standby_feedback = on убирает отмены, но держит горизонт primary (раздувание). Для тяжёлой аналитики — отдельная реплика с большой задержкой или отдельное хранилище.

15.4Автоматическое переключение

PostgreSQL сам не переключается. Это делает внешний менеджер кластера: Patroni (стандарт де-факто), pg_auto_failover, операторы Kubernetes (CloudNativePG, Zalando, Crunchy), управляемые сервисы (RDS, Cloud SQL).

Точка подключенияHAProxy/pgBouncer по REST-проверкам Patroni, VIP, DNS или Kubernetes Service — приложение всегда идёт на текущего primary

Split brain

Главная опасность — два primary одновременно (старый «ожил» после сетевого разделения). Защита: лидерство только с ключом в DCS, старый primary сам понижается, не продлив ключ; fencing/watchdog.

RTO

Время переключения: обнаружение (TTL 30 с по умолчанию) + повышение + переподключение клиентов. Типично 10–60 с. Приложение должно переживать это: повторы, таймауты, пул, который сбрасывает мёртвые соединения.

15.5Логическая репликация

Передаёт не байты страниц, а изменения строк (INSERT/UPDATE/DELETE), декодированные из WAL. Можно выбрать таблицы, строки и столбцы, реплицировать между разными версиями PostgreSQL, писать на получателе.

-- источник (wal_level = logical)
CREATE PUBLICATION shop_pub FOR TABLE orders, order_items;
-- получатель (схема таблиц создаётся заранее — DDL не реплицируется!)
CREATE SUBSCRIPTION shop_sub
  CONNECTION 'host=old-db dbname=shop user=repl'
  PUBLICATION shop_pub;

15.6Самопроверка

Сколько подтверждённых транзакций можно потерять при асинхронной репликации и внезапной потере primary?

  • Ничего
  • Те, что подтверждены за время отставания реплики
  • Все транзакции за последние сутки
  • Только незафиксированные
RPO асинхронной репликации = лаг.

Пользователь обновил данные и сразу увидел старые. Чтения идут с реплики. Что сделать?

  • Отключить репликацию
  • Увеличить shared_buffers на реплике
  • Сделать репликацию логической
  • Чтения сразу после записи направлять на primary (или ждать LSN на реплике)
Read-your-writes — свойство, которое обеспечивает маршрутизация.

Почему с одной синхронной репликой запись может полностью остановиться?

  • Если она недоступна, COMMIT ждёт её подтверждения бесконечно
  • Синхронная реплика блокирует таблицы
  • Из-за нехватки WAL
  • Не может
Используйте ANY 1 (r1, r2) и мониторинг.

Для чего логическая репликация подходит, а физическая — нет?

  • Для автоматического failover
  • Для копирования индексов
  • Для обновления мажорной версии PostgreSQL почти без простоя и репликации отдельных таблиц
  • Для ускорения записи
Физическая требует одинаковой версии и копирует весь кластер.
Спроектируйте отказоустойчивый PostgreSQL для сервиса платежей.

Три узла в разных зонах доступности под Patroni (или оператор Kubernetes / управляемый сервис), etcd из трёх узлов. Синхронная репликация ANY 1 на две реплики — RPO = 0 при потере одной зоны. Точка подключения через HAProxy/Service по проверкам Patroni. Архив WAL и базовые копии в объектное хранилище для PITR (тема 19). В приложении — таймауты, повторы идемпотентных операций, пул с ограниченным временем жизни соединений. Регулярные учения по переключению.

Чем репликация не является?

Резервной копией: ошибочный DELETE или DROP мгновенно реплицируется на все копии. Нужны отдельные бэкапы с PITR (или отложенная реплика с recovery_min_apply_delay как дополнительная страховка). И не масштабированием записи: все записи идут через один primary — для этого шардинг или распределённые SQL-базы.
