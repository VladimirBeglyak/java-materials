Логирование: SLF4J, Logback, уровни

Логи — это то, по чему вы будете разбирать инцидент в 3 часа ночи. Senior обязан уметь: выбрать фасад (SLF4J) и реализацию (Logback), настроить уровни по пакетам, связать записи одного запроса через correlation id (MDC) и не залить логи персональными данными. Это инженерная дисциплина, а не «добавить println».

27.1SLF4J: фасад и реализация

SLF4J — это интерфейс (фасад); реальную запись делает реализация (Logback, Log4j2). Код пишет против SLF4J, а конкретную библиотеку выбирают на уровне зависимостей — так можно менять реализацию без правки кода.

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

private static final Logger log = LoggerFactory.getLogger(OrderService.class);

// параметризованное сообщение: строку собираем лениво, без конкатенации
log.info("Заказ {} оплачен, сумма {}", orderId, total);
Всегда SLF4J + параметры {} log.info("x=" + a + " y=" + b) собирает строку даже если уровень INFO выключен. Параметры {} форматируются лениво — это и быстрее, и не утекает в лог лишнее.

27.3Logback: настройка

<configuration>
  <appender name="STDOUT" class="ch.qos.logback.core.ConsoleAppender">
    <encoder>
      <pattern>%d{ISO8601} %-5level [%thread] %logger{36} - %msg%n</pattern>
    </encoder>
  </appender>

  <root level="INFO">
    <appender-ref ref="STDOUT"/>
  </root>
  <logger name="com.acme.orders" level="DEBUG"/>   <!-- свой пакет подробнее -->
  <logger name="org.hibernate" level="WARN"/>      <!-- шумные библиотеки тише -->
</configuration>

27.4MDC и correlation id

MDC (Mapped Diagnostic Context) хранит значения в контексте потока, которые попадают в каждую запись. Туда кладут correlation id / request id — так все логи одного запроса связываются воедино.

String requestId = UUID.randomUUID().toString();
MDC.put("requestId", requestId);
try {
    log.info("начало обработки");
    process(order);
} finally {
    MDC.remove("requestId");   // обязательно убрать (поток переиспользуется!)
}
MDC — это ThreadLocal Забытый MDC.put без remove утечёт в следующий запрос на том же потоке пула: логи перепутаются. Всегда в finally, либо через фильтр/перехватчик.

27.5Структурированные логи

Вместо свободного текста — JSON-записи: их можно индексировать и искать (ELK, Loki). Поля (level, requestId, userId) — структурированные, сообщение — в отдельном поле.

{"ts":"2026-06-15T10:00:00Z","level":"INFO","logger":"OrderService",
 "requestId":"8f1d…","userId":"42","msg":"заказ оплачен","orderId":101}
Готовые решения Logback: logstash-logback-encoder. Логи собираются (Fluent Bit/Filebeat) → Loki/ELK → Grafana/Kibana. Не стройте это вручную, если уже есть стек.

27.6Что логировать, а что нет

  1. Логируйте: старт/завершение операции, ключевые переходы состояния, ошибки со стектрейсом и контекстом, исходящие вызовы к внешним системам (с таймингом).
  2. Не логируйте: пароли, токены, полные номера карт/паспортов, тела ответов с персональными данными. Маскируйте.
  3. Одна запись на событие, а не по строчке на каждое поле.
  4. Ошибка — с контекстом: log.error("не удалось оплатить заказ {}", id, e), а не голое e.getMessage().

27.7Самопроверка

Зачем нужен SLF4J, если есть Logback?

  • SLF4J — фасад: код зависит от интерфейса, реализацию можно менять
  • SLF4J быстрее
  • SLF4J — это формат логов
  • Они несовместимы
Фасад отделяет API от реализации; выбор Logback/Log4j2 — на уровне зависимостей.

Почему параметры {} лучше конкатенации строк в логах?

  • Строка собирается лениво, только если уровень включён
  • Так короче
  • Конкатенация запрещена
  • Нет разницы
log.info("x={}", a) не форматирует строку, когда INFO выключен — экономия и отсутствие лишних аллокаций.

Почему MDC нужно чистить в finally?

  • MDC — ThreadLocal: значение утечёт в следующий запрос на том же потоке пула
  • Иначе память течёт
  • Иначе лог пуст
  • Не нужно чистить
Поток пула переиспользуется; забытый requestId попадёт в чужие логи.

Что даёт correlation id?

  • Связывает все логи одного запроса в единую цепочку
  • Ускоряет логирование
  • Шифрует логи
  • Заменяет уровни
По requestId можно вытащить весь путь запроса через сервисы и потоки.
Как связать логи распределённого запроса через несколько сервисов?

Генерировать requestId на входе (шлюз/фильтр), класть в MDC, передавать дальше в заголовке (например, X-Request-Id) и на каждом сервисе снова класть в MDC. Тогда все записи одного запроса связываются по этому id.

Чем структурированные логи лучше свободного текста?

Их можно индексировать и искать по полям (level, requestId, userId), строить алерты и дашборды. Текст «заказ 42 оплачен» можно только grep-ать.
