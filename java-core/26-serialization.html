Сериализация: JSON, Jackson, protobuf

Сериализация — превращение объектов в байты/текст для хранения и передачи. Senior сталкивается с ней каждый день: DTO в REST, события в очереди, интеграции с внешними системами. Здесь — чем заменить встроенную Java-сериализацию, как работать с Jackson, и как выбирать формат: JSON, protobuf, Avro или XML.

26.1Зачем сериализация

Сериализация решает две задачи: передать данные между процессами/системами (HTTP, очередь, файл) и сохранить их (кэш, БД, журнал). Правильный формат — это компромисс между читаемостью, размером, скоростью и совместимостью версий.

Читаемость

JSON/XML читает человек; бинарные форматы — нет.

Размер и скорость

Бинарные (protobuf) компактнее и быстрее текстовых.

Совместимость

Возможность менять схему, не ломая старых клиентов.

26.2Почему не встроенная Java-сериализация

Нативный Serializable (тема 13) опасен для обмена данными:

ПроблемаСледствие
Связан с именами классов и полейломается при переименовании/рефакторинге, несовместим между версиями
Десриализация вызывает конструкторы/методывектор атак (gadget chains), RCE через недоверенные данные
Формат бинарный и Java-специфичныйне прочитать из другого языка
serialVersionUID вручнуюлёгкий способ получить InvalidClassException
Правило Встроенная Java-сериализация — только для устаревших внутренних механизмов. Для API, очередей и хранилищ используйте JSON (Jackson) или бинарный protobuf/Avro.

26.3JSON и Jackson: чтение и запись

Jackson — стандарт де-факто для JSON в Java. ObjectMapper — потокобезопасен, создаётся один раз и переиспользуется.

public record Order(long id, String status, List<OrderItem> items) {}
public record OrderItem(String productId, int qty) {}

ObjectMapper mapper = new ObjectMapper();          // один на приложение

Order order = new Order(42, "paid", List.of(new OrderItem("p1", 2)));
String json = mapper.writeValueAsString(order);    // → {"id":42,"status":"paid","items":[{"productId":"p1","qty":2}]}

Order back = mapper.readValue(json, Order.class);  // обратно
Records — идеальные DTO Records автоматически дают конструктор, equals, hashCode и неизменяемость, а Jackson умеет их читать/писать без аннотаций (если имена полей совпадают с JSON).

26.4Аннотации Jackson

public record User(
    @JsonProperty("full_name") String name,     // другое имя поля в JSON
    @JsonIgnore String passwordHash,            // не сериализовать
    @JsonInclude(JsonInclude.Include.NON_NULL)  // пропускать null (на классе)
    String email
) {}
АннотацияЗачем
@JsonPropertyпереименовать поле, задать порядок
@JsonIgnoreисключить поле (секреты, вычисляемые значения)
@JsonIncludeне писать null/пустые (меньше трафика, чище контракт)
@JsonFormatформат даты/числа
Не раскрывайте внутренние объекты Сериализуйте DTO, а не сущности JPA/доменные классы: иначе наружу утекут поля и связи, а добавление поля сущности незаметно изменит API.

26.6Protobuf: схема и бинарный формат

Protobuf описывает данные схемой (.proto), из которой генерируются классы. Поля имеют номера — они и есть «имя» в бинарном формате.

syntax = "proto3";

message Order {
  int64 id = 1;              // номер поля = идентификатор в бинарном виде
  string status = 2;
  repeated OrderItem items = 3;
}
message OrderItem {
  string product_id = 1;
  int32 qty = 2;
}
Ключевое свойство protobuf Номер поля — это и есть ключ в бинарном формате. Поэтому можно добавлять новые поля (с новыми номерами) и не ломать старых читателей: неизвестные поля просто игнорируются.

26.7Версионирование и совместимость

  1. Добавляйте поля, не удаляйте и не переиспользуйте номера (protobuf) — старые читатели проигнорируют новое, новые получат старое значение по умолчанию.
  2. В JSON — добавляйте, не переименовывайте. Лишние поля в JSON по умолчанию игнорируются (в Jackson — настройкой FAIL_ON_UNKNOWN_PROPERTIES).
  3. Не меняйте тип/смысл существующего поля — это ломает контракт тихо.
  4. Для удаления поля — сначала перестаньте писать, затем читать (двухфазный деплой).
  5. Версионируйте API явно (/v1, заголовок версии), когда меняете поведение, а не только схему.

26.8Самопроверка

Почему встроенную Java-сериализацию нельзя использовать для обмена между системами?

  • Она медленная
  • Связана с именами классов, небезопасна при десериализации и не переносима между языками
  • Она не поддерживает коллекции
  • Она текстовый формат
Serializable ломается при рефакторинге, уязвим к gadget-атакам и читается только из Java.

Как создать потокобезопасный ObjectMapper?

  • Создать один экземпляр и переиспользовать
  • Создавать на каждый вызов
  • Обернуть в synchronized
  • Использовать static-блок
ObjectMapper потокобезопасен после настройки — держите один экземпляр на приложение.

Что делает @JsonIgnore?

  • Меняет имя поля
  • Форматирует дату
  • Исключает поле из сериализации/десериализации
  • Задаёт порядок полей
Прячет поля (секреты, вычисляемые значения) из JSON.

Почему в protobuf можно добавлять поля без поломки старых читателей?

  • Потому что он текстовый
  • Потому что нет схемы
  • Потому что все поля опциональны
  • Поле идентифицируется номером, и неизвестные номера игнорируются
Старый читатель пропустит незнакомый номер; новое поле получит значение по умолчанию.
Когда выбирать JSON, а когда protobuf?

JSON — REST/браузер/человекочитаемость, совместимость с JS; по умолчанию. Protobuf — интенсивный межсервисный обмен (gRPC), где важны размер, скорость и строгая схема.

Почему нельзя сериализовать JPA-сущности напрямую в API?

Утекут внутренние поля и ленивые связи, а изменение сущности незаметно изменит публичный контракт. Для API — отдельные DTO (обычно records).

Как безопасно удалить поле из protobuf-схемы?

Двухфазно: сначала перестать писать поле (все продюсеры обновлены), затем — читать. Номер поля при этом не переиспользовать под другое поле.
