HashMap изнутри, Map и Set

HashMap — самая используемая структура данных в Java и самый частый вопрос на собеседовании. Нужно уметь рассказать путь ключа от hashCode() до ячейки, объяснить коллизии, деревья и расширение таблицы — и знать, когда вместо неё взять LinkedHashMap или TreeMap.

9.1Устройство HashMap

Идея хэш-таблицы: вместо поиска ключа перебором вычислить по нему номер ячейки массива и обратиться к ней напрямую. Ячейку называют бакетом (bucket). Несколько ключей могут попасть в один бакет — это коллизия; тогда внутри бакета хранится небольшая цепочка.

Что происходит при put(key, value)

  1. Хэш. Вызывается key.hashCode(); старшие 16 бит «подмешиваются» к младшим: h ^ (h >>> 16). Для ключа null хэш равен 0.
  2. Индекс. (n − 1) & hash, где n — длина таблицы. Так как n — степень двойки, это быстрый эквивалент остатка от деления: берутся младшие биты хэша.
  3. Бакет пуст — создаётся узел.
  4. Бакет занят — узлы просматриваются по очереди. Ключ считается найденным, если совпал хэш и (== или equals). Найден — значение заменяется; нет — новый узел добавляется в конец цепочки.
  5. Цепочка достигла 8 узлов — она превращается в дерево (если таблица меньше 64 бакетов, вместо этого расширяется таблица).
  6. Число элементов превысило порог (capacity × 0,75) — таблица удваивается.

get(key) повторяет шаги 1, 2 и 4. Отсюда видно, зачем нужны оба метода: hashCode выбирает бакет, equals находит ключ внутри него (тема 05).

Зачем подмешивать старшие биты В таблице на 16 бакетов индекс определяют только 4 младших бита хэша. Если у ключей различаются лишь старшие биты (типично для Float, адресов, составных идентификаторов), все они попадут в один бакет. Операция h ^ (h >>> 16) дёшево распространяет влияние старших битов на младшие.
Интерактив: куда попадёт ключ

Хэш вычисляется по тем же формулам, что в String.hashCode() и HashMap.hash(). Обратите внимание на Aa и BB — у них одинаковый хэш — и на то, как меняется раскладка при увеличении таблицы.

9.2Коллизии и деревья

При равномерном хэше цепочки короткие, и операции выполняются за O(1). Но хэш может быть плохим — случайно или по умыслу: злоумышленник подбирает тысячи строк с одинаковым hashCode, отправляет их параметрами запроса, и сервер тратит всё время на перебор одной цепочки. До Java 8 это давало O(n) на операцию.

КонстантаЗначениеСмысл
TREEIFY_THRESHOLD8Длина цепочки, при которой она превращается в красно-чёрное дерево
MIN_TREEIFY_CAPACITY64Минимальный размер таблицы для этого; в меньшей таблице вместо дерева — расширение
UNTREEIFY_THRESHOLD6Дерево снова становится списком, когда в нём остаётся столько узлов

Дерево упорядочено по хэшу, а при равных хэшах — по compareTo, если ключи реализуют Comparable. Поэтому худший случай стал O(log n), но только для сравнимых ключей: у String это работает, у собственного класса без Comparable с константным hashCode поиск в дереве всё равно вырождается.

9.3Расширение таблицы

  • Начальная ёмкость — 16 бакетов; таблица создаётся при первой вставке.
  • Коэффициент загрузки (load factor) — 0,75. Когда элементов становится больше capacity × 0,75, таблица удваивается: 16 → 32 при 13-м элементе.
  • Перераспределение. При удвоении в индексе начинает участвовать ещё один бит хэша. Каждый узел либо остаётся в бакете i, либо переезжает в i + oldCapacity — хэш заново не вычисляется, порядок в цепочке сохраняется.
  • Таблица никогда не уменьшается, даже после clear().

Значение 0,75 — компромисс: меньше — расходуется память на пустые бакеты, больше — растут цепочки.

Ловушка: аргумент конструктора — это не число элементов 
Map<String, User> m1 = new HashMap<>(1000);        // таблица на 1024 бакета, порог 768 —
                                                   // при вставке 769-го элемента произойдёт расширение
Map<String, User> m2 = new HashMap<>(1000 * 4 / 3 + 1);   // правильно: ёмкость = элементы / 0,75
Map<String, User> m3 = HashMap.newHashMap(1000);          // Java 19+: фабрика считает сама
Расширение большой карты — копирование всех узлов. Если размер известен заранее, задайте его.

9.5Современный API Map

// счётчик
Integer old = counts.get(word);
counts.put(word, old == null ? 1 : old + 1);
counts.merge(word, 1, Integer::sum);                       // то же одной строкой

// группировка: ключ → список
List<Order> list = byUser.get(userId);
if (list == null) { list = new ArrayList<>(); byUser.put(userId, list); }
list.add(order);
byUser.computeIfAbsent(userId, k -> new ArrayList<>()).add(order);   // то же одной строкой

int n = counts.getOrDefault(word, 0);                      // без проверки на null
cache.putIfAbsent(key, value);                             // положить, только если ключа нет
stock.computeIfPresent(sku, (k, v) -> v > 1 ? v - 1 : null);   // вернуть null — удалить запись
for (Map.Entry<String, Integer> e : counts.entrySet()) { use(e.getKey(), e.getValue()); }   // один проход
counts.forEach((word, n) -> use(word, n));
for (String k : counts.keySet()) { use(k, counts.get(k)); }      // лишний поиск на каждом шаге — так не надо
  • Map.of(k1, v1, …) — неизменяемая карта (до 10 пар; больше — Map.ofEntries). Не допускает null и дубликатов ключей; порядок обхода намеренно случаен между запусками.
  • Функция в computeIfAbsent не должна изменять ту же карту — это приводит к ConcurrentModificationException или повреждению структуры.
  • get возвращает null в двух случаях: ключа нет или значение равно null. Различить их — containsKey; лучше не хранить null-значения вовсе.

class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int maxSize;
    LruCache(int maxSize) {
        super(16, 0.75f, true);                  // true — порядок по последнему доступу
        this.maxSize = maxSize;
    }
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > maxSize;                 // вызывается после каждой вставки
    }
}   // не потокобезопасен; в рабочем коде — библиотека Caffeine
TreeMap<Integer, String> grades = new TreeMap<>(Map.of(0, "F", 60, "D", 70, "C", 80, "B", 90, "A"));
grades.floorEntry(85).getValue();     // "B": наибольший ключ ≤ 85
grades.ceilingKey(61);                // 70: наименьший ключ ≥ 61
grades.headMap(70);                   // {0=F, 60=D} — представление ключей < 70
grades.firstKey();  grades.lastEntry();  grades.descendingMap();

TreeMap — красно-чёрное дерево. Ключи сравниваются через compareTo или компаратор, а не через equals (тема 05). Методы floor/ceiling — основа диапазонных справочников: тарифные сетки, интервалы времени, кольцо согласованного хэширования.

9.7Множества

HashSet — это HashMap, в котором элементы хранятся как ключи, а значением служит один общий объект-заглушка. LinkedHashSet и TreeSet так же построены на LinkedHashMap и TreeMap. Всё сказанное о ключах карты относится к элементам множества: согласованные equals и hashCode, неизменяемость.

Set<String> a = new HashSet<>(List.of("x", "y", "z"));
Set<String> b = Set.of("y", "z", "w");

a.add("x");            // false — элемент уже есть; add сообщает, изменилось ли множество
a.retainAll(b);        // пересечение: a = {y, z}
a.addAll(b);           // объединение
a.removeAll(b);        // разность

List<String> unique = new ArrayList<>(new LinkedHashSet<>(withDuplicates));   // убрать дубликаты, сохранив порядок

9.8Интерактив: коллизии, resize и превращение в дерево

Симулятор: что происходит с перегруженным бакетом

Введите хэши ключей через запятую (уже после «перемешивания» h ^ (h >>> 16)). По умолчанию — девять ключей, которые при таблице 16 попадают в один бакет.

Почему при resize не пересчитывают индекс заново Длина таблицы — степень двойки, и при удвоении в маске появляется ровно один новый бит. Узел либо остаётся в бакете i, либо уходит в i + oldCap; достаточно проверить (hash & oldCap) == 0. Цепочка делится на две («lo» и «hi») с сохранением относительного порядка.

9.9Самопроверка

Когда цепочка в бакете HashMap превращается в дерево?

  • Когда в бакете 8 узлов
  • Когда load factor превышает 0,75
  • Когда в бакет добавляется узел сверх 8 и размер таблицы не меньше 64; иначе выполняется resize
  • Никогда, дерево только в TreeMap
TREEIFY_THRESHOLD = 8, MIN_TREEIFY_CAPACITY = 64. Обратно в список — при 6 узлах (UNTREEIFY_THRESHOLD).

Какая сложность get() в HashMap в худшем случае (Java 8+)?

  • O(1)
  • O(log n) — бакет с коллизиями хранится деревом
  • O(n)
  • O(n log n)
До Java 8 худший случай был O(n) — длинный связный список, чем пользовались для DoS-атак на хэш-таблицы.

Нужно хранить записи в порядке вставки и вытеснять самую давнюю по обращению. Что выбрать?

  • LinkedHashMap с accessOrder = true и переопределённым removeEldestEntry
  • TreeMap
  • HashMap с сортировкой при чтении
  • IdentityHashMap
Это готовый LRU-кэш в три строки. TreeMap упорядочивает по ключу, а не по времени.
Опишите по шагам, что происходит при map.put(key, value).

Вычисляется hashCode ключа и перемешивается (h ^ h >>> 16); индекс бакета — (n − 1) & hash. Пустой бакет — создаётся узел. Занятый — узлы сравниваются по хэшу и equals: найден — значение заменяется, нет — узел добавляется в конец; при 8 узлах цепочка превращается в дерево (если таблица не меньше 64). Если размер превысил capacity × loadFactor — таблица удваивается.

Что такое коллизия и как HashMap её разрешает?

Ситуация, когда разные ключи попадают в один бакет — из-за совпадения хэшей или их младших битов. Разрешается цепочкой узлов в бакете (метод цепочек); длинные цепочки с Java 8 превращаются в красно-чёрные деревья, что ограничивает худший случай O(log n).

Почему длина таблицы — всегда степень двойки?

Индекс вычисляется побитовым «и» (n − 1) & hash — это быстрее деления и корректно работает с отрицательными хэшами. А при удвоении каждый узел либо остаётся на месте, либо сдвигается ровно на старую ёмкость — определяется одним битом хэша, без пересчёта.

Нужно положить в HashMap 1000 записей. Как создать карту, чтобы избежать расширений?

new HashMap<>(1000) недостаточно: аргумент — ёмкость таблицы, она округлится до 1024, а порог составит 1024 × 0,75 = 768, и на 769-й записи таблица расширится. Надёжно: new HashMap<>((int) (1000 / 0.75f) + 1) или HashMap.newHashMap(1000) в Java 19+.

Чем LinkedHashMap и TreeMap отличаются от HashMap?

LinkedHashMap дополнительно связывает записи двусвязным списком и обходит их в порядке вставки или последнего доступа; операции остаются O(1). TreeMap хранит ключи в красно-чёрном дереве в отсортированном порядке: операции O(log n), зато есть поиск ближайшего ключа и срезы по диапазону; сравнение идёт через compareTo, ключ null запрещён.

Что произойдёт, если изменить поле ключа после вставки в HashMap?

Если поле участвует в hashCode, запись останется в бакете, соответствующем старому хэшу. Поиск по изменённому ключу пойдёт в другой бакет и ничего не найдёт; запись нельзя ни получить, ни удалить, но она занимает память. Ключи должны быть неизменяемыми.
