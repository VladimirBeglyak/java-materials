Исключения — простыми словами

Что делать программе, если файл не найден, сеть пропала, а пользователь ввёл буквы вместо числа? В Java для этого есть исключения. Разберёмся, какие они бывают, как их ловить, как не забыть закрыть ресурсы и каких ошибок избегать.

6.1Какие бывают исключения

Error

Беда с самой машиной: кончилась память, переполнен стек. Ловить почти бессмысленно.

Проверяемые (checked)

Ожидаемые внешние неприятности: файла нет, сеть недоступна. Компилятор заставляет их обработать или явно пробросить.

Непроверяемые (Runtime)

Ошибки в логике программы: null, неверный индекс, неправильный аргумент. Компилятор не заставляет — их надо не ловить, а не допускать.

Главная мысль Error — авария JVM, checked — внешние неприятности, Runtime — ошибки в коде.

6.2try, catch, finally

Исключение летит вверх по цепочке вызовов, как мяч, пока его не поймает catch подходящего типа. Если никто не поймал — программа (точнее, поток) падает со стек-трейсом. Блок finally выполняется всегда — и при успехе, и при ошибке: туда кладут «уборку».

Главная мысль Исключение летит вверх до первого подходящего catch. finally выполняется всегда.

6.3try-with-resources: автоматическая уборка

Файлы, соединения с базой, сетевые сокеты нужно закрывать, иначе они «утекают». Раньше это делали в finally, и это было многословно и легко ошибиться. Теперь пишут ресурс в скобках после try — и Java сама закроет его при выходе из блока, даже при ошибке. Как дверь с доводчиком: закроется сама.

Главная мысль Всё, что нужно закрывать, — в try-with-resources.

6.4Свои исключения и перевод между слоями

Можно создавать свои исключения с понятными именами: OrderNotFoundException говорит больше, чем просто RuntimeException. А когда низкоуровневая ошибка (SQLException) поднимается в бизнес-слой, её заворачивают в своё исключение — но обязательно передают исходную как причину (cause), чтобы не потерять стек-трейс.

Главная мысль Свои исключения — для понятности. Заворачивая, сохраняйте исходную причину.

6.5Чего не делать

  • Пустой catch — «проглотить» ошибку. Программа ведёт себя странно, а следов нет.
  • Ловить всё подряд (catch (Exception e)) там, где не знаешь, что с этим делать.
  • Логировать и пробрасывать одну и ту же ошибку на каждом уровне — в логах дубли.
  • Управлять логикой через исключения — они для нештатных ситуаций, не для обычных «если».
  • return в finally — он «съедает» исключение.
Главная мысль Не глотайте ошибки, не ловите всё подряд, не строите на исключениях обычную логику.

6.8Проверьте себя

Какие исключения компилятор заставляет обработать?

  • RuntimeException
  • проверяемые (checked), например IOException
  • Error
  • никакие
Checked — ожидаемые внешние неприятности.

Выполнится ли finally, если в try было исключение?

  • нет
  • только если его поймали
  • только без return
  • да, всегда
finally — для «уборки», которая нужна в любом случае.

Как правильно работать с файлом, чтобы он точно закрылся?

  • try-with-resources
  • закрыть в конце try
  • надеяться на сборщик мусора
  • закрыть в catch
Ресурс закроется при выходе из блока, даже при ошибке.

Чем плох пустой catch?

  • замедляет программу
  • не компилируется
  • ошибка «проглатывается» без следа, и причину странного поведения не найти
  • ничем
Минимум — залогировать или пробросить.

Вы заворачиваете SQLException в своё исключение. Что важно не забыть?

  • сменить сообщение на английское
  • передать исходное исключение как причину (cause)
  • удалить стек-трейс
  • напечатать его в консоль
Иначе пропадёт информация о настоящей причине.
