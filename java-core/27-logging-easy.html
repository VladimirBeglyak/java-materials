27.1SLF4J: фасад и реализация

Код пишет в журнал через SLF4J — единый «пульт». А кто реально записывает (Logback, Log4j2), подключается отдельно. Как розетка и электростанция: прибору всё равно, откуда ток. Поэтому библиотеки используют SLF4J и не навязывают приложению свою систему логов.

Сообщения пишут с подстановкой: log.info("Заказ {} создан", id), а не склейкой строк — тогда строка не собирается, если этот уровень выключен.

Главная мысль Пишем через SLF4J с {}-подстановкой, реализация — Logback.

27.3Logback: куда и как писать

Настройка (logback.xml или настройки Spring Boot) задаёт: appender — куда писать (консоль, файл), шаблон — как выглядит строка, уровни для разных пакетов (свой код — DEBUG, библиотеки — WARN). Для файлов настраивают ротацию: новый файл каждый день и удаление старых.

Главная мысль Appender — куда, pattern — как, уровни — сколько.

27.4MDC и correlation id

Сервер обрабатывает сотни запросов одновременно, и строки логов перемешаны. Как найти все строки одного запроса? Каждому запросу дают уникальный correlation id и кладут его в MDC — «карман» текущего потока. Logback добавляет его в каждую строку. Тот же id передают в другие сервисы — и путь запроса виден через всю систему.

Найти всё про один запрос
запрос пришёл → фильтр создаёт id = a7f3 → MDC.put("cid", "a7f3")[a7f3] INFO  заказ принят
[c912] INFO  заказ принят        ← другой запрос
[a7f3] WARN  склад отвечает медленновызов в сервис оплаты с заголовком X-Correlation-Id: a7f3
там в логах тоже [a7f3]поиск по a7f3 → вся история запроса во всех сервисах
в конце запроса MDC очищают

Каждый запрос получает свою метку.

Метка позволяет отделить один запрос от другого.

Метка передаётся дальше в заголовке.

Не забудьте очистить MDC: поток из пула достанется следующему запросу.

Главная мысль Correlation id в MDC связывает все строки одного запроса — даже между сервисами.

27.5Структурированные логи

Строки вида «Заказ 42 создан пользователем 7» удобно читать человеку, но трудно искать машиной. Если писать логи в JSON (каждое значение в своём поле), системы вроде Elasticsearch или Loki позволяют фильтровать: «все ошибки по заказу 42 за час».

Главная мысль В продакшене — логи в JSON, чтобы по ним можно было искать.

27.6Что писать и что нельзя

  • Писать: важные события, причины ошибок со стек-трейсом, идентификаторы (заказа, пользователя).
  • Нельзя: пароли, токены, номера карт, персональные данные — логи читают многие и хранят долго.
  • Не дублировать: одну ошибку логирует тот, кто её обработал, а не каждый уровень.
  • Не писать в цикле на каждой итерации — логи станут дороже работы.
Главная мысль Логи — для расследования. Без секретов, без дублей, без спама.

27.8Проверьте себя

Почему лучше log.debug("Заказ {}", id), чем log.debug("Заказ " + id)?

  • так короче
  • это одно и то же
  • при выключенном DEBUG строка даже не собирается
  • иначе ошибка компиляции
Подстановка ленивая.

Как найти все строки логов одного запроса среди тысяч?

  • по correlation id, положенному в MDC
  • по времени
  • по уровню
  • никак
Метка добавляется в каждую строку.

Что нельзя писать в логи?

  • id заказа
  • стек-трейс ошибки
  • время события
  • пароли, токены, номера карт
Логи читают многие и хранят долго.

Какой уровень обычно включён в продакшене?

  • TRACE
  • INFO
  • DEBUG
  • никакой
DEBUG и TRACE включают временно для расследований.

Зачем очищать MDC в конце запроса?

  • для скорости
  • чтобы освободить диск
  • поток из пула достанется следующему запросу, и старая метка попадёт в чужие логи
  • не нужно
MDC привязан к потоку, а потоки переиспользуются.
