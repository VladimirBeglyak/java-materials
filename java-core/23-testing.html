Тестирование: JUnit 5, AssertJ, Mockito

Тест — это исполняемое утверждение о том, как должен вести себя код. Хорошие тесты позволяют менять код без страха; плохие — ломаются при каждом рефакторинге и ничего не ловят. Разберём инструменты (жизненный цикл JUnit, утверждения, моки) и, главное, признаки теста, который стоит своих денег.

23.1Анатомия теста

class PricingPolicyTest {

    private final PricingPolicy pricing = new PricingPolicy();        // тестируемый объект — без Spring и моков

    @Test
    @DisplayName("VIP-клиент получает скидку 10% на сумму заказа")
    void vipCustomerGetsTenPercentDiscount() {
        // arrange — исходные данные
        var order = new OrderRequest(1, CustomerType.VIP, List.of(new OrderLine("A1", Money.rub(1000), 2)));

        // act — одно действие
        Money price = pricing.price(order);

        // assert — проверка результата
        assertThat(price).isEqualTo(Money.rub(1800));
    }
}

Одно поведение

Тест проверяет одно правило. Упал — по имени понятно, что сломано, без чтения кода.

Независимость

Тесты не зависят от порядка и друг от друга: никакого общего изменяемого состояния, статических полей, данных предыдущего теста.

Детерминизм

Нет зависимости от времени (Clock), случайности, сети, порядка в HashMap. Тест, падающий раз в неделю, приучает игнорировать красную сборку.

23.2Жизненный цикл JUnit 5

class CartTest {
    static Database db;                       // дорогой общий ресурс
    Cart cart;                                // состояние одного теста

    CartTest()                 { log("constructor"); }
    @BeforeAll  static void startDb()  { log("@BeforeAll");  db = Database.start(); }
    @BeforeEach void createCart()      { log("@BeforeEach"); cart = new Cart(); }
    @Test       void addsItem()        { log("test addsItem");    cart.add("A1"); }
    @Test       void removesItem()     { log("test removesItem"); cart.remove("A1"); }
    @AfterEach  void cleanTables()     { log("@AfterEach");  db.truncate(); }
    @AfterAll   static void stopDb()   { log("@AfterAll");   db.stop(); }
}

Один раз на класс

Статический метод выполняется до создания экземпляров. Здесь — то, что дорого создавать: контейнер с БД, сервер-заглушка. Всё, что создано здесь, разделяется всеми тестами класса, значит должно либо не меняться, либо очищаться.

Новый экземпляр для первого теста

JUnit по умолчанию создаёт отдельный экземпляр класса на каждый тестовый метод (Lifecycle.PER_METHOD). Поэтому поля экземпляра не протекают между тестами — изоляция бесплатно.

Подготовка перед каждым тестом

Общая для всех тестов часть arrange. Не прячьте сюда данные, важные для понимания конкретного теста, — читающий не должен прыгать по файлу.

Тестовый метод

Порядок методов не гарантирован и намеренно не совпадает с порядком в файле: тесты не должны на него опираться.

Очистка после теста

Выполняется, даже если тест упал. Возвращает общие ресурсы в исходное состояние.

Второй экземпляр

Первый экземпляр больше не используется. Для второго теста создаётся новый объект с новыми полями.

Снова подготовка

Корзина пустая: изменения из addsItem не видны.

Второй тест

Если бы тест рассчитывал, что товар «A1» остался от предыдущего теста, он упал бы — и правильно.

Очистка

Один раз после всех тестов класса

Освобождение общих ресурсов. @TestInstance(PER_CLASS) меняет модель: один экземпляр на класс, @BeforeAll может быть нестатическим — но поля становятся общими для тестов.

23.3Утверждения: AssertJ

assertThat(order.total()).isEqualByComparingTo("1800.00");                     // BigDecimal без учёта масштаба
assertThat(orders).hasSize(2).extracting(Order::status).containsExactly(PAID, NEW);
assertThat(user).usingRecursiveComparison().ignoringFields("id", "createdAt").isEqualTo(expected);
assertThat(result).isPresent().get().satisfies(o -> assertThat(o.items()).isNotEmpty());

assertThatThrownBy(() -> service.pay(order))                                    // исключение — тоже результат
        .isInstanceOf(InsufficientFundsException.class)
        .hasMessageContaining("баланс");

assertThat(response).as("ответ на POST /orders").returns(201, Response::status);   // описание появится в сообщении об ошибке

assertAll(                                                                      // JUnit: показать ВСЕ несовпадения, а не первое
        () -> assertEquals("Ivan", user.name()),
        () -> assertEquals(30, user.age()));

AssertJ читается как предложение и даёт подробное сообщение: что ожидалось, что получено, какой элемент коллекции лишний. Голый assertTrue(list.contains(x)) при падении скажет только «expected true».

Таблица входов и ожидаемых результатов — лучшая форма для правил с границами. Обязательно проверяйте сами границы: 4999, 5000, 5001; пустое, null, максимальное значение.

@ExtendWith(MockitoExtension.class)                       // создаёт моки и проверяет «лишние» заглушки
class CheckoutServiceTest {
    @Mock PaymentGateway payments;
    @Mock Mailer mailer;
    @InjectMocks CheckoutService checkout;                // соберёт объект через конструктор с моками

    @Test
    void sendsReceiptAfterSuccessfulPayment() {
        when(payments.charge(any(Money.class))).thenReturn(PaymentResult.ok("tx-1"));       // stub

        checkout.pay(order());

        ArgumentCaptor<Receipt> receipt = ArgumentCaptor.forClass(Receipt.class);
        verify(mailer).send(eq("ivan@shop.ru"), receipt.capture());                          // взаимодействие
        assertThat(receipt.getValue().transactionId()).isEqualTo("tx-1");
    }

    @Test
    void doesNotSendReceiptWhenPaymentFails() {
        when(payments.charge(any())).thenThrow(new PaymentDeclinedException());

        assertThatThrownBy(() -> checkout.pay(order())).isInstanceOf(PaymentDeclinedException.class);
        verifyNoInteractions(mailer);
    }
}
Симулятор: как поведёт себя мок
Когда моки вредят Тест, который повторяет реализацию через verify («вызвал A, потом B с такими аргументами»), ломается при любом рефакторинге и не ловит ошибок: он проверяет, как код работает, а не что делает. Мокайте границы системы (сеть, платёжный шлюз, почта, время), а не собственные классы. Value-объекты и чистые функции не мокают вовсе. Для БД лучше настоящая база в контейнере, чем мок репозитория.

23.6Что и как тестировать

УровеньЧто проверяетСколько
Модульныебизнес-правила, расчёты, граничные случаи — без I/O, миллисекундыбольшинство
Интеграционныестыки: SQL-запросы на реальной БД, сериализацию, HTTP-контрактыменьше — на каждый стык
Сквозныеосновные пользовательские сценарии целикомнесколько

Покрытие — не цель

90% покрытия строк не говорит, что проверены нужные случаи: можно вызвать код и ничего не утверждать. Покрытие показывает, что точно не тестируется. Качество тестов измеряет мутационное тестирование (PIT): выживает ли намеренно внесённая ошибка.

Тестируемый дизайн

Трудно написать тест — проблема в коде: скрытые зависимости (new внутри, статика, Instant.now()), смешаны вычисления и ввод-вывод. Внедрение через конструктор и чистые функции делают тесты тривиальными.

Тест на баг

Сначала тест, воспроизводящий ошибку (красный), потом исправление (зелёный). Баг не вернётся незамеченным.

Плавающие тесты

Причины: время, порядок, общие данные, гонки, Thread.sleep вместо ожидания условия (Awaitility). Плавающий тест чинят или удаляют сразу — иначе команда перестаёт верить сборке.

23.7Практикум: пишем и запускаем

Пишем и запускаем настоящие тесты. Из командной строки удобнее всего JUnit Console Launcher — один jar, который находит и запускает тесты; в IDEA те же тесты запускаются зелёной стрелкой рядом с классом. Нужны jar-файлы в lib модуля ch23: JUnit (console standalone), AssertJ, Mockito и его зависимости. Здесь используется JUnit 6 — актуальная версия на момент написания; API Jupiter (org.junit.jupiter.api) в нём тот же, что в JUnit 5, весь код главы работает без изменений.

Код набирайте руками — так он запоминается. Перед запуском запишите предсказание в поле «Ваш прогноз», затем сверьтесь с реальным выводом (снят на JDK 25.0.2; адреса, времена и хэши у вас будут другими). Как подготовить окружение — на странице курса.

    public class Discount {
    /** Скидка: 5% от 1000, 10% от 5000, не больше 1500; для отрицательной суммы — исключение. */
    public static double of(double sum) {
        if (sum < 0) throw new IllegalArgumentException("сумма не может быть отрицательной: " + sum);
        double rate = sum >= 5000 ? 0.10 : sum >= 1000 ? 0.05 : 0;
        return Math.min(sum * rate, 1500);
    }
}

Лаба 23.2Жизненный цикл: экземпляр теста на каждый метод10 мин

Увидеть порядок вызова @BeforeAll, @BeforeEach, тестов и @AfterEach и то, что каждый тест получает новый экземпляр класса.

  1. Создайте файл test/LifecycleTest.java:
    import org.junit.jupiter.api.*;

class LifecycleTest {
    private int counter = 0;

    LifecycleTest() { System.out.println("  конструктор, экземпляр @" + Integer.toHexString(System.identityHashCode(this))); }

    @BeforeAll static void beforeAll() { System.out.println("@BeforeAll (static)"); }
    @BeforeEach void beforeEach(TestInfo info) { System.out.println("  @BeforeEach перед " + info.getDisplayName()); }

    @Test void first() { counter++; System.out.println("    first: counter=" + counter); }
    @Test void second() { counter++; System.out.println("    second: counter=" + counter); }

    @AfterEach void afterEach() { System.out.println("  @AfterEach"); }
    @AfterAll static void afterAll() { System.out.println("@AfterAll (static)"); }
}

    public class CheckoutService {
    public interface PaymentGateway { String charge(String card, long amountCents); }
    public interface Notifier { void receipt(String email, String paymentId); }

    private final PaymentGateway gateway;
    private final Notifier notifier;

    public CheckoutService(PaymentGateway gateway, Notifier notifier) { this.gateway = gateway; this.notifier = notifier; }

    public String checkout(String email, String card, long amountCents) {
        if (amountCents <= 0) throw new IllegalArgumentException("сумма должна быть положительной");
        String paymentId = gateway.charge(card, amountCents);
        notifier.receipt(email, paymentId);
        return paymentId;
    }
}
    import org.junit.jupiter.api.Test;

  2. Уберите из CheckoutService.checkout строку notifier.receipt(...). Какие тесты это заметят?

    Только chargesAndSendsReceipt: verify(notifier).receipt(…) упадёт с «Wanted but not invoked: notifier.receipt(…) — Actually, there were zero interactions with this mock». Остальные три теста зелёные — они проверяют другие сценарии. Тест без verify или assertThat ничего не проверяет: убедитесь, что каждый тест может упасть (поломайте код и посмотрите).

Поэкспериментируйте
  • Замените when(gateway.charge("4242", 1999)) на when(gateway.charge("4242", 2000)). Что произойдёт и почему?
    Мок без подходящей заглушки вернёт значение по умолчанию — null; тест упадёт на isEqualTo("pay-1"). Mockito в строгом режиме (MockitoExtension) ещё и сообщит о «unnecessary stubbing / argument mismatch» — подсказка, что заглушка не совпала с вызовом.

23.8Самопроверка

В тестовом классе поле List<String> items = new ArrayList<>(). Первый тест добавляет в него элемент. Что увидит второй тест?

  • Список с одним элементом
  • Пустой список: JUnit создаёт новый экземпляр класса на каждый тест
  • null
  • Зависит от порядка
Lifecycle.PER_METHOD по умолчанию. Общим было бы static-поле — и это источник зависимых тестов.

Что вернёт метод мока, для которого не задана заглушка и тип результата — Optional<User>?

  • null
  • Исключение
  • Optional.empty()
  • Optional с моком User
Mockito возвращает «пустые» значения: 0, false, пустые коллекции, Optional.empty(); для прочих объектов — null.

Что из перечисленного лучше НЕ мокать?

  • Собственные value-объекты и чистые функции расчёта
  • Клиент платёжного шлюза
  • Отправку почты
  • Источник текущего времени
Мокают границы системы. Замена собственной логики моками проверяет заглушки, а не код.

Покрытие строк 95%. Что это гарантирует?

  • Отсутствие ошибок в покрытом коде
  • Что проверены все граничные случаи
  • Что тесты имеют утверждения
  • Только то, что эти строки выполнялись во время тестов
Выполнение не равно проверке. Тест без assert даёт покрытие и не ловит ничего.
Чем mock отличается от stub и от spy?

Stub подставляет ответы, чтобы код мог выполниться. Mock — объект, на котором проверяют взаимодействие (verify). Spy оборачивает настоящий объект: по умолчанию вызывает реальные методы, позволяет подменить часть и проверить вызовы. В Mockito один объект может играть первые две роли.

Какими свойствами обладает хороший модульный тест?

Быстрый, изолированный, повторяемый, сам проверяет результат, проверяет одно поведение через публичный API, читается как спецификация, не ломается при рефакторинге без изменения поведения, при падении указывает на причину.

Как тестировать код, зависящий от времени и случайности?

Вынести источник наружу и внедрять: Clock вместо Instant.now(), Supplier/RandomGenerator вместо new Random(). В тесте подставить фиксированные значения. Ожидание асинхронного результата — Awaitility с таймаутом, а не sleep.
