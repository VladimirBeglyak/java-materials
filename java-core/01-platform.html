1.1JDK, JRE, JVM

С нуля: переводчик, библиотека и мастерская

Процессоры разных компьютеров понимают разные «языки» машинных команд. Чтобы одну и ту же программу не переписывать под каждый, Java придумала посредника: программу переводят в универсальные команды — байткод, а на каждом компьютере работает свой «переводчик», который исполняет этот байткод. Этот переводчик — JVM. Вместе с набором готовых деталей (стандартной библиотекой) он образует JRE, а добавьте к ним инструменты для создания программ — получится JDK. Как матрёшка: JDK ⊃ JRE ⊃ JVM.

Строго

JVM

Java Virtual Machine — «виртуальная машина Java»: загружает классы, проверяет и исполняет байткод, управляет памятью и потоками. Спецификация (документ с точными правилами) одна, реализаций (программ, выполняющих эти правила) несколько; самая распространённая — HotSpot.

JRE

Java Runtime Environment — «среда выполнения Java»: JVM + стандартная библиотека (готовый код, поставляемый вместе с Java: java.lang, java.util, …). Всё, что нужно для запуска программы. Oracle не выпускает его отдельно с Java 11; у некоторых сборок (Temurin) JRE-вариант остался.

JDK

Java Development Kit — «набор разработчика Java»: JRE + инструменты разработки: компилятор javac, jar, javap, jshell, jcmd, jlink. То, что устанавливает разработчик и что лежит в базовом образе контейнера (шаблоне изолированной среды для запуска программы, например в Docker).

OpenJDK — открытая (с доступным всем исходным кодом) эталонная реализация. Oracle JDK, Eclipse Temurin, Amazon Corretto, Azul Zulu, BellSoft Liberica — это сборки одного и того же кода OpenJDK, отличающиеся сроками поддержки, лицензией (условиями использования) и набором исправлений. Для приложения они взаимозаменяемы.

Главное JVM исполняет байткод, JRE = JVM + стандартная библиотека, JDK = JRE + инструменты разработчика. Oracle JDK, Temurin, Corretto и другие — сборки одного OpenJDK.

1.2От исходника до процессора

  • «Write once, run anywhere» («написал один раз — запускай везде»). Файл .class не зависит от ОС (операционной системы: Windows, Linux, macOS) и процессора: зависима только сама JVM.
  • Прогрев. Первые секунды код исполняется интерпретатором (частью JVM, которая выполняет байткод команда за командой) и работает на порядок (примерно в 10 раз) медленнее. По мере накопления статистики JIT (Just-In-Time — компилятор «точно в срок», работающий прямо во время выполнения) заменяет его машинным кодом — командами, которые процессор понимает напрямую. Отсюда правило: производительность Java-сервиса измеряют после прогрева и специальным инструментом (JMH — Java Microbenchmark Harness, инструмент точных замеров скорости), а не System.nanoTime() вокруг одного вызова. Подробнее — в теме 15.
  • Не только Java. Kotlin, Scala, Groovy (другие языки программирования) компилируются в тот же байткод и работают на той же JVM.
Главное javac переводит .java в .class с байткодом, JVM сначала интерпретирует его, а горячий код JIT компилирует в машинный. Поэтому Java-программа «прогревается», и скорость меряют после прогрева.

1.3Байткод

Байткод — набор команд для стековой машины. Представьте стопку тарелок: команды кладут числа наверх стопки, снимают верхние и кладут результат. У каждого метода (функции внутри класса) есть массив локальных переменных (переменных, объявленных внутри метода) и такая стопка — стек операндов (операнд — то, над чем выполняется операция). Команды кладут значения на стек, снимают их и кладут результат.

static int add(int a, int b) {
    return a + b;
}
static int add(int, int);
  Code:
     0: iload_0        // положить на стек локальную переменную 0 (a)
     1: iload_1        // положить на стек локальную переменную 1 (b)
     2: iadd           // снять два int, положить сумму
     3: ireturn        // вернуть int с вершины стека

Ниже — исходный код и его байткод, который показывает утилита javap -c (Java disassembler — «разборщик» class-файла). Префикс команды указывает тип: i — int, l — long, d — double, a — ссылка. Для byte, short, char и boolean отдельной арифметики нет — на стеке они живут как int, и это объясняет несколько правил языка из темы 02.

Версия формата привязана к версии Java: 52 — Java 8, 55 — Java 11, 61 — Java 17, 65 — Java 21, 69 — Java 25. JVM отказывается загружать класс новее, чем она сама: UnsupportedClassVersionError: class file version 65.0, this version of the Java Runtime only recognizes up to 61.0 означает «собрано под 21, запущено на 17».
Главное Байткод — команды стековой машины: положить на стек, снять, вычислить. Вызовы бывают статические, виртуальные (по реальному типу объекта) и invokedynamic. Версия class-файла привязана к версии Java.

1.4Запуск программы

public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, " + (args.length > 0 ? args[0] : "world"));
    }
}
javac -d out src/Hello.java          # компиляция в каталог out
java -cp out Hello Java              # запуск: classpath + имя класса + аргументы
java -jar app.jar                    # запуск архива; класс берётся из Main-Class в MANIFEST.MF
java Hello.java                      # Java 11+: скомпилировать в память и запустить одной командой

Classpath («путь к классам») — список каталогов и JAR-архивов (Java ARchive — zip-архив со скомпилированными классами), в которых JVM ищет классы. Имя класса com.shop.Order (здесь com.shop — пакет, «папка» для классов) соответствует пути com/shop/Order.class относительно элемента classpath. Класс не найден — ClassNotFoundException или NoClassDefFoundError (разница — в теме 06). Если один класс есть в двух архивах, загрузится тот, что раньше в списке, — источник трудноуловимых конфликтов версий библиотек (чужого готового кода, подключённого к программе).

Java 25: точка входа без церемоний 
void main() {
    IO.println("Hello, world");
}
В «компактном исходном файле» (compact source file) не нужны ни объявление класса, ни public static, ни String[] args. Это упрощение для обучения и скриптов (небольших программ на один раз); в приложениях по-прежнему используют обычные классы.

Важные параметры JVM (их пишут после java при запуске): -Xmx и -Xms — максимальный (max) и начальный (start) размер кучи (heap — памяти, где живут объекты), -Xss — размер стека потока (stack size; памяти для вызовов методов одного потока выполнения), -Dимя=значение — системное свойство (настройка, которую программа может прочитать), -XX:+UseZGC и подобные — выбор сборщика мусора (GC, garbage collector — части JVM, которая сама освобождает память от ненужных объектов; ZGC — один из сборщиков) (тема 14).

Главное Программа запускается с метода main. JVM ищет классы по classpath: имя пакета — путь к файлу. Главные параметры запуска: -Xmx (куча), -Xss (стек), -D (свойства), выбор сборщика мусора.

Так, строковые шаблоны были preview в Java 21–22 и затем отозваны. В рабочий код (production — систему, которой пользуются реальные клиенты) preview-возможности не берут.
Главное Новая Java — каждые полгода, LTS-версия — раз в два года: 8, 11, 17, 21, 25. Промышленные системы работают на LTS, preview-возможности в рабочий код не берут.

1.7Интерактив: стековая машина JVM

JVM — стековая машина: у каждого вызова метода есть свой кадр (frame — рабочая область одного вызова) с массивом локальных переменных и стеком операндов. Инструкции байткода берут операнды со стека и кладут результат обратно. Пройдите по шагам метод calc(3, 4):

int calc(int a, int b) {       //  0: iload_1      5: istore_3
    int c = a + b * 2;         //  1: iload_2      6: iload_3
    return c;                  //  2: iconst_2     7: ireturn
}                              //  3: imul
                               //  4: iadd
Симулятор: выполнение байткода
Локальные переменные кадра
0: this1: a = 32: b = 43: c = —3: c = 11
Стек операндов (вершина справа)
34281111

iload_1

Положить на стек значение локальной переменной №1 (a). Префикс i — тип int; для long было бы lload, для ссылок — aload.

iload_2

На стек — переменная №2 (b). Сложение пока не выполняется: умножение приоритетнее, и компилятор расположил инструкции в нужном порядке.

iconst_2

Константа 2. Для чисел от −1 до 5 есть однобайтовые инструкции iconst_m1 … iconst_5; дальше — bipush, sipush, а большие значения берутся из пула констант (ldc).

imul

Снять два верхних значения (4 и 2), перемножить, положить 8.

iadd

Снять 3 и 8, положить 11. Переполнение int не проверяется — результат молча «заворачивается».

istore_3

Снять вершину стека и записать в локальную переменную №3 (c). Стек пуст.

iload_3

Снова загрузить c — для возврата. JIT-компилятор уберёт лишнюю пару store/load; javac оптимизаций почти не делает.

ireturn

Снять значение со стека, уничтожить кадр и положить результат на стек операндов вызывающего метода. Так значения передаются между методами.

Глубина стека операндов и число локальных переменных вычисляются компилятором и записаны в class-файле (stack=3, locals=4) — JVM выделяет кадр фиксированного размера.

ПодробнееГде хранятся кадры, как они появляются и исчезают при вызовах и исключениях, почему локальные переменные потокобезопасны, а объекты — нет: JVM изнутри, тема 03 «Кадр метода и стек потока».

Лаба 1.3Собираем исполняемый jar руками15 мин

Понять, что jar — это zip с манифестом, и собрать его без Maven/Gradle.

  1. Создайте файл app/com/example/App.java:
    package com.example;

import com.example.util.Greeter;

public class App {
    public static void main(String[] args) {
        System.out.println(Greeter.greet("jar"));
    }
}
    package com.example.util;

public class Greeter {
    public static String greet(String who) { return "Запущено из " + who + "!"; }
}
  2. Компилируем в каталог out (пакеты станут подкаталогами) и упаковываем:
    javac -d out app/com/example/App.java app/com/example/util/Greeter.java
jar --create --file app.jar --main-class com.example.App -C out .
jar --list --file app.jar
java -jar app.jar
    Вывод (JDK 25.0.2)
    META-INF/
META-INF/MANIFEST.MF

Запущено из jar!
  3. Что лежит в META-INF/MANIFEST.MF и как JVM узнала, какой класс запускать?
    jar --extract --file app.jar META-INF/MANIFEST.MF
type META-INF\MANIFEST.MF
    Вывод (JDK 25.0.2)
    Manifest-Version: 1.0

    В bash вместо type — cat META-INF/MANIFEST.MF. Можно и просто открыть app.jar любым архиватором.

    В манифесте строка Main-Class: com.example.App (её добавил флаг --main-class) плюс служебные Manifest-Version и Created-By. java -jar читает манифест и ищет классы только внутри jar — флаг -cp при этом игнорируется. Зависимости указывают строкой Class-Path в манифесте или собирают «толстый» jar.

Поэкспериментируйте
  • Запустите java -cp app.jar com.example.App.
    Работает так же: jar можно использовать как обычный элемент classpath и указать главный класс явно.

1.10Самопроверка

Что создаёт javac из файла Order.java?

  • Машинный код для текущего процессора
  • Платформенно-независимый байткод в файле Order.class
  • Исполняемый файл Order.exe
  • Исходный код на C
Байткод один для всех ОС и процессоров; в машинный код его превращает JVM во время выполнения (интерпретатор и JIT).

Когда JIT компилирует метод в машинный код?

  • При запуске программы, все методы сразу
  • При компиляции javac
  • Во время выполнения, когда метод стал «горячим» по счётчикам вызовов и циклов
  • Только по флагу -XX:+JIT
Сначала код интерпретируется и профилируется; горячие методы компилирует C1, самые горячие — C2 с агрессивными оптимизациями.

Что нужно установить на сервер, чтобы запускать готовое Java-приложение, и что — чтобы разрабатывать?

  • Для запуска достаточно среды выполнения (JVM + библиотеки), для разработки нужен JDK с javac и инструментами
  • Для запуска нужен JDK, для разработки — JRE
  • В обоих случаях только JVM
  • Ничего: байткод исполняет операционная система
JDK = среда выполнения + компилятор и утилиты (javac, jar, jshell, jcmd). Отдельный JRE с Java 11 не выпускается; минимальный образ собирают jlink.

Что нужно установить, чтобы писать программы на Java, а не только запускать?

  • JVM
  • JRE
  • JDK
  • Достаточно браузера
JDK = JRE + инструменты разработчика, в том числе компилятор javac.

Почему Java-программа в первые секунды работает медленнее?

  • Код сначала выполняет интерпретатор, а JIT компилирует горячие места в машинный код постепенно
  • JVM скачивает обновления
  • Байткод сжат
  • Сборщик мусора всегда работает при старте
Это прогрев; скорость меряют после него.
Java — компилируемый или интерпретируемый язык?

И то, и другое. javac компилирует исходный код в байткод. JVM сначала интерпретирует байткод, а часто исполняемые методы JIT-компилятор переводит в машинный код во время работы программы. Поэтому Java переносима, как интерпретируемые языки, и после прогрева быстра, как компилируемые.

Чем JDK отличается от JRE и что нужно в образе контейнера?

JRE — JVM и стандартная библиотека, достаточные для запуска. JDK добавляет инструменты разработки и диагностики. Oracle с Java 11 отдельный JRE не выпускает (у части сборок он есть). В образ кладут либо JDK целиком (удобно — есть jcmd для диагностики), либо урезанную среду, собранную jlink.

Что означает ошибка UnsupportedClassVersionError?

Класс скомпилирован под более новую версию Java, чем JVM, на которой его запускают. Версия формата записана в заголовке файла. Решение — запустить на подходящей JVM либо собрать с флагом --release N под нужную версию.

Почему первые запросы к только что запущенному сервису медленные?

Классы загружаются и инициализируются лениво, при первом обращении; код исполняется интерпретатором, пока JIT не накопит статистику и не скомпилирует горячие методы; заполняются пулы соединений и кэши. Поэтому перед включением экземпляра в балансировку его прогревают, а нагрузочные замеры исключают начальный период.

Чем invokevirtual отличается от invokestatic и почему это важно?

invokestatic вызывает метод, известный при компиляции. invokevirtual выбирает реализацию во время выполнения по фактическому классу объекта — на этом построен полиморфизм. Отсюда правило: статические методы не переопределяются, а скрываются (тема 04).
