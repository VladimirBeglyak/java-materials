Компилятор javac — простыми словами

Многое из того, что мы считаем «возможностями Java», на самом деле делает компилятор, а JVM об этом даже не знает. Разберёмся, через какие этапы проходит код в javac, что такое константы времени компиляции, почему checked-исключения существуют только для компилятора и во что превращается синтаксический сахар.

25.1Этапы компиляции

  1. Разбор — текст режется на слова и собирается в дерево: «это класс, в нём метод, в методе цикл».
  2. Анализ — проверка имён и типов: существует ли такая переменная, можно ли сложить строку с числом, все ли исключения обработаны.
  3. Упрощение — удобные конструкции разворачиваются в простые.
  4. Генерация — запись байткода в .class-файлы.
Главная мысль Разобрать → проверить → упростить → записать байткод.

25.2Константы времени компиляции

Если поле static final и его значение известно при компиляции (static final int MAX = 100), компилятор подставляет само значение во все места, где оно используется. Ловушка: если поменять константу в одной библиотеке, а использующий её код не перекомпилировать, там останется старое значение.

Главная мысль Константы «впечатываются» в использующий код. Поменяли константу — пересоберите всех.

В полной главе: 25.2 Константы времени компиляции

25.3Checked-исключения — только для компилятора

Требование «обработай IOException или объяви throws» проверяет только javac. В байткоде и в JVM разницы между checked и unchecked нет. Поэтому, например, код на Kotlin, где checked-исключений нет вообще, спокойно бросает их, и JVM не возражает.

Главная мысль Checked — правило языка Java, а не JVM.

25.5Мостовые методы

Из-за стирания типов (глава 07) метод compareTo(String) класса, реализующего Comparable<String>, после компиляции не совпадает с ожидаемым compareTo(Object). Чтобы полиморфизм работал, javac тихо добавляет мостовой метод compareTo(Object), который приводит тип и вызывает ваш. Их можно увидеть в стек-трейсах и через javap.

Главная мысль Мостовые методы — «переходники», которые javac добавляет из-за стирания типов.

25.6Процессоры аннотаций

Во время компиляции javac может запустить «помощников» — процессоры аннотаций. Они читают аннотации и генерируют новый код. Так работают Lombok (геттеры, конструкторы), MapStruct (преобразования объектов), генераторы метамоделей для JPA. Генерация при сборке быстрее рефлексии во время работы и проверяется компилятором.

Главная мысль Процессоры аннотаций пишут код за вас прямо во время компиляции.

25.7Настройки компилятора

  • --release 21 — компилировать под конкретную версию Java (и проверить, что используется только её API).
  • -Xlint:all и -Werror — включить все предупреждения и считать их ошибками.
  • -parameters — сохранить имена параметров методов (нужно некоторым фреймворкам).
Главная мысль --release для целевой версии, -Xlint для строгости.

25.9Проверьте себя

Кто проверяет, что checked-исключение обработано?

  • JVM при запуске
  • операционная система
  • только компилятор javac
  • сборщик мусора
В байткоде разницы нет.

Константу MAX = 100 в библиотеке поменяли на 200, а приложение не пересобрали. Что увидит приложение?

  • старое значение 100 — оно было подставлено при компиляции
  • 200
  • ошибку
  • null
Константы «впечатываются» в использующий код.

Во что javac превращает for-each по списку?

  • в стрим
  • в цикл с итератором
  • в рекурсию
  • оставляет как есть
Поэтому и ConcurrentModificationException идёт от итератора.

Как работает Lombok?

  • через рефлексию во время работы
  • это часть JVM
  • правит байткод после запуска
  • как процессор аннотаций во время компиляции
Он подключается к javac и добавляет код.

Зачем javac создаёт мостовые методы?

  • для ускорения
  • для безопасности
  • чтобы полиморфизм работал при стирании типов generics
  • для отладки
Переходник с Object-версии на типизированную.
