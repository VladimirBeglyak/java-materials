ООП: классы, наследование, интерфейсы

Объектная модель Java проста по правилам и коварна в деталях: какой из перегруженных методов будет вызван, в каком порядке инициализируются поля родителя и потомка, почему поле «не переопределяется». Глава разбирает механику, на которой держатся эти правила.

4.1Четыре принципа

Инкапсуляция

Состояние скрыто за методами. Класс сам отвечает за корректность своих данных: поле private, изменение — только через метод, проверяющий инварианты. Геттер и сеттер на каждое поле — не инкапсуляция.

Наследование

Класс получает состояние и поведение родителя и может их дополнить. В Java — один родительский класс и сколько угодно интерфейсов.

Полиморфизм

Код работает с объектом через общий тип, а вызывается реализация фактического класса. shape.area() не знает, круг это или квадрат.

Абстракция

Наружу выставляется только существенное — «что делает», а не «как». В языке выражается интерфейсами и абстрактными классами.

Правило: начинать с самого закрытого уровня и открывать по необходимости. Всё, что public или protected, — обязательство перед пользователями класса, которое нельзя изменить без поломки чужого кода. Частая неожиданность: protected открывает доступ ещё и всему пакету, а наследник из другого пакета может обращаться к такому члену только через ссылку собственного типа.

4.3Конструкторы и порядок инициализации

Создание объекта — строго определённая последовательность. Статическая часть выполняется один раз при первом использовании класса, остальное — при каждом new.

class Parent {
    static { System.out.println("1 static Parent"); }
    { System.out.println("3 поля и блоки Parent"); }
    Parent() {
        System.out.println("4 конструктор Parent");
        init();                                   // вызов переопределяемого метода из конструктора
    }
    void init() { }
}

class Child extends Parent {
    static { System.out.println("2 static Child"); }
    private String name = "child";
    { System.out.println("5 поля и блоки Child"); }
    Child() { System.out.println("6 конструктор Child, name = " + name); }
    @Override void init() { System.out.println("  init() видит name = " + name); }
}

new Child();
1 static Parent
2 static Child
3 поля и блоки Parent
4 конструктор Parent
  init() видит name = null
5 поля и блоки Child
6 конструктор Child, name = child
  1. Статические поля и блоки — сначала родителя, затем потомка, в порядке записи в коде. Один раз на класс.
  2. Память под объект выделена, все поля заполнены значениями по умолчанию (0, false, null).
  3. Инициализаторы полей и блоки родителя, затем тело конструктора родителя.
  4. Инициализаторы полей и блоки потомка, затем тело его конструктора.
Не вызывайте переопределяемые методы из конструктора В примере init() потомка выполнился, когда конструктор родителя ещё не завершён, а поля потомка не инициализированы — метод увидел null. Вызов диспетчеризуется по фактическому классу объекта, а объект уже «потомок», хотя ещё не готов. Из конструктора безопасно вызывать только private, final и static методы.
  • Первая инструкция конструктора — this(...) или super(...). Если её нет, компилятор вставит super(); если у родителя нет конструктора без параметров — ошибка компиляции.
  • Конструктор по умолчанию создаётся, только если в классе нет ни одного конструктора.
  • Java 25: гибкие тела конструкторов. Перед super(...) разрешены инструкции, не обращающиеся к создаваемому объекту, — например, проверка аргументов. Раньше для этого приходилось писать вспомогательные статические методы.

4.4Полиморфизм: переопределение и перегрузка

Что этоПотомок заменяет реализацию метода родителяНесколько методов с одним именем и разными параметрами
СигнатураТа жеРазная
Когда выбирается методПри выполнении, по фактическому классу объектаПри компиляции, по объявленным типам аргументов

Правила переопределения: доступ нельзя сузить (public → protected запрещено); нельзя объявить более широкие проверяемые исключения; final-метод переопределить нельзя. Аннотация @Override обязательна по соглашению: с ней опечатка в сигнатуре станет ошибкой компиляции, а не молча созданным новым методом.

void print(Object o) { System.out.println("Object"); }
void print(String s) { System.out.println("String"); }

Object o = "text";
print(o);        // Object — компилятор видит тип переменной
print("text");   // String
print(null);     // String — выбирается самый специфичный подходящий вариант

Что не является полиморфным

class A {
    String name = "A";
    static String kind() { return "A"; }
    String who() { return "A"; }
}
class B extends A {
    String name = "B";                       // скрывает поле родителя
    static String kind() { return "B"; }     // скрывает статический метод
    @Override String who() { return "B"; }   // переопределяет
}

A x = new B();
x.who();     // "B" — виртуальный вызов
x.name;      // "A" — поле выбирается по типу переменной
x.kind();    // "A" — статический метод тоже; вызывать его через экземпляр — дурной тон
Правило Динамически диспетчеризуются только нестатические, не private методы. Поля, статические и приватные методы привязываются при компиляции по объявленному типу — они скрываются (hiding), а не переопределяются. Это следует из байткода: invokevirtual против invokestatic, invokespecial и getfield (тема 01).

Выбор по умолчанию — интерфейс: он не занимает единственное место родителя и позволяет подменять реализацию (в тестах, через прокси). Абстрактный класс уместен, когда у наследников есть общее состояние или шаблонный алгоритм с изменяемыми шагами.

interface Walker  { default String move() { return "walk"; } }
interface Swimmer { default String move() { return "swim"; } }

class Duck implements Walker, Swimmer {
    @Override public String move() {          // без переопределения — ошибка компиляции
        return Walker.super.move() + " and " + Swimmer.super.move();
    }
}

Правила разрешения: реализация из класса-родителя побеждает любой default; более конкретный интерфейс побеждает более общий; если однозначного победителя нет — класс обязан переопределить метод сам. Ромбовидной проблемы состояния в Java нет, потому что у интерфейсов нет полей.

Скрытая ссылка — источник утечек памяти Экземпляр внутреннего или анонимного класса удерживает внешний объект. Если такой объект передан в долгоживущее место — зарегистрирован слушателем, отдан в пул потоков, положен в статическую коллекцию, — внешний объект не будет собран сборщиком мусора. Правило: вложенный класс объявляйте static, если ему не нужен экземпляр внешнего. Лямбда, в отличие от анонимного класса, захватывает this, только если действительно его использует (тема 10).

4.7Перечисления

enum — полноценный класс с фиксированным набором экземпляров, созданных при загрузке. У него могут быть поля, конструктор, методы и даже своя реализация метода в каждой константе.

enum OrderStatus {
    NEW(false), PAID(false), SHIPPED(false), DELIVERED(true), CANCELLED(true);

    private final boolean terminal;
    OrderStatus(boolean terminal) { this.terminal = terminal; }   // конструктор всегда private
    boolean isTerminal() { return terminal; }
}

OrderStatus s = OrderStatus.valueOf("PAID");      // IllegalArgumentException, если такой константы нет
if (s == OrderStatus.PAID) { }                    // == корректно и безопасно при null: экземпляр единственный
Map<OrderStatus, Integer> counts = new EnumMap<>(OrderStatus.class);   // массив внутри, быстрее HashMap
Set<OrderStatus> open = EnumSet.of(OrderStatus.NEW, OrderStatus.PAID);  // битовая маска
  • Не сохраняйте ordinal() в базу и не стройте на нём логику: добавление константы в середину сдвинет все номера. Храните name() или собственный код. В JPA — @Enumerated(EnumType.STRING).
  • values() каждый раз создаёт новый массив — в горячем коде сохраните его в константу.
  • Singleton через enum — самый надёжный способ: единственность гарантирована JVM, включая сериализацию и рефлексию.
  • switch по enum в форме выражения компилятор проверяет на полноту — забытая константа станет ошибкой компиляции (тема 12).

4.8Композиция вместо наследования

Наследование — самая сильная связь между классами: потомок зависит не только от контракта родителя, но и от деталей его реализации.

class CountingSet<E> extends HashSet<E> {
    int added;
    @Override public boolean add(E e) { added++; return super.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) { added += c.size(); return super.addAll(c); }
}
var set = new CountingSet<String>();
set.addAll(List.of("a", "b", "c"));
set.added;   // 6, а не 3: HashSet.addAll внутри вызывает add() для каждого элемента
class CountingSet<E> {
    private final Set<E> delegate = new HashSet<>();
    private int added;
    boolean add(E e) { added++; return delegate.add(e); }
    boolean addAll(Collection<? extends E> c) { added += c.size(); return delegate.addAll(c); }
}

Наследование оправдано, когда выполняется принцип подстановки Лисков: объект потомка можно использовать везде, где ожидается родитель, и программа останется корректной. «Квадрат — это прямоугольник» в математике верно, а в коде с методами setWidth и setHeight — нет. Чтобы запретить наследование, не рассчитанное на это, класс объявляют final или sealed.

4.9Интерактив: порядок инициализации

// log(s) печатает строку; init(s) печатает её и возвращает
class Parent {
    static { log("1 static Parent"); }
    private String name = init("3 поле Parent");
    { log("4 блок Parent"); }
    Parent() { log("5 конструктор Parent"); describe(); }      // вызов переопределяемого метода!
    void describe() { log("Parent.describe"); }
}
class Child extends Parent {
    static { log("2 static Child"); }
    private String title = init("7 поле Child");
    { log("8 блок Child"); }
    Child() { super(); log("9 конструктор Child"); }
    @Override void describe() { log("6 Child.describe, title = " + title); }
}

Статическая инициализация Parent

Первое использование Child запускает инициализацию класса. Сначала инициализируется суперкласс: его статические поля и блоки выполняются сверху вниз, один раз на загрузчик классов, под блокировкой инициализации (потокобезопасно).

Статическая инициализация Child

Затем статика самого Child. При втором new Child() эти два шага уже не повторятся.

new: память и значения по умолчанию

Выделяется память под весь объект (поля Parent и Child), все поля получают значения по умолчанию: name = null, title = null. Затем вызывается конструктор Child, первой инструкцией которого идёт super().

Инициализаторы экземпляра Parent

Компилятор вставляет инициализаторы полей и блоки в начало каждого конструктора (после вызова super), в порядке их записи в классе.

Тело конструктора Parent — и ловушка

Вызов describe() — виртуальный: объект уже имеет тип Child, поэтому выполняется Child.describe(). Но инициализаторы Child ещё не выполнялись — title == null.

Не вызывайте переопределяемые методы из конструктора: подкласс увидит свои поля неинициализированными. Именно поэтому такие методы делают private или final.

Инициализаторы экземпляра Child

Только после возврата из super() выполняются инициализаторы полей и блоки подкласса.

Тело конструктора Child

Объект готов. Итоговый порядок: статика родителя → статика потомка → (поля и блоки родителя → конструктор родителя) → (поля и блоки потомка → конструктор потомка).

4.10Самопроверка

Класс A объявляет static void hi(), класс B extends A объявляет свой static void hi(). Что вызовет A ref = new B(); ref.hi();?

  • B.hi() — полиморфизм
  • Ошибку компиляции
  • A.hi() — статические методы не переопределяются, а скрываются; выбор по типу ссылки
  • Оба метода
Динамическая диспетчеризация работает только для методов экземпляра. Статический вызов привязывается на этапе компиляции к типу переменной.

Какой метод будет вызван: void print(Object o) или void print(String s) при Object x = "text"; print(x);?

  • print(String) — фактический тип String
  • print(Object) — перегрузка выбирается при компиляции по объявленному типу аргумента
  • Оба по очереди
  • Неоднозначность, ошибка компиляции
Перегрузка (overload) — статическое связывание по типам выражений; переопределение (override) — динамическое по типу объекта.

Когда выбрать абстрактный класс, а не интерфейс?

  • Когда нужно общее состояние (поля) и конструктор для семейства тесно связанных классов
  • Всегда — он быстрее
  • Когда нужно множественное наследование
  • Когда в типе есть default-методы
Интерфейс — контракт без состояния, можно реализовать несколько. Абстрактный класс — частичная реализация с полями; наследовать можно только один.
В каком порядке выполняется инициализация при new Child()?

Статические инициализаторы родителя, затем потомка (если классы ещё не инициализированы). Затем для объекта: поля и блоки родителя → конструктор родителя → поля и блоки потомка → конструктор потомка. До начала этой цепочки все поля уже имеют значения по умолчанию.

Чем перегрузка отличается от переопределения с точки зрения выбора метода?

Перегруженный метод выбирает компилятор по объявленным (статическим) типам аргументов. Переопределённый выбирает JVM во время выполнения по фактическому классу объекта, у которого вызван метод. Поэтому Object o = "s"; print(o) вызовет print(Object), даже если есть print(String).

Можно ли переопределить статический метод? А приватный?

Нет. Статический метод в потомке с той же сигнатурой скрывает родительский: какой будет вызван, определяется типом ссылки при компиляции. Приватный метод потомку не виден — одноимённый метод в потомке является новым, никак не связанным с родительским.

Когда выбрать абстрактный класс, а когда интерфейс?

Интерфейс — когда описывается способность или контракт, который могут реализовать несвязанные классы, и нужна подменяемость. Абстрактный класс — когда у семейства есть общее состояние, конструктор или шаблонный алгоритм. С появлением default-методов интерфейс покрывает большинство случаев; отличие остаётся в состоянии и единственности родителя.

Класс реализует два интерфейса с одинаковым default-методом. Что произойдёт?

Ошибка компиляции, пока класс не переопределит метод сам. В реализации можно вызвать нужную версию через Имя.super.метод(). Конфликта нет, если один интерфейс наследует другой (побеждает более конкретный) или если метод реализован в классе-родителе (класс всегда побеждает интерфейс).

Почему внутренний класс может вызвать утечку памяти?

Нестатический вложенный и анонимный классы хранят неявную ссылку на экземпляр внешнего класса. Пока жив объект внутреннего класса (например, в статическом списке слушателей или в очереди пула потоков), внешний объект и всё, на что он ссылается, недостижимы для сборщика мусора.
