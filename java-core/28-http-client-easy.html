28.1Встроенный HttpClient

С Java 11 в JDK есть java.net.http.HttpClient. Работа в три шага, как отправка письма:

  1. Клиент — почтовое отделение: создаётся один раз на приложение и переиспользуется (он держит пул соединений).
  2. Запрос — письмо: адрес, метод (GET, POST), заголовки, тело. Собирается строителем.
  3. Ответ — код статуса (200 — успех, 404 — не найдено, 500 — ошибка сервера) и тело.

Обязательно задавайте таймауты — на соединение и на ответ. Без них зависший чужой сервис будет держать ваши потоки бесконечно.

Главная мысль Один клиент на приложение, запрос через строитель, всегда — таймауты.

28.2Асинхронный вызов

Обычный вызов (send) ждёт ответа — поток стоит. Асинхронный (sendAsync) сразу возвращает «обещание» (CompletableFuture), а ответ придёт потом — можно сразу отправить несколько запросов параллельно и дождаться всех. Как заказать еду в трёх ресторанах одновременно, а не по очереди. С виртуальными потоками (Java 21) часто проще писать обычный блокирующий код — ожидание там почти ничего не стоит.

Три запроса: по очереди и параллельно
по очереди: цены (200 мс) → склад (300 мс) → доставка (250 мс)
итого ≈ 750 мсасинхронно: отправили все три сразу
ждём, пока придут все ответыитого ≈ 300 мс — время самого медленного
важно: таймаут и обработка ошибки для каждого

Времена складываются.

Запросы независимы — отправляем сразу.

Общее время равно самому медленному ответу.

Главная мысль Независимые запросы — параллельно: асинхронно или в виртуальных потоках.

28.3Spring RestClient

В Spring-приложениях удобнее RestClient (Spring 6.1+): цепочка вызовов «метод → адрес → получить → превратить в объект», а JSON автоматически превращается в ваши классы через Jackson. Он также встраивается в наблюдаемость Spring (метрики, трассировка). Старый RestTemplate остался для совместимости, а WebClient нужен в реактивных приложениях.

Главная мысль В Spring — RestClient: коротко, с JSON «из коробки».

28.4Какой клиент выбрать

СитуацияВыбор
Без Spring, простая утилитаjava.net.http.HttpClient
Spring-приложение, обычный кодRestClient
Реактивное приложение (WebFlux)WebClient
Много однотипных вызовов одного APIдекларативный клиент (интерфейс с аннотациями @HttpExchange)

В любом случае: таймауты, обработка ошибочных кодов, повтор только для безопасных (идемпотентных) запросов.

Главная мысль Без Spring — HttpClient, со Spring — RestClient. Таймауты и обработка ошибок — всегда.

28.6Проверьте себя

Сколько экземпляров HttpClient создавать?

  • на каждый запрос новый
  • один на приложение и переиспользовать
  • по одному на поток
  • не создавать
Он держит пул соединений.

Что будет без таймаутов, если чужой сервис завис?

  • запрос сам отменится через секунду
  • Java перезапустится
  • ничего страшного
  • ваши потоки будут ждать бесконечно, и сервис может встать
Зависание соседа становится вашим.

Три независимых запроса по 200, 300 и 250 мс отправили параллельно. Сколько примерно ждать?

  • ~300 мс
  • ~750 мс
  • ~200 мс
  • ~50 мс
Время самого медленного.

Что означает код ответа 503?

  • всё хорошо
  • не найдено
  • ошибка на стороне сервера (сервис недоступен)
  • нет доступа
5xx — проблема сервера; такие запросы иногда имеет смысл повторить.

Какой клиент обычно выбирают в новом Spring-приложении без реактивности?

  • RestTemplate
  • RestClient
  • WebClient
  • HttpURLConnection
Современный и удобный.
