Исключения

Исключение — способ сообщить об ошибке так, чтобы её нельзя было случайно проигнорировать. Механизм прост, но именно в обработке ошибок рождается большинство инцидентов: проглоченное исключение, потерянная причина, незакрытый ресурс.

Современная практика: непроверяемые по умолчанию Проверяемые исключения задумывались как способ заставить обработать ошибку, но на практике приводят к пустым catch и «протекающим» сигнатурам: низкоуровневый SQLException всплывает через пять слоёв. Spring, Hibernate и большинство современных библиотек используют непроверяемые исключения; проверяемые оставляют для случаев, когда вызывающий действительно может и должен отреагировать. Кроме того, они плохо сочетаются с лямбдами (тема 10).

ClassNotFoundException и NoClassDefFoundError. Первое — проверяемое исключение: класс запросили по имени во время выполнения (Class.forName), и его нет в classpath. Второе — ошибка: класс был при компиляции, а при выполнении отсутствует или его статическая инициализация ранее завершилась исключением (тогда первым в логе будет ExceptionInInitializerError, и искать нужно его).

6.2try, catch, finally

try {
    process(file);
} catch (FileNotFoundException e) {          // сначала более конкретный тип,
    log.warn("Файл не найден: {}", file);
} catch (IOException | TimeoutException e) { // затем общий; multi-catch — для одинаковой обработки
    throw new ImportException("Не удалось обработать " + file, e);
} finally {
    cleanup();                               // выполняется при любом исходе
}
  • Порядок catch: от частного к общему. Обратный порядок — ошибка компиляции (недостижимый код).
  • finally выполняется после нормального завершения, после return, после исключения. Не выполнится только при System.exit, аварийной остановке JVM или бесконечном цикле в try.
static int a() {
    try { return 1; } finally { return 2; }        // 2 — и любое исключение из try будет молча потеряно
}
static int b() {
    int x = 1;
    try { return x; } finally { x = 2; }           // 1 — возвращаемое значение уже вычислено и сохранено
}
static StringBuilder c() {
    var sb = new StringBuilder("a");
    try { return sb; } finally { sb.append("b"); } // "ab" — сохранена ссылка, объект изменён
}
Никогда не пишите return и throw в finally Они отменяют всё, что произошло в try: и возвращаемое значение, и летящее исключение. Ошибка исчезает бесследно.

6.3try-with-resources

Всё, что нужно закрывать, — файлы, соединения, потоки ввода-вывода — реализует AutoCloseable. Конструкция try (...) гарантирует вызов close() и правильно обрабатывает ошибки самого закрытия.

Connection conn = null;
try {
    conn = dataSource.getConnection();
    work(conn);                        // бросило SQLException A
} finally {
    if (conn != null) conn.close();    // бросило SQLException B — A потеряно навсегда
}
try (Connection conn = dataSource.getConnection();
     PreparedStatement ps = conn.prepareStatement(sql)) {
    work(ps);
}   // закрытие в обратном порядке: сначала ps, затем conn
  • Порядок закрытия обратен порядку открытия.
  • Подавленные исключения. Если тело бросило исключение, а close() — ещё одно, наружу летит исключение из тела, а второе прикрепляется к нему и доступно через getSuppressed(). В стектрейсе оно помечено Suppressed:.
  • Files.lines(), Files.walk() и другие стримы поверх ресурсов тоже нужно закрывать через try-with-resources (тема 13).

6.4Свои исключения и перевод между слоями

public class OrderNotFoundException extends RuntimeException {
    private final long orderId;
    public OrderNotFoundException(long orderId) {
        super("Заказ не найден: id=" + orderId);     // сообщение с контекстом
        this.orderId = orderId;
    }
    public long orderId() { return orderId; }
}

try {
    return jdbc.queryForObject(sql, mapper, id);
} catch (EmptyResultDataAccessException e) {
    throw new OrderNotFoundException(id);           // перевод на язык предметной области
} catch (DataAccessException e) {
    throw new StorageException("Ошибка чтения заказа " + id, e);   // причина сохранена
}
  • Каждый слой говорит на своём языке. Сервис не должен знать о SQLException; контроллер — о деталях хранилища.
  • Причину передают всегда — вторым аргументом конструктора. Без неё в логе останется «Ошибка чтения заказа» без единого намёка, что именно сломалось.
  • Стандартные исключения для нарушений контракта: IllegalArgumentException — плохой аргумент, IllegalStateException — объект не в том состоянии, UnsupportedOperationException — операция не поддерживается, NullPointerException — через Objects.requireNonNull(x, "x").
Исключения дороги — не для обычного хода программы При создании исключения JVM обходит стек вызовов и сохраняет его (fillInStackTrace) — это на порядки дороже обычного возврата из метода, и чем глубже стек, тем дороже. Проверять «есть ли пользователь» через try/catch в цикле на миллион итераций нельзя. Для ожидаемых ситуаций — Optional, пустая коллекция или результат-объект. Там, где исключение всё же служит сигналом на горячем пути, стектрейс отключают четвёртым параметром конструктора (writableStackTrace = false).

Где перехватывать Исключение ловят там, где с ним можно что-то сделать: повторить, подставить запасное значение, преобразовать в ответ пользователю. В типичном сервисе таких мест немного — граница системы (@RestControllerAdvice, обработчик сообщения из очереди, планировщик) и точки интеграции с внешними системами. Весь код между ними исключения не перехватывает.

6.7Интерактив: поток управления try / catch / finally

static int run() {
    try (Res r = new Res()) {          // Res.close() печатает "close" и может бросить исключение
        print("try");
        /* A: здесь может быть исключение или return 1 */
    } catch (IllegalStateException e) {
        print("catch");
        /* B: здесь может быть новое исключение или return 2 */
    } finally {
        print("finally");
        /* C: здесь может быть return 3 или исключение */
    }
    print("after");
    return 0;
}
Симулятор: что напечатает и что вернёт run()

Попробуйте: (1) A = исключение, C = return 3 — исключение исчезает без следа; поэтому return и throw в finally считаются ошибкой. (2) A = исключение и close() бросает — второе не теряется, а прикрепляется как suppressed. (3) A = return 1 — finally всё равно выполняется.

6.8Самопроверка

Чем checked-исключения отличаются от unchecked?

  • Checked быстрее
  • Unchecked нельзя ловить
  • Checked компилятор заставляет обработать или объявить в throws; unchecked (RuntimeException и Error) — нет
  • Checked наследуют Error
Checked — для ожидаемых ситуаций, из которых вызывающий может восстановиться (IOException). Unchecked — ошибки программирования и нарушения контракта.

В каком порядке закрываются ресурсы в try (A a = …; B b = …)?

  • a, затем b
  • b, затем a — в обратном порядке объявления
  • Одновременно
  • Порядок не определён
Как стек: последний открытый закрывается первым — он может зависеть от предыдущих.

Что плохого в catch (Exception e) { log.error("failed"); }?

  • Теряется стектрейс и причина, ошибка проглочена, выполнение продолжается в некорректном состоянии
  • Exception нельзя ловить
  • Ничего плохого
  • Нужен ещё finally
Минимум — log.error("failed", e) и осмысленная реакция: проброс, обёртка с причиной (new MyException("…", e)) или обоснованное восстановление.
Чем проверяемые исключения отличаются от непроверяемых и когда какие использовать?

Проверяемые (наследники Exception, кроме RuntimeException) компилятор требует перехватить или объявить. Они подходят для ожидаемых сбоев, на которые вызывающий может отреагировать. Непроверяемые — для ошибок программирования и нарушений контракта. В современном коде по умолчанию выбирают непроверяемые, а внешние проверяемые оборачивают на границе слоя.

Что вернёт метод try { return 1; } finally { return 2; } и что в нём опасно?

2. return в finally заменяет результат блока try — и точно так же уничтожает любое исключение, вылетевшее из try: метод вернётся нормально, будто ошибки не было.

Что такое подавленное исключение?

Исключение, возникшее при автоматическом закрытии ресурса, когда тело try уже бросило другое. Основным остаётся исключение из тела, а исключение из close() добавляется к нему и доступно через getSuppressed(). В ручном finally произошло бы обратное: исключение закрытия вытеснило бы исходное.

В логе NoClassDefFoundError: Could not initialize class com.shop.Config, хотя класс в архиве есть. В чём причина?

Статическая инициализация класса при первом обращении завершилась исключением — в логе раньше должен быть ExceptionInInitializerError с настоящей причиной (например, не найден файл настроек). После неудачной инициализации класс помечается непригодным, и все последующие обращения дают эту ошибку.

Почему нельзя перехватывать Throwable?

Вместе с исключениями будут перехвачены Error: нехватка памяти, переполнение стека, ошибки загрузки классов. После них состояние JVM может быть неконсистентным, и продолжение работы приводит к повреждению данных или зависанию. Исключение — самый верх потока-воркера, где ошибку логируют и корректно завершают работу.

Почему исключения нельзя использовать для управления обычным ходом программы?

Создание исключения требует обхода и сохранения стека вызовов, что намного дороже обычного возврата; оно скрывает логику («переход» не виден в сигнатуре); мешает оптимизациям JIT. Ожидаемые исходы — «не найдено», «невалидно» — выражают возвращаемым значением: Optional, результатом-объектом, пустой коллекцией.
