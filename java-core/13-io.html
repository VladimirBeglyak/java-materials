I/O, NIO, сериализация

Ввод-вывод в Java — три поколения API: потоки байтов и символов из java.io, каналы и буферы из java.nio и удобный класс Files. Нужно понимать, чем байты отличаются от символов, зачем нужна буферизация и почему встроенную сериализацию объектов считают ошибкой проектирования.

13.1Байтовые и символьные потоки

Мост между нимиInputStreamReader и OutputStreamWriter — превращают байты в символы по заданной кодировке

Классы java.io построены по шаблону «декоратор»: каждый оборачивает другой поток и добавляет одну возможность.

try (var reader = new BufferedReader(                 // + буфер и readLine()
        new InputStreamReader(                        // байты → символы
            new GZIPInputStream(                      // + распаковка
                new FileInputStream("data.csv.gz")),  // источник байтов
            StandardCharsets.UTF_8))) {
    String line;
    while ((line = reader.readLine()) != null) process(line);
}   // закрытие внешнего потока закрывает всю цепочку
Две обязательные вещи
  • Кодировка — всегда явно. new FileReader(file) и new InputStreamReader(in) без кодировки берут системную; до Java 18 она зависела от ОС (тема 03).
  • Закрытие — только через try-with-resources. Незакрытый поток — утечка файлового дескриптора; через некоторое время процесс получит Too many open files (тема 06).

13.2Буферизация

Вызов read() у FileInputStream — системный вызов: переход в ядро ОС ради одного байта. Чтение мегабайтного файла побайтно — миллион таких переходов.

try (var in = new FileInputStream(file)) {
    int b;
    while ((b = in.read()) != -1) { … }       // системный вызов на каждый байт
}
try (var in = new BufferedInputStream(new FileInputStream(file))) {
    int b;
    while ((b = in.read()) != -1) { … }       // читает из буфера 8 КБ; обращение к ОС — раз в 8192 байта
}
try (var in = Files.newInputStream(path); var out = Files.newOutputStream(target)) {
    in.transferTo(out);                        // Java 9: скопировать поток целиком
}
byte[] all = in.readAllBytes();                // Java 9: только для заведомо небольших данных

Для записи действует то же самое, плюс обязанность сбросить буфер: данные в BufferedWriter попадают в файл при заполнении буфера, flush() или закрытии. Забытое закрытие — усечённый файл.

13.3Files и Path

Класс java.nio.file.Files (Java 7, дополнен в 11) закрывает большинство повседневных задач одной строкой и сообщает об ошибках исключениями с понятной причиной — в отличие от java.io.File, методы которого возвращают false без объяснений.

Path path = Path.of("data", "orders.csv");                      // вместо new File(...)

String text = Files.readString(path);                           // UTF-8 по умолчанию — у Files так было всегда
List<String> lines = Files.readAllLines(path);                  // весь файл в память
Files.writeString(path, text, StandardOpenOption.CREATE, StandardOpenOption.APPEND);

try (Stream<String> stream = Files.lines(path)) {               // лениво, построчно — для больших файлов
    long errors = stream.filter(l -> l.contains("ERROR")).count();
}                                                               // стрим держит открытый файл — закрывать обязательно

try (Stream<Path> tree = Files.walk(dir)) {                     // обход дерева каталогов
    tree.filter(Files::isRegularFile).filter(p -> p.toString().endsWith(".log")).forEach(this::archive);
}

Files.createDirectories(dir);
Files.copy(src, dst, StandardCopyOption.REPLACE_EXISTING);
Files.move(tmp, target, StandardCopyOption.ATOMIC_MOVE);
Атомарная запись файла Если процесс упадёт посреди записи, файл останется наполовину записанным, и читатель получит мусор. Надёжный приём: записать во временный файл в том же каталоге, затем переименовать с ATOMIC_MOVE. Переименование в пределах одной файловой системы атомарно: читатели видят либо старую версию, либо новую целиком.

Большие файлы читают потоково — Files.lines, BufferedReader, InputStream с буфером. readAllBytes и readAllLines на файле в несколько гигабайт закончатся OutOfMemoryError.

13.4NIO: каналы и буферы

В java.nio данные читаются не «из потока по байту», а блоками в буфер через канал. Это ближе к тому, как работает ОС, и открывает три возможности: память вне кучи, передачу без копирования и неблокирующий режим.

try (FileChannel in = FileChannel.open(src, StandardOpenOption.READ);
     FileChannel out = FileChannel.open(dst, StandardOpenOption.CREATE, StandardOpenOption.WRITE)) {

    ByteBuffer buf = ByteBuffer.allocateDirect(64 * 1024);
    while (in.read(buf) != -1) {         // канал ЗАПИСЫВАЕТ в буфер
        buf.flip();                      // буфер готов к чтению
        while (buf.hasRemaining()) out.write(buf);
        buf.clear();                     // буфер готов к записи
    }

}
// альтернатива циклу: in.transferTo(0, in.size(), out) — ОС копирует сама, минуя память приложения (zero-copy)

В прикладном коде каналы и селекторы почти не встречаются напрямую — ими пользуются фреймворки. Как устроена неблокирующая сеть — в «Компьютерных сетях», тема 12. С появлением виртуальных потоков обычный блокирующий код снова масштабируется на тысячи соединений (Java Concurrency, тема 10).

13.5Сериализация Java

Встроенный механизм превращает граф объектов в поток байтов и обратно. Чтобы класс участвовал, достаточно реализовать маркерный интерфейс Serializable.

class Session implements Serializable {
    @Serial private static final long serialVersionUID = 1L;

    private final String userId;
    private transient String token;      // transient — не сохраняется; после чтения будет null
    private static int created;          // static — принадлежит классу, в поток не попадает
}

try (var out = new ObjectOutputStream(Files.newOutputStream(path))) { out.writeObject(session); }
try (var in = new ObjectInputStream(Files.newInputStream(path))) { var s = (Session) in.readObject(); }
ВопросОтвет
Вызывается ли конструктор при чтении?Нет. Объект создаётся в обход конструктора и инициализаторов полей; вызывается только конструктор без параметров ближайшего несериализуемого предка. Проверки из конструктора не выполняются
Зачем serialVersionUID?Версия формата класса. При несовпадении — InvalidClassException. Если не объявить, вычисляется из структуры класса, и любое изменение (даже добавление метода) делает старые данные нечитаемыми
Поле несериализуемого типа?NotSerializableException при записи; помечают transient
Как сохранить единственность синглтона?Метод readResolve(), возвращающий существующий экземпляр; либо enum
Как управлять форматом?Приватные writeObject/readObject или интерфейс Externalizable
Почему её не используют в новом коде
  • Безопасность. Чтение потока создаёт объекты произвольных классов из classpath и вызывает их методы. Цепочки таких вызовов («гаджеты») в популярных библиотеках позволяли выполнить произвольный код на сервере, принявшем данные от недоверенного источника. Это целый класс уязвимостей; главный архитектор Java назвал сериализацию «ужасной ошибкой».
  • Хрупкость. Формат — это приватные поля класса. Любой рефакторинг ломает совместимость с ранее записанными данными.
  • Обход инвариантов. Конструктор не вызывается — можно получить объект в состоянии, которое код создать не позволяет.
  • Только Java. Другой язык эти данные не прочитает.

Что использовать: JSON (Jackson) для API и конфигурации; Protobuf или Avro со схемой — для сообщений и хранения. Если сериализация Java неизбежна (старые протоколы, некоторые кэши), ограничьте допустимые классы фильтром ObjectInputFilter и никогда не десериализуйте данные из недоверенного источника. Записи сериализуются безопаснее: объект восстанавливается через канонический конструктор со всеми проверками.

13.6Интерактив: ByteBuffer — position, limit, capacity

Главная трудность NIO — один и тот же буфер используется и для записи, и для чтения, а режим переключается вручную. Три указателя: capacity (размер, не меняется), limit (граница доступного), position (следующая ячейка).

Симулятор ByteBuffer.allocate(8)
ByteBuffer buf = ByteBuffer.allocateDirect(64 * 1024);
while (in.read(buf) != -1) {        // канал ПИШЕТ в буфер
    buf.flip();                     // → режим чтения
    while (buf.hasRemaining()) out.write(buf);   // канал ЧИТАЕТ из буфера; write может записать не всё
    buf.clear();                    // → режим записи
}
// На практике проще: Files.copy(src, dst) или in.transferTo(out) — без копирования через пользовательскую память.

13.7Самопроверка

Зачем нужен BufferedInputStream поверх FileInputStream?

  • Он шифрует данные
  • Чтение по одному байту без буфера — системный вызов на каждый байт; буфер читает блоками по 8 КБ
  • Он нужен для текстовых файлов
  • Без него файл нельзя закрыть
Системный вызов стоит сотни наносекунд–микросекунды. Буферизация сокращает их число на три порядка.

Что делает flip() у ByteBuffer?

  • Разворачивает порядок байтов
  • Очищает буфер
  • Устанавливает limit = position и position = 0: переключает буфер с записи на чтение
  • Удваивает ёмкость
Забытый flip — самая частая ошибка NIO: чтение начнётся с текущей позиции и вернёт мусор или ничего.

Почему встроенная сериализация Java (Serializable) считается опасной?

  • Десериализация недоверенных данных позволяет выполнить произвольный код через цепочки гаджетов; формат хрупок к изменениям классов
  • Она слишком медленная для любых задач
  • Она не поддерживает коллекции
  • Она удалена из JDK
Для обмена данными используют JSON, Protobuf, Avro. Если Serializable неизбежна — ObjectInputFilter и serialVersionUID.
Чем InputStream отличается от Reader и как перейти от одного к другому?

InputStream читает байты, Reader — символы. Переход — InputStreamReader, которому передают кодировку: он декодирует последовательность байтов в символы. Без явной кодировки результат зависит от окружения.

Почему чтение файла через FileInputStream.read() в цикле медленное?

Каждый вызов — системный вызов и переход в ядро ради одного байта. BufferedInputStream читает блоками по 8 КБ и отдаёт байты из памяти; количество системных вызовов сокращается в тысячи раз.

Что делает flip() у ByteBuffer?

Переключает буфер из режима записи в режим чтения: limit становится равным текущей position (конец записанных данных), а position — нулю. Без него чтение начнётся с места, где закончилась запись, и вернёт пустоту или мусор.

Как записать файл так, чтобы читатели никогда не увидели его наполовину записанным?

Записать во временный файл в том же каталоге, закрыть его и переименовать в целевое имя с StandardCopyOption.ATOMIC_MOVE. Переименование внутри одной файловой системы атомарно.

Вызывается ли конструктор при десериализации объекта?

Конструктор самого сериализуемого класса — нет; поля заполняются напрямую из потока, а transient-поля получают значения по умолчанию. Вызывается конструктор без параметров первого несериализуемого класса в цепочке предков. Поэтому проверки из конструктора не защищают от некорректных данных в потоке.

Почему встроенная сериализация опасна?

При чтении создаются объекты любых доступных классов и выполняется их код (readObject, readResolve, а затем hashCode, compare и т. п.). Специально составленный поток запускает цепочку вызовов, приводящую к выполнению произвольных команд. Защита — не принимать сериализованные объекты извне и использовать форматы данных без исполняемого поведения.
