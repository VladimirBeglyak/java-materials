23.1Анатомия теста: дано — когда — тогда

Хороший тест читается как короткая история:

  1. Дано (given) — подготовка: корзина с двумя товарами по 100 рублей и скидкой 10%.
  2. Когда (when) — одно действие: посчитать итог.
  3. Тогда (then) — проверка: итог равен 180.

Один тест — одна проверяемая мысль. Имя теста описывает поведение: «скидка применяется к сумме корзины».

Главная мысль Дано → одно действие → проверка. Имя теста — описание поведения.

23.2Как JUnit 5 запускает тесты

JUnit находит методы с аннотацией @Test и запускает каждый. Для каждого теста создаётся новый объект тестового класса — тесты не должны зависеть друг от друга и от порядка. Общую подготовку выносят в метод с @BeforeEach (перед каждым тестом), тяжёлую — в @BeforeAll (один раз на класс).

Главная мысль Каждый тест независим и получает свежий экземпляр класса.

23.3Понятные проверки: AssertJ

AssertJ позволяет писать проверки почти как предложения: assertThat(order.total()).isEqualTo(180), assertThat(list).hasSize(3).contains("кот"). А главное — при падении он показывает понятное сообщение: что ожидали и что получили. Исключения проверяют через assertThatThrownBy.

Главная мысль assertThat(…) читается как текст и даёт понятное сообщение при ошибке.

23.4Один тест — много данных

Нужно проверить функцию на десяти наборах данных? Не копируйте тест десять раз. Параметризованный тест (@ParameterizedTest) — один тест и таблица входов и ожидаемых результатов. Удобно для граничных случаев: 0, отрицательное, пустая строка, очень большое число.

Главная мысль Много похожих случаев — один параметризованный тест.

23.5Дублёры: Mockito

В кино опасные трюки выполняет дублёр. В тестах «дублёры» заменяют базу, платёжный шлюз, почту — всё медленное, ненадёжное или внешнее.

Заглушка (stub)

Отвечает заготовленным ответом: «когда спросят клиента 42 — верни Ивана».

Мок с проверкой (verify)

Проверяет, что его вызвали правильно: «письмо отправлено ровно один раз на этот адрес».

Осторожно: если замокать всё подряд, тест проверяет лишь то, что код вызывает моки, а не то, что он работает. Мокайте внешние границы, а не свои простые классы.

Главная мысль Мокайте внешнее и медленное. Слишком много моков — тест ничего не проверяет.

23.6Что и как тестировать

  • Пирамида тестов: много быстрых юнит-тестов, меньше интеграционных (с настоящей базой, например в Testcontainers), совсем немного сквозных.
  • Тестируйте поведение, а не внутренности: тест не должен ломаться от рефакторинга.
  • Граничные случаи: пусто, ноль, максимум, null.
  • Найден баг — сначала тест, который его воспроизводит, потом исправление.
Главная мысль Много быстрых тестов на поведение, граничные случаи — обязательно.

23.8Проверьте себя

Из каких частей состоит хороший тест?

  • из одного assert
  • из логов
  • дано → действие → проверка
  • из main
Given / When / Then.

Может ли один тест зависеть от результата другого?

  • не должен: тесты независимы, порядок не гарантирован
  • да, так и задумано
  • только в JUnit 4
  • только если они в одном классе
Каждый тест получает свежий экземпляр класса.

Что заменять моками?

  • всё подряд
  • сам тестируемый класс
  • строки и числа
  • внешние и медленные зависимости: платёжный шлюз, почту
Иначе тест проверяет только вызовы моков.

Нужно проверить функцию на 15 наборах входов. Как лучше?

  • 15 копий теста
  • параметризованный тест
  • цикл с println
  • не проверять
Один тест и таблица данных.

Вы нашли баг. Что сделать первым?

  • сразу исправить
  • удалить связанные тесты
  • написать тест, который воспроизводит баг, затем исправить
  • добавить лог
Тест гарантирует, что баг не вернётся.
