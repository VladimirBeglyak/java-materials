Generics и стирание типов

Обобщённые типы переносят ошибки приведения из времени выполнения во время компиляции. Но существуют они только для компилятора: в байткоде параметров типов нет. Это одно решение объясняет все странности — от запрета new T() до правила PECS.

7.1Зачем нужны generics

List names = new ArrayList();
names.add("Alice");
names.add(42);                            // компилятор не возражает
String first = (String) names.get(0);     // приведение вручную
String second = (String) names.get(1);    // ClassCastException — далеко от места ошибки
List<String> names = new ArrayList<>();
names.add("Alice");
names.add(42);                            // не компилируется
String first = names.get(0);              // приведение вставит компилятор
class Box<T> {                                         // параметр типа класса
    private final T value;
    Box(T value) { this.value = value; }
    T get() { return value; }
    <R> Box<R> map(Function<? super T, ? extends R> f) { // параметр типа метода
        return new Box<>(f.apply(value));
    }
}

// ограничение сверху: T обязан быть сравнимым
static <T extends Comparable<? super T>> T max(Collection<? extends T> items) { … }
// несколько ограничений через &
static <T extends Number & Comparable<T>> T clamp(T v, T lo, T hi) { … }

7.2Стирание типов

Чтобы новый код работал со старыми библиотеками, generics реализовали стиранием: компилятор проверяет типы, а затем заменяет каждый параметр типа его верхней границей (Object, если границы нет) и вставляет приведения. JVM о параметрах типов не знает.

List<String> list = new ArrayList<>();
list.add("x");
String s = list.get(0);

class Box<T extends Number> {
    T value;
}
List list = new ArrayList();
list.add("x");
String s = (String) list.get(0);

class Box {
    Number value;
}
// true: при выполнении класс один — ArrayList
new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass();

Мостовые методы class Money implements Comparable<Money> объявляет compareTo(Money), но после стирания интерфейс требует compareTo(Object). Компилятор сам добавляет синтетический bridge-метод compareTo(Object o) { return compareTo((Money) o); }. Его видно в javap и в стектрейсах; из-за него рефлексия иногда возвращает «лишний» метод.
Где информация о типах всё-таки сохраняется Стирается тип у объектов. Но объявления — поля, параметры и возвращаемые типы методов, указание суперкласса — записаны в class-файле полностью и доступны через рефлексию (getGenericType, getGenericSuperclass). На этом основан приём «super type token»: анонимный подкласс фиксирует параметр типа в своём объявлении. 
List<Order> orders = mapper.readValue(json, new TypeReference<List<Order>>() { });   // Jackson
// то же — ParameterizedTypeReference в Spring RestClient
Именно поэтому Spring умеет внедрить List<PaymentHandler>, а Jackson — разобрать поле Map<String, List<Item>>.

7.3Инвариантность

Integer — подтип Number, но List<Integer> — не подтип List<Number>. Если бы это было разрешено, типобезопасность сломалась бы:

List<Integer> ints = new ArrayList<>();
List<Number> nums = ints;       // предположим, это компилируется
nums.add(3.14);                 // Double — это Number, всё законно
Integer i = ints.get(0);        // ClassCastException: в списке Integer лежит Double

Массивы устроены иначе — они ковариантны — и расплачиваются проверкой при каждой записи:

Integer[] ints = new Integer[1];
Number[] nums = ints;           // компилируется
nums[0] = 3.14;                 // ArrayStoreException при выполнении

Отсюда совет: не смешивать массивы и generics, предпочитать коллекции.

7.4Wildcards и правило PECS

Инвариантность слишком строга: метод суммирования чисел должен принимать и List<Integer>, и List<Double>. Гибкость возвращают подстановочные типы — ценой ограничения операций.

ОбъявлениеПринимаетЧтениеЗаписьРоль
List<? extends Number>List<Number>, List<Integer>, List<Double>как NumberнельзяProducer — источник данных
List<? super Integer>List<Integer>, List<Number>, List<Object>как ObjectIntegerConsumer — приёмник данных
List<?>Любой списоккак ObjectнельзяТип элементов не важен

Почему в List<? extends Number> нельзя писать: это может быть List<Integer>, а может List<Double> — компилятор не знает, какой именно, и не может проверить ни одно добавление.

PECS: Producer Extends, Consumer Super Если параметр только отдаёт элементы — ? extends T. Если только принимает — ? super T. Если и то и другое — точный тип T. 
static double sum(Collection<? extends Number> src) {       // из src читаем
    double total = 0;
    for (Number n : src) total += n.doubleValue();
    return total;
}
static void fill(List<? super Integer> dst, int n) {        // в dst пишем
    for (int i = 0; i < n; i++) dst.add(i);
}
// классика из JDK: источник — extends, приёмник — super
public static <T> void copy(List<? super T> dest, List<? extends T> src)

Тем же правилом объясняются сигнатуры стандартной библиотеки: Comparator<? super T> — компаратор потребляет элементы, значит, компаратор для Object годится для сортировки строк; Function<? super T, ? extends R> — потребляет T, производит R. Wildcards пишут в параметрах методов и никогда — в возвращаемом типе: вызывающему придётся с ними бороться.

List<Object>List<?>List (сырой тип)

7.5Сырые типы и загрязнение кучи

Сырой тип (List без параметра) оставлен для совместимости и отключает проверки. Через него в коллекцию попадает объект чужого типа, а исключение возникает позже и в другом месте — там, где компилятор вставил приведение. Это называется heap pollution.

List<String> strings = new ArrayList<>();
List raw = strings;                 // предупреждение unchecked, но компилируется
raw.add(42);
// … сотни строк спустя, возможно в другом классе:
String s = strings.get(0);          // ClassCastException — в строке, где нет ни одного приведения
  • Предупреждения unchecked и rawtypes — не шум. Каждое означает: компилятор больше не гарантирует отсутствие ClassCastException. @SuppressWarnings("unchecked") ставят на минимальную область с комментарием, почему приведение безопасно.
  • Обобщённые varargs (List<String>... lists) создают массив обобщённого типа — тот же риск. Если метод не записывает в массив и не отдаёт его наружу, его помечают @SafeVarargs (как List.of, Arrays.asList).

7.7Интерактив: скомпилируется ли? PECS на практике

Проверка компилятором: wildcards

Иерархия: Object ← Number ← Integer, Number ← Double. Выберите тип переменной и операцию.

PECS одной строкой static <T> void copy(List<? super T> dst, List<? extends T> src) — из src читаем (producer → extends), в dst пишем (consumer → super). Так объявлен Collections.copy.

7.8Самопроверка

Почему нельзя написать new T() или T[] arr = new T[10] в обобщённом классе?

  • Это запрещено стилем кодирования
  • Из-за стирания типов: в рантайме T неизвестен, остаётся Object или граница типа
  • T — зарезервированное слово
  • Можно, если T extends Object
Информация о T существует только при компиляции. Обход: передать Class<T> или Supplier<T>.

Скомпилируется ли класс с методами void process(List<String> l) и void process(List<Integer> l)?

  • Да, это перегрузка
  • Да, с предупреждением
  • Только если один из них static
  • Нет: после стирания оба имеют сигнатуру process(List) — name clash
Перегрузка различается по стёртым сигнатурам, а они одинаковы.

Что вернёт new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass()?

  • true — в рантайме существует один класс ArrayList
  • false
  • Ошибку компиляции
  • ClassCastException
Параметры типа стираются; отдельных классов для каждого параметра (как шаблоны C++) в Java нет.
Что такое стирание типов и зачем оно было выбрано?

Компилятор проверяет параметры типов, затем заменяет их верхней границей и вставляет приведения; в байткоде и у объектов параметров типов нет. Так сделано ради совместимости: код с generics работает с библиотеками, написанными до Java 5, и наоборот, без изменения JVM и формата классов.

Почему List<Integer> нельзя присвоить переменной List<Number>?

Через ссылку List<Number> можно было бы добавить Double, и список целых оказался бы испорчен. Обобщённые типы инвариантны. Если нужно только читать числа — List<? extends Number>.

Расшифруйте PECS и приведите пример из JDK.

Producer Extends, Consumer Super. Параметр, из которого читают, объявляют ? extends T; параметр, в который пишут, — ? super T. Пример: Collections.copy(List<? super T> dest, List<? extends T> src); Collection.addAll(Collection<? extends E>); List.sort(Comparator<? super E>).

Чем List<?> отличается от List<Object> и от сырого List?

List<Object> — список именно объектов: ему нельзя присвоить List<String>, зато можно добавить что угодно. List<?> — список неизвестного типа: присвоить можно любой, добавить нельзя ничего, кроме null. Сырой List отключает проверки вовсе.

Почему нельзя написать new T[10], но можно new ArrayList<T>()?

Массив хранит тип элементов и проверяет его при каждой записи, поэтому для создания нужен реальный класс, а T стёрт. ArrayList внутри держит Object[] и типа элементов не знает — ему стирание не мешает.

Как Jackson узнаёт, что нужно создать List<Order>, если типы стёрты?

Стирание касается объектов, но не объявлений. new TypeReference<List<Order>>() { } создаёт анонимный подкласс, в описании которого записан полный обобщённый суперкласс; он читается рефлексией через getGenericSuperclass(). Для полей и параметров методов тип так же доступен из class-файла.
