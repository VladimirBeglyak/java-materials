Лямбды, функциональные интерфейсы, Optional

С Java 8 поведение можно передавать как значение: функцию — в метод, условие — в фильтр, действие — в обработчик. Глава объясняет, что такое лямбда с точки зрения языка и JVM, почему захваченная переменная должна быть «фактически финальной» и как пользоваться Optional, не делая код хуже.

10.1От анонимного класса к лямбде

// Java 7: анонимный класс — пять строк ради одного выражения
users.sort(new Comparator<User>() {
    @Override public int compare(User a, User b) {
        return a.name().compareTo(b.name());
    }
});

users.sort((a, b) -> a.name().compareTo(b.name()));     // лямбда
users.sort(Comparator.comparing(User::name));           // ссылка на метод + фабрика компараторов
x -> x * 2                              // один параметр — скобки не нужны
(x, y) -> x + y                         // типы параметров выводятся
(String s, int n) -> s.repeat(n)        // типы указаны явно
() -> 42                                // без параметров
x -> { log(x); return x * 2; }          // блок: нужен явный return

Лямбда — не самостоятельный тип. Она всегда является реализацией какого-то функционального интерфейса, и компилятор определяет, какого именно, по контексту: типу переменной или параметра метода.

10.2Функциональные интерфейсы

Функциональный интерфейс — интерфейс с ровно одним абстрактным методом (default- и static-методов может быть сколько угодно). Аннотация @FunctionalInterface необязательна, но заставляет компилятор проверить это условие.

Function<String, String> normalize = String::strip;
Function<String, Integer> parse = normalize.andThen(Integer::parseInt);   // сначала strip, затем parseInt
  • Примитивные специализации — IntPredicate, IntFunction<R>, ToIntFunction<T>, IntUnaryOperator, LongSupplier и другие — существуют, чтобы избежать упаковки: Function<Integer, Integer> на каждый вызов создаёт объекты, IntUnaryOperator — нет.
  • Свои интерфейсы оправданы, когда стандартные не передают смысл (PriceRule понятнее, чем BiFunction<Order, Customer, BigDecimal>) или нужны три и более аргументов.
Проверяемые исключения и лямбды Методы стандартных функциональных интерфейсов не объявляют проверяемых исключений, поэтому list.forEach(f -> Files.delete(f)) не компилируется. Варианты: обернуть исключение внутри лямбды в непроверяемое (UncheckedIOException); вынести тело в метод, который делает это сам; объявить собственный интерфейс с throws. Приём «sneaky throw», обманывающий компилятор, лучше не использовать: вызывающий код перестаёт знать, чего ждать.

Третий вид путают чаще всего: String::compareTo как Comparator<String> означает (a, b) -> a.compareTo(b) — первый параметр становится объектом вызова. Тонкость второго вида: в obj::method выражение obj вычисляется один раз, в момент создания ссылки; если obj равен null, исключение возникнет сразу, а не при вызове.

10.4Как лямбда устроена внутри

Лямбда — не синтаксический сахар над анонимным классом. Для анонимного класса компилятор создаёт отдельный файл Outer$1.class. Для лямбды:

  1. Тело лямбды компилируется в приватный метод того же класса: lambda$main$0.
  2. На месте лямбды остаётся команда invokedynamic (тема 01).
  3. При первом выполнении JVM вызывает LambdaMetafactory, которая создаёт класс, реализующий нужный интерфейс и вызывающий этот метод.
  4. Результат кэшируется: повторные проходы через то же место не создают ничего заново.

class Screen {
    String name = "screen";
    Runnable anon = new Runnable() {
        String name = "anon";
        public void run() { System.out.println(this.name); }   // anon
    };
    Runnable lambda = () -> System.out.println(this.name);     // screen
}

Практические следствия: лямбда, не использующая состояние объекта, не удерживает его в памяти (в отличие от анонимного класса — тема 04); в стектрейсе лямбда выглядит как lambda$process$3 — номер ничего не говорит, поэтому длинные лямбды лучше выносить в именованные методы.

10.5Захват переменных

Лямбда может использовать локальные переменные окружающего метода, но только effectively final — те, которым значение присвоено один раз. Слово final писать необязательно.

int count = 0;
list.forEach(x -> count++);                 // ошибка компиляции: count изменяется

for (int i = 0; i < 3; i++) {
    tasks.add(() -> System.out.println(i)); // ошибка: i изменяется циклом
}
long count = list.stream().filter(this::matches).count();   // вычислять результат, а не менять переменную

for (int i = 0; i < 3; i++) {
    int n = i;                                 // новая переменная на каждой итерации
    tasks.add(() -> System.out.println(n));
}
for (String s : names) tasks.add(() -> System.out.println(s));   // переменная for-each — новая на каждом шаге
Почему такое ограничение Локальная переменная живёт в стеке и исчезает, когда метод завершается, а лямбда может быть выполнена позже и в другом потоке. Поэтому лямбда получает копию значения. Если бы переменную разрешалось менять, копия и оригинал разошлись бы, и код вёл бы себя не так, как читается. Запрет на изменение делает копирование незаметным.

Ограничение касается самой переменной, а не объекта: в захваченный список можно добавлять элементы, поля this можно менять. Отсюда «обходы» через массив из одного элемента или AtomicInteger — они компилируются, но возвращают ту самую проблему, от которой защищал компилятор: общее изменяемое состояние, особенно опасное в параллельных стримах и других потоках.

10.6Optional

Optional<T> — контейнер, который либо содержит значение, либо пуст. Он создан для одной цели: быть возвращаемым типом метода, у которого результата может не оказаться. Сигнатура Optional<User> findByEmail(String) сообщает то, что User findByEmail(String) скрывает.

Optional<User> found = repository.findByEmail(email);

String city = found.map(User::address)              // Optional<Address>
                   .map(Address::city)              // Optional<String>; пусто, если адреса нет
                   .filter(c -> !c.isBlank())
                   .orElse("не указан");

User user = found.orElseThrow(() -> new UserNotFoundException(email));
found.ifPresent(mailer::sendWelcome);
found.ifPresentOrElse(mailer::sendWelcome, () -> log.warn("нет пользователя {}", email));   // Java 9

Optional<User> any = primary.find(id).or(() -> backup.find(id));   // Java 9: запасной источник
// flatMap — когда функция сама возвращает Optional:  found.flatMap(User::manager)
Антипаттерны 
if (opt.isPresent()) { use(opt.get()); }             // тот же if (x != null), только длиннее
opt.get();                                           // NoSuchElementException вместо NPE — не лучше

User u = cache.find(id).orElse(loadFromDb(id));      // loadFromDb выполнится ВСЕГДА — аргумент вычисляется до вызова
User u = cache.find(id).orElseGet(() -> loadFromDb(id));   // выполнится только при пустом Optional

Optional.of(maybeNull);                              // NPE; для возможного null — Optional.ofNullable

10.8Самопроверка

Почему лямбда может использовать локальную переменную, только если та effectively final?

  • Так быстрее
  • Лямбда захватывает копию значения; изменяемая переменная рассинхронизировалась бы с копией, а лямбда может выполниться позже и в другом потоке
  • Это ограничение только для анонимных классов
  • Локальные переменные хранятся в куче
Локальная переменная живёт в кадре стека метода и исчезает при выходе из него. Поля объекта и элементы массива менять можно — они в куче.

Чем лямбда отличается от анонимного класса?

  • Ничем, это синтаксический сахар
  • Лямбда медленнее
  • У лямбды нет своего this и отдельного class-файла: она компилируется в метод и создаётся через invokedynamic
  • Лямбда может иметь состояние
this в лямбде — внешний объект. Анонимный класс — настоящий класс со своим this, полями и файлом Outer$1.class.

Где Optional использовать НЕ стоит?

  • В полях класса и параметрах методов
  • В возвращаемых значениях методов поиска
  • В цепочках map/filter
  • В результатах стримов: findFirst, max
Optional задуман как тип возвращаемого значения «результата может не быть». В полях он не сериализуем и добавляет объект, в параметрах заставляет вызывающего оборачивать значение.
Что такое функциональный интерфейс и обязательна ли аннотация @FunctionalInterface?

Интерфейс с единственным абстрактным методом; default- и static-методы не считаются. Аннотация необязательна — лямбду можно присвоить любому такому интерфейсу. Она нужна как защита: при добавлении второго абстрактного метода компилятор выдаст ошибку.

Чем лямбда отличается от анонимного класса?

Реализацией: для лямбды не создаётся класс при компиляции — тело становится приватным методом, а объект формируется при выполнении через invokedynamic. Семантикой: this в лямбде — окружающий объект, у лямбды нет своей области видимости, она не удерживает внешний объект без необходимости, а незахватывающая лямбда существует в одном экземпляре.

Почему в лямбде можно использовать только effectively final локальные переменные?

Лямбда копирует значения захваченных локальных переменных, потому что может выполняться после завершения метода и в другом потоке. Если бы переменную можно было менять, изменения не были бы видны копии, а код выглядел бы так, будто видны. Запрет устраняет эту неоднозначность и заодно защищает от гонок на локальных переменных.

Назовите четыре вида ссылок на методы.

На статический метод (Integer::parseInt); на метод конкретного объекта (System.out::println); на метод экземпляра, где объектом вызова становится первый аргумент (String::length); на конструктор (ArrayList::new).

В чём разница между orElse и orElseGet?

orElse(x) принимает готовое значение — выражение вычисляется всегда, даже если Optional не пуст. orElseGet(supplier) вызывает поставщика только при пустом. Для константы подходит первый, для любого вычисления, запроса или создания объекта — второй.

Почему Optional не рекомендуют использовать в полях и параметрах?

Он спроектирован как возвращаемый тип. В поле — лишняя аллокация и несериализуемость; в параметре — неудобство вызывающему и ложная гарантия (сам Optional может быть null). Для необязательного параметра лучше перегрузка метода или объект-параметры.
