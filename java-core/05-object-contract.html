equals, hashCode, иммутабельность

Каждый класс наследует от Object несколько методов с контрактами, на которые опирается вся стандартная библиотека. Нарушение контракта не вызывает ошибку компиляции — объект просто «теряется» в HashMap или дублируется в Set. Самая спрашиваемая тема Java Core.

5.2equals

Метод определяет логическое равенство. Контракт требует, чтобы оно было отношением эквивалентности:

СвойствоТребование
Рефлексивностьx.equals(x) — true
Симметричностьx.equals(y) ⇔ y.equals(x)
Транзитивностьx.equals(y) и y.equals(z) ⇒ x.equals(z)
СогласованностьПовторные вызовы дают тот же результат, пока объекты не менялись
Сравнение с nullx.equals(null) — false, без исключения
public final class Money {
    private final long amount;
    private final String currency;

    @Override
    public boolean equals(Object o) {               // параметр — именно Object
        if (this == o) return true;                 // быстрый путь
        if (!(o instanceof Money other)) return false;   // заодно отсекает null
        return amount == other.amount && currency.equals(other.currency);
    }

    @Override
    public int hashCode() {
        return Objects.hash(amount, currency);      // те же поля, что и в equals
    }
}
Типичные ошибки
  • public boolean equals(Money other) — это перегрузка, а не переопределение. Коллекции вызывают equals(Object) и получат версию из Object. @Override превращает эту ошибку в ошибку компиляции.
  • double и float сравнивают через Double.compare(a, b) == 0: оператор == считает NaN не равным себе, что нарушает рефлексивность.
  • Массивы — через Arrays.equals и Arrays.hashCode; у самого массива equals сравнивает ссылки.
  • Поля, допускающие null, — через Objects.equals(a, b).

instanceof или getClass

instanceof считает равными объект класса и объект его наследника; getClass() != o.getClass() — только объекты строго одного класса. С instanceof наследник, добавляющий в сравнение своё поле, неизбежно нарушит симметричность: point.equals(colorPoint) — true, а colorPoint.equals(point) — false. Надёжные варианты: сделать класс final (как в примере) или использовать getClass(). Нельзя корректно расширить класс-значение, добавив поле в сравнение, — это ещё один довод в пользу композиции.

5.3hashCode

Контракт в трёх строках
  1. Равные по equals объекты обязаны иметь одинаковый hashCode.
  2. Разные объекты могут иметь одинаковый hashCode (коллизия) — это допустимо, но вредит производительности.
  3. Значение не меняется, пока не изменились поля, участвующие в equals.

Хэш-коллекции ищут объект в два шага: по hashCode находят ячейку, затем внутри ячейки сравнивают через equals (тема 09). Если равные объекты дают разные хэши, поиск идёт не в ту ячейку.

Set<Money> set = new HashSet<>();
set.add(new Money(100, "RUB"));
set.contains(new Money(100, "RUB"));   // false: у двух объектов разные хэши по умолчанию
set.add(new Money(100, "RUB"));
set.size();                            // 2 «одинаковых» элемента в множестве
Что переопределеноПоведение в HashMap / HashSet
НичегоРаботает, но равенство — только тождество объектов
Только equalsСломано: равные объекты не находятся, появляются дубликаты
Только hashCodeОбъекты попадают в одну ячейку, но не считаются равными — дубликаты
hashCode возвращает константуКорректно, но все элементы в одной ячейке — поиск вырождается
Оба, по одним и тем же полямПравильно
Изменяемый ключ 
Set<Point> set = new HashSet<>();
Point p = new Point(1, 2);
set.add(p);
p.x = 5;                 // хэш изменился, а элемент остался в старой ячейке
set.contains(p);         // false
set.remove(p);           // false — элемент нельзя ни найти, ни удалить: утечка памяти
set.size();              // 1
Ключи HashMap и элементы HashSet должны быть неизменяемыми — как минимум в части полей, участвующих в equals и hashCode.
  • Хэш по умолчанию — не адрес в памяти. Объекты перемещаются сборщиком мусора, а хэш обязан сохраняться. HotSpot генерирует псевдослучайное число при первом вызове и хранит его в заголовке объекта.
  • Множитель 31 в ручных реализациях (31 * result + field) — нечётное простое число, дающее хорошее рассеивание; Objects.hash делает то же самое.
  • Record генерирует equals, hashCode и toString по всем компонентам — для объектов-значений это лучший вариант (тема 12).
Сущности JPA — особый случай У сущности нет стабильного набора полей для сравнения: идентификатор появляется только после сохранения, остальные поля меняются. Генерация equals/hashCode по всем полям (Lombok @Data) ломает коллекции и вызывает ленивую загрузку связей. Распространённое решение — сравнивать по идентификатору, считая несохранённые сущности неравными, а hashCode возвращать постоянным для класса.

5.4toString

Строковое представление нужно людям: в логах, сообщениях исключений, отладчике. Строка Order@1b6d3586 в журнале инцидента бесполезна. Включайте поля, достаточные для идентификации, и исключайте секреты и персональные данные — пароли, токены, номера карт попадают в логи именно через toString. Не вызывайте в нём ленивые связи и тяжёлые вычисления: он может быть вызван неявно при конкатенации.

5.5Comparable и Comparator

Comparable<T>

«Естественный» порядок, заданный самим классом: метод compareTo. Один на класс. Есть у String, чисел, дат, enum.

Comparator<T>

Внешнее правило сравнения. Сколько угодно разных; можно сравнивать чужие классы.

record Employee(String name, String dept, int salary, LocalDate hired) { }

Comparator<Employee> byDeptThenSalaryDesc =
        Comparator.comparing(Employee::dept)
                  .thenComparing(Employee::salary, Comparator.reverseOrder())
                  .thenComparing(Employee::hired, Comparator.nullsLast(Comparator.naturalOrder()));

employees.sort(byDeptThenSalaryDesc);
Сравнение вычитанием 
(a, b) -> a.salary() - b.salary()          // переполнение: 2_000_000_000 - (-2_000_000_000) < 0
(a, b) -> Integer.compare(a.salary(), b.salary())   // правильно
Comparator.comparingInt(Employee::salary)            // ещё лучше

Согласованность с equals. Рекомендуется, чтобы compareTo возвращал 0 тогда и только тогда, когда equals — true. Сортированные коллекции (TreeSet, TreeMap) определяют «тот же элемент» именно по сравнению, а не по equals:

var a = new BigDecimal("2.0");  var b = new BigDecimal("2.00");
new HashSet<>(List.of(a, b)).size();   // 2: equals учитывает масштаб
new TreeSet<>(List.of(a, b)).size();   // 1: compareTo вернул 0 — «дубликат»

5.6Копирование объектов

Поверхностная копия дублирует сам объект, но ссылочные поля указывают на те же вложенные объекты. Глубокая копирует и их. Object.clone() делает поверхностную копию и устроен неудачно: требует маркерного интерфейса Cloneable, создаёт объект в обход конструктора, не работает с final-полями, возвращает Object. Современная практика:

public Order(Order other) {                       // конструктор копирования
    this.id = other.id;
    this.items = new ArrayList<>(other.items);    // новый список; сами элементы — общие, если они неизменяемы
}
List<String> snapshot = List.copyOf(source);      // неизменяемая копия коллекции

Для массивов array.clone() и Arrays.copyOf — допустимое и быстрое исключение из правила.

5.7Неизменяемые классы

Объект, состояние которого нельзя изменить после создания, снимает сразу несколько проблем: его безопасно использовать как ключ, отдавать другим потокам без синхронизации, кэшировать и передавать в чужой код без защитного копирования.

  1. Класс final — наследник не сможет добавить изменяемость.
  2. Все поля private final, сеттеров нет.
  3. Изменяемые аргументы копируются в конструкторе — иначе вызывающий изменит внутренности через сохранённую у себя ссылку.
  4. Изменяемые поля не отдаются наружу: геттер возвращает копию или неизменяемое представление.
  5. «Изменение» создаёт новый объект: withAmount(...), plus(...).
public final class Schedule {
    private final String name;
    private final List<LocalDate> dates;

    public Schedule(String name, List<LocalDate> dates) {
        this.name = Objects.requireNonNull(name);
        this.dates = List.copyOf(dates);          // защитная копия + запрет null + неизменяемость
    }
    public List<LocalDate> dates() { return dates; }   // List.copyOf уже неизменяем — отдавать безопасно

    public Schedule withDate(LocalDate d) {       // «изменение» возвращает новый объект
        var copy = new ArrayList<>(dates);
        copy.add(d);
        return new Schedule(name, copy);
    }
}
Три ложных признака неизменяемости
  • final-поле запрещает переприсваивание ссылки, но не изменение объекта, на который она указывает.
  • Collections.unmodifiableList(list) — представление: изменения исходного списка видны через него. List.copyOf делает независимую копию.
  • Record неизменяем поверхностно: компонент типа List или Date остаётся изменяемым, если его не скопировать в компактном конструкторе.

5.9Самопроверка

У двух объектов одинаковый hashCode. Что можно утверждать?

  • Они равны по equals
  • Ничего: это может быть коллизия; равенство решает только equals
  • Это один и тот же объект
  • Контракт нарушен
Контракт односторонний: равные по equals ⇒ равные хэши. Обратное не требуется и при 2³² значений int невозможно гарантировать.

Чем Comparable отличается от Comparator?

  • Ничем, это синонимы
  • Comparable быстрее
  • Comparable — «естественный порядок», реализуется самим классом (compareTo); Comparator — внешняя стратегия сравнения, их может быть много
  • Comparator работает только со строками
list.sort(null) использует compareTo; Comparator.comparing(User::age).thenComparing(User::name) задаёт порядок снаружи, не меняя класс.

Что нужно, чтобы класс был действительно неизменяемым?

  • final-класс, private final поля, нет сеттеров, защитные копии изменяемых полей на входе и выходе
  • Достаточно пометить поля final
  • Достаточно убрать сеттеры
  • Реализовать Cloneable
final List<String> items не мешает менять сам список. Нужны List.copyOf в конструкторе и возврат неизменяемого представления.
Сформулируйте связь equals и hashCode. В какую сторону она действует?

Если a.equals(b), то a.hashCode() == b.hashCode(). Обратное не требуется: одинаковый хэш у неравных объектов — допустимая коллизия. Поэтому оба метода переопределяют вместе и по одному набору полей.

Что произойдёт, если переопределить equals, но не hashCode, и положить объект в HashSet?

Два равных объекта получат разные хэши по умолчанию и попадут в разные ячейки. contains для равного, но другого экземпляра вернёт false, а повторное добавление создаст дубликат. При этом в ArrayList и TreeSet всё будет работать — они не используют хэш, из-за чего ошибку легко не заметить.

Может ли hashCode всегда возвращать 1?

Формально да — контракт соблюдён. Но все элементы окажутся в одной ячейке хэш-таблицы, и операции станут O(n) (O(log n), если ключи сравнимы и ячейка превратилась в дерево). Корректно, но бессмысленно.

Почему ключ HashMap должен быть неизменяемым?

Положение записи определяется хэшем ключа в момент вставки. Если после этого изменить поле, участвующее в hashCode, поиск пойдёт в другую ячейку: запись нельзя ни прочитать, ни удалить, хотя она продолжает занимать память.

Чем Comparable отличается от Comparator и что значит «согласован с equals»?

Comparable — естественный порядок внутри самого класса, один. Comparator — внешнее правило, их может быть много. Согласованность: compareTo(x) == 0 ровно тогда, когда equals(x). Если она нарушена (как у BigDecimal), TreeSet и HashSet по-разному определяют дубликаты.

Класс с полями private final Date start и геттером getStart() — неизменяем ли он?

Нет. Date изменяем: вызывающий код может сохранить ссылку на переданный в конструктор объект или получить его через геттер и вызвать setTime. Нужны защитные копии на входе и выходе, а лучше — неизменяемый тип (Instant, LocalDate).
