Stream API

Стрим описывает, что сделать с данными, а не как их обойти: отфильтровать, преобразовать, сгруппировать. Чтобы пользоваться им уверенно, нужно понимать ленивость конвейера, знать коллекторы и трезво оценивать параллельные стримы.

~3 часаленивостьCollectorsparallelинтерактивтестпрактикум

11.1Конвейер

List<String> topCustomers = orders.stream()                    // источник
        .filter(o -> o.status() == Status.PAID)                 // промежуточная
        .sorted(Comparator.comparing(Order::total).reversed())  // промежуточная
        .map(Order::customer)                                   // промежуточная
        .distinct()
        .limit(10)
        .toList();                                              // терминальная
  • Стрим не хранит данные и не изменяет источник — он описывает вычисление над ним.
  • Стрим одноразовый. После терминальной операции повторное использование даёт IllegalStateException: stream has already been operated upon or closed.
  • Стрим ленив. Без терминальной операции не выполняется ничего.

11.2Ленивость и порядок выполнения

Optional<String> first = Stream.of("a", "b", "c", "d")
        .filter(s -> { System.out.println("filter " + s); return !s.equals("a"); })
        .map(s -> { System.out.println("map " + s); return s.toUpperCase(); })
        .findFirst();
filter a
filter b
map b

Элементы проходят конвейер по одному, сквозь все операции, а не «слоями». Как только findFirst получил результат, обработка прекращается — c и d не затронуты. Это позволяет работать с бесконечными источниками и не делать лишней работы.

Вид операцииПримерыОсобенность
Без состоянияfilter, map, flatMap, peekКаждый элемент обрабатывается независимо
С состояниемsorted, distinctДолжны увидеть все элементы (или помнить виденные) — буферизуют данные и ломают «поэлементность»
Укорачивающиеlimit, takeWhile, findFirst, anyMatchМогут завершить конвейер досрочно

Порядок операций влияет на объём работы: filter перед map и sorted уменьшает число элементов для дорогих шагов; sorted().limit(10) всё равно сортирует всё.

reduce сворачивает элементы ассоциативной операцией: prices.stream().reduce(BigDecimal.ZERO, BigDecimal::add). Первый аргумент — нейтральный элемент: ноль для сложения, единица для умножения, пустая строка для склейки. Для накопления в изменяемый контейнер (список, карту, StringBuilder) используют collect, а не reduce.

Три ловушки toMap 
toMap(User::email, u -> u)                         // IllegalStateException: Duplicate key — при повторе ключа
toMap(User::email, u -> u, (a, b) -> a)            // третий аргумент решает, что делать с повтором

11.5Ловушки

List<String> names = new ArrayList<>();
users.stream().filter(User::isActive).forEach(u -> names.add(u.name()));   // работает, пока стрим не параллельный

users.stream().peek(u -> u.setProcessed(true)).count();   // peek может не выполниться вовсе:
                                                          // с Java 9 count() не запускает конвейер, если размер известен
List<String> names = users.stream().filter(User::isActive).map(User::name).toList();
  • Не изменяйте источник во время работы стрима (list.stream().forEach(x -> list.remove(x))) — результат не определён.
  • Бесконечные стримы (Stream.iterate(1, x -> x * 2), Stream.generate(...)) требуют укорачивающей операции; sorted() или distinct() на бесконечном стриме никогда не завершатся.
  • Стрим поверх ресурса нужно закрыть: Files.lines, Files.walk, результат запроса JPA как Stream — только в try-with-resources.
  • Читаемость важнее. Цепочка на двадцать строк с вложенными лямбдами хуже цикла. Сложные шаги выносят в именованные методы: .filter(this::isEligible).
  • Отладка. Исключение внутри лямбды даёт длинный стектрейс из служебных кадров; точку останова ставят внутрь лямбды, а не на строку с .stream().

Производительность. Последовательный стрим обычно немного медленнее цикла — на создание объектов конвейера и вызовы лямбд; для бизнес-кода это несущественно. Заметно проигрывает только работа с упаковкой (Stream<Integer> вместо IntStream) и использование стримов на очень маленьких коллекциях в горячем цикле.

11.6Параллельные стримы

parallelStream() или .parallel() разбивают источник на части, обрабатывают их в нескольких потоках и объединяют результаты. Выглядит как бесплатное ускорение, на практике полезно редко.

Когда помогает

  • Данных много — десятки тысяч элементов и больше.
  • Работа над элементом чисто вычислительная.
  • Источник хорошо делится пополам: ArrayList, массив, IntStream.range.
  • Операции без состояния и без общего изменяемого состояния.
  • Измерение показало выигрыш.

Когда вредит

  • Блокирующий ввод-вывод внутри: HTTP, запросы в базу.
  • Мало данных — накладные расходы больше выигрыша.
  • Плохо делимый источник: LinkedList, Stream.iterate, BufferedReader.lines.
  • Операции, зависящие от порядка: limit, findFirst, forEachOrdered.
  • Сервер уже загружен параллельными запросами.
Общий пул — главная опасность Все параллельные стримы приложения выполняются в одном ForkJoinPool.commonPool(), размер которого равен числу ядер минус один. Один стрим с медленными запросами к внешнему сервису занимает все его потоки — и останавливает остальные параллельные стримы и CompletableFuture без явного исполнителя во всём процессе. Для ввода-вывода используют отдельный пул или виртуальные потоки (Java Concurrency, тема 08).

В параллельном стриме лямбды обязаны быть без побочных эффектов, а операция в reduce — ассоциативной: (a − b) − c ≠ a − (b − c), и результат вычитания будет зависеть от разбиения.

11.7Gatherers — свои промежуточные операции (Java 24)

До Java 24 набор промежуточных операций был закрытым: «разбить на пачки по 100» или «скользящее окно» приходилось делать вручную. Метод gather принимает произвольную операцию; несколько готовых лежат в классе Gatherers.

Stream.of(1, 2, 3, 4, 5, 6, 7).gather(Gatherers.windowFixed(3)).toList();    // [[1, 2, 3], [4, 5, 6], [7]]
Stream.of(1, 2, 3, 4).gather(Gatherers.windowSliding(2)).toList();           // [[1, 2], [2, 3], [3, 4]]
Stream.of(1, 2, 3, 4).gather(Gatherers.scan(() -> 0, Integer::sum)).toList(); // [1, 3, 6, 10] — нарастающий итог

ids.stream().gather(Gatherers.mapConcurrent(8, client::fetch)).toList();     // не более 8 вызовов одновременно,
                                                                             // порядок сохранён, виртуальные потоки

Увидеть порядок, в котором элементы проходят операции, и сколько работы реально делается.

  1. Создайте файл Trace.java:
    import java.util.List;
import java.util.stream.Stream;

public class Trace {
    public static void main(String[] args) {
        Stream<String> s = Stream.of("один", "два", "три", "четыре", "пять")
                .peek(x -> System.out.println("  источник: " + x))
                .filter(x -> x.length() > 3)
                .peek(x -> System.out.println("  прошёл фильтр: " + x))
                .map(String::toUpperCase);
        System.out.println("конвейер построен, ничего не выполнено");
        List<String> first = s.limit(2).toList();
        System.out.println("результат: " + first);

        System.out.println("--- sorted ломает «вертикальность» ---");
        Stream.of("b", "c", "a")
              .peek(x -> System.out.println("  до sorted: " + x))
              .sorted()
              .peek(x -> System.out.println("  после sorted: " + x))
              .findFirst()
              .ifPresent(x -> System.out.println("first = " + x));
    }
}

Лаба 11.2Коллекторы: группировка, разбиение, статистика20 мин

Решить типичные задачи отчётности одной цепочкой.

  1. Создайте файл Report.java:
    import java.util.*;
import java.util.stream.Collectors;

public class Report {
    record Order(String city, String product, int qty, double price) {
        double total() { return qty * price; }
    }

    public static void main(String[] args) {
        List<Order> orders = List.of(
            new Order("Москва", "кофе", 3, 250), new Order("Казань", "чай", 5, 120),
            new Order("Москва", "чай", 1, 120), new Order("Казань", "кофе", 2, 250),
            new Order("Пермь", "кофе", 10, 230), new Order("Москва", "кофе", 4, 250));

        Map<String, Double> revenueByCity = orders.stream()
            .collect(Collectors.groupingBy(Order::city, TreeMap::new, Collectors.summingDouble(Order::total)));
        System.out.println("выручка по городам: " + revenueByCity);

        Map<String, Set<String>> productsByCity = orders.stream()
            .collect(Collectors.groupingBy(Order::city, TreeMap::new, Collectors.mapping(Order::product, Collectors.toCollection(TreeSet::new))));
        System.out.println("товары по городам:  " + productsByCity);

        Map<Boolean, Long> bigSmall = orders.stream().collect(Collectors.partitioningBy(o -> o.total() >= 1000, Collectors.counting()));
        System.out.println("крупных/мелких:     " + bigSmall);

        DoubleSummaryStatistics stats = orders.stream().mapToDouble(Order::total).summaryStatistics();
        System.out.println("статистика:         " + stats);

        String top = orders.stream().max(Comparator.comparingDouble(Order::total)).map(Order::toString).orElse("-");
        System.out.println("самый крупный:      " + top);

        try {
            orders.stream().collect(Collectors.toMap(Order::city, Order::qty));
        } catch (IllegalStateException e) {
            System.out.println("toMap: " + e.getMessage());
        }
        System.out.println("toMap с merge:      " + orders.stream().collect(Collectors.toMap(Order::city, Order::qty, Integer::sum, TreeMap::new)));
    }
}

Лаба 11.3Параллельный стрим: когда быстрее, а когда неверно20 мин

Сравнить последовательный и параллельный стрим на двух задачах и поймать гонку при побочных эффектах.

  1. Создайте файл Par.java:
    import java.util.ArrayList;
import java.util.List;
import java.util.stream.LongStream;

public class Par {
    static long time(Runnable r) { long t = System.nanoTime(); r.run(); return (System.nanoTime() - t) / 1_000_000; }

    public static void main(String[] args) {
        for (int round = 0; round < 3; round++) {
            long seq = time(() -> LongStream.range(0, 50_000_000).map(x -> x * x % 7).sum());
            long par = time(() -> LongStream.range(0, 50_000_000).parallel().map(x -> x * x % 7).sum());
            System.out.printf("раунд %d: последовательно %4d мс, parallel %4d мс%n", round, seq, par);
        }
        System.out.println("ядер: " + Runtime.getRuntime().availableProcessors());

        List<Long> unsafe = new ArrayList<>();
        try {
            LongStream.range(0, 100_000).parallel().forEach(unsafe::add);
            System.out.println("ArrayList из parallel forEach: " + unsafe.size() + " элементов вместо 100000");
        } catch (Exception e) {
            System.out.println("ArrayList из parallel forEach: " + e);
        }
        List<Long> safe = LongStream.range(0, 100_000).parallel().boxed().toList();
        System.out.println("toList(): " + safe.size() + ", порядок сохранён: " + safe.get(99_999));
    }
}
  2. Во сколько раз ускорится parallel и что будет с ArrayList?

    Parallel — не «включить ускорение»: он использует общий ForkJoinPool.commonPool() на всё приложение, плохо делит LinkedList и стримы из I/O, а для маленьких наборов накладные расходы больше выигрыша. Меряйте.

ArrayList из нескольких потоков — гонка: элементов меньше 100 000 или ArrayIndexOutOfBoundsException при одновременном росте массива. Результат собирают терминальной операцией (toList, collect), а не побочными эффектами.

11.10Самопроверка

Что выведет Stream.of(1, 2, 3).peek(System.out::println);?

  • 1 2 3
  • Ничего — нет терминальной операции
  • Ошибку компиляции
  • IllegalStateException
peek — промежуточная операция. Конвейер запускается только терминальной.

Стрим сохранён в переменную и использован дважды: s.count(); s.toList();. Что произойдёт?

  • Оба вызова отработают
  • Второй вернёт пустой список
  • IllegalStateException: stream has already been operated upon or closed
  • Ошибка компиляции
Стрим одноразовый. Для повторного прохода создайте новый из источника или сохраните Supplier<Stream>.

Когда parallelStream() скорее навредит?

  • Блокирующие вызовы (БД, HTTP) в операциях, мало элементов, LinkedList как источник, общий изменяемый объект в лямбдах
  • Суммирование большого массива чисел
  • Независимые CPU-вычисления над ArrayList из миллиона элементов
  • Никогда — он всегда быстрее
Параллельные стримы работают на общем ForkJoinPool.commonPool: блокировка в нём тормозит всё приложение. Выигрыш — только для больших объёмов чистых вычислений над хорошо делимым источником.
Чем промежуточные операции отличаются от терминальных?

Промежуточные возвращают новый стрим и ничего не выполняют — только достраивают описание конвейера. Терминальная запускает обработку и возвращает результат (или выполняет побочный эффект), после чего стрим использовать нельзя.

Что напечатает Stream.of(1, 2, 3).filter(x -> { System.out.println(x); return true; });?

Ничего. Терминальной операции нет, конвейер не запускается. Лямбда будет вызвана только после добавления, например, .toList().

Чем map отличается от flatMap?

map преобразует каждый элемент в один другой. flatMap преобразует каждый элемент в стрим и объединяет все эти стримы в один плоский: из списка заказов получить поток всех позиций, из строк — поток слов.

Что произойдёт при Collectors.toMap, если два элемента дают одинаковый ключ?

IllegalStateException: Duplicate key. Чтобы этого избежать, передают третий аргумент — функцию слияния значений: оставить первое, последнее, сложить. Если на один ключ нужно много значений — groupingBy.

Почему в параллельном стриме нельзя делать HTTP-запросы?

Параллельные стримы используют общий ForkJoinPool с числом потоков около числа ядер. Блокирующие вызовы занимают эти потоки ожиданием, и все остальные параллельные стримы и асинхронные задачи процесса, использующие тот же пул, останавливаются. Кроме того, степень параллелизма для ввода-вывода должна определяться не числом ядер.

Чем stream.toList() отличается от collect(Collectors.toList())?

toList() возвращает неизменяемый список (допускающий null). Collectors.toList() не гарантирует ни тип, ни изменяемость, фактически возвращая ArrayList. Код, который изменяет результат, после замены сломается.
