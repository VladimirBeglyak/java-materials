26.1Зачем упаковывать объекты

Объект в памяти — это набор ссылок и полей, понятный только этой JVM. Чтобы отправить его другому сервису (возможно, написанному на другом языке) или сохранить, его превращают в последовательность байтов или текст — сериализуют. На другой стороне — десериализуют. Как разобрать мебель для переезда и собрать по инструкции на новом месте.

Главная мысль Сериализация — упаковка объекта для передачи и хранения.

26.2Почему не встроенная сериализация Java

  • Опасна: при чтении данных из чужого источника можно заставить программу выполнить вредный код.
  • Хрупкая: изменили класс — старые данные не читаются.
  • Только Java: сервис на Go или Python её не поймёт.
Главная мысль Для обмена данными Serializable не используют.

26.3JSON и Jackson

JSON — текстовый формат, который понимают все: {"id": 42, "name": "Иван"}. В Java его читают и пишут библиотекой Jackson: главный объект ObjectMapper превращает объект в JSON и обратно, глядя на поля и геттеры (или компоненты record). ObjectMapper создают один раз и переиспользуют — он потокобезопасен и дорог в создании.

Главная мысль JSON — общий язык сервисов, Jackson — переводчик. ObjectMapper — один на приложение.

26.4Аннотации Jackson

  • @JsonProperty("user_name") — другое имя поля в JSON.
  • @JsonIgnore — не выводить поле (например, пароль).
  • @JsonIgnoreProperties(ignoreUnknown = true) — не падать на незнакомых полях.
  • @JsonFormat — формат дат.
Главная мысль Аннотации настраивают имена, скрытые поля и форматы.

26.6Protobuf: схема и бинарный формат

В protobuf сначала пишут схему в файле .proto: «сообщение User: поле 1 — id, поле 2 — name». Из схемы генерируется код для любого языка. В данных хранятся не имена полей, а их номера — поэтому сообщения маленькие и быстрые, но без схемы их не прочитать глазами.

Главная мысль Protobuf — схема + номера полей = компактно, быстро, для любого языка.

26.7Как менять формат, не ломая других

Сервисы обновляются в разное время, поэтому старые и новые версии должны понимать друг друга:

Безопасное изменение формата
добавить новое необязательное поле ✓
старый получатель его проигнорирует (если игнорирует неизвестные)переименовать поле ✗ — для старых клиентов оно «исчезнет»
лучше: добавить новое, какое-то время поддерживать обасменить тип поля ✗ — старые не смогут прочитатьв protobuf: никогда не переиспользовать номер удалённого поля
(пометить reserved)

Самое безопасное изменение.

Ломает совместимость.

Тоже ломает.

Старый номер с новым смыслом — тихая порча данных.

Главная мысль Добавлять — можно, переименовывать и менять тип — нельзя. Получатель должен терпеть незнакомые поля.

26.9Проверьте себя

Почему для обмена между сервисами не используют Serializable?

  • он медленный
  • он опасен, хрупок и понятен только Java
  • он не работает с числами
  • он платный
JSON и protobuf лишены этих проблем.

Как правильно использовать ObjectMapper?

  • создавать на каждый запрос
  • создавать в каждом методе
  • создать один раз и переиспользовать
  • не использовать
Он потокобезопасен и дорог в создании.

Какое изменение формата безопасно?

  • добавить новое необязательное поле
  • переименовать поле
  • сменить тип поля
  • удалить обязательное поле
Старые получатели просто проигнорируют новое поле.

Почему сообщения protobuf меньше JSON?

  • они сжаты zip
  • они не содержат данных
  • они короче по смыслу
  • в них хранятся номера полей, а не имена, и двоичные числа вместо текста
Схема знает, что означает каждый номер.

Как не дать паролю попасть в JSON-ответ?

  • сделать поле public
  • @JsonProperty
  • @JsonIgnore на поле (или отдельный DTO без него)
  • никак
Лучше всего — отдельный объект для ответа без секретных полей.
