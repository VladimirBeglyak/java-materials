Память JVM и сборка мусора

Автоматическое управление памятью не означает, что о ней можно не думать: утечки в Java существуют, паузы сборщика влияют на время ответа, а контейнер убивает процесс без единой строки в логе. Глава о том, где живут объекты, как JVM решает, что они больше не нужны, и что делать, когда память закончилась.

До Java 8 метаданные классов лежали в PermGen — области фиксированного размера внутри кучи, отсюда знаменитая ошибка PermGen space. Metaspace заменил его и по умолчанию ограничен только памятью машины.

Как устроен объект и его создание

  • Заголовок объекта — 12 байт: служебное слово (хэш, возраст, состояние блокировки) и указатель на класс. Размер объекта выравнивается до 8 байт, поэтому new Object() занимает 16 байт, Integer — тоже 16. В Java 25 можно включить компактные заголовки по 8 байт (-XX:+UseCompactObjectHeaders).
  • Сжатые ссылки. При куче до 32 ГБ ссылка занимает 4 байта вместо 8. Куча в 33 ГБ может вмещать меньше объектов, чем куча в 31 ГБ.
  • Выделение памяти дёшево. У каждого потока свой участок Eden (TLAB), и new сводится к сдвигу указателя — несколько машинных команд, без блокировок. Дорого не создание объектов, а их долгая жизнь.
  • Объект может вовсе не попасть в кучу. Если JIT докажет, что объект не покидает метод (escape analysis), он заменит его набором локальных переменных. Поэтому короткоживущие мелкие объекты — итераторы, Optional, записи — в горячем коде часто бесплатны.

14.2Достижимость

Сборщик не считает ссылки на объект. Он определяет достижимость: объект жив, если до него можно дойти по цепочке ссылок от одного из корней (GC roots). Всё остальное — мусор, даже если объекты ссылаются друг на друга по кругу.

Корни

  • Локальные переменные и параметры в стеках всех потоков.
  • Статические поля загруженных классов.
  • Сами работающие потоки.
  • Ссылки из нативного кода (JNI).
  • Объекты, используемые как мониторы.

Следствия

  • Циклические ссылки — не проблема.
  • Присваивать null локальной переменной в конце метода бессмысленно.
  • Статическое поле — корень, живущий, пока загружен класс: всё, что из него достижимо, не будет собрано.
  • System.gc() — просьба, а не команда; в рабочем коде не вызывают.

14.3Поколения

Наблюдение, на котором построены почти все сборщики: большинство объектов умирает молодыми. Временные строки, DTO запроса, итераторы живут миллисекунды. Поэтому кучу делят на поколения и чаще всего убирают только молодое.

  1. Новый объект создаётся в Eden.
  2. Eden заполнен — малая сборка (minor GC): живые объекты из Eden и занятого Survivor копируются во второй Survivor; всё остальное пространство объявляется свободным. Цена пропорциональна числу живых объектов, а их мало.
  3. У каждого пережившего сборку объекта увеличивается возраст. Пережившие несколько сборок (порог до 15) переводятся в Old.
  4. Old заполняется медленно; его сборка — дороже и реже. Полная сборка всей кучи (full GC) с остановкой приложения — признак проблемы.
Stop-the-world На некоторых этапах сборщику нужно, чтобы граф объектов не менялся, и он останавливает все потоки приложения. Различие между сборщиками — в том, какую часть работы они выполняют во время такой паузы, а какую — параллельно с приложением. Паузы сборщика напрямую складываются с временем ответа сервиса и объясняют «необъяснимые» выбросы p99.

  • G1: цель паузы задаётся -XX:MaxGCPauseMillis (по умолчанию 200 мс) — это ориентир, а не гарантия. Объект размером от половины региона считается «огромным» (humongous) и размещается отдельно; обилие таких объектов — частая причина проблем.
  • ZGC платит за короткие паузы процессорным временем и памятью: фоновая работа отнимает часть пропускной способности. С Java 21 он поколенческий, с Java 24 — только поколенческий.

Ловушка контейнеров: неожиданный Serial GC JVM выбирает сборщик по ресурсам машины. Если контейнеру выделено меньше двух процессоров или менее ~2 ГБ памяти, по умолчанию будет выбран Serial, а не G1 — с однопоточными паузами. В настройках сервиса сборщик стоит указывать явно, а в логе запуска — проверять, какой выбран (-Xlog:gc).

14.6Утечки памяти

Утечка в Java — это объект, который программе больше не нужен, но остаётся достижимым. Сборщик работает правильно: он не может знать, что ссылка «забыта».

class SessionRegistry {
    private static final Map<String, Session> SESSIONS = new HashMap<>();   // корень GC
    void login(Session s) { SESSIONS.put(s.id(), s); }
    // logout() забывает вызвать remove — каждая сессия остаётся навсегда
}

Что означает каждая ошибка

СообщениеПричина

OOMKilled — это не OutOfMemoryError Контейнер завершается с кодом 137, в логе приложения — ничего. Это ядро ОС убило процесс за превышение лимита памяти контейнера. Куча могла быть наполовину пуста: лимит считается по всей памяти процесса — куча + Metaspace + стеки потоков + прямые буферы + структуры сборщика + нативные библиотеки. Дамп кучи не создаётся. Решение — оставлять запас: куча обычно 50–75% лимита контейнера, остальное — на всё остальное; для разбора — Native Memory Tracking (-XX:NativeMemoryTracking=summary).

14.7Настройка и диагностика

-XX:MaxRAMPercentage=70                   # куча как доля памяти контейнера (по умолчанию 25%)

-XX:+HeapDumpOnOutOfMemoryError           # снять дамп кучи при OOM
-XX:HeapDumpPath=/dumps
-XX:+ExitOnOutOfMemoryError               # не продолжать работу в непредсказуемом состоянии

jcmd <pid> GC.heap_dump /tmp/heap.hprof   # дамп кучи для Eclipse MAT / VisualVM
jcmd <pid> VM.native_memory summary       # память вне кучи
jcmd <pid> JFR.start duration=60s filename=/tmp/rec.jfr   # запись профиля: аллокации, паузы, блокировки
jstat -gcutil <pid> 1000                  # заполнение поколений и счётчики сборок раз в секунду
Как искать утечку
  1. Посмотреть график занятости кучи после сборок: при утечке нижняя граница «пилы» неуклонно растёт.
  2. Снять два дампа или две гистограммы классов с интервалом и сравнить: какие классы прибавились.
  3. В анализаторе (Eclipse MAT) открыть дерево доминаторов: какой объект удерживает больше всего памяти (retained size).
  4. Проследить путь от него до корня GC — он покажет, какое поле не даёт объектам умереть.

Настройка сборщика — последний шаг, а не первый. Сначала измерить (журнал сборок, JFR), затем уменьшить объём создаваемых и долго живущих объектов, подобрать размер кучи — и только потом менять параметры сборщика. Большинство «проблем GC» оказываются проблемами приложения: утечкой, огромной выборкой из базы, кэшем без границ.

14.8Интерактив: сборка мусора по поколениям

Симулятор: Eden → Survivor → Old

Eden вмещает 8 объектов, каждый Survivor — 4. Объект, переживший 3 сборки, переходит в Old (порог MaxTenuringThreshold, здесь 3; в HotSpot по умолчанию 15). Зелёные объекты достижимы, красные — мусор.

Eden
Survivor S0
Survivor S1
Old generation

Попробуйте: (1) создавайте объекты и сразу теряйте ссылки — почти ничего не доходит до Old: это «слабая гипотеза о поколениях» в действии. (2) Создайте много объектов, не теряя ссылок: Survivor переполняется, и объекты уходят в Old раньше срока (преждевременное повышение) — причина роста Old и частых Full GC. Число на объекте — возраст (сколько сборок он пережил).

14.9Практикум: пишем и запускаем

Три эксперимента с памятью на уровне Java-разработчика: где живут переменные и объекты, как выглядит работа сборщика в логе и как найти утечку на работающем процессе. Глубже — в пособии JVM изнутри (темы 9–15). Модуль IDEA — ch14.

Код набирайте руками — так он запоминается. Перед запуском запишите предсказание в поле «Ваш прогноз», затем сверьтесь с реальным выводом (снят на JDK 25.0.2; адреса, времена и хэши у вас будут другими). Как подготовить окружение — на странице курса.

Лаба 14.1Стек и куча: две разные ошибки15 мин

Переполнить стек рекурсией и кучу объектами и сравнить, от чего зависит каждая ошибка.

  1. Создайте файл StackHeap.java:
    import java.util.ArrayList;
import java.util.List;

public class StackHeap {
    static int depth = 0;
    static void recurse() { depth++; recurse(); }

    public static void main(String[] args) {
        try { recurse(); }
        catch (StackOverflowError e) { System.out.println("StackOverflowError на глубине " + depth); }

        List<int[]> hog = new ArrayList<>();
        try {
            while (true) hog.add(new int[1_000_000]);
        } catch (OutOfMemoryError e) {
            int mb = hog.size() * 4;
            hog = null;                                    // освобождаем, чтобы было на что печатать
            System.out.println("OutOfMemoryError после ~" + mb + " МБ: " + e.getMessage());
        }
    }
}

    IDEAVM options: -Xmx128m -Xss512k

    javac StackHeap.java
java -Xmx128m -Xss512k StackHeap
    Вывод (JDK 25.0.2)
    StackOverflowError на глубине 9716
OutOfMemoryError после ~124 МБ: Java heap space
  2. Что изменится при -Xmx256m -Xss2m?
    java -Xmx256m -Xss2m StackHeap
    Вывод (JDK 25.0.2)
    StackOverflowError на глубине 86717
OutOfMemoryError после ~252 МБ: Java heap space

    Глубина рекурсии вырастет в 4–5 раз (стек потока в 4 раза больше), объём до OOM — примерно вдвое. Локальные переменные и кадры вызовов живут в стеке своего потока (-Xss), объекты — в общей куче (-Xmx). Ловить OutOfMemoryError в реальном коде почти всегда бессмысленно — здесь это только для демонстрации.

Лаба 14.2Сборщик за работой: читаем лог15 мин

Включить лог GC и увидеть, что короткоживущий мусор убирается быстро и дёшево.

  1. Создайте файл Churn.java:
    import java.util.ArrayList;
import java.util.List;

public class Churn {
    public static void main(String[] args) {
        List<String> keep = new ArrayList<>();
        for (int i = 0; i < 3_000_000; i++) {
            String tmp = "запрос-" + i;                    // мусор сразу после итерации
            if (i % 1000 == 0) keep.add(tmp);              // 0,1% живёт долго
        }
        System.out.println("сохранено: " + keep.size());
    }
}

  2. Сколько длится одна пауза и сколько памяти остаётся после каждой сборки?

    Паузы — доли миллисекунды или единицы мс, «после» (число справа от стрелки) — единицы МБ. Молодая сборка копирует только живые объекты, а их почти нет: стоимость сборки пропорциональна живым данным, а не мусору. Поэтому в Java дёшево создавать много короткоживущих объектов.

  • Почини утечку, ограничив размер «кэша» через LinkedHashMap с removeEldestEntry (лаба 9.3), и повтори гистограммы.
    Числа Session стабилизируются на пределе кэша — так выглядит здоровый ограниченный кэш.

14.10Самопроверка

Как сборщик мусора определяет, что объект можно удалить?

  • По счётчику ссылок на объект
  • По времени жизни объекта
  • По недостижимости от GC roots: локальных переменных в стеках потоков, статических полей, JNI-ссылок
  • По вызову System.gc()
Подсчёт ссылок не справляется с циклами. Java обходит граф от корней; всё, до чего не дошли, — мусор, даже если объекты ссылаются друг на друга.

Что вызывает OutOfMemoryError: Java heap space, если мусор собирается исправно?

  • Слишком много потоков
  • Утечка: объекты остаются достижимыми (статическая коллекция, кэш без лимита, ThreadLocal в пуле потоков, слушатели без отписки)
  • Слишком большой стек
  • Нехватка места на диске
GC не может удалить то, на что есть ссылка. Диагностика: heap dump (-XX:+HeapDumpOnOutOfMemoryError) и анализ dominator tree в MAT.

Какой сборщик используется по умолчанию на серверной машине в современных JDK и чем он характерен?

  • G1: куча из регионов, цель по длительности паузы (MaxGCPauseMillis), сборка самых «мусорных» регионов первыми
  • Serial: один поток, полная остановка
  • CMS
  • Epsilon
G1 — по умолчанию с Java 9. Для пауз менее миллисекунды на больших кучах — ZGC (поколенческий с Java 21) или Shenandoah.
Что хранится в стеке, а что в куче?

В стеке потока — кадры вызовов: параметры, локальные переменные примитивных типов и ссылки на объекты. В куче — сами объекты и массивы, включая их поля. Стек свой у каждого потока и освобождается при возврате из метода; куча общая и очищается сборщиком мусора.

Как сборщик понимает, что объект — мусор? Что с циклическими ссылками?

По достижимости: объект жив, если до него можно дойти от корней — локальных переменных в стеках, статических полей, активных потоков, ссылок JNI. Подсчёт ссылок не используется, поэтому группа объектов, ссылающихся друг на друга, но недостижимых от корней, собирается целиком.

Зачем куча разделена на поколения?

Большинство объектов живёт очень недолго. Собирая только молодое поколение копированием выживших, JVM тратит время пропорционально числу живых объектов, которых мало, и делает это часто и быстро. Долгоживущие объекты переносятся в старое поколение и проверяются редко.

Возможна ли утечка памяти в Java? Приведите три примера.

Да: ненужный объект остаётся достижимым. Примеры: растущая статическая коллекция или кэш без ограничения; ThreadLocal без remove() в потоке из пула; незарегистрированный отписавшийся слушатель; экземпляр внутреннего класса, удерживающий внешний объект; ключ HashMap, изменённый после вставки.

Под сервиса перезапускается с кодом 137, в логах нет OutOfMemoryError. Что происходит?

Процесс убит ядром за превышение лимита памяти контейнера. Суммарная память процесса (куча, Metaspace, стеки, прямые буферы, структуры сборщика) превысила лимит, хотя куча могла быть не заполнена. Нужно уменьшить долю кучи или увеличить лимит и разобраться с памятью вне кучи через Native Memory Tracking.

G1 или ZGC?

G1 — разумное значение по умолчанию: хорошая пропускная способность, паузы в десятки–сотни миллисекунд. ZGC — когда важна задержка (жёсткие требования к p99, большие кучи): паузы меньше миллисекунды ценой дополнительного расхода процессора и памяти. Выбор подтверждают измерением на своей нагрузке.
