String и строковый пул

Строки — самый используемый тип в любой программе: ключи, идентификаторы, JSON, логи. Поэтому у String особый статус: он неизменяем, литералы хранятся в общем пуле, а компилятор и JVM оптимизируют работу с ним отдельно.

3.1Неизменяемость

Объект String после создания не меняется. Любой метод, «изменяющий» строку, возвращает новый объект.

String name = "  alice ";
name.trim();              // результат выброшен, name не изменилась
name.toUpperCase();
System.out.println(name); // "  alice "
name = name.trim().toUpperCase();   // "ALICE"

Зачем это нужно

  • Безопасность. Строку с путём к файлу или именем класса нельзя подменить после проверки.
  • Потокобезопасность. Неизменяемый объект можно без синхронизации отдавать любым потокам.
  • Кэш хэша. hashCode() вычисляется один раз — строки идеальны как ключи HashMap.
  • Пул. Одинаковые литералы могут быть одним объектом только потому, что его никто не изменит.

Чем обеспечивается

  • Класс final — нельзя унаследовать и переопределить поведение.
  • Внутренний массив private final и никогда не отдаётся наружу.
  • Нет ни одного метода, меняющего массив.

Это образец для собственных неизменяемых классов (тема 05).

3.2Внутреннее устройство

public final class String {
    private final byte[] value;   // содержимое
    private final byte coder;     // 0 — LATIN1 (1 байт на символ), 1 — UTF16 (2 байта)
    private int hash;             // кэш hashCode, вычисляется при первом вызове
}
  • Compact strings (Java 9+). Если все символы помещаются в Latin-1, строка хранится по байту на символ, иначе — по два. Для типичного приложения с идентификаторами и английским текстом это уменьшило память под строки почти вдвое. Одна кириллическая буква переводит всю строку в UTF-16.
  • length() возвращает число кодовых единиц UTF-16, а не символов, видимых человеку. Символы вне базовой плоскости занимают две единицы (суррогатную пару).
String s = "a😀";
s.length();                         // 3
s.codePointCount(0, s.length());    // 2 — число кодовых точек Юникода
s.charAt(1);                        // половина эмодзи — бессмысленный символ
new StringBuilder(s).reverse();     // корректно: reverse учитывает суррогатные пары

Хэш вычисляется по формуле s[0]·31ⁿ⁻¹ + s[1]·31ⁿ⁻² + … + s[n−1]. Разные строки могут давать одинаковый хэш: у "Aa" и "BB" он равен 2112. На этом строится атака на хэш-таблицы и защита от неё в HashMap (тема 09).

3.3Пул строк

Пул — таблица уникальных строк внутри JVM. Каждый строковый литерал попадает в неё при загрузке класса, и все одинаковые литералы во всей программе — один объект. Оператор new всегда создаёт новый объект в куче в обход пула.

String a = "java";
String d = "ja" + "va";            // константное выражение: компилятор сам запишет "java"
String part = "ja";
String e = part + "va";            // вычисляется при выполнении — новый объект в куче
final String fp = "ja";
String f = fp + "va";              // final-переменная с литералом — тоже константа

a == d;            // true
a == e;            // false
a == f;            // true
a == e.intern();   // true: intern() возвращает экземпляр из пула
Строки сравнивают через equals == проверяет, один ли это объект, и «работает» ровно до тех пор, пока обе строки — литералы. Строка из базы данных, HTTP-запроса или результата substring — отдельный объект, и == вернёт false при одинаковом содержимом. Безопасная форма при возможном null: "ADMIN".equals(role) или Objects.equals(a, b).
  • Пул находится в куче (с Java 7; раньше — в PermGen) и очищается сборщиком мусора.
  • intern() вручную кладёт строку в пул. Имеет смысл редко — когда в памяти миллионы повторяющихся строк; обычно выгоднее собственный HashMap для дедупликации или опция G1 -XX:+UseStringDeduplication.
  • Сколько объектов создаёт new String("java")? Один в куче при выполнении; литерал "java" попал в пул ещё при загрузке класса. Отсюда типичный ответ «один или два».

3.4Конкатенация и StringBuilder

Оператор + для строк компилятор превращает в вызов, который один раз вычисляет итоговую длину и собирает строку (с Java 9 — через invokedynamic, раньше — через временный StringBuilder). В одном выражении это эффективно. Проблема возникает в цикле.

String csv2 = String.join(",", items);                                  // ещё проще

3.6Строки и байты

Строка — последовательность символов; файл и сеть передают байты. Преобразование между ними задаёт кодировка, и её нужно указывать явно.

byte[] bytes = text.getBytes(StandardCharsets.UTF_8);
String back  = new String(bytes, StandardCharsets.UTF_8);

"я".getBytes(StandardCharsets.UTF_8).length;       // 2
"я".getBytes(StandardCharsets.UTF_16LE).length;    // 2
"😀".getBytes(StandardCharsets.UTF_8).length;      // 4
Кодировка по умолчанию getBytes() и new String(bytes) без аргумента используют кодировку платформы. До Java 18 она зависела от ОС (Cp1251 на русской Windows, UTF-8 на Linux) — код, работавший у разработчика, превращал кириллицу в «кракозябры» на сервере. С Java 18 по умолчанию всегда UTF-8, но явное указание по-прежнему обязательно: оно документирует намерение и работает на любой версии.

Пароли и секреты. Строку нельзя стереть из памяти — она живёт до сборки мусора и может попасть в дамп кучи. Поэтому API безопасности (JPasswordField, PBEKeySpec) принимают char[], который можно обнулить сразу после использования.

Литерал

При загрузке класса литерал "java" попадает в пул констант класса; при первом использовании (ldc) JVM ищет такую строку в String Table, не находит и добавляет. a указывает на объект в пуле.

Тот же литерал

Строка уже в пуле — возвращается та же ссылка. a == b → true.

new String

new всегда создаёт новый объект в куче, даже если такая строка есть в пуле. Массив символов внутри общий, но объект другой. a == c → false, a.equals(c) → true.

intern()

Ищет в пуле строку, равную c по equals, и возвращает ссылку из пула (если нет — добавляет саму строку). a == d → true.

Константное выражение

Оба операнда — литералы, поэтому javac склеивает их при компиляции: в class-файле лежит готовый "java". a == e → true.

Конкатенация во время выполнения

part — обычная переменная, компилятор не знает её значения. Конкатенация выполняется в рантайме (через invokedynamic → StringConcatFactory, до Java 9 — StringBuilder) и создаёт новую строку в куче. a == f → false.

final-константа

final String p2 = "ja" — константа времени компиляции, поэтому p2 + "va" снова склеивается компилятором. a == g → true. Одно слово final меняет результат сравнения ссылок — ещё одна причина сравнивать строки только через equals.

Лаба 3.2+= в цикле против StringBuilder15 мин

Измерить квадратичную стоимость конкатенации в цикле.

  1. Создайте файл Concat.java:
    public class Concat {
    public static void main(String[] args) {
        for (int n : new int[] { 5_000, 20_000, 40_000, 80_000 }) {      // первый прогон — разогрев JIT
            long t = System.nanoTime();
            String s = "";
            for (int i = 0; i < n; i++) s += "x";
            long plus = System.nanoTime() - t;

            t = System.nanoTime();
            StringBuilder sb = new StringBuilder();
            for (int i = 0; i < n; i++) sb.append("x");
            String r = sb.toString();
            long builder = System.nanoTime() - t;

            System.out.printf("n=%,6d: += %6.1f мс, StringBuilder %5.2f мс (длины %d/%d)%n",
                    n, plus / 1e6, builder / 1e6, s.length(), r.length());
        }
    }
}
  2. Во сколько раз вырастет время += при удвоении n? А у StringBuilder?
    javac Concat.java
java Concat
    Вывод (JDK 25.0.2)
    n= 5,000: +=   10.6 мс, StringBuilder  0.73 мс (длины 5000/5000)

    У += — в 3–4 раза (замеры «шумят», но рост явно быстрее линейного): каждая итерация копирует всю строку, суммарно ~n²/2 символов. У StringBuilder — примерно в 2 раза (линейно): массив растёт удвоением, копирований O(n). Компилятор не превращает цикл с += в один StringBuilder — оптимизируется только одно выражение.

Лаба 3.3Строки и байты: кодировки15 мин

Увидеть, что длина строки, число байт и число «символов на экране» — разные числа, и получить «кракозябры» своими руками.

  1. Создайте файл Bytes.java:
    import java.nio.charset.Charset;
import java.nio.charset.StandardCharsets;

public class Bytes {
    public static void main(String[] args) {
        String s = "Привет";
        System.out.println("length()       = " + s.length());
        System.out.println("UTF-8 байт     = " + s.getBytes(StandardCharsets.UTF_8).length);
        System.out.println("UTF-16 байт    = " + s.getBytes(StandardCharsets.UTF_16).length);
        System.out.println("windows-1251   = " + s.getBytes(Charset.forName("windows-1251")).length);

        byte[] utf8 = s.getBytes(StandardCharsets.UTF_8);
        System.out.println("UTF-8 как 1251 = " + new String(utf8, Charset.forName("windows-1251")));
        System.out.println("UTF-8 как Latin-1 = " + new String(utf8, StandardCharsets.ISO_8859_1));

        System.out.println("default charset = " + Charset.defaultCharset());
        System.out.println("stdout.encoding = " + System.getProperty("stdout.encoding"));
    }
}

  • Ни одного
Литерал интернируется в пул, конструктор создаёт отдельный объект в куче. Если литерал уже был в пуле — создаётся только один.

Почему конкатенация в цикле через s += x — плохая идея?

  • Она не компилируется
  • Строки пула переполняются
  • Строки неизменяемы: каждая итерация создаёт новую строку и копирует всё накопленное — O(n²)
  • Оператор += не работает со строками
Используйте StringBuilder (один изменяемый буфер) или String.join / Collectors.joining.

Почему String хорош как ключ HashMap?

  • Он неизменяем, поэтому hashCode не меняется и кэшируется в поле объекта
  • У него нет метода hashCode
  • Строки всегда лежат в пуле
  • HashMap обрабатывает строки особым образом
Неизменяемость гарантирует, что ключ не «потеряется» в таблице, а кэш хэша делает повторные вычисления бесплатными.
Почему String неизменяем? Назовите минимум три причины.

Безопасность (строку нельзя изменить после проверки — пути, имена классов, параметры подключения); потокобезопасность без синхронизации; возможность кэшировать hashCode и надёжно использовать строки как ключи; возможность пула строк — общий объект безопасен только потому, что его никто не изменит.

String s1 = "hi"; String s2 = new String("hi"); String s3 = s2.intern(); — какие сравнения через == истинны?

s1 == s3 — true: intern() вернул объект из пула, тот же, на который указывает литерал. s1 == s2 и s2 == s3 — false: new создал отдельный объект в куче.

Почему конкатенация в цикле через += медленная, если компилятор и так использует эффективную сборку?

Оптимизация действует в пределах одного выражения. На каждой итерации создаётся новая строка, в которую копируется всё накопленное содержимое: суммарно 1 + 2 + … + n копирований, то есть O(n²). Один StringBuilder вне цикла дописывает в общий буфер — O(n).

Чем StringBuilder отличается от StringBuffer?

Методы StringBuffer синхронизированы, StringBuilder — нет, поэтому он быстрее. Синхронизация на уровне отдельного вызова редко полезна: последовательность из нескольких append всё равно не атомарна. В новом коде используют StringBuilder.

Что вернёт "a|b|c".split("|")?

Массив из отдельных символов ["a", "|", "b", "|", "c"]: вертикальная черта в регулярном выражении означает «или», пустая альтернатива совпадает между любыми символами. Нужно экранирование: split("\\|") или split(Pattern.quote("|")).
