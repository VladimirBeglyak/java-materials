9.1Шкаф с пронумерованными ящиками

Внутри HashMap — массив «ящиков» (по умолчанию 16). Чтобы положить пару «ключ → значение», HashMap вычисляет hashCode ключа, слегка его перемешивает и по нему выбирает номер ящика. Чтобы найти — делает то же самое и смотрит только в этот ящик. Поэтому поиск почти мгновенный, сколько бы пар ни было.

put("кот", 5) и get("кот")
"кот".hashCode() → большое число → номер ящика 6 (из 16)ящик 6 пуст → кладём пару ("кот" → 5)get("кот"): снова hashCode → ящик 6в ящике 6 сравниваем ключи через equals → нашли → 5
остальные 15 ящиков даже не смотрели

Из hashCode получается номер ящика.

Пара хранится в своём ящике.

Тот же ключ — тот же ящик.

Внутри ящика ключ подтверждается через equals.

Главная мысль hashCode выбирает ящик, equals находит ключ внутри ящика.

9.2Коллизии: два ключа в одном ящике

Ящиков мало, ключей много — иногда разные ключи попадают в один ящик. Это коллизия, она нормальна: в ящике лежит маленький список пар, и нужная находится через equals. Но если в один ящик попадает очень много ключей (например, у ключей плохой hashCode, всегда одинаковый), список становится длинным и поиск — медленным. Тогда Java превращает этот ящик в сбалансированное дерево (когда в нём больше 8 элементов, а сама таблица уже достаточно большая — от 64 ящиков; иначе HashMap просто увеличивает таблицу), чтобы поиск оставался быстрым.

Главная мысль Несколько ключей в ящике — нормально. Плохой hashCode сваливает всё в один ящик и тормозит map.

9.3Расширение: шкаф побольше

Когда пар становится больше 75% от числа ящиков (load factor 0,75), HashMap заводит шкаф вдвое больше и перекладывает все пары по новым ящикам. Это дорогая операция, но редкая. Если заранее знаете, сколько будет элементов, можно создать map сразу нужного размера.

Главная мысль Заполнилось на 3/4 — шкаф удваивается, всё перекладывается.

9.4Что важно знать о HashMap

  • Порядок не гарантирован и может поменяться после расширения.
  • Один ключ null разрешён.
  • Не для многих потоков: одновременная запись из разных потоков портит её. Для этого есть ConcurrentHashMap.
  • Не меняйте ключ после того, как положили его в map: hashCode изменится, и ключ «потеряется» в чужом ящике.
Главная мысль Без порядка, не потокобезопасна, ключи должны быть неизменяемыми.

9.5Удобные методы

  • getOrDefault — значение или запасной вариант.
  • putIfAbsent — положить, только если ключа ещё нет.
  • merge — например, «прибавь 1 к счётчику слова».
  • computeIfAbsent — «если списка для ключа нет — создай и верни».
Главная мысль merge и computeIfAbsent заменяют громоздкие «если нет — создай».

9.6Другие Map

LinkedHashMap

Помнит порядок добавления. Можно сделать простой кэш, вытесняющий давно не использованное.

TreeMap

Ключи всегда отсортированы. Умеет «ближайший ключ больше X». Чуть медленнее (дерево).

ConcurrentHashMap

Для работы из многих потоков.

Главная мысль Нужен порядок добавления — LinkedHashMap, сортировка — TreeMap, потоки — ConcurrentHashMap.

9.7Множества

HashSet — это HashMap, где важны только ключи. Поэтому всё сказанное про hashCode и equals относится и к нему. Есть LinkedHashSet (с порядком добавления) и TreeSet (отсортированный).

Главная мысль Set = Map без значений.
