JDBC: работа с базой данных без фреймворков

Hibernate, Spring Data, jOOQ, MyBatis — все они в итоге вызывают JDBC. Когда ORM выдаёт странный SQL, соединения в пуле заканчиваются, а транзакция «не откатывается», разбираться приходится на этом уровне. Здесь — весь API java.sql, который нужно знать: соединения, подготовленные запросы, транзакции, пакетная вставка и главная уязвимость — SQL-инъекция.

22.2Запрос от начала до конца

record Order(long id, String customer, BigDecimal total, Instant createdAt) { }

List<Order> findByCustomer(DataSource ds, String customer) throws SQLException {
    String sql = "SELECT id, customer, total, created_at FROM orders WHERE customer = ? ORDER BY created_at DESC";
    try (Connection c = ds.getConnection();                          // взять соединение из пула
         PreparedStatement ps = c.prepareStatement(sql)) {
        ps.setString(1, customer);                                    // параметры нумеруются с 1
        try (ResultSet rs = ps.executeQuery()) {
            List<Order> result = new ArrayList<>();
            while (rs.next()) {                                       // курсор стоит ПЕРЕД первой строкой
                result.add(new Order(rs.getLong("id"), rs.getString("customer"),
                        rs.getBigDecimal("total"), rs.getObject("created_at", OffsetDateTime.class).toInstant()));
            }
            return result;
        }
    }                                                                 // close() в обратном порядке: rs → ps → c (возврат в пул)
}
Три ресурса — три закрытия Незакрытый Connection не возвращается в пул: через несколько минут под нагрузкой пул пуст, и приложение стоит. Только try-with-resources. close() у соединения из пула не закрывает TCP-соединение, а возвращает его в пул.
NULL и примитивы rs.getInt("qty") для SQL NULL вернёт 0. Проверка: rs.wasNull() сразу после чтения или rs.getObject("qty", Integer.class), который вернёт null. Запись NULL: ps.setNull(1, Types.INTEGER) или ps.setObject(1, null).

22.4Транзакции

void transfer(DataSource ds, long from, long to, BigDecimal amount) throws SQLException {
    try (Connection c = ds.getConnection()) {
        c.setAutoCommit(false);                                  // по умолчанию true: каждое выражение — своя транзакция
        try (PreparedStatement debit  = c.prepareStatement("UPDATE accounts SET balance = balance - ? WHERE id = ? AND balance >= ?");
             PreparedStatement credit = c.prepareStatement("UPDATE accounts SET balance = balance + ? WHERE id = ?")) {
            debit.setBigDecimal(1, amount); debit.setLong(2, from); debit.setBigDecimal(3, amount);
            if (debit.executeUpdate() != 1) throw new InsufficientFundsException(from);   // число изменённых строк
            credit.setBigDecimal(1, amount); credit.setLong(2, to);
            credit.executeUpdate();
            c.commit();
        } catch (Exception e) {
            c.rollback();                                        // без него транзакция осталась бы открытой
            throw e;
        } finally {
            c.setAutoCommit(true);                               // соединение вернётся в пул — оставляем в исходном состоянии
        }
    }
}

Транзакция — это состояние соединения: всё, что должно быть атомарно, выполняется через один Connection. Именно этот шаблон (взять соединение, выключить autocommit, commit/rollback, вернуть) автоматизирует @Transactional в Spring, пряча соединение в ThreadLocal.

22.5Пакетные операции и большие выборки

try (PreparedStatement ps = c.prepareStatement("INSERT INTO events(id, type, payload) VALUES (?, ?, ?::jsonb)")) {
    int n = 0;
    for (Event e : events) {
        ps.setObject(1, e.id()); ps.setString(2, e.type()); ps.setString(3, e.json());
        ps.addBatch();
        if (++n % 1000 == 0) ps.executeBatch();              // порциями, чтобы не держать всё в памяти
    }
    ps.executeBatch();
}
// PostgreSQL: в URL добавьте reWriteBatchedInserts=true — драйвер склеит вставки в многострочный INSERT (в разы быстрее)

// Сгенерированный ключ:
PreparedStatement ps = c.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS);
ps.executeUpdate();
try (ResultSet keys = ps.getGeneratedKeys()) { keys.next(); long id = keys.getLong(1); }

Почему batch быстрее

10 000 отдельных INSERT — 10 000 сетевых обменов «запрос-ответ». Batch отправляет их пачкой за один обмен. Время определяется не работой БД, а сетевыми задержками.

Чтение миллионов строк

По умолчанию драйвер PostgreSQL загружает весь результат в память. Потоковое чтение: autoCommit=false и ps.setFetchSize(1000) — строки приходят порциями через серверный курсор.

22.6Пул соединений

HikariConfig cfg = new HikariConfig();
cfg.setJdbcUrl("jdbc:postgresql://db:5432/shop");
cfg.setUsername("shop"); cfg.setPassword(System.getenv("DB_PASSWORD"));
cfg.setMaximumPoolSize(10);                    // больше — не значит быстрее: БД ограничена ядрами и дисками
cfg.setConnectionTimeout(3_000);               // сколько ждать свободное соединение
cfg.setMaxLifetime(30 * 60_000);               // пересоздавать раньше, чем соединение закроет БД или сетевое оборудование
try (HikariDataSource ds = new HikariDataSource(cfg)) { /* приложение */ }

Создание соединения — TCP, TLS, аутентификация, выделение процесса на стороне PostgreSQL: десятки миллисекунд. Пул держит готовые соединения и выдаёт их за микросекунды. Подробности настройки и диагностики — пособие Spring, тема 12.

22.8Самопроверка

Почему PreparedStatement защищает от SQL-инъекции?

  • Он экранирует кавычки в строках
  • Текст запроса и значения параметров передаются раздельно: значение не разбирается как SQL
  • Он проверяет ввод регулярным выражением
  • Он шифрует запрос
Это не экранирование, а разделение кода и данных на уровне протокола.

Столбец discount INTEGER NULL содержит NULL. Что вернёт rs.getInt("discount")?

  • null
  • Исключение
  • 0 — и только rs.wasNull() позволит отличить его от настоящего нуля
  • -1
Примитив не может быть null. Используйте getObject("discount", Integer.class).

Метод выполняет два UPDATE через ds.getConnection(), вызванный дважды. Будут ли они в одной транзакции?

  • Нет: транзакция принадлежит соединению, а это два разных соединения
  • Да, если один поток
  • Да, если autocommit выключен
  • Зависит от пула
Атомарность требует одного Connection. Spring решает это привязкой соединения к потоку.

Что произойдёт, если не закрыть Connection, взятый из пула?

  • Его закроет сборщик мусора без последствий
  • Ничего
  • Транзакция закоммитится автоматически
  • Соединение не вернётся в пул; со временем пул исчерпается, и запросы начнут падать по таймауту ожидания
Утечка соединений — одна из самых частых причин «приложение повисло». HikariCP умеет её обнаруживать: leakDetectionThreshold.
Опишите шаги выполнения запроса через JDBC.

Получить Connection из DataSource → prepareStatement с плейсхолдерами → установить параметры → executeQuery/executeUpdate → пройти ResultSet курсором next(), читая столбцы → закрыть ResultSet, Statement, Connection (try-with-resources) → обработать SQLException.

Как реализовать транзакцию на чистом JDBC?

На одном соединении: setAutoCommit(false) → операции → commit(); при исключении — rollback(); в finally вернуть autocommit и закрыть соединение. Все участвующие операции обязаны использовать это же соединение.

Как быстро вставить миллион строк?

PreparedStatement + addBatch/executeBatch порциями по 500–5000, одна транзакция на порцию или несколько порций, reWriteBatchedInserts для PostgreSQL; для максимальной скорости — COPY через API драйвера (CopyManager). Отключить на время лишние индексы, если это разовая загрузка.
