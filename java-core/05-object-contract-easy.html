equals, hashCode и неизменяемость — простыми словами

5.1Общий предок Object

Все классы Java — наследники Object. От него у каждого объекта есть equals (равен ли другому), hashCode (числовой «номер ящика»), toString (текстовое описание) и несколько служебных методов. По умолчанию equals сравнивает адреса, то есть «это тот же самый объект?» — для данных этого обычно мало.

Главная мысль Без переопределения equals считает равными только сам объект с самим собой.

5.2equals: что значит «одинаковые»

Два паспорта с одинаковой серией и номером — это один и тот же документ, даже если это две разные копии. Так и с объектами: equals определяет, какие поля важны для равенства. Правила, которые нельзя нарушать: объект равен самому себе; если A равен B, то и B равен A; если A = B и B = C, то A = C; сравнение с null — false.

Главная мысль equals сравнивает смысл (важные поля), а не адрес, и должен быть симметричным и последовательным.

5.3hashCode: номер ящика

HashMap раскладывает объекты по ящикам по их hashCode, а потом внутри ящика ищет нужный через equals (глава 09). Отсюда главное правило: равные объекты обязаны иметь одинаковый hashCode. Если переопределить equals, а hashCode забыть — два «одинаковых» объекта попадут в разные ящики, и HashMap их не найдёт.

Забыли переопределить hashCode
map.put(new Point(1, 2), "дом")
hashCode у этого объекта (по адресу) = 7731 → ящик №3map.get(new Point(1, 2))  — другой объект с теми же полями
его hashCode (по адресу) = 1955 → ящик №11в ящике №11 пусто → null
хотя equals сказал бы «равны» — до сравнения дело не дошло

Ящик выбран по hashCode первого объекта.

У второго объекта другой hashCode — смотрим в другой ящик.

Чинится переопределением hashCode по тем же полям, что и equals.

Главная мысль Переопределили equals — переопределите hashCode по тем же полям. Или используйте record (глава 12), где это сделано за вас.

5.4toString

По умолчанию объект печатается как Point@1b6d3586 — бесполезно в логах. Переопределите toString, чтобы видеть важные поля. Но не печатайте в нём пароли и персональные данные — toString часто попадает в логи.

Главная мысль Понятный toString экономит часы отладки. Секреты в него не кладите.

5.5Сравнение для сортировки

equals отвечает «равны или нет», а для сортировки нужно «кто раньше». Comparable — «естественный порядок» самого класса (числа по величине, строки по алфавиту). Comparator — внешнее правило, которое можно выбрать на месте: «людей по возрасту, а при равенстве — по имени».

Главная мысль Comparable — порядок «по умолчанию», Comparator — любой порядок по требованию.

5.6Копирование: ксерокопия или переписать

Поверхностная копия копирует поля как есть: если поле — ссылка на список, обе копии будут смотреть на один и тот же список. Глубокая копия копирует и вложенные объекты. Метод clone() в Java неудобен и капризен; проще сделать конструктор копирования или фабричный метод.

Главная мысль Поверхностная копия делит вложенные объекты. Копируйте явно, без clone().

5.7Неизменяемые объекты

Неизменяемый объект — как напечатанная книга: прочитать можно, исправить нельзя, только выпустить новое издание. Такие объекты безопасно передавать куда угодно, делить между потоками и использовать как ключи в HashMap. Рецепт: все поля private final, нет сеттеров, изменяемые части (списки) копируются при создании и не отдаются наружу как есть. Records (глава 12) почти всё это делают сами.

Главная мысль Неизменяемый объект нельзя испортить со стороны. Это проще и безопаснее.

5.9Проверьте себя

Вы переопределили equals, но не hashCode. Что сломается?

  • ничего
  • toString
  • поиск «равных» объектов в HashMap и HashSet
  • сортировка
Равные объекты окажутся в разных ящиках.

Если a.equals(b) — true, что обязано быть верно?

  • a.hashCode() == b.hashCode()
  • a == b
  • a.toString() — пустая строка
  • ничего
Главное правило контракта.

Обратное верно? Одинаковый hashCode → объекты равны?

  • да, всегда
  • да, для строк
  • да, если hashCode большой
  • нет: разные объекты могут случайно попасть в один ящик
Это коллизия; внутри ящика сравнивают через equals.

Нужно отсортировать людей по возрасту в одном месте и по имени — в другом. Что использовать?

  • переписывать equals
  • разные Comparator
  • hashCode
  • toString
Comparator — правило сортировки, выбранное на месте.

Почему неизменяемые объекты хороши как ключи HashMap?

  • они меньше
  • они быстрее создаются
  • их hashCode не изменится после того, как объект положили в map
  • их нельзя сравнить
Изменили ключ — он «переехал» бы в другой ящик, и map его потеряла бы.
