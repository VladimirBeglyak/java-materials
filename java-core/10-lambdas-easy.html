Лямбды и Optional — простыми словами

Иногда методу нужно передать не данные, а действие: как сортировать, что делать с каждым элементом, что выполнить потом. Для этого в Java есть лямбды. Разберёмся, как они выглядят, что такое функциональный интерфейс, ссылки на методы, захват переменных и Optional.

10.1Лямбда: записка с инструкцией

Раньше, чтобы передать действие, нужно было создавать целый анонимный класс — много лишних слов ради одной строчки. Лямбда — короткая запись того же самого: (a, b) -> a.length() - b.length() — «сравни две строки по длине». Как записка повару: «нарежь кубиками» вместо целого договора о нарезке.

Главная мысль Лямбда — короткая запись «вот что сделать», которую можно передать в метод.

10.2Функциональные интерфейсы

Лямбду можно передать туда, где ожидается интерфейс ровно с одним абстрактным методом — функциональный интерфейс. В Java есть готовые на все случаи:

ИнтерфейсЧто делаетПример
Function<T, R>из T делает Rстрока → её длина
Predicate<T>отвечает да/нет«число чётное?»
Consumer<T>что-то делает, ничего не возвращаетнапечатать
Supplier<T>ничего не берёт, выдаёт значение«создай новый список»
Главная мысль Лямбда подставляется вместо интерфейса с одним методом. Function, Predicate, Consumer, Supplier — основные.

10.3Ссылки на методы

Если лямбда просто вызывает существующий метод, её можно записать ещё короче: String::length вместо s -> s.length(), System.out::println вместо x -> System.out.println(x). Это как сказать «сделай как в рецепте №5» вместо пересказа рецепта.

Главная мысль Класс::метод — сокращение для лямбды, которая только вызывает метод.

10.4Как лямбда устроена внутри

Лямбда — не анонимный класс. Компилятор превращает её тело в скрытый метод, а объект-обёртку JVM создаёт «на лету» при первом использовании (через специальную команду invokedynamic). Если лямбда ничего не захватывает, один и тот же объект переиспользуется. Поэтому лямбды дешёвые.

Главная мысль Лямбда — скрытый метод + лёгкая обёртка, которую JVM создаёт при первом вызове.

В полной главе: 10.4 Как лямбда устроена внутри

10.5Захват переменных

Лямбда может использовать локальные переменные вокруг себя, но только те, что не меняются после присваивания (effectively final). Почему? Лямбда получает копию значения и может выполниться позже или в другом потоке — если бы переменная менялась, было бы непонятно, какую версию видит лямбда. Поля объекта менять можно, но это частый источник ошибок в многопоточном коде.

Главная мысль Лямбда берёт копию локальной переменной, поэтому переменная не должна меняться.

10.6Optional: может быть, а может и нет

Optional — коробка, в которой значение либо есть, либо её открывают пустой. Метод findUser(id), возвращающий Optional, честно говорит: «пользователя может не быть». Вместо проверок на null:

  • orElse(значение) — взять или запасной вариант;
  • map(...) — преобразовать, если есть;
  • orElseThrow() — взять или бросить исключение.

Optional хорош как результат метода. Не нужно делать его полем класса или параметром метода, и никогда не возвращайте сам Optional равным null.

Главная мысль Optional — честное «может не быть» в результате метода. Не поле, не параметр, не null.

Какой интерфейс подходит для «проверь, чётное ли число»?

  • Supplier
  • Predicate
  • Consumer
  • Runnable
Predicate отвечает да/нет.

Почему лямбда не может использовать локальную переменную, которую потом меняют?

  • это ошибка Java
  • лямбды не видят переменных
  • для скорости
  • лямбда получает копию и может выполниться позже — версия была бы неясна
Поэтому только effectively final.

  • String::length

  • никак
