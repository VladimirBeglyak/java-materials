Сборка: Maven и Gradle — простыми словами

Настоящий проект — это сотни файлов и десятки библиотек. Собирать его руками невозможно. Разберёмся, что на самом деле делает сборка, как работают Maven и Gradle, откуда берутся конфликты версий и почему сборка должна давать одинаковый результат на любом компьютере.

21.1Что делают инструменты

  1. Скачать библиотеки нужных версий из репозитория (Maven Central).
  2. Скомпилировать javac, подставив библиотеки в classpath — список мест, где искать классы.
  3. Запустить тесты.
  4. Упаковать в JAR — zip-архив с классами и описанием (manifest).

Всё это можно сделать руками, но на десятом файле и третьей библиотеке это становится невозможным.

Главная мысль Сборщик: зависимости → компиляция → тесты → JAR. Автоматически и одинаково.

21.2Maven: рецепт по шаблону

В Maven проект описывается файлом pom.xml: имя, версия, зависимости. Порядок сборки фиксирован — жизненный цикл: compile → test → package → install. Команда mvn package выполнит все этапы до упаковки. Папки тоже стандартные: код в src/main/java, тесты в src/test/java. Это как готовить по строгому шаблонному рецепту — меньше свободы, зато везде одинаково.

Главная мысль Maven — описание в pom.xml и стандартный жизненный цикл.

21.3Транзитивные зависимости и конфликты

Вы подключили библиотеку A, а она тянет за собой B, а та — C. Это транзитивные зависимости. Беда, когда две ваши библиотеки требуют разные версии одной и той же третьей. В итоге в программу попадёт только одна, и вторая библиотека может сломаться с ошибкой вроде NoSuchMethodError.

Конфликт версий
ваш проект → библиотека A → jackson 2.15
ваш проект → библиотека B → jackson 2.17в classpath может быть только одна версия jackson
Maven выбирает «ближайшую» в дереве, Gradle — самую новуювыбрана 2.15, а B вызывает метод, появившийся в 2.17
→ NoSuchMethodError во время работылечение: посмотреть дерево (mvn dependency:tree),
зафиксировать версию явно (dependencyManagement / BOM)

Разные библиотеки хотят разные версии.

Сборщик выбирает одну по своим правилам.

Ошибка проявится только во время работы.

Смотрим дерево и явно фиксируем версию.

Главная мысль Разные версии одной библиотеки — частая причина странных ошибок. Смотрите дерево зависимостей и фиксируйте версии.

21.4Gradle: гибкий сборщик

Gradle описывает сборку кодом (на Kotlin или Groovy) в файле build.gradle.kts. Он гибче Maven и обычно быстрее благодаря кэшу и инкрементальной сборке: пересобирает только изменившееся. Обёртка gradlew в проекте скачивает нужную версию Gradle сама — у всех разработчиков одинаковая. Maven проще и предсказуемее, Gradle гибче и быстрее; оба отличные.

Главная мысль Gradle — сборка как код, кэш и скорость; запускайте через gradlew.

В полной главе: 21.4 Gradle

21.5Воспроизводимость

Сборка должна давать одинаковый результат на ноутбуке разработчика, в CI и через год. Для этого: фиксированные версии зависимостей (без «последней»), обёртки mvnw/gradlew, зафиксированная версия JDK, по возможности — lock-файлы зависимостей.

Главная мысль Никаких «последних версий» — всё зафиксировано.

21.7Проверьте себя

Что такое classpath?

  • путь к JDK
  • папка с исходниками
  • список мест, где JVM ищет классы
  • переменная с паролем
Туда попадают ваши классы и библиотеки.

После обновления библиотеки появился NoSuchMethodError. Вероятная причина?

  • конфликт версий: в classpath попала другая версия зависимости
  • опечатка в коде
  • мало памяти
  • ошибка JVM
Смотрите дерево зависимостей.

Зачем в проекте gradlew или mvnw?

  • для красоты
  • чтобы запускать тесты быстрее
  • для деплоя
  • чтобы у всех была одинаковая версия сборщика
Воспроизводимость.

Какая команда Maven скомпилирует, прогонит тесты и соберёт JAR?

  • mvn clean
  • mvn package
  • mvn compile
  • mvn run
package выполняет все этапы цикла до упаковки.

Почему не стоит указывать «последнюю» версию библиотеки?

  • она медленнее
  • она платная
  • сборка станет невоспроизводимой: завтра может приехать другая версия
  • это запрещено
Версии фиксируют явно.
