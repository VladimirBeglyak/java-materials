Ввод-вывод — простыми словами

Программы читают файлы, пишут логи, получают данные по сети. Разберёмся, чем байты отличаются от символов, зачем нужна буферизация, как просто работать с файлами через Files и Path, что такое NIO и почему встроенную Java-сериализацию лучше не использовать.

13.1Байтовые и символьные трубы

Данные текут по «трубам» — потокам ввода-вывода (не путать со Stream API!). Трубы бывают двух видов:

Байтовые (InputStream / OutputStream)

Для любых данных: картинки, архивы, сеть. Байты как есть.

Символьные (Reader / Writer)

Для текста: сами переводят байты в символы по кодировке. Кодировку указывайте явно — UTF-8.

Главная мысль Не текст — байтовые потоки, текст — символьные с явной кодировкой.

13.2Буферизация: носить ведром, а не ложкой

Каждое обращение к диску или сети — поход к операционной системе, а это дорого. Читать файл по одному байту — как носить воду ложкой. Буфер — ведро: набирается сразу много (обычно 8 КБ), а программа берёт из ведра. Поэтому файлы читают через BufferedReader / BufferedInputStream. При записи не забудьте, что данные могут сидеть в ведре, пока его не опустошат (flush или закрытие).

Главная мысль Буферизуйте ввод-вывод. Записанное попадает на место после flush или close.

В полной главе: 13.2 Буферизация

13.3Files и Path: просто о файлах

Для повседневных задач есть класс Files: прочитать файл целиком (readString), построчно (lines), записать (writeString), скопировать, удалить, обойти папку. Path — путь к файлу, который правильно работает и в Windows, и в Linux. Старый класс File лучше не использовать в новом коде.

Главная мысль Path + Files — современный и простой способ работы с файлами.

В полной главе: 13.3 Files и Path

13.4NIO: каналы и буферы

NIO — более низкоуровневый способ: каналы (трубы в обе стороны) и ByteBuffer (ящик с указателями «где сейчас», «до куда можно», «сколько всего»). Это нужно для быстрого копирования файлов, работы с отображением файла в память и для сетевых серверов, которые обслуживают тысячи соединений одним потоком. Обычный прикладной код с этим почти не сталкивается — его используют фреймворки вроде Netty.

Главная мысль NIO — для скорости и масштабных сетевых серверов; в обычных задачах хватает Files.

В полной главе: 13.4 NIO: каналы и буферы

13.5Встроенная сериализация — не надо

Java умеет превратить объект в байты и обратно (Serializable). Но этот механизм опасен: при чтении чужих данных злоумышленник может заставить программу выполнить вредный код, а формат хрупкий — меняется класс, и старые данные не читаются. Для обмена данными используют JSON или protobuf (глава 26).

Главная мысль Serializable — устаревший и опасный путь. Для данных — JSON, protobuf.

13.7Проверьте себя

Чем читать текстовый файл?

  • InputStream побайтово
  • Reader (или Files.readString / lines) с явной кодировкой
  • ObjectInputStream
  • ByteBuffer
Reader переводит байты в символы.

Зачем нужна буферизация?

  • чтобы шифровать данные
  • чтобы сжимать файлы
  • чтобы читать в обратном порядке
  • чтобы реже обращаться к диску и ОС, читая большими порциями
Ведро вместо ложки.

Программа записала данные через буферизованный поток и завершилась без close. Что может случиться?

  • часть данных останется в буфере и не попадёт в файл
  • файл удалится
  • ничего
  • данные запишутся дважды
Используйте try-with-resources — close сделает flush.

Почему не стоит использовать встроенную Java-сериализацию для обмена данными?

  • она медленная
  • она не работает с классами
  • она небезопасна при чтении чужих данных и хрупка при изменении классов
  • она запрещена
Лучше JSON или protobuf.

Что использовать вместо старого класса File?

  • String с путём
  • Path и Files
  • Scanner
  • URL
Современный API, удобнее и надёжнее.
