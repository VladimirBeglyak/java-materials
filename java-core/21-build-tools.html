Сборка: classpath, JAR, Maven и Gradle

IDE скрывает сборку за зелёной кнопкой — до первого NoSuchMethodError на проде или «у меня локально работает». Разберём, что на самом деле делают javac и java, как устроен JAR, как Maven и Gradle находят зависимости и почему при конфликте версий они выбирают разные варианты.

21.1Сборка руками: что делают инструменты

javac -d out -cp "lib/*" $(find src -name "*.java")     # 1. компиляция: .java → .class, зависимости на classpath
jar --create --file app.jar --main-class com.shop.Main -C out .   # 2. упаковка: zip + META-INF/MANIFEST.MF
java -cp "app.jar:lib/*" com.shop.Main                    # 3. запуск: JVM ищет классы по classpath слева направо

classpath

Упорядоченный список каталогов и jar-файлов, где загрузчик Application ищет классы (тема 15). Если класс есть в двух jar — берётся из первого. Разделитель — : в Unix, ; в Windows.

JAR

ZIP-архив с классами, ресурсами и META-INF/MANIFEST.MF (Main-Class, Class-Path). Обычный jar не содержит зависимостей; «толстый» jar Spring Boot упаковывает их внутрь и использует свой загрузчик.

Системы сборки автоматизируют эти три шага и добавляют главное: управление зависимостями — скачивание нужных jar и их транзитивных зависимостей из репозитория (Maven Central) по координатам groupId:artifactId:version.

21.2Maven

<project>
  <modelVersion>4.0.0</modelVersion>
  <groupId>com.shop</groupId> <artifactId>orders</artifactId> <version>1.4.0</version>
  <properties><maven.compiler.release>21</maven.compiler.release></properties>

  <dependencyManagement>                               <!-- версии, но не сами зависимости -->
    <dependencies><dependency>
      <groupId>org.springframework.boot</groupId><artifactId>spring-boot-dependencies</artifactId>
      <version>3.5.0</version><type>pom</type><scope>import</scope>      <!-- BOM -->
    </dependency></dependencies>
  </dependencyManagement>

  <dependencies>
    <dependency><groupId>com.fasterxml.jackson.core</groupId><artifactId>jackson-databind</artifactId></dependency>   <!-- версия из BOM -->
    <dependency><groupId>org.junit.jupiter</groupId><artifactId>junit-jupiter</artifactId><scope>test</scope></dependency>
  </dependencies>
</project>

Maven — декларативный: вы описываете проект, а порядок действий задан жизненным циклом. Вызов фазы выполняет все предыдущие.

21.3Транзитивные зависимости и конфликты версий

Вы объявляете пять зависимостей, а на classpath оказывается сто: каждая тянет свои. Одна и та же библиотека может прийти по разным путям в разных версиях — а на classpath должна быть ровно одна.

Симулятор: какую версию guava получит приложение
app ├── lib-a:1.0 │ └── guava:31.0 └── lib-b:2.0 └── lib-c:1.5 └── guava:33.0
Как жить без конфликтов Используйте BOM (bill of materials): набор версий, проверенных на совместимость, — spring-boot-dependencies, jackson-bom, testcontainers-bom. Не указывайте версии библиотек, которыми управляет BOM. Включите в CI проверку: Maven Enforcer (dependencyConvergence, banDuplicateClasses) или failOnVersionConflict() в Gradle.

21.4Gradle

plugins {
    java
    id("org.springframework.boot") version "3.5.0"
    id("io.spring.dependency-management") version "1.1.7"
}
java { toolchain { languageVersion = JavaLanguageVersion.of(21) } }   // Gradle сам найдёт или скачает JDK 21

dependencies {
    implementation("org.springframework.boot:spring-boot-starter-web")   // не видна потребителям этого модуля при компиляции
    api("com.shop:common-model:2.1.0")                                    // (плагин java-library) часть публичного API модуля
    runtimeOnly("org.postgresql:postgresql")
    compileOnly("org.projectlombok:lombok"); annotationProcessor("org.projectlombok:lombok")
    testImplementation("org.springframework.boot:spring-boot-starter-test")
}
tasks.test { useJUnitPlatform() }

implementation против api: если модуль A зависит от B через implementation, то потребители A не видят B при компиляции. Изменение B не заставляет перекомпилировать потребителей A, а внутренние зависимости не протекают наружу. api — только для типов, которые присутствуют в публичных сигнатурах модуля.

21.5Воспроизводимость

Wrapper

./mvnw, ./gradlew в репозитории фиксируют версию инструмента: у всех разработчиков и в CI сборка идёт одной версией, устанавливать ничего не нужно.

Версия Java

maven.compiler.release / toolchain: компиляция под конкретный релиз с проверкой API. release 17 на JDK 21 не даст случайно использовать методы из 21.

Никаких плавающих версий

1.+, LATEST, диапазоны [1.0,2.0) делают сборку зависимой от дня запуска. SNAPSHOT — только для разработки. В Gradle — dependency locking.

CI — источник истины

Артефакт для продакшена собирается только в CI из чистого клона, один раз, и продвигается по окружениям без пересборки.

21.6Самопроверка

Что выполнит mvn package?

  • Только упаковку jar
  • Все фазы до package включительно: ресурсы, компиляцию, тесты, упаковку
  • Упаковку и установку в ~/.m2
  • Сначала clean, потом упаковку
Фазы жизненного цикла выполняются последовательно от первой до указанной. clean — отдельный цикл.

Библиотека X приходит транзитивно: версия 1.0 на глубине 2 и версия 3.0 на глубине 3. Что выберут Maven и Gradle?

  • Оба — 3.0
  • Оба — 1.0
  • Maven — 1.0 (ближайшая), Gradle — 3.0 (наибольшая)
  • Обе версии окажутся на classpath
Разные стратегии разрешения — причина того, что проект ведёт себя по-разному после миграции между инструментами.

Какой scope у JDBC-драйвера PostgreSQL в типичном приложении?

  • runtime — код компилируется против java.sql, драйвер нужен только при выполнении
  • compile
  • provided
  • test
Так исключается случайная зависимость кода от классов конкретного драйвера.

На проде NoSuchMethodError в классе библиотеки, локально всё работает. Вероятная причина?

  • Нехватка памяти
  • Ошибка в JDK
  • Неверная кодировка исходников
  • На classpath другая версия библиотеки, чем та, под которую скомпилирован вызывающий код
Проверьте дерево зависимостей и то, из какого jar реально загружен класс (-verbose:class).
Что такое BOM и зачем он нужен?

POM-файл с секцией dependencyManagement — согласованным набором версий. Импортируется (scope import в Maven, platform() в Gradle); после этого зависимости объявляются без версий. Избавляет от конфликтов и ручного подбора совместимых версий.

Чем implementation отличается от api в Gradle?

implementation — зависимость нужна для реализации модуля и не попадает на compile classpath его потребителей (остаётся в runtime). api — зависимость является частью публичного API и видна потребителям. implementation ускоряет сборку и защищает инкапсуляцию.

Как найти, откуда пришла неожиданная версия библиотеки?

mvn dependency:tree -Dverbose (покажет «omitted for conflict») или gradlew dependencyInsight --dependency имя (покажет причину выбора). Затем — выровнять версией в dependencyManagement/constraints, обновить библиотеку-источник или исключить транзитивную зависимость.
