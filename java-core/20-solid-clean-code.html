SOLID и чистый код

Код читают в десять раз чаще, чем пишут, а меняют годами после написания. Принципы проектирования — это накопленный опыт о том, какой код дёшево менять. Здесь каждый принцип показан на паре «было — стало», с объяснением, какую именно боль он снимает, и с границей, за которой его применение превращается в переусложнение.

20.1Цель: низкая стоимость изменений

Связность (cohesion) — высокая

Всё внутри класса или модуля служит одной задаче и меняется по одной причине. Признак низкой связности: методы класса делятся на группы, которые не используют поля друг друга.

Сцепление (coupling) — низкое

Модули знают друг о друге как можно меньше: только публичный контракт. Признак сильного сцепления: правка одного класса требует правок в пяти других.

Все принципы ниже — частные способы добиться этих двух свойств.

20.2S — единственная ответственность

У класса должна быть одна причина для изменения — одна группа людей или одно требование, из-за которого его правят.

class InvoiceCalculator {            // правила бухгалтерии
    Money total(Invoice i) { /* ... */ }
}
class InvoiceRepository {            // хранение
    void save(Invoice i) { /* ... */ }
}
class InvoicePdfRenderer {           // представление
    byte[] render(Invoice i) { /* ... */ }
}
class Invoice {
    Money total() { /* налоги, скидки */ }
    void saveToDatabase() { /* SQL */ }
    byte[] toPdf() { /* шрифты, отступы */ }
}
// Смена шрифта в PDF требует пересборки и
// перетестирования расчёта налогов.
SRP — не «класс делает одну вещь» и не «один метод на класс». Десять классов по три строки, которые всегда меняются вместе, — это одна ответственность, размазанная по десяти файлам.

20.3O — открытость для расширения, закрытость для изменения

Новое поведение добавляется новым кодом, а не правкой работающего.

interface ShippingCost { Money cost(Order o); DeliveryType type(); }

@Component class CourierCost implements ShippingCost { /* ... */ }
@Component class PostCost implements ShippingCost { /* ... */ }

@Service class ShippingService {
    private final Map<DeliveryType, ShippingCost> byType;
    ShippingService(List<ShippingCost> all) {
        byType = all.stream().collect(toMap(ShippingCost::type, c -> c));
    }
    Money cost(Order o) { return byType.get(o.type()).cost(o); }
}
Money cost(Order o) {
    switch (o.type()) {
        case COURIER: return /* ... */;
        case POST:    return /* ... */;
        case PICKUP:  return Money.ZERO;
        // + DRONE: правим здесь, и в трёх других
        // switch по типу доставки
    }
}

Исключение: switch по sealed-типу или enum с проверкой полноты компилятором (тема 12) — нормальное решение, когда набор вариантов закрыт, а операций над ними много. OCP нужен там, где ожидается рост числа вариантов.

20.4L — подстановка Лисков

Код, работающий с базовым типом, должен правильно работать с любым подтипом, не зная о нём. Подтип не может требовать больше и обещать меньше, чем базовый тип.

class Rectangle { void setWidth(int w) { this.w = w; } void setHeight(int h) { this.h = h; } int area() { return w * h; } }
class Square extends Rectangle {
    @Override void setWidth(int w)  { this.w = w; this.h = w; }      // «чинит» инвариант квадрата
    @Override void setHeight(int h) { this.w = h; this.h = h; }
}
void resize(Rectangle r) { r.setWidth(5); r.setHeight(4); assert r.area() == 20; }   // для Square — 16

Признаки нарушения в реальном коде: instanceof с особым случаем для подкласса; метод подкласса бросает UnsupportedOperationException; подкласс ужесточает предусловия (не принимает null, который базовый принимал). Пример из JDK: List.of(...).add(x) бросает исключение — интерфейс List обещает больше, чем неизменяемая реализация выполняет.

Лечение: не наследовать ради переиспользования кода (композиция), делать объекты неизменяемыми (неизменяемый Square — корректный подтип неизменяемого Rectangle), разделять интерфейсы.

20.5I — разделение интерфейсов

Клиент не должен зависеть от методов, которыми не пользуется. Один «толстый» интерфейс заставляет реализации писать заглушки, а клиентов — пересобираться из-за чужих изменений.

interface OrderReader { Optional<Order> find(long id); }
interface OrderWriter { void save(Order o); }
interface OrderReports { Report monthly(YearMonth m); }

class OrderController {          // зависит только от чтения
    OrderController(OrderReader orders) { }
}
interface OrderService {
    Optional<Order> find(long id);
    void save(Order o);
    void delete(long id);
    Report monthly(YearMonth m);
    void exportToCsv(Path p);
    void sendReminderEmails();
}

20.6D — инверсия зависимостей

Модули высокого уровня (бизнес-правила) не зависят от модулей низкого уровня (БД, HTTP, файловая система). Оба зависят от абстракции, и абстракция принадлежит высокоуровневому модулю.

←

Стрелка зависимости от инфраструктуры направлена к домену. Dependency Injection (внедрение через конструктор) — механизм, который это обеспечивает; DIP — принцип, DI — техника, IoC-контейнер (Spring) — инструмент.

20.7Интерактив: рефакторинг по шагам

От «божественного» метода к читаемому коду

Было: один метод делает всё

public String process(Map<String, Object> d) {
    if (d != null) {
        if (d.get("items") != null && ((List) d.get("items")).size() > 0) {
            double t = 0;
            for (Object o : (List) d.get("items")) {
                Map m = (Map) o;
                t += (double) m.get("p") * (int) m.get("q");
            }
            if (d.get("type").equals("vip")) t = t * 0.9;
            if (t > 5000) t = t - 300;
            try { db.execute("insert into orders values (" + d.get("id") + "," + t + ")"); }
            catch (Exception e) { return "error"; }
            return "ok:" + t;
        } else return "empty";
    } else return "null";
}

Запахи: Map вместо типов, double для денег, магические числа, глубина вложенности 4, SQL-инъекция, строка как код результата, проглоченное исключение, три ответственности.

Шаг 1. Ввести типы предметной области

record OrderLine(String sku, Money price, int quantity) {
    Money total() { return price.times(quantity); }
}
record OrderRequest(long id, CustomerType type, List<OrderLine> lines) {
    OrderRequest { lines = List.copyOf(lines); }           // защитная копия, null недопустим
}

Исчезли приведения типов и строковые ключи; опечатка в имени поля теперь ошибка компиляции. Деньги — отдельный тип, а не double.

Шаг 2. Граничные случаи — в начало (guard clauses)

public Order place(OrderRequest request) {
    Objects.requireNonNull(request, "request");
    if (request.lines().isEmpty()) throw new EmptyOrderException(request.id());
    // дальше — «счастливый путь» без вложенности
}

Вложенность ушла. Ошибки стали исключениями с именем и данными, а не строками "empty" и "null", которые вызывающий обязан помнить.

Шаг 3. Назвать правила

private static final BigDecimal VIP_DISCOUNT = new BigDecimal("0.10");
private static final Money FREE_SHIPPING_THRESHOLD = Money.rub(5000);
private static final Money BULK_ORDER_BONUS = Money.rub(300);

Money price(OrderRequest r) {
    Money subtotal = r.lines().stream().map(OrderLine::total).reduce(Money.ZERO, Money::plus);
    Money discounted = r.type() == CustomerType.VIP ? subtotal.minusPercent(VIP_DISCOUNT) : subtotal;
    return discounted.isGreaterThan(FREE_SHIPPING_THRESHOLD) ? discounted.minus(BULK_ORDER_BONUS) : discounted;
}

Теперь видно, что 0.9 — скидка VIP, а 300 — бонус за крупный заказ. Расчёт — чистая функция: тестируется без БД.

Шаг 4. Расчёт, хранение и сценарий — отдельно

@Service
class PlaceOrder {
    private final PricingPolicy pricing;       // правила цены
    private final OrderRepository orders;      // хранение (параметризованные запросы)

    @Transactional
    public Order handle(OrderRequest request) {
        if (request.lines().isEmpty()) throw new EmptyOrderException(request.id());
        Order order = Order.create(request.id(), request.lines(), pricing.price(request));
        return orders.save(order);             // исключения БД не глотаем — их обработают выше
    }
}

Метод читается как описание сценария. Каждая часть меняется по своей причине и тестируется отдельно.

DRY

У каждого знания — одно место в системе. Не «никогда не повторяй строки»: два похожих куска с разными причинами изменения объединять не надо.

KISS

Простое решение, которое работает, лучше умного. Простота измеряется тем, сколько нужно знать, чтобы изменить код.

YAGNI

Не пишите то, что «может пригодиться». Неиспользуемая гибкость стоит денег сейчас и мешает настоящим изменениям потом.

20.10Практикум: пишем и запускаем

Принципы SOLID проверяются не определениями, а ответом на вопрос «что придётся менять, когда придёт новое требование». Возьмём класс, который делает всё, и проведём его через рефакторинг, сохраняя поведение: вывод программы до и после должен совпасть. В IDEA сделайте два модуля — ch20-before и ch20-after (класс OrderService есть в обоих), а в терминале работайте из каталога, где лежат папки before и after. Используйте автоматические рефакторинги IDEA (Ctrl+Alt+Shift+T): Extract Method, Extract Interface, Introduce Parameter.

Код набирайте руками — так он запоминается. Перед запуском запишите предсказание в поле «Ваш прогноз», затем сверьтесь с реальным выводом (снят на JDK 25.0.2; адреса, времена и хэши у вас будут другими). Как подготовить окружение — на странице курса.

Лаба 20.1До: класс, который делает всё10 мин

Найти в коде причины для изменения и записать их, прежде чем что-то трогать.

  1. Создайте файл before/OrderService.java:
    import java.util.List;

public class OrderService {
    record Item(String name, double price, int qty) { }

    public String checkout(String customerEmail, String customerType, List<Item> items) {
        double sum = 0;
        for (Item i : items) sum += i.price() * i.qty();
        if (customerType.equals("VIP")) sum = sum * 0.9;
        else if (customerType.equals("EMPLOYEE")) sum = sum * 0.7;
        String receipt = "Чек: " + items.size() + " поз., итого " + String.format(java.util.Locale.ROOT, "%.2f", sum);
        System.out.println("[SMTP] to=" + customerEmail + " body=" + receipt);
        System.out.println("[FILE] orders.log <- " + customerEmail + ";" + sum);
        return receipt;
    }

    public static void main(String[] args) {
        var svc = new OrderService();
        var items = List.of(new Item("кофе", 250, 2), new Item("круассан", 180, 1));
        System.out.println(svc.checkout("anna@example.com", "VIP", items));
        System.out.println(svc.checkout("boris@example.com", "REGULAR", items));
    }
}

    1) новые правила скидок (новый тип клиента) — нарушает OCP: каждый раз правим if; 2) формат чека; 3) способ уведомления (SMS вместо почты); 4) хранилище заказов (БД вместо файла). Четыре причины — четыре ответственности (SRP). Плюс класс невозможно протестировать без «отправки письма»: зависимости создаются и вызываются напрямую (DIP).

Лаба 20.2После: ответственности, абстракции, внедрение зависимостей30 мин

Разнести ответственности по интерфейсам, сделать скидки расширяемыми без правки кода (OCP) и внедрить зависимости через конструктор (DIP) — с тем же выводом.

  1. Создайте файл after/OrderService.java:
    import java.util.List;
import java.util.Locale;
import java.util.Map;

public class OrderService {
    record Item(String name, double price, int qty) { }

    interface DiscountPolicy { double apply(double sum); }
    interface Notifier { void send(String to, String body); }
    interface OrderRepository { void save(String customer, double sum); }

    static final Map<String, DiscountPolicy> DISCOUNTS = Map.of(
        "VIP", s -> s * 0.9,
        "EMPLOYEE", s -> s * 0.7);

    private final Notifier notifier;
    private final OrderRepository repository;

    OrderService(Notifier notifier, OrderRepository repository) {
        this.notifier = notifier;
        this.repository = repository;
    }

    public String checkout(String email, String customerType, List<Item> items) {
        double sum = DISCOUNTS.getOrDefault(customerType, s -> s).apply(total(items));
        String receipt = receipt(items, sum);
        notifier.send(email, receipt);
        repository.save(email, sum);
        return receipt;
    }

    static double total(List<Item> items) { return items.stream().mapToDouble(i -> i.price() * i.qty()).sum(); }
    static String receipt(List<Item> items, double sum) { return "Чек: " + items.size() + " поз., итого " + String.format(Locale.ROOT, "%.2f", sum); }

    public static void main(String[] args) {
        Notifier smtp = (to, body) -> System.out.println("[SMTP] to=" + to + " body=" + body);
        OrderRepository file = (c, s) -> System.out.println("[FILE] orders.log <- " + c + ";" + s);
        var svc = new OrderService(smtp, file);
        var items = List.of(new Item("кофе", 250, 2), new Item("круассан", 180, 1));
        System.out.println(svc.checkout("anna@example.com", "VIP", items));
        System.out.println(svc.checkout("boris@example.com", "REGULAR", items));
    }
}

Поэкспериментируйте
  • Добавьте тип клиента STUDENT со скидкой 15% — сколько файлов и строк изменилось в «после» и в «до»?

Лаба 20.3LSP: квадрат — не прямоугольник10 мин

Нарушить принцип подстановки и увидеть, как корректный для родителя код ломается на наследнике.

  1. Создайте файл Lsp.java:
    public class Lsp {
    static class Rect {
        protected int w, h;
        void setWidth(int w) { this.w = w; }
        void setHeight(int h) { this.h = h; }
        int area() { return w * h; }
    }
    static class Square extends Rect {
        @Override void setWidth(int w) { this.w = w; this.h = w; }
        @Override void setHeight(int h) { this.w = h; this.h = h; }
    }

    static void resize(Rect r) {
        r.setWidth(5);
        r.setHeight(4);
        System.out.println(r.getClass().getSimpleName() + ": ожидаем площадь 20, получили " + r.area());
    }

    public static void main(String[] args) {
        resize(new Rect());
        resize(new Square());
    }
}
    javac Lsp.java
java Lsp
    Вывод (JDK 25.0.2)
    Rect: ожидаем площадь 20, получили 20
Square: ожидаем площадь 20, получили 16

    Square «является» прямоугольником в геометрии, но не в смысле поведения: он нарушает ожидание «ширина и высота меняются независимо». Решения — неизменяемые фигуры (record Rect(int w, int h) с методом withWidth) или общий интерфейс Shape без сеттеров.

20.11Самопроверка

Класс ReportService считает показатели, форматирует Excel и отправляет письмо. Какой принцип нарушен в первую очередь?

  • LSP
  • ISP
  • SRP — три причины для изменения в одном классе
  • DIP
Изменение формата отчёта, правил расчёта и способа доставки исходит от разных людей и происходит независимо.

Метод подкласса бросает UnsupportedOperationException для операции, объявленной в базовом типе. Какой принцип нарушен?

  • OCP
  • LSP — подтип нельзя подставить вместо базового
  • SRP
  • DRY
Клиент, написанный для базового типа, сломается на этом подтипе.

Чем DIP отличается от DI?

  • DIP — принцип (зависеть от абстракций, принадлежащих высокому уровню); DI — техника передачи зависимостей извне
  • Это одно и то же
  • DI — принцип, DIP — библиотека
  • DIP применим только в Spring
Можно использовать DI и нарушать DIP: внедрять конкретный класс инфраструктуры в доменный сервис.

Два метода в разных модулях содержат одинаковые пять строк проверки. Всегда ли их нужно объединить?

  • Да, DRY запрещает любое повторение
  • Да, если строк больше трёх
  • Нет, дублирование всегда лучше

DRY — про дублирование знания. Случайно совпавший код разных требований объединять вредно.
Расскажите о SOLID на примере из своего кода.

Хороший ответ — не определения, а случай: «был сервис с тремя ответственностями, изменения в отчёте ломали расчёт; разделили — тесты стали независимыми» (SRP); «новые способы оплаты добавляются бином, реализующим интерфейс, без правки сервиса» (OCP); «домен объявляет порт, инфраструктура реализует» (DIP).

Когда следование принципам вредит?

Когда абстракция вводится без вариативности: интерфейс на каждый класс, фабрики и стратегии с одной реализацией, десятки микроклассов. Принципы — средство снизить стоимость изменений там, где изменения реально происходят.

Что такое связность и сцепление?

Связность — насколько элементы модуля относятся к одной задаче (нужна высокая). Сцепление — насколько модули зависят друг от друга (нужно низкое). Хороший модуль можно понять и изменить, не читая остальные.
