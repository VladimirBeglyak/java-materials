Дата и время: java.time

Время — источник самых дорогих и трудноуловимых ошибок: отчёт сдвинулся на день, подписка продлилась на час раньше, тест падает только в ночь перевода часов. Почти все они происходят от одной причины — перепутаны «момент времени» и «дата на календаре». Пакет java.time разводит эти понятия по разным типам; нужно понимать, какой тип что означает.

17.3Главное правило: момент и «время на стене»

Instant2026-10-10T09:15:30Z
+ ZoneId →
ZonedDateTime12:15:30 Europe/Moscow
→ toLocalDateTime →
LocalDateTime2026-10-10T12:15:30 — зона потеряна
Instant now = Instant.now();                                  // момент: одинаков во всём мире
ZonedDateTime moscow = now.atZone(ZoneId.of("Europe/Moscow")); // тот же момент глазами москвича
ZonedDateTime tokyo  = now.atZone(ZoneId.of("Asia/Tokyo"));    // и токийца
moscow.toInstant().equals(tokyo.toInstant());                  // true — это один момент

LocalDateTime wall = moscow.toLocalDateTime();                 // «12:15 на стене» — без зоны это НЕ момент
Instant back = wall.atZone(ZoneId.of("Europe/Moscow")).toInstant();   // чтобы вернуться, зону нужно знать
Типичная ошибка LocalDateTime.now() берёт время в зоне по умолчанию JVM. На ноутбуке разработчика это Москва, в контейнере — UTC: одно и то же значение в БД означает разные моменты. Для событий используйте Instant.now(), а зону сервера (-Duser.timezone=UTC) делайте явной.

Сравнивайте через isBefore/isAfter/equals. У ZonedDateTime и OffsetDateTime метод equals учитывает зону и смещение: один и тот же момент в Москве и Токио — «не равны»; для сравнения моментов есть isEqual или toInstant().

17.7Тестируемость: Clock

@Service
class TrialService {
    private final Clock clock;                                   // бин: Clock.systemUTC()
    TrialService(Clock clock) { this.clock = clock; }

    boolean isExpired(Instant startedAt) {
        return Instant.now(clock).isAfter(startedAt.plus(Duration.ofDays(14)));
    }
}

// тест: время под контролем, никаких Thread.sleep и «тест падает после полуночи»
Clock fixed = Clock.fixed(Instant.parse("2026-10-10T00:00:00Z"), ZoneOffset.UTC);
assertTrue(new TrialService(fixed).isExpired(Instant.parse("2026-09-01T00:00:00Z")));

Правило: в бизнес-коде нет вызовов Instant.now()/LocalDate.now() без аргумента — только с внедрённым Clock.

17.9Самопроверка

Сервис сохраняет LocalDateTime.now() как время создания заказа. Сервис перенесли из Москвы в контейнер с зоной UTC. Что произойдёт?

  • Ничего, LocalDateTime учитывает зону
  • Новые записи будут на 3 часа «раньше» старых: значение без зоны интерпретируется по-разному
  • Ошибка при записи в БД
  • JVM автоматически пересчитает старые записи
LocalDateTime — не момент времени. Для событий — Instant.

Чем Period отличается от Duration?

  • Period точнее
  • Duration только для дат
  • Period — календарные годы, месяцы, дни; Duration — точное количество секунд и наносекунд
  • Ничем
«Плюс месяц» и «плюс 30 × 24 часа» — разные операции; в дни перевода часов различаются даже «плюс день» и «плюс 24 часа».

Шаблон "YYYY-MM-dd" для даты 29 декабря 2025 года выдаст…

  • 2026-12-29 — YYYY означает год по неделям, а эта неделя относится к 2026
  • 2025-12-29
  • Ошибку
  • 2025-52-29
Классический баг, проявляющийся раз в год в последних числах декабря. Нужно yyyy или uuuu.

Как сделать тестируемым код, зависящий от текущего времени?

  • Вызывать Thread.sleep в тестах
  • Менять системные часы
  • Использовать System.currentTimeMillis()
  • Внедрять java.time.Clock и в тесте подставлять Clock.fixed
Clock — стандартная абстракция источника времени; все now()-методы принимают его аргументом.
В каком виде хранить и передавать время события?

Как момент: Instant (в БД — timestamptz/UTC, в JSON — ISO-8601 с Z или смещением). Преобразование в местное время — только на границе с пользователем, с его ZoneId.

Когда хранить Instant недостаточно?

Для будущих событий, заданных местным временем (встреча, рейс, расписание): правила зоны могут измениться, и сохранённый Instant станет неверным. Хранят LocalDateTime + ZoneId и вычисляют момент при необходимости.

Что такое gap и overlap и как java.time их обрабатывает?

Gap — несуществующее местное время при переводе часов вперёд: atZone сдвигает на длину разрыва. Overlap — время, наступающее дважды при переводе назад: выбирается более раннее смещение, второе — withLaterOffsetAtOverlap(). Проверка — ZoneRules.getValidOffsets.

Почему для замера длительности нельзя использовать Instant.now()?

Системные часы корректируются (NTP, ручная установка) и могут скакнуть назад или вперёд. System.nanoTime() монотонен и предназначен именно для интервалов.
