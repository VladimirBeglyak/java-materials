Загрузка классов, рефлексия, JIT

Spring создаёт бины по аннотациям, Hibernate подменяет объекты прокси, а @Transactional «не работает» при вызове из того же класса. За всей этой «магией» стоят три механизма JVM: динамическая загрузка классов, рефлексия и генерация кода на лету. Глава объясняет их — и то, как JIT превращает байткод в быстрый машинный код.

15.1Жизненный цикл класса

С нуля: как библиотекарь выдаёт книгу

JVM не загружает все классы программы сразу при старте. Как библиотекарь, она приносит «книгу» (класс), только когда её впервые попросили: находит на полке (загрузка), проверяет, что это не подделка и страницы на месте (проверка), заводит карточку (подготовка), отмечает ссылки на другие книги (разрешение) и, наконец, выполняет вступление — статические инициализаторы (инициализация).

Строго

ЭтапЧто происходит
ЗагрузкаЗагрузчик классов (ClassLoader, раздел 15.2) находит байты класса (в JAR, каталоге, сети, сгенерированные в памяти) и создаёт объект Class
Связывание (linking): проверкаВерификатор (verifier) убеждается, что байткод корректен и безопасен: типы на стеке совпадают, нет переходов за границы метода
Связывание: подготовкаВыделяется память под статические поля, они получают значения по умолчанию
Связывание: разрешениеСимвольные ссылки (по имени: «метод save класса Order») на другие классы и методы заменяются прямыми (адресами в памяти) — обычно лениво, при первом использовании
ИнициализацияВыполняются статические инициализаторы и присваивания статическим полям — в порядке записи в коде

Классы загружаются и инициализируются лениво — при первом реальном обращении. Инициализацию запускают: создание экземпляра, вызов статического метода, чтение или запись статического поля, инициализация наследника, Class.forName(name).

class Config {
    static final int MAX = 100;                 // константа времени компиляции
    static final Instant STARTED = Instant.now();
    static { System.out.println("Config инициализирован"); }
}

int a = Config.MAX;            // ничего не напечатает: значение 100 подставлено компилятором в вызывающий класс
Class<?> c = Config.class;     // ничего не напечатает: загрузка без инициализации
Instant t = Config.STARTED;    // «Config инициализирован»
Инициализация потокобезопасна — и это используют JVM гарантирует, что статическая инициализация класса выполняется ровно один раз, даже если к нему одновременно обратились несколько потоков. На этом построен самый простой корректный «ленивый синглтон» (класс с единственным объектом, создаваемым при первом обращении) — без synchronized и volatile (средств синхронизации потоков): 
class Registry {
    private Registry() { }
    private static class Holder { static final Registry INSTANCE = new Registry(); }
    static Registry get() { return Holder.INSTANCE; }      // Holder загрузится при первом вызове get()
}
Обратная сторона: исключение в статическом инициализаторе делает класс навсегда непригодным (тема 06), а взаимная зависимость статических инициализаторов двух классов в разных потоках даёт взаимоблокировку (deadlock — два потока вечно ждут друг друга).
Главное Класс загружается и инициализируется лениво, при первом реальном обращении: загрузка → проверка → подготовка → разрешение → инициализация. Статическая инициализация выполняется ровно один раз и потокобезопасна.

15.2Загрузчики классов

Загрузчик классов — объект, который по имени класса находит его байты и превращает их в класс. Загрузчики выстроены в иерархию: Bootstrap (встроенный в JVM, грузит ядро JDK) → Platform (остальные модули JDK) → Application (классы вашего приложения из classpath). Прежде чем искать сам, каждый загрузчик спрашивает родителя — это называется делегированием; так нельзя подменить, например, java.lang.String своей версией.

Класс определяется парой «полное имя + загрузчик» Один и тот же файл .class, загруженный двумя разными загрузчиками, — это два разных класса с разными статическими полями. Отсюда загадочная ошибка ClassCastException: com.shop.Order cannot be cast to com.shop.Order: слева и справа классы с одним именем, но от разных загрузчиков.

Собственные загрузчики создают ради изоляции и динамики: сервер приложений (программа, в которой работает сразу несколько Java-приложений, например Tomcat или WildFly) даёт каждому приложению свой загрузчик (разные версии одной библиотеки не конфликтуют); Spring Boot читает классы из вложенных JAR внутри «толстого» архива (fat jar — один JAR со всеми зависимостями); системы плагинов (подключаемых модулей) и горячая перезагрузка (обновление кода без перезапуска) в инструментах разработки выбрасывают старый загрузчик вместе со всеми его классами.

  • Class.forName(name) загружает и инициализирует класс; loader.loadClass(name) — только загружает.
  • Класс выгружается только вместе со своим загрузчиком, когда ни на загрузчик, ни на один его класс, ни на один объект этих классов не осталось ссылок. Одна забытая ссылка (в статическом поле, ThreadLocal, зарегистрированном драйвере базы данных) удерживает всё — так возникает утечка Metaspace при переразвёртывании.
  • Контекстный загрузчик потока (Thread.getContextClassLoader()) нужен, когда код из ядра JDK должен найти реализацию из приложения: драйверы JDBC (Java Database Connectivity — подключение к базам данных), ServiceLoader (механизм поиска реализаций интерфейса в classpath).

Модули

С Java 9 JDK разбит на модули, а модуль явно объявляет, какие пакеты он экспортирует (module-info.java: exports — «показываю наружу», requires — «мне нужен такой-то модуль», opens — «разрешаю рефлексию»). Большинство приложений по-прежнему живут на classpath — в «безымянном модуле» (unnamed module), которому видно всё экспортированное. На практике модульность проявляется одним образом: с Java 17 внутренности JDK закрыты для рефлексии, и старая библиотека падает с InaccessibleObjectException. Временное решение — флаг запуска --add-opens java.base/java.lang=ALL-UNNAMED («открыть пакет java.lang всем безымянным модулям»), правильное — обновить библиотеку.

Главное Загрузчики выстроены в иерархию и сначала спрашивают родителя. Класс определяется именем и загрузчиком: один файл от двух загрузчиков — два разных класса. С Java 17 внутренности JDK закрыты для рефлексии.

15.3Рефлексия

Рефлексия (reflection — «отражение», программа смотрит на себя как в зеркало) — возможность программы во время выполнения исследовать классы и работать с ними по именам: узнать поля и методы, создать объект, вызвать метод, прочитать приватное поле.

Class<?> type = Class.forName("com.shop.Order");            // или Order.class, или order.getClass()

for (Field f : type.getDeclaredFields())                    // все поля класса, включая приватные
    System.out.println(f.getType().getSimpleName() + " " + f.getName());

Object order = type.getDeclaredConstructor().newInstance();   // создать объект
Method m = type.getMethod("setStatus", String.class);
m.invoke(order, "PAID");                                    // вызвать метод по имени

Field id = type.getDeclaredField("id");
id.setAccessible(true);                                     // снять проверку доступа
id.set(order, 42L);                                         // записать в приватное поле

Кто этим пользуется

  • Spring — находит классы с аннотациями, создаёт бины (beans — объекты, которыми управляет Spring), внедряет зависимости (сам передаёт объекту нужные ему другие объекты).
  • Jackson — читает и заполняет поля по именам из JSON (текстового формата данных).
  • Hibernate — создаёт сущности (объекты, соответствующие строкам таблицы) и заполняет их из базы данных.
  • JUnit, Mockito (библиотеки тестирования, тема 23) — находят тестовые методы, создают подмены (mock — объекты-заглушки).

Чем за это платят

  • Нет проверки компилятором: опечатка в имени — ошибка при выполнении.
  • Обход инкапсуляции: приватное перестаёт быть приватным.
  • Скорость: вызов медленнее прямого и хуже оптимизируется; фреймворки кэшируют найденные методы.
  • Несовместимость с AOT (Ahead-Of-Time — компиляцией заранее, раздел 15.7): компилятор заранее не знает, что понадобится.

В прикладном коде рефлексия нужна редко — обычно задача решается интерфейсом. Для фреймворков есть более быстрые инструменты: MethodHandle и VarHandle («ручка» метода и переменной) — типизированные ссылки на методы и поля, которые JIT оптимизирует почти как прямой вызов.

Главное Рефлексия позволяет во время работы узнавать поля и методы и вызывать их по имени — на ней работают Spring, Jackson, Hibernate. Цена: нет проверки компилятором, обход инкапсуляции, медленнее, плохо с AOT.

15.4Аннотации

Аннотация — метаданные (данные о коде), прикреплённые к элементу кода: пометка с @, как стикер на папке. Сама по себе она ничего не делает: поведение появляется, только когда кто-то её прочитает.

@Retention(RetentionPolicy.RUNTIME)       // до какого момента аннотация сохраняется
@Target(ElementType.METHOD)               // к чему её можно применять
public @interface Timed {
    String value() default "";
    long warnAfterMs() default 500;
}
Retention («сохранение» — где аннотация доступна)Где доступнаКто обрабатываетПримеры
SOURCEТолько в исходном кодеКомпилятор и процессоры аннотаций (программы, работающие внутри javac)@Override, @SuppressWarnings, аннотации Lombok
CLASS (по умолчанию)В файле .class, но не при выполненииИнструменты, работающие с байткодомАннотации для статического анализа (проверки кода без запуска)
RUNTIMEЧерез рефлексию при выполненииФреймворки@Service, @Transactional, @Entity, @Test

Отсюда два принципиально разных способа обработки. При компиляции — процессор аннотаций генерирует код: Lombok добавляет методы (геттеры, конструкторы), MapStruct пишет классы-преобразователи одних объектов в другие; ошибки видны сразу, накладных расходов при работе нет. При выполнении — фреймворк находит аннотации рефлексией и меняет поведение, как правило, через прокси (раздел 15.5).

Главное Аннотация сама ничего не делает: её читает компилятор (SOURCE), инструменты байткода (CLASS) или фреймворк при выполнении (RUNTIME). Обработка при компиляции генерирует код, при выполнении — подключает прокси.

15.5Динамические прокси

Прокси (proxy — «доверенное лицо», заместитель) — объект, созданный во время выполнения, который выглядит как исходный, но перехватывает вызовы методов и может выполнить что-то до и после. Как секретарь, через которого идут все звонки начальнику: он может записать звонок, проверить права, перезвонить. Так реализуются транзакции (группа операций с базой «всё или ничего»), кэширование, проверка прав, повторы.

PaymentService real = new PaymentServiceImpl();

PaymentService proxy = (PaymentService) Proxy.newProxyInstance(
        PaymentService.class.getClassLoader(),
        new Class<?>[] { PaymentService.class },                  // только интерфейсы
        (self, method, args) -> {
            long start = System.nanoTime();
            try {
                return method.invoke(real, args);                 // вызов настоящего объекта
            } finally {
                log.info("{} — {} мкс", method.getName(), (System.nanoTime() - start) / 1000);
            }
        });
JDK ProxyГенерация подкласса (CGLIB — Code Generation Library, Byte Buddy — библиотеки генерации классов)
Что создаётКласс, реализующий заданные интерфейсыНаследника целевого класса с переопределёнными методами
ТребованиеУ цели должен быть интерфейсКласс и методы не должны быть final
Кто используетSpring AOP (Aspect-Oriented Programming — «аспектно-ориентированное программирование»: добавление общего поведения вроде логов и транзакций ко многим методам) для бинов с интерфейсом, Spring Data, Feign (HTTP-клиент по интерфейсу)Spring AOP по умолчанию в Spring Boot, ленивые сущности Hibernate (подгружающие связанные данные при первом обращении), Mockito
Почему @Transactional «не сработал» Прокси стоит снаружи объекта: перехватываются только вызовы, пришедшие через него. Из этого следуют все известные ограничения Spring AOP.
  • Вызов метода того же класса (this.save()) идёт напрямую, минуя прокси, — @Transactional (выполнить в транзакции), @Cacheable (кэшировать результат), @Async (выполнить в другом потоке) на вызываемом методе не действуют.
  • private-методы не перехватываются: наследник не может их переопределить.
  • final классы и методы — тоже (в Kotlin — другом языке для JVM — классы финальны по умолчанию, поэтому нужен плагин kotlin-spring).
  • В конструкторе прокси ещё не существует.
Лечение — вынести метод в другой бин или управлять транзакцией явно через TransactionTemplate.
Главное Прокси перехватывает вызовы снаружи объекта — так работают @Transactional, @Cacheable, @Async. Поэтому они не действуют на вызов метода из того же класса, на private и final методы.

15.6JIT-компиляция

Байткод сначала исполняет интерпретатор, попутно собирая статистику. Методы и циклы, выполняемые часто, компилируются в машинный код — причём в несколько ступеней (tiered compilation — «ступенчатая компиляция»).

Деоптимизация (откат к неоптимизированному коду). Оптимизации C2 основаны на предположениях: «здесь всегда ArrayList», «эта ветка не выполняется». Если предположение нарушено — загрузился новый класс, пришёл объект другого типа, — скомпилированный код отбрасывается, исполнение возвращается в интерпретатор, и метод будет скомпилирован заново. В графиках это видно как внезапный провал производительности после долгой стабильной работы.

Почему нельзя мерить скорость через System.nanoTime() 
long start = System.nanoTime();
for (int i = 0; i < 1_000_000; i++) compute(i);     // результат не используется
long ms = (System.nanoTime() - start) / 1_000_000;
Такой «замер» показывает что угодно: первые итерации идут в интерпретаторе; JIT может выбросить весь цикл как мёртвый код; порядок двух замеряемых вариантов меняет результат; сборка мусора попадает в один из них. Для микрозамеров (бенчмарков отдельных методов) существует JMH (Java Microbenchmark Harness): он прогревает код, запускает каждый вариант в отдельном процессе и защищает от удаления результата. Производительность сервиса целиком измеряют нагрузочным тестом (имитацией множества пользователей) после прогрева.
Главное JIT компилирует горячий код ступенями C1 и C2 с оптимизациями по профилю: встраивание, девиртуализация, escape analysis. При нарушении предположений код деоптимизируется. Скорость меряют JMH, а не nanoTime вокруг цикла.

15.7Быстрый запуск: CDS, AOT, native image

Плата за JIT — медленный старт и прогрев: неудобно для бессерверных функций (serverless — код запускается на каждый запрос и сразу останавливается) и частого масштабирования (запуска новых копий сервиса под нагрузку). Есть несколько способов её снизить.

ПодходИдеяЦена

Лаба 15.1Свой валидатор на аннотациях25 мин

Объявить аннотацию с RetentionPolicy.RUNTIME, разметить поля и проверить объект рефлексией — как это делает Bean Validation.

  1. Создайте файл Range.java:
    import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
public @interface Range {
    int min() default 0;
    int max() default Integer.MAX_VALUE;
    String message() default "значение вне диапазона";
}
    import java.lang.reflect.Field;
import java.util.ArrayList;
import java.util.List;

public class Validator {
    static class Order {
        @Range(min = 1, max = 100, message = "количество 1..100") int qty;
        @Range(min = 0) int discount;
        String comment;                           // без аннотации — не проверяется
        Order(int qty, int discount) { this.qty = qty; this.discount = discount; }
    }

    static List<String> validate(Object o) throws IllegalAccessException {
        List<String> errors = new ArrayList<>();
        for (Field f : o.getClass().getDeclaredFields()) {
            Range r = f.getAnnotation(Range.class);
            if (r == null) continue;
            f.setAccessible(true);
            int v = f.getInt(o);
            if (v < r.min() || v > r.max()) errors.add(f.getName() + "=" + v + ": " + r.message());
        }
        return errors;
    }

    public static void main(String[] args) throws Exception {
        System.out.println("ok:    " + validate(new Order(5, 10)));
        System.out.println("плохо: " + validate(new Order(500, -1)));
    }
}
    javac Range.java Validator.java
java Validator
    Вывод (JDK 25.0.2)
    ok:    []
плохо: [qty=500: количество 1..100, discount=-1: значение вне диапазона]
  2. Поменяйте в Range RUNTIME на CLASS и перекомпилируйте оба файла. Что напечатает валидатор?
    javac Range.java Validator.java
java Validator
    Вывод (JDK 25.0.2)
    ok:    []
плохо: []

    Пустые списки ошибок: аннотация останется в class-файле, но JVM не загрузит её для рефлексии — getAnnotation вернёт null. SOURCE отбросил бы её ещё компилятор (так устроены @Override, @SuppressWarnings). Для фреймворков нужен RUNTIME.

Лаба 15.2Динамический прокси: логирование и замер времени20 мин

Обернуть любой интерфейс прокси, который логирует вызовы, — тот же механизм, что у Spring AOP для интерфейсов.

  1. Создайте файл ProxyDemo.java:
    import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Proxy;
import java.util.Arrays;

public class ProxyDemo {
    interface PaymentService {
        String pay(String user, int amount);
        int balance(String user);
    }

    static class RealPaymentService implements PaymentService {
        public String pay(String user, int amount) { return "оплачено " + amount + " для " + user; }
        public int balance(String user) { return 1000; }
    }

    @SuppressWarnings("unchecked")
    static <T> T logging(T target, Class<T> iface) {
        InvocationHandler h = (proxy, method, args) -> {
            long t = System.nanoTime();
            System.out.println("→ " + method.getName() + (args == null ? "()" : Arrays.toString(args)));
            Object result = method.invoke(target, args);
            System.out.printf("← %s = %s (%d мкс)%n", method.getName(), result, (System.nanoTime() - t) / 1000);
            return result;
        };
        return (T) Proxy.newProxyInstance(iface.getClassLoader(), new Class<?>[] { iface }, h);
    }

    public static void main(String[] args) {
        PaymentService svc = logging(new RealPaymentService(), PaymentService.class);
        svc.pay("anna", 250);
        svc.balance("anna");
        System.out.println("класс прокси: " + svc.getClass().getName() + ", это Proxy? " + Proxy.isProxyClass(svc.getClass()));
        System.out.println("toString тоже идёт через handler: " + svc);
    }
}
    javac ProxyDemo.java
java ProxyDemo
    Вывод (JDK 25.0.2)
    → pay[anna, 250]
← pay = оплачено 250 для anna (9394 мкс)
→ balance[anna]
← balance = 1000 (2346 мкс)
класс прокси: $Proxy0, это Proxy? true
→ toString()
← toString = ProxyDemo$RealPaymentService@36baf30c (188 мкс)
toString тоже идёт через handler: ProxyDemo$RealPaymentService@36baf30c
  2. Почему вызов toString() тоже залогировался, и что будет, если вызвать pay из метода balance внутри RealPaymentService?

    Прокси перехватывает все методы интерфейса и ещё equals, hashCode, toString из Object. А вызов this.pay(…) внутри реального объекта идёт мимо прокси — логирования не будет. Это та самая «самовызов не проходит через прокси», из-за которой в Spring не срабатывает @Transactional на методе, вызванном из того же бина.

Лаба 15.3Рефлексия: цена и обход private15 мин

Вызвать приватный метод своего класса, сравнить стоимость прямого и рефлексивного вызова и упереться в границы модулей.

  1. Создайте файл ReflectCost.java:
    import java.lang.reflect.Method;

public class ReflectCost {
    private int secret(int x) { return x * 2 + 1; }

    public static void main(String[] args) throws Exception {
        ReflectCost obj = new ReflectCost();
        Method m = ReflectCost.class.getDeclaredMethod("secret", int.class);
        m.setAccessible(true);                 // в своём модуле/classpath — можно
        System.out.println("secret(20) = " + m.invoke(obj, 20));

        for (int round = 0; round < 3; round++) {
            long t = System.nanoTime(); long a = 0;
            for (int i = 0; i < 5_000_000; i++) a += obj.secret(i);
            long direct = System.nanoTime() - t;
            t = System.nanoTime(); long b = 0;
            for (int i = 0; i < 5_000_000; i++) b += (int) m.invoke(obj, i);
            long refl = System.nanoTime() - t;
            System.out.printf("раунд %d: прямой %3d мс, через Method.invoke %3d мс%n", round, direct / 1_000_000, refl / 1_000_000);
        }

        try {
            Method value = String.class.getDeclaredMethod("isLatin1");
            value.setAccessible(true);
        } catch (RuntimeException e) {
            System.out.println("JDK закрыт: " + e.getClass().getSimpleName());
        }
    }
}
    javac ReflectCost.java
java ReflectCost
    Вывод (JDK 25.0.2)
    secret(20) = 41
раунд 0: прямой   5 мс, через Method.invoke  67 мс
раунд 1: прямой   7 мс, через Method.invoke  73 мс
раунд 2: прямой   0 мс, через Method.invoke  34 мс
JDK закрыт: InaccessibleObjectException

    Рефлексивный вызов медленнее из-за упаковки аргументов в массив Object[], проверок и боксинга результата; фреймворки кэшируют Method или переходят на MethodHandle и генерацию байткода. Доступ к приватным членам классов JDK закрыт модульной системой (Java 17+) — нужен --add-opens.

15.11Самопроверка

В чём разница между ClassNotFoundException и NoClassDefFoundError?

  • Это одно и то же
  • Первое — класс не найден при явной загрузке по имени; второе — класс был при компиляции, но не найден или не смог инициализироваться при выполнении
  • Первое бросает компилятор
  • Второе возникает только в тестах
NoClassDefFoundError часто следует за ExceptionInInitializerError: static-инициализация упала, и класс помечен как непригодный.

Почему рефлексия медленнее прямого вызова и где это важно?

  • Она всегда в 1000 раз медленнее
  • Она выполняется в отдельном потоке
  • Проверки доступа, упаковка аргументов, труднее инлайнить JIT-у; заметно только в горячих циклах — при старте фреймворков это не проблема
  • Она не медленнее
Современные JDK реализуют Method.invoke через method handles; для горячих путей применяют MethodHandle/LambdaMetafactory или генерацию кода.

Что нужно, чтобы аннотацию можно было прочитать рефлексией во время выполнения?

  • @Retention(RetentionPolicy.RUNTIME)
  • @Target(ElementType.TYPE)
  • @Inherited
  • Ничего, все аннотации доступны
По умолчанию Retention = CLASS: аннотация есть в class-файле, но JVM её не загружает. SOURCE (@Override) исчезает при компиляции.

Метод с @Transactional вызван из другого метода того же класса через this. Будет ли транзакция?

  • Да, всегда
  • Да, если метод public
  • Нет: вызов идёт мимо прокси, который и создаёт транзакцию
  • Только в Spring Boot 3
Прокси стоит снаружи объекта; вынесите метод в другой бин.

Что значит ClassCastException: Order cannot be cast to Order?

  • Опечатка в имени класса
  • Один класс загружен двумя разными загрузчиками — для JVM это разные классы
  • Класс не скомпилирован
  • Ошибка JIT
Класс определяется парой «имя + загрузчик».
Назовите этапы загрузки класса и момент, когда выполняются статические блоки.

Загрузка (чтение байтов и создание Class) → связывание (проверка байткода, подготовка статических полей, разрешение ссылок) → инициализация. Статические блоки и присваивания статическим полям выполняются на этапе инициализации — лениво, при первом активном использовании класса, и ровно один раз.

Как работает делегирование загрузчиков и зачем оно нужно?

Загрузчик сначала просит загрузить класс своего родителя и ищет сам, только если родитель не нашёл. Это гарантирует, что системные классы всегда загружаются загрузчиком платформы и существуют в одном экземпляре: приложение не может подменить java.lang.String собственным.

Откуда берётся ClassCastException: X cannot be cast to X?

Класс с одним и тем же именем загружен двумя разными загрузчиками. Для JVM это разные классы, и объект одного нельзя привести к другому. Типично для серверов приложений, плагинов и инструментов горячей перезагрузки.

Метод a() вызывает this.b(), помеченный @Transactional. Откроется ли транзакция?

Нет. Транзакцию открывает прокси, стоящий перед объектом. Вызов this.b() идёт внутри объекта и через прокси не проходит. Нужно вынести b() в другой бин, пометить аннотацией сам a() или использовать TransactionTemplate.

Чем обработка аннотаций Lombok отличается от обработки аннотаций Spring?

Lombok работает при компиляции: процессор аннотаций изменяет код до создания байткода, и при выполнении от аннотаций ничего не остаётся. Spring читает аннотации при выполнении через рефлексию (retention RUNTIME) и на их основе создаёт бины и прокси.

Что такое деоптимизация?

Откат скомпилированного JIT кода к интерпретации, когда нарушено предположение, на котором была основана оптимизация: например, в точке вызова появился объект второго класса или загружен наследник, переопределяющий встроенный метод. После накопления новой статистики код компилируется снова, уже без этого предположения.
