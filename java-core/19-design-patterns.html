Паттерны проектирования на примерах JDK

Паттерн — это название для повторяющегося решения, а не цель. Знать их нужно по двум причинам: чтобы узнавать в чужом коде (JDK и Spring построены на них) и чтобы одним словом объяснять коллеге идею. Здесь паттерны показаны через классы, которыми вы уже пользуетесь, и в современной записи — с лямбдами, record и sealed-типами.

Singleton

enum Registry { INSTANCE; /* поля и методы */ }           // 1. enum: потокобезопасно, устойчиво к сериализации и рефлексии

final class Config {                                        // 2. holder: лениво и без синхронизации
    private Config() { }
    private static class Holder { static final Config INSTANCE = new Config(); }   // класс загрузится при первом обращении
    static Config get() { return Holder.INSTANCE; }
}

final class Cache {                                         // 3. double-checked locking — только с volatile
    private static volatile Cache instance;
    static Cache get() {
        Cache c = instance;
        if (c == null) synchronized (Cache.class) { c = instance; if (c == null) instance = c = new Cache(); }
        return c;
    }
}
Singleton через статический доступ — глобальное состояние: его трудно подменить в тесте, а порядок инициализации неочевиден. В приложении с DI-контейнером единственность обеспечивает контейнер: класс обычный, а бин один.

19.4Поведенческие: как объекты взаимодействуют

Strategy — с лямбдами это одна строка

orders.sort(Comparator.comparing(Order::createdAt).reversed().thenComparing(Order::id));   // стратегия сравнения

enum Discount implements UnaryOperator<BigDecimal> {              // набор именованных стратегий
    NONE(p -> p), STUDENT(p -> p.multiply(new BigDecimal("0.90"))), VIP(p -> p.multiply(new BigDecimal("0.80")));
    private final UnaryOperator<BigDecimal> f;
    Discount(UnaryOperator<BigDecimal> f) { this.f = f; }
    public BigDecimal apply(BigDecimal price) { return f.apply(price); }
}

State и Visitor через sealed-типы

sealed interface OrderState permits New, Paid, Shipped, Cancelled { }
record New() implements OrderState { }
record Paid(Instant at) implements OrderState { }
record Shipped(String trackingId) implements OrderState { }
record Cancelled(String reason) implements OrderState { }

static OrderState onPayment(OrderState s, Instant now) {
    return switch (s) {
        case New n       -> new Paid(now);
        case Paid p      -> p;                                             // идемпотентно
        case Shipped sh  -> throw new IllegalStateException("already shipped");
        case Cancelled c -> throw new IllegalStateException("cancelled: " + c.reason());
    };                                                                      // новый статус → ошибка компиляции здесь
}

Классический Visitor нужен, чтобы добавлять операции над иерархией без изменения её классов. Sealed-типы и pattern matching дают то же проще: операция — обычный метод со switch, а компилятор проверяет полноту.

19.5Когда паттерн вредит

Преждевременная абстракция

Интерфейс UserService и единственный UserServiceImpl, фабрика фабрик, стратегия с одной реализацией. Каждый слой косвенности — это переход по коду при чтении. Абстракция оправдана, когда вариантов уже два или граница модуля требует инверсии зависимости.

Паттерн ради названия

Класс OrderManagerFactoryBuilder ничего не говорит о задаче. Называйте по предметной области (DeliveryPricing), а паттерн оставляйте в структуре.

Singleton как глобальная переменная

Скрытые зависимости, невозможность параллельных тестов, порядок инициализации.

Глубокое наследование

Template Method в четыре уровня: чтобы понять метод, нужно держать в голове всю иерархию. Предпочитайте композицию (тема 04).

19.6Самопроверка

Какой паттерн реализует new BufferedInputStream(new FileInputStream(f))?

  • Adapter
  • Decorator: обёртка с тем же интерфейсом InputStream добавляет буферизацию
  • Proxy
  • Facade
Интерфейс не меняется, поведение добавляется слоями. Adapter был бы, если бы интерфейс менялся: InputStreamReader превращает InputStream в Reader.

Почему double-checked locking без volatile некорректен?

  • synchronized не работает со статическими полями
  • Он создаёт два экземпляра всегда
  • Другой поток может увидеть ненулевую ссылку на объект, конструктор которого ещё не завершён
  • Он медленнее простой синхронизации
Запись ссылки и инициализация полей могут быть переупорядочены; volatile даёт happens-before. Подробности — пособие Java Concurrency, тема 02.

Что из перечисленного — пример паттерна Strategy в JDK?

  • Comparator, передаваемый в sort
  • StringBuilder
  • Integer.valueOf
  • Iterator
Алгоритм сравнения вынесен в объект и подменяется без изменения сортировки.

Чем Proxy отличается от Decorator?

  • У них разные интерфейсы
  • Proxy всегда создаётся рефлексией
  • Decorator нельзя вкладывать
  • Структура одинакова, различается назначение: Proxy управляет доступом к объекту, Decorator наращивает поведение
На практике граница размыта; важно намерение и то, кто собирает обёртку — клиент или инфраструктура.
Какие паттерны вы видите в Spring?

Proxy (AOP, транзакции), Template Method (refresh, JdbcTemplate с колбэками — на самом деле ближе к Strategy), Factory (BeanFactory, FactoryBean), Singleton (scope), Observer (события), Chain of Responsibility (фильтры, интерцепторы), Strategy (резолверы, конвертеры), Adapter (HandlerAdapter), Decorator (обёртки запроса), Composite (составные резолверы).

Как лямбды и sealed-типы изменили паттерны?

Strategy, Command, Template Method, Factory часто сводятся к передаче функции. State и Visitor заменяются sealed-иерархией с исчерпывающим switch. Builder для небольших объектов вытесняется record. Идеи остались, церемоний стало меньше.

Когда не нужно применять паттерн?

Когда нет вариативности, которую он обслуживает: один алгоритм, одна реализация, простая конструкция объекта. Абстракцию дешевле добавить при появлении второго случая, чем поддерживать лишнюю заранее.
