Здесь паттерны показаны через классы, которыми вы уже пользуетесь, и в современной записи — с лямбдами, record и sealed-типами.

Singleton

enum Registry { INSTANCE; /* поля и методы */ }           // 1. enum: потокобезопасно, устойчиво к сериализации и рефлексии

final class Config {                                        // 2. holder: лениво и без синхронизации
    private Config() { }
    private static class Holder { static final Config INSTANCE = new Config(); }   // класс загрузится при первом обращении
    static Config get() { return Holder.INSTANCE; }
}

final class Cache {                                         // 3. double-checked locking — только с volatile
    private static volatile Cache instance;
    static Cache get() {
        Cache c = instance;
        if (c == null) synchronized (Cache.class) { c = instance; if (c == null) instance = c = new Cache(); }
        return c;
    }
}
Singleton через статический доступ — глобальное состояние: его трудно подменить в тесте, а порядок инициализации неочевиден. В приложении с DI-контейнером единственность обеспечивает контейнер: класс обычный, а бин один.

19.4Поведенческие: как объекты взаимодействуют

Strategy — с лямбдами это одна строка

orders.sort(Comparator.comparing(Order::createdAt).reversed().thenComparing(Order::id));   // стратегия сравнения

enum Discount implements UnaryOperator<BigDecimal> {              // набор именованных стратегий
    NONE(p -> p), STUDENT(p -> p.multiply(new BigDecimal("0.90"))), VIP(p -> p.multiply(new BigDecimal("0.80")));
    private final UnaryOperator<BigDecimal> f;
    Discount(UnaryOperator<BigDecimal> f) { this.f = f; }
    public BigDecimal apply(BigDecimal price) { return f.apply(price); }
}

State и Visitor через sealed-типы

sealed interface OrderState permits New, Paid, Shipped, Cancelled { }
record New() implements OrderState { }
record Paid(Instant at) implements OrderState { }
record Shipped(String trackingId) implements OrderState { }
record Cancelled(String reason) implements OrderState { }

static OrderState onPayment(OrderState s, Instant now) {
    return switch (s) {
        case New n       -> new Paid(now);
        case Paid p      -> p;                                             // идемпотентно
        case Shipped sh  -> throw new IllegalStateException("already shipped");
        case Cancelled c -> throw new IllegalStateException("cancelled: " + c.reason());
    };                                                                      // новый статус → ошибка компиляции здесь
}

Классический Visitor нужен, чтобы добавлять операции над иерархией без изменения её классов. Sealed-типы и pattern matching дают то же проще: операция — обычный метод со switch, а компилятор проверяет полноту.

19.5Когда паттерн вредит

Преждевременная абстракция

Интерфейс UserService и единственный UserServiceImpl, фабрика фабрик, стратегия с одной реализацией. Каждый слой косвенности — это переход по коду при чтении. Абстракция оправдана, когда вариантов уже два или граница модуля требует инверсии зависимости.

Паттерн ради названия

Класс OrderManagerFactoryBuilder ничего не говорит о задаче. Называйте по предметной области (DeliveryPricing), а паттерн оставляйте в структуре.

Singleton как глобальная переменная

Скрытые зависимости, невозможность параллельных тестов, порядок инициализации.

Глубокое наследование

Template Method в четыре уровня: чтобы понять метод, нужно держать в голове всю иерархию. Предпочитайте композицию (тема 04).

Лаба 19.1Builder для объекта с необязательными полями15 мин

Заменить «телескопический» конструктор строителем с проверкой инвариантов при build().

  1. Создайте файл HttpRequestSpec.java:
    import java.time.Duration;
import java.util.LinkedHashMap;
import java.util.Map;

public record HttpRequestSpec(String method, String url, Map<String, String> headers, Duration timeout, int retries) {
    public static Builder get(String url) { return new Builder("GET", url); }
    public static Builder post(String url) { return new Builder("POST", url); }

    public static final class Builder {
        private final String method, url;
        private final Map<String, String> headers = new LinkedHashMap<>();
        private Duration timeout = Duration.ofSeconds(10);
        private int retries = 0;

        private Builder(String method, String url) { this.method = method; this.url = url; }
        public Builder header(String k, String v) { headers.put(k, v); return this; }
        public Builder timeout(Duration t) { this.timeout = t; return this; }
        public Builder retries(int r) { this.retries = r; return this; }

        public HttpRequestSpec build() {
            if (!url.startsWith("http")) throw new IllegalStateException("url должен начинаться с http: " + url);
            if (method.equals("POST") && retries > 0) throw new IllegalStateException("POST не идемпотентен — повторы запрещены");
            return new HttpRequestSpec(method, url, Map.copyOf(headers), timeout, retries);
        }
    }

    public static void main(String[] args) {
        System.out.println(get("https://api.example.com/orders").header("Accept", "application/json").retries(3).build());
        try {
            post("https://api.example.com/pay").retries(2).build();
        } catch (IllegalStateException e) {
            System.out.println("отказ: " + e.getMessage());
        }
    }
}
    javac HttpRequestSpec.java
java HttpRequestSpec
    Вывод (JDK 25.0.2)
    HttpRequestSpec[method=GET, url=https://api.example.com/orders, headers={Accept=application/json}, timeout=PT10S, retries=3]
отказ: POST не идемпотентен — повторы запрещены

    Builder особенно уместен, когда проверка затрагивает несколько полей сразу (POST + retries): конструктор с 5 параметрами такую ошибку пропустил бы молча.

Лаба 19.2Strategy без классов: лямбды в EnumMap15 мин

Заменить разрастающийся switch по типу клиента набором стратегий.

  1. Создайте файл Pricing.java:
    import java.math.BigDecimal;
import java.math.RoundingMode;
import java.util.EnumMap;
import java.util.Map;
import java.util.function.UnaryOperator;

public class Pricing {
    enum Tier { REGULAR, SILVER, GOLD, EMPLOYEE }

    static final Map<Tier, UnaryOperator<BigDecimal>> STRATEGIES = new EnumMap<>(Map.of(
        Tier.REGULAR, p -> p,
        Tier.SILVER, p -> p.multiply(new BigDecimal("0.95")),
        Tier.GOLD, p -> p.multiply(new BigDecimal("0.90")).max(p.subtract(new BigDecimal("500"))),
        Tier.EMPLOYEE, p -> p.multiply(new BigDecimal("0.70"))));

    static BigDecimal price(Tier tier, BigDecimal base) {
        return STRATEGIES.get(tier).apply(base).setScale(2, RoundingMode.HALF_UP);
    }

    public static void main(String[] args) {
        for (Tier t : Tier.values())
            System.out.printf("%-9s 1000 → %8s   10000 → %9s%n", t, price(t, new BigDecimal("1000")), price(t, new BigDecimal("10000")));
        System.out.println("стратегий: " + STRATEGIES.size() + " из " + Tier.values().length);
    }
}
    javac Pricing.java
java Pricing
    Вывод (JDK 25.0.2)

SILVER    1000 →   950.00   10000 →   9500.00

стратегий: 4 из 4
  2. Что произойдёт, если добавить в enum PLATINUM, но забыть стратегию? Как сделать так, чтобы ошибка была видна сразу при старте?

    NullPointerException в момент первого расчёта для PLATINUM — возможно, через неделю в продакшене. Защита: проверка полноты в статическом блоке (if (STRATEGIES.size() != Tier.values().length) throw …) — тогда ошибка будет при загрузке класса. Ещё надёжнее — абстрактный метод в самом enum (каждая константа обязана его реализовать, проверяет компилятор) или switch-выражение без default.

Лаба 19.3Decorator: кэш и замер времени поверх медленного сервиса20 мин

Добавить поведение (кэширование, метрики) без изменения исходного класса — композицией по общему интерфейсу.

  1. Создайте файл Decorators.java:
    import java.util.HashMap;
import java.util.Map;

public class Decorators {
    interface RateService { double rate(String currency); }

    static class SlowBankRates implements RateService {
        public double rate(String currency) {
            try { Thread.sleep(300); } catch (InterruptedException e) { throw new RuntimeException(e); }
            return switch (currency) { case "USD" -> 92.5; case "EUR" -> 100.1; default -> throw new IllegalArgumentException(currency); };
        }
    }

    static class Caching implements RateService {
        private final RateService inner; private final Map<String, Double> cache = new HashMap<>();
        Caching(RateService inner) { this.inner = inner; }
        public double rate(String c) { return cache.computeIfAbsent(c, inner::rate); }
    }

    static class Timing implements RateService {
        private final RateService inner;
        Timing(RateService inner) { this.inner = inner; }
        public double rate(String c) {
            long t = System.nanoTime();
            try { return inner.rate(c); }
            finally { System.out.printf("  rate(%s) за %d мс%n", c, (System.nanoTime() - t) / 1_000_000); }
        }
    }

    public static void main(String[] args) {
        RateService svc = new Timing(new Caching(new SlowBankRates()));
        for (String c : new String[] { "USD", "EUR", "USD", "USD", "EUR" }) System.out.println(c + " = " + svc.rate(c));
    }
}

Лаба 19.4Observer: события и утечка подписчиков15 мин

Сделать простую шину событий и увидеть, почему подписки нужно уметь отменять.

  1. Создайте файл Events.java:
    import java.util.List;
import java.util.concurrent.CopyOnWriteArrayList;
import java.util.function.Consumer;

public class Events {
    record OrderPlaced(String id, double sum) { }

    static class EventBus<E> {
        private final List<Consumer<E>> listeners = new CopyOnWriteArrayList<>();
        Runnable subscribe(Consumer<E> l) { listeners.add(l); return () -> listeners.remove(l); }   // возвращаем «отписку»
        void publish(E event) { listeners.forEach(l -> l.accept(event)); }
        int size() { return listeners.size(); }
    }

    public static void main(String[] args) {
        EventBus<OrderPlaced> bus = new EventBus<>();
        bus.subscribe(e -> System.out.println("  письмо клиенту о заказе " + e.id()));
        Runnable unsubscribeStats = bus.subscribe(e -> System.out.println("  статистика: +" + e.sum()));
        bus.publish(new OrderPlaced("A-1", 990));
        unsubscribeStats.run();
        bus.publish(new OrderPlaced("A-2", 150));

        for (int i = 0; i < 1000; i++) {
            byte[] screenState = new byte[100_000];                      // «экран», который давно закрыт
            bus.subscribe(e -> { int unused = screenState.length; });   // забыли отписаться
        }
        System.out.println("подписчиков: " + bus.size() + " — каждый держит по 100 КБ");
    }
}
    javac Events.java
java Events
    Вывод (JDK 25.0.2)
      письмо клиенту о заказе A-1
  статистика: +990.0
  письмо клиенту о заказе A-2
подписчиков: 1001 — каждый держит по 100 КБ

    Забытые подписчики — классическая утечка памяти: шина живёт долго и держит лямбды, а лямбды держат захваченные объекты. Возвращайте из subscribe способ отписаться (как AutoCloseable/Runnable) и вызывайте его при закрытии компонента.

19.7Самопроверка

Какой паттерн реализует new BufferedInputStream(new FileInputStream(f))?

  • Adapter
  • Decorator: обёртка с тем же интерфейсом InputStream добавляет буферизацию
  • Proxy
  • Facade
Интерфейс не меняется, поведение добавляется слоями. Adapter был бы, если бы интерфейс менялся: InputStreamReader превращает InputStream в Reader.

Почему double-checked locking без volatile некорректен?

  • synchronized не работает со статическими полями
  • Он создаёт два экземпляра всегда
  • Другой поток может увидеть ненулевую ссылку на объект, конструктор которого ещё не завершён
  • Он медленнее простой синхронизации
Запись ссылки и инициализация полей могут быть переупорядочены; volatile даёт happens-before. Подробности — пособие Java Concurrency, тема 02.

Что из перечисленного — пример паттерна Strategy в JDK?

  • Comparator, передаваемый в sort
  • StringBuilder
  • Integer.valueOf
  • Iterator
Алгоритм сравнения вынесен в объект и подменяется без изменения сортировки.

Чем Proxy отличается от Decorator?

  • У них разные интерфейсы
  • Proxy всегда создаётся рефлексией
  • Decorator нельзя вкладывать
  • Структура одинакова, различается назначение: Proxy управляет доступом к объекту, Decorator наращивает поведение
На практике граница размыта; важно намерение и то, кто собирает обёртку — клиент или инфраструктура.
Какие паттерны вы видите в Spring?

Proxy (AOP, транзакции), Template Method (refresh, JdbcTemplate с колбэками — на самом деле ближе к Strategy), Factory (BeanFactory, FactoryBean), Singleton (scope), Observer (события), Chain of Responsibility (фильтры, интерцепторы), Strategy (резолверы, конвертеры), Adapter (HandlerAdapter), Decorator (обёртки запроса), Composite (составные резолверы).

Как лямбды и sealed-типы изменили паттерны?

Strategy, Command, Template Method, Factory часто сводятся к передаче функции. State и Visitor заменяются sealed-иерархией с исчерпывающим switch. Builder для небольших объектов вытесняется record. Идеи остались, церемоний стало меньше.

Когда не нужно применять паттерн?

Когда нет вариативности, которую он обслуживает: один алгоритм, одна реализация, простая конструкция объекта. Абстракцию дешевле добавить при появлении второго случая, чем поддерживать лишнюю заранее.
