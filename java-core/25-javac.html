Компилятор javac изнутри

Между текстом программы и байткодом стоит компилятор, который делает гораздо больше, чем перевод: проверяет типы и потоки управления, сворачивает константы, разворачивает синтаксический сахар (for-each, enum, внутренние классы, records, try-with-resources), стирает generics и добавляет мостовые методы, запускает процессоры аннотаций. Многое из того, что кажется «свойством языка», на самом деле существует только в javac — JVM об этом не знает.

25.1Фазы компиляции

javac — программа на Java (модуль jdk.compiler), её можно вызвать из кода (раздел 25.7). Внутри она проводит исходник через цепочку преобразований дерева разбора (AST):

Важное следствие: правила языка и правила JVM — разные. Checked-исключения, generics, final у локальных переменных, области видимости, definite assignment, вложенность классов — проверяет javac. JVM проверяет свою, более низкоуровневую модель (верификатор байткода, JVM, тема 06). Kotlin, Scala и Groovy компилируются в тот же байткод по своим правилам.

25.2Константы времени компиляции

Константная переменная (JLS §4.12.4) — final-переменная примитивного типа или String, инициализированная константным выражением: литералами, другими константами, арифметикой, конкатенацией, приведениями — без вызовов методов и new. javac вычисляет такие выражения сам (constant folding) и подставляет значение на место использования.

static final int SECONDS = 24 * 60 * 60;   // константа: в байткоде будет ldc 86400
static final String GREETING = "Hi, " + "all"; // константа: одна строка "Hi, all" в пуле
static final Integer BOXED = 42;           // НЕ константа: Integer — не примитив и не String
static final int RANDOM = new Random().nextInt(); // НЕ константа: вызов метода
static final long NOW = System.currentTimeMillis(); // НЕ константа

String a = "ab", b = "a" + "b";            // a == b → true: "a" + "b" свёрнуто при компиляции
final String x = "a";  String c = x + "b"; // c == a → true: x — константная переменная
String y = "a";        String d = y + "b"; // d == a → false: склейка в рантайме, новый объект

Константы нужны языку: только ими можно размечать case в switch, задавать значения элементов аннотаций и условную компиляцию (if (DEBUG) — ветка с константой false не попадёт в байткод). Обращение к константе другого класса не вызывает его инициализацию (JVM, тема 06): класса в этом месте байткода просто нет.

Ловушка: «застывшая» константа Класс App использует Config.TIMEOUT = 10. Вы меняете значение на 20 и пересобираете только Config (например, обновили библиотеку без перекомпиляции зависимых модулей). App продолжит видеть 10: значение было вклеено в его байткод. Отсюда правило для публичных API: меняющиеся значения не делают public static final-константами — отдают через метод или инициализируют не константным выражением (static final int TIMEOUT = Integer.parseInt("10") уже не константа). Инкрементальные сборщики (Gradle, Maven) знают об этой проблеме и пересобирают зависимых при изменении констант.

25.3Проверки, которых нет в JVM: checked-исключения

Требование «поймай или объяви в throws» — чисто компиляторное. В class-файле список throws хранится лишь как атрибут Exceptions для документации и рефлексии; инструкция athrow бросает любой Throwable, и верификатор не проверяет, объявлен ли он. Это можно увидеть, обманув компилятор через generics (приём «sneaky throw», им пользуются Lombok @SneakyThrows и некоторые библиотеки):

@SuppressWarnings("unchecked")
static <E extends Throwable> void sneakyThrow(Throwable t) throws E {
    throw (E) t;                    // приведение к стёртому E — это приведение к Throwable, проверки нет
}

static void read() {                // никакого throws IOException!
    Sneaky.<RuntimeException>sneakyThrow(new IOException("disk"));
}

Компилятор считает, что вызов бросает RuntimeException, а летит настоящий IOException. Побочный эффект: поймать его по типу нельзя — catch (IOException e) вокруг read() не скомпилируется («exception is never thrown in body of try»), ловить придётся Exception. То же происходит с исключениями, проброшенными из кода на Kotlin, где checked-исключений нет вовсе.

Другие проверки фазы Flow: definite assignment (тема 24), недостижимый код, effectively final для захвата в лямбдах, исчерпываемость switch по sealed-типам (тема 12). Исчерпываемость — тоже обещание компилятора: если после компиляции switch в sealed-иерархию добавят новый подкласс, в рантайме прилетит MatchException.

25.5Стирание типов и мостовые методы

После атрибуции javac стирает параметры типов: List<String> становится List, T — своей верхней границей (Object или Comparable при T extends Comparable<T>), а в местах чтения добавляются приведения (тема 07). Сами generic-сигнатуры сохраняются в атрибуте Signature — для компиляции против библиотеки и для рефлексии (getGenericReturnType()), но JVM при исполнении их не читает.

Стирание ломает переопределение. Пусть класс реализует Comparable<Money>:

final class Money implements Comparable<Money> {
    public int compareTo(Money o) { ... }        // сигнатура compareTo(Money)
}
// а интерфейс после стирания объявляет compareTo(Object) — сигнатуры разные!
// javac добавляет МОСТОВОЙ метод (флаги ACC_BRIDGE | ACC_SYNTHETIC):
public int compareTo(Object o) { return compareTo((Money) o); }

Именно мост делает вызов Collections.sort(list) полиморфным, а заодно объясняет ClassCastException «из ниоткуда»: если через сырой тип подсунуть в мост чужой объект, каст внутри моста упадёт. Мосты появляются также при ковариантном возвращаемом типе: Child clone() поверх Object clone() — в байткоде два метода с одной сигнатурой параметров и разными типами результата (JVM это разрешает, язык — нет). Рефлексия видит мосты: Method.isBridge(), и фреймворки (Spring, Jackson) их отфильтровывают.

Синтетические элементы Всё, что javac добавил сам и чего нет в исходнике, помечено флагом ACC_SYNTHETIC: мосты, this$0, val$x, $VALUES, $assertionsDisabled, lambda$main$0. Увидеть их — javap -p -v. Рефлексия — isSynthetic(). Код, перебирающий поля через рефлексию (сериализаторы, маперы), должен их пропускать.

25.6Процессоры аннотаций

Annotation processing (JSR 269) — плагин к компилятору: класс, реализующий javax.annotation.processing.Processor, получает от javac модель исходников (элементы: классы, методы, поля и их аннотации — пакет javax.lang.model) и может:

  • генерировать новые исходники и ресурсы через Filer — они компилируются в следующем раунде, вместе с остальным кодом: так работают MapStruct, Dagger, AutoValue, Micronaut, JPA metamodel (User_), spring-boot-configuration-processor;
  • выдавать ошибки и предупреждения через Messager — проверки на этапе компиляции (Error Prone, NullAway — чуть иначе, через javac plugin API);
  • не может изменять существующие классы — это ограничение API.
Как работает Lombok Lombok формально — процессор аннотаций, но он нарушает правило «только генерировать»: через внутренние API javac (com.sun.tools.javac.tree) он меняет AST вашего класса, дописывая геттеры, конструкторы и equals. Поэтому Lombok ломается на новых версиях JDK, пока не выйдет совместимая версия, а для работы в IDE ему нужен отдельный плагин. MapStruct и records — штатные альтернативы.

Раунды: javac вызывает процессоры для исходников; если они сгенерировали новые файлы — разбирает их и вызывает процессоры снова, пока новых файлов не станет; последний раунд помечен processingOver(). Только после этого идут атрибуция и генерация. Поэтому код может ссылаться на ещё не существующий класс, который сгенерирует процессор.

Java 23+: процессоры не запускаются «сами» Раньше javac находил процессоры на classpath через META-INF/services и молча их выполнял. С JDK 23 по умолчанию действует -proc:none, если процессоры не указаны явно: -processor, --processor-path/-processorpath, --processor-module-path или -proc:full. В Maven и Gradle процессоры подключают через annotationProcessorPaths / конфигурацию annotationProcessor. Симптом забытой настройки при переходе на новый JDK — «cannot find symbol» для генерируемых классов.

Лаба 25.3Мостовые методы10 мин

Увидеть мосты, которые javac добавляет для generic-интерфейса и ковариантного возвращаемого типа.

  1. Создайте файл Money.java:
    import java.lang.reflect.Method;
import java.util.function.Supplier;

public class Money implements Comparable<Money>, Supplier<Money> {
    final long cents;
    Money(long cents) { this.cents = cents; }

    @Override public int compareTo(Money o) { return Long.compare(cents, o.cents); }
    @Override public Money get() { return this; }

    @SuppressWarnings({"rawtypes", "unchecked"})
    public static void main(String[] args) {
        for (Method m : Money.class.getDeclaredMethods()) {
            if (m.getName().equals("main")) continue;
            System.out.printf("%-60s bridge=%s synthetic=%s%n", m, m.isBridge(), m.isSynthetic());
        }
        Comparable raw = new Money(1);
        try {
            raw.compareTo("строка");
        } catch (ClassCastException e) {
            System.out.println("CCE: " + e.getMessage());
        }
    }
}
  2. Сколько методов compareTo и get покажет рефлексия? Откуда возьмётся ClassCastException, если в коде нет ни одного каста?
    javac Money.java
java Money
    Вывод (JDK 25.0.2)
    public java.lang.Object Money.get()                          bridge=true synthetic=true
public Money Money.get()                                     bridge=false synthetic=false
public int Money.compareTo(Money)                            bridge=false synthetic=false
public int Money.compareTo(java.lang.Object)                 bridge=true synthetic=true
CCE: class java.lang.String cannot be cast to class Money (java.lang.String is in module java.base of loader 'bootstrap'; Money is in unnamed module of loader 'app')

    По два: compareTo(Money) и мост compareTo(Object), get() с результатом Money и мост get() с результатом Object — два метода с одинаковыми параметрами, которые язык запрещает, а JVM разрешает. У мостов bridge=true synthetic=true. Каст есть в мосте: compareTo(Object o) вызывает compareTo((Money) o), и строка падает на нём.

Поэкспериментируйте
  • Выполните javap -c -p Money и найдите тело моста compareTo(java.lang.Object).

Лаба 25.4Checked-исключение без throws10 мин

Доказать, что проверку checked-исключений выполняет только компилятор.

  1. Создайте файл Sneaky.java:
    import java.io.IOException;

public class Sneaky {
    @SuppressWarnings("unchecked")
    static <E extends Throwable> void sneakyThrow(Throwable t) throws E {
        throw (E) t;
    }

    static void read() {   // throws не объявлен
        Sneaky.<RuntimeException>sneakyThrow(new IOException("диск недоступен"));
    }

    public static void main(String[] args) {
        try {
            read();
        } catch (Exception e) {
            System.out.println("поймали " + e.getClass().getName() + ": " + e.getMessage());
            System.out.println("это RuntimeException? " + (e instanceof RuntimeException));
        }
    }
}
  2. Скомпилируется ли код? Какое исключение поймает catch?
    javac Sneaky.java
java Sneaky
    Вывод (JDK 25.0.2)
    поймали java.io.IOException: диск недоступен
это RuntimeException? false

    Компилируется: javac считает, что sneakyThrow бросает RuntimeException. В рантайме летит настоящий java.io.IOException — instanceof RuntimeException даёт false. JVM не знает про «checked».

Поэкспериментируйте
  • Замените catch (Exception e) на catch (java.io.IOException e).
    Ошибка компиляции «exception java.io.IOException is never thrown in body of corresponding try statement»: по мнению компилятора, такого исключения тут быть не может.
Лаба 25.5Свой процессор аннотаций25 мин

Написать процессор, который во время компиляции генерирует класс, и использовать этот класс в коде, который без процессора не скомпилировался бы.

  1. Создайте файл proc/Describe.java:
    import java.lang.annotation.*;

@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE)
public @interface Describe {}
    import java.io.IOException;
import java.io.Writer;
import java.util.Set;
import java.util.stream.Collectors;
import javax.annotation.processing.*;
import javax.lang.model.SourceVersion;
import javax.lang.model.element.*;
import javax.tools.Diagnostic;

@SupportedAnnotationTypes("Describe")
public class DescribeProcessor extends AbstractProcessor {
    int round = 0;

    @Override
    public SourceVersion getSupportedSourceVersion() { return SourceVersion.latestSupported(); }

    @Override
    public boolean process(Set<? extends TypeElement> annotations, RoundEnvironment env) {
        round++;
        processingEnv.getMessager().printMessage(Diagnostic.Kind.NOTE,
                "раунд " + round + ", processingOver=" + env.processingOver());
        for (Element e : env.getElementsAnnotatedWith(Describe.class)) {
            if (e.getKind() != ElementKind.RECORD && e.getKind() != ElementKind.CLASS) {
                processingEnv.getMessager().printMessage(Diagnostic.Kind.ERROR, "@Describe только для классов", e);
                continue;
            }
            String name = e.getSimpleName() + "Info";
            String fields = e.getEnclosedElements().stream()
                    .filter(m -> m.getKind() == ElementKind.FIELD)
                    .map(m -> "\"" + m.getSimpleName() + ": " + m.asType() + "\"")
                    .collect(Collectors.joining(", "));
            try (Writer w = processingEnv.getFiler().createSourceFile(name, e).openWriter()) {
                w.write("public final class " + name + " {\n"
                        + "    public static java.util.List<String> fields() {\n"
                        + "        return java.util.List.of(" + fields + ");\n"
                        + "    }\n}\n");
            } catch (IOException ex) {
                throw new RuntimeException(ex);
            }
        }
        return true;
    }
}
    @Describe
public record Person(String name, int age, java.time.LocalDate born) {}
    public class Main {
    public static void main(String[] args) {
        System.out.println(PersonInfo.fields());   // класса PersonInfo нет в исходниках!
    }
}
  2. Соберите процессор отдельно — это обычные классы:
    javac -d proc-out proc/Describe.java proc/DescribeProcessor.java
  3. Попробуйте собрать приложение без процессора:
    javac -cp proc-out -d app-out app/Person.java app/Main.java
    Вывод (JDK 25.0.2)
    app\Main.java:3: error: cannot find symbol
        System.out.println(PersonInfo.fields());   // класса PersonInfo нет в исходниках!
                           ^
  symbol:   variable PersonInfo
  location: class Main
1 error
  4. Теперь соберите с процессором. Сколько будет раундов? Что напечатает Main?
    javac -cp proc-out -processorpath proc-out -processor DescribeProcessor -s gen -d app-out app/Person.java app/Main.java
java -cp app-out Main
    Вывод (JDK 25.0.2)
    Note: раунд 1, processingOver=false
Note: раунд 2, processingOver=false
Note: раунд 3, processingOver=true
[name: java.lang.String, age: int, born: java.time.LocalDate]

    Три раунда: в первом процессор видит Person и генерирует PersonInfo.java; во втором разбирается новый файл (аннотаций в нём нет, генерировать нечего); третий — финальный, processingOver=true. После этого Main компилируется, потому что PersonInfo уже существует. Вывод — [name: java.lang.String, age: int, born: java.time.LocalDate]: поля record видны процессору как элементы FIELD.

  5. Сгенерированный исходник лежит в каталоге, заданном -s:
    cat gen/PersonInfo.java
    Вывод (JDK 25.0.2)
    public final class PersonInfo {
    public static java.util.List<String> fields() {
        return java.util.List.of("name: java.lang.String", "age: int", "born: java.time.LocalDate");
    }
}

    IDEAВ IDEA: Settings → Build, Execution, Deployment → Compiler → Annotation Processors → Enable annotation processing, Processor path — каталог proc-out. В Maven — annotationProcessorPaths у maven-compiler-plugin, в Gradle — конфигурация annotationProcessor.

Поэкспериментируйте
  • Повесьте @Describe на интерфейс.
    Процессор выдаст ошибку компиляции с указанием на элемент: error: @Describe только для классов — так библиотеки проверяют правила использования своих аннотаций.
  • Уберите -processor DescribeProcessor, но оставьте -processorpath и положите в proc-out/META-INF/services/javax.annotation.processing.Processor строку DescribeProcessor.
    Сработает: явный processorpath включает обнаружение через ServiceLoader. А если процессор лежит только на -cp, с JDK 23 он не запустится без -proc:full.
Лаба 25.6Компиляция из программы и --release15 мин

Скомпилировать и выполнить код, собранный строкой во время работы, и увидеть разницу --release и -target.

  1. Создайте файл Dyn.java:
    import java.net.URLClassLoader;
import java.nio.file.*;
import javax.tools.*;

public class Dyn {
    public static void main(String[] args) throws Exception {
        String src = """
                public class Generated {
                    public static String hello(String who) {
                        return "Привет, " + who + "! Скомпилировано в " + Runtime.version();
                    }
                }
                """;
        Path dir = Files.createTempDirectory("gen");
        Path file = dir.resolve("Generated.java");
        Files.writeString(file, src);

        JavaCompiler javac = ToolProvider.getSystemJavaCompiler();
        int code = javac.run(null, null, null, "-d", dir.toString(), file.toString());
        System.out.println("javac вернул " + code);

        try (var loader = new URLClassLoader(new java.net.URL[] {dir.toUri().toURL()})) {
            Class<?> c = loader.loadClass("Generated");
            System.out.println(c.getMethod("hello", String.class).invoke(null, "мир"));
        }
    }
}
  2. Что вернёт javac.run и что напечатает загруженный класс?
    javac Dyn.java
java Dyn
    Вывод (JDK 25.0.2)
    javac вернул 0
Привет, мир! Скомпилировано в 25.0.2+10-69

    javac вернул 0 (0 — успех, как код возврата команды javac), затем строка с версией JDK: класс, которого не было при запуске программы, скомпилирован, загружен новым загрузчиком и вызван через рефлексию. Так устроены jshell и java Hello.java.

  3. Файл, использующий API Java 21, собираем под Java 17 двумя способами:
    import java.util.List;

public class NewApi {
    public static void main(String[] args) {
        System.out.println(List.of(1, 2, 3).getFirst());   // SequencedCollection — Java 21
    }
}
    javac --release 17 NewApi.java
    Вывод (JDK 25.0.2)
    NewApi.java:5: error: cannot find symbol
        System.out.println(List.of(1, 2, 3).getFirst());   // SequencedCollection — Java 21
                                           ^
  symbol:   method getFirst()
  location: interface List<Integer>
1 error
    javac -source 17 -target 17 NewApi.java
javap -v NewApi | grep "major version"
    Вывод (JDK 25.0.2)

  not setting the location of system modules may lead to class files that cannot run on JDK 17

  4. Что разрешит каждый из двух способов?

    --release 17 отказывается: «cannot find symbol: method getFirst()» — компилятор проверяет API платформы 17. -source 17 -target 17 собирает файл версии 61 (Java 17), только предупреждает про bootstrap classpath. На Java 17 такой класс упадёт с NoSuchMethodError. Вывод: всегда --release (в Maven — maven.compiler.release).

Поэкспериментируйте
  • Переименуйте класс Dyn в Runtime (и файл тоже) и запустите снова.
    Сгенерированный код не скомпилируется: «cannot find symbol: method version(), location: class Runtime». Компилятор по умолчанию ищет классы в текущем каталоге (classpath «.»), находит там наш Runtime.class, а тип текущего (безымянного) пакета затеняет java.lang.Runtime. Надёжно — писать в генерируемом коде полные имена: java.lang.Runtime.version().

25.9Самопроверка

Что из этого — константа времени компиляции?

  • static final Integer A = 1;
  • static final int B = Integer.parseInt("1");
  • static final String C = "x" + 1;
  • static final long D = System.nanoTime();
Константа — final примитив или String с константным выражением. Конкатенация литералов константна; Integer не примитив, вызовы методов константами не являются.

Почему checked-исключение можно бросить из метода без throws, обманув компилятор generics?

  • это баг JVM
  • проверка checked-исключений существует только в javac, JVM её не делает
  • generics отключают проверку исключений в JVM
  • так нельзя — верификатор отклонит класс
Атрибут Exceptions носит справочный характер, athrow принимает любой Throwable. Правило «поймай или объяви» — это фаза Flow компилятора.

Зачем javac генерирует мостовой метод compareTo(Object) в классе Money implements Comparable<Money>?

  • после стирания интерфейс объявляет compareTo(Object), и без моста метод класса его не переопределял бы
  • для ускорения сравнения
  • для сериализации
  • чтобы поддержать null
Переопределение в JVM — по совпадению имени и дескриптора. compareTo(LMoney;)I не совпадает с compareTo(Ljava/lang/Object;)I, и мост связывает их кастом.

Перешли на JDK 25, и сборка падает с «cannot find symbol: UserMapperImpl» (генерирует MapStruct). Вероятная причина?

  • MapStruct не поддерживает records
  • JDK 25 удалил javax.annotation.processing
  • сломался classpath
  • с JDK 23 процессоры с classpath не запускаются неявно — их надо указать через processorpath/annotationProcessorPaths
Политика по умолчанию стала -proc:none без явной конфигурации процессоров. Исправление — явный путь процессоров или -proc:full.
Почему изменение public static final int-константы в библиотеке может «не подействовать»?

javac подставляет значение константной переменной прямо в байткод использующего класса, ссылки на класс-владелец не остаётся. Пока зависимый код не перекомпилирован, он видит старое значение. Значения, которые могут меняться, публикуют через методы или не константные выражения.

Во что компилируется for-each по массиву и по списку? Почему по списку бывает ConcurrentModificationException?

По массиву — в цикл по индексу с копией ссылки и длины. По Iterable — в цикл с Iterator: hasNext/next. Итератор коллекций fail-fast: сравнивает modCount с ожидаемым и бросает CME, если коллекцию изменили в обход итератора.

Что такое синтетические члены и где они встречаются?

Поля и методы, добавленные компилятором и отсутствующие в исходнике: мостовые методы, this$0 во внутренних классах, val$x для захваченных переменных, $VALUES в enum, $assertionsDisabled, lambda$…. Помечены ACC_SYNTHETIC; рефлексия возвращает их наравне с обычными, и библиотеки должны их фильтровать.

Чем процессор аннотаций отличается от того, что делает Lombok?

Штатный процессор (JSR 269) может читать модель исходников, генерировать новые файлы и выдавать диагностику, но не менять существующие классы. Lombok через внутренние API javac модифицирует AST компилируемого класса — это мощно, но хрупко: зависит от внутренностей конкретной версии компилятора.

Чем --release лучше -source/-target?

--release N проверяет не только синтаксис и версию class-файла, но и использование API: компилятор подставляет описание API платформы N. С -target код можно собрать новым JDK с вызовом метода, которого нет в старой версии, и получить NoSuchMethodError уже в продакшене.
