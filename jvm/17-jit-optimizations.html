ТЕМА 17 · ИСПОЛНЕНИЕ

Оптимизации JIT и деоптимизация

C2 делает с вашим кодом то, что не сделает ни один человек: встраивает цепочки вызовов, превращает виртуальные вызовы в прямые по профилю, выбрасывает проверки границ массивов, векторизует циклы, удаляет блокировки и объекты. Всё это — спекуляции, и когда предположение нарушается, JVM откатывается в интерпретатор. Разбираем главные оптимизации, профиль типов в месте вызова (с симулятором мономорфных и мегаморфных вызовов) и деоптимизацию.

17.1Встраивание — мать всех оптимизаций

Встраивание (inlining) копирует тело вызываемого метода в место вызова. Само по себе экономит лишь накладные расходы вызова, но главное — открывает остальные оптимизации: после встраивания JIT видит весь код целиком и может удалить проверки, свернуть константы, провести escape analysis.

Встроит ли C2 метод?

Посмотреть решения: -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining («inline (hot)», «too big», «callee is too large», «megamorphic»), или JITWatch по LogCompilation.

17.2Профиль типов: мономорфные и мегаморфные вызовы

Место вызова shape.area() в горячем цикле

Профиль собирается на место вызова, а не на метод: общий метод-утилита, который вызывают с разными типами (например, Stream.map с десятками лямбд в разных частях приложения), становится мегаморфным внутри — так называемое «загрязнение профиля» (profile pollution). Поэтому микробенчмарк со стримом на одной лямбде может быть быстрее, чем тот же стрим в реальном приложении.

Class Hierarchy Analysis: если у класса загружена единственная реализация метода, вызов девиртуализуется без проверки, а JVM запоминает зависимость. При загрузке подкласса, переопределяющего метод, зависимый код деоптимизируется.

По профилю ветка if (order.isVip()) никогда не выполнялась. C2 не генерирует для неё код, а ставит ловушку (uncommon trap). Остальной код оптимизирован так, будто ветки нет.

Пришёл первый VIP-заказ — выполнение доходит до ловушки. Причина (unstable_if, class_check, null_check, range_check, unloaded) и действие записываются.

По отладочной информации, сохранённой при компиляции, JVM восстанавливает состояние так, будто код всё время интерпретировался: встроенные методы снова становятся отдельными кадрами, скалярно заменённые объекты материализуются в куче, значения из регистров раскладываются по слотам.

Выполнение продолжается в интерпретаторе — корректно, но медленно. Версия кода помечается «made not entrant».

Метод снова набирает счётчики и компилируется с учётом новой ветки. Если одна и та же спекуляция проваливается многократно, C2 запоминает это (PerBytecodeTrapLimit) и перестаёт на неё полагаться.

17.5Практикум: пишем и запускаем

Встраивание, профиль типов и деоптимизацию видно в диагностических журналах C2 и чувствуется в замерах. Диагностические флаги требуют -XX:+UnlockDiagnosticVMOptions перед ними. Модуль IDEA — ch17.

Код набирайте руками — так он запоминается. Перед запуском запишите предсказание в поле «Ваш прогноз», затем сверьтесь с реальным выводом (снят на JDK 25.0.2; адреса, времена и хэши у вас будут другими). Как подготовить окружение — на странице курса.

Лаба 17.1PrintInlining: что встроилось и почему нет20 мин

Увидеть решения JIT о встраивании и причины отказов.

  1. Создайте файл Inline.java:
    public class Inline {
    static int small(int x) { return x + 1; }

    static int big(int x) {
        int r = x;
        for (int i = 0; i < 3; i++) {
            r = r * 31 + i; r ^= r >>> 7; r += r << 3; r ^= r >>> 11; r = r * 17 + 5;
            r ^= r >>> 13; r += r << 2; r ^= r >>> 5; r = r * 13 + 7; r ^= r >>> 3;
        }
        return r;
    }

    static int caller(int x) { return small(x) + big(x); }

    public static void main(String[] args) {
        long s = 0;
        for (int i = 0; i < 20_000_000; i++) s += caller(i);
        System.out.println(s);
    }
}

    IDEAVM options: -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining

    javac Inline.java

  2. Встроится ли big, байткод которого больше 35 байт (MaxInlineSize)?

    Зависит от компилятора — и журнал показывает обе строки. C1 отказывается: Inline::big (84 bytes) failed to inline: callee is too large — у него лимит MaxInlineSize = 35 байт. C2 встраивает: inline (hot) — для горячих вызовов действует лимит FreqInlineSize = 325 байт. Размер байткода метода (84) печатается прямо в журнале.

Поэкспериментируйте
  • Добавьте -XX:FreqInlineSize=50. Что напишет журнал про big и как изменится время работы?
    «hot method too big» — big перестанет встраиваться. Сам по себе вызов дёшев, но без встраивания пропадают последующие оптимизации (свёртка, вынос из цикла), и программа обычно замедляется.
Лаба 17.2Моно-, би- и мегаморфный вызов25 мин

Измерить, как число разных типов в одном месте вызова влияет на скорость.

  1. Создайте файл Morph.java:
    public class Morph {
    interface Shape { double area(); }
    record Sq(double a) implements Shape { public double area() { return a * a; } }
    record Circle(double r) implements Shape { public double area() { return 3.14159 * r * r; } }
    record Rect(double a, double b) implements Shape { public double area() { return a * b; } }
    record Tri(double a, double h) implements Shape { public double area() { return a * h / 2; } }

    static double total(Shape[] shapes) {
        double s = 0;
        for (Shape sh : shapes) s += sh.area();      // одно место вызова
        return s;
    }

    public static void main(String[] args) {
        int kinds = Integer.parseInt(args[0]);
        Shape[] all = { new Sq(2), new Circle(1), new Rect(2, 3), new Tri(3, 4) };
        Shape[] arr = new Shape[1000];
        for (int i = 0; i < arr.length; i++) arr[i] = all[i % kinds];
        for (int round = 0; round < 5; round++) {
            long t = System.nanoTime(); double s = 0;
            for (int i = 0; i < 20_000; i++) s += total(arr);
            System.out.printf("типов: %d, раунд %d: %4d мс (%s)%n", kinds, round, (System.nanoTime() - t) / 1_000_000, (long) s);
        }
    }
}
  2. Запустите с аргументом 1, 2, 3 и 4. Где будет скачок времени?

java Morph 4

    1 и 2 типа — быстро и почти одинаково: мономорфный и биморфный вызов JIT встраивает с проверкой класса. С 3 типов вызов мегаморфный: C2 вызывает area() через таблицу (itable), без встраивания, — время заметно растёт. Отсюда совет: в горячем коде полиморфизм через 3+ реализации интерфейса — не бесплатный.

Поэкспериментируйте
  • Сделайте Shape запечатанным (sealed interface Shape permits Sq, Circle, Rect, Tri) и замените вызов на switch с паттернами по типу. Изменится ли картина для 4 типов?
    Часто да: switch по запечатанной иерархии компилируется в проверки типов с встроенными телами, без виртуального вызова. Проверьте на своей машине — это и есть «измеряй, а не верь».
Лаба 17.3Деоптимизация: смена профиля посреди работы20 мин

Поймать момент, когда скомпилированный код становится неверным, и JVM откатывается в интерпретатор.

  1. Создайте файл Deopt.java:
    public class Deopt {
    interface Op { int apply(int x); }
    static final class Inc implements Op { public int apply(int x) { return x + 1; } }
    static final class Dbl implements Op { public int apply(int x) { return x * 2; } }

    static int run(Op op, int n) {
        int s = 0;
        for (int i = 0; i < n; i++) s = op.apply(s) & 0xFFFF;
        return s;
    }

    public static void main(String[] args) {
        for (int i = 0; i < 20_000; i++) run(new Inc(), 100);   // профиль: только Inc
        System.out.println("--- впервые передаём Dbl ---");
        for (int i = 0; i < 20_000; i++) run(new Dbl(), 100);
        System.out.println("готово");
    }
}

    IDEAVM options: -XX:+PrintCompilation

    javac Deopt.java
java -XX:+PrintCompilation Deopt | findstr "Deopt::run впервые готово"

  2. Что произойдёт с C2-версией run после первого вызова с Dbl?

    C2 скомпилировал run со встроенным Inc.apply и проверкой «объект — Inc?». Первый Dbl проваливает проверку — срабатывает uncommon trap: кадр переводится обратно в интерпретатор, скомпилированная версия помечается made not entrant. Затем метод перекомпилируется уже с биморфным профилем. В журнале это строки made not entrant для run сразу после вашей разделительной строки и новые компиляции.

Поэкспериментируйте
  • Добавьте -Xlog:deoptimization=debug. Что показывает журнал?
    Причину и место каждой деоптимизации: reason=class_check (не тот класс), метод, байткодный индекс. В продакшене повторяющиеся деоптимизации одного метода («deopt storm») ищут через JFR-событие jdk.Deoptimization.

17.6Самопроверка

Почему встраивание называют главной оптимизацией JIT?

  • Оно уменьшает размер кода
  • Оно открывает остальные оптимизации: после встраивания компилятор видит код целиком
  • Оно ускоряет загрузку классов
  • Оно убирает GC
Escape analysis, удаление проверок, свёртка констант работают через границы встроенных вызовов.

Что такое мегаморфный вызов?

  • Вызов статического метода
  • Вызов с большим числом аргументов
  • Вызов, который JIT встроил дважды
  • Виртуальный вызов, в месте которого встречалось 3+ типов получателя: без встраивания, через vtable
Мономорфный и биморфный — встраиваются с проверками типа.

Что происходит при срабатывании uncommon trap?

  • Деоптимизация: состояние восстанавливается для интерпретатора, выполнение продолжается корректно, код позже перекомпилируется
  • JVM падает
  • Выбрасывается исключение
  • Метод пропускается
Спекулятивные оптимизации безопасны благодаря деоптимизации.

Почему микробенчмарк стрима с одной лямбдой бывает быстрее того же кода в приложении?

  • В приложении другой GC
  • Бенчмарк использует больше памяти
  • В приложении внутренние места вызова Stream получают много разных лямбд — профиль загрязнён, вызовы мегаморфные, встраивания нет
  • JMH отключает JIT
Profile pollution.
Как написать код, удобный для JIT?

Маленькие методы с горячим путём (меньше FreqInlineSize), редкие ветки — отдельными методами; избегать мегаморфных мест в узких циклах (группировать по типу, специализировать); простые циклы по массивам с int-счётчиком (векторизация, удаление проверок границ); не создавать лишних объектов, которые сбегают; static final для констант и MethodHandle; стабильные типы и ветки. Но всё — после профилирования: в 99% кода JIT справляется сам.

Что такое deoptimization storm и как его заметить?

Повторяющиеся деоптимизации и перекомпиляции одних и тех же методов (например, из-за постоянной смены типов, загрузки классов, переключения редких веток) — CPU уходит на компиляцию, код часто исполняется интерпретатором. Видно в JFR (jdk.Deoptimization), -Xlog:deoptimization, PrintCompilation (много made not entrant для одного метода), по росту времени потоков компилятора.
