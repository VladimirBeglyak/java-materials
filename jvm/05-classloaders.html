Загрузчики классов и делегирование

Класс попадает в JVM лениво — при первом обращении — и всегда через загрузчик. Загрузчики образуют иерархию и по умолчанию сначала спрашивают родителя. Это обеспечивает единственность java.lang.String, но рождает и самые запутанные ошибки: ClassCastException: Foo cannot be cast to Foo, NoClassDefFoundError при наличии класса в jar, «не тот» класс из чужой библиотеки. Симулятор делегирования покажет, кто и откуда загрузит класс.

protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {               // параллельные загрузчики — блокировка на имя
        Class<?> c = findLoadedClass(name);                  // 1. уже загружал?
        if (c == null) {
            try {
                c = parent != null ? parent.loadClass(name, false)   // 2. сначала родитель
                                   : findBootstrapClassOrNull(name);
            } catch (ClassNotFoundException ignored) { }
            if (c == null) c = findClass(name);              // 3. только потом сам (переопределяют это)
        }
        if (resolve) resolveClass(c);
        return c;
    }
}

5.3Симулятор делегирования

Кто загрузит класс?

5.4Идентичность класса = имя + загрузчик

В JVM класс однозначно определяется парой (полное имя, определяющий загрузчик). Один и тот же байткод, загруженный двумя загрузчиками, даёт два разных класса с разными статическими полями, и объекты одного нельзя привести к другому.

URL[] urls = { Path.of("lib/foo.jar").toUri().toURL() };
try (var l1 = new URLClassLoader(urls, null); var l2 = new URLClassLoader(urls, null)) {   // родитель null → bootstrap
    Class<?> a = l1.loadClass("com.x.Foo"), b = l2.loadClass("com.x.Foo");
    System.out.println(a == b);                       // false
    Object foo = a.getDeclaredConstructor().newInstance();
    b.cast(foo);                                      // ClassCastException: class com.x.Foo cannot be cast to class com.x.Foo
                                                      //   (com.x.Foo is in unnamed module of loader URLClassLoader @1b6d3586; …@4554617c)
}
Определяющий и инициирующий загрузчик Определяющий (defining) — тот, кто вызвал defineClass; его возвращает getClassLoader(). Инициирующий (initiating) — тот, у кого спросили; при делегировании их может быть несколько. JVM проверяет loader constraints: если два загрузчика видят под одним именем разные классы там, где сигнатура метода их связывает, будет LinkageError: loader constraint violation — защита от подмены типов.

5.6Class.forName, loadClass и контекстный загрузчик

ВызовЗагрузчикИнициализирует?
Class.forName("X")загрузчик вызывающего классада (выполнит static-блоки)
Class.forName("X", false, loader)указанныйнет
loader.loadClass("X")указанныйнет
X.classзагрузчик текущего классанет

Контекстный загрузчик потока (Thread.getContextClassLoader()) решает проблему «родитель должен загрузить класс ребёнка»: библиотека, загруженная высоко (например, JDBC DriverManager или JAXB в bootstrap/platform), не видит классы приложения через свой загрузчик. Поэтому фреймворки берут контекстный загрузчик, который сервер приложений или Spring Boot выставляет в загрузчик приложения. Проблемы: пулы потоков с чужим контекстным загрузчиком, ForkJoinPool.commonPool (у его потоков — системный загрузчик), утечки в серверах приложений.

# [class,load] com.fasterxml.jackson.databind.ObjectMapper source: jar:file:/app/lib/jackson-databind-2.15.2.jar!/

jcmd <pid> VM.classloaders                    # дерево загрузчиков с числом классов

Лаба 5.1Кто загрузил этот класс10 мин

Увидеть три встроенных загрузчика и то, что у классов ядра загрузчик — null.

  1. Создайте файл WhoLoaded.java:
    public class WhoLoaded {
    static void show(Class<?> c) {
        ClassLoader l = c.getClassLoader();
        System.out.printf("%-34s модуль %-15s загрузчик %s%n",
                c.getName(), c.getModule().getName(), l == null ? "bootstrap (null)" : l.getName());
    }

    public static void main(String[] args) throws Exception {
        show(String.class);
        show(java.sql.Connection.class);
        show(Class.forName("com.sun.net.httpserver.HttpServer"));
        show(Class.forName("com.sun.source.tree.Tree"));
        show(WhoLoaded.class);

        ClassLoader cl = WhoLoaded.class.getClassLoader();
        while (cl != null) {
            System.out.println("  " + cl.getName() + " -> родитель " + cl.getParent());
            cl = cl.getParent();
        }
    }
}
  2. Какие загрузчики окажутся у String, java.sql.Connection, HttpServer, com.sun.source.tree.Tree и WhoLoaded?
    javac WhoLoaded.java
java WhoLoaded
    Вывод (JDK 25.0.2)
    java.lang.String                   модуль java.base       загрузчик bootstrap (null)
java.sql.Connection                модуль java.sql        загрузчик platform
com.sun.net.httpserver.HttpServer  модуль jdk.httpserver  загрузчик platform
com.sun.source.tree.Tree           модуль jdk.compiler    загрузчик app
WhoLoaded                          модуль null            загрузчик app
  app -> родитель jdk.internal.loader.ClassLoaders$PlatformClassLoader@4e0e2f2a
  platform -> родитель null

    String — null (bootstrap, написан на C++ и не имеет Java-объекта); java.sql.Connection и HttpServer — platform (модули java.sql и jdk.httpserver); Tree из модуля jdk.compiler — app: модули инструментов JDK (компилятор, jshell) отданы прикладному загрузчику, не всё из JDK грузит platform; WhoLoaded — app. Цепочка родителей: app → platform → null.

Поэкспериментируйте
  • Выполните jcmd <pid> VM.classloaders для любого работающего процесса (например, Sleeper из темы 01).
    Дерево загрузчиков с числом загруженных ими классов — то же, что вы напечатали, но взгляд со стороны JVM. В Spring Boot-приложении там появится LaunchedClassLoader.
Лаба 5.2Делегирование в логе: свой загрузчик-шпион15 мин

Подсмотреть, какие запросы приходят загрузчику и сколько из них он передаёт родителю.

  1. Создайте файл SpyLoader.java:
    public class SpyLoader extends ClassLoader {
    SpyLoader(ClassLoader parent) { super("spy", parent); }

    @Override
    protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
        System.out.println("  spy.loadClass(" + name + ")");
        return super.loadClass(name, resolve);   // стандартное делегирование: кэш -> родитель -> findClass
    }

    public static void main(String[] args) throws Exception {
        var spy = new SpyLoader(SpyLoader.class.getClassLoader());
        System.out.println("1) загружаем java.util.ArrayList:");
        Class<?> c = spy.loadClass("java.util.ArrayList");
        System.out.println("   получили " + c + ", загрузчик = " + c.getClassLoader());
        System.out.println("2) загружаем Target:");
        Class<?> t = spy.loadClass("Target");
        System.out.println("   получили " + t + ", загрузчик = " + t.getClassLoader().getName());
        System.out.println("3) создаём экземпляр Target:");
        t.getDeclaredConstructor().newInstance();
    }
}

class Target {
    Target() { System.out.println("   Target создан, внутри используется " + new java.util.StringJoiner(",").add("a").add("b")); }
}
  2. Пройдёт ли запрос StringJoiner из конструктора Target через шпиона?
    javac SpyLoader.java
java SpyLoader
    Вывод (JDK 25.0.2)
    1) загружаем java.util.ArrayList:
  spy.loadClass(java.util.ArrayList)
   получили class java.util.ArrayList, загрузчик = null
2) загружаем Target:
  spy.loadClass(Target)
   получили class Target, загрузчик = app
3) создаём экземпляр Target:
   Target создан, внутри используется a,b

    Нет. Шпион лишь получил запрос и делегировал его родителю (app), который и определил класс Target. Ссылки из байткода класса разрешаются через его определяющий загрузчик — app, а не spy. Поэтому в логе только два запроса. Чтобы шпион видел всё, он должен сам определять классы (лаба 7.1).

Поэкспериментируйте
  • Переопределите findClass вместо loadClass и добавьте туда печать. Вызовется ли он для Target?
    Нет: findClass вызывается только если родитель класс не нашёл. Target лежит в classpath — его найдёт app-загрузчик.
Лаба 5.3Один байткод — два класса25 мин

Загрузить один и тот же class-файл двумя загрузчиками и получить знаменитое ClassCastException: Plugin cannot be cast to Plugin.

  1. «Плагин» кладём в отдельный каталог plugin-src — рядом с src, не внутри него, чтобы его не было в classpath приложения:
    public class Plugin {
    public static int counter = 0;
    public String hello() { counter++; return "привет из плагина, counter=" + counter; }
}
    import java.net.URL;
import java.net.URLClassLoader;
import java.nio.file.Path;

public class Host {
    public static void main(String[] args) throws Exception {
        URL[] urls = { Path.of("plugins").toUri().toURL() };
        var l1 = new URLClassLoader("L1", urls, ClassLoader.getPlatformClassLoader());
        var l2 = new URLClassLoader("L2", urls, ClassLoader.getPlatformClassLoader());

        Class<?> a = l1.loadClass("Plugin"), b = l2.loadClass("Plugin");
        System.out.println("имена равны:   " + a.getName().equals(b.getName()));
        System.out.println("классы равны:  " + (a == b));

        Object pa = a.getDeclaredConstructor().newInstance();
        Object pb = b.getDeclaredConstructor().newInstance();
        System.out.println(a.getMethod("hello").invoke(pa));
        System.out.println(a.getMethod("hello").invoke(pa));
        System.out.println(b.getMethod("hello").invoke(pb));

        System.out.println("pb instanceof a? " + a.isInstance(pb));
        a.cast(pb);
    }
}
  2. Скомпилируйте плагин в каталог plugins, а хост — как обычно (IDEA: запуск из терминала в каталоге модуля):
    javac -d plugins plugin-src/Plugin.java
javac Host.java
java Host
    Вывод (JDK 25.0.2)
    имена равны:   true
классы равны:  false
привет из плагина, counter=1
привет из плагина, counter=2
привет из плагина, counter=1
pb instanceof a? false
Exception in thread "main" java.lang.ClassCastException: Cannot cast Plugin to Plugin
	at java.base/java.lang.Class.cast(Class.java:3492)
	at Host.main(Host.java:22)
  3. Почему третий вызов печатает counter=1, а не 3?

    У каждого из двух классов Plugin свои статические поля: класс — это пара «имя + определяющий загрузчик». Отсюда же ClassCastException: Cannot cast Plugin to Plugin. При обычном приведении (Plugin) obj в коде сообщение ещё подробнее: class Plugin cannot be cast to class Plugin (Plugin is in unnamed module of loader 'L2'; Plugin is in unnamed module of loader 'L1') — имя загрузчика в сообщении и есть подсказка. Так изолируют плагины, веб-приложения в Tomcat и версии библиотек.

Поэкспериментируйте
  • Создайте l2 с родителем l1 вместо platform. Что изменится?
    a == b станет true: l2 сначала спросит родителя l1, тот уже загрузил Plugin. Счётчик станет общим (1, 2, 3), исключения не будет.
  • Запустите java -Xlog:class+load Host и найдите строки с Plugin.
    Две строки Plugin source: file:/…/plugins/ — JVM действительно загрузила и разобрала файл дважды.
Лаба 5.4ClassNotFoundException против NoClassDefFoundError15 мин

Вызвать обе ошибки и научиться по стектрейсу понимать, какая именно ситуация произошла.

  1. Создайте файл Errors.java:
    public class Errors {
    public static void main(String[] args) {
        try {
            Class.forName("com.example.Nope");
        } catch (ClassNotFoundException e) {
            System.out.println("1) " + e);
        }
        try {
            new Helper().run();
        } catch (NoClassDefFoundError e) {
            System.out.println("2) " + e);
        }
        for (int i = 0; i < 2; i++) {
            try {
                System.out.println(Broken.VALUE);
            } catch (Throwable e) {
                System.out.println("3." + i + ") " + e);
            }
        }
    }
}

class Helper { void run() { System.out.println("Helper работает"); } }

class Broken {
    static final int VALUE = Integer.parseInt("не число");
}
  2. Скомпилируйте, затем удалите Helper.class — как будто jar с ним забыли положить в рантайм:
    javac Errors.java
del Helper.class
java Errors
    Вывод (JDK 25.0.2)
    1) java.lang.ClassNotFoundException: com.example.Nope
2) java.lang.NoClassDefFoundError: Helper
3.0) java.lang.ExceptionInInitializerError
3.1) java.lang.NoClassDefFoundError: Could not initialize class Broken
  3. Почему для Broken первая и вторая попытки дают разные ошибки?

    Первая попытка запускает инициализацию класса; исключение в статическом инициализаторе оборачивается в ExceptionInInitializerError, класс помечается как «ошибочный». Повторно JVM инициализацию не выполняет и сразу бросает NoClassDefFoundError: Could not initialize class Broken, указывая причину ExceptionInInitializerError. В логах продакшена часто видна только вторая ошибка — ищите первую выше.

Поэкспериментируйте
  • Почему VALUE здесь не подставляется в байткод как константа, как в лабе 2.2?
    Integer.parseInt(...) — не константное выражение, поэтому VALUE — обычное статическое поле, и обращение к нему инициализирует класс.

5.8Самопроверка

Почему нельзя подменить java.lang.String, положив свою версию в classpath?

  • JVM проверяет подпись класса
  • String final
  • Делегирование: app-загрузчик сначала спросит родителей, и bootstrap вернёт настоящий String; к тому же определять java.* может только платформа
  • Classpath читается после запуска
Parent-first — основа безопасности и единственности ядра.

ClassCastException: com.x.Foo cannot be cast to com.x.Foo. Причина?

  • Класс загружен двумя разными загрузчиками — это два разных класса
  • Ошибка компилятора
  • Разные версии Java
  • Нехватка памяти
Идентичность = имя + определяющий загрузчик. Частый случай — devtools/hot reload и плагины.

NoClassDefFoundError: Could not initialize class com.x.Config. Где искать первопричину?

  • В classpath — класса нет
  • В версии JDK
  • В правах доступа
  • Выше в логе: ExceptionInInitializerError при первой попытке выполнить static-инициализатор
После неудачной инициализации класс помечается ошибочным навсегда.

Чем Class.forName("X") отличается от loader.loadClass("X")?

  • Ничем
  • forName по умолчанию инициализирует класс (static-блоки), loadClass — только загружает
  • loadClass не использует делегирование
  • forName работает только для JDK
Старые JDBC-драйверы регистрировались в static-блоке — отсюда Class.forName("…Driver").
Объясните модель делегирования и зачем иногда её нарушают.

Загрузчик сначала проверяет свой кэш, затем просит родителя и только если тот не нашёл — ищет сам. Это даёт единственность классов ядра и безопасность. Нарушают (child-first) в контейнерах, где приложению нужно использовать свои версии библиотек, отличные от библиотек контейнера: веб-приложения в Tomcat, плагины, OSGi. Цена — риск двух копий одного класса и ClassCastException/LinkageError на границах.

Когда класс загружается, если он используется в коде?

Лениво: при первом активном использовании, требующем класс — создание экземпляра, вызов статического метода, обращение к статическому полю, рефлексия, загрузка подкласса (суперкласс грузится раньше). Простое упоминание типа в сигнатуре или объявление переменной не загружает класс, хотя верификатор иногда загружает классы для проверки присваиваний. Увидеть порядок можно через -verbose:class.
