17.1Встраивание — мать всех оптимизаций

Вызов метода стоит времени, но главное — он мешает оптимизатору видеть код целиком. Встраивание подставляет тело маленького метода прямо в место вызова — как вместо ссылки «см. рецепт на стр. 50» вклеить сам рецепт. После этого геттеры исчезают, константы сворачиваются, лишние проверки удаляются. Поэтому в Java не нужно бояться маленьких методов: горячие встраиваются.

Главная мысль Встраивание убирает вызов и открывает дорогу остальным оптимизациям.

17.2Профиль типов

Вызов shape.area() в горячем цикле
профиль: всегда приходил Circle (мономорфный вызов)
JIT: «проверю, что это Circle, и встрою Circle.area()» → очень быстроприходят Circle и Square (биморфный)
JIT: две проверки и два встроенных варианта → всё ещё быстроприходят 5 разных фигур (мегаморфный)
JIT: встраивать нечего → обычный виртуальный вызов через таблицумегаморфные вызовы в самых горячих местах заметно медленнее
но это важно только для действительно горячего кода

Вызов превращается в проверку + встроенный код.

Тоже хорошо оптимизируется.

Оптимизация невозможна.

Не переписывайте дизайн без замеров.

Главная мысль Один-два типа в месте вызова — встраивание; много — обычный медленный вызов.

17.3Каталог оптимизаций

  • Удаление мёртвого кода — то, чей результат не используется.
  • Свёртка констант — 60 × 60 × 24 считается заранее.
  • Вынос из цикла — неизменные вычисления — один раз до цикла.
  • Удаление проверок границ массивов, если доказано, что выхода за границу нет.
  • Escape analysis — объекты без «побега» не создаются (глава 11).
  • Удаление и укрупнение блокировок, которые никому не нужны.
  • Векторизация — одна команда SIMD на несколько элементов.
Главная мысль JIT убирает лишнее, считает заранее, выносит из циклов и векторизует.

17.4Деоптимизация: откат

JIT оптимизирует смело, опираясь на предположения: «эта ветка никогда не выполняется», «здесь всегда Circle». Если реальность изменилась (пришёл Square, сработала «невозможная» ветка, загрузился новый класс), скомпилированный код становится неверным. Тогда JVM деоптимизирует: возвращает выполнение в интерпретатор, собирает новый профиль и позже компилирует заново. Редкие деоптимизации — норма; постоянные — признак проблемы.

Главная мысль Неверное предположение → откат в интерпретатор → перекомпиляция.

17.6Проверьте себя

Почему в Java не стоит бояться маленьких методов вроде геттеров?

  • они не вызываются
  • они в интерпретаторе быстрее
  • горячие маленькие методы встраиваются, и вызова нет
  • стоит бояться
Встраивание.

Что такое мегаморфный вызов?

  • в одном месте вызова встречается много разных реализаций — встроить нельзя
  • очень большой метод
  • вызов статического метода
  • рекурсия
Тогда остаётся обычный виртуальный вызов.

Что происходит при деоптимизации?

  • программа падает
  • метод удаляется
  • JVM перезапускается
  • скомпилированный код отбрасывается, выполнение возвращается в интерпретатор
Позже код перекомпилируется.

Почему встраивание называют «матерью всех оптимизаций»?

  • оно самое старое
  • после него оптимизатор видит код целиком и может применить остальные оптимизации
  • оно самое простое
  • так назвали в честь автора
Без него остальные работают в пределах одного метода.

Что даёт векторизация?

  • сжатие памяти
  • шифрование
  • обработку нескольких элементов массива одной командой процессора
  • параллельные потоки
Команды SIMD.
