Архитектура JVM и запуск

JVM — это спецификация абстрактной машины и её реализации, из которых в продакшене почти всегда работает HotSpot. Здесь — карта подсистем (загрузка классов, области памяти, движок исполнения, сборщик мусора, нативный интерфейс), что именно происходит между командой java -jar app.jar и первой строкой main, как JVM сама подбирает настройки под машину и как читать её флаги.

1.1Спецификация и реализации

The Java Virtual Machine Specification (JVMS) описывает формат class-файла, набор инструкций, модель загрузки и линковки, области данных времени выполнения — но не говорит, как устроить сборщик мусора, JIT или раскладку объектов. Это свобода реализаций:

РеализацияОсобенности
HotSpot (OpenJDK: Oracle, Temurin, Corretto, Zulu, Liberica…)эталон и 95%+ продакшена: интерпретатор + C1/C2, G1/ZGC/Shenandoah/Parallel/Serial. Всё в этом курсе — про него, если не сказано иное
Eclipse OpenJ9 (IBM Semeru)меньше памяти, быстрый старт, общий кэш классов, свои сборщики (gencon, balanced)
GraalVMHotSpot с JIT-компилятором Graal (написан на Java) + Native Image — AOT-компиляция в исполняемый файл (тема 20)
Android ARTне JVM: свой байткод (dex), AOT/JIT — другая спецификация
JDK, JRE, JVM JVM исполняет байткод; JRE = JVM + стандартная библиотека (с Java 11 отдельно не поставляется — собирается jlink); JDK = JRE + компилятор javac и инструменты (jcmd, jfr, javap, jlink). Сама JVM — нативная библиотека libjvm.so / jvm.dll, написанная на C++.

Исполняемый файл java — небольшая программа на C (libjli). Она разбирает командную строку и переменную JDK_JAVA_OPTIONS, файлы аргументов @args.txt, для -jar читает META-INF/MANIFEST.MF (Main-Class, Class-Path), выбирает вариант JVM и загружает libjvm. Главный поток лаунчера создаёт новый поток с большим стеком — он станет потоком main.

JNI_CreateJavaVM → Threads::create_vm: разбор флагов -XX, эргономика (выбор GC, размера кучи и числа потоков под машину — см. ниже), инициализация слоя ОС, механизма safepoint, агентов JVMTI (-javaagent загружается позже, но регистрируется здесь).

Резервируется (но ещё не занимается физически) адресное пространство кучи размера -Xmx, создаются metaspace и code cache, запускаются служебные потоки: GC, компиляторы C1/C2, VM Thread (выполняет операции в safepoint), Signal Dispatcher, Reference Handler, Finalizer.

Встроенный (bootstrap) загрузчик загружает ядро java.base — из файла lib/modules (формат jimage) или из архива CDS (тема 20), что гораздо быстрее. Выполняются System.initPhase1 (свойства, потоки ввода-вывода), initPhase2 (система модулей: boot layer), initPhase3 (SecurityManager-наследие, системный загрузчик).

Создаются платформенный и прикладной (system / app) загрузчики. Прикладной знает classpath (или module path) — именно он загрузит ваш главный класс.

sun.launcher.LauncherHelper.checkAndLoadMain загружает главный класс, проверяет наличие main (с Java 21+ — и «экземплярного» main без static и аргументов), затем лаунчер через JNI вызывает его. Первое обращение к классу запускает его линковку и <clinit> (тема 06).

Когда main вернулся, поток вызывает DestroyJavaVM: ждёт завершения всех не-daemon потоков, затем выполняет shutdown hooks (Runtime.addShutdownHook) и завершает процесс. System.exit(n) запускает hooks сразу, не дожидаясь потоков; kill -9 — без hooks вообще.

java -Xlog:startuptime -Xlog:class+load:file=classes.txt -jar app.jar   # что и когда загружалось
java -Xshare:dump                                                       # (пере)создать CDS-архив JDK
java -verbose:class -version | head                                     # первые загружаемые классы
jcmd <pid> Thread.print | grep '"' | head -20                           # служебные потоки JVM

1.4Эргономика: настройки по умолчанию

1.6Практикум: пишем и запускаем

Здесь вы сами увидите то, о чём шла речь выше: сколько работы JVM делает до первой строки main, какие настройки она выбирает «сама» на вашей машине и как прочитать флаги живого процесса. Создайте в IDEA модуль ch01 и кладите классы в папку src (пакет по умолчанию).

Код набирайте руками — так он запоминается. Перед запуском запишите предсказание в поле «Ваш прогноз», затем сверьтесь с реальным выводом (снят на JDK 25.0.2; адреса, времена и хэши у вас будут другими). Как подготовить окружение — на странице курса.

Лаба 1.1Что JVM успевает сделать до main15 мин

Измерить, сколько классов загружается и сколько миллисекунд проходит до вызова main, и как на это влияет архив CDS.

  1. Создайте класс Hello. Он печатает, сколько прошло от старта процесса и сколько классов уже загружено:
    import java.lang.management.ManagementFactory;

public class Hello {
    public static void main(String[] args) {
        var rt = ManagementFactory.getRuntimeMXBean();
        long sinceStart = System.currentTimeMillis() - rt.getStartTime();
        int classes = ManagementFactory.getClassLoadingMXBean().getLoadedClassCount();
        System.out.println("JVM:            " + rt.getVmName() + " " + rt.getVmVersion());
        System.out.println("до main прошло: ~" + sinceStart + " мс");
        System.out.println("классов загружено: " + classes);
        System.out.println("pid: " + ProcessHandle.current().pid());
    }
}

    IDEAЗапустите зелёным ▶ рядом с main. Затем откройте встроенный терминал (Alt+F12) — дальше часть команд удобнее запускать из него.

  2. Запустите тот же класс из терминала без отдельной компиляции — лаунчер сам скомпилирует один файл в память (JEP 330):
    java Hello.java
    Вывод (JDK 25.0.2)
    JVM:            OpenJDK 64-Bit Server VM 25.0.2+10-69
до main прошло: ~380 мс
классов загружено: 2610
pid: 32272

    Цифра «классов загружено» включает и классы самого компилятора javac, который лаунчер запустил ради однофайлового режима. Чтобы увидеть «чистую» JVM, скомпилируйте заранее.

  3. Скомпилируйте и запустите как обычно:
    javac Hello.java
java Hello
    Вывод (JDK 25.0.2)
    JVM:            OpenJDK 64-Bit Server VM 25.0.2+10-69
до main прошло: ~18 мс

    Вывод (JDK 25.0.2)

Поэкспериментируйте
  • Найдите в логе строку с Hello: какие классы загружены непосредственно до и после него?
    Прямо перед Hello — классы, нужные загрузчику (java.security.Permissions и др.), сразу после — те, которыми лаунчер ищет метод main (MethodFinder), и только потом ManagementFactory и весь JMX. Классы загружаются лениво — по первому обращению.
  • Удалите из кода работу с ManagementFactory, оставьте только println. Сколько классов теперь?
    Около 440 вместо ~780: JMX тянет за собой сотни классов. Подсчитать можно и без кода: java -Xlog:class+load Hello | find /c "source:" (Windows) или | grep -c source:.
Лаба 1.2Эргономика: что JVM выбрала на вашей машине15 мин

Узнать размер кучи, сборщик и число процессоров, которые JVM определила автоматически, и заставить её выбрать иначе.

  1. Создайте класс Ergo:
    import java.lang.management.ManagementFactory;

public class Ergo {
    public static void main(String[] args) {
        Runtime rt = Runtime.getRuntime();
        System.out.println("CPU для JVM:   " + rt.availableProcessors());
        System.out.println("max heap (MB): " + rt.maxMemory() / 1024 / 1024);
        System.out.println("init heap(MB): " + rt.totalMemory() / 1024 / 1024);
        for (var gc : ManagementFactory.getGarbageCollectorMXBeans()) {
            System.out.println("сборщик:       " + gc.getName());
        }
    }
}
    javac Ergo.java
java Ergo
    Вывод (JDK 25.0.2)
    CPU для JVM:   18
max heap (MB): 8056
init heap(MB): 508
сборщик:       G1 Young Generation
сборщик:       G1 Concurrent GC
сборщик:       G1 Old Generation

    На машине, где снят вывод, 18 логических процессоров и 32 ГБ памяти: max heap = ¼ физической памяти, выбран G1. У вас числа будут свои — сверьте их с диспетчером задач.

  2. Запустим с -XX:ActiveProcessorCount=1 -Xmx256m (как в маленьком контейнере). Какой сборщик выберет JVM?

    IDEAVM options: -XX:ActiveProcessorCount=1 -Xmx256m

    java -XX:ActiveProcessorCount=1 -Xmx256m Ergo
    Вывод (JDK 25.0.2)
    CPU для JVM:   1
max heap (MB): 247
init heap(MB): 247
сборщик:       Copy
сборщик:       MarkSweepCompact

    Serial (в выводе — Copy и MarkSweepCompact). Если процессоров меньше двух или памяти меньше 1792 МБ, машина считается не «серверной», и эргономика выбирает однопоточный SerialGC вместо G1. Это частая неожиданность в контейнерах с cpu: 1.

  3. Сверьте с тем, что JVM говорит о себе сама. Флаг -XX:+PrintFlagsFinal печатает все ~700 флагов с итоговыми значениями; {ergonomic} отмечает выбранные автоматически:
    java -XX:+PrintFlagsFinal -version | findstr /R "MaxHeapSize UseG1GC UseSerialGC ParallelGCThreads"
    Вывод (JDK 25.0.2)

     uint ConcGCThreads                            = 4                                         {product} {ergonomic}
   size_t InitialHeapSize                          = 528482304                                 {product} {ergonomic}

Поэкспериментируйте
  • Запустите с -XX:MaxRAMPercentage=50 — как изменился max heap?
    Куча стала равна половине физической памяти: MaxRAMPercentage задаёт долю памяти машины (или лимита контейнера) под кучу, по умолчанию 25%.
  • Почему max heap из Runtime чуть меньше, чем -Xmx? Попробуйте -Xmx256m -XX:+UseSerialGC.
    maxMemory() не учитывает одно из пространств выживших (survivor): в любой момент одно из них пустое и недоступно для объектов.
Лаба 1.3Флаги живого процесса: jcmd15 мин

Подключиться к работающей JVM и прочитать её командную строку, флаги и системные свойства — без перезапуска.

  1. Создайте программу, которая просто ждёт:
    public class Sleeper {
    public static void main(String[] args) throws Exception {
        System.out.println("pid " + ProcessHandle.current().pid() + ", жду 10 минут…");
        Thread.sleep(600_000);
    }
}

    IDEAЗапустите с VM options -Xmx300m -XX:+UseParallelGC. Процесс будет висеть — это и нужно.

  • Выполните jcmd <pid> VM.system_properties и найдите java.class.path — куда IDEA положила скомпилированный класс?
    В …/out/production/ch01 (или target/classes в Maven-проекте) — IDEA компилирует в свой каталог и передаёт его через -classpath.

Лаба 1.4Кто ещё живёт в «однопоточной» программе10 мин

Увидеть служебные потоки JVM: GC, JIT-компиляторы, обработчик ссылок, диспетчер сигналов.

  1. Создайте класс, который печатает все Java-потоки процесса:
    public class Threads {
    public static void main(String[] args) {
        Thread.getAllStackTraces().keySet().stream()
              .sorted((a, b) -> a.getName().compareTo(b.getName()))
              .forEach(t -> System.out.printf("%-22s daemon=%-5s prio=%d group=%s%n",
                      t.getName(), t.isDaemon(), t.getPriority(),
                      t.getThreadGroup() == null ? "-" : t.getThreadGroup().getName()));
    }
}

1.7Самопроверка

Что определяет спецификация JVM, а что оставляет реализации?

  • Определяет алгоритм GC и раскладку объектов
  • Определяет только синтаксис Java
  • Определяет формат class-файла, инструкции и загрузку классов; GC, JIT и раскладка объектов — на усмотрение реализации
  • Ничего не определяет, всё — HotSpot
Поэтому OpenJ9 и HotSpot исполняют одни и те же class-файлы по-разному внутри.

Программа запустила поток и main() завершился. Когда закончится процесс?

  • Когда завершатся все не-daemon потоки (затем shutdown hooks)
  • Сразу после main
  • Никогда
  • Через 30 секунд
DestroyJavaVM ждёт не-daemon потоки — частая причина «зависших» утилит.

Какой GC выберет JDK 21 в контейнере с 1 CPU и 1 ГБ памяти без флагов?

  • G1
  • Serial
  • ZGC
  • Parallel
Меньше 2 процессоров или 1792 МБ — машина «клиентского класса».

Расскажите, что происходит от команды java до первой строки main.

Лаунчер разбирает аргументы и манифест, загружает libjvm и вызывает JNI_CreateJavaVM: флаги и эргономика, резервирование кучи и metaspace, запуск служебных потоков (GC, JIT, VM Thread), загрузка базовых классов bootstrap-загрузчиком (часто из CDS-архива), инициализация System в три фазы и boot layer модулей, создание платформенного и прикладного загрузчиков. Затем LauncherHelper загружает главный класс, его линковка и инициализация, вызов main через JNI.

Какие служебные потоки есть в любой JVM и что они делают?

VM Thread — выполняет операции, требующие safepoint (некоторые фазы GC, деоптимизация, дампы потоков); потоки GC (рабочие и конкурентные); C1/C2 CompilerThread — JIT-компиляция; Reference Handler — ставит очищенные ссылки в очереди; Finalizer — вызывает finalize; Signal Dispatcher — обработка сигналов (например, SIGQUIT для дампа потоков); Common-Cleaner; Attach Listener — подключение jcmd/агентов; Notification Thread, Service Thread.
