Архитектура JVM и запуск

JVM — это спецификация абстрактной машины и её реализации, из которых в продакшене почти всегда работает HotSpot. Здесь — карта подсистем (загрузка классов, области памяти, движок исполнения, сборщик мусора, нативный интерфейс), что именно происходит между командой java -jar app.jar и первой строкой main, как JVM сама подбирает настройки под машину и как читать её флаги.

1.1Спецификация и реализации

The Java Virtual Machine Specification (JVMS) описывает формат class-файла, набор инструкций, модель загрузки и линковки, области данных времени выполнения — но не говорит, как устроить сборщик мусора, JIT или раскладку объектов. Это свобода реализаций:

РеализацияОсобенности
HotSpot (OpenJDK: Oracle, Temurin, Corretto, Zulu, Liberica…)эталон и 95%+ продакшена: интерпретатор + C1/C2, G1/ZGC/Shenandoah/Parallel/Serial. Всё в этом курсе — про него, если не сказано иное
Eclipse OpenJ9 (IBM Semeru)меньше памяти, быстрый старт, общий кэш классов, свои сборщики (gencon, balanced)
GraalVMHotSpot с JIT-компилятором Graal (написан на Java) + Native Image — AOT-компиляция в исполняемый файл (тема 20)
Android ARTне JVM: свой байткод (dex), AOT/JIT — другая спецификация
JDK, JRE, JVM JVM исполняет байткод; JRE = JVM + стандартная библиотека (с Java 11 отдельно не поставляется — собирается jlink); JDK = JRE + компилятор javac и инструменты (jcmd, jfr, javap, jlink). Сама JVM — нативная библиотека libjvm.so / jvm.dll, написанная на C++.

Исполняемый файл java — небольшая программа на C (libjli). Она разбирает командную строку и переменную JDK_JAVA_OPTIONS, файлы аргументов @args.txt, для -jar читает META-INF/MANIFEST.MF (Main-Class, Class-Path), выбирает вариант JVM и загружает libjvm. Главный поток лаунчера создаёт новый поток с большим стеком — он станет потоком main.

JNI_CreateJavaVM → Threads::create_vm: разбор флагов -XX, эргономика (выбор GC, размера кучи и числа потоков под машину — см. ниже), инициализация слоя ОС, механизма safepoint, агентов JVMTI (-javaagent загружается позже, но регистрируется здесь).

Резервируется (но ещё не занимается физически) адресное пространство кучи размера -Xmx, создаются metaspace и code cache, запускаются служебные потоки: GC, компиляторы C1/C2, VM Thread (выполняет операции в safepoint), Signal Dispatcher, Reference Handler, Finalizer.

Встроенный (bootstrap) загрузчик загружает ядро java.base — из файла lib/modules (формат jimage) или из архива CDS (тема 20), что гораздо быстрее. Выполняются System.initPhase1 (свойства, потоки ввода-вывода), initPhase2 (система модулей: boot layer), initPhase3 (SecurityManager-наследие, системный загрузчик).

Создаются платформенный и прикладной (system / app) загрузчики. Прикладной знает classpath (или module path) — именно он загрузит ваш главный класс.

sun.launcher.LauncherHelper.checkAndLoadMain загружает главный класс, проверяет наличие main (с Java 21+ — и «экземплярного» main без static и аргументов), затем лаунчер через JNI вызывает его. Первое обращение к классу запускает его линковку и <clinit> (тема 06).

Когда main вернулся, поток вызывает DestroyJavaVM: ждёт завершения всех не-daemon потоков, затем выполняет shutdown hooks (Runtime.addShutdownHook) и завершает процесс. System.exit(n) запускает hooks сразу, не дожидаясь потоков; kill -9 — без hooks вообще.

java -Xlog:startuptime -Xlog:class+load:file=classes.txt -jar app.jar   # что и когда загружалось
java -Xshare:dump                                                       # (пере)создать CDS-архив JDK
java -verbose:class -version | head                                     # первые загружаемые классы
jcmd <pid> Thread.print | grep '"' | head -20                           # служебные потоки JVM

1.6Самопроверка

Что определяет спецификация JVM, а что оставляет реализации?

  • Определяет алгоритм GC и раскладку объектов
  • Определяет только синтаксис Java
  • Определяет формат class-файла, инструкции и загрузку классов; GC, JIT и раскладка объектов — на усмотрение реализации
  • Ничего не определяет, всё — HotSpot
Поэтому OpenJ9 и HotSpot исполняют одни и те же class-файлы по-разному внутри.

Программа запустила поток и main() завершился. Когда закончится процесс?

  • Когда завершатся все не-daemon потоки (затем shutdown hooks)
  • Сразу после main
  • Никогда
  • Через 30 секунд
DestroyJavaVM ждёт не-daemon потоки — частая причина «зависших» утилит.

Какой GC выберет JDK 21 в контейнере с 1 CPU и 1 ГБ памяти без флагов?

  • G1
  • Serial
  • ZGC
  • Parallel
Меньше 2 процессоров или 1792 МБ — машина «клиентского класса».

Как узнать фактическое значение MaxHeapSize у работающего процесса?

  • Посмотреть Dockerfile
  • Runtime.freeMemory()
  • По умолчанию всегда 1 ГБ
  • jcmd <pid> VM.flags или -XX:+PrintFlagsFinal
Эргономика могла выбрать не то, что вы ожидаете.
Расскажите, что происходит от команды java до первой строки main.

Лаунчер разбирает аргументы и манифест, загружает libjvm и вызывает JNI_CreateJavaVM: флаги и эргономика, резервирование кучи и metaspace, запуск служебных потоков (GC, JIT, VM Thread), загрузка базовых классов bootstrap-загрузчиком (часто из CDS-архива), инициализация System в три фазы и boot layer модулей, создание платформенного и прикладного загрузчиков. Затем LauncherHelper загружает главный класс, его линковка и инициализация, вызов main через JNI.

Какие служебные потоки есть в любой JVM и что они делают?

VM Thread — выполняет операции, требующие safepoint (некоторые фазы GC, деоптимизация, дампы потоков); потоки GC (рабочие и конкурентные); C1/C2 CompilerThread — JIT-компиляция; Reference Handler — ставит очищенные ссылки в очереди; Finalizer — вызывает finalize; Signal Dispatcher — обработка сигналов (например, SIGQUIT для дампа потоков); Common-Cleaner; Attach Listener — подключение jcmd/агентов; Notification Thread, Service Thread.
