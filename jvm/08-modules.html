Модули (JPMS) и слои

С Java 9 сама JDK разбита на ~70 модулей, а доступ определяется не только модификаторами public/private, но и тем, экспортирует ли модуль пакет. Даже если вы не пишете module-info.java, система модулей влияет на вас: InaccessibleObjectException при рефлексии, флаги --add-opens, jlink для маленьких образов. Разбираем, как JVM решает «можно ли обратиться», что такое безымянный и автоматические модули и как слои позволяют грузить две версии одной библиотеки.

8.1Дескриптор модуля

module com.shop.orders {
    requires com.shop.common;                    // читаемость: orders видит экспортированные пакеты common
    requires transitive com.shop.api;            // и всем, кто читает orders, — тоже api
    requires static lombok;                      // нужен при компиляции, необязателен в рантайме
    requires java.sql;

    exports com.shop.orders.api;                 // public-типы пакета доступны другим модулям
    exports com.shop.orders.spi to com.shop.app; // квалифицированный экспорт
    opens com.shop.orders.model to com.fasterxml.jackson.databind, org.hibernate.orm.core;  // глубокая рефлексия

    uses com.shop.orders.spi.DiscountPolicy;     // потребитель ServiceLoader
    provides com.shop.common.Plugin with com.shop.orders.OrdersPlugin;
}

exports

Открывает public-члены public-типов пакета для компиляции и рефлексии. Без экспорта public-класс снаружи модуля недоступен.

opens

Разрешает глубокую рефлексию (setAccessible(true) на private-полях) — нужно Jackson, Hibernate, Spring для внедрения в поля. open module открывает все пакеты.

8.3Classpath, безымянный и автоматические модули

ЧтоКак получаетсяСвойства
Именованный модульjar с module-info.class на --module-pathстрогая инкапсуляция, явные зависимости, проверка при старте (нет модуля → ошибка запуска, а не NoClassDefFoundError через час)
Автоматический модульобычный jar на module path; имя — из Automatic-Module-Name в манифесте или из имени файлаэкспортирует и открывает всё, читает всё — мост для библиотек без module-info
Безымянный модульвсё, что на classpath (у каждого загрузчика свой)читает все модули, экспортирует всё; но именованные модули его не читают. Так работает большинство приложений, включая Spring Boot fat jar
Split packages Один пакет не может находиться в двух модулях одного слоя: Package x.y in both module a and module b. На classpath это «работало» (побеждал первый jar), на module path — ошибка запуска. Частая боль при миграции старых библиотек (javax.annotation, jsr305).

8.4jdeps и jlink: свой маленький runtime

jdeps --ignore-missing-deps --print-module-deps --multi-release 21 -cp 'lib/*' app.jar
# java.base,java.logging,java.management,java.naming,java.net.http,java.sql,jdk.crypto.ec,jdk.unsupported

jlink --add-modules java.base,java.logging,java.management,java.naming,java.net.http,java.sql,jdk.crypto.ec,jdk.unsupported \
      --strip-debug --no-man-pages --no-header-files --compress=zip-6 --output /opt/jre
# полный JDK ~ 300+ МБ → runtime ~ 50–70 МБ

jdk.unsupported содержит sun.misc.Unsafe — его требуют Netty, старые версии многих библиотек; без него — NoClassDefFoundError: sun/misc/Unsafe.

8.5Слои модулей: две версии библиотеки

ModuleLayer — граф модулей, связанный со своими загрузчиками. Boot layer создаётся при запуске; приложение может создавать дочерние слои — например, по слою на плагин, в каждом свою версию библиотеки. Это «правильная» модульная замена child-first загрузчикам.

ModuleFinder finder = ModuleFinder.of(Path.of("plugins/acme"));
ModuleLayer parent = ModuleLayer.boot();
Configuration cf = parent.configuration().resolve(finder, ModuleFinder.of(), Set.of("com.acme.plugin"));
ModuleLayer layer = parent.defineModulesWithOneLoader(cf, ClassLoader.getSystemClassLoader());
ServiceLoader.load(layer, Plugin.class).forEach(Plugin::start);

Лаба 8.1Два модуля: exports, requires и что бывает без них25 мин

Собрать модули com.greet и com.app и проверить три уровня доступа: экспортированный пакет, неэкспортированный пакет и рефлексия.

  1. Создайте файл mods/com.greet/module-info.java:
    module com.greet {
    exports com.greet.api;
}
    package com.greet.api;

import com.greet.impl.Secret;

public class Greeter {
    public static String hello(String who) { return "Привет, " + who + Secret.suffix(); }
}
    package com.greet.impl;

public class Secret {
    public static String suffix() { return "!"; }
    private String token = "s3cr3t";
}
    module com.app {
    requires com.greet;
}
    package com.app;

import com.greet.api.Greeter;

public class Main {
    public static void main(String[] args) throws Exception {
        System.out.println(Greeter.hello("модули"));
        System.out.println("мой модуль: " + Main.class.getModule());
        Class<?> secret = Class.forName("com.greet.impl.Secret");
        var f = secret.getDeclaredField("token");
        f.setAccessible(true);
        System.out.println("token = " + f.get(secret.getDeclaredConstructor().newInstance()));
    }
}
  2. Компиляция всех модулей сразу и запуск по имени модуля:
    javac -d out --module-source-path mods --module com.greet,com.app
java --module-path out -m com.app/com.app.Main
    Вывод (JDK 25.0.2)

	at java.base/java.lang.reflect.AccessibleObject.throwInaccessibleObjectException(AccessibleObject.java:353)
	at java.base/java.lang.reflect.AccessibleObject.checkCanSetAccessible(AccessibleObject.java:329)
	at java.base/java.lang.reflect.AccessibleObject.checkCanSetAccessible(AccessibleObject.java:277)

    --module-source-path mods говорит javac, что каждый подкаталог mods — исходники модуля с тем же именем; --module перечисляет, какие модули собрать.

  3. Компиляция прошла, приветствие напечаталось. Что случится на setAccessible(true)?

    InaccessibleObjectException: Unable to make field private java.lang.String com.greet.impl.Secret.token accessible: module com.greet does not "opens com.greet.impl" to module com.app. Class.forName и getDeclaredField работают, а глубокая рефлексия в неоткрытый пакет запрещена. Исправление — в модуле-владельце: opens com.greet.impl to com.app; или запуск с --add-opens com.greet/com.greet.impl=com.app.

  4. Проверьте исправление флагом командной строки, не трогая код:

    IDEAVM options: --add-opens com.greet/com.greet.impl=com.app

    java --module-path out --add-opens com.greet/com.greet.impl=com.app -m com.app/com.app.Main
    Вывод (JDK 25.0.2)
    Привет, модули!
мой модуль: module com.app
token = s3cr3t
Поэкспериментируйте
  • Импортируйте в Main класс com.greet.impl.Secret и вызовите Secret.suffix() напрямую.
    Ошибка компиляции: «package com.greet.impl is not visible … (package com.greet.impl is declared in module com.greet, which does not export it)». Модули проверяют доступ и при компиляции, и в рантайме.
  • Уберите requires com.greet из com.app.
    «package com.greet.api is not visible»: без requires модуль не читает другой модуль, даже если тот экспортирует пакет.
Лаба 8.2Сильная инкапсуляция JDK10 мин

Попробовать залезть в приватное поле String и понять, откуда в реальных проектах берутся --add-opens java.base/….

  1. Создайте файл DeepReflection.java:
    public class DeepReflection {
    public static void main(String[] args) throws Exception {
        var f = String.class.getDeclaredField("value");
        System.out.println("поле найдено: " + f);
        f.setAccessible(true);
        byte[] v = (byte[]) f.get("hello");
        System.out.println("внутри строки " + v.length + " байт, coder = Latin-1");

    IDEAVM options: --add-opens java.base/java.lang=ALL-UNNAMED

    java --add-opens java.base/java.lang=ALL-UNNAMED DeepReflection.java

    --add-opens java.base/java.lang=ALL-UNNAMED (код из classpath живёт в безымянном модуле). С Java 17 (JEP 403) это единственный способ — раньше хватало предупреждения. Флаг открывает весь пакет всем библиотекам из classpath; правильнее обновить библиотеку, которая требует такого доступа.

8.7Самопроверка

Jackson не может заполнить private-поле класса из вашего модуля. Что нужно в module-info?

  • exports пакета
  • requires com.fasterxml.jackson.databind
  • opens пакета для jackson.databind (или для всех)
  • uses ObjectMapper
Глубокая рефлексия требует opens; exports даёт только доступ к public.

Почему на Java 17 библиотека получила InaccessibleObjectException при доступе к private-полю java.lang.String?

  • JDK строго инкапсулирует внутренности (JEP 403); нужен --add-opens java.base/java.lang=ALL-UNNAMED или обновление библиотеки
  • String стал final
  • Нужен requires java.base
  • Ошибка classpath
В Java 9–16 действовал --illegal-access=permit с предупреждением.

Как обычное приложение на classpath видится системой модулей?

  • Как автоматический модуль
  • Никак, модули на него не влияют
  • Как модуль java.base
  • Как безымянный модуль: читает все модули, но его не читают именованные
При этом инкапсуляция JDK действует и на classpath.
Стоит ли переводить Spring Boot-приложение на модули?

Обычно выгода невелика: Spring Boot fat jar работает на classpath, многие библиотеки не модуляризованы, требуются opens для рефлексии. Полезные части JPMS доступны и без этого: jlink для маленького runtime, jdeps для анализа зависимостей. Модули оправданы для библиотек (Automatic-Module-Name как минимум), для больших монолитов с требованием строгих границ (или используйте Spring Modulith / ArchUnit), для плагинных систем со слоями.

Что даёт JPMS по сравнению с classpath?

Надёжную конфигурацию — отсутствующие и дублирующиеся модули, split packages обнаруживаются при старте; строгую инкапсуляцию — внутренние пакеты недоступны даже через рефлексию без opens; явный граф зависимостей; возможность собрать минимальный runtime (jlink); быстрее поиск классов (пакет → модуль, без перебора jar).
