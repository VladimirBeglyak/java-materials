Области памяти JVM

«У сервиса -Xmx2g, а процесс занимает 3,2 ГБ и его убивает OOM killer» — классика. Куча — лишь одна из областей памяти JVM. Разбираем все: стеки потоков и кадры, кучу, metaspace, code cache, direct-буферы, структуры GC и JIT, — какие ошибки возникают в каждой, как увидеть реальное потребление через Native Memory Tracking и как посчитать память процесса до того, как это сделает Kubernetes.

9.2Стек потока

Что лежит в кадре и как стек операндов работает по инструкциям, разобрано в теме 03. У каждого платформенного потока свой стек — резервируется -Xss адресного пространства, физически занимается по мере роста. Каждый вызов метода добавляет кадр; в интерпретаторе кадр больше, в JIT-коде — меньше (и встроенные методы кадров не создают вовсе). Поэтому глубина рекурсии до StackOverflowError «плавает» между запусками.

Глубина рекурсии до StackOverflowError
Виртуальные потоки У виртуальных потоков (Java 21) нет фиксированного стека ОС: при блокировке их кадры копируются в кучу как объекты StackChunk и возвращаются на стек потока-носителя при продолжении. Поэтому миллион виртуальных потоков — это память кучи пропорционально реальной глубине их стеков (подробно — в пособии по конкурентности и теме 18).
Как ОС создаёт стек потока Резерв -Xss — это mmap(…, MAP_STACK), а «физически занимается по мере роста» — это ленивые page faults; защитные зоны HotSpot — недоступные страницы в конце стека. Подробно, с трассой системных вызовов Thread.start() — «Как устроен компьютер», тема 04; виртуальная память и RSS против VSZ — тема 08.

9.3Куча

Единственная область для объектов (если JIT не убрал выделение — тема 11). -Xms — начальный размер (committed), -Xmx — максимум (reserved). Устройство кучи зависит от сборщика: поколения в Serial/Parallel, регионы в G1 и ZGC (тема 13). Строки, статические поля классов (в зеркалах java.lang.Class) и интернированные строки — тоже в куче с Java 7/8.

Xms = Xmx в продакшене? Для серверов часто ставят одинаковыми (или InitialRAMPercentage = MaxRAMPercentage): нет пауз на расширение кучи, предсказуемое потребление, память контейнера всё равно выделена под JVM. Плюс -XX:+AlwaysPreTouch — обойти страницы при старте, чтобы ОС выделила их сразу (медленнее старт, ровнее задержки).

9.4Metaspace и code cache

Metaspace (с Java 8 вместо PermGen)

Нативная память под метаданные классов, выделяется блоками на загрузчик и освобождается при выгрузке загрузчика (тема 07). Типично 50–300 МБ для Spring-приложения (20–40 тыс. классов). Рост без остановки — утечка загрузчиков или безостановочная генерация классов (прокси, скрипты, лямбды через defineHiddenClass без выгрузки). Ставьте MaxMetaspaceSize, чтобы утечка была ошибкой JVM, а не OOM killer.

Code cache

Сегментирован (Java 9+): служебный код, профилированный код C1, оптимизированный код C2. Если переполнится — JIT отключается, новые горячие методы исполняются интерпретатором, а производительность падает в разы без явной ошибки. Мониторьте jcmd <pid> Compiler.codecache; для больших приложений увеличивайте ReservedCodeCacheSize.

9.7Практикум: пишем и запускаем

Каждую область памяти можно «переполнить» отдельно и получить свою ошибку, а Native Memory Tracking покажет, куда на самом деле уходит память процесса. Модуль IDEA — ch09. Флаги вида -Xss, -Xmx задавайте в VM options конфигурации запуска.

Лаба 9.1Глубина стека: от чего она зависит15 мин

Измерить, сколько кадров помещается в стек потока, и как на это влияют -Xss и размер кадра.

  1. Создайте файл Depth.java:
    public class Depth {
    static int depth;

    static void small() { depth++; small(); }

    static void big(long a, long b, long c, long d) {
        long e = a + b, f = c + d, g = e * f, h = g - a;
        depth++;
        big(e, f, g, h);
    }

    static int measure(Runnable r) {
        depth = 0;
        try { r.run(); } catch (StackOverflowError e) { /* ожидаемо */ }
        return depth;
    }

    public static void main(String[] args) {
        System.out.println("маленький кадр: " + measure(Depth::small));
        System.out.println("большой кадр:   " + measure(() -> big(1, 2, 3, 4)));
        System.out.println("маленький кадр: " + measure(Depth::small) + "  (повторно)");
    }
}
    javac Depth.java
java Depth
    Вывод (JDK 25.0.2)
    маленький кадр: 28459
большой кадр:   7695
маленький кадр: 62226  (повторно)
  2. Что будет с глубиной при -Xss256k и при -Xss4m? Почему повторный замер «маленького кадра» отличается от первого?

    IDEAVM options: -Xss256k, затем -Xss4m

    java -Xss256k Depth
java -Xss4m Depth
    Вывод (JDK 25.0.2)
    маленький кадр: 2956
большой кадр:   976
маленький кадр: 5278  (повторно)
маленький кадр: 101646
большой кадр:   39841
маленький кадр: 103568  (повторно)

    Глубина растёт со стеком, но не строго пропорционально: при 256k она упала примерно в 10 раз, при 4m выросла примерно в 3 раза относительно умолчания (1 МБ на 64-битных Windows и Linux). Часть стека занимают служебные защитные страницы и кадры самой JVM, а глубина ещё и зависит от того, какие кадры уже скомпилированы. Повторный замер больше, потому что метод к этому моменту скомпилирован JIT: у скомпилированного кадра нет «лишних» слотов интерпретатора, и кадры меньше. Именно поэтому глубина рекурсии в Java не детерминирована.

Поэкспериментируйте
  • Запустите рекурсию не в main, а в new Thread(null, r, "deep", 64 * 1024 * 1024).
    Четвёртый аргумент конструктора — размер стека именно этого потока (здесь 64 МБ). Так делают для глубоко рекурсивных алгоритмов, не меняя -Xss для всех потоков.
Лаба 9.2Четыре разных OutOfMemoryError25 мин

Переполнить по очереди кучу, metaspace, прямую память и узнать каждую ошибку по сообщению.

  1. Создайте файл Ooms.java:
    import java.lang.invoke.MethodHandles;
import java.nio.ByteBuffer;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.ArrayList;
import java.util.List;

public class Ooms {
    public static void main(String[] args) throws Exception {
        List<Object> keep = new ArrayList<>();
        switch (args[0]) {
            case "heap" -> { while (true) keep.add(new long[100_000]); }
            case "direct" -> { while (true) keep.add(ByteBuffer.allocateDirect(1024 * 1024)); }
            case "meta" -> {
                // каждый скрытый класс — новые метаданные в metaspace
                byte[] bytes = Files.readAllBytes(Path.of("Ooms$Tiny.class"));
                var lookup = MethodHandles.lookup();
                for (int i = 0; ; i++) {
                    keep.add(lookup.defineHiddenClass(bytes, false).lookupClass());
                    if (i % 10_000 == 0) System.out.println("скрытых классов: " + i);
                }
            }
            case "array" -> keep.add(new long[Integer.MAX_VALUE]);
            default -> System.out.println("heap | direct | meta | array");
        }
    }

    static class Tiny { int a; void m() {} }
}
  2. Компилируем и пробуем каждый вариант с маленьким лимитом соответствующей области (Program arguments: heap, direct…):

  3. А что выдаст Ooms array при -Xmx64m — и при -Xmx64g?
    java -Xmx64m Ooms array
    Вывод (JDK 25.0.2)
    Exception in thread "main" java.lang.OutOfMemoryError: Requested array size exceeds VM limit
	at Ooms.main(Ooms.java:23)

    При 64m — Java heap space: массив на 16 ГБ не влезет. При любом -Xmx — может появиться другой текст: Requested array size exceeds VM limit, потому что максимальная длина массива в HotSpot чуть меньше Integer.MAX_VALUE (заголовок тоже занимает место). Это одно из немногих OOM, которые не зависят от размера кучи.

Поэкспериментируйте
  • Добавьте -XX:+HeapDumpOnOutOfMemoryError к варианту heap. Что появится в каталоге и чем его открыть?
    Файл java_pid<N>.hprof размером около кучи. Открывается в IntelliJ IDEA (Ultimate — Profiler, вкладка с дампом), VisualVM или Eclipse MAT; там видно, что весь объём держит ArrayList keep (тема 14).
  • Почему на direct-варианте -Xmx не помогает, а помогает -XX:MaxDirectMemorySize?
    Прямые буферы живут вне кучи; в куче только маленькие объекты-обёртки DirectByteBuffer. По умолчанию лимит прямой памяти равен -Xmx.
Лаба 9.3Native Memory Tracking: куда ушла память процесса20 мин

Увидеть, из чего складывается память JVM помимо кучи: классы, потоки, код, GC, символы.

  1. Создайте файл Threads500.java:
    import java.util.concurrent.CountDownLatch;

public class Threads500 {
    public static void main(String[] args) throws Exception {
        int n = Integer.parseInt(args[0]);
        var stop = new CountDownLatch(1);
        for (int i = 0; i < n; i++) {
            Thread t = new Thread(() -> { try { stop.await(); } catch (InterruptedException ignored) {} });
            t.setDaemon(true);
            t.start();
        }
        System.out.println("pid " + ProcessHandle.current().pid() + ", потоков запущено: " + n);
        Thread.sleep(600_000);
    }
}

    IDEAVM options: -XX:NativeMemoryTracking=summary -Xmx256m, Program arguments: 10

    reserved вырастет примерно на 490 × 1 МБ (под каждый стек резервируется адресное пространство размером -Xss), а committed — на гораздо меньшую величину: физическая память выделяется только под реально использованные страницы стека. В контейнере лимит считается по RSS (≈ committed), поэтому тысячи «спящих» потоков обходятся дешевле, чем кажется по reserved, — но не бесплатно.

Поэкспериментируйте
  • Сделайте базовую точку и сравнение: jcmd <pid> VM.native_memory baseline, подождите, затем VM.native_memory summary.diff.
    diff показывает прирост по каждой категории с момента baseline — главный приём поиска нативной утечки (растёт Class — генерация классов, Thread — утечка потоков, Other/Internal — direct-буферы или JNI).
  • Сравните строку Total: committed с памятью процесса в диспетчере задач.
    Они близки, но не равны: NMT не видит память нативных библиотек, выделенную через malloc в обход JVM (например, в драйверах или в glibc-аренах на Linux).

9.8Самопроверка

Под с лимитом 2 ГБ и -Xmx2g регулярно перезапускается с кодом 137 без ошибок в логе. Почему?

  • Ошибка в коде приложения
  • Медленный GC
  • Процесс использует память и вне кучи (metaspace, стеки, code cache, GC, direct) и превышает лимит — его убивает OOM killer
  • Не хватает CPU
Куча должна составлять 60–75% лимита.

Где хранятся статические поля класса в HotSpot (Java 8+)?

  • В куче, в объекте java.lang.Class (зеркале класса)
  • В PermGen
  • В стеке main
  • В code cache
Метаданные — в metaspace, значения статических полей — в куче.

Что произойдёт при переполнении code cache?

  • OutOfMemoryError
  • JVM упадёт
  • Код будет компилироваться на диск
  • JIT отключится, новые горячие методы будут интерпретироваться — заметное замедление без явной ошибки
Ищите в логе «CodeCache is full».

Чем ограничен объём direct-буферов по умолчанию?

  • Ничем
  • MaxDirectMemorySize, по умолчанию равным максимальному размеру кучи
  • Размером metaspace
  • 1 ГБ
Освобождаются, когда GC соберёт объекты ByteBuffer — при большой куче и редких GC буферы копятся.
Как выбрать -Xmx для контейнера с лимитом 4 ГБ?

Оценить не-кучевую память: metaspace (по числу классов), code cache, потоки, GC-структуры (зависят от сборщика и размера кучи), direct-буферы (Netty, HTTP-клиенты), нативные библиотеки. Обычно это 0,6–1,5 ГБ. Начать с MaxRAMPercentage=70–75, включить NMT на стенде под нагрузкой, сравнить committed и RSS, оставить запас 5–10%. Мониторить RSS контейнера, а не только кучу.

Отличие StackOverflowError от OutOfMemoryError: unable to create native thread.

StackOverflowError — один поток исчерпал свой стек (обычно бесконечная или слишком глубокая рекурсия). «Unable to create native thread» — ОС отказала в создании нового потока: лимит процессов/потоков (ulimit -u, pids.max в контейнере), нехватка адресного пространства или памяти под стеки. Лечится не Xss, а сокращением числа потоков (пулы, виртуальные потоки) и лимитами.
