Байткод и стековая машина

JVM — стековая машина: у инструкций нет регистров, они берут операнды с вершины стека операндов текущего кадра и кладут туда результат. Локальные переменные — пронумерованные слоты. Пройдите по шагам настоящий байткод (вывод javap -c) в симуляторе интерпретатора и посмотрите, во что javac превращает циклы, тернарный оператор, switch, try/finally и автоупаковку.

3.1Кадр метода

При каждом вызове метода в стеке потока создаётся кадр (frame):

  • массив локальных переменных размера max_locals: слот 0 — this (у экземплярных методов), затем аргументы, затем локальные переменные; long и double занимают по два слота; слоты переиспользуются для переменных из непересекающихся блоков;
  • стек операндов глубиной не более max_stack — оба размера вычисляет javac и проверяет верификатор;
  • ссылка на пул констант времени выполнения класса и адрес возврата.

Типы закодированы в инструкциях: iadd складывает int, ladd — long, dadd — double. Поэтому байткод проверяем статически: верификатор знает тип каждого значения в каждой точке.

3.5Как интерпретирует HotSpot

HotSpot не разбирает байткод в цикле switch на C: при старте он генерирует шаблонный интерпретатор — для каждого опкода готовый кусок машинного кода, а переход между инструкциями — косвенный переход по таблице (dispatch). Значения вершины стека держатся в регистре процессора. Это в разы быстрее «наивного» интерпретатора, но всё равно в 10–50 раз медленнее JIT-кода, поэтому горячие методы компилируются (тема 16).

java -XX:+UnlockDiagnosticVMOptions -XX:+PrintInterpreter -version | head -50
java -Xint -jar app.jar        # только интерпретатор: почувствуйте разницу в скорости

Почему JVM выбрала стековую архитектуру, а не регистровую?

Компактный байткод (у инструкций нет операндов-регистров), независимость от числа регистров процессора, простая генерация кода компилятором и простая верификация. Производительность не страдает, потому что JIT всё равно переводит стековый байткод в регистровый машинный код с распределением регистров. Android Dalvik/ART выбрал регистровый формат ради интерпретации на слабых устройствах.

Как найти в байткоде скрытое создание объектов?

javap -c -p и поиск инструкций new, newarray, вызовов valueOf (автоупаковка), invokedynamic (лямбды и конкатенация создают объекты), varargs (создание массива). Но помните: JIT может убрать выделение памяти через escape analysis (тема 11) — измеряйте профилировщиком аллокаций, а не только читая байткод.
