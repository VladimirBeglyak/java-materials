Байткод и стековая машина

JVM — стековая машина: у инструкций нет регистров, они берут операнды с вершины стека операндов текущего кадра и кладут туда результат. Локальные переменные — пронумерованные слоты. Пройдите по шагам настоящий байткод (вывод javap -c) в симуляторе интерпретатора и посмотрите, во что javac превращает циклы, тернарный оператор, switch, try/finally и автоупаковку.

3.1Кадр метода и стек потока

Кадр метода (stack frame) — блок памяти, который JVM создаёт при каждом вызове метода и уничтожает, когда метод завершается. В нём лежит всё, что нужно одному конкретному вызову: два одновременных вызова одного метода (рекурсия или два потока) — это два независимых кадра.

Что внутри кадра

  • Массив локальных переменных размера max_locals — пронумерованные слоты: слот 0 — this (у экземплярных методов), затем аргументы, затем локальные переменные. long и double занимают по два слота; слоты переиспользуются для переменных из непересекающихся блоков. Это «долговременная» память вызова — живёт, пока метод выполняется.
  • Стек операндов глубиной не больше max_stack — «черновик» для текущего вычисления (разбор ниже).
  • Служебная информация: ссылка на пул констант времени выполнения класса (чтобы invokevirtual #7 знал, какой метод имеется в виду), адрес возврата в вызывающий метод, ссылка на предыдущий кадр.

Оба размера вычисляет javac и записывает в class-файл — в выводе javap -c это строка stack=2, locals=3. Поэтому кадр выделяется одним куском заранее известного размера: вызов метода в JVM дешёвый.

Стек операндов: зачем он и как работает

У JVM нет регистров, как у процессора, поэтому у инструкций нет операндов вида «сложи регистр 1 и регистр 2». Правило другое: инструкция берёт входные значения с вершины стека операндов и кладёт результат туда же. iadd ничего не указывает явно — она снимает два int и кладёт их сумму. Стек работает по принципу LIFO: последним положил — первым снимешь.

Как выглядит int c = a + b;, если a в слоте 1, b — в слоте 2, а c попадёт в слот 3:

ИнструкцияЧто делаетСтек операндов послеСлоты 1 / 2 / 3
iload_1значение слота 1 (a) → на стек[a]a / b / —
iload_2значение слота 2 (b) → на стек[a, b]a / b / —
iaddснять два int, сложить, положить сумму[a+b]a / b / —
istore_3снять вершину → в слот 3 (c)[]a / b / a+b

Видно разделение ролей: load переносит значение из локальной переменной на стек, арифметика работает только со стеком, store переносит со стека в локальную переменную. Так же устроены вызовы: аргументы сначала кладутся на стек операндов вызывающего, инструкция invoke… их снимает и передаёт в слоты нового кадра, а возвращённое значение появляется на стеке операндов вызывающего метода.

Типы закодированы в самих инструкциях: iadd складывает int, ladd — long, dadd — double. Поэтому байткод проверяем статически: верификатор знает тип каждого значения в каждом слоте и на каждой позиции стека в любой точке метода (неверный байткод вы сломаете своими руками в лабе 6.2).

Где хранится кадр: стек потока

Кадры живут в стеке потока — у каждого потока он свой. Кадры лежат друг на друге в порядке вызовов: вызов метода кладёт новый кадр на вершину, return снимает его, и выполнение продолжается в кадре ниже. В HotSpot стек Java-потока — это обычный нативный стек потока ОС; его размер задаёт -Xss (по умолчанию 1 МБ на 64-битных Windows и Linux, тема 09).

Стек вызовов по шагам: main → count → length
public class Main {
    public static void main(String[] args) {
        String t = "Привет";
        int n = Text.count(t);
        System.out.println(n);
    }
}
class Text {
    static int count(String s) {
        int len = s.length();
        return len * 2;
    }
}

Лаунчер вызывает main — в стеке потока создаётся первый кадр. Слот 0 — args (метод статический, this нет). ldc "Привет" + astore_1 кладут в слот 1 ссылку на строку из пула — сам объект лежит в куче.

aload_1 кладёт ссылку t на стек операндов main, invokestatic Text.count снимает её и создаёт новый кадр сверху. Аргумент оказывается в слоте 0 кадра count под именем s. Скопирована ссылка, а не строка: t и s указывают на один объект (передача «по значению ссылки»).

aload_0 + invokevirtual String.length — ещё один кадр. Для экземплярного метода объект-получатель передаётся неявно и попадает в слот 0 как this. Сейчас в стеке три кадра — ровно столько строк at … вы увидели бы в стектрейсе, если бы здесь произошла ошибка.

ireturn снимает 6 со стека операндов length, кадр уничтожается целиком, а значение кладётся на стек операндов вызывающего — count. istore_1 сохраняет его в слот len. Всё, что было в кадре length, исчезло — поэтому локальные переменные не нужно «освобождать».

iload_1, iconst_2 → стек [6, 2]; imul → [12]; ireturn снимает кадр count и передаёт 12 в main.

istore_2 — n = 12, затем println (ещё несколько кадров появятся и исчезнут) и return: кадр main снят, стек потока пуст, поток завершается.

Пусть t = null. В count invokevirtual length бросает NullPointerException. JVM ищет обработчик в таблице исключений текущего метода; не нашла — снимает кадр и ищет в вызывающем, и так далее (раскрутка стека). Стектрейс исключения — это снимок кадров, сделанный в момент создания объекта исключения: at Text.count(Main.java:10), at Main.main(Main.java:4).

Что из этого следует на практике

  • Стектрейс — распечатка кадров. Каждая строка at Класс.метод(Файл.java:строка) — один кадр, сверху — тот, где произошла ошибка. Номер строки JVM восстанавливает по смещению инструкции через атрибут LineNumberTable (лаба 2.4).
  • Локальные переменные потокобезопасны сами по себе: кадр принадлежит одному потоку, и до его слотов не дотянется никто другой. Но если в переменной ссылка, объект лежит в куче — и его могут менять другие потоки. «Локальная переменная» ≠ «локальный объект».
  • StackOverflowError — кадры не поместились в стек потока, чаще всего из-за бесконечной рекурсии. Глубина зависит от -Xss и от размера кадра: больше локальных переменных — меньше глубина, а у скомпилированного JIT метода кадр меньше (лаба 9.1).
  • Кадры — корни сборки мусора. Пока ссылка лежит в слоте активного кадра (и ещё понадобится), объект жив (тема 12, лаба 12.1).
  • Передача параметров — всегда по значению. В слоты нового кадра копируются значения: для примитивов — само число, для объектов — ссылка. Поэтому метод может изменить объект, но не может переназначить переменную вызывающего.
  • После JIT кадры выглядят иначе. Скомпилированный код держит значения в регистрах процессора, а встроенные (inlined) методы вообще не получают своего кадра. Если оптимистичное предположение JIT нарушится, JVM при деоптимизации восстанавливает из этого состояния «интерпретаторские» кадры (темы 16–17).
  • Виртуальные потоки не держат фиксированный стек ОС: при блокировке их кадры копируются из стека потока-носителя в кучу (объект StackChunk) и возвращаются при продолжении. Поэтому миллион «спящих» виртуальных потоков не требует миллиона стеков по 1 МБ (тема 18).

Почему JVM — стековая машина

Компактный байткод (у большинства инструкций нет операндов — один байт), независимость от числа регистров конкретного процессора, простая генерация кода компилятором и простая верификация. На скорость это не влияет: горячий код JIT всё равно переводит в регистровый машинный код, и стек операндов в нём фактически исчезает.

Как увидеть самому
  • Отладчик IntelliJ IDEA: брейкпоинт → окно Debug, панель Frames — стек кадров потока, панель Variables — слоты выбранного кадра. Щёлкая по кадрам, вы «ходите» по стеку вверх и вниз; «Drop Frame» (Reset Frame) снимает верхний кадр и перезапускает метод.
  • javap -c -l -p — stack=…, locals=… и LocalVariableTable с номерами слотов (лаба 3.2).
  • StackWalker и jcmd <pid> Thread.print — кадры из самой программы и снаружи (лаба 3.1, темы 1 и 18).

3.5Как интерпретирует HotSpot

HotSpot не разбирает байткод в цикле switch на C: при старте он генерирует шаблонный интерпретатор — для каждого опкода готовый кусок машинного кода, а переход между инструкциями — косвенный переход по таблице (dispatch). Значения вершины стека держатся в регистре процессора. Это в разы быстрее «наивного» интерпретатора, но всё равно в 10–50 раз медленнее JIT-кода, поэтому горячие методы компилируются (тема 16).

java -XX:+UnlockDiagnosticVMOptions -XX:+PrintInterpreter -version | head -50
java -Xint -jar app.jar        # только интерпретатор: почувствуйте разницу в скорости

Лаба 3.1Кадры своими глазами: StackWalker и отладчик20 мин

Увидеть, что каждый вызов — отдельный кадр со своими слотами, а у каждого потока — свой стек кадров.

  1. Создайте файл Frames.java:
    public class Frames {
    static void show(String where) {
        System.out.println("— " + where + ":");
        StackWalker.getInstance().forEach(f -> System.out.printf("    %s.%s  строка %d, bci %d%n",
                f.getClassName(), f.getMethodName(), f.getLineNumber(), f.getByteCodeIndex()));
    }

    static int fact(int n) {
        if (n == 1) {
            show("fact(1) — дно рекурсии");
            return 1;
        }
        return n * fact(n - 1);
    }

    public static void main(String[] args) throws InterruptedException {
        show("main");
        System.out.println("fact(4) = " + fact(4));
        Thread worker = new Thread(() -> show("поток worker"), "worker");
        worker.start();
        worker.join();
    }
}

    public class Loops {
    static int sum(int n) {
        int s = 0;
        for (int i = 1; i <= n; i++) s += i;
        return s;
    }

    static long fact(int n) {
        long r = 1;
        while (n > 1) r *= n--;
        return r;
    }

    int field;

    int addToField(int a, long b, int c) {
        field += a;
        return (int) (b + c);
    }

    public static void main(String[] args) {
        System.out.println(sum(4) + " " + fact(5) + " " + new Loops().addToField(1, 2L, 3));

3.7Самопроверка

Где хранится кадр метода в HotSpot?

  • В куче, рядом с объектом this
  • В стеке того потока, который вызвал метод
  • В metaspace вместе с байткодом метода
  • В code cache
У каждого потока свой стек (размер -Xss); вызов кладёт кадр на его вершину, return снимает. Объекты, на которые ссылаются слоты, — в куче.

Метод static int f(int x) { return x + 1; } рекурсивно вызывает сам себя из 3 потоков, в каждом на глубину 10. Сколько одновременно существует кадров f и сколько копий слота x?

  • 1 кадр, 1 слот — метод один
  • 3 кадра — по одному на поток
  • 10 кадров, общий слот x
  • 30 кадров и 30 независимых слотов x
Кадр создаётся на каждый вызов: 3 потока × 10 уровней. Поэтому рекурсия и многопоточность не мешают локальным переменным друг друга.

Что лежит в слоте 0 локальных переменных экземплярного метода?

  • Первый аргумент
  • Возвращаемое значение
  • this
  • Адрес возврата
У статических методов слот 0 — первый аргумент.

Почему после new почти всегда идёт dup?

  • Одна ссылка уходит в вызов конструктора, вторая остаётся для дальнейшего использования
  • Чтобы удвоить память
  • Для синхронизации
  • Это ошибка javac
invokespecial <init> потребляет ссылку со стека.

Чему равен x после int x = 5; x = x++;?

  • 6
  • Ошибка компиляции
  • Не определено
  • 5
iload (5) → iinc (слот 6) → istore (5).

Сколько слотов займут аргументы static void m(long a, int b, double c)?

  • 3
  • 5
  • 4
  • 6
long 2 + int 1 + double 2.
Почему JVM выбрала стековую архитектуру, а не регистровую?

Компактный байткод (у инструкций нет операндов-регистров), независимость от числа регистров процессора, простая генерация кода компилятором и простая верификация. Производительность не страдает, потому что JIT всё равно переводит стековый байткод в регистровый машинный код с распределением регистров. Android Dalvik/ART выбрал регистровый формат ради интерпретации на слабых устройствах.

Как найти в байткоде скрытое создание объектов?

javap -c -p и поиск инструкций new, newarray, вызовов valueOf (автоупаковка), invokedynamic (лямбды и конкатенация создают объекты), varargs (создание массива). Но помните: JIT может убрать выделение памяти через escape analysis (тема 11) — измеряйте профилировщиком аллокаций, а не только читая байткод.
