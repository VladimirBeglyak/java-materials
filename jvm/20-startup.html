Быстрый старт: CDS, AOT cache, CRaC, native image

Spring Boot-сервис стартует за 5–10 секунд и ещё минуту прогревается — для автоскейлинга, serverless и CLI это много. Куда уходит время старта, и как его сократить на разных уровнях: общий архив классов (CDS), AOT-кэш проекта Leyden (Java 24–25), снимок прогретого процесса (CRaC) и полная компиляция в исполняемый файл (GraalVM Native Image) — с их ценой и ограничениями.

20.2CDS: общий архив классов

Class Data Sharing сохраняет уже разобранные и проверенные метаданные классов в файл, который отображается в память при старте (mmap) — классы не надо читать из jar, разбирать и верифицировать. Архив JDK включён по умолчанию с Java 12 (lib/server/classes.jsa); AppCDS добавляет классы приложения. Бонус: несколько JVM на одной машине разделяют одни и те же страницы архива.

java -Djarmode=tools -jar app.jar extract --destination app      # распаковать (Spring Boot 3.3+)
java -XX:ArchiveClassesAtExit=app.jsa -Dspring.context.exit=onRefresh -jar app/app.jar   # тренировочный запуск
java -XX:SharedArchiveFile=app.jsa -jar app/app.jar             # старт быстрее на 30–40%
# classpath при использовании архива должен совпадать с тем, на котором его создавали

AOT cacheapp.aot

Приложение запускается в режиме записи и проходит типичные сценарии: старт контекста, несколько характерных запросов. JVM наблюдает, какие классы загружены и связаны, какие indy-вызовы разрешены, какие методы горячие и какой у них профиль.

JVM сохраняет AOT-кэш: классы уже в загруженном и слинкованном состоянии (JEP 483, Java 24), разрешённые лямбды и константы, а в Java 25 — профили методов (JEP 515), чтобы JIT сразу компилировал горячий код по готовому профилю. С JEP 514 запись и создание — одним флагом -XX:AOTCacheOutput.

При запуске с кэшем классы сразу доступны в связанном виде, JIT стартует с профилями — по данным JEP старт Spring PetClinic ускоряется примерно на 40%, а прогрев сокращается. Ограничения: тот же JDK, ОС и архитектура, совместимый classpath; приложение остаётся обычной JVM с динамической загрузкой и JIT — никаких ограничений native image.

20.4CRaC: снимок прогретого процесса

Coordinated Restore at Checkpoint (OpenJDK-проект; сборки Azul Zulu, BellSoft Liberica, поддержка в Spring Boot 3.2+ и AWS Lambda SnapStart по схожей идее) сохраняет образ работающего процесса — кучу, скомпилированный код, состояние потоков — на диск и восстанавливает его за десятки миллисекунд уже прогретым.

  • Перед снимком приложение должно закрыть то, что нельзя сохранить: соединения с БД, сокеты, открытые файлы — через ресурсы org.crac.Resource (beforeCheckpoint/afterRestore); Spring делает это для своего жизненного цикла.
  • Снимок содержит память процесса — секреты (пароли, ключи, токены) попадут в файл. Получайте их после восстановления.
  • Случайность и время: генераторы, инициализированные до снимка, восстановятся с тем же состоянием во всех экземплярах — пересоздавайте после restore.
  • Требуется Linux и CRIU (или его встроенная альтернатива), права на checkpoint в контейнере.

20.5GraalVM Native Image

Компиляция приложения заранее в исполняемый файл: статический анализ достижимости от main («закрытый мир»), компиляция всего достижимого кода, выполнение части инициализации классов при сборке, снимок кучи в образ. Результат — старт за десятки миллисекунд, меньше памяти, никакого прогрева. Цена:

Ограничения

  • Рефлексия, ресурсы, прокси, сериализация, JNI — только объявленные в метаданных (reflect-config, reachability metadata repository, Spring AOT генерирует сам).
  • Нет динамической загрузки классов в рантайме, агентов и большей части JVMTI.
  • Сборка — минуты и гигабайты памяти.

Производительность

  • Пиковая пропускная способность без PGO обычно ниже, чем у C2 (нет спекулятивных оптимизаций по живому профилю); PGO в Oracle GraalVM сокращает разрыв.
  • GC: Serial (по умолчанию) или G1 (Oracle GraalVM, Linux) — меньше выбора.
  • Отладка и профилирование — нативными инструментами.
./mvnw -Pnative native:compile            # GraalVM в окружении
./mvnw spring-boot:build-image -Pnative    # образ через Paketo buildpacks
# тесты в native-режиме: ./mvnw -PnativeTest test

20.7Практикум: пишем и запускаем

Измерим время старта небольшого приложения и ускорим его тремя способами, встроенными в JDK 25: стандартным CDS, архивом своих классов (AppCDS) и AOT-кэшем проекта Leyden. AOT-кэш работает только с classpath из jar-файлов, поэтому приложение сначала соберём в jar. Модуль IDEA — ch20.

Код набирайте руками — так он запоминается. Перед запуском запишите предсказание в поле «Ваш прогноз», затем сверьтесь с реальным выводом (снят на JDK 25.0.2; адреса, времена и хэши у вас будут другими). Как подготовить окружение — на странице курса.

Лаба 20.1Приложение, которому есть что грузить15 мин

Собрать jar, который на старте загружает около тысячи классов (HTTP-клиент, XML, регулярные выражения, стримы), и измерить время до конца main.

  1. Создайте файл app-src/StartApp.java:
    import java.io.StringReader;
import java.lang.management.ManagementFactory;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.util.regex.Pattern;
import java.util.stream.Collectors;
import java.util.stream.IntStream;
import javax.xml.parsers.DocumentBuilderFactory;
import org.xml.sax.InputSource;

public class StartApp {
    public static void main(String[] args) throws Exception {
        var client = HttpClient.newHttpClient();
        var req = HttpRequest.newBuilder(URI.create("http://localhost/health")).build();
        var doc = DocumentBuilderFactory.newInstance().newDocumentBuilder()
                .parse(new InputSource(new StringReader("<cfg><port>8080</port></cfg>")));
        String port = doc.getElementsByTagName("port").item(0).getTextContent();
        var words = Pattern.compile("\\s+").splitAsStream("быстрый старт JVM на JDK 25").collect(Collectors.toList());
        int sum = IntStream.rangeClosed(1, 100).filter(i -> i % 3 == 0).sum();

        long uptime = ManagementFactory.getRuntimeMXBean().getUptime();
        int classes = ManagementFactory.getClassLoadingMXBean().getLoadedClassCount();
        System.out.printf("готов: port=%s, слов=%d, sum=%d, метод=%s | %d мс, классов %d%n",
                port, words.size(), sum, req.method(), uptime, classes);
    }
}

jar --create --file app.jar --main-class StartApp -C app-out .
java -jar app.jar

java -jar app.jar

  2. Почему AOT-кэш быстрее AppCDS, хотя и тот и другой — «архив классов»?

    AppCDS сохраняет разобранные классы, но их всё равно нужно загрузить, связать и инициализировать при каждом старте. AOT-кэш сохраняет состояние после обучающего запуска: классы уже загружены и слинкованы, разрешены вызовы invokedynamic (лямбды, конкатенация), есть профили для JIT. Цена — обучающий прогон и требование одинаковых JDK, флагов и classpath.

    Кэш может быть отклонён (в журнале -Xlog:aot будет причина): часть содержимого зависит от конфигурации JVM. Флаги рабочего запуска должны совпадать с обучающим.

20.8Самопроверка

Что сохраняет CDS-архив?

  • Скомпилированный машинный код приложения
  • Снимок кучи процесса
  • Разобранные и проверенные метаданные классов, отображаемые в память при старте
  • Логи старта
Классы не нужно читать из jar, разбирать и верифицировать.

Чем опасен CRaC-снимок с точки зрения безопасности?

  • В нём сохранена вся память процесса, включая загруженные секреты
  • Он отключает TLS
  • Он требует root в продакшене
  • Он раскрывает исходный код
Секреты получайте после restore.

Почему native image может уступать JIT по пиковой производительности?

  • Он не использует оптимизации вообще
  • Он интерпретирует байткод
  • В нём нет сборщика мусора
  • AOT-компиляция не видит живого профиля и не может делать спекулятивные оптимизации с деоптимизацией (PGO частично компенсирует)
Зато нет прогрева и меньше памяти.
Как бы вы сократили время старта Spring Boot-сервиса с 9 до 2 секунд?

Измерить фазы (startup actuator, -Xlog:startuptime). Убрать лишние зависимости и автоконфигурации, ленивую инициализацию для редко используемых бинов, избегать тяжёлой работы при старте (прогрев кэшей — асинхронно). Распакованный jar + AppCDS или AOT cache (Java 24/25) — 30–50%. Достаточно CPU на старте (лимиты пода). Если нужно ещё быстрее — CRaC или native image с учётом их ограничений.

Что значит «закрытый мир» в GraalVM Native Image?

При сборке должно быть известно всё, что может выполняться: анализ достижимости от точки входа определяет классы и методы, попадающие в образ; всё динамическое (рефлексия, ресурсы, прокси, загрузка классов по имени) должно быть описано в метаданных. В рантайме новые классы не появляются. Это позволяет компилировать заранее и выбрасывать неиспользуемый код, но ломает фреймворки, полагающиеся на динамику без метаданных.
