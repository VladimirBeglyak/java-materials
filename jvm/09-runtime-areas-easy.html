Области памяти JVM — простыми словами

«Почему процесс Java занимает 3 ГБ, если -Xmx=2g?» — частый вопрос. Разберёмся с картой памяти JVM: стеки, куча, Metaspace, code cache, служебные области, — и научимся считать реальный расход и находить, куда он уходит.

9.1Карта памяти процесса

Куча

Все объекты. Ограничена -Xmx. Убирается сборщиком мусора.

Стеки потоков

Вызовы и локальные переменные. Свой у каждого потока (обычно до 1 МБ).

Metaspace

Описания загруженных классов.

Code cache

Машинный код, скомпилированный JIT.

Служебное

Структуры сборщика, внутренние таблицы, память самой JVM.

Direct-буферы

Память вне кучи для ввода-вывода (NIO, Netty).

Главная мысль Куча — только часть. Есть ещё стеки, классы, код, служебное и direct-буферы.

9.2Стек потока

Каждый поток получает свой стек: кадры вызовов с локальными переменными. Размер задаётся -Xss (обычно 1 МБ, но реально занимается только используемая часть). Слишком глубокая рекурсия — StackOverflowError. Много потоков — много стеков: тысяча потоков — до гигабайта зарезервированной памяти.

Главная мысль Стек — у каждого потока свой. Больше потоков — больше памяти.

В полной главе: 9.2 Стек потока

9.3Куча

Все объекты живут в куче — общей для всех потоков. Её нижняя и верхняя границы — -Xms и -Xmx. В сервисах часто ставят их равными, чтобы JVM не тратила время на рост и сжатие кучи. Внутри куча поделена так, как удобно сборщику (поколения, регионы — главы 12–13).

Главная мысль Куча — объекты, -Xmx — её предел.

В полной главе: 9.3 Куча

9.4Metaspace и code cache

Metaspace хранит описания классов (раньше это называлось PermGen). Растёт с числом загруженных классов — в больших Spring-приложениях это сотни мегабайт; утечки загрузчиков (глава 07) переполняют именно его. Code cache — место для машинного кода от JIT. Если оно заполнится, JIT перестанет компилировать, и программа заметно замедлится.

Главная мысль Metaspace — классы, code cache — скомпилированный код. Оба вне кучи.

9.5Сколько займёт процесс

Почему -Xmx2g, а процесс 2,8 ГБ
куча: до 2048 МБ+ Metaspace: ~200 МБ (Spring, сотни библиотек)+ стеки 300 потоков: ~150–300 МБ
+ code cache: ~100 МБ+ структуры GC, direct-буферы, служебное: ~200 МБ
итого ≈ 2,7–2,9 ГБ → лимит контейнера в 2 ГБ гарантирует убийство

Самая большая, но не единственная.

Растут с числом библиотек.

Зависят от числа потоков и объёма горячего кода.

Кучу делают заметно меньше лимита контейнера.

Главная мысль Реальный расход = куча + 20–40% сверху. В контейнере куча — примерно 60–75% лимита.

В полной главе: 9.5 Сколько памяти займёт процесс

9.6Native Memory Tracking

Чтобы узнать, куда ушла память вне кучи, есть NMT: включается флагом -XX:NativeMemoryTracking=summary, а потом jcmd PID VM.native_memory показывает раскладку по областям — классы, потоки, код, GC и прочее. Сравнивая снимки во времени, видно, что растёт.

Главная мысль NMT показывает, куда уходит память вне кучи.

9.8Проверьте себя

Почему процесс с -Xmx2g занимает около 3 ГБ?

  • ошибка JVM
  • кроме кучи есть Metaspace, стеки, code cache и служебная память
  • Linux удваивает память
  • так и должно быть только на Windows
Куча — лишь часть.

Где хранятся описания загруженных классов?

  • в куче
  • в стеке
  • в code cache
  • в Metaspace
Раньше это был PermGen.

Что будет, если заполнится code cache?

  • JIT перестанет компилировать, программа замедлится
  • программа упадёт сразу
  • очистится куча
  • ничего
Горячий код останется в интерпретаторе.

Лимит контейнера 4 ГБ. Какая куча разумна?

  • 4 ГБ
  • 5 ГБ
  • примерно 2,5–3 ГБ
  • 500 МБ всегда
Нужен запас на всё, что вне кучи.

Как узнать, сколько памяти вне кучи занимают потоки и классы?

  • посмотреть -Xmx
  • включить Native Memory Tracking и вызвать jcmd VM.native_memory
  • дамп кучи
  • никак
Дамп кучи показывает только кучу.
