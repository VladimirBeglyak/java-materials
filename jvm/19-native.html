Нативный код: JNI и Foreign Function API

JVM постоянно вызывает нативный код — сама стандартная библиотека полна native-методов, а Netty, RocksDB, драйверы GPU, сжатие и криптография работают через нативные библиотеки. Разбираем классический JNI (как устроен переход Java ↔ C, локальные и глобальные ссылки, почему это опасно), новый Foreign Function & Memory API (финальный в Java 22) с арендами памяти и jextract, и судьбу sun.misc.Unsafe.

19.1JNI: как это устроено

public class Native {
    static { System.loadLibrary("fastzip"); }   // libfastzip.so из java.library.path
    public static native int compress(byte[] in, byte[] out);
}
// javac -h include/ Native.java → генерирует Native.h
JNIEXPORT jint JNICALL Java_Native_compress(JNIEnv *env, jclass cls,
                                            jbyteArray in, jbyteArray out) {
    jsize n = (*env)->GetArrayLength(env, in);
    jbyte *src = (*env)->GetByteArrayElements(env, in, NULL);   // копия или пиннинг
    jbyte *dst = (*env)->GetByteArrayElements(env, out, NULL);
    int r = do_compress(src, n, dst);
    (*env)->ReleaseByteArrayElements(env, in, src, JNI_ABORT);
    (*env)->ReleaseByteArrayElements(env, out, dst, 0);         // 0 = скопировать обратно
    return r;
}
  • Переход Java → native: поток меняет состояние на _thread_in_native (теперь он «безопасен» для safepoint), аргументы-объекты передаются как хэндлы (косвенные ссылки), а не адреса — GC может двигать объекты. Возврат: проверка safepoint и отложенных исключений. Стоимость перехода — десятки наносекунд: JNI невыгоден для мелких частых вызовов.
  • Локальные ссылки живут до возврата из нативного метода (по умолчанию не больше 16 гарантированно — EnsureLocalCapacity); глобальные (NewGlobalRef) — до явного удаления: забыли DeleteGlobalRef — утечка, невидимая для GC.
  • Массивы: GetByteArrayElements может копировать; GetPrimitiveArrayCritical даёт прямой доступ, но блокирует перемещение объекта (GC-locker в старых сборщиках, пиннинг регионов в G1 с JDK 22) — держите критическую секцию минимальной.
  • Ошибка в C — это не исключение, а падение всей JVM (hs_err_pid.log, SIGSEGV). -Xcheck:jni ловит часть ошибок использования API.

19.2Foreign Function & Memory API (Java 22+)

Linker linker = Linker.nativeLinker();
MethodHandle strlen = linker.downcallHandle(
    linker.defaultLookup().find("strlen").orElseThrow(),
    FunctionDescriptor.of(ValueLayout.JAVA_LONG, ValueLayout.ADDRESS));   // size_t strlen(const char*)

try (Arena arena = Arena.ofConfined()) {
    MemorySegment cString = arena.allocateFrom("Привет, JVM");           // UTF-8 + '\0' вне кучи
    long len = (long) strlen.invokeExact(cString);                       // 17: «Привет» — 12 байт в UTF-8 + «, JVM» — 5
}   // память освобождена здесь, детерминированно
StructLayout POINT = MemoryLayout.structLayout(
    ValueLayout.JAVA_INT.withName("x"), ValueLayout.JAVA_INT.withName("y"));
VarHandle X = POINT.varHandle(MemoryLayout.PathElement.groupElement("x"));
try (Arena arena = Arena.ofConfined()) {
    MemorySegment pts = arena.allocate(POINT, 1_000_000);                // массив структур 8 МБ вне кучи
    X.set(pts, POINT.byteSize() * 42, 7);   // pts[42].x = 7; координаты VarHandle: (сегмент, базовое смещение)
}

19.4Практикум: пишем и запускаем

Foreign Function & Memory API (финальный с Java 22) позволяет вызвать функцию из C-библиотеки и работать с памятью вне кучи без единой строки на C — идеально для экспериментов. JNI требует компилятора C, поэтому его здесь только читаем. Модуль IDEA — ch19. Флаг --enable-native-access=ALL-UNNAMED убирает предупреждение о «restricted»-методах.

Код набирайте руками — так он запоминается. Перед запуском запишите предсказание в поле «Ваш прогноз», затем сверьтесь с реальным выводом (снят на JDK 25.0.2; адреса, времена и хэши у вас будут другими). Как подготовить окружение — на странице курса.

Лаба 19.1Вызываем strlen из стандартной библиотеки C20 мин

Найти нативную функцию, описать её сигнатуру и вызвать через downcall handle.

  1. Создайте файл Strlen.java:
    import java.lang.foreign.*;
import java.lang.invoke.MethodHandle;

import static java.lang.foreign.ValueLayout.ADDRESS;
import static java.lang.foreign.ValueLayout.JAVA_LONG;

public class Strlen {
    public static void main(String[] args) throws Throwable {
        Linker linker = Linker.nativeLinker();
        MemorySegment fn = linker.defaultLookup().find("strlen").orElseThrow();
        // size_t strlen(const char *s)
        MethodHandle strlen = linker.downcallHandle(fn, FunctionDescriptor.of(JAVA_LONG, ADDRESS));

        try (Arena arena = Arena.ofConfined()) {
            MemorySegment cStr = arena.allocateFrom("Привет, FFM!");     // UTF-8 + завершающий ноль
            long len = (long) strlen.invokeExact(cStr);
            System.out.println("strlen = " + len + ", Java length() = " + "Привет, FFM!".length());
            System.out.println("размер сегмента: " + cStr.byteSize());
        }
    }
}
  2. Совпадут ли strlen и length()?

    IDEAVM options: --enable-native-access=ALL-UNNAMED

    javac Strlen.java
java --enable-native-access=ALL-UNNAMED Strlen
    Вывод (JDK 25.0.2)
    strlen = 18, Java length() = 12
размер сегмента: 19

    Нет: strlen считает байты до нуля в UTF-8 (кириллица — 2 байта на букву: 6×2 + 6 = 18), а length() — UTF-16 символы (12). Сегмент на 1 байт больше — завершающий ноль. Ровно такие ошибки «длина в символах против длины в байтах» и ловят на границе Java и C.

Поэкспериментируйте
  • Уберите --enable-native-access.
    Программа работает, но печатает WARNING о вызове restricted-метода downcallHandle: в будущих версиях без флага это станет ошибкой. Опасные операции FFM требуют явного разрешения.
Лаба 19.2Память вне кучи: границы, время жизни, структуры20 мин

Убедиться, что FFM, в отличие от Unsafe, проверяет границы и время жизни памяти.

  1. Создайте файл OffHeap.java:
    import java.lang.foreign.*;

import static java.lang.foreign.ValueLayout.JAVA_INT;

public class OffHeap {
    public static void main(String[] args) {
        MemorySegment leaked;
        try (Arena arena = Arena.ofConfined()) {
            MemorySegment ints = arena.allocate(JAVA_INT, 10);         // int[10] вне кучи
            for (int i = 0; i < 10; i++) ints.setAtIndex(JAVA_INT, i, i * i);
            System.out.println("ints[9] = " + ints.getAtIndex(JAVA_INT, 9));
            try {
                ints.setAtIndex(JAVA_INT, 10, 1);                       // за границей
            } catch (IndexOutOfBoundsException e) {
                System.out.println("граница: " + e.getMessage());
            }
            leaked = ints;
        }
        try {
            leaked.getAtIndex(JAVA_INT, 0);                             // после закрытия арены
        } catch (IllegalStateException e) {
            System.out.println("после close: " + e.getMessage());
        }

        // структура struct Point { int x; int y; }
        StructLayout POINT = MemoryLayout.structLayout(JAVA_INT.withName("x"), JAVA_INT.withName("y"));
        var X = POINT.varHandle(MemoryLayout.PathElement.groupElement("x"));
        var Y = POINT.varHandle(MemoryLayout.PathElement.groupElement("y"));
        try (Arena arena = Arena.ofConfined()) {
            MemorySegment p = arena.allocate(POINT);
            X.set(p, 0L, 3); Y.set(p, 0L, 4);
            System.out.println("Point размером " + POINT.byteSize() + " байт: x=" + X.get(p, 0L) + ", y=" + Y.get(p, 0L));
        }
    }
}
  2. Что напечатают две «ошибочные» операции — за границей сегмента и после закрытия арены?
    javac OffHeap.java
java OffHeap
    Вывод (JDK 25.0.2)
    ints[9] = 81
граница: Out of bound access on segment MemorySegment{ kind: native, address: 0x2e13ef00f50, byteSize: 40 }; new offset = 40; new length = 4
после close: Already closed
Point размером 8 байт: x=3, y=4

    Оба доступа безопасно отклоняются исключениями: IndexOutOfBoundsException (out of bounds) и IllegalStateException: Already closed. С sun.misc.Unsafe первая операция испортила бы чужую память, а вторая читала бы освобождённую — с возможным крахом JVM. Проверки почти бесплатны: JIT убирает их там, где может доказать корректность.

Поэкспериментируйте
  • Прочитайте сегмент из confined-арены в другом потоке (new Thread(() -> ints.getAtIndex(JAVA_INT, 0)).start() внутри try).
    WrongThreadException: confined-арена принадлежит одному потоку. Для общего доступа — Arena.ofShared(), для «пусть соберёт GC» — Arena.ofAuto().

19.5Самопроверка

Почему JNI передаёт объекты в C как хэндлы, а не как прямые адреса?

  • Для экономии памяти
  • GC может перемещать объекты; хэндлы остаются валидными
  • C не поддерживает указатели
  • Для шифрования
Прямой доступ к массиву — только в «критической» секции, блокирующей перемещение.

Что произойдёт при обращении к MemorySegment после закрытия его арены?

  • Порча памяти
  • Падение JVM
  • Вернутся нули
  • IllegalStateException — время жизни проверяется
Безопасность — главное преимущество FFM.

Чем опасна ошибка в нативной библиотеке, вызываемой через JNI?

  • Падением всего процесса JVM (SIGSEGV, hs_err_pid.log), а не исключением
  • Только исключением в потоке
  • Ничем, JVM изолирует нативный код
  • Утечкой одного объекта
Нативный код работает в том же адресном пространстве.
Когда оправдан нативный код в Java-сервисе?

Когда есть зрелая нативная библиотека без хорошего Java-аналога (кодеки, RocksDB, GPU/CUDA, системные API ОС), когда нужна работа с памятью вне кучи и с отображёнными файлами большого объёма, и для интеграции с платформой. Не ради «скорости» мелких операций: переход стоит десятки наносекунд, а JIT часто не хуже. Предпочтительно — FFM API и jextract вместо JNI.

Что смотреть в hs_err_pid.log после падения JVM?

Тип сигнала и проблемный кадр (Problematic frame: C [libx.so+0x…] — нативная библиотека; V [libjvm.so] — ошибка JVM; J — скомпилированный Java-код), стек потока, в котором упало, список потоков, состояние кучи, загруженные библиотеки, флаги JVM и информацию о системе (память, лимиты). Нативная библиотека в кадре — смотреть её версию и вызовы; libjvm — обновлять JDK и искать известный баг.
