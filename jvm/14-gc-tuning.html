Логи GC, настройка и OutOfMemoryError

Настройка GC начинается не с флагов, а с измерений: что говорит лог, как меняется занятость кучи после сборок, сколько времени уходит на паузы. Учимся читать строки лога G1 и ZGC, отличать утечку от маленькой кучи по графику, разбираем каждый вид OutOfMemoryError с порядком действий и анализ дампа кучи.

14.1Включить логи GC (всегда, в продакшене)

-Xlog:gc*,safepoint:file=/var/log/app/gc.log:time,uptime,level,tags:filecount=10,filesize=50m
# gc        — одна строка на сборку (кратко)
# gc*       — фазы, размеры поколений, возраст объектов
# safepoint — время до safepoint и длительность пауз
# анализ: GCeasy, GCViewer, JDK Mission Control (по JFR)

Накладные расходы ничтожны, а без лога разбор инцидента «у нас были задержки ночью» превращается в гадание.

Открываем .hprof (нужна память ≈ размеру дампа). Автоматический отчёт сразу указывает подозреваемого: одна ConcurrentHashMap удерживает 78% кучи.

Объект A доминирует над B, если любой путь от корней к B проходит через A. Дерево доминаторов показывает, что именно освободится при удалении объекта.

Shallow size — размер самого объекта (у HashMap — десятки байт). Retained size — всё, что освободится вместе с ним. Сортируйте по retained.

«Path to GC Roots (exclude weak/soft references)» — кто держит объект: статическое поле SessionRegistry.SESSIONS.

Причина в коде: записи добавляются и никогда не удаляются. Типичные утечки: статические коллекции-кэши без ограничения, слушатели без отписки, ThreadLocal в пулах, незакрытые ресурсы, неограниченные очереди. Исправление — ограниченный кэш (Caffeine), явное удаление, WeakReference там, где уместно (тема 15).

14.6Порядок настройки

  1. Цель: что важно — p99 задержек, пропускная способность, память? Без цели настройка бессмысленна.
  2. Размер кучи — главная ручка: живые данные × 2–4 для G1/ZGC; проверить по «после GC».
  3. Выбор сборщика (тема 13) под цель.
  4. Цель паузы G1: -XX:MaxGCPauseMillis (не ставьте нереально малой — G1 уменьшит молодое поколение и будет собирать слишком часто).
  5. Сократить мусор в коде — часто эффективнее любых флагов.
  6. Тонкие флаги (G1NewSizePercent, InitiatingHeapOccupancyPercent, ConcGCThreads) — только по данным лога и с повторным замером.

14.7Самопроверка

По какому признаку в логах GC отличить утечку от слишком маленькой кучи?

  • По длине пауз
  • По тренду занятости после сборок: при утечке он растёт, при малой куче стабилен у предела
  • По числу потоков GC
  • Никак
Живые данные (после GC) — главный индикатор.

Что такое retained size в анализе дампа?

  • Размер объекта без ссылок
  • Размер класса в metaspace
  • Объём, занимаемый строками
  • Объём памяти, который освободится, если объект станет недостижим (всё, над чем он доминирует)
Shallow — сам объект, retained — его «империя».

OutOfMemoryError: unable to create native thread — что увеличивать?

  • Ничего из размеров кучи: проблема в числе потоков ОС — ищите неограниченные пулы и утечку потоков, проверьте лимиты процессов
  • -Xmx
  • MaxMetaspaceSize
  • -Xss
Увеличение Xss даже ухудшит ситуацию.

Зачем в продакшене -XX:+ExitOnOutOfMemoryError?

  • Чтобы ускорить GC
  • Чтобы сохранить дамп
  • После OOM состояние приложения непредсказуемо (потоки умерли, кэши частично заполнены) — лучше упасть и быть перезапущенным оркестратором
  • Чтобы отключить OOM
В связке с HeapDumpOnOutOfMemoryError.
Расскажите ваш порядок действий при OutOfMemoryError: Java heap space в продакшене.

Стабилизировать: перезапуск (ExitOnOutOfMemoryError + оркестратор), при необходимости временно больше памяти. Собрать данные: дамп кучи (HeapDumpOnOutOfMemoryError), логи GC за период (тренд «после GC»), метрики нагрузки. Анализ: Leak Suspects и дерево доминаторов в MAT, путь к GC roots, сравнение гистограмм двух моментов. Определить: утечка (найти и исправить код) или рост рабочего набора/всплеск (увеличить кучу, ограничить кэши, стримить большие данные вместо загрузки в память). Добавить алерт на «heap after GC».

Почему System.gc() в коде — плохая идея?

Это запрос полной сборки с остановкой (в G1 — Full GC или, с -XX:+ExplicitGCInvokesConcurrent, конкурентный цикл): длинная пауза в произвольный момент, обычно без пользы, так как JVM сама знает, когда собирать. Встречается в библиотеках (старые версии для освобождения direct-буферов, RMI каждый час). Можно отключить -XX:+DisableExplicitGC, но осторожно с direct-памятью.
