Формат class-файла

Class-файл — единственное, что JVM знает о вашем коде. Ни исходников, ни импортов, ни имён локальных переменных (без отладочной информации) там нет: только пул констант, описания полей и методов, байткод и атрибуты. Разберём настоящий class-файл в 401 байт побайтово: щёлкайте по структурам и байтам — увидите, как JVM читает каждый из них.

2.1Общая структура

ClassFile {
    u4             magic;                 // 0xCAFEBABE
    u2             minor_version;
    u2             major_version;         // 65 = Java 21, 69 = Java 25
    u2             constant_pool_count;   // число записей + 1
    cp_info        constant_pool[constant_pool_count-1];
    u2             access_flags;          // ACC_PUBLIC, ACC_FINAL, ACC_INTERFACE, ACC_ENUM, ...
    u2             this_class;            // индекс в пуле → CONSTANT_Class
    u2             super_class;
    u2             interfaces_count;   u2 interfaces[];
    u2             fields_count;       field_info  fields[];
    u2             methods_count;      method_info methods[];
    u2             attributes_count;   attribute_info attributes[];   // SourceFile, InnerClasses, Record, ...
}

2.3Пул констант

Пул констант — таблица символов класса. Байткод не содержит строк и имён: getstatic #7 ссылается на запись Fieldref, та — на Class и NameAndType, а те — на строки Utf8. Это символические ссылки: пока класс не слинкован, JVM знает только имена. Превращение их в прямые указатели (на объект Class, смещение поля, точку входа метода) — это разрешение (resolution, тема 06).

ТегЧто хранит
Utf8строка в модифицированной UTF-8 (нулевой символ кодируется двумя байтами)

Class, Stringссылка на Utf8 с именем класса / содержимым строкового литерала

Декодер дескрипторов

Дескриптор метода не содержит возвращаемого типа в «сигнатуре перегрузки» Java, но в class-файле он есть — поэтому на уровне JVM могут существовать два метода с одинаковыми аргументами и разными возвращаемыми типами (так компилятор делает bridge-методы для дженериков и ковариантных возвратов). Дженерики живут только в атрибуте Signature — для рефлексии; байткод работает со стёртыми типами.

2.6Практикум: пишем и запускаем

Class-файл — обычный двоичный файл, и его можно прочитать самому. В этих лабораторных вы напишете крошечный парсер заголовка, найдёте в пуле констант то, что «спрятал» javac, научитесь читать дескрипторы и увидите, какие атрибуты зависят от флагов компиляции. Модуль IDEA — ch02.

Код набирайте руками — так он запоминается. Перед запуском запишите предсказание в поле «Ваш прогноз», затем сверьтесь с реальным выводом (снят на JDK 25.0.2; адреса, времена и хэши у вас будут другими). Как подготовить окружение — на странице курса.

Лаба 2.1Читаем заголовок class-файла своим кодом20 мин

Убедиться, что class-файл начинается с CAFEBABE, номер версии определяет минимальную JVM, а javac --release меняет эту версию.

  1. Класс-«подопытный»:
    public class Point {
    static final int ORIGIN = 0;
    private final int x, y;

    public Point(int x, int y) { this.x = x; this.y = y; }

    public int dist2() { return x * x + y * y; }

    @Override
    public String toString() { return "Point(" + x + ", " + y + ")"; }
}
  2. Мини-парсер: читает первые поля структуры ClassFile из спецификации JVMS §4.1:
    import java.io.DataInputStream;
import java.io.FileInputStream;

public class ClassHeader {
    public static void main(String[] args) throws Exception {
        try (var in = new DataInputStream(new FileInputStream(args[0]))) {
            int magic = in.readInt();
            int minor = in.readUnsignedShort();
            int major = in.readUnsignedShort();
            int cpCount = in.readUnsignedShort();
            System.out.printf("magic         = %X%n", magic);
            System.out.printf("version       = %d.%d  (Java %d)%n", major, minor, major - 44);
            System.out.printf("constant_pool = %d записей (индексы 1..%d)%n", cpCount, cpCount - 1);
        }
    }
}

    IDEAProgram arguments: out/production/ch02/Point.class (относительно корня проекта). Или из терминала — команды ниже.

    javac Point.java ClassHeader.java

    Вывод (JDK 25.0.2)
    magic         = CAFEBABE

constant_pool = 47 записей (индексы 1..46)
  3. Скомпилируем Point для Java 8: javac --release 8 Point.java. Что изменится в заголовке?

    Вывод (JDK 25.0.2)

    version = 52.0 (Java 8): major version = номер Java + 44. Пул констант тоже станет другим: для Java 8 javac собирает строку в toString через StringBuilder, а не через invokedynamic, — в пуле появятся ссылки на методы StringBuilder вместо StringConcatFactory. Предупреждения «source value 8 is obsolete» — JDK напоминает, что поддержку компиляции под Java 8 скоро уберут.

  5. Скомпилируйте Point под Java 25 (просто javac Point.java) и попробуйте загрузить его на JDK 21 (если он у вас есть). Что произойдёт?
    Вывод
    Error: LinkageError occurred while loading main class Point
	java.lang.UnsupportedClassVersionError: Point has been compiled by a more recent version of the Java Runtime (class file version 69.0), this version of the Java Runtime only recognizes class file versions up to 65.0

    UnsupportedClassVersionError: «class file version 69.0, this version of the Java Runtime only recognizes class file versions up to 65.0». Старая JVM не знает новых версий формата и отказывается даже начинать разбор. Обратная ситуация (старый class на новой JVM) работает всегда.

Поэкспериментируйте
  • Почему --release 8 лучше, чем старое -source 8 -target 8?
    --release ещё и проверяет API: компилятор подставляет сигнатуры стандартной библиотеки Java 8 и не даст вызвать, например, List.of, которого там нет. С -target код скомпилируется и упадёт NoSuchMethodError уже на Java 8.
  • Допишите в парсер чтение access_flags, this_class и super_class. Почему просто так не получится?
    Они идут после пула констант, а записи пула имеют разную длину (тег определяет формат). Придётся разобрать пул целиком: 1 — Utf8 (u2 длина + байты), 7 — Class (u2), 10 — Methodref (u2+u2), 3/4 — Integer/Float (u4), 5/6 — Long/Double (u8 и занимают ДВА индекса) и т. д.
Лаба 2.2Пул констант: что туда кладёт javac20 мин

Найти в пуле констант строки, числа и символические ссылки и понять, когда константа попадает в пул, а когда «вшивается» прямо в инструкцию.

  1. Класс с разными видами констант:
    public class Consts {
    static final int SMALL = 100;
    static final int BIG = 100_000;
    static final String HELLO = "hello";

    static int calc(int a) {
        return a * 7 + 40_000 + 1_000_000;
    }

    public static void main(String[] args) {
        System.out.println(HELLO + calc(SMALL) + BIG);
    }
}

javap -v -p Consts.class | findstr "Integer String Methodref Fieldref InvokeDynamic ConstantValue"

  2. Сколько записей Integer окажется в пуле и почему именно таких? Посмотрите заодно на байткод calc: javap -c Consts.
    javap -c Consts.class
    Вывод (JDK 25.0.2)
      static int calc(int);

         3: imul

    Числа 7 и 100 помещаются в инструкцию (bipush — байт, sipush — до 32767), поэтому в пул не попадают как операнды кода. 40 000 и 1 000 000 не влезают в short — для них ldc и записи Integer в пуле. А в main выражение HELLO + calc(SMALL) + BIG использует уже подставленные константы: bipush 100 и строку «…100000» в рецепте конкатенации.

    javap -c -v Consts.class | findstr /C:"invokedynamic" /C:"\u0001"
    Вывод (JDK 25.0.2)

  #49 = Utf8               hello\u0001100000
         8: invokedynamic #21,  0             // InvokeDynamic #0:makeConcatWithConstants:(I)Ljava/lang/String;
      #48 hello\u0001100000

    Символ \u0001 в рецепте — место для динамического аргумента (результат calc), остальное — константный текст: "hello" + ? + "100000".

Поэкспериментируйте
  • Уберите final у BIG и снова посмотрите на main.
    Теперь это обычное статическое поле: появится getstatic Consts.BIG, а в рецепте конкатенации — второй \u0001. Константа времени компиляции — только static final примитив или String, инициализированный константным выражением.
Лаба 2.3Дескрипторы и Signature: что остаётся от generics15 мин

Научиться читать дескрипторы методов и увидеть, где хранится информация о параметрах типов, которую «стирает» компилятор.

  1. Создайте файл Descr.java:
    import java.util.List;
import java.util.Map;

public class Descr {
    void a() {}
    int b(long x, double y) { return 0; }
    String[] c(Map<String, List<Integer>> m, int[][] grid) { return null; }
    <T extends Comparable<T>> T max(List<? extends T> xs) { return null; }
    static boolean d(char c, byte b, short s, float f, Object o) { return true; }
}
  2. Запишите дескриптор каждого метода, прежде чем запускать javap -s. Особенно c и max.
    javac Descr.java
javap -s -p Descr.class
    Вывод (JDK 25.0.2)
    Compiled from "Descr.java"
public class Descr {
  public Descr();
    descriptor: ()V

  void a();
    descriptor: ()V

  int b(long, double);
    descriptor: (JD)I

  java.lang.String[] c(java.util.Map<java.lang.String, java.util.List<java.lang.Integer>>, int[][]);
    descriptor: (Ljava/util/Map;[[I)[Ljava/lang/String;

  <T extends java.lang.Comparable<T>> T max(java.util.List<? extends T>);
    descriptor: (Ljava/util/List;)Ljava/lang/Comparable;

    a: ()V, b: (JD)I, c: (Ljava/util/Map;[[I)[Ljava/lang/String;, max: (Ljava/util/List;)Ljava/lang/Comparable; — тип T стёрт до своей границы Comparable, d: (CBSFLjava/lang/Object;)Z. Буквы: J — long, Z — boolean, L…; — класс, [ — массив.

  3. Где же generics? В атрибуте Signature — его читает компилятор и рефлексия, но не JVM при выполнении:

Поэкспериментируйте
  • Напишите Descr.class.getDeclaredMethod("c", Map.class, int[][].class).getGenericParameterTypes() в jshell или в main. Что выведется?

Лаба 2.4Атрибуты отладки: откуда берутся номера строк15 мин

Увидеть, что номера строк в стектрейсе и имена параметров — это необязательные атрибуты, зависящие от флагов javac.

  1. Создайте файл Boom.java:
    public class Boom {
    static int divide(int numerator, int denominator) {
        return numerator / denominator;
    }

    public static void main(String[] args) throws Exception {
        var m = Boom.class.getDeclaredMethod("divide", int.class, int.class);
        for (var p : m.getParameters()) System.out.println("параметр: " + p.getName());
        divide(1, 0);
    }
}
  2. Обычная компиляция:
    javac Boom.java
java Boom
    Вывод (JDK 25.0.2)
    параметр: arg0
параметр: arg1
Exception in thread "main" java.lang.ArithmeticException: / by zero
	at Boom.divide(Boom.java:3)
	at Boom.main(Boom.java:9)
  3. Скомпилируем с javac -g:none (без отладочной информации). Что изменится в стектрейсе?
    javac -g:none Boom.java
java Boom
    Вывод (JDK 25.0.2)
    параметр: arg0
параметр: arg1
Exception in thread "main" java.lang.ArithmeticException: / by zero
	at Boom.divide(Unknown Source)
	at Boom.main(Unknown Source)

    Вместо Boom.java:3 будет Unknown Source: исчез атрибут LineNumberTable (и SourceFile). JVM знает только смещение инструкции в байткоде, а сопоставить его со строкой исходника нечем.

  4. А как получить настоящие имена параметров numerator, denominator вместо arg0, arg1?
    javac -parameters Boom.java
java Boom
javap -v Boom.class | findstr /C:"MethodParameters" /C:"LineNumberTable"
    Вывод (JDK 25.0.2)
    параметр: numerator
параметр: denominator
Exception in thread "main" java.lang.ArithmeticException: / by zero
	at Boom.divide(Boom.java:3)
	at Boom.main(Boom.java:9)
      LineNumberTable:
      LineNumberTable:
    MethodParameters:
      LineNumberTable:

    Флаг javac -parameters добавляет атрибут MethodParameters. Его используют Spring (@PathVariable без имени), Jackson-модуль parameter-names. Отладочная LocalVariableTable (-g) рефлексией не читается. В IDEA флаг включается в Settings → Build → Compiler → Java Compiler → Additional parameters.

Поэкспериментируйте
  • Скомпилируйте с -g и найдите в javap -v -p таблицу LocalVariableTable метода divide. Что в колонках Start и Length?
    Диапазон байткода, где переменная «жива», и слот локальных переменных. Отладчик IDEA показывает имена переменных именно отсюда; без -g он увидит только slot_0, slot_1.

2.7Самопроверка

Ошибка UnsupportedClassVersionError … class file version 69.0 … only recognizes up to 65.0. Что случилось?

  • Повреждён class-файл
  • Класс скомпилирован для Java 25, а запускается на Java 21
  • Не найден класс
  • Нехватка памяти
major − 44 = версия Java. Компилируйте с --release по минимальной целевой версии.

Где хранится строка «Hi» из println("Hi")?

  • Прямо в байткоде инструкции
  • В куче при компиляции
  • В атрибуте SourceFile
  • В пуле констант: String → Utf8; инструкция ldc ссылается на индекс
При выполнении ldc JVM возвращает интернированный объект String.

Что означает дескриптор (J[Ljava/lang/String;)Z?

  • boolean m(long, String[])
  • int m(String, long)
  • long m(boolean, String[])
  • void m(Object)
J — long, Z — boolean.

Почему в стектрейсе бывает «Unknown Source» вместо номера строки?

  • Класс загружен из сети
  • Ошибка JIT
  • Класс скомпилирован без отладочной информации (нет SourceFile/LineNumberTable)
  • Метод нативный
Флаги javac -g, -g:none.
Как JVM находит поле System.out при выполнении getstatic #7?

#7 — Fieldref на Class #8 (java/lang/System) и NameAndType #9 (out : Ljava/io/PrintStream;). При первом выполнении инструкции запись разрешается: загружается и инициализируется класс System, ищется поле с таким именем и дескриптором, проверяется доступ; результат (адрес статического поля в зеркале класса) кэшируется в пуле констант времени выполнения, следующие выполнения берут его сразу. Интерпретатор даже переписывает инструкцию в «быструю» форму.

Зачем знать формат class-файла прикладному разработчику?

Чтобы понимать ошибки ClassFormatError/UnsupportedClassVersionError/NoSuchMethodError, работу агентов и инструментирования (Mockito, Hibernate, Spring AOP генерируют и меняют классы через Byte Buddy/ASM/Class-File API), что видит рефлексия (параметры, дженерики, аннотации), как javac компилирует лямбды, строковую конкатенацию, records — и читать javap при разборе производительности.
