Линковка и инициализация классов

Загруженный класс ещё нельзя использовать: его байткод надо проверить, под статические поля — выделить память, символические ссылки — разрешить, а статические инициализаторы — выполнить ровно один раз, даже если к классу одновременно обратились сто потоков. Здесь — верификатор, ленивое разрешение, точные правила «когда выполнится static-блок» (с тренажёром) и как инициализация классов приводит к взаимоблокировке.

6.1Верификация

Верификатор доказывает, что байткод не сломает JVM: не выйдет за пределы стека операндов, не использует int как ссылку, не прыгнет в середину инструкции, не обратится к неинициализированному объекту, вызывает методы с правильными типами. Это то, что делает безопасным исполнение байткода из любого источника.

  • Проверка типов (class-файлы версии 50+): javac записывает в атрибут StackMapTable типы на стеке и в слотах в точках ветвления — верификатору остаётся проверить каждый линейный участок за один проход.
  • Классы bootstrap-загрузчика по умолчанию не верифицируются (им доверяют); для остальных — всегда. Флаг -Xverify:none / -XX:-BytecodeVerificationRemote устарел и опасен.
  • Типичные ошибки — от генераторов байткода (агенты, ASM с неверными фреймами): java.lang.VerifyError: Bad type on operand stack, Expecting a stackmap frame at branch target.

6.2Подготовка и разрешение

Preparation

Выделяется место под статические поля (в объекте java.lang.Class — «зеркале» класса) и заполняется значениями по умолчанию: 0, false, null. Не ваши значения! static int counter = 42 в этот момент равно 0. Исключение — static final константы времени компиляции (атрибут ConstantValue): они получают значение сразу.

Resolution

Символические ссылки пула констант (имена классов, полей, методов) превращаются в прямые: указатель на класс, смещение поля, индекс vtable или точку входа метода. HotSpot делает это лениво — при первом выполнении инструкции; результат кэшируется в ConstantPoolCache. Поэтому NoSuchMethodError возникает не при загрузке класса, а при первом вызове метода.

6.3Когда выполняется инициализация

Инициализация — выполнение <clinit>: присваивания статических полей и static { } блоки в порядке их появления в исходнике. Происходит ровно один раз, при первом активном использовании:

Инициализирует

  • new X()
  • чтение/запись статического поля (не константы)
  • вызов статического метода
  • Class.forName("X"), рефлексивный вызов
  • инициализация подкласса (сначала — суперкласс)
  • главный класс при запуске

Не инициализирует

  • X.class, loader.loadClass("X")
  • создание массива new X[10]
  • чтение static final константы примитива или String — javac подставил значение в код
  • обращение к статическому полю родителя через подкласс Child.parentField — инициализирует только родителя
  • суперинтерфейсы — только если у них есть default-методы
Тренажёр: что будет напечатано?
class Parent {
    static { System.out.print("P "); }
    static int a = 1;
    static final int C = 10;              // константа времени компиляции
    static final Integer W = 5;           // не константа: Integer — объект
    static void hello() { }
}
class Child extends Parent {
    static { System.out.print("C "); }
    static int b = 2;
}
Сначала предскажите вывод, затем нажмите «Показать ответ».
Ловушка констант Если библиотека поменяла public static final int VERSION = 2 на 3, ваш класс, скомпилированный против старой версии, продолжит видеть 2 — значение вшито в ваш байткод. Для значений, которые могут меняться, используйте не константы (методы, или поля, не являющиеся константой времени компиляции).

6.4Потокобезопасность и порядок <clinit>

JVMS §5.5 описывает процедуру инициализации с блокировкой на класс: первый поток помечает класс «инициализируется», остальные ждут; рекурсивный запрос из того же потока видит класс «в процессе» и продолжает (с недоинициализированными полями!). Если <clinit> бросил исключение — класс помечается ошибочным, первый получит ExceptionInInitializerError, все последующие — NoClassDefFoundError: Could not initialize class.

public final class Registry {
    private Registry() { /* дорогая инициализация */ }
    private static final class Holder {
        static final Registry INSTANCE = new Registry();   // выполнится при первом обращении к Holder
    }
    public static Registry get() { return Holder.INSTANCE; } // потокобезопасно: гарантия JVMS, без volatile и lock
}
class Config {
    static final Config INSTANCE = new Config();   // конструктор выполнится, когда DEFAULT_PORT ещё 0!
    static final Integer DEFAULT_PORT = 8080;      // Integer — не константа
    final int port;
    Config() { port = DEFAULT_PORT; }              // NullPointerException при распаковке null
}

class A { static B INSTANCE_B = B.create(); } и class B { static A INSTANCE_A = A.create(); }. В одном потоке это работает (рекурсивная инициализация увидит класс «в процессе»), но в двух — нет.

Поток 1 первым обращается к A, захватывает блокировку инициализации A и начинает выполнять его <clinit>.

Одновременно поток 2 обращается к B и начинает его инициализацию.

<clinit> A обращается к B — его инициализирует поток 2, ждём. <clinit> B обращается к A — его инициализирует поток 1, ждём. Оба потока навсегда в состоянии RUNNABLE/«in Object.wait()» в дампе с пометкой waiting on the Class initialization monitor (JDK 21+). Детектор deadlock в jstack это не всегда покажет как deadlock.

Не создавайте циклических зависимостей в статической инициализации; не запускайте потоки и не ждите их из static-блоков; переносите тяжёлую инициализацию из статики в явный жизненный цикл (бины Spring). Классический реальный случай — подкласс, на который ссылается статическое поле родителя (static final Parent DEFAULT = new Child()).

6.6Самопроверка

Чему равно static int counter = 42 после этапа preparation?

  • 42
  • 0 — значение по умолчанию; 42 присвоит <clinit>
  • null
  • не определено
Preparation выделяет память и обнуляет, инициализация присваивает.

Почему ленивый синглтон через вложенный класс-holder потокобезопасен?

  • Из-за volatile
  • Компилятор вставляет synchronized
  • Holder — final
  • JVM гарантирует однократную инициализацию класса Holder под блокировкой при первом обращении
Инициализация классов — встроенный механизм ленивой и безопасной инициализации.

Когда возникнет NoSuchMethodError для отсутствующего в рантайме метода?

  • При первом выполнении инструкции вызова (ленивое разрешение)
  • При загрузке класса вызывающего
  • При компиляции
  • При старте JVM
Поэтому ошибка может проявиться через часы работы, на редкой ветке кода.

int x = Child.a; где a объявлено в Parent. Какие классы инициализируются?

  • Parent и Child
  • Только Child
  • Только Parent
  • Никакие
Инициализируется класс, в котором поле объявлено.
Перечислите этапы линковки и что на каждом может пойти не так.

Верификация — VerifyError (кривой сгенерированный байткод, несовместимые StackMapTable). Подготовка — практически без ошибок (кроме нехватки памяти). Разрешение — NoSuchMethodError, NoSuchFieldError, IllegalAccessError, IncompatibleClassChangeError, LinkageError при нарушении ограничений загрузчиков; происходит лениво при первом выполнении инструкции. Затем инициализация — ExceptionInInitializerError и далее NoClassDefFoundError «Could not initialize class».

Почему опасна тяжёлая работа в static-блоках?

Она выполняется в неочевидный момент (первое обращение), под блокировкой инициализации класса — другие потоки ждут; исключение навсегда делает класс непригодным до перезапуска (и в логе останется только NoClassDefFoundError); возможны взаимоблокировки при циклах; её трудно тестировать и мокать. Лучше — явная инициализация в жизненном цикле приложения.
