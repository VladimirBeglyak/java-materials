Выделение памяти: TLAB, escape analysis

new в Java дешевле, чем malloc в C: обычно это сдвиг указателя в собственном буфере потока — около десятка машинных инструкций без синхронизации. А часть объектов JIT вообще не создаёт, разложив их поля по регистрам. Разбираем быстрый и медленный путь выделения, TLAB, большие объекты, escape analysis со скалярной заменой — и почему темп выделения памяти определяет частоту сборок мусора.

11.1Быстрый путь: bump pointer в TLAB

Каждый поток получает в eden свой TLAB (Thread-Local Allocation Buffer) — кусок от килобайт до мегабайт. Выделение объекта: проверить, что top + size ≤ end, вернуть top, сдвинуть top. Ни блокировок, ни атомарных операций — буфер принадлежит одному потоку. Затем записать заголовок и обнулить поля (или всю TLAB заранее).

obj = thread.tlab_top
new_top = obj + 24                    ; размер Point известен при компиляции
if new_top > thread.tlab_end: goto slow_path
thread.tlab_top = new_top
[obj+0] = mark (unlocked, no hash)    ; заголовок
[obj+8] = klass(Point)
[obj+12..24] = 0                      ; поля по умолчанию — затем конструктор (часто встроен)
Eden, поделённый на TLAB трёх потоков
  • Размер TLAB подстраивается под каждый поток (ResizeTLAB): активно выделяющий поток получает большие буферы.
  • Медленный путь — вызов в рантайм JVM: новая TLAB, выделение в общем eden с CAS, а если eden кончился — сборка мусора.
  • Большие объекты: в G1 объект больше половины региона — humongous, выделяется в старом поколении сразу целыми регионами; массивы на десятки мегабайт — частая причина неожиданных полных сборок.

11.2Escape analysis и скалярная замена

C2 анализирует, может ли объект «сбежать» из метода (после встраивания вызываемых методов). Если нет — объекта в куче может не быть вообще: его поля становятся локальными переменными в регистрах (scalar replacement), а блокировки на нём снимаются (lock elision).

Сбежит ли объект?
Не рассчитывайте вслепую Escape analysis работает только в C2 (и Graal), только для горячего кода, после встраивания, и для небольших объектов (массивы ограниченного размера). В интерпретаторе и C1 всё выделяется. Проверка — профилировщик аллокаций (JFR jdk.ObjectAllocationSample, async-profiler -e alloc) и JMH с -prof gc.

11.3Темп выделения определяет частоту сборок

Как часто будет молодая сборка

Молодая сборка копирует только живые объекты, поэтому её стоимость зависит не от объёма мусора, а от количества выживших. Много короткоживущего мусора — дёшево; много объектов «средней» жизни (кэши на секунды, большие батчи) — дорого: они копируются по нескольку раз и засоряют старое поколение.

11.4Практикум: пишем и запускаем

Сколько байт выделяет ваш код, можно измерить прямо из программы: com.sun.management.ThreadMXBean.getThreadAllocatedBytes считает выделения текущего потока (их и показывают профилировщики аллокаций). На этом счётчике проверим escape analysis и связь темпа выделения с частотой сборок. Модуль IDEA — ch11.

Код набирайте руками — так он запоминается. Перед запуском запишите предсказание в поле «Ваш прогноз», затем сверьтесь с реальным выводом (снят на JDK 25.0.2; адреса, времена и хэши у вас будут другими). Как подготовить окружение — на странице курса.

Лаба 11.1Escape analysis: объекты, которых нет20 мин

Увидеть, как C2 убирает выделение памяти для объектов, не покидающих метод, и как это ломается.

  1. Создайте файл Escape.java:
    import java.lang.management.ManagementFactory;

public class Escape {
    record Point(int x, int y) {
        Point plus(Point o) { return new Point(x + o.x, y + o.y); }
    }

    static Point sink;   // «утечка» наружу

    static long noEscape(int n) {
        long s = 0;
        for (int i = 0; i < n; i++) {
            Point p = new Point(i, i).plus(new Point(1, 2));   // три объекта: два здесь, один в plus
            s += p.x() + p.y();
        }
        return s;
    }

    static long escapes(int n) {
        long s = 0;
        for (int i = 0; i < n; i++) {
            Point p = new Point(i, i);
            sink = p;                                          // объект виден снаружи
            s += p.x();
        }
        return s;
    }

    public static void main(String[] args) {
        var mx = (com.sun.management.ThreadMXBean) ManagementFactory.getThreadMXBean();
        long tid = Thread.currentThread().threadId();
        for (int round = 1; round <= 5; round++) {
            long b0 = mx.getThreadAllocatedBytes(tid);
            noEscape(1_000_000);
            long b1 = mx.getThreadAllocatedBytes(tid);
            escapes(1_000_000);
            long b2 = mx.getThreadAllocatedBytes(tid);
            System.out.printf("раунд %d: noEscape %,12d байт   escapes %,12d байт%n", round, b1 - b0, b2 - b1);
        }
    }
}
  2. Объект Point с двумя int занимает 24 байта (12 заголовок + 8 поля + 4 выравнивание), каждая итерация noEscape создаёт три таких объекта — 72 МБ на миллион итераций. Что покажут раунды?

java Escape

раунд 2: noEscape    9,437,112 байт   escapes   24,000,000 байт
раунд 3: noEscape            0 байт   escapes   24,000,000 байт
раунд 4: noEscape            0 байт   escapes   24,000,000 байт
раунд 5: noEscape            0 байт   escapes   24,000,000 байт

    Первые раунды — меньше 72 МБ, но не ноль: часть итераций выполняется ещё в интерпретаторе или C1, а с середины цикла подключается OSR-версия от C2. Как только C2 скомпилирует noEscape целиком, выделения падают до нуля: объекты не покидают метод, и после встраивания plus скалярная замена превращает их поля в локальные переменные. В escapes объект записывается в статическое поле — сбегает — и честно выделяется: 24 МБ на миллион. С -XX:-DoEscapeAnalysis noEscape стабильно выделяет все 72 МБ.

Поэкспериментируйте
  • Добавьте в noEscape строку if (i == n - 1) sink = p;.
    Объект «сбегает» хотя бы на одной ветке — для C2 это GlobalEscape, и скалярная замена не применяется (C2 не умеет выделять объект «только на редкой ветке»; это частично умеет Graal). Выделения вернутся.
  • Сделайте plus огромным (добавьте в него 50 строк вычислений) — что станет с выделениями и почему?
    Метод перестанет встраиваться (лимит размера байткода, тема 17), объект станет аргументом невстроенного вызова — ArgEscape, — и выделения вернутся. Escape analysis работает только после встраивания.
Лаба 11.2Темп выделения → частота сборок15 мин

Увидеть в логе GC, что молодые сборки происходят каждый раз, когда заполняется eden, и что их частота пропорциональна темпу выделения.

  1. Создайте файл Rate.java:
    public class Rate {
    static byte[] last;

    public static void main(String[] args) throws Exception {
        int kbPerMs = Integer.parseInt(args[0]);
        long end = System.currentTimeMillis() + 2000;
        long total = 0;
        while (System.currentTimeMillis() < end) {
            for (int i = 0; i < kbPerMs; i++) { last = new byte[1024]; total++; }
            Thread.sleep(1);
        }
        System.out.printf("выделено ~%d МБ за 2 с%n", total / 1024);
    }
}

11.5Самопроверка

Почему выделение объекта в Java обычно не требует синхронизации между потоками?

  • Объекты выделяются в стеке
  • JVM блокирует кучу целиком
  • Каждый поток выделяет в своём TLAB простым сдвигом указателя
  • Выделение происходит при компиляции
Синхронизация нужна только на медленном пути — при получении новой TLAB.

Что такое скалярная замена?

  • JIT не создаёт объект, который не покидает метод, а держит его поля в регистрах/локальных переменных
  • Замена объектов на примитивы в исходном коде
  • Сжатие указателей
  • Перемещение объекта в старое поколение
Работает в C2 после встраивания.

От чего в первую очередь зависит время молодой сборки в копирующем сборщике?

  • От размера eden
  • От объёма мусора
  • От числа классов
  • От количества выживших объектов, которые надо скопировать
Мёртвые объекты не трогаются вовсе.
Как найти, кто создаёт больше всего мусора?

JFR (событие jdk.ObjectAllocationSample — стектрейсы выделений с весом) и JDK Mission Control; async-profiler в режиме alloc (флеймграф аллокаций); в тестах — JMH с -prof gc (байт на операцию). Затем смотреть горячие места: boxing в коллекциях, копирования строк, сериализация, логирование с конкатенацией, создание DTO и стримов в циклах.

Стоит ли делать пулы объектов, чтобы «не нагружать GC»?

Для обычных объектов — нет: выделение в TLAB дешевле, чем взятие из пула с синхронизацией, а долгоживущие объекты пула ухудшают работу поколенческого GC (ссылки из старого поколения в молодое, барьеры). Пулы оправданы для дорогих в создании ресурсов (соединения, потоки), больших буферов (особенно direct) и в системах с жёсткими требованиями к задержкам после измерений.
