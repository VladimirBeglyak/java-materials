Быстрый старт JVM — простыми словами

Для серверов, которые живут неделями, старт за 10 секунд неважен. Для автомасштабирования, serverless и командных утилит — критичен. Разберёмся, куда уходит время запуска и какие есть способы его сократить, с их плюсами и ценой.

20.1Куда уходит время старта

  • Загрузка и проверка классов — тысячи классов JDK, библиотек и вашего кода.
  • Инициализация фреймворка — Spring сканирует классы, создаёт бины, читает конфигурацию.
  • Прогрев — пока JIT не скомпилировал горячий код, всё медленнее (глава 16).
Главная мысль Старт = загрузка классов + инициализация фреймворка + прогрев.

20.2CDS: готовый архив классов

CDS (Class Data Sharing) — классы, уже прочитанные, проверенные и разложенные в памяти, сохраняются в архив. При следующем старте JVM просто «отображает» архив в память, пропуская работу. Для классов JDK архив включён по умолчанию, для своего приложения его можно создать отдельно. Выигрыш — заметная часть времени старта, почти бесплатно.

Главная мысль CDS — классы готовы заранее. Почти бесплатный выигрыш.

В полной главе: 20.2 CDS: общий архив классов

20.3AOT-кэш (проект Leyden)

Развитие идеи CDS в новых версиях Java: при «тренировочном» запуске JVM запоминает не только классы, но и их связи, а в дальнейшем — профили и скомпилированный код. Следующий старт начинает «с середины». Это стандартная Java без ограничений native image, но и выигрыш скромнее.

Главная мысль AOT-кэш запоминает результаты тренировочного запуска — без ограничений на код.

В полной главе: 20.3 AOT cache: проект Leyden

20.4CRaC: снимок прогретого процесса

CRaC — как спящий режим ноутбука: запускаете сервис, прогреваете, делаете снимок всего процесса на диск. Новый экземпляр восстанавливается из снимка за десятки миллисекунд, уже прогретый. Сложности: перед снимком нужно закрыть соединения и сокеты, а после восстановления открыть заново; нужна поддерживающая сборка JDK.

Главная мысль CRaC — «разбудить» уже прогретый процесс из снимка.

В полной главе: 20.4 CRaC: снимок прогретого процесса

20.5GraalVM Native Image

Native image компилирует всё приложение заранее в обычный исполняемый файл, без JVM внутри. Старт — миллисекунды, памяти мало. Цена: долгая сборка (минуты), рефлексию и динамическую загрузку классов нужно заранее описать, а пиковая производительность часто ниже, чем у прогретого JIT.

Главная мысль Native image — мгновенный старт и мало памяти ценой ограничений и долгой сборки.

20.8Проверьте себя

Что даёт CDS?

  • сжатие кода
  • шифрование
  • готовый архив загруженных классов для быстрого старта
  • снимок процесса
Работа загрузки пропускается.

Какой подход позволяет запустить сервис сразу прогретым?

  • CRaC: восстановление из снимка прогретого процесса
  • CDS
  • увеличение -Xmx
  • отключение JIT
Снимок делается после прогрева.

Чем приходится платить за native image?

  • ничем
  • долгим стартом
  • большим расходом памяти
  • ограничениями на рефлексию и долгой сборкой
Зато старт мгновенный.

Что выбрать для serverless-функции, которая стартует на каждый запрос?

  • ничего не менять
  • native image
  • больше памяти
  • Parallel GC
Старт и память критичны.

Что нужно сделать перед снимком CRaC?

  • выключить JIT
  • очистить кучу
  • закрыть соединения и открытые ресурсы, а после восстановления открыть снова
  • ничего
Сокеты нельзя «заморозить» в снимке.
