Интерпретатор и JIT: tiered compilation

HotSpot начинает с интерпретации, считает вызовы и итерации циклов и компилирует горячие методы дважды: быстро и без особых оптимизаций (C1), а затем, собрав профиль, — агрессивно (C2). Отсюда «прогрев»: первые запросы после старта в разы медленнее. Разбираем пять уровней компиляции, пороги, OSR, очередь компиляции, вывод -XX:+PrintCompilation и что делать с прогревом.

16.1Зачем компилировать во время работы

Против AOT

JIT видит реальный профиль: какие ветки выполняются, какие классы приходят в виртуальный вызов, какие методы горячие. Он может делать спекулятивные оптимизации («здесь всегда ArrayList») и откатывать их, если предположение нарушится (деоптимизация, тема 17).

Цена

Время старта и прогрева, CPU на компиляцию (потоки C1/C2), память под code cache и профили, непредсказуемость производительности первых минут.

16.2Пять уровней

УровеньЧтоСкорость кода
0интерпретатор (с базовым профилированием)1× (очень медленно)
1C1 без профилирования — для тривиальных методов (геттеры), которым C2 ничего не добавит~ максимум для таких методов
2C1 с ограниченным профилированием (счётчики вызовов и циклов) — когда очередь C2 перегруженабыстро
3C1 с полным профилированием (типы получателей, ветки, null) — основная ступеньбыстро, но ~30% накладных на профиль
4C2: агрессивные оптимизации по профилюмаксимум (в 10–50 раз быстрее интерпретатора)

Типичный путь: 0 → 3 → 4. Метод интерпретируется, после ~200 вызовов (или ~2000 вызовов+итераций) компилируется C1 с профилированием, после ~5000 вызовов (~15000 с итерациями) — C2. Пороги масштабируются при загруженности очереди компиляции.

16.3OSR: компиляция посреди цикла

Метод main с циклом на миллиард итераций вызывается один раз — счётчик вызовов не поможет. Поэтому есть счётчик обратных переходов (backedge): когда он превышает порог, метод компилируется в специальной версии с точкой входа на заголовке цикла, и JVM заменяет кадр интерпретатора на кадр скомпилированного кода прямо в процессе выполнения (On-Stack Replacement). В PrintCompilation такие компиляции отмечены % и номером байткода цикла. Вывод для микробенчмарков: код, измеряемый в одном длинном цикле main, работает не так, как тот же код, вызываемый многократно, — используйте JMH.

16.4Читаем -XX:+PrintCompilation

Расшифровка строки
-XX:+PrintCompilation                                   # каждая компиляция
-XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining       # решения о встраивании (тема 17)
-XX:+UnlockDiagnosticVMOptions -XX:+LogCompilation      # подробный XML → JITWatch
jcmd <pid> Compiler.queue                               # что ждёт компиляции
jcmd <pid> Compiler.codecache                           # заполненность code cache
-XX:TieredStopAtLevel=1                                 # только C1: быстрее старт, медленнее пик (CLI-утилиты, тесты)

16.6Самопроверка

Почему метод сначала компилируется C1 с профилированием, а не сразу C2?

  • C2 не умеет компилировать холодный код
  • C1 быстрее C2 на любом коде
  • C2 нужен профиль (типы, ветки) для спекулятивных оптимизаций, а C1-код с профилем быстро даёт и скорость, и данные
  • Так требует спецификация
Уровень 3 — компромисс скорости и сбора профиля.

Что такое OSR?

  • Замена кадра интерпретатора на кадр скомпилированного кода посреди долгого цикла
  • Оптимизация строк
  • Сборка мусора в старом поколении
  • Удаление скомпилированного кода
Метка % в PrintCompilation.

Почему первые запросы после деплоя медленные, хотя приложение «запустилось»?

  • Медленная сеть
  • Пустой пул соединений — единственная причина
  • GC
  • Код ещё интерпретируется или работает на C1; плюс ленивая загрузка и инициализация классов, первые indy-связывания
Прогрев — сумма ленивых механизмов JVM.

Что значит «made not entrant» в выводе компиляции?

  • Ошибка компиляции
  • Версия кода больше не используется для новых вызовов — заменена или деоптимизирована
  • Метод удалён из класса
  • Метод стал нативным
Код удалится из code cache, когда его перестанут исполнять.
Как правильно измерять производительность Java-кода с учётом JIT?

JMH: отдельный процесс (fork), итерации прогрева до стабильности, Blackhole против удаления мёртвого кода, защита от свёртки констант, несколько форков для разброса, профилировщики (-prof gc, -prof perfasm). Самописный цикл в main измеряет смесь интерпретатора, OSR и компиляции, а JIT может выбросить «бесполезный» код целиком.

Зачем ограничивать JIT уровнем C1 (TieredStopAtLevel=1)?

Для короткоживущих процессов (CLI, сборка, тесты в CI): C2 не успеет окупиться, а его компиляции тратят CPU и память. C1 даёт быстрый старт и разумную скорость. Для долгоживущих серверов — нет: потеря пиковой производительности в разы.
