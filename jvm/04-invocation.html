Вызовы методов и invokedynamic

Пять инструкций вызова определяют, как JVM находит метод: статически, через таблицу виртуальных методов, через поиск по интерфейсу — или динамически, спросив у вашего кода. Разбираем vtable и itable, как работают super, private и конструкторы, во что превращаются лямбды и конкатенация строк, чем MethodHandle лучше рефлексии и откуда берётся NoSuchMethodError.

Перегрузка (overload) решается компилятором: в байткоде уже записан конкретный дескриптор. Переопределение (override) — JVM во время выполнения по классу объекта. Поэтому void f(Object o) и void f(String s) выбираются по статическому типу аргумента, а animal.speak() — по реальному классу.

4.2vtable: виртуальный вызов за один переход

У каждого класса в metaspace есть таблица виртуальных методов: массив указателей на реализации. Подкласс копирует таблицу родителя, заменяет ячейки переопределённых методов и дописывает новые в конец. Номер ячейки метода одинаков во всей иерархии — поэтому invokevirtual = «взять класс объекта → vtable[индекс] → перейти».

Иерархия Animal → Dog → Puppy и Animal → Cat

itable устроена сложнее: класс может реализовывать много интерфейсов, и у одного метода интерфейса нет фиксированного номера во всех классах. Поэтому invokeinterface сначала ищет в классе блок нужного интерфейса, затем ячейку в нём — чуть дороже. На практике разница почти исчезает: JIT ставит inline cache (запоминает класс получателя в месте вызова) и встраивает метод, если на этом месте встречается 1–2 класса (мономорфный и биморфный вызов, тема 17).

final и private final на методе не ускоряет вызов в современной JVM: JIT по иерархии загруженных классов (Class Hierarchy Analysis) сам видит, что переопределений нет, и при загрузке подкласса откатывает оптимизацию. С Java 11 вызовы private-методов между вложенными классами (nestmates) компилируются в invokevirtual/invokeinterface без синтетических методов доступа access$000.

4.3invokedynamic

Появился в Java 7 для динамических языков, а стал главным механизмом самой Java. Идея: инструкция в байткоде указывает на bootstrap-метод (в атрибуте BootstrapMethods) и дескриптор. При первом выполнении JVM вызывает bootstrap-метод, тот возвращает CallSite с целевым MethodHandle, и место вызова навсегда связывается с этой целью. JIT видит цель как константу и встраивает её.

Что происходит при первом выполнении Runnable r = () -> System.out.println("x");

javac выносит тело лямбды в private-метод того же класса (lambda$lambda$0; если лямбда захватывает this — экземплярный), а на месте лямбды ставит invokedynamic с дескриптором «вернуть Runnable», аргументы которого — захваченные переменные. Анонимного класса в jar нет.

JVM разрешает инструкцию: вызывает bootstrap-метод LambdaMetafactory.metafactory с объектом Lookup (правами доступа вызывающего класса), именем метода интерфейса, сигнатурами и MethodHandle на lambda$lambda$0.

Фабрика генерирует байткод класса, реализующего Runnable, метод run которого вызывает lambda$lambda$0, и определяет его как скрытый класс (hidden class, Java 15+): без имени в загрузчике, выгружаемый, недоступный по Class.forName.

Возвращается ConstantCallSite. Для лямбды без захваченных переменных цель возвращает один и тот же объект при каждом выполнении (поэтому == между двумя вычислениями такой лямбды обычно истинно — но полагаться на это нельзя); с захватом — новый объект с полями.

Повторные выполнения не вызывают bootstrap: место вызова уже связано. Цена «первого раза» — генерация класса (заметна при старте: тысячи лямбд Spring-приложения; помогает CDS/AOT cache, тема 20).

4.4MethodHandle против рефлексии

// рефлексия: проверка доступа и упаковка аргументов на каждом вызове (до Java 18)
Method m = Point.class.getDeclaredMethod("dist", Point.class);
double d1 = (double) m.invoke(p1, p2);

// MethodHandle: доступ проверяется один раз при поиске, вызов типизирован
static final MethodHandle DIST = MethodHandles.lookup()
    .findVirtual(Point.class, "dist", MethodType.methodType(double.class, Point.class));
double d2 = (double) DIST.invokeExact(p1, p2);   // static final → JIT встраивает как прямой вызов

С Java 18 (JEP 416) сама рефлексия реализована поверх MethodHandle. Правило производительности: держите MethodHandle в static final поле — тогда JIT считает его константой и встраивает цель.

4.6Самопроверка

Какой инструкцией вызывается super.toString()?

  • invokevirtual
  • invokespecial
  • invokestatic
  • invokedynamic
Нужна ровно реализация родителя, без виртуальной диспетчеризации.

Где выбирается перегруженный метод print(Object) против print(String)?

  • JVM по фактическому типу аргумента
  • JIT
  • Загрузчик классов
  • javac по статическому типу аргумента — в байткоде уже конкретный дескриптор
Перегрузка — статически, переопределение — динамически.

Во что компилируется лямбда () -> work()?

  • Private-метод с телом + invokedynamic, который при первом выполнении создаёт скрытый класс через LambdaMetafactory
  • Анонимный внутренний класс в jar
  • Вызов рефлексии
  • Ничего, лямбды интерпретируются
Поэтому в jar нет классов вида Outer$1 для лямбд.

Приложение упало с NoSuchMethodError: …Builder.build()Lcom/x/Client;, хотя метод build() есть. Причина?

  • Метод private
  • Не хватает памяти
  • В рантайме версия библиотеки, где build() возвращает другой тип — дескриптор не совпадает
  • Ошибка JIT
Дескриптор включает возвращаемый тип.
Объясните, как работает виртуальный вызов в HotSpot от байткода до машинного кода.

javac записывает invokevirtual с символической ссылкой на метод статического типа. При первом выполнении ссылка разрешается в индекс vtable. Интерпретатор берёт класс объекта (klass pointer в заголовке) → vtable[индекс] → переход. JIT собирает профиль типов получателей в этом месте: если тип один (мономорфный) — проверка класса + встроенный код метода; два — две проверки; больше (мегаморфный) — обычный переход через vtable без встраивания.

Зачем invokedynamic для конкатенации строк, если StringBuilder работал?

Стратегия склейки зашита в байткод при StringBuilder и не может улучшаться без перекомпиляции. С indy байткод только описывает рецепт и типы аргументов, а реализацию выбирает рантайм текущей версии JDK: точный предрасчёт длины, без лишних копий и промежуточных буферов. Улучшения JDK ускоряют старые class-файлы.
