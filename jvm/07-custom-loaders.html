Свои загрузчики, изоляция, утечки

Свои загрузчики стоят за плагинами, серверами приложений, горячей перезагрузкой, исполняемым jar Spring Boot, изоляцией тестов и генерацией кода. 7.1Пишем загрузчик

public class DirClassLoader extends ClassLoader {
    static { registerAsParallelCapable(); }            // блокировка на имя класса, а не на весь загрузчик
    private final Path root;

    public DirClassLoader(Path root, ClassLoader parent) { super("dir-loader", parent); this.root = root; }

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        Path file = root.resolve(name.replace('.', '/') + ".class");
        try {
            byte[] bytes = Files.readAllBytes(file);         // сюда можно вставить расшифровку, генерацию, трансформацию
            return defineClass(name, bytes, 0, bytes.length); // → верификация, создание Class в metaspace
        } catch (IOException e) {
            throw new ClassNotFoundException(name, e);
        }
    }

    @Override
    protected URL findResource(String name) {               // getResource тоже должен работать
        Path p = root.resolve(name);
        try { return Files.exists(p) ? p.toUri().toURL() : null; } catch (MalformedURLException e) { return null; }
    }
}
  • Переопределяя findClass, вы сохраняете делегирование родителю. Переопределяйте loadClass, только если нужна child-first модель — и всегда делегируйте java.* родителю.
  • Для jar и URL обычно достаточно URLClassLoader; для сгенерированного в рантайме кода — MethodHandles.Lookup.defineHiddenClass (скрытые классы, выгружаемые независимо).
  • Закрывайте URLClassLoader.close() — иначе на Windows jar-файлы останутся заблокированными.

7.2Горячая перезагрузка

Переопределить уже загруженный класс нельзя (кроме ограниченной редефиниции тел методов через JVMTI — раздел 7.5). Поэтому перезагрузка = новый загрузчик: загрузить новые версии классов в свежий загрузчик, переключить на них, а старый загрузчик оставить сборщику мусора.

7.3Загрузчики в реальных системах

Spring Boot executable jar

Внутри app.jar лежат BOOT-INF/classes и BOOT-INF/lib/*.jar — вложенные jar стандартный загрузчик читать не умеет. Main-Class в манифесте — JarLauncher: он создаёт LaunchedClassLoader с собственным протоколом URL для вложенных jar (jar:nested:…!/BOOT-INF/lib/x.jar) и запускает ваш Start-Class. Распакованный режим (java -Djarmode=tools -jar app.jar extract) быстрее стартует и лучше для слоёв Docker и CDS.

Tomcat

Bootstrap → System → Common (lib/ Tomcat) → WebappClassLoader на каждое приложение. Для webapp порядок child-first: сначала WEB-INF/classes и WEB-INF/lib, кроме java.* и API сервлетов. Поэтому два приложения могут иметь разные версии Jackson, но servlet-api.jar в WEB-INF/lib ломает приложение.

// API: interface PaymentProvider { String id(); … }
// реализация в отдельном jar: META-INF/services/com.shop.PaymentProvider  →  строка: com.acme.AcmeProvider
// или в module-info: provides com.shop.PaymentProvider with com.acme.AcmeProvider;
ServiceLoader<PaymentProvider> sl = ServiceLoader.load(PaymentProvider.class, pluginLoader);
sl.stream().map(ServiceLoader.Provider::get).forEach(p -> registry.put(p.id(), p));
// так находятся JDBC-драйверы (java.sql.Driver), логгеры SLF4J 2, провайдеры JSON-B, Jackson-модули (findAndRegisterModules)

7.4Выгрузка классов и утечки загрузчиков

Класс выгружается только вместе со своим загрузчиком — когда сборщик мусора докажет, что недостижимы одновременно: сам загрузчик, все загруженные им объекты Class и все экземпляры этих классов. Классы bootstrap, platform и app загрузчиков не выгружаются никогда. Одна «забытая» ссылка удерживает весь загрузчик — тысячи классов в metaspace и все их статические поля.

Утечёт ли загрузчик веб-приложения после редеплоя?
java -Xlog:class+load=info,class+unload=info -jar app.jar
jcmd <pid> VM.classloader_stats      # загрузчики, число классов, размер их метаданных
jcmd <pid> GC.class_histogram | head # экземпляры по классам
jcmd <pid> VM.metaspace              # подробности metaspace по загрузчикам

7.5Java-агенты и инструментирование

Агент — jar с методом premain (при старте, -javaagent:agent.jar) или agentmain (подключение к работающей JVM через Attach API). Он получает Instrumentation и может регистрировать ClassFileTransformer — функцию «байты класса → новые байты», вызываемую при каждой загрузке класса, до defineClass.

public class TimingAgent {
    public static void premain(String args, Instrumentation inst) {
        inst.addTransformer(new ClassFileTransformer() {
            @Override
            public byte[] transform(Module module, ClassLoader loader, String className,
                                    Class<?> redefined, ProtectionDomain pd, byte[] bytes) {
                if (className == null || !className.startsWith("com/shop/")) return null;   // null = не менять
                return Weaver.addTiming(bytes);     // ASM / Class-File API / Byte Buddy
            }
        }, true);
    }
}
// MANIFEST.MF: Premain-Class: TimingAgent   Can-Retransform-Classes: true
Кто так работаетЧто делает
APM: OpenTelemetry Java agent, Datadog, New Relicвплетают трассировку в JDBC, HTTP-клиенты, Spring MVC при загрузке
Mockito (inline mock maker)ретрансформирует классы, чтобы мокать final-классы и методы (с JDK 21 — предупреждение о динамической загрузке агента, JEP 451; добавьте -javaagent явно)
JaCoCoвставляет пробы покрытия
async-profiler, JFRнативные агенты JVMTI (не трансформируют байткод)

Retransformation уже загруженных классов (inst.retransformClasses) разрешает менять только тела методов: нельзя добавлять поля и методы или менять иерархию.

7.6Самопроверка

Какой метод переопределять в своём загрузчике, чтобы сохранить делегирование?

  • loadClass
  • findClass
  • defineClass
  • getParent
loadClass реализует делегирование и вызывает findClass, когда родители не нашли класс.

Когда выгружается класс, загруженный пользовательским загрузчиком?

  • Сразу после использования
  • Никогда
  • При System.gc()
  • Когда недостижимы загрузчик, все его Class и все экземпляры этих классов — и прошла сборка мусора
Выгрузка — это сборка мусора загрузчика целиком.

После 20 редеплоев в Tomcat — OutOfMemoryError: Metaspace. Самая вероятная причина?

  • Утечка загрузчика: что-то долгоживущее держит ссылку на класс или объект старого приложения
  • Слишком маленькая куча
  • Слишком много потоков
  • Большие JSP
Ищите пути к GC Roots от старых WebappClassLoader в heap dump.

Как Spring Boot загружает классы из jar, вложенных в app.jar?

  • Распаковывает их во временный каталог при каждом старте
  • Стандартный AppClassLoader это умеет
  • JarLauncher создаёт собственный загрузчик с поддержкой вложенных jar
  • Через ServiceLoader
Main-Class: JarLauncher, Start-Class: ваш класс.
Спроектируйте систему плагинов на JVM.

API плагинов — в отдельном модуле, загружаемом загрузчиком приложения. Каждый плагин — свой URLClassLoader с родителем «загрузчик API» (видит только API и JDK, а не внутренности приложения); при конфликтах библиотек — child-first для всего, кроме java.* и API-пакетов. Обнаружение реализаций — ServiceLoader. Выгрузка — закрыть загрузчик, остановить потоки плагина, снять регистрации; проверять утечки. Готовые решения: PF4J, OSGi, JPMS-слои (тема 08).

Чем агент с ClassFileTransformer отличается от Spring AOP?

Агент меняет байткод любых классов (включая чужие библиотеки и JDK, кроме части ядра) при загрузке — работают и self-invocation, и final-методы, и не-бины. Spring AOP создаёт прокси вокруг бинов в рантайме: перехватываются только внешние вызовы через прокси публичных (для CGLIB — не final) методов. Агент сложнее в отладке и влияет на старт; AOP — проще, но ограничен.
