Объект в памяти: заголовок и раскладка

Сколько байт занимает new Integer(5)? А ArrayList из миллиона Integer? Ответ определяется заголовком объекта, сжатыми указателями, выравниванием и тем, как JVM раскладывает поля. Разберём mark word и klass pointer, compressed oops и «обрыв на 32 ГБ», компактные заголовки Java 25, соберём раскладку своего класса в калькуляторе, повторяющем вывод JOL.

10.1Заголовок объекта

ЧастьРазмер (64 бит)Содержимое
Mark word8 байтв зависимости от состояния: identity hash code (31 бит), возраст для GC (4 бита), биты блокировки; при блокировке — указатель на запись блокировки или монитор; при сборке — пересылочный адрес
Klass pointer4 байта (сжатый) или 8указатель на структуру Klass в metaspace: тип, vtable, раскладка полей
Длина массива4 байтатолько у массивов

Итого обычный заголовок — 12 байт, у массива — 16. С компактными заголовками (JEP 450 экспериментально в Java 24, JEP 519 — продуктовая опция в Java 25: -XX:+UseCompactObjectHeaders) klass pointer сжимается до 22 бит и помещается в mark word — заголовок 8 байт, экономия 10–20% кучи в типичных приложениях.

Состояния mark word (64 бита, упрощённо)
unlocked…hash:31 | age:4 | 0 | 01
lightweight locked…| 00
monitor (inflated)ptr ObjectMonitor | 10
marked (GC)forwarding ptr | 11

Только что созданный объект: хэш ещё не вычислен (identity hash code вычисляется лениво при первом System.identityHashCode / Object.hashCode и записывается в заголовок), возраст 0, два младших бита 01 — «не заблокирован».

Каждая молодая сборка, которую объект пережил, увеличивает 4-битный возраст. Достигнув порога (до 15 — потолок 4 бит), объект переводится в старое поколение (тема 12).

Поток входит в synchronized, конкуренции нет: «лёгкая» блокировка меняет биты атомарной операцией CAS. С Java 21 (по умолчанию с Java 23) HotSpot использует новую lightweight locking со стеком блокировок в потоке; biased locking удалён (Java 15–18, тема 18).

При конкуренции или вызове wait() блокировка «раздувается»: создаётся нативный ObjectMonitor с очередями ожидающих, а mark word хранит указатель на него. Хэш при этом сохраняется в мониторе.

Копирующий сборщик, переместив объект, записывает в mark старой копии адрес новой — так другие ссылки находят, куда объект переехал. После сборки старая область освобождается целиком.

Почему identityHashCode «стабилен», а объекты двигаются Хэш — не адрес (адрес меняется при каждом копировании), а случайное число, вычисленное один раз и сохранённое в заголовке. Если объект заблокирован, хэш хранится в мониторе. С компактными заголовками для хэша при перемещении иногда добавляется дополнительное поле.

10.2Сжатые указатели и обрыв на 32 ГБ

Ссылки на объекты (oops) в 64-битной JVM по умолчанию хранятся в 32 битах: так как объекты выровнены по 8 байт, младшие 3 бита адреса всегда нули, и 32-битное число, сдвинутое на 3, адресует 2³² × 8 = 32 ГБ. Если -Xmx ≥ ~32 ГБ, сжатие отключается: каждая ссылка — 8 байт, и куча 33 ГБ вмещает меньше объектов, чем 31 ГБ.

10.3Раскладка полей: калькулятор

JVM переставляет поля (порядок в исходнике не сохраняется): раскладывает примитивные поля от больших к меньшим, затем ссылки, заполняя «дырки» (в том числе 4 байта после 12-байтного заголовка) подходящими по размеру полями, чтобы каждое было выровнено по своему размеру; поля суперкласса идут раньше полей подкласса. Размер объекта выравнивается до кратного 8.

10.5Практикум: пишем и запускаем

Раскладку объектов в памяти показывает утилита JOL (Java Object Layout) из проекта OpenJDK. Скачайте её в каталог lib модуля ch10 и добавьте как зависимость (Project Structure → Modules → Dependencies → + → JARs). Флаг --sun-misc-unsafe-memory-access=allow только убирает предупреждения JDK 24+ о том, что JOL использует sun.misc.Unsafe.

Код набирайте руками — так он запоминается. Перед запуском запишите предсказание в поле «Ваш прогноз», затем сверьтесь с реальным выводом (снят на JDK 25.0.2; адреса, времена и хэши у вас будут другими). Как подготовить окружение — на странице курса.

  2. Объект без полей занимает 16 байт, из которых 4 — «дырка» выравнивания. А сколько займёт new int[3]?
    import org.openjdk.jol.info.ClassLayout;

public class Layout {
    public static void main(String[] args) {
        System.out.println(ClassLayout.parseInstance(new int[3]).toPrintable());
        Object o = new Object();
        System.out.println("до hashCode:   " + ClassLayout.parseInstance(o).toPrintable().lines().filter(l -> l.contains("mark")).findFirst().orElse(""));
        System.out.printf("hashCode = %x%n", o.hashCode());
        System.out.println("после hashCode:" + ClassLayout.parseInstance(o).toPrintable().lines().filter(l -> l.contains("mark")).findFirst().orElse(""));
        synchronized (o) {
            System.out.println("под synchronized:" + ClassLayout.parseInstance(o).toPrintable().lines().filter(l -> l.contains("mark")).findFirst().orElse(""));
        }
    }
}

    Обратите внимание: identity hashCode записывается прямо в mark word при первом вызове (биты 0x…01 → появилось ваше значение), а под synchronized mark word содержит указатель на запись блокировки в стеке (thin lock). Подробнее — в теме 18.

    32 байта: 8 (mark) + 4 (класс) + 4 (длина массива) = 16 байт заголовка, затем 3 × 4 = 12 байт данных, итого 28 → выравнивание до кратного 8 даёт 32.

Поэкспериментируйте
  • Запустите тот же internals java.lang.Object с -XX:+UseCompactObjectHeaders (продуктовый флаг с Java 25, JEP 519).
    Строки «object header: class» больше нет: указатель на класс поместился внутрь 8-байтного mark word (JOL пометит его «Lilliput»). Объект без полей — по-прежнему 16 байт. Заголовок короче на 4 байта, но объект уменьшается, только если эти 4 байта «перешагивают» границу выравнивания в 8 байт (лаба 10.2 покажет обратный случай). В среднем по куче экономия ощутимая — типичные объекты маленькие.
Лаба 10.2Порядок полей и «дырки» выравнивания15 мин

Убедиться, что JVM переставляет поля по размеру и что поля родителя идут раньше полей наследника.

  1. Создайте файл Fields.java:
    import org.openjdk.jol.info.ClassLayout;

public class Fields {
    static class Base { boolean flag; }
    static class Order extends Base {
        byte status;
        long id;
        int qty;
        Object ref;
        char code;
    }

    public static void main(String[] args) {
        System.out.println(ClassLayout.parseClass(Order.class).toPrintable());
    }
}
  2. Поля объявлены в порядке status, id, qty, ref, code. В каком порядке они лежат в памяти и каков размер объекта?
    javac -cp lib/jol-cli.jar Fields.java
java --sun-misc-unsafe-memory-access=allow -cp "lib/jol-cli.jar;." Fields
    Вывод (JDK 25.0.2)
    OFF  SZ               TYPE DESCRIPTION               VALUE
  0   8                    (object header: mark)     N/A
  8   4                    (object header: class)    N/A
 12   1            boolean Base.flag                 N/A
 13   1               byte Order.status              N/A
 14   2               char Order.code                N/A
 16   8               long Order.id                  N/A
 24   4                int Order.qty                 N/A
 28   4   java.lang.Object Order.ref                 N/A
Instance size: 32 bytes
Space losses: 0 bytes internal + 0 bytes external = 0 bytes total

    JVM сначала кладёт поля родителя (flag), затем поля класса, сгруппированные по убыванию размера: long → int → ссылки → char → byte, заполняя «дырки» мелкими полями. Порядок объявления не важен. Итог — 32 байта, причём без единого потерянного байта: byte и char заняли щель 13–15 перед long, которому нужно выравнивание на 8.

  3. Теперь с компактными заголовками: заголовок на 4 байта короче. Станет ли объект меньше 32 байт?

    IDEAVM options: -XX:+UseCompactObjectHeaders --sun-misc-unsafe-memory-access=allow

    java -XX:+UseCompactObjectHeaders --sun-misc-unsafe-memory-access=allow -cp "lib/jol-cli.jar;." Fields
    Вывод (JDK 25.0.2)
    OFF  SZ               TYPE DESCRIPTION               VALUE
  0   8                    (object header: mark)     N/A
  8   1            boolean Base.flag                 N/A
  9   1               byte Order.status              N/A
 10   2               char Order.code                N/A
 12   4                int Order.qty                 N/A
 16   8               long Order.id                  N/A
 24   4   java.lang.Object Order.ref                 N/A
 28   4                    (object alignment gap)    
Instance size: 32 bytes
Space losses: 0 bytes internal + 4 bytes external = 4 bytes total

    Нет: 8 + 20 байт полей = 28, выравнивание до 8 даёт те же 32 байта, только теперь с 4 байтами «дырки» в конце. Компактный заголовок выигрывает у объектов, где старый размер был «чуть больше» кратного 8, — например, у класса с одним полем long: 24 → 16 байт.

Поэкспериментируйте
  • Отключите сжатые ссылки -XX:-UseCompressedOops. Что изменится?
    Поле ref станет 8 байт, объект вырастет. Указатель на класс при этом останется 4-байтным: за него отвечает отдельный флаг UseCompressedClassPointers. Это то, что происходит при -Xmx ≥ 32 ГБ.
Лаба 10.3Сколько памяти на самом деле занимает коллекция20 мин

Посчитать полный «след» (footprint) структуры данных — со всеми внутренними объектами — и сравнить ArrayList<Integer>, int[] и HashMap.

  1. Создайте файл Footprint.java:
    import org.openjdk.jol.info.GraphLayout;

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

public class Footprint {
    public static void main(String[] args) {
        int n = 1000;
        int[] arr = new int[n];
        List<Integer> list = new ArrayList<>();
        Map<Integer, Integer> map = new HashMap<>();
        for (int i = 0; i < n; i++) { arr[i] = i + 1000; list.add(i + 1000); map.put(i + 1000, i + 1000); }

        System.out.println("int[1000]:            " + GraphLayout.parseInstance((Object) arr).totalSize() + " байт");
        System.out.println("ArrayList<Integer>:   " + GraphLayout.parseInstance(list).totalSize() + " байт");
        System.out.println("HashMap<Int,Int>:     " + GraphLayout.parseInstance(map).totalSize() + " байт");
        System.out.println();
        System.out.println(GraphLayout.parseInstance(map).toFootprint());
    }
}
  2. Во сколько раз ArrayList<Integer> тяжелее int[] на тысяче чисел больше 127? А HashMap?

Поэкспериментируйте
  • Замените i + 1000 на i % 100 в ArrayList. Почему след резко уменьшится?
    Значения −128..127 берутся из кэша Integer.valueOf — все 1000 ссылок указывают на 100 общих объектов, а JOL считает каждый объект графа один раз.

10.6Самопроверка

Сколько байт занимает объект Integer на 64-битной JVM со сжатыми указателями (без компактных заголовков)?

  • 4
  • 16 (12 заголовок + 4 значение)
  • 8
  • 24
С компактными заголовками 8 + 4 = 12 → тоже 16 после выравнивания: выигрыш получают объекты, у которых освободившиеся 4 байта уменьшают размер после выравнивания.

Почему куча 34 ГБ может вместить меньше данных, чем 30 ГБ?

  • GC медленнее
  • Ошибка JVM
  • Больше заголовков
  • Выше ~32 ГБ отключаются сжатые указатели, и каждая ссылка занимает 8 байт вместо 4
Обрыв на 32 ГБ.

Где хранится identity hash code объекта?

  • В mark word заголовка (или в мониторе, если объект заблокирован)
  • Это адрес объекта
  • В отдельной хэш-таблице JVM
  • В klass pointer
Вычисляется лениво и не меняется при перемещении объекта.

Сохраняет ли JVM порядок полей из исходного кода?

  • Да, всегда
  • Да, если поля public
  • Нет: поля переставляются для плотной упаковки и выравнивания; суперкласс раньше подкласса
  • Только для records
@Contended (jdk.internal.vm.annotation) — способ развести поля по разным кэш-линиям.
Как оценить память структуры из 10 млн объектов до запуска?

Посчитать по раскладке: заголовок 12 Б (8 с compact headers), поля по их размерам, ссылки 4 Б при куче < 32 ГБ, выравнивание до 8; добавить накладные расходы контейнера (узлы, массивы-таблицы с коэффициентом заполнения), объекты-обёртки (Integer, Long, String + byte[]). Проверить JOL GraphLayout на выборке и экстраполировать; затем подтвердить гистограммой кучи (jcmd GC.class_histogram).

Что дают компактные заголовки и есть ли у них цена?

Заголовок 8 байт вместо 12: меньше куча (по замерам 10–20%), меньше нагрузка на GC и кэши процессора, иногда быстрее. Ограничения: klass pointer 22 бита (до ~4 млн классов), особенности хранения хэша при перемещении; в Java 25 это продуктовая, но не включённая по умолчанию опция — проверяйте на своей нагрузке.
