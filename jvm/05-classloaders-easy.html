5.2Иерархия загрузчиков

Bootstrap

Встроенный в JVM. Грузит базовые классы: java.lang, java.util.

Platform

Остальные модули платформы: java.sql, java.xml и др.

Application

Ваши классы и библиотеки из classpath или modulepath.

Главная мысль Три уровня: базовый, платформенный, прикладной.

5.3Делегирование: сначала спроси старшего

Кто загрузит java.lang.String и com.shop.Order
Application: «String? сначала спрошу родителя (Platform)»Platform → Bootstrap: «у меня есть java.lang.String» → загружен имApplication: «Order? спрошу родителей» → у них нетApplication ищет сам в classpath → нашёл в shop.jar
подменить String своим классом невозможно — его всегда даст Bootstrap

Запрос всегда сначала идёт к родителю.

Базовые классы грузит самый старший.

Только тогда загрузчик ищет сам.

Системные классы не подменить.

Главная мысль Делегирование вверх защищает системные классы и избавляет от дублей.

5.4Класс = имя + загрузчик

Для JVM класс — это пара «полное имя + загрузчик, который его загрузил». Если один и тот же класс com.shop.Order загрузили два разных загрузчика, это два разных класса — их объекты нельзя привести друг к другу. Отсюда загадочное «ClassCastException: Order cannot be cast to Order» в серверах приложений и плагинах. Зато это позволяет в одной JVM держать две версии библиотеки.

Главная мысль Один класс в двух загрузчиках — два разных класса. «Order нельзя привести к Order».

В полной главе: 5.4 Идентичность класса = имя + загрузчик

5.5ClassNotFoundException и NoClassDefFoundError

ClassNotFoundException

Код явно попросил класс по имени (Class.forName, рефлексия), а его нет. Обычно — опечатка или нет нужного JAR.

NoClassDefFoundError

При компиляции класс был, а при запуске его нет — или его инициализация однажды уже упала. Смотрите на первое исключение в логах: там настоящая причина.

Главная мысль CNFE — попросили по имени и не нашли. NCDFE — был при компиляции, нет (или сломан) при запуске.

В полной главе: 5.5 ClassNotFoundException против NoClassDefFoundError

5.6Class.forName и контекстный загрузчик

Class.forName загружает и инициализирует класс (по умолчанию загрузчиком вызывающего класса), loadClass — только загружает. Фреймворки, которые сами лежат «выше» вашего кода (например, в общем загрузчике сервера), не видят ваших классов. Для этого у каждого потока есть контекстный загрузчик — «подсказка» фреймворку, через какой загрузчик искать классы приложения.

Главная мысль forName инициализирует, loadClass — нет; контекстный загрузчик помогает фреймворкам видеть ваши классы.

5.8Проверьте себя

Кто загрузит java.lang.String?

  • Application
  • Platform
  • Bootstrap
  • любой
Самый старший загрузчик.

Что значит «ClassCastException: Order cannot be cast to Order»?

  • один класс загружен двумя разными загрузчиками — для JVM это разные классы
  • опечатка
  • ошибка компилятора
  • нехватка памяти
Класс = имя + загрузчик.

NoClassDefFoundError для класса, который точно есть в JAR. Что ещё проверить?

  • DNS
  • права на файл
  • версию браузера
  • не упала ли раньше инициализация этого класса — ищите первое исключение
После сбоя инициализации класс считается непригодным.

Чем Class.forName отличается от loadClass?

  • ничем
  • forName ещё и инициализирует класс
  • loadClass быстрее загружает
  • forName работает только с JAR
Статические блоки выполнятся при forName.

Зачем нужно делегирование родителю?

  • для скорости
  • чтобы классы грузились параллельно
  • чтобы системные классы нельзя было подменить и не было дублей
  • не нужно
Безопасность и согласованность.
