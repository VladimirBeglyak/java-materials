Диагностика: jcmd, JFR, дампы, профилировщики

JVM — одна из самых наблюдаемых сред исполнения: в каждый JDK встроены швейцарский нож jcmd, бортовой самописец Java Flight Recorder с накладными расходами около 1%, дампы потоков и кучи. Разбираем, какой инструмент отвечает на какой вопрос, как читать дамп потоков и флеймграф, и пошагово расследуем классические инциденты: «процесс ест 100% CPU», «всё зависло», «медленно, но непонятно где».

Что запустить, чтобы ответить на вопрос

Процесс JVM занимает 4 ядра. Первый вопрос — это GC/JIT или код приложения?

top -H -p <pid> показывает потоки. Если это «GC Thread#…» или «G1 Conc#…» — проблема с памятью (тема 14); «C2 CompilerThread» — компиляция (прогрев, деоптимизации). Здесь — прикладные потоки пула.

Ищем поток по nid в дампе (снимите 2–3 дампа: если стек одинаковый — поток там застрял). Видим регулярное выражение в Validator.check.

Профилировщик за 30 секунд подтверждает: 92% CPU — в Pattern.matches из валидатора. Дамп показывает момент, профиль — статистику.

Регулярное выражение с вложенными квантификаторами на «злом» вводе — экспоненциальный перебор (ReDoS). Исправление: переписать без вложенных повторов, ограничить длину ввода, притяжательные квантификаторы. Похожий сценарий даёт бесконечный цикл в HashMap при гонке (старые JDK) или горячий цикл ожидания.

21.4Как читать флеймграф

Ось X — доля сэмплов (не время по порядку!), ось Y — глубина стека, снизу корень. Ширина кадра = доля времени, когда метод был на стеке (вместе с вызванными). Ищите широкие «плато» наверху — там тратится время непосредственно. Щёлкните кадр, чтобы приблизить.

21.5Java Flight Recorder

-XX:StartFlightRecording=disk=true,maxage=6h,maxsize=500m,settings=default,dumponexit=true,filename=/var/log/app/
jcmd <pid> JFR.dump name=1 filename=/tmp/incident.jfr      # снять запись за последние часы после инцидента
jcmd <pid> JFR.start duration=2m settings=profile filename=/tmp/p.jfr   # подробный профиль на время
jfr print --events jdk.GarbageCollection /tmp/incident.jfr | head
jfr summary /tmp/incident.jfr
# анализ: JDK Mission Control (автоанализ, вкладки GC, Threads, Method Profiling, Allocations, I/O, Exceptions)

JFR пишет события JVM (GC, компиляции, safepoints, блокировки, аллокации, исключения, I/O, CPU по потокам) в кольцевой буфер. Свои события — jdk.jfr.Event с аннотациями. JFR Event Streaming (Java 14+) позволяет потреблять события в реальном времени из того же процесса. Spring Boot и Micrometer умеют отправлять метрики по событиям JFR.

21.6Самопроверка

Как найти в дампе потоков поток, который top -H показал с TID 1802?

  • По имени потока
  • По nid=1802 (в старых JDK — nid=0x70a в шестнадцатеричном)
  • По tid=0x…
  • Никак
tid — адрес структуры JVM, nid — id потока ОС.

Почему CPU-профиль не покажет, что запросы медленные из-за ожидания БД?

  • Профилировщик не видит JDBC
  • БД — другой процесс
  • Это ошибка инструмента
  • Ожидающий поток не тратит CPU и не попадает в CPU-сэмплы — нужен wall-clock профиль или события JFR по I/O
async-profiler -e wall.

Что означает ширина кадра во флеймграфе?

  • Долю сэмплов, в которых метод был на стеке (включая вызванные им)
  • Время вызова в мс по порядку
  • Число вызовов
  • Размер метода
Ось X — не время по порядку, а агрегированная доля.

Почему стоит держать JFR включённым постоянно?

  • Он ускоряет приложение
  • Он заменяет логи
  • При накладных ~1% он сохраняет данные за последние часы, и после инцидента можно снять запись постфактум
  • Он нужен для GC
Самописец полезен, когда уже включён до аварии.
Сервис «завис»: HTTP не отвечает, CPU 0%. Ваши действия?

Снять 2–3 дампа потоков с интервалом. Посмотреть потоки обработки запросов: все ждут? чего — пула соединений (Hikari borrow), блокировки (BLOCKED, waiting to lock — найти владельца), ответа внешнего сервиса (socketRead без таймаута), CompletableFuture.get без таймаута? Проверить секцию deadlock. Проверить GC (не идёт ли бесконечный Full GC — тогда CPU не 0). Исправление: таймауты везде, ограниченные пулы, устранение цикла блокировок.

Чем async-profiler лучше «классических» профилировщиков на JVMTI?

Нет проблемы safepoint bias: классические сэмплируют стеки только в safepoint, искажая картину; async-profiler использует AsyncGetCallTrace и perf_events, видит нативный код, ядро, JIT и GC; низкие накладные расходы, режимы cpu/wall/alloc/lock/itimer, вывод флеймграфом. JFR тоже не имеет safepoint bias для профилирования методов.
