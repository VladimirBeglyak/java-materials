Сборка мусора: основы

Сборщик мусора не ищет мусор — он ищет живое: всё, до чего можно дойти по ссылкам от корней, а остальное объявляет свободным. Поверх этой идеи построены все сборщики JVM: пометка, очистка, уплотнение, копирование, поколения, барьеры записи, safepoints и конкурентная пометка. В симуляторе вы сами пометите граф объектов и увидите, почему конкурентная сборка без барьеров теряет живые объекты.

12.1Достижимость и корни

Корни (GC roots) — ссылки, которые живы по определению: локальные переменные и операнды в кадрах стеков всех потоков, статические поля загруженных классов, ссылки из JNI-кода, объекты-мониторы удерживаемых блокировок, сами объекты Thread, внутренние структуры JVM. Объект жив, если до него есть путь от корня. Циклические ссылки (A ↔ B) не мешают: если до цикла нет пути от корней, оба — мусор. Подсчёта ссылок в JVM нет.

12.4Поколения

Слабая гипотеза поколений: большинство объектов умирает молодыми (временные строки, DTO, итераторы), а пережившие несколько сборок живут долго (кэши, сессии, синглтоны). Поэтому куча делится:

Путь объекта через поколения
Eden
новые объекты
Survivor S0 / S1
выжившие, age 1..15
Old
долгоживущие

Все объекты рождаются в eden (кроме огромных).

Eden заполнен → молодая (minor) сборка: живые объекты из eden и одного survivor копируются в другой survivor, возраст +1. Eden освобождается целиком — 95% его содержимого обычно мусор, и копировать почти нечего.

Объект, переживший порог сборок, или не поместившийся в survivor, продвигается в старое поколение. Преждевременное продвижение (survivor мал, всплеск выделений) засоряет old объектами, которые скоро умрут.

Старое поколение собирается редко и другими алгоритмами (конкурентная пометка в G1, полное уплотнение в Parallel). Задача тюнинга — чтобы туда попадали только действительно долгоживущие объекты.

Ссылки из старого в молодое: card table и барьер записи

Молодая сборка не сканирует всё старое поколение, но старый объект может ссылаться на молодой (кэш, в который положили новый объект) — такая ссылка тоже корень. Поэтому каждая запись ссылки в поле (putfield, aastore) сопровождается барьером записи: несколько инструкций, помечающих «грязной» карту (512 байт кучи) в card table. Молодая сборка сканирует только грязные карты. G1 расширяет это до remembered sets на регион.

12.5Остановка мира и safepoints

Чтобы двигать объекты и обновлять ссылки, потоки приложения («мутаторы») должны остановиться в известных точках — safepoints, где JVM знает, в каких регистрах и слотах лежат ссылки (по картам oop maps от JIT). Пауза = время дойти всем потокам до safepoint (time-to-safepoint) + работа GC. Подробности — тема 18.

12.6Конкурентная пометка и трёхцветная абстракция

Современные сборщики помечают кучу параллельно с работой приложения. Опасность: пока GC сканирует, мутатор меняет ссылки. Классическая потеря объекта требует двух условий одновременно:

  1. мутатор записывает ссылку на белый объект W в уже чёрный (просканированный) объект;
  2. и удаляет последний путь к W от серых объектов.

Тогда W останется белым и будет освобождён, хотя он жив. Барьеры ломают одно из условий:

SATB (snapshot-at-the-beginning)

Барьер перед записью запоминает старое значение поля (удаляемую ссылку) и помечает его серым. Всё, что было живо в начале пометки, будет помечено. Плавающий мусор — объекты, умершие во время пометки, — доживёт до следующего цикла. Используют G1, Shenandoah.

Incremental update

Барьер после записи помечает новую ссылку (или делает чёрный объект снова серым), и GC пересканирует такие объекты в финальной паузе. Использовал CMS. ZGC использует цветные указатели и барьеры чтения (тема 13).

12.7Практикум: пишем и запускаем

Сборщик нельзя «увидеть» напрямую, но можно поставить на объект датчик — WeakReference: она не мешает сборке и становится пустой, когда объект собран. С этим датчиком и логами GC проверим достижимость, поколения и safepoints. Модуль IDEA — ch12.

Код набирайте руками — так он запоминается. Перед запуском запишите предсказание в поле «Ваш прогноз», затем сверьтесь с реальным выводом (снят на JDK 25.0.2; адреса, времена и хэши у вас будут другими). Как подготовить окружение — на странице курса.

Лаба 12.1Достижимость: что соберут, а что нет20 мин

Проверить на живом GC: циклические ссылки не мешают сборке, статические поля и локальные переменные — корни.

  1. Создайте файл Reach.java:
    import java.lang.ref.WeakReference;

public class Reach {
    static class Node { Node next; byte[] payload = new byte[1024]; }
    static Object root;

    static boolean collected(WeakReference<?> probe) {
        for (int i = 0; i < 5 && probe.get() != null; i++) System.gc();
        return probe.get() == null;
    }

    public static void main(String[] args) {
        // 1. цикл a <-> b без внешних ссылок
        Node a = new Node(), b = new Node();
        a.next = b; b.next = a;
        var p1 = new WeakReference<>(a);
        a = null; b = null;
        System.out.println("1. цикл собран:              " + collected(p1));

        // 2. объект в статическом поле
        root = new Node();
        var p2 = new WeakReference<>(root);
        System.out.println("2. статическое поле собрано: " + collected(p2));

        // 3. объект, достижимый только через WeakReference
        var p3 = new WeakReference<>(new Node());
        System.out.println("3. только weak собран:       " + collected(p3));

        // 4. локальная переменная, которая ещё используется ниже
        Node local = new Node();
        var p4 = new WeakReference<>(local);
        System.out.println("4. живая локальная собрана:  " + collected(p4));
        System.out.println("   (local ещё нужна: " + local.payload.length + ")");
    }
}
  2. Запишите для каждого пункта true/false.
    javac Reach.java
java Reach
    Вывод (JDK 25.0.2)
    1. цикл собран:              true
2. статическое поле собрано: false
3. только weak собран:       true
4. живая локальная собрана:  false
   (local ещё нужна: 1024)

    1 — true: трассирующий GC ищет пути от корней; цикл, до которого не дойти, — мусор (подсчёт ссылок здесь ошибся бы). 2 — false: статическое поле загруженного класса — корень. 3 — true: слабая ссылка не удерживает. 4 — false: локальная переменная в активном кадре — корень, пока она ещё понадобится.

Поэкспериментируйте
  • Уберите последнюю строку System.out.println(" (local ещё нужна…") и прогоните метод в цикле много раз, чтобы его скомпилировал JIT. Может ли пункт 4 стать true?
    Да. JIT знает, где переменная используется в последний раз, и после этого не считает её корнем — объект может быть собран раньше, чем закончится метод. Поэтому для «удержания» объекта в Java 9+ есть Reference.reachabilityFence(obj).

  1. Создайте файл Ages.java:
    import java.util.ArrayDeque;

public class Ages {
    public static void main(String[] args) {
        int window = Integer.parseInt(args.length > 0 ? args[0] : "3000");
        var recent = new ArrayDeque<byte[]>();                // «последние запросы» — живут недолго, но не мгновенно
        for (int i = 0; i < 30_000; i++) {
            recent.addLast(new byte[1024]);
            if (recent.size() > window) recent.removeFirst();
            for (int j = 0; j < 20; j++) {
                byte[] garbage = new byte[1024];             // умирает сразу
            }
        }
        System.out.println("готово, в окне " + recent.size());
    }
}

До 15 они не доживают: JVM после каждой сборки пересчитывает порог (new threshold) так, чтобы выжившие помещались в половину survivor (Desired survivor size), и когда выживших много, порог падает до 1–2. Тогда объекты продвигаются в old раньше, чем умрут, — занятость после сборки растёт (5M → 11M): это «преждевременное продвижение», мусор, который потом придётся убирать дорогой сборкой старого поколения.

Поэкспериментируйте
  • Добавьте -XX:MaxTenuringThreshold=0. Что изменится в логе?
    Таблица возрастов опустеет (new threshold 0): всё, что пережило одну молодую сборку, сразу уходит в old. Old растёт быстрее, полные сборки наступают раньше.
  • Передайте аргумент 20000 (окно в 20 МБ).
    Выжившие больше не помещаются в survivor и потоком идут в old, старое поколение заполняется умирающими объектами — в логе появляется Pause Full, на порядок дороже молодых пауз.

12.8Самопроверка

Два объекта ссылаются друг на друга, других ссылок на них нет. Соберёт ли их GC?

  • Нет, у них ненулевой счётчик ссылок
  • Да: они недостижимы от корней
  • Только Full GC
  • Только если вызвать System.gc()
JVM использует трассировку достижимости, а не подсчёт ссылок.

Почему молодая сборка обычно быстрая даже при большом eden?

  • Она не останавливает потоки
  • Eden маленький
  • Она не трогает объекты
  • Копируются только живые объекты, а их в eden обычно единицы процентов
Стоимость копирующего сборщика пропорциональна живым данным.

Зачем барьер записи при присваивании ссылки в поле?

  • Чтобы GC знал о ссылках из старого поколения в молодое (card table) и о ссылках, изменённых во время конкурентной пометки
  • Для синхронизации потоков
  • Для проверки null
  • Для подсчёта ссылок
Цена — несколько инструкций на каждую запись ссылки.

Что из перечисленного — GC root?

  • Любой объект в старом поколении
  • Объект с переопределённым finalize()
  • Локальная переменная в кадре стека работающего потока
  • Объект, на который ссылается другой объект
А также статические поля, JNI-ссылки, мониторы, потоки.
Объясните, как работает поколенческий сборщик.

Куча делится на молодое (eden + два survivor) и старое поколения. Объекты рождаются в eden. Молодая сборка (с остановкой) копирует живые из eden и survivor в другой survivor, увеличивая возраст; старые по возрасту или при переполнении продвигаются в old. Ссылки old → young отслеживаются барьером записи через card table и служат дополнительными корнями. Старое поколение собирается реже: пометка (часто конкурентная) и уплотнение или эвакуация.

Почему конкурентный GC нуждается в барьерах, а stop-the-world — нет?

При STW граф объектов не меняется во время пометки. При конкурентной пометке приложение меняет ссылки, и без перехвата этих изменений GC может не увидеть живой объект (чёрный → белый при удалении серого пути) и освободить его. Барьеры (SATB, incremental update, барьеры чтения) сообщают GC об изменениях. Плата — инструкции на каждую запись/чтение ссылки и плавающий мусор.
