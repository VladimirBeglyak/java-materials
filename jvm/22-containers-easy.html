22.1Что JVM видит в контейнере

Раньше JVM смотрела на всю машину: видела 64 ГБ и 32 ядра, хотя контейнеру разрешено 2 ГБ и 2 ядра, — и выбирала неверную кучу и число потоков. Современные версии читают лимиты контейнера (cgroups) и считают от них: максимум кучи по умолчанию — четверть лимита памяти, число «процессоров» — по квоте CPU.

Главная мысль Современная JVM видит лимиты контейнера, но значения по умолчанию лучше переопределить.

22.2Флаги под лимиты пода

  • -XX:MaxRAMPercentage=70 — куча в процентах от лимита: примерно 60–75%, остальное — Metaspace, стеки, код, буферы (глава 09).
  • -XX:ActiveProcessorCount — если квота дробная или хочется явно задать число ядер для пулов и GC.
  • Лимит памяти пода = request памяти: так под не будет внезапно вытеснен при нехватке памяти на узле.
Главная мысль Куча — проценты от лимита с запасом; память пода — limit = request.

22.3Троттлинг CPU

Лимит 1 CPU, а сервис «подвисает» на 70 мс
квота: 100 мс процессорного времени на каждые 100 мспришёл всплеск запросов + сборка мусора в 4 потока
за первые 25 мс реального времени израсходовано 100 мс квотыостальные 75 мс периода контейнер стоит — его не пускают к процессорув графиках средняя загрузка 40%, а p99 задержки — с провалами
лечение: больше CPU limit или убрать limit, меньше потоков GC, следить за метрикой throttling

Лимит считается за короткие периоды.

Многопоточная работа быстро тратит квоту.

До конца периода контейнер ждёт.

Среднее нормальное, хвосты задержек плохие.

Главная мысль CPU limit режет работу периодами — отсюда невидимые паузы. Смотрите метрику throttling.

22.4Образ

Хороший образ: базовый слой только с JRE (или свой runtime от jlink, глава 08), приложение разложено на слои — сначала редко меняющиеся библиотеки, потом ваш код (тогда при обновлении скачивается маленький слой), запуск не от root, фиксированные версии. Spring Boot и инструменты вроде Jib умеют делать это автоматически.

Главная мысль Маленький базовый образ, слои по частоте изменений, не root.

22.5Корректное завершение пода

При остановке Kubernetes посылает процессу SIGTERM и ждёт (по умолчанию 30 секунд), потом SIGKILL. За это время сервис должен перестать принимать новые запросы, доделать текущие и закрыть соединения. Важно, чтобы Java была главным процессом контейнера (PID 1) или сигнал до неё доходил — иначе она узнает об остановке только по SIGKILL. В Spring Boot для этого есть graceful shutdown.

Главная мысль SIGTERM → дообработать и закрыться за отведённое время. Сигнал должен доходить до JVM.

22.7Проверьте себя

Лимит пода 2 ГБ. Какой MaxRAMPercentage разумен?

  • 100
  • 25 (по умолчанию) всегда
  • около 70: остальное нужно JVM вне кучи
  • 150
Запас на Metaspace, стеки, код.

Средняя загрузка CPU 40%, а задержки скачут на десятки мс. Что проверить?

  • троттлинг CPU в контейнере
  • DNS
  • размер диска
  • версию Kubernetes
Квота тратится всплесками.

Что Kubernetes делает при остановке пода?

  • сразу SIGKILL
  • перезагружает узел
  • ничего
  • шлёт SIGTERM, ждёт grace period, потом SIGKILL
Время на аккуратное завершение.

Зачем раскладывать образ на слои «библиотеки отдельно, код отдельно»?

  • для безопасности
  • при обновлении кода скачивается только маленький слой
  • так требует Docker
  • для скорости JIT
Библиотеки меняются редко.

Почему важно, чтобы сигнал SIGTERM доходил до JVM?

  • иначе образ не соберётся
  • иначе не запустится JIT
  • иначе приложение не успеет завершиться аккуратно и будет убито SIGKILL
  • не важно
Например, если её запускает shell-скрипт без exec.
