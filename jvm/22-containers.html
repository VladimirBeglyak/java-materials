JVM в контейнерах

Большинство Java-сервисов работает в Docker и Kubernetes, и почти все «странные» проблемы там — несоответствие того, что видит JVM, и ограничений контейнера: OOM killer без ошибки в логе, троттлинг CPU с паузами GC в сотни миллисекунд, Serial GC в поде с 1 CPU, SIGTERM, который не доходит до Java. Разбираем, как JVM читает cgroups, как подобрать флаги под лимиты (с генератором), образ и корректное завершение.

22.1Что JVM видит в контейнере

С JDK 10 (и 8u191) включён -XX:+UseContainerSupport: JVM читает ограничения cgroups (v1 и v2) вместо параметров всей машины.

22.3Троттлинг CPU: невидимые паузы

Квота CFS работает периодами по 100 мс: при limits.cpu: 2 контейнер может потратить 200 мс процессорного времени за период — на всех потоках вместе. Пауза G1 параллельно на 8 потоках сжигает квоту за 25 мс, и весь контейнер замораживается до конца периода — до 75 мс сверх паузы. Признаки: метрика container_cpu_cfs_throttled_periods_total растёт, задержки скачут при низкой средней загрузке CPU.

Что делать Число потоков GC/JIT согласовать с лимитом (эргономика это делает, если лимит задан); не ставить лимит CPU ниже реальных всплесков; многие команды задают только requests.cpu без limits.cpu для latency-чувствительных сервисов, но явно указывают -XX:ActiveProcessorCount, чтобы JVM не видела весь узел.

COPY . .
RUN ./mvnw -q package -DskipTests \
 && java -Djarmode=tools -jar target/app.jar extract --layers --launcher --destination /app

COPY --from=build /app/application/ ./

ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]

22.5Корректное завершение пода

→

→
SIGKILL

Под помечается Terminating и удаляется из списка адресов сервиса. Но балансировщики узнают об этом не мгновенно — ещё несколько секунд на под могут приходить новые запросы.

Поэтому добавляют preStop с короткой паузой (sleep 5), чтобы новые запросы перестали приходить до начала остановки.

SIGTERM получает PID 1 контейнера. Если ENTRYPOINT в shell-форме (sh -c "java …"), PID 1 — оболочка, и она не передаст сигнал Java: процесс будет убит через grace period без корректного завершения. Используйте exec-форму или exec java … в скрипте, либо tini.

JVM запускает shutdown hooks; Spring Boot с server.shutdown=graceful перестаёт принимать запросы, дожидается текущих (spring.lifecycle.timeout-per-shutdown-phase), закрывает пулы соединений, коммитит offset Kafka.

Если за terminationGracePeriodSeconds (по умолчанию 30 с) процесс не завершился — SIGKILL. Сумма preStop + время graceful shutdown должна быть меньше grace period.

22.6Практикум: пишем и запускаем

Всё, что JVM «видит» в контейнере, проверяется одной командой docker run. Нужен Docker Desktop (или Docker на Linux) и образ eclipse-temurin:25-jdk (~200 МБ, скачается при первом запуске). Команды одинаковы для PowerShell и bash; в cmd вместо ${PWD} пишите %cd%.

Код набирайте руками — так он запоминается. Перед запуском запишите предсказание в поле «Ваш прогноз», затем сверьтесь с реальным выводом (снят на JDK 25.0.2; адреса, времена и хэши у вас будут другими). Как подготовить окружение — на странице курса.

Лаба 22.1Что JVM видит при разных лимитах20 мин

Сравнить память и процессоры, которые JVM определяет без лимитов и с лимитами cgroups.

  1. docker run --rm eclipse-temurin:25-jdk java -XshowSettings:system -version
docker run --rm eclipse-temurin:25-jdk java -Xlog:gc:stdout -XshowSettings:vm -version
    Вывод (JDK 25.0.2)
        Provider: cgroupv2
    Effective CPU Count: 18
    Memory Limit: Unlimited
[0.003s][info][gc] Using G1
    Max. Heap Size (Estimated): 3.84G
    Using VM: OpenJDK 64-Bit Server VM

    -XshowSettings:system показывает, что JVM прочитала из cgroups, -XshowSettings:vm — итоговый размер кучи, а первая строка лога GC (-Xlog:gc:stdout) называет выбранный сборщик. Без лимитов контейнер видит всю память виртуальной машины Docker Desktop.

  2. Запустим с -m 512m --cpus=1.5. Какие будут Max. Heap Size, число CPU и сборщик?
    docker run --rm -m 512m --cpus=1.5 eclipse-temurin:25-jdk java -XshowSettings:system -version
docker run --rm -m 512m --cpus=1.5 eclipse-temurin:25-jdk java -Xlog:gc:stdout -XshowSettings:vm -version
    Вывод (JDK 25.0.2)
        Provider: cgroupv2
    Effective CPU Count: 2
    Memory Limit: 512.00M
[0.006s][info][gc] Using Serial
    Max. Heap Size (Estimated): 123.75M
    Using VM: OpenJDK 64-Bit Server VM

    Память контейнера — 512 МБ, куча по умолчанию — 25% от неё: 128 МБ. CPU — 2 (квота 1,5 округляется вверх). Сборщик — Serial: при памяти меньше 1792 МБ машина не считается «серверной» (как в лабе 1.2). Это самая частая причина «почему в Kubernetes у нас SerialGC».

  3. Типичная настройка сервиса — процент памяти и явный сборщик:
    docker run --rm -m 512m --cpus=1.5 eclipse-temurin:25-jdk java -XX:MaxRAMPercentage=75 -XX:+UseG1GC -Xlog:gc:stdout -XshowSettings:vm -version
    Вывод (JDK 25.0.2)
    [0.003s][info][gc] Using G1
    Max. Heap Size (Estimated): 384.00M
    Using VM: OpenJDK 64-Bit Server VM
Лаба 22.2OOM killer: код 137 без OutOfMemoryError20 мин

Увидеть, как ядро Linux убивает JVM, которой разрешили кучу больше лимита контейнера, — и как это выглядит снаружи.

  1. Создайте файл Eat.java:
    import java.util.ArrayList;
import java.util.List;

public class Eat {
    public static void main(String[] args) {
        List<byte[]> keep = new ArrayList<>();
        for (int mb = 1; ; mb++) {
            byte[] chunk = new byte[1 << 20];
            for (int i = 0; i < chunk.length; i += 4096) chunk[i] = 1;   // реально занять страницы
            keep.add(chunk);
            if (mb % 50 == 0) System.out.println("занято " + mb + " МБ");
        }
    }
}
  2. Контейнер с -m 256m, а JVM мы разрешили -Xmx1g. Чем закончится программа?
    docker run --rm -m 256m -v "${PWD}:/app" -w /app eclipse-temurin:25-jdk java -Xmx1g Eat.java
echo $LASTEXITCODE    # PowerShell; в bash: echo $?
    Вывод (JDK 25.0.2)
    занято 50 МБ
занято 100 МБ
занято 150 МБ
занято 200 МБ
занято 250 МБ
занято 300 МБ
занято 350 МБ
занято 400 МБ
код возврата: 137

    JVM не знает, что физически памяти меньше, и продолжает расти. Когда RSS процесса упрётся в 256 МБ, ядро пошлёт SIGKILL: процесс исчезает мгновенно, без OutOfMemoryError, без дампа и без строчки в логе приложения. Снаружи — только код возврата 137 (128 + 9) и OOMKilled: true у контейнера.

  3. Теперь без явного -Xmx — пусть JVM сама посчитает кучу от лимита:
    docker run --rm -m 256m -v "${PWD}:/app" -w /app eclipse-temurin:25-jdk java -XX:MaxRAMPercentage=75 Eat.java
    Вывод (JDK 25.0.2)
    занято 50 МБ
занято 100 МБ
занято 150 МБ
Exception in thread "main" java.lang.OutOfMemoryError: Java heap space
код возврата: 1

    Теперь падение «правильное»: OutOfMemoryError: Java heap space — его видно в логах, можно снять дамп (-XX:+HeapDumpOnOutOfMemoryError). 25% запаса оставлены под metaspace, потоки, code cache и буферы — не-кучевую память.

Лаба 22.3Корректное завершение: SIGTERM и shutdown hook15 мин

Проверить, что docker stop (как и удаление пода) доставляет SIGTERM в JVM и hook успевает отработать — и как это ломается, если java запущена через shell.

  1. Создайте файл Graceful.java:
    public class Graceful {
    public static void main(String[] args) throws Exception {
        Runtime.getRuntime().addShutdownHook(new Thread(() -> {
            System.out.println("SIGTERM получен: дописываю буферы, закрываю пул соединений…");
            try { Thread.sleep(500); } catch (InterruptedException ignored) { }
            System.out.println("завершено чисто");
        }));
        System.out.println("работаю, pid в контейнере = " + ProcessHandle.current().pid());
        Thread.sleep(600_000);
    }
}
    docker run -d --name graceful -v "${PWD}:/app" -w /app eclipse-temurin:25-jdk java Graceful.java
docker stop graceful
docker logs graceful
docker rm graceful
    Вывод (JDK 25.0.2)
    работаю, pid в контейнере = 1
SIGTERM получен: дописываю буферы, закрываю пул соединений…
завершено чисто
  2. Запустите то же через shell: sh -c "java Graceful.java". Сколько займёт docker stop и выполнится ли hook?
    docker run -d --name graceful2 -v "${PWD}:/app" -w /app eclipse-temurin:25-jdk sh -c "java Graceful.java; echo java вышла"
docker stop graceful2
docker logs graceful2
docker inspect graceful2 --format "{{.State.ExitCode}}"
docker rm graceful2
    Вывод (JDK 25.0.2)
    docker stop занял 3 с
работаю, pid в контейнере = 7
137

    Интересная деталь: в образе Temurin sh — это dash, который для последней команды иногда сам делает exec. Здесь после java стоит ещё одна команда, поэтому exec невозможен — классический сценарий из реальных entrypoint-скриптов.

    PID 1 в контейнере теперь sh, а не java. Он не пересылает SIGTERM дочернему процессу, и по истечении таймаута docker stop (по умолчанию до 10 с) контейнер получает SIGKILL: hook не выполнится, ни «завершено чисто», ни «java вышла» в логах нет, код выхода — 137. Поэтому в Dockerfile пишут exec-форму ENTRYPOINT ["java", "-jar", "app.jar"] или exec java … в скрипте.

22.7Самопроверка

Под с limits.cpu: 500m. Какой GC выберет JVM по умолчанию?

  • G1
  • ZGC
  • Serial: ActiveProcessorCount = 1 → машина «клиентского класса»
  • Parallel
Задайте сборщик явно или ActiveProcessorCount=2.

Почему при низкой средней загрузке CPU у сервиса в контейнере бывают всплески задержек по 50–100 мс?

  • Троттлинг CFS: параллельная работа (GC) исчерпывает квоту периода, и контейнер замораживается до конца периода
  • Медленная сеть
  • JIT отключён
  • Kubernetes перезапускает под
Смотрите метрики throttled periods.

Shutdown hooks не выполняются при остановке пода. Вероятная причина?

  • Hooks не работают в Docker
  • ENTRYPOINT в shell-форме: SIGTERM получает оболочка, а не java
  • Мало памяти
  • Spring не поддерживает hooks
Exec-форма или exec в скрипте.

Какой параметр Kubernetes определяет объём памяти, от которого JVM считает MaxRAMPercentage?

  • requests.memory
  • Объём памяти узла
  • Размер образа
  • limits.memory (memory.max в cgroup)
Без лимита JVM видит память узла — опасно.
Как настроить JVM-сервис для Kubernetes «по умолчанию правильно»?

Лимит памяти и MaxRAMPercentage 65–75 (или явный Xmx) с запасом под не-кучу; явный сборщик (G1 для большинства, ZGC для больших куч и жёстких задержек); ActiveProcessorCount при дробных лимитах CPU; ExitOnOutOfMemoryError + дамп в том; логи GC; exec-форма ENTRYPOINT, graceful shutdown с preStop; startupProbe с запасом на старт и прогрев, readiness — после прогрева; не-root пользователь, слои образа, по возможности jlink/AOT cache.

Под перезапускается с кодом 137. Как понять причину?

137 = 128 + 9 (SIGKILL). Варианты: OOMKilled (kubectl describe pod → Last State: OOMKilled; RSS превысил limits.memory — не-кучевая память, слишком большая куча) или провал liveness-пробы/истёк grace period при остановке. Для OOMKilled — NMT и пересчёт памяти (тема 09), для проб — таймауты проб, длинные GC-паузы, троттлинг.
