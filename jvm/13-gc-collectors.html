Сборщики: Serial, Parallel, G1, ZGC, Shenandoah

В HotSpot пять продуктовых сборщиков, и каждый — свой компромисс между пропускной способностью, задержками и памятью. Разбираем, как устроен каждый: G1 с регионами и смешанными сборками — в живом симуляторе; ZGC с цветными указателями и барьерами чтения, дающий паузы меньше миллисекунды на терабайтных кучах; Shenandoah; Parallel для пакетной обработки. В конце — мастер выбора сборщика.

13.1Треугольник компромиссов

Пропускная способность

Доля времени CPU на полезную работу, а не на GC. Максимум — у сборщиков с остановкой мира: никаких барьеров и конкурентных потоков.

Задержка

Длина пауз (p99, max). Минимум — у конкурентных сборщиков, которые почти всё делают параллельно с приложением.

Память

Сколько кучи и служебных структур нужно сверх живых данных. Конкурентным сборщикам нужен запас: приложение выделяет память, пока идёт сборка.

13.3G1: регионы и смешанные сборки

G1 (по умолчанию с Java 9) делит кучу на ~2048 регионов одинакового размера (1–32 МБ). Регион в каждый момент — eden, survivor, old, humongous или свободен. Поколения — это просто множества регионов. Каждая пауза эвакуирует (копирует живое) из набора регионов — collection set, подобранного так, чтобы уложиться в цель -XX:MaxGCPauseMillis (200 мс по умолчанию).

Симулятор G1 (48 регионов)
E — eden, S — survivor, O — old (число — % живых данных после пометки), H — humongous; рамка — регион в collection set
  • Remembered sets: у каждого региона — набор карт других регионов, которые на него ссылаются; позволяет эвакуировать любой набор регионов, не сканируя всю кучу. Поддерживаются барьером записи и потоками уточнения (refinement).
  • IHOP (Initiating Heap Occupancy Percent) — порог занятости, при котором стартует конкурентная пометка; адаптивный по умолчанию.
  • Full GC в G1 (параллельный mark-compact всей кучи) — признак проблемы: пометка не успела, эвакуации не хватило места («to-space exhausted»), фрагментация humongous.

13.4ZGC: паузы меньше миллисекунды

ZGC (продуктовый с Java 15, поколенческий с Java 21, только поколенческий режим с Java 23) делает конкурентно всё, включая перемещение объектов. Паузы не зависят от размера кучи и числа живых объектов — обычно десятки–сотни микросекунд — на кучах от сотен МБ до 16 ТБ.

Как ZGC перемещает объект, пока приложение его читает
Ссылка в поле
0x…A000 [цвет: good]цвет устарел
Страница-источник
объект по адресу A
Страница-приёмник
копия по адресу B
Таблица пересылки
A → B

ZGC хранит метаданные GC прямо в неиспользуемых битах 64-битной ссылки — «цвет». По цвету барьер мгновенно понимает, актуальна ли ссылка для текущей фазы. Следствие: ZGC не использует сжатые указатели (ссылки 8 байт).

При каждой загрузке ссылки из поля JIT-код проверяет её цвет. Если цвет «хороший» — продолжает без задержки (одна инструкция test + условный переход). Если нет — медленный путь барьера.

Короткая пауза переключает, какой цвет считается хорошим — все ссылки в куче логически устаревают, ничего не перезаписывая. GC выбирает страницы с наибольшей долей мусора и начинает конкурентно копировать из них живые объекты.

Поток приложения загрузил устаревшую ссылку на A. Барьер видит, что объект на перемещаемой странице: если GC ещё не скопировал объект — поток копирует его сам и регистрирует A → B в таблице пересылки (CAS: при гонке побеждает одна копия).

Барьер возвращает адрес B и перезаписывает поле, откуда ссылка была загружена, исправленным значением с хорошим цветом (self-healing). Остальные устаревшие ссылки исправит следующая фаза пометки. Страница-источник освобождается, как только все её живые объекты скопированы — память можно переиспользовать ещё до исправления всех ссылок.

Shenandoah (Red Hat, в OpenJDK с Java 12/15) решает ту же задачу без цветных указателей: барьеры при загрузке ссылок (load reference barrier) и конкурентная эвакуация с пересылкой через заголовок объекта; поддерживает сжатые указатели, поколенческий режим — с Java 24 (экспериментально → продуктово в 25). Epsilon (-XX:+UseEpsilonGC) не собирает мусор вовсе — для тестов производительности и короткоживущих задач.

13.6Практикум: пишем и запускаем

Лучший способ понять разницу сборщиков — прогнать один и тот же код под каждым и измерить то, что чувствует приложение: паузы. Напишем мини-аналог jHiccup: поток, который каждую миллисекунду засыпает и замеряет, насколько проснулся позже. Модуль IDEA — ch13.

Код набирайте руками — так он запоминается. Перед запуском запишите предсказание в поле «Ваш прогноз», затем сверьтесь с реальным выводом (снят на JDK 25.0.2; адреса, времена и хэши у вас будут другими). Как подготовить окружение — на странице курса.

Лаба 13.1Один код — четыре сборщика30 мин

Сравнить Serial, Parallel, G1 и ZGC по максимальной «икоте» приложения, числу и суммарному времени сборок.

  1. Создайте файл GcBench.java:
    import java.lang.management.ManagementFactory;
import java.util.HashMap;
import java.util.Map;
import java.util.Random;

public class GcBench {
    static volatile long maxHiccupNanos;

    public static void main(String[] args) throws Exception {
        Thread meter = new Thread(() -> {
            while (true) {
                long t = System.nanoTime();
                try { Thread.sleep(1); } catch (InterruptedException e) { return; }
                long late = System.nanoTime() - t - 1_000_000;
                if (late > maxHiccupNanos) maxHiccupNanos = late;
            }
        });
        meter.setDaemon(true);
        meter.start();

        // «кэш» на ~300 МБ живых данных, в котором постоянно заменяются записи
        Map<Integer, byte[]> cache = new HashMap<>();
        Random rnd = new Random(42);
        long end = System.currentTimeMillis() + 6000, ops = 0;
        while (System.currentTimeMillis() < end) {
            cache.put(rnd.nextInt(300_000), new byte[1024]);
            for (int i = 0; i < 10; i++) { byte[] tmp = new byte[256]; }
            ops++;
        }

        long count = 0, time = 0;
        for (var gc : ManagementFactory.getGarbageCollectorMXBeans()) { count += gc.getCollectionCount(); time += gc.getCollectionTime(); }
        String names = ManagementFactory.getGarbageCollectorMXBeans().stream().map(g -> g.getName()).toList().toString();
        System.out.printf("%-58s операций: %,d   сборок: %d, суммарно %d мс   max hiccup: %.1f мс%n",
                names, ops, count, time, maxHiccupNanos / 1e6);
    }
}
  2. Запустите четыре раза с разными сборщиками и одинаковой кучей (в IDEA удобно сделать четыре конфигурации запуска — Edit Configurations → Copy):
    javac GcBench.java
java -Xmx1g -XX:+UseSerialGC GcBench
java -Xmx1g -XX:+UseParallelGC GcBench
java -Xmx1g -XX:+UseG1GC GcBench
java -Xmx1g -XX:+UseZGC GcBench
    Вывод (JDK 25.0.2)
    [Copy, MarkSweepCompact]                                   операций: 9,433,747   сборок: 42, суммарно 3833 мс   max hiccup: 173.4 мс
[PS MarkSweep, PS Scavenge]                                операций: 22,183,614   сборок: 178, суммарно 2411 мс   max hiccup: 63.4 мс
[G1 Young Generation, G1 Concurrent GC, G1 Old Generation] операций: 20,574,002   сборок: 291, суммарно 1899 мс   max hiccup: 39.9 мс
[ZGC Minor Cycles, ZGC Minor Pauses, ZGC Major Cycles, ZGC Major Pauses] операций: 13,102,688   сборок: 470, суммарно 7391 мс   max hiccup: 3.2 мс
  3. Расставьте сборщики по максимальной паузе и по числу выполненных операций (пропускной способности) до того, как смотреть вывод.

    Цифры сильно зависят от машины: на 2–4 ядрах ZGC и G1 теряют больше пропускной способности, на 16+ — меньше. Счётчик «сборок» у ZGC и G1 включает конкурентные циклы, а «суммарно мс» у ZGC — время циклов, а не пауз.

    По паузам: ZGC — единицы миллисекунд (паузы не зависят от объёма живых данных), G1 — десятки мс, Serial и Parallel — сотни мс: старое поколение они собирают с остановкой мира по всей куче. По операциям картина иная: Parallel и G1 впереди, ZGC — заметно ниже (за низкие паузы он платит процессорным временем фоновых потоков и барьерами), Serial — последний: на 1 ГБ кучи его однопоточные сборки отнимают больше всего времени. Это и есть «треугольник компромиссов».

Поэкспериментируйте
  • Увеличьте живые данные: замените 300_000 на 700_000 (≈ 700 МБ из 1 ГБ).
    Serial и Parallel начнут делать почти непрерывные полные сборки, G1 — смешанные и, возможно, Full GC, ZGC может уйти в «Allocation Stall» (потоки ждут, пока сборщик освободит память). Конкурентному сборщику нужен запас кучи.
  • Добавьте к G1 -XX:MaxGCPauseMillis=20.
    G1 уменьшит молодое поколение, чтобы уложиться в цель: пауз станет больше, каждая — короче. Цель — желание, а не гарантия.
Лаба 13.2Регионы G1 и humongous-объекты15 мин

Узнать размер региона G1 и увидеть, как большие массивы попадают в особые «огромные» регионы.

  1. Создайте файл Humongous.java:
    import java.util.ArrayList;
import java.util.List;

public class Humongous {
    public static void main(String[] args) {
        List<byte[]> keep = new ArrayList<>();
        for (int i = 0; i < 30; i++) keep.add(new byte[600 * 1024]);   // 600 КБ — больше половины региона 1 МБ
        System.gc();
        System.out.println("массивов: " + keep.size());
    }
}

    IDEAVM options: -XX:+UseG1GC -Xmx128m -XX:G1HeapRegionSize=1m -Xlog:gc,gc+heap=info

    javac Humongous.java
java -XX:+UseG1GC -Xmx128m -XX:G1HeapRegionSize=1m -Xlog:gc*=info Humongous

[0.037s][info][gc,heap        ] GC(0) Humongous regions: 30->30
[0.037s][info][gc             ] GC(0) Pause Full (System.gc()) 32M->31M(110M) 2.216ms

  2. Объект больше половины региона — humongous: он занимает регион(ы) целиком. Сколько памяти «потеряется» на 30 массивах по 600 КБ при регионе 1 МБ?

    Каждый массив занимает отдельный регион 1 МБ, из которого ~424 КБ не используется: ~12 МБ впустую на 18 МБ данных. В логе видно Humongous regions: 30->30. Лечится увеличением региона (G1HeapRegionSize=2m — массив станет обычным объектом) или изменением размеров буферов в коде.

Поэкспериментируйте
  • Поставьте -XX:G1HeapRegionSize=2m. Что станет со строкой Humongous regions?
    0: при регионе 2 МБ порог humongous — 1 МБ, массивы по 600 КБ — обычные объекты в eden/old.

13.7Самопроверка

Почему сборщик называется Garbage-First?

  • Сначала собирает молодое поколение
  • Удаляет мусор до пометки
  • В смешанных сборках выбирает старые регионы с наибольшей долей мусора — максимум освобождённой памяти за единицу паузы
  • Это просто имя
Доля живого известна после конкурентной пометки.

Как ZGC перемещает объекты без длинной паузы?

  • Конкурентно копирует, а барьер при загрузке ссылки находит новый адрес через таблицу пересылки и исправляет ссылку
  • Никогда не перемещает объекты
  • Останавливает только один поток
  • Использует подсчёт ссылок
Цветные указатели + load barriers + self-healing.

В логе G1 — «Pause Full (G1 Compaction Pause)». Что это значит?

  • Нормальная молодая сборка
  • Конкурентная фаза
  • Ошибка JVM
  • Аварийная полная сборка: пометка или эвакуация не успели — нужна настройка (размер кучи, IHOP, утечки, humongous)
В здоровом G1-приложении Full GC не должно быть.

Что такое humongous-объект в G1?

  • Объект, переживший 15 сборок
  • Объект больше половины региона: размещается сразу в старом поколении в смежных регионах
  • Объект с финализатором
  • Объект в metaspace
Большие массивы → humongous; помогает увеличение G1HeapRegionSize.
Сравните G1 и ZGC для сервиса с кучей 16 ГБ и требованием p99 < 50 мс.

G1 с MaxGCPauseMillis=20–50 обычно укладывается, но паузы растут при большом числе живых объектов в молодом поколении и на remark; при ошибках настройки — Full GC. Generational ZGC даёт паузы < 1 мс, но требует запаса кучи (конкурентная работа при высоком темпе выделения — иначе allocation stall) и немного больше CPU; ссылки 8 байт увеличат занятость кучи. Решение — нагрузочный тест обоих на реальном трафике с замером p99 и CPU.

Что такое allocation stall в ZGC и как его лечить?

Приложение выделяет память быстрее, чем ZGC успевает конкурентно освобождать, и потоку, которому негде выделить, приходится ждать окончания цикла — фактически пауза. Лечится запасом кучи (Xmx больше), снижением темпа выделения, большим числом конкурентных потоков GC (ConcGCThreads), с JDK 21 — поколенческим режимом, который собирает молодые объекты чаще и дешевле.
