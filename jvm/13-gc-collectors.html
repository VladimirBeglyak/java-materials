Сборщики: Serial, Parallel, G1, ZGC, Shenandoah

В HotSpot пять продуктовых сборщиков, и каждый — свой компромисс между пропускной способностью, задержками и памятью. 13.1Треугольник компромиссов

Пропускная способность

Доля времени CPU на полезную работу, а не на GC. Максимум — у сборщиков с остановкой мира: никаких барьеров и конкурентных потоков.

Задержка

Длина пауз (p99, max). Минимум — у конкурентных сборщиков, которые почти всё делают параллельно с приложением.

Память

Сколько кучи и служебных структур нужно сверх живых данных. Конкурентным сборщикам нужен запас: приложение выделяет память, пока идёт сборка.

13.3G1: регионы и смешанные сборки

G1 (по умолчанию с Java 9) делит кучу на ~2048 регионов одинакового размера (1–32 МБ). Регион в каждый момент — eden, survivor, old, humongous или свободен. Поколения — это просто множества регионов. Каждая пауза эвакуирует (копирует живое) из набора регионов — collection set, подобранного так, чтобы уложиться в цель -XX:MaxGCPauseMillis (200 мс по умолчанию).

Симулятор G1 (48 регионов)
E — eden, S — survivor, O — old (число — % живых данных после пометки), H — humongous; рамка — регион в collection set
  • Remembered sets: у каждого региона — набор карт других регионов, которые на него ссылаются; позволяет эвакуировать любой набор регионов, не сканируя всю кучу. Поддерживаются барьером записи и потоками уточнения (refinement).
  • IHOP (Initiating Heap Occupancy Percent) — порог занятости, при котором стартует конкурентная пометка; адаптивный по умолчанию.
  • Full GC в G1 (параллельный mark-compact всей кучи) — признак проблемы: пометка не успела, эвакуации не хватило места («to-space exhausted»), фрагментация humongous.

13.4ZGC: паузы меньше миллисекунды

ZGC (продуктовый с Java 15, поколенческий с Java 21, только поколенческий режим с Java 23) делает конкурентно всё, включая перемещение объектов. Паузы не зависят от размера кучи и числа живых объектов — обычно десятки–сотни микросекунд — на кучах от сотен МБ до 16 ТБ.

ZGC хранит метаданные GC прямо в неиспользуемых битах 64-битной ссылки — «цвет». По цвету барьер мгновенно понимает, актуальна ли ссылка для текущей фазы. Следствие: ZGC не использует сжатые указатели (ссылки 8 байт).

При каждой загрузке ссылки из поля JIT-код проверяет её цвет. Если цвет «хороший» — продолжает без задержки (одна инструкция test + условный переход). Если нет — медленный путь барьера.

Короткая пауза переключает, какой цвет считается хорошим — все ссылки в куче логически устаревают, ничего не перезаписывая. GC выбирает страницы с наибольшей долей мусора и начинает конкурентно копировать из них живые объекты.

Поток приложения загрузил устаревшую ссылку на A. Барьер видит, что объект на перемещаемой странице: если GC ещё не скопировал объект — поток копирует его сам и регистрирует A → B в таблице пересылки (CAS: при гонке побеждает одна копия).

Барьер возвращает адрес B и перезаписывает поле, откуда ссылка была загружена, исправленным значением с хорошим цветом (self-healing). Остальные устаревшие ссылки исправит следующая фаза пометки. Страница-источник освобождается, как только все её живые объекты скопированы — память можно переиспользовать ещё до исправления всех ссылок.

Shenandoah (Red Hat, в OpenJDK с Java 12/15) решает ту же задачу без цветных указателей: барьеры при загрузке ссылок (load reference barrier) и конкурентная эвакуация с пересылкой через заголовок объекта; поддерживает сжатые указатели, поколенческий режим — с Java 24 (экспериментально → продуктово в 25). Epsilon (-XX:+UseEpsilonGC) не собирает мусор вовсе — для тестов производительности и короткоживущих задач.

13.6Самопроверка

Почему сборщик называется Garbage-First?

  • Сначала собирает молодое поколение
  • Удаляет мусор до пометки
  • В смешанных сборках выбирает старые регионы с наибольшей долей мусора — максимум освобождённой памяти за единицу паузы
  • Это просто имя
Доля живого известна после конкурентной пометки.

Как ZGC перемещает объекты без длинной паузы?

  • Конкурентно копирует, а барьер при загрузке ссылки находит новый адрес через таблицу пересылки и исправляет ссылку
  • Никогда не перемещает объекты
  • Останавливает только один поток
  • Использует подсчёт ссылок
Цветные указатели + load barriers + self-healing.

В логе G1 — «Pause Full (G1 Compaction Pause)». Что это значит?

  • Нормальная молодая сборка
  • Конкурентная фаза
  • Ошибка JVM
  • Аварийная полная сборка: пометка или эвакуация не успели — нужна настройка (размер кучи, IHOP, утечки, humongous)
В здоровом G1-приложении Full GC не должно быть.

Что такое humongous-объект в G1?

  • Объект, переживший 15 сборок
  • Объект больше половины региона: размещается сразу в старом поколении в смежных регионах
  • Объект с финализатором
  • Объект в metaspace
Большие массивы → humongous; помогает увеличение G1HeapRegionSize.
Сравните G1 и ZGC для сервиса с кучей 16 ГБ и требованием p99 < 50 мс.

G1 с MaxGCPauseMillis=20–50 обычно укладывается, но паузы растут при большом числе живых объектов в молодом поколении и на remark; при ошибках настройки — Full GC. Generational ZGC даёт паузы < 1 мс, но требует запаса кучи (конкурентная работа при высоком темпе выделения — иначе allocation stall) и немного больше CPU; ссылки 8 байт увеличат занятость кучи. Решение — нагрузочный тест обоих на реальном трафике с замером p99 и CPU.

Что такое allocation stall в ZGC и как его лечить?

Приложение выделяет память быстрее, чем ZGC успевает конкурентно освобождать, и потоку, которому негде выделить, приходится ждать окончания цикла — фактически пауза. Лечится запасом кучи (Xmx больше), снижением темпа выделения, большим числом конкурентных потоков GC (ConcGCThreads), с JDK 21 — поколенческим режимом, который собирает молодые объекты чаще и дешевле.
