Слабые ссылки, Cleaner, финализация

Иногда нужно ссылаться на объект, не продлевая ему жизнь: кэш, который не должен удерживать данные, метаданные «рядом» с чужими объектами, освобождение нативных ресурсов после смерти Java-объекта. Для этого в JVM есть мягкие, слабые и фантомные ссылки, очереди ссылок и Cleaner. Разбираем, когда каждая очищается, ловушки WeakHashMap и мягких кэшей, и почему finalize() уходит из Java.

15.2ReferenceQueue и обработка ссылок

Ссылку можно создать с очередью: new WeakReference<>(obj, queue). Когда GC очищает ссылку, служебный поток Reference Handler ставит объект-ссылку в очередь, и ваш код узнаёт, что референт умер — без опроса всех ссылок. Обработка Reference-объектов — отдельная фаза каждой сборки; миллионы слабых ссылок заметно удлиняют паузы (в логах G1 — фаза «Reference Processing»).

class Entry<K, V> extends WeakReference<K> { V value; … }   // слабый — только ключ
private final ReferenceQueue<K> queue = new ReferenceQueue<>();
private void expungeStaleEntries() {                          // вызывается при get/put/size
    for (Object x; (x = queue.poll()) != null; ) { … удалить запись x из таблицы … }
}

15.3Ловушки WeakHashMap и мягких кэшей

Почему WeakHashMap «не очищается»
Ключ
Session s
Запись WeakHashMap
weak → svalue: Context
Значение
Context { session = s }

Хотим хранить контекст для сессии, пока она жива: ключ слабый, значит, запись пропадёт вместе с сессией.

Значение хранится в карте сильно, а значение ссылается на ключ. Путь «карта → значение → ключ» делает ключ сильно достижимым — он никогда не станет слабо достижимым, запись не удалится. Утечка.

Значение не должно ссылаться на ключ (или ссылаться через WeakReference). Ещё ловушки: ключи сравниваются через equals — для строковых литералов и интернированных строк (сильно достижимы из пула) записи не удалятся никогда; WeakHashMap не потокобезопасна.

Кэш на SoftReference ведёт себя плохо: GC очищает мягкие ссылки по своим правилам, а не по ценности данных; при нехватке памяти — почти всё разом (лавина промахов), а пока памяти «достаточно», кэш раздувает старое поколение и удлиняет сборки. Для кэшей используйте ограниченные по размеру/времени (Caffeine), а не GC как политику вытеснения.

15.4Cleaner вместо finalize

class NativeBuffer {
    private long address = malloc(1024);
    @Override protected void finalize() {     // когда? в каком потоке? один раз?
        free(address);                          // объект можно «воскресить» из finalize
    }
}
class NativeBuffer implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();
    private record State(long address) implements Runnable {
        public void run() { free(address); }    // НЕ ссылается на NativeBuffer!
    }
    private final Cleaner.Cleanable cleanable;
    NativeBuffer() { cleanable = CLEANER.register(this, new State(malloc(1024))); }
    @Override public void close() { cleanable.clean(); }   // явно и детерминированно; Cleaner — страховка
}
  • Финализируемые объекты переживают минимум одну лишнюю сборку, обрабатываются одним потоком Finalizer (медленный финализатор = утечка памяти), порядок и момент не гарантированы, исключения проглатываются. Запуск с --finalization=disabled проверит, зависит ли ваш код от финализации.
  • Cleaner основан на фантомных ссылках: действие не имеет доступа к объекту, воскресить его нельзя. Главное правило — действие (лямбда/класс) не должно ссылаться на регистрируемый объект, иначе он никогда не станет фантомно достижимым.
  • Освобождение ресурсов должно быть явным (close(), try-with-resources); GC — лишь страховка от забывчивости.

Лаба 15.1Strong, Soft, Weak, Phantom под давлением памяти20 мин

Увидеть, в какой момент очищается каждый вид ссылки.

  1. Создайте файл RefKinds.java:
    import java.lang.ref.*;
import java.util.ArrayList;
import java.util.List;

public class RefKinds {
    public static void main(String[] args) throws Exception {
        var queue = new ReferenceQueue<Object>();
        var soft = new SoftReference<>(new byte[10 << 20]);
        var weak = new WeakReference<>(new byte[10 << 20]);
        var phantom = new PhantomReference<>(new byte[10 << 20], queue);
        report("после создания", soft, weak, phantom, queue);

        System.gc();
        report("после System.gc()", soft, weak, phantom, queue);

        List<byte[]> pressure = new ArrayList<>();
        try {
            while (true) pressure.add(new byte[1 << 20]);
        } catch (OutOfMemoryError e) {
            pressure = null;
            report("после нехватки памяти", soft, weak, phantom, queue);
        }
    }

    static void report(String when, SoftReference<?> s, WeakReference<?> w, PhantomReference<?> p, ReferenceQueue<?> q) throws Exception {
        Thread.sleep(100);
        System.out.printf("%-24s soft=%-5s weak=%-5s phantom в очереди=%s%n", when,
                s.get() != null, w.get() != null, q.poll() != null);
    }
}
  2. Запишите для каждой строки, какие ссылки ещё «живы».

    IDEAVM options: -Xmx64m

    javac RefKinds.java
java -Xmx64m RefKinds
    Вывод (JDK 25.0.2)
    после создания           soft=true  weak=true  phantom в очереди=false
после System.gc()        soft=true  weak=false phantom в очереди=true
после нехватки памяти    soft=false weak=false phantom в очереди=false

    После создания — soft и weak живы (у phantom get() всегда null, поэтому смотрим очередь). После System.gc() weak очищена, phantom попала в очередь, soft — жива: при достаточном запасе памяти мягкие ссылки не трогают. Перед OutOfMemoryError JVM обязана очистить все мягкие ссылки — soft=false.

Поэкспериментируйте
  • Почему кэш на SoftReference — плохая идея на сервере?
    Мягкие ссылки чистятся по эвристике (примерно «секунда жизни на каждый свободный МБ кучи», -XX:SoftRefLRUPolicyMSPerMB) и массово — перед OOM. Кэш раздувает старое поколение, а при нагрузке внезапно пустеет целиком. Ограниченный кэш (Caffeine) с явным размером предсказуемее.
Лаба 15.2Ловушка WeakHashMap15 мин

Сделать «самоочищающийся» кэш на WeakHashMap, убедиться, что он не очищается, и починить.

  1. Создайте файл WeakTrap.java:
    import java.util.Map;
import java.util.WeakHashMap;

public class WeakTrap {
    static class Key { final String id; Key(String id) { this.id = id; } }
    static class Value {
        final Key owner; final byte[] data = new byte[1024];
        Value(Key owner) { this.owner = owner; }
    }

    public static void main(String[] args) throws Exception {
        Map<Key, Value> broken = new WeakHashMap<>();
        Map<Key, byte[]> fixed = new WeakHashMap<>();
        for (int i = 0; i < 10_000; i++) {
            Key k1 = new Key("k" + i), k2 = new Key("k" + i);
            broken.put(k1, new Value(k1));       // значение ссылается на ключ
            fixed.put(k2, new byte[1024]);       // значение ключ не держит
        }
        System.gc();
        Thread.sleep(200);
        System.out.println("broken.size() = " + broken.size());
        System.out.println("fixed.size()  = " + fixed.size());
    }
}
  2. Ключи нигде больше не хранятся. Что покажут размеры?
    javac WeakTrap.java
java WeakTrap
    Вывод (JDK 25.0.2)
    broken.size() = 10000
fixed.size()  = 0

    broken.size() = 10000, fixed.size() = 0. В WeakHashMap значения хранятся сильными ссылками из самой карты; значение ссылается на ключ — значит, ключ сильно достижим через карту и никогда не будет собран. Это утечка, замаскированная под кэш.

Поэкспериментируйте
  • Почему new WeakHashMap<String, …> с ключами-литералами "k1" тоже никогда не очищается?
    Строковые литералы интернированы и сильно достижимы из пула строк (и из констант класса). Слабые ключи имеют смысл только для объектов, жизненный цикл которых контролирует кто-то другой.
Лаба 15.3Cleaner: страховка для нативного ресурса20 мин

Написать ресурс, который освобождается явно через close(), а если забыли — сборщиком через Cleaner.

  1. Создайте файл NativeBuffer.java:
    import java.lang.ref.Cleaner;

public class NativeBuffer implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();

    // Состояние для очистки — отдельный класс, НЕ ссылающийся на NativeBuffer
    private record State(int id) implements Runnable {
        public void run() { System.out.println("  освобождаю нативную память #" + id + " в потоке " + Thread.currentThread().getName()); }
    }

    private final Cleaner.Cleanable cleanable;

    NativeBuffer(int id) {
        System.out.println("  выделяю #" + id);
        cleanable = CLEANER.register(this, new State(id));
    }

    @Override public void close() { cleanable.clean(); }   // повторный clean() ничего не делает

    public static void main(String[] args) throws Exception {
        System.out.println("1) try-with-resources:");
        try (var b = new NativeBuffer(1)) { }

        System.out.println("2) забыли close():");
        new NativeBuffer(2);
        System.gc();
        Thread.sleep(300);
        System.out.println("конец main");
    }
}
  2. В каком потоке выполнится очистка в каждом случае?
    javac NativeBuffer.java
java NativeBuffer
    Вывод (JDK 25.0.2)
    1) try-with-resources:
  выделяю #1
  освобождаю нативную память #1 в потоке main
2) забыли close():
  выделяю #2
  освобождаю нативную память #2 в потоке Cleaner-0
конец main

    №1 — в main, синхронно, при выходе из try. №2 — в служебном потоке нашего Cleaner (Cleaner-0; у системного Cleaner JDK поток называется Common-Cleaner), после того как GC обнаружил объект фантомно-достижимым. Момент второго не гарантирован — поэтому Cleaner только страховка, а не основной путь.

Поэкспериментируйте
  • Сделайте State нестатическим внутренним классом (или лямбдой, использующей поле NativeBuffer). Что сломается?
    State будет держать ссылку на NativeBuffer, а Cleaner держит State сильно — объект никогда не станет фантомно-достижимым, очистка в случае №2 не выполнится. Это самая частая ошибка с Cleaner.

15.6Самопроверка

Что вернёт phantomRef.get()?

  • Объект, пока он жив
  • Объект после очистки
  • Всегда null
  • Исключение
Фантомная ссылка нужна только как уведомление о смерти объекта.

Почему запись в WeakHashMap может никогда не удалиться?

  • Значение сильно ссылается на ключ, и ключ остаётся сильно достижимым через саму карту
  • WeakHashMap не работает в Java 17
  • GC не обрабатывает слабые ссылки
  • Ключ — Integer
Классическая утечка.

Чем плох кэш на SoftReference?

  • Он не потокобезопасен по определению
  • Он очищается при каждой молодой сборке
  • SoftReference запрещены в Java 21
  • Вытеснение решает GC по своей эвристике: непредсказуемо, массовые промахи при нехватке памяти, раздувание старого поколения
Используйте кэши с явными ограничениями.
Как гарантированно освободить нативный ресурс, связанный с Java-объектом?

Явно: AutoCloseable и try-with-resources (или явный close в жизненном цикле). Страховка — Cleaner: регистрируем объект и действие очистки, не ссылающееся на объект; действие выполнится после того, как объект станет фантомно достижимым, если close не был вызван. Не finalize: он медленный, непредсказуемый и удаляется из платформы. В FFM API (тема 19) ресурсы привязываются к Arena с явным закрытием.

Где в JDK и фреймворках используются слабые ссылки?

WeakHashMap и ThreadLocalMap (ключ — слабая ссылка на ThreadLocal; значение — сильная, отсюда утечки в пулах); кэши интроспекции и метаданных классов (ClassValue, Spring ConcurrentReferenceHashMap, чтобы не держать загрузчики); интернирование (Guava Interners.newWeakInterner); слушатели, которые не должны удерживать подписчика; DirectByteBuffer освобождается через Cleaner.
