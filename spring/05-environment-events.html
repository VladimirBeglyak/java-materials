Environment, профили, конвертация и события

Контейнер отвечает не только за бины. Environment даёт единый доступ к настройкам из любых источников и знает активные профили. ConversionService превращает строки в типы. Механизм событий позволяет компонентам общаться без прямых зависимостей — с тонкостями про потоки и транзакции, на которых ошибаются даже опытные разработчики.

5.1Environment и PropertySource

Environment объединяет две вещи: профили и свойства. Свойства хранятся в упорядоченном списке MutablePropertySources. Поиск ключа идёт по списку сверху вниз, побеждает первый источник, где ключ найден (PropertySourcesPropertyResolver).

commandLineArgs--server.port=9000 (Boot)
↓ если не найдено
systemProperties-Dserver.port=9000
↓
systemEnvironmentSERVER_PORT=9000 (с «расслабленным» сопоставлением имён)
↓
Config resource 'class path resource [application.yml]'файлы конфигурации Boot
↓
@PropertySource("classpath:extra.properties")добавляются в конец списка

Полный порядок источников Spring Boot (их 15+) — тема 08. Здесь важен механизм: любая библиотека может добавить свой PropertySource (Vault, Consul, Kubernetes ConfigMap) в нужную позицию, и для кода ничего не меняется.

@Component
class Example {
    Example(Environment env,
            @Value("${app.timeout:5s}") Duration timeout,           // плейсхолдер с значением по умолчанию
            @Value("#{${app.retries:3} * 2}") int attempts) {      // SpEL поверх плейсхолдера
        String region = env.getProperty("app.region", "eu");
        boolean prod  = env.matchesProfiles("prod");
    }
}
// Для групп настроек — @ConfigurationProperties (тема 08): типобезопасно и с валидацией.

Как разрешается @Value

  1. AutowiredAnnotationBeanPostProcessor находит @Value на поле/параметре и передаёт строку в beanFactory.resolveEmbeddedValue().
  2. Зарегистрированные StringValueResolver-ы (в Boot — от PropertySourcesPlaceholderConfigurer) раскрывают ${...} по Environment, рекурсивно и с поддержкой :default.
  3. Если результат содержит #{...}, его вычисляет StandardBeanExpressionResolver (SpEL).
  4. TypeConverter / ConversionService приводит строку к типу параметра: Duration, List<String>, enum.
Симулятор: разрешение плейсхолдеров

Слева — свойства в Environment (формат key=value). Справа — строка, как в @Value. Пробуйте вложенность, значения по умолчанию, циклы.

5.2Профили

Профиль — именованный набор бинов и настроек, который включается целиком. @Profile — это @Conditional(ProfileCondition.class): условие проверяется при разборе конфигурации, неподходящие классы и @Bean-методы просто не регистрируются.

@Configuration
class StorageConfig {
    @Bean @Profile("!cloud")                       // все профили, кроме cloud
    FileStorage localStorage() { return new LocalFileStorage(Path.of("/tmp/files")); }

    @Bean @Profile("cloud & (eu | us)")            // выражения: !, &, |, скобки
    FileStorage s3Storage(S3Client s3) { return new S3FileStorage(s3); }
}

Как активировать

spring.profiles.active=prod в любом источнике свойств (переменная SPRING_PROFILES_ACTIVE, аргумент --spring.profiles.active); в тестах — @ActiveProfiles. Если ничего не активно, работает профиль default.

Группы профилей (Boot)

spring.profiles.group.prod=postgres,kafka,metrics — активация prod включает всю группу. spring.profiles.include добавляет профили всегда.

Практика Профили хороши для подключения реализаций (локальное хранилище против S3, заглушка платёжного шлюза). Плохо, когда профиль на каждое окружение (dev, stage, prod) содержит разные бины: на проде запускается код, который не прогонялся в тестах. Разницу между окружениями держите в значениях свойств, а код — одинаковым.

5.3Конвертация типов

Строки из конфигурации и HTTP превращаются в типы через ConversionService (в Boot — ApplicationConversionService с расширенным набором конвертеров). Расширяется так:

@Component
@ConfigurationPropertiesBinding                         // использовать и при биндинге @ConfigurationProperties
class MoneyConverter implements Converter<String, Money> {
    public Money convert(String s) {                    // "100.50 RUB"
        String[] p = s.trim().split("\\s+");
        return Money.of(new BigDecimal(p[0]), p[1]);
    }
}
// Встроенные форматы Boot: Duration — "30s", "5m", "PT1H"; DataSize — "10MB", "512KB";
// списки — "a,b,c"; Period — "1y2m3d".

5.4События: механизм

public record OrderPlaced(long orderId, String email) { }   // событие — любой объект

@Service
class OrderService {
    private final ApplicationEventPublisher events;
    OrderService(ApplicationEventPublisher events) { this.events = events; }

    @Transactional
    public Order place(Cart cart) {
        Order o = repo.save(Order.from(cart));
        events.publishEvent(new OrderPlaced(o.id(), cart.email()));   // обёртывается в PayloadApplicationEvent
        return o;
    }
}

@Component
class Notifications {
    @EventListener                                     // по умолчанию: синхронно, в том же потоке и транзакции
    void onPlaced(OrderPlaced e) { /* ... */ }

    @EventListener(condition = "#e.email.endsWith('@corp.ru')")
    void onCorporate(OrderPlaced e) { /* SpEL-условие */ }
}

Внутри: на шаге 11 refresh() EventListenerMethodProcessor (это SmartInitializingSingleton) находит методы с @EventListener и через DefaultEventListenerFactory регистрирует для каждого ApplicationListenerMethodAdapter. publishEvent передаёт событие в SimpleApplicationEventMulticaster, который выбирает слушателей по типу (с учётом generics, результат кэшируется) и вызывает их по очереди в потоке публикующего. Если метод слушателя возвращает объект — он публикуется как новое событие.

Синхронность — это и плюс, и риск Исключение синхронного слушателя пробрасывается в publishEvent → в метод place() → транзакция заказа откатывается из-за упавшей отправки письма. И наоборот: письмо уже ушло, а транзакция потом откатилась — клиент получил подтверждение несуществующего заказа. Для побочных эффектов наружу используйте @TransactionalEventListener.

@TransactionalEventListener

Слушатель не вызывается сразу. TransactionalApplicationListenerMethodAdapter регистрирует TransactionSynchronization в текущей транзакции, и метод выполнится в выбранной фазе: BEFORE_COMMIT, AFTER_COMMIT (по умолчанию), AFTER_ROLLBACK, AFTER_COMPLETION.

5.5Самопроверка

Свойство задано в application.yml и в переменной окружения. Что увидит Environment.getProperty?

  • Значение из application.yml
  • Значение из переменной окружения — этот источник стоит выше в списке
  • Ошибку неоднозначности
  • Последнее загруженное
Поиск идёт по упорядоченному списку PropertySource, побеждает первый найденный. Переменные окружения в Boot выше файлов конфигурации.

@TransactionalEventListener, а publishEvent вызван вне транзакции. Что будет?

  • Слушатель вызовется немедленно
  • Слушатель вызовется после ближайшей транзакции в этом потоке
  • Событие будет отброшено, если не указан fallbackExecution = true
  • IllegalStateException
Регистрировать синхронизацию не в чем. По умолчанию такое событие игнорируется — частая причина «пропавших» писем.

В каком потоке выполняется обычный @EventListener?

  • В потоке, вызвавшем publishEvent
  • В отдельном пуле Spring
  • В main-потоке
  • В ForkJoinPool.commonPool
SimpleApplicationEventMulticaster без настроенного executor вызывает слушателей синхронно в потоке публикующего.
Как разрешается @Value("${a:${b:x}}")?

AutowiredAnnotationBPP передаёт строку в resolveEmbeddedValue; резолвер PropertySourcesPlaceholderConfigurer ищет a по PropertySources; если нет — разрешает значение по умолчанию ${b:x}: ищет b, если нет — x. Затем при необходимости SpEL и конвертация к типу. Неразрешимый плейсхолдер без default — IllegalArgumentException и падение старта.

Почему внешние побочные эффекты лучше делать в AFTER_COMMIT, и чего этот подход не гарантирует?

Эффект происходит только если данные реально закоммичены — не бывает писем о несуществующих заказах. Но нет гарантии доставки: падение процесса между коммитом и вызовом слушателя теряет событие, а исключения слушателя проглатываются. Для гарантий — Transactional Outbox: запись события в таблицу в той же транзакции и отдельная доставка (Debezium, Spring Modulith Event Publication Registry).

Как сделать обработку событий асинхронной?

@Async на методе слушателя (с @EnableAsync) — выполнение в TaskExecutor, ошибки в AsyncUncaughtExceptionHandler. Либо настроить executor у бина applicationEventMulticaster — тогда асинхронными станут все слушатели, включая системные, что обычно нежелательно. Комбинация @Async + @TransactionalEventListener — асинхронно и только после коммита.

Как работает @Profile технически?

Это мета-аннотация @Conditional(ProfileCondition.class). ConfigurationClassPostProcessor при разборе вызывает ConditionEvaluator; ProfileCondition проверяет environment.matchesProfiles(...). Не прошло — класс или @Bean-метод не регистрируется как BeanDefinition.
