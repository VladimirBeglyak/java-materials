12.2Пул соединений HikariCP

Открыть TCP-соединение к PostgreSQL с TLS и аутентификацией — десятки миллисекунд. Пул держит готовые соединения; getConnection() отдаёт свободное, а close() возвращает его в пул, а не закрывает.

spring:
  datasource:
    url: jdbc:postgresql://db:5432/shop
    username: shop
    password: ${DB_PASSWORD}
    hikari:
      maximum-pool-size: 20          # по умолчанию 10; формула-ориентир: ядра_БД × 2 + диски
      minimum-idle: 20               # фиксированный пул — рекомендация автора Hikari
      connection-timeout: 3000         # мс; ожидание свободного соединения → SQLTransientConnectionException
      max-lifetime: 1800000            # мс (30 мин); меньше, чем таймаут простоя у БД/прокси
      leak-detection-threshold: 20000  # мс; лог со стектрейсом, если соединение не вернули
      # Hikari-сеттеры принимают long в миллисекундах — суффиксы 3s/30m здесь не работают
Больший пул не значит быстрее. БД выполняет параллельно столько запросов, сколько у неё ядер и дисков; сотни соединений создают конкуренцию за блокировки и кэш. Сумма пулов всех экземпляров сервиса должна помещаться в max_connections БД.

12.3JdbcClient и JdbcTemplate

@Repository
class ReportDao {
    private final JdbcClient jdbc;
    ReportDao(JdbcClient jdbc) { this.jdbc = jdbc; }       // бин создаёт автоконфигурация

    List<DailyRevenue> revenue(LocalDate from) {
        return jdbc.sql("""
                SELECT date_trunc('day', created_at) AS day, sum(total) AS revenue
                FROM orders WHERE created_at >= :from GROUP BY 1 ORDER BY 1""")
            .param("from", from)
            .query(DailyRevenue.class)                       // маппинг колонок в record по именам
            .list();
    }
}

Внутри JdbcTemplate.execute: DataSourceUtils.getConnection(ds) (соединение текущей транзакции или новое) → создание PreparedStatement → выполнение → маппинг → закрытие ресурсов → DataSourceUtils.releaseConnection. SQLException переводится SQLExceptionTranslator (по умолчанию с Spring 6 — SQLExceptionSubclassTranslator: по типу SQLException из JDBC 4 и SQLState; по кодам ошибок БД — только если в classpath есть sql-error-codes.xml) в DuplicateKeyException, DataIntegrityViolationException, CannotAcquireLockException и т.д. — единая иерархия DataAccessException (unchecked).

12.4JPA: persistence context

EntityManager держит persistence context — карту «id → управляемая сущность» (кэш первого уровня). Внутри одной транзакции:

  • find(Order.class, 1) дважды → один SQL, один и тот же объект;
  • изменили поле управляемой сущности → при flush Hibernate сравнит со снимком (dirty checking) и сам выполнит UPDATE — save() не нужен;
  • flush происходит перед коммитом, перед JPQL-запросом, затрагивающим изменённые таблицы, и при явном flush().

Как в синглтон-бин внедряется EntityManager

EntityManager не потокобезопасен и должен быть свой на каждую транзакцию. Но в репозиторий он внедряется один раз. Внедряется прокси (SharedEntityManagerCreator): каждый вызов прокси ищет EntityManager, привязанный к текущей транзакции через TransactionSynchronizationManager (его туда положил JpaTransactionManager.doBegin). Нет транзакции — создаётся временный EntityManager на одну операцию.

Open Session in View Boot по умолчанию включает spring.jpa.open-in-view=true (и пишет WARN при старте): OpenEntityManagerInViewInterceptor открывает EntityManager на весь HTTP-запрос, и ленивые связи грузятся даже при сериализации JSON в контроллере. Удобно, но соединение держится до конца запроса, а ленивые SQL-запросы разлетаются по слою представления незаметно. В продакшен-сервисах рекомендуют false и явную загрузку данных в сервисе.

12.5Как устроен репозиторий Spring Data

  1. @EnableJpaRepositories (в Boot — автоконфигурация) через ImportBeanDefinitionRegistrar сканирует пакет и для каждого интерфейса-наследника Repository регистрирует описание бина с классом JpaRepositoryFactoryBean.
  2. Фабрика (JpaRepositoryFactory) создаёт target — SimpleJpaRepository, общую реализацию CRUD (save, findById, findAll(Pageable)…).
  3. Для каждого метода интерфейса выбирается стратегия (QueryLookupStrategy, по умолчанию CREATE_IF_NOT_FOUND): @Query → именованный запрос → разбор имени метода (PartTree). Ошибка в имени метода обнаруживается на старте.
  4. ProxyFactory собирает JDK-прокси над интерфейсом с перехватчиками: трансляция исключений, TransactionInterceptor (SimpleJpaRepository помечен @Transactional(readOnly = true), изменяющие методы — @Transactional), QueryExecutorMethodInterceptor (вызов → заранее подготовленный запрос), default-методы интерфейса, фрагменты с пользовательской реализацией.
public interface OrderRepository extends JpaRepository<Order, Long> {

    List<Order> findByCustomerEmailAndStatusOrderByCreatedAtDesc(String email, Status status);

    @Query("select o from Order o join fetch o.items where o.id = :id")
    Optional<Order> findWithItems(long id);                          // fetch join против N+1

    @EntityGraph(attributePaths = {"customer"})   // коллекцию items с Pageable так не грузить — пагинация уйдёт в память
    Page<Order> findByStatus(Status status, Pageable page);

    interface OrderSummary { Long getId(); BigDecimal getTotal(); }     // интерфейсная проекция → SELECT только этих колонок
    List<OrderSummary> findTop10ByOrderByTotalDesc();

    @Modifying(clearAutomatically = true)
    @Query("update Order o set o.status = 'EXPIRED' where o.createdAt < :before and o.status = 'NEW'")
    int expireOlderThan(Instant before);                               // массовый UPDATE мимо persistence context
}
Симулятор PartTree: имя метода → JPQL

Так Spring Data на старте разбирает имя метода. Сущность — Order.

Длинные имена методов быстро становятся нечитаемыми. Правило: два-три условия — производный запрос; больше — @Query, Specification/Querydsl для динамических фильтров или JdbcClient для отчётов.

12.6save(): persist или merge

@Transactional
public <S extends T> S save(S entity) {
    if (entityInformation.isNew(entity)) {   // есть @Version-обёртка → version == null; иначе id == null (примитивный id — 0); Persistable → isNew()
        em.persist(entity);
        return entity;
    } else {
        return em.merge(entity);             // SELECT по id + копирование состояния в управляемую копию
    }
}

Если id назначается вручную (UUID в конструкторе), isNew вернёт false, и каждый «новый» объект пойдёт через merge: лишний SELECT перед INSERT. Решение — @Version-поле (null у нового) или реализация Persistable.

12.8Самопроверка

Кто реализует интерфейс OrderRepository extends JpaRepository?

  • Annotation processor генерирует класс при компиляции
  • JpaRepositoryFactoryBean создаёт в рантайме JDK-прокси над интерфейсом с target SimpleJpaRepository и перехватчиками запросов
  • Hibernate
  • CGLIB-подкласс интерфейса
Spring Data строит прокси через ProxyFactory; CRUD-методы делегируются SimpleJpaRepository, производные и @Query — QueryExecutorMethodInterceptor. (Для AOT/native эти части генерируются заранее, но в обычном режиме — рантайм-прокси.)

В транзакции загрузили Order, поменяли статус, save() не вызывали. Что будет при коммите?

  • Ничего, изменения потеряны
  • Исключение: сущность не сохранена
  • UPDATE: dirty checking при flush найдёт изменение управляемой сущности
  • INSERT дубликата
Сущность managed: Hibernate сравнит её со снимком при flush перед коммитом и выполнит UPDATE.

Зачем Spring внедряет в репозитории прокси EntityManager, а не настоящий?

  • EntityManager не потокобезопасен и должен быть свой на транзакцию; прокси на каждом вызове находит EntityManager текущей транзакции
  • Для ленивой загрузки сущностей
  • Для кэширования запросов
  • Чтобы можно было использовать CGLIB
SharedEntityManagerCreator делегирует в EntityManager, привязанный к потоку через TransactionSynchronizationManager.
Что такое persistence context и dirty checking?

Кэш управляемых сущностей EntityManager на время транзакции: идентичность объектов по id, повторный find без SQL. При загрузке Hibernate сохраняет снимок состояния; при flush сравнивает текущее состояние со снимком и генерирует UPDATE для изменённых. Поэтому save() для управляемых сущностей не нужен, а readOnly-транзакции экономят память на снимках.

Как бороться с N+1?

Обнаружить: логирование SQL, счётчик запросов в тестах (datasource-proxy, Hibernate statistics). Лечить: fetch join или @EntityGraph для нужных связей, batch fetching, DTO-проекции для чтения; не использовать EAGER как «решение».

Когда JdbcClient лучше JPA?

Отчёты и агрегаты, массовые операции, сложный SQL с оконными функциями, работа с чужой схемой, критичные по производительности чтения. JPA удобна для агрегатов с бизнес-логикой и изменений через объектную модель. В одном сервисе их нормально совмещать — они разделяют одну транзакцию через JpaTransactionManager.

Почему derived deleteBy… может быть медленным?

Spring Data сначала выбирает сущности, затем вызывает em.remove для каждой — N операций, загрузка в persistence context, каскады и колбэки. Для массового удаления — @Modifying @Query("delete from …"), помня, что он обходит persistence context (clearAutomatically).
