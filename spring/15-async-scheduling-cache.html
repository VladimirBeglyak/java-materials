@Async, @Scheduled и кэширование

Три аннотации, которые выглядят как «включил и работает», а в продакшене дают неограниченные очереди, задачи, выполняющиеся на каждом из пяти подов, и кэш, который не сбрасывается. Все три построены на уже знакомых механизмах: прокси, пост-процессорах и пулах потоков. Разберём их устройство и правила безопасного использования.

15.1@Async

@EnableAsync регистрирует AsyncAnnotationBeanPostProcessor. Он оборачивает бины с @Async в прокси с AnnotationAsyncExecutionInterceptor: вызов метода превращается в задачу, отправленную в TaskExecutor, а вызывающий сразу получает управление.

Какой executor будет использован

  1. Имя в аннотации: @Async("reportExecutor") — бин с этим именем.
  2. Иначе AsyncConfigurer.getAsyncExecutor(), если вы его реализовали.
  3. Иначе единственный бин TaskExecutor или бин с именем taskExecutor.
  4. В Spring Boot таким бином будет applicationTaskExecutor — ThreadPoolTaskExecutor с 8 потоками и неограниченной очередью (spring.task.execution.pool.*) — если вы не объявили свой Executor: иначе автоконфигурация отступает (кроме spring.task.execution.mode=force), и @Async без имени попадёт в ваш единственный TaskExecutor, а с spring.threads.virtual.enabled=true — SimpleAsyncTaskExecutor на виртуальных потоках.
@Configuration
@EnableAsync
class AsyncConfig {
    @Bean
    ThreadPoolTaskExecutor reportExecutor() {
        var ex = new ThreadPoolTaskExecutor();
        ex.setThreadNamePrefix("report-");
        ex.setCorePoolSize(4);
        ex.setMaxPoolSize(8);
        ex.setQueueCapacity(200);                                  // ограниченная очередь!
        ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        ex.setTaskDecorator(task -> {                              // MDC и SecurityContext из вызывающего потока
            Map<String, String> mdc = MDC.getCopyOfContextMap();
            SecurityContext sc = SecurityContextHolder.getContext();
            return () -> {
                try { if (mdc != null) MDC.setContextMap(mdc); SecurityContextHolder.setContext(sc); task.run(); }
                finally { MDC.clear(); SecurityContextHolder.clearContext(); }
            };
        });
        ex.setWaitForTasksToCompleteOnShutdown(true);
        ex.setAwaitTerminationSeconds(30);
        return ex;
    }
}

@Service
class ReportService {
    @Async("reportExecutor")
    public CompletableFuture<Report> build(long id) {
        return CompletableFuture.completedFuture(heavyBuild(id));
    }
}
Ловушки @Async Self-invocation (вызов из того же класса выполнится синхронно). Транзакция вызывающего не переходит в асинхронный метод. Неограниченная очередь по умолчанию копит задачи до OOM. Request-scoped бины и RequestContextHolder в потоке пула недоступны. @Async и циклическая зависимость на этом же бине дают ошибку «has been injected into other beans in its raw version» (тема 03).

15.2@Scheduled

@EnableScheduling → ScheduledAnnotationBeanPostProcessor находит методы с @Scheduled и регистрирует их в ScheduledTaskRegistrar; задачи запускаются после refresh контекста на TaskScheduler. В Boot это ThreadPoolTaskScheduler с одним потоком (spring.task.scheduling.pool.size).

@Component
class Jobs {
    @Scheduled(fixedRate = 30, timeUnit = TimeUnit.SECONDS)     // от начала до начала; запуски не перекрываются
    void refreshRates() { /* ... */ }

    @Scheduled(fixedDelay = 10_000, initialDelay = 5_000)       // пауза от конца предыдущего
    void pollOutbox() { /* ... */ }

    @Scheduled(cron = "0 0 3 * * MON-FRI", zone = "Europe/Moscow")  // 6 полей: секунды первыми!
    void nightlyReport() { /* ... */ }
}

Один поток на всех

Если nightlyReport работает 20 минут, все остальные задачи ждут. Увеличьте пул или включите виртуальные потоки (SimpleAsyncTaskScheduler: каждый запуск в своём виртуальном потоке).

Несколько экземпляров

5 подов — задача выполнится 5 раз. Решения: ShedLock (блокировка в БД/Redis через аннотацию @SchedulerLock), лидер-выборы (Spring Integration, Kubernetes Lease), Quartz в кластерном режиме, вынести задачу в отдельный CronJob.

Исключение в задаче логируется через ErrorHandler, следующий запуск состоится (в отличие от голого ScheduledExecutorService, где исключение отменяет расписание). Endpoint /actuator/scheduledtasks показывает все зарегистрированные задачи; метрики выполнения даёт Observation (tasks.scheduled.execution).

15.3Абстракция кэширования

@EnableCaching добавляет advisor с CacheInterceptor. Прокси перед вызовом вычисляет ключ, ищет значение в Cache из CacheManager и при попадании не вызывает метод вовсе. Хранилище подключаемое: ConcurrentMapCacheManager (Boot по умолчанию, без TTL и лимита — только для разработки), Caffeine (локальный, с TTL и размером), Redis (распределённый).

@Service
class PriceService {
    @Cacheable(cacheNames = "prices", key = "#sku", sync = true)   // sync=true нельзя сочетать с unless; null отсекайте настройкой кэша
    public Price get(String sku) { return repo.load(sku); }            // ключ по умолчанию: один аргумент — он сам, нет аргументов — SimpleKey.EMPTY, несколько — SimpleKey(args)

    @CachePut(cacheNames = "prices", key = "#p.sku")                    // всегда вызывает метод и обновляет кэш
    public Price update(Price p) { return repo.save(p); }

    @CacheEvict(cacheNames = "prices", allEntries = true)
    public void reloadAll() { /* ... */ }
}

О чём помнить с кэшем Инвалидация: изменения в обход аннотированных методов (другой сервис, SQL) кэш не видит — нужен TTL или событийная инвалидация. Локальный кэш в кластере: у каждого пода своя копия, @CacheEvict чистит только локальную. Транзакции: @CachePut внутри откатившейся транзакции оставит в кэше несуществующее значение — TransactionAwareCacheManagerProxy откладывает запись до коммита. Ключи: по умолчанию сам аргумент (если он один) или SimpleKey из всех аргументов — изменяемые объекты в качестве аргументов портят кэш. Redis: значения сериализуются — нужен согласованный сериализатор (JSON) и версионирование формата.

15.4Самопроверка

В Boot без настроек @Async-методы получают тысячи задач в минуту, каждая работает долго. Что случится?

  • Spring создаст новые потоки под нагрузку
  • applicationTaskExecutor с 8 потоками и неограниченной очередью будет копить задачи — растут задержка и память
  • Лишние задачи будут отклонены
  • Задачи выполнятся синхронно
Очередь по умолчанию неограниченная, поэтому потоков больше core не станет, а отказов не будет — до OOM. Задайте queue-capacity и политику.

Приложение развёрнуто в 3 экземплярах, в нём @Scheduled(cron = "0 0 * * * *") отправляет отчёт. Сколько отчётов в час?

  • Один — Spring синхронизирует экземпляры
  • Ноль
  • Три — каждый экземпляр запускает свой планировщик
  • Зависит от БД
@Scheduled ничего не знает о других экземплярах. Нужен ShedLock, лидер-выборы или вынос задачи.

Что делает sync = true в @Cacheable?

  • При одновременных промахах по одному ключу метод вызывается один раз, остальные потоки ждут результат
  • Синхронизирует кэш между экземплярами
  • Записывает в кэш синхронно с транзакцией
  • Делает метод synchronized
Защита от cache stampede на уровне одного экземпляра; поддержка зависит от реализации кэша (Caffeine — да).
Как работает @Async внутри и как выбирается executor?

AsyncAnnotationBeanPostProcessor оборачивает бин в прокси с AnnotationAsyncExecutionInterceptor; вызов упаковывается в Callable и отправляется в executor: по имени из аннотации, из AsyncConfigurer, единственный TaskExecutor или бин taskExecutor (в Boot — applicationTaskExecutor). void-исключения уходят в AsyncUncaughtExceptionHandler.

Чем fixedRate отличается от fixedDelay?

fixedRate — интервал между началами запусков (если запуск длится дольше интервала, следующий стартует сразу после окончания, параллельно не запускается на одном потоке). fixedDelay — пауза между окончанием предыдущего и началом следующего.

Какие проблемы у локального кэша в нескольких экземплярах и как их решать?

Каждый экземпляр видит свою копию: evict на одном не чистит другие, данные расходятся. Решения: короткий TTL, распределённый кэш (Redis), двухуровневый кэш с инвалидацией через pub/sub, или кэшировать только неизменяемые/редко меняющиеся данные.
