Транзакции: @Transactional изнутри

@Transactional — самая используемая и самая непонятая аннотация Spring. Под ней — прокси, перехватчик, менеджер транзакций и ThreadLocal, к которому привязано соединение с БД. Из этого устройства следуют все правила: какие исключения откатывают транзакцию, что делают propagation-режимы, откуда берётся UnexpectedRollbackException и почему REQUIRES_NEW может повесить приложение.

11.1Что такое транзакция на уровне JDBC

try (Connection c = dataSource.getConnection()) {
    c.setAutoCommit(false);                 // начало транзакции
    try {
        debit(c, from, amount);             // все операции — через ОДНО соединение
        credit(c, to, amount);
        c.commit();
    } catch (SQLException e) {
        c.rollback();
        throw e;
    }
}

Главное ограничение: все операции транзакции должны идти через одно и то же соединение. Как сделать это, если debit вызывает репозиторий, а тот — JdbcTemplate, и никто не передаёт соединение параметром? Spring кладёт соединение в ThreadLocal текущего потока, и все компоненты доступа к данным берут его оттуда.

PlatformTransactionManagergetTransaction(def), commit(status), rollback(status). Реализации: JdbcTransactionManager (JDBC), JpaTransactionManager (JPA, управляет и EntityManager, и JDBC-соединением), JtaTransactionManager (распределённые XA)

Следствия из ThreadLocal Транзакция живёт в потоке. Код в @Async, CompletableFuture.supplyAsync, parallel stream, отдельном пуле — вне транзакции вызывающего: другой поток, другое соединение, свой коммит. Нельзя «распараллелить» работу внутри одной транзакции.

11.3Propagation: что делать, если транзакция уже есть

РежимТранзакция естьТранзакции нет
REQUIRED (по умолчанию)участвовать в нейсоздать новую
REQUIRES_NEWприостановить, создать новую (второе соединение!)создать новую
NESTEDsavepoint в текущейсоздать новую
SUPPORTSучаствоватьвыполнить без транзакции
MANDATORYучаствоватьIllegalTransactionStateException
NOT_SUPPORTEDприостановить, выполнить без транзакциибез транзакции
NEVERIllegalTransactionStateExceptionбез транзакции

Физическая транзакция — реальная транзакция в БД на одном соединении. Логическая — область действия каждого @Transactional-метода. При REQUIRED несколько логических разделяют одну физическую. Внутренний метод, упавший с исключением, не может откатить физическую транзакцию сам — он помечает её rollback-only.

Симулятор propagation

OrderService.place() вызывает AuditService.log() через прокси. Выберите конфигурацию — увидите физические транзакции и итог.

Попробуйте: (1) REQUIRED + «place() ловит» — UnexpectedRollbackException. (2) REQUIRES_NEW + «ловит» — аудит откатился, заказ сохранён. (3) REQUIRES_NEW без ошибки и с ошибкой «летит дальше» — аудит сохранён, заказ откачен: так пишут журнал попыток.

11.4Правила отката

Откатывают по умолчанию

RuntimeException и Error (наследие EJB). С Spring 6.2 правило можно поменять глобально: @EnableTransactionManagement(rollbackOn = RollbackOn.ALL_EXCEPTIONS). Исключение должно вылететь из прокси — пойманное внутри метода ничего не откатывает.

НЕ откатывают

Checked-исключения (IOException, свои extends Exception) — транзакция коммитится, хотя метод завершился исключением. Нужно @Transactional(rollbackFor = Exception.class).

@Transactional(rollbackFor = PaymentException.class, noRollbackFor = NotificationException.class)
public void pay(Order o) throws PaymentException { /* ... */ }

// Пометить откат без исключения:
TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();

Isolation.DEFAULT — уровень БД. Нестандартный уровень применяется только при создании новой физической транзакции; участник с другим уровнем по умолчанию молча получит уровень внешней (строгая проверка — validateExistingTransaction=true у менеджера).

readOnly = true: Connection.setReadOnly(true) (драйвер может оптимизировать, PostgreSQL выполнит SET TRANSACTION READ ONLY), в JPA — FlushMode.MANUAL и отключение dirty checking в Hibernate: меньше памяти и CPU на больших выборках. Используется для маршрутизации на реплику через AbstractRoutingDataSource + LazyConnectionDataSourceProxy.

timeout: секунды; JDBC-операции получают Statement.setQueryTimeout по остатку времени.

11.7Программное управление

@Service
class ImportService {
    private final TransactionTemplate tx;
    ImportService(PlatformTransactionManager tm) {
        this.tx = new TransactionTemplate(tm);
        this.tx.setTimeout(30);
    }

    void importAll(List<Batch> batches) {
        for (Batch b : batches) {
            try {
                tx.executeWithoutResult(status -> save(b));       // отдельная транзакция на пачку
            } catch (DataAccessException e) {
                log.warn("batch {} failed", b.id(), e);           // остальные пачки продолжат
            }
        }
    }

    void onCommit(Runnable r) {                                     // выполнить после коммита текущей транзакции
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override public void afterCommit() { r.run(); }
        });
    }
}

11.8Самопроверка

Метод @Transactional бросает IOException. Что с транзакцией?

  • Откат
  • Зависит от БД
  • Коммит: checked-исключения по умолчанию не откатывают транзакцию
  • Транзакция остаётся открытой
По умолчанию rollbackOn = RuntimeException || Error. Для checked — rollbackFor.

Как JdbcTemplate внутри @Transactional-метода получает соединение именно этой транзакции?

  • Транзакционный менеджер передаёт его в параметрах
  • DataSourceUtils.getConnection находит ConnectionHolder, привязанный к потоку в TransactionSynchronizationManager
  • JdbcTemplate открывает новое соединение, а БД объединяет их
  • Через AOP-прокси JdbcTemplate
Соединение привязано к ThreadLocal по ключу DataSource в doBegin; JdbcTemplate ищет его там.

Откуда UnexpectedRollbackException?

  • БД откатила транзакцию из-за deadlock
  • Истёк timeout
  • Ошибка сети при коммите
  • Участник REQUIRED упал и пометил транзакцию rollback-only, а внешний метод поймал исключение и попытался закоммитить
Внешний метод не знает, что общая физическая транзакция уже обречена. Spring откатывает её и сообщает об этом исключением, чтобы ошибка не осталась незамеченной.
Расскажите, как работает @Transactional от аннотации до COMMIT.

Бин обёрнут в прокси (BeanFactoryTransactionAttributeSourceAdvisor нашёл аннотацию). Вызов → TransactionInterceptor → атрибуты из AnnotationTransactionAttributeSource → выбор TransactionManager → getTransaction: проверка существующей транзакции в TransactionSynchronizationManager, решение по propagation, doBegin (соединение из пула, autoCommit=false, привязка к ThreadLocal) → вызов метода (репозитории берут соединение из ThreadLocal) → по результату commit или rollback по правилам → синхронизации → отвязка, возврат соединения в пул.

Чем REQUIRES_NEW отличается от NESTED?

REQUIRES_NEW — независимая физическая транзакция на втором соединении; её коммит не зависит от внешней, внешняя приостановлена. NESTED — savepoint внутри той же физической транзакции: откат вложенной возвращает к savepoint, но коммит происходит только вместе с внешней, и откат внешней откатывает всё. NESTED требует поддержки savepoints (JDBC), REQUIRES_NEW — второго соединения.

Почему нельзя делать HTTP-вызов внутри транзакции?

Соединение с БД (и блокировки строк) удерживается на всё время сетевого вызова — пул истощается, растут конфликты. Откат транзакции не отменит внешний эффект (деньги списаны, письмо отправлено). Правильно: внешние вызовы до/после транзакции, после коммита — через @TransactionalEventListener или outbox.

Что даёт readOnly = true?

Подсказку драйверу/БД (Connection.setReadOnly), в Hibernate — FlushMode.MANUAL и отказ от снимков для dirty checking (экономия памяти и CPU), возможность маршрутизации на реплику. Это не защита: запись не обязательно запрещена — зависит от драйвера и БД.
