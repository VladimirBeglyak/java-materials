Kafka в Spring: KafkaTemplate и @KafkaListener изнутри

Spring for Apache Kafka прячет цикл poll(), коммит смещений и обработку ошибок за аннотацией @KafkaListener. Чтобы не терять и не дублировать сообщения, нужно знать, что именно делает контейнер слушателя: в каком потоке он работает, когда коммитит offset, что происходит с «ядовитым» сообщением и почему запись в БД и отправка в Kafka не бывают атомарными. Сама Kafka (партиции, ISR, ребаланс) разобрана в пособии System Design.

18.2Отправка

@Service
class OrderEvents {
    private final KafkaTemplate<String, OrderPlaced> kafka;
    OrderEvents(KafkaTemplate<String, OrderPlaced> kafka) { this.kafka = kafka; }

    void publish(OrderPlaced e) {
        kafka.send("orders.placed", e.orderId().toString(), e)        // ключ → партиция → порядок событий одного заказа
             .whenComplete((result, ex) -> {                          // send асинхронный: CompletableFuture<SendResult>
                 if (ex != null) log.error("send failed for order {}", e.orderId(), ex);
                 else log.debug("sent to {}-{}@{}", result.getRecordMetadata().topic(),
                         result.getRecordMetadata().partition(), result.getRecordMetadata().offset());
             });
    }
}

send() кладёт запись в буфер продюсера и сразу возвращается; фоновый поток kafka-producer-network-thread отправляет батчи. Метод может заблокироваться до max.block.ms, если буфер полон или нет метаданных. Игнорировать future нельзя: ошибка доставки иначе останется незамеченной.

18.3Как работает @KafkaListener

  1. KafkaListenerAnnotationBeanPostProcessor при инициализации бинов находит методы с @KafkaListener и регистрирует endpoint в KafkaListenerEndpointRegistry.
  2. Для каждого endpoint фабрика ConcurrentKafkaListenerContainerFactory создаёт ConcurrentMessageListenerContainer; он содержит concurrency штук KafkaMessageListenerContainer.
  3. Контейнеры — SmartLifecycle: стартуют в finishRefresh(), когда все бины готовы, и останавливаются первыми при закрытии контекста.
  4. Каждый дочерний контейнер запускает один поток (…-0-C-1) со своим KafkaConsumer (он не потокобезопасен) и крутит цикл: poll() → для каждой записи: конвертация аргументов → вызов вашего метода → коммит offset по AckMode.
@Component
class BillingListener {
    @KafkaListener(topics = "orders.placed", groupId = "billing", concurrency = "3")
    void onOrder(@Payload OrderPlaced event,
                 @Header(KafkaHeaders.RECEIVED_PARTITION) int partition,
                 @Header(KafkaHeaders.OFFSET) long offset) {
        billing.charge(event);            // исключение отсюда → ErrorHandler контейнера
    }
}
AckModeКогда коммитится offset
BATCH (по умолчанию)после обработки всех записей одного poll()
RECORDпосле каждой записи — меньше повторов при сбое, больше коммитов
MANUAL / MANUAL_IMMEDIATEкогда код вызвал Acknowledgment.acknowledge()
TIME, COUNTпо времени или числу записей

Spring Kafka выставляет enable.auto.commit=false и коммитит сам — после успешной обработки. Отсюда гарантия at-least-once: при падении между обработкой и коммитом запись придёт повторно. Обработчик должен быть идемпотентным (ключ идемпотентности, upsert, таблица обработанных событий).

18.4Обработка ошибок

Исключение слушателя ловит DefaultErrorHandler. По умолчанию: 10 попыток без паузы (FixedBackOff(0, 9)), затем запись логируется и пропускается. Между попытками контейнер делает seek назад на сбойный offset — партиция стоит, пока запись не обработана или не пропущена.

@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
    var recoverer = new DeadLetterPublishingRecoverer(template);     // → orders.placed-dlt (с Spring Kafka 3.3; раньше .DLT), та же партиция, заголовки с причиной
    var backOff = new ExponentialBackOffWithMaxRetries(4);            // 1с, 2с, 4с, 8с
    backOff.setInitialInterval(1000); backOff.setMultiplier(2.0);
    var handler = new DefaultErrorHandler(recoverer, backOff);
    handler.addNotRetryableExceptions(ValidationException.class);     // сразу в DLT, без повторов
    return handler;                                                    // Boot подключит бин к фабрике контейнеров
}
Симулятор: сбойное сообщение в партиции

В партиции записи с offset 0–5. Запись offset=2 вызывает исключение в слушателе.

18.5БД и Kafka: атомарности нет

@Transactional
public Order place(Cart cart) {
    Order o = repo.save(Order.from(cart));
    kafka.send("orders.placed", o.idString(), OrderPlaced.of(o));   // 1) ушло в Kafka, а транзакция потом откатилась → событие-призрак
    return o;                                                        // 2) или коммит прошёл, а send упал → событие потеряно
}

Транзакция БД и Kafka — разные системы; общий коммит возможен только через XA, который Kafka не поддерживает. Рабочие решения:

Transactional Outbox

В той же транзакции БД записать событие в таблицу outbox. Отдельный процесс (Debezium CDC или @Scheduled-поллер) читает таблицу и отправляет в Kafka, помечая отправленные. Гарантия at-least-once без потерь и призраков.

Идемпотентный потребитель

Раз доставка «минимум один раз», потребитель хранит id обработанных событий (уникальный индекс) в той же транзакции, что и свои изменения, и пропускает повторы.

@Transactional
public Order place(Cart cart) {
    Order o = repo.save(Order.from(cart));
    outbox.save(new OutboxEvent(UUID.randomUUID(), "orders.placed", o.idString(), json(OrderPlaced.of(o))));
    return o;
}

@Scheduled(fixedDelay = 500)
@SchedulerLock(name = "outbox-relay")                         // один экземпляр за раз (ShedLock)
void relay() {
    for (OutboxEvent e : outbox.findTop100ByPublishedAtIsNullOrderByCreatedAt()) {
        kafka.send(e.topic(), e.key(), e.payload()).join();   // дождаться подтверждения брокера
        outbox.markPublished(e.id());                         // упали между строками → повторная отправка → нужен идемпотентный потребитель
    }
}

Транзакции самой Kafka (transactional.id, KafkaTransactionManager) дают exactly-once только в цепочке «прочитал из Kafka → обработал → записал в Kafka»: offset и выходные записи коммитятся атомарно. К базе данных это не относится.

18.6Параллелизм и порядок

  • concurrency больше числа партиций бессмысленна: лишние потоки простаивают. Одна партиция — один потребитель группы.
  • Порядок гарантируется только внутри партиции, то есть для записей с одним ключом.
  • Долгая обработка: если между poll() проходит больше max.poll.interval.ms, брокер считает потребителя мёртвым → ребаланс → записи перечитает другой экземпляр → дубли. Уменьшайте max.poll.records или выносите тяжёлую работу.
  • Пакетный слушатель (List<ConsumerRecord>, spring.kafka.listener.type=batch) — для массовых вставок в БД.
  • Graceful shutdown: контейнер дожидается обработки текущих записей и коммитит offset-ы.

18.7Самопроверка

Что делает DefaultErrorHandler по умолчанию при постоянной ошибке в слушателе?

  • Останавливает контейнер
  • Повторяет бесконечно
  • 10 попыток без паузы, затем логирует и пропускает запись
  • Отправляет в DLT
FixedBackOff(0, 9) и восстановление «залогировать». DLT появляется, только если задать DeadLetterPublishingRecoverer.

Почему нельзя просто вызвать kafka.send() внутри @Transactional-метода, сохраняющего заказ?

  • Транзакция БД и Kafka не атомарны: возможны событие без заказа или заказ без события
  • KafkaTemplate не работает в транзакциях
  • Это замедляет запрос
  • Kafka требует autocommit
Проблема двойной записи. Решения — outbox или события AFTER_COMMIT с допущением потерь при падении.

В топике 4 партиции, у слушателя concurrency = 10, приложение в одном экземпляре. Сколько потоков реально обрабатывают сообщения?

  • 10
  • 1
  • 40
  • 4 — по одному потребителю на партицию, остальные 6 простаивают
Партицию в группе читает ровно один потребитель.
Что происходит от старта приложения до вызова метода @KafkaListener?

BPP регистрирует endpoint → фабрика создаёт ConcurrentMessageListenerContainer → он стартует как SmartLifecycle в finishRefresh → каждый дочерний контейнер в своём потоке создаёт KafkaConsumer, подписывается, в цикле делает poll, для каждой записи конвертирует аргументы и вызывает метод, затем коммитит offset по AckMode; исключения идут в ErrorHandler.

Как обеспечить обработку «ровно один раз» по эффекту?

Доставка at-least-once + идемпотентность потребителя: уникальный id события, таблица обработанных в одной транзакции с бизнес-изменениями, либо естественно идемпотентные операции (upsert, установка статуса). На стороне отправителя — outbox и идемпотентный продюсер.

Блокирующие и неблокирующие ретраи — в чём компромисс?

Блокирующие (DefaultErrorHandler с backoff): порядок в партиции сохраняется, но партиция стоит на время повторов, риск превысить max.poll.interval.ms. Неблокирующие (@RetryableTopic): запись уходит в retry-топики с задержками, основная партиция идёт дальше, но порядок нарушается и появляется дополнительная инфраструктура топиков.
