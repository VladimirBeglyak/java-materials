AOT, GraalVM native image и быстрый старт

Классический Spring делает много работы при запуске: сканирует classpath, читает аннотации, вычисляет условия, генерирует прокси. Это даёт гибкость, но стоит секунд старта и сотен мегабайт памяти. Spring AOT переносит часть этой работы на этап сборки, а GraalVM компилирует приложение в нативный исполняемый файл. Разберём, что именно переносится, чем за это платят и какие есть промежуточные варианты.

1. Обычная компиляция

Ваш код компилируется как всегда. Затем плагин Boot (org.springframework.boot.aot в Gradle, process-aot в Maven) запускает отдельный процесс — SpringApplicationAotProcessor.

2. Контекст доводится до конца шага 5 refresh()

AOT-процессор создаёт ApplicationContext и выполняет refreshForAotProcessing: пост-процессоры фабрики отрабатывают (сканирование, @Import, автоконфигурация, все условия), но обычные бины не создаются. Получается итоговый набор BeanDefinition.

Условия вычисляются с окружением сборки: @ConditionalOnProperty, @Profile, @ConditionalOnClass решаются сейчас и навсегда.

3. BeanDefinition → Java-код

// сгенерировано: OrderService__BeanDefinitions.java
public class OrderService__BeanDefinitions {
    public static BeanDefinition getOrderServiceBeanDefinition() {
        RootBeanDefinition bd = new RootBeanDefinition(OrderService.class);
        bd.setInstanceSupplier(BeanInstanceSupplier.<OrderService>forConstructor(OrderRepository.class, PaymentClient.class)
            .withGenerator((registeredBean, args) -> new OrderService(args.get(0), args.get(1))));  // прямой вызов конструктора
        return bd;
    }
}

И один ShopApplication__ApplicationContextInitializer, который регистрирует все описания. Точки @Autowired на полях тоже превращаются в код.

4. Подсказки для native image

GraalVM должен заранее знать обо всей рефлексии, ресурсах, JDK-прокси и сериализации. Spring собирает RuntimeHints: методы контроллеров, DTO для Jackson, @ConfigurationProperties, application.yml, интерфейсы репозиториев — и пишет их в META-INF/native-image/…/reachability-metadata.json (единый формат GraalVM в Spring 7; до 6.2 — reflect-config.json, resource-config.json и соседние файлы).

5. Классы прокси генерируются при сборке

В нативном образе нельзя создавать классы в рантайме. Поэтому CGLIB-подклассы для @Configuration, AOP-прокси (@Transactional…) и scoped proxy генерируются сейчас и записываются как обычные .class.

6. Компиляция GraalVM (только для native)

native-image выполняет статический анализ достижимости от main: в бинарник попадает только код, который может быть вызван («закрытый мир»). Весь байткод компилируется в машинный, часть классов инициализируется при сборке, и их состояние сохраняется в образе кучи. Результат — один исполняемый файл без JVM.

7. Старт AOT-приложения

SpringApplication видит AOT-режим и вместо разбора конфигурации вызывает сгенерированный инициализатор. Нет сканирования, нет чтения аннотаций, нет вычисления условий, нет генерации классов. Дальше обычные шаги: создание бинов (через instance supplier — прямые вызовы конструкторов), BeanPostProcessor-ы, lifecycle.

8. Что нельзя после AOT

  • Менять набор бинов профилями и свойствами при запуске: условия уже вычислены. Значения свойств менять можно.
  • Рефлексия, Class.forName, ресурсы без подсказки → MissingReflectionRegistrationError / ClassNotFoundException в нативном образе.
  • Java-агенты, динамическая загрузка классов, часть библиотек с генерацией байткода.

@Configuration
@ImportRuntimeHints(ReportHints.class)
@RegisterReflectionForBinding({ ReportRow.class, ReportMeta.class })     // DTO, которые сериализуются «вручную»
class ReportConfig { }

class ReportHints implements RuntimeHintsRegistrar {
    @Override public void registerHints(RuntimeHints hints, ClassLoader cl) {
        hints.resources().registerPattern("templates/*.xlsx");
        hints.reflection().registerType(LegacyFormatter.class, MemberCategory.INVOKE_PUBLIC_METHODS);
        hints.proxies().registerJdkProxy(ReportListener.class);
    }
}

Как узнать, каких подсказок не хватает: запустить обычное приложение с агентом трассировки GraalVM (-agentlib:native-image-agent=config-output-dir=…) под тестами; для библиотек — общий репозиторий GraalVM Reachability Metadata, который подключает плагин сборки. Проверка в тестах: RuntimeHintsPredicates и запуск тестов в нативном режиме (./gradlew nativeTest).

./gradlew nativeCompile              # бинарник в build/native/nativeCompile/
./gradlew bootBuildImage             # контейнер с нативным приложением через buildpacks (GraalVM локально не нужен)
java -Dspring.aot.enabled=true -jar app.jar     # AOT-режим на обычной JVM

17.5CDS и AOT cache JDK: дешёвое ускорение

Class Data Sharing сохраняет в архив уже разобранные и проверенные классы; при следующем запуске JVM отображает архив в память, а не загружает классы заново. В JDK 24 это развилось в AOT cache (JEP 483, двухшаговый вариант), в JDK 25 — одношаговый -XX:AOTCacheOutput (JEP 514/515); Spring Boot поддерживает AOT cache с Java 25: кэшируются ещё и результаты линковки и профили методов.

RUN java -Djarmode=tools -jar app.jar extract --destination app          # распакованный вид: быстрее и нужен для CDS
WORKDIR /app
# тренировочный запуск: поднять контекст и сразу выйти
RUN java -XX:AOTCacheOutput=app.aot -Dspring.context.exit=onRefresh -jar app.jar
ENTRYPOINT ["java", "-XX:AOTCache=app.aot", "-jar", "app.jar"]
# JDK 21–23: -XX:ArchiveClassesAtExit=app.jsa  →  -XX:SharedArchiveFile=app.jsa

Условия: тот же JDK, тот же classpath и порядок jar. Buildpacks делают это одной настройкой (BP_JVM_CDS_ENABLED=true).

17.6Другие рычаги

Ленивая инициализация

spring.main.lazy-initialization=true — бины создаются при первом обращении. Старт быстрее, но ошибки конфигурации всплывают на первом запросе, а первый запрос медленный. Годится для локальной разработки и тестов, в проде — осторожно.

Меньше работы

Уберите ненужные стартеры (каждый — автоконфигурации и классы), отключите неиспользуемое (spring.jmx.enabled=false уже по умолчанию), найдите медленные бины через /actuator/startup. Самые тяжёлые обычно Hibernate (метамодель), Flyway/Liquibase, клиенты с прогревом.

17.7Самопроверка

Приложение собрано с Spring AOT с профилем default. При запуске указали --spring.profiles.active=prod, в коде есть @Bean @Profile("prod"). Появится ли этот бин?

  • Да, профили вычисляются при старте
  • Нет: условия, включая @Profile, вычислены при сборке, набор бинов зафиксирован
  • Да, но без зависимостей
  • Приложение не запустится
AOT фиксирует результат шага invokeBeanFactoryPostProcessors. Профиль при запуске влияет только на значения свойств (файлы application-prod.yml).

Почему в native image нужны RuntimeHints для рефлексии?

  • Рефлексия в GraalVM запрещена
  • Для ускорения JIT
  • Это требование Spring, а не GraalVM
  • Статический анализ включает в образ только достижимый код; о классах и методах, вызываемых через рефлексию, компилятор не знает, если ему не сообщить
«Закрытый мир»: всё, что не видно анализу и не объявлено в метаданных, в бинарнике отсутствует.

Какой способ ускорить старт требует меньше всего изменений и почти не имеет ограничений?

  • CDS / AOT cache JDK с тренировочным запуском
  • GraalVM native image
  • Переписать на WebFlux
  • CRaC
Поведение приложения не меняется, нужна только стадия сборки образа. Native и CRaC дают больше, но с ограничениями.
Что именно Spring AOT делает на этапе сборки?

Поднимает контекст до конца обработки BeanFactoryPostProcessor-ов (без создания бинов), вычисляет условия, и по итоговым BeanDefinition генерирует: Java-код регистрации описаний и создания бинов без рефлексии, классы прокси, RuntimeHints (рефлексия, ресурсы, прокси, сериализация). На старте вместо разбора конфигурации выполняется сгенерированный ApplicationContextInitializer.

Чем приходится платить за native image?

Долгая и ресурсоёмкая сборка; закрытый мир — нет динамической загрузки классов, агентов, часть библиотек требует метаданных; набор бинов фиксирован; пиковая производительность без PGO ниже JIT; другой GC по умолчанию (Serial в community-версии); отладка и профилирование сложнее; тесты надо гонять и в нативном режиме.

Как найти, что тормозит старт приложения?

BufferingApplicationStartup + /actuator/startup (длительности шагов и бинов), DEBUG-лог создания бинов, JFR с FlightRecorderApplicationStartup, отчёт условий для лишних автоконфигураций. Затем: убрать лишние стартеры, отложить тяжёлую инициализацию, CDS/AOT cache.
