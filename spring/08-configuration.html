Внешняя конфигурация и @ConfigurationProperties

Один и тот же jar запускается локально, в тесте и на проде — отличаются только настройки. Boot читает их из полутора десятков источников в строгом порядке. Нужно точно знать, какой источник побеждает, как имя spring.datasource.hikari.maximum-pool-size превращается в переменную окружения и как получить настройки в код типобезопасно и с валидацией.

8.1Порядок источников: кто побеждает

От низшего приоритета к высшему (поздний перекрывает ранний):

  1. Свойства по умолчанию: SpringApplication.setDefaultProperties
  2. @PropertySource на @Configuration (добавляются в Environment только во время refresh контекста — для logging.* и spring.main.* слишком поздно)
  3. Файлы конфигурации: application.yml в jar → application-{profile}.yml в jar → application.yml рядом с jar → application-{profile}.yml рядом с jar
  4. random.*
  5. Переменные окружения ОС
  6. Системные свойства Java (-D)
  7. JNDI, параметры ServletContext/ServletConfig
  8. SPRING_APPLICATION_JSON
  9. Аргументы командной строки (--server.port=9000)
  10. В тестах: properties у @SpringBootTest → @DynamicPropertySource → @TestPropertySource
  11. Глобальные настройки devtools (~/.config/spring-boot)
Симулятор: какое значение получит server.port

Профиль prod активен. Включайте источники и меняйте значения. Список отсортирован от высшего приоритета к низшему.

В одном месте .properties перекрывает .yml. Не держите оба формата — это путает. Для отладки «откуда взялось значение» используйте /actuator/env/server.port: он покажет все источники, где ключ задан, и победителя.

8.2Файлы конфигурации

Boot ищет application.* в classpath:/, classpath:/config/, ./, ./config/, ./config/*/ — каждое следующее место перекрывает предыдущее. Переопределить: spring.config.location (заменяет) или spring.config.additional-location (добавляет).

spring:
  application:
    name: shop
  config:
    import:
      - optional:file:./secrets.yml            # optional: — не падать, если файла нет
      - optional:configtree:/run/secrets/      # каждый файл в каталоге = свойство (Kubernetes secrets)
server:
  port: 8080
---
spring:
  config:
    activate:
      on-profile: prod                         # этот документ — только для prod
server:
  port: 80
shop:
  payments:
    timeout: 3s

Документы внутри файла (---) обрабатываются сверху вниз, нижние перекрывают верхние. spring.profiles.active нельзя задавать в профильном документе — профили определяются до их чтения.

8.3Relaxed binding: одно свойство — много написаний

Каноническая форма имени — kebab-case в нижнем регистре: shop.payments.retry-count. При биндинге к @ConfigurationProperties подходят и shop.payments.retryCount, shop.payments.retry_count, и переменная SHOP_PAYMENTS_RETRYCOUNT. Внутри Boot все источники оборачиваются в ConfigurationPropertySource, который нормализует имена к ConfigurationPropertyName.

Имя свойства → переменная окружения

8.4@ConfigurationProperties

@ConfigurationProperties("shop.payments")
@Validated                                              // JSR-380: ошибка — на старте, а не в рантайме
public record PaymentProperties(
        @NotNull URI gatewayUrl,
        @DefaultValue("5s") Duration timeout,           // "5s", "PT5S", "5000ms"
        @DefaultValue("3") @Min(0) @Max(10) int retryCount,
        @DefaultValue("1MB") DataSize maxPayload,
        Map<String, Merchant> merchants,                // shop.payments.merchants.acme.api-key=…
        List<String> allowedCurrencies) {               // shop.payments.allowed-currencies=RUB,USD

    public record Merchant(String apiKey, @DefaultValue("true") boolean enabled) { }
}

@SpringBootApplication
@ConfigurationPropertiesScan                            // или @EnableConfigurationProperties(PaymentProperties.class)
class ShopApplication { }

@Service
class PaymentService {
    PaymentService(PaymentProperties props) { /* обычный бин — внедряется как любой другой */ }
}

Как это работает внутри

  1. @EnableConfigurationProperties (или сканирование) регистрирует описание бина-настроек и инфраструктуру: ConfigurationPropertiesBindingPostProcessor, ConfigurationPropertiesBinder.
  2. Для record/класса с одним конструктором с параметрами используется constructor binding: ValueObjectBinder создаёт объект, разрешая каждый параметр по имени. Для JavaBean-класса с сеттерами — JavaBeanBinder в postProcessBeforeInitialization.
  3. Binder обходит ConfigurationPropertySources (тот же Environment, но с нормализацией имён), конвертирует значения через ApplicationConversionService (единицы для Duration/DataSize, списки из строки через запятую).
  4. Если класс помечен @Validated, результат проверяется валидатором; ошибка → BindValidationException и понятный отчёт при старте.

8.5Секреты и окружения

Не в git

Пароли и ключи — в переменных окружения, Kubernetes Secret (смонтированный как configtree), Vault (spring.config.import=vault:// через Spring Cloud Vault). В application.yml оставляйте плейсхолдеры: password: ${DB_PASSWORD}.

Сокрытие в Actuator

/actuator/env и /configprops маскируют значения (management.endpoint.env.show-values=never по умолчанию с Boot 3). Не открывайте эти endpoints наружу.

8.6Самопроверка

server.port=8080 в application.yml внутри jar, SERVER_PORT=9000 в окружении, запуск с --server.port=7000. Какой порт?

  • 8080
  • 9000
  • 7000
  • Ошибка конфликта
Аргументы командной строки — выше переменных окружения, а те — выше файлов.

Как задать через переменную окружения свойство shop.retry-count?

  • SHOP_RETRYCOUNT
  • SHOP_RETRY-COUNT
  • shop.retry-count
  • SHOP__RETRY__COUNT
Точки → подчёркивания, дефисы удаляются, верхний регистр.

В record с @ConfigurationProperties поле Duration timeout, а в yml timeout: 30. Что получится?

  • 30 секунд
  • 30 миллисекунд — единица по умолчанию для Duration
  • Ошибка биндинга
  • 30 минут
Число без единицы трактуется в миллисекундах, если не указано @DurationUnit. Пишите единицы явно: 30s.
Назовите порядок приоритета основных источников конфигурации Spring Boot.

По возрастанию: default properties → @PropertySource → файлы (в jar, профильные в jar, снаружи, профильные снаружи) → random → переменные окружения → системные свойства → SPRING_APPLICATION_JSON → аргументы командной строки → тестовые источники → devtools.

Чем @ConfigurationProperties лучше @Value?

Типобезопасная группировка, relaxed binding, вложенные структуры и коллекции, валидация на старте, неизменяемость через record, метаданные для IDE, единое место для настроек вместо разбросанных строк-ключей.

Как Boot сопоставляет SPRING_DATASOURCE_URL и spring.datasource.url?

Источник переменных окружения оборачивается в SystemEnvironmentPropertySource/ConfigurationPropertySource, который умеет преобразовывать канонические имена: при поиске spring.datasource.url проверяются варианты SPRING_DATASOURCE_URL и др. Это сопоставление работает для @ConfigurationProperties и Environment.getProperty с каноническими именами.
