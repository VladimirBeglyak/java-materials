Spring Security изнутри

Spring Security — это цепочка servlet-фильтров перед вашим приложением плюс AOP-перехватчики на методах. Каждый фильтр отвечает за одну задачу: восстановить контекст, проверить CSRF, аутентифицировать по токену, решить, пускать ли. Разобравшись в цепочке, вы ответите, откуда 401, а откуда 403, почему CORS-запрос падает до контроллера и как пользователь попадает в SecurityContextHolder.

13.2Конфигурация resource server с JWT

@Configuration
@EnableWebSecurity
@EnableMethodSecurity                                         // @PreAuthorize на методах
class SecurityConfig {

    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        return http
            .securityMatcher("/api/**")
            .authorizeHttpRequests(a -> a
                .requestMatchers(HttpMethod.GET, "/api/products/**").permitAll()
                .requestMatchers("/api/admin/**").hasAuthority("SCOPE_admin")
                .anyRequest().authenticated())
            .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))   // BearerTokenAuthenticationFilter + JwtDecoder
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .cors(Customizer.withDefaults())                          // ищет бин CorsConfigurationSource
            .build();
    }

    @Bean
    CorsConfigurationSource cors() {
        var c = new CorsConfiguration();
        c.setAllowedOrigins(List.of("https://shop.ru"));
        c.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE"));
        c.setAllowedHeaders(List.of("Authorization", "Content-Type"));
        var src = new UrlBasedCorsConfigurationSource();
        src.registerCorsConfiguration("/api/**", c);
        return src;
    }
}

@Bean
JwtAuthenticationConverter jwtAuthConverter() {
    var authorities = new JwtGrantedAuthoritiesConverter();
    authorities.setAuthoritiesClaimName("roles");          // claim "roles": ["ADMIN","USER"]
    authorities.setAuthorityPrefix("ROLE_");               // hasRole('ADMIN') проверяет ROLE_ADMIN
    var c = new JwtAuthenticationConverter();
    c.setJwtGrantedAuthoritiesConverter(authorities);
    return c;
}

13.5Авторизация: URL и методы

По URL

AuthorizationFilter + RequestMatcherDelegatingAuthorizationManager: правила проверяются по порядку, срабатывает первое совпавшее. Общие правила (anyRequest) — в конце. Роль — authority с префиксом ROLE_: hasRole("ADMIN") ≡ hasAuthority("ROLE_ADMIN").

По методам

@EnableMethodSecurity регистрирует advisors с AuthorizationManagerBeforeMethodInterceptor. Это AOP-прокси — те же ограничения, что у @Transactional: self-invocation не проверяется. @PostAuthorize, @PreFilter работают на результате/аргументах.

@Service
class OrderQueries {
    @PreAuthorize("hasAuthority('SCOPE_orders.read') and #customerId == authentication.name")
    List<OrderDto> forCustomer(String customerId) { /* ... */ }

    @PostAuthorize("returnObject.ownerId == authentication.name or hasRole('SUPPORT')")
    OrderDto get(long id) { /* проверка ПОСЛЕ выполнения — для чтения по id */ }
}

13.8Самопроверка

Зачем нужен DelegatingFilterProxy?

  • Для шифрования запроса
  • Servlet-контейнер регистрирует фильтры до создания Spring-бинов; прокси лениво находит бин springSecurityFilterChain и делегирует ему
  • Чтобы обойти CORS
  • Для асинхронных запросов
Он связывает жизненный цикл servlet-фильтров с контейнером Spring: сама цепочка Security — бин со всеми зависимостями.

Аноним обратился к защищённому URL. Какой фильтр выбросит исключение и какой сформирует ответ?

  • BearerTokenAuthenticationFilter бросит, он же ответит 401
  • AnonymousAuthenticationFilter бросит, ExceptionTranslationFilter ответит 403
  • CsrfFilter бросит и ответит 403
  • AuthorizationFilter бросит AccessDeniedException, ExceptionTranslationFilter увидит анонима и вызовет AuthenticationEntryPoint → 401
ExceptionTranslationFilter стоит перед AuthorizationFilter и ловит его исключения; для анонима отказ трактуется как требование аутентификации.

@Async-метод вызывает SecurityContextHolder.getContext().getAuthentication(). Что получит?

  • null — контекст лежит в ThreadLocal потока запроса и в поток пула не переносится без DelegatingSecurityContextExecutor
  • Пользователя запроса
  • Системного пользователя
  • Исключение
Стратегия по умолчанию — MODE_THREADLOCAL. Перенос — декоратор задач или executor-обёртка Spring Security.
Как устроена цепочка фильтров Spring Security?

DelegatingFilterProxy (servlet-фильтр) → FilterChainProxy (бин) → выбор SecurityFilterChain по securityMatcher → упорядоченные фильтры: контекст (SecurityContextHolderFilter), заголовки, CORS, CSRF, logout, аутентификация (Bearer/Basic/форма), request cache, anonymous, ExceptionTranslationFilter, AuthorizationFilter. В конце запроса контекст очищается.

Как проходит аутентификация по JWT?

BearerTokenAuthenticationFilter извлекает токен → BearerTokenAuthenticationToken → AuthenticationManager → JwtAuthenticationProvider: JwtDecoder проверяет подпись (ключи JWKS по issuer), срок (exp/nbf), issuer; audience — только если задано spring.security.oauth2.resourceserver.jwt.audiences → JwtAuthenticationConverter делает authorities (по умолчанию из scope с префиксом SCOPE_) → JwtAuthenticationToken в SecurityContextHolder. Сессия не создаётся, проверка на каждом запросе.

Нужен ли CSRF для REST API?

CSRF возможен, когда браузер автоматически прикладывает учётные данные — cookie сессии или Basic. Если API аутентифицируется только токеном в заголовке Authorization, который JavaScript добавляет явно, CSRF-атака невозможна, защиту отключают. Для SPA с cookie-сессией CSRF нужен (CookieCsrfTokenRepository + заголовок X-XSRF-TOKEN).

Чем hasRole отличается от hasAuthority?

Authority — произвольная строка-право. Роль — соглашение: authority с префиксом ROLE_. hasRole("ADMIN") проверяет ROLE_ADMIN, hasAuthority("ADMIN") — ровно ADMIN. Scope из JWT по умолчанию становятся SCOPE_xxx.
