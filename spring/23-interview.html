23.1Как отвечать

  1. Определение одной фразой. «@Transactional — декларативное управление транзакцией через AOP-прокси».
  2. Механизм. Кто создаёт (BeanPostProcessor), что перехватывает (TransactionInterceptor), где состояние (ThreadLocal в TransactionSynchronizationManager).
  3. Следствия и ловушки. Self-invocation, checked-исключения, другой поток.
  4. Практика. Случай из своего опыта: как проявилось, как нашли, как исправили.
Не знаете точного ответа — рассуждайте от механизма: «Аннотация работает через прокси, значит, вызов через this её не увидит». Умение вывести поведение из устройства ценится выше заученного ответа.

23.3Найдите ошибку

Типичная часть собеседования: показывают код и спрашивают, что с ним не так.

@Service
class UserService {
    @Transactional
    public void register(User u) throws IOException {
        repo.save(u);
        mailer.sendWelcome(u);      // бросает IOException
    }
}

Письмо не отправилось (IOException). Что с пользователем в БД?

  • Не сохранён — транзакция откатится
  • Сохранён — checked-исключение не откатывает транзакцию
  • Зависит от уровня изоляции
  • Сохранён частично
По умолчанию откат только на RuntimeException и Error. Нужен rollbackFor = Exception.class, а отправку письма лучше вынести в AFTER_COMMIT-слушатель.
@Service
class ReportService {
    public void generateAll(List<Long> ids) { ids.forEach(this::generate); }

    @Async
    public void generate(Long id) { /* 30 секунд */ }
}

generateAll(100 ids) вызван из контроллера. Что произойдёт?

  • 100 задач уйдут в пул, метод вернётся сразу
  • Ошибка компиляции
  • Все 100 отчётов выполнятся синхронно в потоке запроса — 50 минут
  • Выполнится только первый
this::generate — вызов мимо прокси. @Async не сработает. Вынести generate в отдельный бин.
@Component
class PriceCache {
    private final Map<String, Price> cache = new HashMap<>();
    public Price get(String sku) { return cache.computeIfAbsent(sku, loader::load); }
}

Что не так с этим бином?

  • Singleton с изменяемым непотокобезопасным состоянием: HashMap под конкурентным доступом из потоков запросов
  • Нужен @Scope("prototype")
  • Нельзя иметь поля в @Component
  • Всё в порядке
Singleton-бин разделяется всеми потоками. Нужен ConcurrentHashMap, а лучше — Caffeine/@Cacheable с лимитом и TTL.
@RestController
class OrderController {
    @GetMapping("/orders/{id}")
    Order get(@PathVariable long id) { return orderRepository.findById(id).orElseThrow(); }   // Order — JPA-сущность с @OneToMany(lazy) items
}
// application.yml: spring.jpa.open-in-view: false

Что произойдёт при запросе?

  • Вернётся заказ без items
  • Вернётся заказ с items одним запросом
  • 404
  • LazyInitializationException при сериализации: Jackson обращается к items после закрытия EntityManager
Сущность detached, ленивая коллекция не инициализирована. Возвращайте DTO, собранный в транзакции сервиса с нужной выборкой.
@Configuration
class AppConfig {
    @Bean BeanFactoryPostProcessor customizer() { return bf -> { /* ... */ }; }
    @Value("${app.name}") private String name;
    @Bean Greeter greeter() { return new Greeter(name); }
}

В чём проблема?

  • Нельзя объявлять BeanFactoryPostProcessor как @Bean
  • Нестатический @Bean-метод с BFPP заставляет создать AppConfig слишком рано — @Value не обработается, name будет null
  • @Value нельзя использовать в @Configuration
  • Проблем нет
BFPP нужен до регистрации BeanPostProcessor-ов, обрабатывающих @Value/@Autowired. Метод должен быть static.
@Service
class TransferService {
    @Transactional
    public void transfer(long from, long to, BigDecimal amount) {
        accounts.debit(from, amount);
        CompletableFuture.runAsync(() -> accounts.credit(to, amount));
    }
}

Что не так?

  • CompletableFuture нельзя использовать в Spring
  • Ничего, это оптимизация
  • credit выполняется в другом потоке вне транзакции: при откате debit он не откатится, и наоборот
  • Нужен propagation = NESTED
Транзакция привязана к потоку. Атомарность перевода потеряна; к тому же ошибка в credit нигде не обрабатывается.
@Component
class Scheduler {
    @Scheduled(fixedRate = 1000)
    void poll() throws InterruptedException { Thread.sleep(5000); }     // медленная задача

    @Scheduled(fixedRate = 1000)
    void heartbeat() { log.info("alive"); }
}

Как часто будет печататься «alive» в Boot по умолчанию?

  • Примерно раз в 5 секунд: планировщик однопоточный, poll блокирует его
  • Каждую секунду
  • Никогда
  • 5 раз в секунду
spring.task.scheduling.pool.size=1 по умолчанию. Увеличить пул или включить виртуальные потоки.
@SpringBootTest
class OrderServiceTest {
    @MockitoBean PaymentClient payments;
    // ...
}
@SpringBootTest
class RefundServiceTest {
    @MockitoBean PaymentClient payments;
    @MockitoBean MailSender mail;

Сколько контекстов поднимется для этих двух классов?

  • Один
  • Два: наборы подменённых бинов разные — разные ключи кэша
  • Четыре
  • Ни одного

23.4Практические задачи

1. Напишите свой @Timed-аспект, публикующий метрику времени выполнения.

@Aspect + @Around("@annotation(timed)"), Timer.Sample из Micrometer, stop в finally; @Order(HIGHEST_PRECEDENCE), чтобы охватить транзакцию. Обсудите: self-invocation, кардинальность тегов, что есть готовый @Timed/@Observed. Образец — тема 04.

2. Реализуйте идемпотентный POST /payments с заголовком Idempotency-Key.

Таблица idempotency_keys с уникальным ключом и сохранённым ответом. В одной транзакции: вставка ключа (конфликт → вернуть сохранённый ответ или 409, если ещё обрабатывается) + бизнес-операция + сохранение ответа. Обсудите: гонку двух одинаковых запросов (уникальный индекс решает), TTL ключей, что делать при падении посередине.

3. Сервис должен обрабатывать заказы пачками по 100 так, чтобы ошибка одной пачки не откатывала остальные.

Цикл в методе БЕЗ транзакции, каждая пачка — через TransactionTemplate или метод другого бина с @Transactional (не this!). Обсудите: REQUIRES_NEW не нужен, если внешней транзакции нет; очистку persistence context (em.clear) между пачками; повторяемость.

4. Напишите свой стартер, добавляющий в каждый сервис фильтр с X-Request-Id.

Модуль autoconfigure: @AutoConfiguration + @ConditionalOnWebApplication(SERVLET) + @ConditionalOnMissingBean + @ConfigurationProperties с enabled; FilterRegistrationBean с порядком; файл AutoConfiguration.imports; тест через WebApplicationContextRunner. Образец — тема 07.

5. Запрос GET /orders отдаёт 50 заказов за 2 секунды. Найдите и исправьте причину.

Включить лог SQL или счётчик запросов → увидеть N+1 по items/customer → заменить на DTO-проекцию или @EntityGraph/join fetch; проверить пагинацию (fetch join + Pageable пагинирует в памяти) → два запроса: id страницы, затем выборка с fetch по id; индексы под сортировку.

6. Спроектируйте надёжную отправку письма после регистрации пользователя.

Варианты по возрастанию надёжности: @Async после сохранения (теряется при падении, гонка с коммитом) → @TransactionalEventListener(AFTER_COMMIT) (не теряет согласованность, но теряет событие при падении) → outbox / Spring Modulith Event Publication Registry (at-least-once, нужна идемпотентность отправки).

7. Приложение стартует 40 секунд. Ваши действия?

BufferingApplicationStartup + /actuator/startup, DEBUG создания бинов → найти медленные бины (Hibernate, миграции, прогрев клиентов, сканирование лишних пакетов) → убрать лишние стартеры, отложить инициализацию, исключить ненужные автоконфигурации → CDS/AOT cache → при требованиях serverless — native image.
