ТЕМА 07 · SPRING BOOT

Автоконфигурация и стартеры

Добавили spring-boot-starter-data-jpa и строку spring.datasource.url — и в контексте появились DataSource, пул Hikari, EntityManagerFactory, менеджер транзакций и репозитории. Это не магия, а около полутора сотен обычных @Configuration-классов с условиями. Разберём, как Boot их находит, в каком порядке применяет и почему ваш бин всегда побеждает.

~3 часа@ConditionalAutoConfiguration.importsсвой стартеринтерактив

7.1Идея: бины по умолчанию, которые уступают

Каждая автоконфигурация отвечает на два вопроса: есть ли технология (класс на classpath, свойство задано) и не сделал ли пользователь это сам (бина такого типа ещё нет). Если технология есть, а бина нет — создаётся разумный бин по умолчанию. Если вы объявили свой — автоконфигурация отступает (back off). Поэтому настройка Boot — это почти всегда либо свойство, либо свой бин.

7.2Механизм загрузки

@EnableAutoConfiguration@Import(AutoConfigurationImportSelector.class) — это DeferredImportSelector: срабатывает после разбора всей вашей конфигурации
↓
ImportCandidates.load(AutoConfiguration.class)читает все файлы META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports на classpath (с Boot 2.7; spring.factories для автоконфигурации не поддерживается с 3.0)
↓
exclusions@SpringBootApplication(exclude = …), excludeName, свойство spring.autoconfigure.exclude
↓
AutoConfigurationImportFilter: быстрый фильтрOnClassCondition, OnWebApplicationCondition, OnBeanCondition по предвычисленным метаданным META-INF/spring-autoconfigure-metadata.properties — без загрузки классов
↓
AutoConfigurationSorterсортировка: по алфавиту → @AutoConfigureOrder → @AutoConfiguration(before/after) — топологически
↓
ConfigurationClassParserкаждый класс разбирается как обычная @Configuration: условия на классе и на каждом @Bean

Быстрый фильтр важен для скорости: из ~150 кандидатов большая часть отбрасывается по отсутствию классов, причём без загрузки самих классов автоконфигурации. Метаданные генерирует spring-boot-autoconfigure-processor при сборке Boot.

Spring Boot 4 Монолитный модуль spring-boot-autoconfigure разделён на модули по технологиям (spring-boot-jdbc, spring-boot-webmvc, spring-boot-data-jpa…), и автоконфигурации переехали в пакеты вида org.springframework.boot.jdbc.autoconfigure. Механизм, описанный здесь, не изменился.

7.3Условия

АннотацияСрабатывает, если
@ConditionalOnClass / OnMissingClassкласс есть / нет на classpath
@ConditionalOnBean / OnMissingBeanбин такого типа (имени, аннотации) уже зарегистрирован / не зарегистрирован
@ConditionalOnSingleCandidateровно один бин типа или один @Primary
@ConditionalOnPropertyсвойство задано; havingValue — равно значению; matchIfMissing — считать выполненным, если свойства нет
@ConditionalOnBooleanProperty (3.5+)короткая форма для булевых свойств
@ConditionalOnWebApplication(type = SERVLET)тип приложения
@ConditionalOnResourceресурс существует (classpath:logback.xml)
@ConditionalOnThreading(VIRTUAL)включены виртуальные потоки
@ConditionalOnExpression, OnJava, OnCloudPlatformSpEL, версия Java, Kubernetes/Cloud Foundry

Все они — мета-аннотации над @Conditional(SomeCondition.class), где Condition.matches(ConditionContext, AnnotatedTypeMetadata) получает реестр, Environment, ClassLoader. Boot-условия наследуют SpringBootCondition, который записывает каждое решение в ConditionEvaluationReport.

Почему @ConditionalOnClass(Foo.class) не падает, когда Foo нет Аннотации классов конфигурации читаются из байткода через ASM (AnnotationMetadata), а не через рефлексию — ссылка на отсутствующий класс остаётся просто строкой. Но если условие стоит на @Bean-методе класса, который сам загружается рефлексией, ссылка на отсутствующий класс в сигнатуре даст NoClassDefFoundError. Поэтому Boot выносит такие бины во вложенные статические классы-конфигурации с условием на классе.
@ConditionalOnMissingBean в своей конфигурации Условие проверяет бины, зарегистрированные к этому моменту. В автоконфигурации это надёжно: она обрабатывается после пользовательской конфигурации. В обычных @Configuration порядок разбора не гарантирован — условие может «не увидеть» бин, объявленный в другом классе. Используйте эти условия только в автоконфигурациях.

7.4Пример: как устроена DataSourceAutoConfiguration

@AutoConfiguration(before = SqlInitializationAutoConfiguration.class)
@ConditionalOnClass({ DataSource.class, EmbeddedDatabaseType.class })   // spring-jdbc на classpath
@ConditionalOnMissingBean(type = "io.r2dbc.spi.ConnectionFactory")
@EnableConfigurationProperties(DataSourceProperties.class)              // spring.datasource.*
public class DataSourceAutoConfiguration {

    @Configuration(proxyBeanMethods = false)
    @Conditional(EmbeddedDatabaseCondition.class)       // нет url, нет пула, есть H2/HSQL/Derby
    @ConditionalOnMissingBean({ DataSource.class, XADataSource.class })
    @Import(EmbeddedDataSourceConfiguration.class)
    protected static class EmbeddedDatabaseConfiguration { }

    @Configuration(proxyBeanMethods = false)
    @Conditional(PooledDataSourceCondition.class)       // есть Hikari/Tomcat/DBCP2 или spring.datasource.type
    @ConditionalOnMissingBean({ DataSource.class, XADataSource.class })
    @Import({ DataSourceConfiguration.Hikari.class, DataSourceConfiguration.Tomcat.class,
              DataSourceConfiguration.Dbcp2.class, DataSourceConfiguration.Generic.class })
    protected static class PooledDataSourceConfiguration { }
}

// DataSourceConfiguration.Hikari:
@ConditionalOnClass(HikariDataSource.class)
@ConditionalOnProperty(name = "spring.datasource.type", havingValue = "com.zaxxer.hikari.HikariDataSource", matchIfMissing = true)
static class Hikari {
    @Bean @ConfigurationProperties("spring.datasource.hikari")   // spring.datasource.hikari.* → сеттеры пула
    HikariDataSource dataSource(DataSourceProperties props, JdbcConnectionDetails details) { /* ... */ }
}

7.5Диагностика

Отчёт условий

java -jar app.jar --debug или debug=true — отчёт при старте: Positive matches, Negative matches с причиной, Exclusions, Unconditional classes. При ошибке старта отчёт печатается автоматически, если включён DEBUG для ConditionEvaluationReportLogger.

Actuator

/actuator/conditions — тот же отчёт в JSON в работающем приложении. /actuator/beans — все бины с зависимостями. /actuator/configprops — значения @ConfigurationProperties.

Порядок действий, когда «бин не создаётся» или «создаётся не тот»: найти автоконфигурацию в отчёте → прочитать причину Negative match → проверить classpath (./gradlew dependencies, mvn dependency:tree) и свойства (/actuator/env).

7.6Свой стартер

Свой стартер нужен, когда несколько сервисов компании подключают одну и ту же инфраструктуру: клиент внутреннего API, аудит, единую настройку трассировки. Классическая структура — два модуля:

acme-audit-spring-boot-autoconfigure

Классы @AutoConfiguration, @ConfigurationProperties, файл imports. Зависимости на сам аудит — optional.

acme-audit-spring-boot-starter

Пустой модуль, только зависимости: autoconfigure + сама библиотека. Его подключают сервисы.

@AutoConfiguration(after = JacksonAutoConfiguration.class)
@ConditionalOnClass(AuditClient.class)
@ConditionalOnBooleanProperty(name = "acme.audit.enabled", matchIfMissing = true)
@EnableConfigurationProperties(AuditProperties.class)
public class AuditAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean                         // пользователь может подменить
    AuditClient auditClient(AuditProperties props, ObjectMapper mapper) {   // Boot 4: tools.jackson.databind.ObjectMapper (Jackson 3)
        return new AuditClient(props.endpoint(), props.timeout(), mapper);
    }
}

@ConfigurationProperties("acme.audit")
public record AuditProperties(URI endpoint, @DefaultValue("2s") Duration timeout, boolean enabled) { }
com.acme.audit.autoconfigure.AuditAutoConfiguration
class AuditAutoConfigurationTest {
    private final ApplicationContextRunner runner = new ApplicationContextRunner()
            .withConfiguration(AutoConfigurations.of(AuditAutoConfiguration.class, JacksonAutoConfiguration.class))
            .withPropertyValues("acme.audit.endpoint=http://audit");

    @Test void createsClientByDefault() {
        runner.run(ctx -> assertThat(ctx).hasSingleBean(AuditClient.class));

    @Test void backsOffWhenUserDefinesClient() {

              .run(ctx -> assertThat(ctx).getBean(AuditClient.class).isSameAs(ctx.getBean("myClient")));

    @Test void disabledByProperty() {

}

7.7Самопроверка

Почему ваш @Bean DataSource побеждает DataSourceAutoConfiguration, хотя обе конфигурации — обычные @Configuration?

  • Ваши бины имеют @Primary по умолчанию
  • AutoConfigurationImportSelector — DeferredImportSelector, автоконфигурации разбираются после пользовательских, и @ConditionalOnMissingBean видит ваш бин
  • Boot сравнивает имена пакетов
  • Автоконфигурация создаёт бин, но потом удаляет его
Порядок регистрации описаний гарантирован отложенным импортом. Условие OnMissingBean проверяется в фазе REGISTER_BEAN, когда ваше описание уже в реестре.

Где Spring Boot 3+ ищет список автоконфигураций?

  • META-INF/spring.factories, ключ EnableAutoConfiguration
  • В application.yml, свойство spring.autoconfigure.include
  • Сканирует пакет org.springframework.boot
  • META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
Формат imports появился в 2.7, а поддержка spring.factories для автоконфигураций удалена в 3.0. spring.factories по-прежнему используется для слушателей, инициализаторов, EnvironmentPostProcessor, FailureAnalyzer.

Чем быстрый фильтр AutoConfigurationImportFilter отличается от обычной проверки условий?

  • Работает по предвычисленным метаданным, не загружая классы автоконфигураций
  • Проверяет только свойства
  • Выполняется в отдельном потоке
  • Ничем, это одно и то же
spring-autoconfigure-metadata.properties содержит для каждой автоконфигурации её ConditionalOnClass и т.п. — большинство кандидатов отбрасывается без загрузки классов.
Как работает автоконфигурация Spring Boot? Расскажите от аннотации до бина.

@SpringBootApplication содержит @EnableAutoConfiguration → @Import(AutoConfigurationImportSelector). Это DeferredImportSelector: после разбора пользовательской конфигурации он загружает кандидатов из AutoConfiguration.imports, убирает исключения, отфильтровывает по метаданным (OnClass/OnBean/OnWebApplication), сортирует по before/after/order. ConfigurationClassParser разбирает каждую как @Configuration, условия @Conditional* проверяются на классе и @Bean-методах; прошедшие регистрируют BeanDefinition. Бины создаются как обычно на шаге 11 refresh().

Как отключить автоконфигурацию и как переопределить один её бин?

Отключить целиком: @SpringBootApplication(exclude = X.class) или spring.autoconfigure.exclude. Переопределить бин: объявить свой бин нужного типа — сработает @ConditionalOnMissingBean. Часто достаточно свойства или бина-кастомайзера (JsonMapperBuilderCustomizer для Jackson 3 в Boot 4, в Boot 3 — Jackson2ObjectMapperBuilderCustomizer; WebServerFactoryCustomizer, RestClientCustomizer), которые донастраивают бин по умолчанию.

Как протестировать свою автоконфигурацию?

ApplicationContextRunner (WebApplicationContextRunner для веба): поднимает минимальный контекст с указанными автоконфигурациями, свойствами и бинами; AssertJ-утверждения hasSingleBean, doesNotHaveBean, hasFailed. Плюс FilteredClassLoader — имитация отсутствия класса на classpath для проверки @ConditionalOnClass.

Почему автоконфигурации используют proxyBeanMethods = false?

Без CGLIB-подкласса быстрее старт и меньше памяти, проще AOT/native image. Межбиновые зависимости передаются параметрами @Bean-методов, поэтому перехват вызовов не нужен.
