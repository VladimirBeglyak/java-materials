ТЕМА 06 · SPRING BOOT

Запуск Spring Boot: от main() до ApplicationReadyEvent

Spring Boot — не другой фреймворк, а надстройка над Spring Framework: готовые наборы зависимостей, автоконфигурация, встроенный сервер и единая система настроек. Строка SpringApplication.run(App.class, args) делает много работы до и после refresh(). Разберём её по шагам и посмотрим, как устроен исполняемый jar.

6.1Что добавляет Boot к Spring Framework

Стартеры и BOM

spring-boot-starter-webmvc (в Boot 4; прежний spring-boot-starter-web объявлен устаревшим) — набор согласованных зависимостей. Версии всех библиотек задаёт BOM spring-boot-dependencies: вы не пишете версию Jackson или Hibernate.

Автоконфигурация

Бины по умолчанию создаются, если на classpath есть библиотека и вы не определили свой бин (тема 07).

Внешняя конфигурация

Единый порядок источников свойств, @ConfigurationProperties, профили (тема 08).

Встроенный сервер

Tomcat/Jetty/Netty внутри приложения — запуск через java -jar, без установки сервера.

Исполняемый jar

Один артефакт со всеми зависимостями и своим загрузчиком классов.

Продакшен

Actuator: health, метрики, пробы Kubernetes, graceful shutdown (тема 15).

6.2Что внутри @SpringBootApplication

@SpringBootConfiguration                 // = @Configuration (+ поиск конфигурации тестами)
@EnableAutoConfiguration                 // @Import(AutoConfigurationImportSelector) + @AutoConfigurationPackage
@ComponentScan(excludeFilters = {        // сканирует пакет этого класса и все подпакеты
    @Filter(type = CUSTOM, classes = TypeExcludeFilter.class),
    @Filter(type = CUSTOM, classes = AutoConfigurationExcludeFilter.class) })
public @interface SpringBootApplication { }

@SpringBootApplication
public class ShopApplication {
    public static void main(String[] args) {
        SpringApplication.run(ShopApplication.class, args);
    }
}
Пакет главного класса имеет значение Сканирование компонентов и @AutoConfigurationPackage (откуда Spring Data ищет репозитории и сущности) берут пакет главного класса. Класс в com.shop не увидит бины в com.common. Главный класс в пакете по умолчанию (без package) заставит сканировать весь classpath, включая библиотеки.

6.3SpringApplication.run() пошагово

Конструктор SpringApplication определяет тип приложения по classpath (в Boot 3 — WebApplicationType.deduceFromClasspath, в Boot 4 — deduce() через реализации WebApplicationType.Deducer: есть DispatcherServlet → SERVLET; только DispatcherHandler из WebFlux → REACTIVE; нет Servlet API → NONE) и загружает из META-INF/spring.factories инициализаторы и слушатели. Дальше работает run():

Симулятор: SpringApplication.run()

Справа — события, которые получают слушатели. Слушатели ранних событий (до создания контекста) регистрируются через spring.factories или app.addListeners(): бины ещё не существуют, и @EventListener на бине их не получит.

1. Конструктор

Определяется WebApplicationType; через SpringFactoriesLoader загружаются BootstrapRegistryInitializer, ApplicationContextInitializer и ApplicationListener из всех META-INF/spring.factories на classpath; по стеку вызовов находится класс с main.

2. Запуск слушателей: starting()

Создаётся DefaultBootstrapContext (для объектов, нужных до контекста, например клиента Config Server). EventPublishingRunListener публикует ApplicationStartingEvent. LoggingApplicationListener уже на этом событии выбирает систему логирования (Logback по умолчанию).

3. prepareEnvironment()

Создаётся ApplicationServletEnvironment, добавляются аргументы командной строки. Публикуется ApplicationEnvironmentPreparedEvent; его слушатель EnvironmentPostProcessorApplicationListener запускает все EnvironmentPostProcessor:

  • ConfigDataEnvironmentPostProcessor — читает application.properties/yml, профильные файлы, spring.config.import (Vault, Consul, configtree);
  • RandomValuePropertySourceEnvironmentPostProcessor — добавляет RandomValuePropertySource (${random.uuid});
  • SpringApplicationJsonEnvironmentPostProcessor — SPRING_APPLICATION_JSON.

Затем LoggingApplicationListener применяет logging.level.*, а свойства spring.main.* привязываются к самому SpringApplication.

4. Баннер

Печатается баннер (banner.txt или стандартный). Отключается spring.main.banner-mode=off.

5. createApplicationContext()

ApplicationContextFactory по типу приложения создаёт контекст: для SERVLET — AnnotationConfigServletWebServerApplicationContext, для REACTIVE — AnnotationConfigReactiveWebServerApplicationContext, для NONE — AnnotationConfigApplicationContext. Его конструктор регистрирует внутренние процессоры (ConfigurationClassPostProcessor и др.).

6. prepareContext()

  • контексту передаётся Environment;
  • вызываются ApplicationContextInitializer-ы (например, ConditionEvaluationReportLoggingListener — он потом печатает отчёт условий при --debug или ошибке) → ApplicationContextInitializedEvent;
  • регистрируются singleton-ы springApplicationArguments, springBootBanner; при spring.main.lazy-initialization=true — LazyInitializationBeanFactoryPostProcessor;
  • BeanDefinitionLoader регистрирует описание главного класса — отсюда ConfigurationClassPostProcessor начнёт разбор всей конфигурации;
  • слушатели из spring.factories переносятся в контекст → ApplicationPreparedEvent.

7. refreshContext() → refresh()

Те самые 12 шагов из темы 02: сканирование, автоконфигурация, создание бинов, Tomcat создаётся в onRefresh и открывает порт в finishRefresh. Регистрируется shutdown hook JVM (SpringApplicationShutdownHook) — он закроет контекст по SIGTERM.

8. started()

В лог пишется «Started ShopApplication in 2.41 seconds (process running for 2.9)». Публикуются ApplicationStartedEvent и AvailabilityChangeEvent(LivenessState.CORRECT): процесс жив, но ещё не готов принимать трафик.

9. callRunners()

Вызываются все бины ApplicationRunner и CommandLineRunner, отсортированные по @Order. Здесь все прокси работают — место для прогрева кэшей и разовых задач. Исключение в runner-е считается провалом запуска.

10. ready()

ApplicationReadyEvent и AvailabilityChangeEvent(ReadinessState.ACCEPTING_TRAFFIC). Readiness-проба Kubernetes (/actuator/health/readiness) начинает отвечать UP — балансировщик пускает трафик.

При исключении на любом шаге: ApplicationFailedEvent, FailureAnalyzers печатают блок «APPLICATION FAILED TO START» с описанием и действием, контекст закрывается.

6.5Исполняемый jar изнутри

Обычный jar не умеет содержать другие jar: стандартный URLClassLoader не читает вложенные архивы. Boot решает это своим загрузчиком.

META-INF/MANIFEST.MF
    Main-Class: org.springframework.boot.loader.launch.JarLauncher
    Start-Class: com.shop.ShopApplication
    Spring-Boot-Classes: BOOT-INF/classes/
    Spring-Boot-Lib: BOOT-INF/lib/
org/springframework/boot/loader/...      ← классы загрузчика, лежат несжатыми в корне
BOOT-INF/classes/                        ← ваши классы и application.yml
BOOT-INF/lib/                            ← зависимости как вложенные jar (храниться без сжатия)
BOOT-INF/classpath.idx                   ← порядок jar на classpath
BOOT-INF/layers.idx                      ← слои для Docker
  1. JVM запускает JarLauncher.main (из MANIFEST).
  2. Лаунчер строит LaunchedClassLoader с URL на BOOT-INF/classes и каждый jar из BOOT-INF/lib, регистрируя свой обработчик URL для вложенных архивов (jar:nested:...).
  3. Через рефлексию вызывает main класса из Start-Class в новом загрузчике.

Слои для Docker

java -Djarmode=tools -jar app.jar extract --layers --launcher раскладывает jar на слои: dependencies, spring-boot-loader, snapshot-dependencies, application. В Dockerfile слои копируются отдельно, и при изменении кода пересобирается только тонкий слой application.

Ускорение старта

CDS (Class Data Sharing, -XX:SharedArchiveFile) и AOT cache из JDK 24+ кэшируют загруженные классы между запусками. GraalVM native image — старт за десятки миллисекунд ценой долгой сборки и ограничений (тема 15).

6.6Встроенный сервер

TomcatServletWebServerAutoConfiguration из модуля spring-boot-tomcat (в Boot 3 — ServletWebServerFactoryAutoConfiguration) регистрирует TomcatServletWebServerFactory (в Boot 4 — пакет org.springframework.boot.tomcat.servlet) (если на classpath Tomcat). Настраивается свойствами server.* или бином-кастомайзером:

@Bean
WebServerFactoryCustomizer<TomcatServletWebServerFactory> tomcatCustomizer() {
    return f -> f.addConnectorCustomizers(c -> c.setProperty("relaxedQueryChars", "[]|"));
}
server:
  port: 8080
  shutdown: graceful              # по умолчанию с Boot 3.4: дождаться активных запросов
  tomcat:
    threads:
      max: 200                    # рабочие потоки (по умолчанию 200)
      min-spare: 10
    accept-count: 100             # очередь соединений ОС, когда все потоки заняты
    max-connections: 8192         # одновременно открытых соединений (NIO)
    connection-timeout: 20s
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
  threads:
    virtual:
      enabled: true               # JDK 21+: запросы на виртуальных потоках (тема 10)

6.7Самопроверка

Где читается application.yml?

  • В ConfigurationClassPostProcessor на шаге refresh()
  • В конструкторе SpringApplication
  • В ConfigDataEnvironmentPostProcessor при ApplicationEnvironmentPreparedEvent, до создания контекста
  • В @PropertySource главного класса
Конфигурация нужна до создания контекста (например, чтобы знать активные профили), поэтому её загружает EnvironmentPostProcessor на этапе prepareEnvironment.

Бин с @EventListener(ApplicationStartingEvent.class). Получит ли он событие?

  • Да
  • Нет: событие публикуется до создания контекста и бинов
  • Да, но асинхронно
  • Только при --debug
ApplicationStartingEvent, EnvironmentPrepared, ContextInitialized публикуются раньше, чем бины созданы. Такие слушатели регистрируют через spring.factories или SpringApplication.addListeners.

Что в MANIFEST.MF указано как Main-Class у Boot fat jar?

  • Ваш класс с @SpringBootApplication
  • org.springframework.boot.SpringApplication
  • java.lang.ClassLoader
  • JarLauncher из spring-boot-loader, а ваш класс — в Start-Class
Сначала нужен загрузчик, умеющий читать вложенные jar. JarLauncher строит его и вызывает main из Start-Class.
Что происходит при вызове SpringApplication.run()? Назовите ключевые шаги.

Определение типа приложения и загрузка инициализаторов/слушателей из spring.factories → ApplicationStartingEvent → подготовка Environment (EnvironmentPostProcessor-ы, application.yml, профили) → баннер → создание контекста по типу → prepareContext (инициализаторы, регистрация главного класса) → refresh() (автоконфигурация, бины, веб-сервер) → ApplicationStartedEvent → runners → ApplicationReadyEvent.

Чем ApplicationRunner отличается от @PostConstruct для логики при старте?

@PostConstruct выполняется при инициализации конкретного бина: другие бины могут быть ещё не созданы, прокси этого бина ещё нет (транзакции, @Async не работают), веб-сервер не запущен. ApplicationRunner вызывается после полного refresh: все бины готовы и обёрнуты, порт открыт, доступны аргументы командной строки.

Как Spring Boot определяет, что приложение веб и какого типа?

В Boot 4 — WebApplicationType.deduce(): реализации WebApplicationType.Deducer из spring.factories опрашиваются по порядку. Сначала WebMvc (@Order(10)): есть Servlet API, DispatcherServlet и ConfigurableWebApplicationContext → SERVLET; затем WebFlux (@Order(20)): есть Mono и DispatcherHandler → REACTIVE; иначе есть Servlet API → SERVLET, нет → NONE. (В Boot 3 это был deduceFromClasspath() с проверкой Jersey.) Переопределяется spring.main.web-application-type.

Как устроен исполняемый jar Spring Boot и зачем layered jar?

Классы приложения в BOOT-INF/classes, зависимости как вложенные jar в BOOT-INF/lib, загрузчик Boot в корне; JarLauncher создаёт ClassLoader для вложенных jar и вызывает Start-Class. Слои позволяют Docker кэшировать редко меняющиеся зависимости отдельно от часто меняющегося кода — быстрее сборка и меньше трафик при деплое.
