BeanDefinition и запуск контекста: refresh()

Контекст стартует в две фазы. Сначала собираются описания бинов (BeanDefinition) и правятся пост-процессорами фабрики — ни одного вашего объекта ещё нет. Потом по описаниям создаются экземпляры. Весь запуск — это 12 шагов метода AbstractApplicationContext.refresh(). Эту последовательность спрашивают на Senior-собеседованиях и по ней читают любой стектрейс старта.

2.1BeanDefinition — рецепт бина

Контейнер никогда не работает напрямую с вашими аннотациями при создании объекта. Аннотации, @Bean-методы и XML сначала превращаются в объекты BeanDefinition, и дальше контейнер работает только с ними. Поэтому одинаково работают бины из любого источника, а пост-процессоры могут менять описания до создания объектов.

@Component
class DefinitionsDump implements ApplicationRunner {
    private final ConfigurableListableBeanFactory bf;
    DefinitionsDump(ConfigurableListableBeanFactory bf) { this.bf = bf; }

    public void run(ApplicationArguments args) {
        for (String name : bf.getBeanDefinitionNames()) {
            BeanDefinition bd = bf.getBeanDefinition(name);
            if (bd.getRole() == BeanDefinition.ROLE_APPLICATION)
                System.out.printf("%s → %s scope=%s factory=%s%n",
                    name, bd.getBeanClassName(), bd.getScope(), bd.getFactoryMethodName());
        }
    }
}

2.2Две точки расширения: пост-процессоры фабрики и бинов

BeanFactoryPostProcessor

Работает с описаниями, до создания обычных бинов. Может менять и добавлять BeanDefinition.

BeanDefinitionRegistryPostProcessor — расширение, которое запускается раньше и может регистрировать новые описания.

Примеры: ConfigurationClassPostProcessor (парсит всю аннотационную конфигурацию), PropertySourcesPlaceholderConfigurer (подставляет ${...}), регистратор репозиториев Spring Data.

BeanPostProcessor

Работает с экземплярами: вызывается для каждого создаваемого бина до и после инициализации. Может вернуть другой объект — например, прокси.

Примеры: AutowiredAnnotationBeanPostProcessor (@Autowired, @Value), CommonAnnotationBeanPostProcessor (@PostConstruct, @Resource), AnnotationAwareAspectJAutoProxyCreator (AOP-прокси), ConfigurationPropertiesBindingPostProcessor.

Порядок вызова внутри каждой группы: сначала реализующие PriorityOrdered, потом Ordered, потом остальные. Все эти пост-процессоры — тоже бины, поэтому контексту приходится создавать их заранее, до остальных.

Ловушка: BFPP из @Bean-метода Чтобы вызвать нестатический @Bean-метод, нужен экземпляр конфигурации. Если метод возвращает BeanFactoryPostProcessor, конфигурация создаётся слишком рано, и @Autowired/@Value в ней не обработаются (в логе INFO-сообщение «@Bean method X.y is non-static and returns an object assignable to Spring's BeanFactoryPostProcessor interface…»). Решение — static @Bean.
«Bean 'x' is not eligible for getting processed by all BeanPostProcessors» Это WARN-сообщение («Bean 'x' of type [...] is not eligible for getting processed by all BeanPostProcessors (for example: not eligible for auto-proxying)») значит: бин x понадобился какому-то BeanPostProcessor (например, через его зависимость) и был создан до того, как зарегистрировались все BPP. На нём могут не сработать прокси (транзакции, кэш, @Async). Лечится тем, что зависимости BPP делают ленивыми (ObjectProvider, @Lazy) или инфраструктурными.

2.3refresh(): 12 шагов

public void refresh() {
    synchronized (startupShutdownMonitor) {             // в 6.x — ReentrantLock
        prepareRefresh();                                     // 1
        ConfigurableListableBeanFactory bf = obtainFreshBeanFactory(); // 2
        prepareBeanFactory(bf);                               // 3
        try {
            postProcessBeanFactory(bf);                       // 4  хук для подклассов
            invokeBeanFactoryPostProcessors(bf);              // 5  ← здесь появляются описания ваших бинов
            registerBeanPostProcessors(bf);                   // 6
            initMessageSource();                              // 7
            initApplicationEventMulticaster();                // 8
            onRefresh();                                      // 9  Boot: создаёт веб-сервер
            registerListeners();                              // 10
            finishBeanFactoryInitialization(bf);              // 11 ← здесь создаются ваши singleton-бины
            finishRefresh();                                  // 12 старт SmartLifecycle, ContextRefreshedEvent
        } catch (RuntimeException | Error ex) {               // до 6.2 — BeansException
            // 7.0: сначала останавливаются уже запущенные Lifecycle-бины
            destroyBeans();                                   // уже созданные бины уничтожаются
            cancelRefresh(ex);
            throw ex;
        }
    }
}

1. prepareRefresh()

Запоминает время старта, ставит флаг active, вызывает initPropertySources() (веб-контексты подменяют заглушки servlet-параметров) и getEnvironment().validateRequiredProperties() — если обязательное свойство не задано, старт падает здесь.

В реестре уже есть описания, зарегистрированные до refresh: главный класс приложения и внутренние процессоры, которые добавил AnnotatedBeanDefinitionReader (через AnnotationConfigUtils.registerAnnotationConfigProcessors).

2. obtainFreshBeanFactory()

Для GenericApplicationContext (на нём построены аннотационные контексты и все контексты Boot) фабрика DefaultListableBeanFactory уже создана в конструкторе — метод лишь проверяет, что refresh вызывается впервые. Повторный refresh() → IllegalStateException: GenericApplicationContext does not support multiple refresh attempts.

Классические XML-контексты (AbstractRefreshableApplicationContext) здесь уничтожают старую фабрику, создают новую и загружают в неё XML.

3. prepareBeanFactory(bf)

  • ClassLoader, SpEL-резолвер (#{...}), редакторы ресурсов.
  • BPP ApplicationContextAwareProcessor — будет вызывать EnvironmentAware, ApplicationContextAware и другие *Aware.
  • registerResolvableDependency: BeanFactory, ApplicationContext, ResourceLoader, ApplicationEventPublisher можно внедрять, хотя это не бины.
  • BPP ApplicationListenerDetector — находит бины-слушатели.
  • Регистрирует готовые singleton-объекты environment, systemProperties, systemEnvironment.

4. postProcessBeanFactory(bf)

Пустой хук для подклассов. Веб-контексты регистрируют здесь scopes request и session и BPP WebApplicationContextServletContextAwareProcessor.

5. invokeBeanFactoryPostProcessors(bf) — главный шаг первой фазы

PostProcessorRegistrationDelegate вызывает сначала все BeanDefinitionRegistryPostProcessor (PriorityOrdered → Ordered → остальные, повторяя, пока появляются новые), затем обычные BeanFactoryPostProcessor.

ConfigurationClassPostProcessor разбирает главный класс: @ComponentScan → находит orderService, orderRepository; @Import, @Bean-методы → dataSource; в конце — DeferredImportSelector автоконфигурации Boot, которые добавляют сотни описаний. Затем он же подменяет классы @Configuration CGLIB-подклассами.

PropertySourcesPlaceholderConfigurer подставляет ${...} в значения описаний.

6. registerBeanPostProcessors(bf)

Создаёт все бины-BeanPostProcessor (в порядке PriorityOrdered → Ordered → остальные) и добавляет их в список фабрики. С этого момента каждый создаваемый бин будет проходить через них. Бины, созданные раньше (зависимости самих BPP), — «not eligible for getting processed by all BeanPostProcessors».

7. initMessageSource()

Берёт бин с именем messageSource (Boot создаёт ResourceBundleMessageSource, если есть messages.properties) или ставит пустой DelegatingMessageSource. Нужен для i18n и сообщений валидации.

8. initApplicationEventMulticaster()

Бин applicationEventMulticaster или SimpleApplicationEventMulticaster по умолчанию — он рассылает события слушателям. Без executor'а — синхронно, в потоке публикующего (тема 05).

9. onRefresh()

Хук для подклассов. ServletWebServerApplicationContext в Spring Boot создаёт здесь встроенный сервер: получает бин ServletWebServerFactory (Tomcat/Jetty), создаёт и инициализирует Tomcat, регистрирует DispatcherServlet и фильтры через ServletContextInitializer-ы. Коннектор ещё не открыт: порт начнёт принимать запросы на шаге 12, когда контекст полностью готов.

10. registerListeners()

Добавляет в мультикастер статически заданных слушателей и имена бинов-ApplicationListener (сами бины не создаются, чтобы не инициализировать их раньше времени). Рассылает «ранние» события, накопленные до появления мультикастера.

11. finishBeanFactoryInitialization(bf) — главный шаг второй фазы

Регистрирует ConversionService, замораживает конфигурацию (freezeConfiguration: описания больше не меняются, их можно кэшировать) и вызывает preInstantiateSingletons(): для каждого не-абстрактного, singleton, не-ленивого описания — getBean(name). Каждый вызов запускает полный жизненный цикл: создание → внедрение → BPP → init (тема 03). orderService выходит из цикла уже обёрнутым в прокси, если на нём есть @Transactional.

После создания всех singleton-бинов вызывается SmartInitializingSingleton.afterSingletonsInstantiated() — так, например, EventListenerMethodProcessor регистрирует методы с @EventListener.

12. finishRefresh()

Создаёт LifecycleProcessor и вызывает onRefresh(): стартуют все SmartLifecycle-бины с isAutoStartup()=true по возрастанию phase. Среди них — WebServerStartStopLifecycle (Tomcat открывает порт), контейнеры слушателей Kafka/RabbitMQ. Затем публикуется ContextRefreshedEvent.

Если на любом шаге вылетело исключение — destroyBeans() уничтожает уже созданные бины (их @PreDestroy вызовутся), и исключение пробрасывается: контекст не поднялся.

2.4ConfigurationClassPostProcessor: как разбирается конфигурация

ConfigurationClassParser обходит класс конфигурации в фиксированном порядке и рекурсивно применяет то же самое к найденным классам:

  1. Условия: @Conditional на классе (фаза PARSE_CONFIGURATION) — не прошло, класс пропускается целиком.
  2. Вложенные классы-конфигурации (member classes).
  3. @PropertySource — файлы добавляются в Environment.
  4. @ComponentScan — сканирование, найденные классы-конфигурации сразу разбираются рекурсивно.
  5. @Import: обычный класс → как конфигурация; ImportSelector → возвращает имена классов; ImportBeanDefinitionRegistrar → регистрирует описания программно (так работают @EnableJpaRepositories, @EnableConfigurationProperties); DeferredImportSelector → откладывается до конца разбора всего остального.
  6. @ImportResource (XML), затем @Bean-методы, default-методы интерфейсов, суперкласс.

Затем ConfigurationClassBeanDefinitionReader превращает результат в BeanDefinition, проверяя условия ещё раз в фазе REGISTER_BEAN (так работает @ConditionalOnMissingBean — тема 07).

Почему автоконфигурации Boot не перебивают ваши бины Автоконфигурацию подключает AutoConfigurationImportSelector — это DeferredImportSelector. Он обрабатывается после всей пользовательской конфигурации. К моменту проверки @ConditionalOnMissingBean(DataSource.class) ваш DataSource уже зарегистрирован, и автоконфигурация отступает.

2.5@Configuration: режимы full и lite

@Configuration                          // proxyBeanMethods = true по умолчанию → режим full
class PersistenceConfig {
    @Bean DataSource dataSource() { return new HikariDataSource(); }

    @Bean JdbcTemplate jdbc()        { return new JdbcTemplate(dataSource()); }  // тот же бин
    @Bean TransactionManager txm()   { return new DataSourceTransactionManager(dataSource()); }
}

Как dataSource(), вызванный дважды, возвращает один объект? На шаге 5 ConfigurationClassPostProcessor.enhanceConfigurationClasses заменяет класс в описании на CGLIB-подкласс PersistenceConfig$$SpringCGLIB$$0. Его BeanMethodInterceptor перехватывает каждый вызов @Bean-метода:

  • если этот метод сейчас вызывается самим контейнером для создания бина — выполняется оригинальный код;
  • иначе — вместо вызова возвращается beanFactory.getBean("dataSource"), то есть существующий singleton.

full: @Configuration

Вызовы @Bean-методов друг из друга безопасны: возвращаются бины из контекста. Цена — генерация CGLIB-класса на старте; класс и @Bean-методы не могут быть final/private.

lite: @Component с @Bean или proxyBeanMethods=false

Подкласса нет. dataSource() — обычный вызов Java: каждый раз новый HikariDataSource, мимо контейнера (без пост-процессоров и закрытия при остановке). Правильный стиль — получать зависимости параметрами: @Bean JdbcTemplate jdbc(DataSource ds).

Все автоконфигурации Spring Boot объявлены как @AutoConfiguration, а она включает @Configuration(proxyBeanMethods = false): так быстрее старт и проще AOT/GraalVM. Для своего кода годятся оба режима, но параметры @Bean-методов вместо вызовов работают в любом.

2.7Самопроверка

На каком шаге refresh() регистрируются описания классов, найденных @ComponentScan?

  • finishBeanFactoryInitialization
  • invokeBeanFactoryPostProcessors — их регистрирует ConfigurationClassPostProcessor
  • registerBeanPostProcessors
  • prepareRefresh
Сканирование выполняет ConfigurationClassPostProcessor — BeanDefinitionRegistryPostProcessor, который вызывается на шаге 5. Экземпляры будут созданы позже, на шаге 11.

Класс помечен @Component (не @Configuration), в нём @Bean a() и @Bean b() { return new B(a()); }. Что получит B?

  • Бин a из контекста
  • Ошибку старта
  • Новый экземпляр A, созданный мимо контейнера
  • null
Это lite-режим: CGLIB-подкласса нет, a() — обычный вызов метода. Получится второй объект A, о котором контейнер не знает.

Когда Tomcat в Spring Boot начинает принимать соединения?

  • На finishRefresh, когда стартуют SmartLifecycle-бины
  • На onRefresh, сразу после создания
  • До refresh, в SpringApplication.run
  • После ApplicationReadyEvent
Сервер создаётся в onRefresh(), но порт открывает WebServerStartStopLifecycle.start() на шаге 12, когда все бины уже созданы. Так запросы не приходят в недособранное приложение.
Перечислите шаги refresh() и скажите, где создаются ваши бины.

prepareRefresh → obtainFreshBeanFactory → prepareBeanFactory → postProcessBeanFactory → invokeBeanFactoryPostProcessors (описания: сканирование, @Import, @Bean, автоконфигурация) → registerBeanPostProcessors → initMessageSource → initApplicationEventMulticaster → onRefresh (веб-сервер в Boot) → registerListeners → finishBeanFactoryInitialization (создание всех не-ленивых singleton) → finishRefresh (SmartLifecycle, ContextRefreshedEvent).

Чем BeanFactoryPostProcessor отличается от BeanPostProcessor? Приведите примеры.

BFPP работает с описаниями до создания бинов (ConfigurationClassPostProcessor, PropertySourcesPlaceholderConfigurer). BPP — с экземплярами при их инициализации и может подменить объект (AutowiredAnnotationBeanPostProcessor, AOP auto-proxy creator). BFPP не должен получать бины через getBean — это создаст их преждевременно.

Зачем static у @Bean-метода, возвращающего BeanFactoryPostProcessor?

BFPP нужен на шаге 5, когда обычные бины ещё не создаются. Нестатический метод требует экземпляр конфигурационного класса — его пришлось бы создать слишком рано, без обработки @Autowired/@Value и без всех BPP. Статический метод вызывается без экземпляра.

Как работает ImportBeanDefinitionRegistrar и где он используется?

Класс, указанный в @Import, получает BeanDefinitionRegistry и метаданные аннотированного класса и регистрирует описания программно. Так устроены @EnableJpaRepositories (по описанию на каждый интерфейс-репозиторий), @EnableConfigurationProperties, @EnableFeignClients, @ImportHttpServices.

Что происходит с уже созданными бинами, если на шаге 11 один бин бросил исключение?

refresh ловит RuntimeException | Error (до 6.2 — только BeansException), в 7.0 сначала останавливает уже запущенные Lifecycle-бины, затем вызывает destroyBeans() — для созданных singleton выполняются destroy-колбэки (@PreDestroy, DisposableBean, close), затем cancelRefresh, и исключение пробрасывается. В Boot его разбирают FailureAnalyzer-ы и печатают блок «APPLICATION FAILED TO START» с описанием и советом.
