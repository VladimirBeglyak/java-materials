IoC, DI и контейнер

Spring — это прежде всего контейнер: объект, который по описаниям (BeanDefinition) создаёт ваши объекты, связывает их зависимостями и управляет их жизнью. Всё остальное — MVC, транзакции, Security, Boot — построено как расширения этого контейнера. Поймёте контейнер — остальное перестанет быть магией.

1.1Инверсия управления: какую проблему решаем

Без контейнера каждый класс сам создаёт свои зависимости. Класс знает не только что ему нужно, но и как это собрать: какой драйвер, какой URL, какой пул. Подменить реализацию в тесте или в другом окружении нельзя, не меняя код.

class OrderService {
    private final OrderRepository repo =
        new JdbcOrderRepository(
            new HikariDataSource(cfg("jdbc:pg://prod")));
    private final PaymentClient payments =
        new StripeClient(System.getenv("KEY"));
    // тест без настоящей БД и Stripe не написать
}
@Service
class OrderService {
    private final OrderRepository repo;
    private final PaymentClient payments;

    OrderService(OrderRepository repo, PaymentClient payments) {
        this.repo = repo;          // кто и как создал —
        this.payments = payments;  // не забота этого класса
    }
}

Inversion of Control (IoC) — принцип: управление созданием и связыванием объектов передаётся внешнему механизму («не звоните нам, мы вам позвоним»). Dependency Injection (DI) — конкретный способ реализовать IoC: зависимости передаются через конструктор, сеттер или поле. Альтернативный способ IoC — Service Locator (context.getBean(...) внутри бизнес-кода) — в Spring считается анти-паттерном: класс снова зависит от инфраструктуры.

Термины Бин (bean) — объект, жизненным циклом которого управляет контейнер. Объект, созданный через new в вашем коде, бином не является: контейнер о нём не знает, не внедрит в него зависимости и не обернёт в прокси (значит, на нём не сработают @Transactional, @Async, @Cacheable).

1.2Устройство контейнера: BeanFactory и ApplicationContext

В Spring два уровня контейнера. BeanFactory — минимальный интерфейс «дай бин по имени/типу». ApplicationContext — надстройка для приложений: события, ресурсы, i18n, окружение, автоматическая регистрация пост-процессоров. Реальную работу в обоих случаях делает один класс — DefaultListableBeanFactory.

Внутри фабрики три главные структуры: beanDefinitionMap (имя → BeanDefinition, «рецепт» бина), singletonObjects (имя → готовый экземпляр) и индекс по типам для поиска кандидатов. Об устройстве BeanDefinition и о том, как контекст заполняется, — тема 02.

1.3Как описать бины: четыре способа

@Configuration
@ComponentScan("com.shop")            // ищет классы с @Component и мета-аннотациями
class AppConfig { }

@Service                              // = @Component с семантикой «сервисный слой»
class OrderService { /* ... */ }

@Repository                           // + трансляция исключений БД в DataAccessException
class JdbcOrderRepository implements OrderRepository { /* ... */ }
@Configuration
class InfraConfig {
    @Bean(destroyMethod = "close")
    HikariDataSource dataSource(DbProperties p) {      // параметры метода — тоже DI
        var ds = new HikariDataSource();
        ds.setJdbcUrl(p.url());
        ds.setMaximumPoolSize(p.poolSize());
        return ds;
    }

    @Bean
    JdbcTemplate jdbcTemplate(DataSource ds) { return new JdbcTemplate(ds); }
}
var ctx = new GenericApplicationContext();
ctx.registerBean(Clock.class, Clock::systemUTC);
ctx.registerBean("orderService", OrderService.class);   // конструктор разрешится автоматически
ctx.refresh();

// Spring Framework 7: BeanRegistrar — программная регистрация с условиями, дружит с AOT
class MyRegistrar implements BeanRegistrar {
    public void register(BeanRegistry registry, Environment env) {
        if (env.matchesProfiles("dev")) registry.registerBean("clock", Clock.class, s -> s.supplier(c -> Clock.systemUTC()));
    }
}

Четвёртый способ — XML (<bean class="..."/>) — встречается в старых проектах; механизм тот же: XML читается в BeanDefinition.

Компонент или @Bean? @Component — для своих классов, у которых одна очевидная реализация. @Bean — для классов из библиотек (их нельзя пометить аннотацией), для бинов, которым нужна нетривиальная сборка, и когда нужно несколько бинов одного класса с разной настройкой (два DataSource, два RestClient).

1.4Способы внедрения

С Spring 4.3 при единственном конструкторе @Autowired писать не нужно. При нескольких конструкторах контейнер возьмёт помеченный @Autowired, а если такого нет — конструктор без аргументов. Это решает AutowiredAnnotationBeanPostProcessor.determineCandidateConstructors.

@Service
class CheckoutService {
    private final CartRepository carts;
    private final PricingPolicy pricing;
    private final ObjectProvider<FraudCheck> fraud;   // опциональная зависимость

    CheckoutService(CartRepository carts, PricingPolicy pricing, ObjectProvider<FraudCheck> fraud) {
        this.carts = carts; this.pricing = pricing; this.fraud = fraud;
    }

    Order checkout(long cartId) {
        Cart cart = carts.find(cartId);
        fraud.ifAvailable(f -> f.verify(cart));        // бина нет — шаг пропускается
        return pricing.apply(cart);
    }
}

1.5Как контейнер выбирает, какой бин внедрить

Точка внедрения описывается DependencyDescriptor (тип, generics, аннотации, имя параметра/поля). Её разрешает DefaultListableBeanFactory.doResolveDependency:

  1. Особые типы. Optional<T>, ObjectProvider<T>, Provider<T> — обёртка, разрешение откладывается. List<T>, Set, Map<String,T>, массивы — внедряются все кандидаты (List отсортирован по @Order/Ordered).
  2. Поиск по типу (findAutowireCandidates): все бины, совместимые по типу с учётом generics, у которых autowireCandidate=true. Если в точке есть @Qualifier("x") — остаются только бины с таким квалификатором или с таким именем.
  3. 0 кандидатов → NoSuchBeanDefinitionException (если зависимость обязательная).
  4. 1 кандидат → внедряется.
  5. Несколько (determineAutowireCandidate): единственный @Primary → он; если @Primary нет, но ровно один кандидат без @Fallback (6.2+) — он; иначе бин, имя которого совпадает с именем поля/параметра; иначе бин с наивысшим приоритетом, то есть с наименьшим значением @Priority. Не получилось выбрать → NoUniqueBeanDefinitionException.
До Spring 6.2 @Priority проверялся раньше совпадения по имени. Совпадение по имени работает, только если компилятор сохранил имена параметров (-parameters; Spring Boot включает этот флаг в своих плагинах сборки). Без него в 6.1+ Spring больше не читает имена из отладочной информации — именная стратегия молча перестаёт работать.
Симулятор: какой бин получит точка внедрения

Контекст: интерфейс PaymentGateway и три реализации. Включайте и выключайте бины и аннотации — алгоритм doResolveDependency покажет каждый шаг.

Попробуйте: (1) Включите mockGateway и уберите у него @Fallback — три кандидата и ни один не выбран. (2) Поставьте @Primary двум бинам. (3) Выберите имя параметра paypalGateway — именная стратегия. (4) Квалификатор yandexGateway и тип Optional.

1.6Коллекции, generics, ObjectProvider, @Lazy

interface PaymentGateway { String code(); Receipt pay(Money m); }

@Service
class PaymentRouter {
    private final Map<String, PaymentGateway> byCode;

    PaymentRouter(List<PaymentGateway> all) {                // все бины этого типа
        this.byCode = all.stream().collect(toMap(PaymentGateway::code, g -> g));
    }
    // Альтернатива: Map<String, PaymentGateway> — ключ = имя бина
}

Generics как квалификатор

Бины Repository<User> и Repository<Order> различаются по параметру типа: точка Repository<User> users получит нужный без @Qualifier. Работает через ResolvableType.

ObjectProvider<T>

Ленивое и опциональное получение: getIfAvailable(), getIfUnique(), orderedStream(). Каждый вызов getObject() для prototype даёт новый экземпляр — так singleton получает свежий prototype (тема 03).

@Lazy на точке внедрения

Внедряется не бин, а прокси, который при первом вызове метода достанет настоящий бин. Используется, чтобы разорвать цикл в конструкторах или отложить дорогую инициализацию.

@Value

Внедряет значение из Environment или результат SpEL: @Value("${app.timeout:5s}") Duration timeout. Строка конвертируется в тип через ConversionService. Для групп настроек лучше @ConfigurationProperties (тема 08).

1.7Стереотипы и мета-аннотации

Сканер (ClassPathBeanDefinitionScanner) ищет классы, помеченные @Component прямо или через мета-аннотацию. @Service, @Repository, @Controller, @Configuration сами помечены @Component. Сканер читает байткод через ASM и не загружает классы, пока не решит, что класс подходит, — поэтому сканирование тысяч классов идёт быстро.

АннотацияЧто добавляет кроме регистрации
@Componentничего — базовый стереотип
@Serviceничего технического, только смысл: «бизнес-логика»
@RepositoryPersistenceExceptionTranslationPostProcessor оборачивает бин в прокси, который переводит SQLException/исключения JPA в иерархию DataAccessException
@Controller / @RestControllerRequestMappingHandlerMapping регистрирует методы с @RequestMapping как обработчики HTTP
@Configurationкласс обрабатывается ConfigurationClassPostProcessor, по умолчанию подменяется CGLIB-подклассом (тема 02)
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Service
@Transactional(readOnly = true)
public @interface ReadOnlyService {
    @AliasFor(annotation = Service.class, attribute = "value")
    String value() default "";        // имя бина пробрасывается в @Service
}

Имя бина по умолчанию — имя класса с маленькой буквы (OrderService → orderService; URLParser → URLParser, если первые две буквы заглавные), для @Bean — имя метода. Два бина с одинаковым именем: в Spring Boot по умолчанию spring.main.allow-bean-definition-overriding=false → ошибка старта.

1.8Самопроверка

Чем ApplicationContext принципиально отличается от BeanFactory при старте?

  • ApplicationContext не поддерживает prototype-бины
  • BeanFactory создаёт бины через рефлексию, а ApplicationContext — через CGLIB
  • ApplicationContext сразу создаёт все не-ленивые singleton-бины и сам регистрирует пост-процессоры
  • Ничем, это синонимы
Метод refresh() контекста вызывает preInstantiateSingletons() и автоматически находит BeanPostProcessor/BeanFactoryPostProcessor среди бинов. Голая фабрика создаёт бины лениво, а пост-процессоры нужно добавлять руками.

Два бина PaymentGateway, ни одного @Primary, поле называется paypalGateway. Что будет (Spring 6.2)?

  • NoUniqueBeanDefinitionException
  • Внедрится бин с именем paypalGateway
  • Внедрится первый зарегистрированный
  • Внедрится null
Совпадение имени точки внедрения с именем бина — одна из стратегий выбора среди нескольких кандидатов. Она работает, если имена параметров доступны (для полей — всегда).

Почему на объекте, созданном через new OrderService(...), не работает @Transactional?

  • @Transactional работает только на интерфейсах
  • Нужно добавить @EnableTransactionManagement в сам класс
  • new создаёт объект без конструктора по умолчанию
  • Объект не бин: контейнер не прогнал его через BeanPostProcessor-ы и не обернул в прокси
Транзакции, кэш, @Async реализуются прокси, которые создаёт BeanPostProcessor при инициализации бина. Объекта из new контейнер не видит.
Что такое IoC и чем DI отличается от Service Locator?

IoC — передача управления созданием и связыванием объектов внешнему механизму. DI — зависимости передаются объекту (конструктор/сеттер/поле), объект не знает, откуда они. Service Locator — объект сам запрашивает зависимости у реестра: остаётся зависимость от инфраструктуры, зависимости не видны в API, тестировать сложнее.

Почему внедрение через конструктор предпочтительнее полевого?

Неизменяемость (final), гарантия полной инициализации, явный список зависимостей, тестирование без контейнера и рефлексии, ранняя ошибка при циклической зависимости. Полевое внедрение прячет зависимости и оставляет поля null вне контейнера.

Как внедрить все реализации интерфейса и в каком порядке они придут?

List<T>/Set<T>/T[] или Map<String,T> (ключ — имя бина). Порядок List — по @Order/Ordered/@Priority, без них — порядок регистрации определений. ObjectProvider.orderedStream() — ленивый вариант.

Что делает @Repository кроме регистрации бина?

Делает бин кандидатом для PersistenceExceptionTranslationPostProcessor: он оборачивает бин в прокси с PersistenceExceptionTranslationInterceptor, который переводит специфичные исключения (JDBC, JPA, Hibernate) в единую иерархию DataAccessException (например DuplicateKeyException).

Когда @Component, а когда @Bean?

@Component — свои классы с единственной естественной реализацией. @Bean — классы сторонних библиотек, сложная сборка, несколько бинов одного класса с разными настройками, условная регистрация в конфигурации.
