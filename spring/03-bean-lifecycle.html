Жизненный цикл бина, scopes и циклические зависимости

Вызов getBean() — это конвейер из десятка этапов: создание экземпляра, внедрение, Aware-колбэки, пост-процессоры, init-методы, обёртка в прокси. Понимание конвейера отвечает на практические вопросы: почему @Transactional не работает в @PostConstruct, почему prototype внутри singleton «не обновляется» и как Spring разрешает циклы через три кэша.

AutowiredAnnotationBeanPostProcessor.determineCandidateConstructors находит единственный конструктор. Для каждого InstantiationAwareBeanPostProcessor вызывается postProcessProperties. Здесь же обрабатываются @Value и сеттеры с @Autowired; @Resource — в CommonAnnotationBeanPostProcessor.

invokeAwareMethods

Фабрика сама вызывает три «базовых» Aware: BeanNameAware, BeanClassLoaderAware, BeanFactoryAware. Остальные (EnvironmentAware, ApplicationContextAware, ApplicationEventPublisherAware…) — не фабрика, а BPP на следующем шаге.

postProcessBeforeInitialization — ApplicationContextAwareProcessor

Первый BPP в списке, добавлен на шаге 3 refresh(). Вызывает setApplicationContext. Внедрять ApplicationContext конструктором проще — Aware-интерфейсы остались в основном для инфраструктурного кода.

postProcessBeforeInitialization — CommonAnnotationBeanPostProcessor

Его родитель InitDestroyAnnotationBeanPostProcessor вызывает методы с @PostConstruct (jakarta.annotation). Здесь же ConfigurationPropertiesBindingPostProcessor заполнил бы поля @ConfigurationProperties-бина.

Важно: this здесь — ещё не прокси. Вызов транзакционного метода из @PostConstruct выполнится без транзакции, @Async — синхронно.

invokeInitMethods

Сначала InitializingBean.afterPropertiesSet(), затем метод из @Bean(initMethod=...). Если один и тот же метод объявлен несколькими способами — вызывается один раз.

Рекомендуемый порядок предпочтения: @PostConstruct (без зависимости от Spring API) → initMethod (для чужих классов) → InitializingBean (инфраструктура).

postProcessAfterInitialization — AbstractAutoProxyCreator

AnnotationAwareAspectJAutoProxyCreator.wrapIfNecessary собирает advisors, подходящие к классу: BeanFactoryTransactionAttributeSourceAdvisor находит @Transactional на методе build. Создаётся CGLIB-прокси ReportService$$SpringCGLIB$$0, внутри которого лежит настоящий объект (target).

Именно прокси (а не исходный объект) попадёт в singletonObjects и будет внедряться в другие бины.

addSingleton → использование

Регистрируются destroy-колбэки (DisposableBeanAdapter), объект кладётся в кэш. Вызов reportService.build(1) из контроллера идёт через прокси → TransactionInterceptor → настоящий метод.

После создания всех singleton-ов вызовутся SmartInitializingSingleton, затем SmartLifecycle.start(), затем события (Boot: ApplicationReadyEvent). Логику «на старте приложения» с транзакциями пишите в обработчике ApplicationReadyEvent или ApplicationRunner — там прокси уже работают.

close() → destroyBeans()

При context.close() или по shutdown hook JVM (Boot регистрирует его сам): публикуется ContextClosedEvent, останавливаются SmartLifecycle (по убыванию phase: сначала веб-сервер перестаёт принимать запросы), затем singleton-ы уничтожаются в порядке, обратном зависимостям: ReportService раньше, чем ReportRepository, который ему нужен.

Порядок колбэков: @PreDestroy → DisposableBean.destroy() → destroy-method (для @Bean по умолчанию выводится: публичный close() или shutdown()). Для prototype-бинов destroy не вызывается никогда.

Проблема «узкий scope внутри широкого»

Зависимости singleton-а внедряются один раз, при его создании. Если внедрить prototype или request-бин напрямую, singleton навсегда получит один экземпляр. Решения:

// 1. ObjectProvider — явное получение при каждом вызове
@Service class Exporter {
    private final ObjectProvider<CsvWriter> writers;            // CsvWriter — @Scope("prototype")
    Exporter(ObjectProvider<CsvWriter> writers) { this.writers = writers; }
    void export() { CsvWriter w = writers.getObject(); /* новый объект */ }
}

// 2. @Lookup — контейнер переопределяет метод в CGLIB-подклассе
@Service abstract class Exporter2 {
    @Lookup protected abstract CsvWriter writer();
}

// 3. Scoped proxy — внедряется прокси, который на каждый вызов ищет объект в текущем scope
@Component
@RequestScope                     // = @Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)
class RequestContextData { String tenantId; }

@Service class TenantService {
    private final RequestContextData data;   // на самом деле прокси; data.tenantId берётся из текущего запроса
    TenantService(RequestContextData data) { this.data = data; }
}
Обращение к request-scoped прокси вне потока HTTP-запроса (в @Async, в @Scheduled, в отдельном потоке пула) даёт IllegalStateException: No thread-bound request found — scope хранится в ThreadLocal потока запроса.

3.4Циклические зависимости и три уровня кэша

DefaultSingletonBeanRegistry хранит singleton-ы в трёх картах:

УровеньПолеСодержимое
1singletonObjectsполностью готовые бины
2earlySingletonObjectsранние ссылки, уже выданные кому-то, но бин ещё не доинициализирован
3singletonFactoriesфабрики () -> getEarlyBeanReference(bean), которые могут выдать раннюю ссылку — при необходимости уже обёрнутую в прокси

Зачем третий уровень, а не сразу второй? Ранняя ссылка должна быть тем же объектом, который в итоге окажется в контексте. Если бин будет обёрнут в AOP-прокси, то и в цикл нужно отдать прокси. Фабрика вызывает SmartInstantiationAwareBeanPostProcessor.getEarlyBeanReference — auto-proxy creator создаёт прокси заранее и запоминает, что этот бин уже обёрнут. Но делает это только если ссылка действительно понадобилась: без цикла прокси создаётся обычным путём.

Симулятор: A ↔ B через поля (field injection)

class A { @Autowired B b; } и class B { @Autowired A a; }, spring.main.allow-circular-references=true.

getBean("a")

getSingleton("a"): в кэшах ничего нет. Имя добавляется в singletonsCurrentlyInCreation, вызывается конструктор A без аргументов.

addSingletonFactory("a", …)

Так как A — singleton, циклы разрешены и A сейчас в создании, в кэш 3-го уровня кладётся фабрика ранней ссылки. Сам объект A пока «сырой»: поле b == null.

populateBean(a)

AutowiredAnnotationBeanPostProcessor пытается внедрить поле b → getBean("b").

getBean("b")

B создаётся конструктором, помечается «в создании», его фабрика тоже уходит в кэш 3-го уровня. Начинается populateBean(b): нужно поле a → getBean("a").

getSingleton("a", allowEarlyReference=true)

Нет в L1. A числится «в создании» — значит, это цикл. Ищем в L2 — пусто. Берём фабрику из L3.

singletonFactory.getObject()

Фабрика вызывает getEarlyBeanReference: если A должен быть проксирован (например, на нём @Transactional), auto-proxy creator создаёт прокси прямо сейчас. Результат переносится в L2, фабрика удаляется из L3. B получает ссылку на A — ещё не инициализированный: @PostConstruct у A пока не вызывался.

initializeBean(b) → addSingleton("b")

B проходит Aware/BPP/init и попадает в L1, удаляется из L2/L3 и из «в создании».

populateBean(a) завершён → initializeBean(a)

A получает готовый B. Затем инициализация: @PostConstruct, init-методы, postProcessAfterInitialization. Auto-proxy creator видит, что A уже был обёрнут при выдаче ранней ссылки, и второй прокси не создаёт.

addSingleton("a") + проверка согласованности

Если ранняя ссылка выдавалась, Spring сверяет: итоговый объект A после всех BPP — тот же, что ранняя ссылка? Если какой-то BPP подменил объект, не поддержав getEarlyBeanReference (типичный случай — @Async), старт падает: BeanCurrentlyInCreationException: Bean with name 'a' has been injected into other beans [b] in its raw version as part of a circular reference, but has eventually been wrapped.

Конструкторы: цикл не разрешается

Чтобы положить раннюю ссылку в L3, объект должен уже существовать. При A(B b) и B(A a) ни один конструктор вызвать нельзя → BeanCurrentlyInCreationException: Requested bean is currently in creation: Is there an unresolvable circular reference or an asynchronous initialization dependency?

Spring Boot 2.6+: циклы запрещены

spring.main.allow-circular-references=false по умолчанию — даже полевой цикл падает на старте с отчётом «The dependencies of some of the beans in the application context form a cycle». Включать обратно — временная мера.

Как правильно разрывать цикл 1. Перепроектировать: вынести общую логику в третий бин, от которого зависят оба. Цикл почти всегда означает смешение ответственностей. 2. События: A публикует событие, B на него подписан — прямая зависимость исчезает. 3. @Lazy на параметре конструктора или ObjectProvider<B>: вместо B внедряется ленивый прокси, B создаётся при первом вызове.

3.5FactoryBean

FactoryBean<T> — бин, который сам является фабрикой другого объекта. getBean("x") вернёт результат getObject(), а getBean("&x") — саму фабрику. Так интегрируются библиотеки со сложной сборкой: JpaRepositoryFactoryBean (каждый репозиторий Spring Data), LocalContainerEntityManagerFactoryBean, SqlSessionFactoryBean из MyBatis.

class CryptoKeyFactoryBean implements FactoryBean<SecretKey> {
    @Override public SecretKey getObject() throws Exception {
        return KeyGenerator.getInstance("AES").generateKey();
    }
    @Override public Class<?> getObjectType() { return SecretKey.class; } // нужен для поиска по типу без создания
    @Override public boolean isSingleton() { return true; }               // результат кэшируется в factoryBeanObjectCache
}

Не путайте с BeanFactory — это контейнер. FactoryBean — бин внутри контейнера.

3.6Самопроверка

В каком порядке вызываются колбэки инициализации?

  • afterPropertiesSet → @PostConstruct → init-method
  • init-method → @PostConstruct → afterPropertiesSet
  • @PostConstruct → init-method → afterPropertiesSet
  • @PostConstruct → afterPropertiesSet → init-method
@PostConstruct вызывается в postProcessBeforeInitialization (CommonAnnotationBeanPostProcessor), затем invokeInitMethods: сначала InitializingBean, потом пользовательский init-method.

Prototype-бин внедрён в singleton через конструктор. Сколько экземпляров prototype увидит singleton за время работы?

  • Новый на каждый вызов метода singleton-а
  • Один — внедрение произошло один раз при создании singleton-а
  • Новый на каждый HTTP-запрос
  • Ноль, будет ошибка старта
Scope влияет на то, что происходит при запросе бина у контейнера. Внедрение — один запрос. Чтобы получать новые экземпляры, нужен ObjectProvider, @Lookup или scoped proxy.

Зачем нужен третий уровень кэша, если есть earlySingletonObjects?

  • Чтобы раннюю ссылку можно было при необходимости сразу обернуть в прокси, и только если цикл действительно возник
  • Для хранения prototype-бинов
  • Для потокобезопасности
  • Для бинов с @Lazy
Фабрика в L3 откладывает решение: getEarlyBeanReference вызывается только при реальном цикле и отдаёт тот объект (возможно, прокси), который окажется в контексте.
Почему @Transactional-метод, вызванный из @PostConstruct, работает без транзакции?

@PostConstruct выполняется в postProcessBeforeInitialization на исходном объекте; прокси создаётся позже, в postProcessAfterInitialization. Плюс вызов идёт через this, мимо прокси. Решение — ApplicationReadyEvent/ApplicationRunner или SmartInitializingSingleton, где вызывать метод через внедрённый бин, или TransactionTemplate.

Объясните разрешение циклической зависимости через три кэша.

A создаётся конструктором, фабрика ранней ссылки — в L3. При внедрении нужен B; B создаётся, при внедрении нужен A → getSingleton находит A «в создании», вызывает фабрику из L3, кладёт результат (возможно, прокси) в L2. B доинициализируется и уходит в L1, затем A получает B, инициализируется и уходит в L1. Для конструкторов не работает: объекта ещё нет.

Как request-scoped бин попадает в singleton-контроллер и остаётся корректным?

Внедряется scoped proxy (CGLIB-подкласс), а не сам объект. Каждый вызов метода прокси делает beanFactory.getBean("scopedTarget.name"), а RequestScope ищет экземпляр в атрибутах текущего запроса через ThreadLocal RequestContextHolder; при отсутствии — создаёт и кладёт туда.

Почему для prototype не вызывается @PreDestroy?

Контейнер не хранит ссылки на prototype-экземпляры после выдачи — он не знает, когда объект больше не нужен. Освобождение ресурсов — ответственность того, кто получил объект (или своего BPP, отслеживающего такие объекты).

В каком порядке уничтожаются singleton-ы?

В обратном порядке зависимостей (контейнер ведёт карту dependentBeanMap): бин уничтожается раньше бинов, от которых зависит. До этого публикуется ContextClosedEvent и останавливаются SmartLifecycle-бины по убыванию phase.
