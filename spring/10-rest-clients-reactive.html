HTTP-клиенты, модели потоков, WebFlux и виртуальные потоки

Сервис не только принимает запросы, но и сам ходит в другие сервисы. Как он это делает — блокируя поток, через event loop или на виртуальных потоках — определяет, сколько нагрузки он выдержит и где у него узкое место. Разберём клиенты Spring, три модели исполнения и посчитаем пропускную способность.

Таймауты по умолчанию — бесконечность или близко к ней Клиент без read timeout при зависшем downstream держит поток навсегда. 200 зависших вызовов — и пул Tomcat исчерпан, сервис «лёг», хотя сам он здоров. Каскадный отказ начинается именно так. Минимум: connect и read timeout на каждом клиенте; лучше — ещё circuit breaker (Resilience4j) и ограничение конкурентности.

Spring Framework 7 добавил в ядро @Retryable и @ConcurrencyLimit (включаются @EnableResilientMethods). Ретраи — только для идемпотентных операций и с экспоненциальной задержкой и джиттером, иначе вы добиваете уже перегруженный сервис.

10.2Три модели исполнения

Поток на запрос (MVC)

Платформенный поток на весь запрос, блокируется на I/O. Простой код, понятные стектрейсы, ThreadLocal работает. Предел — число потоков: 200 по умолчанию, каждый ≈1 МБ стека и переключения контекста ОС.

Event loop (WebFlux)

Несколько потоков Netty (≈ числу ядер) обслуживают тысячи соединений. Код не блокирует поток — описывает конвейер, который продолжится, когда придут данные. Высокая конкурентность, но сложнее код, отладка и контекст (нет ThreadLocal).

Виртуальные потоки (MVC + JDK 21)

Блокирующий код, но блокировка виртуального потока лишь отмонтирует его от carrier-потока. Миллионы потоков дёшевы. Код как в MVC, масштабируемость близка к WebFlux для I/O-нагрузки.

10.3Сколько выдержит сервис: закон Литтла

10.4WebFlux изнутри

@RestController
class PriceController {
    private final WebClient rates;
    private final PriceRepository repo;          // R2DBC: реактивный драйвер БД

    @GetMapping("/prices/{sku}")
    Mono<PriceDto> price(@PathVariable String sku) {
        Mono<Price> base = repo.findBySku(sku);                            // запрос ещё НЕ отправлен
        Mono<Rate> rate = rates.get().uri("/rates/RUB").retrieve().bodyToMono(Rate.class)
                .timeout(Duration.ofSeconds(1))
                .onErrorResume(e -> Mono.just(Rate.FALLBACK));
        return Mono.zip(base, rate, PriceDto::convert);                     // оба запроса пойдут параллельно
    }   // фреймворк подпишется на Mono и запишет результат, когда он будет готов
}

  • Ленивость: Mono/Flux — описание конвейера; работа начинается при subscribe(), которое делает фреймворк.
  • Никаких блокировок в event loop: block(), JDBC, Thread.sleep в потоке Netty останавливают обслуживание тысяч соединений. Блокирующий вызов — в Mono.fromCallable(...).subscribeOn(Schedulers.boundedElastic()) (publishOn переключает только операторы ниже по цепочке). BlockHound ловит такие ошибки в тестах.
  • Backpressure: подписчик запрашивает request(n) элементов — производитель не заваливает медленного потребителя.
  • Контекст: вместо ThreadLocal — Reactor Context; Micrometer context-propagation переносит MDC и трейсы между ними.

10.5Виртуальные потоки в Spring Boot

spring.threads.virtual.enabled=true (JDK 21+) переключает: рабочие потоки Tomcat/Jetty на виртуальные, applicationTaskExecutor (для @Async) — на SimpleAsyncTaskExecutor с виртуальными потоками, планировщик @Scheduled, контейнеры слушателей Kafka/RabbitMQ.

Где выигрыш

Много одновременных запросов, большая часть времени — ожидание I/O (HTTP-вызовы, БД, очереди). Код остаётся простым блокирующим.

Где ловушки

Pinning: до JDK 24 блокировка внутри synchronized «пришпиливала» виртуальный поток к carrier (JEP 491 исправил). Пулы ресурсов становятся узким местом — ограничивайте конкурентность семафором. ThreadLocal-кэши на миллион потоков съедают память. CPU-нагрузку виртуальные потоки не ускоряют.

Что выбрать для нового сервиса По умолчанию — Spring MVC + виртуальные потоки: простота блокирующего кода и высокая конкурентность. WebFlux — когда нужна потоковая обработка (SSE, WebSocket с большим числом клиентов, стриминг данных), backpressure или весь стек уже реактивный (R2DBC, реактивные драйверы).

10.7Самопроверка

Сервис на MVC, 200 потоков Tomcat, downstream перестал отвечать, у RestClient нет read timeout. Что произойдёт?

  • Spring сам прервёт вызов через 30 секунд
  • Запросы переключатся на другие потоки
  • Ничего страшного: Tomcat создаст новые потоки
  • Потоки по одному повиснут в ожидании, пул исчерпается, сервис перестанет отвечать на любые запросы
Классический каскадный отказ. Нужны таймауты, circuit breaker и изоляция (bulkhead).

Что произойдёт, если в контроллере WebFlux вызвать JDBC-репозиторий напрямую?

  • Spring автоматически вынесет вызов в пул
  • Поток event loop заблокируется и перестанет обслуживать другие соединения
  • Ошибка компиляции
  • Вызов станет неблокирующим
Event loop потоков мало. Блокирующие вызовы — только через Schedulers.boundedElastic или реактивные драйверы (R2DBC).

После включения виртуальных потоков сервис начал сыпать ошибками «Connection is not available, request timed out». Почему?

  • Ограничение по потокам снято, и пул соединений БД стал узким местом
  • Виртуальные потоки не поддерживают JDBC
  • Hikari несовместим с JDK 21
  • Утечка памяти
Раньше 200 потоков естественно ограничивали конкурентность. Теперь тысячи потоков одновременно ждут соединения. Ограничьте конкурентность явно или пересмотрите размер пула.
RestTemplate, RestClient, WebClient — когда что?

RestClient — синхронный клиент для MVC и виртуальных потоков, современный fluent API. WebClient — для реактивного стека и потоковой обработки. RestTemplate (deprecated с Spring 7) — только поддержка существующего кода. Для внешних API удобно описывать интерфейс @HttpExchange поверх любого из них.

Почему нужно внедрять RestClient.Builder, а не вызывать RestClient.create()?

Builder из контекста настроен автоконфигурацией: конвертеры сообщений с вашим ObjectMapper, наблюдаемость (метрики http.client.requests, распространение трейса), кастомайзеры. create() даёт голый клиент без всего этого.

Объясните, как работает WebFlux и чем он отличается от MVC.

Неблокирующий стек на Reactor и Netty: малое число потоков event loop, обработка через асинхронные конвейеры Mono/Flux, ленивое выполнение по подписке, backpressure. DispatcherHandler аналогичен DispatcherServlet. Отличия: нет ThreadLocal-контекста, нельзя блокировать, сложнее отладка, нужны реактивные драйверы.

Как оценить нужное число потоков или соединений?

Закон Литтла: L = RPS × среднее время удержания ресурса. Добавить запас на пики и проверить нагрузочным тестом с метриками (активные потоки, ожидание соединения из пула, p99). Ресурс за пулом (лимиты БД, downstream) задаёт верхнюю границу.
