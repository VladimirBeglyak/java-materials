Actuator и наблюдаемость

Сервис в продакшене должен отвечать на три вопроса: жив ли он, готов ли принимать трафик и что у него внутри происходит. Actuator даёт health-пробы и служебные endpoints, Micrometer — метрики, Observation API и Micrometer Tracing — распределённые трейсы, Boot — структурированные логи с traceId. Разберём, как это устроено и как не убить сервис неправильной пробой.

16.2Health и пробы Kubernetes

Каждый HealthIndicator (автоконфигурация добавляет db, redis, diskSpace, ssl, mail, rabbit…; для Kafka встроенного индикатора нет — только свой) возвращает Health. StatusAggregator сводит статусы по порядку тяжести: DOWN → OUT_OF_SERVICE → UP → UNKNOWN. DOWN и OUT_OF_SERVICE дают HTTP 503.

Liveness: «процесс жив?»

Не прошла → Kubernetes перезапускает под. Должна зависеть только от состояния самого процесса (livenessState). Boot ставит CORRECT после refresh контекста; в BROKEN её переводит само приложение (AvailabilityChangeEvent.publish(ctx, LivenessState.BROKEN)).

Readiness: «готов к трафику?»

Не прошла → под убирается из балансировки, но не перезапускается. Сюда — критичные зависимости, без которых запрос не обработать. Boot ставит REFUSING_TRAFFIC при остановке.

Симулятор health-проб

Отметьте, какие индикаторы в состоянии DOWN, и выберите, что входит в группы.

@Component("paymentGateway")                           // имя в ответе: "paymentGateway"
class PaymentGatewayHealth implements HealthIndicator {
    private final PaymentClient client;
    PaymentGatewayHealth(PaymentClient client) { this.client = client; }

    @Override public Health health() {
        try {
            Duration d = client.ping();                  // быстрая проверка с коротким таймаутом!
            return Health.up().withDetail("latencyMs", d.toMillis()).build();
        } catch (Exception e) {
            return Health.down(e).build();
        }
    }
}

16.3Метрики: Micrometer

Micrometer — фасад метрик (как SLF4J для логов). MeterRegistry собирает метрики, а реализация (PrometheusMeterRegistry, OTLP, Datadog) отдаёт их в систему мониторинга. Boot автоматически снимает: http.server.requests, http.client.requests, jvm.memory.*, jvm.gc.*, jvm.threads.*, hikaricp.connections.*, executor.*, cache.*, spring.kafka.*, tomcat.*.

@Service
class CheckoutMetrics {
    private final Counter placed;
    private final Timer paymentTimer;

    CheckoutMetrics(MeterRegistry r, OrderQueue queue) {
        this.placed = Counter.builder("orders.placed").tag("channel", "web").register(r);
        this.paymentTimer = Timer.builder("payment.duration").publishPercentileHistogram().register(r);
        Gauge.builder("orders.queue.size", queue, OrderQueue::size).register(r);   // значение читается при опросе
    }

    void onPlaced() { placed.increment(); }
    <T> T timePayment(Supplier<T> call) { return paymentTimer.record(call); }
}
Кардинальность Каждое уникальное сочетание тегов — отдельный временной ряд. Тег userId или orderId породит миллионы рядов и положит Prometheus. Теги — только ограниченные множества: метод, статус, канал, тип ошибки. Boot нормализует uri в шаблон (/api/orders/{id}) именно поэтому.

16.4Observation API и трейсинг

С Boot 3 инструментирование идёт через Observation API: код один раз описывает наблюдаемую операцию, а зарегистрированные обработчики превращают её одновременно в метрику (таймер), в span трейса и в записи лога. Spring MVC, RestClient, JDBC (через datasource-micrometer), Kafka, @Scheduled уже инструментированы.

@Service
class FraudCheck {
    private final ObservationRegistry registry;

    Verdict check(Order o) {
        return Observation.createNotStarted("fraud.check", registry)
                .lowCardinalityKeyValue("channel", o.channel())       // тег метрики и span
                .highCardinalityKeyValue("order.id", o.id().toString())  // только в span, не в метрике
                .observe(() -> engine.evaluate(o));
    }

    @Observed(name = "fraud.rules.reload")                            // декларативно: management.observations.annotations.enabled=true + spring-boot-starter-aspectj
    void reloadRules() { /* ... */ }
}

16.5Graceful shutdown в Kubernetes

  1. Kubernetes помечает под Terminating, начинает удалять его из Endpoints и одновременно шлёт SIGTERM (сначала выполняется preStop).
  2. Удаление из балансировщиков распространяется не мгновенно, поэтому preStop: sleep 5–10 даёт время перестать слать трафик на под.
  3. Shutdown hook JVM → context.close(): readiness → REFUSING_TRAFFIC, ContextClosedEvent.
  4. SmartLifecycle-фазы останавливаются по убыванию phase: веб-сервер в SmartLifecycle-фазы останавливаются по убыванию: сначала контейнеры слушателей Kafka (phase Integer.MAX_VALUE - 100), затем веб-сервер в режиме server.shutdown=graceful перестаёт принимать соединения и ждёт активные запросы до spring.lifecycle.timeout-per-shutdown-phase.
  5. Уничтожаются бины: пул соединений закрывается последним, когда запросы уже завершены.
  6. Если не уложились в terminationGracePeriodSeconds (по умолчанию 30) — SIGKILL.

16.6Самопроверка

Почему проверку БД нельзя включать в liveness-пробу?

  • Она медленная
  • Spring это запрещает
  • При сбое БД Kubernetes перезапустит все поды, что не лечит БД и вызывает каскад рестартов
  • Liveness не поддерживает индикаторы
Рестарт помогает только от проблем самого процесса (дедлок, сломанный контекст). Внешние зависимости — в readiness или только в мониторинг.

Добавили тег userId к метрике http.server.requests. Чем это грозит?

  • Взрывом кардинальности: по ряду на пользователя, перерасход памяти приложения и Prometheus
  • Ничем
  • Метрика перестанет собираться
  • Утечкой персональных данных в логи
Высококардинальные данные — в span трейса (highCardinalityKeyValue) или логи, но не в теги метрик.

Как связать строки логов разных сервисов одного запроса?

  • По времени
  • По traceId, который Micrometer Tracing передаёт в traceparent и кладёт в MDC
  • По имени потока
  • По sessionId
traceId сквозной для всех сервисов запроса и автоматически попадает в лог-паттерн или структурированный лог.
Чем liveness отличается от readiness и что включать в каждую?

Liveness — жив ли процесс; провал → рестарт пода. Только внутреннее состояние (livenessState). Readiness — может ли под обслуживать трафик; провал → исключение из балансировки без рестарта. Состояние готовности и критичные зависимости. Некритичные зависимости — ни туда, ни туда, только в общий health/алерты.

Что такое Observation API и зачем он, если есть Micrometer метрики?

Единая абстракция «наблюдаемой операции»: один раз инструментируем код, а обработчики создают и таймер, и span, и логи с корреляцией. Низкокардинальные ключи идут в метрики и спаны, высококардинальные — только в спаны. Spring-проекты инструментированы через него.

Как устроен graceful shutdown Spring Boot?

SIGTERM → shutdown hook → context.close(): readiness REFUSING_TRAFFIC, ContextClosedEvent, остановка SmartLifecycle по фазам (веб-сервер перестаёт принимать соединения и ждёт активные запросы до timeout-per-shutdown-phase), затем уничтожение бинов. В Kubernetes дополняется preStop-задержкой и достаточным terminationGracePeriodSeconds.
