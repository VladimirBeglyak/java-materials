Диагностика: типичные ошибки и как их читать

Сообщения об ошибках Spring длинные, но устроены одинаково: цепочка «кто кого пытался создать» и первопричина в самом низу. Зная внутренности из предыдущих глав, любую ошибку можно свести к конкретному механизму. Эта глава — справочник: как читать стектрейс, что означают частые исключения, какие логи включить и куда ставить точки останова.

22.1Как читать стектрейс старта

org.springframework.beans.factory.UnsatisfiedDependencyException:
  Error creating bean with name 'orderController' defined in file [.../OrderController.class]:
  Unsatisfied dependency expressed through constructor parameter 0:
    Error creating bean with name 'orderService' defined in file [.../OrderService.class]:
    Unsatisfied dependency expressed through constructor parameter 1:
      No qualifying bean of type 'com.shop.payment.PaymentClient' available:
      expected at least 1 bean which qualifies as autowire candidate. Dependency annotations: {}
...
Caused by: org.springframework.beans.factory.NoSuchBeanDefinitionException:
  No qualifying bean of type 'com.shop.payment.PaymentClient' available   ← ПЕРВОПРИЧИНА
  1. Найдите последний «Caused by» — это первопричина. Всё выше — обёртки, показывающие путь.
  2. Прочитайте цепочку «Error creating bean with name» сверху вниз: это стек рекурсивных getBean: контроллер → сервис → отсутствующий клиент.
  3. «through constructor parameter 1» — индекс параметра (с нуля); «through field 'x'» — полевое внедрение.
  4. В Spring Boot сначала смотрите блок APPLICATION FAILED TO START: FailureAnalyzer уже перевёл ошибку в «Description / Action».

22.5Проблемы под нагрузкой

Сервис «завис»

Thread dump (jstack, /actuator/threaddump): в каком методе стоят потоки http-nio-*. Все в HikariPool.getConnection — исчерпан пул; в SocketInputStream.read — ждут downstream без таймаута; BLOCKED на мониторе — блокировка в коде.

Медленные ответы

Трейс запроса (тема 16) покажет, какой span длинный. Затем: счётчик SQL-запросов на HTTP-запрос (N+1), метрика ожидания соединения hikaricp.connections.acquire, GC-паузы (jvm.gc.pause), очередь пула потоков.

Рост памяти

Heap dump и анализ в Eclipse MAT / VisualVM. Частые причины в Spring-приложениях: неограниченный кэш (ConcurrentMapCacheManager), неограниченная очередь executor'а, большие выборки сущностей в persistence context, ThreadLocal без очистки.

Медленный старт

/actuator/startup и DEBUG-лог создания бинов — найдите долгие бины (тема 17).

22.6Самопроверка

В стектрейсе пять вложенных UnsatisfiedDependencyException и в конце NoSuchBeanDefinitionException. С чего начать?

  • С первого исключения
  • С последнего «Caused by» — это первопричина, остальное — путь до неё
  • С третьего
  • Перезапустить
Каждый уровень — один рекурсивный getBean. Корень внизу.

Метод с @Cacheable вызывается, но кэш не используется, ошибок нет. Что проверить в первую очередь?

  • Версию Java
  • Размер пула соединений
  • Настройки Tomcat
  • Как вызывается метод (не через this ли), public ли он, включён ли @EnableCaching, прокси ли бин
Молчаливое игнорирование аннотаций почти всегда значит, что вызов не прошёл через прокси.

Все потоки http-nio в thread dump стоят в HikariPool.getConnection. Что это значит?

  • Пул соединений исчерпан: кто-то держит соединения слишком долго
  • БД недоступна
  • Tomcat перегружен
  • Deadlock в JVM
Ищите в том же дампе потоки, которые держат соединение: долгие транзакции, внешние вызовы внутри транзакции, REQUIRES_NEW.
Приложение не стартует с ошибкой создания бина. Ваш алгоритм действий?

Прочитать блок APPLICATION FAILED TO START (Description/Action) → найти последний Caused by → пройти цепочку «Error creating bean» → определить механизм (нет бина, неоднозначность, цикл, свойство, условие) → проверить отчёт условий (--debug), активные профили, пакет сканирования, дерево зависимостей.

Как узнать, действительно ли метод выполняется в транзакции?

TRACE-лог org.springframework.transaction.interceptor («Getting transaction for…», «Completing transaction for…»), в отладчике TransactionSynchronizationManager.isActualTransactionActive() и getCurrentTransactionName(), стек вызовов должен содержать TransactionInterceptor.invoke между вызывающим и методом.

Как диагностировать «всё тормозит» в продакшене без отладчика?

Метрики (латентность по endpoint-ам, пул потоков, пул соединений, GC), распределённый трейс медленного запроса, thread dump (несколько с интервалом), временное повышение уровня логирования через /actuator/loggers, при подозрении на память — heap dump.
