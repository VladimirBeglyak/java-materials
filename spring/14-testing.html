Тестирование Spring-приложений

Spring умеет поднимать в тесте контекст целиком, частично (срез) или не поднимать вовсе. Ключевой механизм — кэш контекстов TestContext Framework: от него зависит, идут ли тесты 2 минуты или 20. Разберём, как устроен кэш, когда он ломается, как работают срезы и как тестировать с настоящей БД в контейнере.

14.2TestContext Framework изнутри

JUnit 5 → SpringExtension@SpringBootTest и срезы мета-аннотированы @ExtendWith(SpringExtension.class)
↓
TestContextManagerодин на тестовый класс; bootstrapper (SpringBootTestContextBootstrapper) собирает конфигурацию: ищет @SpringBootConfiguration вверх по пакетам
↓
MergedContextConfigurationклассы конфигурации, профили, свойства, инициализаторы, ContextCustomizer-ы (моки, @ServiceConnection, срезы) — это КЛЮЧ кэша
↓
ContextCacheстатический, на JVM; LRU, по умолчанию 32 контекста (spring.test.context.cache.maxSize)
↓
TestExecutionListener-ыDependencyInjection (внедряет @Autowired в тест), Transactional (откат после теста), SqlScripts (@Sql), сброс моков, DirtiesContext, события

Контекст поднимается один раз для всех тестовых классов с одинаковым ключом и живёт до конца JVM (или до вытеснения/@DirtiesContext). Gradle и Maven Surefire по умолчанию запускают тесты модуля в одной JVM — кэш работает на весь прогон.

14.3Что ломает кэш

Любое различие в ключе — новый контекст: свой набор @MockitoBean, другие @ActiveProfiles, properties, @TestPropertySource, @Import тестовой конфигурации, вложенный @TestConfiguration. @DirtiesContext закрывает контекст после класса.

Симулятор кэша контекстов

Шесть классов с @SpringBootTest выполняются по порядку. Старт контекста ≈ 9 с. Меняйте аннотации — смотрите, сколько контекстов поднимется.

Как держать число контекстов малым Общий абстрактный базовый класс AbstractIntegrationTest с одним набором аннотаций, моков и контейнеров; все интеграционные тесты наследуют его. Вместо @DirtiesContext — очищать данные (@Sql, truncate в @AfterEach). В логе (logging.level.org.springframework.test.context.cache=DEBUG) видна статистика попаданий в кэш.

Как это сделано: аннотация среза включает @TypeExcludeFilters(WebMvcTypeExcludeFilter.class) — сканирование пропускает всё, кроме веб-компонентов, — и @AutoConfigureWebMvc, который через @ImportAutoConfiguration подключает только перечисленные в файле META-INF/spring/…AutoConfigureWebMvc.imports автоконфигурации.

@WebMvcTest(OrderController.class)
class OrderControllerTest {
    @Autowired MockMvcTester mvc;
    @MockitoBean OrderService orders;                   // заменяет бин в контексте среза

    @Test
    void returns400OnInvalidBody() {
        assertThat(mvc.post().uri("/api/orders").with(jwt())
                .contentType(MediaType.APPLICATION_JSON)
                .content("{\"items\": [], \"address\": \"\"}"))
            .hasStatus(HttpStatus.BAD_REQUEST)
            .bodyJson().extractingPath("$.errors[*].field").asArray().contains("items", "address");
        verifyNoInteractions(orders);
    }
}
@MockBean → @MockitoBean Spring Framework 6.2 добавил собственные @MockitoBean, @MockitoSpyBean и @TestBean (подмена бина фабричным методом). @MockBean из Boot объявлен устаревшим в 3.4 и удалён в 4.0. Механизм тот же: BeanOverrideContextCustomizer входит в ключ кэша.

14.5@SpringBootTest и Testcontainers

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureRestTestClient                             // Boot 4: клиент для запросов к запущенному серверу
@Testcontainers
abstract class AbstractIntegrationTest {

    @Container
    @ServiceConnection                                   // Boot сам подставит url/user/password в DataSource
    static PostgreSQLContainer postgres = new PostgreSQLContainer("postgres:17-alpine");   // Testcontainers 2 (Boot 4): org.testcontainers.postgresql

    @Container
    @ServiceConnection
    static KafkaContainer kafka = new KafkaContainer("apache/kafka:3.9.0");

    @Autowired protected RestTestClient http;           // в Boot 3 — TestRestTemplate (внедряется без доп. аннотаций)
}

class OrderFlowIT extends AbstractIntegrationTest {
    @Autowired OrderRepository repo;

    @Test
    void createsOrder() {
        http.post().uri("/api/orders").body(validRequest()).exchange()
            .expectStatus().isCreated();
        assertThat(repo.count()).isEqualTo(1);
    }
}

webEnvironment

MOCK (по умолчанию) — mock servlet-окружение, тестируется через MockMvc, всё в одном потоке. RANDOM_PORT — настоящий Tomcat на случайном порту, запросы идут по сети. NONE — без веба.

@ServiceConnection

Контейнер превращается в бин ConnectionDetails (JdbcConnectionDetails, KafkaConnectionDetails), который автоконфигурация использует вместо свойств. Раньше — @DynamicPropertySource с ручной передачей URL.

Тот же контейнер можно использовать при локальной разработке: класс TestShopApplication в test-исходниках с SpringApplication.from(ShopApplication::main).with(ContainersConfig.class).run(args) поднимает приложение с БД в Docker без ручной установки.

14.6@Transactional в тестах: удобство и ловушки

TransactionalTestExecutionListener открывает транзакцию до теста и откатывает её после — база чистая без уборки. Но:

  • С RANDOM_PORT запрос обрабатывает поток Tomcat — у него своя транзакция, она коммитится, и откат теста её не затрагивает.
  • Тест и код в одной транзакции и одном persistence context: ленивые связи грузятся, хотя в проде упадут с LazyInitializationException; ошибки ограничений БД не проявятся, если flush не случился. Вызывайте entityManager.flush() или проверяйте без транзакции.
  • @TransactionalEventListener(AFTER_COMMIT) не вызывается — коммита нет.

Поэтому для сквозных сценариев надёжнее тесты без @Transactional и явная очистка данных.

14.7Самопроверка

Два тестовых класса @SpringBootTest отличаются только тем, что во втором есть @MockitoBean EmailSender. Сколько контекстов поднимется?

  • Один — моки не влияют на контекст
  • Один, но мок будет и в первом классе
  • Два — набор подменённых бинов входит в ключ кэша
  • Ноль, моки отключают кэш
ContextCustomizer подмены бинов — часть MergedContextConfiguration. Разный набор моков — разные ключи.

Тест @SpringBootTest(webEnvironment = RANDOM_PORT) помечен @Transactional и через HTTP создаёт заказ. Откатится ли заказ после теста?

  • Нет: запрос выполнялся в потоке сервера в собственной транзакции, которая закоммитилась
  • Да, всегда
  • Да, если БД PostgreSQL
  • Тест упадёт
Транзакции привязаны к потоку. Транзакция теста и транзакция обработки запроса — разные.

Что делает @DataJpaTest с DataSource по умолчанию?

  • Использует DataSource из application.yml
  • Не создаёт DataSource
  • Подключается к Testcontainers автоматически
  • Заменяет его встроенной БД (H2 и т.п.), если не указано @AutoConfigureTestDatabase(replace = NONE) или @ServiceConnection
Для проверки нативных запросов и диалекта нужна та же СУБД, что в проде — используйте контейнер.
Как работает кэш контекстов и почему тесты могут быть медленными?

ContextCache — статическая LRU-карта MergedContextConfiguration → ApplicationContext на JVM. Одинаковая конфигурация тестовых классов — один контекст. Разные моки, профили, свойства, @Import, @DirtiesContext создают и пересоздают контексты, каждый — секунды старта. Лечится унификацией конфигурации через базовый класс.

Чем @WebMvcTest отличается от @SpringBootTest с MockMvc?

@WebMvcTest поднимает только веб-слой (контроллеры, advice, фильтры, конвертеры, Security) — сервисы надо мокать; быстро и изолированно. @SpringBootTest + @AutoConfigureMockMvc поднимает весь контекст — проверяет интеграцию слоёв, медленнее.

Почему H2 вместо настоящей БД в тестах — плохая идея?

Другой SQL-диалект, типы, функции, поведение блокировок и уровней изоляции, ограничения. Тест зелёный — прод падает на нативном запросе или миграции. Testcontainers с той же версией СУБД даёт реальное поведение ценой нескольких секунд старта, которые кэш контекста амортизирует.
