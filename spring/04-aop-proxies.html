AOP и прокси

Транзакции, кэширование, @Async, безопасность методов, ретраи, репозитории Spring Data — всё это прокси. Прокси стоит между вызывающим кодом и вашим объектом и выполняет цепочку перехватчиков до и после настоящего метода. Почти все «магические» баги Spring (транзакция не откатилась, кэш не сработал, @Async выполнился синхронно) объясняются тем, что вызов прошёл мимо прокси.

Boot выбрал CGLIB по умолчанию, чтобы внедрение по конкретному классу не ломалось от появления @Transactional.

У CGLIB-прокси пустые поля Экземпляр прокси создаётся через Objenesis — без вызова конструктора. Поля прокси-объекта не инициализированы, все данные живут в target. Пока вызов перехватывается, это незаметно. Но final-метод не переопределён, выполняется на самом прокси — и его обращение к полям даёт null и NullPointerException.

4.3Как Spring решает обернуть бин

@EnableAspectJAutoProxy (в Boot включается автоконфигурацией AopAutoConfiguration) регистрирует AnnotationAwareAspectJAutoProxyCreator — это BeanPostProcessor. В postProcessAfterInitialization каждого бина он вызывает wrapIfNecessary:

findCandidateAdvisorsбины-Advisor (транзакции, кэш, @Async…) + advisors из классов @Aspect
→
findAdvisorsThatCanApplyClassFilter, затем MethodMatcher по каждому методу класса
→
sortAdvisors@Order / Ordered
→
ProxyFactory.getProxyпустой список → бин возвращается как есть

Сами инфраструктурные классы (Advisor, Advice, AopInfrastructureBean) не проксируются. Решения кэшируются: для каждого класса подходящие advisors вычисляются один раз.

4.4Как выполняется вызов через прокси

Прокси хранит AdvisedSupport — конфигурацию: target, список advisors, интерфейсы. При вызове метода он получает цепочку перехватчиков для этого метода (кэшируется в methodCache) и создаёт ReflectiveMethodInvocation (для CGLIB — CglibMethodInvocation). Это паттерн «цепочка ответственности»: каждый перехватчик решает, вызывать ли proceed().

public Object proceed() throws Throwable {
    if (currentInterceptorIndex == interceptors.size() - 1) {
        return invokeJoinpoint();                 // конец цепочки: method.invoke(target, args)
    }
    MethodInterceptor next = interceptors.get(++currentInterceptorIndex);
    return next.invoke(this);                     // перехватчик сам вызовет proceed() — или нет
}

// Так выглядит любой around-перехватчик, например упрощённый TransactionInterceptor:
public Object invoke(MethodInvocation mi) throws Throwable {
    TransactionStatus tx = tm.getTransaction(def);
    try {
        Object result = mi.proceed();             // дальше по цепочке и в целевой метод
        tm.commit(tx);
        return result;
    } catch (RuntimeException | Error e) {
        tm.rollback(tx);
        throw e;
    }
}

Порядок перехватчиков определяется порядком advisors. Транзакционный advisor по умолчанию имеет Ordered.LOWEST_PRECEDENCE, его можно поменять через @EnableTransactionManagement(order = ...). Важный практический случай: ретрай должен быть снаружи транзакции, иначе повтор пойдёт в уже помеченной на откат транзакции.

4.5Свой аспект

@Target(ElementType.METHOD) @Retention(RetentionPolicy.RUNTIME)
public @interface Timed { String value(); }

@Aspect
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)        // самый внешний — замеряет и транзакцию
class TimingAspect {
    private final MeterRegistry registry;
    TimingAspect(MeterRegistry registry) { this.registry = registry; }

    @Around("@annotation(timed)")          // параметр связывается с аннотацией метода
    Object time(ProceedingJoinPoint pjp, Timed timed) throws Throwable {
        Timer.Sample s = Timer.start(registry);
        try {
            return pjp.proceed();
        } finally {
            s.stop(registry.timer(timed.value(), "method", pjp.getSignature().getName()));
        }
    }
}
PointcutВыбирает
execution(* com.shop..*Service.*(..))все методы классов, чьё имя заканчивается на Service, в пакете com.shop и подпакетах
within(com.shop.web..*)все методы классов в пакете
@annotation(com.shop.Timed)методы с аннотацией
@within(org.springframework.stereotype.Service)методы классов с аннотацией
bean(*Repository)бины по имени (только Spring AOP)
args(java.util.UUID, ..)по типам аргументов в рантайме

Виды advice: @Before, @AfterReturning, @AfterThrowing, @After (finally), @Around. Внутри одного аспекта с Spring 5.2.7 порядок приоритета: @Around → @Before → @After → @AfterReturning/@AfterThrowing; фактически @After (finally) выполняется после @AfterReturning/@AfterThrowing того же аспекта. Между аспектами — по @Order: меньшее значение — внешний слой (первым входит, последним выходит).

4.6Когда прокси не срабатывает

@Service
class InvoiceService {
    public void generateAll(List<Long> ids) {
        for (long id : ids) generate(id);           // this.generate(id) — вызов мимо прокси!
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void generate(long id) { /* ожидаем отдельную транзакцию на каждый счёт — её не будет */ }
}

Внешний код вызывает proxy.generateAll(). Прокси передаёт вызов в target, и внутри target this — это target, а не прокси. Перехватчики видят только вызовы, пришедшие через ссылку на прокси.

Как починить self-invocation Лучший способ — вынести метод в отдельный бин (InvoiceGenerator): вызов пойдёт через его прокси. Допустимо: внедрить себя же (@Lazy InvoiceService self или ObjectProvider<InvoiceService>) и звать self.generate(). Для транзакций — TransactionTemplate вместо аннотации. Тяжёлая артиллерия: AspectJ weaving (@EnableTransactionManagement(mode = AdviceMode.ASPECTJ)) встраивает логику в байткод, прокси не нужен.

4.8Самопроверка

Бин OrderServiceImpl implements OrderService с @Transactional, приложение на «чистом» Spring без proxyTargetClass. Внедряем по классу: @Autowired OrderServiceImpl s. Что будет?

  • Всё работает
  • Внедрится target без прокси
  • BeanNotOfRequiredTypeException: прокси реализует интерфейс, но не является OrderServiceImpl
  • Создастся второй бин
Есть интерфейс → JDK-прокси, который не наследует класс реализации. В Spring Boot этого не случится: там CGLIB по умолчанию.

Два аспекта: A с @Order(1) и B с @Order(2), оба @Around. Порядок выполнения?

  • B до → A до → метод → A после → B после
  • A до → B до → метод → B после → A после
  • Неопределён
  • Только A — аспект с меньшим порядком отменяет остальные
Меньший order = более высокий приоритет = внешний слой: входит первым и выходит последним.

Что Spring AOP НЕ может перехватить?

  • public-метод бина, вызванный из контроллера
  • метод интерфейса репозитория Spring Data
  • protected-метод при CGLIB, вызванный из того же пакета
  • вызов метода объекта, созданного через new
Spring AOP работает только для бинов: прокси создаёт BeanPostProcessor контейнера. Объекты из new требуют AspectJ weaving.
Как создаётся AOP-прокси для бина? Какие классы участвуют?

AnnotationAwareAspectJAutoProxyCreator (BeanPostProcessor) в postProcessAfterInitialization → wrapIfNecessary: находит advisors (бины Advisor + методы @Aspect через ReflectiveAspectJAdvisorFactory), фильтрует по pointcut (AopUtils.findAdvisorsThatCanApply), сортирует, создаёт ProxyFactory; DefaultAopProxyFactory выбирает JdkDynamicAopProxy или ObjenesisCglibAopProxy.

Почему self-invocation не проходит через прокси и как это исправить?

Прокси — отдельный объект, который делегирует в target. Внутри target this ссылается на target. Исправления: вынести метод в другой бин; self-инъекция прокси; AopContext.currentProxy() с exposeProxy; программный API (TransactionTemplate); AspectJ weaving.

Чем отличаются JDK dynamic proxy и CGLIB? Что выбирает Spring Boot?

JDK — реализует интерфейсы через java.lang.reflect.Proxy, перехватывает методы интерфейсов. CGLIB — генерирует подкласс, перехватывает переопределяемые методы, не работает с final-классами/методами, создаёт экземпляр через Objenesis. Boot: spring.aop.proxy-target-class=true → CGLIB всегда.

Чем Spring AOP отличается от AspectJ?

Spring AOP — прокси в рантайме, только вызовы методов бинов, проблемы с self-invocation, final, private. AspectJ — изменение байткода (compile-time через ajc или load-time weaving через агент), любые join points (поля, конструкторы, static), любые объекты, без self-invocation-проблем, но сложнее сборка. Spring использует библиотеку AspectJ только для разбора и сопоставления pointcut-ов; выполнение — прокси Spring AOP, без компилятора и weaver-а AspectJ.
