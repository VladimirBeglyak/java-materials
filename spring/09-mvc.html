Spring MVC: путь HTTP-запроса

От байтов в сокете до вызова метода контроллера и обратно — около десятка компонентов: Tomcat, цепочка фильтров, DispatcherServlet, HandlerMapping, HandlerAdapter, резолверы аргументов, конвертеры сообщений, обработчики исключений. Каждый — точка расширения. Зная маршрут, вы понимаете, где добавить логирование, почему ошибка из фильтра не попадает в @ControllerAdvice и откуда берётся 415.

9.1Контроллер, который будем разбирать

@RestController
@RequestMapping("/api/orders")
class OrderController {
    private final OrderService orders;
    OrderController(OrderService orders) { this.orders = orders; }

    @PostMapping(consumes = MediaType.APPLICATION_JSON_VALUE)
    ResponseEntity<OrderDto> create(@Valid @RequestBody CreateOrderRequest req,
                                    @RequestHeader("Idempotency-Key") UUID key,
                                    @AuthenticationPrincipal Jwt jwt,
                                    UriComponentsBuilder uri) {
        OrderDto dto = orders.create(req, key, jwt.getSubject());
        return ResponseEntity.created(uri.path("/api/orders/{id}").build(dto.id())).body(dto);
    }

    @GetMapping("/{id}")
    OrderDto get(@PathVariable long id) { return orders.get(id); }
}

record CreateOrderRequest(@NotEmpty List<@Valid Item> items, @NotBlank String address) {
    record Item(@NotBlank String sku, @Positive int qty) { }
}

Коннектор Tomcat (NIO)

Поток Acceptor принимает TCP-соединение и регистрирует сокет в Poller (селектор NIO). Когда в сокете появились данные, Poller отдаёт его рабочему потоку из пула http-nio-8080-exec-N (по умолчанию до 200). Этот поток будет держать запрос до конца — модель «поток на запрос».

Http11Processor разбирает HTTP, CoyoteAdapter создаёт HttpServletRequest/Response и передаёт их в конвейер контейнера (Engine → Host → Context → Wrapper), который вызывает цепочку фильтров.

ApplicationFilterChain

Фильтры Servlet API (Boot регистрирует бины-Filter автоматически, порядок по @Order): CharacterEncodingFilter, ServerHttpObservationFilter (метрика http.server.requests и трейс), DelegatingFilterProxy → FilterChainProxy Spring Security (тема 13), RequestContextFilter.

Фильтры работают до DispatcherServlet: исключение здесь не увидит @ControllerAdvice — его обработает контейнер через страницу ошибки /error.

FrameworkServlet.processRequest → doDispatch

Привязывает к потоку LocaleContextHolder и RequestContextHolder (ThreadLocal), затем doDispatch — сердце MVC:

HandlerExecutionChain chain = getHandler(request);          // 1. кто обработает
HandlerAdapter ha = getHandlerAdapter(chain.getHandler());  // 2. как вызвать
if (!chain.applyPreHandle(request, response)) return;       // 3. интерцепторы
ModelAndView mv = ha.handle(request, response, handler);    // 4. вызов
chain.applyPostHandle(request, response, mv);
processDispatchResult(request, response, chain, mv, ex);    // 5. исключения / view
// finally: triggerAfterCompletion

RequestMappingHandlerMapping

Карта маршрутов построена на старте: в afterPropertiesSet маппинг перебрал бины с @Controller, для каждого метода с @RequestMapping создал RequestMappingInfo (путь, HTTP-метод, consumes, produces, params, headers) и сохранил в MappingRegistry → HandlerMethod.

Сейчас по запросу отбираются подходящие условия и выбирается самое специфичное (/api/orders/{id} проигрывает /api/orders/latest). Пути разбираются PathPatternParser. Результат — HandlerExecutionChain: HandlerMethod + интерцепторы.

Не нашли — следующий HandlerMapping (функциональные роуты, статические ресурсы); никто не подошёл — NoResourceFoundException → 404. Путь есть, но метод не тот — 405; не тот Content-Type — 415.

HandlerInterceptor.preHandle

Интерцепторы Spring MVC знают обработчик (HandlerMethod) — можно читать аннотации метода. preHandle вернул false → обработка прекращается (интерцептор сам пишет ответ). Регистрируются через WebMvcConfigurer.addInterceptors.

HandlerMethodArgumentResolver

RequestMappingHandlerAdapter создаёт ServletInvocableHandlerMethod и для каждого параметра ищет резолвер (список ~30, результат кэшируется):

  • @RequestBody → RequestResponseBodyMethodProcessor: по Content-Type: application/json выбирает HttpMessageConverter (Jackson), читает тело в CreateOrderRequest; @Valid → валидатор, ошибки → MethodArgumentNotValidException (400);
  • @RequestHeader UUID → строка из заголовка + конвертация через ConversionService;
  • @AuthenticationPrincipal → резолвер Spring Security достаёт principal из SecurityContextHolder;
  • UriComponentsBuilder → создаётся из текущего запроса.

InvocableHandlerMethod.doInvoke

Метод вызывается рефлексией. orders.create(...) идёт через прокси сервиса: транзакция открывается здесь, в рабочем потоке Tomcat, и закрывается до возврата в контроллер.

HandlerMethodReturnValueHandler

ResponseEntity → HttpEntityMethodProcessor: статус 201, заголовок Location. Тело: content negotiation — пересечение Accept клиента и типов, которые могут записать конвертеры (и produces). Перед записью вызываются ResponseBodyAdvice. Jackson сериализует OrderDto прямо в выходной поток ответа.

Тело записано, значит ModelAndView не нужен (requestHandled=true) — view не рендерится.

afterCompletion → фильтры → Tomcat

postHandle и afterCompletion интерцепторов (последний — даже при исключении), очистка ThreadLocal, фильтры завершаются в обратном порядке (Observation фиксирует длительность и статус). Tomcat дописывает ответ; при keep-alive сокет возвращается в Poller, рабочий поток — в пул.

9.3Обработка исключений

Исключение из контроллера ловит doDispatch и передаёт в processHandlerException — по очереди в HandlerExceptionResolver-ы:

  1. ExceptionHandlerExceptionResolver: @ExceptionHandler в самом контроллере, затем в бинах @ControllerAdvice (по @Order); внутри одного класса выбирается обработчик с ближайшим типом исключения, а между несколькими advice побеждает первый по @Order, в котором нашёлся подходящий обработчик — даже если в менее приоритетном совпадение точнее.
  2. ResponseStatusExceptionResolver: ResponseStatusException и исключения с @ResponseStatus.
  3. DefaultHandlerExceptionResolver: стандартные исключения MVC → коды (HttpMediaTypeNotSupportedException → 415, MissingServletRequestParameterException → 400…).
  4. Никто не обработал → исключение уходит в контейнер → forward на /error → BasicErrorController Boot.
@RestControllerAdvice
class ApiErrors extends ResponseEntityExceptionHandler {     // уже обрабатывает стандартные исключения MVC в ProblemDetail

    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail notFound(OrderNotFoundException e) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
        pd.setType(URI.create("https://api.shop.ru/errors/order-not-found"));
        pd.setProperty("orderId", e.orderId());
        return pd;
    }

    @Override   // ошибки @Valid → 400 со списком полей
    protected ResponseEntity<Object> handleMethodArgumentNotValid(MethodArgumentNotValidException ex,
            HttpHeaders headers, HttpStatusCode status, WebRequest request) {
        ProblemDetail pd = ex.getBody();
        pd.setProperty("errors", ex.getFieldErrors().stream()
                .map(f -> Map.of("field", f.getField(), "message", f.getDefaultMessage())).toList());
        return ResponseEntity.badRequest().body(pd);
    }
}
В Boot достаточно spring.mvc.problemdetails.enabled=true, чтобы стандартные исключения MVC отдавались как application/problem+json. Свой @ControllerAdvice нужен для доменных исключений.

9.4Валидация

Тело запроса

@Valid @RequestBody — валидация объекта Bean Validation (Hibernate Validator). Ошибка → MethodArgumentNotValidException. Каскад во вложенные объекты — через @Valid на поле или элементе списка.

Параметры метода (6.1+)

Ограничения прямо на @PathVariable/@RequestParam (@Min(1) long id) MVC проверяет встроенной валидацией методов → HandlerMethodValidationException. Раньше требовался @Validated на классе и AOP-прокси.

@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
class CorrelationIdFilter extends OncePerRequestFilter {      // гарантирует один вызов на запрос (в т.ч. при forward/error)
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String id = Optional.ofNullable(req.getHeader("X-Request-Id")).orElseGet(() -> UUID.randomUUID().toString());
        MDC.put("requestId", id);                               // MDC — ThreadLocal: попадёт во все логи этого потока
        res.setHeader("X-Request-Id", id);
        try { chain.doFilter(req, res); }
        finally { MDC.remove("requestId"); }                    // поток вернётся в пул — чистим обязательно
    }
}

9.6Потоки и асинхронная обработка

Весь путь выполняется в одном рабочем потоке Tomcat, поэтому Spring хранит контекст в ThreadLocal: RequestContextHolder, SecurityContextHolder, LocaleContextHolder, транзакционные ресурсы, MDC. Если внутри запроса уйти в другой поток (свой пул, CompletableFuture), этот контекст не переедет сам.

Возврат Callable, DeferredResult, CompletableFuture, SseEmitter, ResponseBodyEmitter включает асинхронную обработку Servlet 3: рабочий поток Tomcat освобождается, ответ дописывается позже из другого потока. При 200 медленных запросах одновременно это спасает пул Tomcat, но с JDK 21 ту же задачу проще решают виртуальные потоки (тема 10).

9.7Самопроверка

Фильтр бросил исключение до DispatcherServlet. Обработает ли его @RestControllerAdvice?

  • Да, всегда
  • Да, если у него @Order(HIGHEST_PRECEDENCE)
  • Нет: резолверы исключений работают внутри DispatcherServlet; ошибка уйдёт в контейнер и на /error
  • Нет, приложение упадёт
@ControllerAdvice обслуживается ExceptionHandlerExceptionResolver внутри doDispatch. Для фильтров — обработка в самом фильтре или HandlerExceptionResolver, вызванный вручную.

Клиент отправил POST с Content-Type: text/plain, а метод объявлен с consumes = application/json. Ответ?

  • 400 Bad Request
  • 415 Unsupported Media Type
  • 406 Not Acceptable
  • 500
Условие consumes не совпало при выборе обработчика → HttpMediaTypeNotSupportedException → 415. 406 бывает, когда нельзя произвести тип из Accept.

Кто превращает JSON-тело в объект параметра @RequestBody?

  • RequestResponseBodyMethodProcessor с подходящим HttpMessageConverter (Jackson)
  • DispatcherServlet напрямую
  • Фильтр Jackson
  • HandlerInterceptor
Резолвер аргумента выбирает конвертер по Content-Type и целевому типу и вызывает его read().
Опишите путь HTTP-запроса в Spring MVC.

Tomcat (Acceptor → Poller → рабочий поток) → цепочка Servlet-фильтров (в т.ч. Spring Security) → DispatcherServlet.doDispatch: HandlerMapping находит HandlerMethod и интерцепторы → HandlerAdapter → preHandle → резолверы аргументов (конвертеры сообщений, валидация) → вызов метода → обработчики результата (content negotiation, конвертер пишет тело) → postHandle → обработка исключений резолверами → afterCompletion → фильтры в обратном порядке → ответ.

Когда регистрируются маршруты @RequestMapping?

На старте: RequestMappingHandlerMapping — бин с InitializingBean; в afterPropertiesSet он перебирает бины, помеченные @Controller (с Spring 6.0 одного @RequestMapping на классе недостаточно), собирает RequestMappingInfo для методов и регистрирует в MappingRegistry. Конфликтующие маршруты дают ошибку старта «Ambiguous mapping».

Чем Filter отличается от HandlerInterceptor?

Filter — компонент Servlet API, вызывается контейнером до DispatcherServlet, видит любой запрос, может обернуть request/response. Interceptor — механизм Spring MVC, вызывается внутри DispatcherServlet после выбора обработчика, знает HandlerMethod, имеет preHandle/postHandle/afterCompletion.

Как реализовать единый формат ошибок API?

@RestControllerAdvice, наследующий ResponseEntityExceptionHandler, с @ExceptionHandler для доменных исключений, возвращающими ProblemDetail (RFC 9457). Плюс обработка ошибок вне MVC (фильтры, Security) — через их собственные обработчики (AuthenticationEntryPoint, AccessDeniedHandler) в том же формате, и настройка /error.
