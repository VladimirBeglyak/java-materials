Архитектура приложения и Spring Modulith

Spring не навязывает структуру кода: в контекст можно сложить что угодно, и любой бин может внедрить любой другой. Именно поэтому большие Spring-приложения превращаются в клубок, где всё зависит от всего. Разберём, как раскладывать код по слоям и модулям, как держать границы средствами языка и как Spring Modulith проверяет их автоматически.

20.2Порты и адаптеры со Spring

Идея: бизнес-логика объявляет порты — интерфейсы того, что ей нужно снаружи. Инфраструктура предоставляет адаптеры — реализации. Зависимости направлены внутрь: домен не знает про JPA и Kafka. Spring связывает их через DI.

// --- com.shop.order (ядро модуля) ---
public interface PaymentPort {                                   // порт: что нужно сценарию
    PaymentResult charge(OrderId id, Money amount);
}

@Service
class PlaceOrderUseCase {                                        // package-private: снаружи модуля не виден
    private final OrderRepository orders;
    private final PaymentPort payments;
    private final ApplicationEventPublisher events;

    @Transactional
    public OrderId place(PlaceOrderCommand cmd) {
        Order order = Order.create(cmd.customer(), cmd.items());  // инварианты — в самой сущности
        orders.save(order);
        events.publishEvent(new OrderPlaced(order.id(), order.total()));
        return order.id();
    }
}

// --- com.shop.order.adapter.payment (адаптер) ---
@Component
class StripePaymentAdapter implements PaymentPort {              // знает про HTTP-клиент и формат Stripe
    private final RestClient stripe;
    public PaymentResult charge(OrderId id, Money amount) { /* ... */ }
}
Не доводите до догмы. Для CRUD-сервиса три слоя интерфейсов и мапперов — лишняя церемония. Признак, что порт оправдан: реализаций действительно несколько, внешняя система нестабильна или её нужно подменять в тестах.

20.3Модульный монолит и Spring Modulith

Модульный монолит — одно развёртываемое приложение с жёсткими внутренними границами. Он даёт большую часть пользы микросервисов (независимые модули, понятные зависимости) без сетевых вызовов, распределённых транзакций и зоопарка инфраструктуры. Spring Modulith формализует это соглашениями:

  • Модуль — прямой подпакет главного пакета приложения: com.shop.order, com.shop.inventory.
  • API модуля — типы в корневом пакете модуля. Всё в подпакетах (order.internal, order.web) — внутреннее, другим модулям обращаться к нему нельзя. Дополнительные публичные пакеты объявляются @NamedInterface.
  • Циклы между модулями запрещены.
  • Проверка — обычный тест на базе ArchUnit:
class ModularityTests {
    ApplicationModules modules = ApplicationModules.of(ShopApplication.class);

    @Test void verifiesModularStructure() { modules.verify(); }             // падает при циклах и доступе к internal

    @Test void writesDocumentation() { new Documenter(modules).writeDocumentation(); }   // C4/PlantUML-диаграммы модулей
}
Симулятор modules.verify()

Четыре модуля: order, inventory, payment, catalog. Включайте зависимости между ними и смотрите результат проверки.

События между модулями

// модуль payment
@Component
class PaymentOnOrder {
    @ApplicationModuleListener        // = @Async + @Transactional(REQUIRES_NEW) + @TransactionalEventListener(AFTER_COMMIT)
    void on(OrderPlaced event) { payments.charge(event.orderId(), event.total()); }
}

Проблема обычного AFTER_COMMIT-слушателя — потеря события при падении процесса (тема 05). Modulith добавляет Event Publication Registry: при публикации событие для каждого транзакционного слушателя записывается в таблицу event_publication в той же транзакции, что и бизнес-данные; после успешного завершения слушателя запись помечается выполненной. Незавершённые публикации можно повторить при рестарте (spring.modulith.events.republish-outstanding-events-on-restart) или по расписанию. Это встроенный outbox. Аннотация @Externalized("orders.placed::#{orderId()}") дополнительно отправляет событие в Kafka/RabbitMQ.

@ApplicationModuleTest                           // поднимает только модуль order (и при необходимости его зависимости)
class OrderModuleTests {
    @Autowired PlaceOrderFacade facade;

    @Test
    void publishesOrderPlaced(Scenario scenario) {
        scenario.stimulate(() -> facade.place(command()))
                .andWaitForEventOfType(OrderPlaced.class)
                .toArriveAndVerify(e -> assertThat(e.total()).isEqualTo(Money.rub(1500)));
    }
}

20.4Практики, которые окупаются

DTO на границах

API и события — отдельные record-ы, не JPA-сущности: иначе изменение схемы БД ломает контракт, а ленивые связи вызывают N+1 и LazyInitializationException при сериализации. Маппинг — MapStruct или вручную.

Транзакция = сценарий

@Transactional на методе сервиса-сценария, а не на классе «на всякий случай» и не на репозитории. Чтение — readOnly = true. Внешние вызовы — вне транзакции.

Конфигурация по модулям

У каждого модуля свой @ConfigurationProperties-record с префиксом (shop.payment.*) и при необходимости своя @Configuration. Никакого общего AppConfig на 500 строк.

Доменные исключения

Свои unchecked-исключения домена (OrderNotFound, InsufficientStock), маппинг в HTTP — в одном @RestControllerAdvice. Сервисы не возвращают ResponseEntity.

20.6Самопроверка

Что Spring Modulith считает внутренней частью модуля com.shop.order?

  • Классы с аннотацией @Internal
  • Все package-private классы
  • Всё, что лежит в подпакетах модуля (order.internal, order.web…), если пакет не объявлен @NamedInterface
  • Классы без @Component
API модуля — типы корневого пакета модуля. Подпакеты закрыты для других модулей по соглашению, и verify() это проверяет.

Модуль order вызывает inventory, а inventory должен отменить заказ при нехватке товара. Как избежать цикла?

  • Сделать оба класса @Lazy
  • inventory публикует событие StockShortage, order на него подписывается
  • Включить allow-circular-references
  • Объединить модули в один пакет common
Событие разворачивает зависимость: inventory ничего не знает об order, а order уже зависит от API inventory (в том числе от типа события).

Чем Event Publication Registry лучше простого @TransactionalEventListener(AFTER_COMMIT)?

  • Публикация сохраняется в БД в той же транзакции и может быть повторена, если слушатель не завершился
  • Работает быстрее
  • Не требует транзакции
  • Гарантирует порядок событий
Это outbox для внутренних событий: падение между коммитом и обработкой больше не теряет событие.
Пакеты по слоям или по функциям — что выбрать и почему?

По функциям: связанный код рядом, высокая связность внутри и низкая между пакетами, можно использовать package-private как границу модуля, проще выделить сервис позже. По слоям допустимо для небольших сервисов; на росте приводит к тому, что всё публично и всё зависит от всего.

Когда модульный монолит лучше микросервисов?

Одна команда или несколько тесно связанных, домен ещё меняется, нет требований к независимому масштабированию и релизам частей. Монолит даёт транзакции, простые вызовы и одну инфраструктуру; модульность сохраняет возможность выделить сервис, когда появится реальная причина (нагрузка, команда, технология).

Как обеспечить, чтобы границы модулей не размывались со временем?

Автоматические проверки в сборке: Spring Modulith verify() или правила ArchUnit (запрет зависимостей между пакетами, циклов, обращений к internal), package-private по умолчанию, ревью публичного API модуля, события вместо обратных вызовов.
