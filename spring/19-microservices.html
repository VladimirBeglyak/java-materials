Микросервисы: Spring Cloud и устойчивость

Когда сервисов становится много, появляются задачи, которых не было в монолите: где лежит конфигурация, как найти адрес другого сервиса, что делать, когда он не отвечает, как не уронить всё каскадом. Spring Cloud — набор библиотек, решающих эти задачи в стиле Spring Boot. Разберём, как они устроены и какие из них заменяет Kubernetes.

19.2Config Server и обновление без перезапуска

spring:
  application:
    name: order-service
  config:
    import: "optional:configserver:http://config:8888"     # подключается как ещё один источник ConfigData

Config Server отдаёт свойства из git-репозитория по имени приложения и профилю. Источник встраивается в Environment с высоким приоритетом. Как изменить настройку без рестарта:

  1. POST /actuator/refresh (или событие по Spring Cloud Bus всем экземплярам) → ContextRefresher перечитывает источники и вычисляет изменившиеся ключи.
  2. Публикуется EnvironmentChangeEvent → бины @ConfigurationProperties перепривязываются (ConfigurationPropertiesRebinder).
  3. Бины в @RefreshScope — это scoped proxy (тема 03): кэш scope очищается, и при следующем вызове бин создаётся заново с новыми значениями.
Объекты с привязкой через конструктор, включая record с @ConfigurationProperties, при refresh не обновляются, и @RefreshScope им не поможет: record — final-класс, CGLIB-прокси для него не создать. Для обновляемых настроек используйте изменяемый JavaBean-класс с сеттерами или читайте значения через Environment. В Kubernetes чаще выбирают простой путь: изменили ConfigMap → rolling restart.

19.4Устойчивость к отказам

ПаттернОт чего защищаетПравило
Timeoutзависший вызов держит поток и соединениена каждом вызове; меньше, чем таймаут вашего клиента
Retryкратковременные сбоитолько идемпотентные операции; экспоненциальная пауза + джиттер; ограниченное число
Circuit Breakerбесполезные вызовы упавшего сервиса, каскадбыстрый отказ + fallback, пока сервис не восстановится
Bulkheadодин медленный downstream съедает все потокилимит одновременных вызовов на зависимость
Rate Limiterпревышение квоты чужого API, перегрузкаN вызовов в интервал
@Service
class InventoryGateway {
    @Retry(name = "inventory", fallbackMethod = "stockFallback")   // внешний слой; fallback — здесь, после исчерпания повторов
    @CircuitBreaker(name = "inventory")                            // fallback на breaker «съел» бы ошибку до Retry
    @Bulkhead(name = "inventory")
    Stock stock(String sku) { return client.get().uri("/stock/{sku}", sku).retrieve().body(Stock.class); }

    Stock stockFallback(String sku, Throwable t) { return Stock.unknown(sku); }   // деградация вместо ошибки
}

        sliding-window-size: 10

        wait-duration-in-open-state: 10s
        permitted-number-of-calls-in-half-open-state: 3

        slow-call-rate-threshold: 50            # доля медленных ≥ 50% тоже открывает breaker (по умолчанию 100%)
  retry:
    instances:
      inventory:
        max-attempts: 3
        wait-duration: 200ms
        enable-exponential-backoff: true
        enable-randomized-wait: true
        ignore-exceptions:
          - io.github.resilience4j.circuitbreaker.CallNotPermittedException   # не повторять то, что breaker уже отклонил

Порядок аспектов Resilience4j фиксирован: Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( вызов ) ) ) ) ). Поэтому fallback ставят на самый внешний аспект: fallback на @CircuitBreaker вернёт значение раньше, чем Retry увидит исключение, и повторов не будет. В Spring Framework 7 простые повторы и ограничение параллельности есть и в ядре: @Retryable, @ConcurrencyLimit (@EnableResilientMethods).

Попробуйте: «5 сбоев подряд» → OPEN; ещё несколько вызовов — они отклоняются, не нагружая упавший сервис; «прошло 10 секунд» → три успешных вызова → CLOSED.

Ретраи усиливают аварию Три уровня сервисов, каждый делает по 3 попытки: один запрос пользователя превращается в 27 запросов к нижнему сервису именно тогда, когда ему плохо (retry storm). Ретраи — на одном уровне, с бюджетом и джиттером, а circuit breaker их вовремя отключает.

Шлюз — единая точка входа: маршрутизация, аутентификация, лимиты, CORS, агрегирование. Классический Gateway работает на WebFlux/Netty (неблокирующий — хорошо для прокси с тысячами соединений); есть вариант для Spring MVC. Не кладите в шлюз бизнес-логику.

19.6Согласованность данных между сервисами

Распределённой транзакции между сервисами нет (2PC/XA плохо масштабируется и не поддерживается брокерами). Применяют Saga: цепочку локальных транзакций, где каждая публикует событие, а при сбое выполняются компенсации.

Хореография

Сервисы реагируют на события друг друга: OrderPlaced → Payment списывает → PaymentCompleted → Inventory резервирует. Нет центра, но логика процесса размазана и трудно отслеживается.

Оркестрация

Оркестратор (свой сервис, Temporal, Camunda) явно ведёт процесс: команды сервисам, ожидание ответов, компенсации. Процесс виден в одном месте, но появляется центральный компонент.

Обязательные спутники саги: outbox для надёжной публикации (тема 18), идемпотентные обработчики, ключи идемпотентности в API (Idempotency-Key), таймауты шагов.

19.7Самопроверка

Что делает Circuit Breaker в состоянии OPEN?

  • Ставит вызовы в очередь
  • Сразу отклоняет вызовы (fallback), не обращаясь к downstream, до истечения времени ожидания
  • Повторяет вызовы с паузой
  • Переключает на резервный экземпляр
Цель — не тратить потоки и время на заведомо неуспешные вызовы и дать сервису восстановиться.

Как @RefreshScope-бин получает новые значения конфигурации без рестарта?

  • Spring меняет поля через рефлексию
  • Пересоздаётся весь контекст
  • Бин — scoped proxy; при refresh кэш scope очищается, и при следующем вызове создаётся новый экземпляр
  • Никак, нужен рестарт
RefreshScope — пользовательский scope с кэшем экземпляров, который сбрасывается событием обновления.

Какие операции можно безопасно ретраить?

  • Идемпотентные: GET, PUT с полным состоянием, операции с ключом идемпотентности
  • Любые POST
  • Все, если есть circuit breaker
  • Только внутри транзакции
Повтор неидемпотентной операции (списание денег) может выполнить её дважды, если первый ответ потерялся.
Какие компоненты Spring Cloud заменяет Kubernetes, а какие нет?

Заменяет: обнаружение сервисов и балансировку (Service/DNS), частично конфигурацию (ConfigMap/Secret), вход (Ingress/Gateway API). Не заменяет: устойчивость на уровне приложения (fallback, bulkhead, семантические ретраи), декларативные клиенты, Stream, контрактное тестирование; шлюз с прикладной логикой аутентификации и лимитов часто остаётся.

Объясните состояния Circuit Breaker.

CLOSED — вызовы идут, результаты пишутся в скользящее окно; доля ошибок/медленных выше порога → OPEN. OPEN — вызовы отклоняются немедленно; после wait-duration первый же вызов переводит breaker в HALF_OPEN (сам по себе, без вызовов, — только при automatic-transition-from-open-to-half-open-enabled=true). HALF_OPEN — пропускается ограниченное число пробных вызовов; успешны → CLOSED, иначе снова OPEN.

Как обеспечить согласованность данных между двумя сервисами?

Saga из локальных транзакций с компенсациями (хореография или оркестрация), надёжная публикация событий через outbox, идемпотентные потребители, ключи идемпотентности. Согласованность — итоговая (eventual), промежуточные состояния надо уметь показывать пользователю (например, «заказ обрабатывается»).
