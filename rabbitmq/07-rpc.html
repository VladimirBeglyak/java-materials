RPC поверх RabbitMQ

RabbitMQ — асинхронный брокер, но поверх него можно построить синхронный «запрос–ответ» (RPC): клиент публикует запрос и ждёт ответ в своей очереди. Паттерн решает задачу, когда нужно получить ответ от другого сервиса через очередь, но требует аккуратности с correlationId и таймаутами.

~2 часаRPCreply-tocorrelationIdтаймаутытест

7.1Паттерн запрос–ответ

Клиент создаёт временную очередь ответов, кладёт в запрос её имя (reply_to) и уникальный correlation_id. Сервер обрабатывает запрос и публикует ответ в reply_to с тем же correlation_id. Клиент читает свою очередь и сопоставляет ответ по id.

Клиентreply_to=rpc.resp.1, correlation_id=42запрос → rpc.queue→ Серверобрабатываетответ → rpc.resp.1correlation_id=42← Клиентсовпал id → готово

7.2correlationId и reply-to

Без correlation_id клиент не отличит ответы разных запросов в общей очереди; без reply_to сервер не узнает, куда отвечать.

String replyQueue = channel.queueDeclare().getQueue();      // временная очередь
String corrId = UUID.randomUUID().toString();

AMQP.BasicProperties props = new AMQP.BasicProperties.Builder()
        .correlationId(corrId)
        .replyTo(replyQueue)
        .build();
channel.basicPublish("", "rpc.queue", props, requestBody);

// читаем replyQueue, пока не встретим correlationId == corrId
Одна очередь на запрос или общая Проще — временная очередь на каждый запрос (reply_to уникален). Можно и общую очередь ответов, но тогда correlationId обязателен для разбора, и очередь нужно чистить от «чужих»/просроченных ответов.

7.3Таймауты и ловушки

ЛовушкаРешение
Ответ потерян — клиент ждёт вечнотаймаут ожидания, обработать как ошибку
Сервер упал после обработки, до отправки ответаидемпотентность запроса, повтор с тем же correlationId
«Чужие» ответы в общей очередиуникальный correlationId и фильтр
RPC вместо событий там, где ответ не нуженне строить RPC ради RPC: если ответ не нужен — обычная очередь
RPC — не замена HTTP без причины Синхронный вызов через очередь добавляет задержку и сложность. RPC уместен, когда общение уже идёт через брокер и нужен ответ «здесь и сейчас» (например, запрос расчёта цены).

7.4Самопроверка

Зачем нужен correlationId в RPC?

  • Сопоставить ответ с конкретным запросом среди многих
  • Зашифровать сообщение
  • Ускорить доставку
  • Задать приоритет
В очереди ответов может быть несколько сообщений; correlationId связывает ответ с запросом.

Что указывает reply_to в запросе?

  • Очередь, куда сервер должен отправить ответ
  • Адрес продюсера
  • Exchange для маршрутизации
  • Имя потребителя
reply_to — имя очереди ответов клиента; сервер публикует ответ туда.

Что делать, если ответ RPC не пришёл за таймаут?

  • Ждать бесконечно
  • Удалить очередь
  • Завершить запрос ошибкой; при повторе — идемпотентность запроса
  • Игнорировать
Таймаут обязателен; повтор безопасен только при идемпотентном сервере.

Когда RPC поверх RabbitMQ уместен?

  • Всегда вместо HTTP
  • Когда общение уже идёт через брокер и нужен синхронный ответ
  • Только для fanout
  • Никогда
RPC добавляет задержку и сложность; его используют, когда нужен ответ и инфраструктура брокера уже есть.
Опишите полный цикл RPC-вызова.

Клиент объявляет очередь ответов, публикует запрос с reply_to и correlationId. Сервер читает запрос, обрабатывает и публикует ответ в reply_to с тем же correlationId. Клиент читает свою очередь, находит ответ по correlationId и возвращает результат вызывающему.

Временная очередь на запрос или общая очередь ответов — что выбрать?

Временная очередь проще: reply_to уникален, чужих ответов нет, очередь удаляется сама. Общая экономит очереди, но требует строгой фильтрации по correlationId и чистки просроченных ответов.
