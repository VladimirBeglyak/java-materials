Exchanges и маршрутизация

Exchange — это маршрутизатор: он принимает сообщение и решает, в какие очереди его положить. Правило зависит от типа exchange и binding — связок между exchange и очередью. Четыре типа покрывают почти все сценарии маршрутизации.

2.1Четыре типа exchange

ТипМаршрутизацияТиповой сценарий
directпо точному совпадению routing keyточечная доставка одному обработчику
fanoutво все привязанные очереди, ключ игнорируетсяшироковещательная рассылка
topicпо шаблону routing key (точки, *, #)гибкая маршрутизация по категориям
headersпо заголовкам сообщениямаршрутизация по атрибутам, не по ключу

2.2Direct

Сообщение попадает в очередь, чей binding key точно равен routing key сообщения. Один ключ может вести в несколько очередей (тогда это и fan-out).

exchange: logs_direct (type=direct)
  очередь errors ← binding key "error"
  очередь all    ← binding key "info", "error"

publish("error")  → errors, all
publish("info")   → all
publish("debug")  → никуда (нет binding)

2.3Fanout

Кладёт сообщение во все привязанные очереди, игнорируя routing key. Классика — «одно событие, много независимых потребителей» (рассылка всем).

exchange: news (type=fanout)
  очередь notify ← привязана
  очередь audit  ← привязана
  очередь search ← привязана

publish(любой ключ) → notify, audit, search  (все три)

2.4Topic

Routing key — слова, разделённые точками (например, orders.eu.paid). В binding key можно использовать * (ровно одно слово) и # (ноль или более слов).

exchange: events (type=topic)
  очередь eu_orders ← binding "orders.eu.#"
  очередь paid      ← binding "orders.*.paid"

publish("orders.eu.paid")   → eu_orders, paid
publish("orders.us.paid")   → paid
publish("orders.eu.created")→ eu_orders
publish("users.eu.created") → никуда
Topic покрывает direct и fanout Binding # ловит всё (как fanout), а точный ключ без звёздочек — как direct. Topic — самый гибкий тип.

2.5Headers

Маршрутизация по заголовкам сообщения, а не по routing key. Binding задаёт, какие заголовки и с каким правилом (x-match: all — все должны совпасть, any — хотя бы один).

exchange: format (type=headers)
  очередь pdf  ← x-match=all, format=pdf
  очередь big  ← x-match=all, format=pdf, size=large

publish(headers={format: pdf})          → pdf
publish(headers={format: pdf, size: large}) → pdf, big
Headers редок Обычно достаточно topic. Headers используют, когда маршрутизация зависит от многих атрибутов, а не от одного ключа.

2.7Самопроверка

Какой exchange доставляет во все привязанные очереди?

  • direct
  • fanout
  • topic
  • headers
Fanout игнорирует routing key и кладёт сообщение во все очереди.

Что означает # в binding key topic-exchange?

  • Ноль или более слов (любая последовательность)
  • Ровно одно слово
  • Только цифры
  • Конец строки
# — ноль или более слов, * — ровно одно слово.

Что произойдёт, если сообщение не совпало ни с одним binding?

  • Оно вернётся продюсеру всегда
  • Оно сохранится навсегда
  • Оно будет отброшено (если не включён mandatory/alternate exchange)
  • Ошибка протокола
По умолчанию несовпавшее сообщение молча теряется; mandatory/alternate exchange позволяют это перехватить.

Когда выбирают headers-exchange?

  • Когда маршрутизация зависит от многих атрибутов-заголовков, а не одного ключа
  • Всегда вместо topic
  • Только для fan-out
  • Когда нет заголовков
Headers маршрутизирует по заголовкам с x-match all/any; обычно проще обойтись topic.
Чем topic отличается от direct и fanout?

Topic маршрутизирует по шаблону из слов с * и #, покрывая и точное совпадение (как direct), и широкую рассылку (как fanout через #). Это самый гибкий тип.

Как избежать тихой потери несовпавшего сообщения?

Включить mandatory-флаг (брокер вернёт сообщение продюсеру, если оно никуда не попало) или настроить alternate exchange — запасной exchange для несовпавших сообщений.
