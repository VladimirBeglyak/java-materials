Сеть в Linux: очереди, сокеты, контейнеры

Между сетевой картой и вызовом read() в вашем приложении — ядро Linux (главная часть операционной системы, управляющая железом) с десятком очередей и таблиц. У каждой есть предельный размер, и когда он исчерпан, пакеты молча выбрасываются. Большинство «необъяснимых» сетевых проблем бэкенда — переполнение одной из них. Разберём путь пакета через ядро, очереди слушающего сокета, порты, дескрипторы и то, как из тех же деталей собрана сеть контейнера.

16.1Путь входящего пакета через ядро

Пакет пришёл на сетевую карту. Что с ним происходит, прежде чем приложение его прочитает? По шагам, сверху вниз:

Что значат слова на схеме:

NIC, RX ring
NIC — Network Interface Card, «сетевая карта». RX (receive, «приём») ring — кольцевой буфер: область памяти, куда карта складывает пришедшие кадры по кругу. Не успевают забрать — новые кадры теряются
Прерывание, softirq, NAPI
прерывание — сигнал от железа процессору «у меня новые данные». Чтобы не дёргать процессор на каждый пакет, Linux обрабатывает их пачками в отложенной задаче ядра (softirq, «программное прерывание») по механизму NAPI (New API, «новый интерфейс» драйверов)
sk_buff
socket buffer — «буфер сокета», структура ядра, в которой пакет живёт, пока идёт по стеку
netfilter
набор точек перехвата пакетов в ядре, на которых работают файрвол и NAT (раздел 16.6)
Четвёрка
адрес и порт отправителя + адрес и порт получателя — по ним ядро находит нужное соединение

Исходящий путь зеркальный. write() лишь копирует данные в буфер отправки ядра и сразу возвращается; дальше ядро само режет данные на сегменты, ждёт окна, повторяет потерянное. Поэтому успешный write() не значит, что данные доставлены, и даже что они покинули машину.

Главное Пакет идёт: сетевая карта → кольцевой буфер → ядро → netfilter (conntrack, NAT, файрвол) → TCP → буфер сокета → read(). На каждом шаге есть очередь с пределом.

16.2Две очереди слушающего сокета

Когда сервер вызывает listen(fd, backlog) («слушать», fd — номер сокета), ядро заводит для него две очереди (их мы видели в главе 06). Важно понять: рукопожатие выполняет ядро, без участия приложения. Приложение вызовом accept() забирает уже готовые соединения.

  • Очередь SYN — полуоткрытые соединения: SYN пришёл, SYN-ACK отправлен, ждём ACK.
  • Accept-очередь — соединения, где рукопожатие завершено, ждут, пока приложение их заберёт.

Аналогия: гардероб. Ядро принимает пальто (делает рукопожатие) и вешает номерки на стойку (accept-очередь), а приложение — гардеробщик, который уносит пальто в зал. Если гардеробщик медлит, стойка заполняется, и новых посетителей не принимают.

Симулятор: очередь SYN и accept-очередь

Для наглядности accept-очередь вмещает 3 соединения, очередь SYN — 4.

Как это выглядит на продакшене Сервис под нагрузкой: все потоки заняты, accept() вызывается редко, accept-очередь переполняется. Клиенты видят таймауты подключения и редкие RST, хотя сервис «жив» и процессор не загружен. Проверка: nstat -az TcpExtListenOverflows TcpExtListenDrops («переполнения» и «сбросы» слушающих сокетов) — если счётчики растут, это оно. А ss -ltn покажет у слушающих сокетов столбцы Recv-Q (сколько сейчас в accept-очереди) и Send-Q (её предел).
Главное Рукопожатие делает ядро, приложение лишь забирает готовые соединения. Если не успевает — accept-очередь переполняется, и клиенты получают таймауты. Смотрите счётчик ListenOverflows.

16.3Буферы сокета и обратное давление

Медленный получатель

Приложение не успевает читать → буфер приёма заполняется → TCP объявляет окно 0 → на другой стороне заполняется буфер отправки → write() отправителя блокируется (в неблокирующем режиме — записывает 0 байт). Обратное давление (backpressure) TCP работает само собой (глава 06) — если только приложение не обходит его, складывая всё в собственную неограниченную очередь в памяти. Тогда вместо замедления будет нехватка памяти.

Размеры буферов

Ядро само подстраивает буферы (autotuning) в пределах net.ipv4.tcp_rmem / tcp_wmem — три числа: минимум, начальный размер, максимум (r — read, приём; w — write, отправка). Явная установка SO_RCVBUF (socket option receive buffer) отключает автоподстройку — делайте это, только понимая зачем. Для быстрых дальних каналов максимум должен быть не меньше BDP (глава 07).

Главное Медленный получатель через окно TCP сам тормозит отправителя. Не ломайте это неограниченными очередями в приложении и не трогайте размеры буферов без замеров.

16.4Порты и дескрипторы — конечные ресурсы

Каждое исходящее соединение занимает эфемерный порт (в Linux по умолчанию диапазон 32768–60999, около 28 000 портов), и после закрытия порт ещё 60 секунд держит TIME_WAIT (глава 06). Калькулятор показывает, сколько новых соединений в секунду можно открывать:

Важная деталь: ограничение действует на четвёрку (адрес и порт источника, адрес и порт назначения). К разным серверам один и тот же локальный порт можно использовать одновременно. Поэтому порты кончаются именно при множестве соединений к одному адресу — к базе данных, к прокси, к NAT-шлюзу.

Too many open files Каждый сокет — это файловый дескриптор (номер, которым ОС учитывает открытые процессом файлы и сокеты). У процесса есть лимит: посмотреть — ulimit -n, часто по умолчанию всего 1024; для служб, запущенных через systemd (менеджер служб Linux), он задаётся параметром LimitNOFILE. Лимит кончается при утечке соединений или просто при большом числе клиентов. Симптом: accept() падает с ошибкой EMFILE («слишком много файлов у процесса»), сервис перестаёт принимать соединения, а заодно не может открыть ни файл лога, ни соединение с базой. Проверка: ls /proc/<pid>/fd | wc -l — сколько открыто сейчас (/proc — виртуальная папка, через которую ядро показывает сведения о процессах; pid — номер процесса), cat /proc/<pid>/limits — какие лимиты.
Главное Эфемерные порты кончаются при множестве коротких соединений к одному адресу. Дескрипторы кончаются при утечках или больших нагрузках. Оба ресурса конечны и требуют присмотра.

16.5epoll: как один поток обслуживает тысячи сокетов

epoll («event poll» — «опрос событий») — механизм ядра Linux, на котором построены event loop'ы (глава 12): Netty, NIO-коннектор Tomcat, веб-сервер nginx, хранилище Redis. Программа регистрирует сокеты в epoll и потом спрашивает: «какие из них готовы?». Вот его цикл в упрощённом виде (это псевдокод, а не настоящий язык):

epfd = epoll_create1(0)                                   # создать объект epoll
epoll_ctl(epfd, EPOLL_CTL_ADD, listen_fd, EPOLLIN)        # «сообщи, когда появятся новые соединения»
loop:
    n = epoll_wait(epfd, events, MAX, timeout)            # спим, пока ни один сокет не готов
    for ev in events[0..n]:
        if ev.fd == listen_fd:
            conn = accept(listen_fd)                      # не блокируется: соединение уже в очереди
            epoll_ctl(epfd, EPOLL_CTL_ADD, conn, EPOLLIN) # следить и за ним
        else:
            data = read(ev.fd)                            # не блокируется: данные уже в буфере приёма
            handle(data)                                  # обработчик не должен блокировать поток!

Ядро само ведёт список готовых сокетов и возвращает только их, поэтому стоимость не зависит от общего числа соединений. Старые механизмы select и poll каждый раз перебирали все сокеты — при 10 000 соединений это медленно. В Java epoll скрыт за классом Selector из NIO. Виртуальные потоки используют тот же механизм незаметно: «блокирующий» read() на самом деле регистрирует сокет в epoll и снимает виртуальный поток с платформенного, пока данных нет.

Главное epoll сообщает, какие сокеты готовы, и один поток обслуживает тысячи соединений. На нём держатся Netty, nginx, Redis и виртуальные потоки Java.

16.6netfilter и conntrack

netfilter — точки перехвата пакетов в ядре: PREROUTING («до маршрутизации», сразу после приёма), INPUT («вход», для пакетов этому компьютеру), FORWARD («пересылка» транзитных пакетов), OUTPUT («выход», пакеты от этого компьютера), POSTROUTING («после маршрутизации», перед отправкой). На них вешают правила утилитами iptables или её преемницей nftables: фильтрация, NAT, пометки.

conntrack (connection tracking, «отслеживание соединений») — таблица всех соединений, проходящих через компьютер. Без неё невозможны NAT (надо помнить, куда вернуть ответ) и правила вида «разрешить ответы на исходящие».

Таблица conntrack конечна

Сообщение в журнале ядра (команда dmesg): nf_conntrack: table full, dropping packet («таблица полна, пакет выброшен»). Новые соединения через этот компьютер отбрасываются — часто это узел Kubernetes или NAT-шлюз, — хотя сами сервисы исправны. Проверка: conntrack -S, sysctl net.netfilter.nf_conntrack_count net.netfilter.nf_conntrack_max (сколько записей сейчас и сколько максимум).

Гонка DNAT в Kubernetes

Программа одновременно шлёт с одного сокета два UDP-запроса к DNS (A и AAAA). При вставке в conntrack они могут столкнуться, и один пакет теряется — запрос к DNS висит 5 секунд до повтора. Это известная причина «случайных пятисекундных задержек» в кластерах. Лечится кэшем NodeLocal DNSCache или опцией резолвера single-request-reopen (слать A и AAAA с разных сокетов).

Главное netfilter — точки, где ядро фильтрует и подменяет пакеты; conntrack — таблица соединений для NAT и файрвола. Таблица конечна, и её переполнение молча роняет новые соединения.

16.7Сеть контейнера — из тех же деталей

Docker и Kubernetes не изобретают свою сеть — они собирают её из стандартных возможностей ядра Linux:

  • Network namespace («сетевое пространство имён») — отдельный экземпляр всего сетевого стека: свои интерфейсы, таблица маршрутов, правила netfilter, порты, свой loopback lo. Поэтому два контейнера могут одновременно слушать порт 8080.
  • veth-пара (virtual Ethernet, «виртуальный Ethernet») — виртуальный кабель с двумя концами: один в контейнере (там он называется eth0), другой на хосте, воткнут в мост.
  • Мост (bridge) docker0 — виртуальный коммутатор внутри хоста, соединяющий все контейнеры.
  • Исходящий трафик — SNAT (Source NAT, подмена адреса источника), в iptables это правило MASQUERADE («маскарад»): адрес контейнера заменяется адресом хоста, как дома у роутера (глава 04).
  • Публикация порта docker run -p 8080:80 — правило DNAT в PREROUTING: пакеты на порт 8080 хоста переписываются на 172.17.0.2:80.
  • Под Kubernetes — несколько контейнеров в одном network namespace: у них общий IP, и друг до друга они достают через localhost. Связь подов на разных узлах обеспечивает CNI-плагин (overlay или маршрутизация), а Service — правила DNAT на каждом узле (глава 13).
ip netns list;  lsns -t net                     # список сетевых пространств имён
nsenter -t <pid контейнера> -n ip addr          # выполнить команду в сети контейнера, даже если в образе нет утилит
ip link show type veth;  bridge link            # veth-пары и порты моста
iptables -t nat -L -n -v | head -40             # правила DNAT и MASQUERADE от Docker и kube-proxy

nsenter («войти в namespace») с ключом -n запускает команду внутри сетевого пространства процесса — удобно, когда в образе контейнера нет никаких сетевых утилит.

Главное Контейнер — отдельный сетевой стек (namespace), соединённый с хостом виртуальным кабелем (veth) через виртуальный коммутатор (мост). Наружу — через SNAT, внутрь по опубликованному порту — через DNAT.

16.10Самопроверка

Кто выполняет TCP-рукопожатие для входящего соединения?

  • Приложение в вызове accept()
  • Сетевая карта
  • Ядро; приложение получает из accept-очереди уже установленное соединение
  • Балансировщик
Поэтому клиент может «подключиться» к зависшему приложению: рукопожатие пройдёт, а ответа не будет.

Сервис падает с «Cannot assign requested address» при вызовах к одному внешнему API.

  • Закончилась память
  • Исчерпаны эфемерные порты: слишком много коротких соединений к одному адресу, порты висят в TIME_WAIT
  • Неверный DNS
  • Закрыт порт на файрволе
Нужен пул соединений с keep-alive.

Почему два контейнера на одном хосте могут одновременно слушать порт 80?

  • У каждого свой network namespace — отдельный сетевой стек со своими портами
  • Docker меняет номер порта в приложении
  • Порт 80 особый
  • Не могут
Конфликт возникает только при публикации на один и тот же порт хоста.

В dmesg: «nf_conntrack: table full, dropping packet». Что происходит?

  • Переполнен диск
  • Сетевая карта неисправна
  • Закончились дескрипторы
  • Таблица отслеживания соединений заполнена: новые соединения через этот узел выбрасываются
Увеличить nf_conntrack_max, сократить таймауты, уменьшить число коротких соединений.

write() вернул успех. Что это гарантирует?

  • Данные доставлены получателю
  • Только то, что данные скопированы в буфер отправки ядра
  • Получатель прочитал данные
  • Данные покинули сетевую карту
Дальше ядро отправляет сегменты само. О доставке говорит только ответ прикладного протокола.

Почему epoll эффективнее select при 10 000 соединений?

  • Он шифрует данные
  • Он использует UDP
  • Ядро само ведёт список готовых сокетов и возвращает только их, не перебирая все
  • Он открывает меньше соединений
Стоимость epoll зависит от числа готовых, а не всех сокетов.

Вопросы для разговора (с собеседований)

Что происходит с пакетом от сетевой карты до read() в приложении?

Карта → кольцевой буфер → softirq/NAPI → sk_buff → netfilter PREROUTING (conntrack, DNAT) → решение о маршруте → INPUT → TCP: поиск сокета, проверка, ACK → буфер приёма → пробуждение через epoll → read() копирует данные в процесс. На каждом этапе — очередь с пределом.

Чем отличаются очередь SYN и accept-очередь и что бывает при переполнении?

В первой — соединения, получившие SYN-ACK и ждущие ACK; при переполнении SYN выбрасывается или включаются SYN cookies. Во второй — установленные соединения, ждущие accept(); при переполнении последний ACK клиента игнорируется, клиент видит задержки и таймауты. Размер второй задают backlog и somaxconn.

Как устроена сеть Docker-контейнера?

Отдельный network namespace; veth-пара соединяет его с мостом docker0 на хосте; исходящий трафик маскируется (SNAT) адресом хоста; публикация порта — правило DNAT. Под Kubernetes — общий namespace для контейнеров пода плюс CNI для связи между узлами.
