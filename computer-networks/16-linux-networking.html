Сеть в Linux: очереди, сокеты, контейнеры

Между сетевой картой и вызовом read() в вашем приложении — ядро Linux с десятком очередей и таблиц. У каждой есть размер, и когда он исчерпан, пакеты молча отбрасываются. Большинство «необъяснимых» сетевых проблем бэкенда — это переполнение одной из них. Разберём путь пакета через ядро, очереди слушающего сокета, порты, дескрипторы и то, как из тех же кирпичей собрана сеть контейнера.

Исходящий путь зеркален: write() копирует данные в буфер отправки и возвращается сразу; ядро само нарезает сегменты, ждёт окна, повторяет потери. Успешный write() не означает, что данные доставлены и даже что они покинули машину.

16.2Две очереди слушающего сокета

Когда приложение вызывает listen(fd, backlog), ядро заводит две очереди. Рукопожатие выполняет ядро, без участия приложения; приложение забирает уже готовые соединения вызовом accept().

Симулятор: очередь SYN и accept-очередь

Для наглядности accept-очередь вмещает 3 соединения, очередь SYN — 4.

16.3Буферы сокета и обратное давление

Медленный получатель

Приложение не успевает читать → буфер приёма заполняется → TCP объявляет окно 0 → буфер отправки на другой стороне тоже заполняется → write() отправителя блокируется (или возвращает 0 в неблокирующем режиме). Обратное давление TCP работает само — если приложение его не обходит неограниченной внутренней очередью.

Размеры

Ядро автоматически подстраивает буферы в пределах net.ipv4.tcp_rmem / tcp_wmem (минимум, начальный, максимум). Явный SO_RCVBUF отключает автонастройку — задавайте его, только понимая зачем. Для быстрых длинных каналов максимум должен быть не меньше BDP (тема 07).

16.4Порты и дескрипторы — конечные ресурсы

Калькулятор: сколько исходящих соединений возможно

Ограничение действует на четвёрку (адрес источника, порт источника, адрес назначения, порт назначения): к разным серверам один и тот же локальный порт использовать можно. Поэтому порты заканчиваются именно при множестве соединений к одному адресу — к базе, к прокси, к NAT-шлюзу.

Too many open files Каждый сокет — файловый дескриптор. Лимит процесса (ulimit -n, часто 1024 по умолчанию; в systemd — LimitNOFILE) исчерпывается при утечке соединений или просто при большом числе клиентов. Симптом: accept() падает с EMFILE, сервис перестаёт принимать соединения, а заодно не может открыть ни файл лога, ни соединение с БД. Проверка: ls /proc/<pid>/fd | wc -l, cat /proc/<pid>/limits.

16.5epoll: как один поток обслуживает тысячи сокетов

epfd = epoll_create1(0)
epoll_ctl(epfd, EPOLL_CTL_ADD, listen_fd, EPOLLIN)        # «сообщи, когда появятся новые соединения»

loop:
    n = epoll_wait(epfd, events, MAX, timeout)            # спим, пока ни один сокет не готов
    for ev in events[0..n]:
        if ev.fd == listen_fd:
            conn = accept(listen_fd)                      # не блокируется: соединение уже в очереди
            epoll_ctl(epfd, EPOLL_CTL_ADD, conn, EPOLLIN)
        else:
            data = read(ev.fd)                            # не блокируется: данные уже в буфере приёма
            handle(data)                                  # обработчик не должен блокировать поток!

Ядро ведёт список готовых сокетов и возвращает только их — стоимость не зависит от общего числа соединений (в отличие от старых select/poll, перебиравших все). В Java это Selector из NIO; виртуальные потоки используют тот же механизм скрытно: «блокирующий» read() регистрирует сокет в поллере и размонтирует поток.

16.6netfilter и conntrack

netfilter — точки перехвата в ядре (PREROUTING, INPUT, FORWARD, OUTPUT, POSTROUTING), на которые вешаются правила iptables/nftables: фильтрация, NAT, маркировка. conntrack — таблица отслеживаемых соединений: без неё невозможны NAT и правила «разрешить ответы на исходящие».

Таблица conntrack конечна

Сообщение в dmesg: nf_conntrack: table full, dropping packet — новые соединения отбрасываются на узле (часто на узле Kubernetes или NAT-шлюзе), при том что сервисы исправны. Проверка: conntrack -S, sysctl net.netfilter.nf_conntrack_count net.netfilter.nf_conntrack_max.

Гонка DNAT в Kubernetes

Два одновременных UDP-пакета (запросы A и AAAA к DNS) с одного сокета могут конфликтовать при вставке в conntrack — один теряется, и запрос к DNS висит 5 с. Известная причина «случайных пятисекундных задержек» в кластерах; лечится NodeLocal DNSCache или опцией single-request-reopen.

16.7Сеть контейнера — из тех же деталей

Контейнерсвой network namespace: eth0 172.17.0.2, свои маршруты, свой lo
⇄ veth-пара ⇄
Мост docker0виртуальный коммутатор, 172.17.0.1
→ маршрутизация + MASQUERADE →
eth0 хоста192.168.1.50
  • Network namespace — отдельный экземпляр сетевого стека: интерфейсы, таблица маршрутов, правила netfilter, порты. Поэтому два контейнера могут слушать порт 8080 одновременно.
  • veth-пара — виртуальный кабель: один конец в контейнере (eth0), другой на хосте, воткнут в мост.
  • Исходящий трафик — SNAT (MASQUERADE): адрес контейнера заменяется адресом хоста.
  • Публикация порта -p 8080:80 — правило DNAT в PREROUTING: пакеты на порт 8080 хоста переписываются на 172.17.0.2:80.
  • Под Kubernetes — несколько контейнеров в одном network namespace: они делят IP и видят друг друга через localhost. Связь между подами разных узлов обеспечивает CNI-плагин (overlay или маршрутизация), а Service — правила DNAT на каждом узле (тема 13).
ip netns list;  lsns -t net                     # пространства имён
nsenter -t <pid контейнера> -n ip addr          # выполнить команду в сети контейнера, даже если в образе нет утилит
ip link show type veth;  bridge link            # veth-пары и порты моста
iptables -t nat -L -n -v | head -40             # правила DNAT/MASQUERADE Docker и kube-proxy

16.9Самопроверка

Кто выполняет TCP-рукопожатие для входящего соединения?

  • Приложение в вызове accept()
  • Сетевая карта
  • Ядро; приложение получает из accept-очереди уже установленное соединение
  • Балансировщик
Поэтому клиент может «подключиться» к зависшему приложению: рукопожатие пройдёт, а ответа не будет.

Сервис падает с «Cannot assign requested address» при вызовах к одному внешнему API.

  • Закончилась память
  • Исчерпаны эфемерные порты: слишком много коротких соединений к одному адресу, порты висят в TIME_WAIT
  • Неверный DNS
  • Закрыт порт на файрволе
Нужен пул соединений с keep-alive.

Почему два контейнера на одном хосте могут одновременно слушать порт 80?

  • У каждого свой network namespace — отдельный сетевой стек со своими портами
  • Docker меняет номер порта в приложении
  • Порт 80 особый
  • Не могут
Конфликт возникает только при публикации на один и тот же порт хоста.

В dmesg: «nf_conntrack: table full, dropping packet». Что происходит?

  • Переполнен диск
  • Сетевая карта неисправна
  • Закончились дескрипторы
  • Таблица отслеживания соединений netfilter заполнена: новые соединения через этот узел отбрасываются
Увеличить nf_conntrack_max, сократить таймауты, уменьшить число коротких соединений.
Что происходит с пакетом от сетевой карты до read() в приложении?

Карта → кольцевой буфер → softirq/NAPI → sk_buff → netfilter PREROUTING (conntrack, DNAT) → маршрутизация → INPUT → TCP: поиск сокета, проверка, ACK → буфер приёма → пробуждение через epoll → read() копирует данные в процесс. На каждом этапе есть очередь с пределом.

Чем отличаются очередь SYN и accept-очередь и что бывает при переполнении?

В первой — соединения, получившие SYN-ACK и ждущие ACK; при переполнении SYN отбрасывается или включаются SYN cookies. Во второй — установленные соединения, ждущие accept(); при переполнении финальный ACK игнорируется, клиент видит задержки и таймауты. Размер второй задаёт backlog и somaxconn.

Как устроена сеть Docker-контейнера?

Отдельный network namespace; veth-пара соединяет его с мостом docker0 на хосте; исходящий трафик маскируется (SNAT) адресом хоста; публикация порта — правило DNAT. Под Kubernetes — общий namespace для контейнеров пода плюс CNI для связи между узлами.
