11.1HTTP/1.1: одна касса

В одном соединении HTTP/1.1 запросы идут строго по очереди: пока не пришёл ответ на первый, второй ждёт. Медленный ответ задерживает всех, кто за ним, — это блокировка начала очереди. Браузеры обходят это, открывая до 6 соединений к одному сайту, — как открыть шесть касс, но каждая всё равно работает по очереди.

Главная мысль HTTP/1.1: один запрос за раз на соединение. Медленный блокирует остальных.

11.2HTTP/2: всё вперемешку по одному соединению

HTTP/2 режет запросы и ответы на маленькие кадры и пускает их вперемешку по одному соединению — мультиплексирование. Медленный ответ больше не задерживает быстрые. Плюс сжатие заголовков. Но осталась проблема уровнем ниже: TCP отдаёт данные строго по порядку, и если потерялся один пакет, ждут все потоки, пока его не перешлют.

Главная мысль HTTP/2 — много запросов в одном соединении. Но потеря пакета в TCP тормозит всех.

11.3HTTP/3 и QUIC

QUIC — новый транспорт поверх UDP, который сам делает надёжность, но для каждого потока отдельно: потеря пакета одного запроса не тормозит остальные. Ещё QUIC объединяет установку соединения и TLS в один круг, а соединение переживает смену сети (с Wi-Fi на мобильную) без переподключения. HTTP поверх QUIC — это HTTP/3.

Потерялся один пакет, в работе три запроса
HTTP/1.1: запросы по очереди → второй и третий ждут первогоHTTP/2: все три в одном TCP → пакет запроса 1 потерян
TCP держит ВСЁ, пока не придёт повтор → ждут все триHTTP/3 (QUIC): у каждого запроса свой поток
ждёт только запрос 1, запросы 2 и 3 получены сразу

Потеря затрагивает только свой поток.

Главная мысль HTTP/3 = HTTP поверх QUIC (UDP): потеря не тормозит соседей, быстрее установка.

11.5gRPC

gRPC — способ вызывать методы другого сервиса, как будто они локальные. Описываете в схеме (protobuf), какие методы и сообщения есть, — и получаете готовый клиент и сервер на разных языках. Работает поверх HTTP/2, компактно и быстро, умеет потоки в обе стороны. Хорош для общения сервисов внутри компании; для публичных API и браузеров обычно удобнее REST/JSON.

Главная мысль gRPC — быстрый вызов методов между сервисами по схеме protobuf поверх HTTP/2.

11.7Проверьте себя

Какую проблему HTTP/2 решил не до конца?

  • сжатие заголовков
  • количество соединений
  • потеря пакета TCP задерживает все потоки соединения
  • шифрование
Это решает HTTP/3.

Почему HTTP/3 работает поверх UDP?

  • чтобы сделать надёжность для каждого потока отдельно и не зависеть от порядка TCP
  • UDP надёжнее TCP
  • TCP запрещён
  • UDP шифрует данные
Надёжность реализована в самом QUIC.

Нужно присылать пользователю уведомления, ответы от него не нужны. Что проще всего?

  • WebSocket
  • gRPC
  • polling раз в секунду
  • SSE
Односторонний поток событий по HTTP.

Для чего лучше подходит WebSocket?

  • загрузки картинок
  • чата, где сообщения идут в обе стороны
  • кэширования
  • DNS
Постоянный двусторонний канал.

Почему браузеры с HTTP/1.1 открывали несколько соединений к одному сайту?

  • для безопасности
  • для экономии
  • в одном соединении запросы шли строго по очереди
  • так требовал сервер
Несколько «касс» вместо одной.
