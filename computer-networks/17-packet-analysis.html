Практикум: читаем дампы трафика

Когда логи приложения молчат, а метрики противоречат друг другу, остаётся источник, который не врёт, — сами пакеты. Дамп трафика (dump — «сброс», запись) — файл со всеми пакетами, прошедшими через сетевой интерфейс. Умение за минуту снять дамп и увидеть в нём «SYN без ответа» или «нулевое окно» превращает многочасовое гадание в диагноз. Здесь — минимум tcpdump, конструктор фильтров и восемь дампов из реальных аварий: по каждому нужно поставить диагноз.

~3 часас нуля8 разборовинтерактивсловариктест
Если совсем просто Дамп трафика — запись всего, что прошло по проводу. tcpdump снимает её, Wireshark показывает удобно. По дампу видно то, что скрывают логи: был ли ответ вообще, кто первым оборвал соединение, где повторы и где время уходит в ожидание. Вся глава простыми словами →
Что нужно знать заранее Флаги TCP (SYN, ACK, FIN, RST), номера seq и ack, окно и повторные передачи из главы 06; MTU из главы 02; DNS из главы 08. tcpdump — консольная утилита записи пакетов (Linux, macOS). Wireshark — бесплатная графическая программа для разбора записей (есть и для Windows). Сокращения — в словарике.

17.1Как снять дамп

Команда записи с пояснением каждой части. Линии под ней указывают, к чему относится пояснение:

tcpdump -i any -nn -s 0 -w /tmp/dump.pcap 'host 10.2.3.40 and port 8443'
#        │      │   │    │                 └ фильтр захвата (BPF): чем уже, тем меньше файл и нагрузка
#        │      │   │    └ писать в файл для Wireshark (без -w — печатать на экран)
#        │      │   └ захватывать пакет целиком (по умолчанию может обрезать)
#        │      └ не превращать адреса и порты в имена: быстрее и однозначнее
#        └ все интерфейсы; в контейнере — nsenter -t <pid> -n tcpdump …
tcpdump -r /tmp/dump.pcap -nn -tttt 'tcp[tcpflags] & (tcp-syn|tcp-rst) != 0'   # прочитать файл, показать только SYN и RST
  • -i (interface) — с какого интерфейса записывать; any — со всех.
  • -w (write) — записать в файл; .pcap (packet capture, «захват пакетов») — стандартный формат, который открывает Wireshark. -r (read) — прочитать такой файл.
  • Фильтр в кавычках пишется на языке BPF (Berkeley Packet Filter — «пакетный фильтр Беркли»): host — адрес, port — порт, and / or / not — «и», «или», «не». Фильтр tcp[tcpflags] & (tcp-syn|tcp-rst) != 0 читается так: «пакеты, у которых в TCP-флагах есть SYN или RST».
  • -tttt — печатать полную дату и время у каждого пакета.
  • nsenter -t <pid> -n — выполнить tcpdump в сетевом пространстве контейнера (глава 16).

Соберите фильтр в конструкторе: выберите, что хотите поймать, и получите готовую команду.

Конструктор фильтра
Где снимать Один и тот же обмен выглядит по-разному с двух сторон. Если клиент видит ушедший SYN, а на сервере его нет — пакет потерян в пути. Снимайте дамп с обеих сторон и на промежуточных узлах (например, на балансировщике) и сравнивайте по времени и номерам seq. Помните про NAT: адреса и порты на разных участках разные (глава 04).
Главное tcpdump -i any -nn -s 0 -w файл 'фильтр' — записать; Wireshark — разобрать. Фильтр делайте узким, а снимайте по возможности с двух сторон.

17.2Как читать строку tcpdump

Каждая строка — один пакет. Разберём одну по полям:

12:00:01.000123 IP 10.0.0.5.51000 > 10.2.3.40.8443: Flags [P.], seq 1:201, ack 1, win 502, length 200
│               │  │                │                      │      │           │      │        └ байт данных
│               │  │                │                      │      │           │      └ окно приёма отправителя (× масштаб)
│               │  │                │                      │      │           └ «жду от тебя байт №1»
│               │  │                │                      │      └ относительные номера: байты с 1 по 200
│               │  │                │                      └ S=SYN  F=FIN  R=RST  P=PSH  .=ACK
│               │  └ источник:порт  └ назначение:порт
└ время с микросекундами: разница между строками — главное, на что смотреть
  • Адрес и порт пишутся через точку: 10.0.0.5.51000 — адрес 10.0.0.5, порт 51000. Стрелка > показывает направление.
  • Флаги (глава 06): [S] — SYN, [S.] — SYN-ACK, [.] — просто подтверждение ACK, [P.] — данные с флагом PSH, [F.] — FIN, [R] — RST.
  • Относительные номера: tcpdump вычитает из seq начальный случайный номер, чтобы считать от 1. seq 1:201 — байты с 1-го по 200-й.
  • win — окно приёма (глава 06); реальное значение надо умножить на масштаб окна, о котором договорились в рукопожатии.
  • Главный инструмент анализа — разница времени между строками: где пауза, там и проблема.

17.3Восемь дампов: поставьте диагноз

Каждый дамп — из типичной аварии. Попробуйте поставить диагноз сами, прежде чем выбрать ответ. Обозначения A, B, LB — условные имена хостов (LB — load balancer, балансировщик).

Дамп 1

12:00:01.000 IP 10.0.0.5.51000 > 10.2.3.40.8443: Flags [S], seq 1000, win 64240, options [mss 1460]
12:00:02.003 IP 10.0.0.5.51000 > 10.2.3.40.8443: Flags [S], seq 1000, win 64240, options [mss 1460]
12:00:04.011 IP 10.0.0.5.51000 > 10.2.3.40.8443: Flags [S], seq 1000, win 64240, options [mss 1460]
12:00:08.027 IP 10.0.0.5.51000 > 10.2.3.40.8443: Flags [S], seq 1000, win 64240, options [mss 1460]

Подсказка: посмотрите на интервалы между строками и на то, есть ли хоть один ответ.

Что происходит?

  • Порт закрыт
  • SYN уходит, ответа нет: пакеты выбрасывает файрвол или облачные правила доступа (security group), либо хост недоступен; клиент повторяет, удваивая интервал
  • Сервер перегружен и отвечает медленно
  • Проблема TLS
Тишина в ответ на SYN и интервалы 1 → 2 → 4 секунды. Закрытый порт дал бы мгновенный RST. Следующий шаг — дамп на сервере: доходят ли до него SYN.

Дамп 2

12:00:01.000 IP 10.0.0.5.51002 > 10.2.3.40.8443: Flags [S], seq 2000
12:00:01.001 IP 10.2.3.40.8443 > 10.0.0.5.51002: Flags [R.], seq 0, ack 2001, win 0

Диагноз?

  • Файрвол выбрасывает пакеты
  • Потеря пакета
  • Хост доступен, но на порту 8443 никто не слушает — «Connection refused»
  • Сервер закрыл соединение по таймауту
RST в ответ на SYN за 1 мс: ядро сервера получило пакет и не нашло слушающего сокета. Сервис не запущен или слушает другой адрес или порт (например, 127.0.0.1 вместо 0.0.0.0, глава 03).

Дамп 3

12:00:01.000 IP A.51003 > B.443: Flags [P.], seq 1:1461, ack 1, length 1460
12:00:01.000 IP A.51003 > B.443: Flags [P.], seq 1461:2921, ack 1, length 1460
12:00:01.000 IP A.51003 > B.443: Flags [P.], seq 2921:4381, ack 1, length 1460
12:00:01.041 IP B.443 > A.51003: Flags [.], ack 1, win 501, options [sack 1461:4381]
12:00:01.041 IP B.443 > A.51003: Flags [.], ack 1, win 501, options [sack 1461:4381]
12:00:01.042 IP A.51003 > B.443: Flags [P.], seq 1:1461, ack 1, length 1460
12:00:01.083 IP B.443 > A.51003: Flags [.], ack 4381, win 490

Что здесь видно?

  • Первый сегмент потерян: получатель через SACK сообщает, что у него есть байты 1461–4380, но ждёт байт 1; отправитель повторяет сегмент
  • Получатель не успевает читать
  • Соединение сброшено
  • Рукопожатие не завершилось
ack 1 при sack 1461:4381 — «дыра» в начале. После повторной передачи ack сразу прыгает на 4381. Единичные потери — норма; если их много, ищите перегруженный канал или плохую линию (глава 06).

Дамп 4

12:00:01.000 IP A.51004 > B.9000: Flags [P.], seq 1:65536, ack 1, length 65535
12:00:01.001 IP B.9000 > A.51004: Flags [.], ack 65536, win 0
12:00:01.250 IP A.51004 > B.9000: Flags [.], seq 65535:65536, ack 1, length 1     (zero window probe)
12:00:01.251 IP B.9000 > A.51004: Flags [.], ack 65536, win 0
12:00:01.750 IP A.51004 > B.9000: Flags [.], seq 65535:65536, ack 1, length 1
12:00:01.751 IP B.9000 > A.51004: Flags [.], ack 65536, win 0

«Zero window probe» — «проба нулевого окна»: отправитель время от времени шлёт 1 байт, чтобы узнать, не освободилось ли место у получателя.

Почему передача остановилась?

  • Потери пакетов в сети
  • Файрвол
  • Перегрузка канала
  • Получатель B объявил окно 0: его приложение не читает данные из сокета, буфер приёма заполнен
Сеть работает идеально — ответы приходят за 1 мс. Проблема в приложении на стороне B: зависло, заблокировано, не успевает. Смотреть нужно его thread dump (снимок того, чем заняты все потоки программы), а не сеть.

Дамп 5

12:00:01.000 IP A.51005 > LB.443: Flags [P.], seq 501:701, ack 9001, length 200       (предыдущий обмен был в 11:53:40)
12:00:01.001 IP LB.443 > A.51005: Flags [R], seq 9001, win 0

Клиент получил «Connection reset by peer» на первом запросе после перерыва. Почему?

  • Сервер упал
  • Балансировщик закрыл соединение, простаивавшее дольше его таймаута, а клиентский пул этого не заметил и отправил в него запрос
  • Потерян пакет
  • Неверный сертификат
Между обменами прошло 6 минут 20 секунд — больше типичного таймаута простоя (60–350 с). Лечение: время жизни и проверка соединений в пуле короче таймаута балансировщика, повтор идемпотентных запросов (глава 12).

Дамп 6

12:00:01.000 IP 10.0.0.5.40112 > 10.0.0.2.53: 4411+ A? payments.internal. (35)
12:00:06.005 IP 10.0.0.5.40112 > 10.0.0.3.53: 4411+ A? payments.internal. (35)
12:00:06.007 IP 10.0.0.3.53 > 10.0.0.5.40112: 4411 1/0/0 A 10.2.3.40 (51)

Как читать DNS в tcpdump: 4411 — номер запроса, + — «нужна рекурсия», A? — вопрос о записи A, 1/0/0 — в ответе 1 запись, 0 в разделе полномочий и 0 дополнительных, (35) — размер в байтах. Порт 53 — DNS.

Откуда задержка ровно 5 секунд?

  • Медленная сеть
  • Долгая обработка на авторитативном сервере
  • Первый DNS-сервер из resolv.conf не ответил; через таймаут 5 с резолвер обратился ко второму
  • Потеря TCP-сегмента
Таймаут резолвера по умолчанию — 5 с. Ровные задержки 5, 10, 15 секунд на новых соединениях — почти всегда DNS. Починить первый сервер, задать в /etc/resolv.conf options timeout:1 attempts:2, добавить локальный кэш (глава 08).

Дамп 7

12:00:01.000 IP A.51007 > B.443: Flags [S], seq 100, options [mss 1460]
12:00:01.020 IP B.443 > A.51007: Flags [S.], seq 900, ack 101, options [mss 1460]
12:00:01.020 IP A.51007 > B.443: Flags [.], ack 901
12:00:01.021 IP A.51007 > B.443: Flags [P.], seq 101:618, length 517      (TLS ClientHello)
12:00:01.041 IP B.443 > A.51007: Flags [.], ack 618
12:00:01.250 IP B.443 > A.51007: Flags [P.], seq 901:2361, length 1460    — не дошёл до A
12:00:01.500 IP B.443 > A.51007: Flags [P.], seq 901:2361, length 1460    — не дошёл до A
12:00:02.000 IP B.443 > A.51007: Flags [P.], seq 901:2361, length 1460    — не дошёл до A
                 (дамп снят на стороне B; на стороне A этих пакетов нет)

Маленькие пакеты проходят, а полноразмерные от B до A — нет. Причина?

  • На пути MTU меньше 1500 (туннель, VPN), а ICMP-сообщение «нужна фрагментация» не доходит до B — «чёрная дыра» PMTUD
  • Сервер B перегружен
  • Закрыт порт 443
  • Клиент не поддерживает TLS 1.3
Рукопожатие TCP (40 байт) и ClientHello (517 байт) проходят, а ответ сервера с сертификатом (1460 байт) — нет. Симптом: «соединение устанавливается, а TLS зависает». Лечение: разрешить ICMP «Destination Unreachable — Fragmentation Needed» (тип 3, код 4), MSS clamping, меньший MTU на интерфейсе (глава 02).

Дамп 8

12:00:01.000 IP A.51008 > B.8080: Flags [P.], seq 1:201, ack 1, length 200        (HTTP-запрос)
12:00:01.001 IP B.8080 > A.51008: Flags [.], ack 201, win 502
12:00:09.340 IP B.8080 > A.51008: Flags [P.], seq 1:1201, ack 201, length 1200     (HTTP-ответ)
12:00:09.340 IP A.51008 > B.8080: Flags [.], ack 1201

Ответ пришёл через 8,3 секунды. Виновата ли сеть?

  • Да, потери пакетов
  • Да, малое окно
  • Да, проблема MTU
  • Нет: запрос подтверждён за 1 мс, повторов нет; 8 секунд сервер B готовил ответ — искать нужно в приложении
Самый частый и самый полезный результат анализа дампа — доказательство, что сеть ни при чём. Время между ACK запроса и первым байтом ответа — это время работы сервера.

17.4Wireshark: пять приёмов

Откройте файл .pcap в Wireshark (File → Open). Каждая строка — пакет, внизу — его разбор по уровням. Пять приёмов, которые экономят больше всего времени:

ПриёмГде найтиЧто даёт
Follow → TCP Stream («проследить поток TCP»)правый клик по пакетувесь диалог одного соединения как текст
Expert Information («экспертная информация»)меню Analyzeсводка проблем: повторы, дубли ACK, нулевое окно, RST — с переходом к пакетам
Время «с предыдущего пакета»View → Time Display Format → Seconds Since Previous Displayed Packetсразу видно, где пауза
Conversations («разговоры»)меню Statisticsкто с кем, сколько байт и пакетов; сортировка по длительности
Расшифровка TLSу клиента — переменная окружения SSLKEYLOGFILE, в Wireshark — Preferences → Protocols → TLS → (Pre)-Master-Secret log filenameсодержимое HTTPS ваших собственных клиентов (браузер, curl; для Java — агент jSSLKeyLog). Ключи сеанса пишутся в файл, и Wireshark по ним расшифровывает трафик

Строка поиска сверху — фильтр отображения (display filter); у него свой синтаксис, отличный от BPF: например tcp.flags.reset == 1 или tcp.analysis.retransmission. Набор полезных фильтров — в главе 14.

Осторожно с дампами Дамп содержит всё, что не зашифровано: токены, пароли, персональные данные. Снимайте с узким фильтром и ограничением размера (-s 96 — только первые 96 байт каждого пакета, то есть заголовки; -c 1000 — не больше 1000 пакетов), храните недолго, не выкладывайте в общие чаты.

17.6Самопроверка

Ответьте вслух, потом откройте ответ.

Как по дампу отличить проблему сети от проблемы приложения?

Сеть: SYN без ответа, повторные передачи, дубли ACK, большие задержки между отправкой и подтверждением. Приложение: быстрые ACK при долгой паузе до ответа, нулевое окно (не читает), RST после простоя или на закрытый сокет, FIN без ответного закрытия. Время «ACK запроса → первый байт ответа» — время работы сервера.

Что означают «SYN без ответа» и «SYN → RST»?

Без ответа — пакет не дошёл или выброшен (файрвол, правила доступа, выключенный хост, переполненная очередь SYN). RST — дошёл до хоста, но порт закрыт. Первое даёт таймаут подключения, второе — мгновенный Connection refused.

Почему стоит снимать дамп с двух сторон?

Чтобы определить, где теряется пакет: отправлен, но не получен — потеря в пути; получен, но без ответа — проблема на получателе. К тому же NAT и балансировщики меняют адреса, а задержку вносит какой-то конкретный участок.

По дампу соединение устанавливается, ClientHello уходит, а ответ сервера не приходит. Ваша гипотеза?

Если на стороне сервера видно, что большой ответ отправлен и повторяется, а до клиента не доходит, — MTU и «чёрная дыра» PMTUD: маленькие пакеты проходят, полноразмерные теряются. Проверить ping с запретом фрагментации и разными размерами.
