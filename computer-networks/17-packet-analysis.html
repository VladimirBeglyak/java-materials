Практикум: читаем дампы трафика

Когда логи приложения молчат, а метрики противоречат друг другу, остаётся источник, который не врёт, — сами пакеты. Умение за минуту снять дамп и увидеть в нём «SYN без ответа» или «окно ноль» превращает многочасовое гадание в диагноз. Здесь — минимум tcpdump, конструктор фильтров и восемь дампов из реальных аварий: по каждому нужно поставить диагноз.

17.1Как снять дамп

tcpdump -i any -nn -s 0 -w /tmp/dump.pcap 'host 10.2.3.40 and port 8443'
#        │      │   │    │                 └ фильтр захвата (BPF): чем уже, тем меньше файл и нагрузка
#        │      │   │    └ писать в файл для Wireshark (без -w — печатать на экран)
#        │      │   └ захватывать пакет целиком (по умолчанию может обрезать)
#        │      └ не превращать адреса и порты в имена: быстрее и однозначнее
#        └ все интерфейсы; в контейнере — nsenter -t <pid> -n tcpdump …

tcpdump -r /tmp/dump.pcap -nn -tttt 'tcp[tcpflags] & (tcp-syn|tcp-rst) != 0'   # прочитать файл, показать только SYN и RST
Конструктор фильтра
Где снимать Один и тот же обмен выглядит по-разному с двух сторон: если клиент видит ушедший SYN, а на сервере его нет — пакет потерян по пути. Снимайте с обеих сторон и на промежуточных узлах (балансировщик), сравнивайте по времени и номерам последовательности. Помните о NAT: адреса и порты на разных участках разные.

17.3Восемь дампов: поставьте диагноз

Дамп 1

12:00:01.000 IP 10.0.0.5.51000 > 10.2.3.40.8443: Flags [S], seq 1000, win 64240, options [mss 1460]
12:00:02.003 IP 10.0.0.5.51000 > 10.2.3.40.8443: Flags [S], seq 1000, win 64240, options [mss 1460]
12:00:04.011 IP 10.0.0.5.51000 > 10.2.3.40.8443: Flags [S], seq 1000, win 64240, options [mss 1460]
12:00:08.027 IP 10.0.0.5.51000 > 10.2.3.40.8443: Flags [S], seq 1000, win 64240, options [mss 1460]

Что происходит?

  • Порт закрыт
  • SYN уходит, ответа нет: пакеты отбрасываются файрволом/security group или хост недоступен; клиент повторяет с удвоением интервала
  • Сервер перегружен и отвечает медленно
  • Проблема TLS
Тишина в ответ на SYN и интервалы 1–2–4 с. Закрытый порт дал бы мгновенный RST. Следующий шаг — дамп на сервере: доходят ли SYN.

Дамп 2

12:00:01.000 IP 10.0.0.5.51002 > 10.2.3.40.8443: Flags [S], seq 2000
12:00:01.001 IP 10.2.3.40.8443 > 10.0.0.5.51002: Flags [R.], seq 0, ack 2001, win 0

Диагноз?

  • Файрвол отбрасывает пакеты
  • Потеря пакета
  • Хост доступен, но на порту 8443 никто не слушает — «Connection refused»
  • Сервер закрыл соединение по таймауту
RST в ответ на SYN за 1 мс: ядро сервера получило пакет и не нашло слушающего сокета. Сервис не запущен или слушает другой адрес/порт.

Дамп 3

12:00:01.000 IP A.51003 > B.443: Flags [P.], seq 1:1461, ack 1, length 1460
12:00:01.000 IP A.51003 > B.443: Flags [P.], seq 1461:2921, ack 1, length 1460
12:00:01.000 IP A.51003 > B.443: Flags [P.], seq 2921:4381, ack 1, length 1460
12:00:01.041 IP B.443 > A.51003: Flags [.], ack 1, win 501, options [sack 1461:4381]
12:00:01.041 IP B.443 > A.51003: Flags [.], ack 1, win 501, options [sack 1461:4381]
12:00:01.042 IP A.51003 > B.443: Flags [P.], seq 1:1461, ack 1, length 1460
12:00:01.083 IP B.443 > A.51003: Flags [.], ack 4381, win 490

Что здесь видно?

  • Первый сегмент потерян: получатель сообщает через SACK, что имеет 1461–4381, но ждёт байт 1; отправитель повторяет сегмент
  • Получатель не успевает читать
  • Соединение сброшено
  • Рукопожатие не завершилось
ack 1 при sack 1461:4381 — «дыра» в начале. После ретрансляции ack сразу прыгает на 4381. Единичные потери нормальны; много — ищите перегруженный канал или плохой линк.

12:00:01.000 IP A.51004 > B.9000: Flags [P.], seq 1:65536, ack 1, length 65535
12:00:01.001 IP B.9000 > A.51004: Flags [.], ack 65536, win 0

В чём причина остановки передачи?

  • Потери пакетов в сети
  • Файрвол
  • Перегрузка канала

Сеть работает идеально — ответы приходят за 1 мс. Проблема в приложении на стороне B: зависло, заблокировано, не успевает. Смотреть нужно его thread dump, а не сеть.

Дамп 5

12:00:01.000 IP A.51005 > LB.443: Flags [P.], seq 501:701, ack 9001, length 200       (предыдущий обмен был в 11:53:40)
12:00:01.001 IP LB.443 > A.51005: Flags [R], seq 9001, win 0

Клиент получил «Connection reset by peer» на первом запросе после перерыва. Почему?

  • Сервер упал
  • Балансировщик закрыл простаивавшее больше его таймаута соединение, а клиент из пула этого не заметил и отправил в него запрос
  • Потерян пакет
  • Неверный сертификат
Между обменами прошло 6 минут 20 секунд — больше типичного таймаута простоя (60–350 с). Лечение: время жизни и проверка соединений в пуле короче таймаута балансировщика, повтор идемпотентных запросов.

Дамп 6

12:00:01.000 IP 10.0.0.5.40112 > 10.0.0.2.53: 4411+ A? payments.internal. (35)
12:00:06.005 IP 10.0.0.5.40112 > 10.0.0.3.53: 4411+ A? payments.internal. (35)
12:00:06.007 IP 10.0.0.3.53 > 10.0.0.5.40112: 4411 1/0/0 A 10.2.3.40 (51)

Откуда задержка ровно 5 секунд?

  • Медленная сеть
  • Долгая обработка на авторитетном сервере
  • Первый DNS-сервер из resolv.conf не ответил; через таймаут 5 с резолвер обратился ко второму
  • Потеря TCP-сегмента
Таймаут резолвера по умолчанию — 5 с. Ровные задержки 5/10/15 с на новых соединениях почти всегда DNS. Починить первый сервер, уменьшить options timeout:1 attempts:2, добавить локальный кэш.

Дамп 7

12:00:01.000 IP A.51007 > B.443: Flags [S], seq 100, options [mss 1460]
12:00:01.020 IP B.443 > A.51007: Flags [S.], seq 900, ack 101, options [mss 1460]
12:00:01.020 IP A.51007 > B.443: Flags [.], ack 901
12:00:01.021 IP A.51007 > B.443: Flags [P.], seq 101:618, length 517      (TLS ClientHello)
12:00:01.041 IP B.443 > A.51007: Flags [.], ack 618
12:00:01.250 IP B.443 > A.51007: Flags [P.], seq 901:2361, length 1460    — не дошёл до A
12:00:01.500 IP B.443 > A.51007: Flags [P.], seq 901:2361, length 1460    — не дошёл до A
12:00:02.000 IP B.443 > A.51007: Flags [P.], seq 901:2361, length 1460    — не дошёл до A
                 (дамп снят на стороне B; на стороне A этих пакетов нет)

Маленькие пакеты проходят, полноразмерные от B до A — нет. Причина?

  • На пути MTU меньше 1500 (туннель, VPN), а ICMP «fragmentation needed» не доходит до B — чёрная дыра PMTUD
  • Сервер B перегружен
  • Закрыт порт 443
  • Клиент не поддерживает TLS 1.3
Рукопожатие TCP (40 байт) и ClientHello (517 байт) проходят, а ServerHello с сертификатом (1460 байт) — нет. Симптом: «соединение устанавливается, TLS зависает». Лечение: разрешить ICMP type 3 code 4, MSS clamping, меньший MTU на интерфейсе.

Дамп 8

12:00:01.000 IP A.51008 > B.8080: Flags [P.], seq 1:201, ack 1, length 200        (HTTP-запрос)
12:00:01.001 IP B.8080 > A.51008: Flags [.], ack 201, win 502
12:00:09.340 IP B.8080 > A.51008: Flags [P.], seq 1:1201, ack 201, length 1200     (HTTP-ответ)
12:00:09.340 IP A.51008 > B.8080: Flags [.], ack 1201

Ответ пришёл через 8,3 секунды. Виновата ли сеть?

  • Да, потери пакетов
  • Да, малое окно
  • Да, проблема MTU
  • Нет: запрос подтверждён за 1 мс, ретрансляций нет; 8 секунд сервер B формировал ответ — искать нужно в приложении
Самый частый и самый полезный результат анализа дампа — доказательство, что сеть ни при чём. Время между ACK запроса и первым байтом ответа — это время работы сервера.

17.5Самопроверка

Как по дампу отличить проблему сети от проблемы приложения?

Сеть: SYN без ответа, ретрансляции, дубли ACK, потери, большие задержки между отправкой и ACK. Приложение: быстрые ACK при долгой паузе до ответа, окно ноль (не читает), RST после простоя или на закрытый сокет, FIN без ответного close. Время «ACK запроса → первый байт ответа» — время сервера.

Что означают SYN без ответа и SYN → RST?

Без ответа — пакет не дошёл или отброшен (файрвол, security group, выключенный хост, переполненная очередь SYN). RST — дошёл до хоста, но порт закрыт. Первое даёт таймаут соединения, второе — мгновенный Connection refused.

Почему стоит снимать дамп с двух сторон?

Чтобы определить, где теряется пакет: отправлен, но не получен — потеря на пути; получен, но без ответа — проблема на получателе. Плюс NAT и балансировщики меняют адреса, а задержку вносит конкретный участок.
