12.1Модели ввода-вывода

Задача. Программа вызвала read() — прочитать данные из сокета. А данных ещё нет: они в пути, RTT 50 мс. Что в это время делать потоку? Ввод-вывод (I/O, input/output) — обмен данными с внешним миром: сетью, диском. Есть два подхода:

  • Блокирующий, «поток на соединение». Поток просто стоит и ждёт, пока придут данные (блокируется). Код простой: прочитал → обработал → ответил. Но каждому соединению нужен свой поток, а классический платформенный поток (поток операционной системы) занимает около мегабайта памяти. 10 000 соединений — 10 000 потоков, и ОС не справляется. С Java 21 есть виртуальные потоки — лёгкие потоки, которыми управляет сама JVM: их могут быть миллионы, и пока виртуальный поток ждёт сеть, JVM отдаёт платформенный поток другим.
  • Event loop («цикл событий», неблокирующий ввод-вывод). Несколько потоков (обычно по одному на ядро процессора) обслуживают тысячи соединений. Поток спрашивает ОС «какие сокеты уже готовы к чтению или записи?» и обрабатывает только их. В Java это NIO (New I/O, «новый ввод-вывод») с классом Selector («выбиратель»), а внутри ОС — механизмы epoll (Linux) и kqueue (macOS). На этом построен сетевой фреймворк Netty. Аналогия: официант не стоит у одного столика, пока гость выбирает блюдо, а обходит зал и подходит к тем, кто поднял руку.

Где что используется: Tomcat (веб-сервер, который по умолчанию запускает Spring Boot) — пул потоков, по потоку на запрос; WebFlux и Reactor Netty (реактивный стек Spring) — event loop; Spring MVC на виртуальных потоках — простой блокирующий код с масштабом event loop; встроенный JDK HttpClient внутри асинхронный, а метод sendAsync() возвращает CompletableFuture (объект «результат будет позже»).

Главное правило event loop Никогда не блокируйте поток event loop: не ждите там базу данных, DNS или Thread.sleep. Пока один обработчик ждёт, стоят все тысячи соединений, которые обслуживает этот поток.

Минимальный TCP-сервер и клиент на блокирующем API с виртуальными потоками. Сервер «эхо» возвращает каждую полученную строку обратно:

public final class EchoServer {
    public static void main(String[] args) throws IOException {
        try (ServerSocket server = new ServerSocket()) {
            server.setReuseAddress(true);                                  // можно сразу перезапустить на том же порту
            server.bind(new InetSocketAddress("0.0.0.0", 7000), 1024);   // backlog = размер accept-очереди
            try (ExecutorService exec = Executors.newVirtualThreadPerTaskExecutor()) {
                while (true) {
                    Socket s = server.accept();                            // ждём следующего клиента
                    exec.submit(() -> handle(s));                         // каждому — свой виртуальный поток
                }
            }
        }
    }

    private static void handle(Socket s) {
        try (s;
             BufferedReader in = new BufferedReader(new InputStreamReader(s.getInputStream(), StandardCharsets.UTF_8));
             Writer out = new OutputStreamWriter(s.getOutputStream(), StandardCharsets.UTF_8)) {
            s.setSoTimeout(30_000);              // read timeout: клиент молчит 30 с — закрываем
            s.setTcpNoDelay(true);               // отключить алгоритм Нейгла (глава 07)
            String line;
            while ((line = in.readLine()) != null) {
                out.write(line + "\n");
                out.flush();
            }
        } catch (SocketTimeoutException e) {
            // простаивающий клиент — освобождаем ресурсы
        } catch (IOException e) {
            // Connection reset и т.п. — клиент ушёл
        }
    }
}

final class EchoClient {
    static String call(String host, String msg) throws IOException {
        try (Socket s = new Socket()) {
            s.connect(new InetSocketAddress(host, 7000), 2_000);   // connect timeout: 2 с на рукопожатие
            s.setSoTimeout(5_000);                                 // read timeout: 5 с на ответ
            s.getOutputStream().write((msg + "\n").getBytes(StandardCharsets.UTF_8));
            return new BufferedReader(new InputStreamReader(s.getInputStream(), StandardCharsets.UTF_8)).readLine();
        }
    }
}

Обратите внимание на try (s; …) — это try-with-resources: сокет и потоки закроются автоматически, даже если случилась ошибка. Без этого появляются утечки и состояния CLOSE_WAIT (глава 06). setSoTimeout (SO — socket option, «опция сокета») задаёт, сколько ждать данных при чтении.

Главное Блокирующий код прост, но требует поток на соединение — виртуальные потоки делают это дешёвым. Event loop обслуживает тысячи соединений немногими потоками, но блокировать его нельзя.

12.2Пулы соединений

Задача. Новое соединение к сервису в соседнем регионе стоит дорого: DNS-запрос + TCP-рукопожатие (1 RTT) + TLS (ещё 1 RTT) + медленный старт TCP + процессорное время на шифрование. А после закрытия соединение ещё 60 секунд занимает порт в состоянии TIME_WAIT.

Решение — пул соединений (connection pool): набор заранее открытых соединений, которые программа берёт, использует и возвращает обратно, как велосипеды в прокате. Цена установки соединения платится один раз, а не на каждый запрос.

Ключевые настройки пула. Downstream («ниже по течению») — сервис, который вы вызываете; upstream — тот, кто вызывает вас.

ПараметрЗачемТипичная ошибка
max total / max per route — максимум соединений всего и к одному адресуне перегрузить downstreamу Apache HttpClient по умолчанию соединений на один адрес мало, и под нагрузкой потоки стоят в очереди за соединением
acquire / pool timeout — сколько ждать свободного соединенияне висеть вечно, когда все занятытаймаута нет → потоки ждут бесконечно
idle timeout / eviction — через сколько закрывать простаивающие (eviction — «выселение»)не держать ненужноебольше, чем таймаут простоя сервера или NAT → «протухшие» соединения
max lifetime — максимальный возраст соединенияперераспределение по серверам, учёт смены DNS, обновление сертификатовсоединения живут вечно

Правило таймаутов простоя Клиент должен закрывать простаивающее соединение раньше, чем сервер или любой промежуточный узел. Иначе клиент берёт из пула соединение, которое сервер только что закрыл, и получает Connection reset или NoHttpResponseException («нет HTTP-ответа»), а прокси отвечает 502. Пример правильной цепочки: keep-alive клиента 30 с < балансировщик 60 с < сервер (у Tomcat — keepAliveTimeout) 65 с. Для базы MySQL: maxLifetime в пуле HikariCP (самый популярный пул соединений с базой в Java) на несколько секунд меньше wait_timeout сервера и таймаутов прокси и файрвола между ними.
Главное Пул соединений платит за рукопожатия один раз. У него должны быть лимит, таймаут ожидания, таймаут простоя (меньше серверного) и максимальный возраст.

12.3Таймауты: полная карта

Таймаут — сколько максимум ждать, прежде чем сдаться. У одного HTTP-запроса несколько этапов, и зависнуть может каждый:

TCP-рукопожатие
TLS

read

Почему нужен общий: read timeout ограничивает паузу между порциями данных, а не весь ответ. Сервер, который присылает по байту каждые 20 секунд, никогда не нарушит read timeout в 30 секунд, и запрос будет длиться вечно. Поэтому нужен общий дедлайн (deadline, «крайний срок»): таймаут запроса в HttpClient, CompletableFuture.orTimeout, дедлайн gRPC (глава 11).

public final class RatesClient {
    private final HttpClient http = HttpClient.newBuilder()
            .version(HttpClient.Version.HTTP_2)          // откатится на 1.1, если сервер не умеет
            .connectTimeout(Duration.ofMillis(500))      // 0,5 с на установку соединения
            .followRedirects(HttpClient.Redirect.NEVER)  // не ходить по перенаправлениям молча
            .build();                                     // создаётся один раз: внутри пул соединений

    public String fetch(URI uri) throws IOException, InterruptedException {
        HttpRequest req = HttpRequest.newBuilder(uri)
                .timeout(Duration.ofSeconds(2))           // до получения заголовков ответа
                .header("Accept", "application/json")
                .GET()
                .build();
        HttpResponse<String> resp = http.send(req, HttpResponse.BodyHandlers.ofString());
        if (resp.statusCode() != 200) throw new IOException("status " + resp.statusCode());
        return resp.body();
    }
}

Главная мысль кода: HttpClient создаётся один раз на приложение и переиспользуется — внутри него пул соединений. Создавать новый клиент на каждый запрос — значит каждый раз заново открывать соединения.

Иерархия таймаутов в цепочке вызовов Вызывающий ждёт дольше, чем вызываемый тратит на свою работу вместе со всеми его собственными вызовами: шлюз 10 с > сервис A 8 с > сервис B 3 с > база 2 с. Если наоборот, верхний уровень сдаётся и повторяет запрос, пока нижние ещё работают над первым, — двойная нагрузка. Ещё лучше передавать вниз по цепочке оставшийся бюджет времени, как делает gRPC.
Главное Ставьте таймауты на каждый этап и общий дедлайн на весь запрос. Чем выше по цепочке, тем таймаут длиннее. HttpClient — один на приложение.

12.4Повторы без шторма

Повтор запроса после ошибки (ретрай, retry) спасает от случайных сбоев, но легко превращает маленькую проблему в катастрофу. Пять правил:

  1. Повторять только идемпотентные операции или операции с ключом идемпотентности (глава 10).
  2. Повторять только временные ошибки: таймаут подключения, обрыв соединения, 502, 503, 504, 429 (с учётом заголовка Retry-After — «повторить через»). Не повторять 400, 401, 404, 422: повтор того же ошибочного запроса даст ту же ошибку.
  3. Экспоненциальная пауза с разбросом (exponential backoff with jitter): пауза = случайное(0, min(предел, база · 2^попытка)). Каждая следующая пауза вдвое длиннее, но со случайным разбросом. Без разброса тысячи клиентов, получивших ошибку одновременно, повторяют тоже одновременно — волнами.
  4. Повторять на одном уровне. Если каждый из 4 сервисов в цепочке делает по 3 попытки, получается 3 × 3 × 3 × 3 = 81 запрос к базе на один клик пользователя.
  5. Бюджет повторов и предохранитель. Повторов — не больше ~10% от обычных запросов (retry budget). Circuit breaker («автоматический выключатель», как в электрощитке): при массовых ошибках он «размыкается», и вызовы сразу получают отказ, не нагружая и так лежащий сервис; через время пробует снова. Готовая библиотека — Resilience4j.
Главное Повторяйте только безопасное и временное, с растущей случайной паузой, на одном уровне и с бюджетом. При массовых отказах circuit breaker отключает вызовы.

12.6Чек-лист любого исходящего вызова

  1. Клиент создаётся один раз и переиспользует соединения.
  2. Заданы таймауты подключения, чтения и общий; ожидание в пуле ограничено.
  3. Таймаут простоя и максимальный возраст соединений меньше серверных и сетевых.
  4. Повторы — только идемпотентных запросов и временных ошибок, с разбросом пауз, на одном уровне.
  5. Circuit breaker и bulkhead для внешних зависимостей.
  6. Метрики: время ответа p50 / p99 (перцентили: p99 = 200 мс значит «99% запросов быстрее 200 мс»), ошибки по типам, занятость пула, время ожидания соединения.
  7. Тело ответа всегда прочитано или закрыто — иначе соединение не вернётся в пул.
  8. Блокирующие вызовы не выполняются в event loop (Netty, WebFlux).

12.7Интерактив: шторм повторов и бюджет таймаутов

Цепочка сервисов, один из которых начал сбоить. Меняйте число повторов на каждом уровне и таймауты — и смотрите, сколько запросов получит нижний сервис и успеет ли пользователь получить ответ.

Симулятор: цепочка сервисов под сбоем

Запрос проходит цепочку gateway → A → B → C → БД. Нижний сервис начал отвечать ошибками. Каждый уровень повторяет неудачные вызовы.

12.9Самопроверка

У HTTP-клиента задан только connect timeout. Сервер принял соединение и перестал отвечать. Что произойдёт?

  • Сработает connect timeout
  • Соединение закроется через 30 секунд
  • Поток будет ждать ответ бесконечно: нужен ещё read (или общий) таймаут
  • Клиент автоматически повторит запрос
Таймауты разные: на установку соединения, на ожидание в пуле, на чтение, на весь запрос. Нужны все.

Зачем к паузе между повторами добавляют случайный разброс (jitter)?

  • Для экономии памяти
  • Чтобы клиенты, получившие ошибку одновременно, не повторяли запросы синхронными волнами
  • Чтобы увеличить число попыток
  • Для шифрования
Без разброса все клиенты возвращаются в один момент и снова перегружают сервис.

Пул HTTP-соединений на 50, а вызываемый сервис стал отвечать за 10 с вместо 100 мс. Что случится с вызывающим сервисом?

  • Все 50 соединений будут заняты, остальные потоки встанут в очередь за соединением и исчерпают пул потоков — сбой пойдёт вверх по цепочке
  • Ничего
  • Пул вырастет автоматически
  • Запросы пойдут в обход пула
Каскадный отказ. Защита: короткие таймауты, таймаут ожидания соединения из пула, bulkhead, circuit breaker.

Таймаут простоя: у клиента 90 с, у балансировщика 60 с. Что будет?

  • Всё в порядке
  • Соединения станут быстрее
  • Балансировщик будет ждать клиента
  • Клиент иногда будет брать из пула соединение, которое балансировщик уже закрыл, и получать reset или 502
Клиентский таймаут простоя должен быть меньше, чем у всех на пути.

Какие ошибки имеет смысл повторять?

  • 400 и 404
  • 401 и 403
  • Таймауты подключения, обрывы, 502, 503, 504 и 429 (после Retry-After)
  • Любые
Ошибки клиента (4xx, кроме 429) при повторе дадут тот же результат.

Почему нельзя вызывать JDBC в обработчике запроса WebFlux?

  • JDBC медленнее
  • JDBC блокирует поток, а в WebFlux это поток event loop, обслуживающий тысячи соединений
  • WebFlux не поддерживает базы данных
  • Можно, это безопасно
Выносите блокирующий код на Schedulers.boundedElastic() или используйте R2DBC.

Вопросы для разговора (с собеседований)

Что такое read timeout и почему его недостаточно?

Максимальная пауза между поступлением данных из сокета. Сервер, который медленно, но регулярно шлёт байты, никогда его не нарушит, и запрос может длиться бесконечно. Нужен общий дедлайн на весь запрос.

Как связаны таймаут простоя пула клиента и keep-alive timeout сервера?

Клиентский должен быть меньше. Иначе есть окно, когда сервер уже закрыл соединение, а клиент берёт его из пула и получает reset или пустой ответ.

Почему 3 повтора — это может быть 81 запрос?

Если повторяет каждый уровень цепочки из четырёх сервисов, число попыток перемножается: 3 × 3 × 3 × 3. Под нагрузкой это превращает частичную деградацию в полный отказ. Повторы — на одном уровне (обычно ближе к клиенту) и с бюджетом.

Сервис делает 2 000 запросов в секунду к партнёрскому API без пула. Какие проблемы вы ожидаете?

На каждый запрос — TCP- и TLS-рукопожатия (лишние 2 RTT и процессор), медленный старт, TIME_WAIT на 60 с: 2 000 × 60 = 120 000 занятых портов при ~28 000 эфемерных → порты кончатся, пойдут ошибки подключения. Плюс нагрузка на NAT-шлюз. Решение — пул с keep-alive.

Почему в Reactor Netty нельзя вызывать JDBC в обработчике запроса?

Обработчик выполняется в потоке event loop, который обслуживает тысячи соединений. Блокирующий вызов останавливает их все. Блокирующий код выносят на Schedulers.boundedElastic() (отдельный пул для блокирующих задач) или используют неблокирующий драйвер R2DBC; альтернатива — Spring MVC на виртуальных потоках.
