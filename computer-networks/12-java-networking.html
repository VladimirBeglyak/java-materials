12.1Модели ввода-вывода

public final class EchoServer {
    public static void main(String[] args) throws IOException {
        try (ServerSocket server = new ServerSocket()) {
            server.setReuseAddress(true);
            server.bind(new InetSocketAddress("0.0.0.0", 7000), 1024);   // backlog = accept queue
            try (ExecutorService exec = Executors.newVirtualThreadPerTaskExecutor()) {
                while (true) {
                    Socket s = server.accept();
                    exec.submit(() -> handle(s));
                }
            }
        }
    }

    private static void handle(Socket s) {
        try (s;
             BufferedReader in = new BufferedReader(new InputStreamReader(s.getInputStream(), StandardCharsets.UTF_8));
             Writer out = new OutputStreamWriter(s.getOutputStream(), StandardCharsets.UTF_8)) {
            s.setSoTimeout(30_000);              // read timeout: клиент молчит 30 с — закрываем
            s.setTcpNoDelay(true);
            String line;
            while ((line = in.readLine()) != null) {
                out.write(line + "\n");
                out.flush();
            }
        } catch (SocketTimeoutException e) {
            // простаивающий клиент — освобождаем ресурсы
        } catch (IOException e) {
            // Connection reset и т.п. — клиент ушёл
        }
    }
}

final class EchoClient {
    static String call(String host, String msg) throws IOException {
        try (Socket s = new Socket()) {
            s.connect(new InetSocketAddress(host, 7000), 2_000);   // connect timeout
            s.setSoTimeout(5_000);                                 // read timeout
            s.getOutputStream().write((msg + "\n").getBytes(StandardCharsets.UTF_8));
            return new BufferedReader(new InputStreamReader(s.getInputStream(), StandardCharsets.UTF_8)).readLine();
        }
    }
}

12.2Пулы соединений

Новое соединение к сервису в соседнем регионе стоит DNS + TCP (1 RTT) + TLS (1 RTT) + медленный старт + CPU на криптографию, а после закрытия ещё 60 с занимает эфемерный порт в TIME_WAIT. Пул превращает это в одноразовую цену.

ПараметрЗачемТипичная ошибка
max total / max per routeограничить нагрузку на downstreamApache HttpClient по умолчанию — небольшое число соединений на маршрут: под нагрузкой потоки ждут в пуле
acquire / pool timeoutсколько ждать свободного соединениянет таймаута → потоки висят бесконечно
idle timeout / evictionзакрывать простаивающиебольше, чем idle timeout сервера/NAT → «протухшие» соединения

validationпроверка соединения перед выдачейдорогой SQL-запрос перед каждым использованием
Правило idle-таймаутов Клиент должен закрывать простаивающее соединение раньше, чем сервер или любой промежуточный узел. Иначе клиент берёт из пула соединение, которое сервер только что закрыл, и получает Connection reset / NoHttpResponseException, а прокси — 502. Пример цепочки: keep-alive клиента 30 с < балансировщик 60 с < сервер (Tomcat keepAliveTimeout) 65 с. Для MySQL: maxLifetime HikariCP должен быть на несколько секунд меньше wait_timeout сервера и таймаутов прокси/файрвола между ними.

12.3Таймауты: полная карта

public final class RatesClient {
    private final HttpClient http = HttpClient.newBuilder()
            .version(HttpClient.Version.HTTP_2)          // откатится на 1.1, если сервер не умеет
            .connectTimeout(Duration.ofMillis(500))
            .followRedirects(HttpClient.Redirect.NEVER)
            .build();                                     // создаётся один раз: внутри пул соединений

    public String fetch(URI uri) throws IOException, InterruptedException {
        HttpRequest req = HttpRequest.newBuilder(uri)
                .timeout(Duration.ofSeconds(2))           // до получения заголовков ответа
                .header("Accept", "application/json")
                .GET()
                .build();
        HttpResponse<String> resp = http.send(req, HttpResponse.BodyHandlers.ofString());
        if (resp.statusCode() != 200) throw new IOException("status " + resp.statusCode());
        return resp.body();
    }
}
Иерархия таймаутов в цепочке вызовов Вызывающий ждёт дольше, чем вызываемый тратит на свою работу вместе с его собственными вызовами: gateway 10 с > сервис A 8 с > сервис B 3 с > БД 2 с. Если наоборот, верхний уровень сдаётся и повторяет запрос, пока нижние всё ещё работают над первым, — двойная нагрузка. Лучше всего передавать оставшийся бюджет (дедлайн) вниз по цепочке, как делает gRPC.

12.4Ретраи без шторма

  1. Повторять только идемпотентные операции или с ключом идемпотентности (тема 10).
  2. Повторять только временные ошибки: connect timeout, reset, 502/503/504, 429 (с учётом Retry-After). Не повторять 400, 401, 404, 422.
  3. Экспоненциальная пауза с jitter: sleep = random(0, min(cap, base · 2^attempt)). Без jitter тысячи клиентов повторяют синхронно — волны нагрузки.
  4. Ретраить на одном уровне. 3 попытки на каждом из 4 уровней = 3⁴ = 81 запрос к БД на один пользовательский клик.
  5. Retry budget и circuit breaker (Resilience4j): не больше ~10% дополнительных запросов на ретраи; при массовых отказах — быстрый отказ, а не добивание лежащего сервиса.

12.6Чек-лист любого исходящего вызова

  1. Клиент создаётся один раз и переиспользует соединения.
  2. Заданы connect, read и общий таймаут; ожидание в пуле ограничено.
  3. Idle timeout и max lifetime соединений меньше серверных и сетевых.
  4. Ретраи только идемпотентных и временных ошибок, с jitter, на одном уровне.
  5. Circuit breaker и bulkhead для внешних зависимостей.
  6. Метрики: время ответа p50/p99, ошибки по типам, занятость пула, время ожидания соединения.
  7. Тело ответа всегда читается или закрывается — иначе соединение не вернётся в пул.
  8. Блокирующие вызовы не выполняются в event loop (Netty, WebFlux).

12.7Интерактив: шторм ретраев и бюджет таймаутов

Симулятор: цепочка сервисов под сбоем

Запрос проходит цепочку gateway → A → B → C → БД. Нижний сервис начал отвечать ошибками. Каждый уровень повторяет неудачные вызовы.

12.8Самопроверка

У HTTP-клиента задан только connect timeout. Сервер принял соединение и перестал отвечать. Что произойдёт?

  • Сработает connect timeout
  • Соединение закроется через 30 секунд
  • Поток будет ждать ответ бесконечно: нужен ещё read (response) timeout
  • Клиент автоматически повторит запрос
Таймауты разные: на установку соединения, на получение соединения из пула, на чтение, на весь запрос. Нужны все.

Зачем к паузе между ретраями добавляют jitter?

  • Для экономии памяти
  • Чтобы клиенты, получившие ошибку одновременно, не повторяли запросы синхронными волнами
  • Чтобы увеличить число попыток
  • Для шифрования
Без разброса все клиенты возвращаются в один момент и снова перегружают сервис.

Пул HTTP-соединений на 50, сервис-получатель стал отвечать за 10 с вместо 100 мс. Что случится с вызывающим сервисом?

  • Все 50 соединений будут заняты, остальные потоки встанут в очередь за соединением и исчерпают пул потоков — сбой распространится вверх
  • Ничего
  • Пул вырастет автоматически
  • Запросы пойдут в обход пула
Каскадный отказ. Защита: короткие таймауты, таймаут ожидания соединения из пула, bulkhead, circuit breaker.
Что такое read timeout и почему его недостаточно?

Максимальная пауза между поступлением данных из сокета. Сервер, который медленно, но регулярно шлёт байты, никогда его не нарушит, и запрос может длиться бесконечно. Нужен общий дедлайн на весь запрос.

Как связаны idle timeout пула клиента и keep-alive timeout сервера?

Клиентский должен быть меньше. Иначе есть окно, когда сервер уже закрыл соединение, а клиент берёт его из пула и получает reset или пустой ответ.

Почему 3 ретрая — это может быть 81 запрос?

Если повторяет каждый уровень цепочки из четырёх сервисов, число попыток перемножается: 3 × 3 × 3 × 3. Под нагрузкой это превращает частичную деградацию в полный отказ. Ретраи должны быть на одном уровне (обычно ближе к клиенту) с бюджетом.

Сервис делает 2 000 запросов в секунду к партнёрскому API без пула. Какие проблемы вы ожидаете?

На каждый запрос — TCP и TLS рукопожатия (лишние 2 RTT и CPU), медленный старт, TIME_WAIT на 60 с: 2 000 × 60 = 120 000 занятых портов при ~28 000 эфемерных → исчерпание портов и ошибки подключения. Плюс нагрузка на NAT-шлюз. Решение — пул с keep-alive.

Почему в Reactor Netty нельзя вызывать JDBC в обработчике запроса?

Обработчик выполняется в потоке event loop, который обслуживает тысячи соединений. Блокирующий вызов останавливает их все. Блокирующий код выносится на Schedulers.boundedElastic() или используется неблокирующий драйвер (R2DBC); альтернатива — MVC на виртуальных потоках.
