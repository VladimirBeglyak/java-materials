TLS и PKI

TLS превращает TCP-соединение в защищённый канал: никто по пути не прочитает и не изменит данные, а клиент уверен, что говорит именно с bank.by. Разбираем рукопожатие TLS 1.3, цепочку доверия сертификатов и ошибки, которые чаще всего видит Java-разработчик.

9.1Три гарантии и инструменты для них

ГарантияМеханизмПримеры
Конфиденциальностьсимметричное шифрование общим ключом сессии (быстро)AES-128/256-GCM, ChaCha20-Poly1305
ЦелостностьAEAD: шифр сразу проверяет, что данные не измененыGCM, Poly1305
Аутентификациясертификат + цифровая подпись приватным ключом сервераECDSA, RSA, Ed25519
Общий ключ без передачи ключаобмен Диффи–Хеллмана на эллиптических кривых, эфемерные ключиECDHE (X25519), гибридный X25519+ML-KEM (постквантовый)

Forward secrecy: ключи сессии получены из эфемерных ключей ECDHE, которые уничтожаются после рукопожатия. Даже если позже украдут приватный ключ сервера, записанный ранее трафик не расшифровать. В TLS 1.3 это обязательно; старый обмен ключами RSA (без FS) удалён.

9.2Рукопожатие TLS 1.3

0-RTT и повторное воспроизведение Ранние данные 0-RTT злоумышленник может записать и отправить повторно — у них нет защиты от replay. Поэтому 0-RTT допустим только для идемпотентных запросов (GET без побочных эффектов). Платёжный POST в 0-RTT — уязвимость. CDN обычно ставят заголовок Early-Data: 1, а сервер может ответить 425 Too Early.

9.3Сертификаты и цепочка доверия

  • Let's Encrypt и ACME: бесплатные сертификаты на 90 дней с автоматическим продлением. Индустрия идёт к ещё более коротким срокам — автоматизация ротации обязательна.
  • Wildcard *.bank.by покрывает один уровень поддоменов (api.bank.by, но не a.b.bank.by).
  • Certificate Transparency: все публичные сертификаты попадают в открытые журналы — можно мониторить выпуск сертификатов на свой домен (crt.sh).

9.4SNI, ALPN, mTLS, терминация

SNI

Имя сайта в ClientHello — чтобы один IP обслуживал много доменов с разными сертификатами. Передаётся открыто (по нему работают блокировки); ECH (Encrypted Client Hello) его шифрует.

ALPN

Согласование прикладного протокола в рукопожатии без лишнего RTT: h2, http/1.1. Без ALPN HTTP/2 по TLS не включится.

mTLS

Сервер тоже запрашивает сертификат клиента. Стандарт для межсервисного взаимодействия (service mesh, Istio/Linkerd), API банковских партнёров и open banking. Удостоверение сервиса — сертификат, а не IP.

Где завершать TLS

На балансировщике (проще, L7-маршрутизация, WAF) — тогда до бэкенда трафик открыт или шифруется заново. End-to-end / passthrough — для строгих требований (PCI DSS). Во внутренней сети zero-trust предполагает шифрование везде.

9.5TLS в Java

ПонятиеЧто это
KeyStoreсвои приватные ключи и сертификаты (сервер; клиент при mTLS). Формат PKCS12 (.p12), JKS устарел.
TrustStoreкому доверяем: корневые CA. По умолчанию $JAVA_HOME/lib/security/cacerts. Корпоративный CA добавляется сюда или в свой truststore.
SSLContextсвязывает KeyManager и TrustManager; передаётся в HttpClient.newBuilder().sslContext(...), Netty, драйверы БД.
KeyStore trust = KeyStore.getInstance("PKCS12");
try (InputStream in = Files.newInputStream(Path.of("/etc/certs/truststore.p12"))) {
    trust.load(in, trustPassword);
}
TrustManagerFactory tmf = TrustManagerFactory.getInstance(TrustManagerFactory.getDefaultAlgorithm());
tmf.init(trust);

KeyStore identity = KeyStore.getInstance("PKCS12");
try (InputStream in = Files.newInputStream(Path.of("/etc/certs/client.p12"))) {
    identity.load(in, keyPassword);
}
KeyManagerFactory kmf = KeyManagerFactory.getInstance(KeyManagerFactory.getDefaultAlgorithm());
kmf.init(identity, keyPassword);

SSLContext ctx = SSLContext.getInstance("TLSv1.3");
ctx.init(kmf.getKeyManagers(), tmf.getTrustManagers(), null);

HttpClient client = HttpClient.newBuilder()
        .sslContext(ctx)
        .connectTimeout(Duration.ofSeconds(2))
        .build();
ОшибкаПричина
PKIX path building failed: unable to find valid certification pathцепочка не доходит до доверенного корня: самоподписанный/корпоративный CA не в truststore или сервер не прислал промежуточный сертификат
No subject alternative names matching IP address / nameподключаетесь по IP или другому имени, чем в SAN
CertificateExpiredExceptionпросроченный сертификат — нужен мониторинг сроков
handshake_failure / protocol_versionнет общих версий/шифров; mTLS — сервер не получил клиентский сертификат
Никогда «Доверять всем» (TrustManager с пустыми проверками, HostnameVerifier, всегда возвращающий true) — это отключение аутентификации: любой в сети может выдать себя за сервер. Правильное решение ошибки PKIX — добавить нужный CA в truststore. Отладка: -Djavax.net.debug=ssl:handshake.

9.7Интерактив: рукопожатие TLS 1.3 и что видит наблюдатель

Симулятор: от ClientHello до зашифрованных данных
Клиент знает
свой эфемерный ключ x, X = g^xобщий секрет g^xyсервер подлинный
Сервер знает
закрытый ключ сертификатасвой эфемерный ключ y, Y = g^yобщий секрет g^xy
Наблюдатель в сети видит
IP-адреса, порт 443SNI: api.shop.ruXYдальше — только шифротекст и размеры записей

ClientHello (открытым текстом)

Клиент сразу отправляет свою половину обмена ключами (X25519) — не дожидаясь выбора сервера. Это и сокращает рукопожатие до одного RTT. Расширение SNI называет хост — по нему сервер выберет сертификат, а балансировщик — бэкенд. SNI не зашифрован (ECH решает это, но пока не везде).

ServerHello: обмен Диффи — Хеллмана завершён

Сервер выбирает шифр и присылает Y. Обе стороны вычисляют общий секрет: клиент — Y^x, сервер — X^y. Наблюдатель видел X и Y, но получить g^xy из них не может (задача дискретного логарифма). Ключи эфемерные: утечка закрытого ключа сертификата в будущем не раскроет записанный сегодня трафик — forward secrecy.

Всё остальное рукопожатие зашифровано

Из общего секрета через HKDF выводятся ключи рукопожатия. Сертификат сервера идёт уже под шифром — наблюдатель не видит даже его (в TLS 1.2 видел).

Клиент проверяет подлинность

  1. Цепочка подписей ведёт к корневому сертификату из хранилища доверенных (truststore).
  2. Имя хоста совпадает с subjectAltName, срок действия не истёк.
  3. CertificateVerify — подпись всего рукопожатия закрытым ключом сервера: доказывает, что собеседник владеет ключом, а не просто переслал чужой сертификат.

Ошибка на любом шаге — SSLHandshakeException: PKIX path building failed / No subject alternative names matching.

Finished и первые данные

MAC от всей переписки подтверждает, что рукопожатие никто не изменил (например, не убрал сильные шифры из списка). Клиент отправляет запрос приложения в том же пакете. Итог: 1 RTT на TLS (в TLS 1.2 было 2). При возобновлении сессии по PSK возможен 0-RTT — данные в первом же пакете, но с риском повторного воспроизведения (только для идемпотентных запросов).

Защищённый канал

Симметричный AEAD-шифр даёт конфиденциальность и целостность. Наблюдатель видит адреса, время, размеры и SNI — этого достаточно, чтобы понять, куда вы ходите, но не что передаёте.

9.8Самопроверка

Что даёт forward secrecy?

  • Ускоряет рукопожатие
  • Компрометация долговременного закрытого ключа сервера не позволяет расшифровать ранее записанный трафик
  • Скрывает IP-адрес клиента
  • Заменяет сертификаты
Сеансовые ключи получаются из эфемерного обмена Диффи — Хеллмана и нигде не сохраняются. В TLS 1.3 это обязательно.

Java-клиент падает с «PKIX path building failed». Что это значит?

  • Сервер недоступен
  • Истёк таймаут
  • Не удалось построить цепочку от сертификата сервера до доверенного корня: в truststore нет нужного CA или сервер не прислал промежуточный сертификат
  • Неверный пароль
Проверьте цепочку: openssl s_client -connect host:443 -showcerts. Отключать проверку сертификатов нельзя — это снимает защиту от подмены.

Чем mTLS отличается от обычного TLS?

  • Клиент тоже предъявляет сертификат, и сервер проверяет его — взаимная аутентификация
  • Используется два шифра
  • Соединение устанавливается дважды
  • Не используются сертификаты
Типично для связи сервис — сервис и service mesh: идентичность сервиса подтверждается сертификатом.
Почему TLS 1.3 требует 1 RTT, а TLS 1.2 — 2?

В 1.3 клиент сразу шлёт key_share для предполагаемой группы, сервер в первом же ответе завершает обмен ключами и отправляет сертификат и Finished в зашифрованном виде. В 1.2 сначала согласовывались параметры (Hello), затем отдельным обменом — ключи.

Что именно доказывает сертификат, а что — CertificateVerify?

Сертификат (через подпись CA) связывает имя хоста с публичным ключом. CertificateVerify — подпись хэша текущего рукопожатия приватным ключом — доказывает, что собеседник владеет приватным ключом этого сертификата именно сейчас.

Что такое forward secrecy и как её обеспечивает TLS 1.3?

Компрометация долгосрочного ключа сервера не раскрывает прошлые сессии. Ключи сессий выводятся из эфемерного ECDHE, который не сохраняется. Приватный ключ сертификата используется только для подписи, а не для шифрования ключа сессии.

Java-клиент падает с PKIX path building failed на внутреннем сервисе. Ваши действия?

Посмотреть цепочку (openssl s_client -showcerts): присылает ли сервер промежуточный сертификат, кем выпущен. Если корпоративным CA — добавить его корень в truststore приложения (или в образ), если не хватает промежуточного — исправить конфигурацию сервера. Не отключать проверку.

Почему 0-RTT опасен для POST /payments?

Ранние данные не защищены от повторного воспроизведения: перехвативший их может отправить тот же запрос ещё раз, и сервер его выполнит. Допустимо только для идемпотентных операций; для платежей — ключ идемпотентности и отказ от 0-RTT.
