HTTP: семантика для бэкенда

HTTP (HyperText Transfer Protocol — «протокол передачи гипертекста») — язык, на котором браузеры и программы разговаривают с серверами. Его семантика (смысл: методы, коды ответов, заголовки, кэширование) одинакова во всех версиях — HTTP/1.1, HTTP/2 и HTTP/3 — и описана в стандартах RFC 9110 и RFC 9111. Здесь — всё, что нужно для проектирования API, работы с прокси и CDN и безопасности в браузере.

Что нужно знать заранее TCP-соединения из главы 06 и TLS из главы 09: HTTP-сообщения едут внутри них. API (Application Programming Interface) — набор адресов, по которым программы обращаются к сервису. Ресурс — то, к чему обращаются по адресу: платёж, пользователь, курс валют. Адрес ресурса — URI (Uniform Resource Identifier, «единый идентификатор ресурса»), его частный случай — знакомый URL. Сокращения — в словарике.

10.1Сообщение

HTTP-обмен — это всегда пара: клиент отправляет запрос (request), сервер возвращает ответ (response). В HTTP/1.1 оба — обычный текст:

POST /v1/payments HTTP/1.1
Host: api.bank.by
Content-Type: application/json
Content-Length: 58
Authorization: Bearer eyJhbGciOi...
Idempotency-Key: 6f1c2a9e-3b7d-4c2e
traceparent: 00-4bf92f3577b34da6-00f067aa0ba902b7-01

{"from":"BY12...","to":"BY98...","amount":"150.00"}
HTTP/1.1 201 Created
Content-Type: application/json
Location: /v1/payments/8812
Cache-Control: no-store
Content-Length: 41

{"id":8812,"status":"PROCESSING"}

Устройство сообщения:

  • Стартовая строка. В запросе — метод (что сделать: POST — «создать»), путь (/v1/payments) и версия. В ответе — версия, код статуса (201) и его название (Created — «создано»).
  • Заголовки (headers) — строки «Имя: значение» со служебной информацией. Затем пустая строка.
  • Тело (body) — сами данные. Здесь в формате JSON (JavaScript Object Notation — популярный текстовый формат «ключ: значение»).

Что значат заголовки из примера:

Host
к какому сайту запрос. Обязателен: по нему один IP-адрес обслуживает много сайтов (virtual hosting, «виртуальный хостинг»)
Content-Type
формат тела: application/json
Content-Length
длина тела в байтах
Authorization: Bearer …
«пропуск» клиента. Bearer token («токен предъявителя») — строка, выданная при входе: кто её предъявил, тот и считается владельцем. Строка на eyJ — это обычно JWT (JSON Web Token): подписанный JSON с данными о пользователе
Idempotency-Key
«ключ идемпотентности» — уникальный номер операции, чтобы сервер распознал повтор (раздел 10.2)
traceparent
номер «трассы» запроса для распределённого трейсинга (раздел 10.7)
Location
адрес созданного ресурса
Cache-Control: no-store
«не сохранять в кэше» (раздел 10.4)

Длину тела можно задать двумя способами: Content-Length или, если длина заранее неизвестна, Transfer-Encoding: chunked («передача кусками»: тело идёт порциями, перед каждой — её размер). Если цепочка прокси по-разному понимает, где кончается одно сообщение и начинается другое, злоумышленник может «протащить» внутрь чужой запрос — атака HTTP request smuggling («контрабанда запросов»).

Главное Запрос — метод + путь + заголовки + тело; ответ — код статуса + заголовки + тело. Заголовки несут служебное: кому, в каком формате, чей пропуск, можно ли кэшировать.

10.2Методы и идемпотентность

Метод говорит серверу, что сделать с ресурсом. У методов есть три важных свойства: безопасный (safe — ничего не меняет на сервере), идемпотентный (повтор даёт тот же результат, что и один вызов) и кэшируемый (ответ можно сохранить и переиспользовать).

МетодБезопасныйИдемпотентныйКэшируемыйСмысл
GET / HEAD✔✔✔получить ресурс («get»); HEAD — только заголовки, без тела
PUT✘✔✘«положить»: заменить ресурс целиком по известному адресу
DELETE✘✔✘удалить
POST✘✘редко«отправить»: создать ресурс или выполнить действие
PATCH✘не гарантирован✘«заплатка»: частичное изменение
OPTIONS✔✔✘«варианты»: что можно делать с ресурсом; используется в CORS (раздел 10.6)

Почему идемпотентность так важна. Это вопрос сети, а не красоты кода. Клиент отправил запрос и получил таймаут. Он не знает, что случилось: запрос не дошёл? дошёл, но сервер упал? сервер всё сделал, но потерялся ответ? Повторить безопасно только идемпотентный запрос: «удалить платёж 8812» дважды — то же, что один раз. А «создать платёж» дважды — два платежа. Прокси, балансировщики и HTTP-клиенты иногда повторяют запросы автоматически.

Для POST, создающих платёж, придумали ключ идемпотентности: клиент генерирует уникальный номер операции и отправляет в заголовке Idempotency-Key. Сервер сохраняет результат по этому ключу и на повтор с тем же ключом возвращает сохранённый ответ, а не создаёт второй платёж.

Главное GET, PUT, DELETE идемпотентны — их можно повторять. POST — нет, поэтому для важных операций нужен Idempotency-Key.

10.3Коды ответа

Код статуса — трёхзначное число. Первая цифра — класс: 2xx — успех, 3xx — перенаправление (ресурс в другом месте), 4xx — ошибка клиента (неправильный запрос), 5xx — ошибка сервера.

КодКогдаКто обычно генерирует
200 OK / 201 Created / 202 Accepted / 204 No Contentуспех / ресурс создан (адрес в Location) / принят и будет обработан позже / успех без телаприложение
301 / 308ресурс переехал навсегда (308 сохраняет метод и тело при переходе)приложение, прокси
302 / 307временно в другом месте (307 сохраняет метод)приложение

400 Bad Request / 422 Unprocessable Contentзапрос испорчен (например, сломанный JSON) / формально верный, но не прошёл проверку по смыслуприложение
401 Unauthorized / 403 Forbiddenне понятно, кто вы — нужен вход (с заголовком WWW-Authenticate, как войти) / понятно, кто вы, но вам нельзяприложение

503 Service Unavailable«сервис недоступен»: нет здоровых серверов, перегрузка, техработыпрокси или приложение
504 Gateway Timeout«шлюз не дождался»: сервис не ответил за отведённое прокси времяпрокси или балансировщик
Совет при разборе аварий Получив 502 или 504, первым делом выясните, какой именно прокси его сгенерировал. Между пользователем и кодом их может быть несколько: CDN, ингресс (входной прокси кластера Kubernetes), sidecar («коляска» — прокси, работающий рядом с каждым сервисом в service mesh). У каждого свои таймауты, и они должны быть согласованы: внешний ждёт дольше внутреннего (глава 12).
Главное 2xx — успех, 3xx — иди туда, 4xx — ты ошибся, 5xx — мы ошиблись. 502 и 504 обычно создаёт прокси, а не ваш код.

10.4Кэширование

Задача. Курс валют меняется раз в минуту, а запрашивают его тысячи раз в секунду. Каждый раз ходить на сервер — дорого и медленно.

Решение — кэш: браузер, прокси или CDN сохраняют копию ответа и какое-то время отдают её сами. Что и сколько хранить, сервер сообщает заголовком Cache-Control («управление кэшем»). Кэши бывают частные (браузер одного пользователя) и общие (CDN, прокси — одна копия для многих пользователей).

Директива Cache-ControlСмысл
max-age=600ответ «свежий» 600 секунд для любых кэшей
s-maxage=60для общих кэшей (shared) — заменяет max-age
private / publicхранить только в браузере пользователя / можно и в общих кэшах
no-cacheхранить можно, но перед каждым использованием перепроверить у сервера. Название обманчиво: это не «не кэшировать»!
no-storeне хранить вообще — для персональных и финансовых данных
immutable«неизменяемый»: не перепроверять до истечения срока. Для файлов с хэшем в имени (app.3f9a1c.js): новая версия — новое имя
stale-while-revalidate=30«устаревшее, пока перепроверяешь»: 30 секунд после истечения можно отдавать старую копию, обновляя её в фоне

Как работает перепроверка. Вместе с ответом сервер присылает ETag (entity tag, «метка версии») — например, "v42". Когда срок свежести истёк, клиент спрашивает: «дай /rates, если версия уже не v42» (заголовок If-None-Match, «если не совпадает»). Если ничего не поменялось, сервер отвечает коротким 304 Not Modified без тела — экономия трафика. Такой запрос называется условным.

  • ETag + If-Match на PUT/PATCH — оптимистическая блокировка по HTTP. Клиент говорит: «измени, только если версия всё ещё v42». Если кто-то успел изменить ресурс после того, как вы его прочитали, сервер вернёт 412, и ваши изменения не затрут чужие. «Оптимистическая» — потому что мы не запрещаем другим менять ресурс заранее, а только проверяем в момент записи.
  • Vary («различается по»): от каких заголовков запроса зависит ответ, например Vary: Accept-Encoding, Accept-Language — от сжатия и языка. Если забыть Vary, CDN может отдать пользователю ответ, сохранённый для другого (на другом языке или в другом формате).
  • Опасность: персональный ответ с public или вообще без Cache-Control может закэшироваться на CDN и уйти другим людям. Для API с авторизацией по умолчанию ставьте no-store или private.
Главное Cache-Control говорит кэшам, можно ли хранить ответ и сколько. no-cache — «храни, но перепроверяй», no-store — «не храни». ETag позволяет перепроверять дёшево (304) и защищает от затирания чужих изменений.

10.5Cookies

Cookie («печенька») — небольшая запись, которую сервер просит браузер сохранить и затем присылать с каждым запросом к этому сайту. Так сайт «помнит», что вы вошли: в cookie лежит номер вашей сессии (сеанса работы). Сервер устанавливает cookie заголовком Set-Cookie:

Set-Cookie: SESSION=8f2c...; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=1800

Здесь SESSION=8f2c... — имя и значение, Path=/ — для всех путей сайта, Max-Age=1800 — хранить 1800 секунд (30 минут). Остальные атрибуты защищают от атак:

АтрибутЗащищает от
Secureотправки по незашифрованному HTTP — только по HTTPS
HttpOnlyкражи через JavaScript: скрипты на странице cookie не видят. Важно при XSS (Cross-Site Scripting, «межсайтовый скриптинг»: злоумышленник внедрил свой скрипт на вашу страницу)
SameSite=Lax / StrictCSRF (Cross-Site Request Forgery, «подделка межсайтового запроса»): чужой сайт заставляет ваш браузер отправить запрос к банку, а браузер прикладывает вашу cookie. С SameSite cookie не отправляется в запросах POST с чужих сайтов (Strict — вообще ни в каких переходах с чужих сайтов). SameSite=None требует Secure. Если атрибута нет, современные браузеры считают его равным Lax
Domainбез него cookie действует только для точного хоста; с Domain=bank.by — для всех поддоменов, что обычно шире, чем нужно
Главное Cookie — запись, которую браузер присылает с каждым запросом. Для cookie сессии всегда ставьте Secure, HttpOnly и SameSite.

10.6CORS

Задача. Вы открыли сайт злоумышленника. Его JavaScript отправляет запрос к вашему банку — браузер приложит ваши cookies. Если скрипт сможет прочитать ответ, он узнает ваш баланс.

Решение браузеров — политика одного источника (same-origin policy): JavaScript со страницы может читать ответы только от того же origin («источника» — сочетания схемы, хоста и порта). Страница https://app.bank.by и API https://api.bank.by — разные origin, хост ведь разный.

Но иногда это нужно легально: ваш же фронтенд на app.bank.by обращается к вашему API на api.bank.by. Для этого есть CORS (Cross-Origin Resource Sharing — «совместное использование ресурсов между разными источниками»): сервер сам сообщает браузеру, каким origin разрешено читать его ответы.

Для «непростых» запросов (например, POST с JSON или с заголовком Authorization) браузер сначала отправляет предварительный запрос — preflight: OPTIONS с вопросом «можно ли с origin app.bank.by сделать POST с заголовком authorization?». Сервер отвечает заголовками Access-Control-Allow-* («разрешить доступ»): какие origin, методы и заголовки разрешены, и Max-Age — сколько секунд браузер может помнить это разрешение, не спрашивая снова. Только после этого уходит настоящий запрос.

CORS — не защита сервера CORS ограничивает только браузер. curl, Postman (программа для ручной отправки HTTP-запросов) и другие серверы его не проверяют. Он защищает пользователя от чужого сайта, который хочет читать ответы от его имени. Важные правила: Access-Control-Allow-Origin: * («всем») нельзя совмещать с Allow-Credentials: true («с cookies»); а возвращать в ответе любой присланный Origin вместе с credentials — уязвимость: так вы разрешаете читать ответы любому сайту.
Главное Браузер не даёт скрипту читать ответы с чужого origin. CORS — способ сервера разрешить это конкретным сайтам. От curl и ботов CORS не защищает.

10.7Сжатие, диапазоны, согласование

  • Сжатие. Клиент сообщает, какие алгоритмы понимает: Accept-Encoding: gzip, br, zstd (gzip — классический; br — Brotli от Google; zstd — Zstandard от Meta). Сервер отвечает Content-Encoding: br. JSON сжимается в 5–10 раз. Не сжимайте мелкие ответы и уже сжатые форматы (картинки, zip-архивы) — выигрыша не будет.
  • Диапазоны. Range: bytes=1000000- — «дай с миллионного байта до конца». Ответ 206 Partial Content («частичное содержимое»). Так работает докачка файлов и перемотка видео.
  • Согласование содержимого (content negotiation): клиент сообщает, что хочет получить — Accept: application/json (формат), Accept-Language: ru (язык), и сервер выбирает подходящий вариант.
  • Корреляция запросов. Один клик пользователя может пройти через десяток сервисов. Чтобы потом собрать в логах всю цепочку, каждому запросу дают номер и передают его дальше в заголовках: traceparent (стандарт W3C Trace Context; W3C — World Wide Web Consortium, организация, утверждающая веб-стандарты) или X-Request-Id. Так строится распределённый трейсинг (distributed tracing) — картина того, где запрос провёл время.
Главное Сжатие — Accept-Encoding / Content-Encoding, докачка — Range / 206, выбор формата и языка — Accept-*. traceparent связывает запрос через все сервисы.

10.8Интерактив: что сделает кэш

Выберите заголовки ответа и ситуацию — симулятор покажет, сохранит ли ответ браузер и CDN и что произойдёт при следующем запросе.

Симулятор HTTP-кэширования
Браузер пользователя
CDN / общий прокси
Самая дорогая ошибка кэширования Ответ с персональными данными (/api/me, страница с именем пользователя) без private или no-store за CDN: общий кэш отдаст страницу одного пользователя другому. Для всего, что зависит от авторизации, — Cache-Control: private или no-store, плюс Vary по заголовкам, которые влияют на ответ.

10.10Самопроверка

Какие методы HTTP идемпотентны?

  • Только GET
  • GET и POST
  • GET, HEAD, PUT, DELETE, OPTIONS — повтор не меняет результат; POST и PATCH — не обязаны
  • Все
Идемпотентные запросы клиент и прокси могут безопасно повторять при обрыве. Для POST нужен ключ идемпотентности.

Чем 401 отличается от 403?

  • Ничем
  • 401 — сервер не знает, кто вы (нужно войти); 403 — знает, но вам нельзя
  • 401 — ошибка сервера
  • 403 — ресурс не найден
Названия исторически путают: 401 «Unauthorized» на деле означает «не аутентифицирован».

Браузер перед запросом PUT на другой домен отправил OPTIONS. Что это?

  • CORS preflight: браузер спрашивает сервер, разрешён ли такой запрос с этого origin
  • Проверка доступности сервера
  • Ошибка браузера
  • Запрос сертификата
curl и серверные клиенты preflight не делают — отсюда «в Postman работает, в браузере нет».

Что значит Cache-Control: no-cache?

  • Нельзя хранить вообще
  • Хранить только в CDN
  • Кэш выключен на сервере
  • Хранить можно, но перед использованием надо перепроверить у сервера
«Не хранить вообще» — это no-store.

Пользователь получил 504 Gateway Timeout. Кто, скорее всего, сгенерировал ответ?

  • Код вашего контроллера
  • Прокси или балансировщик, не дождавшийся ответа сервиса
  • Браузер
  • DNS-сервер
Ищите, какой из прокси на пути (CDN, ингресс, sidecar) и с каким таймаутом.

Какой атрибут cookie не даёт скриптам на странице её прочитать?

  • Secure
  • SameSite
  • HttpOnly
  • Domain
Secure — только HTTPS, SameSite — против CSRF, HttpOnly — против кражи через JavaScript.

Вопросы для разговора (с собеседований)

Клиент отправил POST /payments и получил таймаут. Можно ли повторить?

Без ключа идемпотентности — нельзя: запрос мог выполниться, и повтор создаст второй платёж. С Idempotency-Key сервер сохранит результат первого выполнения и вернёт его на повтор. Повторять нужно с тем же ключом и с экспоненциальной паузой.

Чем no-cache отличается от no-store?

no-cache — сохранять можно, но каждый раз перепроверять у сервера (условный запрос, часто 304). no-store — не сохранять нигде и никогда.

Чем 502 отличается от 504?

Оба генерирует прокси. 502 — сервис за ним ответил некорректно или соединение не удалось или оборвалось (сервис упал, отказал в соединении, закрыл keep-alive-соединение). 504 — сервис не ответил вовремя, по таймауту прокси.

Как реализовать оптимистическую блокировку через HTTP?

GET возвращает ETag — версию ресурса. Клиент шлёт PUT или PATCH с If-Match: "версия". Если версия на сервере изменилась — 412 Precondition Failed, клиент перечитывает и повторяет. Это аналог колонки version в базе данных.

Защищает ли CORS API от запросов злоумышленника?

Нет. Это политика браузера, защищающая пользователя от чтения ответов чужим сайтом. Прямые запросы (curl, скрипты, другие серверы) CORS не проверяют. API защищают аутентификация, авторизация и лимиты.
