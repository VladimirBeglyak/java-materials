HTTP: семантика для бэкенда

Семантика HTTP (RFC 9110) не зависит от версии протокола: методы, коды, заголовки и кэширование одинаковы в HTTP/1.1, /2 и /3. Здесь — то, что нужно для проектирования API, работы с прокси и CDN и безопасности в браузере.

~4 часаRFC 9110, 9111интерактивтест

10.1Сообщение

POST /v1/payments HTTP/1.1
Host: api.bank.by
Content-Type: application/json
Content-Length: 58
Authorization: Bearer eyJhbGciOi...
Idempotency-Key: 6f1c2a9e-3b7d-4c2e
traceparent: 00-4bf92f3577b34da6-00f067aa0ba902b7-01

{"from":"BY12...","to":"BY98...","amount":"150.00"}
HTTP/1.1 201 Created
Content-Type: application/json
Location: /v1/payments/8812
Cache-Control: no-store
Content-Length: 41

{"id":8812,"status":"PROCESSING"}

Host обязателен: по нему один IP обслуживает много сайтов (virtual hosting). Длина тела задаётся Content-Length или кодированием Transfer-Encoding: chunked в HTTP/1.1 (поток неизвестной длины). Расхождение между ними на цепочке прокси — основа атак HTTP request smuggling.

10.2Методы и идемпотентность

МетодSafeИдемпотентныйКэшируемыйСмысл
GET / HEAD✔✔✔получить представление (HEAD — только заголовки)
PUT✘✔✘заменить ресурс целиком по известному URI
DELETE✘✔✘удалить
POST✘✘редкосоздать / выполнить действие
PATCH✘не гарантирован✘частичное изменение
OPTIONS✔✔✘возможности ресурса, CORS preflight

Идемпотентность — повтор запроса даёт тот же эффект на сервере, что и один запрос. Это вопрос сети, а не стиля: при таймауте клиент не знает, дошёл ли запрос. Повторять безопасно только идемпотентные запросы — так делают прокси, балансировщики и HTTP-клиенты (иногда автоматически!). Для POST, создающих платёж, нужен ключ идемпотентности: сервер сохраняет результат по Idempotency-Key и на повтор возвращает его же, а не создаёт второй платёж.

10.4Кэширование

Директива Cache-ControlСмысл
max-age=600свежий 600 с для любых кэшей
s-maxage=60для общих кэшей (CDN, прокси) — переопределяет max-age
private / publicтолько браузер пользователя / можно хранить в общих кэшах
no-cacheхранить можно, но перед использованием проверить на сервере (не «не кэшировать»!)
no-storeне хранить вообще — для персональных и финансовых данных
immutableне перепроверять до истечения: для файлов с хэшем в имени (app.3f9a1c.js)
stale-while-revalidate=30отдать устаревшее и обновить в фоне
  • ETag + If-None-Match — экономия трафика. ETag + If-Match на PUT/PATCH — оптимистическая блокировка по HTTP: если ресурс изменили с момента чтения, сервер вернёт 412.
  • Vary: от каких заголовков запроса зависит ответ (Vary: Accept-Encoding, Accept-Language). Забытый Vary — CDN отдаёт одному пользователю ответ, закэшированный для другого.
  • Опасность: персональный ответ с public или без Cache-Control может закэшироваться на CDN и утечь другим пользователям. Для API с авторизацией по умолчанию — no-store или private.

10.6CORS

Same-origin policy: JavaScript со страницы https://app.bank.by не может читать ответы от другого origin (схема + хост + порт), например https://api.bank.by. CORS — способ серверу разрешить это.

CORS — не защита сервера CORS ограничивает только браузер. curl, Postman и бэкенды его игнорируют. Он защищает пользователя от чужого сайта, который хочет читать ответы от его имени. Access-Control-Allow-Origin: * нельзя совмещать с Allow-Credentials: true; отражать любой Origin в ответе вместе с credentials — уязвимость.

10.7Сжатие, диапазоны, согласование

  • Сжатие: Accept-Encoding: gzip, br, zstd → Content-Encoding: br. JSON сжимается в 5–10 раз. Не сжимайте мелкие ответы и уже сжатые форматы (изображения, zip).
  • Range: Range: bytes=1000000- → 206 Partial Content — докачка, видео.
  • Content negotiation: Accept: application/json, Accept-Language.
  • Корреляция: traceparent (W3C Trace Context) и X-Request-Id прокидываются через все сервисы — так собираются распределённые трейсы.

10.8Интерактив: что сделает кэш

Симулятор HTTP-кэширования

Самая дорогая ошибка кэширования Ответ с персональными данными (/api/me, страница с именем пользователя) без private или no-store за CDN: общий кэш отдаст страницу одного пользователя другому. Для всего, что зависит от авторизации, — Cache-Control: private или no-store и Vary по заголовкам, влияющим на ответ.

10.9Самопроверка

Какие методы HTTP идемпотентны?

  • Только GET
  • GET и POST
  • GET, HEAD, PUT, DELETE, OPTIONS — повтор не меняет результат; POST и PATCH — не обязаны
  • Все
Идемпотентные запросы клиент и прокси могут безопасно повторять при обрыве. Для POST нужен ключ идемпотентности.

Чем 401 отличается от 403?

  • Ничем
  • 401 — клиент не аутентифицирован (нужны учётные данные); 403 — аутентифицирован, но доступ запрещён
  • 401 — ошибка сервера
  • 403 — ресурс не найден
Названия исторически путают: 401 «Unauthorized» на деле означает «не аутентифицирован».

Браузер перед запросом PUT на другой домен отправил OPTIONS. Что это?

  • CORS preflight: браузер спрашивает сервер, разрешён ли такой запрос с этого origin
  • Проверка доступности сервера
  • Ошибка браузера
  • Запрос сертификата
CORS — защита пользователя, реализованная в браузере. curl и серверные клиенты её не выполняют, поэтому «в Postman работает, в браузере нет».
Клиент отправил POST /payments и получил таймаут. Можно ли повторить?

Без ключа идемпотентности — нельзя: запрос мог быть выполнен, и повтор создаст второй платёж. С Idempotency-Key сервер сохранит результат первого выполнения и вернёт его на повтор. Повторять нужно с тем же ключом и с экспоненциальной паузой.

Чем no-cache отличается от no-store?

no-cache — сохранять можно, но каждый раз перепроверять у сервера (условный запрос, часто 304). no-store — не сохранять нигде и никогда.

Чем 502 отличается от 504?

Оба генерирует прокси. 502 — бэкенд ответил некорректно или соединение не удалось/сброшено (бэкенд упал, отказал в соединении, закрыл keep-alive соединение). 504 — бэкенд не ответил вовремя по таймауту прокси.

Как реализовать оптимистическую блокировку через HTTP?

GET возвращает ETag (версию ресурса). Клиент шлёт PUT/PATCH с If-Match: "версия". Если версия на сервере изменилась — 412 Precondition Failed, клиент перечитывает и повторяет. Это аналог version-колонки в БД.

Защищает ли CORS API от запросов злоумышленника?

Нет. Это политика браузера, защищающая пользователя от чтения ответов чужим сайтом. Прямые запросы (curl, скрипты, бэкенды) CORS не проверяют. Защита API — аутентификация, авторизация, лимиты.
