SSH, почта, время, VPN: протоколы вокруг сервиса

HTTP — не единственный протокол в жизни бэкенд-разработчика. Вы каждый день заходите на серверы по SSH и пробрасываете порты; ваш сервис отправляет письма, которые попадают в спам; токены «истекают» из-за разъехавшихся часов; доступ к базе идёт через VPN. Эта глава — рабочий минимум по каждому из этих протоколов: как устроен, что настраивать и что ломается.

18.1SSH

SSH (Secure Shell — «безопасная оболочка») — способ зайти на удалённый сервер и работать в его терминале так, будто сидишь за ним. Оболочка (shell) — программа, принимающая команды (bash, zsh). SSH работает поверх TCP на порту 22 и создаёт зашифрованный канал, внутри которого по одному соединению идут несколько каналов: интерактивная оболочка, выполнение одной команды, передача файлов (SFTP — SSH File Transfer Protocol), проброс TCP-портов.

Подключение проходит в три шага:

  1. Обмен ключами — Диффи — Хеллман на эллиптической кривой (глава 09): стороны получают общий секрет, из которого выводятся ключи шифрования.
  2. Проверка сервера. Сервер подписывает обмен своим ключом хоста (host key). Клиент сверяет этот ключ со списком известных серверов ~/.ssh/known_hosts (~ — домашняя папка пользователя). При первом подключении появляется вопрос «The authenticity of host can't be established» («подлинность хоста не установлена»): вы принимаете ключ на веру. Этот подход называется TOFU (Trust On First Use — «доверие при первом использовании»). Сообщение «REMOTE HOST IDENTIFICATION HAS CHANGED» («ключ удалённого хоста изменился») означает: либо сервер переустановили, либо между вами кто-то стоит (атака «человек посередине»).
  3. Проверка пользователя. Вместо пароля обычно используют пару ключей. Клиент подписывает данные сеанса своим закрытым ключом, а сервер проверяет подпись открытым ключом, заранее записанным в ~/.ssh/authorized_keys («разрешённые ключи»). Закрытый ключ никогда не покидает ваш компьютер.

Чтобы не писать длинные команды, настройки серверов сохраняют в файле ~/.ssh/config. Бастион (bastion, jump host — «хост-трамплин») — единственный сервер, открытый для SSH снаружи; на остальные заходят только через него.

Host bastion
    HostName bastion.shop.ru
    User deploy
    IdentityFile ~/.ssh/id_ed25519      # какой закрытый ключ использовать
Host db-prod
    HostName 10.2.3.40              # адрес во внутренней сети
    ProxyJump bastion               # зайти через бастион одной командой: ssh db-prod
    LocalForward 15432 localhost:5432   # проброс порта базы на ваш компьютер
    ServerAliveInterval 30          # keepalive каждые 30 с: соединение не умрёт на NAT

Проброс портов (SSH-туннели)

SSH умеет доставлять через себя любые TCP-соединения. Три вида:

  • Локальный (ssh -L локальный_порт:цель:порт сервер): порт открывается на вашем компьютере, а соединение к цели устанавливает SSH-сервер. Так достают до базы во внутренней сети: psql -h localhost -p 15432 попадёт на базу за бастионом.
  • Обратный (ssh -R): порт открывается на сервере, а соединения ведут на ваш компьютер. Так показывают локальный сервис наружу.
  • Динамический (ssh -D): ваш компьютер становится прокси SOCKS (SOCKet Secure, протокол прокси для любых TCP-соединений), и всё, что идёт через этот прокси, выходит в сеть со стороны сервера.
Конструктор SSH-туннеля
Гигиена SSH Ключи типа Ed25519 (современный алгоритм подписи) с парольной фразой (passphrase — пароль, которым зашифрован сам файл ключа) и ssh-agent (программа, которая держит расшифрованный ключ в памяти, чтобы не вводить фразу каждый раз). Вход по паролю и вход под root (администратором) отключены: PasswordAuthentication no, PermitRootLogin no. Доступ — через бастион или VPN, а не с открытым в Интернет портом 22 на каждом сервере. Для больших парков серверов — короткоживущие SSH-сертификаты вместо ручной раздачи authorized_keys.
Главное SSH — зашифрованный удалённый терминал. Сервер проверяется по known_hosts, пользователь — по ключу в authorized_keys. Через SSH можно пробрасывать порты: -L — к себе, -R — на сервер, -D — SOCKS-прокси.

18.2Почта: почему письмо попало в спам

Путь письма от вашего сервиса до ящика пользователя:

Ваш сервисSMTP submission :587 + STARTTLS + логин
→
Почтовый сервис отправителяподписывает DKIM
→ DNS: MX получателя → SMTP :25 →
Сервер получателяпроверяет SPF, DKIM, DMARC, репутацию
→
ЯщикIMAP/веб
  • SMTP (Simple Mail Transfer Protocol — «простой протокол передачи почты») — протокол пересылки писем между серверами (порт 25) и отправки писем программами (submission, «подача», порт 587, с логином).
  • STARTTLS — команда «начать TLS»: соединение начинается открытым и переключается на шифрование.
  • Сервер получателя находится по DNS-записи MX его домена (глава 08).
  • Читают почту по IMAP (Internet Message Access Protocol — «протокол доступа к сообщениям») или через веб-интерфейс.

Проблема: SMTP 1982 года не проверяет отправителя — в поле From можно написать что угодно, хоть адрес банка. Три механизма на основе DNS это исправляют, и без них крупные почтовые сервисы ваши письма не примут или отправят в спам:

МеханизмЧто проверяетЗапись DNS
SPF (Sender Policy Framework — «политика отправителей»)разрешено ли этому IP отправлять почту от домена из служебного адреса письма (envelope from — «адрес на конверте», куда возвращаются отбойники; пользователь его обычно не видит)shop.ru TXT "v=spf1 include:_spf.mailprovider.com -all" — «разрешены серверы провайдера, остальным (-all) — нельзя»
DKIM (DomainKeys Identified Mail — «почта, опознанная по ключам домена»)цифровая подпись заголовков и текста письма ключом домена: письмо не изменили по дороге, и отправил его владелец ключаs1._domainkey.shop.ru TXT "v=DKIM1; k=rsa; p=MIIB…" — открытый ключ для проверки подписи
DMARC (Domain-based Message Authentication, Reporting and Conformance — «проверка, отчёты и соответствие на основе домена»)совпадает ли домен в видимом From с доменом, прошедшим SPF или DKIM (alignment, «выравнивание»), и что делать при провале_dmarc.shop.ru TXT "v=DMARC1; p=reject; rua=mailto:dmarc@shop.ru" — «отклонять (reject) не прошедшие, отчёты слать сюда (rua — адрес для сводных отчётов)»

Посмотрите, как сервер получателя проверяет письмо при разных настройках:

Симулятор проверки письма получателем

Письмо с видимым адресом From: orders@shop.ru.

Практика для сервиса: отправляйте письма через почтового провайдера (по его API или по SMTP на порт 587), а не напрямую со своих серверов; настройте DKIM со своим доменом; разделите транзакционные письма (подтверждения, коды, чеки) и рассылки по разным поддоменам, чтобы проблемы рассылок не роняли доставку кодов; обрабатывайте отбойники (bounce — «отскок», уведомления о недоставке) и жалобы на спам — отправка на несуществующие адреса быстро губит репутацию домена.

Главное SPF — какие серверы могут слать почту от домена, DKIM — подпись письма, DMARC — требует, чтобы проверки прошли именно для домена из From. Без всех трёх письма уходят в спам.

18.3Время: NTP и почему оно важно

Кварцевые часы сервера уходят на секунды в сутки. NTP (Network Time Protocol — «протокол сетевого времени», UDP-порт 123) периодически сверяет их с точными серверами времени. Хитрость в том, что ответ идёт по сети какое-то время, и это надо учесть. Клиент запоминает четыре момента: t1 — отправил запрос, t2 — сервер получил, t3 — сервер ответил, t4 — клиент получил ответ. Отсюда смещение часов:

смещение = ((t2 − t1) + (t3 − t4)) / 2

Формула вычитает время в пути, предполагая, что туда и обратно сигнал идёт одинаково долго.

Что ломается при неверных часахСимптом
TLS (глава 09)«certificate is not yet valid» («сертификат ещё не действует») или «has expired» («истёк») на исправном сертификате
JWT (JSON Web Token) и подписи запросов (например, AWS SigV4 — Signature Version 4, способ подписи запросов к Amazon)«token used before issued» («токен использован до выпуска»), «request time too skewed» («время запроса слишком расходится»). Поэтому при проверке полей exp (expiration — «истекает»), nbf (not before — «не раньше») и iat (issued at — «выпущен в») делают допуск (leeway) в несколько секунд
TOTP (Time-based One-Time Password — «одноразовый пароль на основе времени») — коды двухфакторной аутентификации из приложениякод «неверный» при расхождении больше 30 секунд
Kerberos (система входа в корпоративных сетях)отказ при расхождении больше 5 минут
Логи и трейсысобытия разных серверов в «невозможном» порядке: ответ раньше запроса
Распределённые системыправило «последняя запись побеждает» выбирает не ту запись; лизы (lease — «аренда» права на ресурс на время) и блокировки со сроком истекают не вовремя

Часы могут идти назад

При коррекции NTP системное время может скачком уйти назад. Поэтому длительности измеряют монотонными часами — они только растут и не корректируются (System.nanoTime() в Java), а не System.currentTimeMillis(). А порядок событий в распределённой системе определяют логическими часами (счётчиками, которые увеличиваются с каждым событием) или номерами версий, а не метками времени.

Проверка

timedatectl — строка «System clock synchronized: yes» («системные часы синхронизированы»); chronyc tracking — текущее смещение (chrony — популярная реализация NTP в Linux). В контейнере часы общие с хостом: настраивать NTP нужно на узле. Смещение часов — обязательная метрика мониторинга инфраструктуры.

Главное NTP держит часы серверов в согласии. Неверное время ломает TLS, токены, двухфакторные коды и порядок логов. Длительности меряют монотонными часами, порядок событий — версиями, а не временем.

18.4VPN

VPN (Virtual Private Network — «виртуальная частная сеть») создаёт на компьютере виртуальный сетевой интерфейс (tun0 — tunnel, «туннель»; wg0 — WireGuard). Пакет, отправленный в него, шифруется, заворачивается во внешний пакет (обычно UDP) и уходит на VPN-сервер. Там он разворачивается и попадает во внутреннюю сеть, будто вы подключены к ней напрямую. Какие адреса идут в туннель, а какие мимо, решает таблица маршрутов (глава 03).

WireGuardOpenVPNIPsec (IKEv2)
ТранспортUDPUDP или TCPESP (Encapsulating Security Payload — «инкапсуляция защищённых данных», свой протокол IP) или UDP 4500 (чтобы пройти через NAT)
Модельпары открытых ключей; у каждого собеседника (пира, peer) — список разрешённых адресов (AllowedIPs)TLS с сертификатами, множество настроексложное согласование по протоколу IKEv2 (Internet Key Exchange v2 — «обмен ключами в Интернете»); встроен в ОС и сетевое оборудование

Особенностьнет состояния «подключён»: пир молчит, пока нет трафика; спокойно переживает смену сетиработает через TCP 443 там, где UDP закрытстандарт для постоянной связи офисов и облаков (site-to-site, «площадка — площадка»)

Вся конфигурация клиента WireGuard умещается в десяток строк:

[Interface]
PrivateKey = <закрытый ключ клиента>
Address = 10.8.0.2/32              # адрес клиента внутри VPN
DNS = 10.8.0.1                     # корпоративный DNS-сервер

[Peer]
PublicKey = <открытый ключ сервера>
Endpoint = vpn.shop.ru:51820       # куда отправлять зашифрованные пакеты
AllowedIPs = 10.0.0.0/8            # split tunnel: в VPN идёт только корпоративная сеть;  0.0.0.0/0 — весь трафик
PersistentKeepalive = 25           # пакет каждые 25 с, чтобы NAT не забыл соединение

AllowedIPs работает в обе стороны: пакеты для этих адресов отправляются в туннель к этому пиру, и только пакеты от этих адресов принимаются от него. Split tunnel («раздельный туннель») — в VPN идёт только трафик к корпоративным сетям, а остальное — напрямую в Интернет.

Типичные проблемы VPN MTU: заголовки туннеля отнимают 60–80 байт, и большие пакеты не пролезают (глава 02); у интерфейса WireGuard MTU обычно 1420. Пересечение подсетей: дома сеть 192.168.1.0/24 и в офисе такая же — пакеты уходят не туда. DNS: внутренние имена не находятся, если запросы идут не на корпоративный резолвер. Split tunnel: если весь трафик идёт в VPN — медленно; если только корпоративные сети — их нужно точно перечислить в маршрутах.
Главное VPN — виртуальный интерфейс, пакеты из которого шифруются и едут туннелем во внутреннюю сеть. WireGuard прост и быстр. Типичные беды: MTU, пересекающиеся подсети и DNS.

ssh -L 15432:10.2.3.40:5432 bastion — где открывается порт 15432 и кто подключается к базе?

  • Порт на бастионе, к базе подключается ноутбук
  • Порт на вашем компьютере; к 10.2.3.40:5432 подключается бастион
  • Порт на сервере базы данных
  • Порт нигде не открывается
Локальный проброс: слушает клиент, а соединение к цели открывает SSH-сервер.

Письма сервиса через провайдера рассылок отклоняются с «DMARC policy reject», хотя SPF проходит. Почему?

  • Неверный MX
  • Закрыт порт 25
  • SPF проходит для домена провайдера, а не для домена в From; DKIM со своим доменом не настроен — выравнивания нет
  • Письмо слишком большое
DMARC требует, чтобы SPF или DKIM прошёл именно для домена из видимого From.

JWT, только что выданный сервером авторизации, отклоняется сервисом как «ещё не действителен».

  • Часы сервиса отстают от часов сервера авторизации; нужен NTP и допуск на расхождение
  • Неверная подпись
  • Токен слишком длинный
  • Ошибка DNS
Проверки iat, nbf и exp зависят от локального времени проверяющего.

Чем мерить длительность операции в Java?

  • System.currentTimeMillis()
  • System.nanoTime() — монотонными часами, которые не корректируются NTP
  • Датой из базы данных
  • Временем из HTTP-заголовка Date
Системное время может скачком уйти назад при коррекции, и длительность получится отрицательной.

При первом SSH-подключении появилось «The authenticity of host can't be established». Что это значит?

  • Сервер взломан
  • Неверный пароль
  • Ключа этого сервера ещё нет в known_hosts; вы решаете, доверять ли ему (TOFU)
  • Порт 22 закрыт
Опасно другое сообщение — «REMOTE HOST IDENTIFICATION HAS CHANGED»: ключ известного сервера изменился.

Вопросы для разговора (с собеседований)

Как SSH проверяет сервер и пользователя?

Сервер подписывает обмен ключами своим ключом хоста; клиент сверяет открытый ключ с known_hosts (при первом подключении принимает на веру). Пользователь подписывает данные сеанса закрытым ключом, а сервер проверяет подпись ключом из authorized_keys. Закрытые ключи сторон не передаются.

Что такое SPF, DKIM и DMARC?

SPF — список IP, которым домен разрешает отправлять почту. DKIM — криптографическая подпись письма ключом домена. DMARC — политика домена: требует, чтобы SPF или DKIM прошёл для домена из From, и сообщает получателю, что делать при провале (none — ничего, quarantine — в спам, reject — отклонить), плюс отчёты.

Почему в распределённой системе нельзя упорядочивать события по времени серверов?

Часы расходятся на миллисекунды и секунды, корректируются скачками и могут идти назад. Событие с «более поздней» меткой могло произойти раньше. Используют логические часы, версии, номера в журнале или сервис, задающий единый порядок.
