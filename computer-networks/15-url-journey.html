Путь запроса и собеседование

Классический вопрос на собеседовании — «что происходит, когда вы вводите адрес сайта и нажимаете Enter?» — идеальный экзамен: правильный ответ проходит через все предыдущие главы. Здесь — полный разбор по шагам, калькулятор бюджета задержки и вопросы уровня опытного инженера.

15.1https://app.bank.by/accounts — по шагам

  1. Браузер разбирает адрес (URL — Uniform Resource Locator): схема https, хост app.bank.by, путь /accounts. Проверяет список HSTS (HTTP Strict Transport Security): если домен там, http:// сразу заменяется на https:// без лишнего запроса (глава 14). Смотрит свой HTTP-кэш и Service Worker — скрипт сайта, который может отвечать на запросы прямо из браузера, без сети (глава 10).
  2. DNS — поиск IP-адреса по имени (глава 08): кэш браузера → кэш ОС → рекурсивный резолвер провайдера или зашифрованный DoH (DNS over HTTPS) → при пустых кэшах корень → зона .by → авторитативный сервер bank.by. Параллельно запрашиваются записи A (IPv4), AAAA (IPv6) и HTTPS; последняя может сразу сообщить, что сервер умеет HTTP/3.
  3. Выбор адреса: приём Happy Eyeballs — браузер пробует IPv6 и IPv4 почти одновременно и берёт тот, что ответит первым (глава 03).
  4. Доставка до роутера: адрес сервера вне домашней подсети → пакет отдаётся шлюзу по умолчанию; MAC-адрес роутера узнаётся через ARP (Address Resolution Protocol); кадр уходит по Wi-Fi на роутер (главы 02, 03).
  5. NAT на роутере подменяет адрес и порт отправителя на внешние; возможно, ещё раз — на CGNAT провайдера (глава 04).
  6. Интернет: сеть провайдера → точка обмена IXP или платный транзит → по маршрутам BGP к ближайшему узлу CDN, который отвечает по anycast-адресу (глава 05).
  7. TCP-рукопожатие SYN → SYN-ACK → ACK с ближайшим сервером CDN (edge) — 1 RTT, затем медленный старт (главы 06, 07). Если доступен HTTP/3 — вместо этого QUIC (глава 11).
  8. TLS 1.3: ClientHello с именем сайта (SNI) и списком версий HTTP (ALPN), сертификат сервера, проверка цепочки до доверенного корня, подпись CertificateVerify — ещё 1 RTT (глава 09).
  9. HTTP/2-запрос: кадр HEADERS с заголовками, сжатыми HPACK, и cookie сессии (главы 10, 11).
  10. CDN: страница персональная (Cache-Control: private), в общем кэше её нет (cache miss) — edge пересылает запрос к origin, серверу банка, по заранее открытому «прогретому» соединению.
  11. Инфраструктура банка: облачный балансировщик (L4 или L7) → WAF (фильтр атак) → ингресс-контроллер Kubernetes (расшифровывает TLS или шифрует заново) → Service → kube-proxy подменяет виртуальный адрес на адрес пода (DNAT) → под с приложением. Возможно, ещё sidecar-прокси с mTLS (глава 13).
  12. Приложение: поток веб-сервера Tomcat (или виртуальный поток) принимает запрос; проверяет, кто пользователь; вызывает сервис счетов по gRPC через пул HTTP/2-соединений и базу MySQL через пул HikariCP — всё с таймаутами и дедлайнами (глава 12).
  13. Ответ: JSON или HTML, сжатый алгоритмом Brotli, с заголовками кэширования и Set-Cookie с атрибутами Secure, HttpOnly, SameSite (глава 10). Ответ проходит обратно через все прокси.
  14. Браузер разбирает HTML, находит нужные стили (CSS — Cascading Style Sheets), скрипты (JS — JavaScript) и шрифты и запрашивает их по тому же HTTP/2-соединению. Статические файлы с хэшем в имени CDN отдаёт из кэша с пометкой immutable.
  15. Соединение остаётся открытым (keep-alive) для следующих запросов и закрывается по таймауту простоя — у той стороны, у которой он короче.
Главное Имя → адрес → кадр до роутера → NAT → Интернет до CDN → TCP → TLS → HTTP → CDN → балансировщик → Kubernetes → приложение → база → и обратно. Это и есть готовый ответ на собеседовании.

15.2Калькулятор бюджета задержки

Сколько стоит первый запрос пользователя? Задайте RTT до CDN и до сервера, включите или выключите кэш и переиспользование соединений — калькулятор сложит все этапы.

Сколько стоит первый запрос

Главный вывод, который стоит произнести на собеседовании: на дальних маршрутах время ответа определяется числом RTT, а не скоростью канала. Отсюда все оптимизации:

  • CDN — уменьшить сам RTT, приблизив сервер к пользователю;
  • TLS 1.3 и QUIC — меньше рукопожатий;
  • keep-alive и пулы — ни рукопожатий, ни медленного старта;
  • HTTP/2 — меньше соединений;
  • кэширование — ноль RTT;
  • батчинг (объединение многих мелких запросов в один) и меньше последовательных вызовов между сервисами.

15.3Вопросы System Design с сетевой частью

System Design («проектирование систем») — тип собеседования, где нужно спроектировать большую систему. Сетевая часть почти всегда в нём есть. p99 — время, быстрее которого проходят 99% запросов.

Платёжный API для клиентов в Европе и Азии. Как уложиться в 300 мс p99?

Разложить бюджет: RTT Европа — Азия ~150–200 мс, новое соединение с TLS 1.3 — 2 RTT плюс сам запрос, и это уже больше 300 мс. Значит: точки входа (edge, CDN) рядом с клиентом — TCP и TLS за 10–20 мс; прогретые соединения от edge до origin; всё, что можно, обрабатывать в ближайшем регионе (проверка пользователя, валидация), а запись — в «домашний» регион по постоянным соединениям. Синхронные цепочки вызовов между регионами исключить. Повторы на клиенте — с ключом идемпотентности (глава 10).

Как спроектировать уведомления в реальном времени для 1 млн пользователей онлайн?

SSE или WebSocket (глава 11) через L7-балансировщик, поддерживающий долгие соединения. Шлюзы соединений без собственного состояния (stateless), по 50–100 тысяч соединений на экземпляр — на event loop или виртуальных потоках. Распределение событий по шлюзам через шину (Kafka → Redis Pub/Sub или маршрутизация по номеру пользователя). Heartbeat чаще таймаута простоя NAT и балансировщиков, переподключение со случайной паузой (jitter) и Last-Event-ID, достаточные лимиты файловых дескрипторов и эфемерных портов на прокси, плавное отключение клиентов (graceful drain) при выкатке.

Вызовы между сервисами внутри кластера дают редкие 502 и Connection reset. План расследования?

Сопоставить с выкатками (гонка при остановке пода → нужна пауза preStop) и с периодами простоя (таймаут простоя клиента больше, чем у сервера или sidecar → reset на переиспользованном соединении). Найти, какой прокси генерирует 502 (ингресс, sidecar, клиентская библиотека), сравнить таймауты всех слоёв, записать tcpdump на поде с фильтром RST. Исправления: таймаут простоя клиента меньше серверного, повторы идемпотентных запросов на одном уровне, мягкое завершение (главы 12, 13).

Почему после перехода на gRPC нагрузка между подами распределилась неравномерно?

HTTP/2 гонит всё по одному долгому соединению, а Service Kubernetes балансирует на L4 — соединения, а не запросы. Решение: L7-прокси (Envoy, service mesh), клиентская балансировка через headless Service, ограничение возраста соединения max_connection_age на сервере.

Нужно защитить публичный API от всплесков нагрузки и ботов. Что и на каком уровне?

L3/L4 — провайдер или CDN с anycast-очисткой трафика, SYN cookies. L7 на edge — WAF, ограничение частоты по ключу API или пользователю (не только по IP — из-за CGNAT), защита от ботов. В приложении — bulkhead и лимиты одновременных запросов, backpressure (ограниченные очереди, ответ 429 с Retry-After), кэширование. Таймауты на чтение заголовков против Slowloris (глава 14).

15.4Экспресс-тест по всему курсу

Десять симптомов из практики. По каждому определите, на каком уровне искать причину.

curl к сервису мгновенно возвращает «Connection refused».

  • Файрвол выбрасывает пакеты
  • Хост доступен, но на этом порту никто не слушает
  • DNS не нашёл имя
  • Истёк сертификат
Глава 14: в ответ на SYN пришёл RST. Файрвол дал бы таймаут, DNS — ошибку поиска имени.

Первый запрос к сервису после простоя занимает 15 секунд, следующие — 20 мс.

  • Медленный диск
  • Сборка мусора
  • NAT или файрвол забыл простаивавшее соединение из пула; TCP повторяет отправку «в пустоту» до таймаута
  • Малый MTU
Главы 04 и 12: keepalive и ограничение времени жизни соединений в пуле.

Файлы до 1 КБ скачиваются, большие — зависают; через другой канал всё работает.

  • Проблема MTU: большие пакеты не проходят, а ICMP «нужна фрагментация» отфильтрован
  • Ошибка DNS
  • Перегрузка процессора
  • Неверный Content-Type
Глава 02: «чёрная дыра» Path MTU Discovery, типична для VPN и туннелей.

После смены IP сервиса часть клиентов ещё сутки ходит на старый адрес.

  • BGP не сошёлся
  • Проблема ARP
  • Потеряны пакеты
  • Кэши DNS: TTL у резолверов, кэш в JVM, долгоживущие соединения
Глава 08: TTL снижают заранее, а клиенты должны заново искать адрес.

Сервис на HTTP/2 в сети с 2% потерь работает медленнее, чем на HTTP/1.1.

  • HTTP/2 не сжимает заголовки
  • Блокировка начала очереди в TCP: одна потеря тормозит все потоки единственного соединения
  • HTTP/2 не поддерживает keep-alive
  • Больше рукопожатий TLS
Глава 11: это и есть причина появления QUIC.

Запросы маленькие, RTT 1 мс, но каждый ответ приходит через ~40 мс.

  • Медленный DNS
  • Медленный старт
  • Алгоритм Нейгла + отложенные ACK
  • Потери пакетов
Глава 07: TCP_NODELAY.

Браузер пишет «blocked by CORS policy», а тот же запрос из curl проходит.

  • Сервер не вернул заголовки Access-Control-Allow-*; проверку делает браузер, а curl — нет
  • Проблема сертификата
  • Сервер недоступен из браузера
  • Неверный DNS в браузере
Глава 10: CORS — политика браузера, а разрешение настраивается на сервере.

gRPC-сервис за L4-балансировщиком: из трёх подов нагружен один.

  • Ошибка проверки здоровья
  • Неверный алгоритм хэширования
  • Утечка памяти
  • Одно долгое HTTP/2-соединение закреплено за одним подом; нужна балансировка запросов на L7 или на клиенте
Главы 11 и 13.

В облаке сервис перестал открывать новые соединения к одному внешнему API, а к остальным — открывает.

  • Закончилась память
  • Исчерпаны порты NAT-шлюза для пары «адрес источника — адрес:порт назначения»
  • Истёк TTL
  • Сломался BGP
Глава 04: нужен пул соединений с переиспользованием или больше адресов на NAT.

Java-клиент: «PKIX path building failed» при обращении к внутреннему сервису.

  • Неверный пароль
  • Сервер перегружен
  • Клиент не доверяет издателю сертификата или сервер не прислал промежуточный сертификат
  • Не совпали версии HTTP
Глава 09: truststore и полная цепочка сертификатов.

15.5Блиц

Короткие вопросы, на которые на собеседовании ждут ответа за полминуты.

TCP и UDP в трёх предложениях.

TCP — соединение, надёжный упорядоченный поток байтов, управление потоком и перегрузкой; цена — рукопожатие и блокировка начала очереди. UDP — отдельные датаграммы без гарантий и без соединения, минимум накладных расходов. Поверх UDP строят свои протоколы с другими компромиссами (QUIC).

Что такое RTT, bandwidth и BDP?

RTT — время туда и обратно. Bandwidth — пропускная способность канала в бит/с. BDP = bandwidth × RTT — сколько данных должно быть «в полёте», чтобы канал был загружен; если окно TCP или буферы меньше, скорость упирается в них.

Зачем TIME_WAIT и у кого он появляется?

У стороны, закрывшей соединение первой, на 2×MSL (Maximum Segment Lifetime; в Linux 60 с): чтобы повторить последний ACK, если он потерялся, и не принять опоздавшие пакеты старого соединения в новое с той же пятёркой адресов и портов.

Как работает NAT и что он ломает?

Подменяет адрес (и порт) отправителя, храня таблицу соответствий. Ломает входящие соединения, рвёт простаивающие соединения по таймауту, прячет настоящие IP клиентов, собирает многих пользователей за одним IP.

Как сертификат защищает от «человека посередине»?

Сертификат, подписанный доверенным удостоверяющим центром, связывает имя сайта с открытым ключом, а CertificateVerify доказывает владение закрытым ключом. Посредник не может предъявить действительный сертификат на чужое имя без взлома CA или кражи ключа.

Чем 502 отличается от 504 и кто их генерирует?

Оба — прокси. 502: сервис за прокси недоступен или ответил некорректно (reset, refused). 504: сервис не ответил в пределах таймаута прокси.

Почему изменения DNS применяются не сразу?

Ответы кэшируются на каждом уровне по TTL (и сверх него — в JVM и библиотеках), отрицательные ответы тоже кэшируются, а открытые соединения в пулах продолжают ходить на старые адреса.

Чем L4-балансировщик отличается от L7?

L4 распределяет соединения по IP и портам — быстро и для любого протокола. L7 разбирает HTTP, распределяет отдельные запросы, маршрутизирует по пути и заголовкам, расшифровывает TLS, умеет повторы и лимиты.

15.6Итоговый практикум

  1. Запишите в Wireshark (программа разбора трафика, глава 17) открытие любого HTTPS-сайта и найдите: DNS-запрос и ответ, SYN / SYN-ACK / ACK, ClientHello (SNI, ALPN), закрытие или переиспользование соединения. Посчитайте RTT по меткам времени.
  2. Напишите на Java клиент с явными таймаутами подключения, чтения и общим, и с повторами со случайной паузой для идемпотентного GET. Проверьте поведение против nc -l 9000 (netcat в режиме «слушать порт и молчать») и против закрытого порта.
  3. Нарисуйте по памяти путь запроса в вашем рабочем сервисе: все прокси, балансировщики, пулы и их таймауты. Найдите хотя бы одно место, где нарушено правило «таймаут простоя клиента меньше серверного» или «верхний таймаут больше нижнего».
  4. Проверьте дома, не за CGNAT ли вы (глава 04), и снимите отчёт mtr до двух сервисов — в соседней стране и на другом континенте.
  5. Расскажите вслух раздел 15.1 за 5 минут без подсказок — это и есть готовый ответ на собеседовании.
