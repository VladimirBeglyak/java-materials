HashMap изнутри

Массив корзин, в каждой — цепочка узлов, превращающаяся в красно-чёрное дерево при большом числе коллизий. Разберём на живой хеш-таблице, как из hashCode() получается номер корзины, что делает «перемешивание» старших битов, как идёт put и get, и как при росте таблицы каждая цепочка ровно делится на две — без пересчёта хэшей.

8.1Устройство

public class HashMap<K, V> extends AbstractMap<K, V> implements Map<K, V>, Cloneable, Serializable {
    static final int DEFAULT_INITIAL_CAPACITY = 16;     // всегда степень двойки
    static final float DEFAULT_LOAD_FACTOR = 0.75f;
    static final int TREEIFY_THRESHOLD = 8, UNTREEIFY_THRESHOLD = 6, MIN_TREEIFY_CAPACITY = 64;

    transient Node<K, V>[] table;                        // создаётся лениво при первом put
    transient int size;
    int threshold;                                       // capacity * loadFactor: при size > threshold — resize()

    static class Node<K, V> { final int hash; final K key; V value; Node<K, V> next; }   // хэш сохранён в узле!

    static final int hash(Object key) {
        int h;
        return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);   // старшие биты подмешиваются в младшие
    }
    // индекс корзины: (n - 1) & hash   — то же, что hash mod n для n = 2^k, но без деления
}

8.3Почему именно так

РешениеЗачем
Ёмкость — степень двойкииндекс через побитовое И вместо медленного деления; при росте ×2 каждый узел либо остаётся, либо сдвигается ровно на старую ёмкость
h ^ (h >>> 16)при маленькой таблице индекс берёт только младшие биты; плохие hashCode (различаются только старшими битами, например Float, адресоподобные числа) иначе давали бы сплошные коллизии
Хэш хранится в Nodeне вызывать hashCode повторно при сравнении и resize; быстрое отсечение неравных ключей до equals
Load factor 0.75баланс памяти и длины цепочек: при случайных хэшах средняя цепочка < 1, вероятность цепочки длиной 8 ≈ 6·10⁻⁸ (распределение Пуассона, из комментария в исходниках HashMap)
Деревья в корзинах (Java 8)защита от худшего случая: при множестве коллизий (плохой hashCode или атака) поиск O(log n), а не O(n); для Comparable-ключей сравнение через compareTo, иначе — по классу и identityHashCode
Вставка в хвост цепочки (Java 8)в Java 7 вставка шла в голову, и параллельный resize без синхронизации мог создать цикл в списке — бесконечный цикл get() на 100% CPU

8.4null, порядок итерации, итераторы

  • HashMap допускает один ключ null (хэш 0, корзина 0) и любые null-значения. Поэтому get(k) == null не отличает «нет ключа» от «значение null» — используйте containsKey или getOrDefault. ConcurrentHashMap и Map.of null запрещают.
  • Итерация идёт по корзинам по порядку — порядок «случайный» и меняется после resize. Нужен порядок — LinkedHashMap.
  • Итераторы keySet/values/entrySet — fail-fast (тема 03). Изменение значения через entry.setValue — разрешено.
  • Обход entrySet() вместо keySet() + get(k) экономит повторный поиск каждого ключа.

8.5Самопроверка

Как вычисляется номер корзины в HashMap?

  • key.hashCode() % capacity
  • Math.abs(key.hashCode()) % capacity
  • (capacity − 1) & (h ^ (h >>> 16)), где h = key.hashCode()
  • Случайно
Степень двойки позволяет заменить деление битовой маской.

Что происходит с узлами при resize с 16 до 32 корзин?

  • Каждый либо остаётся в корзине i, либо переходит в i + 16 — по биту hash & 16, без пересчёта хэшей
  • Все хэши пересчитываются
  • Все узлы переходят в новые корзины случайно
  • Узлы не перемещаются
Цепочка делится на «lo» и «hi» с сохранением порядка.

Когда корзина превращается в дерево?

  • При любой коллизии
  • Когда size > threshold
  • При 64 элементах в карте
  • Когда цепочка длиннее 8 и в таблице не меньше 64 корзин (иначе таблица растёт)
Обратно в список — при уменьшении до 6.

Сколько корзин у new HashMap<>() сразу после создания?

  • 16
  • 0 — таблица создаётся лениво при первом put
  • 10
  • 12
Как и у ArrayList — экономия на пустых картах.
Расскажите, что происходит при map.put(key, value).

Вычисляется hash = h ^ (h >>> 16); если таблицы нет — resize до 16; индекс (n−1) & hash; пустая корзина — новый узел; иначе обход цепочки (или дерева): совпал hash и (== или equals) — заменить значение и вернуть старое; не нашли — добавить в хвост; если длина цепочки превысила 8 — treeifyBin (дерево или resize при n < 64); modCount++, size++; если size > threshold — resize с удвоением и разделением цепочек.

Почему в Java 7 HashMap мог зациклиться в многопоточном коде, и почему это не значит, что Java 8 HashMap потокобезопасен?

В Java 7 resize переносил узлы, вставляя их в голову новой цепочки — порядок разворачивался; два потока, одновременно делающие resize, могли создать циклическую ссылку, и get() крутился бесконечно. Java 8 сохраняет порядок при разделении, и цикла нет, но без синхронизации по-прежнему возможны потерянные записи, неверный size, частично видимые узлы. Для многопоточности — ConcurrentHashMap.
