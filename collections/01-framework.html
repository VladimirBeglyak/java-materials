1.3Необязательные операции и скелетные реализации

Интерфейсы объявляют операции изменения «необязательными»: реализация может бросать UnsupportedOperationException. Так устроены неизменяемые коллекции (List.of), представления фиксированного размера (Arrays.asList — set можно, add нельзя), представления-ключи (keySet().add не поддерживается). Это компромисс дизайна: иначе потребовались бы десятки интерфейсов (ModifiableList, FixedSizeList…).

Чтобы написать свою коллекцию, не реализуя 20 методов, есть скелетные классы: AbstractCollection (достаточно iterator() и size()), AbstractList (get и size; итератор и equals/hashCode — готовые), AbstractMap (entrySet()).

final class Range extends AbstractList<Integer> implements RandomAccess {
    private final int from, to;
    Range(int from, int to) { this.from = from; this.to = to; }
    @Override public Integer get(int i) { Objects.checkIndex(i, size()); return from + i; }
    @Override public int size() { return to - from; }
}
List<Integer> r = new Range(10, 15);   // [10, 11, 12, 13, 14] — iterator, contains, indexOf, subList, equals уже работают
r.add(15);                              // UnsupportedOperationException — AbstractList.add по умолчанию
Маркерный интерфейс RandomAccess Говорит алгоритмам, что get(i) — O(1). Collections.binarySearch, shuffle и другие выбирают индексный обход для RandomAccess-списков и итераторный — для LinkedList. Реализуйте его в своих индексных списках.

1.5Наследие: Vector, Hashtable, Stack, Enumeration

Классы Java 1.0 (до Collections Framework, 1998): Vector и Hashtable синхронизируют каждый метод, но это не делает составные операции безопасными («проверить и добавить»); Stack наследует Vector (можно вставить в середину стека); Enumeration — предшественник Iterator без remove. В новом коде: ArrayList, HashMap/ConcurrentHashMap, ArrayDeque вместо Stack.

1.6Самопроверка

Почему Map не наследует Collection?

  • Из-за обратной совместимости с Hashtable
  • Map не умеет итерироваться
  • Map — отображение ключей в значения, а не группа элементов; операция add(E) для неё не имеет смысла. Коллекции доступны через keySet/values/entrySet
  • Это ошибка дизайна, исправленная в Java 21
Представления дают обход и удаление, но не добавление.

Arrays.asList(1, 2, 3).add(4) — что произойдёт?

  • UnsupportedOperationException: список фиксированного размера поверх массива
  • Список станет [1, 2, 3, 4]
  • ArrayIndexOutOfBoundsException
  • Ошибка компиляции
set() при этом работает и меняет исходный массив.

Чем отличаются offer/poll от add/remove в Queue?

  • Ничем
  • offer/poll потокобезопасны
  • add/remove работают с хвостом
  • При невозможности операции offer/poll возвращают false/null, а add/remove бросают исключение
Две «формы» API для очередей с ограничением и без.

Что достаточно реализовать в наследнике AbstractList, чтобы получить неизменяемый список?

  • iterator() и size()
  • get(int) и size()
  • add и remove
  • все методы List
Итераторы, contains, equals, hashCode, subList — уже готовы на основе get и size.
Почему программировать нужно «от интерфейса»: List<X> xs = new ArrayList<>()?

Код зависит от контракта, а не от реализации: можно сменить ArrayList на неизменяемый List.of, CopyOnWriteArrayList или представление без изменения клиентов. Но в сигнатурах публичных API иногда полезнее более общий тип (Collection, Iterable) для параметров и более конкретный (List, SequencedCollection) для результатов, чтобы клиенту были доступны нужные гарантии.

Что такое «представление» (view) коллекции?

Объект-коллекция без собственного хранения, читающий и (если позволено) изменяющий другую коллекцию: keySet/values/entrySet у Map, subList, Arrays.asList, Collections.unmodifiableList, reversed() в Java 21. Изменения видны в обе стороны; структурное изменение источника в обход представления может сделать его некорректным (subList → ConcurrentModificationException).
