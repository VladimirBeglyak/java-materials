Неизменяемые коллекции и представления

В Java как минимум пять способов получить «нельзя изменить»: List.of, List.copyOf, Collections.unmodifiableList, Arrays.asList, Stream.toList() — и все ведут себя по-разному: где-то можно set, где-то запрещён null, где-то изменения исходника просачиваются наружу. Матрица поведения покажет разницу, а разбор устройства ImmutableCollections объяснит, почему порядок Set.of меняется от запуска к запуску.

14.1Неизменяемая, немодифицируемая, представление

Неизменяемая (immutable)

Содержимое не может измениться никак и никогда: List.of, List.copyOf, Stream.toList(), Guava ImmutableList. Можно безопасно делиться и кэшировать.

Немодифицируемое представление (unmodifiable view)

Collections.unmodifiableList(list) — обёртка, запрещающая изменения через неё. Владелец исходного списка меняет его — и обёртка это показывает.

Представление фиксированного размера

Arrays.asList(array) — окно в массив: set пишет в массив, add/remove запрещены.

Неизменяемость коллекции не делает неизменяемыми элементы: List.of(new StringBuilder()) — элемент можно поменять. Глубокая неизменяемость — это неизменяемая коллекция неизменяемых объектов (records, String).

14.3Как устроены List.of, Set.of, Map.of

  • Специализированные классы (java.util.ImmutableCollections): List12 и Set12 хранят 1–2 элемента в полях без массива; ListN — массив ровно нужной длины; MapN и SetN — открытая адресация с линейным пробированием в одном массиве (ключи и значения чередуются), заполнение около 50%.
  • Случайный порядок итерации Set.of и Map.of: смещение пробирования зависит от SALT, вычисляемого при старте JVM. Порядок меняется между запусками — специально, чтобы никто не полагался на него (тесты, которые сравнивают toString() таких множеств, «мигают»).
  • Дубликаты запрещены при создании: Set.of("a", "a") и Map.of("k", 1, "k", 2) бросают IllegalArgumentException.
  • Map.of — до 10 пар; больше — Map.ofEntries(entry(k, v), …).
  • Отсутствие проверок изменяемости и компактность дают выигрыш по памяти и иногда по скорости; JIT может считать содержимое static final List.of(…) константой.

14.4Защитные копии

public final class Order {
    private final List<Item> items;
    public Order(List<Item> items) { this.items = items; }      // вызывающий может изменить список позже
    public List<Item> items() { return items; }                 // клиент может изменить наш список
}
record Team(List<String> members) {}                            // record не копирует сам!
public final class Order {
    private final List<Item> items;
    public Order(List<Item> items) { this.items = List.copyOf(items); }  // + проверка на null-элементы
    public List<Item> items() { return items; }                          // уже неизменяемый — копировать не нужно
}
record Team(List<String> members) {
    Team { members = List.copyOf(members); }                    // компактный конструктор
}
Hibernate и неизменяемые коллекции Сущности JPA ожидают изменяемые коллекции (Hibernate подменяет их своими PersistentBag/PersistentSet). Не присваивайте полям сущностей List.of — при попытке Hibernate изменить коллекцию будет UnsupportedOperationException. Защитные копии — для DTO и доменных объектов.

14.5Самопроверка

var u = Collections.unmodifiableList(src); src.add("x"); — что увидит u?

  • Ничего, u — копия
  • Новый элемент: u — представление поверх src
  • UnsupportedOperationException
  • ConcurrentModificationException
Немодифицируемое ≠ неизменяемое.

Что произойдёт при List.of("a", "b").contains(null)?

  • false
  • true
  • UnsupportedOperationException
  • NullPointerException
Коллекции из List.of враждебны к null даже при поиске.

Почему тест, сравнивающий Set.of("a", "b", "c").toString() со строкой, иногда падает?

  • Порядок итерации Set.of рандомизирован при старте JVM (SALT)
  • Set.of удаляет элементы
  • toString не определён
  • Из-за GC
Специально, чтобы не полагались на порядок.

Чем stream.toList() отличается от collect(Collectors.toList())?

  • Ничем
  • toList() возвращает ArrayList
  • toList() гарантированно неизменяемый (но допускает null), а Collectors.toList() на практике ArrayList без гарантий
  • toList() запрещает null
Замена в существующем коде может сломать места, которые меняют результат.
Как вернуть из метода коллекцию, которую вызывающий не сможет испортить?

Если поле — изменяемый список, который класс продолжает менять: вернуть Collections.unmodifiableList(list) (дёшево, но вызывающий увидит будущие изменения) или List.copyOf(list) (снимок). Если поле с самого начала неизменяемое (List.copyOf в конструкторе) — возвращать его напрямую. Для очень больших коллекций и частых вызовов — представление; для передачи между потоками и кэшей — неизменяемую копию.

Почему Arrays.asList(new int[]{1, 2, 3}).size() == 1?

Arrays.asList(T... a) — дженерик-метод; int[] не может быть T[] (примитивы не параметризуют), поэтому весь массив становится одним элементом T = int[]. Для примитивов — IntStream.of(arr).boxed().toList() или Arrays.stream(arr).boxed().toList().
