LinkedHashMap и LRU-кэш

LinkedHashMap — это HashMap, у которого узлы дополнительно связаны в двусвязный список. Отсюда предсказуемый порядок итерации, а с режимом «порядок доступа» и одним переопределённым методом — готовый LRU-кэш на 10 строк. Разбираем устройство, оба режима порядка, хук removeEldestEntry и сравниваем LRU с FIFO на разных паттернах обращений.

10.1Устройство

static class Entry<K, V> extends HashMap.Node<K, V> {
    Entry<K, V> before, after;                 // + 8 байт к узлу: двусвязный список порядка
}
transient LinkedHashMap.Entry<K, V> head;     // старейший
transient LinkedHashMap.Entry<K, V> tail;     // новейший
final boolean accessOrder;                     // false — порядок вставки, true — порядок доступа

// хуки, которые HashMap вызывает в нужные моменты:
void afterNodeAccess(Node<K, V> e)      { if (accessOrder) переместить e в хвост; }
void afterNodeInsertion(boolean evict)  { if (removeEldestEntry(head)) удалить head; }
void afterNodeRemoval(Node<K, V> e)     { исключить e из списка; }
protected boolean removeEldestEntry(Map.Entry<K, V> eldest) { return false; }

Поиск по ключу — как в HashMap, O(1). Итерация идёт по списку, а не по корзинам: O(size), а не O(capacity), и в предсказуемом порядке. Повторный put существующего ключа в режиме вставки порядок не меняет.

10.2LRU-кэш

final class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int maxSize;
    LruCache(int maxSize) {
        super(16, 0.75f, true);             // accessOrder = true: get и put двигают запись в хвост
        this.maxSize = maxSize;
    }
    @Override protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > maxSize;            // после вставки: вытеснить самую давно использованную (голову)
    }
}
// не потокобезопасен: в режиме доступа даже get — структурное изменение (меняет порядок, modCount++)
// для многопоточности — Collections.synchronizedMap(...) или, лучше, Caffeine
Симулятор кэша на 3 записи
Что сравнить Паттерн с горячим ключом: LRU держит A в кэше, FIFO периодически его вытесняет. Цикл длиннее кэша (A B C D…): у LRU 0% попаданий — каждый раз вытесняется ровно тот ключ, который понадобится следующим. Поэтому продакшен-кэши (Caffeine) используют W-TinyLFU: учитывают и частоту, и недавность, устойчивы к сканированию.

10.3Порядок вставки на практике

  • Детерминированный JSON (Jackson сериализует Map в порядке итерации), стабильные отчёты и тесты.
  • LinkedHashSet — удаление дубликатов с сохранением порядка: new ArrayList<>(new LinkedHashSet<>(list)) или list.stream().distinct().toList().
  • Java 21: SequencedMap — firstEntry(), pollLastEntry(), putFirst(k, v), putLast, reversed() (тема 15). putFirst перемещает существующий ключ в начало.
  • Цена: +8 байт на узел и чуть медленнее вставка; итерация обычно быстрее, чем у HashMap с большой разреженной таблицей.

Что нужно, чтобы LinkedHashMap работал как LRU-кэш?

  • Использовать TreeMap

Меняет ли повторный put существующего ключа его позицию в LinkedHashMap с порядком вставки?

  • Да, переносит в конец
  • Да, в начало

В режиме доступа — переносит в хвост.

Почему LinkedHashMap в режиме доступа нельзя читать из нескольких потоков без синхронизации?

  • get меняет порядок списка — это структурное изменение, гонки портят связи узлов
  • Он вообще не поддерживает get
  • Он использует ThreadLocal
  • Можно, get только читает
Синхронизация или специализированный кэш.
Реализуйте LRU-кэш без LinkedHashMap (классическая задача).

HashMap<K, Node> + собственный двусвязный список с фиктивными головой и хвостом. get: найти узел в карте, переставить в хвост, вернуть значение. put: если есть — обновить и переставить; иначе создать узел в хвосте, положить в карту; если size > capacity — удалить узел после головы из списка и из карты. Все операции O(1).

Чем LRU хуже LFU и W-TinyLFU?

LRU учитывает только недавность: однократное сканирование большого набора (отчёт, обход) вытесняет весь полезный горячий набор; циклический доступ длиннее кэша даёт 0% попаданий. LFU учитывает частоту, но медленно забывает старое. W-TinyLFU (Caffeine) — небольшое LRU-окно для новых записей + основной сегмент, куда кандидат попадает, только если по приблизительной частоте (Count-Min Sketch) он «ценнее» вытесняемой записи.
