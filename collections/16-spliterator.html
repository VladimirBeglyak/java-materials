Spliterator и параллельный обход

Iterator умеет только «дай следующий». Spliterator (split + iterator, Java 8) умеет ещё и разделиться на две части для параллельной обработки, сообщить свой размер и свойства — на нём построены все стримы. Симулятор покажет, как по-разному делятся ArrayList, LinkedList и HashSet и почему linkedList.parallelStream() почти бесполезен. В конце — свой Spliterator.

16.1Интерфейс

public interface Spliterator<T> {
    boolean tryAdvance(Consumer<? super T> action);   // обработать один элемент, если есть (hasNext + next в одном вызове)
    default void forEachRemaining(Consumer<? super T> action) { do { } while (tryAdvance(action)); }
    Spliterator<T> trySplit();      // отдать «префикс» элементов новому сплитератору, себе оставить остаток; null — не делится
    long estimateSize();            // сколько осталось (точно, если SIZED)
    int characteristics();          // битовая маска свойств
    int ORDERED = 0x10, DISTINCT = 0x1, SORTED = 0x4, SIZED = 0x40, NONNULL = 0x100,
        IMMUTABLE = 0x400, CONCURRENT = 0x1000, SUBSIZED = 0x4000;
}
ХарактеристикаЧто даёт стриму
SIZED / SUBSIZEDразмер известен (и у частей после split) — toArray выделит массив точно, count() может не обходить элементы (Java 9+)
ORDEREDпорядок встречи важен: findFirst, limit, forEachOrdered обязаны его соблюдать — дороже в параллели
DISTINCTdistinct() становится пустой операцией (у Set)
SORTEDsorted() с тем же порядком пропускается (у TreeSet)
IMMUTABLE / CONCURRENTисточник не изменится / может изменяться безопасно — без проверок fail-fast

16.3Late-binding и fail-fast

Сплитераторы коллекций JDK — late-binding: привязываются к состоянию источника не при создании, а при первом обходе/делении/запросе размера. Поэтому можно создать стрим, затем изменить список и только потом запустить терминальную операцию — изменения будут учтены. Изменение во время обхода приводит к ConcurrentModificationException по завершении (сплитератор проверяет modCount в конце forEachRemaining, а не на каждом элементе — ради скорости).

List<String> list = new ArrayList<>(List.of("a", "b"));
Stream<String> s = list.stream();     // сплитератор ещё не привязан
list.add("c");                         // изменение ДО терминальной операции — допустимо
s.forEach(System.out::print);          // abc

list.stream().forEach(x -> list.add("z"));   // изменение ВО ВРЕМЯ — ConcurrentModificationException

16.4Свой Spliterator

final class RangeSpliterator implements Spliterator.OfLong {
    private long from; private final long to;               // [from, to)
    RangeSpliterator(long from, long to) { this.from = from; this.to = to; }
    @Override public boolean tryAdvance(LongConsumer action) {
        if (from >= to) return false;
        action.accept(from++); return true;
    }
    @Override public Spliterator.OfLong trySplit() {
        long mid = (from + to) >>> 1;
        if (mid <= from + 1024) return null;                // мелкие части не делим: накладные расходы выше выгоды
        RangeSpliterator prefix = new RangeSpliterator(from, mid);
        from = mid;                                          // себе — суффикс
        return prefix;
    }
    @Override public long estimateSize() { return to - from; }
    @Override public int characteristics() { return ORDERED | SIZED | SUBSIZED | IMMUTABLE | NONNULL | DISTINCT | SORTED; }
    @Override public Comparator<? super Long> getComparator() { return null; }   // SORTED в естественном порядке
}
LongStream s = StreamSupport.longStream(new RangeSpliterator(0, 1_000_000_000), true);   // parallel

Чаще не нужно писать сплитератор вручную: Spliterators.spliterator(array, characteristics), Spliterators.spliteratorUnknownSize(iterator, ORDERED) для своего итератора, Iterable.spliterator() по умолчанию.

16.5Самопроверка

Что возвращает trySplit()?

  • Две новые половины
  • Новый сплитератор с префиксом элементов, а текущий остаётся с остатком; null, если делиться нецелесообразно
  • Количество частей
  • Копию сплитератора
Так ForkJoin рекурсивно раздаёт работу.

Почему parallelStream() по LinkedList обычно неэффективен?

  • LinkedList не поддерживает стримы
  • Он синхронизирован
  • Список нельзя разделить без последовательного обхода: части формируются партиями в массивы, несбалансированно и с копированием
  • Параллельные стримы запрещены для списков
ArrayList и массивы делятся пополам за O(1).

Что значит характеристика SIZED?

  • Точное число оставшихся элементов известно без обхода
  • Элементы отсортированы
  • Коллекция неизменяемая
  • Нет null-элементов
SUBSIZED — то же верно и для частей после trySplit.

Список изменили между вызовом list.stream() и forEach. Что будет?

  • ConcurrentModificationException
  • Стрим обойдёт старое содержимое
  • IllegalStateException
  • Изменения учтутся: сплитератор late-binding привязывается при начале обхода
Изменение во время обхода — CME.
Чем Spliterator отличается от Iterator, кроме деления?

tryAdvance объединяет hasNext и next в один вызов (меньше вызовов и проверок, проще реализация для источников, где «есть ли следующий» дорого узнать); forEachRemaining позволяет обойти всё в плотном цикле без проверок на каждом элементе; estimateSize и характеристики дают стриму информацию для оптимизаций (точный размер массива, пропуск distinct/sorted, отказ от учёта порядка).

Когда parallelStream ускоряет работу?

Когда данных много (обычно от десятков–сотен тысяч элементов), источник хорошо делится (массивы, ArrayList, IntStream.range, HashMap), операции на элемент дорогие и независимые, нет блокирующего I/O и общего изменяемого состояния, а терминальная операция хорошо комбинируется (sum, reduce, collect с конкурентными коллекторами). Учитывайте, что общий ForkJoinPool разделяется со всем приложением. Подробнее — в пособии по конкурентности.
