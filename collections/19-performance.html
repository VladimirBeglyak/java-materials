19.3Кэш процессора: почему O(n) бывает разным

Процессор читает память строками кэша по 64 байта и предсказывает последовательный доступ. Обход int[] — 16 значений за одну загрузку строки, предвыборка работает идеально. Обход ArrayList<Integer> — ссылки подряд, но объекты Integer разбросаны (хотя часто выделены рядом в TLAB). Обход LinkedList — каждый следующий узел по случайному адресу: промах кэша стоит ~100 нс против ~1 нс попадания.

Сумма 10 млн элементов (порядок величин на современном x86)Время
int[] (векторизовано JIT)~3 мс
ArrayList<Integer>, элементы выделены подряд~15 мс

Цифры ориентировочные и сильно зависят от железа, GC и прогрева — проверяйте своими JMH-бенчмарками.

19.4Как правильно мерить

@State(Scope.Benchmark) @BenchmarkMode(Mode.AverageTime) @OutputTimeUnit(TimeUnit.MILLISECONDS)
@Warmup(iterations = 5) @Measurement(iterations = 5) @Fork(2)
public class SumBench {
    @Param({"1000", "1000000"}) int n;
    List<Integer> arrayList, linkedList; int[] array;
    @Setup public void setup() {
        array = IntStream.range(0, n).toArray();
        arrayList = Arrays.stream(array).boxed().collect(Collectors.toCollection(ArrayList::new));
        linkedList = new LinkedList<>(arrayList);
    }
    @Benchmark public long arraySum()  { long s = 0; for (int x : array) s += x; return s; }      // возвращаем результат — иначе JIT выбросит цикл
    @Benchmark public long arrayList() { long s = 0; for (int x : arrayList) s += x; return s; }
    @Benchmark public long linked()    { long s = 0; for (int x : linkedList) s += x; return s; }
}
// запуск с профилировщиком аллокаций: -prof gc ; нативный: -prof perfasm
Практические советы Задавайте начальную ёмкость при известном размере; используйте примитивные массивы и стримы (IntStream) для числовых данных; примитивные коллекции (fastutil, Eclipse Collections, HPPC) для больших объёмов чисел; не держите миллионы маленьких коллекций (у каждой пустой HashMap — ~48 Б, а с таблицей — больше); удаляйте ссылки, которые больше не нужны (кэши с ограничением).

19.5Самопроверка

Сколько примерно байт на элемент занимает HashSet<Integer> с 1 млн элементов?

  • 4
  • 16
  • ~50–60: узел 32 + слот таблицы + объект Integer 16
  • ~200
Против 4 байт в int[] — разница более чем в 10 раз.

Почему обход LinkedList медленнее ArrayList при одинаковом O(n)?

  • Узлы разбросаны по памяти — промахи кэша и невозможность предвыборки
  • LinkedList синхронизирован
  • LinkedList проверяет modCount
  • Итератор LinkedList создаёт копию
Локальность данных важнее асимптотики на реальном железе.

Почему обход HashMap с ёмкостью 1 млн и 10 элементами медленный?

  • Из-за коллизий
  • Из-за блокировок
  • HashMap копирует данные при итерации
  • Итератор проходит все корзины таблицы, включая пустые: O(capacity)
Таблица не сжимается после удаления элементов.
Сервис хранит 50 млн пар long → long в HashMap и занимает 6 ГБ. Как сократить?

Каждая пара — узел 32 Б + два Long по 24 Б + слот таблицы ≈ 85–90 Б, то есть ~4,5 ГБ только на карту. Примитивная карта с открытой адресацией (fastutil Long2LongOpenHashMap) — ~16 Б на пару с учётом заполнения: ~1 ГБ. Если ключи плотные — просто long[] по индексу. Если данные отсортированы — два long[] и бинарный поиск. Для ещё больших объёмов — off-heap (Chronicle Map) или внешнее хранилище.
