equals, hashCode, Comparable, Comparator

Коллекции ничего не знают о ваших объектах — они полагаются на три контракта: equals (равенство), hashCode (быстрый отбор кандидатов) и сравнение (compareTo/Comparator). Нарушение любого из них не даёт ошибку компиляции, а тихо ломает поиск. Лаборатория ошибок покажет, что происходит с HashMap при неверных ключах, а конструктор компараторов — как собирать сортировку по нескольким полям.

4.1Контракты

equals

  • рефлексивность: x.equals(x)
  • симметричность: x = y ⇔ y = x
  • транзитивность
  • согласованность: результат не меняется, пока не меняются поля
  • x.equals(null) == false

hashCode

  • равные объекты — обязательно равные хэши
  • неравные — желательно разные (иначе коллизии и деградация до O(n) или O(log n))
  • не меняется, пока не меняются поля, участвующие в equals

Как HashMap ищет ключ: вычисляет hashCode() → выбирает корзину → в ней сравнивает сначала хэши, потом ссылки (==), потом equals. Если хэш «не тот», до equals дело не дойдёт вовсе.

4.3Сравнение, согласованное с equals

TreeMap и TreeSet вообще не вызывают equals — ключи равны, если compare(a, b) == 0. Если порядок «не согласован с equals», одна и та же пара объектов будет разной для HashSet и TreeSet.

var a = new BigDecimal("1.0"); var b = new BigDecimal("1.00");
a.equals(b);          // false — учитывается масштаб (scale)
a.compareTo(b);       // 0     — численно равны
new HashSet<>(List.of(a, b)).size();   // 2
new TreeSet<>(List.of(a, b)).size();   // 1

var names = new TreeSet<String>(String.CASE_INSENSITIVE_ORDER);
names.addAll(List.of("Anna", "anna", "ANNA"));   // [Anna] — остальные «дубликаты» по компаратору

4.4Comparator: сборка из частей

Конструктор компаратора
Компаратор через вычитание (a, b) -> a.age - b.age ломается на больших числах: Integer.MIN_VALUE - 1 переполняется и меняет знак — сортировка становится некорректной, а TimSort может бросить IllegalArgumentException: Comparison method violates its general contract!. Используйте Integer.compare или Comparator.comparingInt.

4.5Самопроверка

Переопределили только equals. Что с HashSet?

  • Работает правильно
  • Равные объекты почти всегда попадают в разные корзины — дубликаты и «ненаходимые» элементы
  • Ошибка компиляции
  • ClassCastException
Равные объекты обязаны иметь равные хэши.

Сколько элементов в new TreeSet<>(List.of(new BigDecimal("2.0"), new BigDecimal("2.00")))?

  • 2
  • 0
  • Исключение
  • 1 — TreeSet считает равными элементы с compareTo == 0
У HashSet — 2, так как equals учитывает масштаб.

Почему ключ HashMap не должен меняться после put?

  • Запись остаётся в корзине по старому хэшу и перестаёт находиться и по новому, и по старому ключу
  • Карта бросит исключение
  • Ключ скопируется
  • Ничего страшного
Используйте неизменяемые ключи.

Чем плох компаратор (a, b) -> a.id - b.id?

  • Он медленный
  • Он не стабилен
  • Переполнение int при больших разностях меняет знак — некорректный порядок и возможное исключение TimSort
  • Ничем
Integer.compare(a.id, b.id).
Как правильно реализовать equals в иерархии классов?

Проблема: equals между родителем и наследником с дополнительным полем нарушает симметричность или транзитивность. Варианты: сравнивать getClass() (наследники не равны родителю), делать классы final или использовать композицию вместо наследования; records — final по определению. instanceof-equals допустим, если наследники не добавляют полей, участвующих в равенстве.

Что значит «comparison method violates its general contract»?

TimSort обнаружил нарушение контракта компаратора: несимметричность (sgn(compare(a,b)) ≠ −sgn(compare(b,a))), нетранзитивность или непостоянство (компаратор зависит от изменяемого состояния, случайности, текущего времени). Частые причины: вычитание с переполнением, сравнение double через вычитание с NaN, компаратор с особыми случаями для null только с одной стороны.
