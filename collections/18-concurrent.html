Конкурентные коллекции изнутри

Обычные коллекции в многопоточном коде ломаются тихо: теряются записи, портятся структуры, итераторы видят полуизменённое состояние. Синхронизированные обёртки спасают отдельные операции, но не составные «проверить-и-сделать». Разбираем, как устроен ConcurrentHashMap (CAS на пустую корзину, блокировка головы корзины, распределённый счётчик, совместный resize), CopyOnWriteArrayList, списки с пропусками и блокирующие очереди — и какую коллекцию брать для какой задачи.

18.1Синхронизация отдельных методов не спасает составные операции

Два потока регистрируют один и тот же логин в Collections.synchronizedMap
Поток 1
containsKey("anna")put("anna", user1)
Карта
{}
Поток 2
containsKey("anna")put("anna", user2)

Каждый метод обёртки берёт монитор, поэтому сами вызовы атомарны. Но между containsKey и put монитор отпускается.

Оба потока проверили — логина нет.

Оба вставили; второй затёр первого. Два пользователя думают, что зарегистрированы.

Атомарная составная операция внутри коллекции: putIfAbsent, computeIfAbsent, merge, replace(k, old, new), remove(k, v) у ConcurrentMap. С synchronizedMap — внешний synchronized (map) { … } вокруг обеих операций. И итерацию синхронизированной обёртки тоже нужно вручную обернуть в synchronized (map).

18.3CopyOnWriteArrayList и снимки

public class CopyOnWriteArrayList<E> {
    private transient volatile Object[] array;
    public boolean add(E e) {
        synchronized (lock) {
            Object[] es = getArray();
            es = Arrays.copyOf(es, es.length + 1);   // КОПИЯ всего массива на каждую запись: O(n)
            es[es.length - 1] = e;
            setArray(es);                            // volatile-публикация
            return true;
        }
    }
    public E get(int i) { return elementAt(getArray(), i); }   // без блокировок
    public Iterator<E> iterator() { return new COWIterator<>(getArray(), 0); }   // снимок: remove() не поддерживается
}

Идеален для «читают постоянно, пишут редко»: списки слушателей и обработчиков событий, конфигурация, маршруты. Ужасен для частых записей: 10 000 add = 50 млн копирований ссылок.

18.4Списки с пропусками и очереди

  • ConcurrentSkipListMap/Set — упорядоченная конкурентная карта (аналог TreeMap): список с пропусками на CAS, без блокировок, O(log n) в среднем; навигационные методы, диапазоны.
  • ConcurrentLinkedQueue/Deque — неблокирующие очереди Майкла–Скотта на CAS: максимальная пропускная способность, но без ожидания при пустоте.

18.5Самопроверка

Почему ConcurrentHashMap запрещает null-значения?

  • Для экономии памяти
  • Чтобы get(k) == null однозначно означало отсутствие ключа: проверить containsKey и затем get атомарно нельзя
  • Из-за ограничений CAS
  • Это ошибка дизайна
Даг Ли: неоднозначность null недопустима в конкурентных картах.

Как атомарно увеличить счётчик слова в ConcurrentHashMap<String, Long>?

  • map.put(w, map.get(w) + 1)
  • synchronized (w) { … }
  • map.get(w).increment()
  • map.merge(w, 1L, Long::sum)
Или LongAdder в качестве значения для горячих ключей.

Что видит итератор CopyOnWriteArrayList, если во время обхода добавить элемент?

  • Снимок на момент создания итератора — нового элемента нет, исключения нет
  • CME
  • Новый элемент
  • Итератор блокируется
Запись создала новый массив; итератор держит старый.

Чем опасна неограниченная LinkedBlockingQueue в пуле потоков?

  • Она медленная
  • Она не потокобезопасна
  • Если задачи поступают быстрее, чем обрабатываются, очередь растёт без предела — OutOfMemoryError вместо отказа
  • Она теряет задачи

Объясните, как ConcurrentHashMap в Java 8 обеспечивает потокобезопасность без глобальной блокировки.

Таблица корзин с volatile-доступом (Unsafe/VarHandle). Вставка в пустую корзину — CAS. В непустую — synchronized на узле-голове этой корзины (блокируется только она). Чтение — без блокировок, через volatile-поля узлов. Размер — распределённый счётчик (baseCount + CounterCells). Расширение — совместное: потоки, встретившие ForwardingNode, помогают переносить диапазоны корзин. Длинные цепочки — TreeBin. Итераторы — слабо согласованные.

synchronizedList против CopyOnWriteArrayList против ConcurrentLinkedQueue — когда что?

synchronizedList — простая защита при умеренной конкуренции и смешанной нагрузке; итерацию надо синхронизировать вручную. CopyOnWriteArrayList — много чтений и итераций, редкие записи (слушатели). ConcurrentLinkedQueue — очередь с частыми добавлениями и извлечениями без индексного доступа. Для производитель–потребитель — BlockingQueue.
