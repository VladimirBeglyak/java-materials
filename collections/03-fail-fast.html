Fail-fast, modCount и ConcurrentModificationException

ConcurrentModificationException чаще всего бросается в однопоточном коде: удалили элемент из списка внутри for-each. Разбираемся, как устроен механизм fail-fast через счётчик modCount, почему удаление предпоследнего элемента «проходит» без исключения, как правильно удалять при обходе, и чем fail-fast отличается от итераторов-снимков и слабо согласованных итераторов конкурентных коллекций.

3.1Механизм

public class ArrayList<E> … {
    protected transient int modCount = 0;     // в AbstractList: счётчик структурных изменений
    public boolean add(E e)   { modCount++; … }
    public E remove(int i)    { modCount++; … }
    public E set(int i, E e)  { … }             // НЕ структурное изменение — modCount не меняется

    private class Itr implements Iterator<E> {
        int cursor;                              // индекс следующего элемента
        int lastRet = -1;
        int expectedModCount = modCount;         // снимок при создании итератора

        public boolean hasNext() { return cursor != size; }
        public E next() {
            checkForComodification();            // modCount != expectedModCount → CME
            int i = cursor;
            if (i >= size) throw new NoSuchElementException();
            cursor = i + 1;
            return (E) elementData[lastRet = i];
        }
        public void remove() {
            if (lastRet < 0) throw new IllegalStateException();
            checkForComodification();
            ArrayList.this.remove(lastRet);      // modCount++
            cursor = lastRet; lastRet = -1;
            expectedModCount = modCount;         // итератор «узаконивает» собственное изменение
        }
    }
}

Структурное изменение — то, что меняет размер или устройство (add, remove, clear, rehash у HashMap). Замена значения (set, put существующего ключа) структурным не считается.

Fail-fast — лишь «best effort» Документация: «поведение fail-fast не гарантируется… следует использовать только для обнаружения ошибок». modCount — не volatile; при изменении из другого потока итератор может не заметить его, прочитать полуизменённую структуру или зациклиться. CME — не механизм синхронизации, а сигнал о баге.

3.5Самопроверка

Почему удаление предпоследнего элемента ArrayList внутри for-each не бросает CME?

  • Предпоследний элемент особенный
  • Удаление в конце не меняет modCount
  • После удаления size уменьшился и сравнялся с cursor, hasNext() вернул false — до проверки в next() дело не дошло; последний элемент пропущен
  • Это поведение LinkedList
Тихая ошибка хуже исключения.

Меняет ли list.set(i, x) modCount?

  • Нет: это не структурное изменение
  • Да
  • Только у LinkedList
  • Только если x равен null
Поэтому replaceAll и set внутри обхода безопасны.

Что делает итератор CopyOnWriteArrayList, если во время обхода добавили элемент?

  • Бросает CME
  • Включает новый элемент в обход
  • Блокируется
  • Ничего не замечает: обходит снимок массива на момент создания
Снимок неизменен — запись создаёт новый массив.

Можно ли полагаться на CME для обнаружения гонок между потоками?

  • Да, это гарантия
  • Нет: fail-fast — best effort, без синхронизации изменения из другого потока могут быть не замечены или испортить обход
  • Да, если коллекция synchronized
  • Только для HashMap
Для многопоточности — конкурентные коллекции или синхронизация.
Почему removeIf у ArrayList быстрее, чем удаление через итератор в цикле?

Каждый it.remove() сдвигает хвост массива (System.arraycopy) — k удалений = O(n·k). removeIf проходит массив один раз, отмечает удаляемые элементы в битовой маске, затем одним проходом уплотняет оставшиеся — O(n), и меняет modCount один раз. Плюс, если предикат бросит исключение, список остаётся неизменным.

CME при обходе HashMap внутри одного метода без циклов удаления — где искать?

Изменение карты в теле цикла косвенно: вызов метода, который кладёт в эту же карту (например, кэш с computeIfAbsent, рекурсивно меняющий ту же карту — у HashMap computeIfAbsent с изменением внутри функции тоже даёт CME), слушатели и колбэки, обход keySet с put нового ключа. Также — обход в одном потоке при изменении в другом (тогда это гонка, и CME — удача).
