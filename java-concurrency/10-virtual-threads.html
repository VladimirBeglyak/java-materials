Виртуальные потоки и Structured Concurrency

Project Loom вернул простой блокирующий стиль «поток на запрос» без ограничения в несколько тысяч потоков. Разбираем механику монтирования, где виртуальные потоки не помогают, что такое pinning и как структурировать конкурентные подзадачи.

~3 часаJEP 444 · 491 · 505 · 506JDK 21+интерактивтест

10.1Что такое виртуальный поток

Виртуальный поток (VT) — это java.lang.Thread, которым управляет JVM, а не ОС. Его стек хранится в куче как объект-продолжение (continuation) и занимает сотни байт – единицы КБ. Выполняется VT на небольшом пуле платформенных carrier-потоков (по умолчанию ForkJoinPool с числом потоков ≈ ядрам). Схема M:N: миллион VT на 8 carrier'ах.

Thread vt = Thread.ofVirtual().name("req-", 0).start(() -> handle(request));
Thread.startVirtualThread(() -> work());

try (ExecutorService exec = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<Response>> fs = requests.stream()
            .map(r -> exec.submit(() -> client.send(r)))   // 10 000 блокирующих вызовов — нормально
            .toList();
    for (Future<Response> f : fs) process(f.get());
}   // close() дожидается всех задач
// Spring Boot 3.2+: spring.threads.virtual.enabled=true — Tomcat, @Async, планировщик на VT

10.2Когда помогают, а когда нет

✔ Помогают

  • Много одновременных задач, которые в основном ждут: HTTP-вызовы, БД, очереди.
  • Цель — пропускная способность (throughput) при простом блокирующем коде вместо реактивного.
  • Ограничение «поток на запрос» было узким местом.

✘ Не помогают

  • CPU-bound задачи: ядер больше не стало, а планирование добавит накладных расходов.
  • Узкое место — внешний ресурс: пул соединений БД на 20 не обслужит 10 000 VT быстрее.
  • Задержку (latency) отдельного запроса VT не уменьшают.

Правила работы с VT

  1. Не пулируйте виртуальные потоки. Они дешёвые — один VT на задачу. Пул VT — антипаттерн.
  2. Ограничивайте ресурсы, а не потоки. Раньше размер пула неявно ограничивал нагрузку на БД. Теперь это нужно делать явно — Semaphore на вызовы downstream, пул соединений с таймаутом ожидания.
  3. Осторожно с ThreadLocal. Миллион VT × тяжёлый кэш в ThreadLocal = гигабайты. Используйте ScopedValue для контекста.
  4. Не используйте VT для долгих CPU-вычислений — они не вытесняются планировщиком по времени и могут монополизировать carrier.
private final Semaphore dbPermits = new Semaphore(50);   // ≤ размера пула соединений

Response handle(Request r) throws InterruptedException {
    dbPermits.acquire();             // VT паркуется дёшево, carrier свободен
    try {
        return repo.load(r.id());
    } finally {
        dbPermits.release();
    }
}

10.3Pinning — когда VT не может отцепиться

Pinning — ситуация, когда VT при блокировке не может размонтироваться и держит carrier заблокированным. Если все carrier'ы пришпилены — приложение стоит, хотя VT много.

ПричинаJDK 21–23JDK 24+
Блокировка внутри synchronized (I/O, wait(), ожидание монитора)pinning — главная проблема ранних миграций; совет был «заменить на ReentrantLock»исправлено JEP 491: VT отпускает carrier и внутри synchronized
Блокировка в нативном фрейме (JNI, Foreign Function API через downcall)pinningpinning (остаётся)
Файловый I/O на некоторых ОСcarrier временно компенсируется доп. потокомто же

Диагностика: событие JFR jdk.VirtualThreadPinned (по умолчанию пишется при блокировке дольше 20 мс). В JDK 21–23 также -Djdk.tracePinnedThreads=full (свойство удалено в JDK 24). Thread dump с виртуальными потоками: jcmd <pid> Thread.dump_to_file -format=json file.json.

10.4ScopedValue вместо ThreadLocal

Финален в JDK 25 (JEP 506). Неизменяемое значение, привязанное к динамической области выполнения: видно в вызванном коде и в дочерних задачах structured concurrency, недоступно после выхода из области. Нет set, нет утечек, нет копирования при наследовании.

private static final ScopedValue<RequestContext> CTX = ScopedValue.newInstance();

void serve(Request req) {
    ScopedValue.where(CTX, new RequestContext(req.userId(), req.traceId()))
               .run(() -> controller.handle(req));          // внутри: CTX.get()
}   // здесь CTX уже не привязан — забыть remove() невозможно

void audit(String action) {
    RequestContext c = CTX.get();     // NoSuchElementException, если вне области; CTX.isBound() для проверки
    log.info("user={} trace={} action={}", c.userId(), c.traceId(), action);
}

10.5Structured Concurrency

Идея: подзадачи живут не дольше, чем блок кода, который их создал — как локальные переменные. Если одна упала, остальные отменяются; если родителя прервали, прерываются дети; в thread dump видна иерархия. Это решает проблему «осиротевших» задач у CompletableFuture и ExecutorService.

В JDK 25 API — preview (JEP 505, пятая итерация, нужен --enable-preview). Сигнатуры менялись между версиями — сверяйтесь с javadoc вашего JDK.
Dashboard dashboard(long id) throws InterruptedException {
    try (var scope = StructuredTaskScope.open()) {        // Joiner по умолчанию: все должны быть успешны
        Subtask<Client> client = scope.fork(() -> clients.find(id));       // каждая — в своём VT
        Subtask<List<Account>> acc = scope.fork(() -> accountsApi.list(id));
        scope.join();                  // ждём всех; если одна упала — остальные прерываются,
                                       // join бросает StructuredTaskScope.FailedException
        return new Dashboard(client.get(), acc.get());
    }                                  // close(): гарантированно ни одной живой подзадачи
}

// «Кто первый ответил»: опросить две реплики, взять первый успех, вторую отменить
String fastest() throws InterruptedException {
    try (var scope = StructuredTaskScope.open(
            StructuredTaskScope.Joiner.<String>anySuccessfulResultOrThrow(),
            cfg -> cfg.withTimeout(Duration.ofMillis(300)))) {
        scope.fork(() -> replicaA.query());
        scope.fork(() -> replicaB.query());
        return scope.join();
    }
}

10.7Интерактив: монтирование и размонтирование виртуального потока

Три задачи, два carrier-потока

Виртуальный поток — объект в куче плюс continuation. Чтобы исполняться, он «монтируется» на платформенный carrier-поток из пула планировщика (ForkJoinPool, размер по умолчанию = число ядер). VT1 и VT2 работают, VT3 ждёт в очереди.

VT1 вызывает socket.read()

JDK внутри переводит сокет в неблокирующий режим, регистрирует его в поллере (epoll) и вызывает Continuation.yield(): кадры стека VT1 копируются с carrier-стека в кучу. Carrier 1 свободен — системный поток не заблокирован.

Монтирование VT3

Освободившийся carrier берёт из очереди следующий виртуальный поток. Код VT1 выглядит блокирующим, но ни один системный поток не простаивает.

Поллер будит VT1

Отдельный поток-поллер получил событие готовности сокета и вызвал unpark(VT1): VT1 поставлен в очередь планировщика. Он ещё не выполняется — нужен свободный carrier.

VT2 завершился → Carrier 2 монтирует VT1

Кадры VT1 копируются из кучи обратно на стек carrier-а, выполнение продолжается после read(). Carrier другой, чем до блокировки, — поэтому идентичность потока для кода — это VT, а не carrier: Thread.currentThread() возвращает виртуальный поток, и его ThreadLocal-ы переезжают вместе с ним.

VT3 блокируется внутри synchronized (JDK 21–23)

Если блокирующий вызов происходит внутри synchronized-блока или нативного кадра, стек нельзя размонтировать: VT «пришпилен» (pinned), и carrier блокируется вместе с ним. При двух carrier-ах два таких вызова останавливают все виртуальные потоки приложения.

С JDK 24 (JEP 491) synchronized больше не вызывает pinning; остаются нативные кадры (JNI) и инициализаторы классов. Диагностика: событие JFR jdk.VirtualThreadPinned, ранее — -Djdk.tracePinnedThreads=full.

10.8Самопроверка

Для какой нагрузки виртуальные потоки дают выигрыш?

  • Перемножение матриц
  • Любой, они всегда быстрее
  • Много одновременных задач, которые большую часть времени ждут I/O
  • Один долгий расчёт
VT не ускоряют вычисления: ядер столько же. Они делают ожидание дешёвым.

Нужно ли создавать пул виртуальных потоков?

  • Да, как и для обычных
  • Нет: они дёшевы, создаются на задачу; конкурентность ограничивают семафором, а не размером пула
  • Да, размером с число ядер
  • Пул создаёт JVM автоматически под каждый класс
Executors.newVirtualThreadPerTaskExecutor(). Пулинг нужен дорогим ресурсам; VT к ним не относятся.

Чем ScopedValue лучше ThreadLocal для виртуальных потоков?

  • Значение неизменяемо, привязано к области вызова, автоматически исчезает и дёшево наследуется дочерними задачами
  • Он работает быстрее только на одном потоке
  • Он позволяет менять значение из любого места
  • Ничем
ThreadLocal на миллион потоков — миллион копий и риск утечек; ScopedValue задаёт значение на время выполнения блока.
Почему 10 000 виртуальных потоков, вызывающих HTTP, не требуют 10 000 потоков ОС?

При блокирующей операции JDK переводит её в неблокирующую, регистрирует в poller'е и размонтирует continuation VT с carrier-потока. Carrier берёт следующий готовый VT. Стек ожидающего VT хранится в куче. Потоков ОС ≈ числу ядер плюс служебные.

Переводим сервис на VT, пул соединений Hikari = 20. Что изменится и что нужно сделать?

Раньше пул Tomcat (200 потоков) ограничивал конкурентность. Теперь каждый запрос — VT, и тысячи VT одновременно будут ждать соединения из Hikari: рост времени ожидания, таймауты connectionTimeout. Нужно: явный лимит (Semaphore / bulkhead) с быстрым отказом, разумный connectionTimeout, метрики ожидания соединения; размер Hikari определяется возможностями БД, а не числом потоков.

Что такое pinning и актуален ли он в JDK 25?

Ситуация, когда VT не может размонтироваться при блокировке и занимает carrier. До JDK 24 главная причина — блокировка внутри synchronized. JEP 491 (JDK 24) это убрал. Остаётся pinning при блокировке в нативных фреймах (JNI/FFM). Диагностика — JFR-событие jdk.VirtualThreadPinned.

Почему ScopedValue лучше ThreadLocal для контекста запроса?

Значение неизменяемо и привязано к лексически ограниченной области: не нужно вызывать remove, утечка в следующую задачу невозможна. Наследуется дочерними задачами StructuredTaskScope без копирования (у InheritableThreadLocal — копия на каждый поток). Дешевле по памяти при миллионах VT.

Чем StructuredTaskScope лучше allOf из CompletableFuture?

Подзадачи гарантированно завершены к выходу из блока; при ошибке одной остальные реально прерываются (а не просто перестают ждаться); прерывание родителя распространяется на детей; иерархия видна в thread dump; код блокирующий и читаемый, исключения — обычные.
