12.1Шесть вопросов: как объяснить любую программу

Используйте этот порядок и на собеседовании («объясните, что здесь происходит»), и на code review, и при проектировании своего кода.

Разбор на примере

public final class RateService implements AutoCloseable {
    private volatile Map<String, BigDecimal> rates = Map.of();
    private final ScheduledExecutorService scheduler =
            Executors.newSingleThreadScheduledExecutor(Thread.ofPlatform().name("rates-refresh").factory());
    private final RatesApi api;
    private final LongAdder misses = new LongAdder();

    public RateService(RatesApi api) {
        this.api = api;
        scheduler.scheduleWithFixedDelay(this::refresh, 0, 30, TimeUnit.SECONDS);
    }

    private void refresh() {
        try {
            rates = Map.copyOf(api.fetchAll());          // новый неизменяемый снимок
        } catch (Exception e) {
            log.warn("rates refresh failed, keeping old snapshot", e);
        }
    }

    public Optional<BigDecimal> rate(String ccy) {      // вызывается из потоков Tomcat
        BigDecimal r = rates.get(ccy);
        if (r == null) misses.increment();
        return Optional.ofNullable(r);
    }

    @Override public void close() { scheduler.shutdownNow(); }
}
ВопросОтвет для этой программы
1. ПотокиОдин поток планировщика rates-refresh пишет; N потоков веб-сервера читают через rate().
2. Общее состояниеrates (ссылка), сама карта, misses. api и scheduler — final, задаются в конструкторе.
3. БезопасностьКарта неизменяемая (Map.copyOf) → безопасна после публикации. Публикация через volatile: запись ссылки HB чтения в rate(), поэтому читатель видит полностью построенную карту. Один писатель — нет read-modify-write на rates. misses — LongAdder, атомарный инкремент. Каждый читатель видит согласованный снимок всех курсов. Замечание: планировщик стартует из конструктора — this утекает в другой поток до конца конструктора; здесь безопасно, потому что все поля уже присвоены, а schedule даёт HB, но лучше вынести запуск в метод start().
4. ЖивучестьЛоков нет → deadlock невозможен. Риск: api.fetchAll() без таймаута повиснет, и обновления прекратятся навсегда (single thread). Нужен таймаут на HTTP-клиенте.
5. ПроизводительностьЧтение — одно volatile-чтение + HashMap lookup, без конкуренции. LongAdder вместо AtomicLong — нет contention на счётчике. Копия карты раз в 30 с — пренебрежимо.
6. ОтказыИсключение в refresh поймано — иначе расписание бы отменилось. При отказе API остаётся старый снимок (нужна метрика «возраст курсов» и алерт). scheduleWithFixedDelay — запуски не накладываются. close() прерывает поток.

12.3Задачи

Порядок работы: прочитать условие → написать код в IDE → прогнать стресс-тест → объяснить по шести вопросам → сверить с решением.

Задача 1. Чередование чёт/нечет

Два потока печатают числа от 1 до N: первый — нечётные, второй — чётные, строго по очереди. Без sleep.

Решение на ReentrantLock + Condition
public final class OddEvenPrinter {
    private final int max;
    private int current = 1;                                    // guarded by lock
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition turnChanged = lock.newCondition();

    public OddEvenPrinter(int max) { this.max = max; }

    public void run(boolean odd) throws InterruptedException {
        while (true) {
            lock.lock();
            try {
                while (current <= max && (current % 2 == 1) != odd) turnChanged.await();
                if (current > max) { turnChanged.signalAll(); return; }   // разбудить партнёра для выхода
                System.out.println(Thread.currentThread().getName() + " " + current++);
                turnChanged.signalAll();
            } finally {
                lock.unlock();
            }
        }
    }

    public static void main(String[] args) throws InterruptedException {
        OddEvenPrinter p = new OddEvenPrinter(10);
        Thread a = Thread.ofPlatform().name("odd").start(() -> { try { p.run(true); } catch (InterruptedException ignored) { Thread.currentThread().interrupt(); } });
        Thread b = Thread.ofPlatform().name("even").start(() -> { try { p.run(false); } catch (InterruptedException ignored) { Thread.currentThread().interrupt(); } });
        a.join(); b.join();
    }
}

Альтернатива — два Semaphore (oddTurn=1, evenTurn=0): каждый поток делает acquire своего и release чужого. Объясните, почему здесь signalAll можно заменить на signal (ждёт максимум один поток).

Задача 2. Rate limiter со скользящим окном

Не более limit вызовов за любое окно длиной window. Потокобезопасно, время инжектируется для тестов.

Решение (sliding log)
public final class SlidingWindowRateLimiter {
    private final int limit;
    private final long windowMillis;
    private final Clock clock;
    private final ArrayDeque<Long> timestamps = new ArrayDeque<>();   // guarded by this

    public SlidingWindowRateLimiter(int limit, Duration window, Clock clock) {
        if (limit <= 0) throw new IllegalArgumentException("limit");
        this.limit = limit;
        this.windowMillis = window.toMillis();
        this.clock = clock;
    }

    public synchronized boolean tryAcquire() {
        long now = clock.millis();
        while (!timestamps.isEmpty() && now - timestamps.peekFirst() >= windowMillis) {
            timestamps.pollFirst();                 // выкидываем вышедшие из окна
        }
        if (timestamps.size() < limit) {
            timestamps.addLast(now);
            return true;
        }
        return false;
    }
}

Разбор: check-then-act (размер → добавить) должен быть атомарным — поэтому весь метод под одним локом. Память O(limit). Если limit огромный — sliding window counter (два счётчика соседних окон с весом) или токен-бакет на AtomicLong с CAS. В кластере — Redis + Lua. Тест: Clock из фиксированного мутабельного источника, проверка границ окна (ровно windowMillis — вышел или нет).

Задача 3. Memoizer: вычислить один раз на ключ

Дорогая функция f(k). Параллельные запросы одного ключа должны вызвать её ровно один раз; ошибки не кэшировать; не держать лок во время вычисления.

Решение
public final class Memoizer<K, V> {
    private final ConcurrentHashMap<K, CompletableFuture<V>> cache = new ConcurrentHashMap<>();
    private final Function<K, V> fn;
    private final Executor executor;

    public Memoizer(Function<K, V> fn, Executor executor) { this.fn = fn; this.executor = executor; }

    public CompletableFuture<V> get(K key) {
        CompletableFuture<V> f = cache.computeIfAbsent(key,
                k -> CompletableFuture.supplyAsync(() -> fn.apply(k), executor)); // под локом бакета — только создание future
        f.whenComplete((v, ex) -> {
            if (ex != null) cache.remove(key, f);   // remove(key, value): не удалить чужой, более новый future
        });
        return f;
    }
}

Это эволюция Memoizer из JCiP (там — putIfAbsent + FutureTask). Почему нельзя computeIfAbsent(key, fn)? Вычисление под локом бакета блокирует другие ключи и запрещает рекурсивные обращения к кэшу. Для продакшена с вытеснением — Caffeine AsyncLoadingCache.

Задача 4. Single-flight (схлопывание запросов)

Как Memoizer, но без постоянного кэша: пока запрос по ключу выполняется, новые вызовы присоединяются к нему; после завершения ключ освобождается.

Решение
public final class SingleFlight<K, V> {
    private final ConcurrentHashMap<K, CompletableFuture<V>> inFlight = new ConcurrentHashMap<>();

    public CompletableFuture<V> execute(K key, Supplier<V> loader, Executor executor) {
        CompletableFuture<V> mine = new CompletableFuture<>();
        CompletableFuture<V> existing = inFlight.putIfAbsent(key, mine);
        if (existing != null) return existing;                 // присоединились к идущему запросу

        CompletableFuture.supplyAsync(loader, executor).whenComplete((v, ex) -> {
            inFlight.remove(key, mine);                        // сначала освобождаем ключ
            if (ex != null) mine.completeExceptionally(ex); else mine.complete(v);
        });
        return mine;
    }
}

Применение: защита от «стада» (thundering herd) при протухании кэша — 1000 запросов за одним курсом превращаются в один вызов API.

Задача 5. Потокобезопасный LRU-кэш

Ёмкость N, get/put из многих потоков.

Решение и обсуждение
public final class LruCache<K, V> {
    private final Map<K, V> map;
    public LruCache(int capacity) {
        this.map = new LinkedHashMap<>(16, 0.75f, true) {            // accessOrder = true
            @Override protected boolean removeEldestEntry(Map.Entry<K, V> e) { return size() > capacity; }
        };
    }
    public synchronized V get(K k) { return map.get(k); }            // get МЕНЯЕТ порядок → тоже под локом
    public synchronized void put(K k, V v) { map.put(k, v); }
}

Ключевой момент: в LRU даже чтение — запись (перестановка в списке), поэтому ReadWriteLock не поможет. Узкое место — один лок. Масштабирование: шардирование на M независимых LRU по hash(key) % M (приблизительный LRU) или буферизация обращений и их пакетное применение — так делает Caffeine (W-TinyLFU + ring buffers).

Задача 6. Переводы между счетами

Сервис переводов с in-memory счетами: без deadlock, без потери денег, инвариант «сумма всех балансов постоянна». Напишите стресс-тест, который это проверяет.

Ключевые элементы решения

Порядок захвата локов по id (тема 11), проверка достаточности баланса внутри обоих локов, BigDecimal для сумм. Тест: 100 счетов, 16 потоков × 100 000 случайных переводов между случайными парами (включая обратные), старт через latch, future.get с таймаутом (таймаут = обнаруженный deadlock), в конце — сумма балансов равна начальной и нет отрицательных. Плюс ThreadMXBean.findDeadlockedThreads() в случае таймаута для диагностики.

Задача 7. Параллельная агрегация с дедлайном

Запросить 5 провайдеров курсов параллельно, вернуть медиану ответивших за 200 мс, минимум 3 ответа, иначе ошибка.

Решение
public BigDecimal medianRate(List<RateProvider> providers, String pair) {
    List<CompletableFuture<BigDecimal>> calls = providers.stream()
            .map(p -> CompletableFuture.supplyAsync(() -> p.rate(pair), io)
                    .completeOnTimeout(null, 200, TimeUnit.MILLISECONDS)   // не успел — null
                    .exceptionally(ex -> null))                            // упал — null
            .toList();

    List<BigDecimal> ok = CompletableFuture.allOf(calls.toArray(CompletableFuture[]::new))
            .thenApply(v -> calls.stream().map(CompletableFuture::join).filter(Objects::nonNull).sorted().toList())
            .join();

    if (ok.size() < 3) throw new IllegalStateException("quorum not reached: " + ok.size());
    return ok.get(ok.size() / 2);
}

Вариант с StructuredTaskScope (JDK 25 preview) — свой Joiner, который собирает успешные результаты, а withTimeout отменит оставшиеся подзадачи; не забудьте таймаут на самих HTTP-клиентах провайдеров.

Задача 8. Найдите баги

public class OrderProcessor {
    private final ExecutorService pool = Executors.newFixedThreadPool(4);
    private final Map<Long, Order> orders = new HashMap<>();
    private boolean stopped;
    private static final ThreadLocal<User> USER = new ThreadLocal<>();

    public void submit(Order o, User u) {
        pool.submit(() -> {
            USER.set(u);
            if (!orders.containsKey(o.id())) orders.put(o.id(), o);
            process(o);
        });
    }
    public void stop() { stopped = true; pool.shutdown(); }
    private void process(Order o) {
        if (stopped) return;
        synchronized (o) { o.setStatus(PROCESSED); notifyExternalSystem(o); }
    }
}
Ответ: минимум 7 проблем
  1. HashMap из 4 потоков — гонка, порча структуры. → ConcurrentHashMap.
  2. containsKey + put — check-then-act. → putIfAbsent.
  3. stopped без volatile — потоки пула могут не увидеть изменение.
  4. ThreadLocal без remove() в пуле — следующий заказ на этом потоке увидит чужого пользователя.
  5. submit без обработки результата — исключения из process потеряются молча.
  6. newFixedThreadPool — неограниченная очередь, OOM под перегрузкой; потоки без имён.
  7. Вызов внешней системы под локом o (не open call) — лок держится на время сетевого вызова, риск deadlock; синхронизация на объекте, доступном снаружи.
  8. Бонус: shutdown() без awaitTermination — вызывающий не знает, когда обработка закончится.

Десять ситуаций из реального кода. Сначала ответьте сами, потом проверьте — в объяснении указана тема, где механизм разобран.

Поток-воркер крутится в while (!stopped) { … }, поле boolean stopped без volatile. Главный поток ставит stopped = true. Что возможно?

  • IllegalStateException

synchronized void inc() и static synchronized void reset() в одном классе меняют одно статическое поле. Защищено ли оно?

  • Пул вырастет до 8 потоков
  • RejectedExecutionException

map.put(key, map.getOrDefault(key, 0) + 1) на ConcurrentHashMap из нескольких потоков.

  • Корректный счётчик
  • ConcurrentModificationException
  • Потерянные обновления: два отдельных атомарных вызова не образуют атомарную операцию

Тема 07: нужен merge(key, 1, Integer::sum).

Singleton с ленивой инициализацией через double-checked locking, поле instance не volatile. Риск?

  • Другой поток может получить ссылку на не до конца сконструированный объект
  • Будет создано много экземпляров при каждом вызове

  • Никакого
Тема 02: публикация ссылки и инициализация полей могут быть переупорядочены.

Сервис на виртуальных потоках обращается к БД с пулом из 10 соединений, приходит 5000 одновременных запросов. Что будет узким местом?

  • Число carrier-потоков
  • Память под стеки
  • Планировщик ForkJoinPool
  • Пул соединений: 4990 потоков ждут соединения, часть получит таймаут
Тема 10: потоки перестали быть ограничителем — ограничивать конкурентность нужно явно.

cf.thenApply(this::blockingCall), где cf завершается в потоке Netty event loop.

  • blockingCall выполнится в commonPool
  • blockingCall выполнится в event loop и заблокирует его
  • blockingCall выполнится в вызывающем потоке всегда

12.5Блиц: вопросы собеседования

Чем отличаются synchronized и volatile?

volatile — видимость и порядок для одной переменной, без взаимного исключения и атомарности составных операций. synchronized — взаимное исключение + видимость + порядок для всего, что сделано под одним монитором.

Что такое happens-before? Назовите 5 правил.

Отношение, гарантирующее видимость: если W HB R, то R видит W. Program order, monitor unlock→lock, volatile write→read, Thread.start, join/termination, транзитивность (+ interrupt, final-поля, гарантии j.u.c).

Как работает ConcurrentHashMap и почему get не блокируется?

CAS для пустого бакета, synchronized на голове бакета для остальных, деревья при коллизиях, кооперативный resize. get читает volatile-элементы таблицы и volatile поля узлов — запись под локом публикуется через них.

Как устроен ReentrantLock?

На AQS: volatile int state (счётчик реентерабельных захватов), владелец, CLH-очередь узлов, парковка через LockSupport. Fair/unfair различаются проверкой очереди перед CAS (barging).

Алгоритм execute() в ThreadPoolExecutor?

< core → новый поток; иначе в очередь; очередь полна и < max → новый поток; иначе RejectedExecutionHandler. Следствие: при неограниченной очереди max не работает.

wait vs sleep?

wait — метод Object, только под монитором, отпускает этот монитор, просыпается по notify/таймауту/interrupt (или ложно), используется в цикле с условием. sleep — статический метод Thread, ничего не отпускает, только пауза.

Что такое CAS и проблема ABA?

Атомарная инструкция «сравнить и заменить». ABA — значение вернулось к ожидаемому через промежуточные изменения, CAS этого не замечает. Лечится версией/штампом.

Когда LongAdder, когда AtomicLong?

LongAdder — частые записи из многих потоков, редкое чтение суммы (метрики). AtomicLong — нужна точная атомарная операция с результатом (id) или CAS.

Что дают виртуальные потоки и чего не дают?

Дешёвые потоки M:N на carrier'ах: высокая пропускная способность I/O-bound кода в блокирующем стиле. Не ускоряют CPU-задачи, не уменьшают латентность, не снимают лимиты внешних ресурсов; их не пулируют.

Как избежать deadlock?

Глобальный порядок захвата локов, tryLock с таймаутом и откатом, open calls, меньше локов (неизменяемые снимки, один лок на инвариант), таймауты на всех ожиданиях.

Почему Double-Checked Locking без volatile сломан?

Запись ссылки на объект может стать видимой другому потоку раньше записей полей в конструкторе (нет HB). Поток на первой проверке без синхронизации увидит не-null и полуинициализированный объект. volatile на поле даёт HB.

Как бы вы реализовали очередь задач с приоритетами и ограничением размера?

PriorityBlockingQueue неограниченна, поэтому: обернуть в Semaphore на ёмкость (acquire перед offer, release после take), или свой класс на ReentrantLock + PriorityQueue + два Condition (notFull/notEmpty) — по образцу BoundedBuffer.
