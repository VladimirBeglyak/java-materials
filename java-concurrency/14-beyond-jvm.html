Конкурентность за пределами JVM: база данных и распределённые блокировки

Всё, что было до сих пор, — synchronized, ReentrantLock, атомарные типы — работает внутри одного процесса. Но сервис запущен в трёх экземплярах, а общее состояние лежит в базе данных. Гонки никуда не делись: они переехали на уровень транзакций. Разберём потерянное обновление в БД, оптимистичные и пессимистичные блокировки, идемпотентность и то, почему распределённый лок коварнее, чем кажется.

14.1Почему synchronized не помогает

@Service
class StockService {
    public synchronized void reserve(long productId, int qty) {      // монитор — в памяти ОДНОГО процесса
        Product p = repo.findById(productId).orElseThrow();
        if (p.getStock() < qty) throw new OutOfStockException();
        p.setStock(p.getStock() - qty);
        repo.save(p);
    }
}

Два экземпляра сервиса не знают о мониторах друг друга. К тому же даже в одном экземпляре synchronized на методе с @Transactional отпускается до коммита (прокси коммитит после выхода из метода) — второй поток успевает прочитать старое значение. Общее состояние в БД нужно защищать средствами БД.

14.3Оптимистичная и пессимистичная блокировки в коде

@Entity
class Product {
    @Id Long id;
    int stock;
    @Version long version;                      // Hibernate сам добавит «AND version = ?» и увеличит версию
}

@Retryable(retryFor = ObjectOptimisticLockingFailureException.class, maxAttempts = 3)   // повтор — СНАРУЖИ транзакции
@Transactional
public void reserve(long id, int qty) {
    Product p = repo.findById(id).orElseThrow();
    if (p.getStock() < qty) throw new OutOfStockException(id);
    p.setStock(p.getStock() - qty);            // при коммите: UPDATE … WHERE id = ? AND version = ?
}
public interface ProductRepository extends JpaRepository<Product, Long> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)                                         // SELECT … FOR UPDATE
    @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "2000"))
    @Query("select p from Product p where p.id = :id")
    Optional<Product> findForUpdate(long id);
}

14.4Уникальные ограничения как инструмент конкурентности

if (!repo.existsByEmail(email)) repo.save(new User(email));    // check-then-act: два запроса проходят проверку одновременно
try {
    repo.saveAndFlush(new User(email));                         // UNIQUE(email) в схеме — арбитр
} catch (DataIntegrityViolationException e) {
    throw new EmailAlreadyUsedException(email);
}
// или: INSERT … ON CONFLICT (email) DO NOTHING — и проверить число вставленных строк

Ограничение уникальности — единственный способ гарантировать «не более одного» при параллельных вставках: блокировать строку, которой ещё нет, нельзя. На этом строится идемпотентность: таблица processed_requests(idempotency_key UNIQUE), вставка ключа в той же транзакции, что и действие. Повторный запрос с тем же ключом упрётся в ограничение и вернёт сохранённый результат.

14.5Распределённые блокировки

Иногда нужно, чтобы операцию выполнял только один экземпляр: запуск задачи по расписанию, обращение к внешнему API без поддержки конкурентности. Варианты: advisory lock PostgreSQL (pg_try_advisory_lock), строка-замок в таблице (ShedLock), Redis (SET key value NX PX 30000), ZooKeeper/etcd.

A получает лок с временем жизни

TTL обязателен: если клиент упадёт, лок должен освободиться сам. Вместе с локом выдаётся монотонно растущий номер — fencing token.

Stop-the-world пауза

Долгая сборка мусора, вытеснение виртуальной машины, сетевая задержка — процесс A «выключен» на 40 секунд и не знает об этом.

Лок освобождается по таймауту

Сервис блокировок не может отличить упавшего клиента от медленного.

B получает лок и токен 34

B законно начинает работу и пишет в хранилище, передавая свой токен. Хранилище запоминает наибольший виденный токен.

A продолжает с того же места

Проверка «лок ещё мой?» была выполнена до паузы. С точки зрения A прошло мгновение. Теперь два клиента одновременно считают себя владельцами — взаимное исключение нарушено.

Хранилище отклоняет устаревший токен

A пишет с токеном 33, хранилище уже видело 34 — запись отклонена. Безопасность обеспечивает не лок, а проверка токена на стороне ресурса (или условная запись по версии).

Вывод: распределённый лок с TTL годится для экономии работы (не запускать задачу дважды — не страшно, если иногда запустится). Для корректности нужна проверка на стороне хранилища: fencing token, оптимистичная версия, уникальный ключ.

14.6Идемпотентность — главный инструмент

Почему без неё никак

Сеть ненадёжна: клиент не получил ответ и повторил запрос; брокер доставил сообщение дважды; сработал ретрай. «Ровно один раз» по доставке недостижимо — достижимо «ровно один раз по эффекту».

Как сделать

Естественная идемпотентность (SET status = 'PAID' вместо balance += 100); ключ идемпотентности с уникальным индексом; таблица обработанных сообщений в одной транзакции с изменениями; условные обновления по версии.

14.7Самопроверка

Сервис в трёх экземплярах, метод помечен synchronized и @Transactional. Защищён ли остаток товара от гонки?

  • Да
  • Нет: монитор существует только в одном процессе, и даже в нём освобождается до коммита транзакции
  • Да, если БД PostgreSQL
  • Да, если метод static
Общее состояние в БД защищают средствами БД: атомарный UPDATE, блокировки строк, версии.

Когда оптимистичная блокировка лучше пессимистичной?

  • При частых конфликтах
  • Никогда
  • При редких конфликтах и длительном «времени на подумать» между чтением и записью
  • Только для чтения
Она не держит блокировок; цена — повтор при конфликте. При частых конфликтах повторы съедают выигрыш.

Как гарантировать, что email будет зарегистрирован не более одного раза при параллельных запросах?

  • Уникальным ограничением в БД и обработкой ошибки вставки
  • Проверкой existsByEmail перед вставкой
  • synchronized в сервисе
  • Кэшем занятых адресов
Проверка перед вставкой — check-then-act; только ограничение БД атомарно для несуществующей ещё строки.

Зачем fencing token в распределённой блокировке?

  • Для шифрования
  • Для ускорения получения лока
  • Чтобы продлевать TTL
  • Чтобы ресурс мог отклонить запись клиента, чей лок уже истёк, но который об этом не знает
Клиент не может надёжно узнать, что он всё ещё владелец; проверять должен ресурс.
Как защититься от потерянного обновления в БД?

Атомарный UPDATE с условием в WHERE; пессимистичная блокировка SELECT … FOR UPDATE; оптимистичная блокировка по версии с повтором; более строгий уровень изоляции с повтором транзакций при ошибке сериализации. Выбор — по частоте конфликтов и сложности логики.

Почему распределённый лок на Redis не гарантирует взаимное исключение?

Лок с TTL может истечь, пока владелец в паузе (GC, сеть), и перейти другому; владелец об этом не узнает. Плюс отказоустойчивость самого Redis (асинхронная репликация теряет лок при failover). Для корректности нужен fencing token или условная запись на стороне хранилища.

Как сделать обработчик сообщений идемпотентным?

У сообщения уникальный id; в одной транзакции с бизнес-изменениями вставить id в таблицу обработанных (уникальный индекс); при нарушении уникальности — пропустить. Или сделать само действие идемпотентным: upsert, установка состояния, условное обновление.
