11.1Deadlock

Взаимная блокировка возникает, только когда одновременно выполнены все четыре условия Коффмана: (1) взаимное исключение, (2) удержание и ожидание (держу A, жду B), (3) нет принудительного отбора ресурса, (4) циклическое ожидание. Достаточно сломать любое — на практике ломают (4) или (2).

public void transfer(Account from, Account to, BigDecimal amount) {
    synchronized (from) {
        synchronized (to) {               // transfer(a,b) || transfer(b,a) → deadlock
            from.debit(amount);
            to.credit(amount);
        }
    }
}
public void transfer(Account from, Account to, BigDecimal amount) {
    if (from.id() == to.id()) throw new IllegalArgumentException("same account");
    Account first  = from.id() < to.id() ? from : to;   // всегда сначала меньший id
    Account second = first == from ? to : from;
    synchronized (first) {
        synchronized (second) {
            from.debit(amount);
            to.credit(amount);
        }
    }
}
// Нет уникального ключа? System.identityHashCode + отдельный «tie-breaker» лок при равенстве (JCiP 10.1.2).

11.2Livelock, starvation и голодание пула

Livelock

Потоки не заблокированы, но бесконечно уступают друг другу: оба сделали tryLock, оба откатились, оба повторили одновременно. Лечится случайной задержкой (jitter) перед повтором.

Starvation

Поток постоянно проигрывает конкуренцию: несправедливый лок, писатель в RW-локе при потоке читателей, низкий приоритет. Лечится fair-режимом или перепроектированием.

Thread starvation deadlock

Задачи пула ждут результатов других задач того же пула, а свободных потоков нет. Локов нет, а система стоит. Классика с future.get()/join() внутри задачи.

11.5Тестирование конкурентного кода

Обычный юнит-тест запускает код один раз на одном расписании потоков — он почти никогда не ловит гонку. Нужны: множество повторений с максимальной конкуренцией, проверки инвариантов, специальные инструменты.

Стресс-тест со «стартовым пистолетом»

@RepeatedTest(50)
void concurrentIncrementsAreNotLost() throws Exception {
    Counter counter = new Counter();
    int threads = 16, perThread = 10_000;
    CountDownLatch start = new CountDownLatch(1);
    try (ExecutorService pool = Executors.newFixedThreadPool(threads)) {
        List<Future<?>> fs = new ArrayList<>();
        for (int t = 0; t < threads; t++) {
            fs.add(pool.submit(() -> {
                start.await();                              // все стартуют одновременно
                for (int i = 0; i < perThread; i++) counter.increment();
                return null;
            }));
        }
        start.countDown();
        for (Future<?> f : fs) f.get(10, TimeUnit.SECONDS); // пробрасывает исключения потоков в тест
    }
    assertEquals((long) threads * perThread, counter.get());
}
  • Потоков больше, чем ядер — больше переключений и чередований.
  • Всегда future.get() — иначе AssertionError в потоке пула не провалит тест.
  • Асинхронные ожидания — через Awaitility (await().atMost(2, SECONDS).until(...)), а не Thread.sleep.
  • Время — через инжектируемый Clock, как в вашем RateLimiter: тест управляет временем детерминированно.

jcstress: проверка на уровне модели памяти

OpenJDK-инструмент, который запускает крошечные «акторы» миллионы раз в разных потоках и собирает все наблюдённые результаты. Только так можно увидеть переупорядочивания, которые разрешает JMM.

JMH: производительность

Сравнение synchronized / ReentrantLock / AtomicLong / LongAdder делайте только в JMH с @Threads(N) и @State(Scope.Benchmark): прогрев JIT, защита от dead-code elimination, форки JVM. Самописный цикл с System.nanoTime измеряет что угодно, кроме того, что вы хотите.

11.6Чек-лист code review

  1. Для каждого общего изменяемого поля понятно, каким механизмом обеспечен HB (аннотируйте: @GuardedBy("lock")).
  2. Нет check-then-act и read-modify-write вне лока/атомарной операции.
  3. Несколько локов — задокументирован порядок захвата; под локом не вызывается чужой код.
  4. unlock(), release(), countDown(), ThreadLocal.remove() — в finally.
  5. InterruptedException не проглатывается.
  6. Все пулы: ограниченная очередь, именованные потоки, политика отказа, graceful shutdown.
  7. Нет блокирующих вызовов в commonPool, event loop и под локом бакета CHM.
  8. У каждого ожидания есть таймаут.
  9. Исключения из асинхронных задач кто-то логирует или обрабатывает.

11.8Самопроверка

Какие условия нужны для deadlock (условия Коффмана)?

  • Достаточно двух потоков
  • Взаимное исключение, удержание и ожидание, отсутствие вытеснения, циклическое ожидание — все четыре сразу
  • Только циклическое ожидание
  • Нехватка памяти
Сломайте любое: порядок блокировок (нет цикла), tryLock с таймаутом (есть «вытеснение»), один лок (нет удержания и ожидания).

Приложение не отвечает, CPU 0%. Что сделать первым?

  • Перезапустить
  • Увеличить heap
  • Снять thread dump (jstack / jcmd Thread.print) — он покажет, чего ждут потоки, и сам найдёт deadlock мониторов
  • Включить GC-логи
Сначала сохранить диагностику, потом перезапуск. Лучше два-три дампа с интервалом.

Чем livelock отличается от deadlock?

  • Потоки не заблокированы и активно работают, но бесконечно уступают друг другу и не продвигаются
  • Это одно и то же
  • Livelock бывает только с одним потоком
  • При livelock CPU 0%
В дампе потоки RUNNABLE, CPU загружен. Лечится случайной задержкой (jitter) перед повтором.
Назовите четыре условия deadlock и способ сломать каждое.

Взаимное исключение — неизменяемые/lock-free структуры. Удержание и ожидание — захватывать всё сразу или tryLock с откатом. Отсутствие отбора — таймауты и отмена (в БД — жертва deadlock откатывается). Циклическое ожидание — глобальный порядок захвата.

Сервис «завис», CPU 0%. Ваши действия?

Несколько thread dump'ов с интервалом; поиск «Found one Java-level deadlock»; группировка потоков по стекам: где все ждут — пул соединений, внешний HTTP без таймаута, монитор, Future.get в задачах пула (голодание). Параллельно метрики пулов (active/queue), соединений БД, downstream-латентность. Затем исправление и тест, воспроизводящий сценарий.

Почему тест «запустить 2 потока и проверить результат» почти всегда проходит даже на неправильном коде?

Потоки стартуют с задержкой, первый успевает закончить до старта второго — пересечения нет. Окно гонки — наносекунды. Нужно много итераций, синхронный старт (latch), больше потоков, чем ядер; для эффектов модели памяти — jcstress.

Что такое open call и почему это важно?

Вызов внешнего (чужого, переопределяемого, удалённого) метода без удержания локов. Если вызывать чужой код под своим локом, неизвестно, какие локи он возьмёт — легко получить цикл и deadlock, плюс лок удерживается неопределённо долго. Порядок: под локом скопировать нужное состояние, выйти, вызвать внешний код.
