Синхронизаторы

Готовые объекты, которые координируют потоки по состоянию, а не защищают данные: «подожди, пока N событий не произойдёт», «не больше K одновременно», «все дошли до точки — идём дальше».

6.2CountDownLatch

public static long timeTasks(int nThreads, Runnable task) throws InterruptedException {
    CountDownLatch startGate = new CountDownLatch(1);
    CountDownLatch endGate = new CountDownLatch(nThreads);

    for (int i = 0; i < nThreads; i++) {
        Thread.ofPlatform().start(() -> {
            try {
                startGate.await();          // все ждут одного сигнала — максимальная конкуренция
                try { task.run(); }
                finally { endGate.countDown(); }  // в finally: иначе при исключении await зависнет
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });
    }
    long start = System.nanoTime();
    startGate.countDown();                  // «марш!»
    endGate.await();                        // ждём всех
    return System.nanoTime() - start;
}
  • countDown() HB возврата из await() — результаты участников видны.
  • await(timeout, unit) возвращает false по таймауту — используйте в продакшене, бесконечное ожидание опасно.
  • Счётчик нельзя увеличить или сбросить. Нужен сброс — CyclicBarrier/Phaser.

6.3Semaphore

Набор из N разрешений. acquire() берёт одно (ждёт, если нет), release() возвращает. Разрешения не привязаны к потоку: вернуть может другой поток. Semaphore(1) — мьютекс без владельца и без реентерабельности.

public final class PaymentGatewayClient {
    private final Semaphore permits = new Semaphore(10);
    private final HttpClient http;

    public PaymentGatewayClient(HttpClient http) { this.http = http; }

    public Response pay(Request req) throws InterruptedException, TimeoutException {
        if (!permits.tryAcquire(200, TimeUnit.MILLISECONDS)) {
            throw new TimeoutException("bulkhead full");   // быстрый отказ вместо очереди без конца
        }
        try {
            return http.send(req);
        } finally {
            permits.release();                              // строго в finally
        }
    }
}
Типичные ошибки
  • release() без парного acquire() увеличивает число разрешений сверх начального — лимит тихо «расползается».
  • Semaphore ограничивает конкурентность, а не частоту (RPS). Для RPS нужен rate limiter (токен-бакет, sliding window — задача в теме 12; в продакшене — Resilience4j RateLimiter/Bulkhead).

6.4CyclicBarrier

static volatile boolean stop;              // поле класса: лямбды читают актуальное значение

int parts = Runtime.getRuntime().availableProcessors();
double[][] grid = initGrid();
CyclicBarrier barrier = new CyclicBarrier(parts, () -> {
    // barrierAction: выполняет последний пришедший поток, пока остальные ждут
    swapBuffers();
    if (converged()) stop = true;
});

for (int p = 0; p < parts; p++) {
    int part = p;
    Thread.ofPlatform().start(() -> {
        try {
            while (!stop) {
                computePart(grid, part);   // каждый считает свою полосу
                barrier.await();           // ждём остальных перед следующей итерацией
            }
        } catch (InterruptedException | BrokenBarrierException e) {
            // если один участник прервался/упал, барьер «ломается» для всех
        }
    });
}

BrokenBarrierException: если любой участник прерван, получил таймаут или barrierAction бросил исключение, барьер переходит в сломанное состояние, и все ожидающие сразу получают исключение. Это защищает от вечного ожидания «пропавшего» участника. reset() чинит барьер.

6.5Phaser

Обобщение латча и барьера: участники регистрируются и уходят динамически, фазы нумеруются, можно переопределить onAdvance для завершения.

Phaser phaser = new Phaser(1);              // 1 = координатор (main)
for (Task t : tasks) {
    phaser.register();                      // +1 участник
    executor.submit(() -> {
        t.stage1();
        phaser.arriveAndAwaitAdvance();     // барьер фазы 0
        t.stage2();
        phaser.arriveAndDeregister();       // ушёл, больше не ждём его
    });
}
phaser.arriveAndAwaitAdvance();            // main ждёт конца фазы 0
phaser.arriveAndDeregister();              // main больше не участвует

На практике Phaser встречается редко; на собеседовании достаточно объяснить, чем он отличается от CyclicBarrier (динамический состав, номер фазы, иерархия phaser'ов для снижения конкуренции).

6.6Exchanger

Точка встречи двух потоков: каждый отдаёт объект и получает объект партнёра. Классика — двойная буферизация: producer заполняет буфер, consumer опустошает, затем меняются.

Exchanger<ByteBuffer> ex = new Exchanger<>();
// producer:  full = fill(buf); buf = ex.exchange(full);   // отдал полный, получил пустой
// consumer:  empty = drain(buf); buf = ex.exchange(empty);

6.8Самопроверка

Чем CountDownLatch отличается от CyclicBarrier?

  • Ничем
  • Latch одноразовый: одни потоки ждут, другие уменьшают счётчик; Barrier переиспользуемый: потоки ждут друг друга в общей точке
  • Barrier одноразовый
  • Latch работает только с двумя потоками
Latch — «дождаться N событий», Barrier — «собраться всем вместе и пойти дальше», повторяемо.

Можно ли использовать Semaphore(1) как замену ReentrantLock?

  • Да, полностью
  • Нет, он не блокирует
  • С оговорками: он не реентерабелен (повторный acquire того же потока зависнет) и release может вызвать не владелец
  • Да, он быстрее
Бинарный семафор — не мьютекс с владельцем.

Поток вызвал latch.await() без таймаута, а один из рабочих потоков упал, не вызвав countDown(). Что будет?

  • Ожидающий поток зависнет навсегда
  • await() бросит исключение
  • Счётчик уменьшится автоматически
  • JVM завершится
countDown() — всегда в finally, await — с таймаутом.
Чем CountDownLatch принципиально отличается от CyclicBarrier?

Latch одноразовый, и те, кто вызывает countDown, не ждут — ждут наблюдатели в await. Barrier многоразовый, его участники сами ждут друг друга в await; есть barrierAction и «поломка» при сбое любого участника.

Почему countDown() надо ставить в finally?

Если задача бросит исключение, счётчик не уменьшится, и await() без таймаута зависнет навсегда. В finally счётчик уменьшается в любом случае; об ошибке нужно сообщить отдельно (сохранить исключение в общую коллекцию или использовать CompletableFuture).

Чем Semaphore(1) отличается от ReentrantLock?

У семафора нет владельца: release может вызвать любой поток, повторный acquire тем же потоком заблокирует его (не реентерабелен), нет Condition. Зато подходит для сценариев «взял в одном потоке, отпустил в другом» (например, в колбэке асинхронного вызова).

Нужно не более 100 запросов в секунду к API. Подойдёт ли Semaphore(100)?

Нет. Он ограничит число одновременных запросов. Если запрос длится 10 мс, через 100 разрешений пройдёт до 10 000 запросов в секунду. Нужен rate limiter: токен-бакет или скользящее окно с временными метками.
