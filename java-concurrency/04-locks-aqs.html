Lock, Condition и AQS

Явные локи из java.util.concurrent.locks дают то, чего нет у synchronized: таймауты, прерываемость, несколько условий, разделение чтения и записи. Все они построены на одном фундаменте — AbstractQueuedSynchronizer. Поняв AQS, вы понимаете половину пакета.

4.1Интерфейс Lock и обязательная идиома

private final ReentrantLock lock = new ReentrantLock();

public void transfer(Account to, long amount) {
    lock.lock();            // ДО try: если lock() бросит, unlock вызывать нельзя
    try {
        // критическая секция
    } finally {
        lock.unlock();      // всегда, иначе лок утечёт навсегда
    }
}

public boolean transfer(Account from, Account to, long amount, long timeoutMs)
        throws InterruptedException {
    long deadline = System.nanoTime() + TimeUnit.MILLISECONDS.toNanos(timeoutMs);
    while (true) {
        if (from.lock.tryLock()) {
            try {
                if (to.lock.tryLock()) {
                    try {
                        if (from.balance < amount) return false;
                        from.balance -= amount;
                        to.balance += amount;
                        return true;
                    } finally { to.lock.unlock(); }
                }
            } finally { from.lock.unlock(); }
        }
        if (System.nanoTime() > deadline) return false;
        Thread.sleep(ThreadLocalRandom.current().nextInt(1, 5)); // случайная пауза против livelock
    }
}

Альтернатива проще — глобальный порядок захвата (например, по id счёта), см. тему 11. tryLock полезен, когда порядок задать нельзя.

Справедливость (fairness)

new ReentrantLock(true) — потоки получают лок в порядке очереди. По умолчанию — несправедливый: пришедший поток может «перехватить» (barging) лок у того, кто ждёт в очереди. Это кажется нечестным, но даёт в разы большую пропускную способность: разбудить припаркованный поток — микросекунды, а пришедший уже на CPU. Fair-лок нужен редко: когда голодание недопустимо и важнее предсказуемость задержек.

4.2Condition: несколько очередей ожидания

Condition — аналог wait/notify, но у одного лока их может быть сколько угодно. Producer'ы ждут notFull, consumer'ы — notEmpty, и signal() будит ровно того, кого нужно.

public final class BoundedBuffer<T> {
    private final Object[] items;
    private int head, tail, count;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull  = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();

    public BoundedBuffer(int capacity) { items = new Object[capacity]; }

    public void put(T x) throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (count == items.length) notFull.await();
            items[tail] = x;
            if (++tail == items.length) tail = 0;
            count++;
            notEmpty.signal();          // signal, а не signalAll: ждут однородные consumer'ы
        } finally { lock.unlock(); }
    }

    @SuppressWarnings("unchecked")
    public T take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (count == 0) notEmpty.await();
            T x = (T) items[head];
            items[head] = null;
            if (++head == items.length) head = 0;
            count--;
            notFull.signal();
            return x;
        } finally { lock.unlock(); }
    }

    public boolean offer(T x, long timeout, TimeUnit unit) throws InterruptedException {
        long nanos = unit.toNanos(timeout);
        lock.lockInterruptibly();
        try {
            while (count == items.length) {
                if (nanos <= 0) return false;
                nanos = notFull.awaitNanos(nanos);  // возвращает остаток времени
            }
            items[tail] = x;
            if (++tail == items.length) tail = 0;
            count++;
            notEmpty.signal();
            return true;
        } finally { lock.unlock(); }
    }
}
Правила те же, что для wait: await/signal только под локом-владельцем, условие в while. Не перепутайте condition.await() с унаследованным от Object condition.wait() — второе бросит IllegalMonitorStateException.

4.3ReentrantReadWriteLock

Много читателей одновременно ИЛИ один писатель. Выгоден, когда чтений намного больше, чем записей, и критическая секция чтения не микроскопическая (иначе накладные расходы съедят выигрыш).

public final class RateCache {
    private final Map<String, BigDecimal> rates = new HashMap<>();
    private final ReentrantReadWriteLock rw = new ReentrantReadWriteLock();

    public BigDecimal get(String ccy) {
        rw.readLock().lock();
        try { return rates.get(ccy); } finally { rw.readLock().unlock(); }
    }
    public void putAll(Map<String, BigDecimal> fresh) {
        rw.writeLock().lock();
        try { rates.clear(); rates.putAll(fresh); } finally { rw.writeLock().unlock(); }
    }
}

Downgrade — можно

Держа write, взять read, затем отпустить write. Так вы публикуете изменение и продолжаете читать без окна, в которое вклинится другой писатель.

Upgrade — deadlock

Держа read, вызвать writeLock().lock() — поток ждёт, пока все читатели уйдут, включая его самого. Вечное ожидание. Если два потока так сделают — тем более.

Для примера выше в реальном коде проще и быстрее: volatile Map с подменой неизменяемого снимка (Map.copyOf) — читатели вообще без локов. RW-лок нужен, когда состояние нельзя дёшево скопировать.

4.4StampedLock: оптимистичное чтение

JDK 8. Три режима: write, read и optimistic read — вообще без захвата: берём «штамп» (версию), читаем поля в локальные переменные, затем проверяем, не было ли записи. Читатели не пишут в общую память → нет cache-line ping-pong.

public final class Point {
    private double x, y;
    private final StampedLock sl = new StampedLock();

    public void move(double dx, double dy) {
        long stamp = sl.writeLock();
        try { x += dx; y += dy; } finally { sl.unlockWrite(stamp); }
    }

    public double distanceFromOrigin() {
        long stamp = sl.tryOptimisticRead();     // 0, если сейчас держат write
        double cx = x, cy = y;                   // копируем в локальные!
        if (!sl.validate(stamp)) {               // была запись — данные могли быть несогласованны
            stamp = sl.readLock();               // откат на пессимистичное чтение
            try { cx = x; cy = y; } finally { sl.unlockRead(stamp); }
        }
        return Math.hypot(cx, cy);               // работаем только с копиями
    }
}
Ограничения StampedLock Не реентерабелен (повторный writeLock в том же потоке — самоблокировка), нет Condition, нет владельца (unlock по штампу из любого потока). В оптимистичной ветке нельзя делать ничего, что сломается на несогласованных данных (разыменовать ссылку, которая может быть null, индексировать массив) — до validate данные считаются мусором.

4.5AQS изнутри

AbstractQueuedSynchronizer — каркас для синхронизаторов. Он хранит:

  • volatile int state — смысл задаёт подкласс: у ReentrantLock — счётчик захватов (0 = свободен), у Semaphore — число разрешений, у CountDownLatch — оставшийся счёт, у ReentrantReadWriteLock — старшие 16 бит читатели, младшие 16 — писатель.
  • FIFO-очередь ожидающих — вариант CLH-очереди: двусвязный список узлов с head/tail, вставка через CAS в tail.
  • Владельца в эксклюзивном режиме (exclusiveOwnerThread).

Алгоритм acquire (упрощённо)

  1. tryAcquire(arg) — метод подкласса: попытка CAS на state. Успех → вошли, очередь не трогаем (быстрый путь без конкуренции).
  2. Неудача → создать узел, CAS-ом прицепить к tail.
  3. Если узел — первый после head, ещё раз попробовать tryAcquire (лок мог освободиться).
  4. Иначе пометить предшественника «разбуди меня» и LockSupport.park(this).
  5. После unpark — повторить с шага 3. Успех → наш узел становится новым head.

Release: tryRelease(arg) подкласса уменьшает state; если лок полностью свободен — разбудить преемника head. Shared-режим (acquireShared, используют Semaphore, CountDownLatch, read-lock) отличается тем, что пробуждение распространяется по цепочке: проснувшийся будит следующего, если ресурса хватает.

LockSupport: park / unpark

Примитив под AQS. У каждого потока есть один «пропуск» (permit), максимум 1. unpark(t) выдаёт пропуск; park() поглощает его и возвращается сразу, если он есть, иначе блокирует поток. Поэтому unpark до park не теряется — в отличие от notify до wait. park может вернуться и без причины (spurious) — вызывающий обязан перепроверить условие в цикле.

4.6Пишем свой синхронизатор на AQS

Подкласс переопределяет только tryAcquire/tryRelease (эксклюзивный режим) или tryAcquireShared/tryReleaseShared (разделяемый). Очередь, парковка, таймауты и прерывания — бесплатно.

public final class Mutex {
  private static final class Sync
      extends AbstractQueuedSynchronizer {
    @Override protected boolean tryAcquire(int a) {
      if (compareAndSetState(0, 1)) {
        setExclusiveOwnerThread(
            Thread.currentThread());
        return true;
      }
      return false;
    }
    @Override protected boolean tryRelease(int a) {
      if (getState() == 0)
        throw new IllegalMonitorStateException();
      setExclusiveOwnerThread(null);
      setState(0);   // volatile write = release
      return true;
    }
  }
  private final Sync sync = new Sync();
  public void lock()   { sync.acquire(1); }
  public void unlock() { sync.release(1); }
  public boolean tryLock(long t, TimeUnit u)
      throws InterruptedException {
    return sync.tryAcquireNanos(1, u.toNanos(t));
  }
}
public final class OneShotLatch {
  private static final class Sync
      extends AbstractQueuedSynchronizer {
    // >= 0 — пропускаем, < 0 — в очередь
    @Override protected int tryAcquireShared(int a) {
      return getState() == 1 ? 1 : -1;
    }
    @Override protected boolean tryReleaseShared(int a) {
      setState(1);    // открыто навсегда
      return true;    // разбудить всех
    }
  }
  private final Sync sync = new Sync();

  public void signal() {
    sync.releaseShared(0);
  }
  public void await() throws InterruptedException {
    sync.acquireSharedInterruptibly(0);
  }
}

Сравните с CountDownLatch: это та же схема, только state = счётчик, а tryReleaseShared делает CAS-декремент и возвращает true, когда дошли до нуля.

4.8Интерактив: очередь AQS внутри ReentrantLock

Симулятор ReentrantLock

state — счётчик захватов (0 — свободен), owner — поток-владелец, очередь — узлы AQS со спящими (park) потоками.

state / owner
Очередь AQS (head → tail)

Сценарий barging: T1 берёт лок, T2 встаёт в очередь, T1 делает unlock() (T2 разбужен), и в этот момент T3 вызывает lock(). В нечестном режиме T3 выигрывает CAS, пока T2 ещё просыпается. Включите честный режим и повторите — T3 встанет в очередь.

4.9Самопроверка

Почему lock.unlock() пишут в finally?

  • Это требование компилятора
  • В отличие от synchronized, Lock не освобождается автоматически при исключении — лок останется захваченным навсегда
  • Так быстрее
  • Чтобы избежать реентерабельности
Идиома: lock.lock(); try { … } finally { lock.unlock(); } — и lock() ДО try.

Чем ReentrantLock лучше synchronized?

  • Он всегда быстрее
  • Он не может вызвать deadlock
  • tryLock с таймаутом, прерываемое ожидание, честность, несколько Condition
  • Он не требует unlock
Если эти возможности не нужны, synchronized проще и безопаснее от ошибок.

Что хранит поле state в AQS для ReentrantLock и Semaphore?

  • Число повторных захватов владельцем / число оставшихся разрешений
  • Идентификатор потока
  • Длину очереди
  • Время захвата
AQS даёт очередь и park/unpark, а смысл state определяет конкретный синхронизатор в tryAcquire/tryRelease.
Почему lock.lock() пишут до try, а не внутри?

Если lock() внутри try бросит исключение (например, lockInterruptibly — InterruptedException), выполнится finally { unlock(); } для лока, который мы не захватили → IllegalMonitorStateException, маскирующий исходную ошибку (или, хуже, освобождение чужого захвата при реентерабельности).

Почему несправедливый лок быстрее справедливого?

При освобождении fair-лок обязан отдать его первому в очереди, а тот припаркован: пока ОС его разбудит и он попадёт на CPU (микросекунды), лок простаивает. Unfair позволяет уже работающему потоку захватить лок немедленно (barging), используя это «мёртвое» время. Цена — возможное голодание отдельных потоков.

Что хранит state в AQS у ReentrantLock, Semaphore, CountDownLatch и ReentrantReadWriteLock?

ReentrantLock — число повторных захватов владельцем (0 = свободен). Semaphore — доступные разрешения. CountDownLatch — оставшийся счёт до нуля. RRWL — int поделён: старшие 16 бит — число read-захватов, младшие 16 — write-захватов (реентерабельных).

Чем park/unpark лучше wait/notify для построения синхронизаторов?

Не нужен монитор; можно будить конкретный поток; permit «запоминает» unpark, сделанный раньше park, поэтому нет гонки lost wake-up между проверкой условия и засыпанием. Вся логика очереди — в обычных объектах с CAS.

Как реализовать кэш с редкой полной перезагрузкой и частым чтением? Предложите 3 варианта и сравните.

(1) volatile-ссылка на неизменяемую Map.copyOf, перезагрузка подменяет ссылку — чтения без локов, самый быстрый вариант, цена — копия при обновлении. (2) ReentrantReadWriteLock — подходит, если данные огромные и меняются частично. (3) ConcurrentHashMap с поэлементным обновлением — но читатель может увидеть смесь старых и новых курсов (нет атомарности снимка). Для курсов валют в финтехе обычно (1): снимок должен быть согласованным.

Почему в optimistic read нужно копировать поля в локальные переменные до validate?

validate(stamp) проверяет, что с момента выдачи штампа не было записи. Если читать поля после проверки, запись может произойти уже после неё. Поэтому: прочитать всё в локальные → validate → работать только с копиями. Кроме того, между чтениями x и y могла вклиниться запись — validate отловит и эту несогласованность.
