Пулы потоков — простыми словами

Создавать новый поток на каждую задачу дорого и опасно. Поэтому задачи отдают пулу. Разберёмся, зачем нужны пулы, как устроен ThreadPoolExecutor, по какому алгоритму он принимает задачи, чем опасны готовые фабрики, что делать при переполнении, как выбрать размер и куда пропадают исключения.

8.1Зачем пулы

Нанимать нового рабочего на каждую мелкую задачу и увольнять после — долго и дорого. Лучше держать бригаду и очередь заданий. Пул даёт: переиспользование потоков (создание потока дорогое), ограничение их числа (тысяча потоков задушат машину) и управление: очередь, отказ при перегрузке, корректная остановка.

Главная мысль Пул = бригада потоков + очередь задач + правила перегрузки.

8.2Жизненный цикл пула

Задачи отдают через execute (без результата) или submit (с результатом — Future). Пул нужно останавливать: shutdown() — «новых не принимаем, доделываем начатое», затем awaitTermination — подождать. shutdownNow() — «срочно прерываем всех». Забытый пул держит потоки, и программа может не завершиться.

Главная мысль submit — с результатом, shutdown + awaitTermination — корректная остановка.

8.3Алгоритм приёма задачи

У ThreadPoolExecutor есть «основная бригада» (core), очередь и «временные работники» (до max). Порядок неочевидный, его спрашивают на собеседованиях:

Пришла новая задача: core = 2, очередь = 3 места, max = 4
1. работников меньше core (2)? → нанять нового под эту задачу2. core заняты → положить задачу в очередь (если есть место)3. очередь полна → нанять временного, пока работников меньше max (4)4. и очередь полна, и работников max → ОТКАЗ (политика reject)
временные увольняются, если долго простаивают

Сначала набирается core.

Потом задачи копятся в очереди, а не нанимаются новые.

Временные работники появляются, только когда очередь заполнена.

Всё полно — срабатывает политика отказа.

Отсюда ловушка: с бесконечной очередью шаг 3 никогда не наступит — пул никогда не вырастет выше core, а очередь будет расти до нехватки памяти.

Главная мысль core → очередь → временные до max → отказ. С бесконечной очередью max не работает.

8.4Ловушки готовых фабрик

  • newFixedThreadPool — фиксированная бригада и бесконечная очередь: при перегрузке задачи копятся до OutOfMemoryError.
  • newCachedThreadPool — нанимает без ограничения: при наплыве создаст тысячи потоков.

Для серверного кода лучше создавать ThreadPoolExecutor явно, с ограниченной очередью и понятной политикой отказа.

Главная мысль Готовые фабрики прячут бесконечность. Ограничивайте очередь или число потоков.

8.5Что делать при перегрузке

ПолитикаЧто делает
Abort (по умолчанию)бросает исключение — вызывающий узнаёт о перегрузке
CallerRunsзадачу выполняет сам отправитель — естественно его замедляет
Discard / DiscardOldestтихо выбрасывает задачу — опасно, если задачи важны
Главная мысль CallerRuns — простое обратное давление. Тихо выбрасывать — только неважное.

8.6Размер пула

Если задачи считают (процессор) — потоков примерно по числу ядер. Если задачи в основном ждут (база, сеть) — потоков нужно больше: пока одни ждут, другие работают. Приближённая формула: ядра × (1 + время ожидания / время работы). Но лучший ответ — замер под нагрузкой. А для задач с ожиданием сегодня часто проще виртуальные потоки (глава 10).

Главная мысль Счёт — по числу ядер, ожидание — больше. Проверяйте замером.

В полной главе: 8.6 Размер пула

8.7Куда пропадают исключения

Если задача отправлена через submit и упала, исключение тихо сохраняется внутри Future. Пока никто не вызовет get(), о нём никто не узнает — в логах пусто. Через execute исключение хотя бы напечатается. Правило: ловите и логируйте ошибки внутри задачи или обязательно проверяйте результат Future.

Главная мысль submit прячет исключения в Future. Логируйте внутри задачи.

В полной главе: 8.7 Исключения и задачи

8.8ForkJoinPool и кража работы

ForkJoinPool — особый пул для задач «раздели пополам и реши части». У каждого работника своя стопка задач; освободившийся работник крадёт задачи из чужой стопки — никто не сидит без дела. На нём работают параллельные стримы и асинхронные операции CompletableFuture по умолчанию (общий пул). Блокирующие операции в общем пуле — плохая идея: они занимают и без того немногочисленных работников.

Главная мысль ForkJoinPool — для деления задач; не блокируйте общий пул.

8.10Проверьте себя

core = 4, max = 20, очередь бесконечная. Сколько потоков будет при большой нагрузке?

  • 20
  • сколько угодно
  • 4: временные нанимаются, только когда очередь полна, а она никогда не заполнится
  • 0
Классическая ловушка конфигурации.

Чем опасен Executors.newFixedThreadPool под перегрузкой?

  • бесконечная очередь копит задачи до нехватки памяти
  • создаёт тысячи потоков
  • сразу отказывает
  • ничем
Ограничивайте очередь.

Задача, отправленная через submit, бросила исключение. Где оно?

  • в логах
  • оно уронило программу
  • потерялось навсегда
  • сохранено внутри Future и всплывёт при get()
Если get не вызвать — о нём никто не узнает.

Какая политика отказа заставляет отправителя притормозить?

  • Abort
  • CallerRuns
  • Discard
  • DiscardOldest
Отправитель сам выполняет задачу и не успевает слать новые.

Задачи в основном ждут ответа базы. Сколько потоков в пуле?

  • ровно по числу ядер
  • один
  • больше числа ядер — пока одни ждут, другие работают (или виртуальные потоки)
  • тысячи всегда
Для ожидания нужно больше исполнителей.
