Future и CompletableFuture — простыми словами

Как запустить задачу и получить её результат позже, не простаивая в ожидании? Разберёмся, что умеет обычный Future и чего ему не хватает, как CompletableFuture собирает цепочки асинхронных шагов, в каком потоке выполняются эти шаги, как обрабатывать ошибки, отменять и ставить таймауты.

9.1Future: квитанция

Отдали задачу пулу — получили Future, как квитанцию в химчистке. Результат можно забрать get(), но если он не готов, вы будете стоять у окошка и ждать (поток блокируется). Нельзя сказать «когда будет готово — сделай вот это», нельзя удобно объединить несколько квитанций.

Главная мысль Future — результат в будущем, но забрать можно только ожиданием.

9.2Создание CompletableFuture

supplyAsync(задача) — запустить задачу с результатом в фоне, runAsync — без результата. Обязательно передавайте свой пул вторым аргументом: по умолчанию используется общий ForkJoinPool, маленький и общий для всего приложения — блокирующие задачи (база, сеть) его быстро забьют.

Главная мысль supplyAsync со своим пулом — особенно для задач с ожиданием.

9.4В каком потоке выполнится шаг

Неочевидная вещь: thenApply без суффикса Async выполнится либо в том потоке, который завершил предыдущий шаг, либо — если результат уже был готов — прямо в потоке, который вызвал thenApply. Варианты ...Async отправляют шаг в пул. Если шаг тяжёлый или блокирующий — используйте Async со своим пулом, чтобы не занимать чужой поток.

Главная мысль Без Async — «в каком-то из уже работающих потоков». Тяжёлые шаги — Async со своим пулом.

9.5Ошибки

Если шаг упал, ошибка «едет» по цепочке, пропуская обычные шаги, до первого обработчика: exceptionally (заменить ошибку значением по умолчанию), handle (получить и результат, и ошибку), whenComplete (посмотреть, но не менять). Без обработчика ошибка тихо лежит внутри future, пока кто-нибудь не вызовет join/get.

Главная мысль Ошибка пропускает шаги до exceptionally/handle. Не оставляйте цепочку без обработчика.

9.6Отмена и таймауты

orTimeout — завершить ошибкой, если не успели; completeOnTimeout — подставить запасное значение. Важно: cancel у CompletableFuture не прерывает уже работающую задачу — он лишь помечает результат как отменённый. Задача может продолжать тратить ресурсы.

Главная мысль Таймауты ставьте всегда. cancel не останавливает уже запущенную работу.

В полной главе: 9.6 Отмена и таймауты

9.7Частые ошибки

  • Блокирующие задачи в общем пуле по умолчанию.
  • get()/join() сразу после запуска — асинхронность пропала.
  • thenApply вместо thenCompose — получается «future внутри future».
  • Нет обработки ошибок и таймаутов.
Главная мысль Свой пул, никаких get посреди цепочки, ошибки и таймауты — обязательно.

9.9Проверьте себя

Чего не умеет обычный Future?

  • хранить результат
  • выполнить действие по готовности без блокирующего ожидания
  • сообщить, готов ли результат
  • отменить задачу
Только get с ожиданием.

Почему для запросов к базе в supplyAsync нужно передавать свой пул?

  • иначе не скомпилируется
  • так быстрее считается
  • общий пул по умолчанию маленький и делится со всем приложением — блокирующие задачи его забьют
  • не нужно
Общий ForkJoinPool рассчитан на вычисления.

Нужно по id заказа асинхронно получить пользователя, а по нему — асинхронно адрес. Какой метод соединяет шаги?

  • thenCompose
  • thenApply
  • thenAccept
  • allOf
thenApply дал бы future внутри future.

Что сделает cancel(true) у CompletableFuture с уже работающей задачей?

  • прервёт её поток
  • удалит задачу из памяти
  • перезапустит её
  • только пометит результат отменённым, задача может продолжить работу
Остановка работы — отдельная забота.

Шаг цепочки бросил исключение. Что будет с последующими thenApply?

  • выполнятся как обычно
  • программа упадёт
  • пропустятся до ближайшего exceptionally/handle
  • повторятся
