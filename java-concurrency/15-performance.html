ТЕМА 15 · КОНКУРЕНТНОСТЬ В СИСТЕМЕ

Производительность конкурентного кода

Добавили потоков — стало медленнее. Это обычная история: параллелизм упирается в последовательную часть программы, в блокировки, в кэш процессора. Разберём два закона, которые предсказывают предел масштабирования, источники накладных расходов, приёмы снижения конкуренции и способ измерять всё это без самообмана — JMH.

15.1Пределы масштабирования

Закон Амдала: если доля p программы выполняется параллельно, а остальное — последовательно, то ускорение на N ядрах не больше 1 / ((1 − p) + p / N). При бесконечном числе ядер — не больше 1 / (1 − p).

Универсальный закон масштабируемости (USL) Гюнтера добавляет второй тормоз — согласование между потоками (инвалидация кэшей, обмен данными): C(N) = N / (1 + α(N − 1) + βN(N − 1)). Из-за слагаемого с β пропускная способность после некоторого N начинает падать.

Калькулятор масштабирования

Попробуйте: последовательная доля 5% — и 64 ядра дают всего ×15. Доля 1% — уже ×39. Каждый процент времени под общей блокировкой стоит дороже, чем кажется.

15.3Как снижать конкуренцию за блокировку

public synchronized Report build(String userId) {
    User u = users.get(userId);
    List<Order> orders = httpClient.fetchOrders(userId);     // сетевой вызов под блокировкой: все ждут
    stats.merge(u.region(), 1, Integer::sum);
    return render(u, orders);                                 // тяжёлое вычисление под блокировкой
}
public Report build(String userId) {
    User u = users.get(userId);                               // ConcurrentHashMap — без общего лока
    List<Order> orders = httpClient.fetchOrders(userId);      // вне блокировок
    stats.merge(u.region(), 1, Integer::sum);                 // блокируется один бакет на наносекунды
    return render(u, orders);                                 // локальные данные — блокировка не нужна
}

Сократить критическую секциювынести из-под лока всё, что не трогает общее состояниевычисления, I/O, логирование — снаружи
Разделить блокировку (lock splitting)независимые данные — под разными локамиотдельный лок для очереди и для статистики
Раздробить (lock striping)N локов на части одной структурыбакеты ConcurrentHashMap, ячейки LongAdder
Разделить чтение и записьчитатели не мешают друг другуReadWriteLock, StampedLock, CopyOnWrite, volatile-ссылка на неизменяемый снимок
Отказаться от разделенияу каждого потока свои данныеThreadLocal, локальные переменные, акторы, очередь к одному потоку-владельцу

final class RateTable {
    private volatile Map<String, BigDecimal> rates = Map.of();      // неизменяемая карта

    BigDecimal rate(String currency) { return rates.get(currency); }  // чтение: одно volatile-чтение, без локов
    void reload(Map<String, BigDecimal> fresh) { rates = Map.copyOf(fresh); }   // запись: подменить ссылку целиком
}

15.4Измерять правильно: JMH

Самодельный замер через System.nanoTime() вокруг цикла почти всегда врёт: JIT ещё не прогрелся, компилятор выбросил «мёртвый» код, результат которого не используется, или свернул константы; сборка мусора попала в один из замеров. JMH (Java Microbenchmark Harness) — инструмент от авторов JVM, который учитывает всё это.

@BenchmarkMode(Mode.Throughput)
@OutputTimeUnit(TimeUnit.MICROSECONDS)
@Warmup(iterations = 5, time = 1)          // прогрев JIT
@Measurement(iterations = 5, time = 1)
@Fork(2)                                    // две свежие JVM: исключить влияние профиля предыдущего теста
@State(Scope.Benchmark)                     // состояние общее для всех потоков — мерим конкуренцию
public class CounterBenchmark {
    private final AtomicLong atomic = new AtomicLong();
    private final LongAdder adder = new LongAdder();
    private long plain; private final Object lock = new Object();

    @Benchmark @Threads(8) public long atomic() { return atomic.incrementAndGet(); }
    @Benchmark @Threads(8) public void adder()  { adder.increment(); }
    @Benchmark @Threads(8) public long locked() { synchronized (lock) { return ++plain; } }

    @Benchmark public void consume(Blackhole bh) { bh.consume(compute()); }   // Blackhole не даёт JIT выбросить вычисление
}
// Типичный результат на 8 потоках: adder ≫ atomic > locked. На 1 потоке — все примерно равны.

Ловушки микробенчмарков

Результат не возвращён и не отдан в Blackhole — код удалён компилятором. Константы на входе — выражение вычислено при компиляции. Один fork — случайный профиль JIT. Замер на ноутбуке с троттлингом и фоновыми процессами.

Что бенчмарк не скажет

Как код поведёт себя в приложении: с другим распределением данных, другой нагрузкой на кэш, другими соседями по блокировкам. Микробенчмарк сравнивает варианты; узкое место всего сервиса ищут профилировщиком под реалистичной нагрузкой.

Порядок действий 1. Измерить: пропускная способность и латентность под нагрузкой. 2. Понять, что насыщено: CPU (вычисления), потоки (BLOCKED/WAITING), внешний ресурс. 3. Найти конкретное место профилировщиком. 4. Изменить одно. 5. Измерить снова. Оптимизация без измерения в конкурентном коде чаще добавляет ошибки, чем скорость.

10% времени программа проводит под общей блокировкой. Максимальное ускорение на любом числе ядер?

  • ×100
  • ×90
  • ×10
  • Не ограничено
Закон Амдала: 1 / (1 − p) = 1 / 0,1.

Сервис на 32 потоках работает медленнее, чем на 16. Возможная причина?

  • Закон Амдала запрещает больше 16 потоков
  • Рост конкуренции за блокировки и согласования кэшей (β в USL), переключения контекста
  • JVM ограничивает число потоков
  • Так не бывает
После пика пропускная способность падает: потоки мешают друг другу больше, чем помогают.

Зачем в JMH Blackhole?

  • Чтобы JIT не удалил вычисление, результат которого иначе никому не нужен
  • Чтобы очищать память
  • Чтобы замедлять тест
  • Для синхронизации потоков
Удаление мёртвого кода превращает бенчмарк в замер пустого цикла.

Какой приём уменьшает конкуренцию сильнее всего?

  • Замена synchronized на ReentrantLock
  • Увеличение числа потоков
  • Повышение приоритета потоков
  • Отказ от общего изменяемого состояния: неизменяемые данные, данные потока, дробление блокировок
Самая быстрая блокировка — та, которой нет. Смена типа лока при том же времени удержания почти ничего не даёт.
Что такое закон Амдала и что из него следует на практике?

Ускорение ограничено последовательной долей: S = 1 / ((1 − p) + p/N). Следствие: сокращать время под общими блокировками и в последовательных участках важнее, чем добавлять ядра; небольшая общая блокировка определяет потолок всей системы.

Как уменьшить конкуренцию за блокировку?

Сократить критическую секцию; разделить или раздробить блокировку; разделить чтение и запись; заменить на lock-free или неизменяемые снимки; отказаться от разделения (данные потока, акторы). Сначала измерить, что блокировка действительно горячая.

Почему нельзя мерить производительность циклом с System.nanoTime()?

Нет прогрева JIT, возможны удаление мёртвого кода и свёртка констант, OSR-компиляция искажает цикл, GC и фоновые процессы дают шум, один запуск не показывает разброс. JMH решает это прогревом, форками, Blackhole и статистикой.
