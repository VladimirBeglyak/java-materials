Java Memory Model

Главная тема курса. JMM отвечает на один вопрос: какое значение может увидеть чтение поля, если в него пишут другие потоки. Всё остальное — synchronized, volatile, атомики, пулы — лишь способы получить нужные гарантии.

2.1Три проблемы многопоточности

Атомарность

Операция, которая выглядит одной, состоит из нескольких шагов, и другой поток вклинивается между ними. count++ = прочитать, прибавить, записать.

Видимость

Запись одного потока может никогда не стать видна другому: значение осталось в регистре, кэше ядра или JIT вынес чтение из цикла.

Порядок

Компилятор, JIT и процессор переставляют независимые операции. Другой поток может увидеть их в «невозможном» порядке.

Каждый инструмент решает свой набор: volatile — видимость и порядок, но не атомарность составных операций; synchronized/Lock — все три; AtomicXxx — атомарность отдельных операций + видимость.

2.2Атомарность: потерянное обновление

Пощёлкайте шаги двух потоков в разном порядке. Оба выполняют count++, начальное значение 0. Найдите порядок, при котором итог — 1, а не 2.

Нажимайте кнопки, чтобы выбрать, какой поток делает следующий шаг.
public class LostUpdate {
    static int count = 0;                       // попробуйте volatile — не поможет!

    public static void main(String[] args) throws InterruptedException {
        Runnable inc = () -> { for (int i = 0; i < 1_000_000; i++) count++; };
        Thread a = new Thread(inc), b = new Thread(inc);
        a.start(); b.start(); a.join(); b.join();
        System.out.println(count);              // обычно < 2_000_000
    }
}

Атомарны по JLS только чтения и записи ссылок и примитивов, кроме long/double без volatile (их запись может «порваться» на две 32-битные половины — на практике на 64-битных JVM этого не бывает, но спецификация разрешает). Любое «прочитать-изменить-записать» неатомарно.

2.3Откуда берутся проблемы видимости и порядка

Второй источник — компилятор и JIT. Если JIT доказал, что в цикле поле не меняется этим потоком, он имеет право прочитать его один раз:

boolean running = true;  // без volatile

void worker() {
    while (running) {
        doWork();
    }
}
void worker() {
    if (running) {
        while (true) {      // вечный цикл:
            doWork();       // running = false
        }                   // из другого потока
    }                       // не увидим никогда
}

Это не теоретический баг: на HotSpot он стабильно воспроизводится, если doWork() тривиален и заинлайнен. Исправление — volatile boolean running.

2.4Happens-before — единственное, что нужно запомнить

JMM не описывает кэши и барьеры. Он определяет отношение happens-before (HB) между действиями. Правило: если запись W happens-before чтения R, то R гарантированно видит W (или более позднюю запись). Если между W и R нет HB-цепочки и хотя бы одно из действий — запись, это гонка данных (data race), и чтение может вернуть что угодно из допустимого.

#Правило HBПример
1Program order: в пределах одного потока каждое действие HB следующеговнутри одного потока всё «как написано» (as-if-serial)
2Monitor lock: unlock монитора HB каждого последующего lock того же мониторавыход из synchronized(m) → вход в synchronized(m)
3Volatile: запись volatile-поля HB каждого последующего чтения этого поляready = true → if (ready)
4Thread start: t.start() HB любого действия в tполя, заполненные до start(), видны в новом потоке
5Thread termination: любое действие в t HB возврата из t.join() / isAlive()==falseрезультаты видны после join
6Interrupt: вызов t.interrupt() HB обнаружения прерывания в t
7Finalizer: конец конструктора HB начала finalize()(устарело)
8Транзитивность: A HB B и B HB C ⇒ A HB Cоснова «piggybacking»

Плюс гарантии java.util.concurrent (javadoc «Memory Consistency Properties»): помещение в конкурентную коллекцию/очередь HB извлечения; действия до executor.submit() HB начала задачи; действия задачи HB возврата из future.get(); countDown() HB возврата из await(); освобождение Lock HB его захвата.

HB — это не «раньше по времени» Если запись физически произошла раньше чтения, но HB нет — гарантий нет. И наоборот: HB не означает, что действия реально выполнятся в этом порядке; означает лишь, что результат будет неотличим от такого порядка.

2.5volatile: что даёт и чего не даёт

✔ Даёт

  • Видимость: чтение видит последнюю запись volatile-поля.
  • Порядок: всё, что было до volatile-записи, видно после volatile-чтения того же поля (release/acquire).
  • Атомарность чтения/записи long/double.

✘ Не даёт

  • Атомарность составных операций: v++, if (v == null) v = x, check-then-act.
  • Взаимное исключение.
  • Видимость для полей внутри объекта, изменённых после публикации ссылки.

Когда volatile достаточно: (1) записи не зависят от текущего значения (флаги, «последнее значение»), или пишет только один поток; (2) переменная не участвует в инвариантах вместе с другими полями; (3) блокировка при доступе не нужна по другим причинам.

// 1. Флаг остановки
private volatile boolean shutdown;
public void stop() { shutdown = true; }

// 2. Публикация неизменяемого снимка (один писатель, много читателей)
private volatile Config current = Config.defaults();
public void reload() { current = Config.loadFromDb(); }     // новая неизменяемая ссылка
public Config config() { return current; }

// 3. Cheap read-write lock: пишем под локом, читаем без него
private volatile long value;
public long get() { return value; }
public synchronized void increment() { value++; }

2.6final-поля и безопасная публикация

Публикация — сделать ссылку на объект доступной другому потоку. Если опубликовать небезопасно (обычное поле без синхронизации), другой поток может увидеть ссылку на объект, конструктор которого «ещё не закончился» — поля со значениями по умолчанию.

class Holder {
    private int n;
    Holder(int n) { this.n = n; }
    void check() { if (n != n) throw new AssertionError(); } // может упасть (JCiP §3.5)!
}
public Holder holder;                           // обычное поле
public void init() { holder = new Holder(42); } // запись ссылки может «обогнать» запись n
4 способа безопасной публикации (JCiP)
  1. Инициализация из статического инициализатора (static final X x = new X()) — гарантируется блокировкой инициализации класса.
  2. Сохранение ссылки в volatile-поле или AtomicReference.
  3. Сохранение в final-поле корректно сконструированного объекта.
  4. Сохранение в поле, защищённое локом, или в потокобезопасную коллекцию/очередь.

Семантика final: если объект корректно сконструирован (ссылка this не утекла из конструктора), любой поток, получивший ссылку на объект даже через гонку, увидит правильно инициализированные final-поля и всё, что достижимо через них на момент конца конструктора («freeze»). Поэтому неизменяемые объекты (все поля final, состояние не меняется) потокобезопасны без синхронизации — это главный инструмент проектирования.

public class Listener {
    private final int threshold;
    public Listener(EventBus bus) {
        bus.register(this);   // this утёк: другой поток может вызвать onEvent()
        threshold = 10;       // до этой строки, и увидит threshold == 0
    }
    public void onEvent(int v) { if (v > threshold) alert(); }
}
// Решение: приватный конструктор + статическая фабрика, регистрирующая уже готовый объект.

2.7Double-checked locking — экзамен на JMM

private static Singleton instance;
public static Singleton get() {
    if (instance == null) {                    // 1. чтение без синхронизации — гонка
        synchronized (Singleton.class) {
            if (instance == null) instance = new Singleton(); // 2. allocate → publish ref → init?
        }
    }
    return instance;  // может вернуть ссылку на недоинициализированный объект
}

new Singleton() — это «выделить память, вызвать конструктор, записать ссылку». Без HB запись ссылки может стать видимой другому потоку раньше, чем записи полей в конструкторе. Поток на строке 1 увидит не-null и вернёт полуготовый объект.

private static volatile Singleton instance;
public static Singleton get() {
    Singleton local = instance;        // одно volatile-чтение
    if (local == null) {
        synchronized (Singleton.class) {
            local = instance;
            if (local == null) {
                instance = local = new Singleton();
            }
        }
    }
    return local;
}
public final class Singleton {
    private Singleton() {}
    private static final class Holder {
        static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton get() {
        return Holder.INSTANCE;  // ленивость и
    }                            // потокобезопасность
}                                // даёт JVM при
                                 // инициализации класса

2.8False sharing — проблема производительности

Кэш оперирует линиями по 64 байта. Если два независимых горячих поля, которые пишут разные потоки, лежат в одной линии, каждое изменение инвалидирует линию у другого ядра — и «независимые» потоки начинают сериализоваться через протокол когерентности. Корректность не страдает, страдает пропускная способность (в разы).

Ручной padding (7 полей long до и после) хрупок: JVM может переупорядочить поля. @Contended решает это на уровне раскладки объекта и не требует читать/писать «пустые» поля. Для пользовательского кода аннотация работает только с флагом -XX:-RestrictContended.

2.9Итог: как рассуждать о любом коде

Гарантия DRF-SC Если программа корректно синхронизирована (в ней нет гонок данных — все конфликтующие доступы упорядочены HB), то все её исполнения выглядят последовательно согласованными: как будто действия всех потоков перемешаны в один порядок, согласованный с порядком в каждом потоке. Отсюда практическое правило: убедитесь, что для каждого общего изменяемого поля любая пара «запись + чтение/запись из разных потоков» связана HB — и можно рассуждать о коде «обычно».
  1. Выпишите все поля, доступные более чем одному потоку.
  2. Для каждого — неизменяемое ли оно (final + неизменяемый объект)? Тогда достаточно безопасной публикации.
  3. Если изменяемое — каким механизмом даётся HB для каждой пары доступов: тот же лок? volatile? конкурентная коллекция? join?
  4. Есть ли составные операции (check-then-act, read-modify-write)? Они должны быть под одним локом или выражены одной атомарной операцией (CAS, compute).
  5. Участвуют ли несколько полей в одном инварианте? Тогда их надо менять под одним локом или собрать в один неизменяемый объект и менять ссылку атомарно.

2.10Интерактив: есть ли happens-before

Весь анализ конкурентного кода сводится к одному вопросу: связаны ли запись и чтение отношением happens-before. Если да — читатель гарантированно видит запись. Если нет — это гонка данных, и JVM вправе показать что угодно.

2.11Самопроверка

Поле volatile int count, два потока выполняют count++ по 10 000 раз. Результат?

  • Всегда 20 000
  • Обычно меньше 20 000: volatile даёт видимость, но не атомарность чтения-изменения-записи
  • Всегда 10 000
  • Ошибка компиляции
count++ — три действия. Нужен AtomicInteger, LongAdder или блокировка.

Что гарантирует final-поле в многопоточной программе?

  • Что объект нельзя изменить
  • Ничего особенного
  • Что после завершения конструктора любой поток увидит его инициализированным без синхронизации (если this не утёк)
  • Что поле хранится в регистре
Поэтому неизменяемые объекты с final-полями потокобезопасны и могут публиковаться как угодно.

Что такое false sharing?

  • Независимые переменные разных потоков лежат в одной кэш-линии, и запись одним ядром инвалидирует кэш другого
  • Два потока читают одну переменную
  • Утечка ссылки this
  • Вид deadlock
Корректность не страдает, страдает скорость — в разы. Лечение: @Contended, LongAdder, разнесение полей.
Почему volatile int counter; counter++ из нескольких потоков теряет обновления?

volatile гарантирует видимость каждого отдельного чтения и записи, но ++ — это чтение, сложение и запись. Два потока могут прочитать одно и то же значение, оба прибавят 1 и оба запишут одинаковый результат. Нужна атомарность: AtomicInteger.incrementAndGet(), LongAdder или лок.

Дайте определение data race в терминах JMM.

Два доступа к одной переменной из разных потоков, хотя бы один — запись, и они не упорядочены отношением happens-before. Программа без гонок данных — корректно синхронизированная, для неё действует DRF-SC.

Поток A: x = 1; flag = true; (flag — volatile). Поток B: if (flag) print(x). Может ли B напечатать 0? А если flag не volatile?

С volatile — нет: запись x HB записи flag (program order), запись flag HB чтения flag, которое вернуло true (volatile rule), чтение flag HB чтения x. По транзитивности B видит x = 1. Без volatile — да, может: нет HB, записи могут быть переставлены компилятором или CPU, и B увидит flag = true, а x = 0.

Почему неизменяемый объект можно передавать между потоками без синхронизации?

Все поля final → семантика freeze в конце конструктора гарантирует, что любой поток, получивший ссылку, увидит инициализированные значения final-полей и всё достижимое через них. Состояние больше не меняется → нет конфликтующих записей → нет гонок. Условие: this не утёк из конструктора, а изменяемые объекты внутри (массивы, коллекции) не модифицируются после конструирования.

Зачем в исправленном DCL локальная переменная local?

Оптимизация: на «горячем» пути, когда экземпляр уже создан, происходит одно volatile-чтение вместо двух (проверка + return). volatile-чтение дешевле лока, но не бесплатно — оно запрещает часть оптимизаций. Корректность от этого не зависит.

Что такое false sharing и как его найти?

Два независимых поля, интенсивно изменяемые разными потоками, оказываются в одной 64-байтной кэш-линии, и протокол когерентности гоняет линию между ядрами. Признак: плохая масштабируемость при росте числа потоков без видимой конкуренции за локи. Инструменты: perf c2c на Linux, JOL для просмотра раскладки объекта, JMH-бенчмарк с и без @Contended.
