Параллельные стримы и ForkJoin на практике

.parallel() — самая дешёвая в написании и самая дорогая в последствиях строка в Java. Она может ускорить расчёт в восемь раз, замедлить его втрое или тихо выдать неправильный результат. Разберём, как параллельный стрим делит работу, от чего зависит выигрыш и какие три правила делают его корректным.

13.1Как работает параллельный стрим

Дерево задачделим пополам до порога

ForkJoinPool.commonPoolядра − 1 потоков + вызывающий

Слияние результатовcombiner
  1. Разделение. Spliterator.trySplit() делит источник на две части, те — ещё на две, пока часть не станет меньше порога (примерно размер / (4 × число потоков)).
  2. Выполнение. Каждая часть — задача ForkJoin. Потоки берут свои задачи с головы очереди и крадут чужие с хвоста (work-stealing, тема 08). Вызывающий поток тоже участвует.
  3. Слияние. Результаты частей объединяются вверх по дереву: для reduce — тем же оператором, для collect — функцией combiner.

Отсюда три фактора выигрыша: насколько дёшево и ровно источник делится, сколько работы приходится на элемент и насколько дёшево результаты сливаются.

13.3Три правила корректности

1. Никакого общего изменяемого состояния

List<String> result = new ArrayList<>();
names.parallelStream().map(String::toUpperCase).forEach(result::add);    // гонка: теряются элементы, null, AIOOBE

Map<String, Integer> counts = new HashMap<>();
words.parallelStream().forEach(w -> counts.merge(w, 1, Integer::sum));   // HashMap разрушается
List<String> result = names.parallelStream().map(String::toUpperCase).toList();          // сборку делает стрим: у каждого потока свой контейнер
Map<String, Long> counts = words.parallelStream().collect(groupingByConcurrent(w -> w, counting()));

2. Ассоциативность операции свёртки

IntStream.rangeClosed(1, 100).parallel().reduce(0, Integer::sum);          // 5050 — сложение ассоциативно: (a+b)+c == a+(b+c)
IntStream.rangeClosed(1, 100).parallel().reduce(0, (a, b) -> a - b);       // результат зависит от того, как разделили!
Stream.of("a", "b", "c").parallel().reduce(">", String::concat);           // ">a>b>c": identity подставился в каждую часть — ">" не нейтральный элемент

Требования к reduce(identity, op): op ассоциативна, а identity — действительно нейтральный элемент (op(identity, x) == x). В последовательном стриме нарушение незаметно.

3. Невмешательство и отсутствие зависимости от порядка

list.parallelStream().forEach(System.out::println);           // порядок произвольный
list.parallelStream().forEachOrdered(System.out::println);    // порядок источника, но параллелизм в конце теряется
list.parallelStream().map(this::slow).toList();               // порядок результата СОХРАНЯЕТСЯ: collect учитывает порядок источника
// Нельзя менять источник во время выполнения стрима и полагаться на то, в каком потоке выполнится лямбда

13.4Общий пул и его последствия

commonPool один на JVM

Его делят все параллельные стримы, CompletableFuture.*Async без executor, Arrays.parallelSort. Размер — availableProcessors() − 1; в контейнере с лимитом 1 CPU — ноль рабочих потоков: «параллельный» стрим выполняется в вызывающем потоке.

В веб-приложении

200 потоков запросов одновременно запускают параллельные стримы на пуле из 7 потоков: параллелизма нет, только очередь и переключения. В серверном коде параллельные стримы уместны для редких тяжёлых расчётов, а не в обработке каждого запроса.

try (ForkJoinPool pool = new ForkJoinPool(4)) {
    long sum = pool.submit(() -> data.parallelStream().mapToLong(this::heavy).sum()).get();
}   // стрим, запущенный из задачи ForkJoinPool, использует этот пул, а не commonPool; документацией не гарантировано

Когда нужен точный контроль (свой пул, приоритеты, отмена, таймауты), честнее написать RecursiveTask или разбить работу на задачи ExecutorService.

13.5Самопроверка

Какой источник хуже всего подходит для параллельного стрима?

  • int[]
  • ArrayList
  • LinkedList
  • IntStream.range
Чтобы разделить связный список пополам, нужно пройти половину узлов; части неравные.

Stream.of(1,2,3,4).parallel().reduce(10, Integer::sum) — что может получиться?

  • Всегда 20
  • Больше 20: identity 10 прибавляется в каждой части, а 10 — не нейтральный элемент для сложения
  • Всегда 10
  • Исключение
Нейтральный элемент для суммы — 0. Начальное значение добавляйте отдельно после свёртки.

Сохраняет ли list.parallelStream().map(f).toList() порядок элементов?

  • Да: для упорядоченного источника collect собирает результат в порядке источника
  • Нет, порядок случайный
  • Только если добавить sorted()
  • Только для массивов
Порядок выполнения произвольный, порядок результата — нет. Это стоит производительности; unordered() её возвращает, когда порядок не нужен.

Приложение в контейнере с лимитом 1 CPU. Как выполнится parallelStream()?

  • На 8 потоках хоста
  • Упадёт с ошибкой
  • На двух потоках
  • Фактически последовательно в вызывающем потоке: параллелизм commonPool равен нулю
JVM учитывает лимиты cgroup: availableProcessors() = 1 → commonPool без рабочих потоков.
От чего зависит, ускорит ли parallel() обработку?

Объём работы N × Q (нужно много элементов или дорогая операция), делимость источника (массивы — да, связные списки и итераторы — нет), стоимость слияния (сумма дёшево, HashMap дорого), наличие операций с состоянием и требований порядка (sorted, limit), число свободных ядер и загрузка commonPool.

Какие требования к лямбдам в параллельном стриме?

Без побочных эффектов и общего изменяемого состояния, невмешательство в источник, ассоциативность операций свёртки и корректный нейтральный элемент, отсутствие блокирующих вызовов.

Почему параллельные стримы редко уместны в обработчике HTTP-запроса?

Параллелизм уже обеспечен потоками запросов; общий commonPool мал и разделяется всеми запросами, поэтому вместо ускорения получается конкуренция. Блокирующие операции в нём недопустимы. Уместны для фоновых пакетных расчётов.
