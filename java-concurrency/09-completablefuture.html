Future и CompletableFuture

Как описать «сделай A и B параллельно, затем C из их результатов, при ошибке — запасной вариант, но не дольше 300 мс» без блокировок и вложенных колбэков. И, главное, понимать, в каком потоке выполнится каждый шаг.

9.1Future: что умеет и чего нет

Future<Report> f = executor.submit(() -> buildReport());   // Callable
Report r = f.get(2, TimeUnit.SECONDS);   // блокирует; TimeoutException / ExecutionException
f.cancel(true);                          // true → interrupt потока, выполняющего задачу
f.isDone(); f.state();                   // JDK 19+: RUNNING / SUCCESS / FAILED / CANCELLED

Ограничения: результат можно получить только блокирующим get; нельзя сказать «когда будет готово — сделай X»; нельзя скомбинировать два Future; нельзя завершить Future извне. CompletableFuture (JDK 8) решает всё это и реализует CompletionStage — конвейер этапов.

9.2Создание

ExecutorService io = Executors.newFixedThreadPool(32, Thread.ofPlatform().name("io-", 0).factory());

CompletableFuture<Client> a = CompletableFuture.supplyAsync(() -> clientRepo.find(id), io); // свой пул!
CompletableFuture<Void>   b = CompletableFuture.runAsync(() -> audit.log(id), io);
CompletableFuture<Rate>   c = CompletableFuture.completedFuture(cachedRate);           // уже готов
CompletableFuture<Rate>   d = CompletableFuture.failedFuture(new IllegalStateException()); // JDK 9

// Мост из колбэк-API: «обещание», которое завершим сами
CompletableFuture<Response> promise = new CompletableFuture<>();
httpClient.send(req, new Callback() {
    public void onSuccess(Response r) { promise.complete(r); }
    public void onError(Throwable t)  { promise.completeExceptionally(t); }
});
Без второго аргумента supplyAsync использует ForkJoinPool.commonPool() (размер ≈ ядер − 1). Для I/O это почти всегда ошибка: несколько медленных вызовов займут весь общий пул JVM.

public CompletableFuture<Dashboard> dashboard(long clientId) {
    CompletableFuture<Client> client = CompletableFuture
            .supplyAsync(() -> clients.find(clientId), io)
            .orTimeout(500, TimeUnit.MILLISECONDS);                     // обязательное — ошибка по таймауту

    CompletableFuture<List<Account>> accounts = CompletableFuture
            .supplyAsync(() -> accountsApi.list(clientId), io)
            .orTimeout(500, TimeUnit.MILLISECONDS);

    CompletableFuture<Limits> limits = CompletableFuture
            .supplyAsync(() -> limitsApi.get(clientId), io)
            .completeOnTimeout(Limits.unknown(), 300, TimeUnit.MILLISECONDS) // необязательное — дефолт
            .exceptionally(ex -> {
                log.warn("limits unavailable for {}", clientId, ex);
                return Limits.unknown();
            });

    return CompletableFuture.allOf(client, accounts, limits)
            .thenApply(v -> new Dashboard(client.join(), accounts.join(), limits.join())); // join не блокирует: всё уже готово
}

9.4В каком потоке выполнится колбэк

Самая частая неочевидность. Для не-Async методов (thenApply, thenAccept…):

Этап ещё не завершён

Колбэк регистрируется и выполнится в потоке, который завершит предыдущий этап (поток пула io, или поток, вызвавший complete(), например, I/O-поток HTTP-клиента).

Этап уже завершён

Колбэк выполнится сразу, в вызывающем потоке — прямо внутри thenApply(...). Например, в потоке обработки HTTP-запроса или event loop.

Async-методы (thenApplyAsync(fn, executor)) всегда отправляют колбэк в executor (без аргумента — в commonPool). Правило: тяжёлые или блокирующие колбэки — только через ...Async(fn, свойПул); лёгкие преобразования — обычными методами, без лишних переключений потоков.

Опасно Если future завершается из потока event loop (Netty, HTTP-клиент на NIO), то синхронный thenApply с блокирующим вызовом БД выполнится в event loop и заблокирует обработку всех соединений. В Reactor та же проблема решается publishOn/subscribeOn.

9.5Ошибки

  • Исключение на этапе пропускает все последующие thenApply/thenAccept до ближайшего exceptionally/handle/whenComplete.
  • Исключение оборачивается в CompletionException при переходе между этапами; в exceptionally обычно стоит развернуть: ex instanceof CompletionException ce ? ce.getCause() : ex.
  • join() бросает непроверяемое CompletionException, get() — проверяемое ExecutionException (+ InterruptedException).
  • whenComplete не «лечит» ошибку — она идёт дальше. handle — лечит.
  • Если в цепочке нет обработчика и никто не вызвал join/get, исключение исчезнет молча. Каждую «выстрелил и забыл» цепочку заканчивайте whenComplete с логированием.
CompletableFuture<Rate> rate = fetchRate(ccy)
        .handle((r, ex) -> {
            if (ex == null) return r;
            Throwable cause = ex instanceof CompletionException ce ? ce.getCause() : ex;
            if (cause instanceof TimeoutException) return cache.lastKnown(ccy);
            throw new CompletionException(cause);   // остальное пробрасываем дальше
        });

9.6Отмена и таймауты

CompletableFuture.cancel(true) не прерывает поток, выполняющий задачу: CF не знает, кто его вычисляет. Он лишь завершает future с CancellationException, зависимые этапы получают ошибку, а задача в пуле продолжает работать. То же с orTimeout: future завершится по таймауту, но HTTP-запрос/SQL продолжат выполняться. Поэтому таймауты нужно ставить и на сам ресурс (таймаут HTTP-клиента, statement timeout в БД), а не только на future.

9.9Самопроверка

Чем thenApply отличается от thenCompose?

  • Ничем
  • thenApply принимает функцию T → R; thenCompose — функцию T → CompletableFuture<R> и «разворачивает» вложенный future
  • thenCompose выполняется синхронно
  • thenApply не обрабатывает ошибки
Аналог map и flatMap. С thenApply и асинхронной функцией получится CompletableFuture<CompletableFuture<R>>.

Что делает future.cancel(true) у CompletableFuture?

  • Прерывает поток, выполняющий задачу
  • Ничего
  • Завершает future с CancellationException, но выполняющуюся задачу не прерывает
  • Останавливает executor
CompletableFuture не связан с потоком-исполнителем: параметр mayInterruptIfRunning игнорируется. Задача продолжит работу впустую.

Почему для блокирующих операций нельзя использовать supplyAsync без executor?

  • Задача попадёт в ForkJoinPool.commonPool — маленький общий пул; блокировка в нём тормозит всё приложение
  • Он не поддерживает лямбды
  • Результат будет потерян
  • Это запрещено компилятором
Для I/O — собственный ограниченный пул или виртуальные потоки.
Чем thenApply отличается от thenCompose? Когда какой?

thenApply — синхронное преобразование значения (map). thenCompose — функция возвращает новый CompletionStage, и результат «расплющивается» (flatMap). Если следующий шаг — асинхронный вызов, возвращающий CF, нужен thenCompose.

В каком потоке выполнится thenApply, если future уже завершён к моменту вызова?

Сразу в потоке, вызвавшем thenApply. Если не завершён — в потоке, который его завершит. Чтобы явно выбрать поток — thenApplyAsync(fn, executor).

Остановит ли cf.cancel(true) выполнение задачи в пуле?

Нет. CF не связан с потоком-исполнителем, флаг mayInterruptIfRunning игнорируется. Будущее завершится с CancellationException, но задача доработает. Для настоящей отмены — Future из executor.submit (FutureTask прерывает поток) или structured concurrency (тема 10).

Как может возникнуть deadlock с CompletableFuture без единого лока?

Пул из N потоков; каждая задача в пуле создаёт подзадачу в том же пуле и блокируется на её join(). Когда все N потоков ждут подзадачи, а подзадачи стоят в очереди того же пула — никто не продвигается (thread starvation deadlock). Лечится неблокирующей композицией (thenCompose), раздельными пулами или виртуальными потоками.

Напишите комбинатор «первый успешный из N».
static <T> CompletableFuture<T> firstSuccess(List<CompletableFuture<T>> cfs) {
    CompletableFuture<T> result = new CompletableFuture<>();
    AtomicInteger failures = new AtomicInteger();
    for (CompletableFuture<T> cf : cfs) {
        cf.whenComplete((v, ex) -> {
            if (ex == null) result.complete(v);                  // complete идемпотентен: выиграет первый
            else if (failures.incrementAndGet() == cfs.size())
                result.completeExceptionally(ex);                // упали все
        });
    }
    return result;
}
