13.1Как это работает

Параллельный стрим — как бригада, разбирающая большую кучу писем: кучу делят пополам, половины — ещё пополам, пока куски не станут маленькими; каждый работник обрабатывает свои куски, а результаты потом объединяются. Работники берутся из общего ForkJoinPool — по умолчанию их на один меньше, чем ядер (плюс сам вызывающий поток).

Главная мысль Делим данные на куски → обрабатываем параллельно → объединяем результаты.

13.2Стоит ли распараллеливать

Делить, раздавать и объединять — накладные расходы. Они окупаются, только если:

  • данных много (десятки тысяч элементов и больше);
  • работа на элемент тяжёлая (вычисления, а не сложение двух чисел);
  • источник легко делится: массив и ArrayList — да, LinkedList и чтение строк из файла — плохо.

Правило: не распараллеливать «на всякий случай», а замерять (JMH, глава 15).

Главная мысль Много данных + тяжёлая работа + делимый источник. Иначе — медленнее.

13.3Три правила корректности

Почему результат «прыгает»
✗ list = new ArrayList();  stream.parallel().forEach(x -> list.add(x))
несколько потоков пишут в обычный список → потери и исключения✓ stream.parallel().toList() — коллектор сам собирает куски безопасно✗ reduce(0, (a, b) -> a - b) — вычитание зависит от порядка группировки
результат меняется от запуска к запускуправила: 1) без побочных эффектов  2) операции ассоциативны
3) не полагаться на порядок (forEach в параллели идёт вразнобой)

Побочный эффект в параллели — гонка данных.

collect и toList объединяют куски правильно.

(a−b)−c ≠ a−(b−c) — куски сложатся иначе.

Соблюдайте — и результат совпадёт с последовательным.

Главная мысль Без побочных эффектов, только ассоциативные операции, не надеяться на порядок.

13.4Общий пул и его последствия

Все параллельные стримы приложения (и CompletableFuture по умолчанию) делят один общий пул. Если в одном месте внутри параллельного стрима делать блокирующие вызовы (база, сеть), его немногочисленные потоки будут стоять — и замедлятся все остальные параллельные стримы приложения. Как если бы один отдел занял все общие переговорки на целый день. На сервере, обрабатывающем много запросов, параллельные стримы вообще редко полезны: ядра и так заняты запросами.

Главная мысль Общий пул — один на всех. Никаких блокирующих вызовов в параллельных стримах.

13.6Проверьте себя

Когда параллельный стрим скорее ускорит работу?

  • 100 элементов, сложение
  • миллион элементов массива, тяжёлый расчёт на каждый
  • чтение строк из сетевого потока
  • запросы в базу для каждого элемента
Много данных, тяжёлая работа, делимый источник.

Что не так с parallel().forEach(x -> list.add(x)) для ArrayList?

  • ничего
  • слишком медленно
  • порядок будет обратный
  • гонка данных: несколько потоков пишут в обычный список
Используйте collect / toList.

Почему reduce с вычитанием даёт разный результат в параллели?

  • вычитание не ассоциативно, а куски объединяются в разном порядке
  • ошибка в JVM
  • из-за переполнения
  • из-за сборщика мусора
Для reduce нужны ассоциативные операции.

Чем опасны сетевые вызовы внутри параллельного стрима?

  • они не выполнятся
  • они выполнятся дважды
  • они занимают потоки общего пула, и тормозят все параллельные операции приложения
  • ничем
Общий пул маленький и один на всех.

Сколько потоков в общем ForkJoinPool по умолчанию?

  • один
  • на один меньше числа ядер
  • сколько угодно
  • 200
Плюс вызывающий поток тоже участвует в работе.
