Виртуальные потоки — простыми словами

10.1Что такое виртуальный поток

Обычный поток Java — это поток операционной системы: дорогой (мегабайт стека, работа планировщика), их тысячи, а не миллионы. Виртуальный поток — лёгкий объект внутри JVM. Работать ему всё равно нужно на настоящем потоке — носителе (carrier). Но когда виртуальный поток начинает ждать (сеть, база, sleep), JVM «снимает» его с носителя и сажает другой. Ждущий виртуальный поток почти ничего не стоит.

10.2Когда помогают, а когда нет

Помогают, когда задач много и они в основном ждут: веб-сервис, который ходит в базу и другие сервисы. Не помогают для вычислений: виртуальный поток не делает процессор быстрее, а носителей всё равно столько, сколько ядер. Их не нужно объединять в пул — создавайте новый на каждую задачу. Но ограничивать доступ к ресурсам (например, к базе) всё равно нужно — семафором или пулом соединений.

Главная мысль Много ожидания — да; вычисления — нет. Без пулов, но с ограничением ресурсов.

В полной главе: 10.2 Когда помогают, а когда нет

10.3Pinning: пассажир не может выйти

Иногда виртуальный поток не может отцепиться от носителя и блокирует его на всё время ожидания — pinning. Классические причины: ожидание внутри synchronized (в Java 21–23; в Java 24 это исправлено) и вызовы нативного кода. Если таких мест много, носители заканчиваются, и всё встаёт. Решение для старых версий — ReentrantLock вместо synchronized в местах с долгим ожиданием; диагностика — событие JFR о pinning.

Главная мысль Pinning — виртуальный поток прилип к носителю. В Java 21 — осторожно с synchronized вокруг ожиданий.

В полной главе: 10.3 Pinning — когда VT не может отцепиться

10.4ScopedValue вместо ThreadLocal

ThreadLocal при миллионах виртуальных потоков — миллионы копий данных, которые легко забыть очистить. ScopedValue — значение, привязанное к блоку кода: задали «текущий пользователь = Иван» на время выполнения блока, и все вызовы внутри его видят; блок кончился — значения нет. Нельзя случайно изменить или забыть убрать.

Главная мысль ScopedValue — неизменяемый контекст на время блока, без утечек.

В полной главе: 10.4 ScopedValue вместо ThreadLocal

10.5Structured Concurrency

Запустили три подзадачи параллельно, одна упала. Что с остальными? Обычно они продолжают работать впустую. Structured Concurrency делает подзадачи «детьми» блока кода: блок не закончится, пока не закончатся все дети; если одна упала — остальные отменяются; ошибка поднимается наверх. Как поход с детьми: домой возвращаются все вместе, и если один заболел, поворачивают все. Это API пока в статусе preview.

Главная мысль Подзадачи живут внутри блока: ждут друг друга и отменяются вместе.

В полной главе: 10.5 Structured Concurrency

10.6Виртуальные потоки против реактивного стека

Реактивные библиотеки (WebFlux, Reactor) решали ту же проблему — тысячи соединений малым числом потоков, — но ценой сложного кода из цепочек операторов. Виртуальные потоки дают ту же эффективность для ожидания с обычным последовательным кодом и понятными стек-трейсами. Реактивный стек остаётся сильным для потоковой обработки данных и обратного давления.

Главная мысль Для типичного сервиса — виртуальные потоки и простой код. Реактив — для потоков данных.

10.8Проверьте себя

Что происходит с виртуальным потоком, когда он ждёт ответ базы?

  • блокирует свой носитель
  • завершается
  • отцепляется от носителя, и тот выполняет другие виртуальные потоки
  • ускоряется
Поэтому ожидание почти бесплатно.

Ускорят ли виртуальные потоки чистые вычисления?

  • нет: носителей по числу ядер, процессор быстрее не станет
  • да, в разы
  • да, если их миллион
  • только на ARM
Они помогают при ожидании, а не при расчётах.

Нужно ли складывать виртуальные потоки в пул?

  • да, обязательно
  • да, по числу ядер
  • да, на 200 потоков
  • нет: создавайте новый на задачу, а ресурсы ограничивайте семафором
Они дешёвые, пул лишь мешает.

Что такое pinning?

  • закрепление задачи за ядром для скорости
  • ситуация, когда виртуальный поток не может отцепиться от носителя во время ожидания
  • ошибка компиляции
  • вид deadlock
В Java 21 — например, ожидание внутри synchronized.

Что даёт Structured Concurrency, если одна из трёх подзадач упала?

  • остальные продолжают работать впустую
  • программа падает
  • остальные отменяются, ошибка поднимается наверх
  • подзадача перезапускается
Подзадачи живут и умирают вместе с блоком.
