Executors и ThreadPoolExecutor

В продакшене потоки почти никогда не создают руками. Задачи отдают пулу, а пул решает, на каком потоке и когда их выполнить, сколько их держать в очереди и что делать при перегрузке. Неправильно настроенный пул — одна из самых частых причин падений под нагрузкой.

8.1Зачем пулы

Цена создания

Платформенный поток — системный вызов и ~1 МБ стека. Пул переиспользует потоки.

Ограничение ресурсов

«Поток на запрос» под пиком создаст 10 000 потоков → OOM или трэшинг планировщика. Пул ограничивает конкурентность.

Управление

Отмена, таймауты, graceful shutdown, метрики, политика перегрузки — в одном месте.

8.2Иерархия и жизненный цикл

Состояния пула: RUNNING → shutdown() → SHUTDOWN (новые задачи отклоняются, очередь дорабатывается) → TIDYING → TERMINATED. shutdownNow() → STOP: прерывает работающие потоки, возвращает невыполненные задачи из очереди. Внутри состояние и число потоков упакованы в одно AtomicInteger ctl (старшие 3 бита — runState, младшие 29 — workerCount), чтобы менять их одним CAS.

void shutdownAndAwait(ExecutorService pool) {
    pool.shutdown();                                       // больше не принимаем задачи
    try {
        if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
            List<Runnable> dropped = pool.shutdownNow();    // прерываем зависшие
            log.warn("Dropped {} tasks", dropped.size());
            if (!pool.awaitTermination(10, TimeUnit.SECONDS))
                log.error("Pool did not terminate");
        }
    } catch (InterruptedException e) {
        pool.shutdownNow();
        Thread.currentThread().interrupt();
    }
}
// JDK 19+: ExecutorService реализует AutoCloseable — close() делает shutdown + ожидание.

8.3Алгоритм execute() — выучить наизусть

Конструктор: ThreadPoolExecutor(corePoolSize, maximumPoolSize, keepAliveTime, unit, workQueue, threadFactory, handler).

  1. Потоков меньше corePoolSize → создать новый поток с этой задачей (даже если есть простаивающие).
  2. Иначе → положить в очередь (workQueue.offer).
  3. Очередь полна и потоков меньше maximumPoolSize → создать дополнительный поток с этой задачей.
  4. Иначе → RejectedExecutionHandler.
Контринтуитивное следствие Пул растёт сверх core, только когда очередь переполнена. С неограниченной очередью (LinkedBlockingQueue()) maximumPoolSize не имеет никакого смысла — дополнительных потоков никогда не будет, а очередь будет расти до OOM. Это и есть ловушка Executors.newFixedThreadPool.

8.6Размер пула

Формула Гётца: N_threads = N_cpu × U_cpu × (1 + W / C), где U — целевая загрузка CPU (0..1), W/C — отношение времени ожидания (I/O) к времени вычислений.

CPU-bound

W/C ≈ 0 → N_cpu или N_cpu + 1. Больше потоков — только переключения контекста и вытеснение кэша.

I/O-bound

8 ядер, запрос ждёт БД 90 мс и считает 10 мс: 8 × 1 × (1 + 9) = 80. Но верхнюю границу задаёт ресурс за пулом: если пул соединений с БД — 20, то 80 потоков будут ждать соединения.

Закон Литтла: L = λ × W. Нужно обслуживать 400 RPS при 50 мс на запрос → в среднем 400 × 0,05 = 20 одновременно выполняющихся запросов; с запасом на пики — 30–40 потоков. Ёмкость очереди выбирайте из допустимой задержки: если терпим 200 мс ожидания при пропускной способности 400 RPS → очередь не больше ~80.

Формулы дают начальную точку. Финальное значение — нагрузочным тестом с метриками: загрузка CPU, длина очереди, p99 задержки, время ожидания соединения из пула БД.

8.8ForkJoinPool и work-stealing

Пул для задач «разделяй и властвуй». У каждого потока своя двусторонняя очередь (deque): свои задачи поток берёт с головы (LIFO — горячий кэш), а простаивающий поток крадёт с хвоста чужой очереди (FIFO — там крупные, ещё не разделённые задачи).

final class SumTask extends RecursiveTask<Long> {
    private static final int THRESHOLD = 10_000;
    private final long[] a; private final int from, to;
    SumTask(long[] a, int from, int to) { this.a = a; this.from = from; this.to = to; }

    @Override protected Long compute() {
        if (to - from <= THRESHOLD) {                  // достаточно мелко — считаем сами
            long s = 0; for (int i = from; i < to; i++) s += a[i]; return s;
        }
        int mid = (from + to) >>> 1;
        SumTask left = new SumTask(a, from, mid);
        left.fork();                                   // в свою deque, могут украсть
        long right = new SumTask(a, mid, to).compute(); // правую половину считаем сами
        return right + left.join();                     // join может выполнить left сам, если не украли
    }
}
long total = ForkJoinPool.commonPool().invoke(new SumTask(data, 0, data.length));
commonPool — общий для всей JVM На нём работают parallelStream(), CompletableFuture.*Async без executor'а, bulk-операции CHM. Размер ≈ N_cpu − 1. Блокирующий вызов (JDBC, HTTP) внутри parallel stream или supplyAsync без своего пула занимает этот маленький пул и тормозит всё приложение. Для I/O всегда передавайте собственный executor.

8.10Самопроверка

ThreadPoolExecutor(core = 4, max = 16, очередь LinkedBlockingQueue без лимита). Сколько потоков будет под нагрузкой в 100 одновременных задач?

  • 16
  • 100
  • 4 — дополнительные потоки создаются только при заполненной очереди, а она бесконечная
  • 20
Порядок execute(): core → очередь → max → отказ. С неограниченной очередью max не работает.

Что делает CallerRunsPolicy при переполнении?

  • Бросает исключение
  • Выполняет задачу в потоке, вызвавшем execute, — отправитель замедляется (backpressure)
  • Молча выбрасывает задачу
  • Создаёт новый поток
Естественное обратное давление. Не годится, если отправитель — поток event loop.

Задачу отправили через submit(), внутри неё NullPointerException. Где его увидеть?

  • Только при вызове future.get() — как ExecutionException
  • В логе через UncaughtExceptionHandler
  • Пул остановится
  • В System.err автоматически
submit сохраняет исключение в Future. Никто не вызвал get() — ошибка потеряна молча. Для execute() сработал бы UncaughtExceptionHandler.
core=10, max=50, очередь LinkedBlockingQueue без ограничения. Сколько потоков будет при 1000 одновременных задачах?

10. Новые потоки сверх core создаются, только когда offer в очередь вернул false, а неограниченная очередь всегда принимает. 990 задач будут ждать в очереди; max=50 бесполезен.

Почему newCachedThreadPool опасен под нагрузкой?

max = Integer.MAX_VALUE и SynchronousQueue: если свободного потока нет, на каждую задачу создаётся новый. При всплеске медленных задач — тысячи потоков, исчерпание памяти/лимитов ОС (OutOfMemoryError: unable to create native thread).

Задачу отправили через submit, внутри NPE. Где мы её увидим?

Нигде, пока не вызовем future.get() — тогда ExecutionException с NPE в причине. UncaughtExceptionHandler не сработает. Можно переопределить afterExecute(Runnable, Throwable) у ThreadPoolExecutor, но для submit там t == null — исключение нужно доставать из FutureTask.

Как работает CallerRunsPolicy как механизм backpressure?

При переполнении задача выполняется в потоке-отправителе. Пока он выполняет её, он не может отправлять новые задачи — поток поступления естественно замедляется до скорости обработки, а пул тем временем разгребает очередь. Если отправитель — поток приёма HTTP-запросов, начинают расти очереди уже на уровне сервера/TCP, что даёт давление дальше вверх.

Почему в ForkJoinPool свои задачи берутся LIFO, а крадутся FIFO?

LIFO для владельца: последняя созданная подзадача — самая мелкая и её данные горячие в кэше. FIFO для вора: в хвосте лежат самые ранние, самые крупные задачи — одна кража даёт много работы и сокращает число краж (а владелец и вор работают с разных концов deque, меньше конфликтов).

Как вы выберете размер пула для сервиса, который ходит в БД?

Оценка по формуле N_cpu × U × (1 + W/C) и закону Литтла (RPS × время обработки), затем ограничение сверху ресурсом за пулом — размером пула соединений БД (больше потоков, чем соединений, бесполезно), лимитами downstream. Ограниченная очередь по допустимой задержке, политика отказа. Финально — нагрузочный тест с метриками активных потоков, длины очереди, p99 и времени ожидания соединения.
