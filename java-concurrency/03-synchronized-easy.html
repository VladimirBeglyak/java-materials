synchronized и wait/notify — простыми словами

synchronized — самый старый и простой способ защитить общие данные. 3.1Что делает synchronized

Представьте примерочную с одним ключом. Кто взял ключ — заходит, остальные ждут у двери. Вышел — отдал ключ следующему. synchronized даёт сразу две вещи:

  • Взаимное исключение — внутри блока только один поток.
  • Видимость — всё, что поток сделал внутри, увидит следующий, кто возьмёт тот же ключ (happens-before, глава 02).
Главная мысль synchronized = один поток за раз + видимость изменений для следующего.

3.2Что защищает ключ

Ключ — это конкретный объект-монитор. synchronized-метод экземпляра запирает на this, статический — на объект класса. Защита работает, только если все обращения к данным идут через один и тот же ключ. Если один метод запирает на this, а другой меняет те же данные без замка или на другом объекте — защиты нет. Как две двери в комнату, у одной из которых нет замка.

Главная мысль Одни данные — один замок, и все обращения через него.

В полной главе: 3.2 Что именно защищает лок

3.3Повторный вход

Поток, уже держащий ключ, может снова войти в synchronized на том же объекте — например, один synchronized-метод вызывает другой. Он не заблокирует сам себя: JVM считает, сколько раз ключ взят, и отпускает, когда счётчик дойдёт до нуля. Это называется реентерабельностью.

Главная мысль Свой же замок повторно взять можно — сам себя поток не запрёт.

В полной главе: 3.3 Реентерабельность

3.4Как это устроено в JVM

У каждого объекта в заголовке есть место для отметки о блокировке. Если конкуренции нет, взятие ключа — одна быстрая атомарная операция. Если потоки реально толкаются, JVM заводит полноценный монитор с очередью ожидающих, и потоки «засыпают» через операционную систему — это дороже. Поэтому неконкурентный synchronized почти бесплатен.

Главная мысль Без конкуренции synchronized дешёвый, при толкотне — дорогой.

3.5Составные действия

Даже если каждая операция коллекции потокобезопасна, их комбинация — нет. «Если ключа нет — положи» — это проверка и действие; между ними другой поток может успеть положить свой ключ. Нужно либо держать один замок на всё составное действие, либо использовать атомарные методы вроде putIfAbsent / computeIfAbsent.

Главная мысль «Проверь, потом сделай» — гонка, даже на потокобезопасной коллекции.

3.6wait и notify: подождать, пока позовут

Иногда потоку нужно ждать условия: «в очереди появился заказ». Крутиться в цикле и проверять — трата процессора. wait() — «отдаю ключ и сажусь в зал ожидания», notifyAll() — «эй, в зале, что-то изменилось».

Повар ждёт заказ
повар (взял ключ): заказов нет → wait()
→ ключ отдан, повар в зале ожиданияофициант (взял ключ): добавил заказ → notifyAll() → вышелповар проснулся, снова получил ключ
ПРОВЕРЯЕТ УСЛОВИЕ ЕЩЁ РАЗ — может, заказ уже забрал другой поварправило: while (заказов нет) wait();   — всегда цикл, не if

wait освобождает ключ, иначе никто не смог бы добавить заказ.

notifyAll будит всех ждущих.

Проснуться можно и «ложно», и опоздав к заказу.

Условие проверяется в цикле.

На практике wait/notify пишут редко — проще готовые очереди (BlockingQueue, глава 07) и синхронизаторы (глава 06).

Главная мысль wait — только внутри synchronized и только в цикле while. Обычно лучше BlockingQueue.

3.7Когда synchronized, а когда другое

synchronized хорош по умолчанию: короткие критические секции, простой код, автоматическое освобождение даже при исключении. Если нужно ждать ключ с таймаутом, прерываемо, несколько условий ожидания или раздельные замки для чтения и записи — берите Lock (глава 04). Для простых счётчиков — атомики (глава 05).

Главная мысль По умолчанию synchronized; особые возможности — Lock; счётчики — атомики.
