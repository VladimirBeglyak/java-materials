14.1Почему synchronized не помогает

Замок в Java — это ключ, который существует только внутри одной JVM. Если сервис запущен в трёх копиях, у каждой свой ключ — как три одинаковых замка на трёх разных дверях в одну и ту же комнату. Два запроса, попавшие в разные копии, спокойно пройдут одновременно.

Главная мысль Замки Java не работают между копиями сервиса. Общая точка — база данных.

14.3Оптимистичная и пессимистичная блокировки

Оптимистичная (версия)

У строки есть номер версии. Обновляем «где версия = 5», ставим 6. Если кто-то успел раньше, версия уже 6 — обновится 0 строк, значит, конфликт: перечитываем и пробуем снова (или говорим пользователю). Как CAS, только в базе. Хороша, когда конфликты редки. В JPA — аннотация @Version.

Пессимистичная (FOR UPDATE)

SELECT … FOR UPDATE запирает строку до конца транзакции — остальные ждут. Как synchronized, но в базе. Хороша, когда конфликты часты. Держите такие транзакции короткими.

Главная мысль Конфликты редки — версия; часты — FOR UPDATE с короткой транзакцией.

14.4Уникальные ограничения

«Проверь, нет ли пользователя с таким email, и создай» — гонка: две копии одновременно проверят «нет» и обе создадут. Надёжное решение — уникальный индекс на email в базе: вторая вставка просто упадёт с ошибкой, которую код обработает. База — единственный судья, которому видны все копии.

Главная мысль Правило «должно быть уникально» — в уникальный индекс базы, а не в проверку в коде.

14.5Распределённые блокировки

Иногда нужно, чтобы во всём кластере что-то делала только одна копия (например, ночной отчёт). Для этого есть распределённые блокировки (Redis, ZooKeeper, таблица в базе, ShedLock). Но они сложнее, чем кажутся: копия может «заснуть» (пауза сборщика мусора, сеть) и не заметить, что её блокировка истекла и уже взята другой — и теперь работают двое. Защита — номер-«жетон» (fencing token), который проверяет тот, к кому обращаются. По возможности обходитесь без распределённых блокировок.

Главная мысль Распределённая блокировка может «протечь». Предпочитайте решения на уровне базы и идемпотентность.

14.6Идемпотентность: повтор ничего не ломает

В распределённой системе запросы повторяются: клиент не дождался ответа и отправил снова, сообщение из очереди доставлено дважды. Идемпотентная операция при повторе даёт тот же результат, что и в первый раз. Как кнопка лифта: нажали пять раз — лифт приедет один раз. Приём: клиент присылает уникальный ключ запроса, сервер запоминает обработанные ключи (уникальный индекс!) и на повтор возвращает прежний ответ, а не списывает деньги второй раз.

Главная мысль Делайте операции идемпотентными: ключ запроса + уникальный индекс.
