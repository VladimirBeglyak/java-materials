11.1Deadlock: взаимная блокировка

Два повара: первому нужны нож и доска, второму — доска и нож. Первый взял нож и ждёт доску, второй взял доску и ждёт нож. Оба будут ждать вечно. Это deadlock.

Перевод денег между двумя счетами
поток 1: перевод A → B: lock(A) ✓ … теперь lock(B)
поток 2: перевод B → A: lock(B) ✓ … теперь lock(A)поток 1 ждёт B (у потока 2)
поток 2 ждёт A (у потока 1) → вечное ожиданиелечение: брать замки в едином порядке — например, по id счёта
оба потока сначала lock(меньший id), потом lock(больший) → цикл невозможен

По отдельности всё правильно.

Каждый ждёт то, что держит другой.

Если все берут замки в одном порядке, замкнутого круга не бывает.

Другие способы: tryLock с таймаутом (не смог взять второй — отпусти первый и попробуй позже), меньше вложенных замков, не вызывать чужой код под своим замком.

Главная мысль Deadlock = круг ожидания. Единый порядок взятия замков его исключает.

11.2Livelock, голодание и голодание пула

  • Livelock — двое в коридоре одновременно уступают друг другу дорогу, шагая в одну сторону, — оба «работают», но не продвигаются.
  • Starvation (голодание) — поток бесконечно не получает ресурс, потому что его постоянно обгоняют другие.
  • Голодание пула — задачи в пуле ждут результат других задач того же пула, а свободных потоков для них нет — всё стоит.
Главная мысль Не только deadlock: livelock, голодание и «задача ждёт задачу в том же пуле».

В полной главе: 11.2 Livelock, starvation и голодание пула

11.3Thread dump: снимок всех потоков

Thread dump (команды jstack, jcmd Thread.print) — «фотография» всех потоков в момент: в каком состоянии каждый, какой у него стек вызовов, какие замки держит и каких ждёт. JVM даже сама находит deadlock и пишет «Found one Java-level deadlock». Совет: снимите несколько дампов с интервалом в пару секунд — если поток всё время стоит на одной строке, вот она, проблема.

Главная мысль Сервис завис — снимите несколько thread dump и сравните.

В полной главе: 11.3 Thread dump: читать и находить

11.4JFR: бортовой самописец

Java Flight Recorder записывает события работающей программы почти без потерь скорости: кто и сколько ждал замков, где потоки блокировались, где были паузы. Открываете запись в JDK Mission Control и видите, какие замки самые «горячие».

Главная мысль JFR показывает, где потоки ждут друг друга, прямо на рабочем сервисе.

11.5Как тестировать конкурентный код

Обычный тест прогоняет код один раз — и гонка, случающаяся раз на миллион, не проявится. Помогает: запускать много потоков одновременно и много раз (одновременный старт через CountDownLatch); специальные инструменты вроде jcstress, которые перебирают варианты перемешивания; и главное — проектировать так, чтобы общего изменяемого состояния было как можно меньше.

Главная мысль «Тест прошёл» не доказывает отсутствие гонок. Меньше общего состояния — меньше ошибок.

11.6Чек-лист ревью

  1. У каждого общего изменяемого поля понятна защита (замок, volatile, atomic, неизменяемость).
  2. Нет «проверь, потом сделай» без атомарности.
  3. Замки берутся в едином порядке, unlock — в finally.
  4. Пулы ограничены, задачи ловят исключения, пулы останавливаются.
  5. InterruptedException не проглатывается.
  6. Нет долгих операций (сеть, база) под замком.
Главная мысль Шесть пунктов ловят большинство многопоточных ошибок.

11.8Проверьте себя

Как надёжно избежать deadlock при переводе между счетами?

  • увеличить число потоков
  • брать замки счетов всегда в одном порядке, например по id
  • добавить sleep
  • не использовать замки вообще
Без цикла ожидания deadlock невозможен.

Сервис завис. Что снять первым?

  • дамп кучи
  • логи GC
  • скриншот
  • несколько thread dump с интервалом
Видно, кто что ждёт и на какой строке стоит.

Задачи в пуле на 4 потока ждут результат других задач того же пула. Что может случиться?

  • голодание пула: все потоки ждут, а задачам, которых ждут, некому выполниться
  • ускорение
  • ничего
  • пул увеличится сам
Не ждите внутри пула задач того же пула.

Тест многопоточного кода прошёл 10 раз. Значит, гонок нет?

  • да
  • да, если тест быстрый
  • нет: гонка может проявляться раз на миллион запусков
  • да, на любой машине
Нужны стресс-тесты и правильный дизайн.

Почему опасно ходить в базу под замком?

  • база не работает с замками
  • замок держится долго, и все остальные потоки ждут
  • это запрещено
  • неопасно
Под замком — только быстрые операции с памятью.
