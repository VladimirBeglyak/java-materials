5.1Compare-and-Swap

CAS(адрес, ожидаемое, новое) — одна атомарная инструкция процессора (LOCK CMPXCHG на x86, LDAXR/STLXR или CAS на ARMv8.1+): «если в памяти сейчас ожидаемое — запиши новое и верни успех, иначе ничего не меняй и верни неуспех». Поверх неё строится CAS-цикл:

public final int updateAndGet(IntUnaryOperator f) {
    int prev, next;
    do {
        prev = get();                        // volatile read
        next = f.applyAsInt(prev);           // f должна быть чистой: её могут вызвать много раз!
    } while (!compareAndSet(prev, next));    // CAS c volatile-семантикой
    return next;
}
Lock-free vs wait-free Lock-free: система в целом продвигается (кто-то всегда выигрывает CAS), но отдельный поток может проигрывать бесконечно. Wait-free: каждый поток завершает операцию за конечное число шагов. getAndAdd на x86 — wait-free (LOCK XADD), CAS-цикл — только lock-free.

Несколько полей → один неизменяемый снимок

CAS работает с одним словом. Если инвариант связывает два поля, соберите их в неизменяемый объект и меняйте ссылку:

public final class NumberRange {
    private record Bounds(int lower, int upper) {
        Bounds { if (lower > upper) throw new IllegalArgumentException(); }
    }
    private final AtomicReference<Bounds> bounds = new AtomicReference<>(new Bounds(0, 0));

    public void setLower(int v) {
        bounds.updateAndGet(b -> new Bounds(v, b.upper()));   // повтор при конкуренции
    }
    public boolean contains(int x) {
        Bounds b = bounds.get();                             // согласованный снимок
        return x >= b.lower() && x <= b.upper();
    }
}

5.3Lock-free структура: стек Трайбера

public final class TreiberStack<E> {
    private record Node<E>(E item, Node<E> next) {}
    private final AtomicReference<Node<E>> top = new AtomicReference<>();

    public void push(E item) {
        Node<E> oldTop, newTop;
        do {
            oldTop = top.get();
            newTop = new Node<>(item, oldTop);
        } while (!top.compareAndSet(oldTop, newTop));
    }

    public E pop() {
        Node<E> oldTop;
        do {
            oldTop = top.get();
            if (oldTop == null) return null;
        } while (!top.compareAndSet(oldTop, oldTop.next()));
        return oldTop.item();
    }
}

5.4Проблема ABA

CAS проверяет «значение то же», а не «никто не менял». Поток 1 прочитал A и уснул; поток 2 поменял A→B→A; CAS потока 1 успешен, хотя структура уже другая.

AtomicStampedReference<Node> top = new AtomicStampedReference<>(null, 0);
int[] stampHolder = new int[1];
Node cur = top.get(stampHolder);
top.compareAndSet(cur, cur.next, stampHolder[0], stampHolder[0] + 1);  // версия растёт при каждом изменении

5.5LongAdder и Striped64

Под высокой конкуренцией AtomicLong деградирует: все ядра бьются CAS-ами в одну кэш-линию, большинство попыток проваливается и повторяется. LongAdder распределяет конкуренцию:

LongAdder

Счётчики запросов, метрики, частоты — пишут часто, читают редко. Пропускная способность записи на многоядерной машине выше в разы.

AtomicLong

Нужно значение «здесь и сейчас» или CAS: генератор id (incrementAndGet возвращает уникальное число), лимит с проверкой. LongAdder так не умеет.

ConcurrentHashMap.size() внутри использует ту же идею (baseCount + CounterCell[]), поэтому размер мапы под нагрузкой — оценка.

5.6VarHandle и режимы доступа к памяти

С JDK 9 VarHandle — публичная замена sun.misc.Unsafe: атомарные операции и тонкие режимы упорядочивания для любого поля или элемента массива. Внутри JDK на нём построены атомики и j.u.c.

public final class Sequence {
    private volatile long value;
    private static final VarHandle VALUE;
    static {
        try {
            VALUE = MethodHandles.lookup().findVarHandle(Sequence.class, "value", long.class);
        } catch (ReflectiveOperationException e) { throw new ExceptionInInitializerError(e); }
    }
    public long next() { return (long) VALUE.getAndAdd(this, 1L) + 1; }
    public void publish(long v) { VALUE.setRelease(this, v); }   // дешевле volatile-записи
    public boolean cas(long exp, long upd) { return VALUE.compareAndSet(this, exp, upd); }
}
Release/acquire и opaque — инструменты авторов библиотек (Disruptor, JCTools). В прикладном коде достаточно volatile и Atomic*; используйте слабые режимы только с JMH-доказательством выигрыша и jcstress-тестом корректности.

5.7Когда CAS хуже лока

  • Очень высокая конкуренция за одну переменную: проваленные CAS — это сожжённый CPU; лок паркует проигравших. Решение — шардирование (LongAdder) или лок.
  • Долгое вычисление новой версии: updateAndGet(heavy) будет пересчитывать heavy при каждом проигрыше.
  • Побочные эффекты в лямбде CAS-цикла — выполнятся несколько раз. Лямбда должна быть чистой функцией.
  • Инвариант на нескольких независимых объектах — CAS не умеет атомарно менять два места (нет DCAS). Лок проще и надёжнее.

5.8Интерактив: CAS-цикл и проблема ABA

int incrementAndGet() {
    for (;;) {
        int expected = value;                 // 1. прочитать
        int next = expected + 1;              // 2. вычислить
        if (compareAndSet(expected, next))    // 3. записать, только если value всё ещё == expected
            return next;                      //    иначе — кто-то успел раньше: повторить с шага 1
    }
}
Симулятор: два потока увеличивают счётчик
value (общая память)
567
Поток A
expected = 5, next = 6CAS(5→6) ✘expected = 6, next = 7CAS(6→7) ✓
Поток B
expected = 5, next = 6CAS(5→6) ✓

A: expected = 5, next = 6

Поток A прочитал значение и вычислил новое. Планировщик ОС вытесняет его до записи.

B: expected = 5, next = 6

Поток B видит то же значение 5. С обычным value++ оба записали бы 6 — потерянное обновление.

B: compareAndSet(5, 6) → true

Одна инструкция процессора (lock cmpxchg на x86) атомарно сравнивает содержимое памяти с 5 и записывает 6. value = 6.

A: compareAndSet(5, 6) → false

В памяти уже 6, а A ожидал 5. Запись не выполнена, ничего не испорчено. A не блокировался и не спал — он просто узнал, что проиграл гонку.

A: повтор цикла — expected = 6, next = 7

Оптимистичный подход: «попробую, а при конфликте повторю». Под высокой конкуренцией таких повторов много — потоки жгут CPU впустую, и LongAdder (у каждого потока своя ячейка) становится быстрее.

A: compareAndSet(6, 7) → true

Итог 7 — ни одно обновление не потеряно, блокировок не было. Алгоритм lock-free: хотя бы один поток всегда продвигается.

Проблема ABA на стеке Трайбера

5.9Самопроверка

Что возвращает compareAndSet(expected, newValue), если текущее значение не равно expected?

  • Бросает исключение
  • Блокирует поток до совпадения
  • false, значение не меняется
  • Записывает newValue и возвращает старое значение
CAS никогда не блокирует. Повтор — забота вызывающего кода (цикл).

Когда LongAdder предпочтительнее AtomicLong?

  • Всегда
  • Много потоков часто пишут, читают редко (счётчики метрик)
  • Когда нужно точное мгновенное значение при каждом чтении
  • Для одного потока
LongAdder распределяет записи по ячейкам и суммирует при чтении; sum() не атомарен относительно параллельных записей.

if (atomic.get() < 10) atomic.incrementAndGet(); — потокобезопасно ли ограничение «не больше 10»?

  • Нет: проверка и изменение — два отдельных атомарных действия, между ними может вклиниться другой поток
  • Да, оба метода атомарны
  • Да, если поле final
  • Только с двумя потоками
Нужна одна операция: atomic.updateAndGet(v -> v < 10 ? v + 1 : v) или CAS-цикл.
Напишите потокобезопасный «выполнить инициализацию ровно один раз» без synchronized.
private final AtomicBoolean started = new AtomicBoolean();
public void start() {
    if (!started.compareAndSet(false, true)) return; // проиграли — уже стартовали
    doStart();
}

Тонкость: другие потоки вернутся сразу, не дожидаясь окончания doStart(). Если им нужно дождаться результата — используйте CompletableFuture/CountDownLatch или holder idiom.

Почему лямбда в updateAndGet должна быть без побочных эффектов?

При проигрыше CAS функция будет вызвана повторно с новым значением. Отправка сообщения, запись в лог, инкремент внешнего счётчика внутри неё произойдут несколько раз.

Когда LongAdder нельзя использовать вместо AtomicLong?

Когда нужно атомарное «изменить и получить результат» (уникальные id), CAS, или точный согласованный снимок значения в момент чтения: sum() складывает ячейки по очереди без блокировки, параллельные инкременты могут частично попасть в результат.

Что такое ABA и почему в Java со сборкой мусора она встречается реже?

CAS видит то же значение A, хотя между чтением и CAS оно менялось A→B→A. В языках с ручным управлением памятью освобождённый узел переиспользуется по тому же адресу. В Java объект не может быть переиспользован, пока на него держится ссылка (у нас она в локальной переменной), поэтому для ссылочных lock-free структур ABA обычно не возникает. Но остаётся для числовых состояний и пулов объектов; лечится версией (AtomicStampedReference).

Как LongAdder использует @Contended и зачем?

Ячейки Striped64.Cell аннотированы @jdk.internal.vm.annotation.Contended, поэтому каждая лежит в своей кэш-линии. Иначе соседние ячейки, обновляемые разными ядрами, попали бы в одну линию — false sharing уничтожил бы смысл шардирования.
