Встроенный механизм взаимного исключения: каждый объект в Java может быть локом. Разбираем, что именно он защищает, как устроен внутри и как на нём строить ожидание условий.

3.1Что делает synchronized

Вход в synchronized(obj) захватывает монитор объекта obj; выход (нормальный или исключением) — освобождает. Одновременно монитором владеет максимум один поток. Это даёт сразу все три гарантии:

  • Взаимное исключение → атомарность блока относительно других блоков на том же мониторе.
  • Видимость и порядок → unlock HB последующего lock того же монитора: всё, что поток записал внутри блока, увидит следующий владелец.
public class Account {
    private final Object lock = new Object();   // приватный лок — рекомендуемый вариант
    private long balance;

    public synchronized void a() { }            // монитор = this
    public static synchronized void b() { }     // монитор = Account.class
    public void c() {
        synchronized (lock) { balance++; }      // монитор = lock, область минимальна
    }
}

3.2Что именно защищает лок

Лок защищает не код и не объект, а инвариант: набор полей, которые должны меняться согласованно. Правило JCiP: каждая изменяемая переменная, доступная из нескольких потоков, должна читаться и писаться под одним и тем же локом, и все переменные одного инварианта — под одним локом.

class Range {
    private int lower, upper;                      // инвариант: lower <= upper
    public synchronized void setLower(int v) { if (v > upper) throw new IllegalArgumentException(); lower = v; }
    public void setUpper(int v) {                  // забыли synchronized
        if (v < lower) throw new IllegalArgumentException(); upper = v; // гонка: lower мог измениться между проверкой и записью
    }
    public int lower() { return lower; }           // чтение без лока — гонка видимости
}
На чём нельзя синхронизироваться
  • Строковые литералы и интернированные строки — один объект на всю JVM, чужая библиотека может взять тот же лок.
  • Boxed-типы (Integer, Boolean) — кэшируются (Integer.valueOf(1) — один объект на всех); а после count++ ссылка указывает уже на другой объект. С JDK 16 javac предупреждает о синхронизации на value-based классах.
  • Неfinal-поле — его переприсвоят, и потоки окажутся на разных мониторах.
  • Публичный this — внешний код может захватить ваш лок и устроить deadlock. Приватный final Object lock инкапсулирует политику синхронизации.

3.3Реентерабельность

Поток, владеющий монитором, может войти в него повторно — JVM увеличит счётчик рекурсии. Без этого вызов одного synchronized-метода из другого на том же объекте (или super.method()) приводил бы к самоблокировке.

class Widget { public synchronized void doSomething() { /* ... */ } }
class LoggingWidget extends Widget {
    @Override public synchronized void doSomething() {
        log("calling");
        super.doSomething();   // тот же монитор this — повторный вход разрешён
    }
}

3.4Как это устроено в HotSpot

В заголовке каждого объекта есть mark word (64 бита). По нему JVM понимает состояние лока. Захват без конкуренции дешёвый (CAS в заголовке или в per-thread стеке локов), с конкуренцией — лок «раздувается» (inflation) в полноценный ObjectMonitor с очередями, а ожидающие потоки паркуются в ОС.

РежимКогдаСтоимость
Biased lockingОбъект «привязан» к первому потоку. Выключен по умолчанию с JDK 15 и удалён в JDK 18 — дорогой revoke, мало пользы на современных CPU.—

JIT дополнительно умеет lock elision (убрать лок с объекта, не вышедшего за пределы потока — escape analysis) и lock coarsening (склеить соседние блоки на одном мониторе). Поэтому микробенчмарки «synchronized vs ReentrantLock» без JMH почти всегда врут.

3.5Составные действия на «потокобезопасных» объектах

Каждый метод Collections.synchronizedList или Vector атомарен, но их последовательность — нет:

List<String> list = Collections.synchronizedList(new ArrayList<>());
if (!list.contains(x)) {   // поток B может добавить x здесь
    list.add(x);           // дубликат
}
synchronized (list) {      // клиентская блокировка: synchronizedList использует себя как монитор
    if (!list.contains(x)) list.add(x);
}
// Итерация тоже требует внешнего лока, иначе ConcurrentModificationException:
synchronized (list) { for (String s : list) process(s); }

Для мап лучше сразу брать атомарные операции ConcurrentHashMap: putIfAbsent, computeIfAbsent, merge (тема 07).

3.6wait / notify: ожидание условия

Задача: поток должен ждать, пока не станет истинным некоторое условие на защищённом состоянии (очередь не пуста, баланс достаточен). Спин-цикл while(!cond) {} жжёт CPU; sleep добавляет задержку и не даёт HB. Правильный инструмент — условное ожидание.

Канонический шаблон — запомнить дословно 
synchronized (lock) {
    while (!condition) {      // ВСЕГДА while, не if
        lock.wait();          // атомарно: отпустить монитор + уснуть; при пробуждении — снова захватить
    }
    // здесь condition == true и мы владеем монитором
    doAction();
}

// Сторона, меняющая состояние:
synchronized (lock) {
    changeState();
    lock.notifyAll();         // будим ожидающих; они перепроверят условие
}
ПравилоПочему
wait/notify только внутри synchronized на том же объектеиначе IllegalMonitorStateException; и без лока проверка условия и засыпание неатомарны → потерянное пробуждение (lost wake-up).
Проверять условие в whileSpurious wakeup (спецификация разрешает пробуждения без notify); кроме того, между notify и повторным захватом монитора другой поток мог «съесть» условие.
По умолчанию notifyAllnotify будит один произвольный поток. Если в wait set потоки ждут разных условий (producer и consumer на одном мониторе), можно разбудить «не того», и сигнал потеряется → зависание. notify допустим, только когда все ожидающие равноправны и одного пробуждения достаточно.
Менять состояние до notify, в том же блокеиначе разбуженный поток увидит старое состояние и снова уснёт.

Ограниченный буфер на wait/notifyAll

public final class BoundedBuffer<T> {
    private final Object[] items;
    private int head, tail, count;
    private final Object lock = new Object();

    public BoundedBuffer(int capacity) { items = new Object[capacity]; }

    public void put(T item) throws InterruptedException {
        synchronized (lock) {
            while (count == items.length) lock.wait();   // ждём «не полон»
            items[tail] = item;
            tail = (tail + 1) % items.length;
            count++;
            lock.notifyAll();                            // будим потребителей
        }
    }

    @SuppressWarnings("unchecked")
    public T take() throws InterruptedException {
        synchronized (lock) {
            while (count == 0) lock.wait();              // ждём «не пуст»
            T item = (T) items[head];
            items[head] = null;                          // не держим ссылку для GC
            head = (head + 1) % items.length;
            count--;
            lock.notifyAll();                            // будим производителей
            return item;
        }
    }
}

Недостаток: у монитора один wait set, поэтому producer'ы и consumer'ы будят друг друга без разбора — лишние пробуждения. В теме 04 тот же буфер на ReentrantLock с двумя Condition (notFull, notEmpty) — именно так устроен ArrayBlockingQueue.

3.7Когда synchronized, а когда что-то другое

synchronized подходит

  • Короткая критическая секция, простая логика.
  • Нужен автоматический unlock (нельзя забыть).
  • JDK 24+: в виртуальных потоках больше не пиннинг (JEP 491).

Нужен Lock (тема 04)

  • tryLock с таймаутом, прерываемое ожидание.
  • Несколько условий ожидания.
  • Справедливость, read/write-разделение.
  • Лок захватывается в одном методе, отпускается в другом.

3.8Интерактив: монитор, entry set и wait set

Симулятор монитора объекта lock

Три потока работают с одним монитором. Кнопки каждого потока — действия, доступные ему сейчас.

Владелец монитора
Entry set — ждут входа (BLOCKED)
Wait set — вызвали wait() (WAITING)
Вне монитора

Попробуйте воспроизвести: (1) T1 входит и делает wait(), T2 входит и делает notify() — заметьте, что T1 оказывается в entry set и ждёт, пока T2 выйдет. (2) «Потерянный сигнал»: notify() при пустом wait set, затем другой поток делает wait() — он будет ждать вечно. Поэтому ожидание всегда пишут как while (!condition) lock.wait(); — проверка условия под тем же монитором защищает и от потерянных, и от ложных пробуждений.

3.9Самопроверка

Почему wait() вызывают в цикле while, а не в if?

  • Так быстрее
  • Возможны ложные пробуждения, а между notify и повторным захватом монитора условие может снова стать ложным
  • if не компилируется
  • wait() всегда бросает исключение
После пробуждения поток конкурирует за монитор наравне с другими; условие нужно перепроверить.

Метод synchronized void a() вызывает synchronized void b() того же объекта. Что произойдёт?

  • Deadlock
  • IllegalMonitorStateException
  • Всё работает: мониторы реентерабельны, счётчик входов увеличится
  • b() выполнится в другом потоке
Владелец монитора может входить в него повторно; монитор освобождается, когда счётчик вернётся к нулю.

Чем отличаются sleep(100) и wait(100)?

  • sleep не отпускает удерживаемый монитор, wait — отпускает и требует владения монитором
  • Ничем
  • wait нельзя прервать
  • sleep работает только в главном потоке
sleep внутри synchronized держит блокировку всё время сна — другие потоки ждут.
Какой монитор захватывают static synchronized и synchronized-метод экземпляра? Могут ли они выполняться одновременно?

static → объект Class (Foo.class), экземплярный → this. Это разные мониторы, поэтому да, могут выполняться одновременно — и если оба трогают одно статическое поле, это гонка.

Почему wait() нужно вызывать в цикле while?

Три причины: (1) spurious wakeup разрешён спецификацией; (2) при notifyAll просыпаются все, а условие может «забрать» первый успевший; (3) между notify и повторным захватом монитора состояние могло снова измениться. После пробуждения условие нужно перепроверить.

Отпускает ли sleep() монитор? А wait()?

sleep — нет, поток спит, держа все свои мониторы (частая причина «тормозов»). wait — отпускает только монитор того объекта, на котором вызван; остальные удерживаемые мониторы остаются захваченными (риск deadlock при вложенных локах).

Как может зависнуть буфер, если заменить notifyAll на notify?

Буфер ёмкостью 1, два producer'а и два consumer'а ждут на одном мониторе. Consumer забрал элемент и вызвал notify — проснулся второй consumer, а не producer. Он видит пустой буфер и снова засыпает. Сигнал «есть место» потерян, все четверо ждут. С notifyAll проснутся все, и producer продвинется.

Что такое lock elision и lock coarsening?

Оптимизации JIT. Elision: если escape analysis доказал, что объект-монитор не виден другим потокам (например, локальный StringBuffer), синхронизация удаляется. Coarsening: последовательные блоки на одном мониторе (цикл sb.append()) объединяются в один, чтобы не брать лок много раз.

Почему synchronized(Integer counter) — баг, даже если counter — поле?

Integer неизменяем: counter++ создаёт (или берёт из кэша) другой объект и меняет ссылку. Потоки начинают синхронизироваться на разных объектах. Плюс значения −128..127 кэшируются и общие для всей JVM — посторонний код может держать тот же монитор.
