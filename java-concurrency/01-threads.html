Потоки: жизненный цикл и API

Что такое поток на самом деле, как его создать, остановить и дождаться — и почему stop() запрещён, а interrupt() — это просьба, а не приказ.

1.1Процесс, поток, ядро

Процесс — изолированное адресное пространство (своя память, файловые дескрипторы). Поток — независимый поток исполнения внутри процесса: свой стек вызовов и регистры (включая program counter), но общая куча со всеми остальными потоками процесса. Именно общая куча делает потоки дешёвыми для обмена данными — и опасными.

Классический («платформенный») Thread в HotSpot — это 1:1 обёртка над потоком ОС (pthread в Linux, Windows thread). Планирует его ядро ОС, а не JVM. Отсюда цена: ~1 МБ зарезервированного стека, системный вызов на создание, переключение контекста через ядро (единицы микросекунд). Поэтому тысячи платформенных потоков — нормально, сотни тысяч — нет. Это ограничение снимают виртуальные потоки (тема 10).

Вопрос с собеседования: конкурентность vs параллелизм Concurrency — структура программы: несколько задач в процессе выполнения одновременно, их шаги могут чередоваться (даже на одном ядре). Parallelism — свойство исполнения: шаги буквально выполняются одновременно на разных ядрах. Конкурентный код может не быть параллельным, но проблемы видимости и гонок возникают в обоих случаях.

1.2Создание и запуск

public class ThreadBasics {
    public static void main(String[] args) throws InterruptedException {
        // 1. Runnable — задача отделена от механизма исполнения (предпочтительно)
        Runnable task = () -> System.out.println("run in " + Thread.currentThread().getName());

        Thread t1 = new Thread(task, "worker-1");
        t1.start();          // создаёт поток ОС, который вызовет run()
        // t1.run();         // ОШИБКА: выполнится в текущем потоке, нового не будет

        // 2. Builder API (JDK 21+): единый способ для платформенных и виртуальных
        Thread t2 = Thread.ofPlatform().name("worker-", 2).daemon(false).start(task);
        Thread t3 = Thread.ofVirtual().name("virt-1").start(task);

        t1.join(); t2.join(); t3.join();  // ждём завершения
        System.out.println("all done");
    }
}

start() vs run()

start() можно вызвать один раз — повтор бросит IllegalThreadStateException. run() — обычный метод: вызвали напрямую — никакого параллелизма.

Наследовать Thread?

Почти никогда. Наследование смешивает «что делать» и «как исполнять». С Runnable/Callable задачу можно отдать в пул, в виртуальный поток, в тест.

1.3Состояния потока

Thread.getState() возвращает одно из шести значений Thread.State. Это состояния с точки зрения JVM: поток в RUNNABLE может в этот момент не исполняться на CPU (ждать квант времени или блокирующий системный вызов чтения сокета).

1.4Прерывание: кооперативная отмена

В Java нет безопасного способа «убить» поток. Thread.stop() освобождал все мониторы посреди операции и оставлял объекты в полуизменённом состоянии; в JDK 20+ он всегда бросает UnsupportedOperationException. Вместо этого — прерывание: у каждого потока есть флаг interrupted, а код сам решает, как на него реагировать.

Если поток заблокирован

В sleep, wait, join, BlockingQueue.take, lockInterruptibly — он просыпается с InterruptedException, и флаг сбрасывается.

Если поток считает

Ничего не происходит, кроме установки флага. Код должен сам проверять Thread.currentThread().isInterrupted().

public final class CancellableWorker implements Runnable {
    private final BlockingQueue<String> queue;

    public CancellableWorker(BlockingQueue<String> queue) { this.queue = queue; }

    @Override
    public void run() {
        try {
            while (!Thread.currentThread().isInterrupted()) {   // проверка для CPU-работы
                String job = queue.take();                        // блокирующий вызов — сам реагирует
                process(job);
            }
        } catch (InterruptedException e) {
            // Мы владеем этим потоком и выходим из run() — это и есть «обработка».
            Thread.currentThread().interrupt(); // восстанавливаем флаг для кода выше по стеку
        } finally {
            cleanup();
        }
    }
    private void process(String job) { /* ... */ }
    private void cleanup() { /* закрыть ресурсы */ }
}
Антипаттерн: проглотить прерывание 
try { Thread.sleep(1000); } catch (InterruptedException e) { /* ignore */ }
После этого флаг сброшен, и вызывающий код (например, пул при shutdownNow()) никогда не узнает, что поток просили остановиться. Правило: либо пробросьте InterruptedException выше, либо восстановите флаг Thread.currentThread().interrupt().

Методы: t.interrupt() — выставить флаг; t.isInterrupted() — прочитать; статический Thread.interrupted() — прочитать и сбросить флаг текущего потока (легко ошибиться).

1.6Исключения в потоках

Исключение, вылетевшее из run(), не попадает в поток, который вызвал start(). Поток просто умирает, а стек печатается в System.err обработчиком по умолчанию. В продакшене это значит: исключение пропадёт мимо логов.

Thread.setDefaultUncaughtExceptionHandler((thread, ex) ->
        log.error("Uncaught in {}", thread.getName(), ex));

Thread t = new Thread(() -> { throw new IllegalStateException("boom"); });
t.setUncaughtExceptionHandler((th, ex) -> metrics.increment("worker.crash"));
t.start();
Важно для пулов Задача, отправленная через executor.submit(), не вызывает UncaughtExceptionHandler: исключение «упаковывается» в Future и всплывёт только на future.get() как ExecutionException. Если get() никто не вызовет — ошибка исчезнет молча. С execute() обработчик сработает. Подробно — в теме 08.

1.7ThreadLocal и thread confinement

Самый простой способ избежать гонки — не разделять данные. Thread confinement: объект доступен только одному потоку. Варианты: локальные переменные (stack confinement), ThreadLocal, передача владения через очередь.

// SimpleDateFormat не потокобезопасен — даём каждому потоку свой экземпляр
private static final ThreadLocal<SimpleDateFormat> FMT =
        ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

String format(Date d) { return FMT.get().format(d); }
// В современном коде: DateTimeFormatter — неизменяемый и потокобезопасный, ThreadLocal не нужен.
Утечка в пулах Потоки пула живут вечно, значит и их ThreadLocal-значения тоже. Если положить в ThreadLocal контекст запроса (userId, транзакцию, MDC) и не вызвать remove() в finally, следующая задача на этом потоке увидит чужие данные. В финтехе это инцидент безопасности, а не просто утечка памяти. Для виртуальных потоков и structured concurrency используйте ScopedValue (тема 10). 
CONTEXT.set(requestContext);
try {
    handle(request);
} finally {
    CONTEXT.remove();  // обязательно
}

  1. Создайте поток, который в цикле инкрементирует счётчик без sleep, и прервите его из main через 100 мс. Почему он не останавливается? Добавьте проверку флага.
  2. Замените проверку флага на Thread.sleep(10) внутри цикла и catch с пустым телом. Объясните, почему поток снова не останавливается.
  3. Запустите 3 потока, каждый бросает исключение. Установите default handler и убедитесь, что все три залогированы. Повторите через ExecutorService.submit — что изменилось?

1.10Самопроверка

Поток заблокирован в inputStream.read() на сокете. Какое состояние покажет getState()?

  • BLOCKED
  • WAITING
  • RUNNABLE — состояния Java не отражают блокировку в системном вызове
  • TIMED_WAITING
BLOCKED — только ожидание монитора. I/O-ожидание JVM считает выполнением нативного кода.

Что делает thread.interrupt()?

  • Немедленно останавливает поток
  • Устанавливает флаг прерывания; блокирующие методы (sleep, wait, join) реагируют InterruptedException, остальной код должен проверять флаг сам
  • Убивает поток в ОС
  • Приостанавливает до resume()
Отмена в Java кооперативная. Поток сам решает, когда и как завершиться.

Что нужно сделать в catch (InterruptedException e), если метод не может пробросить исключение?

  • Восстановить флаг: Thread.currentThread().interrupt(), и завершить работу
  • Оставить catch пустым
  • Вызвать System.exit
  • Повторить sleep
Исключение сбрасывает флаг. Не восстановив его, вы скрываете запрос на остановку от кода выше — пул не сможет корректно завершиться.
Что разделяют потоки одного процесса, а что у каждого своё?

Общее: куча (все объекты), статические поля, загруженные классы, открытые файлы/сокеты процесса. Своё: стек вызовов (фреймы, локальные переменные, ссылки), program counter, набор ThreadLocal-значений, состояние прерывания. Поэтому локальная переменная потокобезопасна, а объект по ссылке из неё — нет, если ссылка «утекла» в другой поток.

В каком состоянии поток, ожидающий ReentrantLock.lock()? А ожидающий synchronized?

lock() → WAITING (реализован через LockSupport.park). synchronized → BLOCKED. В thread dump у первого будет parking to wait for <...ReentrantLock$NonfairSync>, у второго — waiting to lock <0x...>.

Почему stop() убрали, и как правильно остановить поток?

stop() бросал ThreadDeath в произвольной точке и отпускал все мониторы — инварианты защищённых объектов могли остаться нарушенными, и другие потоки видели «полусостояние». Правильно — кооперативно: interrupt() + код, который проверяет флаг и реагирует на InterruptedException; либо volatile-флаг; в пулах — shutdownNow() или future.cancel(true), которые сами вызывают interrupt.

Что произойдёт с флагом прерывания после того, как sleep() бросил InterruptedException?

Флаг будет сброшен. Поэтому, если вы не пробрасываете исключение дальше, нужно восстановить его: Thread.currentThread().interrupt(). Иначе код выше по стеку не узнает об отмене.

Гарантирует ли join() видимость записей другого потока?

Да. По JMM: все действия в потоке T happens-before успешного возврата из T.join() в другом потоке. Поэтому после join() можно без volatile читать результаты, записанные T в обычные поля.

Почему ThreadLocal + пул потоков — источник багов? Как защититься?

Значение хранится в объекте Thread, а потоки пула переиспользуются. Без remove() следующая задача получит значение предыдущей (утечка контекста, а при больших объектах — памяти; в контейнерах приложений ещё и ClassLoader leak). Защита: всегда try/finally { remove(); }, обёртка-декоратор для задач, либо ScopedValue с ограниченной областью действия.
