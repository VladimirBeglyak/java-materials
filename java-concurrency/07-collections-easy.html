7.1Три поколения

Старые: Vector, Hashtable

Каждый метод под одним замком. Безопасно, но медленно, и составные действия всё равно не защищены.

Обёртки: synchronizedList

То же самое для обычных коллекций. При обходе нужно вручную держать замок.

Конкурентные: java.util.concurrent

Спроектированы для многих потоков: мелкие замки или CAS, безопасный обход. Их и используют.

Главная мысль Для многопоточности — коллекции из java.util.concurrent.

7.2ConcurrentHashMap: замки на ящиках

Обычная HashMap — шкаф с ящиками (глава 09 java-core). Чтобы несколько потоков работали одновременно, ConcurrentHashMap не запирает весь шкаф: пустой ящик заполняется через CAS, а при записи в непустой запирается только этот ящик. Чтение вообще без замков. Поэтому сотни потоков работают параллельно, если попадают в разные ящики.

Составные действия делайте её атомарными методами: computeIfAbsent, merge, compute — а не «get, потом put». Ещё особенности: null нельзя ни в ключах, ни в значениях; size() во время записей — примерный.

Подсчёт слов из многих потоков
✗ c = map.get(w); map.put(w, c + 1)
два потока прочитали 5 → оба записали 6 → одно слово потеряно✓ map.merge(w, 1, Integer::sum)
чтение + сложение + запись — одно атомарное действие для ключаразные слова в разных ящиках → потоки вообще не мешают друг другу

Каждая операция безопасна, а их связка — нет.

merge выполняет всё под замком ящика.

Замок только на ящик — остальные свободны.

Главная мысль ConcurrentHashMap — замки на отдельные ящики. Составные действия — через merge/compute.

В полной главе: 7.2 ConcurrentHashMap изнутри (JDK 8+)

7.3CopyOnWrite: копия при каждой записи

CopyOnWriteArrayList при каждом изменении делает полную копию массива и подменяет ссылку. Читатели всегда видят целый, неизменный «снимок» и не ждут ни секунды. Идеально для списка подписчиков или настроек: читают постоянно, меняют редко. Для частых записей — ужасно: каждое добавление копирует всё.

Главная мысль Много чтений, редкие записи — CopyOnWrite. Частые записи — никогда.

В полной главе: 7.3 CopyOnWriteArrayList / Set

7.4BlockingQueue: конвейер между потоками

Производители кладут задачи на ленту, потребители забирают. BlockingQueue сама разруливает ожидание: если лента пуста, take() ждёт; если полна (у очереди есть вместимость), put() ждёт. Так естественно возникает обратное давление: быстрый производитель не завалит медленного потребителя.

  • ArrayBlockingQueue — фиксированная вместимость;
  • LinkedBlockingQueue — по умолчанию практически без ограничения (осторожно с памятью);
  • SynchronousQueue — без места вовсе: «из рук в руки»;
  • PriorityBlockingQueue, DelayQueue — по приоритету и по времени.
Главная мысль BlockingQueue — готовый производитель-потребитель. Ограничивайте вместимость.

В полной главе: 7.4 BlockingQueue: передача данных между потоками

7.5ConcurrentSkipListMap: отсортированная и конкурентная

Если нужна map с отсортированными ключами для многих потоков (аналог TreeMap), есть ConcurrentSkipListMap. Внутри — «список с экспресс-полосами»: несколько уровней ссылок, по которым поиск перескакивает через многие элементы, как экспресс-поезд мимо мелких станций.

Главная мысль Нужна сортировка и потоки — ConcurrentSkipListMap.

7.8Проверьте себя

Как правильно увеличить счётчик слова в ConcurrentHashMap из многих потоков?

  • get, затем put
  • map.merge(слово, 1, Integer::sum)
  • synchronized вокруг get
  • volatile map
merge атомарен для ключа.

Когда CopyOnWriteArrayList — плохой выбор?

  • список подписчиков
  • настройки, которые меняются раз в час
  • когда читают чаще, чем пишут
  • когда в список часто добавляют элементы
Каждая запись копирует весь массив.

Что делает take() у пустой BlockingQueue?

  • ждёт, пока появится элемент
  • возвращает null
  • бросает исключение
  • создаёт элемент
Поэтому она удобна для производителя-потребителя.

Можно ли положить null в ConcurrentHashMap?

  • да
  • только как значение
  • нет, ни ключ, ни значение
  • только как ключ
Иначе null в get был бы неоднозначен при параллельной работе.

Почему ConcurrentHashMap быстрее Hashtable при многих потоках?

  • она меньше
  • она запирает не всю таблицу, а только нужный ящик, а чтение идёт без замков
  • она не потокобезопасна
  • Hashtable быстрее
Потоки в разных ящиках не мешают друг другу.
