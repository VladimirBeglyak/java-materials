Конкурентные коллекции

Коллекции, которые сами отвечают за потокобезопасность — и при этом масштабируются. Главное здесь — понять какие операции атомарны, а какие нет, и как ConcurrentHashMap добивается параллельной записи.

7.1Три поколения

Synchronized (JDK 1.0–1.2)

Vector, Hashtable, Collections.synchronizedXxx. Один лок на всё. Итерация требует внешнего лока. Пропускная способность ≈ одного потока.

Concurrent (JDK 5+)

ConcurrentHashMap, ConcurrentLinkedQueue, ConcurrentSkipListMap. Тонкие локи / CAS, атомарные составные операции, слабо согласованные итераторы.

Copy-on-write и очереди

CopyOnWriteArrayList для «читают всегда, пишут редко»; семейство BlockingQueue для передачи данных между потоками.

7.2ConcurrentHashMap изнутри (JDK 8+)

В JDK 7 карта делилась на 16 сегментов-локов. С JDK 8 устройство другое — и спрашивают именно его:

  • Null запрещён и в ключах, и в значениях: иначе get(k) == null неоднозначно (нет ключа или значение null), а проверить containsKey атомарно с get нельзя.
  • Итераторы слабо согласованные (weakly consistent): не бросают ConcurrentModificationException, отражают состояние на какой-то момент во время обхода, могут увидеть или не увидеть параллельные изменения.
  • size() — оценка под конкурентной записью (счётчик на CounterCell[], как LongAdder). Для больших карт — mappingCount() (long).

Атомарные составные операции — главное, что нужно уметь

if (!map.containsKey(k)) map.put(k, create(k));      // два потока создадут оба
Integer old = map.get(word); map.put(word, old == null ? 1 : old + 1);  // потеря инкрементов
ConcurrentHashMap<String, Long> counts = new ConcurrentHashMap<>();
counts.merge(word, 1L, Long::sum);                         // атомарный счётчик

ConcurrentHashMap<String, LongAdder> hot = new ConcurrentHashMap<>();
hot.computeIfAbsent(word, k -> new LongAdder()).increment(); // ещё лучше под высокой нагрузкой

Map<Long, Client> cache = new ConcurrentHashMap<>();
Client c = cache.computeIfAbsent(id, this::loadClient);    // загрузка ровно один раз на ключ

map.compute(k, (key, v) -> v == null ? init() : v.next()); // произвольное атомарное обновление
map.putIfAbsent(k, v);  map.replace(k, expected, newV);  map.remove(k, expected);
Ловушки compute*/merge
  • Функция выполняется под локом бакета. Медленная функция (HTTP, запрос в БД) блокирует запись во все ключи этого бакета, а при resize — может тормозить и больше. Для дорогих загрузок кладите в карту CompletableFuture (см. Memoizer в теме 12) или используйте Caffeine.
  • Нельзя менять ту же карту изнутри функции (computeIfAbsent, внутри которого снова computeIfAbsent на этой карте) — в JDK 9+ это IllegalStateException: Recursive update, в JDK 8 мог быть вечный цикл.
  • Функция должна быть короткой и без побочных эффектов, видимых другим потокам.

Bulk-операции

forEach, search, reduce с порогом параллелизма — выполняются в ForkJoinPool.commonPool():

long total = balances.reduceValuesToLong(1_000, BigDecimal::longValue, 0L, Long::sum);
String vip = clients.search(1_000, (id, c) -> c.isVip() ? c.name() : null);

7.3CopyOnWriteArrayList / Set

Каждая модификация копирует весь массив под локом и публикует новую ссылку через volatile. Чтение и итерация — без локов по неизменяемому снимку; итератор никогда не бросает CME и не видит изменений, сделанных после его создания.

✔ Идеально

Списки слушателей/подписчиков, конфигурация маршрутов, whitelist — сотни чтений на одну запись, маленький размер.

✘ Катастрофа

Частые записи или большой список: каждая вставка — O(n) копирование и мусор для GC. add в цикле на 100 000 элементов = квадратичная сложность.

public final class Pipeline {
    private static final Payment POISON = new Payment(-1, BigDecimal.ZERO);
    private final BlockingQueue<Payment> queue = new ArrayBlockingQueue<>(1_000); // backpressure

    void produce(Iterable<Payment> source) throws InterruptedException {
        for (Payment p : source) queue.put(p);   // блокируется, если consumer не успевает
        queue.put(POISON);                        // сигнал конца (по одной пилюле на consumer)
    }

    void consume() throws InterruptedException {
        while (true) {
            Payment p = queue.take();
            if (p == POISON) return;              // сравнение по ссылке
            process(p);
        }
    }
    private void process(Payment p) { /* ... */ }
    record Payment(long id, BigDecimal amount) {}
}

Передача объекта через очередь даёт HB (put HB take), поэтому producer может заполнить обычные поля объекта до put, а consumer — читать их без синхронизации, если producer после этого объект не трогает (передача владения). Пачками забирайте через drainTo(list, max) — меньше захватов лока.

7.5ConcurrentSkipListMap / Set

Конкурентный аналог TreeMap: упорядоченная карта на skip list с CAS, O(log n), без локов. Нужна, когда требуется сортировка и диапазоны (headMap, ceilingKey) под конкурентной записью: стакан заявок, окна по времени, планировщики.

7.8Самопроверка

Как ConcurrentHashMap (Java 8+) обеспечивает потокобезопасность записи?

  • Один общий лок на всю таблицу
  • 16 сегментов с ReentrantLock
  • CAS для пустого бакета и synchronized на первом узле занятого бакета
  • Копирование таблицы при каждой записи
Сегменты были в Java 7. Сейчас гранулярность — один бакет, а чтение вообще без блокировок (volatile-чтение узлов).

Для чего подходит CopyOnWriteArrayList?

  • Для очереди задач с частыми вставками
  • Для редко изменяемых списков, которые часто читают и обходят: слушатели, конфигурация
  • Для хранения больших объёмов данных
  • Для сортировки
Каждая запись копирует весь массив — O(n). Зато итерация идёт по неизменяемому снимку без блокировок.

Почему ConcurrentHashMap не допускает null в качестве ключа и значения?

  • В конкурентной среде get(k) == null был бы неоднозначен: «ключа нет» или «значение null» — а проверить вторым вызовом нельзя атомарно
  • Так исторически сложилось, причин нет
  • null нельзя хэшировать
  • Для экономии памяти
В HashMap неоднозначность снимается containsKey, но здесь между двумя вызовами карта может измениться.
Как ConcurrentHashMap в JDK 8+ обеспечивает параллельную запись?

Вставка в пустой бакет — CAS без лока. В непустой — synchronized на первом узле бакета: блокируется только этот бакет. Чтение без локов через volatile. Resize кооперативный: таблица переносится частями, перенесённые бакеты помечаются ForwardingNode, и потоки, пришедшие писать, помогают переносу. Длинные цепочки превращаются в красно-чёрные деревья.

Почему в ConcurrentHashMap нельзя класть null?

Чтобы get однозначно сообщал «ключа нет». В однопоточной HashMap можно уточнить через containsKey, а в конкурентной между get и containsKey карта может измениться, и неоднозначность не разрешить.

Что не так с computeIfAbsent(id, this::loadFromRemoteService)?

Удалённый вызов выполняется под локом бакета: другие записи в этот бакет ждут, пока сервис ответит; при таймаутах — каскадная деградация. Решение: хранить CompletableFuture<V> (функция только создаёт future, загрузка идёт вне лока) или специализированный кэш.

Почему new LinkedBlockingQueue<>() опасна в продакшене?

Ёмкость по умолчанию Integer.MAX_VALUE, то есть очередь фактически неограничена. Если consumer медленнее producer'а, очередь растёт до OutOfMemoryError, а задержка обработки растёт неограниченно. Всегда задавайте ёмкость — это и есть backpressure.

Видит ли итератор CopyOnWriteArrayList элементы, добавленные после его создания?

Нет. Итератор держит ссылку на массив-снимок на момент создания. Добавления создают новый массив, итератор продолжает обходить старый. Методы remove итератора не поддерживаются (UnsupportedOperationException).
