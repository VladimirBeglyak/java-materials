TLS: криптография рукопожатия и forward secrecy

TLS — самый массовый потребитель криптографии: он собирает вместе всё изученное — сертификаты, подписи, ECDH, симметричное шифрование. Здесь разбираем TLS с криптографической стороны: как две стороны без общего секрета договариваются о ключе, что такое forward secrecy и из чего состоит набор шифров.

9.1Что решает TLS

TLS даёт три свойства поверх TCP: конфиденциальность (симметричное шифрование трафика), целостность (AEAD) и аутентичность сервера (сертификат + подпись). Ключевая задача рукопожатия — безопасно согласовать симметричный ключ сессии между двумя сторонами, которые раньше не встречались.

Сетевой взгляд — в соседнем пособии Порядок сообщений, SNI, ALPN, mTLS и работа с keystore/truststore разобраны в теме 09 пособия «Компьютерные сети». Здесь — только криптографическая суть.

9.2Обмен ключами: ECDHE

Стороны используют эфемерный Диффи — Хеллман на эллиптической кривой (ECDHE): каждая генерирует временную пару ключей и отправляет открытую часть другой стороне. Из своего закрытого и чужого открытого ключа обе вычисляют одинаковый общий секрет, который наблюдатель из двух открытых ключей восстановить не может.

клиент:  закрытый a, открытый A = a·G  ── A ──▶
сервер:  закрытый b, открытый B = b·G  ◀── B ──
клиент:  общий секрет S = a·B
сервер:  общий секрет S = b·A          # a·b·G = b·a·G — совпадают!

Из общего секрета через HKDF (тема 08) выводятся ключи шифрования и целостности для обоих направлений.

9.3Набор шифров (cipher suite)

Набор шифров описывает всю цепочку алгоритмов. В TLS 1.3 остались только AEAD-шифры:

TLS_AES_128_GCM_SHA256
 └─ обмен ключами: ECDHE (фиксирован в 1.3)
    └─ шифрование: AES-128-GCM (AEAD)
       └─ хэш/PRF: SHA-256 (для HKDF)
TLS 1.3 упростил выбор Убраны слабые варианты (RSA-обмен ключами без forward secrecy, CBC-режимы, RC4). Остались AEAD (AES-GCM, ChaCha20-Poly1305) и обязательный ECDHE. Это и есть причина, почему TLS 1.3 и быстрее, и безопаснее.

9.4Forward secrecy

Forward secrecy — свойство, при котором компрометация долговременного закрытого ключа сервера не позволяет расшифровать ранее записанный трафик. Оно достигается тем, что ключ сессии выводится из эфемерных ключей, которые уничтожаются после рукопожатия.

С forward secrecy (ECDHE)

Украли приватный ключ сертификата позже — старые записи всё равно не расшифровать: эфемерные ключи уже удалены.

Без forward secrecy (старый RSA-обмен)

Ключ сессии шифровался открытым RSA-ключом сервера; украв приватный ключ, атакующий расшифрует и старый трафик.

Почему старый RSA-обмен убрали Он не давал forward secrecy, а приватный ключ становился «золотым ключом» ко всей истории. TLS 1.3 требует ECDHE, поэтому forward secrecy теперь обязателен.

9.5Самопроверка

Какую главную задачу решает рукопожатие TLS?

  • Сжать трафик
  • Безопасно согласовать симметричный ключ сессии через ECDHE
  • Выбрать браузер
  • Найти IP-адрес
Рукопожатие согласует общий секрет, из которого выводятся ключи шифрования трафика.

Что даёт forward secrecy?

  • Компрометация закрытого ключа сервера не раскрывает прошлый трафик
  • Ускорение рукопожатия
  • Скрытие IP
  • Сжатие сертификатов
Сеансовые ключи — из эфемерного ECDHE и не сохраняются; долговременный ключ используется только для подписи.

Почему TLS 1.3 безопаснее и быстрее TLS 1.2?

  • В нём больше шифров
  • Он не использует сертификаты
  • Убраны слабые варианты (RSA-обмен, CBC), остались AEAD и обязательный ECDHE; рукопожатие короче
  • Он не шифрует заголовки
TLS 1.3 оставил только AEAD-шифры и обязательный ECDHE, сократив рукопожатие до 1 RTT.

Из чего выводится ключ сессии в TLS 1.3?

  • Из пароля пользователя
  • Из IP-адреса
  • Из случайного числа
  • Из общего секрета ECDHE через HKDF
Общий секрет a·b·G через HKDF превращается в независимые ключи для каждого направления.
Объясните ECDHE своими словами.

Каждая сторона создаёт временную пару ключей и отправляет открытую часть. Из своего закрытого и чужого открытого ключа обе вычисляют одинаковый общий секрет, который наблюдатель восстановить не может. Временные ключи удаляются после рукопожатия — отсюда forward secrecy.

Почему сертификат и подпись недостаточны без обмена ключами?

Сертификат подтверждает, кто сервер, но не создаёт общий секрет для шифрования. Подпись доказывает авторство, а ECDHE создаёт ключ сессии. В TLS оба механизма работают вместе: сначала доверяем серверу, затем согласуем ключ.
