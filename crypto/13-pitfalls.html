Типичные ошибки и атаки

Криптографию почти никогда не «взламывают» математически — её ломают через ошибки реализации: слабый режим, предсказуемая случайность, ключ в коде, неаккуратное сравнение. Знание этих ошибок в лицо — то, что отличает специалиста, который не повторит чужой провал.

13.1ECB и утечка структуры

В ECB одинаковые блоки открытого текста дают одинаковый шифротекст. Изображение, зашифрованное ECB, остаётся узнаваемым по контурам. Это самая наглядная ошибка выбора режима.

Признак AES/ECB/… в коде или конфигурации. Лечение — аутентифицированный режим (GCM).

13.2Слабая случайность

Ключи и nonce, сгенерированные java.util.Random или из времени, предсказуемы: атакующий воспроизводит генератор и угадывает ключ. Реальные инциденты (например, предсказуемые nonce в ECDSA) приводили к восстановлению закрытых ключей.

Random r = new Random(System.currentTimeMillis());   // предсказуемо
byte[] key = new byte[32]; r.nextBytes(key);          // НЕЛЬЗЯ
Лечение Только SecureRandom без ручного seed (тема 07).

13.3Захардкоженные ключи и секреты

Ключ в исходниках, конфигурации, docker-образе или логе — утечка навсегда (git-история не забывает). Поиск таких ключей автоматизирован (сканеры секретов).

String key = "supersecret123";      // в коде — утёк
Cipher c = Cipher.getInstance("AES/GCM/NoPadding");
Лечение KMS/менеджер секретов, ротация, сканеры секретов в CI, никогда не логировать ключи и пароли.

13.4Padding oracle

В CBC, если сервер по-разному отвечает на «неверный padding» и «неверный MAC», атакующий, посылая модифицированные шифротексты, байт за байтом восстанавливает открытый текст. Классические атаки (POODLE, Lucky13) эксплуатировали именно это.

Лечение Не использовать CBC; в AEAD (GCM) такой атаки нет, потому что тег проверяется атомарно до любых различимых ответов.

13.5Timing-атаки

Если сравнение секретов (пароль, HMAC, тег) выполняется побайтово с ранним выходом, время ответа утекает число совпавших байт. Атакующий подбирает значение по одному байту.

if (!Arrays.equals(expectedMac, receivedMac)) throw ...;  // ранний выход
Лечение MessageDigest.isEqual(a, b) — сравнение за постоянное время (тема 12).

13.6Downgrade-атаки

Злоумышленник заставляет стороны договориться о более слабом протоколе/шифре, отбрасывая сильные варианты (или клиент поддерживает устаревшие). TLS 1.3 борется с этим, фиксируя сильные алгоритмы и подписывая согласование.

Лечение Минимальная версия TLS 1.2+ (лучше 1.3), запрет слабых cipher suites, отключение SSLv3/TLS 1.0/1.1.

13.7Чек-лист ревью криптографии

  1. Режим шифрования — AEAD (GCM/ChaCha20), не ECB и не «голый» CBC?
  2. Случайность — SecureRandom без ручного seed?
  3. Ключи — не в коде/логах, а в KMS; есть ли ротация?
  4. Сравнение секретов — за постоянное время?
  5. Пароли — argon2/bcrypt с солью, не SHA/MD5?
  6. TLS — минимальная версия и сильные cipher suites?
  7. Nonce/IV — уникальные, не переиспользуются?

13.8Самопроверка

Что такое padding oracle?

  • Атака на неправильную обработку ошибок padding в CBC, позволяющая восстановить открытый текст
  • Утечка ключа
  • Перебор пароля
  • Подмена DNS
Разные ответы на «плохой padding»/«плохой MAC» дают оракул, по которому байт за байтом восстанавливают текст. AEAD лечит.

Почему Arrays.equals опасен для сравнения секретов?

  • Он медленный
  • Он выходит раньше при расхождении — время утекает, сколько байт совпало
  • Он возвращает строку
  • Он не поддерживает byte[]
Timing-атака: по задержке подбирают байты. Используйте MessageDigest.isEqual.

Чем опасен ключ, закоммиченный в git?

  • Он станет публичным и утечёт навсегда вместе с историей
  • Он замедлит сборку
  • Он не работает
  • Он конфликтует с ветками
Git хранит всю историю: даже удаление из текущей версии не убирает ключ из старых коммитов.

Как защититься от downgrade-атак TLS?

  • Использовать SSLv3
  • Разрешить все версии
  • Отключить шифрование
  • Минимальная версия TLS 1.2+, запрет слабых cipher suites
Фиксация минимальной версии и сильных наборов не даёт сторонам «договориться» о слабом шифре.
Назовите три самых частых ошибки криптографии в коде.

Слабый режим (ECB/CBC без MAC), предсказуемая случайность (java.util.Random/время) и захардкоженные ключи/секреты. Далее — неаккуратное сравнение (timing) и хранение паролей быстрым хэшем.

Почему AEAD устраняет целый класс атак?

AEAD (GCM) проверяет целостность и конфиденциальность атомарно: любое изменение шифротекста ломает тег, и нет «различимых» ошибок, на которых строится padding oracle. Плюс исчезает риск «шифрование без целостности».
