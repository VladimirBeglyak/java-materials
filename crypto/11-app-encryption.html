Шифрование в приложении (field-level)

Field-level шифрование — когда приложение само шифрует отдельные поля (номер паспорта, токен, платёжные данные) до записи в БД. Это защищает даже от чтения файлов БД и частично от SQL-доступа, но ломает поиск, сортировку и индексы по зашифрованному полю. Задача — понять этот trade-off и выбрать правильный режим.

11.1Зачем шифровать поле

Обычно БД уже защищена (TLS, роли, шифрование at rest), но есть поля, которые не должны видеть даже администраторы БД или те, кто получил дамп: номера документов, секреты, чувствительные персональные данные. Их шифруют в приложении — ключ лежит только в приложении/KMS, а не в БД.

Дополнение, а не замена Field-level не отменяет остальные меры: это последний рубеж для самых чувствительных полей. Для всех остальных данных достаточно TLS + at rest + контроля доступа.

11.2Как шифровать поле

// ключ — из KMS (обёрнутый, тема 08), nonce — случайный 96 бит
byte[] encrypt(byte[] plain, SecretKey key) {
    byte[] nonce = new byte[12];
    new SecureRandom().nextBytes(nonce);
    Cipher c = Cipher.getInstance("AES/GCM/NoPadding");
    c.init(Cipher.ENCRYPT_MODE, key, new GCMParameterSpec(128, nonce));
    byte[] ct = c.doFinal(plain);
    return concat(nonce, ct);   // храним nonce + шифротекст вместе
}
Храните nonce с шифротекстом Nonce не секретен, но нужен для расшифровки — сохраняйте его в той же колонке (nonce || ciphertext) или отдельным полем. Не переиспользуйте nonce с одним ключом (тема 04).

11.3Trade-off: что ломается

ОперацияРаботает ли по зашифрованному полю
Точное сравнение (WHERE field = ?)❌ нельзя — шифротекст разный каждый раз
Поиск подстроки (LIKE)❌
Сортировка (ORDER BY)❌ порядок шифротекста не совпадает
Индекс❌ обычный индекс бесполезен
Агрегаты, диапазоны (BETWEEN)❌

Поэтому field-level применяют к полям, по которым не ищут, а ищут по соседним незашифрованным полям или по отдельному «слепому индексу» (см. ниже).

11.4Детерминированное шифрование

Если по полю всё же нужно точное сравнение, используют детерминированное шифрование: один и тот же открытый текст всегда даёт один и тот же шифротекст (фиксированный nonce/синтетический IV). Тогда WHERE enc = ? работает.

Вероятностное (GCM, случайный nonce)

Один текст → разный шифротекст. Безопаснее (не видно повторов), но поиск невозможен.

Детерминированное

Один текст → один шифротекст. Позволяет точное равенство, но утекает факт «у двух записей одинаковое значение».

Компромисс детерминированности Детерминированное шифрование раскрывает равенство значений (кто-то может сопоставить записи). Используйте его только когда точный поиск необходим, и сочетайте с высокой энтропией значений (например, уникальные номера документов).

11.5Самопроверка

Что ломает field-level шифрование у поля?

  • Поиск, сортировку, индексы и агрегаты по этому полю
  • Ничего
  • Только запись
  • Только чтение соседних полей
Шифротекст случаен, поэтому сравнивать, искать и сортировать по нему нельзя.

Когда оправдано детерминированное шифрование?

  • Когда нужен точный поиск по равенству, но можно смириться с утечкой равенства значений
  • Всегда
  • Никогда
  • Только для паролей
Оно даёт равенство ценой раскрытия повторов. Приемлемо для полей высокой энтропии (уникальные номера).

Куда девать nonce при field-level шифровании?

  • Выбросить после шифрования
  • Держать в памяти
  • Хранить вместе с шифротекстом (он не секретен, но нужен для расшифровки)
  • Зашифровать другим ключом
Nonce нужен при расшифровке, но не секретен — хранится рядом с шифротекстом.

Где должен лежать ключ field-level шифрования?

  • В той же БД
  • В коде
  • В логах
  • В приложении/KMS, отдельно от данных — не в БД
Смысл field-level — защитить поле даже от администратора БД; если ключ в БД, защиты нет.
Чем field-level отличается от TDE?

TDE шифрует файлы БД целиком и прозрачно — администратор БД всё равно видит открытые данные. Field-level шифрует поле в приложении ключом, которого нет в БД, — защищает даже от дампа и SQL-доступа, но ломает поиск по полю.

Как искать по зашифрованному полю?

Варианты: детерминированное шифрование (только равенство), «слепой индекс» (хранить отдельно HMAC значения и искать по нему), или искать по незашифрованным соседним полям. Полноценный LIKE/диапазоны по надёжно зашифрованному полю невозможны.
