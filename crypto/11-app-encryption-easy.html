Шифрование отдельных полей — простыми словами

Иногда нужно спрятать отдельное поле — номер паспорта, карты, медицинский диагноз — так, чтобы его не видел даже администратор базы. Для этого приложение само шифрует поле перед записью. Разберёмся, как это делается, что при этом ломается и как всё-таки искать по зашифрованному.

11.1Зачем шифровать отдельное поле

В анкете клиента имя, город и дата рождения нужны многим сотрудникам, а номер паспорта — почти никому. Его запечатывают в отдельный конверт: база хранит мешанину, а ключ есть только у приложения (точнее, в KMS, к которому приложение обращается).

Что это даёт: утечка дампа базы, резервной копии или логов не раскрывает паспорта; администратор базы и аналитики видят только мешанину; доступ к ключу можно ограничить и записывать в журнал.

Главная мысль Шифрование поля прячет данные от всех, у кого есть доступ к базе, но нет доступа к ключу.

11.3Что при этом ломается

За защиту приходится платить. С запечатанным конвертом базе нечего делать:

  • Поиск — «найти клиента по номеру паспорта» обычным запросом не получится: в базе мешанина, и каждый раз разная.
  • Сортировка и диапазоны — «паспорта от … до …» невозможны.
  • Индексы на зашифрованное поле бесполезны.
  • Отчёты и аналитика по этому полю — только через приложение с ключом.

Поэтому шифруют только то, что действительно нужно прятать, а не все поля подряд.

Главная мысль По зашифрованному полю база не умеет искать, сортировать и строить отчёты. Шифруйте точечно.

11.4Как всё-таки искать: детерминированное шифрование и «слепой индекс»

Если по полю нужен поиск на точное совпадение, есть два приёма:

Детерминированное шифрование

Одинаковое значение всегда даёт одинаковый шифр. Можно искать «где шифр = …». Цена: наблюдатель видит, у каких записей значения совпадают, — а это тоже утечка.

Слепой индекс

Рядом с нормальным шифром хранят HMAC значения с отдельным ключом (глава 02). Ищут по HMAC, а сами данные зашифрованы обычным способом. Тоже видно совпадения, но ключи разделены.

Оба приёма раскрывают, что значения совпадают. Для полей с маленьким выбором (пол, город) это почти полное раскрытие — по частоте легко догадаться. Применяйте их только для уникальных значений вроде номеров документов.

Главная мысль Поиск по зашифрованному возможен, но всегда выдаёт совпадения. Для значений с малым выбором — опасно.

11.6Проверьте себя

От кого защищает шифрование поля в приложении, в отличие от TDE?

  • от кражи ноутбука
  • ни от кого дополнительно
  • от администратора базы и утечек дампов: он видит только мешанину
  • от взлома самого приложения
Ключ у приложения, а не у базы.

Зачем привязывать (пломбировать) id записи к шифру?

  • чтобы шифр нельзя было незаметно перенести в чужую запись
  • чтобы ускорить поиск
  • чтобы сжать данные
  • чтобы зашифровать id
Пломба не сойдётся, если шифр окажется в записи с другим id.

Что становится невозможным для зашифрованного обычным способом поля?

  • хранение
  • чтение приложением
  • резервное копирование
  • поиск, сортировка и индексы средствами базы
Каждый раз шифр разный, и база не понимает смысла значений.

Почему детерминированное шифрование опасно для поля «пол»?

  • оно слишком медленное
  • значений всего несколько, и по частоте совпадений их легко угадать
  • его нельзя расшифровать
  • оно не поддерживает русский язык
Одинаковые значения — одинаковые шифры, а частоты выдают смысл.

Зачем хранить вместе с шифром версию ключа?

  • для красоты
  • чтобы шифр был длиннее
  • чтобы после смены ключа понимать, каким ключом расшифровывать старые записи
  • не нужно
Это основа спокойной ротации ключей.
