Reactive Streams и Reactor: сигналы и подписка

Вся реактивная экосистема JVM стоит на четырёх интерфейсах спецификации Reactive Streams (в JDK — java.util.concurrent.Flow). Поняв протокол «подписка → запрос n → не больше n элементов → завершение», вы поймёте, почему «ничего не происходит, пока не подпишешься», как работает противодавление и что на самом деле делает каждый оператор.

2.1Четыре интерфейса

public interface Publisher<T> {
    void subscribe(Subscriber<? super T> s);
}
public interface Subscriber<T> {
    void onSubscribe(Subscription s);   // ровно один раз, первым
    void onNext(T t);                   // 0..N раз, не больше, чем запрошено
    void onError(Throwable t);          // терминальный
    void onComplete();                  // терминальный
}
public interface Subscription {
    void request(long n);               // «готов принять ещё n»
    void cancel();
}
public interface Processor<T, R> extends Subscriber<T>, Publisher<R> {}

Грамматика сигналов: onSubscribe onNext* (onError | onComplete)?. Правила спецификации (их 40+) среди прочего требуют: сигналы подписчику подаются последовательно (никогда параллельно), onNext — не больше суммы запрошенного, после терминального сигнала — тишина, request(n ≤ 0) — ошибка, Long.MAX_VALUE означает «без ограничений».

2.3Ничего не происходит, пока не подпишешься

Код с операторами строит описание конвейера (assembly time). Работа начинается при subscribe() (subscription time): подписка поднимается снизу вверх до источника, затем сверху вниз идут onSubscribe, снизу вверх — request, сверху вниз — данные.

Flux.range(1,3).map(x → x*10).filter(x → x > 10).subscribe(print)

Каждый оператор — неизменяемая обёртка над предыдущим издателем. Конвейер можно переиспользовать: каждая подписка запустит его заново.

Терминальная операция. В WebFlux её делает сам фреймворк, когда вы возвращаете Mono/Flux из контроллера.

Подписка идёт снизу вверх: filter создаёт FilterSubscriber(actual=lambda) и подписывает его на map; map — MapSubscriber на range.

Источник отдаёт подписку, операторы пробрасывают её вниз (иногда оборачивая).

Спрос поднимается вверх. Filter умнее: если элемент отброшен, он сам запрашивает ещё один у источника (request(1)), чтобы не «съесть» спрос подписчика.

Элементы текут вниз синхронно, в потоке, вызвавшем subscribe (планировщиков нет). Потом — терминальный сигнал.

Сигналы — последовательны, но не привязаны к потоку Спецификация гарантирует happens-before между сигналами, но не то, что все они придут в одном потоке. onNext(1) может прийти в reactor-http-nio-2, а onNext(2) — в parallel-3. Не храните состояние в ThreadLocal — для этого есть Context.

2.5Самопроверка

Что произойдёт после Flux.range(1,5).map(this::save); без subscribe?

  • 5 вызовов save
  • 1 вызов save
  • Ничего: конвейер только собран
  • Исключение
Холодный издатель ленив: работа начинается только при подписке.

Подписчик запросил request(3), а источник имеет 10 элементов. Сколько onNext придёт до следующего request?

  • 10
  • 3
  • 1
  • 0
Правило 1.1: не больше запрошенного.

Что происходит после cancel()?

  • onComplete
  • onError(CancellationException)
  • onNext(null)
  • Издатель прекращает отдавать элементы, терминального сигнала нет
Отмена — путь вверх, сигналов вниз не порождает (кроме doOnCancel-хуков).

Может ли onNext вызываться из двух потоков одновременно?

  • Нет, сигналы последовательны (правило 1.3)
  • Да, для Flux.parallel
  • Да, если издатель горячий
  • Да, после publishOn
Даже ParallelFlux — это N отдельных последовательных «рельсов».
Чем Mono отличается от CompletableFuture?

CompletableFuture — жадный (вычисление уже запущено), кэширует результат, не поддерживает отмену источника и противодавление, композиция смешивает потоки исполнения. Mono ленив, может быть пере-подписан (каждый раз заново выполнит работу), отмена распространяется вверх до источника (WebClient закроет соединение), есть Context и богатая библиотека операторов. Перейти: Mono.fromFuture(() -> cf) (supplier — чтобы сохранить ленивость), обратно — toFuture().

Зачем Reactive Streams, если есть Iterator?

Iterator — pull-модель с блокировкой: hasNext() ждёт данные. Reactive Streams — асинхронный push с pull-управлением спросом: потребитель говорит «готов к n», производитель толкает, когда данные есть, и никто не блокирует поток. Это позволяет связывать асинхронные системы с противодавлением через границы потоков и сети (RSocket переносит request(n) по сети).
