14.2Server-Sent Events

@GetMapping(path = "/api/orders/{id}/events", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
Flux<ServerSentEvent<OrderEvent>> events(@PathVariable long id,
        @RequestHeader(name = "Last-Event-ID", required = false) Long lastId) {
    Flux<ServerSentEvent<OrderEvent>> data = orderEvents.since(id, lastId)   // догоняем пропущенное
        .map(e -> ServerSentEvent.builder(e)
                .id(String.valueOf(e.seq()))
                .event(e.type())                 // имя события для addEventListener
                .build());
    Flux<ServerSentEvent<OrderEvent>> heartbeat = Flux.interval(Duration.ofSeconds(15))
        .map(i -> ServerSentEvent.<OrderEvent>builder().comment("ping").build());
    return Flux.merge(data, heartbeat)
        .doOnCancel(() -> log.info("client left order {}", id));
}

14.3Переподключение и Last-Event-ID

Сервер выдаёт событие каждый тик; EventSource переподключается через 2 тика (retry)

Сервер

Браузер (EventSource)

Прокси и балансировщики Nginx по умолчанию буферизует ответы и рвёт соединение после 60 с тишины (proxy_read_timeout). Для SSE: proxy_buffering off (или заголовок X-Accel-Buffering: no), heartbeat-комментарий чаще таймаута, HTTP/1.1 к upstream. HTTP/1.1-браузер держит не больше 6 соединений на домен — несколько вкладок с SSE исчерпают лимит; HTTP/2 снимает проблему.

14.4NDJSON между сервисами

@GetMapping(path = "/export", produces = MediaType.APPLICATION_NDJSON_VALUE)
Flux<Order> export() { return repo.findAll(); }          // R2DBC: строки идут по мере чтения

// клиент: обрабатывает по одной строке, не собирая всё в память
webClient.get().uri("/export").accept(MediaType.APPLICATION_NDJSON)
    .retrieve().bodyToFlux(Order.class)
    .buffer(500).concatMap(warehouse::saveBatch)
    .then();

Противодавление работает сквозь сеть: если клиент пишет медленно, он не запрашивает новые элементы, Reactor Netty перестаёт читать сокет, окно TCP закрывается, запись на сервере приостанавливается, и R2DBC перестаёт запрашивать строки у базы.

14.5WebSocket

@Bean
HandlerMapping wsMapping(ChatHandler h) {
    return new SimpleUrlHandlerMapping(Map.of("/ws/chat", h), -1);
}

@Component
class ChatHandler implements WebSocketHandler {
    private final Sinks.Many<String> room = Sinks.many().multicast().directBestEffort();

    public Mono<Void> handle(WebSocketSession session) {
        Mono<Void> in = session.receive()                          // входящие фреймы
            .map(WebSocketMessage::getPayloadAsText)
            .doOnNext(msg -> room.tryEmitNext(session.getId() + ": " + msg))
            .then();
        Mono<Void> out = session.send(room.asFlux()
            .onBackpressureDrop()                                  // медленный клиент теряет, а не тормозит
            .map(session::textMessage));
        return Mono.zip(in, out).then();                           // сессия живёт, пока живы оба направления
    }
}
STOMP Реактивный WebFlux не поддерживает STOMP-брокер (@MessageMapping поверх STOMP есть только в стеке Servlet). Для сообщений поверх WebSocket с маршрутизацией в реактивном мире используют RSocket (spring-boot-starter-rsocket, @MessageMapping, request-stream с настоящим request(n) по сети).

14.6Самопроверка

Что делает браузерный EventSource после обрыва соединения?

  • Ничего, нужно перезагрузить страницу
  • Переподключается сам через retry и отправляет Last-Event-ID
  • Переходит на WebSocket
  • Повторяет все события с начала
Возобновление встроено в протокол; сервер должен его поддержать.

Зачем heartbeat в SSE-потоке?

  • Для противодавления
  • Чтобы браузер не закрыл вкладку
  • Для сжатия
  • Чтобы прокси и балансировщики не закрыли «молчащее» соединение и чтобы быстрее обнаружить ушедшего клиента
Запись в закрытый сокет сразу выявляет отключение.

Что произойдёт с Flux SSE, когда клиент закроет вкладку?

  • Подписка отменится (cancel), источник остановится
  • Flux продолжит выдавать в никуда
  • Ошибка в логах сервера
  • Сервер перезапустится
Отмена распространяется вверх: doOnCancel, doFinally.

Какой медиатип даёт построчную потоковую выдачу JSON между сервисами?

  • application/json
  • text/html
  • application/x-ndjson
  • multipart/mixed
application/json для Flux — массив без поэлементного flush.
Сколько SSE-соединений выдержит один инстанс WebFlux?

Ограничивает не число потоков, а память и файловые дескрипторы: каждое соединение — канал Netty с буферами (единицы-десятки КБ) плюс объекты подписки. Десятки тысяч соединений на инстанс реальны при достаточном ulimit -n и памяти. Узкие места: общие ресурсы на каждое соединение (подписка на БД на каждого клиента вместо общего multicast-источника), неограниченные буферы медленных клиентов, балансировщики с лимитами соединений.
