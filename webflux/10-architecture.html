Архитектура WebFlux: путь запроса

WebFlux повторяет знакомую по MVC архитектуру — DispatcherHandler вместо DispatcherServlet, HandlerMapping, HandlerAdapter, — но всё возвращает Mono, а под капотом нет Servlet API. Проходим путь байтов от сокета Netty до вашего контроллера и обратно, разбираем ServerWebExchange и то, как Spring Boot решает, какой стек поднять.

Event loop Netty получает событие готовности. Каждое соединение навсегда привязано к одному event loop — все его события обрабатывает один поток.

Netty разбирает стартовую строку и заголовки. Тело не читается: оно станет доступно как Flux<DataBuffer> и будет прочитано, только когда кто-то подпишется.

Создаётся ServerWebExchange — аналог пары HttpServletRequest/Response плюс атрибуты, сессия (лениво, Mono<WebSession>) и principal (Mono).

Каждый WebFilter возвращает Mono<Void> и решает, вызывать ли chain.filter(exchange). Здесь работают безопасность, CORS, метрики, ваши фильтры (тема 13).

DispatcherHandler опрашивает HandlerMapping-и по порядку: Flux.fromIterable(mappings).concatMap(m -> m.getHandler(exchange)).next(). Ничего не нашлось — 404 (ResponseStatusException).

RequestMappingHandlerAdapter разрешает аргументы (часть резолверов асинхронны — @RequestBody читает тело как Mono) и вызывает метод. Метод возвращает описание работы: запрос в БД ещё не отправлен.

HandlerResultHandler выбирается по типу результата (ResponseEntity, @ResponseBody, ServerResponse, имя View). Он подписывается на Mono — именно в этот момент выполняется ваша цепочка — и кодирует результат в DataBuffer.

Mono<Void> всей цепочки завершается, когда ответ записан. Отмена (клиент закрыл соединение) распространяется вверх и отменяет всё, включая запрос к БД.

10.3DispatcherHandler в сокращении

public Mono<Void> handle(ServerWebExchange exchange) {
    if (this.handlerMappings == null) return createNotFoundError();
    if (CorsUtils.isPreFlightRequest(exchange.getRequest())) return handlePreFlight(exchange);
    return Flux.fromIterable(this.handlerMappings)
            .concatMap(mapping -> mapping.getHandler(exchange))   // первый нашедший
            .next()
            .switchIfEmpty(createNotFoundError())
            .onErrorResume(ex -> handleResultMono(exchange, Mono.error(ex)))
            .flatMap(handler -> handleRequestWith(exchange, handler));
}
private Mono<Void> handleRequestWith(ServerWebExchange ex, Object handler) {
    for (HandlerAdapter adapter : this.handlerAdapters)
        if (adapter.supports(handler))
            return adapter.handle(ex, handler)                  // Mono<HandlerResult>
                          .flatMap(result -> handleResult(ex, result));
    return Mono.error(new IllegalStateException("No HandlerAdapter: " + handler));
}

Какой стек поднимет Spring Boot WebApplicationType определяется по classpath: есть spring-webmvc (DispatcherServlet) — SERVLET, даже если рядом webflux (часто ради WebClient). Только webflux — REACTIVE. Принудительно: spring.main.web-application-type=reactive. Сервер — Reactor Netty из spring-boot-starter-reactor-netty; заменить можно, исключив его и добавив starter-tomcat или starter-jetty. В Boot 4 стартер MVC называется spring-boot-starter-webmvc, а только ради WebClient есть spring-boot-starter-webclient — он не переключает приложение в REACTIVE.

Что происходит, когда клиент закрывает соединение посреди обработки?

Netty обнаруживает закрытие канала, Reactor Netty отменяет подписку на Mono<Void> ответа. Отмена распространяется вверх по всей цепочке: WebClient закроет исходящие запросы, R2DBC отменит запрос, Flux SSE остановится. Сработают doOnCancel/doFinally. В логах это видно как «cancel», без исключения. В MVC аналогичная ситуация обнаруживается только при попытке записи (ClientAbortException).

Почему тело запроса — Flux<DataBuffer>, а не byte[]?

Тело приходит кусками по мере чтения из сокета; Flux позволяет обрабатывать его потоково (загрузка файлов, NDJSON) и уважать противодавление: пока никто не подписался, Netty не читает дальше. Декодеры собирают куски, когда нужен целый объект (с лимитом spring.http.codecs.max-in-memory-size, по умолчанию 256 КБ). DataBuffer — пулированные буферы Netty, их нужно освобождать (DataBufferUtils.release), если вы работаете с ними вручную.
