Производительность и блокировка event loop

Главная угроза реактивного сервиса — не медленный код, а блокирующий. Потоков event loop по умолчанию max(ядра, 4); один Thread.sleep, JDBC-вызов или синхронная запись лога в обработчике останавливает все соединения этого потока. Моделируем последствия, учимся находить блокировки BlockHound-ом и разбираем настройки Reactor Netty, влияющие на пропускную способность.

// BlockingOperationError: Blocking call! java.net.Socket$SocketInputStream#read

BlockHound — Java-агент, который инструментирует блокирующие методы JDK (Thread.sleep, чтение сокета, Object.wait, LockSupport.park и др.) и бросает ошибку, если вызов произошёл в потоке, помеченном как неблокирующий (NonBlocking: parallel, event loop Netty). На JDK 13+ нужен флаг -XX:+AllowRedefinitionToAddDeleteMethods. Держите его включённым во всех интеграционных тестах.

20.4Настройки и нагрузочное тестирование

Reactor Netty

  • reactor.netty.ioWorkerCount — потоков event loop (по умолчанию max(ядра, 4)); увеличивать почти никогда не нужно.
  • Нативный транспорт epoll/kqueue (netty-transport-native-*) — меньше накладных расходов, чем NIO.
  • HTTP/2: server.http2.enabled=true — мультиплексирование, меньше соединений.
  • server.compression.enabled — экономит сеть, тратит CPU loop.
  • Контейнер: укажите реальные ядра (cgroup), иначе потоков будет больше или меньше нужного.

Как мерить

  • Нагрузка открытой моделью (Gatling, k6 с constant-arrival-rate) — закрытая модель (N потоков JMeter) скрывает рост латентности.
  • Смотрите p99/p999 и ошибки, а не только среднее и RPS.
  • Сравнивайте с MVC на виртуальных потоках на том же сценарии (тема 21).
  • Профилирование: async-profiler в режиме wall — покажет, где ждут event loop-потоки.
  • Прогрев JIT перед замерами.
Микрооптимизации Reactor Цепочка из десятков операторов на каждый элемент стоит аллокаций и вызовов; Reactor сглаживает это «слиянием» (operator fusion: map+filter над синхронным источником выполняются без очередей). Но не дробите логику на операторы ради красоты: один map с методом дешевле пяти. Mono.just + flatMap там, где хватит map, — лишняя подписка на каждый элемент.

20.5Самопроверка

Почему блокирующий вызов в одном эндпоинте замедляет другие, не связанные с ним эндпоинты?

  • Из-за общего пула БД
  • Соединения, обслуживаемые тем же потоком event loop, ждут, пока поток не освободится
  • Netty перезапускается
  • Не замедляет
Каждое соединение навсегда привязано к своему event loop.

Что делает BlockHound?

  • Ускоряет блокирующие вызовы
  • Автоматически переносит их на boundedElastic
  • Считает метрики потоков
  • Бросает ошибку при блокирующем вызове в неблокирующем потоке
Инструмент обнаружения, а не исправления.

Почему для нагрузочного теста реактивного сервиса предпочтительна открытая модель нагрузки?

  • Закрытая модель (фиксированное число пользователей) сама снижает частоту запросов при росте латентности и скрывает деградацию
  • Она быстрее
  • Закрытая модель не поддерживает HTTP/2
  • Это требование Netty
Coordinated omission: тест «подстраивается» под медленный сервер.
WebFlux-сервис показывает высокую латентность при CPU 20%. Как искать причину?

1) Дамп потоков: есть ли reactor-http-nio в состояниях, отличных от epoll_wait (socketRead, park, sleep) — это блокировка. 2) Метрика reactor.netty.eventloop.pending.tasks — растущая очередь подтверждает. 3) Пулы: reactor.netty.connection.provider.pending.connections (WebClient ждёт соединений), r2dbc.pool.pending — запросы стоят в очереди к БД. 4) boundedElastic: все потоки заняты, задачи в очереди. 5) Внешние зависимости и их таймауты. Низкий CPU при высокой латентности — почти всегда ожидание, а не вычисления.
