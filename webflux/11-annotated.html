Аннотированные контроллеры

Аннотации те же, что в MVC: @RestController, @GetMapping, @PathVariable, @RequestBody. Отличаются типы: аргументы и результаты могут быть Mono и Flux, и от выбора типа зависят статус ответа, момент фиксации заголовков, буферизация и поведение при ошибке посреди потока. Разбираем сигнатуры, валидацию и обработку ошибок с ProblemDetail.

11.1CRUD-контроллер

@RestController
@RequestMapping("/api/users")
@RequiredArgsConstructor
class UserController {
    private final UserService users;

    @GetMapping("/{id}")
    Mono<ResponseEntity<UserDto>> get(@PathVariable long id) {
        return users.find(id)
                    .map(ResponseEntity::ok)
                    .defaultIfEmpty(ResponseEntity.notFound().build());   // пустой Mono → 404
    }

    @GetMapping
    Flux<UserDto> list(@RequestParam(defaultValue = "0") int page,
                       @RequestParam(defaultValue = "20") int size) {
        return users.page(page, size);
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    Mono<UserDto> create(@Valid @RequestBody Mono<CreateUser> body) {   // тело читается асинхронно
        return body.flatMap(users::create);
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    Mono<Void> delete(@PathVariable long id) {
        return users.delete(id);       // ответ отправится, когда Mono<Void> завершится
    }
}

@RequestBody CreateUser body (без Mono) тоже работает: фреймворк сам дождётся декодирования перед вызовом метода. Mono-аргумент нужен, если вы хотите контролировать момент чтения или обработку ошибок декодирования внутри цепочки.

11.4Валидация и ошибки

@RestControllerAdvice
class ApiErrors extends ResponseEntityExceptionHandler {      // реактивная версия из spring-webflux

    @ExceptionHandler(UserNotFound.class)
    ProblemDetail notFound(UserNotFound e) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
        pd.setProperty("userId", e.id());
        return pd;                                             // application/problem+json
    }

    @ExceptionHandler(DuplicateKeyException.class)
    Mono<ResponseEntity<ProblemDetail>> conflict(DuplicateKeyException e) {
        return Mono.just(ResponseEntity.status(409)
                .body(ProblemDetail.forStatus(409)));         // обработчик тоже может быть реактивным
    }
}

Что бросает фреймворк

  • WebExchangeBindException — @Valid не прошёл (400), содержит FieldError-ы
  • ServerWebInputException — не разобран параметр/тело (400)
  • UnsupportedMediaTypeStatusException (415), NotAcceptableStatusException (406)
  • ResponseStatusException — ваш статус из кода
  • DataBufferLimitException — тело больше max-in-memory-size; при чтении через @RequestBody превращается в 413 (Spring 6.2 — PayloadTooLargeException, с 7.0 — ContentTooLargeException)

Порядок обработки

  1. @ExceptionHandler в самом контроллере
  2. @ControllerAdvice
  3. WebExceptionHandler-ы (Boot: DefaultErrorWebExceptionHandler, order −1, формирует JSON по ErrorAttributes)
  4. spring.webflux.problemdetails.enabled=true — встроенные исключения в формате ProblemDetail
@ExceptionHandler не видит ошибку в WebFilter Исключения из WebFilter-ов (до DispatcherHandler) и после начала записи ответа не попадают в @ExceptionHandler. Их обрабатывают WebExceptionHandler-ы — либо ловите в самом фильтре через onErrorResume.

11.5Самопроверка

Контроллер вернул пустой Mono<User>. Какой статус получит клиент?

  • 404
  • 204
  • 200 с пустым телом
  • 500
Пустота — не ошибка. Нужен defaultIfEmpty(404) или ResponseStatusException.

Flux<User> выдал 2 элемента и упал (application/json). Что увидит клиент?

  • 200 и оборванное тело
  • 500 с ProblemDetail
  • 200 и полный массив из 2 элементов
  • Повторный запрос
Статус зафиксирован при первом элементе.

Чем Mono<ResponseEntity<T>> отличается от ResponseEntity<Mono<T>>?

  • Ничем
  • В первом статус и заголовки определяются асинхронно по результату, во втором известны сразу
  • Второй не поддерживается
  • Первый блокирует поток
Для «200 или 404» нужен Mono<ResponseEntity>.

Где обработать исключение, брошенное в WebFilter?

  • @ExceptionHandler в контроллере
  • @ControllerAdvice
  • HandlerInterceptor
  • WebExceptionHandler или onErrorResume в самом фильтре
Фильтры работают до DispatcherHandler.
Как принять загрузку большого файла без загрузки в память?

@PostMapping(consumes = MULTIPART_FORM_DATA_VALUE) Mono<Void> upload(@RequestPart("file") FilePart file) { return file.transferTo(Path.of(dir, file.filename())); } — FilePart.content() это Flux<DataBuffer>, transferTo пишет неблокирующе через AsynchronousFileChannel. Или Flux<PartEvent> для полностью потоковой обработки. Лимиты — spring.webflux.multipart.max-disk-usage-per-part, max-in-memory-size; помните про проверку имени файла (path traversal).

Что делает @Valid на @RequestBody Mono<T>?

Валидация встраивается в Mono: при декодировании объект проверяется, и при нарушении Mono завершается ошибкой WebExchangeBindException. Если вы обрабатываете ошибку внутри цепочки (onErrorResume), получите управление; иначе она дойдёт до обработчиков и станет 400. С Spring 6.1 также доступна валидация параметров методов (@Constraint на @RequestParam/@PathVariable) через HandlerMethodValidationException.
