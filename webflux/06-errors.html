Ошибки, повторы и таймауты

В реактивном конвейере исключение — не throw, пролетающий по стеку, а сигнал onError, идущий вниз по цепочке и завершающий её. try/catch вокруг конвейера бесполезен. Разбираем операторы обработки ошибок, повторы с экспоненциальной задержкой, таймауты и то, почему retry работает только с ленивыми источниками.

6.1Ошибка — терминальный сигнал

Flux.just("1", "2", "x", "4")
    .map(Integer::parseInt)           // NumberFormatException → оператор ловит и шлёт onError вниз,
    .subscribe(                        // а источнику — cancel(). "4" никогда не будет обработан.
        v -> log.info("{}", v),
        e -> log.error("failed", e));  // без этого колбэка — ErrorCallbackNotImplemented в лог

Reactor ловит исключения из лямбд операторов (map, filter, flatMap) и превращает их в onError. «Фатальные» (VirtualMachineError, LinkageError, ThreadDeath) пробрасываются как есть — Exceptions.throwIfJvmFatal. Checked-исключения внутри лямбд оборачивают через Exceptions.propagate(e).

    .retrieve()

        .filter(e -> e instanceof TimeoutException
                  || e instanceof WebClientResponseException.ServiceUnavailable)
        .onRetryExhaustedThrow((spec, sig) -> sig.failure()))           // отдать исходную ошибку

                e -> new PriceNotFound(id))
    .onErrorResume(e -> !(e instanceof PriceNotFound), e -> cache.lastKnown(id));

6.3Симулятор повторов

Вызов длится 50 мс; сервис падает первые N раз (S — момент подписки, P — ответ)
retry переподписывается — источник должен быть ленивым Mono.just(callService()).retry(3) не повторит вызов: результат (или исключение) вычислен один раз при сборке. Mono.fromCallable(this::callService).retry(3) и WebClient-запросы — повторяются, потому что каждая подписка выполняет работу заново. Не ставьте retry после неидемпотентной операции (POST создания заказа) без ключа идемпотентности.

6.4Таймауты

timeout(Duration)

Если следующий сигнал не пришёл за указанное время, источник отменяется и выдаётся TimeoutException. Для Flux таймер перезапускается на каждый элемент — это таймаут бездействия, а не общего времени. Общее время для Flux — take(Duration) или timeout на collectList().

Порядок с retry

.timeout(2s).retry(3) — до 2 с на каждую попытку, всего до 8 с. .retry(3).timeout(2s) — 2 с на всё, включая повторы. Обычно нужно первое, плюс общий таймаут сверху. Таймеры работают на Schedulers.parallel().

6.5Ошибки в потоках элементов

Ошибка в одном элементе Flux завершает весь поток. Чтобы «пропустить плохой элемент и продолжить», обрабатывайте ошибку внутри flatMap:

Flux.fromIterable(ids)
    .flatMap(id -> client.get(id)
        .doOnError(e -> log.warn("skip {}", id, e))
        .onErrorResume(e -> Mono.empty()), 8)      // ошибка гасится во внутреннем Mono
    .collectList();
onErrorContinue — не используйте без крайней нужды onErrorContinue работает через Context и поддерживается не всеми операторами; он действует на операторы выше себя, меняя их поведение неочевидно, и плохо сочетается с onErrorResume ниже. Документация Reactor прямо рекомендует предпочитать обработку ошибок во внутреннем издателе.

6.6Самопроверка

Почему try/catch вокруг repo.findById(id).map(...) не ловит ошибку БД?

  • Reactor подавляет исключения
  • Нужен checked-тип
  • Метод лишь собирает конвейер; ошибка придёт позже сигналом onError
  • catch работает только с block()
Ошибка возникнет при подписке, в другом стеке и, возможно, потоке.

Что выдаст Retry.backoff(3, 100ms) после трёх неудачных повторов?

  • RetryExhaustedException с исходной ошибкой в cause
  • Исходное исключение
  • Пустой Mono
  • Будет повторять бесконечно
Изменить можно через onRetryExhaustedThrow.

Flux.interval(1s).timeout(Duration.ofSeconds(5)) — когда сработает таймаут?

  • Через 5 секунд после старта
  • После 5 элементов
  • Никогда, Flux бесконечный
  • Только если между элементами пройдёт больше 5 секунд — здесь никогда
timeout для Flux — это таймаут между сигналами.

Как продолжить обработку Flux, если вызов для одного элемента упал?

  • onErrorResume после flatMap
  • onErrorResume внутри flatMap для каждого внутреннего Mono
  • retry()
  • Это невозможно
После flatMap ошибка уже завершила внешний поток.
Как сделать повтор только для временных ошибок, а 4xx — не повторять?

Retry.backoff(3, Duration.ofMillis(200)).filter(e -> e instanceof WebClientResponseException w && w.getStatusCode().is5xxServerError() || e instanceof TimeoutException || e instanceof PrematureCloseException). 4xx означает ошибку запроса — повтор даст тот же результат. Добавьте maxBackoff, jitter и doBeforeRetry(s -> log...) для наблюдаемости.

Чем onErrorResume отличается от onErrorReturn с точки зрения ленивости?

onErrorReturn принимает готовое значение (вычисленное при сборке), onErrorResume — функцию, вызываемую только при ошибке и возвращающую издатель: fallback-вызов произойдёт только тогда. Поэтому для дорогих fallback — onErrorResume.
