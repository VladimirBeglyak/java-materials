Противодавление и Sinks

Противодавление (backpressure) — способ медленного потребителя сказать быстрому производителю «не больше n». Пока производитель умеет подчиняться (база, файл, генератор), потерь нет. Когда не умеет (таймер, клики, сообщения из сокета, ваш код через Sinks) — нужна стратегия: буферизовать, отбрасывать, оставлять последнее или падать. Разбираем, как спрос течёт по цепочке, моделируем стратегии и учимся безопасно отправлять события через Sinks.

8.1Как спрос течёт по цепочке

Спрос не передаётся «как есть» от подписчика к источнику: операторы с очередью (publishOn, limitRate, внутренние подписки flatMap) запрашивают у источника свою предвыборку (prefetch) и пополняют её, когда израсходовано 75% (порог replenish). flatMap у самого источника запрашивает concurrency элементов и добирает по одному на каждый завершившийся внутренний издатель; concatMap (с 3.5) предвыборки не делает.

8.3Sinks: как отдавать события из императивного кода

Sinks — безопасная замена устаревшим Processor: объект, в который вы «кладёте» сигналы, и Flux/Mono, на который подписываются потребители.

SinkПодписчиковПоздний подписчикНет спроса
Sinks.one()многополучает значение—
Sinks.empty()многополучает complete/error—
many().unicast().onBackpressureBuffer()одинполучает всё накопленное до подпискибуферизует (неограниченно)
many().multicast().onBackpressureBuffer()многотолько новые (+ буфер до первого подписчика)копит до 256, затем FAIL_OVERFLOW; медленный тормозит всех
many().multicast().directBestEffort()многотолько новыемедленному элемент не доставляется, остальным — да
many().multicast().directAllOrNothing()многотолько новыеесли хоть один не готов — не получает никто
many().replay().limit(n | Duration)многопоследние n / за периодбуферизует
@Component
class OrderEvents {
    private final Sinks.Many<OrderEvent> sink =
        Sinks.many().multicast().directBestEffort();      // медленный клиент не тормозит остальных

    void publish(OrderEvent e) {
        Sinks.EmitResult r = sink.tryEmitNext(e);
        if (r.isFailure()) log.warn("emit {} failed: {}", e.id(), r);
    }
    Flux<OrderEvent> stream() {
        return sink.asFlux().onBackpressureBuffer(100);   // свой буфер на каждого подписчика
    }
}
Что вернёт tryEmitNext?
emitNext против tryEmitNext tryEmitNext возвращает результат и не бросает. emitNext(v, handler) вызывает handler при неудаче (повторить или нет); EmitFailureHandler.FAIL_FAST: на FAIL_NON_SERIALIZED бросит EmissionException, на FAIL_ZERO_SUBSCRIBER тихо отбросит элемент, на FAIL_OVERFLOW завершит sink ошибкой переполнения. Не вызывайте emit из нескольких потоков без busyLooping — это самая частая причина «потерянных» событий.

8.4Самопроверка

Почему Flux.interval(1ms).publishOn(single()).map(slow) падает с OverflowException?

  • interval не поддерживает publishOn
  • Таймер не умеет замедляться, а очередь publishOn (256) переполняется
  • single() запрещён для interval
  • map бросает исключение
Нужна стратегия onBackpressure* перед publishOn.

Котировки: потребителю нужно только самое свежее значение. Стратегия?

  • onBackpressureBuffer()
  • onBackpressureError()
  • onBackpressureLatest()
  • onBackpressureDrop()
Latest хранит последнее непереданное значение.

Что вернёт tryEmitNext при одновременном вызове из двух потоков?

  • Одному из них — FAIL_NON_SERIALIZED
  • Оба OK
  • Бросит ConcurrentModificationException
  • Заблокирует второй поток
Sinks детектируют гонку, но не разрешают её за вас.

Сколько элементов запросит limitRate(100) после первых 75 полученных?

  • 100
  • 25
  • 1
  • 75
Пополнение на 75% от размера окна.
Работает ли противодавление по HTTP между WebFlux-сервером и клиентом?

Частично. Внутри приложения — да, по протоколу Reactive Streams. На границе сети Reactor Netty переводит спрос в управление чтением из сокета: если подписчик не запрашивает данные, Netty перестаёт читать (autoRead=false), заполняется приёмный буфер TCP, и окно TCP сообщает отправителю замедлиться. Так что медленное чтение ответа клиентом в итоге притормозит запись сервером. Точного «request(n)» по HTTP нет — это умеет RSocket.

Чем Sinks.many().multicast().onBackpressureBuffer() опасен для SSE с множеством клиентов?

Буфер общий: если один клиент читает медленно, буфер (256) заполняется, и sink начинает возвращать FAIL_OVERFLOW для всех — один медленный клиент тормозит или ломает доставку всем. Для broadcast клиентам с разной скоростью лучше directBestEffort плюс индивидуальный onBackpressureBuffer/Latest/Drop на asFlux() каждого подписчика.
