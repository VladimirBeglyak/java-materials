WebClient и Reactor Netty

WebClient — неблокирующий HTTP-клиент поверх Reactor Netty HttpClient: цепочка вызова ленива, отменяема и встраивается в реактивный конвейер. В продакшене решают детали: пул соединений и его очередь ожидания, четыре разных таймаута, обработка статусов, освобождение тела ответа и «протухшие» соединения за балансировщиком. Разбираем всё это и декларативные клиенты @HttpExchange.

15.1Запрос и ответ

Mono<Price> price = webClient.get()
    .uri("/prices/{sku}?currency={c}", sku, "EUR")
    .header("X-Request-Id", rid)
    .retrieve()
    .onStatus(HttpStatusCode::is4xxClientError, resp ->
        resp.bodyToMono(ProblemDetail.class)
            .map(pd -> new PriceRejected(sku, pd.getDetail())))   // своё исключение вместо WebClientResponseException
    .bodyToMono(Price.class);

Mono<ResponseEntity<Price>> withHeaders = webClient.get().uri("/prices/{sku}", sku)
    .retrieve().toEntity(Price.class);                             // статус + заголовки + тело

Mono<Price> manual = webClient.get().uri("/prices/{sku}", sku)
    .exchangeToMono(resp -> resp.statusCode().is2xxSuccessful()
        ? resp.bodyToMono(Price.class)
        : resp.releaseBody().then(Mono.empty()));                  // явное освобождение; иначе тело освободится
                                                                   // автоматически после завершения функции
Тело ответа держит соединение Пока тело не прочитано или не освобождено, соединение не вернётся в пул. retrieve и exchangeToMono делают это за вас; устаревший exchange() удалён именно из-за утечек соединений.

15.2Пул соединений

Что будет через минуту такой нагрузки на один хост?

По умолчанию WebClient использует глобальный пул Reactor Netty «http»: max(2 × max(ядра, 8), 500), то есть на практике 500 соединений на каждый удалённый адрес, очередь ожидания — 1000, таймаут получения 45 с. (Значение 2 × max(ядра, 8) и очередь 500 получает собственный ConnectionProvider.create(name).) Для важных зависимостей создавайте отдельный ConnectionProvider.

15.3Настройка: пул и таймауты

@Bean
WebClient pricingClient(WebClient.Builder builder) {          // Boot-овский билдер: кодеки, observation
    ConnectionProvider pool = ConnectionProvider.builder("pricing")
        .maxConnections(100)
        .pendingAcquireMaxCount(200)
        .pendingAcquireTimeout(Duration.ofSeconds(2))          // fail fast вместо 45 с
        .maxIdleTime(Duration.ofSeconds(20))                   // меньше idle-таймаута балансировщика!
        .maxLifeTime(Duration.ofMinutes(5))
        .evictInBackground(Duration.ofSeconds(30))
        .metrics(true)                                         // reactor.netty.connection.provider.* в Micrometer
        .build();
    HttpClient http = HttpClient.create(pool)
        .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 1_000)   // установка TCP-соединения
        .responseTimeout(Duration.ofSeconds(3))                // от отправки запроса до заголовков ответа (и между чтениями)
        .compress(true);
    return builder.baseUrl("https://pricing.internal")
        .clientConnector(new ReactorClientHttpConnector(http))
        .build();
}
ТаймаутЧто ограничиваетОшибка
CONNECT_TIMEOUT_MILLISTCP-handshake (по умолчанию 30 с)ConnectTimeoutException
pendingAcquireTimeoutожидание свободного соединения в пулеPoolAcquireTimeoutException
responseTimeoutмаксимальный интервал между чтениями из сети от отправки запроса до полного получения ответа (включая тело)ReadTimeoutException
Mono.timeout(d)всё целиком, включая чтение тела и повторы (если стоит после retry)TimeoutException
Connection reset by peer / PrematureCloseException Балансировщик (AWS ALB — 60 с по умолчанию, NLB/NAT Gateway — 350 с, nginx keepalive_timeout — 75 с) молча закрывает простаивающие соединения, а клиент берёт «мёртвое» соединение из пула. Лечится maxIdleTime меньше idle-таймаута на той стороне и повтором только для идемпотентных запросов.

15.4Фильтры и декларативные клиенты

ExchangeFilterFunction bearer = (req, next) -> tokenProvider.token()      // Mono<String>, кэшируется
    .flatMap(t -> next.exchange(ClientRequest.from(req).headers(h -> h.setBearerAuth(t)).build()));

WebClient client = builder.filter(bearer).filter(logRequests()).build();

// Декларативный интерфейс (Spring 6)
@HttpExchange("/prices")
interface PricingApi {
    @GetExchange("/{sku}") Mono<Price> get(@PathVariable String sku);
    @PostExchange          Mono<Void>  update(@RequestBody Price p);
}
@Bean PricingApi pricingApi(WebClient pricingClient) {
    return HttpServiceProxyFactory.builderFor(WebClientAdapter.create(pricingClient))
        .build().createClient(PricingApi.class);
}

Для OAuth2 есть готовый ServerOAuth2AuthorizedClientExchangeFilterFunction (client_credentials, обновление токена), для балансировки по Spring Cloud LoadBalancer — @LoadBalanced WebClient.Builder или ReactorLoadBalancerExchangeFilterFunction.

15.5Самопроверка

Что вернёт retrieve().bodyToMono(...) при ответе 503 без onStatus?

  • Пустой Mono
  • null
  • Ошибку WebClientResponseException.ServiceUnavailable
  • Тело ошибки как Price
retrieve по умолчанию превращает 4xx/5xx в WebClientResponseException.

Почему из WebClient удалили метод exchange()?

  • Он перекладывал чтение/освобождение тела на приложение — забытое тело удерживало соединение и буферы
  • Он был медленным
  • Он не поддерживал заголовки
  • Его заменил RestTemplate
retrieve и exchangeToMono/Flux освобождают непрочитанное тело автоматически.

Сервис отвечает за 500 мс, нагрузка 300 зап/с, пул 100 соединений. Что произойдёт?

  • Всё хорошо
  • Пропускная способность 1000 зап/с
  • Ошибка компиляции
  • Нужно 150 соединений — запросы копятся в очереди ожидания пула
По Литтлу 300 × 0,5 = 150 > 100.

Что ограничивает responseTimeout?

  • TCP-handshake
  • Паузу между чтениями из сети от отправки запроса до полного получения ответа
  • Ожидание соединения в пуле
  • Время жизни соединения
Для пула — pendingAcquireTimeout, для соединения — CONNECT_TIMEOUT_MILLIS.
Можно ли использовать WebClient в Spring MVC-приложении?

Да, это распространённый сценарий: подключается spring-webflux ради клиента, приложение остаётся Servlet. Для синхронного кода вызывают .block() — это допустимо в потоках Tomcat (не event loop). Однако с Spring 6.1 для синхронного кода естественнее RestClient — у него тот же fluent-API, а с виртуальными потоками блокировка дёшева. WebClient остаётся выбором, когда нужны параллельные вызовы, стриминг или композиция через Reactor.
