WebFilter, кодеки и лимиты

WebFilter — единственное место для сквозной логики в WebFlux: логирование, идентификатор запроса, аутентификация, изменение запроса и ответа. Кодеки превращают байты в объекты и обратно и защищают от огромных тел лимитом в 256 КБ, о котором узнают по DataBufferLimitException в проде. Разбираем порядок фильтров, типичные ошибки и настройку кодеков для сервера и WebClient.

13.1Устройство WebFilter

@Component
@Order(Ordered.HIGHEST_PRECEDENCE + 10)
class AccessLogFilter implements WebFilter {
    public Mono<Void> filter(ServerWebExchange ex, WebFilterChain chain) {
        long start = System.nanoTime();                                   // «до» — при сборке/подписке
        ServerWebExchange mutated = ex.mutate()
            .request(r -> r.header("X-Request-Id", UUID.randomUUID().toString()))
            .build();                                                     // запрос неизменяем — только mutate
        mutated.getResponse().beforeCommit(() -> {                        // последний шанс поменять заголовки
            mutated.getResponse().getHeaders().add("X-Took-Ms", ms(start));
            return Mono.empty();
        });
        return chain.filter(mutated)                                      // ВСЕГДА возвращать результат
            .doFinally(sig -> log.info("{} {} {} {}ms ({})",
                ex.getRequest().getMethod(), ex.getRequest().getPath(),
                ex.getResponse().getStatusCode(), ms(start), sig));       // «после» — complete/error/cancel
    }
}

13.2Симулятор цепочки фильтров

Фильтры: RequestId (−100) → Auth (−50) → AccessLog (0) → контроллер
Порядок фильтров Фильтры-бины сортируются по @Order/Ordered. Ориентиры: HTTP-наблюдаемость встроена в HttpWebHandlerAdapter (с 6.1; ServerHttpObservationFilter удалён в 7.0) и охватывает все фильтры, WebFilterChainProxy Spring Security — -100. Фильтры, которым нужен пользователь, ставьте после безопасности; логирование и request id — до неё.

13.4Лимит буферизации

Пройдёт ли тело запроса?
// сервер: spring.http.codecs.max-in-memory-size=2MB или
@Configuration
class CodecConfig implements WebFluxConfigurer {
    public void configureHttpMessageCodecs(ServerCodecConfigurer c) {
        c.defaultCodecs().maxInMemorySize(2 * 1024 * 1024);
        c.defaultCodecs().jacksonJsonDecoder(new JacksonJsonDecoder(customJsonMapper));   // Jackson 3
    }
}
// WebClient — свой лимит! Boot-овский WebClient.Builder учитывает spring.http.codecs.*,
// а WebClient.create() — нет
WebClient client = WebClient.builder()
    .codecs(c -> c.defaultCodecs().maxInMemorySize(16 * 1024 * 1024))
    .build();

13.5Самопроверка

Фильтр вызывает chain.filter(ex); и возвращает Mono.empty(). Что будет?

  • Всё работает
  • Ошибка компиляции
  • Контроллер не вызовется: на результат chain.filter никто не подписался
  • Контроллер вызовется дважды
Нужно return chain.filter(ex).

Как добавить заголовок ответа с временем обработки?

  • В response.beforeCommit(...) или до chain.filter
  • В doFinally после chain.filter
  • В @ExceptionHandler
  • Через ThreadLocal
После записи тела заголовки неизменяемы.

WebClient получает JSON в 3 МБ и падает с DataBufferLimitException, хотя spring.http.codecs.max-in-memory-size=10MB. Почему?

  • Лимит сервера меньше
  • JSON нельзя больше 1 МБ
  • Нужен retry
  • WebClient создан через WebClient.create(), не через Boot-овский WebClient.Builder
Только автоконфигурированный билдер применяет spring.http.codecs.*.

Как изменить запрос в фильтре (добавить заголовок)?

  • request.getHeaders().add(...)
  • exchange.mutate().request(r -> r.header(...)).build()
  • Нельзя
  • Через HttpServletRequestWrapper
Заголовки запроса только для чтения; mutate создаёт декоратор.
Как залогировать тело запроса в WebFilter?

Тело — Flux<DataBuffer>, который можно прочитать один раз. Нужно декорировать запрос: ServerHttpRequestDecorator с переопределённым getBody(), который через doOnNext копирует байты в лог (с лимитом размера!) и пропускает буферы дальше. Альтернатива — DataBufferUtils.join(body) и подмена тела закэшированным буфером, но это буферизация всего тела в памяти. Не логируйте тела с персональными данными и не забывайте освобождать буферы.
