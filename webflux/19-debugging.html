Отладка реактивного кода

Стектрейс реактивного исключения показывает внутренности Reactor и Netty, но не то, где в вашем коде собрана упавшая цепочка: сборка и выполнение разнесены во времени и по потокам. Разбираем, как вернуть полезный контекст — checkpoint, Hooks.onOperatorDebug, ReactorDebugAgent, — а также log(), метрики операторов и наблюдаемость через Micrometer.

19.1Почему стектрейс бесполезен

Метод orderService.total(id) собрал цепочку и вернул её. Через 40 мс ответ БД пришёл в поток reactor-tcp-nio-2, и в map случился NPE. В стеке этого момента — только драйвер, Netty и операторы Reactor: вашего метода в стеке нет, он давно завершился.

19.3log() и сигналы

userRepo.findAll()
    .log("users", Level.FINE, SignalType.ON_NEXT, SignalType.REQUEST, SignalType.CANCEL)
    .take(2)
    .subscribe();
[reactor-tcp-nio-1] users : request(2)          ← take(2) с 3.5 ограничивает спрос
[reactor-tcp-nio-1] users : onNext(User[id=1])
[reactor-tcp-nio-1] users : onNext(User[id=2])
[reactor-tcp-nio-1] users : cancel()            ← take отменил источник

log() — лучший способ увидеть противодавление, отмены и потоки. Ставьте его в несколько мест цепочки с разными категориями, чтобы понять, где «застревают» сигналы. Зависание без ошибки почти всегда означает: никто не подписался, спрос равен нулю или источник не завершается (пустой Sinks, забытый complete).

19.4Метрики и наблюдаемость

Flux<Order> orders = repo.findRecent()
    .name("orders.recent")                                     // имя последовательности
    .tag("source", "r2dbc")
    .tap(Micrometer.metrics(meterRegistry));                   // reactor-core-micrometer:
                                                               // orders.recent.subscribed, .requested, .flow.duration…

Mono<Price> price = client.get().uri("/p/{id}", id).retrieve().bodyToMono(Price.class)
    .name("pricing.get")
    .tap(Micrometer.observation(observationRegistry));         // span + timer через Observation API

Что смотреть в проде

  • http.server.requests — латентность и ошибки WebFlux (Observation)
  • reactor.netty.connection.provider.* — пул WebClient: active, idle, pending
  • reactor.netty.eventloop.pending.tasks — очередь задач event loop
  • executor.* для boundedElastic: Schedulers.enableMetrics() (устарело) → Micrometer.timedScheduler
  • r2dbc.pool.* — acquired, pending

Дампы потоков

  • Реактивное приложение в дампе: 8 reactor-http-nio в RUNNABLE (epoll_wait) — это норма.
  • Тревога: поток event loop в socketRead, LockSupport.park, Thread.sleep — кто-то блокирует.
  • Много boundedElastic в WAITING на JDBC — исчерпан пул БД.
  • Ищите по дампу BlockingSingleSubscriber.blockingGet — следы block().

19.5Самопроверка

Какой способ отладки подходит для продакшена и показывает все места сборки?

  • Hooks.onOperatorDebug()
  • log() на каждом операторе
  • ReactorDebugAgent
  • Отладчик IDE
Агент инструментирует байткод при загрузке, без захвата стеков в рантайме.

Почему в стектрейсе реактивной ошибки нет вашего сервисного метода?

  • Метод только собрал цепочку и завершился до того, как ошибка произошла в другом потоке
  • Reactor обрезает стек
  • JIT инлайнит методы
  • Из-за Netty
Сборка и выполнение разделены во времени.

Запрос «висит» без ошибок. Что проверить первым?

  • Увеличить таймаут
  • Перезапустить сервис
  • Включить onOperatorDebug
  • log() в цепочке: есть ли подписка, request и терминальный сигнал
Зависание — это отсутствие сигнала: подписки, спроса или завершения.
Как отлаживать реактивный код в IDE с точками останова?

Точки останова внутри лямбд операторов работают — вы окажетесь в потоке, где выполняется сигнал. IntelliJ IDEA показывает «async stack traces» для Reactor (Reactor Debug mode в настройках отладчика), склеивая стек выполнения со стеком сборки. Помните: остановка в event loop останавливает обработку всех соединений этого потока, а таймауты продолжают тикать.
