Операторы: map, flatMap, concatMap, switchMap

Самый частый вопрос на собеседовании по Reactor — «чем flatMap отличается от map и concatMap». Ответ определяет порядок результатов, параллельность вызовов и нагрузку на внешние сервисы. Разбираем трансформирующие операторы на живых marble-диаграммах, а также filter, take, distinct, side-effect-операторы doOn* и их ловушки.

4.1map против flatMap

map(T → R) — синхронное преобразование одного элемента в один. flatMap(T → Publisher<R>) — асинхронное: каждый элемент превращается во внутренний издатель (обычно вызов WebClient или репозитория), flatMap подписывается на них и сливает результаты в один поток.

Flux<Mono<Order>> wrong = ids.map(id -> orderClient.get(id));      // Flux<Mono>: запросы НЕ выполнятся
Flux<Order>       right = ids.flatMap(id -> orderClient.get(id));  // подписка на каждый внутренний Mono

flatMap по умолчанию — 256 одновременных запросов Flux.fromIterable(10_000 ids).flatMap(client::get) откроет до 256 параллельных HTTP-запросов и упрётся в пул соединений Reactor Netty (глобальный пул WebClient по умолчанию — 500 соединений на адрес, очередь ожидания 1000: при её переполнении — PoolAcquirePendingLimitException, после 45 с ожидания — PoolAcquireTimeoutException), а внешний сервис может это не пережить. Всегда задавайте concurrency явно.

4.4Фильтрация и выборка

Выборка

  • filter, filterWhen (асинхронный предикат)
  • take(n) — отменяет источник после n; take(Duration); takeWhile, takeUntil
  • skip, skipWhile, skipUntil
  • next() — Flux → Mono первого; last(), elementAt
  • distinct() — держит HashSet всех ключей (память!); distinctUntilChanged() — только соседние

Агрегация

  • collectList, collectMap, collectMultimap — Flux → Mono коллекции (держит всё в памяти)
  • reduce, scan (scan отдаёт промежуточные)
  • count, hasElements, any, all
  • then() — дождаться завершения, игнорируя элементы; thenReturn(v), then(mono)
  • defaultIfEmpty, switchIfEmpty
repo.findById(id)
    .switchIfEmpty(createDefault(id));   // createDefault() вызовется ВСЕГДА при сборке —
                                         // если он сам что-то делает до subscribe, побочный эффект случится
repo.findById(id)
    .switchIfEmpty(Mono.defer(() -> createDefault(id)));   // вызов только при пустом результате

4.5doOn* и побочные эффекты

ХукКогда вызывается
doOnSubscribeпри onSubscribe
doOnRequestпри request(n) — удобно отлаживать противодавление
doOnNextкаждый элемент
doOnError, doOnCompleteтерминальные сигналы
doOnCancelотмена подписчиком (клиент разорвал соединение, take, timeout)
doOnTerminate / doAfterTerminateдо / после complete или error (не cancel)
doFinally(SignalType)после любого завершения, включая cancel — место для освобождения ресурсов и метрик
log()печатает все сигналы, включая request — первый инструмент отладки
Асинхронная работа в doOnNext не выполнится .doOnNext(o -> auditClient.send(o)), где send возвращает Mono, — запрос никогда не уйдёт: на возвращённый Mono никто не подписался. Используйте flatMap(o -> auditClient.send(o).thenReturn(o)) или delayUntil(o -> auditClient.send(o)).

4.6Самопроверка

Нужно сохранить 1000 записей в порядке поступления, каждая запись — асинхронный insert. Что выбрать?

  • flatMap
  • map
  • concatMap
  • switchMap
Только concatMap выполняет вызовы по одному в исходном порядке.

Поле поиска: на каждое нажатие клавиши — запрос подсказок. Что выбрать?

  • concatMap
  • switchMap
  • flatMap
  • flatMapSequential
Устаревший запрос отменяется, ответы на старые префиксы не перезапишут новые.

Чем опасен flatMap(client::call) на Flux из 10 000 элементов?

  • До 256 одновременных вызовов — перегрузка сервиса и пула соединений
  • Вызовы пойдут последовательно
  • Порядок гарантирован, но медленно
  • Ничем
Задайте concurrency вторым аргументом.

Почему .doOnNext(x -> kafka.send(x)) (send возвращает Mono) ничего не отправляет?

  • doOnNext вызывается только при ошибке
  • Нужен publishOn
  • Kafka не поддерживает Reactor
  • Возвращённый Mono не подписан — он просто выброшен
Асинхронный побочный эффект — через flatMap/delayUntil.
Как flatMap обеспечивает противодавление?

flatMap запрашивает у источника не больше concurrency элементов (по умолчанию 256), у каждого внутреннего — prefetch (32) и держит их в очереди, пока подписчик не запросит. Когда внутренний издатель завершается, flatMap запрашивает у источника следующий элемент. Поэтому concurrency — это одновременно и предел параллельности, и окно спроса к источнику.

Что произойдёт с запросом WebClient внутри switchMap, если пришёл новый элемент?

switchMap вызовет cancel() у текущей внутренней подписки, и отмена дойдёт до Reactor Netty: соединение будет закрыто, ответ проигнорирован. На сервере может остаться уже выполняемая работа — отмена не откатывает побочные эффекты на удалённой стороне.
