Комбинирование: zip, merge, concat, buffer, groupBy

Реальный эндпоинт редко делает один вызов: профиль собирается из трёх сервисов, события двух топиков сливаются в один стрим, записи пишутся в базу пачками. Разбираем операторы, объединяющие несколько издателей, и операторы, нарезающие один поток на группы и окна, — с поведением при ошибках и завершении.

5.1Параллельные вызовы: Mono.zip

Mono<Profile> profile(String id) {
    Mono<User>          user   = userClient.get(id);
    Mono<List<Order>>   orders = orderClient.recent(id).collectList();
    Mono<Loyalty>       points = loyaltyClient.get(id)
                                   .onErrorReturn(Loyalty.UNKNOWN);   // некритичный — не валит весь ответ
    return Mono.zip(user, orders, points)                             // подписка на все три сразу
               .map(t -> new Profile(t.getT1(), t.getT2(), t.getT3()));
}   // время ответа = max(задержек), а не сумма
Пустой Mono обнуляет zip Если любой из Mono в zip завершится пусто, результат тоже пустой, а остальные отменяются. Для необязательных частей — defaultIfEmpty или map(Optional::of).defaultIfEmpty(Optional.empty()). Mono.when(...) ждёт завершения без значений, zipWhen — вызов, зависящий от результата первого.

Источник 1…7 с неравномерными паузами
events.bufferTimeout(500, Duration.ofSeconds(1))     // до 500 штук или раз в секунду

window(…) делает то же, что buffer, но выдаёт не списки, а вложенные Flux — элементы не копятся в памяти, обработка идёт по мере поступления. Используйте, когда окно большое.

5.5Самопроверка

Три независимых вызова по 100, 200 и 300 мс объединены через Mono.zip. Время ответа?

  • 600 мс
  • ≈300 мс
  • 100 мс
  • Зависит от порядка аргументов
zip подписывается на все сразу.

Один из Mono в zip завершился пусто. Результат?

  • Кортеж с null
  • Ошибка NoSuchElementException
  • zip ждёт таймаута
  • Пустой Mono, остальные источники отменяются
Пустой источник — нет полного кортежа.

Чем concat(A, B) отличается от merge(A, B) для холодных источников?

  • concat подписывается на B только после завершения A
  • Ничем
  • merge сохраняет порядок источников
  • concat параллелен
Поэтому concat даёт строгий порядок, а merge — минимальную задержку.

Пачки по 100 записей для вставки в БД, но не реже раза в 2 секунды. Оператор?

  • buffer(100)
  • window(Duration)
  • bufferTimeout(100, Duration.ofSeconds(2))
  • groupBy
Ограничены и размер, и максимальная задержка.
Как вызвать сервис B, которому нужен результат сервиса A, и вернуть оба результата?

a.zipWhen(ra -> serviceB.call(ra.id())) вернёт Tuple2<A, B>, или a.flatMap(ra -> serviceB.call(ra.id()).map(rb -> new Result(ra, rb))). Это последовательные вызовы — время ответа складывается.

Почему groupBy может зависнуть?

groupBy не может выдать элемент новой группы, пока подписчик не запросит новую GroupedFlux, а элементы существующей группы, пока на неё не подписались, копятся в очереди с ограниченным prefetch. Если число одновременно открытых групп превышает concurrency flatMap (по умолчанию 256), а группы не завершаются (бесконечный источник), спрос заканчивается — поток встаёт. Решения: ограничить число ключей, увеличить concurrency, завершать группы через take/timeout.
