R2DBC и реактивный доступ к данным

JDBC блокирует поток на каждом запросе — с ним реактивный стек теряет смысл. R2DBC — неблокирующий драйверный SPI для реляционных БД (PostgreSQL, MySQL/MariaDB, SQL Server, Oracle, H2). Spring Data R2DBC даёт репозитории и R2dbcEntityTemplate, но это не JPA: нет ленивой загрузки, связей, кэша первого уровня. Разбираем модель, транзакции, пул соединений и типичные ловушки.

16.1Сущности и репозитории

@Table("orders")
record Order(@Id Long id, long customerId, String status,
             BigDecimal total, @Version Long version, @CreatedDate Instant createdAt) {}

interface OrderRepository extends ReactiveCrudRepository<Order, Long> {
    Flux<Order> findByCustomerIdOrderByCreatedAtDesc(long customerId, Pageable page);

    @Query("UPDATE orders SET status = :status WHERE id = :id AND status = 'NEW'")
    @Modifying
    Mono<Integer> markPaid(long id, String status);
}
Flux<OrderWithLines> withLines = db.sql("""
        SELECT o.id, o.status, l.sku, l.qty
        FROM orders o JOIN order_lines l ON l.order_id = o.id
        WHERE o.customer_id = :cid ORDER BY o.id""")
    .bind("cid", customerId)
    .map((row, meta) -> new Row(row.get("id", Long.class), row.get("status", String.class),
                                row.get("sku", String.class), row.get("qty", Integer.class)))
    .all()
    .bufferUntilChanged(Row::orderId)                 // группировка строк соседних заказов
    .map(OrderWithLines::from);
N+1 возвращается Связей нет, и соблазн написать orders.flatMap(o -> lineRepo.findByOrderId(o.id())) велик: это N+1 запросов, только параллельных (до 256 одновременно — и пул в 10 соединений встанет). Используйте JOIN, WHERE order_id IN (:ids) пачками или ограничивайте concurrency.

16.2Транзакции

Реактивная транзакция привязана не к потоку, а к подписке: R2dbcTransactionManager (ReactiveTransactionManager) хранит соединение в Reactor Context. Поэтому транзакция охватывает только то, что выполняется внутри возвращённого издателя.

Перевод: списать со счёта A, зачислить на B (зачисление может упасть)
@Transactional
public Mono<Void> transfer(String from, String to, BigDecimal amount) {
    return accounts.debit(from, amount)
        .filter(updated -> updated == 1)
        .switchIfEmpty(Mono.error(new InsufficientFunds(from)))
        .then(accounts.credit(to, amount))
        .then(outbox.save(new TransferDone(from, to, amount)))   // outbox в той же транзакции
        .then();
}

      initial-size: 10
      max-size: 20          # по умолчанию 10
      max-idle-time: 30m
      max-acquire-time: 3s  # fail fast
      validation-query: SELECT 1

Сколько соединений нужно

Неблокирующий драйвер не освобождает от закона Литтла: соединение занято, пока БД выполняет запрос. 20 соединений × 5 мс на запрос = 4000 запросов/с максимум. Узкое место — сама база, а не потоки приложения. Выигрыш R2DBC — в том, что ожидание соединения не держит поток.

Стриминг результатов repo.findAll() возвращает Flux, и драйвер PostgreSQL выдаёт строки с учётом противодавления (fetchSize/курсор в транзакции). Но collectList() снова собирает всё в память, а удерживаемое соединение блокирует пул на всё время стрима. Для больших выгрузок — стрим с NDJSON-ответом и ограничением времени.

16.5Самопроверка

Где хранится транзакционное соединение в реактивной транзакции?

  • В ThreadLocal
  • В Reactor Context подписки
  • В статическом поле
  • В HTTP-сессии
Поэтому отдельная подписка (subscribe()) выпадает из транзакции.

Поддерживает ли Spring Data R2DBC ленивую загрузку связей @OneToMany?

  • Да, как JPA
  • Да, через Mono
  • Только с Hibernate Reactive
  • Нет: связей и ленивой загрузки нет, агрегаты собираются вручную
Spring Data R2DBC — простой маппер без ORM-сессии.

Пул R2DBC — 10 соединений. Код: orders.flatMap(o -> lines.findByOrderId(o.id())) для 1000 заказов. Что будет?

  • До 256 одновременных запросов в очереди к 10 соединениям; возможны таймауты получения соединения
  • 1 запрос
  • Ошибка компиляции
  • Последовательные запросы
Ограничьте concurrency или используйте JOIN/IN.
Чем Hibernate Reactive отличается от Spring Data R2DBC?

Hibernate Reactive — полноценный ORM (сущности JPA, связи, ленивая загрузка через явный fetch, сессия, кэш) поверх неблокирующих драйверов Vert.x SQL client, с API на Mutiny или CompletionStage. Spring Data R2DBC — лёгкий маппер на R2DBC SPI с репозиториями Spring Data. Spring не интегрирует Hibernate Reactive в свою транзакционную модель так же глубоко, поэтому в Spring-приложениях чаще выбирают R2DBC, а в Quarkus — Hibernate Reactive.
