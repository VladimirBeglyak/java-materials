WebFlux или MVC на виртуальных потоках

С Java 21 и Spring Boot 3.2 (spring.threads.virtual.enabled=true) обычный блокирующий MVC-код масштабируется по числу одновременных запросов почти как реактивный: виртуальный поток при блокировке на I/O отпускает поток-носитель. Значит ли это, что WebFlux больше не нужен? Сравниваем модели по существу, смотрим один и тот же сценарий в двух стилях и выбираем осознанно.

21.1Как виртуальные потоки решают ту же задачу

WebFlux

Код явно асинхронный: вместо ожидания вы возвращаете Mono, а продолжение регистрируется как колбэк. Мало потоков, потому что никто не ждёт. Цена — другой стиль программирования, «окрашенные» функции (Mono везде), сложные стектрейсы.

Виртуальные потоки

Код блокирующий и последовательный, но блокировка дешёвая: JVM снимает стек виртуального потока с потока-носителя (ForkJoinPool, по числу ядер) и возвращает его, когда I/O готов. По сути, JVM делает «реактивное» преобразование за вас.

21.2Один сценарий — два стиля

Профиль пользователя: параллельно вызвать два сервиса с таймаутом 2 с, некритичный — с запасным значением.

Mono<Profile> profile(String id) {
    Mono<User> user = userClient.get(id).timeout(Duration.ofSeconds(2));
    Mono<Loyalty> loyalty = loyaltyClient.get(id).timeout(Duration.ofSeconds(2))
                                          .onErrorReturn(Loyalty.UNKNOWN);
    return Mono.zip(user, loyalty, Profile::new);
}
Profile profile(String id) throws Exception {
    try (var scope = StructuredTaskScope.open(                          // в JDK 21–24 был конструктор
            Joiner.awaitAllSuccessfulOrThrow(),                         // и ShutdownOnFailure/joinUntil
            cfg -> cfg.withTimeout(Duration.ofSeconds(2)))) {
        var user    = scope.fork(() -> userClient.get(id));            // RestClient, блокирует — дёшево
        var loyalty = scope.fork(() -> {
            try { return loyaltyClient.get(id); } catch (Exception e) { return Loyalty.UNKNOWN; }
        });
        scope.join();                                                   // ошибка или таймаут → исключение
        return new Profile(user.get(), loyalty.get());
    }
}
// без preview-API: CompletableFuture.supplyAsync(..., virtualExecutor) + orTimeout

Подводные камни виртуальных потоков Pinning: до JDK 24 блокировка внутри synchronized «прибивала» виртуальный поток к носителю (JEP 491 в JDK 24 это исправил); нативные вызовы прибивают всегда. ThreadLocal-кэши на поток (пулы буферов) теряют смысл при миллионах потоков. Перегрузка зависимостей: 10 000 виртуальных потоков радостно ринутся в пул БД из 20 соединений — нужен явный лимит параллельности.

21.5Миграция в обе стороны

  • MVC → виртуальные потоки: Boot 3.2+, spring.threads.virtual.enabled=true — Tomcat, @Async, планировщики, Kafka-листенеры переходят на виртуальные потоки. Проверить: synchronized вокруг I/O (до JDK 24), размеры пулов соединений, нагрузку на БД.
  • WebFlux в MVC частично: контроллер MVC может возвращать Mono/Flux — Spring MVC подпишется и обработает асинхронно (поток Servlet освобождается), а SSE через Flux работает и в MVC.
  • MVC → WebFlux: оправдано, только если стек целиком неблокирующий; переписывание сервисного слоя на Mono/Flux — главная стоимость.

21.6Самопроверка

Что происходит с виртуальным потоком, когда он блокируется на чтении сокета?

  • Блокируется поток-носитель
  • Выбрасывается исключение
  • Он снимается с носителя, носитель выполняет другие виртуальные потоки
  • JVM создаёт новый платформенный поток
Так блокирующий код получает масштабируемость асинхронного.

Какой сценарий остаётся сильной стороной WebFlux даже при наличии виртуальных потоков?

  • Стриминг со сквозным противодавлением и богатая композиция асинхронных операций
  • CRUD поверх JPA
  • Простые REST-эндпоинты
  • Пакетная обработка файлов
Loom решает проблему стоимости потоков, а не потоков данных.

Почему с виртуальными потоками нужно явно ограничивать параллельность обращений к БД?

  • Виртуальные потоки медленнее
  • JDBC не поддерживает виртуальные потоки
  • Из-за pinning
  • Число потоков больше не ограничивает нагрузку, а пул соединений остаётся конечным
Раньше пул Tomcat (200) неявно ограничивал давление на БД.
Что ответить на собеседовании на вопрос «WebFlux устарел из-за Loom?»

Нет, но его ниша сузилась. Loom снимает главный аргумент «реактивность нужна, чтобы не держать поток на ожидание»: для типичного CRUD-сервиса MVC на виртуальных потоках проще и масштабируется сопоставимо. WebFlux остаётся оправданным для стриминга с противодавлением, шлюзов (Spring Cloud Gateway), сложной асинхронной композиции, полностью неблокирующего стека и там, где он уже есть. Выбор — по характеру нагрузки, зависимостям и компетенциям команды, подкреплённый нагрузочным тестом.
