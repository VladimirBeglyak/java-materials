Планировщики: publishOn и subscribeOn

Reactor не создаёт потоков сам: без планировщиков весь конвейер выполняется в потоке, вызвавшем subscribe(), или в потоке, где источник выдал данные. publishOn переключает поток для операторов ниже, subscribeOn — поток, в котором происходит подписка (а значит, и работа синхронного источника), где бы он ни стоял. Разбираем правила на конструкторе конвейера и выясняем, какой пул для чего.

7.3Правила

publishOn(s)

  • Влияет на операторы ниже по цепочке.
  • Можно ставить несколько раз — каждый переключает снова.
  • Внутри очередь (prefetch 256) и задача-воркер на планировщике: сигналы по-прежнему последовательны.
  • Применение: увести тяжёлую обработку ответа с event loop.

subscribeOn(s)

  • Влияет на подписку и запросы спроса вверх — значит, на поток синхронного источника.
  • Положение в цепочке почти не важно; из нескольких действует ближайший к источнику.
  • Не меняет поток уже асинхронного источника.
  • Применение: Mono.fromCallable(blocking).subscribeOn(boundedElastic()).
@GetMapping("/report/{id}")
Mono<Report> report(@PathVariable long id) {
    return Mono.fromCallable(() -> legacyJdbcDao.load(id))   // блокирует
               .subscribeOn(Schedulers.boundedElastic())     // ...но не event loop
               .map(this::enrich);                           // продолжится в boundedElastic-N
}

7.4Параллелизм: flatMap и ParallelFlux

Ни publishOn, ни subscribeOn не делают обработку параллельной — элементы идут по одному. Параллельность даёт flatMap с внутренними издателями на планировщике или ParallelFlux:

// 1. flatMap: каждый элемент — свой Mono на parallel()
Flux.fromIterable(images)
    .flatMap(img -> Mono.fromCallable(() -> resize(img))
                        .subscribeOn(Schedulers.parallel()), 8)
    .collectList();

// 2. ParallelFlux: рельсы по числу ядер
Flux.fromIterable(images)
    .parallel()                     // N рельсов (по умолчанию = ядрам)
    .runOn(Schedulers.parallel())   // каждый рельс — на своём потоке
    .map(this::resize)
    .sequential()                   // обратно в один Flux (порядок не сохраняется)
    .collectList();
Где продолжается цепочка после flatMap Элементы результата flatMap приходят в тех потоках, где их выдали внутренние издатели. После flatMap(id -> webClient...) дальнейшие операторы работают в reactor-http-nio-*, после flatMap с subscribeOn(boundedElastic) — в boundedElastic-*. Это нормально: сигналы всё равно сериализуются.

Почему boundedElastic ограничен 10 × ядер и что будет при исчерпании?

Раньше был неограниченный elastic(): при массовой блокировке создавались тысячи потоков, и сервис падал от нехватки памяти. boundedElastic ограничивает число потоков (по умолчанию 10 × ядер, настраивается reactor.schedulers.defaultBoundedElasticSize) и ставит лишние задачи в очередь (до 100 000 на поток, defaultBoundedElasticQueueSize). При переполнении очереди — RejectedExecutionException. Это сигнал, что блокирующих операций слишком много для реактивного приложения.

Почему в WebFlux-сервисе после WebClient-вызова код выполняется в reactor-http-nio, хотя запрос пришёл в другой поток?

По умолчанию сервер Reactor Netty и WebClient используют общие LoopResources. Ответ клиента обрабатывается в event loop, к которому привязано исходящее соединение, и именно там подписчик получает onNext. Все последующие операторы работают в этом потоке, пока не встретится publishOn.
