Reactor Context и пропагация контекста

В MVC идентификатор запроса, пользователь, trace id и MDC живут в ThreadLocal: один запрос — один поток. В реактивном конвейере запрос перескакивает между потоками, и ThreadLocal «теряется». Его замена — Reactor Context: неизменяемая карта, привязанная к подписке и путешествующая снизу вверх по цепочке. Разбираем правила видимости, Spring Security и автоматическую пропагацию в ThreadLocal для логов и трассировки.

9.1Почему не ThreadLocal

MDC.put("requestId", rid);                 // поток reactor-http-nio-2
return client.get().retrieve().bodyToMono(Price.class)
        .map(p -> { log.info("price {}", p);   // поток reactor-http-nio-7 — MDC пуст
                    return p; });
// к тому же nio-2 обслуживает другие запросы — в его MDC «чужой» requestId

9.2API

Mono<String> greet = Mono.deferContextual(ctx ->           // чтение: ContextView (только чтение)
        Mono.just("Hello, " + ctx.getOrDefault("user", "anonymous")));

greet.contextWrite(Context.of("user", "alice"))               // запись: новая неизменяемая карта
     .subscribe(System.out::println);                         // Hello, alice

// внутри операторов
flux.transformDeferredContextual((f, ctx) -> f.map(x -> x + ctx.get("tenant")));
flux.flatMap(x -> Mono.deferContextual(ctx -> repo.find(ctx.get("tenant"), x)));
flux.contextWrite(ctx -> ctx.put("attempt", ctx.getOrDefault("attempt", 0) + 1));

Context передаётся при подписке: каждый подписчик (CoreSubscriber) отдаёт свой currentContext() вверх. contextWrite оборачивает подписчика, дополняя контекст, поэтому видят запись только операторы выше него.

Цепочка сверху вниз; подписка (и контекст) идут снизу вверх

9.4Context в WebFlux

@Component
class RequestContextFilter implements WebFilter {
    public Mono<Void> filter(ServerWebExchange ex, WebFilterChain chain) {
        String rid = Optional.ofNullable(ex.getRequest().getHeaders().getFirst("X-Request-Id"))
                             .orElseGet(() -> UUID.randomUUID().toString());
        return chain.filter(ex)                                    // вся обработка запроса — выше
                    .contextWrite(Context.of("requestId", rid,
                                             "tenant", tenantOf(ex)));
    }
}

Spring Security хранит аутентификацию именно так: ReactorContextWebFilter кладёт Mono<SecurityContext> в Context, а ReactiveSecurityContextHolder.getContext() — это Mono.deferContextual. Поэтому в реактивном коде нет «SecurityContextHolder.getContext()» — только Mono (тема 17).

9.5Автоматическая пропагация в ThreadLocal

Библиотеки логирования и трассировки читают ThreadLocal (MDC, текущий span). Библиотека Micrometer context-propagation связывает два мира: зарегистрированные ThreadLocalAccessor восстанавливают ThreadLocal из Context перед каждым сигналом.

Включение

spring:
  reactor:
    context-propagation: auto   # Boot 3.2+: Hooks.enableAutomaticContextPropagation()
management:
  tracing:
    sampling.probability: 1.0   # доля трасс, отправляемых в бэкенд (по умолчанию 0.1)

Что происходит

  • Reactor ≥ 3.5.3 при каждом сигнале через границу потоков восстанавливает зарегистрированные ThreadLocal из Context и очищает после.
  • ObservationThreadLocalAccessor из micrometer-observation регистрируется автоматически (ServiceLoader), а Micrometer Tracing кладёт traceId/spanId текущего Observation в MDC.
  • Свой ThreadLocal: ContextRegistry.getInstance().registerThreadLocalAccessor("rid", RID::get, RID::set, RID::remove).
  • Ручной вариант: contextCapture() захватывает ThreadLocal в Context в точке перехода из императивного кода.
Цена Автоматическая пропагация добавляет работу на каждый сигнал. Не кладите в Context большие объекты и не используйте его как «глобальный кэш»: каждый put создаёт новую карту (оптимизированные Context1…Context5, дальше — ContextN).

Mono.deferContextual(c -> Mono.just(c.get("k"))).contextWrite(Context.of("k","1")).map(...).contextWrite(Context.of("k","2")) — что выдаст источник?

  • "2"
  • NoSuchElementException
  • "1"
  • "12"
Ближайший contextWrite ниже источника перекрывает дальний.

Почему contextWrite нужно ставить ближе к концу цепочки?

  • Контекст распространяется от подписчика вверх и виден только операторам выше
  • Так быстрее
  • Иначе Context потокоопасен
  • Это требование Netty
Операторы ниже записи её не видят.

Как получить аутентификацию в реактивном сервисе?

  • SecurityContextHolder.getContext()
  • ThreadLocal из фильтра
  • @Autowired Authentication
  • ReactiveSecurityContextHolder.getContext() — Mono, читающий Reactor Context

Почему Context неизменяемый?

Один и тот же конвейер может иметь много подписок одновременно, и каждая несёт свой контекст. Если бы Context был изменяемым, запись в одной подписке протекала бы в другие, а операторы, выполняющиеся в разных потоках, требовали бы синхронизации. Неизменяемость делает put «созданием новой версии» и сохраняет потокобезопасность без блокировок. Если нужно изменяемое состояние на запрос — кладите в Context изменяемый holder (AtomicReference), понимая последствия.
